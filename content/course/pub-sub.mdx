# Publish-Subscribe

A radio station sends one signal. It does not know who listens. Anyone with a radio can tune in, and a radio that is off simply misses the show. Publish-subscribe works in a similar way for software. This comparison is the tutorial's own.

<PageMeta />

## In plain words

<Voices>
<Technical>

In publish-subscribe (pub/sub) messaging, a sender publishes an event and does not need to know which consumers receive it <Cite n={1} />. A broker in the middle passes the event on.

Without a broker, a sender must know every consumer, deliver to each one, and handle each failure. A new consumer then means a change in the sender <Cite n={1} />. A plain queue links a sender to one consumer, so many consumers need many queues <Cite n={1} />.

The pattern has three parts <Cite n={1} />:

- An input channel, where the sender (the **publisher**) puts its messages.
- One output channel for each consumer (each **subscriber**).
- A mechanism, usually a message broker or event bus, that copies each message to the output channels of the interested subscribers.

In this pattern a message is a unit of data. An event is one kind of message. It reports a change or an action to other parts of the system <Cite n={1} />. Google Pub/Sub uses two more names. A **topic** is a named feed of messages. A **subscription** is a named entity that shows interest in the messages of one topic <Cite n={3} />.

</Technical>

## How it works

<Voices>
<Technical>

Google Pub/Sub shows the flow well. This is one product, but the steps explain the general idea <Cite n={3} />:

1. A publisher sends a message to a topic.
2. The message is written to storage.
3. Pub/Sub sends the message on to every subscription attached to the topic.
4. A subscription hands the message to a subscriber application.
5. The subscriber sends an acknowledgment (ack) after it processes the message.
6. When at least one subscriber of each subscription has acked, Pub/Sub deletes the message.

**Fan-out.** Each subscription gets its own copy of every message <Cite n={3} />. Subscribers inside one subscription share the work, and each gets a subset. A subscription with one subscriber sends that subscriber everything <Cite n={3} />. A subscription must exist before it can receive messages. It only gets messages that were published after it was created <Cite n={4} />.

**Choosing what you receive.** Subscribers usually need only some messages. A broker can use topics, where each topic has its own output channel. It can also use content filtering, where the broker looks inside the message <Cite n={1} />. Broad topics are simpler, but subscribers filter more <Cite n={1} />.

**Delivery style.** In Google Pub/Sub a subscription can be pull (the subscriber asks) or push (the server calls the subscriber) <Cite n={4} />.

</Technical>

<Bangla>

Google Pub/Sub প্রবাহটি ভালোভাবে দেখায়। এটি একটি নির্দিষ্ট প্রোডাক্ট, কিন্তু ধাপগুলো সাধারণ ধারণাটি বোঝায়। <Cite n={3} />

1. একটি পাবলিশার একটি টপিকে মেসেজ পাঠায়।
2. মেসেজটি স্টোরেজে লেখা হয়।
3. Pub/Sub মেসেজটি টপিকের প্রতিটি সাবস্ক্রিপশনে পাঠায়।
4. একটি সাবস্ক্রিপশন মেসেজটি একটি সাবস্ক্রাইবার অ্যাপ্লিকেশনকে দেয়।
5. মেসেজ প্রসেস করার পর সাবস্ক্রাইবার একটি অ্যাকনলেজমেন্ট (acknowledgment বা ack) পাঠায়।
6. প্রতিটি সাবস্ক্রিপশনের অন্তত একজন সাবস্ক্রাইবার অ্যাক পাঠালে Pub/Sub মেসেজটি মুছে ফেলে।

**ফ্যান-আউট (fan-out)।** প্রতিটি সাবস্ক্রিপশন প্রতিটি মেসেজের নিজস্ব কপি পায়। <Cite n={3} /> একই সাবস্ক্রিপশনের সাবস্ক্রাইবাররা কাজ ভাগ করে নেয়। প্রত্যেকে মেসেজের একটি অংশ পায়। যে সাবস্ক্রিপশনে একজন সাবস্ক্রাইবার, সে সবকিছু পায়। <Cite n={3} /> মেসেজ পাওয়ার আগে সাবস্ক্রিপশন থাকতে হয়। সাবস্ক্রিপশন তৈরির পরে পাবলিশ হওয়া মেসেজই শুধু সে পায়। <Cite n={4} />

**কী পাবেন তা বাছাই।** সাবস্ক্রাইবারদের সাধারণত কিছু মেসেজই লাগে। ব্রোকার টপিক ব্যবহার করতে পারে। প্রতিটি টপিকের নিজস্ব আউটপুট চ্যানেল থাকে। ব্রোকার কনটেন্ট ফিল্টারিংও (content filtering) ব্যবহার করতে পারে। তখন ব্রোকার মেসেজের ভেতরে দেখে। <Cite n={1} /> ব্যাপক টপিক সহজ, কিন্তু সাবস্ক্রাইবারদের বেশি ফিল্টার করতে হয়। <Cite n={1} />

**ডেলিভারির ধরন।** Google Pub/Sub-এ একটি সাবস্ক্রিপশন পুল (pull) বা পুশ (push) হতে পারে। পুলে সাবস্ক্রাইবার মেসেজ চায়। পুশে সার্ভার সাবস্ক্রাইবারকে কল করে। <Cite n={4} />

## Delivery, duplicates, and order

<Voices>
<Technical>

**At-least-once delivery.** Azure names three guarantees. At-most-once can lose messages. At-least-once delivers every message but can create duplicates. Exactly-once removes duplicates but adds coordination cost and delay <Cite n={1} />. Google Pub/Sub gives at-least-once delivery by default, and it also supports exactly-once delivery as an option <Cite n={4} />.

Duplicates can happen when the ack step goes wrong. For example, the ack may arrive after the deadline, or a network problem may lose it. Then the message may arrive again <Cite n={3} />. Google also says that Pub/Sub might redeliver a message after a successful ack, for example after a server restart. It calls this rare, but possible for any message <Cite n={4} />. So Google says the subscriber must be idempotent <Cite n={4} />. Idempotent means that handling a message twice causes no harm. This definition is the tutorial's own. Azure gives the same advice when the broker has no deduplication <Cite n={1} />.

**Ordering.** Azure says the order of receipt is not guaranteed and may differ from the order of creation <Cite n={1} />. Some brokers offer ordered delivery inside a partition or session, but this limits scalability <Cite n={1} />. Google Pub/Sub has no expected order by default <Cite n={4} />. To get order, you set the same ordering key on related messages, publish them in the same region, and turn on ordering in the subscription <Cite n={5} />. The order holds only inside one key. Messages with different keys can arrive in any order <Cite n={5} />. A redelivery of one message also triggers redelivery of the later messages for that key <Cite n={5} />.

</Technical>

**অ্যাট-লিস্ট-ওয়ান্স ডেলিভারি (at-least-once delivery)।** Azure তিনটি গ্যারান্টির নাম বলে। অ্যাট-মোস্ট-ওয়ান্সে (at-most-once) মেসেজ হারাতে পারে। অ্যাট-লিস্ট-ওয়ান্স প্রতিটি মেসেজ পৌঁছে দেয়, কিন্তু ডুপ্লিকেট হতে পারে। এক্স্যাক্টলি-ওয়ান্স (exactly-once) ডুপ্লিকেট সরায়, কিন্তু সমন্বয়ের খরচ ও দেরি যোগ করে। <Cite n={1} /> Google Pub/Sub ডিফল্টভাবে অ্যাট-লিস্ট-ওয়ান্স ডেলিভারি দেয়। এটি অপশন হিসেবে এক্স্যাক্টলি-ওয়ান্স ডেলিভারিও সমর্থন করে। <Cite n={4} />

অ্যাক ধাপে গোলমাল হলে ডুপ্লিকেট হতে পারে। যেমন অ্যাক ডেডলাইনের পরে পৌঁছাতে পারে, অথবা নেটওয়ার্ক সমস্যায় হারিয়ে যেতে পারে। তখন মেসেজ আবার আসতে পারে। <Cite n={3} /> Google আরও বলে, সফল অ্যাকের পরেও Pub/Sub একটি মেসেজ আবার পাঠাতে পারে, যেমন সার্ভার রিস্টার্টের পরে। Google একে বিরল বলে, কিন্তু যেকোনো মেসেজের জন্য সম্ভব বলে। <Cite n={4} /> তাই Google বলে সাবস্ক্রাইবারকে আইডেমপোটেন্ট (idempotent) হতে হবে। <Cite n={4} /> আইডেমপোটেন্ট মানে একটি মেসেজ দুইবার হ্যান্ডেল করলে কোনো ক্ষতি হয় না। এই সংজ্ঞাটি টিউটোরিয়ালের নিজের। ব্রোকারে ডিডুপ্লিকেশন (deduplication) না থাকলে Azure একই পরামর্শ দেয়। <Cite n={1} />

**অর্ডারিং (ordering)।** Azure বলে, পাওয়ার ক্রমের কোনো গ্যারান্টি নেই। এটি তৈরির ক্রম থেকে আলাদা হতে পারে। <Cite n={1} /> কিছু ব্রোকার একটি পার্টিশন বা সেশনের ভেতরে ক্রম মেনে ডেলিভারি দেয়, কিন্তু এতে স্কেলেবিলিটি কমে। <Cite n={1} /> Google Pub/Sub-এ ডিফল্টভাবে কোনো প্রত্যাশিত ক্রম নেই। <Cite n={4} /> ক্রম পেতে তিনটি কাজ করতে হয়। সম্পর্কিত মেসেজে একই অর্ডারিং কী (ordering key) দিতে হয়। সেগুলো একই রিজিয়নে পাবলিশ করতে হয়। সাবস্ক্রিপশনে অর্ডারিং চালু করতে হয়। <Cite n={5} /> ক্রম শুধু একটি কী-র ভেতরে থাকে। আলাদা কী-র মেসেজ যেকোনো ক্রমে আসতে পারে। <Cite n={5} /> একটি মেসেজ আবার পাঠানো হলে ওই কী-র পরের মেসেজগুলোও আবার পাঠানো হয়। <Cite n={5} />

</Bangla>
</Voices>

## When not to use it

<Voices>
<Technical>

Azure says pub/sub may be a poor fit in these cases <Cite n={1} />:

- There are only a few consumers that need very different data. The broker adds complexity with no scaling benefit.
- You need near real-time interaction. The broker adds latency, so request-reply may fit better.
- Consumers must process messages in a strict, guaranteed order.
- One atomic transaction must cover the publisher and its consumers. Pub/Sub is asynchronous and eventually consistent.

Google adds that its Pub/Sub is for service-to-service communication, not for end-user or IoT clients <Cite n={2} />.

</Technical>
<Layman>

Azure says pub/sub may be a poor fit in these cases: <Cite n={1} />

- There are only a few consumers, and they need very different data. The broker adds complexity with no scaling benefit.
- You need near real-time interaction. The broker adds latency, so request-reply may fit better.
- Consumers must process messages in a strict, guaranteed order.
- One atomic transaction must cover the publisher and its consumers. Pub/Sub is asynchronous and eventually consistent.

Google adds that its Pub/Sub is for service-to-service communication. It is not for end-user or IoT clients. <Cite n={2} />

</Layman>
<Bangla>

Azure বলে, এই ক্ষেত্রগুলোতে pub/sub ভালো না-ও মানাতে পারে: <Cite n={1} />

- কনজিউমার মাত্র কয়েকজন, এবং তাদের একদম আলাদা ডেটা লাগে। ব্রোকার জটিলতা বাড়ায়, কিন্তু স্কেলিংয়ে কোনো সুবিধা দেয় না।
- প্রায় রিয়েল-টাইম ইন্টারঅ্যাকশন দরকার। ব্রোকার ল্যাটেন্সি যোগ করে, তাই রিকুয়েস্ট-রিপ্লাই (request-reply) বেশি মানাতে পারে।
- কনজিউমারদের কঠোর, নিশ্চিত ক্রমে মেসেজ প্রসেস করতে হয়।
- পাবলিশার ও তার কনজিউমারদের সবাইকে একটি অ্যাটমিক ট্রানজেকশনের আওতায় থাকতে হয়। Pub/Sub অ্যাসিনক্রোনাস এবং ইভেন্চুয়ালি কনসিসটেন্ট।

Google আরও বলে, তাদের Pub/Sub সার্ভিস-টু-সার্ভিস যোগাযোগের জন্য। এটি এন্ড-ইউজার বা IoT ক্লায়েন্টের জন্য নয়। <Cite n={2} />

</Bangla>
</Voices>

## A real-life example

<Voices>
<Technical>

This example is the tutorial's own. An exam platform publishes an event "answer submitted" to a topic. Three subscriptions listen: grading, a confirmation email, and analytics. Each subscription gets its own copy. If the email service is down, grading still works. The analytics team can add a fourth subscription later without a change in the publisher.

After a lost ack, the email subscriber gets the same event twice. It must not send two emails.

</Technical>

এই উদাহরণটি টিউটোরিয়ালের নিজের। একটি পরীক্ষার প্ল্যাটফর্ম একটি টপিকে "answer submitted" ইভেন্ট পাবলিশ করে। তিনটি সাবস্ক্রিপশন শোনে: গ্রেডিং, একটি কনফার্মেশন ইমেইল এবং অ্যানালিটিক্স। প্রতিটি সাবস্ক্রিপশন নিজস্ব কপি পায়। ইমেইল সার্ভিস বন্ধ থাকলেও গ্রেডিং কাজ করে। অ্যানালিটিক্স টিম পরে চতুর্থ একটি সাবস্ক্রিপশন যোগ করতে পারে। পাবলিশারকে বদলাতে হয় না।

অ্যাক হারিয়ে গেলে ইমেইল সাবস্ক্রাইবার একই ইভেন্ট দুইবার পায়। তাকে দুটি ইমেইল পাঠালে চলবে না।

## Common mistakes

<Voices>
<Technical>

- **Expecting order.** Without a special setting, messages can arrive in a different order than the sender created them <Cite n={1} /> <Cite n={4} />.
- **Expecting exactly one delivery.** Google Cloud Pub/Sub gives at-least-once delivery by default, so duplicates can happen <Cite n={4} />.
- **Expecting a reply.** The channels are one way <Cite n={1} />.
- **Creating the subscription too late.** In Google Cloud Pub/Sub, a new subscription gets only messages published after it was created <Cite n={4} />. With topic retention on, a subscription can seek back in time and replay earlier messages <Cite n={4} />.

</Technical>
<Layman>

- **Expecting order.** Without a special setting, messages can arrive in a different order than the sender created them. <Cite n={1} /> <Cite n={4} />
- **Expecting exactly one delivery.** Google Cloud Pub/Sub gives at-least-once delivery by default. So duplicates can happen. <Cite n={4} />
- **Expecting a reply.** The channels are one way. <Cite n={1} />
- **Creating the subscription too late.** In Google Cloud Pub/Sub, a new subscription gets only messages that were published after it was created. <Cite n={4} /> With topic retention on, a subscription can seek back in time and replay earlier messages. <Cite n={4} />

</Layman>
<Bangla>

- **ক্রম আশা করা।** বিশেষ সেটিং ছাড়া মেসেজ সেন্ডারের তৈরির ক্রম থেকে আলাদা ক্রমে আসতে পারে। <Cite n={1} /> <Cite n={4} />
- **ঠিক একবার ডেলিভারি আশা করা।** Google Cloud Pub/Sub ডিফল্টভাবে অ্যাট-লিস্ট-ওয়ান্স ডেলিভারি দেয়। তাই ডুপ্লিকেট হতে পারে। <Cite n={4} />
- **রিপ্লাই আশা করা।** চ্যানেলগুলো একমুখী। <Cite n={1} />
- **সাবস্ক্রিপশন খুব দেরিতে তৈরি করা।** Google Cloud Pub/Sub-এ নতুন সাবস্ক্রিপশন শুধু তৈরির পরে পাবলিশ হওয়া মেসেজ পায়। <Cite n={4} /> টপিক রিটেনশন (topic retention) চালু থাকলে একটি সাবস্ক্রিপশন সময়ে পিছিয়ে গিয়ে আগের মেসেজ রিপ্লে করতে পারে। <Cite n={4} />

</Bangla>
</Voices>

## What a tester can check

- **Send the same event twice.** Check that the subscriber gives the same end result as for one event.
- **Change the order.** Send "updated" before "created". Check that the subscriber copes, or that the design keeps order.
- **Stop one subscriber.** Check that the others keep working. Start it again and check that it catches up.
- **Add a bad message.** Send a malformed event. Check that it does not block the others.

## Key words

| Word | Meaning |
|---|---|
| Publisher | The sender. It publishes events and does not know the consumers <Cite n={1} /> |
| Subscriber | A consumer that receives messages through its own output channel <Cite n={1} /> |
| Broker | The intermediary that copies each message to interested subscribers <Cite n={1} /> |
| Topic | In Google Pub/Sub, a named feed of messages <Cite n={3} /> |
| Subscription | In Google Pub/Sub, a named entity that shows interest in one topic <Cite n={3} /> |
| Acknowledgment (ack) | The subscriber tells Pub/Sub that it processed a message <Cite n={3} /> |
| At-least-once delivery | Every message arrives, but some may arrive more than once <Cite n={1} /> |
| Idempotent | The tutorial's own definition: handling a message again causes no extra effect |
| Ordering key | In Google Pub/Sub, a string that groups messages that must stay in order <Cite n={5} /> |
