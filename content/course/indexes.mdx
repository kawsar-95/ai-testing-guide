# Indexes

At the back of a textbook, an alphabetical list tells you which page to open for a topic. A database index does the same job for a table: it helps the database go straight to the rows you want.

<PageMeta />

## In plain words

<Voices>
<Technical>

An **index** is an extra structure that a database keeps next to a table, so that it can find rows by the value of a column. Without it, the database has to read the table row by row <Cite n={1} />. MySQL says the same: it starts at the first row and reads the whole table, and a bigger table means more work <Cite n={5} />. With an index, the database can find the right place in the data without looking at all of it <Cite n={5} />.

The PostgreSQL manual uses the same book comparison, and says that the database programmer must foresee which indexes will be useful <Cite n={1} />.

You create an index with a command such as the one below. You can add or remove an index at any time <Cite n={1} />.

```sql
CREATE INDEX orders_customer_idx ON orders (customer_id);
```

</Technical>
<Layman>

An index is an extra structure that a database keeps next to a table. The database uses it to find rows by the value of a column. </Layman>

PostgreSQL ম্যানুয়াল একই বইয়ের তুলনা ব্যবহার করে। সেখানে বলা হয়েছে, কোন ইনডেক্স কাজে লাগবে তা ডেটাবেস প্রোগ্রামারকে আগে থেকে ভেবে নিতে হবে <Cite n={1} />।

আপনি `CREATE INDEX orders_customer_idx ON orders (customer_id);` এর মতো একটি কমান্ড দিয়ে ইনডেক্স তৈরি করেন। যেকোনো সময় ইনডেক্স যোগ করা বা মুছে ফেলা যায় <Cite n={1} />।

## When you need it

<Voices>
<Technical>

You need an index when many queries look for a few rows in a big table, for example "all orders of one customer". An index can also help `UPDATE` and `DELETE` commands that have a search condition, and joins <Cite n={1} />.

Indexes matter less for small tables, and for reports that read most rows of a big table: reading in order is faster there <Cite n={5} />.

</Technical>
<Layman>

You need an index when many queries look for a few rows in a big table. An example is "all orders of one customer". An index can also help `UPDATE` and `DELETE` commands that have a search condition. It can help joins too <Cite n={1} />.

Indexes matter less for small tables. They also matter less for reports that read most rows of a big table. Reading in order is faster there <Cite n={5} />.

</Layman>
<Bangla>

বড় টেবিলে অনেক কুয়েরি যখন অল্প কয়েকটি রো খোঁজে, তখন ইনডেক্স দরকার হয়। যেমন "একজন কাস্টমারের সব অর্ডার"। যেসব `UPDATE` ও `DELETE` কমান্ডে সার্চ কন্ডিশন আছে, সেগুলোতেও ইনডেক্স সাহায্য করতে পারে। জয়েনেও সাহায্য করতে পারে <Cite n={1} />।

ছোট টেবিলের জন্য ইনডেক্স কম গুরুত্বপূর্ণ। বড় টেবিলের বেশিরভাগ রো পড়ে এমন রিপোর্টের জন্যও তাই, কারণ সেখানে ক্রমানুসারে পড়া দ্রুত <Cite n={5} />।

</Bangla>
</Voices>

## How it works

<Voices>
<Technical>

Most MySQL indexes are stored in B-trees <Cite n={5} />. PostgreSQL also creates a B-tree by default <Cite n={2} />. With a search tree, the database may need to walk only a few levels <Cite n={1} />.

This table shows what some PostgreSQL index types handle <Cite n={2} />:

| Type | What it handles |
|---|---|
| B-tree | Equality and range queries on sortable data, such as `<`, `=`, `>`, `BETWEEN`, and `IN` |
| Hash | Simple equality only |

A B-tree can help with `LIKE 'foo%'` (a fixed start), but not with `LIKE '%bar'` <Cite n={2} />.

An index can have more than one column. A multicolumn B-tree index works best when the query limits the first (leftmost) columns <Cite n={3} />. In MySQL, an index on `(col1, col2, col3)` serves a search on `col1`, on `col1, col2`, and on all three <Cite n={5} />. PostgreSQL says to use multicolumn indexes sparingly <Cite n={3} />.

If a query needs only columns that are in an index, the database can take the values from the index tree. This is a **covering index** <Cite n={5} />.

### What an index costs

An index is not free:

- **Writes.** The database must keep the index in step with the table, which adds work to every data change <Cite n={1} />.
- **Space.** An index takes space of its own. The PostgreSQL manual notes that a single-column index "saves space and time" compared with a wider one <Cite n={3} />.
- **Build time.** Building an index on a big table may be slow. During the build, PostgreSQL by default lets reads run but blocks writes <Cite n={1} />.

For this reason, the manual says to remove an index that is seldom or never used <Cite n={1} />.

</Technical>

<Bangla>

MySQL-এর বেশিরভাগ ইনডেক্স B-tree-তে রাখা হয় <Cite n={5} />। PostgreSQL-ও ডিফল্ট হিসেবে B-tree তৈরি করে <Cite n={2} />। সার্চ ট্রি থাকলে ডেটাবেসকে হয়তো মাত্র কয়েকটি স্তর পার হতে হয় <Cite n={1} />।

PostgreSQL-এর কিছু ইনডেক্স টাইপ বিভিন্ন কুয়েরি সামলায় <Cite n={2} />:

- B-tree সাজানো যায় এমন ডেটার ওপর ইকুয়ালিটি (equality) ও রেঞ্জ কুয়েরি সামলায়। যেমন `<`, `=`, `>`, `BETWEEN` ও `IN`।
- Hash ইনডেক্স শুধু সাধারণ ইকুয়ালিটি সামলায়।

B-tree `LIKE 'foo%'` (শুরুর অংশ নির্দিষ্ট) এ সাহায্য করতে পারে, কিন্তু `LIKE '%bar'` এ পারে না <Cite n={2} />।

একটি ইনডেক্সে একাধিক কলাম থাকতে পারে। কুয়েরি প্রথম (leftmost, অর্থাৎ একেবারে বাঁ দিকের) কলামগুলোকে সীমিত করলে মাল্টিকলাম B-tree ইনডেক্স সবচেয়ে ভালো কাজ করে <Cite n={3} />। MySQL-এ `(col1, col2, col3)` এর ইনডেক্স `col1` দিয়ে, `col1, col2` দিয়ে এবং তিনটি দিয়েই সার্চ সামলায় <Cite n={5} />। PostgreSQL বলে মাল্টিকলাম ইনডেক্স কম ব্যবহার করতে <Cite n={3} />।

কখনো একটি কুয়েরির দরকারি সব কলাম ইনডেক্সেই থাকে। তখন ডেটাবেস ইনডেক্স ট্রি থেকেই মান নিতে পারে। একে কভারিং ইনডেক্স (covering index) বলে <Cite n={5} />।

ইনডেক্স বিনামূল্যে পাওয়া যায় না। এর তিনটি খরচ আছে:

- **রাইট (write)।** ডেটাবেসকে ইনডেক্স আর টেবিল একসাথে ঠিক রাখতে হয়। এতে প্রতিটি ডেটা পরিবর্তনে কাজ বাড়ে <Cite n={1} />।
- **জায়গা।** ইনডেক্স নিজের জন্য জায়গা নেয়। PostgreSQL ম্যানুয়াল বলে, আরও চওড়া ইনডেক্সের তুলনায় সিঙ্গেল-কলাম ইনডেক্স "saves space and time" <Cite n={3} />।
- **তৈরির সময়।** বড় টেবিলে ইনডেক্স তৈরি ধীর হতে পারে। তৈরি চলার সময় PostgreSQL ডিফল্টভাবে রিড চলতে দেয়, কিন্তু রাইট আটকে দেয় <Cite n={1} />।

এই কারণে ম্যানুয়াল বলে, যে ইনডেক্স কদাচিৎ বা কখনোই ব্যবহার হয় না, তা মুছে ফেলতে <Cite n={1} />।

</Bangla>
</Voices>

## A real-life example

<Voices>
<Technical>

A learning platform has an `enrollments` table with 5 million rows. The page "My courses" runs `SELECT * FROM enrollments WHERE student_id = 42`. This is the tutorial's own example, and the numbers are not from a source.

Without an index on `student_id`, the database reads the table for each page view. With the index, it goes to the few rows of student 42, and the page gets faster. But every new enrollment now also updates the index, so a bulk import has more work to do. With ten more indexes added "just in case", every import pays for all of them.

</Technical>

</Layman>

## Common mistakes

<Voices>
<Technical>

- **Indexing every column.** Each index adds work on writes <Cite n={1} /> and takes space <Cite n={3} />.
- **Expecting a multicolumn index to help every query.** A query that skips the leftmost column may get little help <Cite n={3} />.
- **Comparing columns of different types.** In MySQL, a comparison between two string columns with different character sets (for example `utf8mb4` and `latin1`) rules out an index <Cite n={5} />.
- **Using a leading wildcard.** `LIKE '%bar'` cannot use a B-tree <Cite n={2} />. The database uses an index when it thinks that is more efficient than a full scan <Cite n={1} />.

</Technical>
<Layman>

- **Indexing every column.** Each index adds work on writes <Cite n={1} />. Each index also takes space <Cite n={3} />.
- **Expecting a multicolumn index to help every query.** A query that skips the leftmost column may get little help <Cite n={3} />.
- **Comparing columns of different types.** In MySQL, a comparison between two string columns with different character sets rules out an index. An example is `utf8mb4` and `latin1` <Cite n={5} />.
- **Using a leading wildcard.** `LIKE '%bar'` cannot use a B-tree <Cite n={2} />. The database uses an index when it thinks that is more efficient than a full scan <Cite n={1} />.

</Layman>
<Bangla>

- **প্রতিটি কলামে ইনডেক্স দেওয়া।** প্রতিটি ইনডেক্স রাইটে কাজ বাড়ায় <Cite n={1} />, আর জায়গাও নেয় <Cite n={3} />।
- **ভাবা যে মাল্টিকলাম ইনডেক্স প্রতিটি কুয়েরিতে সাহায্য করবে।** যে কুয়েরি লেফটমোস্ট কলাম বাদ দেয়, সে হয়তো খুব কম সাহায্য পায় <Cite n={3} />।
- **ভিন্ন টাইপের কলাম তুলনা করা।** MySQL-এ ভিন্ন ক্যারেক্টার সেটের দুটি স্ট্রিং কলাম তুলনা করলে ইনডেক্স ব্যবহার হয় না। যেমন `utf8mb4` আর `latin1` <Cite n={5} />।
- **শুরুতে ওয়াইল্ডকার্ড ব্যবহার করা।** `LIKE '%bar'` B-tree ব্যবহার করতে পারে না <Cite n={2} />। ডেটাবেস যখন মনে করে ইনডেক্স ফুল স্ক্যানের চেয়ে বেশি কার্যকর, তখন সে ইনডেক্স ব্যবহার করে <Cite n={1} />।

</Bangla>
</Voices>

## How to see if a query uses an index

<Voices>
<Technical>

Put `EXPLAIN` before the query to see the plan that the database chose <Cite n={7} />.

In PostgreSQL, the plan is a tree of nodes. The bottom nodes are scan nodes, and a table can be read by a sequential scan, an index scan, or a bitmap index scan <Cite n={4} />. A **Seq Scan** with a `Filter` checks the condition on each row it reads <Cite n={4} />. An **Index Scan** shows an `Index Cond` line <Cite n={4} />.

The cost numbers are estimates <Cite n={4} />. With `EXPLAIN ANALYZE`, PostgreSQL executes the statement, not only plans it <Cite n={7} />, then shows the true row counts and times next to the estimates <Cite n={4} />. The manual says that a key check is whether the estimated row counts are near the real ones <Cite n={4} />.

In MySQL, read two columns of the `EXPLAIN` result. `key` is the index that MySQL decided to use, and `NULL` means it found no index to use <Cite n={6} />. If `possible_keys` is `NULL`, no index is relevant <Cite n={6} />. The join type `ALL` is a full table scan, which is normally not good for the first table <Cite n={6} />. To list the indexes of a table, use `SHOW INDEX FROM tbl_name` <Cite n={6} />.

</Technical>
<Layman>

Put `EXPLAIN` before the query. It shows the plan that the database chose <Cite n={7} />.

In PostgreSQL, the plan is a tree of nodes. The bottom nodes are scan nodes. A table can be read by a sequential scan, an index scan, or a bitmap index scan <Cite n={4} />. A Seq Scan with a `Filter` checks the condition on each row it reads <Cite n={4} />. An Index Scan shows an `Index Cond` line <Cite n={4} />.

The cost numbers are estimates <Cite n={4} />. With `EXPLAIN ANALYZE`, PostgreSQL executes the statement. It does not only plan it <Cite n={7} />. Then it shows the true row counts and times next to the estimates <Cite n={4} />. The manual says that a key check is whether the estimated row counts are near the real ones <Cite n={4} />.

In MySQL, read two columns of the `EXPLAIN` result. The column `key` is the index that MySQL decided to use. `NULL` means it found no index to use <Cite n={6} />. If `possible_keys` is `NULL`, no index is relevant <Cite n={6} />. The join type `ALL` is a full table scan. This is normally not good for the first table <Cite n={6} />. To list the indexes of a table, use `SHOW INDEX FROM tbl_name` <Cite n={6} />.

</Layman>
<Bangla>

কুয়েরির আগে `EXPLAIN` লিখুন। এটি ডেটাবেস যে প্ল্যান বেছে নিয়েছে তা দেখায় <Cite n={7} />।

PostgreSQL-এ প্ল্যান হলো নোডের একটি ট্রি। নিচের নোডগুলো স্ক্যান নোড। একটি টেবিল sequential scan, index scan বা bitmap index scan দিয়ে পড়া যায় <Cite n={4} />। `Filter` সহ একটি **Seq Scan** যে প্রতিটি রো পড়ে, তাতে কন্ডিশন যাচাই করে <Cite n={4} />। একটি **Index Scan**-এ `Index Cond` লাইন দেখা যায় <Cite n={4} />।

কস্টের সংখ্যাগুলো আন্দাজ <Cite n={4} />। `EXPLAIN ANALYZE` দিলে PostgreSQL স্টেটমেন্ট শুধু প্ল্যান করে না, চালায়ও <Cite n={7} />। তারপর আন্দাজের পাশে সত্যিকারের রো সংখ্যা ও সময় দেখায় <Cite n={4} />। ম্যানুয়াল বলে, একটি মূল পরীক্ষা হলো আন্দাজ করা রো সংখ্যা আসল সংখ্যার কাছাকাছি কি না <Cite n={4} />।

MySQL-এ `EXPLAIN` ফলাফলের দুটি কলাম পড়ুন। `key` হলো সেই ইনডেক্স, যেটি MySQL ব্যবহার করবে বলে ঠিক করেছে। `NULL` মানে ব্যবহার করার মতো কোনো ইনডেক্স সে পায়নি <Cite n={6} />। `possible_keys` `NULL` হলে কোনো ইনডেক্স প্রাসঙ্গিক নয় <Cite n={6} />। জয়েন টাইপ `ALL` মানে ফুল টেবিল স্ক্যান। প্রথম টেবিলের জন্য এটি সাধারণত ভালো নয় <Cite n={6} />। একটি টেবিলের ইনডেক্সগুলো দেখতে `SHOW INDEX FROM tbl_name` ব্যবহার করুন <Cite n={6} />।

</Bangla>

## What a tester can check

<Voices>
<Technical>

<Callout type="tip" title="Tutorial advice">
These test ideas are the tutorial's own advice.

- **Test with a realistic amount of data.** With 50 rows, every query is fast and a missing index stays hidden. Use a data set as large as production.
- **Run `EXPLAIN` on the slow query.** Look for a full scan on a big table, and for `key: NULL` in MySQL.
- **Compare before and after.** Check the plan and the time before and after you add the index.
- **Measure the write side too.** Time a bulk insert or update with and without the index.
- **Be careful with `EXPLAIN ANALYZE` on `UPDATE` or `DELETE`.** It really runs the query, so use a copy of the data.
</Callout>

</Technical>

## Key words

| Word | Meaning |
|---|---|
| Index | An extra structure that helps the database find rows by column value without reading every row <Cite n={5} /> |
| Full table scan | Reading the whole table, row by row <Cite n={1} /> |
| B-tree | The default index type of PostgreSQL, and the type of most MySQL indexes <Cite n={2} /> <Cite n={5} /> |
| Multicolumn index | One index on several columns, best when the query limits the leftmost ones <Cite n={3} /> |
| Covering index | An index that holds all the columns a query needs <Cite n={5} /> |
| EXPLAIN | A command that shows the plan of a query <Cite n={4} /> |
