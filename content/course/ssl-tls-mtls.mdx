# SSL, TLS, and mTLS

You open a bank site and see a padlock. A teammate says "the site has an SSL certificate". Another says "we need mTLS between the services". The words sound alike, but they name different things. This page sorts them out.

<PageMeta />

## In plain words

<Voices>
<Technical>

TLS (Transport Layer Security) is a protocol that lets a client and a server talk over an untrusted network. When it protects HTTP, the result is HTTPS <Cite n={5} />. The main goal of TLS is a secure channel between two peers. It needs only a reliable, in-order stream of data from the layer below <Cite n={1} />.

The channel should give three properties <Cite n={1} />:

| Property | What it means |
|---|---|
| Authentication | The server is always authenticated. The client is optionally authenticated. |
| Confidentiality | Data sent after the setup is visible only to the two endpoints. The size of the data is not hidden, unless the endpoints pad it. |
| Integrity | An attacker cannot change the data without detection. |

The RFC says these properties should hold even when an attacker has complete control of the network <Cite n={1} />.

**Why people still say "SSL".** SSL (Secure Sockets Layer) is the older family of protocols. SSL 3.0 came out in 1996, and TLS 1.0 replaced it in 1999 <Cite n={2} />. RFC 7568 says SSL 3.0 must not be used <Cite n={2} />. RFC 8446 says the same for SSL 3.0 and SSL 2.0: an implementation must not negotiate them <Cite n={1} />. So the safe protocol today is TLS. The word "SSL" lives on in everyday speech, such as "SSL certificate". This habit is the tutorial's own remark, not a claim of the sources. When you read "SSL" in a ticket, it nearly always means TLS.

</Technical>

<Bangla>

TLS (Transport Layer Security) হলো একটি protocol। এটি একটি client আর একটি server-কে অবিশ্বস্ত network-এর উপর দিয়ে কথা বলতে দেয়। TLS যখন HTTP-কে সুরক্ষিত করে, ফলাফল হলো HTTPS <Cite n={5} />। TLS-এর মূল লক্ষ্য দুই peer-এর মধ্যে একটি secure channel। এর জন্য নিচের স্তর থেকে শুধু একটি নির্ভরযোগ্য, ক্রমানুসারী data stream দরকার <Cite n={1} />।

Channel-টির তিনটি বৈশিষ্ট্য দেওয়া উচিত <Cite n={1} />:

- **Authentication।** Server সবসময় authenticated থাকে। Client ঐচ্ছিকভাবে authenticated হয়।
- **Confidentiality।** Setup-এর পরে পাঠানো data শুধু দুই endpoint দেখতে পায়। Data-র আকার লুকানো থাকে না, যদি না endpoint সেটি pad করে।
- **Integrity।** কোনো attacker ধরা না পড়ে data বদলাতে পারে না।

RFC বলে, attacker network-এর পূর্ণ নিয়ন্ত্রণ পেলেও এই বৈশিষ্ট্যগুলো বজায় থাকা উচিত <Cite n={1} />।

**মানুষ কেন এখনো "SSL" বলে।** SSL (Secure Sockets Layer) হলো protocol-এর পুরনো পরিবার। SSL 3.0 বের হয় 1996 সালে, আর 1999 সালে TLS 1.0 তার জায়গা নেয় <Cite n={2} />। RFC 7568 বলে SSL 3.0 ব্যবহার করা যাবে না <Cite n={2} />। RFC 8446 SSL 3.0 আর SSL 2.0-র ক্ষেত্রে একই কথা বলে: একটি implementation এগুলো negotiate করবে না <Cite n={1} />। তাই আজ নিরাপদ protocol হলো TLS। "SSL" শব্দটি দৈনন্দিন কথায় টিকে আছে, যেমন "SSL certificate"। এই অভ্যাস নিয়ে কথাটি টিউটোরিয়ালের নিজস্ব মন্তব্য, source-গুলোর দাবি নয়। কোনো ticket-এ "SSL" পড়লে, তার মানে প্রায় সবসময় TLS।

## When you need it

<Voices>
<Technical>

MDN advises every website to use HTTPS for its pages and for the resources they load <Cite n={5} />. TLS also fits any other link where two programs talk over a network you do not control, such as an API call between two services. The RFC says TLS is independent of the application protocol, so higher protocols can run on top of it <Cite n={1} />.

mTLS (mutual TLS) is the case where the client also proves who it is. MDN says that on the web it appears mostly in specialized applications <Cite n={5} />. Teams often think of it for calls between internal services. That remark is the tutorial's own.

</Technical>

MDN প্রতিটি website-কে HTTPS ব্যবহার করার পরামর্শ দেয়। এটি তার পাতার জন্য এবং সেগুলো যেসব resource load করে তাদের জন্যও প্রযোজ্য <Cite n={5} />। যেখানে দুটি program এমন network-এর উপর দিয়ে কথা বলে, যা আপনি নিয়ন্ত্রণ করেন না, সেরকম যেকোনো link-এও TLS মানায়। একটি উদাহরণ হলো দুটি service-এর মধ্যে একটি API call। RFC বলে TLS application protocol থেকে স্বাধীন, তাই উপরের স্তরের protocol তার উপর চলতে পারে <Cite n={1} />।

## How it works

<Voices>
<Technical>

A TLS connection starts with a handshake, then uses a record protocol. The handshake authenticates the parties, agrees on the parameters, and sets up shared keys. The record protocol then protects the traffic with those keys <Cite n={1} />. MDN lists what the two sides agree on: the TLS version, the cipher suite (the set of algorithms), the secret key, and, as an option, mutual authentication <Cite n={5} />. After that, HTTP headers and bodies are encrypted <Cite n={5} />.

**The server certificate.** A site needs a digital certificate. It holds a signed copy of the public key that matches the private key of the site. This ties the keys to the domain name <Cite n={5} />. A Certification Authority (CA) issues the certificate. Let's Encrypt is one example <Cite n={5} />. In the handshake, the server sends the Certificate message and a CertificateVerify message. CertificateVerify is a signature over the whole handshake, made with the private key that goes with the certificate <Cite n={1} />.

**The client certificate in mTLS.** If the server wants a client certificate, it sends a CertificateRequest. If it does not want one, it leaves that message out <Cite n={1} />. The client then sends its own Certificate and CertificateVerify <Cite n={1} />. The server can now check who the client is, as well as the client checking the server.

TLS does not decide what a valid client is. The RFC says it leaves to the higher protocol how to read the certificates that were exchanged <Cite n={1} />. RFC 8705 shows one such design for OAuth 2.0. The authorization server decides by policy whether a client must use mTLS. The client sends its `client_id`, and the server checks the certificate against what it expects for that client. A missing or wrong certificate gives an `invalid_client` error <Cite n={4} />. RFC 8705 has two methods <Cite n={4} />:

| Method | How the server decides |
|---|---|
| PKI | It validates the certificate chain and matches one subject name. Whether to check revocation is a deployment decision. |
| Self-signed | The client registers its certificates. The server does not validate a chain. It accepts a certificate that matches a registered one. |

The same RFC can also bind an access token to the client certificate. The resource server must check that the certificate matches the token. If it does not, the server rejects the request with HTTP 401 and `invalid_token` <Cite n={4} />.

**The versions.** Each fact has the RFC that states it:

| Version | Status | RFC |
|---|---|---|
| SSL 3.0 | Must not be used. Must not be negotiated from any TLS version. | RFC 7568 <Cite n={2} /> |
| TLS 1.0 and 1.1 | Deprecated. They lack current algorithms. They must not be used. | RFC 8996 <Cite n={3} /> |
| TLS 1.2 | Obsoleted by TLS 1.3. MDN says some sites still use it. | RFC 8446 <Cite n={1} /> <Cite n={5} /> |
| TLS 1.3 | The current version (August 2018) and the most widely used. | RFC 8446 <Cite n={1} /> <Cite n={5} /> |

RFC 8996 gives a reason for TLS 1.0 and 1.1: their integrity and signatures depend on SHA-1, and the only upgrade path is a newer version <Cite n={3} />. It adds that removing old versions reduces the attack surface and the chance of misconfiguration <Cite n={3} />.

</Technical>

<Bangla>

একটি TLS connection শুরু হয় handshake দিয়ে। তারপর সে একটি record protocol ব্যবহার করে। Handshake পক্ষগুলোকে authenticate করে, parameter ঠিক করে এবং shared key বানায়। তারপর record protocol সেই key দিয়ে traffic সুরক্ষিত করে <Cite n={1} />। MDN তালিকা দেয় দুই পক্ষ কী নিয়ে একমত হয়: TLS version, cipher suite (algorithm-এর সেট), secret key, এবং ঐচ্ছিকভাবে mutual authentication <Cite n={5} />। এরপর HTTP header আর body encrypted হয় <Cite n={5} />।

**Server certificate।** একটি site-এর একটি digital certificate দরকার। এতে site-এর private key-র সঙ্গে মেলে এমন public key-র একটি signed কপি থাকে। এটি key-গুলোকে domain name-এর সঙ্গে বাঁধে <Cite n={5} />। একটি Certification Authority (CA) certificate ইস্যু করে। Let's Encrypt একটি উদাহরণ <Cite n={5} />। Handshake-এ server Certificate message আর একটি CertificateVerify message পাঠায়। CertificateVerify হলো পুরো handshake-এর উপর একটি signature। Server এটি বানায় certificate-এর সঙ্গে যুক্ত private key দিয়ে <Cite n={1} />।

**mTLS-এ client certificate।** Server client certificate চাইলে সে একটি CertificateRequest পাঠায়। না চাইলে সে ওই message বাদ দেয় <Cite n={1} />। তখন client নিজের Certificate আর CertificateVerify পাঠায় <Cite n={1} />। এখন client যেমন server-কে যাচাই করে, server-ও তেমন client কে তা যাচাই করতে পারে।

কোনটি valid client, তা TLS ঠিক করে না। RFC বলে, আদান-প্রদান হওয়া certificate কীভাবে পড়তে হবে, তা সে উপরের protocol-এর হাতে ছেড়ে দেয় <Cite n={1} />। RFC 8705 OAuth 2.0-এর জন্য এমন একটি design দেখায়। Authorization server policy দিয়ে ঠিক করে একটি client-কে mTLS ব্যবহার করতে হবে কি না। Client তার `client_id` পাঠায়। Server certificate-টি মিলিয়ে দেখে, সেই client-এর জন্য সে কী প্রত্যাশা করে। Certificate না থাকলে বা ভুল হলে `invalid_client` error আসে <Cite n={4} />। RFC 8705-এ দুটি পদ্ধতি আছে <Cite n={4} />:

- **PKI।** Server certificate chain validate করে এবং একটি subject name মেলায়। Revocation যাচাই করা হবে কি না, তা একটি deployment-এর সিদ্ধান্ত।
- **Self-signed।** Client তার certificate register করে। Server কোনো chain validate করে না। সে এমন certificate গ্রহণ করে, যা register করা একটির সঙ্গে মেলে।

একই RFC একটি access token-কে client certificate-এর সঙ্গে bind-ও করতে পারে। Resource server-কে যাচাই করতে হবে যে certificate-টি token-এর সঙ্গে মেলে। না মিললে server HTTP 401 আর `invalid_token` দিয়ে request প্রত্যাখ্যান করে <Cite n={4} />।

**Version-গুলো।** প্রতিটি তথ্যের পাশে সেই RFC আছে, যা সেটি বলে:

- **SSL 3.0।** এটি ব্যবহার করা যাবে না। কোনো TLS version থেকে এটি negotiate করা যাবে না। RFC 7568 <Cite n={2} />।
- **TLS 1.0 আর 1.1।** এগুলো deprecated। এগুলোতে বর্তমান algorithm নেই। এগুলো ব্যবহার করা যাবে না। RFC 8996 <Cite n={3} />।
- **TLS 1.2।** TLS 1.3 এটিকে obsolete করেছে। MDN বলে কিছু site এখনো এটি ব্যবহার করে। RFC 8446 <Cite n={1} /> <Cite n={5} />।
- **TLS 1.3।** এটি বর্তমান version (আগস্ট 2018) এবং সবচেয়ে বেশি ব্যবহৃত। RFC 8446 <Cite n={1} /> <Cite n={5} />।

RFC 8996 TLS 1.0 আর 1.1-এর একটি কারণ দেয়: এগুলোর integrity আর signature SHA-1-এর উপর নির্ভর করে, এবং একমাত্র upgrade-এর পথ হলো নতুন version <Cite n={3} />। এটি আরও বলে, পুরনো version সরালে attack surface আর ভুল configuration-এর সম্ভাবনা কমে <Cite n={3} />।

## A real-life example

<Voices>
<Technical>

This example is the tutorial's own. A test team runs a payments API. Browsers call the public site over HTTPS, and the server shows a certificate for its domain. Two internal services, "orders" and "ledger", also call each other. The ledger service accepts a call only if the caller shows a client certificate that the company's CA issued. A test that calls the ledger without a certificate fails in the handshake, before any request reaches the application.

এই উদাহরণ টিউটোরিয়ালের নিজস্ব। একটি test দল একটি payments API চালায়। Browser public site-কে HTTPS দিয়ে call করে। Server তার domain-এর জন্য একটি certificate দেখায়। দুটি অভ্যন্তরীণ service, "orders" আর "ledger", পরস্পরকেও call করে। Ledger service কোনো call গ্রহণ করে শুধু তখনই, যখন caller এমন একটি client certificate দেখায়, যা কোম্পানির CA ইস্যু করেছে। Certificate ছাড়া ledger-কে call করা একটি test handshake-এই fail করে। কোনো request application-এ পৌঁছানোর আগেই সেটি fail করে।

</Bangla>

## Common mistakes

<Voices>
<Technical>

- **Saying "TLS makes the app secure".** TLS protects the data in transit between two endpoints <Cite n={1} />. The RFC leaves it to the protocol above TLS to decide how to read the certificates that were exchanged <Cite n={1} />. The rest of this point is the tutorial's own advice: TLS does not test how the application treats the data, so a site can use TLS and still have login bugs.
- **Leaving old versions on.** RFC 8996 says TLS 1.0 and 1.1 must not be used <Cite n={3} />.
- **Mixed content.** An HTTPS page that loads a script over HTTP gives that script no protection. Browsers upgrade or block such loads <Cite n={5} />.
- **Treating a self-signed certificate as the same case everywhere.** In RFC 8705 the server accepts it only when it matches a registered one <Cite n={4} />. A browser has its own rules for certificates, and this page does not cover them.

</Technical>

## What a tester can check

<Voices>
<Technical>

<Callout type="tip" title="Tutorial advice">
These test ideas are the tutorial's own advice, not a claim of the sources.

- **Versions.** Check which TLS versions the test server accepts. Confirm that SSL 3.0, TLS 1.0, and TLS 1.1 are refused.
- **Certificate.** Check that the certificate matches the domain, has not expired, and comes from a CA that the client trusts.
- **No client certificate.** On an mTLS endpoint, call without a client certificate. Expect a refusal, and check how the client shows the error.
- **Wrong client certificate.** Use a certificate that the server does not expect. Expect a refusal.
- **Expiry.** Plan a test for a client certificate that expires, and for its rotation.
- **Mixed content.** Open pages in a browser and look for HTTP resources on HTTPS pages.
- **Scope.** Do not call a feature "secure" because TLS works. Test login, access rules, and data handling on their own.
</Callout>

</Technical>
<Layman>

<Bangla>

এই test-এর ধারণাগুলো টিউটোরিয়ালের নিজস্ব পরামর্শ, source-গুলোর কোনো দাবি নয়।

- **Version।** Test server কোন TLS version গ্রহণ করে তা যাচাই করুন। নিশ্চিত করুন যে SSL 3.0, TLS 1.0 আর TLS 1.1 প্রত্যাখ্যাত হয়।
- **Certificate।** যাচাই করুন যে certificate domain-এর সঙ্গে মেলে, মেয়াদ শেষ হয়নি, এবং এটি এমন একটি CA থেকে এসেছে যাকে client বিশ্বাস করে।
- **Client certificate নেই।** একটি mTLS endpoint-এ client certificate ছাড়া call করুন। প্রত্যাখ্যান আশা করুন, এবং client error কীভাবে দেখায় তা যাচাই করুন।
- **ভুল client certificate।** এমন একটি certificate ব্যবহার করুন, যা server প্রত্যাশা করে না। প্রত্যাখ্যান আশা করুন।
- **মেয়াদ শেষ।** মেয়াদ শেষ হওয়া একটি client certificate-এর জন্য, এবং তার rotation-এর জন্য, একটি test পরিকল্পনা করুন।
- **Mixed content।** Browser-এ পাতা খুলুন এবং HTTPS পাতায় HTTP resource খুঁজুন।
- **পরিধি।** TLS কাজ করছে বলেই কোনো feature-কে "secure" বলবেন না। Login, access rule আর data handling আলাদাভাবে test করুন।

</Bangla>
</Voices>

## Key words

| Word | Meaning |
|---|---|
| TLS | A protocol for a secure channel between a client and a server <Cite n={1} /> |
| SSL | The older protocol family that TLS replaced. SSL 3.0 must not be used <Cite n={2} /> |
| HTTPS | HTTP carried over TLS <Cite n={5} /> |
| Handshake | The first step of TLS: it agrees on the parameters, authenticates, and sets up keys <Cite n={1} /> |
| Cipher suite | The set of algorithms the two sides agree to use <Cite n={5} /> |
| Digital certificate | A document with a signed public key that ties the key to a domain name <Cite n={5} /> |
| CA | Certification Authority: an entity that issues certificates <Cite n={5} /> |
| mTLS | Mutual TLS: the client also authenticates with a certificate, in addition to the server <Cite n={1} />. RFC 8705 uses it for OAuth 2.0 client authentication <Cite n={4} /> |
| CertificateRequest | The handshake message in which the server asks for a client certificate <Cite n={1} /> |
| Certificate-bound token | An access token tied to the client certificate <Cite n={4} /> |
