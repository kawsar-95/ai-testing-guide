# TCP and UDP

Two ways to send a message to a friend: a registered letter and a postcard. For the registered letter, the post office checks that it arrives, in the right order, and tells you if it got lost. The postcard is cheap and quick, but nobody promises anything. TCP is the registered letter. UDP is the postcard.

## In plain words

<Voices>
<Technical>

IP moves packets from one computer to another. TCP and UDP sit on top of IP. They get the data to the right program on that computer, and they differ in how much they promise.

**TCP** gives a reliable, in-order byte stream to applications <Cite n={1} />. It detects lost packets with sequence numbers and damaged data with checksums, and it repairs a loss by sending the data again <Cite n={1} />. Each TCP segment travels inside an IP datagram <Cite n={1} />.

**UDP** gives a way to send messages with a minimum of protocol mechanism <Cite n={2} />. Delivery and duplicate protection are not guaranteed <Cite n={2} />. If an application needs ordered, reliable delivery of a stream, the UDP standard says to use TCP <Cite n={2} />.

Both protocols use **port numbers** to pick the program. In TCP the source port and the destination port are each 16 bits <Cite n={1} />. A UDP header has a source port, a destination port, a length, and a checksum <Cite n={2} />.

</Technical>

## How it works

<Voices>
<Technical>

TCP first builds a connection. This is the **three-way handshake**:

```text
Client                      Server
  | ---- SYN (my number X) --->  |
  | <--- SYN+ACK (Y, got X) ---  |
  | ---- ACK (got Y) -------->   |
  |   connection is open         |
```

Each side picks a starting sequence number, and the other side confirms it. Four steps become three messages, because the middle two combine in one message <Cite n={1} />. The main reason for the handshake is to stop old duplicate connection requests from causing confusion <Cite n={1} />.

While data flows, the receiver tells the sender a **window**: the range of sequence numbers it can accept now. This is related to its free buffer space <Cite n={1} />. A TCP endpoint must also slow down when the network is crowded: it starts slowly, grows its speed with care, and waits longer after each repeated timeout. The goal is to avoid a congestion collapse <Cite n={1} />. The timeout is not fixed. It is computed while the connection runs <Cite n={1} />.

To close, one side sends a FIN segment. The other side acknowledges it, but it sends its own FIN only when its own user has closed the connection too <Cite n={1} />. The side that closes waits for a while in the **TIME-WAIT** state. This makes sure the peer got the acknowledgment, and it keeps delayed segments of the old connection away from a new one <Cite n={1} />. A **reset** (RST) is the hard stop: it aborts a connection that is open and informs the user <Cite n={1} />.

UDP has none of this. There is no handshake and no window. A sender just sends a datagram. The header has a length field, and the minimum length is 8 octets (the header alone) <Cite n={2} />. The source port is optional; if it is not used, it is zero <Cite n={2} />. An all-zero checksum means that the sender did not compute one <Cite n={2} />.

</Technical>

</Layman>
<Bangla>

TCP প্রথমে একটি connection তৈরি করে। একে বলে **three-way handshake**:

1. Client তার শুরুর সংখ্যা X দিয়ে SYN পাঠায়।
2. Server SYN+ACK দিয়ে উত্তর দেয়। সে নিজের সংখ্যা Y জানায় এবং নিশ্চিত করে যে X পেয়েছে।
3. Client ACK পাঠিয়ে নিশ্চিত করে যে Y পেয়েছে। এখন connection খোলা।

প্রতিটি পক্ষ একটি শুরুর sequence number বেছে নেয়, আর অন্য পক্ষ সেটি নিশ্চিত করে। চার ধাপ তিনটি message হয়ে যায়, কারণ মাঝের দুটি এক message-এ মিলে যায় <Cite n={1} />। Handshake-এর মূল কারণ হলো পুরোনো duplicate connection request যেন বিভ্রান্তি না ঘটায় <Cite n={1} />।

Data চলার সময় receiver sender-কে একটি **window** জানায়। Window হলো receiver এখন যে sequence number-এর পরিসর নিতে পারে। এটি তার ফাঁকা buffer space-এর সঙ্গে সম্পর্কিত <Cite n={1} />। Network ভিড় হলে TCP endpoint-কে ধীর হতে হয়। সে ধীরে শুরু করে। সাবধানে গতি বাড়ায়। প্রতিটি পুনরাবৃত্ত timeout-এর পর বেশি সময় অপেক্ষা করে। লক্ষ্য হলো congestion collapse এড়ানো <Cite n={1} />। Timeout স্থির নয়। Connection চলার সময় এটি হিসাব করা হয় <Cite n={1} />।

বন্ধ করতে এক পক্ষ একটি FIN segment পাঠায়। অন্য পক্ষ তা acknowledge করে। কিন্তু নিজের FIN পাঠায় তখনই, যখন তার নিজের user-ও connection বন্ধ করেছে <Cite n={1} />। যে পক্ষ বন্ধ করে, সে কিছুক্ষণ **TIME-WAIT** অবস্থায় অপেক্ষা করে। এতে নিশ্চিত হয় যে অপর পক্ষ acknowledgment পেয়েছে। এটি পুরোনো connection-এর দেরিতে আসা segment-কে নতুন connection থেকে দূরে রাখে <Cite n={1} />। **Reset** (RST) হলো কঠোর থামানো। এটি খোলা connection বাতিল করে এবং user-কে জানায় <Cite n={1} />।

UDP-তে এসবের কিছুই নেই। কোনো handshake নেই, কোনো window নেই। Sender শুধু একটি datagram পাঠায়। Header-এ একটি length field আছে। সর্বনিম্ন length 8 octet (শুধু header) <Cite n={2} />। Source port ঐচ্ছিক। ব্যবহার না হলে এটি শূন্য <Cite n={2} />। সব-শূন্য checksum মানে sender checksum হিসাব করেনি <Cite n={2} />।

</Bangla>
</Voices>

## When you need it

<Voices>
<Technical>

Pick TCP when every byte must arrive, in order: a web page, a file, a database call, a login. Pick UDP when speed matters more than perfect delivery, and the application can live with a gap or can repair it by itself.

The early UDP standard names two major uses: the name server and trivial file transfer <Cite n={2} />. UDP is IP protocol number 17 <Cite n={2} />.

</Technical>
<Layman>

Pick TCP when every byte must arrive, in order. Examples are a web page, a file, a database call, and a login. Pick UDP when speed matters more than perfect delivery. The application also needs to be able to live with a gap, or to repair it by itself.

The early UDP standard names two major uses: the name server and trivial file transfer <Cite n={2} />. UDP is IP protocol number 17 <Cite n={2} />.

</Layman>
<Bangla>

প্রতিটি byte ক্রমানুসারে পৌঁছানো দরকার হলে TCP বেছে নিন। উদাহরণ: web page, file, database call এবং login। নিখুঁত delivery-র চেয়ে গতি বেশি জরুরি হলে UDP বেছে নিন। এর সঙ্গে application-কে ফাঁক মেনে নিতে পারতে হবে, অথবা নিজে সেটি মেরামত করতে পারতে হবে।

শুরুর দিকের UDP standard দুটি প্রধান ব্যবহারের নাম দেয়: name server এবং trivial file transfer <Cite n={2} />। UDP হলো IP protocol number 17 <Cite n={2} />।

</Bangla>
</Voices>

| Connection | Handshake first | None |
| Delivery | Reliable, in order <Cite n={1} /> | Not guaranteed <Cite n={2} /> |
| Overhead | More messages and state | Very little <Cite n={2} /> |
| Typical fit | Pages, files, transactions | Live media, quick lookups |

## Common mistakes

<Voices>
<Technical>

- **"UDP is broken."** UDP does what it says. The missing promises are the design <Cite n={2} />.
- **"TCP means the message was processed."** TCP only delivers bytes to the other program. The program can still fail to handle them.
- **Mixing up a slow network with a lost connection.** A slow reply is not always a failed one. Test both, and check what the user sees.
- **Forgetting that the server needs the port to be open.** A closed port or a firewall rule can stop a connection even when the server runs. This is the tutorial's own advice, not a statement of the RFCs.

</Technical>
<Layman>

- **"UDP is broken."** UDP does what it says. The missing promises are the design <Cite n={2} />.

- **Forgetting that the server needs the port to be open.** A closed port or a firewall rule can stop a connection even when the server runs. This is the tutorial's own advice, not a statement of the RFCs.

</Layman>
<Bangla>

- **"UDP ভাঙা।"** UDP যা বলে তা-ই করে। প্রতিশ্রুতি না থাকাই এর নকশা <Cite n={2} />।
- **"TCP মানে message process হয়েছে।"** TCP শুধু অন্য program-এ byte পৌঁছে দেয়। Program সেগুলো সামলাতে ব্যর্থ হতেও পারে।
- **ধীর network আর হারানো connection গুলিয়ে ফেলা।** ধীর উত্তর মানেই ব্যর্থ উত্তর নয়। দুটোই test করুন। User কী দেখে তা দেখুন।
- **Server-এর জন্য port খোলা লাগে, তা ভুলে যাওয়া।** Server চললেও বন্ধ port বা firewall rule connection আটকাতে পারে। এটি tutorial-এর নিজস্ব পরামর্শ, RFC-র বক্তব্য নয়।

## What a tester can check

<Voices>
<Technical>

<Callout type="tip" title="Tutorial advice">

This advice is the tutorial's own. It is not from a standard.

- Test with a bad network: add delay, packet loss, and a dropped connection. Check that the app shows a clear message and does not hang.
- For a TCP-based feature, cut the connection in the middle of a request. Check that nothing is saved twice and nothing is half saved.
- For a UDP-based feature, check that the app copes with a lost, late, or duplicate message.
- Use a packet tool to look at the handshake, and see when connections open and close.
- Check timeouts: what does the user see when the server is slow, and when the port is closed?

</Callout>

</Technical>

## Key words

| Word | Meaning |
|---|---|
| TCP | A reliable, in-order byte stream between two programs |
| UDP | A simple message service with no delivery guarantee |
| Segment | One piece of a TCP stream, sent inside an IP datagram |
| Datagram | One UDP message |
| Port | A 16-bit number that picks the program on a computer |
| Three-way handshake | The set-up of a TCP connection |
| SYN, ACK, FIN, RST | TCP flags: start, confirm, finish, reset |
| Window | How much data the receiver can accept now |
| Retransmission | Sending lost data again |
| TIME-WAIT | A short wait after close, to avoid mixing old and new connections |
