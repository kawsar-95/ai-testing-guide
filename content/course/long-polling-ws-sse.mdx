# Long Polling, WebSockets, and SSE

A chat page must show a new message the moment it arrives. But a browser normally asks, and the server answers. So how can the server speak first? This page compares three answers: long polling, WebSockets, and server-sent events (SSE).

<PageMeta />

## In plain words

<Voices>
<Technical>

In plain HTTP, a client sends a request and the server sends one response. A server cannot open a connection to the client, and it cannot send a response that nobody asked for <Cite n={1} />. A client can ask again and again (polling). This wastes bandwidth when nothing is new, and data waits until the next poll <Cite n={1} />.

The three techniques below let the server send data sooner. They differ in the direction of data and in how they recover from a broken connection.

</Technical>

তিনটি technique server-কে আগে data পাঠাতে দেয়। এগুলো data-র দিকে আলাদা। ভাঙা connection থেকে ফিরে আসার উপায়েও এগুলো আলাদা।

## How it works

<Voices>
<Technical>

### Long polling

The server holds a request open. It answers only when there is an event, a status change, or a timeout <Cite n={1} />. Then the client usually sends a new request at once, or after a short pause <Cite n={1} />. Data pushes from server to client. For data in the other direction, the client sends ordinary HTTP requests <Cite n={2} />. Each request and each response is a complete HTTP message with its own headers <Cite n={1} />.

### WebSockets

A WebSocket starts as an HTTP request with an `Upgrade: websocket` header. If the server agrees, it answers with status `101 Switching Protocols` <Cite n={2} />. After that, both sides can send data at any time, on the same connection <Cite n={2} />. Data travels in messages, and a message is made of one or more frames. A frame can hold text (UTF-8), binary data, or a control signal such as Close, Ping, or Pong <Cite n={2} />. A Ping can serve as a keepalive <Cite n={2} />. The RFC says implementations must support TLS (`wss` URLs) and should use it <Cite n={2} />.

MDN warns that the `WebSocket` interface has no backpressure. If messages arrive faster than the app can handle them, the memory may fill, the CPU may reach 100%, or both <Cite n={4} />.

**Reconnection.** After an abnormal closure, a client should wait before it reconnects. The RFC says the first attempt should follow a random delay (0 to 5 seconds is given as a reasonable start). Later attempts should wait longer each time, for example with truncated binary exponential backoff <Cite n={2} />. Many clients that reconnect at once may act like a denial-of-service attack <Cite n={2} />. The sources on this page describe no built-in way to get messages sent while the client was offline. This is the tutorial's own note: the app must design that part.

### Server-sent events (SSE)

The page creates an `EventSource` with a URL. The server answers with the MIME type `text/event-stream` <Cite n={5} />. The stream is UTF-8 text <Cite n={3} />. Each message is a block of lines such as `data: hello`, and a blank line ends the block <Cite n={5} />. The fields are `event`, `data`, `id`, and `retry` <Cite n={3} />. SSE is a one-way connection: the client cannot send events to the server <Cite n={5} />.

**Reconnection.** By default, the browser restarts the connection when it closes <Cite n={5} />. Before it retries, it waits for the reconnection time. The first value depends on the browser, and the standard says it is probably a few seconds <Cite n={3} />. The `retry` field sets this time in milliseconds <Cite n={5} />. The `id` field sets the last event ID. On reconnection, the browser sends that ID in the `Last-Event-ID` request header <Cite n={3} />. What the server then sends is up to the server. This is the tutorial's own note.

Two ways to stop the reconnection: the server answers with `204 No Content` <Cite n={3} />, or the client calls `close()` <Cite n={5} />. If the response status is not 200, or the content type is not `text/event-stream`, the browser fails the connection and does not reconnect <Cite n={3} />.

</Technical>

<Bangla>

**Long polling।** Server একটি request খোলা ধরে রাখে। সে শুধু তখনই উত্তর দেয়, যখন একটি event, status-এর পরিবর্তন বা একটি timeout থাকে <Cite n={1} />। তারপর client সাধারণত সাথে সাথে, বা অল্প বিরতির পরে, একটি নতুন request পাঠায় <Cite n={1} />। Data server থেকে client-এর দিকে push হয়। উল্টো দিকের data-র জন্য client সাধারণ HTTP request পাঠায় <Cite n={2} />। প্রতিটি request ও প্রতিটি response নিজস্ব header সহ একটি সম্পূর্ণ HTTP message <Cite n={1} />।

**WebSockets।** WebSocket শুরু হয় `Upgrade: websocket` header সহ একটি HTTP request হিসেবে। Server রাজি হলে সে `101 Switching Protocols` status দিয়ে উত্তর দেয় <Cite n={2} />। এরপর দুই পক্ষই একই connection-এ যেকোনো সময় data পাঠাতে পারে <Cite n={2} />। Data message হিসেবে চলে, আর একটি message এক বা একাধিক frame দিয়ে তৈরি। একটি frame-এ text (UTF-8), binary data, বা Close, Ping ও Pong-এর মতো একটি control signal থাকতে পারে <Cite n={2} />। একটি Ping keepalive হিসেবে কাজ করতে পারে <Cite n={2} />। RFC বলে, implementation-কে অবশ্যই TLS (`wss` URL) support করতে হবে এবং TLS ব্যবহার করা উচিত <Cite n={2} />।

MDN সতর্ক করে যে `WebSocket` interface-এ backpressure নেই। ধরুন message app-এর সামলানোর চেয়ে দ্রুত আসছে। তখন memory ভরে যেতে পারে, CPU 100%-এ পৌঁছাতে পারে, বা দুটিই হতে পারে <Cite n={4} />।

WebSocket-এর reconnection: অস্বাভাবিকভাবে বন্ধ হওয়ার পর একটি client-এর reconnect করার আগে অপেক্ষা করা উচিত। RFC বলে, প্রথম চেষ্টা একটি random delay-র পরে হওয়া উচিত (একটি যুক্তিসঙ্গত শুরু হিসেবে 0 থেকে 5 সেকেন্ড বলা হয়েছে)। পরের চেষ্টাগুলোতে প্রতিবার আরও বেশি অপেক্ষা করা উচিত, যেমন truncated binary exponential backoff দিয়ে <Cite n={2} />। অনেক client একসাথে reconnect করলে তা denial-of-service attack-এর মতো কাজ করতে পারে <Cite n={2} />। এই page-এর source-গুলো এমন কোনো built-in উপায় বর্ণনা করে না, যা দিয়ে client offline থাকার সময় পাঠানো message পাওয়া যায়। এটি tutorial-এর নিজস্ব মন্তব্য: app-কে সেই অংশটি design করতে হবে।

**Server-sent events (SSE)।** Page একটি URL দিয়ে একটি `EventSource` তৈরি করে। Server MIME type `text/event-stream` দিয়ে উত্তর দেয় <Cite n={5} />। Stream হলো UTF-8 text <Cite n={3} />। প্রতিটি message হলো `data: hello`-এর মতো কয়েকটি লাইনের একটি block, আর একটি ফাঁকা লাইন block শেষ করে <Cite n={5} />। Field-গুলো হলো `event`, `data`, `id` ও `retry` <Cite n={3} />। SSE একমুখী connection। Client server-কে event পাঠাতে পারে না <Cite n={5} />।

SSE-র reconnection: By default, connection বন্ধ হলে browser সেটি আবার শুরু করে <Cite n={5} />। আবার চেষ্টা করার আগে সে reconnection time পর্যন্ত অপেক্ষা করে। প্রথম মান browser-এর ওপর নির্ভর করে, আর standard বলে এটি সম্ভবত কয়েক সেকেন্ড <Cite n={3} />। `retry` field এই সময় millisecond-এ ঠিক করে <Cite n={5} />। `id` field শেষ event ID ঠিক করে। Reconnection-এর সময় browser সেই ID `Last-Event-ID` request header-এ পাঠায় <Cite n={3} />। তখন server কী পাঠাবে তা server-এর ওপর নির্ভর করে। এটি tutorial-এর নিজস্ব মন্তব্য।

দুটি জিনিস reconnection থামায়। Server `204 No Content` দিয়ে উত্তর দেয় <Cite n={3} />, অথবা client `close()` call করে <Cite n={5} />। Response status 200 না হলে, বা content type `text/event-stream` না হলে, browser connection fail করে এবং reconnect করে না <Cite n={3} />।

## When you need it

<Voices>

This is the tutorial's own advice. Use one of these when the server must tell the client about a change at once: a chat, a live score, or a progress bar. Ask first which way data must flow. If only the server sends, SSE or long polling may be enough. If both sides send often, a WebSocket fits.

## Issues that RFC 6202 lists

<Voices>
<Technical>

RFC 6202 says that HTTP was not designed for two-way communication. It neither encourages nor discourages these techniques, and it lists their issues <Cite n={1} />. It dates from 2011, so check newer browser details. The main points:

**Long polling**

- **Header overhead.** Every message carries full HTTP headers. For small messages, the headers can be a large part of the data <Cite n={1} />.
- **Latency.** The average latency is close to one network transit. The worst case is over three, because the server must wait for the next request <Cite n={1} />.
- **Held resources.** Each client holds a TCP connection and an HTTP request. Some gateways, proxies, and servers can hold only a limited number of requests <Cite n={1} />.
- **Timeouts.** A high timeout cuts the work, but a value that is too high can bring a `408 Request Timeout` or a `504 Gateway Timeout`. The RFC says 30 seconds is generally safer <Cite n={1} />.
- **Caching.** A long poll should suppress caching, with `Cache-Control: no-cache` <Cite n={1} />.

**HTTP streaming** (SSE sends its events with this technique <Cite n={1} />)

- **Intermediaries.** A proxy may buffer a whole response before it forwards it. Streaming does not work through such a proxy <Cite n={1} />.
- **Framing.** HTTP chunks cannot mark the end of a message, because a proxy might merge them <Cite n={1} />.

**Security.** Many open connections can make a denial-of-service attack easier <Cite n={1} />.

</Technical>

RFC 6202 বলে, HTTP দ্বিমুখী যোগাযোগের জন্য design করা হয়নি। এটি এই technique-গুলোকে উৎসাহও দেয় না, নিরুৎসাহও করে না। এটি এগুলোর সমস্যা তালিকাভুক্ত করে <Cite n={1} />। এটি 2011 সালের, তাই browser-এর নতুন তথ্য যাচাই করুন। প্রধান পয়েন্টগুলো নিচে দেওয়া হলো।

- **Latency।** গড় latency এক network transit-এর কাছাকাছি। সবচেয়ে খারাপ ক্ষেত্রে তা তিনটির বেশি, কারণ server-কে পরের request-এর জন্য অপেক্ষা করতে হয় <Cite n={1} />।
- **ধরে রাখা resource।** প্রতিটি client একটি TCP connection আর একটি HTTP request ধরে রাখে। কিছু gateway, proxy ও server সীমিত সংখ্যক request-ই ধরে রাখতে পারে <Cite n={1} />।
- **Timeout।** বেশি timeout কাজ কমায়। কিন্তু খুব বেশি মান `408 Request Timeout` বা `504 Gateway Timeout` ডেকে আনতে পারে। RFC বলে 30 সেকেন্ড সাধারণত বেশি নিরাপদ <Cite n={1} />।

**HTTP streaming** (SSE তার event এই technique দিয়ে পাঠায় <Cite n={1} />)

- **Intermediary (মাঝখানের অংশ)।** একটি proxy পুরো response buffer করে তারপর forward করতে পারে। এমন proxy-র ভেতর দিয়ে streaming কাজ করে না <Cite n={1} />।
- **Framing।** HTTP chunk একটি message-এর শেষ চিহ্নিত করতে পারে না, কারণ proxy সেগুলো মিলিয়ে দিতে পারে <Cite n={1} />।

**Security।** অনেক খোলা connection denial-of-service attack সহজ করতে পারে <Cite n={1} />।

## Common mistakes

<Voices>
<Technical>

- **Expecting a WebSocket to stay open for ever.** An abnormal closure can happen, so the client needs a reconnect plan <Cite n={2} />.
- **Using SSE to send data from the client.** SSE is one-way <Cite n={5} />.
- **Setting a poll timeout above what proxies allow.** The client may get a `408` or a `504` <Cite n={1} />.

</Technical>

- **Using SSE to send data from the client.** SSE is one-way <Cite n={5} />.
- **Setting a poll timeout above what proxies allow.** The client may get a `408` or a `504` <Cite n={1} />.

## What a tester can check

<Voices>
<Technical>

<Callout type="tip" title="Tutorial advice">
These test ideas are the tutorial's own advice, not a claim of the sources.

- **Cut the link.** Drop the network for a moment. Check that the client reconnects, waits longer after each failure, and does not flood the server.
- **Look for lost messages.** Send events while the client is offline. After it returns, check which events it misses.
- **Test the stop signals.** For SSE, check what the page does after a `204` and after an error status.
- **Test behind a proxy.** Use the same proxies as production, and watch for dropped idle connections.
</Callout>

</Technical>

## Key words

| Word | Meaning |
|---|---|
| Long polling | The server holds a request open and answers when it has something to send <Cite n={1} /> |
| HTTP streaming | The server keeps a response open and sends data in pieces without ending it <Cite n={1} /> |
| WebSocket | A two-way channel that starts with an HTTP Upgrade request <Cite n={2} /> |
| Frame | A unit of a WebSocket message. It holds text, binary data, or a control signal <Cite n={2} /> |
| Ping and Pong | WebSocket control frames. A Ping can serve as a keepalive <Cite n={2} /> |
| Server-sent events (SSE) | A one-way stream of events from server to browser, read through `EventSource` <Cite n={5} /> |
| `retry` | An SSE field that sets the reconnection time in milliseconds <Cite n={5} /> |
| `Last-Event-ID` | The request header that tells the server the last event ID, sent on reconnection <Cite n={3} /> |
| Backpressure | A way to slow the sender when the receiver is too slow. The `WebSocket` interface has none <Cite n={4} /> |
