# DNS

A phone keeps names in a contact list, so you tap a name and the phone finds the number. DNS is the contact list of the internet: you type a name, and DNS finds the address of the computer behind it.

<PageMeta />

## In plain words

<Voices>
<Technical>

**DNS** (the Domain Name System) is a naming system with a tree shape and no single owner. Its best-known job is to turn a human-friendly name, such as `learn.example.com`, into a numeric IP address <Cite n={1} />. This step is called a DNS lookup. A reverse lookup goes the other way: it finds the name for an IP address <Cite n={1} />.

Nobody owns one big list. The names form a tree. The top of the tree is the root, and the root has an empty label <Cite n={2} />. You read a name from the most specific part on the left to the least specific part on the right <Cite n={2} />:

```text
learn . example . com . (root)
  |        |       |
  |        |       +-- top level
  |        +---------- the company's zone
  +------------------- one host name
```

Each organization looks after its own part of the tree and runs more than one name server for it <Cite n={2} />.

</Technical>

In `learn.example.com`, `learn` is one host name. `example` is the zone of the company. `com` is the top level.

প্রতিটা organization tree-র নিজের অংশ দেখে। সে তার জন্য একাধিক name server চালায় <Cite n={2} />।

## How it works

<Voices>
<Technical>

Your computer has a small program called a **stub resolver**. It does not do the hard work. It asks a **recursive name server** (often from your network or provider), and that server does the work and keeps a shared cache <Cite n={2} />. In a **recursive** query the first server chases the answer for you. In an **iterative** query a server only points you to the next server <Cite n={2} />.

The resolver follows four steps <Cite n={2} />:

1. Check local data, such as the cache. If the answer is there, return it.
2. Find the best servers to ask. The search starts at the full name, then goes up to the parent name, and so on to the root <Cite n={2} />.
3. Send them a query until one answers.
4. Read the answer. If it answers the question, or says the name does not exist, cache it and return it. If it points to better servers, ask them. If it is an alias, restart with the real name.

```text
browser --> stub resolver --> recursive server --> root server
                                   |           --> "com" server
                                   |           --> "example.com" server
                                   v
                          answer 203.0.113.10 (cached for the TTL)
```

The resolver answers most requests from its cache, so the network and the servers have less work <Cite n={2} />.

</Technical>

<Bangla>

আপনার computer-এ **stub resolver** নামে একটা ছোট program থাকে। সে কঠিন কাজ করে না। সে একটা **recursive name server**-কে জিজ্ঞেস করে। এই server প্রায়ই আপনার network বা provider-এর হয়। সে কাজটা করে এবং একটা shared cache রাখে <Cite n={2} />। **Recursive** query-তে প্রথম server আপনার হয়ে উত্তরের পেছনে ছোটে। **Iterative** query-তে একটা server শুধু পরের server-টা দেখিয়ে দেয় <Cite n={2} />।

Resolver চারটা ধাপ অনুসরণ করে <Cite n={2} />:

1. স্থানীয় data দেখে, যেমন cache। উত্তর সেখানে থাকলে তা ফেরত দেয়।
2. কাদের জিজ্ঞেস করা সবচেয়ে ভালো তা খুঁজে বের করে। খোঁজা শুরু হয় পুরো নাম থেকে, তারপর parent নামে, এভাবে root পর্যন্ত যায় <Cite n={2} />।
3. তাদের কাছে query পাঠায়, যতক্ষণ না একজন উত্তর দেয়।
4. উত্তর পড়ে। উত্তর প্রশ্নের জবাব দিলে, বা বলে যে নামটা নেই, তা cache করে ফেরত দেয়। ভালো server-এর দিকে নির্দেশ করলে তাদের জিজ্ঞেস করে। এটা alias হলে আসল নাম দিয়ে আবার শুরু করে।

ক্রম এই রকম। Browser stub resolver-কে জিজ্ঞেস করে। Stub resolver recursive server-কে জিজ্ঞেস করে। Recursive server জিজ্ঞেস করে একটা root server-কে, তারপর "com" server-কে, তারপর "example.com" server-কে। উত্তর হলো `203.0.113.10`। Resolver সেটা TTL পর্যন্ত cache করে।

Resolver বেশিরভাগ request cache থেকে উত্তর দেয়। তাই network ও server-এর কাজ কম হয় <Cite n={2} />।

</Bangla>

## Record types and TTL

<Voices>
<Technical>

A DNS answer is made of **resource records**. These are the types that testers meet most <Cite n={3} />:

| Type | What it holds |
|---|---|
| A | A host address |
| NS | An authoritative name server for the zone |
| CNAME | The canonical (real) name for an alias |
| MX | A mail exchange: the host that takes mail for the name |
| TXT | Text strings |
| PTR | A domain name pointer, used for reverse lookups |

An MX record has a preference number, and a lower number is preferred <Cite n={3} />. What a TXT text means is set by the domain that holds it <Cite n={3} />. A name with a CNAME record has no other record types, except some DNSSEC records <Cite n={4} />. The value of an NS record, and the host of an MX record, must not be an alias <Cite n={4} />.

Each record has a **TTL** (time to live). It is a time limit on how long a cache may keep the record <Cite n={2} />. It is a number of seconds <Cite n={5} />, from 0 to 2147483647 <Cite n={4} />. A TTL of 0 forbids caching <Cite n={2} />. The TTL is a maximum, not a promise, because a cache may use a lower limit <Cite n={4} />. Before a planned change, the zone administrator can lower the TTL, and raise it again after the change <Cite n={2} />.

A server can also say that a name does not exist. This is response code 3, "Name Error", and only an authoritative server gives it <Cite n={3} />. A resolver may cache this answer for a TTL too <Cite n={2} />.

</Technical>

<Bangla>

একটা DNS উত্তর তৈরি হয় **resource record** দিয়ে। Tester-রা সবচেয়ে বেশি এই type-গুলোর মুখোমুখি হয় <Cite n={3} />:

- A: একটা host address।
- NS: zone-এর একটা authoritative name server।
- CNAME: একটা alias-এর canonical (আসল) নাম।
- MX: একটা mail exchange। এটা সেই host যে নামটার mail নেয়।
- TXT: text string।
- PTR: একটা domain name pointer। এটা reverse lookup-এ ব্যবহার হয়।

একটা MX record-এ একটা preference number থাকে। কম সংখ্যা বেশি পছন্দের <Cite n={3} />। TXT-এর text-এর মানে ঠিক করে যে domain সেটা ধরে রাখে সে <Cite n={3} />। CNAME record আছে এমন নামে অন্য কোনো record type থাকে না, কিছু DNSSEC record ছাড়া <Cite n={4} />। একটা NS record-এর মান alias হওয়া চলবে না। একটা MX record-এর host-ও alias হওয়া চলবে না <Cite n={4} />।

প্রতিটা record-এর একটা **TTL** (time to live) আছে। এটা একটা cache কতক্ষণ record রাখতে পারবে তার সময়সীমা <Cite n={2} />। এটা সেকেন্ডের সংখ্যা <Cite n={5} />, 0 থেকে 2147483647 পর্যন্ত <Cite n={4} />। TTL 0 হলে cache করা নিষেধ <Cite n={2} />। TTL একটা সর্বোচ্চ সীমা, প্রতিশ্রুতি নয়, কারণ একটা cache কম সীমা ব্যবহার করতে পারে <Cite n={4} />। পরিকল্পিত পরিবর্তনের আগে zone administrator TTL কমাতে পারেন। পরিবর্তনের পর তিনি আবার বাড়াতে পারেন <Cite n={2} />।

একটা server এটাও বলতে পারে যে একটা নাম নেই। এটা response code 3, "Name Error"। শুধু একটা authoritative server এটা দেয় <Cite n={3} />। একটা resolver এই উত্তরও একটা TTL পর্যন্ত cache করতে পারে <Cite n={2} />।

## A real-life example

<Voices>
<Technical>

A learning platform moves its site to a new server. The old address is `203.0.113.10` and the new one is `203.0.113.20`. The A record for `learn.example.com` has a TTL of 86400 seconds (one day).

The team changes the A record to the new address. Some students still reach the old server for hours, because their resolvers keep the old answer until the TTL ends. Nothing is broken. The design of DNS (RFC 1034, section 2.3) says that access to information is more critical than instant updates, and that updates spread out slowly <Cite n={2} />. A careful team lowers the TTL days before the move and raises it again after <Cite n={2} />.

</Technical>
<Layman>

A learning platform moves its site to a new server. The old address is `203.0.113.10`. The new one is `203.0.113.20`. The A record for `learn.example.com` has a TTL of 86400 seconds (one day).

The team changes the A record to the new address. Some students still reach the old server for hours. Their resolvers keep the old answer until the TTL ends. Nothing is broken. The design of DNS (RFC 1034, section 2.3) says that access to information is more critical than instant updates. It says that updates spread out slowly <Cite n={2} />. A careful team lowers the TTL days before the move. It raises the TTL again after the move <Cite n={2} />.

</Layman>
<Bangla>

একটা learning platform তার site নতুন server-এ সরায়। পুরোনো address `203.0.113.10`। নতুনটা `203.0.113.20`। `learn.example.com`-এর A record-এর TTL 86400 seconds (এক দিন)।

দল A record নতুন address-এ বদলায়। কিছু student কয়েক ঘণ্টা পর্যন্ত পুরোনো server-এই পৌঁছায়। TTL শেষ না হওয়া পর্যন্ত তাদের resolver পুরোনো উত্তর রাখে। কিছুই ভাঙেনি। DNS-এর design (RFC 1034, section 2.3) বলে, information-এ access তাৎক্ষণিক update-এর চেয়ে বেশি জরুরি। এটা বলে যে update ধীরে ছড়ায় <Cite n={2} />। একটা সতর্ক দল সরানোর কয়েক দিন আগে TTL কমায়। সরানোর পর তারা TTL আবার বাড়ায় <Cite n={2} />।

</Bangla>

## Common mistakes

<Voices>
<Technical>

- **Waiting for the change to be visible at once.** A changed record reaches users only after the old copies expire <Cite n={2} />.
- **Using a CNAME next to other records.** It is not allowed <Cite n={4} />.
- **Pointing an MX or NS record at an alias.** The specification says this must not be done <Cite n={4} />.
- **Testing on a cached answer.** You may see the old address and think the new one is wrong.

</Technical>
<Layman>

- **Waiting for the change to be visible at once.** A changed record reaches users only after the old copies expire <Cite n={2} />.
- **Using a CNAME next to other records.** It is not allowed <Cite n={4} />.
- **Pointing an MX or NS record at an alias.** The specification says this must not be done <Cite n={4} />.
- **Testing on a cached answer.** You may see the old address and think the new one is wrong.

</Layman>
<Bangla>

- **পরিবর্তন সঙ্গে সঙ্গে দেখা যাবে বলে অপেক্ষা করা।** বদলানো record user-দের কাছে পৌঁছায় পুরোনো copy-গুলোর মেয়াদ শেষ হওয়ার পর <Cite n={2} />।
- **অন্য record-এর পাশে CNAME ব্যবহার করা।** এটা অনুমোদিত নয় <Cite n={4} />।
- **MX বা NS record-কে alias-এর দিকে নির্দেশ করানো।** Specification বলে এটা করা চলবে না <Cite n={4} />।
- **Cache করা উত্তরে test করা।** আপনি পুরোনো address দেখতে পারেন এবং ভাবতে পারেন নতুনটা ভুল।

</Bangla>
</Voices>

## What a tester can check

<Voices>
<Technical>

<Callout type="tip" title="Tutorial advice">
These test ideas are the tutorial's own advice.

- **Look up the record.** Use a tool such as `dig` or `nslookup` on the test host name. Check the address, the record type, and the TTL.
- **Watch the TTL.** Ask twice, a few seconds apart. The TTL in the answer should count down.
- **Plan a switch.** Before a release that changes an address, ask when the TTL was lowered.
- **Bad names.** Open a host name that does not exist. The app should show a clear error.
- **Different networks.** Test from two networks. Their resolvers may hold different cached answers.
</Callout>

</Technical>
