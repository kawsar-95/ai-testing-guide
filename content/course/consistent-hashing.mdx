# Consistent Hashing

Think of a library with four rooms, where each book goes to the room that its code points to. If the library opens a fifth room and changes the rule, almost every book must move. Consistent hashing is a rule that keeps most books where they are.

<PageMeta />

## In plain words

A **hash function** turns a key (such as a user id) into a number. A simple way to pick a server is to take that number modulo the number of servers. The weak point is a change in the server count. With a plain modulo hash, almost every item hashes to a new place when the range changes, and cached data becomes useless <Cite n={1} />. Cassandra's documentation says the same: adding one node can invalidate almost all mappings <Cite n={3} />.

**Consistent hashing** is a hash scheme that changes minimally when the set of buckets (servers) changes <Cite n={1} />. Changing the bucket set a little does not remap all the items <Cite n={1} />. When the number of nodes changes, only a small fraction of the keys must move <Cite n={3} />.

## When you need it

You need it when data or cache entries are spread over many servers, and servers join or leave from time to time. The original paper was about caches for the web <Cite n={1} />. Amazon's Dynamo key-value store uses it to spread data over its storage hosts <Cite n={2} />. Apache Cassandra uses it to split data over its nodes <Cite n={3} />.

## How it works

Dynamo describes the idea this way. The values that the hash function can give are laid out as a fixed circle, a **ring**, where the largest value wraps around to the smallest <Cite n={2} />. Each node gets a random value in this space, which is its position on the ring <Cite n={2} />. To store a key, you hash the key to a position, then walk the ring clockwise to the first node with a larger position <Cite n={2} />. Each node is then responsible for the region between it and the node before it <Cite n={2} />.

Cassandra uses the same walk, and calls the ring positions **tokens** <Cite n={3} />. For replication, it keeps walking until it meets as many distinct nodes as the replication factor: with a factor of 3, it walks to three distinct nodes, and these hold the replicas <Cite n={3} />.

```text
Tutorial example: positions 0 to 99. Clockwise means "up", and 99 wraps to 0.

  0        10(A)        40(B)        70(C)        90(D)      99
  |---------|------------|------------|------------|----------|
  keys 91-99, 0-10 -> A    11-40 -> B   41-70 -> C   71-90 -> D

A new server E joins at position 55:

  0        10(A)        40(B)   55(E)   70(C)        90(D)   99
  keys 41-55 move from C to E.  All other keys stay where they were.
```

### Why few keys move

In the example above, the ring and the positions are the tutorial's own. When E joins, only the keys between B and E change owner. This is the rule that Dynamo states: the arrival or departure of a node affects only its immediate neighbors, and the other nodes stay unaffected <Cite n={2} />. The paper names a related rule, **monotonicity**: when new buckets are added, an item can move to a new bucket, but never between two old buckets <Cite n={1} />. The paper also describes a **smoothness** goal: when a machine joins or leaves, the expected share of objects that move is the minimum needed to keep the load balanced <Cite n={1} />.

### Virtual nodes

The basic ring has two weak points. Random positions give uneven data and load, and the basic scheme ignores the fact that nodes differ in performance <Cite n={2} />. The fix in Dynamo is **virtual nodes**: a node is not one point on the ring but several points, which Dynamo calls tokens <Cite n={2} />. A virtual node looks like one node to the rest of the system <Cite n={2} />.

The Dynamo paper lists these benefits <Cite n={2} />:

- When a node is unavailable, its load is spread over the other nodes.
- A new or returning node takes about the same share of work from every other node.
- The number of virtual nodes of a machine can follow its capacity.

Cassandra adds a view from the small cluster. With few nodes and evenly spaced tokens, it is hard to add just one node and keep the ring balanced <Cite n={3} />. With a node that owns many tokens, a new node takes many small pieces of data from many neighbors <Cite n={3} />. The Karger paper also gives each bucket more than one point on its unit interval <Cite n={1} />.

Many tokens have a cost. Each token adds up to 2 x (RF - 1) neighbors on the ring, so more combinations of node failures can make part of the ring unavailable, and cluster maintenance can be slower <Cite n={3} />.

## A real-life example

A test team runs a cache with four servers. Tutorial example, with simple numbers: keys have the hash values 0 to 19. With the rule "hash modulo 4", a fifth server changes the rule to "hash modulo 5". Only 4 of these 20 keys (hash values 0 to 3) land on the same server as before. The other 16 keys, 80 %, move, and a cache looks empty for them.

With a ring, as in the diagram, adding the fifth server moves only the keys that fall between its neighbor and its own position. The team sees a few misses and not a full cold cache.

## Common mistakes

- **Using hash modulo N and thinking the cache survives a resize.** A change of N moves almost all keys <Cite n={1} />.
- **Expecting a perfect balance from one point per node.** Random positions give uneven load <Cite n={2} />.
- **Adding many tokens without a limit.** More tokens raise the number of ring neighbors and the chance of an outage <Cite n={3} />.
- **Treating the ring as a safety net.** The ring decides where a key lives. It does not copy data. Replication is a separate step <Cite n={3} />.

## What a tester can check

<Callout type="tip" title="Tutorial advice">
These test ideas are the tutorial's own advice.

- **Count the moved keys.** Store a known set of keys. Add one node. Check that most keys keep their owner and that only a small share moves.
- **Remove a node.** Check that reads for its keys still work, from the node that now owns that range.
- **Check the balance.** Count keys for each node. A big gap may point to a poor token setup.
- **Test during the change.** Read and write while a node joins, and look for misses and errors.
</Callout>

## Key words

| Word | Meaning |
|---|---|
| Consistent hashing | A hash scheme that changes minimally when the set of buckets changes <Cite n={1} /> |
| Ring | The hash range as a circle, where the largest value wraps to the smallest <Cite n={2} /> |
| Token | One position of a node on the ring <Cite n={3} /> |
| Virtual node (vnode) | One of several ring positions that a physical node owns <Cite n={3} /> |
| Token range | A range of keys that maps to the same set of nodes <Cite n={3} /> |
| Replication factor (RF) | The number of nodes that hold a copy of a key <Cite n={3} /> |
