# SQL vs NoSQL

Two shops can sell the same goods and keep their records in different ways. One keeps strict ledgers with fixed columns. The other keeps a folder for each customer, and each folder can hold different papers. Neither way is better for every shop.

<PageMeta />

## In plain words

<Voices>
<Technical>

A **relational** (SQL) database keeps data in tables with rows and columns. The columns hold attributes, and the rows hold values <Cite n={1} />. A key links rows of one table to rows of another table, and one SQL query can read both <Cite n={1} />.

A **non-relational** (NoSQL) database uses other data models. The common ones are key-value, document, and graph <Cite n={1} />. A document database stores JSON-like objects that can have a nested shape <Cite n={1} />.

The names are a simplification. "NoSQL" names a group of systems with many data models <Cite n={1} />, and they are not all alike. So the useful question is not "which one wins" but "what does my data look like, and how will the application read it".

</Technical>
<Layman>

A **non-relational** (NoSQL) database uses other data models. The common ones are key-value, document, and graph <Cite n={1} />. A document database stores JSON-like objects. These objects can have a nested shape <Cite n={1} />.

The names are a simplification. "NoSQL" names a group of systems with many data models <Cite n={1} />. They are not all alike. So do not ask "which one wins". Ask "what does my data look like, and how will the application read it".

</Layman>
<Bangla>

**Relational** (SQL) database data রাখে table-এ, যেখানে row আর column থাকে। Column-এ থাকে attribute, আর row-তে থাকে value <Cite n={1} />। একটি key এক table-এর row-কে অন্য table-এর row-এর সঙ্গে যুক্ত করে। একটি SQL query দুটোই পড়তে পারে <Cite n={1} />।

**Non-relational** (NoSQL) database অন্য data model ব্যবহার করে। সাধারণ model হলো key-value, document আর graph <Cite n={1} />। Document database JSON-এর মতো object রাখে। এই object-এর গঠন nested হতে পারে <Cite n={1} />।

নাম দুটি একটি সরলীকরণ। "NoSQL" অনেক data model-এর একদল system-কে বোঝায় <Cite n={1} />। সেগুলো সব একরকম নয়। তাই "কোনটি জিতবে" জিজ্ঞেস করবেন না। জিজ্ঞেস করুন, "আমার data দেখতে কেমন, আর application কীভাবে তা পড়বে"।

</Bangla>
</Voices>

## A real-life example

<Voices>
<Technical>

A learning platform stores students, courses, and enrollments.

- **Enrollments and payments.** Each student row links to course rows, and a failed payment must not leave half an enrollment. This fits a relational design with keys and transactions.
- **Course catalog pages.** Each course has different fields: a video course has a length, a lab course has a tool list. A document database can keep each course as one document with its own fields.

The platform can use both. This example is the tutorial's own.

</Technical>

Platform দুটোই ব্যবহার করতে পারে। এই উদাহরণ টিউটোরিয়ালের নিজস্ব।

## Trade-offs

<Voices>
<Technical>

The choice depends on the data and on the access pattern. The table shows where the vendor docs say the two sides differ.

| Question | Relational (SQL) | Non-relational (NoSQL) |
|---|---|---|
| Structure | Tables with strict rules for data and relations <Cite n={1} /> | More flexible, for data that changes <Cite n={1} /> |
| Schema | Set before you insert data <Cite n={4} /> | Documents in one collection can have different fields <Cite n={4} /> |
| Rules in the database | Constraints such as primary key, foreign key, unique, check, and not-null <Cite n={2} /> | In MongoDB, optional validation rules, added where you need them <Cite n={4} /><Cite n={5} /> |
| Transactions | Several steps are all-or-nothing <Cite n={3} /> | In MongoDB, a single-document write is atomic. Multi-document transactions exist too, with a performance cost in most cases <Cite n={6} /> |
| Consistency model | Strict ACID <Cite n={1} /> | Often BASE, with eventual consistency <Cite n={1} /> |
| Scaling | Usually vertical. Horizontal scaling of writes needs partitioning or sharding <Cite n={1} /> | Spread the load across many nodes more easily <Cite n={1} /> |
| Related data | Joins across tables <Cite n={4} /> | In MongoDB, embed related data, or reference it <Cite n={4} /> |

Three points need care:

- **No side is "all or nothing" on integrity.** Some NoSQL databases offer ACID, with trade-offs in performance or other areas <Cite n={1} />. MongoDB supports ACID transactions <Cite n={6} />.
- **A flexible schema is not a missing schema.** MongoDB lets you add validation rules to a collection. By default it rejects an insert or update that breaks them <Cite n={5} />.
- **The model follows the access pattern.** MongoDB advises to design the model from the access patterns of the application, and to keep together the data that is accessed together <Cite n={4} />.

A rule of thumb, the tutorial's own: if your data is stable and its relations matter, start with relational. If the shape varies or one very large workload must spread over many nodes, look at NoSQL. Treat this as a first guess, not a rule.

</Technical>

- **Structure.** Relational: tables with strict rules for data and relations <Cite n={1} />. NoSQL: more flexible, for data that changes <Cite n={1} />.

</Layman>
<Bangla>

বাছাই নির্ভর করে data আর access pattern-এর উপর। এই তালিকা দেখায়, vendor docs অনুযায়ী দুই পক্ষ কোথায় আলাদা। প্রতিটি বিষয়ে আগে relational পক্ষ, তারপর non-relational পক্ষ দেওয়া হলো।

- **গঠন।** Relational: data আর সম্পর্কের জন্য কঠোর নিয়মের table <Cite n={1} />। NoSQL: বদলাতে থাকা data-র জন্য আরও নমনীয় <Cite n={1} />।
- **Schema।** Relational: data insert করার আগে এটি ঠিক করতে হয় <Cite n={4} />। NoSQL: একই collection-এর document-এ আলাদা field থাকতে পারে <Cite n={4} />।
- **Database-এর নিয়ম।** Relational: primary key, foreign key, unique, check আর not-null-এর মতো constraint <Cite n={2} />। NoSQL: MongoDB-তে ঐচ্ছিক validation rule, যা আপনি যেখানে দরকার সেখানে যোগ করেন <Cite n={4} /><Cite n={5} />।
- **Transaction।** Relational: কয়েকটি ধাপ সব-অথবা-কিছুই-নয় (all-or-nothing) <Cite n={3} />। NoSQL: MongoDB-তে একটি single-document write atomic। Multi-document transaction-ও আছে, বেশিরভাগ ক্ষেত্রে performance-এর খরচ সহ <Cite n={6} />।
- **Consistency model।** Relational: কঠোর ACID <Cite n={1} />। NoSQL: প্রায়ই BASE, eventual consistency সহ <Cite n={1} />।
- **Scaling।** Relational: সাধারণত vertical। Write-এর horizontal scaling-এ partitioning বা sharding লাগে <Cite n={1} />। NoSQL: load অনেক node-এ আরও সহজে ছড়িয়ে দেয় <Cite n={1} />।
- **সম্পর্কিত data।** Relational: table জুড়ে join <Cite n={4} />। NoSQL: MongoDB-তে সম্পর্কিত data embed করুন, অথবা reference করুন <Cite n={4} />।

তিনটি বিষয়ে সতর্ক থাকতে হবে:

- **Integrity-র ক্ষেত্রে কোনো পক্ষই "সব অথবা কিছুই নয়" নয়।** কিছু NoSQL database ACID দেয়, তবে performance বা অন্য ক্ষেত্রে কিছু ছাড় দিয়ে <Cite n={1} />। MongoDB ACID transaction সমর্থন করে <Cite n={6} />।
- **নমনীয় schema মানে schema নেই, তা নয়।** MongoDB আপনাকে একটি collection-এ validation rule যোগ করতে দেয়। ডিফল্টভাবে এই rule ভাঙে এমন insert বা update সে প্রত্যাখ্যান করে <Cite n={5} />।
- **Model অনুসরণ করে access pattern।** MongoDB পরামর্শ দেয়, application-এর access pattern থেকে model ঠিক করুন। এটি আরও পরামর্শ দেয়, যে data একসঙ্গে access করা হয়, তা একসঙ্গে রাখুন <Cite n={4} />।

একটি মোটামুটি নিয়ম (rule of thumb), টিউটোরিয়ালের নিজস্ব: আপনার data স্থির হলে এবং তার সম্পর্ক গুরুত্বপূর্ণ হলে relational দিয়ে শুরু করুন। গঠন একেক রকম হলে, বা একটি খুব বড় workload অনেক node-এ ছড়াতে হলে, NoSQL দেখুন। এটিকে প্রথম অনুমান হিসেবে নিন, নিয়ম হিসেবে নয়।

</Bangla>

## Common mistakes

<Voices>
<Technical>

- **Choosing by fashion.** Pick from the data and the queries, not from a trend.
- **Thinking a flexible schema means no rules.** In MongoDB you can add validation rules <Cite n={5} />. Without them, the application must keep the data in shape. This second point is the tutorial's own advice.
- **Thinking SQL cannot scale.** The vendor says it needs extra strategies for write scaling, not that it cannot <Cite n={1} />.
- **Using one rule for every service.** One system can use a relational database for some data and a document database for other data.
- **Assuming a transaction works the same everywhere.** Check what the chosen database guarantees <Cite n={6} />.

</Technical>
<Layman>

- **Choosing by fashion.** Pick from the data and the queries, not from a trend.
- **Thinking a flexible schema means no rules.** In MongoDB you can add validation rules <Cite n={5} />. Without them, the application must keep the data in shape. This second point is the tutorial's own advice.
- **Thinking SQL cannot scale.** The vendor says it needs extra strategies for write scaling, not that it cannot <Cite n={1} />.
- **Using one rule for every service.** One system can use a relational database for some data and a document database for other data.
- **Assuming a transaction works the same everywhere.** Check what the chosen database guarantees <Cite n={6} />.

</Layman>
<Bangla>

- **ফ্যাশন দেখে বাছাই করা।** Data আর query দেখে বাছাই করুন, trend দেখে নয়।
- **নমনীয় schema মানে কোনো নিয়ম নেই, এমন ভাবা।** MongoDB-তে আপনি validation rule যোগ করতে পারেন <Cite n={5} />। সেগুলো না থাকলে application-কে data ঠিক গঠনে রাখতে হবে। এই দ্বিতীয় কথাটি টিউটোরিয়ালের নিজস্ব পরামর্শ।
- **SQL scale করতে পারে না, এমন ভাবা।** Vendor বলে, write scaling-এর জন্য তার বাড়তি কৌশল লাগে, এমন নয় যে সে পারে না <Cite n={1} />।
- **সব service-এ একই নিয়ম ব্যবহার করা।** একটি system কিছু data-র জন্য relational database আর অন্য data-র জন্য document database ব্যবহার করতে পারে।
- **ধরে নেওয়া যে transaction সব জায়গায় একইভাবে কাজ করে।** বেছে নেওয়া database কী নিশ্চিত করে, তা যাচাই করুন <Cite n={6} />।

</Bangla>

## What a tester can check

<Voices>
<Technical>

<Callout type="tip" title="Tutorial advice">
These test ideas are the tutorial's own advice.

- **Ask which promises the database keeps.** Is a multi-step change all-or-nothing, or does the application handle it?
- **Try bad data.** Insert a missing value, a wrong type, or a duplicate. See whether the database or the application rejects it.
- **Test old data.** In a flexible schema, old records may lack new fields. Open one.
- **Test stale reads.** With eventual consistency, read right after a write, from another connection. Check what the user sees.
- **Test a failure halfway.** Stop a multi-step change in the middle. Look for half-saved data.
</Callout>

</Technical>

These test ideas are the tutorial's own advice.

- **Ask which promises the database keeps.** Is a multi-step change all-or-nothing, or does the application handle it?
- **Try bad data.** Insert a missing value, a wrong type, or a duplicate. See whether the database or the application rejects it.
- **Test old data.** In a flexible schema, old records may lack new fields. Open one.
- **Test stale reads.** With eventual consistency, read right after a write, from another connection. Check what the user sees.

<Bangla>

এই test-এর ধারণাগুলো টিউটোরিয়ালের নিজস্ব পরামর্শ।

- **জিজ্ঞেস করুন database কোন প্রতিশ্রুতি রাখে।** একটি বহু-ধাপের পরিবর্তন কি all-or-nothing, নাকি application তা সামলায়?
- **খারাপ data দিয়ে চেষ্টা করুন।** একটি অনুপস্থিত value, ভুল type, বা duplicate insert করুন। দেখুন database প্রত্যাখ্যান করে, নাকি application।
- **পুরনো data test করুন।** নমনীয় schema-তে পুরনো record-এ নতুন field না-ও থাকতে পারে। একটি খুলে দেখুন।
- **Stale read test করুন।** Eventual consistency থাকলে write-এর ঠিক পরে অন্য connection থেকে পড়ুন। user কী দেখে তা যাচাই করুন।
- **মাঝপথে failure test করুন।** একটি বহু-ধাপের পরিবর্তন মাঝখানে থামিয়ে দিন। অর্ধেক-সংরক্ষিত data খুঁজুন।

</Bangla>

## Key words

| Word | Meaning |
|---|---|
| Relational database | Stores data in tables with rows and columns, linked by keys <Cite n={1} /> |
| NoSQL | A group of non-relational models, such as key-value, document, and graph <Cite n={1} /> |
| Schema | The structure of the data (the tutorial's own plain definition). A relational table sets it before inserts <Cite n={4} /> |
| Constraint | A rule that the database enforces on a column or table <Cite n={2} /> |
| Transaction | Several steps that act as one all-or-nothing operation <Cite n={3} /> |
| Eventual consistency | The state changes over time and later becomes consistent <Cite n={1} /> |
