# Enterprise Service Bus

A large company has an old billing system that speaks one data format, a new web shop that speaks another, and a partner system that uses a third. Wiring each pair by hand takes a lot of work. One idea is to put a single hub in the middle that translates and delivers every message. That hub is an enterprise service bus.

<PageMeta />

## In plain words

An enterprise service bus (ESB) is a design pattern. One centralized software component performs the integrations between applications <Cite n={1} />. Applications connect to the ESB. The ESB then handles the rest <Cite n={1} />.

IBM lists these jobs of an ESB <Cite n={1} />:

| Job | What it means |
|---|---|
| Transformation | Change data from the model of one application to the model of another |
| Connectivity | Handle the link to each application |
| Routing | Send each message to the right place |
| Protocol conversion | Change one way of communicating into another |
| Composition | Possibly manage several requests as one |

The ESB can also offer these integrations as a service interface that new applications reuse <Cite n={1} />. Teams usually build the pattern with an ESB product, which is an integration runtime and a set of tools <Cite n={1} />.

The ESB belongs to service-oriented architecture (SOA), which appeared in the late 1990s. SOA makes software components reusable through service interfaces <Cite n={1} />. These interfaces give loose coupling: a caller needs little knowledge of how the service is built <Cite n={1} />. Services often use standard protocols such as SOAP over HTTP or JSON over HTTP <Cite n={1} />.

## When you need it

IBM names the problem that an ESB solves. Without it, each application owner connects directly to every service it needs and does its own data transformation. That is a lot of work, and because each link is point to point, it is hard to maintain later <Cite n={1} />.

An ESB also helps with old systems. A team can connect to a legacy system through an adapter or connector. The ESB then shields the new application from the old interface and does the transformation and routing <Cite n={1} />. IBM says the approach supports linking applications, linking data, and automating business processes by orchestrating services <Cite n={1} />.

## A real-life example

This example is the tutorial's own. A school has a student record system from 2005, a new mobile app, and an exam platform. All three need the same student data, but each wants a different format.

With an ESB, the mobile app sends one request to the bus. The bus calls the old system through an adapter, turns the answer into the format the app wants, and returns it. If the exam platform later needs the same data, it asks the bus too. Nobody writes a new direct link to the old system.

## Trade-offs

IBM says that in theory a central ESB can standardize and simplify communication across the enterprise. Costs can be shared, and one team of specialists can build and maintain the integrations <Cite n={1} />. Developers can then spend less time on integration <Cite n={1} />.

IBM also says the picture was mixed. Many organizations deployed ESBs with success. In many others people saw the ESB as a bottleneck <Cite n={1} />. IBM gives these reasons:

- A change to one integration could destabilize other integrations that used it <Cite n={1} />.
- Updates to the ESB middleware often affected existing integrations, so each update needed a lot of testing <Cite n={1} />.
- The ESB was centrally managed, so application teams waited in line for their integrations <Cite n={1} />.
- As integrations grew, keeping the ESB servers highly available and recoverable after a disaster cost more <Cite n={1} />.
- A cross-enterprise project was hard to fund <Cite n={1} />.

IBM states that the work of maintaining, updating, and scaling a central ESB often proved so large and costly that it delayed the gains that the ESB and SOA were meant to bring <Cite n={1} />.

## ESB and microservices

IBM compares the ESB with microservices. A microservices architecture splits one application into small pieces that teams can change, scale, and administer on their own <Cite n={1} />. Azure Architecture Center describes microservices as small, autonomous services. Each service is a separate codebase, deploys on its own, keeps its own data, and talks to others through well-defined APIs <Cite n={2} />. Its advice is to decentralize everything, so that individual teams design and build services end to end <Cite n={2} />.

IBM applies the same idea to integration. It calls this agile integration: split the ESB into small, decentralized integration parts that application teams own and manage <Cite n={1} />. Azure lists message-oriented middleware as a component of a typical microservices architecture. It names Apache Kafka and Azure Service Bus as platforms for asynchronous communication with loose coupling <Cite n={2} />.

Decentralized design has its own costs. Azure lists more moving parts, more interservice communication, a risk of weak governance, and harder testing of service dependencies <Cite n={2} />. The tutorial's own view: a decentralized design does not remove the problems of integration. It moves them to different places.

## Common mistakes

- **Treating the ESB as free glue.** A central hub is one more system to run, fund, and test <Cite n={1} />.
- **Putting too much in the middle.** An ESB can transform, route, and compose requests <Cite n={1} />. When one team owns all of it, other teams may wait for changes <Cite n={1} />.
- **Mixing up names.** The name "Azure Service Bus" sounds like an ESB. Azure describes it as a messaging platform for asynchronous communication <Cite n={2} />. The tutorial's own advice: read what a product does, and do not trust its name.
- **Saying the ESB failed everywhere.** IBM says many organizations used ESBs with success <Cite n={1} />.

## What a tester can check

<Callout type="tip" title="Tutorial advice">
These test ideas are the tutorial's own advice, not a claim of the sources.

- **Test each route.** For every path through the bus, send a sample message and check that it reaches the right system.
- **Test the transformation.** Compare the data before and after the bus. Look for lost fields, changed dates, and wrong number formats.
- **Test the adapters.** Send bad input and a slow reply from a legacy system. Check the error that the caller sees.
- **Plan for change.** When the bus or one integration changes, run the tests for the other integrations that share it. Shared parts can break each other.
- **Ask who owns it.** Find out which team owns each integration, so you know where a defect goes.
</Callout>

## Key words

| Word | Meaning |
|---|---|
| Enterprise service bus (ESB) | A pattern in which one central component performs integrations between applications <Cite n={1} /> |
| SOA | Service-oriented architecture: reusable components with service interfaces <Cite n={1} /> |
| Message routing | Sending a message to the right target <Cite n={1} /> |
| Protocol conversion | Changing one communication protocol into another <Cite n={1} /> |
| Adapter or connector | A part that links the ESB to a legacy system <Cite n={1} /> |
| Point to point | A direct link between two applications, one link for each pair <Cite n={1} /> |
| Agile integration | Breaking the ESB into small, decentralized integration parts that app teams own <Cite n={1} /> |
| Microservices | Small, autonomous services; each one should cover a single business capability inside its own bounded context <Cite n={2} /> |
