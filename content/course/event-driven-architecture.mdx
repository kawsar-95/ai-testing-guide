# Event-Driven Architecture

A shop takes an order. Payment, stock, email, and delivery must all react. The order service could call each of them one by one, or it could shout "order placed" once and let each of them listen. The second way is an event-driven architecture.

<PageMeta />

## In plain words

<Voices>
<Technical>

An event is a change in state, such as an item put in a shopping cart <Cite n={2} />. An event can carry the data (the item, its price, the address), or it can be only an identifier, such as a notice that an order shipped <Cite n={2} />.

An event-driven architecture has three parts <Cite n={1} /> <Cite n={2} />:

| Part | Job |
|---|---|
| Event producer | Creates the events |
| Event router, broker, or channel | Moves events from producers to consumers. AWS says the router filters events and pushes them to consumers <Cite n={2} />. |
| Event consumer | Listens for events and acts on them |

Events arrive in near real time, so consumers can react at once <Cite n={1} />. A producer does not know which consumers listen, and consumers are decoupled from each other <Cite n={1} />. Because services know only the router and not each other, one service can fail while the others keep running <Cite n={2} />. Producers and consumers can be scaled, updated, and deployed on their own <Cite n={2} />.

</Technical>

ইভেন্ট (event) হলো স্টেটের একটি পরিবর্তন, যেমন শপিং কার্টে একটি আইটেম রাখা <Cite n={2} />। একটি ইভেন্ট ডেটা বহন করতে পারে (আইটেম, তার দাম, ঠিকানা)। এটি শুধু একটি আইডেন্টিফায়ারও হতে পারে, যেমন একটি অর্ডার পাঠানো হয়েছে এমন নোটিশ <Cite n={2} />।

ইভেন্ট-ড্রিভেন আর্কিটেকচারের তিনটি অংশ <Cite n={1} /> <Cite n={2} />:

- ইভেন্ট প্রোডিউসার (event producer) ইভেন্ট তৈরি করে।
- ইভেন্ট রাউটার, ব্রোকার বা চ্যানেল (event router, broker, channel) ইভেন্টকে প্রোডিউসার থেকে কনজিউমারের কাছে নিয়ে যায়। AWS বলে, রাউটার ইভেন্ট ফিল্টার করে এবং কনজিউমারের কাছে পুশ করে <Cite n={2} />।
- ইভেন্ট কনজিউমার (event consumer) ইভেন্ট শোনে এবং সে অনুযায়ী কাজ করে।

ইভেন্ট প্রায় রিয়েল টাইমে আসে, তাই কনজিউমার সাথে সাথে সাড়া দিতে পারে <Cite n={1} />। প্রোডিউসার জানে না কোন কনজিউমার শুনছে। কনজিউমাররা একে অপরের থেকে ডিকাপলড (decoupled) <Cite n={1} />। সার্ভিস শুধু রাউটারকে চেনে, একে অপরকে নয়। তাই একটি সার্ভিস ফেইল করলেও বাকিগুলো চলতে থাকে <Cite n={2} />। টিমগুলো প্রোডিউসার ও কনজিউমারকে নিজেরাই স্কেল, আপডেট ও ডিপ্লয় করতে পারে <Cite n={2} />।

## When you need it

<Voices>
<Technical>

Azure lists these cases <Cite n={1} />:

- Several subsystems must process the same events.
- You need real-time processing with little delay.
- You need to find patterns in events, for example over a time window.
- Data comes in high volume and speed, as with IoT.
- You want to decouple producers and consumers so each can scale and stay reliable on its own.

AWS names these uses: copying data between accounts and regions, watching resource state and sending alerts, sending one event to many systems at once (fanout), and joining systems that run on different stacks <Cite n={2} />.

The style may not fit when simple synchronous calls already meet your needs, when a business transaction needs strong consistency across services, or when the team has no experience with distributed asynchronous systems <Cite n={1} />.

</Technical>

এই ক্ষেত্রগুলোতে স্টাইলটি নাও মানাতে পারে <Cite n={1} />:

- সহজ সিঙ্ক্রোনাস কলই আপনার প্রয়োজন মেটায়।
- একটি বিজনেস ট্রানজেকশনের জন্য সার্ভিসগুলোর মধ্যে শক্তিশালী কনসিসটেন্সি দরকার।
- টিমের ডিস্ট্রিবিউটেড অ্যাসিঙ্ক্রোনাস সিস্টেমের অভিজ্ঞতা নেই।

## How it works

<Voices>
<Technical>

**Two models.** Azure describes two models for this style: publish-subscribe and event streaming <Cite n={1} />. A sibling page covers [publish-subscribe](/course/pub-sub/) in more detail.

- In publish-subscribe, the infrastructure tracks subscriptions and sends each published event to every subscriber. The event is not kept in a durable log, so a new subscriber does not see past events <Cite n={1} />.
- In event streaming, events go into a log. They are strictly ordered within a partition and they are durable. Clients do not subscribe. A client reads from any part of the stream and moves its own position, so it can join late and replay events <Cite n={1} />. Replay helps with recovery, late consumers, and reprocessing after a bug fix <Cite n={1} />.

Azure also contrasts this with the Competing Consumers pattern. There, consumers pull messages from a queue, and each message is processed one time if there are no errors <Cite n={1} />.

**Router types.** AWS says there are two main kinds of router: event buses and event topics <Cite n={2} />. A router is also a central place to audit the system and to set policies about who may publish and subscribe. Events can be encrypted in transit and at rest <Cite n={2} />.

**Two topologies.** In a broker topology, components broadcast events, and others act on them or ignore them. This suits simple flows and has no central control. No component owns the state of a multistep transaction, and there is no built-in way to restart or replay one <Cite n={1} />. In a mediator topology, an event mediator manages the flow, keeps state, and handles errors and restarts. It gives more control, but it adds coupling and can become a bottleneck <Cite n={1} />.

</Technical>

<Bangla>

**দুটি মডেল।** Azure এই স্টাইলের জন্য দুটি মডেল বর্ণনা করে: পাবলিশ-সাবস্ক্রাইব (publish-subscribe) এবং ইভেন্ট স্ট্রিমিং (event streaming) <Cite n={1} />। পাশের একটি পাতা [publish-subscribe](/course/pub-sub/) আরও বিস্তারিত বলে।

- পাবলিশ-সাবস্ক্রাইবে ইনফ্রাস্ট্রাকচার সাবস্ক্রিপশন ট্র্যাক করে এবং প্রতিটি পাবলিশ করা ইভেন্ট সব সাবস্ক্রাইবারের কাছে পাঠায়। ইভেন্ট কোনো টেকসই লগে (durable log) রাখা হয় না। তাই নতুন সাবস্ক্রাইবার আগের ইভেন্ট দেখে না <Cite n={1} />।
- ইভেন্ট স্ট্রিমিংয়ে ইভেন্ট একটি লগে যায়। এগুলো একটি পার্টিশনের মধ্যে কঠোরভাবে ক্রমানুযায়ী থাকে এবং টেকসই হয়। ক্লায়েন্ট সাবস্ক্রাইব করে না। ক্লায়েন্ট স্ট্রিমের যেকোনো অংশ থেকে পড়ে এবং নিজের অবস্থান নিজে সরায়। তাই সে দেরিতে যোগ দিতে এবং ইভেন্ট রিপ্লে (replay) করতে পারে <Cite n={1} />। রিপ্লে রিকভারি, দেরিতে আসা কনজিউমার এবং বাগ ঠিক করার পর আবার প্রসেস করতে সাহায্য করে <Cite n={1} />।

Azure এটিকে Competing Consumers প্যাটার্নের সাথেও তুলনা করে। সেখানে কনজিউমাররা একটি কিউ থেকে মেসেজ টেনে নেয়। কোনো এরর না হলে প্রতিটি মেসেজ একবার প্রসেস হয় <Cite n={1} />।

**রাউটারের ধরন।** AWS বলে, রাউটারের দুটি প্রধান ধরন আছে: ইভেন্ট বাস (event bus) এবং ইভেন্ট টপিক (event topic) <Cite n={2} />। রাউটার হলো সিস্টেম অডিট করার এবং কে পাবলিশ ও সাবস্ক্রাইব করতে পারবে সেই পলিসি ঠিক করার একটি কেন্দ্রীয় জায়গাও। ইভেন্ট ট্রানজিটে এবং স্টোরেজে এনক্রিপ্ট করা যায় <Cite n={2} />।

**দুটি টপোলজি।** ব্রোকার টপোলজিতে (broker topology) কম্পোনেন্ট ইভেন্ট ব্রডকাস্ট করে। অন্য কম্পোনেন্ট সেগুলোতে সাড়া দেয় বা উপেক্ষা করে। এটি সহজ ফ্লোর জন্য মানানসই এবং এতে কোনো কেন্দ্রীয় নিয়ন্ত্রণ নেই। কোনো কম্পোনেন্ট একাধিক ধাপের ট্রানজেকশনের স্টেটের মালিক নয়। একটি ট্রানজেকশন রিস্টার্ট বা রিপ্লে করার কোনো বিল্ট-ইন উপায় নেই <Cite n={1} />। মিডিয়েটর টপোলজিতে (mediator topology) একটি ইভেন্ট মিডিয়েটর ফ্লো পরিচালনা করে, স্টেট রাখে এবং এরর ও রিস্টার্ট সামলায়। এটি বেশি নিয়ন্ত্রণ দেয়। কিন্তু কাপলিং বাড়ায় এবং বটলনেক হয়ে উঠতে পারে <Cite n={1} />।

## Challenges

<Voices>
<Technical>

These are the challenges that Azure and AWS state.

- **Guaranteed delivery.** In some systems, especially IoT, you must be sure that events are delivered <Cite n={1} />. AWS says the event source should guarantee delivery if you must process every event <Cite n={2} />.
- **Order and one-time processing.** Consumers usually run as many instances. This can cause trouble if events need processing in order, or the processing logic is not idempotent <Cite n={1} />. Azure adds that exactly-once semantics can be a challenge too <Cite n={1} />. To rebuild state, AWS says the event source should be deduplicated and ordered <Cite n={2} />.
- **Data loss.** If a component crashes before it hands the event on, the event is dropped. Azure advises you to keep in-transit events and remove them only after the next component confirms receipt <Cite n={1} />.
- **Eventual consistency.** Data is not at once the same everywhere after an event. For a time, parts of the system see different state, so consumers must tolerate stale data <Cite n={1} />.
- **Error handling.** One option is an error-handler processor. It tries to fix a bad event and resend it, or it sends the event on to a dead-letter queue (DLQ), where an administrator can inspect it. Resent events are processed out of sequence <Cite n={1} />.
- **Seeing the flow.** There is no shared call context, so Azure advises a correlation ID in every event. It also says that end-to-end testing needs more deliberate strategies <Cite n={1} />. AWS adds that you can track the flow by monitoring, not by static code analysis <Cite n={2} />.

</Technical>

Azure ও AWS এই চ্যালেঞ্জগুলোর কথা বলে।

- **গ্যারান্টিযুক্ত ডেলিভারি (guaranteed delivery)।** কিছু সিস্টেমে, বিশেষ করে IoT-তে, ইভেন্ট যে পৌঁছেছে তা নিশ্চিত হতে হয় <Cite n={1} />। AWS বলে, প্রতিটি ইভেন্ট প্রসেস করতে হলে ইভেন্ট সোর্সের ডেলিভারি গ্যারান্টি করা উচিত <Cite n={2} />।
- **ক্রম এবং একবার প্রসেস করা।** কনজিউমার সাধারণত অনেক ইনস্ট্যান্স হিসেবে চলে। ইভেন্ট ক্রমানুযায়ী প্রসেস করতে হলে, বা প্রসেসিং লজিক আইডেমপটেন্ট (idempotent) না হলে, এতে সমস্যা হতে পারে <Cite n={1} />। Azure যোগ করে, এক্সাক্টলি-ওয়ান্স (exactly-once) সেম্যান্টিক্সও একটি চ্যালেঞ্জ হতে পারে <Cite n={1} />। স্টেট আবার তৈরি করতে AWS বলে, ইভেন্ট সোর্স ডিডুপ্লিকেটেড ও ক্রমানুযায়ী হওয়া উচিত <Cite n={2} />।
- **ডেটা লস।** কোনো কম্পোনেন্ট ইভেন্ট এগিয়ে দেওয়ার আগে ক্র্যাশ করলে ইভেন্ট হারিয়ে যায়। Azure পরামর্শ দেয়, ট্রানজিটে থাকা ইভেন্ট রেখে দিন। পরের কম্পোনেন্ট প্রাপ্তি নিশ্চিত করলে তবেই সেগুলো সরান <Cite n={1} />।
- **ইভেন্চুয়াল কনসিসটেন্সি।** ইভেন্টের পর ডেটা সাথে সাথে সব জায়গায় এক হয় না। কিছু সময় সিস্টেমের বিভিন্ন অংশ ভিন্ন স্টেট দেখে। তাই কনজিউমারকে পুরোনো (stale) ডেটা মেনে নিতে হয় <Cite n={1} />।
- **এরর হ্যান্ডলিং।** একটি উপায় হলো এরর-হ্যান্ডলার প্রসেসর। সেটি খারাপ ইভেন্ট ঠিক করে আবার পাঠানোর চেষ্টা করে। অথবা ইভেন্টটিকে একটি ডেড-লেটার কিউতে (dead-letter queue, DLQ) পাঠায়, যেখানে অ্যাডমিনিস্ট্রেটর সেটি পরীক্ষা করতে পারে। আবার পাঠানো ইভেন্ট ক্রমের বাইরে প্রসেস হয় <Cite n={1} />।
- **ফ্লো দেখা।** কোনো শেয়ার করা কল কনটেক্সট নেই, তাই Azure প্রতিটি ইভেন্টে একটি কোরিলেশন ID (correlation ID) রাখার পরামর্শ দেয়। এটি আরও বলে, এন্ড-টু-এন্ড টেস্টিংয়ের জন্য আরও সুচিন্তিত কৌশল দরকার <Cite n={1} />। AWS যোগ করে, আপনি মনিটরিং দিয়ে ফ্লো ট্র্যাক করতে পারেন, স্ট্যাটিক কোড অ্যানালাইসিস দিয়ে নয় <Cite n={2} />।

</Bangla>
</Voices>

## A real-life example

<Voices>
<Technical>

This example is the tutorial's own. An online exam platform publishes an event "exam submitted". The grading service, the email service, and the report service each listen for it. If the email service is down, grading still runs. A new "certificate" service can start listening later, and the exam service does not change.

The cost is that the certificate may appear a few seconds after the grade. Each part sees the event at its own time.

</Technical>

## Common mistakes

<Voices>
<Technical>

- **Assuming one global order.** Several consumer instances may process events in a different order <Cite n={1} />.
- **Treating "delivered" as "processed".** A crash between receive and hand-over can drop an event <Cite n={1} />.
- **Using it for every call.** Simple request-response flows may not justify the extra operating work <Cite n={1} />.
- **Putting private data in events.** Many components can see an event, even those that should not use it <Cite n={1} />.

</Technical>
<Layman>

- **Assuming one global order.** Several consumer instances may process events in a different order <Cite n={1} />.
- **Treating "delivered" as "processed".** A crash between receive and hand-over can drop an event <Cite n={1} />.
- **Using it for every call.** Simple request-response flows may not justify the extra operating work <Cite n={1} />.
- **Putting private data in events.** Many components can see an event, even those that should not use it <Cite n={1} />.

</Layman>
<Bangla>

- **একটি গ্লোবাল ক্রম ধরে নেওয়া।** কয়েকটি কনজিউমার ইনস্ট্যান্স ভিন্ন ক্রমে ইভেন্ট প্রসেস করতে পারে <Cite n={1} />।
- **"delivered"-কে "processed" মনে করা।** গ্রহণ ও হস্তান্তরের মাঝে ক্র্যাশ হলে একটি ইভেন্ট হারিয়ে যেতে পারে <Cite n={1} />।
- **প্রতিটি কলে এটি ব্যবহার করা।** সহজ রিকুয়েস্ট-রেসপন্স ফ্লোর জন্য বাড়তি পরিচালনার কাজ ন্যায্য নাও হতে পারে <Cite n={1} />।
- **ইভেন্টে ব্যক্তিগত ডেটা রাখা।** অনেক কম্পোনেন্ট একটি ইভেন্ট দেখতে পারে, এমনকি যাদের সেটি ব্যবহার করা উচিত নয় তারাও <Cite n={1} />।

</Bangla>
</Voices>

## What a tester can check

<Voices>
<Technical>

<Callout type="tip" title="Tutorial advice">
These test ideas are the tutorial's own advice, not a claim of the sources.

- **Send the same event twice.** Check that the result does not change, for example no second payment.
- **Send events out of order.** Check that a late "updated" event does not hide a newer one.
- **Stop a consumer, then start it.** Check that no event is lost and that a failed event reaches the dead-letter queue.
- **Check the delay.** Read the data right after an event and again later. Know how long the system may show old data.
- **Follow the correlation ID.** Check that one ID links the logs of all the parts.
</Callout>

</Technical>

এই টেস্টের ধারণাগুলো টিউটোরিয়ালের নিজের পরামর্শ। এগুলো সোর্সের দাবি নয়।

- **একই ইভেন্ট দুবার পাঠান।** দেখুন ফলাফল বদলায় না, যেমন দ্বিতীয় পেমেন্ট হয় না।
- **ইভেন্ট ক্রমের বাইরে পাঠান।** দেখুন দেরিতে আসা একটি "updated" ইভেন্ট নতুনটিকে ঢেকে দেয় না।
- **একটি কনজিউমার থামান, তারপর চালু করুন।** দেখুন কোনো ইভেন্ট হারায় না। আরও দেখুন ব্যর্থ ইভেন্ট ডেড-লেটার কিউতে পৌঁছায়।
- **দেরি পরীক্ষা করুন।** ইভেন্টের ঠিক পরে ডেটা পড়ুন এবং পরে আবার পড়ুন। জানুন সিস্টেম কতক্ষণ পুরোনো ডেটা দেখাতে পারে।
- **কোরিলেশন ID অনুসরণ করুন।** দেখুন একটি ID সব অংশের লগ যুক্ত করে।

## Key words

| Word | Meaning |
|---|---|
| Event | A change in state or an update <Cite n={2} /> |
| Producer | A component that creates and publishes events <Cite n={1} /> <Cite n={2} /> |
| Consumer | A component that listens for events and acts on them <Cite n={1} /> |
| Event router or broker | The part that moves events from producers to consumers <Cite n={1} /> <Cite n={2} /> |
| Event streaming | A model where events go to a durable log that clients read at their own position <Cite n={1} /> |
| Idempotent | Safe to run more than once with the same result (the tutorial's own definition; Azure uses the word without defining it) <Cite n={1} /> |
| Dead-letter queue (DLQ) | A queue where a failed event goes for an administrator to inspect <Cite n={1} /> |
| Correlation ID | An identifier in every event that links related operations <Cite n={1} /> |
