# ACID and BASE

When you pay a bill, you expect the money to leave one account and arrive in the other, or to stay where it was. When you "like" a post, you accept that a friend may see the old count for a few seconds. ACID and BASE name these two attitudes to data.

## In plain words

<Voices>
<Technical>

**ACID** is a set of four properties that make database transactions reliable: Atomicity, Consistency, Isolation, Durability <Cite n={7} />. A **transaction** is a group of steps that the database treats as one operation <Cite n={1} />.

| Letter | Plain meaning |
|---|---|
| **A**tomicity | All the steps happen, or none do. Other transactions never see a half-done result <Cite n={1} />. |
| **C**onsistency | *The tutorial's own simplification:* the data follows the rules you define. A constraint is one such rule: if a statement would break it, the database raises an error <Cite n={5} />. |
| **I**solation | Open transactions do not show their unfinished changes to each other <Cite n={1} />. The level of isolation can be chosen <Cite n={2} />. |
| **D**urability | After the database reports "done", the change is logged on permanent storage <Cite n={1} />. |

**BASE** is the other side. In Brewer's 2000 keynote, BASE means "Basically Available, Soft-state, Eventual consistency" <Cite n={8} />. His slides contrast it with ACID: BASE accepts weaker consistency (stale data is acceptable) and puts availability first <Cite n={8} />.

</Technical>
<Layman>

**ACID** is a set of four properties. They make database transactions reliable <Cite n={7} />. The four words are Atomicity, Consistency, Isolation, and Durability. A **transaction** is a group of steps. The database treats the group as one operation <Cite n={1} />.

- **Atomicity:** All the steps happen, or none do. Other transactions never see a half-done result <Cite n={1} />.
- **Consistency:** This is the tutorial's own simplification. The data follows the rules you define. A constraint is one such rule. If a statement would break it, the database raises an error <Cite n={5} />.
- **Isolation:** Open transactions do not show their unfinished changes to each other <Cite n={1} />. You can choose the level of isolation <Cite n={2} />.
- **Durability:** After the database reports "done", the change is logged on permanent storage <Cite n={1} />.

**BASE** is the other side. In the 2000 keynote of Brewer, BASE means "Basically Available, Soft-state, Eventual consistency" <Cite n={8} />. BASE accepts weaker consistency. Stale data is acceptable. BASE puts availability first <Cite n={8} />.

</Layman>
<Bangla>

**ACID** হলো চারটি বৈশিষ্ট্যের (property) একটি সেট। এগুলো ডেটাবেস ট্রানজেকশনকে নির্ভরযোগ্য করে <Cite n={7} />। চারটি শব্দ হলো Atomicity, Consistency, Isolation এবং Durability। **ট্রানজেকশন** (transaction) হলো কয়েকটি ধাপের একটি দল। ডেটাবেস এই দলকে একটি কাজ (operation) হিসেবে ধরে <Cite n={1} />।

- **অ্যাটমিসিটি (Atomicity):** সব ধাপ ঘটে, অথবা একটিও ঘটে না। অন্য ট্রানজেকশন কখনো অর্ধেক-শেষ ফলাফল দেখে না <Cite n={1} />।
- **কনসিসটেন্সি (Consistency):** এটি টিউটোরিয়ালের নিজস্ব সরল ব্যাখ্যা। ডেটা আপনার ঠিক করা নিয়ম মেনে চলে। কনস্ট্রেইন্ট (constraint) এমন একটি নিয়ম। কোনো স্টেটমেন্ট সেটি ভাঙলে ডেটাবেস এরর দেয় <Cite n={5} />।
- **আইসোলেশন (Isolation):** খোলা ট্রানজেকশনগুলো একে অপরকে নিজেদের অসমাপ্ত পরিবর্তন দেখায় না <Cite n={1} />। আইসোলেশনের লেভেল বেছে নেওয়া যায় <Cite n={2} />।
- **ডিউরেবিলিটি (Durability):** ডেটাবেস "done" জানানোর পর পরিবর্তনটি স্থায়ী স্টোরেজে লগ করা থাকে <Cite n={1} />।

**BASE** হলো অন্য দিক। 2000 সালের একটি মূল বক্তৃতায় (keynote) Brewer বলেছেন, BASE মানে "Basically Available, Soft-state, Eventual consistency" <Cite n={8} />। BASE দুর্বল কনসিসটেন্সি মেনে নেয়। পুরোনো (stale) ডেটা গ্রহণযোগ্য। BASE অ্যাভেইলেবিলিটিকে আগে রাখে <Cite n={8} />।

## How it works

<Voices>
<Technical>

**Atomicity.** A payment needs several separate updates. A transaction groups them, and `ROLLBACK` cancels the updates so far <Cite n={1} />.

**Isolation levels.** The SQL standard defines four levels. The strictest, Serializable, gives the same effect as running the transactions one at a time in some order <Cite n={2} />. A **dirty read** is when a transaction reads data from another transaction that is not yet committed <Cite n={2} />. PostgreSQL uses Read Committed by default. In it, two reads in one transaction can see different data if another transaction commits in between <Cite n={2} />. The PostgreSQL docs call this level adequate for many applications, but not for all cases <Cite n={2} />. At Serializable, an application must be ready to retry a transaction that fails <Cite n={2} />.

**Durability and the log.** PostgreSQL writes a change to its log (the write-ahead log) and flushes the log to permanent storage before the change goes to the data files. After a crash, it recovers from the log <Cite n={3} />.

**An eventually consistent design.** The Dynamo paper describes a store that accepts weaker consistency for high availability. It gives no isolation guarantees and allows only single-key updates <Cite n={7} />. Its design is eventually consistent: all updates reach all replicas eventually <Cite n={7} />. Updates can travel to replicas in the background <Cite n={7} />. The paper does not use the word BASE. Linking Dynamo to BASE is the tutorial's own framing.

</Technical>

<Bangla>

**অ্যাটমিসিটি।** একটি পেমেন্টের জন্য কয়েকটি আলাদা আপডেট লাগে। ট্রানজেকশন সেগুলোকে একসঙ্গে বাঁধে। `ROLLBACK` এ পর্যন্ত করা আপডেট বাতিল করে <Cite n={1} />।

**আইসোলেশন লেভেল।** SQL স্ট্যান্ডার্ড চারটি লেভেল ঠিক করেছে। Serializable সবচেয়ে কঠোর। এটি ট্রানজেকশনগুলোকে কোনো একটি ক্রমে একটির পর একটি চালানোর মতো ফল দেয় <Cite n={2} />। **ডার্টি রিড** (dirty read) হয় যখন একটি ট্রানজেকশন অন্য ট্রানজেকশনের এমন ডেটা পড়ে, যা এখনো কমিট হয়নি <Cite n={2} />। PostgreSQL ডিফল্টভাবে Read Committed ব্যবহার করে। এই লেভেলে একটি ট্রানজেকশনের দুটি রিড ভিন্ন ডেটা দেখতে পারে। এটি হয় যদি মাঝখানে অন্য ট্রানজেকশন কমিট করে <Cite n={2} />। PostgreSQL ডকুমেন্টেশন বলে, এই লেভেল অনেক অ্যাপ্লিকেশনের জন্য যথেষ্ট, তবে সব ক্ষেত্রের জন্য নয় <Cite n={2} />। Serializable-এ অ্যাপ্লিকেশনকে ব্যর্থ ট্রানজেকশন আবার চালানোর (retry) জন্য প্রস্তুত থাকতে হয় <Cite n={2} />।

**ডিউরেবিলিটি এবং লগ।** PostgreSQL পরিবর্তনটি আগে তার লগে (write-ahead log) লেখে। পরিবর্তনটি ডেটা ফাইলে যাওয়ার আগে সে লগকে স্থায়ী স্টোরেজে ফ্লাশ করে। ক্র্যাশের পর সে লগ থেকে রিকভার করে <Cite n={3} />।

**ইভেন্চুয়ালি কনসিসটেন্ট ডিজাইন।** Dynamo পেপার এমন একটি স্টোর বর্ণনা করে, যা উচ্চ অ্যাভেইলেবিলিটির জন্য দুর্বল কনসিসটেন্সি মেনে নেয়। এটি আইসোলেশনের কোনো গ্যারান্টি দেয় না। এটি শুধু একটি কী-র (single-key) আপডেটের অনুমতি দেয় <Cite n={7} />। এর ডিজাইন ইভেন্চুয়ালি কনসিসটেন্ট (eventually consistent): সব আপডেট শেষ পর্যন্ত সব রেপ্লিকায় পৌঁছায় <Cite n={7} />। আপডেট ব্যাকগ্রাউন্ডে রেপ্লিকায় যেতে পারে <Cite n={7} />। পেপারে BASE শব্দটি নেই। Dynamo-কে BASE-এর সঙ্গে যুক্ত করা টিউটোরিয়ালের নিজস্ব ভাবনা।

## A real-life example

<Voices>
<Technical>

*The numbers here are the tutorial's own.* A learning platform sells course credits. Ana has 100 credits and sends 40 to Ben, who has 20.

**With ACID.** The platform removes 40 from Ana and adds 40 to Ben in one transaction. If the server fails after the first step, the database cancels the transaction, and Ana still has 100. Nobody sees Ana at 60 and Ben at 20.

**With BASE.** The platform also shows a "learners online" counter on many replicas. One replica shows 118 and another shows 120 for a moment. Nothing is broken, because BASE accepts stale data <Cite n={8} />.

A real case from the Dynamo paper is the shopping cart. It must accept "add" and "remove" even during network and server failures <Cite n={7} />. If the latest cart is not reachable, the change goes to an older version, and the versions are reconciled later <Cite n={7} />. Brewer notes that real systems mix both: he used ACID for user profiles and logging <Cite n={8} />.

</Technical>

## Trade-offs

<Voices>
<Technical>

Brewer says the trade-off between consistency and availability is fundamental <Cite n={8} />. The Dynamo authors report that, in their experience at Amazon, stores with ACID guarantees tend to have poor availability <Cite n={7} />. That is their result, not a law for every system.

With eventual consistency, two copies can change at the same time, and the conflict must be found and resolved <Cite n={7} />. In Dynamo, the application can merge the versions, or the store can use a simple rule such as "last write wins" <Cite n={7} />. Dynamo also keeps writes from being rejected, so the work of conflict handling moves to the reads <Cite n={7} />.

ACID does not mean "nothing can ever go wrong".

- PostgreSQL stores committed data safely only if the storage does what it should. Disk and controller caches can lose data in a power failure, and the administrator must check the hardware <Cite n={4} />.
- A setting can trade durability for speed. With `synchronous_commit` off, the database reports success before the change is safe. A crash can lose recent transactions, but the data is left as if they had been cancelled <Cite n={6} />. The default is on <Cite n={6} />.

</Technical>

Brewer বলেন, কনসিসটেন্সি ও অ্যাভেইলেবিলিটির মধ্যে ট্রেড-অফ (trade-off) মৌলিক <Cite n={8} />। Dynamo-র লেখকরা Amazon-এ তাদের অভিজ্ঞতার একটি ফল জানান। ACID গ্যারান্টিযুক্ত স্টোরের অ্যাভেইলেবিলিটি প্রায়ই খারাপ হয় <Cite n={7} />। এটি তাদের ফল, সব সিস্টেমের জন্য কোনো নিয়ম নয়।

ইভেন্চুয়াল কনসিসটেন্সিতে দুটি কপি একই সময়ে বদলাতে পারে। সিস্টেমকে এই কনফ্লিক্ট (conflict) খুঁজে বের করে সমাধান করতে হয় <Cite n={7} />। Dynamo-তে অ্যাপ্লিকেশন ভার্সনগুলো মার্জ করতে পারে। স্টোর "last write wins"-এর মতো সহজ নিয়মও ব্যবহার করতে পারে <Cite n={7} />। Dynamo রাইট প্রত্যাখ্যান হওয়াও আটকায়। তাই কনফ্লিক্ট সামলানোর কাজ রিডে সরে যায় <Cite n={7} />।

ACID মানে "কখনো কিছু ভুল হতে পারে না" নয়।

- PostgreSQL কমিট করা ডেটা নিরাপদে রাখে শুধু তখনই, যখন স্টোরেজ ঠিকভাবে কাজ করে। ডিস্ক ও কন্ট্রোলারের ক্যাশ বিদ্যুৎ চলে গেলে ডেটা হারাতে পারে। অ্যাডমিনিস্ট্রেটরকে হার্ডওয়্যার যাচাই করতে হয় <Cite n={4} />।
- একটি সেটিং গতির জন্য ডিউরেবিলিটি ছাড়তে পারে। `synchronous_commit` বন্ধ থাকলে ডেটাবেস পরিবর্তন নিরাপদ হওয়ার আগেই সফল বলে জানায়। ক্র্যাশ সাম্প্রতিক ট্রানজেকশন হারাতে পারে। তখন ডেটা এমন থাকে, যেন সেগুলো বাতিল হয়েছিল <Cite n={6} />। ডিফল্ট হলো চালু <Cite n={6} />।

</Bangla>

## Common mistakes

<Voices>
<Technical>

- **Treating ACID as a guarantee against all loss.** Durability depends on storage and settings <Cite n={4} /> <Cite n={6} />.
- **Mixing up two meanings of "consistent".** In this tutorial, the "C" of ACID means data rules (see the table above). Eventual consistency is about copies that agree later <Cite n={7} />.
- **Assuming the strictest isolation is the default.** PostgreSQL uses Read Committed unless you change it <Cite n={2} />.
- **Forgetting retries.** At the Serializable level, the application must be prepared to retry a transaction that fails <Cite n={2} />.

</Technical>

## What a tester can check

<Voices>
<Technical>

<Callout type="tip" title="Tutorial advice">
These test ideas are the tutorial's own advice.

- **Cut the transaction in half.** Make the second step fail on purpose. Check that the first step is not saved.
- **Break a rule.** Try a value that a constraint should refuse. Check for a clear error and no partial data.
- **Open two sessions.** Change data in one and read it in the other, before and after the commit. Write down what you expect to see.
- **Kill the service.** Stop the server right after a "success" message. Restart it and check that the saved data is still there.
- **Wait and read again.** On an eventually consistent feature, read from two places, then again after a pause. Ask the team how long "eventually" may take.
</Callout>

</Technical>

<Bangla>

এই টেস্টের ধারণাগুলো টিউটোরিয়ালের নিজস্ব পরামর্শ।

- **ট্রানজেকশনকে মাঝপথে কাটুন।** দ্বিতীয় ধাপ ইচ্ছা করে ব্যর্থ করান। প্রথম ধাপ যে সেভ হয়নি, তা যাচাই করুন।
- **একটি নিয়ম ভাঙুন।** এমন মান দিন, যা কনস্ট্রেইন্ট গ্রহণ করবে না। স্পষ্ট এরর আছে কিনা এবং আংশিক ডেটা নেই কিনা দেখুন।
- **দুটি সেশন খুলুন।** একটিতে ডেটা বদলান এবং কমিটের আগে ও পরে অন্যটিতে পড়ুন। কী দেখার আশা করছেন, তা লিখে রাখুন।
- **সার্ভিস বন্ধ করুন।** "success" মেসেজ আসার ঠিক পরে সার্ভার বন্ধ করুন। আবার চালু করে দেখুন সেভ করা ডেটা এখনো আছে কিনা।
- **অপেক্ষা করে আবার পড়ুন।** ইভেন্চুয়ালি কনসিসটেন্ট ফিচারে দুই জায়গা থেকে পড়ুন, তারপর বিরতির পর আবার পড়ুন। "Eventually" কত সময় নিতে পারে, তা টিমকে জিজ্ঞেস করুন।

## Key words

| Word | Meaning |
|---|---|
| ACID | Atomicity, Consistency, Isolation, Durability: four properties of reliable transactions <Cite n={7} /> |
| BASE | Basically Available, Soft-state, Eventual consistency, as named in a 2000 keynote <Cite n={8} /> |
| Transaction | A group of steps that the database treats as one operation <Cite n={1} /> |
| Atomic | All steps happen, or none do <Cite n={1} /> |
| Dirty read | Reading data of another transaction that is not yet committed <Cite n={2} /> |
| Write-ahead log | A log that is flushed to permanent storage before the data files change <Cite n={3} /> |
| Eventual consistency | All updates reach all replicas eventually <Cite n={7} /> |
