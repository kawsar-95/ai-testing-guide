# VMs and Containers

Your test passes on your laptop and fails on the test server. The server has another library version, another setting, or another app that uses the same port. A virtual machine and a container are two ways to give each app a clean, separate place to run on shared hardware.

<PageMeta />

## In plain words

<Voices>
<Technical>

Virtual machines (VMs) and containers both let several apps share the same physical machine, but they keep the apps apart in different ways <Cite n={1} />.

A VM uses a hypervisor. The hypervisor gives hardware-level isolation of resources across the VMs. To each VM the hardware looks like its own virtual hardware. Each VM also runs a complete guest operating system (OS) with the app on top. Different VMs can run different OSs, for example Linux and Windows <Cite n={1} />.

Containers skip the guest OS. Many containers share one OS kernel, which is part of the host OS, and each one is kept apart from the others <Cite n={1} />. Docker describes a container as an isolated process, with the files it needs to run <Cite n={2} />. A container depends on the OS family of its host: a Linux host runs Linux containers, and a Windows host runs Windows containers <Cite n={1} />.

</Technical>

<Bangla>

ভার্চুয়াল মেশিন (virtual machine, VM) এবং কনটেইনার (container) দুটিই কয়েকটি অ্যাপকে একই ফিজিক্যাল মেশিন ভাগ করে চালাতে দেয়। তবে তারা অ্যাপগুলোকে আলাদা রাখে ভিন্ন উপায়ে <Cite n={1} />।

VM একটি হাইপারভাইজার (hypervisor) ব্যবহার করে। হাইপারভাইজার সব VM জুড়ে রিসোর্সের হার্ডওয়্যার-লেভেল আইসোলেশন (hardware-level isolation) দেয়। প্রতিটি VM-এর কাছে হার্ডওয়্যার মনে হয় তার নিজের ভার্চুয়াল হার্ডওয়্যার। প্রতিটি VM একটি সম্পূর্ণ গেস্ট অপারেটিং সিস্টেমও (guest operating system, OS) চালায়, তার উপরে থাকে অ্যাপ। ভিন্ন VM ভিন্ন OS চালাতে পারে, যেমন Linux এবং Windows <Cite n={1} />।

কনটেইনার গেস্ট OS বাদ দেয়। অনেক কনটেইনার একটি OS কার্নেল (kernel) ভাগ করে, যা হোস্ট OS-এর অংশ। প্রতিটি কনটেইনার অন্যদের থেকে আলাদা থাকে <Cite n={1} />। Docker কনটেইনারকে বর্ণনা করে একটি আইসোলেটেড প্রসেস (isolated process) হিসেবে, যার সঙ্গে চলার জন্য দরকারি ফাইল থাকে <Cite n={2} />। কনটেইনার নির্ভর করে তার হোস্টের OS ফ্যামিলির (OS family) উপর। Linux হোস্ট Linux কনটেইনার চালায়। Windows হোস্ট Windows কনটেইনার চালায় <Cite n={1} />।

## How it works

<Voices>
<Technical>

**Container isolation.** The container runtime asks the host OS to give each container its own view of the system <Cite n={1} />. NIST names three tools <Cite n={1} />:

- Namespace isolation limits what a container can see, such as files, network interfaces, and processes.
- Resource limits cap how much of the host a container may use. On Linux this is mainly done with control groups (cgroups).
- Filesystem virtualization lets containers share storage without access to each other's data.

**Images.** A container image is a ready-to-run package with the code, the runtime, the libraries, and default settings <Cite n={3} />. NIST calls it an immutable snapshot of what the app needs in user space. So the developer, the build system, and production run the same artifact, which solves the "works on my machine" problem <Cite n={1} />. Kubernetes says containers are meant to be stateless and immutable. To change an app, you build a new image and recreate the container. You do not change a running one <Cite n={3} />. You usually push the image to a registry before a Pod uses it <Cite n={4} />.

**Orchestration.** In Kubernetes, each node runs the containers of the Pods assigned to it, and containers of one Pod run together on one node <Cite n={3} />.

</Technical>

<Bangla>

**কনটেইনার আইসোলেশন।** কনটেইনার রানটাইম (container runtime) হোস্ট OS-কে বলে প্রতিটি কনটেইনারকে সিস্টেমের নিজস্ব একটি দৃশ্য দিতে <Cite n={1} />। NIST তিনটি উপায়ের নাম দেয় <Cite n={1} />:

- নেমস্পেস আইসোলেশন (namespace isolation) একটি কনটেইনার কী দেখতে পারে তা সীমিত করে, যেমন ফাইল, নেটওয়ার্ক ইন্টারফেস এবং প্রসেস।
- রিসোর্স লিমিট (resource limit) একটি কনটেইনার হোস্টের কতটা ব্যবহার করতে পারবে তা সীমিত করে। Linux-এ এটি মূলত কন্ট্রোল গ্রুপ (control groups, cgroups) দিয়ে করা হয়।
- ফাইলসিস্টেম ভার্চুয়ালাইজেশন (filesystem virtualization) কনটেইনারদের স্টোরেজ ভাগ করতে দেয়, কিন্তু একে অপরের ডেটায় ঢুকতে দেয় না।

**ইমেজ।** কনটেইনার ইমেজ (container image) হলো কোড, রানটাইম, লাইব্রেরি এবং ডিফল্ট সেটিংসহ একটি রেডি-টু-রান প্যাকেজ <Cite n={3} />। NIST একে বলে ইউজার স্পেসে (user space) অ্যাপের যা দরকার তার একটি ইমিউটেবল স্ন্যাপশট (immutable snapshot)। তাই ডেভেলপার, বিল্ড সিস্টেম এবং প্রোডাকশন একই আর্টিফ্যাক্ট (artifact) চালায়। এতে "works on my machine" সমস্যার সমাধান হয় <Cite n={1} />। Kubernetes বলে কনটেইনারের উদ্দেশ্য স্টেটলেস (stateless) এবং ইমিউটেবল হওয়া। অ্যাপ বদলাতে হলে আপনি নতুন ইমেজ বিল্ড করেন এবং কনটেইনার আবার তৈরি করেন। চলমান কনটেইনার বদলান না <Cite n={3} />। Pod ব্যবহার করার আগে সাধারণত ইমেজ রেজিস্ট্রিতে (registry) পুশ করা হয় <Cite n={4} />।

**অর্কেস্ট্রেশন (orchestration)।** Kubernetes-এ প্রতিটি নোড নিজের Pod-গুলোর কনটেইনার চালায়। একটি Pod-এর কনটেইনারগুলো একই নোডে একসঙ্গে চলে <Cite n={3} />।

## When you need it

<Voices>
<Technical>

Docker says that starting a whole VM to isolate one app is a lot of overhead. Because containers share a kernel, you can run more apps on less infrastructure <Cite n={2} />. Docker also lists traits that help with development and test: a container holds what it needs, it has little effect on the host and on other containers, you can delete one without harm to the others, and it should behave the same on a laptop, in a data center, or in a cloud <Cite n={2} />. Kubernetes adds that containers are repeatable and decouple the app from the host <Cite n={3} />.

VMs are still useful. NIST lists strong isolation, OS automation, and a wide ecosystem as VM benefits <Cite n={1} />. Containers share the host kernel, so a container cannot bring a different OS family. A VM can run another OS <Cite n={1} />.

</Technical>

<Bangla>

Docker বলে, একটি অ্যাপ আলাদা করতে পুরো VM চালু করা অনেক ওভারহেড। কনটেইনার একটি কার্নেল ভাগ করে। তাই কম ইনফ্রাস্ট্রাকচারে (infrastructure) বেশি অ্যাপ চালানো যায় <Cite n={2} />। Docker ডেভেলপমেন্ট ও টেস্টে সহায়ক কিছু বৈশিষ্ট্যও তালিকাভুক্ত করে। কনটেইনারের ভেতরে তার প্রয়োজনীয় সবকিছু থাকে। হোস্ট এবং অন্য কনটেইনারের উপর এর প্রভাব কম। একটি মুছলে অন্যগুলোর ক্ষতি হয় না। ল্যাপটপ, ডেটা সেন্টার বা ক্লাউডে এর আচরণ একই হওয়ার কথা <Cite n={2} />। Kubernetes যোগ করে যে কনটেইনার রিপিটেবল (repeatable) এবং অ্যাপকে হোস্ট থেকে আলাদা করে <Cite n={3} />।

VM এখনও কাজের। NIST VM-এর সুবিধা হিসেবে তালিকাভুক্ত করে শক্তিশালী আইসোলেশন, OS অটোমেশন এবং বিস্তৃত ইকোসিস্টেম <Cite n={1} />। কনটেইনার হোস্ট কার্নেল ভাগ করে, তাই একটি কনটেইনার ভিন্ন OS ফ্যামিলি আনতে পারে না। VM অন্য OS চালাতে পারে <Cite n={1} />।

## Trade-offs

<Voices>
<Technical>

এই তালিকা দুটির তুলনা করে। প্রতিটি পয়েন্টে সোর্স যা বলে তা আছে। শেষ পয়েন্টটি টিউটোরিয়ালের নিজস্ব বিচার, কোনো সোর্স তা বলে না।

- **আলাদা রাখা।** VM-এ একটি হাইপারভাইজার আছে, যা হার্ডওয়্যার-লেভেল আইসোলেশন দেয় <Cite n={1} />। কনটেইনারগুলো OS কার্নেল ভাগ করে, আর রানটাইম তাদের আলাদা রাখে <Cite n={1} />।
- **আইসোলেশনের শক্তি।** NIST VM-এর সীমানাকে বেশি স্পষ্ট ও মূর্ত বলে <Cite n={1} />। কনটেইনারে শক্তিশালী আইসোলেশন আছে, কিন্তু VM-এর মতো স্পষ্ট সীমানা নেই। VM-গুলোর মধ্যে যতটা সেগমেন্টেশন (segmentation), এখানে তার চেয়ে অনেক কম। শেয়ার করা কার্নেল হাইপারভাইজারের চেয়ে বড় ইন্টার-অবজেক্ট অ্যাটাক সারফেস (inter-object attack surface) দেয়। অসতর্ক সেটআপে কনটেইনারগুলো একে অপরের এবং হোস্টের কাছে সহজে পৌঁছাতে পারে <Cite n={1} />।
- **প্রতিটি অ্যাপ কী বহন করে।** VM বহন করে নিজের কার্নেল ও ড্রাইভারসহ একটি পূর্ণ গেস্ট OS <Cite n={2} />। কনটেইনার বহন করে তার ফাইলসহ একটি আইসোলেটেড প্রসেস <Cite n={2} />।
- **ওভারহেড।** একটি অ্যাপের জন্য VM ব্যবহার করলে ওভারহেড অনেক <Cite n={2} />। কনটেইনারে কম, কারণ কার্নেল ভাগ করা হয় <Cite n={2} />।
- **ভিন্ন OS।** Linux এবং Windows VM একটি মেশিন ভাগ করতে পারে <Cite n={1} />। Linux হোস্ট শুধু Linux কনটেইনার চালায় <Cite n={1} />।
- **বদলানোর প্রক্রিয়া।** VM সাধারণত স্টেটফুল (stateful) সিস্টেম হিসেবে রাখা হয়। টিমগুলো এগুলোকে সেট আপ করে, বদলায় এবং এগুলোর পুরো জীবনকাল জুড়ে আপগ্রেড করে <Cite n={1} />। কনটেইনার ইমিউটেবল হওয়ার জন্য তৈরি। আপনি নতুন ইমেজ বিল্ড করেন, তারপর কনটেইনার আবার তৈরি করেন <Cite n={1} /> <Cite n={3} />।
- **কোনটি বেছে নেবেন (টিউটোরিয়ালের নিজস্ব)।** শক্ত সীমানা বা অন্য OS দরকার হলে VM প্রায়ই ভালো মানায়। অ্যাপ প্যাকেজ করে এক এনভায়রনমেন্ট থেকে আরেকটিতে নিতে কনটেইনার প্রায়ই ভালো মানায়।

NIST-এর বক্তব্যের দুই দিকই লক্ষ্য করুন। সে বলে রানটাইম হাইপারভাইজারের চেয়ে কম আইসোলেশন দেয়। কিন্তু সে এও বলে যে বেশিরভাগ কনটেইনার প্ল্যাটফর্ম কনটেইনারগুলোকে ভালোভাবে আলাদা করে <Cite n={1} />।

NIST আপনাকে একটি বেছে নিতে বলে না। VM এবং কনটেইনার প্রায়ই একসঙ্গে কাজ করে। একটি টিম হার্ডওয়্যার ডিপ্লয়, ভাগ ও পরিচালনা করতে VM ব্যবহার করতে পারে। অ্যাপ প্যাকেজ করতে এবং প্রতিটি VM আরও ভালোভাবে ব্যবহার করতে কনটেইনার ব্যবহার করতে পারে <Cite n={1} />। Docker ক্লাউডের জন্য একই ছবি দেয়। আপনি যে মেশিন পান তা সাধারণত VM। কনটেইনার রানটাইমসহ একটি VM অনেক কনটেইনারাইজড (containerized) অ্যাপ চালাতে পারে <Cite n={2} />।

</Bangla>
</Voices>

## Common mistakes

<Voices>
<Technical>

- **Treating a container as a VM.** A container shares the host kernel. NIST says its boundary is less clear than a VM boundary <Cite n={1} />.
- **Mixing sensitive and ordinary workloads on one host.** NIST advises that a host kernel runs containers of one sensitivity level only. It also says VMs can provide this separation <Cite n={1} />.
- **Running apps next to containers on the same host.** NIST advises against mixing containerized and non-containerized workloads on one host instance <Cite n={1} />.
- **Using the `latest` tag in production.** Kubernetes warns that it is harder to know which version runs and to roll back. A tag can also be moved to another image, but a digest is fixed <Cite n={4} />.
- **Fixing a running container by hand.** Kubernetes says to build a new image and recreate the container <Cite n={3} />.

</Technical>

<Bangla>

- **কনটেইনারকে VM মনে করা।** কনটেইনার হোস্ট কার্নেল ভাগ করে। NIST বলে এর সীমানা VM-এর সীমানার চেয়ে কম স্পষ্ট <Cite n={1} />।
- **একই হোস্টে সংবেদনশীল ও সাধারণ ওয়ার্কলোড (workload) মেশানো।** NIST পরামর্শ দেয়, একটি হোস্ট কার্নেল যেন শুধু একই সংবেদনশীলতার স্তরের (sensitivity level) কনটেইনার চালায়। সে এও বলে যে VM এই আলাদা করা দিতে পারে <Cite n={1} />।
- **একই হোস্টে কনটেইনারের পাশে সাধারণ অ্যাপ চালানো।** NIST পরামর্শ দেয়, এক হোস্ট ইনস্ট্যান্সে (instance) কনটেইনারাইজড এবং নন-কনটেইনারাইজড ওয়ার্কলোড মেশাবেন না <Cite n={1} />।
- **প্রোডাকশনে `latest` ট্যাগ ব্যবহার করা।** Kubernetes সতর্ক করে যে কোন ভার্সন চলছে তা জানা এবং রোলব্যাক করা কঠিন হয়। একটি ট্যাগ অন্য ইমেজে সরেও যেতে পারে, কিন্তু ডাইজেস্ট (digest) স্থির <Cite n={4} />।
- **চলমান কনটেইনার হাতে ঠিক করা।** Kubernetes বলে নতুন ইমেজ বিল্ড করতে এবং কনটেইনার আবার তৈরি করতে <Cite n={3} />।

## What a tester can check

<Voices>
<Technical>

<Callout type="tip" title="Tutorial advice">
These test ideas are the tutorial's own advice, not a claim of the sources.

- **Which image runs.** Find the exact image tag or digest in the test environment. Check that it is the one you meant to test, and that it is not `latest`.
- **Same image, same result.** Run the same image on a laptop and on the CI host. Compare the results.
- **Restart from clean.** Delete a container and start it again. Check that no data or setting that you expect is lost, and no old state remains by accident.
- **Resource limits.** Give a container a small memory limit and send a heavy load. Check that the app fails in a clear way, and that other containers on the host stay up.
- **Privileges and mounts.** Ask the team which containers run with extra privileges or mount host folders. Report them as a risk to check, and do not test beyond your permission.
- **Right host for the test.** If the test needs a different OS or kernel version, check that the environment is a VM or host that supplies it.
</Callout>

</Technical>

এই টেস্টের ধারণাগুলো টিউটোরিয়ালের নিজস্ব পরামর্শ, সোর্সগুলোর দাবি নয়।

- **কোন ইমেজ চলছে।** টেস্ট এনভায়রনমেন্টে সঠিক ইমেজ ট্যাগ বা ডাইজেস্ট খুঁজে বের করুন। দেখুন এটিই সেই ইমেজ, যা আপনি টেস্ট করতে চেয়েছিলেন, এবং এটি `latest` নয়।
- **একই ইমেজ, একই ফল।** একই ইমেজ ল্যাপটপে এবং CI হোস্টে চালান। ফল তুলনা করুন।
- **পরিষ্কার অবস্থা থেকে আবার শুরু।** একটি কনটেইনার মুছে আবার চালু করুন। দেখুন আপনি যে ডেটা বা সেটিং আশা করেন তা হারায়নি। দেখুন ভুলবশত কোনো পুরোনো স্টেট থেকে যায়নি।
- **রিসোর্স লিমিট।** একটি কনটেইনারকে ছোট মেমোরি লিমিট দিন এবং ভারী লোড পাঠান। দেখুন অ্যাপ স্পষ্টভাবে ব্যর্থ হয়, এবং হোস্টের অন্য কনটেইনার চালু থাকে।
- **প্রিভিলেজ এবং মাউন্ট।** টিমকে জিজ্ঞেস করুন কোন কনটেইনার বাড়তি প্রিভিলেজ (privilege) নিয়ে চলে বা হোস্ট ফোল্ডার মাউন্ট করে। এগুলোকে পরীক্ষার যোগ্য ঝুঁকি হিসেবে জানান। আপনার অনুমতির বাইরে টেস্ট করবেন না।
- **টেস্টের জন্য সঠিক হোস্ট।** টেস্টে ভিন্ন OS বা কার্নেল ভার্সন লাগলে দেখুন এনভায়রনমেন্টটি এমন VM বা হোস্ট, যা তা দেয়।

## Key words

| Word | Meaning |
|---|---|
| Virtual machine (VM) | A simulated computer with virtual hardware and a complete guest OS <Cite n={1} /> |
| Hypervisor | The software that gives hardware-level isolation of resources across VMs <Cite n={1} /> |
| Container | An isolated process with the files it needs to run <Cite n={2} /> |
| Kernel | The part of the host OS that all containers on one host share <Cite n={1} /> |
| Container image | A ready-to-run package with the code, runtime, libraries, and default settings <Cite n={3} /> |
| Container runtime | The software on the host that sets up and runs each container, for example containerd or CRI-O <Cite n={1} /> <Cite n={3} /> |
| Namespace isolation | A way to limit which resources a container can see <Cite n={1} /> |
| cgroups | The Linux control groups that limit how much of the host a container may use <Cite n={1} /> |
| Registry | A place where you store images before a Pod uses them <Cite n={4} /> |
| Tag and digest | A tag names an image version and can move. A digest is a hash of the content and is fixed <Cite n={4} /> |
| Immutable | Not changed after it starts. You build a new image instead <Cite n={3} /> |
