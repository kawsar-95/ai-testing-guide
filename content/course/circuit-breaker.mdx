# Circuit Breaker

A checkout page calls a payment service. The payment service is down. Each call waits a long time and then fails. Soon the checkout page is slow too, and then other pages slow down. A circuit breaker helps prevent this kind of cascading failure <Cite n={1} />.

<PageMeta />

## In plain words

<Voices>
<Technical>

The Circuit Breaker pattern blocks access to a remote service for a while, after the failures reach a threshold. This avoids repeated retries of an operation that is likely to fail. It also gives the failing service room to recover <Cite n={1} />. The AWS guidance says the pattern also detects when the called service works again <Cite n={2} />.

The AWS guidance says breaker objects work like electrical circuit breakers <Cite n={2} />. The breaker object sits between the caller and the called service, and it trips if the called service is unavailable <Cite n={2} />.

Some faults are transient, such as a slow network. They typically fix themselves in a short time, and a retry can handle them. Other faults last longer, up to a full outage. Then the application should not keep retrying <Cite n={1} />.

A time-out alone does not solve this. Waiting requests can hold memory, threads, and database connections. This can exhaust resources and break unrelated parts of the system <Cite n={1} />. Repeated retries can also add network load and use up database threads <Cite n={2} />.

</Technical>

## When you need it

<Voices>
<Technical>

Azure lists these cases <Cite n={1} />:

- You want to stop cascading failures by not sending calls that are likely to fail.
- You want to protect your service-level objectives from slow dependencies.
- You want to manage intermittent connection problems.

AWS adds these signs: a call is most likely to fail, or a synchronous call goes to a callee that is unavailable or slow <Cite n={2} />.

</Technical>
<Layman>

Azure lists these cases <Cite n={1} />:

- You want to stop cascading failures by not sending calls that are likely to fail.
- You want to protect your service-level objectives from slow dependencies.
- You want to manage intermittent connection problems.

AWS adds these signs. A call is most likely to fail. Or a synchronous call goes to a callee that is unavailable or slow <Cite n={2} />.

</Layman>
<Bangla>

Azure এই ক্ষেত্রগুলো তালিকাভুক্ত করে <Cite n={1} />:

- ব্যর্থ হওয়ার সম্ভাবনাযুক্ত call না পাঠিয়ে আপনি cascading failure থামাতে চান।
- ধীর dependency থেকে আপনি আপনার service-level objective রক্ষা করতে চান।
- আপনি মাঝেমধ্যে হওয়া connection সমস্যা সামলাতে চান।

## How it works

<Voices>
<Technical>

The breaker works as a proxy. It watches the recent failures and decides if a call goes through or fails at once. You can build it as a state machine with three states <Cite n={1} />.

```text
              failures pass the threshold
             within the time period
   CLOSED ------------------------------> OPEN
      ^                                     |
      |                                     | time-out timer ends
      | enough trial calls succeed          v
      +------------- HALF-OPEN <------------+
                        |
                        | a trial call fails
                        +--------> OPEN (timer restarts)
```

This drawing is the tutorial's own picture of the Azure description.

| State | What happens |
|---|---|
| Closed | Calls go to the operation. The proxy counts recent failures. If the count passes the threshold in the time period, the proxy goes to Open and starts a time-out timer <Cite n={1} />. |
| Open | Each call fails at once with an exception <Cite n={1} />. |
| Half-Open | The timer ended. A limited number of calls pass through. If they succeed, the breaker assumes the fault is fixed and goes to Closed. If any call fails, it goes back to Open and restarts the timer <Cite n={1} />. |

The Half-Open state helps to avoid a flood of requests to a service that is still recovering <Cite n={1} />. The AWS page does not name this state. It describes the same idea in simpler words: after the circuit opens, the breaker tries calls from time to time and closes the circuit when they succeed <Cite n={2} />.

</Technical>

</Layman>
<Bangla>

Breaker একটি proxy হিসেবে কাজ করে। সে সাম্প্রতিক ব্যর্থতা দেখে এবং ঠিক করে একটি call পার হবে নাকি সঙ্গে সঙ্গে ব্যর্থ হবে। আপনি এটিকে তিনটি state-সহ একটি state machine হিসেবে বানাতে পারেন <Cite n={1} />।

এটি Azure-এর বর্ণনার tutorial-এর নিজস্ব ছবি:

- **Closed থেকে Open:** time period-এর মধ্যে ব্যর্থতা threshold পার হয়।
- **Open থেকে Half-Open:** time-out timer শেষ হয়।
- **Half-Open থেকে Closed:** যথেষ্ট trial call সফল হয়।
- **Half-Open থেকে Open:** একটি trial call ব্যর্থ হয়। Timer আবার শুরু হয়।

তিনটি state:

- **Closed:** Call operation-এ যায়। Proxy সাম্প্রতিক ব্যর্থতা গোনে। সংখ্যা time period-এর মধ্যে threshold পার হলে proxy Open-এ যায় এবং একটি time-out timer শুরু করে <Cite n={1} />।
- **Open:** প্রতিটি call একটি exception-সহ সঙ্গে সঙ্গে ব্যর্থ হয় <Cite n={1} />।
- **Half-Open:** Timer শেষ হয়েছে। সীমিত সংখ্যক call পার হয়। সেগুলো সফল হলে breaker ধরে নেয় fault ঠিক হয়েছে এবং Closed-এ যায়। কোনো call ব্যর্থ হলে সে আবার Open-এ ফেরে এবং timer আবার শুরু করে <Cite n={1} />।

Half-Open state এমন service-এ request-এর বন্যা এড়াতে সাহায্য করে, যা এখনো সেরে উঠছে <Cite n={1} />। AWS page এই state-এর নাম দেয় না। সে একই ধারণা সহজ কথায় বর্ণনা করে। Circuit খোলার পর breaker মাঝেমধ্যে call চেষ্টা করে। সেগুলো সফল হলে সে circuit বন্ধ করে <Cite n={2} />।

## Thresholds and time-outs

<Voices>
<Technical>

Azure describes these settings <Cite n={1} />:

- **Failure threshold.** The failure counter of the Closed state is time based, and it resets at intervals. This design helps prevent a few random failures from opening the breaker.
- **Success count.** In Half-Open, the breaker returns to Closed after a set number of successful calls in a row. One failure opens it at once.
- **Time-out.** It can grow. The first Open period can be a few seconds, and a later one a few minutes.

The source gives no default numbers. It says to match the settings to the likely recovery of the protected operation <Cite n={1} />. If the Open period is too long, the breaker can raise errors after the fault is fixed. If the breaker moves to Half-Open too fast, it can fluctuate and slow the responses <Cite n={1} />.

More details:

- In Open, the breaker can return a default value that makes sense for the application, not an exception <Cite n={1} />.
- An administrator should be able to open or close a circuit by hand <Cite n={1} /> <Cite n={2} />.
- With many threads, the first failed call sets the AWS expiration time. Later calls should not keep moving it <Cite n={2} />.

</Technical>

- **Failure threshold।** Closed state-এর failure counter সময়-ভিত্তিক, এবং এটি বিরতি দিয়ে reset হয়। এই design কিছু এলোমেলো ব্যর্থতাকে breaker খুলে দেওয়া থেকে আটকাতে সাহায্য করে।
- **Success count।** Half-Open-এ breaker পরপর নির্দিষ্ট সংখ্যক সফল call-এর পর Closed-এ ফেরে। একটি ব্যর্থতা সঙ্গে সঙ্গে তাকে খুলে দেয়।
- **Time-out।** এটি বাড়তে পারে। প্রথম Open সময় কয়েক সেকেন্ড হতে পারে, আর পরের সময় কয়েক মিনিট।

Source কোনো ডিফল্ট সংখ্যা দেয় না। সে বলে, setting-গুলো সুরক্ষিত operation-এর সম্ভাব্য recovery-র সঙ্গে মেলাতে হবে <Cite n={1} />। Open সময় বেশি লম্বা হলে fault ঠিক হওয়ার পরও breaker error তুলতে পারে। Breaker খুব দ্রুত Half-Open-এ গেলে সে ওঠানামা করতে পারে এবং response ধীর করতে পারে <Cite n={1} />।

আরও কিছু বিষয়:

- Open-এ breaker exception না দিয়ে application-এর জন্য অর্থবহ একটি ডিফল্ট মান ফেরত দিতে পারে <Cite n={1} />।
- Administrator-এর হাতে circuit খোলা বা বন্ধ করার সুযোগ থাকা উচিত <Cite n={1} /> <Cite n={2} />।
- অনেক thread থাকলে প্রথম ব্যর্থ call AWS-এর expiration time ঠিক করে। পরের call-গুলোর তা সরাতে থাকা উচিত নয় <Cite n={2} />।

## Circuit breaker and retry

<Voices>
<Technical>

The two patterns have different goals. Retry expects the operation to succeed in the end. The circuit breaker stops an operation that is likely to fail <Cite n={1} />. A retry with backoff handles transient errors <Cite n={2} />.

You can combine them: retry through a breaker. Then the retry logic should stop when the breaker shows that the fault is not transient <Cite n={1} />. The AWS sample retries with exponential backoff a set number of times. If all fail, it records an expiry time, and later calls fail at once until that time passes <Cite n={2} />.

</Technical>
<Layman>

The two patterns have different goals. Retry expects the operation to succeed in the end. The circuit breaker stops an operation that is likely to fail <Cite n={1} />. A retry with backoff handles transient errors <Cite n={2} />.

You can combine them: retry through a breaker. Then the retry logic should stop when the breaker shows that the fault is not transient <Cite n={1} />. The AWS sample retries with exponential backoff a set number of times. If all fail, it records an expiry time. Later calls fail at once until that time passes <Cite n={2} />.

</Layman>
<Bangla>

দুটি pattern-এর লক্ষ্য আলাদা। Retry আশা করে operation শেষ পর্যন্ত সফল হবে। Circuit breaker ব্যর্থ হওয়ার সম্ভাবনাযুক্ত operation থামায় <Cite n={1} />। Backoff-সহ retry transient error সামলায় <Cite n={2} />।

আপনি দুটি মেলাতে পারেন: breaker-এর মধ্য দিয়ে retry। তখন breaker যখন দেখায় fault transient নয়, retry logic-এর থামা উচিত <Cite n={1} />। AWS sample নির্দিষ্ট সংখ্যকবার exponential backoff-সহ retry করে। সব ব্যর্থ হলে সে একটি expiry time লিখে রাখে। ওই সময় পার না হওয়া পর্যন্ত পরের call সঙ্গে সঙ্গে ব্যর্থ হয় <Cite n={2} />।

</Bangla>
</Voices>

## When not to use it

<Voices>
<Technical>

Azure says the pattern might not suit these cases <Cite n={1} />:

- Local private resources, such as in-memory data. The breaker adds overhead there.
- A replacement for exception handling in business logic.
- Well-known retry methods are enough and the dependencies handle retries. The breaker may add needless complexity.
- A wait for the reset would cause unacceptable delay.
- Message-driven or event-driven systems, where failed messages often go to a dead letter queue.
- The platform already handles recovery, for example health checks in a load balancer or a service mesh.

</Technical>
<Layman>

Azure says the pattern might not suit these cases <Cite n={1} />:

- Local private resources, such as in-memory data. The breaker adds overhead there.
- A replacement for exception handling in business logic.
- Well-known retry methods are enough and the dependencies handle retries. The breaker may add needless complexity.
- A wait for the reset would cause unacceptable delay.
- Message-driven or event-driven systems, where failed messages often go to a dead letter queue.
- The platform already handles recovery, for example health checks in a load balancer or a service mesh.

</Layman>
<Bangla>

Azure বলে, pattern-টি এই ক্ষেত্রগুলোর জন্য মানাতে নাও পারে <Cite n={1} />:

- স্থানীয় ব্যক্তিগত resource, যেমন in-memory data। সেখানে breaker বাড়তি overhead যোগ করে।
- Business logic-এ exception handling-এর বিকল্প হিসেবে।
- সুপরিচিত retry পদ্ধতিই যথেষ্ট এবং dependency-গুলো নিজেরাই retry সামলায়। Breaker অপ্রয়োজনীয় জটিলতা যোগ করতে পারে।
- Reset-এর জন্য অপেক্ষা অগ্রহণযোগ্য দেরি ঘটাবে।
- Message-driven বা event-driven system, যেখানে ব্যর্থ message প্রায়ই dead letter queue-তে যায়।
- Platform আগে থেকেই recovery সামলায়, যেমন load balancer বা service mesh-এর health check।

</Bangla>
</Voices>

## A real-life example

<Voices>
<Technical>

This example is the tutorial's own. An order service calls a payment service through a breaker. The breaker is Closed. Then the payment service starts to time out, and the failure threshold is reached. The breaker opens.

Now the order service gets an error at once and shows "Payments are busy. Try again soon." When the timer ends, a few trial calls pass. They succeed, so the breaker closes.

</Technical>
<Layman>

This example is the tutorial's own. An order service calls a payment service through a breaker. The breaker is Closed. Then the payment service starts to time out. The failure threshold is reached. The breaker opens.

Now the order service gets an error at once. It shows "Payments are busy. Try again soon." When the timer ends, a few trial calls pass. They succeed, so the breaker closes.

</Layman>

## Common mistakes

<Voices>
<Technical>

- **Retrying for a long fault with no breaker.** Blocked requests can use up threads and connections <Cite n={1} />.
- **No plan for the exception.** The application can degrade a feature, call an alternative, or ask the user to try later <Cite n={1} />.
- **A time-out that is too long.** A thread can stay blocked for a long time before the breaker sees the failure <Cite n={1} />.
- **One breaker for unrelated providers.** A problem in one shard can block calls to a healthy shard <Cite n={1} />.

</Technical>

- **Breaker ছাড়া দীর্ঘ fault-এর জন্য retry করা।** আটকে থাকা request thread ও connection ফুরিয়ে দিতে পারে <Cite n={1} />।
- **Exception-এর জন্য কোনো পরিকল্পনা না থাকা।** Application একটি feature সীমিত করতে পারে, একটি বিকল্প ডাকতে পারে, অথবা user-কে পরে চেষ্টা করতে বলতে পারে <Cite n={1} />।
- **খুব লম্বা time-out।** Breaker ব্যর্থতা দেখার আগে একটি thread দীর্ঘ সময় আটকে থাকতে পারে <Cite n={1} />।
- **সম্পর্কহীন provider-এর জন্য একটি breaker।** একটি shard-এর সমস্যা একটি সুস্থ shard-এ call আটকে দিতে পারে <Cite n={1} />।

## What a tester can check

<Voices>
<Technical>

<Callout type="tip" title="Tutorial advice">
These test ideas are the tutorial's own advice, not a claim of the sources.

- **Trip it.** Make the dependency fail until the threshold. Check that the breaker opens and that the next call fails at once.
- **Check the user message.** In Open, check that the user sees a clear message or a sensible default, not a raw error.
- **Watch the Half-Open step.** Wait for the time-out. Check that only a few trial calls pass, then that success closes the breaker and a failure opens it again.
- **Try random failures.** Send a few failures spread over time. Check that the breaker stays Closed.
- **Check the logs and events.** Check that each state change and each rejected call is visible to the team.
</Callout>

</Technical>

<Bangla>

এই test-এর ধারণাগুলো tutorial-এর নিজস্ব পরামর্শ, source-এর দাবি নয়।

- **Trip করান।** Threshold পর্যন্ত dependency-কে ব্যর্থ করান। Breaker খোলে কিনা এবং পরের call সঙ্গে সঙ্গে ব্যর্থ হয় কিনা যাচাই করুন।
- **User message যাচাই করুন।** Open-এ user একটি স্পষ্ট message বা যুক্তিসঙ্গত ডিফল্ট দেখে কিনা দেখুন, কাঁচা error নয়।
- **Half-Open ধাপ দেখুন।** Time-out পর্যন্ত অপেক্ষা করুন। শুধু কয়েকটি trial call পার হয় কিনা দেখুন। তারপর দেখুন সাফল্য breaker বন্ধ করে এবং ব্যর্থতা আবার খুলে দেয় কিনা।
- **এলোমেলো ব্যর্থতা চেষ্টা করুন।** সময়ের উপর ছড়ানো কয়েকটি ব্যর্থতা পাঠান। Breaker Closed থাকে কিনা দেখুন।
- **Log ও event যাচাই করুন।** প্রতিটি state পরিবর্তন ও প্রতিটি প্রত্যাখ্যাত call team-এর কাছে দৃশ্যমান কিনা দেখুন।

</Bangla>

## Key words

| Word | Meaning |
|---|---|
| Circuit breaker | A proxy between a caller and a called service that stops calls likely to fail <Cite n={1} /> <Cite n={2} /> |
| Closed | The state in which calls go through and the proxy counts recent failures <Cite n={1} /> |
| Open | The state in which each call fails at once <Cite n={1} /> |
| Half-Open | The state in which a limited number of trial calls pass <Cite n={1} /> |
| Threshold | The number of failures in a time period that opens the breaker <Cite n={1} /> |
| Time-out timer | The wait in the Open state before the breaker tries again <Cite n={1} /> |
| Expiration timeout | In the AWS guidance, how long the circuit stays tripped before calls are routed again <Cite n={2} /> |
| Cascading failure | A failure in one part that spreads to other parts <Cite n={1} /> |
| Transient fault | A short fault that typically corrects itself <Cite n={1} /> |
| Retry | Trying a failed operation again, in the hope that it succeeds <Cite n={1} /> |
