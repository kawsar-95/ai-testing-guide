# CQRS

A shop shows a product page to thousands of visitors each minute. Only a few people change the price or the stock. Both jobs use the same table, the same code, and the same rules. CQRS asks: why must reading and writing use one model?

<PageMeta />

## In plain words

<Voices>
<Technical>

CQRS means Command Query Responsibility Segregation. The pattern splits the reads and the writes of a data store into separate data models, so you can tune each model on its own <Cite n={1} />. A command updates data. A query gets data <Cite n={1} />.

A common design uses one model for both jobs. This fits simple create, read, update, and delete (CRUD) work <Cite n={1} />. As an application grows, it can cause lock contention, slow queries, and security problems. The fields that an update needs are often not the fields that a read needs <Cite n={1} />. Reads and writes also often have different speed and scaling needs <Cite n={1} />.

</Technical>

## When you need it

<Voices>
<Technical>

The source lists cases where the pattern may help <Cite n={1} />:

- Many users change the same data at the same time. Small, clear commands can reduce conflicts.
- The user interface guides people through a task in steps.
- You must tune reads apart from writes. This helps most when the system has more reads than writes.
- Different teams build the write side and the read side.

The same source says the pattern might not suit a simple domain, or a case where a plain CRUD interface is enough <Cite n={1} />.

</Technical>
<Layman>

The source lists cases where the pattern may help <Cite n={1} />:

- Many users change the same data at the same time. Small, clear commands can reduce conflicts.
- The user interface guides people through a task in steps.
- You must tune reads apart from writes. This helps most when the system has more reads than writes.
- Different teams build the write side and the read side.

The same source says the pattern might not suit a simple domain, or a case where a plain CRUD interface is enough <Cite n={1} />.

</Layman>
<Bangla>

সোর্স কিছু ক্ষেত্রের কথা বলে যেখানে এই প্যাটার্ন সাহায্য করতে পারে <Cite n={1} />:

- অনেক ইউজার একই সময়ে একই ডেটা বদলায়। ছোট, পরিষ্কার কমান্ড কনফ্লিক্ট কমাতে পারে।
- ইউজার ইন্টারফেস ধাপে ধাপে মানুষকে একটি কাজের মধ্য দিয়ে নিয়ে যায়।
- রিডকে রাইট থেকে আলাদা করে টিউন করতে হয়। সিস্টেমে রাইটের চেয়ে রিড বেশি হলে এটি সবচেয়ে বেশি কাজে লাগে।
- রাইট দিক আর রিড দিক আলাদা টিম বানায়।

একই সোর্স বলে, সহজ ডোমেইনের জন্য, অথবা সাধারণ CRUD ইন্টারফেস যথেষ্ট হলে, এই প্যাটার্ন হয়তো মানায় না <Cite n={1} />।

</Bangla>
</Voices>

## How it works

<Voices>
<Technical>

**Commands.** A command should state a business task, not a low-level data change. The source gives this example: use "Book hotel room", not "Set ReservationStatus to Reserved" <Cite n={1} />. It also suggests that a queue can run commands asynchronously <Cite n={1} />.

**Queries.** A query never changes data. It returns data transfer objects (DTOs), which hold the data in a convenient shape and carry no domain logic <Cite n={1} />.

**The write model** handles commands. It has validation and domain logic, and it works to keep the data correct <Cite n={1} />. **The read model** serves queries and has no domain logic <Cite n={1} />.

There are two levels of separation <Cite n={1} />:

| Level | What it means |
|---|---|
| One data store | Both models use one database, but each has its own logic. |
| Two data stores | The read and write models have their own stores. You can scale each one to its load. They may use different storage technology, for example a document database for reads and a relational database for writes. |

With two stores, the stores must stay in sync <Cite n={1} />. A common way is that the write model publishes an event after it updates its database, and the read model uses the event to refresh its data <Cite n={1} />. The read store can have its own schema, for example a materialized view that avoids complex joins. It can also be a read-only copy (replica) of the write database <Cite n={1} />.

Updating a database and publishing an event are two steps. Usually you cannot put a message broker and a database in one distributed transaction, so the two steps can disagree <Cite n={1} />. The source suggests the Transactional Outbox pattern, which saves the state change and the event together. It also suggests that the read-model consumer be idempotent, so a duplicate message does no harm <Cite n={1} />.

</Technical>

**কমান্ড।** একটি কমান্ডে একটি বিজনেস কাজ বলা উচিত, নিচু স্তরের ডেটা বদল নয়। সোর্স এই উদাহরণ দেয়: "Book hotel room" ব্যবহার করুন, "Set ReservationStatus to Reserved" নয় <Cite n={1} />। সোর্স এটিও বলে যে একটি কিউ কমান্ডগুলো অ্যাসিনক্রোনাসলি (asynchronously) চালাতে পারে <Cite n={1} />।

আলাদা করার দুটি স্তর আছে <Cite n={1} />:

- **একটি ডেটা স্টোর:** দুটি মডেলই একটি ডেটাবেস ব্যবহার করে, কিন্তু প্রতিটির নিজের লজিক আছে।
- **দুটি ডেটা স্টোর:** রিড মডেল আর রাইট মডেলের নিজের নিজের স্টোর আছে। প্রতিটিকে তার লোড অনুযায়ী স্কেল করা যায়। তারা আলাদা স্টোরেজ টেকনোলজি ব্যবহার করতে পারে। উদাহরণ: রিডের জন্য একটি ডকুমেন্ট ডেটাবেস এবং রাইটের জন্য একটি রিলেশনাল ডেটাবেস।

দুটি স্টোর থাকলে স্টোর দুটিকে সিঙ্কে রাখতে হয় <Cite n={1} />। একটি সাধারণ উপায় এরকম। রাইট মডেল তার ডেটাবেস আপডেট করার পর একটি ইভেন্ট পাবলিশ করে। রিড মডেল সেই ইভেন্ট দিয়ে তার ডেটা রিফ্রেশ করে <Cite n={1} />। রিড স্টোরের নিজের স্কিমা থাকতে পারে, যেমন একটি ম্যাটেরিয়ালাইজড ভিউ (materialized view), যা জটিল জয়েন এড়ায়। এটি রাইট ডেটাবেসের একটি রিড-অনলি কপি (রিপ্লিকা) ও হতে পারে <Cite n={1} />।

একটি ডেটাবেস আপডেট করা আর একটি ইভেন্ট পাবলিশ করা দুটি আলাদা ধাপ। সাধারণত একটি মেসেজ ব্রোকার আর একটি ডেটাবেসকে একটি ডিস্ট্রিবিউটেড ট্রানজেকশনে রাখা যায় না, তাই দুই ধাপ একমত নাও হতে পারে <Cite n={1} />। সোর্স Transactional Outbox প্যাটার্নের পরামর্শ দেয়, যা স্টেটের পরিবর্তন আর ইভেন্ট একসাথে সংরক্ষণ করে। সোর্স আরও বলে, রিড মডেলের কনজিউমার আইডেম্পোটেন্ট (idempotent) হোক, যাতে একই মেসেজ দুইবার এলে ক্ষতি না হয় <Cite n={1} />।

## Eventual consistency

<Voices>
<Technical>

When the stores are separate, the read data might not show the latest change at once. A reader can get stale data <Cite n={1} />. The source says the read side catches up with the write side after a delay, which is eventual consistency <Cite n={1} />. It adds that keeping the read store current can be hard, and that you must plan for a user who acts on stale data <Cite n={1} />.

</Technical>
<Layman>

When the stores are separate, the read data might not show the latest change at once. A reader can get stale data <Cite n={1} />. The source says the read side catches up with the write side after a delay. This is eventual consistency <Cite n={1} />. The source adds that keeping the read store current can be hard. It also says you must plan for a user who acts on stale data <Cite n={1} />.

</Layman>
<Bangla>

স্টোর আলাদা হলে রিড ডেটা হয়তো সাথে সাথে সর্বশেষ পরিবর্তন দেখায় না। একজন রিডার পুরোনো ডেটা পেতে পারে <Cite n={1} />। সোর্স বলে রিড দিক কিছুক্ষণ পরে রাইট দিকের সমান হয়ে যায়। একেই বলে ইভেন্চুয়াল কনসিসটেন্সি (eventual consistency) <Cite n={1} />। সোর্স আরও বলে, রিড স্টোরকে হালনাগাদ রাখা কঠিন হতে পারে। আর যে ইউজার পুরোনো ডেটা দেখে কাজ করে তার জন্যও আগে থেকে পরিকল্পনা করতে হবে <Cite n={1} />।

</Bangla>
</Voices>

## Combining CQRS with event sourcing

<Voices>
<Technical>

Some CQRS designs use the Event Sourcing pattern. It stores state as a chronological list of events, and the system replays them in order to find the current state <Cite n={1} />. (The page [Event Sourcing](/course/event-sourcing/) explains this pattern.) In this design the write side is the event store, and it is the one place that holds the true state. The read model builds materialized views from the events <Cite n={1} />.

The source names these gains: you can rebuild a view, or make a new one, by replaying old events, and an event stream as the write store can reduce update conflicts <Cite n={1} />. It also names these costs: the read store can lag behind the events, the design can be harder, and building views can take much time and many resources. Snapshots at regular intervals can avoid a full replay each time <Cite n={1} />.

</Technical>
<Layman>

Some CQRS designs use the Event Sourcing pattern. It stores state as a chronological list of events. The system replays them in order to find the current state <Cite n={1} />. (The page [Event Sourcing](/course/event-sourcing/) explains this pattern.) In this design the write side is the event store. It is the one place that holds the true state. The read model builds materialized views from the events <Cite n={1} />.

The source names these gains. You can rebuild a view, or make a new one, by replaying old events. An event stream as the write store can reduce update conflicts <Cite n={1} />. Snapshots at regular intervals can avoid a full replay each time <Cite n={1} />.

</Layman>
<Bangla>

কিছু CQRS ডিজাইন ইভেন্ট সোর্সিং (Event Sourcing) প্যাটার্ন ব্যবহার করে। এটি স্টেটকে সময়ক্রমে সাজানো ইভেন্টের তালিকা হিসেবে রাখে। সিস্টেম বর্তমান স্টেট জানতে সেগুলো ক্রমানুসারে রিপ্লে (replay) করে <Cite n={1} />। ([Event Sourcing](/course/event-sourcing/) পাতা এই প্যাটার্ন ব্যাখ্যা করে।) এই ডিজাইনে রাইট দিক হলো ইভেন্ট স্টোর। এটিই একমাত্র জায়গা যেখানে সত্যিকারের স্টেট থাকে। রিড মডেল ইভেন্ট থেকে ম্যাটেরিয়ালাইজড ভিউ বানায় <Cite n={1} />।

সোর্স এই সুবিধাগুলো বলে। পুরোনো ইভেন্ট রিপ্লে করে একটি ভিউ আবার বানানো যায়, বা নতুন ভিউ বানানো যায়। রাইট স্টোর হিসেবে ইভেন্ট স্ট্রিম আপডেট কনফ্লিক্ট কমাতে পারে <Cite n={1} />। সোর্স এই খরচগুলোও বলে। রিড স্টোর ইভেন্ট থেকে পিছিয়ে থাকতে পারে। ডিজাইন কঠিন হতে পারে। ভিউ বানাতে অনেক সময় আর অনেক রিসোর্স লাগতে পারে। নিয়মিত বিরতিতে স্ন্যাপশট (snapshot) নিলে প্রতিবার পুরো রিপ্লে এড়ানো যায় <Cite n={1} />।

</Bangla>
</Voices>

## Trade-offs

<Voices>
<Technical>

The source lists these benefits: independent scaling, schemas that suit each job, tighter security for writes, cleaner models, and simpler queries <Cite n={1} />. The price is as follows <Cite n={1} />:

- **More complexity.** The core idea is simple, but the design can become much more complex, especially with Event Sourcing.
- **Custom code.** Tools that map objects to database tables cannot make CQRS code from a schema for you.
- **Messaging problems.** Messaging is not required, but it is often used. Then you must handle failed, duplicate, and retried messages.

</Technical>

## A real-life example

<Voices>
<Technical>

This example is the tutorial's own. A test-management tool has a screen that lists all test runs with their pass rate. Thousands of testers open it every day. A few CI jobs write results all the time.

With CQRS, the write side accepts a command such as "Record test result". The write side checks the rules and saves the result. Then it publishes an event. The read side updates a ready-made summary table. The screen reads only this table, so it stays fast, and it does not block the writes. The cost is a short delay: a tester who just ran a test may see the old pass rate for a moment.

</Technical>

## What a tester can check

<Voices>
<Technical>

<Callout type="tip" title="Tutorial advice">
These test ideas are the tutorial's own advice, not a claim of the source.

- **Read right after write.** Send a command, then query at once. Check what the user sees, and how long it takes for the new data to show.
- **Send the same event twice.** Check that the read side does not count the change two times.
- **Stop the event flow.** Pause the link between the stores, make some changes, then restart it. Check that the read store catches up.
- **Act on old data.** Open a screen, change the data in another session, and then act on the first screen. Check that the system handles it with a clear message.
- **Rebuild the read store.** If the design allows it, rebuild a view from scratch and compare it with the old one.
</Callout>

</Technical>

## Key words

| Word | Meaning |
|---|---|
| Command | A request that changes data, best stated as a business task <Cite n={1} /> |
| Query | A request that returns data and never changes it <Cite n={1} /> |
| DTO | Data transfer object: the data that a query returns, with no domain logic <Cite n={1} /> |
| Write model | The part that handles commands, with validation and domain logic <Cite n={1} /> |
| Read model | The part that serves queries, with no domain logic <Cite n={1} /> |
| Materialized view | A prepared view of data that avoids complex joins when you query <Cite n={1} /> |
| Eventual consistency | The read data may lag behind the write data and catch up later <Cite n={1} /> |
| Transactional Outbox | A way to save a state change and its event together <Cite n={1} /> |
| Idempotent | Safe to run more than once, as for a duplicate message <Cite n={1} /> |
| Snapshot | A saved state taken at intervals, so you need not replay all events <Cite n={1} /> |
