# REST, GraphQL, and gRPC

A shop app shows an order and the name of its customer. The app and the server must agree on how to ask for this data. REST, GraphQL, and gRPC are three common answers.

<PageMeta />

## In plain words

<Voices>
<Technical>

An API is the way one program asks another for data or work. These names are not three versions of one thing. REST is a style of design. GraphQL is a query language. gRPC lets a program call a method on a remote server.

**REST** is an architectural style: a set of constraints chosen for the properties they give a system <Cite n={1} />. Fielding starts from a style with no constraints and adds client-server, stateless communication, caching, a uniform interface, and a layered system <Cite n={1} />. Code-on-demand is an optional extra <Cite n={1} />. The uniform interface is the feature that sets REST apart from other network styles <Cite n={1} />. It has four constraints <Cite n={1} />:

1. Identification of resources.
2. Manipulation of resources through representations.
3. Self-descriptive messages.
4. Hypermedia as the engine of application state.

REST does not limit communication to one protocol <Cite n={1} />. So "REST" does not mean "JSON over HTTP". A server can send JSON over HTTP and still not follow these constraints.

**GraphQL** is a query language for an API, plus a server-side runtime that runs queries against a type system that you define <Cite n={2} />. It is not tied to one database <Cite n={2} />. The client writes a query in the shape of the data it wants <Cite n={2} />.

**gRPC** lets a client call a method on a server on another machine as if the method were a local object <Cite n={7} />. By default it uses Protocol Buffers to describe and serialize the data <Cite n={7} />.

</Technical>

<Bangla>

API হলো একটি প্রোগ্রামের অন্য প্রোগ্রামের কাছে ডেটা বা কাজ চাওয়ার উপায়। REST, GraphQL ও gRPC একই জিনিসের তিনটি ভার্সন নয়। REST হলো একটি ডিজাইন স্টাইল। GraphQL হলো একটি কোয়েরি ল্যাঙ্গুয়েজ (query language)। gRPC একটি প্রোগ্রামকে রিমোট সার্ভারের একটি মেথড কল করতে দেয়।

**REST** একটি আর্কিটেকচারাল স্টাইল (architectural style)। এটি কিছু কনস্ট্রেইন্টের (constraint) সমষ্টি। কনস্ট্রেইন্টগুলো বাছা হয়েছে সেগুলো সিস্টেমকে যে বৈশিষ্ট্য দেয়, তার জন্য। <Cite n={1} /> Fielding শুরু করেন কনস্ট্রেইন্ট ছাড়া একটি স্টাইল থেকে। তিনি যোগ করেন ক্লায়েন্ট-সার্ভার, স্টেটলেস কমিউনিকেশন, ক্যাশিং, ইউনিফর্ম ইন্টারফেস এবং লেয়ার্ড সিস্টেম। <Cite n={1} /> কোড-অন-ডিমান্ড একটি ঐচ্ছিক বাড়তি অংশ। <Cite n={1} /> ইউনিফর্ম ইন্টারফেস (uniform interface) REST-কে অন্য নেটওয়ার্ক স্টাইল থেকে আলাদা করে। <Cite n={1} /> এর চারটি কনস্ট্রেইন্ট আছে: <Cite n={1} />

1. রিসোর্সের শনাক্তকরণ।
2. রিপ্রেজেন্টেশনের মাধ্যমে রিসোর্স পরিবর্তন।
3. নিজেই নিজেকে বর্ণনা করে এমন মেসেজ।
4. অ্যাপ্লিকেশনের অবস্থার ইঞ্জিন হিসেবে হাইপারমিডিয়া।

REST যোগাযোগকে একটি প্রোটোকলে সীমাবদ্ধ করে না। <Cite n={1} /> তাই "REST" মানে "JSON over HTTP" নয়। একটি সার্ভার HTTP-র ওপর JSON পাঠিয়েও এই কনস্ট্রেইন্টগুলো না মানতে পারে।

**GraphQL** একটি API-র কোয়েরি ল্যাঙ্গুয়েজ। এর একটি সার্ভার-সাইড রানটাইমও আছে। রানটাইম আপনার সংজ্ঞায়িত টাইপ সিস্টেমের সাথে মিলিয়ে কোয়েরি চালায়। <Cite n={2} /> GraphQL কোনো একটি ডেটাবেসের সাথে বাঁধা নয়। <Cite n={2} /> ক্লায়েন্ট যে ডেটা চায়, তার আকারে একটি কোয়েরি লেখে। <Cite n={2} />

**gRPC** একটি ক্লায়েন্টকে অন্য মেশিনের সার্ভারের একটি মেথড কল করতে দেয়, যেন মেথডটি একটি লোকাল অবজেক্ট। <Cite n={7} /> ডিফল্টভাবে এটি ডেটা বর্ণনা ও সিরিয়ালাইজ করতে Protocol Buffers ব্যবহার করে। <Cite n={7} />

## How it works

<Voices>
<Technical>

**REST.** The key idea is the resource: any information that can be named <Cite n={1} />. A resource is a mapping to a set of values, not the value at one moment <Cite n={1} />. Components send a representation: bytes plus metadata that describes them <Cite n={1} />. Its format is its media type <Cite n={1} />.

Each request must carry all the information needed to understand it, with no stored context on the server <Cite n={1} />. This helps visibility, reliability, and scalability, but repeats data in each request <Cite n={1} />. A response is labeled cacheable or not, and a cacheable one may be reused <Cite n={1} />. A response to a retrieval request is cacheable unless the message says otherwise <Cite n={1} />.

**GraphQL.** A service defines types and fields, and a function for each field <Cite n={2} />. These capabilities form the schema <Cite n={4} />. There are three operation types: query, mutation, and subscription <Cite n={3} />. A query starts at a root type and selects fields down to the leaf values, and the result mirrors the shape of the query <Cite n={3} />. The server checks the query against the schema, then runs the functions <Cite n={2} />. One query can follow links between related objects, saving round trips that a classic REST design may need <Cite n={3} />.

The specification does not require a protocol, but HTTP is the most common choice <Cite n={5} />. A server usually has one endpoint, often `/graphql`, and entities are not identified by URLs <Cite n={5} />. The server must handle POST for queries and mutations, and it may accept GET for queries <Cite n={5} />. The result is in a top-level `data` key, and errors are in a top-level `errors` key <Cite n={3} />.

**gRPC.** You define a service, with its methods, parameters, and return types, in a `.proto` file <Cite n={7} />. The compiler `protoc` generates code from it, and the client calls the methods on a stub <Cite n={7} /><Cite n={8} />. gRPC has four kinds of method <Cite n={8} />:

- **Unary:** one request, one response.
- **Server streaming:** one request, a stream of responses.
- **Client streaming:** a stream of requests, one response.
- **Bidirectional streaming:** both sides send streams.

A client can set a deadline. A call that takes longer ends with `DEADLINE_EXCEEDED` <Cite n={8} />. Each call ends with a status code and an optional message <Cite n={8} />.

</Technical>

<Bangla>

**REST।** মূল ধারণা হলো রিসোর্স (resource)। রিসোর্স হলো যেকোনো তথ্য, যার নাম দেওয়া যায়। <Cite n={1} /> রিসোর্স হলো একসেট ভ্যালুর একটি ম্যাপিং। এটি কোনো এক মুহূর্তের ভ্যালু নয়। <Cite n={1} /> কম্পোনেন্ট একটি রিপ্রেজেন্টেশন (representation) পাঠায়। রিপ্রেজেন্টেশন হলো বাইট এবং সেগুলোকে বর্ণনাকারী মেটাডেটা। <Cite n={1} /> এর ফরম্যাট হলো এর মিডিয়া টাইপ (media type)। <Cite n={1} />

প্রতিটি রিকুয়েস্টে তা বোঝার জন্য প্রয়োজনীয় সব তথ্য থাকতে হয়। সার্ভার কোনো কনটেক্সট জমা রাখে না। <Cite n={1} /> এতে দৃশ্যমানতা, নির্ভরযোগ্যতা ও স্কেলেবিলিটির সুবিধা হয়। কিন্তু প্রতিটি রিকুয়েস্টে ডেটার পুনরাবৃত্তি হয়। <Cite n={1} /> একটি রেসপন্স ক্যাশযোগ্য (cacheable) বা ক্যাশযোগ্য নয় হিসেবে চিহ্নিত থাকে। ক্যাশযোগ্য রেসপন্স আবার ব্যবহার করা যেতে পারে। <Cite n={1} /> মেসেজ অন্যভাবে না বললে রিট্রিভাল রিকুয়েস্টের রেসপন্স ক্যাশযোগ্য। <Cite n={1} />

**GraphQL।** একটি সার্ভিস টাইপ ও ফিল্ড সংজ্ঞায়িত করে, এবং প্রতিটি ফিল্ডের জন্য একটি ফাংশন। <Cite n={2} /> এই সক্ষমতাগুলো মিলে স্কিমা (schema) তৈরি হয়। <Cite n={4} /> তিন ধরনের অপারেশন আছে: কোয়েরি, মিউটেশন ও সাবস্ক্রিপশন। <Cite n={3} /> একটি কোয়েরি একটি রুট টাইপ থেকে শুরু হয়। এটি লিফ ভ্যালু পর্যন্ত ফিল্ড বাছে। ফলাফলের আকার কোয়েরির আকারের মতোই হয়। <Cite n={3} /> সার্ভার স্কিমার সাথে মিলিয়ে কোয়েরি যাচাই করে, তারপর ফাংশন চালায়। <Cite n={2} /> একটি কোয়েরি সম্পর্কিত অবজেক্টের মধ্যে লিংক অনুসরণ করতে পারে। এতে সেই রাউন্ড ট্রিপ বাঁচে, যা একটি ক্লাসিক REST ডিজাইনে লাগতে পারে। <Cite n={3} />

স্পেসিফিকেশন কোনো প্রোটোকল বাধ্যতামূলক করে না, কিন্তু HTTP সবচেয়ে প্রচলিত পছন্দ। <Cite n={5} /> একটি সার্ভারে সাধারণত একটি এন্ডপয়েন্ট থাকে, প্রায়ই `/graphql`। এন্টিটি URL দিয়ে চেনা যায় না। <Cite n={5} /> কোয়েরি ও মিউটেশনের জন্য সার্ভারকে POST হ্যান্ডেল করতে হয়। কোয়েরির জন্য সে GET নিতে পারে। <Cite n={5} /> ফলাফল টপ-লেভেল `data` কী-তে থাকে। এরর থাকে টপ-লেভেল `errors` কী-তে। <Cite n={3} />

**gRPC।** আপনি একটি `.proto` ফাইলে একটি সার্ভিস সংজ্ঞায়িত করেন। এতে এর মেথড, প্যারামিটার ও রিটার্ন টাইপ দেন। <Cite n={7} /> কম্পাইলার `protoc` তা থেকে কোড তৈরি করে। ক্লায়েন্ট একটি স্টাবের (stub) ওপর মেথড কল করে। <Cite n={7} /><Cite n={8} /> gRPC-তে চার ধরনের মেথড আছে: <Cite n={8} />

- **ইউনারি (Unary):** একটি রিকুয়েস্ট, একটি রেসপন্স।
- **সার্ভার স্ট্রিমিং (Server streaming):** একটি রিকুয়েস্ট, রেসপন্সের একটি স্ট্রিম।
- **ক্লায়েন্ট স্ট্রিমিং (Client streaming):** রিকুয়েস্টের একটি স্ট্রিম, একটি রেসপন্স।
- **বাইডিরেকশনাল স্ট্রিমিং (Bidirectional streaming):** দুই পক্ষই স্ট্রিম পাঠায়।

একটি ক্লায়েন্ট ডেডলাইন (deadline) ঠিক করতে পারে। এর চেয়ে বেশি সময় লাগলে কল `DEADLINE_EXCEEDED` দিয়ে শেষ হয়। <Cite n={8} /> প্রতিটি কল একটি স্ট্যাটাস কোড এবং একটি ঐচ্ছিক মেসেজ দিয়ে শেষ হয়। <Cite n={8} />

Each point has a cite, or starts with "Tutorial's view". "Tutorial's view" means it is the tutorial's own judgment.

**What it is**

- REST: an architectural style with constraints. <Cite n={1} />
- GraphQL: a query language and a server-side runtime. <Cite n={2} />
- gRPC: a way to call a method on a remote server as if it were local. <Cite n={7} />

**Where the contract lives**

- REST: Tutorial's view: there is no one schema file. The agreement is the uniform interface, with its resources, representations, and media types.
- GraphQL: in the schema of types and fields. <Cite n={4} />
- gRPC: in a service definition, by default a `.proto` file. <Cite n={8} />

**Data on the wire**

- REST: a representation in some media type. <Cite n={1} />
- GraphQL: clients and servers should support JSON. <Cite n={5} />
- gRPC: Protocol Buffers by default. Other formats are possible. <Cite n={7} />

**Related data**

- REST: data moves in a standard form, not one fitted to each application. This can cost efficiency. <Cite n={1} />
- GraphQL: one query can fetch related data in one request. <Cite n={3} />
- gRPC: Tutorial's view: a method returns what its message type defines. So related data is a design choice of the service.

**Caching**

- REST: a cache constraint. Retrieval responses are cacheable by default. <Cite n={1} />
- GraphQL: there is no URL-like unique id. So the API should expose ids for client caching. <Cite n={6} /> GET for queries may help HTTP and CDN caching. But long queries can pass URL limits. <Cite n={5} />
- gRPC: Tutorial's view: the gRPC pages used here do not describe response caching. So check the team's design.

**Streaming and push**

- REST: Tutorial's view: outside this page. The next page covers long polling, WebSockets, and SSE.
- GraphQL: subscriptions are one operation type. <Cite n={3} />
- gRPC: server, client, and bidirectional streaming. <Cite n={8} />

**Errors**

- REST: Tutorial's view: it depends on the protocol in use, often HTTP status codes.
- GraphQL: a response can hold both `data` and `errors`. The status can still be 2xx. <Cite n={5} />
- gRPC: a status code and an optional message. <Cite n={8} />

**Best fit**

- REST: Tutorial's view: resource-style APIs where caching and many different clients matter.
- GraphQL: Tutorial's view: clients that need different shapes of the same data.
- gRPC: Tutorial's view: calls between services, and calls that stream.

The REST interface has costs. Fielding writes that it lowers efficiency. He also writes that it is not optimal for kinds of interaction other than large-grain hypermedia transfer. <Cite n={1} /> A cache can also lower reliability when its old data differs a lot from the server's data. <Cite n={1} />

**নেটওয়ার্কে ডেটা (data on the wire)**

- REST: কোনো একটি মিডিয়া টাইপে একটি রিপ্রেজেন্টেশন। <Cite n={1} />
- GraphQL: ক্লায়েন্ট ও সার্ভারের JSON সমর্থন করা উচিত। <Cite n={5} />
- gRPC: ডিফল্টভাবে Protocol Buffers। অন্য ফরম্যাটও সম্ভব। <Cite n={7} />

**সম্পর্কিত ডেটা**

- REST: ডেটা একটি স্ট্যান্ডার্ড রূপে যায়, প্রতিটি অ্যাপ্লিকেশনের জন্য মাপা রূপে নয়। এতে দক্ষতা কমতে পারে। <Cite n={1} />
- GraphQL: একটি কোয়েরি একটি রিকুয়েস্টে সম্পর্কিত ডেটা আনতে পারে। <Cite n={3} />
- gRPC: টিউটোরিয়ালের মত: একটি মেথড তা-ই ফেরত দেয়, যা এর মেসেজ টাইপ সংজ্ঞায়িত করে। তাই সম্পর্কিত ডেটা সার্ভিসের একটি ডিজাইন পছন্দ।

**ক্যাশিং**

- REST: একটি ক্যাশ কনস্ট্রেইন্ট। রিট্রিভাল রেসপন্স ডিফল্টভাবে ক্যাশযোগ্য। <Cite n={1} />
- GraphQL: URL-এর মতো কোনো ইউনিক আইডি নেই। তাই ক্লায়েন্ট ক্যাশিংয়ের জন্য API-কে আইডি প্রকাশ করা উচিত। <Cite n={6} /> কোয়েরির জন্য GET HTTP ও CDN ক্যাশিংয়ে সাহায্য করতে পারে। কিন্তু লম্বা কোয়েরি URL-এর সীমা পার করতে পারে। <Cite n={5} />
- gRPC: টিউটোরিয়ালের মত: এখানে ব্যবহৃত gRPC পেজগুলো রেসপন্স ক্যাশিং বর্ণনা করে না। তাই টিমের ডিজাইন দেখে নিন।

**স্ট্রিমিং ও পুশ**

- REST: টিউটোরিয়ালের মত: এই পেজের বাইরে। পরের পেজে লং পোলিং, WebSockets ও SSE আছে।
- GraphQL: সাবস্ক্রিপশন একটি অপারেশন টাইপ। <Cite n={3} />
- gRPC: সার্ভার, ক্লায়েন্ট ও বাইডিরেকশনাল স্ট্রিমিং। <Cite n={8} />

**এরর**

- REST: টিউটোরিয়ালের মত: এটি ব্যবহৃত প্রোটোকলের ওপর নির্ভর করে, প্রায়ই HTTP স্ট্যাটাস কোড।
- GraphQL: একটি রেসপন্সে `data` ও `errors` দুটোই থাকতে পারে। স্ট্যাটাস তবু 2xx হতে পারে। <Cite n={5} />
- gRPC: একটি স্ট্যাটাস কোড এবং একটি ঐচ্ছিক মেসেজ। <Cite n={8} />

**সবচেয়ে মানানসই**

- REST: টিউটোরিয়ালের মত: রিসোর্স-স্টাইল API, যেখানে ক্যাশিং ও অনেক আলাদা ক্লায়েন্ট গুরুত্বপূর্ণ।
- GraphQL: টিউটোরিয়ালের মত: যে ক্লায়েন্টদের একই ডেটার আলাদা আলাদা আকার লাগে।
- gRPC: টিউটোরিয়ালের মত: সার্ভিসের মধ্যে কল এবং যে কল স্ট্রিম করে।

REST ইন্টারফেসের খরচ আছে। Fielding লেখেন যে এটি দক্ষতা কমায়। তিনি আরও লেখেন, বড় আকারের হাইপারমিডিয়া ট্রান্সফার ছাড়া অন্য ধরনের ইন্টারঅ্যাকশনের জন্য এটি সবচেয়ে ভালো নয়। <Cite n={1} /> ক্যাশের পুরনো ডেটা সার্ভারের ডেটা থেকে অনেক আলাদা হলে ক্যাশ নির্ভরযোগ্যতাও কমাতে পারে। <Cite n={1} />

## A real-life example

<Voices>
<Technical>

This example is the tutorial's own. An exam platform has an app that shows an exam, its teacher, and the score of a student.

- With a REST design, the app may ask for the exam, then the teacher, then the score, each at its own address. A cache can keep the exam and the teacher.
- With GraphQL, the app sends one query that names the fields it needs from all three. The answer has the same shape as the query.
- With gRPC, a grading service calls a `GetScore` method on a scoring service, with typed messages. The app does not call it directly.

None of the three is "best". Each has a different price for the same job.

</Technical>

## Common mistakes

<Voices>
<Technical>

- **Calling every JSON-over-HTTP API "REST".** REST is a set of constraints, including the uniform interface <Cite n={1} />, and it is not tied to one protocol <Cite n={1} />.
- **Checking only the HTTP status of a GraphQL call.** A response with data and errors can still have status 2xx <Cite n={5} />. Read the `errors` key <Cite n={3} />.
- **Thinking GraphQL replaces the database.** It is not tied to any database or storage engine <Cite n={2} />.
- **Thinking both sides of a gRPC call agree.** The client and the server judge the call on their own, and the results may not match <Cite n={8} />. Changes made before a cancel are not rolled back <Cite n={8} />.

</Technical>

এই টেস্ট ধারণাগুলো টিউটোরিয়ালের নিজের পরামর্শ। এগুলো সোর্সগুলোর দাবি নয়।

- **REST:** আগের কোনো সেশন ছাড়া একটি রিকুয়েস্ট পাঠান। দেখুন, সার্ভার এটি বোঝে কি না। কোন রেসপন্স ক্যাশ করা যেতে পারে, তা দেখুন।
- **GraphQL:** প্রতিটি রেসপন্সে শুধু স্ট্যাটাস কোড নয়, `data` ও `errors` দুটোই পড়ুন। এমন একটি ফিল্ড চান, যা এই ইউজারের দেখার কথা নয়। কী ফেরত আসে দেখুন।
- **gRPC:** খুব ছোট একটি ডেডলাইন ঠিক করুন। `DEADLINE_EXCEEDED` আছে কি না দেখুন। তারপর দেখুন, সার্ভার তবু কাজটি করেছে কি না। একটি কল মাঝপথে ক্যানসেল করুন। আধা-শেষ পরিবর্তন আছে কি না দেখুন।
- **কন্ট্রাক্ট:** স্কিমা বা `.proto` ফাইল বদলালে পুরনো ক্লায়েন্ট নতুন সার্ভারের সাথে চালান।
</Callout>
