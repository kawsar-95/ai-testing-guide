# N-tier Architecture

A restaurant has a dining room, a kitchen, and a store room. The waiter talks to the kitchen. The kitchen talks to the store room. The waiter does not walk into the store room. N-tier architecture splits an application in a similar way.

<PageMeta />

## In plain words

An N-tier architecture splits an application in two ways: into logical layers, and into physical tiers <Cite n={1} />. The two words do not mean the same thing.

| Word | What it is |
|---|---|
| Layer | A part of the design. Each layer has one job, and layers help to manage dependencies <Cite n={1} />. |
| Tier | A part of the deployment. Tiers are physically separate and run on separate machines <Cite n={1} />. |

A higher layer can use the services of a lower layer. A lower layer cannot use the services of a higher layer <Cite n={1} />. You can put each layer in its own tier, but you do not have to. Several layers can share one tier <Cite n={1} />.

The classic design has three tiers: one for presentation, one for the database, and a middle tier that is optional. A more complex application can use more than three <Cite n={1} />.

## How it works

The source shows a web application with these parts <Cite n={1} />. The diagram below is a simplified view of that flow. It leaves out the firewall, the remote service, and the cache.

```text
  Client
    |
    v
+----------+     +-------------+     +-----------+
| Web tier | --> | Middle tier | --> | Data tier |
| (screens)|     | (logic)     |     | (storage) |
+----------+     +-------------+     +-----------+
  A request goes down. The answer goes back up.
```

In the full diagram of the source, a client reaches a web application firewall (WAF), and then the web tier. The web tier talks to one middle tier directly. It reaches a second middle tier through messaging. Middle tier 1 reaches a remote service and the data tier. Middle tier 2 reaches the data tier. A cache sits between the data tier and the middle tiers <Cite n={1} />.

### Strict and relaxed communication

Tiers can follow a strict or a relaxed communication model <Cite n={1} />.

- **Strict.** A request goes through the adjacent tiers one by one. It cannot skip a tier <Cite n={1} />. The cost is more latency and overhead <Cite n={1} />.
- **Relaxed.** A request can skip some tiers if needed <Cite n={1} />. The cost is more couplings, which makes changes harder <Cite n={1} />.

One system can use both models <Cite n={1} />.

A tier can call another tier directly, or it can use asynchronous messaging through a message queue <Cite n={1} />.

### Closed and open layers

These two words are about layers, not tiers <Cite n={1} />.

- **Closed layers.** A layer can call only the next layer directly below it <Cite n={1} />. This limits the dependencies between layers. But it can create extra network traffic, if a layer only passes requests on to the next layer <Cite n={1} />.
- **Open layers.** A layer can call any layer below it <Cite n={1} />.

## When you need it

The source says to consider this style in three cases <Cite n={1} />:

1. Your architectural requirements are still changing.
2. You move an on-premises application to the cloud with few changes.
3. You build an application that spans both on-premises and cloud.

The style is common in traditional on-premises systems, so it suits the move of existing workloads to the cloud <Cite n={1} />. The source lists these benefits <Cite n={1} />:

- You can move it between on-premises systems, the cloud, and different cloud platforms.
- For most developers, it has a smaller learning curve.
- It costs relatively little, because you do not re-architect the solution.
- It is a natural step from the traditional application model.
- It supports mixed Windows and Linux environments.

Separating tiers physically can help scalability and resiliency. It also adds latency, because of the extra network communication <Cite n={1} />. A tier is also a boundary for scale, reliability, and security. So the source suggests separate tiers for services that have different needs in those areas <Cite n={1} />.

## Challenges

The source names four challenges <Cite n={1} />:

- A middle tier may only do basic create, read, update, and delete (CRUD) work. Then it adds latency and complexity and gives little value.
- A monolithic design prevents independent deployment of features.
- In large systems, network security can be hard to manage.
- Requests and data move through several tiers, so testing and monitoring are more difficult.

The source also lists good practices. They include autoscaling, asynchronous messaging to decouple tiers, caching of data that changes rarely, and high availability for the database tier <Cite n={1} />. For security, it suggests a firewall in front of the web tier, a separate subnet for each tier as a security boundary, and access to the data tier only from a middle tier <Cite n={1} />.

## A real-life example

This example is the tutorial's own. A school has an online exam site with three tiers.

- The **web tier** shows the question page and sends the answers.
- The **middle tier** checks the answers, adds up the score, and applies the rules for a retake.
- The **data tier** stores students, questions, and results.

A student presses "Submit". The web tier sends the answers to the middle tier. The middle tier calculates the score and writes it to the data tier. The result goes back up the same way.

If the middle tier only copied data from the web tier to the data tier with no rules, it would be the weak case that the source warns about: it adds latency and complexity and gives little value <Cite n={1} />.

## Common mistakes

- **Treating layer and tier as one word.** A layer is a design idea. A tier is a place where code runs <Cite n={1} />.
- **Putting each layer in its own tier by habit.** The source says this is not required <Cite n={1} />.
- **Skipping tiers without a plan.** The relaxed model has more couplings, so changes get harder <Cite n={1} />.
- **Adding a middle tier that does nothing.** A tier that only passes CRUD calls adds latency and complexity <Cite n={1} />.
- **Expecting independent releases.** The source lists a monolithic design as a challenge, because features cannot deploy on their own <Cite n={1} />.

## What a tester can check

<Callout type="tip" title="Tutorial advice">
These test ideas are the tutorial's own advice, not a claim of the source.

- **Draw the tiers.** Ask the team which layers run in which tier. Write the list in the test plan.
- **Test each tier alone, then together.** Use test doubles for the other tiers first. Then run a test through all the tiers.
- **Follow one request.** Use logs or traces to follow a single request from the web tier to the data tier. Check where time is lost.
- **Test the rules between tiers.** If a tier is only allowed to talk to the next tier, try a direct call and check that it is refused.
- **Break one tier.** Stop the middle tier in a test environment. Check what the user sees and what the web tier does.
</Callout>

## Key words

| Word | Meaning |
|---|---|
| Layer | A logical part of the design with one responsibility <Cite n={1} /> |
| Tier | A physically separate part that runs on separate machines <Cite n={1} /> |
| Closed layer architecture | A layer can call only the next layer directly below it <Cite n={1} /> |
| Open layer architecture | A layer can call any layer below it <Cite n={1} /> |
| Strict model | A request goes through adjacent tiers one by one <Cite n={1} /> |
| Relaxed model | A request can skip some tiers <Cite n={1} /> |
| CRUD | Create, read, update, and delete operations <Cite n={1} /> |
| Web application firewall (WAF) | A firewall placed between the front end and the internet <Cite n={1} /> |
