# AI-Assisted Security Testing

An AI assistant can explain a strange response, draft fifty test cases, or read a diff in seconds. It can also invent a vulnerability, miss a real one, or leak the data you paste into it. This page shows five jobs that an assistant such as Claude or ChatGPT does well in a security test, and the checks that keep the tester in charge.

<PageMeta />

## In plain words

<Voices>
<Technical>

An AI assistant speeds up the thinking parts of a security test: explaining a finding, drafting test cases, reviewing code, judging whether an alert is a false positive, and suggesting a fix. It cannot be the final judge.

Language models, Claude included, can sometimes generate text that is factually incorrect or inconsistent with the given context; Anthropic calls this **hallucination** <Cite n={4} />. OWASP lists the wider risk as **LLM09:2025 Misinformation**: an LLM produces false or misleading information that appears credible <Cite n={7} />. A related problem is **overreliance**: users trust the output too much and do not verify it <Cite n={7} />.

So this page follows one rule: the AI proposes, and the tester proves. Every finding that goes into a report is reproduced by hand, in the lab, before it counts.

</Technical>

## How it works

<Voices>
<Technical>

### Five jobs for an assistant

| Job | What you give the assistant | What you prove yourself |
|---|---|---|
| Vulnerability analysis | The finding and its evidence, with secrets removed | The finding, with one request that reproduces it |
| Test case generation | The specification, the roles, and the endpoints | That every case is in scope and covers allowed and denied users |
| Code review | The diff of a branch | Each reported issue, in the running app |
| False-positive check | The scanner alert and the raw request and response | The verdict, with your own request |
| Remediation advice | The vulnerable code and the OWASP cheat sheet | The fix, with a retest of the original attack |

For code review, Claude Code has a built-in `/security-review` command. It analyzes the changes on your current branch for security vulnerabilities: it reviews the diff between your branch and the default branch of `origin`, and it looks for risks such as injection, authentication issues, and data exposure. It needs an `origin` remote <Cite n={1} />.

For pull requests, Anthropic publishes a GitHub Action, `claude-code-security-review`, that uses Claude to analyze code changes for security vulnerabilities <Cite n={3} />. For a pull request it analyzes only the changed files, and it filters false positives to reduce noise <Cite n={3} />.

### Three risks to manage

- **Wrong answers.** Anthropic's guide to reducing hallucinations suggests allowing Claude to say "I don't know", grounding answers in direct quotes, and verifying claims with citations <Cite n={4} />. Code suggestions need the same care: OWASP warns that a model can suggest insecure or non-existent code libraries <Cite n={7} />.
- **Sensitive data.** Sensitive information includes personal data, financial details, health records, confidential business data, security credentials, and legal documents <Cite n={6} />. OWASP advises guidance on avoiding the input of sensitive information <Cite n={6} />.
- **Prompt injection.** Prompt injection is an attempt to override or manipulate an AI assistant's instructions by inserting malicious text <Cite n={2} />. It can be indirect: the model reads external content, such as a website or a file, and that content changes its behavior <Cite n={5} />. In a security test, the content you analyze (a response, a page, a pull request) is untrusted. For untrusted content, Claude Code's guide says to review suggested commands before you approve them, to avoid piping untrusted content directly to Claude, and to verify proposed changes to critical files <Cite n={2} />. The security review Action is not hardened against prompt injection, and its README says to use it only to review trusted pull requests <Cite n={3} />.

</Technical>
<Layman>

**Five jobs for an assistant.**

- **Explaining a finding.** Give it the finding and the evidence, with secrets removed. Prove the finding yourself with one request.
- **Writing test cases.** Give it the specification, the roles, and the endpoints. Check that every case is in scope and covers both allowed and refused users.
- **Reviewing code.** Give it the changes of a branch. Check each issue it reports in the running app.
- **Checking false alarms.** Give it the alert and the raw request and response. Prove the answer with your own request.
- **Suggesting fixes.** Give it the weak code and the OWASP cheat sheet. Prove the fix by repeating the original attack.

For code review, Claude Code has a built-in command, `/security-review`. It looks at the changes on your current branch, compared with the main branch of `origin`, and looks for risks such as injection, login problems, and data leaks. It needs an `origin` remote <Cite n={1} />.

For pull requests, Anthropic offers a GitHub Action, `claude-code-security-review`, that uses Claude to look for security flaws in code changes <Cite n={3} />. On a pull request it looks only at the changed files, and it filters out false alarms <Cite n={3} />.

**Three risks to manage.**

- **Wrong answers.** Anthropic's guide says: let Claude say "I don't know", base answers on direct quotes, and check claims with citations <Cite n={4} />. Code tips need the same care: OWASP warns that a model can suggest unsafe libraries, or libraries that do not exist <Cite n={7} />.
- **Private data.** Private information includes personal data, money details, health records, secret business data, passwords and keys, and legal papers <Cite n={6} />. OWASP says that users should be told not to type such information in <Cite n={6} />.
- **Prompt injection.** This is an attempt to take over the assistant's instructions with harmful text <Cite n={2} />. It can come in through something the model reads, such as a website or a file <Cite n={5} />. In a security test, what you analyze (a response, a page, a pull request) cannot be trusted. Claude Code's guide says: check suggested commands before you approve them, do not pipe untrusted content straight into Claude, and check proposed changes to important files <Cite n={2} />. The review Action is not protected against prompt injection. Its README says to use it only on pull requests you trust <Cite n={3} />.

</Layman>
<Bangla>

**Assistant-এর পাঁচটা কাজ।**

- **Finding ব্যাখ্যা করা।** Finding আর তার প্রমাণ দিন, secret সরিয়ে। একটা request দিয়ে finding নিজে প্রমাণ করুন।
- **Test case লেখা।** Specification, role আর endpoint দিন। দেখুন প্রতিটা case scope-এর ভেতরে কি না, আর অনুমতি পাওয়া ও না-পাওয়া দুই ধরনের user-ই আছে কি না।
- **Code পর্যালোচনা।** একটা branch-এর পরিবর্তনগুলো দিন। এটা যে সমস্যা বলে, প্রতিটা চালু app-এ যাচাই করুন।
- **ভুয়া alert যাচাই।** Alert আর মূল request ও response দিন। নিজের request দিয়ে উত্তরটা প্রমাণ করুন।
- **Fix-এর পরামর্শ।** দুর্বল code আর OWASP cheat sheet দিন। মূল আক্রমণটা আবার চালিয়ে fix প্রমাণ করুন।

Code পর্যালোচনার জন্য Claude Code-এ একটা built-in command আছে: `/security-review`। এটা আপনার বর্তমান branch-এর পরিবর্তনগুলো `origin`-এর মূল branch-এর সঙ্গে তুলনা করে দেখে, আর injection, login-এর সমস্যা আর data ফাঁসের মতো ঝুঁকি খোঁজে। এর জন্য একটা `origin` remote লাগে <Cite n={1} />।

Pull request-এর জন্য Anthropic একটা GitHub Action দেয়, `claude-code-security-review`, যেটা Claude দিয়ে code-এর পরিবর্তনে security দুর্বলতা খোঁজে <Cite n={3} />। একটা pull request-এ এটা শুধু বদলানো ফাইলগুলো দেখে, আর ভুয়া alert ছেঁকে বাদ দেয় <Cite n={3} />।

**যে তিনটা ঝুঁকি সামলাতে হবে।**

- **ভুল উত্তর।** Anthropic-এর গাইড বলে: Claude-কে "I don't know" বলার সুযোগ দিন, উত্তর সরাসরি উদ্ধৃতির ওপর দাঁড় করান, আর citation দিয়ে দাবি যাচাই করুন <Cite n={4} />। Code-এর পরামর্শেও একই সতর্কতা লাগে: OWASP সতর্ক করে যে model অনিরাপদ library, বা অস্তিত্বহীন library-র নাম বলতে পারে <Cite n={7} />।
- **গোপন data।** গোপন তথ্যের মধ্যে আছে ব্যক্তিগত data, আর্থিক তথ্য, স্বাস্থ্যের রেকর্ড, ব্যবসার গোপন data, password ও key, আর আইনি কাগজপত্র <Cite n={6} />। OWASP বলে, এমন তথ্য না লেখার নির্দেশনা দিতে হবে <Cite n={6} />।
- **Prompt injection।** এটা ক্ষতিকর লেখা ঢুকিয়ে assistant-এর নির্দেশনা দখল করার চেষ্টা <Cite n={2} />। Model যা পড়ে, যেমন একটা website বা ফাইল, তার ভেতর দিয়েও এটা আসতে পারে <Cite n={5} />। Security test-এ আপনি যা বিশ্লেষণ করেন (একটা response, একটা পেজ, একটা pull request), তার কোনোটাই বিশ্বাসযোগ্য নয়। Claude Code-এর গাইড বলে: approve করার আগে প্রস্তাবিত command দেখে নিন, অবিশ্বস্ত content সরাসরি Claude-এ pipe করবেন না, আর গুরুত্বপূর্ণ ফাইলের প্রস্তাবিত পরিবর্তন যাচাই করুন <Cite n={2} />। Review Action prompt injection-এর বিরুদ্ধে সুরক্ষিত নয়। এর README বলে, শুধু বিশ্বস্ত pull request-এ এটা ব্যবহার করুন <Cite n={3} />।

</Bangla>

## In practice

<Voices>
<Technical>

**1. Ask about a finding, with the evidence.** This prompt is the tutorial's own example. It removes the token and asks for quotes and for "I don't know", as Anthropic's guide suggests <Cite n={4} />:

```text
Context: an authorized test of my practice lab (OWASP Juice Shop on localhost).
Finding: ZAP reports possible SQL injection on GET /api/search?q=
Evidence: the request and the response below. The session token is replaced by <token>.

1. Explain what the alert means and what an attacker could do with it.
2. Give me one Burp Repeater request that would confirm or reject it.
3. Quote the part of the response that supports each point.
4. If the evidence is not enough, say "I don't know".
```

**2. Review a branch before it merges.** Open Claude Code in the repository, on the feature branch, and run `/security-review`. It compares the branch with the default branch of `origin` <Cite n={1} />. Treat each issue as a lead: reproduce it in the lab before you report it.

**3. Check a false positive.** Give the assistant the alert and the raw request and response, and ask for the strongest case for and against. Then send your own request in Repeater. Your request decides, not the answer.

**4. Ask for a fix, then check it.** Ask for the fix of a query built from strings, with the OWASP SQL Injection Prevention Cheat Sheet as the reference. Before you install any library that the answer names, confirm that it exists and that it is the one you expect: OWASP describes attackers who publish malicious packages under names that coding assistants invent <Cite n={7} />.

</Technical>

1. **Ask about a finding, with the evidence.** The Technical view has an example prompt. It removes the token, and it asks for quotes and for "I don't know", as Anthropic's guide suggests <Cite n={4} />.

4. **Fix চান, তারপর যাচাই করুন।** Text জুড়ে বানানো একটা query-র fix চান, OWASP SQL Injection Prevention Cheat Sheet-কে নির্দেশিকা ধরে। উত্তরে যে library-র নাম আসে, install করার আগে দেখুন সেটা সত্যিই আছে কি না আর সঠিকটা কি না। OWASP এমন আক্রমণকারীদের কথা বলে, যাঁরা coding assistant-এর বানানো নামে ক্ষতিকর package প্রকাশ করেন <Cite n={7} />।

## Common mistakes

<Voices>
<Technical>

- **Pasting secrets or customer data into a chat.** Credentials and personal data are sensitive information <Cite n={6} />. Replace them with placeholders such as `<token>`.
- **Reporting what the AI said without reproducing it.** Overreliance is the problem that OWASP describes: trusting the output without verifying it <Cite n={7} />.
- **Running the review Action on pull requests from outside contributors.** The Action is not hardened against prompt injection and is meant for trusted pull requests <Cite n={3} />.
- **Letting an agent run what an untrusted page tells it.** Review suggested commands before you approve them, and do not pipe untrusted content straight to Claude <Cite n={2} />.
- **Installing a library because an answer named it.** A model can suggest libraries that do not exist <Cite n={7} />.
- **Asking the model to be sure.** Allow "I don't know" instead <Cite n={4} />.

</Technical>
<Layman>

- **Pasting secrets or customer data into a chat.** Passwords, keys, and personal data are private information <Cite n={6} />. Replace them with placeholders such as `<token>`.
- **Reporting what the AI said without checking it.** This is the overreliance that OWASP warns about: trusting the answer without checking it <Cite n={7} />.
- **Running the review Action on pull requests from strangers.** The Action is not protected against prompt injection and is meant for pull requests you trust <Cite n={3} />.
- **Letting an agent run what an untrusted page tells it.** Check suggested commands before you approve them, and do not pipe untrusted content straight into Claude <Cite n={2} />.
- **Installing a library because an answer named it.** A model can name libraries that do not exist <Cite n={7} />.
- **Asking the model to be sure.** Let it say "I don't know" instead <Cite n={4} />.

</Layman>
<Bangla>

- **Chat-এ secret বা গ্রাহকের data পেস্ট করা।** Password, key আর ব্যক্তিগত data গোপন তথ্য <Cite n={6} />। এগুলোর বদলে `<token>`-এর মতো placeholder দিন।
- **AI যা বলেছে, যাচাই না করে রিপোর্ট করা।** এটাই OWASP-এর বলা overreliance: যাচাই না করে উত্তরে ভরসা করা <Cite n={7} />।
- **বাইরের কারো pull request-এ review Action চালানো।** Action-টা prompt injection-এর বিরুদ্ধে সুরক্ষিত নয়, আর এটা বিশ্বস্ত pull request-এর জন্য <Cite n={3} />।
- **অবিশ্বস্ত পেজ যা বলে, agent-কে তা চালাতে দেওয়া।** Approve করার আগে প্রস্তাবিত command দেখে নিন, আর অবিশ্বস্ত content সরাসরি Claude-এ pipe করবেন না <Cite n={2} />।
- **উত্তরে নাম এসেছে বলেই library install করা।** Model অস্তিত্বহীন library-র নামও বলতে পারে <Cite n={7} />।
- **Model-কে নিশ্চিত হতে বলা।** বরং "I don't know" বলার সুযোগ দিন <Cite n={4} />।

## Key words

| Term | Meaning |
|---|---|
| Hallucination | Model output that is factually wrong or does not match the given context. |
| Misinformation | OWASP LLM09: false or misleading output that appears credible. |
| Overreliance | Trusting AI output without verifying it. |
| Prompt injection | Text that tries to override or manipulate the assistant's instructions. |
| Indirect prompt injection | Prompt injection that arrives in content the model reads, such as a web page or a file. |
| `/security-review` | A Claude Code command that reviews the changes of the current branch for security issues. |
| False positive | An alert for a flaw that is not really there. |
| Sensitive information | Data such as credentials, personal data, health records, and confidential business data. |
