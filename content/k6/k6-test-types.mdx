# Smoke, Load, Stress, Spike, Soak, and Breakpoint Tests

Each type of performance test asks a different question, and each has its own load shape. This page gives one short k6 script for each type, with thresholds, so you can copy it and change the URL.

<PageMeta />

## The six types and how to use them

<Voices>
<Technical>

The k6 docs name six main types: smoke, average-load, stress, soak, spike, and breakpoint <Cite n={1} />. Each one has its own goal and its own load shape. This tutorial writes "load test" for the average-load type. The k6 docs avoid the plain name "load test", because it can also mean any test that simulates traffic <Cite n={3} />. For the concepts behind each type, see [Types of Performance Testing](/k6/performance-test-types/).

Three rules from the docs apply to every type:

- Start with a smoke test. Check that the script works and that the system copes with a few users. Then move to average load, and then to heavier or longer patterns <Cite n={1} />.
- No single type removes all risk. The risk profile of your system decides which types matter most. A system that runs for days needs soak tests. A system with heavy use needs stress tests <Cite n={1} />.
- Keep the load shape simple: ramp up, plateau, ramp down. Avoid a "rollercoaster" where the load rises and falls many times. It wastes resources and hides the cause of a problem <Cite n={1} />.

The names are not standard. The docs say that no consensus exists about them, and that a stress test for one application can be an average-load test for another <Cite n={1} />. Every number on this page is an example value. Replace it with numbers from your own system.

<Callout type="danger" title="Run only the smoke test against a public host">

All scripts on this page use `https://quickpizza.grafana.com`, a demo site for learning. Run only the smoke test against it, with a few VUs for a few seconds. Do not run the load, stress, spike, soak, or breakpoint scripts against a public host that you do not own. They send heavy traffic and can harm the host. Run them only against your own system, in a test environment, with the permission of its owner. This is the tutorial's own safety rule. The other scripts here were only checked with `k6 inspect`, which reads a script and prints its options without sending any request.

</Callout>

Every script sends one `GET` request and checks the status. All except the breakpoint script then pause for one second. The breakpoint script has no pause, as the breakpoint section explains. Only `options` changes from one type to the next. The docs say that this keeps the load setup apart from the iteration logic <Cite n={1} />.

## Smoke test

<Voices>
<Technical>

**Goal.** A smoke test checks that your script has no errors, that the system has no errors under minimal load, and it gathers baseline numbers for the response time <Cite n={2} />. The docs say to use a few VUs. More than 5 VUs is already a mini-load test. The test lasts from seconds to a few minutes at most, or a low number of iterations <Cite n={2} />. Some people call it a shakeout test <Cite n={2} />.

**When to run it.** Run it whenever you create or change a script, and whenever the application code changes. It is the first step before any larger test <Cite n={2} />.

**Load shape.** A flat line at a very low level:

```text
VUs
 3 |###########
   +-----------> time
    10 s (flat)
```

```js
import http from 'k6/http';
import { check, sleep } from 'k6';

export const options = {
  vus: 3,
  duration: '10s',
  thresholds: {
    http_req_failed: ['rate<0.01'],
    http_req_duration: ['p(95)<1000'],
    checks: ['rate>0.99'],
  },
};

export default function () {
  const res = http.get('https://quickpizza.grafana.com');
  check(res, { 'status is 200': (r) => r.status === 200 });
  sleep(1);
}
```

The thresholds are example values: fewer than 1 % failed requests, `p(95)` under 1 second, and more than 99 % of checks passing. The docs show the same idea with a check on status 200 <Cite n={2} />. Thresholds can also fail a run by themselves <Cite n={8} />. This is the one script that you may run for real. Here are lines from one real run against the demo site, with 3 VUs for 10 seconds. It is one run, so your numbers will differ:

```text
checks_total.......: 24      2.130895/s
checks_succeeded...: 100.00% 24 out of 24
checks_failed......: 0.00%   0 out of 24
http_req_duration..............: avg=318.48ms min=302.7ms med=317.79ms max=345.86ms p(90)=334.68ms p(95)=336.4ms
http_req_failed................: 0.00%  0 out of 24
iterations.....................: 24     2.130895/s
vus_max........................: 3      min=3       max=3
```

If the smoke test shows errors from the script, fix the script first. If it shows poor performance at this tiny load, report it, fix the environment, and run the smoke test again before any larger test <Cite n={2} />.

</Technical>

## Average-load test (the load test)

<Voices>
<Technical>

**Goal.** An average-load test checks how the system performs under typical load, such as a normal day in production <Cite n={3} />. The docs say it may also be called a day-in-life test or a volume test <Cite n={3} />.

**When to run it.** Run it to check that the system meets its goals on a typical day, to find early signs of degradation during the ramp-up or the full-load period, and to confirm that the standards still hold after a code or infrastructure change <Cite n={3} />.

**Load shape.** A ramp up, a long plateau at the average, and a ramp down. The docs give these guides: take the number of users and the throughput from monitoring or analytics tools of production, or from the business. Make the ramp-up 5 % to 15 % of the test time, so the system can warm up or auto-scale. Keep the plateau at least five times the length of the ramp-up. The ramp-down lasts about as long as the ramp-up, or a bit less <Cite n={3} />.

```text
VUs
100 |      ##############
    |     #              #
    |    #                #
  0 +---#------------------#--> time
     5 min    30 min     5 min
```

```js
import http from 'k6/http';
import { check, sleep } from 'k6';

export const options = {
  stages: [
    { duration: '5m', target: 100 },
    { duration: '30m', target: 100 },
    { duration: '5m', target: 0 },
  ],
  thresholds: {
    http_req_failed: ['rate<0.01'],
    http_req_duration: ['p(95)<500'],
  },
};

export default function () {
  const res = http.get('https://quickpizza.grafana.com');
  check(res, { 'status is 200': (r) => r.status === 200 });
  sleep(1);
}
```

The thresholds are example values for a system with a one-second pause per iteration. The ramp-up shows whether the response time gets worse as the load grows. The plateau shows whether the system and its resources stay stable under full load <Cite n={3} />. If a first test makes your system or staging environment crash, that is a useful result: start small, or ramp up more slowly <Cite n={3} />. Thresholds turn the result into a pass or a fail <Cite n={8} />.

</Technical>

## Soak test

<Technical>

**Goal.** A soak test checks the system over a long time: its loss of performance, its use of resources, and its availability and stability <Cite n={6} />. **When to run it.** Run it for a system that must stay on for days, weeks, or months. Run it only after the smoke test and the average-load test <Cite n={6} />. **কখন চালাবেন।** যে সিস্টেমকে দিনের পর দিন, সপ্তাহ বা মাস ধরে চালু থাকতে হয়, তার জন্য চালান। শুধু smoke test আর average-load test-এর পরে চালান <Cite n={6} />। পারলে average-load স্ক্রিপ্ট আবার ব্যবহার করুন, শুধু plateau-র সময় বদলান। ডকুমেন্টেশন সাধারণ সময় হিসেবে ৩ ঘণ্টা থেকে ৭২ ঘণ্টা পর্যন্ত দেয় <Cite n={6} />।

```text
    |#                                     #

```

## Breakpoint test

<Voices>
<Technical>

**Goal.** A breakpoint test finds the limits of the system. You learn where and how the system starts to fail, so you can tune the weak spots or plan what to do when the system nears a limit <Cite n={7} />. The docs say it may also be called a capacity, point load, or limit test <Cite n={7} />.

**When to run it.** Run it when you must know the limits: when the load will grow, when resource use is high, or after a big change to code or infrastructure. After you tune the system, repeat the test to see if the limits moved <Cite n={7} />. Run it only when the system already performs well under the other types <Cite n={7} />. Avoid it in an elastic cloud environment. The environment may grow with the load, and you would only find the limit of your cloud bill. If you must, turn the elasticity off <Cite n={7} />.

**Load shape.** The load rises slowly to an unrealistically high level. There is no plateau and no ramp-down. The test usually fails before it reaches the target, and you must stop it <Cite n={7} />:

```text
iterations/s
20000 |                               #
      |                          #
      |                    #
      |              #
      |        #
   10 +--#--------------------------------> time
       0                                2 h
   (the test stops early, at the first failed threshold)
```

```js
import http from 'k6/http';
import { check } from 'k6';

export const options = {
  scenarios: {
    breakpoint: {
      executor: 'ramping-arrival-rate',
      startRate: 10,
      timeUnit: '1s',
      preAllocatedVUs: 500,
      maxVUs: 5000,
      stages: [{ duration: '2h', target: 20000 }],
    },
  },
  thresholds: {
    http_req_failed: [{ threshold: 'rate<0.05', abortOnFail: true, delayAbortEval: '1m' }],
    http_req_duration: [{ threshold: 'p(95)<2000', abortOnFail: true, delayAbortEval: '1m' }],
  },
};

export default function () {
  const res = http.get('https://quickpizza.grafana.com');
  check(res, { 'status is 200': (r) => r.status === 200 });
}
```

The docs recommend the `ramping-arrival-rate` executor for this type. It keeps raising the rate of new iterations even when the system slows down <Cite n={7} />. Because the executor paces the iterations, the script has no `sleep()` at the end <Cite n={9} />. The executor needs `preAllocatedVUs`. `startRate`, `timeUnit`, and `maxVUs` are optional <Cite n={9} />. All numbers here are example values.

You can stop the test by hand with `Ctrl+C`, or by a threshold with `abortOnFail: true` <Cite n={7} />. `delayAbortEval` waits before the threshold is checked, so the metric has some samples <Cite n={8} />. When a threshold stops the test, you have found a limit.

Failure means different things to different teams. The docs list five points that you may want to find: degraded performance, troublesome performance, timeouts, errors, and system failure <Cite n={7} />. After the run, you can accept the limits and prepare for them, or tune the system and run the test again <Cite n={7} />.

</Technical>

## Key words

| Term | Meaning |
| --- | --- |
| Smoke test | A test with a few VUs for a short time. It checks the script and gives baseline numbers. |
| Average-load test | A test at the typical load of a normal day. Many people call it a load test. |
| Stress test | A test at a load above the average, to see how much performance falls. |
| Spike test | A test with a sudden, massive rise in load and no or a very short plateau. |
| Soak test | An average-load test with a plateau of hours or days. It finds leaks and slow decay. |
| Breakpoint test | A test with a load that rises until the system fails or a threshold stops the test. |
| Ramp-up | The part of a test where the load rises to its target. |
| Plateau | The part of a test where the load stays at its target. |
| `stages` | An option that lists the ramp-up, plateau, and ramp-down steps of a test. |
| `ramping-arrival-rate` | An executor that raises the rate of new iterations, even when the system slows down. |
| `abortOnFail` | A threshold setting that stops the test as soon as the threshold fails. |
