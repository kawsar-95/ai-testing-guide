# Reports and the Web Dashboard

The terminal summary is enough for a quick look, but a team often needs a file or a page to share. k6 can write the summary as JSON or text, show a live web dashboard, save an HTML report, and dump every raw data point.

<PageMeta />

## Pick the right output

<Voices>
<Technical>

k6 gives you 4 ways to get results out of a run. Each one answers a different need.

| You want | Use | Output |
| --- | --- | --- |
| A custom summary: JSON, text, XML, HTML | `handleSummary(data)` <Cite n={1} /> | Any file, `stdout`, or `stderr` |
| A live view and a shareable report | The web dashboard <Cite n={2} /> | A browser page and an HTML file |
| Every raw data point | `--out json=…` or `--out csv=…` <Cite n={4} /> <Cite n={5} /> | A JSON or CSV file |
| The summary as one JSON file, from the command line | `--summary-export` <Cite n={6} /> | A JSON file |

The next sections show each one. The tutorial's own view: start with `handleSummary()` and the dashboard. Use the raw files only when you need to analyze each request.

## Write your own summary with handleSummary

<Voices>
<Technical>

After the test, k6 collects the metrics into one JavaScript object. It passes this object to your `handleSummary()` function. The function is optional <Cite n={1} />. k6 calls it at the end of the test lifecycle <Cite n={1} />.

The function returns a map. Each key says where to put the content. A key is `stdout`, `stderr`, or a path to a file. k6 overwrites a file that already exists. Each value is a string or an `ArrayBuffer` <Cite n={1} />. One return can have several keys <Cite n={1} />.

If your script exports `handleSummary()`, k6 does not print its default summary <Cite n={1} />. To keep a text summary, use `textSummary`, which the k6 JS utilities library exports <Cite n={1} />. The version in the k6 docs is `0.0.2` <Cite n={1} />. The k6 docs say that these helpers can change, so check jslib.k6.io for the latest <Cite n={1} />.

```javascript
import http from 'k6/http';
import { textSummary } from 'https://jslib.k6.io/k6-summary/0.0.2/index.js';

export const options = { vus: 2, duration: '5s' };

export default function () {
  http.get('https://quickpizza.grafana.com/');
}

export function handleSummary(data) {
  return {
    stdout: textSummary(data, { indent: ' ', enableColors: false }),
    'summary.json': JSON.stringify(data),
  };
}
```

`textSummary` has 2 options: `indent` and `enableColors` <Cite n={1} />. This script prints the text summary and writes all the data to `summary.json`.

The output below is one short run of this script on the tutorial's machine. Your numbers will differ.

```text
     http_req_duration..............: avg=340.19ms min=311.2ms  med=338.64ms max=376.46ms p(90)=362.48ms p(95)=371.71ms
       { expected_response:true }...: avg=340.19ms min=311.2ms  med=338.64ms max=376.46ms p(90)=362.48ms p(95)=371.71ms
     http_req_failed................: 0.00%  ✓ 0        ✗ 26
     http_reqs......................: 26     5.081088/s
     iterations.....................: 26     5.081088/s
     vus............................: 2      min=2     max=2
```

All metrics are in the top-level `metrics` object of `data`. For example, `data.metrics.http_req_duration` is the object of that metric <Cite n={1} />. Each metric has a `type`, a `contains`, and a `values` object. A metric with a threshold also has `thresholds`, and each threshold has an `ok` flag <Cite n={1} />. The keys inside `values` for a Trend follow the `summaryTrendStats` option <Cite n={1} />.

In the same run, `summary.json` had the top-level keys `root_group`, `options`, `state`, and `metrics`. The docs describe a newer machine-readable format. k6 v1.5.0 added it, and you turn it on with the `--new-machine-readable-summary` flag <Cite n={1} />. The docs say it will become the default in k6 v2 <Cite n={1} />. So print the file once with your k6 version before you write code that reads it.

You are not limited to JSON. The `handleSummary()` function can turn the data into JSON, HTML, console text, or XML. It can also send the data to a remote server <Cite n={1} />. For example, the `jUnit` helper of the same library makes a JUnit XML file that says if the thresholds failed <Cite n={1} />.

</Technical>

## Use the built-in web dashboard

<Voices>
<Technical>

k6 has a built-in web dashboard. It shows the results in real time while the test runs <Cite n={2} />. Since k6 v2.0.0, the dashboard code is part of the k6 binary, so you do not install an extension <Cite n={7} />. Set the variable `K6_WEB_DASHBOARD` to `true` <Cite n={2} />:

```bash
K6_WEB_DASHBOARD=true k6 run script.js
```

k6 prints the address of the dashboard in its header. The default is localhost, port `5665` <Cite n={2} />. In the check run of this page, k6 v2.3.0 printed this line:

```text
 web dashboard: http://127.0.0.1:5665
        output: -
```

Open the address in a browser while the test runs. You can set the dashboard with these environment variables <Cite n={2} />:

| Variable | Meaning | Default |
| --- | --- | --- |
| `K6_WEB_DASHBOARD` | Turns the dashboard on | `false` |
| `K6_WEB_DASHBOARD_HOST` | The host to bind to | `localhost` |
| `K6_WEB_DASHBOARD_PORT` | The port to bind to | `5665` |
| `K6_WEB_DASHBOARD_PERIOD` | How often the dashboard updates | `10s` |
| `K6_WEB_DASHBOARD_OPEN` | Opens the dashboard in the default browser | `false` |
| `K6_WEB_DASHBOARD_EXPORT` | The file name for an HTML report at the end of the run | empty (no report) |

The k6 process waits to exit while a browser window for the dashboard is open <Cite n={2} />. This is a problem in a CI pipeline. There, the docs advise you to set the port to `-1`, which turns off the HTTP port <Cite n={2} />.

</Technical>

## Save the dashboard as an HTML report

<Voices>
<Technical>

The dashboard can give you a report that is one self-contained HTML file. You share it with your team <Cite n={2} />. There are 2 ways to get it <Cite n={2} />:

- In the dashboard, click **Report** in the menu.
- From the command line, set `K6_WEB_DASHBOARD_EXPORT`. k6 writes the file when the test ends.

```bash
K6_WEB_DASHBOARD=true K6_WEB_DASHBOARD_EXPORT=html-report.html k6 run script.js
```

There is a rule about the length of the test. The report has graphs only if the test lasts more than 3 times the aggregation period <Cite n={2} />. The period is `K6_WEB_DASHBOARD_PERIOD`, and its default is `10s` <Cite n={2} />. So with the default, a test must run for more than 30 seconds.

This page checked the rule. A script with 2 VUs and `duration: '10s'` ran with the default period. k6 v2.3.0 printed a warning and wrote no file:

```text
level=warning msg="The test run was short, report generation was skipped (not enough data)"
```

The same script ran again with `K6_WEB_DASHBOARD_PERIOD=1s`. The 10 second test is then longer than 3 periods, and k6 wrote the HTML file:

```bash
K6_WEB_DASHBOARD=true \
K6_WEB_DASHBOARD_PERIOD=1s \
K6_WEB_DASHBOARD_EXPORT=html-report.html \
k6 run script.js
```

Use a short period only for short practice runs. For a real test, keep the default period and run the test long enough.

The tutorial's owner made an HTML report from `handleSummary()` with a community package that the script loaded from a URL. The built-in export needs no import from a URL, so this page teaches it instead.

</Technical>

টিউটোরিয়ালের মালিক `handleSummary()` থেকে HTML report বানিয়েছিলেন একটা community package দিয়ে, যেটা script একটা URL থেকে লোড করত। built-in export-এ URL থেকে import লাগে না, তাই এই পেজ সেটাই শেখায়।

## Save raw results to a file

<Voices>
<Technical>

The summary has only totals. To get every data point, use the `--out` flag. It writes each sample as k6 collects it.

```bash
k6 run --out json=test_results.json script.js
k6 run --out csv=test_results.csv script.js
```

A file name that ends in `.gz` gives a gzip file <Cite n={4} /> <Cite n={5} />. You can follow a file live with `tail -f` <Cite n={4} /> <Cite n={5} />.

The JSON file has one JSON object on each line. A `Metric` line says that a metric exists. A `Point` line is one sample <Cite n={4} />. A `Point` has a `time`, a `value`, and `tags`. Time values are in milliseconds <Cite n={4} />. The `jq` tool can filter the lines, for example by the metric name <Cite n={4} />.

The 2 lines below are from one short run of a script on the tutorial's machine, with the URL and tags shortened. Your lines will differ.

```text
{"type":"Metric","data":{"name":"http_req_duration","type":"trend","contains":"time","thresholds":[]},"metric":"http_req_duration"}
{"metric":"http_req_duration","type":"Point","data":{"time":"2026-10-27T09:43:31+06:00","value":376.401122,"tags":{"method":"GET","status":"200","scenario":"default"}}}
```

The CSV file has a header line. The columns start with `metric_name`, `timestamp`, and `metric_value`. They go on with the tags, such as `check`, `error`, `group`, `method`, `status`, and `url` <Cite n={5} />. If an error happens, the `error` and `error_code` fields have a value <Cite n={5} />.

These files get large, because they have one line for each sample. A long test with many VUs gives a big file. Use them to analyze requests one by one, not as a report to share.

</Technical>

## Duration and iterations together

<Voices>
<Technical>

The tutorial owner's script had these options:

```javascript
export const options = {
  vus: 100,
  duration: '10s',
  iterations: 100,
};
```

The options `vus` and `duration` alone are a shortcut for one scenario with the constant-VUs executor <Cite n={6} />. The options `vus` and `iterations` alone are a shortcut for one scenario with the shared-iterations executor <Cite n={6} />. When you give all three, the `iterations` shortcut wins. The `duration` option then sets the `maxDuration` of that scenario <Cite n={6} />. The default `maxDuration` is 10 minutes <Cite n={6} />.

So the owner's options mean: run 100 iterations shared among 100 VUs, and stop after 10 seconds if the iterations are not done. The run ends at whichever comes first. This page ran a small version of this to check it, with `vus: 2`, `duration: '5s'` and `iterations: 6`. k6 v2.3.0 printed this scenario line:

```text
default: 6 iterations shared among 2 VUs (maxDuration: 5s, gracefulStop: 30s)
```

The 6 iterations ended in less than 2 seconds, so the run did not wait for 5 seconds. With shared iterations, a faster VU completes more iterations than the others <Cite n={6} />. So 100 VUs and 100 iterations do not always give one iteration for each VU.

The tutorial's own advice: set the duration or the iterations, not both, unless you want a time limit as a safety net. It keeps the meaning of the test clear.

</Technical>

## Key words

| Term | Meaning |
| --- | --- |
| `handleSummary(data)` | A function that k6 calls at the end of the test. It returns where to put the summary: `stdout`, `stderr`, or files <Cite n={1} />. |
| `textSummary` | A helper from the k6 JS utilities library. It makes the text summary that k6 prints by default <Cite n={1} />. |
| Web dashboard | A built-in page that shows results in real time. You turn it on with `K6_WEB_DASHBOARD=true` <Cite n={2} />. |
| `K6_WEB_DASHBOARD_EXPORT` | The file name for an HTML report at the end of the run <Cite n={2} />. |
| Aggregation period | How often the dashboard updates (`K6_WEB_DASHBOARD_PERIOD`, default `10s`). A report has graphs only if the test lasts more than 3 periods <Cite n={2} />. |
| `--out json=…` and `--out csv=…` | Flags that write every data point to a file <Cite n={4} /> <Cite n={5} />. |
| `--summary-export` | A flag that saves the summary to a JSON file. The docs discourage it, and prefer `handleSummary()` <Cite n={6} />. |
| `--summary-mode` | A flag that sets the end-of-test summary: `compact` (default), `full`, or `disabled` <Cite n={7} /> <Cite n={6} />. |
| Shared iterations | An executor that shares a fixed number of iterations among the VUs. The shortcut `vus` plus `iterations` uses it <Cite n={6} />. |
