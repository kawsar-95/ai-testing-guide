# Environment Variables and Test Data

Pass settings with __ENV and load test data from a CSV file.

<PageMeta />

## Why pass values from outside the script

<Voices>
<Technical>

A script often needs only small changes to run in another place. The base URL, the user name, and the number of VUs are examples. You can write one script and use environment variables to change these parts <Cite n={1} />. This gives two benefits.

1. **No hardcoded values.** You do not edit the code each time. One script runs on Dev, QA, and Prod with different values.
2. **Secrets stay out of the script file.** A password or a token is not in the code or in a file in the repository. You pass it when you start the run.

The second benefit needs care. This is the tutorial's own view, not a claim of the k6 docs. A value that you pass with `-e` is out of your code, but k6 does not hide it. The k6 docs say that values from secret sources are redacted from logs, unlike values from environment variables or files <Cite n={6} />. So a script that prints the value shows it in the log. The section "Keep secrets out of the logs" shows the safer way.

</Technical>

## Pass values with __ENV and -e

<Voices>
<Technical>

k6 gives the environment variables to the script in a global JavaScript object named `__ENV` <Cite n={1} />. The recommended way to set them is one or more `-e` (or `--env`) flags on the command line <Cite n={1} />.

This script is the tutorial's login and search flow. It reads every setting from `__ENV`. It uses `||` to give a default when a variable is not set. The host `https://api.example.com` and all values are placeholders.

```javascript
import http from 'k6/http';
import { check, sleep } from 'k6';

const baseUrl = __ENV.BASE_URL;

export const options = {
  vus: __ENV.VUS ? parseInt(__ENV.VUS) : 1,
  duration: __ENV.DURATION || '1s',
};

export default function () {
  const payload = JSON.stringify({
    email: __ENV.LOGIN_EMAIL,
    password: __ENV.LOGIN_PASSWORD,
  });
  const headers = { 'Content-Type': 'application/json' };

  const loginRes = http.post(`${baseUrl}/user/login`, payload, { headers });
  check(loginRes, {
    'login status is 200': (r) => r.status === 200,
    'login token is present': (r) => r.json('token') !== undefined,
  });

  const token = loginRes.json('token');
  const searchRes = http.get(`${baseUrl}/user/search/id/${__ENV.SEARCH_USER_ID}`, {
    headers: { Authorization: `Bearer ${token}`, 'Content-Type': 'application/json' },
  });
  check(searchRes, {
    'search status is 200': (r) => r.status === 200,
  });

  sleep(1);
}
```

Run it with one `-e` flag for each variable:

```bash
k6 run \
  -e BASE_URL=https://api.example.com \
  -e LOGIN_EMAIL=tester@example.com \
  -e LOGIN_PASSWORD=change-me \
  -e SEARCH_USER_ID=1001 \
  -e VUS=1 -e DURATION=1s \
  index.js
```

The script does not print the token. The tutorial's own advice is to keep it that way, because a printed token goes into the log.

The `-e` flag only gives variables to the script. It does not set k6 options. For example, `-e K6_ITERATIONS=120` does not set the number of iterations <Cite n={1} /><Cite n={2} />. This is why the script reads `__ENV.VUS` and puts it into `options` itself.

By default, `__ENV` is a plain object that the script can change. The `freeze-env` feature flag makes it read-only <Cite n={1} />.

</Technical>

## System environment variables

<Voices>
<Technical>

You can also set a variable in the shell before `k6 run`. k6 then reads it from the system <Cite n={1} />:

```bash
MY_HOSTNAME=test.example.com k6 run script.js
```

For `k6 run`, the `--include-system-env-vars` option is `true` by default. So `__ENV` has your system variables. For all other commands the default is `false`, to prevent inadvertent leaks of sensitive data <Cite n={2} />. For example, `k6 inspect`, `k6 archive`, and `k6 cloud run` get no system variables by default. The docs give a reason: k6 Cloud must not get sensitive data by mistake. To change it, give the `--include-system-env-vars` option <Cite n={1} />.

A variable with the `K6_` prefix is different. k6 reads it as an option. `K6_VUS=5 K6_DURATION=20s k6 run script.js` runs 5 VUs for 20 seconds. Not every option has such a variable <Cite n={1} />.

When you set an option in more than one place, an order of precedence decides which value k6 uses. Command-line flags have the highest precedence <Cite n={1} />.

</Technical>

## Keep secrets out of the logs

<Voices>
<Technical>

A secret source is a way to give secrets to k6. The k6 docs say that values from secret sources are redacted from the logs. Values from environment variables or files are not <Cite n={6} />.

You set a source with the `--secret-source` flag. The built-in sources for local tests are `file` (a `key=value` file), `mock` (values from CLI arguments), and `url` (values from an HTTP endpoint) <Cite n={6} />. The script reads a secret with the `k6/secrets` API <Cite n={6} />. This script reads the password from a secret source and the e-mail from `__ENV`:

```javascript
import http from 'k6/http';
import secrets from 'k6/secrets';

export default async function () {
  const password = await secrets.get('login_password');
  http.post('https://api.example.com/user/login', JSON.stringify({
    email: __ENV.LOGIN_EMAIL,
    password,
  }), { headers: { 'Content-Type': 'application/json' } });
}
```

The `secrets.txt` file has one `key=value` line:

```text
login_password=placeholder
```

Run it with the `file` source:

```bash
k6 run --secret-source=file=secrets.txt -e LOGIN_EMAIL=tester@example.com index.js
```

If the script prints a secret, the log shows `***SECRET_REDACTED***`. The script can still use the real value <Cite n={6} />. This output is from a k6 v2.3.0 check with a script that logs a secret and a normal `-e` value:

```text
level=info msg="password is ***SECRET_REDACTED***" source=console
level=info msg="env is visible" source=console
```

Keep the secret file out of the repository. This is the tutorial's own advice.

</Technical>

## Read data from a CSV file

<Voices>
<Technical>

A load test with one fixed value is not realistic. Parameterization turns test values into inputs, so each request can use other data. The k6 docs say it also helps to stop server-side caching from affecting the test <Cite n={5} />.

The function `open()` reads a whole file into memory. You can call it only in the init context, which is the code outside the default function <Cite n={3} />. Every VU keeps its own copy of the file <Cite n={3} />. Each VU is a separate JavaScript VM <Cite n={5} />. So a big file can use too much memory <Cite n={5} />.

`SharedArray` from `k6/data` fixes this. It shares the memory between VUs. Its function runs only once, and k6 keeps the result in memory once. When the script asks for an element, k6 gives a copy of it <Cite n={4} />. A `SharedArray` has a small CPU cost to read elements, but the docs say it is negligible next to the time of the requests <Cite n={5} />. You must build it in the init context. It is read-only, so VUs cannot use it to send data to each other <Cite n={4} />.

Here the file `users.csv` has one user id on each line. The owner's script reads it this way:

```text
1001
1002
1003
```

```javascript
import http from 'k6/http';
import { check, sleep } from 'k6';
import { SharedArray } from 'k6/data';

const userIds = new SharedArray('userIds', function () {
  return open('./users.csv')
    .split('\n')
    .map((line) => line.trim())
    .filter(Boolean);
});

export const options = { vus: 2, duration: '1s' };

export default function () {
  const userId = userIds[__ITER % userIds.length];
  const res = http.get(`https://api.example.com/user/search/id/${userId}`);
  check(res, { 'search status is 200': (r) => r.status === 200 });
  sleep(1);
}
```

How the constructor works:

- `open('./users.csv')` reads the whole file as one string <Cite n={3} />.
- `.split('\n')` makes one array item for each line.
- `.map((line) => line.trim())` removes spaces at the start and the end of each id.
- `.filter(Boolean)` removes the empty lines.

The `.map()` and `.filter()` calls are inside the constructor, so they run once. This is important. When you call `.map()` or `.filter()` on a `SharedArray` outside the constructor, you get a regular array and lose the memory benefit <Cite n={4} />.

`__ITER % userIds.length` picks a row. `__ITER` is the zero-based iteration number of one VU <Cite n={7} />. The `%` operator goes back to the first row after the last one.

</Technical>

## Parse a CSV file with Papa Parse

<Voices>
<Technical>

k6 does not parse CSV files by itself. The docs use an outside library, Papa Parse. You can download it and import it from a local file. You can also import it from `jslib.k6.io` <Cite n={5} />. With `header: true`, each row becomes an object, and the first line gives the keys <Cite n={9} />.

The file `data.csv` has a header line:

```text
username,password
user1,pass1
user2,pass2
```

```javascript
import http from 'k6/http';
import { check, sleep } from 'k6';
import { SharedArray } from 'k6/data';
import papaparse from 'https://jslib.k6.io/papaparse/5.1.1/index.js';

const users = new SharedArray('users', function () {
  return papaparse.parse(open('./data.csv'), { header: true, skipEmptyLines: true }).data;
});

export default function () {
  const user = users[Math.floor(Math.random() * users.length)];
  const res = http.post('https://api.example.com/user/login', JSON.stringify({
    email: user.username,
    password: user.password,
  }), { headers: { 'Content-Type': 'application/json' } });
  check(res, { 'login status is 200': (r) => r.status === 200 });
  sleep(1);
}
```

The parse is inside the `SharedArray` function, so it runs once and every VU shares the result <Cite n={5} />. This script picks a random row. The values are placeholders. Do not put real passwords in a CSV file in the repository.

</Technical>

## Use unique data for each VU and iteration

<Voices>
<Technical>

Sometimes a test must not use the same row two times. The `k6/execution` module gives the numbers for this <Cite n={5} />. The property `scenario.iterationInTest` is a zero-based number that is unique for the scenario <Cite n={8} />. The note in the docs says it is unique for each scenario, not for the whole test. With more than one scenario, you may need to split the data for each scenario <Cite n={5} />.

This script uses the `shared-iterations` executor with `iterations: userIds.length`, so each row is used one time <Cite n={5} />:

```javascript
import http from 'k6/http';
import { SharedArray } from 'k6/data';
import exec from 'k6/execution';

const userIds = new SharedArray('userIds', function () {
  return open('./users.csv')
    .split('\n')
    .map((line) => line.trim())
    .filter(Boolean);
});

export const options = {
  scenarios: {
    use_all_rows: {
      executor: 'shared-iterations',
      vus: 2,
      iterations: userIds.length,
      maxDuration: '1m',
    },
  },
};

export default function () {
  const userId = userIds[exec.scenario.iterationInTest];
  http.get(`https://api.example.com/user/search/id/${userId}`);
}
```

To give each VU its own row, use `exec.vu.idInTest`. It is the VU identifier, and it is unique in the whole test run <Cite n={8} />. VU identifiers start at one and arrays start at zero, so subtract 1 <Cite n={5} />.

Older k6 versions have no `k6/execution` module. They use the globals `__VU` and `__ITER` <Cite n={7} />. `__VU` is the VU number, counted from 1. It is 0 in setup and teardown. `__ITER` is the zero-based iteration counter of one VU <Cite n={7} />. Two VUs both have `__ITER` 0 for their first iteration. So `__ITER` alone does not give unique rows across VUs. The tutorial's own check ran k6 v2.3.0 with 2 VUs and 4 iterations. It printed `VU 1 ITER 0`, `VU 1 ITER 1`, `VU 1 ITER 2`, and `VU 2 ITER 0`. The split of iterations between VUs can differ from run to run.

</Technical>

## Key words

| Term | Meaning |
| --- | --- |
| `__ENV` | A global object in the script. It holds the environment variables that k6 gives to the script <Cite n={1} />. |
| `-e` / `--env` | A flag of `k6 run`. It gives a variable to the script. It does not set an option <Cite n={1} />. |
| `--include-system-env-vars` | An option that puts the system variables in `__ENV`. It is `true` for `k6 run` and `false` for other commands <Cite n={2} />. |
| `K6_` prefix | A system variable with this prefix sets a k6 option, for example `K6_VUS` <Cite n={1} />. |
| Secret source | A way to give secrets to k6. k6 redacts these values in the logs <Cite n={6} />. |
| `open()` | A function that reads a file into memory. It works only in the init context <Cite n={3} />. |
| `SharedArray` | An array-like, read-only object that shares memory between VUs <Cite n={4} />. |
| Parameterization | Turning test values into inputs, so requests use different data <Cite n={5} />. |
| Papa Parse | An outside library that parses CSV files in k6 <Cite n={5} />. |
| `scenario.iterationInTest` | A zero-based iteration number that is unique in a scenario <Cite n={8} />. |
| `vu.idInTest` | The VU identifier, unique in the whole test run. It starts at 1 <Cite n={8} /><Cite n={5} />. |
| `__VU` / `__ITER` | Older globals: the VU number and the iteration counter of one VU <Cite n={7} />. |
