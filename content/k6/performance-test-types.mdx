# Types of Performance Testing

Performance testing is not one test. Each type asks a different question about the system, so each type uses a different load shape and a different duration.

<PageMeta />

## Why one test is not enough

<Voices>
<Technical>

The k6 guide says that different traffic patterns give different risk profiles <Cite n={1} />. So teams run several test types. No single type removes all risk <Cite n={1} />.

This page covers the five types in the owner's notes and adds soak testing:

- **Capacity test:** how many users the system handles at an acceptable level.
- **Load test:** how the system behaves under the expected load.
- **Stress test:** how the system behaves when the load grows step by step.
- **Volume test:** whether the software handles and processes a large amount of data at once without breaking, slowing down, or losing information.
- **Spike test:** how the system behaves when a huge load arrives in a short time.
- **Soak test:** how the system behaves when a normal load runs for a very long time.

The k6 documentation names six types: smoke, average-load, stress, soak, spike, and breakpoint <Cite n={1} />. The next sections map the two lists to each other. The mapping is the tutorial's own reading of the sources. Part 5 has a k6 script for each k6 type: see [Smoke, Load, Stress, Spike, Soak, and Breakpoint Tests](/k6/k6-test-types/).

## Compare the types

<Voices>
<Technical>

The table shows the goal, the load shape, and the duration of each type. The k6 columns follow the k6 cheat sheet <Cite n={1} />. The volume row is not in the k6 cheat sheet.

| Type (k6 name) | Goal | Load shape | Duration |
| --- | --- | --- | --- |
| Smoke | Check that the script and the system work under minimal load, and get a baseline <Cite n={3} /> | Low: a few VUs <Cite n={3} /> | Short: seconds or minutes <Cite n={1} /> |
| Load (average-load) | Check performance under typical load <Cite n={2} /> | Ramp up, hold the average, ramp down <Cite n={2} /> | Mid: 5 to 60 minutes <Cite n={1} /> |
| Stress | Check performance when the load is heavier than usual <Cite n={4} /> | Like average-load, but higher, with a longer ramp-up <Cite n={4} /> | Mid: 5 to 60 minutes <Cite n={1} /> |
| Spike | Check if the system survives a sudden, massive rush <Cite n={5} /> | Very fast ramp-up to a very high load, a brief plateau or none <Cite n={5} /> | Short: a few minutes <Cite n={1} /> |
| Soak | Find problems that show only after long use <Cite n={6} /> | Like average-load, with a much longer plateau <Cite n={6} /> | Long: hours <Cite n={1} /> |
| Breakpoint (capacity) | Find the limits of the system <Cite n={7} /> | Ramps up until the system fails <Cite n={7} /> | As long as necessary <Cite n={1} /> |
| Volume | Check that a large amount of data is handled without loss | Not a user count: the size of the data | Depends on the data |

The volume row is the owner's definition. It has no k6 test type and no cite.

**Smoke.** The k6 guide says to run a smoke test each time you create or change a test script. It also finds errors in the system under minimal load <Cite n={3} />. It is the first test to run <Cite n={1} />.

**Load (average-load).** The load matches a typical day in production: how many users are active at once, and how many requests arrive each second <Cite n={2} />. The guide gives a ramp-up of 5 to 15 percent of the test duration. It advises a plateau that lasts five times the ramp-up or more <Cite n={2} />.

**Stress.** The k6 guide gives no fixed percentage above the average. The load depends on the risk patterns of the system. It can be a few percent above the average, or 50 to 100 percent <Cite n={4} />. Run stress tests only after average-load tests <Cite n={4} />.

**Spike.** The test often does not finish, and errors are common. Backend monitoring is a must <Cite n={5} />. Real users do not stay long in such a rush, so the plateau is brief or missing <Cite n={5} />.

**Soak.** The k6 guide says a soak test must run considerably longer than any other test. It gives values from 3 hours up to 72 hours <Cite n={6} />. It names four defects that show only after long use: slower responses, leaks of memory or other resources, full data stores, and used-up storage <Cite n={6} />.

**Breakpoint (capacity).** The load rises to unrealistically high numbers. The test is stopped by hand, or by failing thresholds <Cite n={7} />. The k6 guide advises against running it in an elastic cloud environment. The environment may grow, and the test then finds only the limit of your cloud bill <Cite n={7} />.

For every type, keep the shape simple: ramp up, plateau, ramp down. Avoid "rollercoaster" tests where the load rises and falls many times <Cite n={1} />.

</Technical>

**Smoke।** k6 গাইড বলে, প্রতিবার টেস্ট স্ক্রিপ্ট বানালে বা বদলালে একটা smoke test চালান। ন্যূনতম load-এ সিস্টেমের এরর-ও এটা ধরে <Cite n={3} />। এটাই প্রথমে চালানোর টেস্ট <Cite n={1} />।

**Load (average-load)।** load মেলে production-এর একটা typical দিনের সঙ্গে: একসাথে কতজন ইউজার সক্রিয়, আর প্রতি সেকেন্ডে কয়টা request আসে <Cite n={2} />। ramp-up নেয় টেস্টের সময়ের ৫ থেকে ১৫ শতাংশ। plateau থাকে ramp-up-এর অন্তত পাঁচগুণ লম্বা <Cite n={2} />।

**Stress।** k6 গাইড গড়ের উপরে কোনো নির্দিষ্ট শতাংশ দেয় না। load নির্ভর করে সিস্টেমের ঝুঁকির প্যাটার্নের উপর। এটা গড়ের চেয়ে কয়েক শতাংশ বেশি হতে পারে, বা ৫০ থেকে ১০০ শতাংশ <Cite n={4} />। stress test চালান শুধু average-load টেস্টের পরে <Cite n={4} />।

**Spike।** টেস্ট প্রায়ই শেষ হয় না, আর এরর সাধারণ। backend monitoring অবশ্যই দরকার <Cite n={5} />। এমন ভিড়ে আসল ইউজার বেশিক্ষণ থাকে না, তাই plateau ছোট বা নেই <Cite n={5} />।

**Soak।** k6 গাইড বলে, soak test অন্য যেকোনো টেস্টের চেয়ে অনেক লম্বা সময় চালাতে হয়। এতে ৩ ঘণ্টা থেকে ৭২ ঘণ্টা পর্যন্ত মান দেওয়া আছে <Cite n={6} />। লম্বা ব্যবহারের পরে দেখা দেয় এমন চারটা ত্রুটির নাম আছে: ধীর response, memory বা অন্য resource-এর leak, ভরে যাওয়া data store, আর শেষ হয়ে যাওয়া storage <Cite n={6} />।

**Breakpoint (capacity)।** load অবাস্তব উঁচু সংখ্যায় ওঠে। আপনি হাতে টেস্ট থামান, অথবা ফেইল হওয়া threshold তা থামায় <Cite n={7} />। elastic cloud environment-এ এটা চালাবেন না। environment বড় হয়ে যেতে পারে, আর তখন টেস্ট শুধু আপনার cloud বিলের সীমা খুঁজে পায় <Cite n={7} />।

সব টাইপে আকার সহজ রাখুন: ramp up, plateau, ramp down। "rollercoaster" টেস্ট এড়ান, যেখানে load বহুবার ওঠে আর নামে <Cite n={1} />।

## Names differ between sources

<Voices>
<Technical>

The k6 documentation says that no consensus exists about the names of the test types <Cite n={1} />. Each k6 guide lists other names for its type:

| k6 name | Other names in the k6 guides |
| --- | --- |
| Smoke | shakeout <Cite n={3} /> |
| Average-load | day-in-life, volume <Cite n={2} /> |
| Stress | rush-hour, surge, scale <Cite n={4} /> |
| Soak | endurance, constant high load, stamina <Cite n={6} /> |
| Breakpoint | capacity, point load, limit <Cite n={7} /> |

The k6 guide for spike testing lists no other names <Cite n={5} />.

Here is how the owner's names map to the k6 names. This mapping is the tutorial's own reading.

| Owner's name | Closest k6 name | Note |
| --- | --- | --- |
| Capacity | Breakpoint | The k6 guide lists "capacity" as another name for breakpoint <Cite n={7} />. |
| Load | Average-load | The k6 guide uses "average-load" because "load test" can mean all traffic tests <Cite n={2} />. |
| Stress | Stress (or breakpoint) | The owner says "gradually increase the load". The k6 stress test raises the load above average <Cite n={4} />. The k6 breakpoint test raises it gradually until the system fails <Cite n={7} />. |
| Volume | None | The k6 guide lists "volume" as another name for average-load <Cite n={2} />. The owner means a large amount of data. Check which meaning a team uses. |
| Spike | Spike | The same idea <Cite n={5} />. |
| Soak (added) | Soak | The k6 guide lists "endurance" as another name <Cite n={6} />. |

The ISTQB glossary, a standard source of testing terms, gives its own definitions. They are close to the k6 ideas but not the same:

- **Load testing:** a kind of performance testing. It checks a component or system under different loads. The loads are usually between low, typical, and peak use <Cite n={8} />. This is wider than the k6 average-load test.
- **Stress testing:** testing at the limits of the expected workload, or beyond them. It can also reduce resources, such as memory or servers <Cite n={9} />.
- **Spike testing:** testing if a system can recover after a sudden burst of peak load. The system must return to a steady state <Cite n={10} />.
- **Endurance testing:** testing if a system stays stable under a significant load for a long time <Cite n={11} />. This is the idea of a soak test.

## Key words

| Term | Meaning |
| --- | --- |
| Load shape | How the number of users or requests changes over time: ramp up, plateau, ramp down. |
| VU (virtual user) | One simulated user in a k6 test. |
| Ramp-up | The period where the load rises from zero to the target. |
| Plateau | The period where the load stays at the target. |
| Smoke test | A test with minimal load that checks the script and the system, and gives a baseline. |
| Average-load test | A test at the typical production load. Many sources call it a load test. |
| Stress test | A test with a load heavier than usual. |
| Spike test | A test with a sudden, massive rise in load. |
| Soak test | A test with a normal load for hours or days. Also called an endurance test. |
| Breakpoint test | A test where the load rises until the system fails. Also called a capacity test. |
| Volume test | A test of how the system handles a large amount of data. This is the owner's meaning. |
