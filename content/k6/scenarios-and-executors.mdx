# Scenarios and Executors

Real users do not all do the same thing. A scenario lets one script run several kinds of user work at the same time, and an executor decides how k6 schedules the VUs and iterations of each scenario.

<PageMeta />

## Why one script needs many scenarios

<Voices>
<Technical>

Until now, one script had one flow and one load shape. Real traffic is a mix. In a mobile wallet, some users recharge a phone, some send money, some withdraw cash, some pay a shop, and some pay a bill. A **scenario** configures the VU and iteration schedule in detail, so that one script can model this mix <Cite n={1} />.

The benefits of scenarios are these <Cite n={1} />:

- You can declare many scenarios in one script. Each one can run a different JavaScript function.
- Each scenario can have its own VU and iteration pattern.
- Scenarios are independent and run in parallel. You can make them look sequential with `startTime`.
- You can set environment variables and tags for each scenario, so the results are easier to split.

You set scenarios with the `scenarios` key of the `options` object. The scenario name must be unique in the script. It shows in the result summary and in the tags <Cite n={1} />.

</Technical>

## A traffic-mix example

<Voices>
<Technical>

This is the tutorial's own example, from the owner's notes. A mobile wallet handles 100,000 transactions each day. The owner splits the users like this. The split is the tutorial's own assumption. It is not a measured fact.

| Operation | Share of users | Scenario name |
| --- | --- | --- |
| Mobile recharge | 50 % | `recharge` |
| Send money | 20 % | `sendMoney` |
| Withdraw money | 10 % | `withdrawMoney` |
| Merchant payment | 10 % | `merchantPayment` |
| Utility bill payment | 10 % | `utilityPayment` |

The notes use one `constant-vus` scenario for each operation, and 100,000 VUs in total. One machine has limits. The k6 docs say that one k6 instance can run about 30,000 to 40,000 VUs when the machine and the script are tuned <Cite n={5} />. For a larger test, the docs say that you can split the load over many k6 instances, and that Grafana Cloud k6 runs large tests for you <Cite n={5} />. So 100,000 VUs needs distributed or cloud execution.

For learning, keep the same split and make the scale 1,000 times smaller: 50, 20, 10, 10, and 10 VUs for 1 minute. The script below has the same shape, and it runs on a laptop. The host `https://wallet.example.com` is a placeholder. Point the script at your own test system, not at a real service.

```javascript
import http from 'k6/http';
import { sleep } from 'k6';

export const options = {
  scenarios: {
    recharge: { executor: 'constant-vus', vus: 50, duration: '1m', exec: 'recharge' },
    sendMoney: { executor: 'constant-vus', vus: 20, duration: '1m', exec: 'sendMoney' },
    withdrawMoney: { executor: 'constant-vus', vus: 10, duration: '1m', exec: 'withdrawMoney' },
    merchantPayment: { executor: 'constant-vus', vus: 10, duration: '1m', exec: 'merchantPayment' },
    utilityPayment: { executor: 'constant-vus', vus: 10, duration: '1m', exec: 'utilityPayment' },
  },
};

const BASE_URL = 'https://wallet.example.com';

function call(path) {
  http.post(`${BASE_URL}${path}`, JSON.stringify({ amount: 100 }), {
    headers: { 'Content-Type': 'application/json' },
  });
  sleep(1);
}

export function recharge() { call('/recharge'); }
export function sendMoney() { call('/sendMoney'); }
export function withdrawMoney() { call('/withdrawMoney'); }
export function merchantPayment() { call('/merchantPayment'); }
export function utilityPayment() { call('/utilityPayment'); }
```

Each scenario has three parts:

- `executor: 'constant-vus'` keeps a fixed number of VUs busy for the whole `duration` <Cite n={10} />.
- `vus` is that number. Here it is the share of the 100 VUs.
- `exec` is the name of the exported function that the scenario runs <Cite n={1} />. Without `exec`, a scenario runs the default function <Cite n={1} />.

So the `recharge` scenario runs 50 VUs for 1 minute, and each VU runs `recharge()` again and again. All five scenarios start together and run in parallel <Cite n={1} />.

</Technical>

## Common scenario options

<Voices>
<Technical>

Every scenario takes the `executor` option, which is required, and a set of common options <Cite n={1} />:

| Option | What it does | Default |
| --- | --- | --- |
| `executor` | The name of the executor. | None (required) |
| `startTime` | The time offset from the test start at which the scenario begins. | `"0s"` |
| `gracefulStop` | How long k6 waits for running iterations to finish before it stops them by force. | `"30s"` |
| `exec` | The name of the exported function to run. | `"default"` |
| `env` | Environment variables for this scenario only. | `{}` |
| `tags` | Tags for this scenario only. | `{}` |

Every executor accepts `gracefulStop` <Cite n={12} />. A forced stop in the middle of an iteration can skew the metrics, and a graceful stop avoids this <Cite n={12} />.

The script below runs two scenarios. `browse` starts at once. `checkout` starts after 10 seconds, so it overlaps with `browse`. It has its own `env` and `tags`, and each scenario runs its own function. The script uses the QuickPizza demo site, which the k6 docs use for examples.

```javascript
import http from 'k6/http';

export const options = {
  scenarios: {
    browse: {
      executor: 'constant-vus',
      vus: 5,
      duration: '30s',
      exec: 'browse',
    },
    checkout: {
      executor: 'per-vu-iterations',
      vus: 2,
      iterations: 5,
      startTime: '10s',
      gracefulStop: '5s',
      exec: 'checkout',
      env: { STEP: 'checkout' },
      tags: { flow: 'checkout' },
    },
  },
};

export function browse() {
  http.get('https://quickpizza.grafana.com/');
}

export function checkout() {
  http.get(`https://quickpizza.grafana.com/?step=${__ENV.STEP}`);
}
```

When you run a script with scenarios, the k6 output gives high-level information about each scenario <Cite n={1} />. You can set tags for each scenario with the `tags` option <Cite n={1} />.

</Technical>

## The executors

<Voices>
<Technical>

An **executor** schedules the VU workload of one scenario. It decides how long the scenario runs, whether the load stays constant or changes, and whether k6 models the load by VUs or by arrival rate <Cite n={1} />. You write its name in the `executor` key, with hyphens <Cite n={2} />. These are the six current executors <Cite n={2} />:

| Executor | Value | What it does | Model |
| --- | --- | --- | --- |
| Shared iterations | `shared-iterations` | A fixed number of iterations is shared between a number of VUs <Cite n={2} />. The test ends when all iterations are done <Cite n={8} />. | Closed |
| Per VU iterations | `per-vu-iterations` | Each VU runs an exact number of iterations <Cite n={2} />. The total is `vus * iterations` <Cite n={9} />. | Closed |
| Constant VUs | `constant-vus` | A fixed number of VUs run as many iterations as possible for a set time <Cite n={2} />. | Closed |
| Ramping VUs | `ramping-vus` | A variable number of VUs run as many iterations as possible for a set time <Cite n={2} />. | Closed |
| Constant arrival rate | `constant-arrival-rate` | A fixed number of iterations start in a set period <Cite n={2} />. | Open |
| Ramping arrival rate | `ramping-arrival-rate` | A variable number of iterations start in a set period <Cite n={2} />. | Open |

The model column follows the next section: the arrival-rate executors use the open model, and the other executors use the closed model <Cite n={3} />.

When to use each one <Cite n={8} /> <Cite n={9} /> <Cite n={10} /> <Cite n={11} /> <Cite n={7} />:

- `shared-iterations`: you want a fixed amount of work and you care about the time to finish. A quick check in the development cycle is a good use. The number of iterations for each VU is not important.
- `per-vu-iterations`: each VU must do the same number of iterations. This helps when you split a fixed set of test data between VUs.
- `constant-vus`: you need a fixed number of VUs for a set time.
- `ramping-vus`: the number of VUs must go up or down in `stages`. Its extra options include `startVUs` and `gracefulRampDown`.
- `constant-arrival-rate` and `ramping-arrival-rate`: you want iterations to start at a set rate, whatever the system does. The ramping type changes the rate in `stages`, with `startRate` and `timeUnit`.

The `vus` and `duration` options, the `vus` and `iterations` options, and the `stages` option are shortcuts for `constant-vus`, `shared-iterations`, and `ramping-vus` <Cite n={10} /> <Cite n={8} /> <Cite n={11} />. You used these shortcuts in the earlier pages.

## Open and closed models

<Voices>
<Technical>

The executors schedule VUs in two different ways. Some use the **closed model**. The arrival-rate executors use the **open model** <Cite n={3} />. In the closed model, a VU starts its next iteration only when the last one ends. In the open model, iterations start on their own schedule, whether or not earlier ones have ended <Cite n={3} />.

**Closed model.** The run time of each iteration decides how many iterations the test runs <Cite n={3} />. The docs give an example: one VU with `constant-vus`, and a request that takes about 6 seconds. New iterations start about once every 6 seconds, so a 1-minute test gets about 10 iterations <Cite n={3} />.

A closed model has a drawback. When the system under test gets slower, each iteration takes longer, and k6 starts new iterations less often <Cite n={3} />. The load on the system goes down just when the system is under stress. The docs call this problem *coordinated omission* <Cite n={3} />. It is a bad fit when you want to simulate a set arrival rate or a set number of requests per second <Cite n={3} />.

**Open model.** The open model separates the start of new iterations from the run time of iterations. The response time of the system no longer changes the load <Cite n={3} />. In the docs example, `constant-arrival-rate` starts 1 iteration every second, even with a 6-second request. A 1-minute test gets 60 iterations <Cite n={3} />. For this, k6 uses more VUs at the same time. The docs output shows 11 VUs for that run <Cite n={3} />.

The tutorial's own rule of thumb: use a closed model when you care about "N users doing things", and an open model when you care about "N requests or arrivals every second".

</Technical>

## An arrival-rate example

<Voices>
<Technical>

This script uses `constant-arrival-rate` to start 5 iterations every second for 30 seconds. It pre-allocates 5 VUs and lets k6 add more, up to 20, if the system gets slower.

```javascript
import http from 'k6/http';

export const options = {
  scenarios: {
    steady_rate: {
      executor: 'constant-arrival-rate',
      rate: 5,
      timeUnit: '1s',
      duration: '30s',
      preAllocatedVUs: 5,
      maxVUs: 20,
    },
  },
};

export default function () {
  http.get('https://quickpizza.grafana.com/');
}
```

The options of this executor are these <Cite n={4} />:

| Option | Meaning | Default |
| --- | --- | --- |
| `duration` | The total scenario time, without `gracefulStop`. Required. | None |
| `rate` | How many iterations start in each `timeUnit`. Required. | None |
| `preAllocatedVUs` | How many VUs k6 makes before the test starts, to save resources at run time. Required. | None |
| `timeUnit` | The period that the `rate` applies to. | `"1s"` |
| `maxVUs` | The most VUs that k6 may use in the run. | The same as `preAllocatedVUs` |

How it works:

- While VUs are free, the executor keeps starting iterations at your rate <Cite n={4} />. If iterations get slower, it starts more VUs to keep the rate <Cite n={4} />.
- With the arrival-rate executors, k6 drops iterations when no VU is free, and it counts them in the `dropped_iterations` metric <Cite n={13} />. A `maxVUs` that is too low can cause this. If you set `preAllocatedVUs` too low, k6 must make VUs during the test, and the test spends less time at the target rate <Cite n={4} />.
- Do not put `sleep()` at the end of the VU code. The `rate` and `timeUnit` already set the pace <Cite n={4} />.
- Iterations do not start at the same instant. If `rate` is 10 per second (`timeUnit` of `1s`), one iteration starts about every 100 ms <Cite n={4} />.

The `ramping-arrival-rate` executor works in the same way, but it takes `stages` with a target rate for each stage, and it has `startRate` as well <Cite n={7} />.

A loop over a list of 13 flows builds one `constant-arrival-rate` scenario for each flow, and `startTime` puts each flow in its time window. This is the tutorial's own example project, not an official source.

Technical টেক্সটের স্ক্রিপ্ট `constant-arrival-rate` দিয়ে ৩০ সেকেন্ড ধরে প্রতি সেকেন্ডে ৫টা iteration শুরু করে। এটা ৫টা VU আগে থেকে তৈরি (pre-allocate) করে রাখে। সিস্টেম ধীর হলে k6 ২০ পর্যন্ত আরও VU যোগ করতে পারে।

কীভাবে কাজ করে। VU খালি থাকলে executor দেওয়া হারে iteration শুরু করতে থাকে <Cite n={4} />। iteration ধীর হলে হার ধরে রাখতে সে আরও VU চালু করে <Cite n={4} />। arrival-rate executor-এ কোনো VU খালি না থাকলে k6 iteration বাদ দেয় (drop করে) এবং `dropped_iterations` metric-এ গোনে <Cite n={13} />। `maxVUs` খুব কম হলে এটা ঘটতে পারে। `preAllocatedVUs` খুব কম দিলে k6-কে টেস্টের সময় VU বানাতে হয়। তখন টেস্ট টার্গেট রেটে কম সময় থাকে <Cite n={4} />।

VU code-এর শেষে `sleep()` দেবেন না। `rate` আর `timeUnit` আগেই গতি ঠিক করে দেয় <Cite n={4} />। iteration গুলো ঠিক একই মুহূর্তে শুরু হয় না। `timeUnit` `1s` আর `rate` ১০ হলে প্রায় প্রতি ১০০ ms-এ একটা iteration শুরু হয় <Cite n={4} />।

`ramping-arrival-rate` executor একইভাবে কাজ করে। এতে প্রতিটা stage-এর জন্য টার্গেট রেট সহ `stages` দিতে হয়, আর `startRate`-ও আছে <Cite n={7} />।

## Key words

| Term | Meaning |
| --- | --- |
| Scenario | A named block in `options.scenarios` with its own executor and function <Cite n={1} />. |
| Executor | The part of a scenario that schedules VUs and iterations <Cite n={1} />. |
| `exec` | The name of the exported function that a scenario runs <Cite n={1} />. |
| `startTime` | The offset from the test start at which a scenario begins <Cite n={1} />. |
| `gracefulStop` | The time that k6 waits for running iterations before a forced stop <Cite n={12} />. |
| Closed model | VUs start a new iteration only when the last one ends <Cite n={3} />. |
| Open model | Iterations start at a set rate, whether or not earlier ones have ended <Cite n={3} />. |
| Arrival rate | The number of iterations that start in a period of time <Cite n={2} />. |
| `preAllocatedVUs` | The VUs that k6 makes before an arrival-rate test starts <Cite n={4} />. |
| Coordinated omission | The closed-model effect where slow responses lower the rate of new iterations <Cite n={3} />. |
| Distributed execution | Splitting one test over many k6 instances <Cite n={5} />. |
