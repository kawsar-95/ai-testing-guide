# Choosing a Performance Testing Tool

Many tools can run a load test. This page lists eleven of them, then shows one way to choose: remove the tools that do not fit, step by step, until one is left.

<PageMeta />

## The tools at a glance

<Voices>
<Technical>

JMeter is the first name that most people know. There are many other tools. The table gives a short, sourced picture of each tool. A tool changes over time, so check its own site before you decide.

| Tool | What its own site or repo says |
| --- | --- |
| Apache JMeter | A 100 % pure Java application for load tests. It tests HTTP, HTTPS, SOAP and REST, FTP, JDBC, LDAP, JMS, and mail <Cite n={1} />. It is open source under the Apache license, and it needs Java 17 <Cite n={2} />. |
| k6 | Open source under AGPL-3.0. It has an embedded JavaScript engine, so you write tests in JavaScript <Cite n={3} />. |
| Locust | Open source under the MIT license. You write tests as regular Python code, and you can run them on many machines <Cite n={5} />. |
| Artillery | You write tests in YAML, TypeScript, or JavaScript <Cite n={6} />. Most of the code is under the MPL 2.0 license. Some Azure modules need a commercial license for production use <Cite n={7} />. |
| LoadRunner | Check the vendor's site for the current details. |
| Grinder | Check the project's site for the current details. |
| wrk | An HTTP benchmarking tool. It can make significant load from one multi-core CPU. An optional LuaJIT script builds requests and reports <Cite n={8} />. |
| Gatling | Open source under Apache 2.0. Its tests can be in Java, JavaScript, TypeScript, Kotlin, or Scala <Cite n={9} />. |
| BlazeMeter | A platform that works with open source tools such as JMeter, Selenium, and Playwright. Its prices are on a separate pricing page <Cite n={10} />. |
| NeoLoad | A Tricentis product. It has pass or fail gates for CI pipelines such as Jenkins, Azure DevOps, and GitLab. Tricentis offers a demo or a trial <Cite n={11} />. |
| StormForge | Its documentation now describes Kubernetes rightsizing powered by machine learning <Cite n={12} />. The tutorial's first notes listed it as a load testing tool. Do not count it as one. |

The tools differ in language, cost, and how hard they are to learn. Some need a Java runtime. Some need a plugin for a complex scenario. This is the tutorial's own view from its first notes, not a rule.

</Technical>

## Choosing by elimination

<Voices>
<Technical>

You can pick a tool by removing the tools that do not fit. The steps below are the tutorial's own method, and the tool facts come from the table above.

1. Remove the tools that are not free or open source. In the owner's view, this removes LoadRunner, BlazeMeter, NeoLoad, and StormForge. This is the tutorial's own view, so check each vendor's site for its current prices. JMeter, k6, Locust, Artillery, Grinder, wrk, and Gatling stay.
2. Look at the language of most developers. In the Stack Overflow Developer Survey 2024, 62.3 % of all respondents said they did extensive development work in JavaScript over the past year <Cite n={13} />. The figure is a share of survey respondents who used a language. It is not a share of all code. If you learn a JavaScript tool, you can often write tests in the same stack as the developers, and you can connect them to CI/CD.
3. In the notes, this step removes JMeter, Locust, Grinder, and wrk, which leaves k6 and Artillery. The notes also remove Gatling. That is out of date: the Gatling repo now lists JavaScript and TypeScript <Cite n={9} />. A current run of this step keeps Gatling too.
4. Compare k6 and Artillery. Both support JavaScript. In the notes, Artillery uses YAML as its main format, which the owner finds hard for a beginner, and JavaScript only for advanced scripting. The Artillery docs say you can write a script in YAML, TypeScript, or JavaScript <Cite n={6} />. In the notes, this leaves k6.

<Callout type="note" title="The owner's experience">

This box is the tutorial's own view. It is not a fact from a source.

The owner works on a project with a JavaScript backend. The end-to-end tests use Playwright, a JavaScript framework. A performance test with JMeter means a new setup: install a JDK, set `JAVA_HOME`, install JMeter, and build a `.jmx` file in the UI. The owner did not want a separate Java environment only for performance tests.

With k6, the owner installed one tool and wrote JavaScript at once. The owner then sent live results to Grafana through the built-in InfluxDB output, with no InfluxDB plugin to install, unlike JMeter. The owner's conclusion: for a JavaScript stack, k6 is a good tool, because it is quick, simple, and friendly to developers.

</Callout>

The steps give one answer for one team. A team with a Java stack or a Python stack can follow the same steps and get another tool. The k6 docs call k6 an open-source tool that is friendly to developers and easy to extend <Cite n={4} />.

</Technical>

## Key words

| Term | Meaning |
| --- | --- |
| Load testing tool | A program that sends many requests to a system to measure how it behaves under load. |
| Open source | Software whose source code is public under a license. The licenses differ: k6 uses AGPL-3.0 <Cite n={3} />, Locust uses MIT <Cite n={5} />, and Gatling uses Apache 2.0 <Cite n={9} />. |
| Scripting language | The language in which you write the test. k6 uses JavaScript <Cite n={3} />, and Locust uses Python <Cite n={5} />. |
| Elimination | A way to choose: remove each option that fails a rule, until one is left. |
| Developer experience | How easy a tool is for a developer to learn and use. The k6 README names it as the key design goal <Cite n={3} />. |
