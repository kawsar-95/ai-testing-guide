# What Is Performance Testing?

A shop can work perfectly for one user and still fail when a thousand users arrive at the same time. Performance testing finds out how the system behaves when many people use it together.

<PageMeta />

## What performance testing is

<Voices>
<Technical>

The ISTQB glossary defines **performance testing** as a test type that determines the performance efficiency of a component or system <Cite n={1} />. A functional test asks "does it work?". A performance test asks "how well does it work, and how many users can it serve?".

The tutorial's own view: the main questions are about efficiency, stability, and scalability. Does the system answer fast enough? Does it stay up? Does it keep working when more users come? A test usually puts many users on the system at the same time, then watches how it behaves and how much load it can carry.

Different traffic patterns create different risks, so teams use more than one test type <Cite n={2} />. The k6 documentation names six: smoke, average-load, stress, soak, spike, and breakpoint tests <Cite n={2} />. The next page explains each one.

</Technical>

## Why it matters

<Voices>
<Technical>

Many people use public web apps at the same time. Examples are shops, banking apps, school sites, news sites, and government services. All these users put pressure on the servers. If the servers cannot serve them well, people suffer.

Two examples, with made-up names:

- **A slow shop search.** You visit `shop.example.com` and search for a product. The result takes a very long time, and sometimes the page says the server is down. Will you visit that shop again? Most people will not.
- **A bank statement that never comes.** You ask `bank.example.com` for your statement. The page loads for a long time. Then it shows an error before it shows your data. You will probably think about using another bank.

The tutorial's own view: functional testing alone is not enough. A feature can pass every functional test and still fail in production, because customers leave when the system is slow or broken.

The k6 documentation names two common goals for a load test: to confirm reliability under the expected traffic, and to find problems and limits under unusual traffic <Cite n={4} />. A component that does not meet its performance requirements is a bottleneck <Cite n={4} />. Finding the bottleneck before the users do is the point of the test.

</Technical>

## What it measures

<Voices>
<Technical>

A performance test collects numbers. Four groups of numbers matter most. The table shows each group and the k6 built-in metric that matches it <Cite n={3} />.

| Group | Question | k6 metric |
| --- | --- | --- |
| Response time | How long does one request take? | `http_req_duration` |
| Throughput | How many requests does the system handle? | `http_reqs` |
| Error rate | What share of requests fail? | `http_req_failed` |
| Resource use | How much CPU and memory does the server use? | not a k6 metric |

`http_req_duration` is the total time of a request. It equals the time to send, plus the time to wait, plus the time to receive <Cite n={3} />. The waiting part is also called the time to first byte <Cite n={3} />. `http_reqs` counts all HTTP requests that k6 made <Cite n={3} />. `http_req_failed` is the rate of failed requests <Cite n={3} />.

Resource use is on the server side. k6 sends the load and measures what the user sees. To see CPU and memory, you watch the server with a monitoring tool. This is the tutorial's own advice.

A good test also sets what "acceptable" means before the run. The k6 documentation says to use thresholds to check that the system stays within its SLOs <Cite n={4} />. Later pages show how.

</Technical>

## Key words

| Term | Meaning |
| --- | --- |
| Performance testing | A test type that checks the performance efficiency of a component or system <Cite n={1} />. |
| Load | The traffic that a test puts on the system. The test goal sets the test type, and the test type sets the load <Cite n={4} />. |
| Response time | How long a request takes. k6 measures it as `http_req_duration` <Cite n={3} />. |
| Throughput | How many requests are made. k6 counts them with `http_reqs` <Cite n={3} />. |
| Error rate | The rate of failed requests. k6 reports it as `http_req_failed` <Cite n={3} />. |
| Bottleneck | A component that does not meet its performance requirements <Cite n={4} />. |
| SLO | A service level objective: a target for how well the system must perform <Cite n={4} />. |
| Threshold | A pass or fail rule on a metric, used to keep the system within its SLOs <Cite n={4} />. |
| Test type | A kind of load test, such as smoke, average-load, stress, soak, spike, or breakpoint <Cite n={2} />. |
