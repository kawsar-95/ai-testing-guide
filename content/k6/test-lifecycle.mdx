# The k6 Test Lifecycle

The four stages of a k6 script: init, setup, VU code, and teardown.

<PageMeta />

## The four stages

<Voices>
<Technical>

A k6 script always runs through the same stages in the same order <Cite n={1} />. Init code prepares the script. Setup prepares the test environment and data. VU code is the test itself. Teardown cleans up. Except for init, each stage is a **lifecycle function**: a function that k6 calls at a set point of the run <Cite n={1} />.

| Stage | Purpose | Example | How often it runs |
| --- | --- | --- | --- |
| 1. Init | Load files, import modules, set `options`, define the lifecycle functions. Required. | `import http from 'k6/http'` | Once for each VU <Cite n={1} /> |
| 2. Setup | Prepare data. Share it with the VUs. Optional. | Log in and get a token | Once for the whole test |
| 3. VU code | Run the test steps. Required. | Send HTTP requests, check the answers | Once for each iteration, as many times as the options need |
| 4. Teardown | Process the result of setup. Stop the test environment. Optional. | Check a result, send a webhook | Once for the whole test |

In a cloud run, init code can run more often than once for each VU <Cite n={1} />.

The data flows in one direction only:

```text
init (each VU)
   |
   v
setup()  -- runs once -- returns data (JSON only)
   |
   +--> a copy of data --> default(data)  (VU 1, every iteration)
   +--> a copy of data --> default(data)  (VU 2, every iteration)
   +--> a copy of data --> default(data)  (VU N, every iteration)
   |
   +--> a copy of data --> teardown(data) -- runs once, after all VUs stop
```

This is the skeleton of every k6 script <Cite n={1} />:

```js
// 1. init code: runs once for each VU
import http from 'k6/http';
import { sleep } from 'k6';

export const options = {
  vus: 2,
  duration: '5s',
};

// 2. setup code: runs once for the whole test
export function setup() {
  return { startedAt: Date.now() };
}

// 3. VU code: runs again and again for each VU
export default function (data) {
  http.get('https://quickpizza.grafana.com/api/json?name=Margherita');
  sleep(1);
}

// 4. teardown code: runs once at the end
export function teardown(data) {
  console.log(`The test ran for ${Date.now() - data.startedAt} ms`);
}
```

Each stage has its own rules:

- **Init** is the code outside of every lifecycle function. It runs first. It loads files, imports modules, sets the options, and defines the lifecycle functions <Cite n={1} />. It cannot make HTTP requests, so the init stage is the same in every run <Cite n={1} />.
- **Setup** runs after init and before the VU stage. **Teardown** runs after the VU stage <Cite n={1} />. Both can use the full k6 API, for example HTTP requests <Cite n={1} />.
- **VU code** is the `default` function, or the function of a scenario. A VU runs it from start to end, then starts it again. Each time, k6 resets the VU: it clears cookies, and it can close TCP connections <Cite n={1} />. VU code does not load local files and does not import modules <Cite n={1} />.
- Setup must finish within `setupTimeout`. The default is 60 seconds. If setup takes longer, the test fails before any VU starts <Cite n={1} />.
- If setup throws an error, k6 does not call teardown <Cite n={1} />.
- `k6 run --no-setup --no-teardown script.js` skips both stages <Cite n={1} />.
- `handleSummary()` is one more lifecycle function. k6 calls it at the very end of the test <Cite n={1} />.

</Technical>
<Layman>

A k6 script always runs in the same order <Cite n={1} />. First, k6 prepares the script. Then it runs setup. Then the virtual users run the test. At the end, teardown cleans up.

| Stage | What it is for | Example | How often it runs |
| --- | --- | --- | --- |
| 1. Init | Load files and modules, set the options | `import http from 'k6/http'` | Once for each VU <Cite n={1} /> |
| 2. Setup | Prepare data for the test | Log in and get a token | Once for the whole test |
| 3. VU code | The test steps | Send requests, check the answers | Once for each iteration |
| 4. Teardown | Clean up after the test | Check a result, send a webhook | Once for the whole test |

The data moves in one direction. Setup returns data. Each virtual user gets its own copy of that data. Teardown gets a copy too. Nobody sends data back.

Init code cannot make HTTP requests <Cite n={1} />. Setup and teardown can <Cite n={1} />. A virtual user starts the test function again and again. Each time, k6 clears its cookies <Cite n={1} />.

Setup has a time limit of 60 seconds by default. If setup is slower, the test fails before any virtual user starts <Cite n={1} />. If setup throws an error, teardown does not run <Cite n={1} />.

</Layman>
<Bangla>

k6 স্ক্রিপ্ট সবসময় একই ক্রমে চলে <Cite n={1} />। শুরুতে init, তারপর setup, তারপর VU code, শেষে teardown।

| Stage | কী কাজ | উদাহরণ | কতবার চলে |
| --- | --- | --- | --- |
| 1. Init | ফাইল ও মডিউল লোড করা, `options` সেট করা | `import http from 'k6/http'` | প্রতিটা VU-র জন্য একবার <Cite n={1} /> |
| 2. Setup | টেস্টের ডেটা তৈরি করা | লগইন করে token নেওয়া | পুরো টেস্টে একবার |
| 3. VU code | টেস্টের ধাপগুলো | HTTP request পাঠানো, response check করা | প্রতিটা iteration-এ একবার |
| 4. Teardown | টেস্টের পরে পরিষ্কার করা | ফলাফল যাচাই করা, webhook পাঠানো | পুরো টেস্টে একবার |

ডেটা শুধু একদিকে যায়। `setup()` ডেটা return করে। প্রতিটা VU তার নিজের একটা কপি পায়। `teardown()`-ও একটা কপি পায়। কেউ ডেটা ফেরত পাঠায় না।

Init code HTTP request পাঠাতে পারে না <Cite n={1} />। `setup()` ও `teardown()` পারে <Cite n={1} />। একটা VU টেস্ট ফাংশন বারবার চালায়। প্রতিবার k6 তার cookie মুছে দেয় <Cite n={1} />।

`setup()`-এর ডিফল্ট সময়সীমা ৬০ সেকেন্ড। এর বেশি লাগলে কোনো VU শুরু হওয়ার আগেই টেস্ট fail করে <Cite n={1} />। `setup()` error throw করলে `teardown()` চলে না <Cite n={1} />।

</Bangla>

## A login and token example

<Voices>
<Technical>

A common use of setup is to log in one time and share the token with all VUs. The script below does this with QuickPizza, the public demo app of Grafana k6. It creates a new user in setup. The endpoints and the status codes in the script come from the tutorial's own test of the app, not from the k6 docs, so they can change. The tutorial uses this app only for short runs with a few VUs.

```js
import http from 'k6/http';
import { check, sleep } from 'k6';

const BASE_URL = 'https://quickpizza.grafana.com';
const JSON_HEADERS = { 'Content-Type': 'application/json' };

export const options = {
  stages: [{ duration: '5s', target: 3 }],
};

// Runs once. It creates a user and logs in to get one shared token.
export function setup() {
  const username = `user_${Date.now()}`;
  const password = `pw_${Math.random().toString(36).slice(2)}`;
  const credentials = JSON.stringify({ username, password });

  const registerRes = http.post(`${BASE_URL}/api/users`, credentials, { headers: JSON_HEADERS });
  if (registerRes.status !== 201) {
    throw new Error(`Failed to register: ${registerRes.status}`);
  }

  const loginRes = http.post(`${BASE_URL}/api/users/token/login`, credentials, { headers: JSON_HEADERS });
  if (loginRes.status !== 200) {
    throw new Error(`Failed to log in: ${loginRes.status}`);
  }
  return { token: loginRes.json('token') };
}

// Runs again and again for each VU. Every VU gets its own copy of data.
export default function (data) {
  const params = { headers: { Authorization: `Bearer ${data.token}` } };
  const res = http.get(`${BASE_URL}/api/ratings`, params);
  check(res, { 'status is 200': (r) => r.status === 200 });
  sleep(1);
}

// Runs once at the end. It does not print the token.
export function teardown(data) {
  console.log(`Teardown finished. The token has ${data.token.length} characters.`);
}
```

One local run of this script (3 VUs, 5 seconds) printed this. Your numbers will differ:

```text
level=info msg="Teardown finished. The token has 16 characters." source=console
checks_succeeded...: 100.00% 5 out of 5
✓ status is 200
http_req_failed................: 0.00%  0 out of 7
iterations.....................: 5      0.65728/s
```

The `http_req_failed` line shows 7 requests. Five of them are from the VU code. The other two are the register and login requests from setup.

To test your own API, replace `BASE_URL` and the two requests. Never write a real email or password in the script. k6 gives the environment variables to the script in the global `__ENV` object <Cite n={2} />. Read the email and the password from it, for example `__ENV.TEST_EMAIL` and `__ENV.TEST_PASSWORD`, and give them with `k6 run -e TEST_EMAIL=… -e TEST_PASSWORD=… script.js` <Cite n={2} />. The host `https://api.example.com` in the next sections is an example name, so do not run load against it.

Each transaction then sends the token of its sender. Before the load starts, `setup()` also checks the balances and stops the test with `fail()` if a sender does not have enough money. ## How the example works

<Voices>
<Technical>

The owner's original notes explain a similar script with `https://api.example.com`. The same four steps apply to the QuickPizza script above.

**Init.** The script imports `http`, `check`, and `sleep` from k6, and it sets the load in `options`: a ramp to 100 VUs over 60 seconds in the owner's version <Cite n={1} />. The owner's first version used `check` without an import. Import it from `k6`, as the checks docs show <Cite n={3} />.

**Setup.** Setup makes the prerequisite of the test: it gets one token. Each VU then uses this token <Cite n={1} />. If the login fails, the script throws an error. Setup then ends abnormally, and k6 does not call teardown <Cite n={1} />.

**VU code.** The default function holds the VU code of the test. A scenario function can hold it too <Cite n={1} />. In the owner's version it sends a `GET` request to `/users/list` with the token in the `Authorization` header. It does not call `/user/login`: the login is in setup. Then it checks that the status is 200. Each VU runs this function again and again for the whole duration <Cite n={1} />.

**Teardown.** Teardown runs one time at the end. The owner's version printed the token. In this tutorial's view, do not print a token or a password in a log, because logs are often stored and shared. Instead, teardown can call a logout API to make the token invalid, or it can write a short log line.

Here is the same script with `https://api.example.com` and credentials from `__ENV`. It is a pattern for your own API, not a script to run against that host:

```js
import http from 'k6/http';
import { check, sleep } from 'k6';

export const options = {
  stages: [{ duration: '60s', target: 100 }],
};

export function setup() {
  const res = http.post(
    'https://api.example.com/user/login',
    JSON.stringify({ email: __ENV.TEST_EMAIL, password: __ENV.TEST_PASSWORD }),
    { headers: { 'Content-Type': 'application/json' } },
  );
  if (res.status !== 200) {
    throw new Error(`Failed to log in: ${res.status}`);
  }
  return { token: res.json('token') };
}

export default function (data) {
  const params = { headers: { Authorization: `Bearer ${data.token}` } };
  const res = http.get('https://api.example.com/users/list', params);
  check(res, { 'is status 200': (r) => r.status === 200 });
  sleep(1);
}

export function teardown(data) {
  console.log('Teardown completed.');
}
```

## Five good practices

<Voices>
<Technical>

The first four points come from how k6 passes data between the stages. The fifth is the owner's advice.

1. **Return only JSON data from `setup()`.** Setup can hand over plain data (JSON) only, and it cannot hand over a function <Cite n={1} />. Objects, arrays, strings, numbers, and booleans are fine.
2. **Return only the data you need.** If setup returns a large object, it uses more memory <Cite n={1} />. A large dataset in setup makes the whole test heavier.
3. **Do not change `data` in the default function and expect teardown to see it.** You cannot change data in the default function and then pass it to teardown <Cite n={1} />. k6 avoids this because it is complex and costly to pass changing data between all VUs and teardown, especially in distributed runs <Cite n={1} />.
4. **Each VU gets its own copy of the setup data.** Each stage and each VU has a fresh copy of what setup returns <Cite n={1} />. If one VU changes its copy, other VUs do not see the change. Teardown also gets a copy of the original data <Cite n={1} />.
5. **Plan the data flow (the owner's advice).** In the tutorial owner's view, decide before you write the script what setup prepares and what it returns. A script that passes only the needed data is smaller and easier to read. This point is the owner's own view, not a rule of the k6 docs.

## Key words

| Term | Meaning |
| --- | --- |
| Init context | The code outside every lifecycle function. It runs first, once for each VU. |
| Lifecycle function | A function that k6 calls at a set point: `setup`, `default` (or a scenario function), `teardown`, and `handleSummary`. |
| `setup()` | An optional function that runs once before the VUs start. It can return data. |
| VU code | The test function that each VU runs again and again, usually `default`. |
| Iteration | One run of the VU code from start to end. |
| `teardown(data)` | An optional function that runs once after the VU stage. |
| `setupTimeout` | The time limit of `setup()`. The default is 60 seconds. |
| `__ENV` | A global object with the environment variables <Cite n={2} />. Use it for credentials and hosts. |
