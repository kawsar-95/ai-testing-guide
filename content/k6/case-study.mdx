# Case Study: Testing a Money-Transfer API

This page walks through one real k6 project, line by line, so that you can copy its patterns into your own project. The project, its code, and its numbers come from the owner of this tutorial, not from the k6 documentation.

## The project in plain words

<Voices>
<Technical>

The project is [kawsar-95/k6-performance-testing](https://github.com/kawsar-95/k6-performance-testing) (commit `51e4b9e`). Every fact about the project on this page comes from its files: the scripts, the `README.md`, and the files in `results/`. These facts have no cite, because they are not k6 documentation. The k6 facts have cites.

The project tests a practice mobile-wallet API (dMoney) that runs on the local machine. The test drives 3 transaction APIs: deposit, send money, and payment. It uses 6 users: 2 agents, 2 customers, and 2 merchants. The test lasts 2 minutes. It has 4 windows of 30 seconds each, and each window adds or changes the traffic.

The goal is to compare the response time, the throughput, and the failure rate of each API as the load changes. The pass or fail result of each API is a threshold.

| File | Job |
|---|---|
| `dmoney-seed.k6.js` | Creates and funds the 6 users. You run it before the test, and again when the balances get low. |
| `dmoney-transactions.k6.js` | The main test: 13 scenarios, checks, thresholds, and the report. |
| `lib/dmoney.js` | Shared helpers: the base URL, the headers, the login, and the balance call. |
| `sendmoney-concurrency.k6.js` | A second test: customers send money in stages of load. |
| `results/` | The saved reports and a written analysis. |

## The traffic plan: 13 flows

<Voices>
<Technical>

The project calls one kind of transaction between two users a **flow**. A window runs several flows at the same time, and each flow sends 1 request per second for the full 30 seconds. The plan from `README.md` has 13 flows:

| Window | API | From | To |
|---|---|---|---|
| w1 (0–30 s) | send money | Customer 1 | Customer 2 |
| | payment | Customer 2 | Merchant 1 |
| w2 (30–60 s) | send money | Customer 2 | Customer 1 |
| | deposit | Agent 1 | Customer 2 |
| | payment | Customer 1 | Merchant 1 |
| w3 (60–90 s) | deposit | Agent 1 | Customer 1 |
| | deposit | Agent 2 | Customer 2 |
| | send money | Customer 1 | Customer 2 |
| | payment | Customer 2 | Merchant 2 |
| w4 (90–120 s) | payment | Agent 1 | Merchant 1 |
| | payment | Agent 2 | Merchant 2 |
| | payment | Customer 1 | Merchant 1 |
| | payment | Customer 2 | Merchant 2 |

The window w4 has the same load as w3: 4 flows, 4 requests per second. The difference is the mix. In w4, all 4 flows are payments from 4 different senders. This detail matters for the deadlock later on this page.

This plan is a good model for your own test. Write the traffic as data first: who does what, to whom, and when. Then turn the data into scenarios.

</Technical>

## Pattern: scenarios built from a list of flows

<Voices>
<Technical>

The script does not write 13 scenarios by hand. It keeps the 13 flows in a `FLOWS` list and builds the `scenarios` object with a loop. Each scenario uses the `constant-arrival-rate` executor, which starts a fixed number of iterations in a period and starts them without waiting for the system to answer <Cite n={2} />. This executor needs `preAllocatedVUs`, and `maxVUs` is the upper limit of VUs that k6 can add to keep the rate <Cite n={2} />.

Excerpt from `dmoney-transactions.k6.js`:

```js
const scenarios = {};
for (const f of FLOWS) {
    scenarios[`w${f.window}_${f.api}_${f.from}_to_${f.to}`] = {
        executor: 'constant-arrival-rate',
        exec: 'transact',
        startTime: `${(f.window - 1) * WINDOW_S}s`,
        duration: `${WINDOW_S}s`,
        rate: RATE,
        timeUnit: TIME_UNIT,
        preAllocatedVUs: Math.max(2, Math.ceil(RATE * 2)),
        maxVUs: 20,
        gracefulStop: '5s',
        env: { API: f.api, FROM: f.from, TO: f.to },
        tags: { window: `w${f.window}` },
    };
}
```

Four scenario options do the work <Cite n={1} />:

- `startTime` is the offset from the start of the test at which the scenario begins. A window w3 flow gets `startTime` of `60s`, so it starts when w3 starts. Scenarios run in parallel, so all flows of a window run together.
- `exec` is the name of the exported function to run. All 13 scenarios run the same function, `transact`.
- `env` sets environment variables for one scenario. The scenario tells `transact` its API, its sender, and its receiver this way.
- `tags` sets tags for one scenario. Each request gets the `window` tag (`w1` to `w4`).

The `transact` function reads the flow from `__ENV`. One shared function serves all 13 flows, so a change to the request code is one change, not 13.

```js
export function transact(data) {
    const { API, FROM, TO } = __ENV;
    const api = APIS[API];
    const from = data.users[FROM];
    // ... the http.post call and the checks
}
```

The project's analysis says that k6 dropped 0 iterations. A dropped iteration is an iteration that k6 could not start. With `constant-arrival-rate`, iterations drop when no VU is free <Cite n={7} />. So 0 dropped iterations means that the API kept up with the arrival rate.

Read more about scenarios on [Scenarios and Executors](/k6/scenarios-and-executors/).

</Technical>

## Pattern: log in once in setup() and check the test data

<Voices>
<Technical>

The `setup()` function runs one time, after the init stage and before the VU code <Cite n={4} />. You can use the full k6 API in it, so it can make HTTP requests. The data that it returns goes to the VU code. Only data (JSON) can pass, and each VU gets its own copy <Cite n={4} />.

The project uses `setup()` for two jobs.

1. **Log in once.** Each of the 6 users logs in with its own credentials, and `setup()` returns the tokens. The 13 scenarios then use the token of the sender, so a transaction does not log in again before each request.
2. **Check the test data before the load.** The money flows change the balance of the users. If a sender has too little money, the test would fail for a reason that is not a defect in the API. So `setup()` works out the most that each user can send and receive, reads the real balances, and calls `fail()` when the data is not enough.

Excerpt from `dmoney-transactions.k6.js`:

```js
const problems = [];
for (const key of Object.keys(USERS)) {
    const balance = getBalance(users[key].token, users[key].phone);
    console.log(`${key.padEnd(10)} ${users[key].phone}  balance=${balance}  outgoing<=${out[key] || 0}  incoming<=${inc[key] || 0}`);
    if (out[key] && balance < out[key]) problems.push(`${key} has ${balance} tk and needs ${out[key]} tk`);
    if (USERS[key].role === 'Customer' && balance + (inc[key] || 0) >= CUSTOMER_CAP) {
        problems.push(`${key} can reach the ${CUSTOMER_CAP} tk deposit cap (${balance} + ${inc[key]})`);
    }
}
if (problems.length) fail(`balance pre-check failed: ${problems.join('; ')}. Run dmoney-seed.k6.js.`);
```

The function `fail()` throws an error <Cite n={6} />. An error in `setup()` means that setup ends abnormally, and k6 does not call `teardown()` <Cite n={4} />. The project's `README.md` says that the test stops with a clear message when the pre-check fails. That is the project's own statement. The message also tells you what to do: run the seed script. The pre-check uses an upper bound of the iterations that a scenario can start, plus a fee estimate for each transfer.

A long `setup()` can hit the setup time limit. The `setupTimeout` option (60 seconds by default) is that limit, and the test fails before any VU starts if `setup()` takes longer <Cite n={4} />. The project sets `setupTimeout` to `60s` in its options.

Read more on [Test Lifecycle](/k6/test-lifecycle/).

</Technical>

## Pattern: strict checks on the response body

<Voices>
<Technical>

A status code alone can lie. An API can return `201` with an empty or wrong body. The `transact` function runs 4 checks on each response, and a request passes only when all 4 pass. The project's `README.md` lists them.

| Check | Rule |
|---|---|
| Status | `status === 201` |
| Success | status 201, `currentBalance` is in the body, and there is no `error` field |
| Transaction ID | `trnxId` matches `^TXN[A-Z0-9]{10}$` |
| Message | `Deposit successful`, `Send money successful`, or `Payment successful` |

Excerpt from `dmoney-transactions.k6.js`:

```js
let body = {};
try { body = res.json() || {}; } catch (e) { /* not JSON: checks below fail */ }

const ok = check(res, {
    [`${API}: status is 201`]: (r) => r.status === 201,
    [`${API}: transaction is successful`]: (r) => r.status === 201 && body.currentBalance !== undefined && !body.error,
    [`${API}: transaction ID is returned`]: () => /^TXN[A-Z0-9]{10}$/.test(body.trnxId || ''),
    [`${API}: message is "${api.message}"`]: () => body.message === api.message,
}, { type: 'transaction', api: API });
```

Three details are worth copying:

- The body is parsed one time in a `try` block. A body that is not JSON does not stop the iteration. It makes the checks fail, and that is what you want.
- The check names include the API name, so the output shows which API failed which check.
- The checks have tags (`type` and `api`). A tag on a check lets a threshold look at a group of checks <Cite n={3} />. The next section uses this.

The project's analysis says that each failed request failed all 4 checks. A failed request was an HTTP 500 with an error body.

Read more on [Stages and Checks](/k6/stages-and-checks/).

</Technical>

## Pattern: tags, thresholds for each API, and report-only thresholds

<Voices>
<Technical>

The project tags each request with `api` (`deposit`, `sendmoney`, or `payment`), and each scenario adds the `window` tag. Tagged requests create sub-metrics that a threshold can name, in the form `metric_name{tag_name:tag_value}` <Cite n={3} />. So the script can set one pass or fail limit for each API.

Excerpt from `dmoney-transactions.k6.js`:

```js
const thresholds = {
    http_req_failed: ['rate<0.01'],
    http_req_duration: ['p(95)<1000'],
    'checks{type:transaction}': ['rate>=0.99'],
};
for (const [api, cfg] of Object.entries(APIS)) {
    thresholds[`http_req_duration{api:${api}}`] = [`p(95)<${cfg.p95}`];
    thresholds[`http_req_failed{api:${api}}`] = ['rate<0.01'];
    thresholds[`checks{api:${api}}`] = ['rate>=0.99'];
}
```

Each API gets 3 limits: p95 of the duration under 1000 ms, a failure rate under 1%, and a check pass rate of 99% or more. The p95 limits are in `APIS`, so you can change them with environment variables. The failure-rate and check-rate limits are fixed in the script. A failed threshold fails the test <Cite n={3} />.

The project uses a second trick. The per-window report needs numbers for each pair of `window` and `api`. The script's own comment says that k6 adds a sub-metric to the summary only when a threshold names it. So the script adds thresholds that always pass, only to get the numbers.

```js
const reportOnly = (key, expr) => { thresholds[key] = [expr]; };
// for each flow:
reportOnly(`http_req_duration{${sel}}`, 'max>=0');
reportOnly(`http_reqs{${sel}}`, 'count>=0');
reportOnly(`http_req_failed{${sel}}`, 'rate>=0');
```

The `sel` value is `window:w3,api:deposit` for example. An expression such as `count>=0` is always true, so it never fails the test. The project keeps a set of the real pass or fail keys (`PASS_FAIL`), so the threshold table of the report skips the report-only ones.

The project's second script, `sendmoney-concurrency.k6.js`, uses a threshold in a different way. It has a `Counter` named `sendmoney_skipped`. The script counts one when it has no slot left for a send. The threshold `sendmoney_skipped: ['count==0']` fails the run when the reusable customers ran out of limit or balance. A counter supports the `count` aggregation <Cite n={3} />. Read more on [Custom Metrics](/k6/custom-metrics/).

Read more on [Thresholds](/k6/thresholds/) and [Tags and Groups](/k6/tags-and-groups/).

</Technical>

## Pattern: a custom report with handleSummary()

<Voices>
<Technical>

At the end of the test, k6 gives the summary data to `handleSummary()`. The function returns a map. A key is `stdout` or a file path, and a value is the text to write. A file write overwrites the file <Cite n={5} />. If a script exports `handleSummary()`, k6 does not print the default summary, so a script that wants it must print it itself <Cite n={5} />. The project keeps the default text with `textSummary` from the k6 JS utilities library, and adds its own report.

The summary data has a `metrics` object. Each metric, and each sub-metric, has `values` and `thresholds` <Cite n={5} />. The project's `buildReport()` reads them to build 3 tables: the thresholds, the numbers for each API, and the numbers for each window.

Excerpt from `dmoney-transactions.k6.js`:

```js
export function handleSummary(data) {
    const report = buildReport(data);
    return {
        stdout: `${textSummary(data, { indent: ' ', enableColors: true })}\n\n${report}\n`,
        [`${RESULTS_DIR}/dmoney-transactions-summary.md`]: report,
        // setup_data holds the login tokens, so it is left out of the saved file.
        [`${RESULTS_DIR}/dmoney-transactions-summary.json`]: JSON.stringify({ ...data, setup_data: undefined }, null, 2),
    };
}
```

The excerpt is shortened: the project also writes an HTML report with a third-party library. This module teaches `handleSummary()` and the k6 web dashboard instead, so that part is not a pattern to copy. See [Reports and Dashboard](/k6/reports-and-dashboard/).

Note the comment on the last key. The project's script says that the data holds the login tokens, so it removes `setup_data` before it saves the JSON. This keeps the tokens out of the saved file. Never save secrets in a report.

## How the test found a deadlock

<Voices>
<Technical>

Look at w3 and w4 in the table above. Both windows have the same load: 4 flows and 4 requests per second. Yet w3 has 50 failures (40%) and w4 has 0. The project's analysis says this means the failures depend on lock conflicts, not on the load.

The project's analysis gives this reason. In w2 and w3, deposits write to Customer 1 and Customer 2. At the same time, the same customers send money and pay. So 2 or 3 flows lock the same accounts. In w4, all 4 flows are payments from 4 different senders, and no sender account is shared.

All 64 failures in the run were HTTP 500 responses. The analysis says that the cause is a MySQL deadlock (`ER_LOCK_DEADLOCK`). The server log has 66 deadlock errors. 64 of them are from this run and match the 64 failed requests in k6. The other 2 are from a smoke run before it.

The analysis also gives the root cause, from the project's own investigation of the API:

- The `Transactions` table has only the `PRIMARY` index. It has no index on `account`.
- Each transaction API runs a locked read, `SELECT SUM(credit) - SUM(debit) … WHERE account = ? FOR UPDATE`. Without an index on `account`, MySQL scans the full table and locks rows on the `PRIMARY` index. Two transactions can each hold a lock that the other one needs.
- The controllers do not retry after a deadlock. They return HTTP 500.

The analysis lists 3 possible fixes. It says that they are not applied, and that the development team decides:

1. Add an index on `Transactions(account)`, so that the locked read locks only the rows of that account.
2. Lock the accounts in a fixed order, for example the lower phone number first, when a request locks 2 accounts.
3. Retry the transaction 1 or 2 times on a deadlock before the API returns an error.

The analysis also reports that the same script ran 3 times on 2026-10-09. The pass or fail result was the same each time, but the number of deadlocks changed (39, 32, and 64 failed transactions), because it depends on the exact timing of concurrent requests. So run a test like this more than once.

What did the test teach? The test used 4 windows with a different mix of flows on purpose. Because the windows had different mixes, comparing them showed that the failures follow the shared accounts. A test with one flow and one rate would not have found this.

</Technical>

The windows had different mixes on purpose. This is how the test showed that the failures follow the shared accounts. A test with one flow and one rate would not have found this.

</Layman>
<Bangla>

ফলাফলের w৩ আর w৪ দেখুন। দুটোরই লোড একই: ৪টা flow আর প্রতি সেকেন্ডে ৪টা request। তবু w৩-এ ৫০টা failure (৪০%), আর w৪-এ ০টা। প্রজেক্টের analysis বলে এর মানে failure লোডের উপর নির্ভর করে না, lock conflict-এর উপর নির্ভর করে।

analysis এই কারণ দেয়। w২ আর w৩-এ deposit Customer 1 আর Customer 2-এ লেখে। একই সময়ে একই customer টাকা পাঠায় আর পেমেন্ট করে। তাই ২ বা ৩টা flow একই account lock করে। w৪-এ ৪টা flow-ই ৪ জন আলাদা sender-এর payment, আর কোনো sender account শেয়ার হয় না।

রানের ৬৪টা failure-ই ছিল HTTP 500 response। analysis বলে কারণ একটা MySQL deadlock (`ER_LOCK_DEADLOCK`)। সার্ভার লগে ৬৬টা deadlock error আছে। এর ৬৪টা এই রানের, আর k6-র ৬৪টা failed request-এর সাথে মেলে। বাকি ২টা এর আগের একটা smoke run-এর।

analysis মূল কারণও দেয়:

- `Transactions` টেবিলে শুধু `PRIMARY` index আছে। `account`-এর উপর কোনো index নেই।
- প্রতিটা transaction API একটা locked read চালায়: `SELECT SUM(credit) - SUM(debit) … WHERE account = ? FOR UPDATE`। `account`-এ index না থাকলে MySQL পুরো টেবিল scan করে আর `PRIMARY` index-এর row lock করে। দুটো transaction প্রত্যেকে এমন lock ধরে রাখতে পারে যা অন্যটার লাগে।
- controller deadlock-এর পর আবার চেষ্টা (retry) করে না। তারা HTTP 500 return করে।

analysis ৩টা সম্ভাব্য সমাধান দেয়। সেগুলো প্রয়োগ করা হয়নি, ডেভেলপমেন্ট টিম সিদ্ধান্ত নেবে:

1. `Transactions(account)`-এর উপর একটা index যোগ করা, যাতে locked read শুধু ওই account-এর row lock করে।
2. একটা request ২টা account lock করলে একটা নির্দিষ্ট ক্রমে lock করা, যেমন ছোট ফোন নম্বর আগে।
3. API error দেওয়ার আগে deadlock হলে transaction ১ বা ২ বার retry করা।

analysis আরও জানায় একই স্ক্রিপ্ট ২০২৬-১০-০৯ তারিখে ৩ বার চলেছিল। pass বা fail ফলাফল প্রতিবার একই ছিল, কিন্তু deadlock-এর সংখ্যা বদলেছিল (৩৯, ৩২ আর ৬৪টা failed transaction), কারণ এটা concurrent request-এর ঠিক সময়ের উপর নির্ভর করে। তাই এমন টেস্ট একাধিকবার চালান।

টেস্ট কী শেখাল? টেস্ট ইচ্ছা করেই ৪টা window-তে আলাদা flow-মিক্স ব্যবহার করেছে। মিক্স আলাদা ছিল বলে তুলনা করে বোঝা গেছে failure শেয়ার করা account-কে অনুসরণ করে। একটা flow আর একটা rate-এর টেস্ট এটা ধরতে পারত না।

## What to copy into your own project

<Voices>
<Technical>

Here is a checklist from this project. Take the patterns, not the files.

1. Write the traffic plan as a list of data rows, then build the scenarios in a loop. Give all scenarios one shared `exec` function, and pass the flow in `env`.
2. Log in once in `setup()`, and check the test data before the load starts. Stop with a message that tells the reader what to fix.
3. Check the body of each response, not only the status code.
4. Tag requests by the thing that you want to compare (an API, a window), and write a threshold for each tag value.
5. Compare windows with different mixes. A change in the failure rate between two windows with the same load points to a cause that is not load.
6. Keep secrets out of saved reports.
7. Write the analysis in plain words, and mark what is a fact, what is a cause, and what is only a possible fix.

<Callout type="tip" title="Tutorial advice">

This advice is the tutorial's own, not a fact from a source.

- Keep credentials out of the repository. This example project commits its test passwords. That is acceptable for a local practice API, and it is a bad habit for any real project. - Run a test like this only against a local or test environment. It writes real records, and the example uses a login shortcut that exists only for development.
- Do not copy a result table as a promise. Say that it is one run on one machine, with the date.
- Do not use a third-party report library only because the example does. Learn `handleSummary()` and the k6 web dashboard first.

## Key words

| Term | Meaning |
|---|---|
| Flow | In this project, one kind of transaction between two users, such as a payment from a customer to a merchant. Each flow is one scenario. |
| Window | A part of the test with a start time and a length. This project has 4 windows of 30 seconds. |
| `startTime` | A scenario option: the offset from the start of the test at which the scenario begins. |
| `exec` | A scenario option: the name of the exported function that the scenario runs. |
| `constant-arrival-rate` | An executor that starts a fixed number of iterations in a period, whatever the response time. |
| Pre-check | A check in `setup()` that the test data is enough, before the load starts. |
| Sub-metric | A metric filtered by a tag, written `metric{tag:value}`. A threshold can name it. |
| Report-only threshold | A threshold that always passes. This project uses it to get a sub-metric into the summary. |
| `handleSummary()` | A function that gets the summary data at the end of the test and returns what to print or save. |
| Deadlock | A fault in a database where two transactions each hold a lock that the other one needs. The database ends one of them with an error. |
