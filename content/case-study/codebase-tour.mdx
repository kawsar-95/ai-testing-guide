# The dMoney Codebase

Parts 18 and 20 to 24 describe a QA workspace. The author also published it as the public repository [kawsar-95/genAI-project](https://github.com/kawsar-95/genAI-project). This part is a tour of that repository. It shows what each folder does and how the folders work together.

<Callout type="note" title="Where these facts come from">

The facts on this page come from the files of the public repository, read on 2026-10-27. They have no cites, because a cite links to an official source. Facts about Claude Code, MCP, and Playwright link to the official docs. The repository changes over time, so check its README for the latest state.

</Callout>

<Callout type="warning" title="The app has bugs on purpose">

dMoney is a practice target. It has known weaknesses, for example a default JWT secret, an OTP bypass for development, open CORS, and a balance query that builds SQL from a string. The repository documents known weaknesses in `qa-findings/` and in the `CLAUDE.md` file of the API. Do not deploy the app. Do not open it to the internet.

## The backend

<Voices>
<Technical>

A request goes through these files in this order:

```text
server.js → app.js → routes/*.route.js → controllers/**/*.controller.js
          → sequelizeModel/* and services/* → MySQL
```

| File or folder | What it does |
|---|---|
| `server.js` | Creates the HTTP server and listens on the port. |
| `app.js` | Adds body parsing, CORS, request logging, and the Swagger pages. It mounts all routes at `/` (there is no `/api` prefix). It ends with a 404 handler and an error handler. |
| `jwtMiddleware.js` | `authenticateJWT` needs a valid Bearer token and a matching `X-AUTH-SECRET-KEY` header. `publicAuthenticateJWT` checks the token only. |
| `routes/` | `/user/*` routes and `/transaction/*` routes. |
| `controllers/users/` | Register, two-step login, OTP check, user CRUD, and password reset. |
| `controllers/transactions/` | One file for each operation: deposit, withdraw, send money, payment, admin deposit, Stripe cash-in, and the read endpoints. |
| `sequelizeModel/` | The models: `Users`, `Role`, `Transactions`, `Commission`, and `TransactionLimit`. The `Users`, `Transactions`, and `Role` models create their tables when they load. `Users` and `Transactions` also add seed rows. The fee and limit tables come from the scripts in `migrations/`. |
| `services/` | Helpers for the balance, the transaction ID, the daily and monthly limits, and OTP email. |
| `migrations/` | One-off scripts that change the schema. Each script checks first, so you can run it twice. |
| `performance/` | The k6 load test. |

### Login and the two middlewares

Login has two steps for most roles. `POST /user/login` sends a 4-digit OTP that expires after 2 minutes. `POST /user/verify-otp` returns the JWT. Admin and SYSTEM accounts skip the OTP. A development switch (`?env=dev` with a default OTP) skips the real OTP too. The security report lists it as a known weakness.

### The ledger

The database has no balance column. The `Transactions` table is an append-only double-entry ledger. A row has an `account`, a `debit`, a `credit`, a `trnxId`, and a `transaction_type`. The balance of an account is the sum of its credits minus the sum of its debits.

The fees come from the `Commissions` table. The caps for a customer come from the `TransactionLimits` table. The rules are data, so a test can check them without a code change.

### Send Money, step by step

`sendMoney.controller.js` is the most important file for the case study. It does these steps:

1. It checks the input: both accounts are text, and the amount is a number with at most 2 decimals.
2. It loads the fee rule from `Commission`.
3. It checks that the token belongs to the sender.
4. It checks that both accounts are active Customers, that they are not the same account, and that the amount meets the minimum.
5. It opens a database transaction and reads the sender balance with `FOR UPDATE`. This lock makes parallel requests from one sender wait for each other.
6. It checks the daily and monthly limits inside the lock.
7. It checks that the balance covers the amount plus the fee.
8. It writes 3 ledger rows: the sender debit, the receiver credit, and the fee credit to SYSTEM.
9. It commits. If any step fails, it rolls back all 3 rows.

The lock and the rollback are the reason for the k6 test in [part 23](/case-study/automation/).

</Technical>

একটি request এই ক্রমে file-গুলোর মধ্য দিয়ে যায়: `server.js`, `app.js`, একটি route file, একটি controller, তারপর একটি model বা service, এবং শেষে MySQL।

- Admin ও SYSTEM OTP বাদ দেয়।

টাকা যেভাবে রাখা হয়:

- Database-এ কোনো balance column নেই।
- `Transactions` table একটি ledger। প্রতিটি row একটি debit বা credit যোগ করে, এবং row কখনো বদলানো হয় না।

Send Money যেভাবে কাজ করে:

1. এটি input check করে ও fee load করে।
2. এটি check করে যে token sender-এর, এবং দুটি account-ই active Customer।
3. এটি একটি database transaction খোলে ও `FOR UPDATE` দিয়ে sender-এর balance lock করে। একই sender-এর parallel request অপেক্ষা করে।
4. Lock-এর ভেতরে এটি limit ও balance check করে।
5. এটি 3টি ledger row লেখে: sender-এর debit, receiver-এর credit এবং SYSTEM-এ fee-এর credit।
6. এটি commit করে। কোনো ধাপ fail করলে 3টি row-ই rollback হয়।

## The web app

<Voices>

| File or folder | What it does |

## The AI layer

<Voices>
<Technical>

The workspace skills are in `.claude/skills/`. A skill is a folder with a `SKILL.md` file <Cite n={1} />.

| Skill | Job |
|---|---|
| `understand-task` | Explains an issue, a pull request, or a Jira ticket and lists its acceptance criteria. |
| `find-bug` | Hunts bugs in one module through the UI and the API. |
| `blast-radius` | Finds what a change can affect and ranks the retest list by risk. |
| `pr-review` | Reviews a pull request against the issues it closes. |
| `test-charter` | Writes exploratory test charters. |
| `test-design` | Designs traceable test cases. |
| `execute-test` | Runs prepared test cases and records pass, failed, or not executed. |

Two subagents do work that must stay separate <Cite n={2} />. `qa-reviewer-agent` only reads. It marks each drafted bug as approved, flagged, or rejected. `test-executor-agent` only runs existing test cases with `curl` and a browser tool. It does not design tests and it does not raise bugs.

One hook runs before the `test-design` and `find-bug` skills <Cite n={3} />. The hook runs a `graphify query` with the arguments of the skill. If the skill has no arguments, it adds the overview of the graph. The model does not have to remember this step.

The file `.mcp.json` lists three MCP servers <Cite n={4} />: `playwright` for the browser, `jira` for tickets, and `dmoney-db` for the database. The README says the database server is for read-only checks during analysis.

</Technical>

## How the layers work together

<Voices>
<Technical>

```text
find-bug ─▶ qa-reviewer-agent ─▶ qa-findings/NN-*-bugs.md ─▶ GitHub issues
                                                                  │
analyze-requirement ◀─────────────────────────────────────────────┘
        │
fix on a branch ─▶ PR ─▶ pr-review ─▶ blast-radius ─▶ test-charter
        │
test-design + qa-agent-advocate ─▶ test-executor-agent ─▶ fix failures ─▶ retest ─▶ k6
```

Each step writes a file. The next step reads it. The `analyze-requirement` skill (in each sub-project) turns an issue into acceptance criteria. The files are in `qa-findings/` and `.artifacts/`.

| Folder | Content |
|---|---|
| `qa-findings/` | Eight numbered reports: login and auth bugs, deposit bugs, deposit test cases, 11 security issues, deposit charters, a deposit test design, cash-in bugs, and 7 Send Money bugs. |
| `.artifacts/` | The files that skills write for each issue and each pull request: requirements, reviews, impact reports, charters, test cases, and test results. |

The Send Money work followed the whole chain. PR #8 had 17 passed, 5 failed, and 2 not executed test cases. PR #9 fixed the 5 failures.

</Technical>
<Layman>

The steps run in a chain. Each step writes a file, and the next step reads it.

1. `find-bug` finds a bug, and `qa-reviewer-agent` checks it. The bug goes to `qa-findings/` and then to a GitHub issue.
2. `analyze-requirement` turns the issue into acceptance criteria.
3. A fix goes on a branch and into a pull request.
4. `pr-review` and `blast-radius` check the pull request.
5. `test-charter` and `test-design` plan the tests.
6. `test-executor-agent` runs the tests.
7. The author fixes the failures, retests, and runs the k6 check.

The files are in `qa-findings/` (eight numbered reports) and `.artifacts/` (the files for each issue and each pull request). PR #8 had 17 passed, 5 failed, and 2 not executed test cases. PR #9 fixed the 5 failures.

</Layman>
<Bangla>

ধাপগুলো একটি chain-এ চলে। প্রতিটি ধাপ একটি file লেখে, এবং পরের ধাপ সেটি পড়ে।

1. `find-bug` একটি bug খোঁজে, এবং `qa-reviewer-agent` সেটি check করে। Bug যায় `qa-findings/`-এ, তারপর একটি GitHub issue-তে।
2. `analyze-requirement` issue-টিকে acceptance criteria-তে বদলায়।
3. একটি fix একটি branch-এ যায় ও একটি pull request-এ ঢোকে।
4. `pr-review` ও `blast-radius` pull request-টি check করে।
5. `test-charter` ও `test-design` test-এর পরিকল্পনা করে।
6. `test-executor-agent` test চালায়।
7. লেখক failure ঠিক করেন, retest করেন এবং k6 check চালান।

File-গুলো আছে `qa-findings/`-এ (আটটি নম্বর দেওয়া report) ও `.artifacts/`-এ (প্রতিটি issue ও pull request-এর file)। PR #8-এ 17টি test case pass, 5টি failed এবং 2টি not executed ছিল। PR #9 সেই 5টি failure ঠিক করেছে।

</Bangla>

## Take-aways

<Voices>
<Technical>

- Keep the app, the AI setup, and the outputs in one repository. Each layer can then point to the other two.
- Store the business rules in data. Tests and reviews can read them.
- Give each subagent one job. A reviewer that cannot write and an executor that cannot design catch more mistakes.
- Use a hook for a step that must run before a skill starts.
- Write each result to a file. The next skill reads the file, not the chat.

</Technical>
<Layman>

- Keep the app, the AI setup, and the outputs in one repository. Each layer can then point to the other two.
- Store the business rules in data. Tests and reviews can read them.
- Give each subagent one job.
- Use a hook for a step that must run before a skill starts.
- Write each result to a file. The next skill reads the file, not the chat.

- Business rule data হিসেবে রাখুন। Test ও review সেগুলো পড়তে পারে।
- প্রতিটি subagent-কে একটি কাজ দিন।
- যে ধাপ একটি skill শুরু হওয়ার আগে চলতে হবে তার জন্য hook ব্যবহার করুন।

## Key words

| Term | Meaning |
|---|---|
| Ledger | A table where each row adds a debit or a credit. Rows are never changed. |
| `FOR UPDATE` | A database lock. Other requests wait until the transaction ends. |
| JWT | A signed token that proves who the user is. |
| OTP | A one-time password. It is valid for a short time. |
| Skill | A folder with a `SKILL.md` file that Claude loads for a type of task. |
| Subagent | A helper with its own role and its own tool list. |
| Hook | A command that the tool runs at a set point, for example before a skill. |
| MCP server | A program that gives Claude extra tools, for example a browser. |
