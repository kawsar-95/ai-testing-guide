# Production Observability

Production monitoring for an AI system is not a dashboard. It is a list of conditions that make a human look at the system right now.

<PageMeta />

## In plain words

<Voices>
<Technical>

Observability for an LLM system has three layers, and each one answers a different question.

1. **Tracing.** Every model call, every retrieval, every tool use, recorded with its input, its output, its latency, and its token count. LangSmith describes these as the trace concepts <Cite n={4} />, and Langfuse captures the same shape of data <Cite n={1} />.
2. **Evaluation in production.** Running the metrics against real traffic rather than a fixed dataset. Langfuse documents the evaluation methods <Cite n={3} /> and Arize Phoenix documents the eval-in-production setup <Cite n={2} />.
3. **Alerting.** The conditions that make a human look. Four are worth having on day one: the hallucination rate rising, the faithfulness score falling, the cost per request rising, and the p95 latency rising past its budget.

The fourth alert is the one nobody plans for: **a silent model update**. The provider changes the model under the same model id, the behaviour shifts, and nothing in your code changed. The only defence is a canary: a small fixed dataset run on a schedule, with the score compared to the last one.

</Technical>
<Layman>

LLM সিস্টেমের observability-এর তিনটা স্তর আছে, আর প্রতিটা আলাদা প্রশ্নের উত্তর দেয়।

1. **Tracing।** প্রতিটা model call, প্রতিটা retrieval, প্রতিটা tool use, তার input, output, latency আর token সংখ্যাসহ রেকর্ড করা। LangSmith এগুলোকে trace concept বলে <Cite n={4} />, আর Langfuse একই ধরনের ডেটা ধরে <Cite n={1} />।

চতুর্থ alertটাই কেউ পরিকল্পনা করে না: **নীরবে model update**। provider একই model id রেখে model বদলে দেয়, আচরণ বদলে যায়, আর আপনার code-এ কিছুই বদলায়নি। একমাত্র প্রতিরক্ষা হলো একটা canary: নির্দিষ্ট ছোট dataset নির্ধারিত সময়ে চালিয়ে আগের স্কোরের সাথে তুলনা।

## How it works

<Voices>
<Technical>

The instrumentation is a decorator or a wrapper around the model call, and it has to capture enough to be useful without capturing anything sensitive:

```python
@observe(name="support.answer")
def answer_question(question: str, policy: str) -> str:
    chunks = retrieve(question, k=5)
    prompt = build_prompt(policy, chunks, question)
    return call_model(prompt)
```

The **trace** then contains the question, the retrieved chunk ids, the model call, the answer, the latency, and the token counts. The chunk ids matter as much as the answer: without them you cannot tell a grounding failure from a generation failure.

The **evaluation in production** samples real traffic and scores it. The sampling has to be **stratified**: if you sample the top 1% of traffic by confidence, you only ever see the good cases. Sample across categories, and always include the categories that matter most, even if they are rare. A compliance question is 2% of traffic and 80% of the risk.

The **alerts** are thresholds on the metrics, and each one needs three things that people forget:

```text
a threshold      the number, and it comes from the baseline, not a guess
a window         how long the metric must be out of line
an owner         who gets woken up
```

A threshold on a single request is noise. A threshold on the score over a rolling hour, with a named owner, is a signal.

And the **canary** is the fourth alert, done properly. A fixed dataset of real questions run every few hours against the production model, with the scores stored and compared. The check is not "is the score good" but "has the score moved", because the provider can change the model without changing the id, and the stored score history is what shows it <Cite n={3} />.

</Technical>

## In practice

<Voices>
<Technical>

The production eval samples traffic, scores it, and stores the result. The stratification is the part that matters:

```python
# app/observability/production_eval.py
CATEGORIES = {"refund", "account", "shipping", "compliance", "out_of_scope"}


def sample_traffic(rate: float = 0.02) -> list[Trace]:
    traces = trace_store.recent(hours=1)
    by_category = group_by(traces, key=lambda t: t.metadata["category"])
    sampled = []
    for category in CATEGORIES:
        pool = by_category.get(category, [])
        take = max(1, int(len(pool) * rate))  # always take some of the rare ones
        sampled += pool[:take]
    return sampled
```

And the alert, with the three parts it needs:

```python
ALERTS = [
    {
        "name": "hallucination_rate",
        "metric": "hallucination_rate",
        "threshold": 0.05,
        "window": "1h",
        "owner": "team-ai-quality",
    },
    {
        "name": "faithfulness_drop",
        "metric": "faithfulness",
        "threshold": 0.85,
        "window": "1h",
        "owner": "team-ai-quality",
    },
    {
        "name": "cost_per_request",
        "metric": "cost_usd_per_request",
        "threshold": 0.02,
        "window": "24h",
        "owner": "team-platform",
    },
    {
        "name": "p95_latency",
        "metric": "latency_p95_ms",
        "threshold": 5000,
        "window": "15m",
        "owner": "team-platform",
    },
]
```

Now the **canary**, which is the test that catches a silent model update:

```python
# tests/ai/test_canary.py
def test_the_production_model_has_not_changed_behaviour(canary, last_run):
    scores = canary.evaluate()
    assert scores.faithfulness >= last_run.faithfulness - 0.02, (
        f"faithfulness fell from {last_run.faithfulness} to {scores.faithfulness}"
    )
    assert scores.hallucination_rate <= last_run.hallucination_rate + 0.01
```

Notice the direction. A **drop** in faithfulness is a regression. A **rise** in the hallucination rate is a regression. The thresholds are small, because a silent provider change is usually a few points, not a cliff.

And the trace assertion, which is what makes a production failure diagnosable instead of a mystery:

```python
def test_the_trace_carries_the_retrieved_chunks(tracer):
    answer_question("How long do I have to return a laptop?", RETURN_POLICY)
    trace = tracer.last()
    assert trace.retrieved_chunk_ids, "the trace has no chunks, so a grounding failure is undiagnosable"
    assert trace.input_tokens > 0 and trace.output_tokens > 0
```

That last test is the one that stops the observability system from degrading into a log dump. It fails when someone adds a new code path and forgets to instrument the retrieval.

লক্ষ্য করুন দিকটা। faithfulness-এ **পতন** regression। hallucination rate-এ **বৃদ্ধি** regression। threshold ছোট রাখা, কারণ নীরব provider change সাধারণত কয়েক পয়েন্ট, কোনো চিহ্ন নয়।

আর trace assertion, যেটা production-এর ব্যর্থতাকে রহস্য না রেখে নির্ণয়যোগ্য করে:

```python
def test_the_trace_carries_the_retrieved_chunks(tracer):
    answer_question("How long do I have to return a laptop?", RETURN_POLICY)
    trace = tracer.last()
    assert trace.retrieved_chunk_ids, "the trace has no chunks, so a grounding failure is undiagnosable"
    assert trace.input_tokens > 0 and trace.output_tokens > 0
```

শেষ টেস্টটাই observability system-কে log dump-এ পরিণত হওয়া থেকে বাঁচায়। কেউ নতুন code path যোগ করে retrieval instrument করতে ভুলে গেলে সেটা ব্যর্থ হয়।

## Common mistakes

<Voices>
<Technical>

**Mistake 1: sampling only the easy traffic.** A confidence-weighted sample never sees the failures. Stratify by category and always include the rare high-risk ones <Cite n={2} />.

**Mistake 2: no canary.** Without a fixed dataset run on a schedule, a silent provider change is discovered by users <Cite n={3} />.

**Mistake 3: alerting on a single request.** One bad answer is noise. Alert on a windowed aggregate.

**Mistake 4: no owner.** An alert with no owner is a notification nobody reads.

**Mistake 5: logging the prompt and the answer but not the chunks.** Then a grounding failure and a generation failure look identical <Cite n={4} />.

**Mistake 6: no cost metric.** The cost alert is the one that stops a looping agent from becoming an invoice.

</Technical>
<Layman>

**Mistake ১: শুধু সহজ ট্রাফিক sample করা।** confidence-এর ওপর weight করা sample কখনো ব্যর্থতা দেখায় না। ধরন অনুযায়ী stratify করুন আর কম দেখা যায় এমন ঝুঁকিপূর্ণগুলো অবশ্যই রাখুন <Cite n={2} />।

## What a tester can check

<Voices>
<Technical>

<Callout type="tip" title="Tutorial advice">

This advice is the tutorial's own. It does not come from the sources.

- Make the canary dataset from real user questions, not from the eval set. The eval set tells you what you expected; the canary tells you what happened.
- Store the canary scores with a date. The trend is the signal, and a single score is not.
- Put the trace assertion in CI, not only in production. It is a unit test of your instrumentation.
- Set the alert thresholds from a week of baseline data. A threshold picked from intuition is either silent or noisy.
- Give every alert an owner and a runbook link. An alert without a runbook is a panic button.
- Test the alert path itself: trigger it in a staging environment and check that the message arrives and says what to do.
</Callout>

</Technical>

## Key words

| Word | What it means |
| --- | --- |
| Tracing | The record of every model call with its input, output, latency, and token counts |
| Production eval | Running the metrics against sampled real traffic |
| Stratified sampling | Sampling across categories so the rare high-risk cases are included |
| Canary | A fixed dataset run on a schedule to detect a provider's silent model change |
| Silent model update | A provider changing the model under the same id |
| Alert threshold | The value a metric must cross, set from a baseline |
| Alert window | How long the metric must be out of line before the alert fires |
| Owner | The team that receives an alert and knows what to do about it |
| Cost per request | The metric that catches a runaway agent before it becomes an invoice |
