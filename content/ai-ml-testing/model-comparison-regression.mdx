# Model Comparison and Regression Testing

A model upgrade is a code change with no diff. The only way to know what it broke is to run the same questions through it and compare.

<PageMeta />

## In plain words

<Voices>
<Technical>

A **golden dataset** is a fixed set of question-and-expected-fact pairs that stays the same for the whole life of the feature. Fifty pairs is a reasonable start. The pairs do not need to be exhaustive; they need to be **stable**, so that two runs, weeks apart, are comparing the same thing.

**Model comparison** runs that dataset against more than one model and puts the scores side by side. Promptfoo does this with a list of providers in one config, so the comparison is one command <Cite n={1} />.

**Regression testing** is the same dataset run again after a change, to see what the change broke. The changes that matter here: a model version bump, a prompt edit, a retrieval change, a chunking change, a temperature change, and a change to the safety settings. Any of these can move the score without anyone touching the feature's visible behaviour on purpose. Even a trivial formatting change, such as switching answer options from (A) to (1), is reported to change an evaluation's results <Cite n={2} />.

The report has to be broken down by category. An overall score across a mixed dataset hides the failure: a model that is perfect on short factual questions and invents facts on multi-hop ones still has a good average, and the average is the number everyone looks at first.

</Technical>

</Layman>
<Bangla>

**Golden dataset** হলো প্রশ্ন আর প্রত্যাশিত তথ্যের একটা নির্দিষ্ট তালিকা, যেটা ফিচারের সারা জীবন ধরে একই থাকে। পঞ্চাশটা জোড়া দিয়ে শুরু করা যুক্তিসঙ্গত। এগুলোর সম্পূর্ণ হওয়ার দরকার নেই; **স্থিতিশীল** হওয়া দরকার, যাতে কয়েক সপ্তাহ পরের দুটো run একই জিনিস তুলনা করে।

**Model comparison** সেই dataset একাধিক model-এর ওপর চালিয়ে স্কোর পাশাপাশি রাখে। Promptfoo একটা config-এ provider-এর তালিকা দিয়ে এটা করে, তাই তুলনা একটা কমান্ড <Cite n={1} />।

**Regression testing** হলো পরিবর্তনের পরে একই dataset আবার চালানো, যাতে দেখা যায় পরিবর্তন কী ভাঙল। যেসব পরিবর্তন গুরুত্বপূর্ণ: model version বাড়ানো, prompt সম্পাদনা, retrieval বদল, chunking বদল, temperature বদল, আর safety setting বদল। এগুলোর যেকোনোটাই ফিচারের দৃশ্যমান আচরণ ইচ্ছাকৃতভাবে না বদলেও স্কোর সরাতে পারে। এমনকি একটা তুচ্ছ formatting বদল, যেমন উত্তরের option (A) থেকে (1) করা, একটা evaluation-এর ফল বদলে দেয় বলে জানানো হয়েছে <Cite n={2} />।

রিপোর্ট ধরন অনুযায়ী ভাগ করতে হবে। মিশ্র dataset-এর সামগ্রিক স্কোর ব্যর্থতা ঢেকে দেয়: ছোট তথ্যমূলক প্রশ্নে পারফেক্ট আর multi-hop প্রশ্নে বানানো model-ও গড়ে ভালো স্কোর পায়, আর সেই গড়টাই সবাই প্রথমে দেখে।

</Bangla>

## How it works

<Voices>
<Technical>

One config, several providers, one test list:

```yaml
providers:
  - id: anthropic:messages:claude-sonnet-4-6
    label: sonnet-4-6
  - id: anthropic:messages:claude-haiku-4-5
    label: haiku-4-5
  - id: openai:chat:gpt-4o-mini
    label: gpt-4o-mini

tests: file://evals/golden-cases.yaml
```

One run produces one row per case per provider. The useful comparison is not the average but the **per-category breakdown**, because different models fail differently:

```text
category         cases   sonnet   haiku   mini
short fact         12     0.98    0.96    0.91
policy lookup      18     0.95    0.94    0.72
multi-hop          10     0.91    0.68    0.55
```

That table tells you the cheap model is fine for most traffic and useless for multi-hop questions, which is a routing decision, not a model decision.

**Regression tracking** is the same command over time, with the output files diffed:

```bash
npx promptfoo eval --output runs/2026-11-01.json
# by_category.py prints the per-category table (below) as JSON
diff <(python by_category.py runs/2026-11-01.json) <(python by_category.py runs/2026-11-08.json)
```

Two costs belong in the report, because they decide whether a quality gain is worth it: **token usage** and **latency** per case. A model that scores 0.95 instead of 0.90 and costs three times as much may be right for one case and wrong for ten thousand <Cite n={3} />.

</Technical>

## In practice

<Voices>
<Technical>

Build the golden dataset with the category as a field:

```yaml
# evals/golden-cases.yaml
tests:
  - description: Return window, simple lookup
    vars:
      policy: file://fixtures/return-policy.txt
      question: How long do I have to return a laptop?
      category: short-fact
    assert:
      - type: contains
        value: "30 day"
```

Produce the per-category breakdown:

```python
import json
from collections import defaultdict


def by_category(result_file: str) -> dict[str, dict[str, float]]:
    data = json.load(open(result_file))
    scores: dict = defaultdict(lambda: defaultdict(list))
    # field names follow Promptfoo's JSON example; confirm them against your own results file
    for output in data["results"]["outputs"]:
        category = output["vars"]["category"]
        passed = 1.0 if output["pass"] else 0.0
        scores[category][output["provider"]].append(passed)
    return {
        c: {p: sum(v) / len(v) for p, v in ps.items()}
        for c, ps in scores.items()
    }
```

Keep the run files; they are the regression history:

```bash
npx promptfoo eval --output runs/$(date +%F).json
git add runs/ && git commit -m "chore(evals): golden run $(date +%F)"
```

The golden dataset rots: a case the model has learned, or a policy that has changed, makes the case wrong. Review it on a schedule and version it with the policy it tests.

</Technical>

## Common mistakes

<Voices>
<Technical>

**Mistake 1: one overall score.** The average hides the category that broke.

**Mistake 2: no held-out cases.** A golden dataset you also tuned the prompt on measures memorisation.

**Mistake 3: comparing only against the current model.** A new model is only interesting against alternatives, including the cheaper one.

**Mistake 4: no cost column.** A quality gain that costs five times more is a business decision the tester has to surface <Cite n={3} />.

**Mistake 5: the dataset never changes.** A case that became wrong makes every future run look like a regression.

**Mistake 6: comparing free-text answers exactly.** Use a metric for prose and an exact match only for structured output.

</Technical>
<Layman>

**Mistake 1: one overall score.** The average hides the category that broke.

**Mistake 2: no held-out cases.** You tuned the prompt on the golden dataset too. Then it measures memorisation.

**Mistake 3: comparing only against the current model.** A new model is only interesting next to alternatives. Include the cheaper one.

**Mistake 4: no cost column.** A quality gain that costs five times more is a business decision the tester has to surface <Cite n={3} />.

**Mistake 5: the dataset never changes.** A case that became wrong makes every future run look like a regression.

</Layman>

**ভুল ১: একটাই গড় স্কোর।** গড় ঢেকে দেয় কোন ধরন ভাঙল।

**ভুল ২: held-out কেস নেই।** যে dataset-এর ওপর prompt টিউন করেছেন তা মুখস্থ মাপে।

**ভুল ৩: শুধু বর্তমান model-এর সাথে তুলনা।** নতুন model কেবল বিকল্পগুলোর তুলনায় আগ্রহজনক, সস্তাটাও তার মধ্যে।

**ভুল ৪: খরচের কলাম নেই।** পাঁচগুণ বেশি খরচে পাওয়া মান উন্নতি একটা business সিদ্ধান্ত, টেস্টারকে সংখ্যাটা দেখাতে হবে <Cite n={3} />।

**ভুল ৫: dataset কখনো বদলায় না।** ভুল হয়ে যাওয়া কেস পরের প্রতিটা run-কে regression দেখায়।

## What a tester can check

<Voices>
<Technical>

<Callout type="tip" title="Tutorial advice">

This advice is the tutorial's own. It does not come from the sources.

- Store the category in the test data, not in a spreadsheet beside it.
- Commit the run files. They are the history of quality.
- Report the per-category table and the cost per category together.
- Date the golden dataset and review it on the same schedule as the policy.
- Keep one known-bad case per category, so the scores mean something.
- Compare against the model you would switch to, not only the one you run.

## Key words

| Word | What it means |
| --- | --- |
| Golden dataset | A fixed, versioned set of question-and-answer pairs kept for comparisons |
| Model comparison | Running the same dataset against several models and comparing scores |
| Regression testing | Re-running the dataset after a change to catch what broke |
| Per-category score | The score for one class of question, which is what the breakdown needs |
| Token cost | The number of tokens a case consumed, which belongs beside the score |
| Held-out set | Cases not used while tuning, so the score is not memorisation |
