# Advanced Capstone: Production Pipeline and Monitoring

The pipeline does not stop at merge. It watches the model in production, too.

<PageMeta />

## In plain words

<Voices>
<Technical>

This session connects two things built separately in this course: the CI gate from the eval modules, and the observability tools from the monitoring modules, into one pipeline that covers both pre-merge and post-deploy. Promptfoo's eval runs as a required check on every PR <Cite n={1} />, wired through GitHub Actions <Cite n={6} />, exactly as in the first capstone. What is new here is adding LangFuse tracing <Cite n={3} /> and Arize Phoenix continuous evaluation <Cite n={4} /> on the deployed app, so quality is checked twice: once before the code merges, and continuously after it is live.

Cost monitoring and an A/B framework are the two pieces that only make sense once there is live traffic to measure: cost monitoring sums real token usage instead of a test suite's fixed case count, and an A/B framework compares two model or prompt versions on real questions instead of a frozen eval set.

</Technical>

## How it works

<Voices>
<Technical>

The two halves of the pipeline, pre-merge and post-deploy, side by side:

```text
PRE-MERGE (CI, blocks the PR)
  Promptfoo eval + agent decision tests -> exit code 100 fails the check

POST-DEPLOY (continuous, does not block anything by itself)
  every call traced via Langfuse
  a sample continuously scored by Arize Phoenix
  cost summed per session, alerted on a spike
  A/B split: a fraction of traffic on a candidate model or prompt version
```

The post-deploy half does not replace the pre-merge gate; it catches what the gate cannot, because it only sees the fixed eval set, not real traffic. A quality drop that only appears on a question nobody wrote a test case for shows up here first.

The A/B framework works by routing a small percentage of live traffic to a candidate version and comparing its traced metrics against the baseline's, over the same Phoenix or LangFuse pipeline already in place <Cite n={4} /> <Cite n={3} /> — it does not need a separate tracing setup, only a routing decision and a comparison query.

</Technical>

## In practice

<Voices>
<Technical>

The CI workflow, required on every PR <Cite n={6} /> <Cite n={1} /> <Cite n={2} />:

```yaml
# .github/workflows/advanced-capstone.yml
on: pull_request
jobs:
  gate:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npx promptfoo eval -c promptfooconfig.yaml  # exit code 100 fails the job
      - run: python -m pytest tests/agent_routing/
```

Production tracing and continuous eval on the deployed app <Cite n={3} /> <Cite n={5} />:

```python
from langfuse import observe
from phoenix.otel import register

register(project_name="advanced-capstone", auto_instrument=True)

@observe()
def handle_request(question: str) -> dict:
    return agent.invoke({"question": question})
```

Cost monitoring with an alert on a spike:

```python
def check_cost_anomaly(today_cost: float, trailing_7_day_avg: float) -> None:
    if today_cost > trailing_7_day_avg * 2:
        alert(f"cost spike: {today_cost:.2f} vs 7-day avg {trailing_7_day_avg:.2f}")
```

A minimal A/B split, comparing a candidate prompt against the baseline:

```python
import random

def handle_request_ab(question: str) -> dict:
    variant = "candidate" if random.random() < 0.1 else "baseline"
    result = agent_variants[variant].invoke({"question": question})
    return {**result, "variant": variant}  # tagged for later comparison in Phoenix/LangFuse
```

<Callout type="tip" title="Tutorial advice">

This advice is the tutorial's own. It does not come from the sources.

- Keep the CI gate and the production monitoring as separate systems with separate alerts; conflating them makes it unclear which one caught a given problem.
- Start the A/B split small (5-10% of traffic) and only widen it once the candidate's traced metrics hold up.
- Build the executive dashboard from the same stored metrics as the quality module, so there is one source of truth, not two.
</Callout>

## Common mistakes

<Voices>
<Technical>

**Mistake 1: treating the CI gate as sufficient on its own.** It only sees the fixed eval set; production tracing is what catches a problem the eval set never anticipated <Cite n={1} />.

**Mistake 2: starting an A/B split at 50%.** A bad candidate at 50% traffic does twenty-five times the damage of one at 2%; start small.

**Mistake 3: separate dashboards for cost, quality, and A/B results.** A reviewer checking three places misses the one that mattered this week.

**Mistake 4: alerting on a cost spike with no trailing baseline.** A fixed dollar threshold does not account for normal traffic growth; compare against a trailing average instead.

**Mistake 5: no link from a production alert back to a trace.** An alert that only says "quality dropped" with no trace id attached cannot be diagnosed <Cite n={4} /> <Cite n={3} />.

</Technical>
<Layman>

**Mistake ১: CI gate-কে নিজে নিজে যথেষ্ট ভাবা।** এটা শুধু স্থির eval সেট দেখে; production tracing-ই এমন একটা সমস্যা ধরে যা eval সেট কখনো অনুমান করেনি <Cite n={1} />।

**Mistake ২: ৫০%-এ একটা A/B split শুরু করা।** ৫০% traffic-এ একটা খারাপ candidate ২%-এর চেয়ে পঁচিশ গুণ ক্ষতি করে; ছোট শুরু করুন।

**Mistake ৩: cost, quality, আর A/B ফলাফলের জন্য আলাদা dashboard।** তিন জায়গা চেক করা একজন reviewer এই সপ্তাহে যা গুরুত্বপূর্ণ ছিল সেটা মিস করে।

**Mistake ৪: trailing baseline ছাড়া একটা cost spike-এ alert করা।** একটা স্থির ডলার threshold স্বাভাবিক traffic বৃদ্ধি হিসাব করে না; এর বদলে একটা trailing average-এর সাথে তুলনা করুন।

**Mistake ৫: একটা production alert থেকে একটা trace-এ ফিরে কোনো লিংক নেই।** শুধু "quality কমেছে" বলা একটা alert যাতে কোনো trace id নেই তা diagnose করা যায় না <Cite n={4} /> <Cite n={3} />।

</Layman>

- Confirm every alert links to the specific trace that triggered it.
- Confirm the cost alert compares against a trailing average, not a fixed number.

## Key words

| Word | What it means |
| --- | --- |

| A/B split | Routing a fraction of live traffic to a candidate version for comparison |
