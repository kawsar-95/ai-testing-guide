# Model Drift and A/B Testing

Two questions that look the same and are not: did the model change, or did the users change? The second one is drift, and it is a product problem.

<PageMeta />

## In plain words

<Voices>
<Technical>

**Drift** is a change in the data, not in the code. The users start asking different questions, the knowledge base changes, or the season changes, and the system's behaviour shifts with no deployment. The measurements tell you *that* something moved; they do not tell you *why*.

There are three kinds worth separating, because the fix is different for each:

```text
input drift       the questions changed
knowledge drift   the documents changed
output drift      the model's behaviour changed
```

Output drift is the one that gets called "the model got worse", and it is usually a provider change or a prompt change. Input drift is a product signal: the users want something you did not build for.

**A/B testing** two models in production is a different problem. You route a share of the traffic to each, measure both, and decide. The difficulty is statistical: with a low traffic volume, the difference you see can be noise. And with a small sample, a model that is better on average can still be worse for your users, because the categories differ.

The measurement has to be **per category** and the sample has to be big enough. The related idea runs in the other direction: instead of comparing two models, you run one model several times on the same input (the self-consistency paper samples several reasoning paths from one model <Cite n={2} />), and the spread between runs gives you a noise floor.

</Technical>

## How it works

<Voices>
<Technical>

The drift test and the A/B test are the same measurement with a different control, and the implementation is the same too:

```text
what changed?      compare the metric distribution of two periods
which is better?    compare the metric distribution of two arms
```

**Drift detection** needs a baseline. You take the distribution of a metric over a window, and you compare it to the distribution of the same metric over the baseline window. The comparison has to be on the **distribution**, not on the mean, because a distribution can shift without its mean moving much, and a mean can move because of one outlier.

The **category breakdown** is what makes the finding actionable. A drift in the overall faithfulness might be a drift in one category, and that category is usually a data problem you can fix.

For the A/B test, the implementation is a **router** in front of the model call, with the arm recorded on the trace:

```python
import hashlib


def choose_arm(user_id: str) -> str:
    bucket = int(hashlib.sha256(user_id.encode()).hexdigest(), 16) % 100
    if bucket < TRAFFIC_PERCENT:
        return "candidate"
    return "control"
```

The hash has to be on the **user id**, not random per request, or the same user sees both models and the comparison is contaminated.

The **analysis** has three requirements:

1. **Enough traffic.** A difference smaller than the noise floor is not a difference. The noise floor comes from repeated runs: run the control model several times on the same inputs and see how much its own score moves. The scores from both arms are kept in the evaluation store, so the comparison is against stored history and not against a number someone remembers <Cite n={1} />.
2. **A fixed decision rule, written before the test.** A test that looks at the results and then decides what counts as a win is not a test.
3. **Per-category analysis.** A model that wins on 80% of traffic and loses badly on the other 20% is a decision, not an average.

And the **guardrail metric** has to be checked in both arms. A candidate that scores 0.02 higher on relevance but refuses three times as many requests is not a win, and the average would hide it.

</Technical>

## In practice

<Voices>
<Technical>

The drift check compares two windows of the same metric, and it has to work on the distribution:

```python
# tests/ai/test_drift.py
import pytest
from scipy.stats import wasserstein_distance


@pytest.mark.slow
def test_the_faithfulness_distribution_has_not_drifted(trace_store, baseline):
    current = trace_store.scores(metric="faithfulness", window="24h")
    assert current.count() > 100, "not enough samples to compare"
    assert current.mean() >= baseline.mean() - 0.02, (
        f"mean fell from {baseline.mean():.3f} to {current.mean():.3f}"
    )
    drift = wasserstein_distance(baseline.samples, current.samples)
    assert drift < 0.05, f"the distribution moved by {drift:.3f}"
```

And the per-category version, which is the one that tells you where to look:

```python
@pytest.mark.slow
def test_no_single_category_has_drifted(trace_store, baseline):
    for category in CATEGORIES:
        current = trace_store.scores(metric="faithfulness", category=category, window="24h")
        if current.count() < 20:
            continue
        assert current.mean() >= baseline.for_category(category).mean() - 0.03, (
            f"category {category} drifted"
        )
```

Now the A/B test, with the arm recorded so the analysis can group by it:

```python
def test_the_router_is_stable_for_a_user():
    arms = {choose_arm("user-42") for _ in range(50)}
    assert len(arms) == 1, "the user was split across arms"
```

```python
def test_the_arms_get_roughly_equal_traffic(trace_store):
    counts = trace_store.count_by_arm(window="7d")
    total = sum(counts.values())
    share = counts["candidate"] / total
    assert 0.35 < share < 0.45, f"the candidate arm got {share:.0%} of traffic"
```

And the decision rule, written before the test runs, as a test:

```python
def test_the_candidate_arm_won_by_the_pre_written_rule(results):
    candidate = results["candidate"].mean_faithfulness
    control = results["control"].mean_faithfulness
    noise = results["noise_floor"]
    assert candidate - control > noise, (
        f"the gain {candidate - control:.4f} is inside the noise floor {noise:.4f}"
    )
    assert results["candidate_refusal_rate"] <= results["control_refusal_rate"] + 0.01
```

That last assertion is the guardrail check. A candidate that wins on relevance and refuses more is not a win, and the average score would never have shown it.

</Technical>

## Common mistakes

<Voices>
<Technical>

**Mistake 1: comparing means only.** The mean hides a distribution shift and a shift in one category.

**Mistake 2: no noise floor.** Without one you cannot tell a real difference from a lucky sample.

**Mistake 3: deciding the winner after seeing the results.** That is curve-fitting to noise. Write the rule first.

**Mistake 4: routing per request.** The same user sees both models and the comparison is contaminated.

**Mistake 5: only the overall score.** The categories differ, and the users who matter are in the smaller one.

**Mistake 6: no guardrail metric in the A/B test.** A candidate that wins on relevance and refuses more is a regression in disguise.

</Technical>
<Layman>

**Mistake 1: looking only at means.** The mean hides a shift in the distribution. It also hides a shift in one category.

**Mistake 2: no noise floor.** Without one, you cannot tell a real difference from a lucky sample.

**Mistake 3: picking the winner after seeing the results.** That fits your rule to noise. Write the rule first.

**Mistake 4: routing per request.** The same user sees both models. The comparison is contaminated.

**Mistake 5: using only the overall score.** The categories differ. The users who matter are in the smaller one.

**Mistake 6: no guardrail metric in the A/B test.** A candidate that wins on relevance but refuses more is a regression in disguise.

</Layman>
<Bangla>

**Mistake ১: শুধু গড় তুলনা।** গড় বিতরণের সরণ ঢেকে দেয় আর একটা ধরনের সরণও ঢেকে দেয়।

**Mistake ২: noise floor নেই।** ছাড়া আপনি বুঝতে পারেন না পার্থক্যটা আসল নাকি ভাগ্যকরম।

**Mistake ৩: ফল দেখে তারপর জেতা ঠিক করা।** এটা noise-এর সাথে curve-fitting। আগে নিয়ম লিখুন।

**Mistake ৪: প্রতি request-এ route।** একই ব্যবহারকারী দুটো model দেখে তুলনা নষ্ট হয়।

**Mistake ৫: শুধু সামগ্রিক স্কোর।** ধরনগুলো আলাদা, আর যারা গুরুত্বপূর্ণ তারা ছোট ধরনে।

**Mistake ৬: A/B test-এ guardrail metric নেই।** যে candidate relevance-এ জেতে আর বেশি প্রত্যাখ্যান করে সেটা ছদ্মবেশে regression।

</Bangla>

## What a tester can check

<Voices>
<Technical>

<Callout type="tip" title="Tutorial advice">

This advice is the tutorial's own. It does not come from the sources.

- Measure the noise floor before you run any A/B test. Five samples of the control model on the same inputs tell you what a difference has to beat.
- Write the decision rule into the test file, not into a document. A rule in the code cannot be quietly changed after the results arrive.
- Keep the per-category table for every A/B run. The average decides; the table explains.
- Route on a hash of the user id, and test that the hash is stable. A session-scoped random is a silent contamination.
- Compare the candidate's refusal rate as well as its quality score, every single time.
- When drift is detected, check the knowledge base and the corpus before the model. A provider change is the least likely of the three.
</Callout>

## Key words

| Word | What it means |
| --- | --- |
| Drift | A change in the input data or the knowledge base, with no code change |
| Input drift | The users started asking different questions |
| Knowledge drift | The documents changed under the system |
| Output drift | The model's own behaviour changed |
| A/B test | Routing a share of traffic to each variant and comparing them |
| Arm | One group in an A/B test, the control or the candidate |
| Noise floor | The amount the metric moves on its own, which a real difference must beat |
| Wasserstein distance | A measure of how far two distributions have moved apart |
| Guardrail metric | The metric checked in both arms so a quality win cannot hide a refusal spike |
