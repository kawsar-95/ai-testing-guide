# Your First Eval with Promptfoo

An eval is a test suite where the assertion is a property instead of an exact answer. Promptfoo is an open-source tool that runs one for you.

<PageMeta />

## In plain words

<Voices>
<Technical>

Promptfoo takes a **provider**, a set of **test cases**, and a set of **assertions**, runs them, and shows you the results in a table. It is an open-source command-line tool and library for evaluating LLM apps <Cite n={1} />. Its goal is test-driven LLM development instead of trial and error <Cite n={1} />.

The three parts of a Promptfoo config:

```yaml
prompts:
  - "Answer the question using only the policy.\n\nPolicy: {{policy}}\n\nQuestion: {{question}}"

providers:
  - id: anthropic:messages:claude-sonnet-4-6
    label: sonnet

tests:
  - vars:
      policy: 30-day returns for unopened items
      question: How long do I have to return a laptop?
    assert:
      - type: contains
        value: "30"
```

**Prompts** are the templates. **Providers** are the models to run. **Tests** are the cases, each with its variables and its assertions. The configuration reference is where the exact key names live <Cite n={2} />. It is worth reading before you guess <Cite n={2} />.

**Separation.** The thing that makes Promptfoo useful to a tester is the separation between **what you send** and **what you check**. The `vars` are the inputs. The `assert` list is the test. Changing an assertion does not change the prompt. So you can tighten a check without changing what the model sees. You can also compare two prompts against the same assertions without rewriting them.

</Technical>
<Layman>

Promptfoo needs three things: the model to use (the **provider**), some example questions (the **test cases**), and the checks to run on each answer (the **assertions**). It runs them all and shows the results in a table. It is an open-source tool for testing LLM apps <Cite n={1} />.

## How it works

<Voices>
<Technical>

When Promptfoo runs, it does this for every test case:

```text
1. render     the prompt template with the case's vars
2. call       the provider, once for each prompt and provider
3. assert     run each assertion against the output
4. record     the result, the output, and the timing
```

The rendering step is where `{{variable}}` placeholders are filled. The assertion step is where the quality lives, and it is the part that decides whether the eval is worth anything.

Promptfoo's assertion reference splits the assertion types into two groups <Cite n={3} />, and mixing them up is the usual mistake:

- **Deterministic assertions** are programmatic checks on the text: `contains`, `regex`, `javascript`, `equals`, `is-json`, `starts-with`, and any type with `not-` in front, such as `not-contains`. They are fast, free, and exact. They are also brittle when the wording can legitimately vary.
- **Model-assisted (model-graded) assertions** use a model to judge the output. `llm-rubric` grades the output against a rubric that you write. They handle "is this polite and on-topic", but each one costs a model call and the verdict can drift.

**Rule of thumb.** For a test suite, use deterministic assertions wherever a deterministic check exists. Use model grading only for the properties that genuinely need judgement. This is the tutorial's own advice. A suite of only rubric assertions is slow and noisy. A suite of only string assertions does not measure quality.

**Output.** The output of a run is a table with the pass or fail per case, the actual output, and the score. Promptfoo shows the results as a matrix, so you can compare the outputs of many prompts side by side <Cite n={1} />. That table is the artefact a tester attaches to a pull request.

</Technical>
<Layman>

For each test case, Promptfoo does four things:

```text
1. render     the prompt template with the case's vars
2. call       the provider, once for each prompt and provider
3. assert     run each assertion against the output
4. record     the result, the output, and the timing
```

First it fills the `{{variable}}` gaps in the prompt. Then it sends the prompt to the model. Then it runs your checks on the answer. Last, it saves the result. The checks are the part that decides whether the eval is worth anything.

Promptfoo has two kinds of checks <Cite n={3} />:

- **Rule checks** (deterministic), like `contains`, `regex`, or `is-json`. They look at the text. They are fast, free, and exact, but they break when a right answer uses different words.
- **Model checks** (model-graded), like `llm-rubric`. Another model reads the answer and your written rule and says pass or fail. They can judge things like "is this polite", but each one costs a model call, and the verdict can change.

The tutorial's advice: use a rule check when one can do the job, and a model check only when you really need judgement.

The result is a table: pass or fail for each case, the real answer, and the score. Promptfoo can show many prompts side by side <Cite n={1} />. A tester attaches the table to the pull request.

</Layman>

render ধাপে `{{variable}}` জায়গাগুলো ভরে যায়। assert ধাপেই মান যাচাই হয়, আর এই অংশটাই ঠিক করে eval-টার আসলে কোনো মূল্য আছে কি না।

Promptfoo-র assertion reference assertion type-গুলোকে দুটো দলে ভাগ করে <Cite n={3} />, আর এদের গুলিয়ে ফেলা সাধারণ ভুল:

- **Deterministic assertion** লেখাটা program দিয়ে যাচাই করে: `contains`, `regex`, `javascript`, `equals`, `is-json`, `starts-with`, আর সামনে `not-` লাগানো যেকোনো type, যেমন `not-contains`। এগুলো দ্রুত, বিনামূল্যে, আর হুবহু। কিন্তু সঠিক উত্তর অন্য ভাষায় এলে এগুলো সহজে ভেঙে যায়।
- **Model-assisted (model-graded) assertion** উত্তর বিচার করতে একটা model ব্যবহার করে। `llm-rubric` আপনার লেখা rubric অনুযায়ী উত্তরকে নম্বর দেয়। "উত্তরটা কি ভদ্র আর প্রাসঙ্গিক" — এমন প্রশ্ন এগুলো ধরতে পারে, কিন্তু প্রতিটায় একটা model call খরচ হয়, আর রায় বদলে যেতে পারে।

টিউটোরিয়ালের নিজের পরামর্শ: যেখানে deterministic যাচাই সম্ভব, সেখানে সেটাই ব্যবহার করুন; model grading রাখুন শুধু যেখানে সত্যিই বিচার লাগে। শুধু rubric assertion-এর suite ধীর আর অস্থির; শুধু string assertion-এর suite মান মাপে না।

একটা run-এর **ফলাফল** একটা টেবিল: প্রতি কেসের pass বা fail, আসল উত্তর, আর স্কোর। Promptfoo ফলাফল matrix আকারে দেখায়, তাই অনেক prompt-এর উত্তর পাশাপাশি তুলনা করা যায় <Cite n={1} />। এই টেবিলটাই টেস্টার pull request-এ যুক্ত করেন।

</Bangla>

## In practice

<Voices>
<Technical>

Promptfoo loads a `promptfooconfig.*` file, such as `promptfooconfig.yaml`, from the current folder, and `npx promptfoo eval` runs it. Use `-c` for a config file with another name <Cite n={2} />:

```bash
npx promptfoo eval
npx promptfoo eval -c path/to/config.yaml   # a config file with another name
```

A complete first config for a support bot:

```yaml
# promptfooconfig.yaml
description: Support bot quality checks

prompts:
  - file://prompts/support.txt

providers:
  - id: anthropic:messages:claude-sonnet-4-6
    label: sonnet-4-6

defaultTest:
  options:
    rubricPrompt: file://prompts/rubric.txt

tests:
  - description: Policy question
    vars:
      policy: file://fixtures/return-policy.txt
      question: How long do I have to return a laptop?
    assert:
      - type: contains
        value: "30 day"
      - type: llm-rubric
        value: The answer only uses the policy and does not promise a refund
      - type: javascript
        value: output.split(/\s+/).length <= 60
```

Notice the third assertion: a plain JavaScript check on the word count. A one-line `javascript` assertion gets the answer as `output` and returns the value of its expression <Cite n={3} />. That is a deterministic check for a property that might seem to need a rubric, and it costs no model call.

Run it and read the table. `--filter-providers` runs only the providers whose `id` or `label` matches <Cite n={2} />:

```bash
npx promptfoo eval
npx promptfoo eval --filter-providers sonnet-4-6   # only this provider
```

Then save the results before and after a prompt change, and compare them case by case:

```bash
npx promptfoo eval --output results-before.json
# change the prompt, then run the same tests again
npx promptfoo eval --output results-after.json
```

The comparison is where the value is. A prompt change that fixes four cases and breaks two is not obviously good, and only the comparison shows that.

</Technical>

## Common mistakes

<Voices>
<Technical>

**Mistake 1: testing with the prompt you tuned on.** An eval over the examples you wrote while building tells you nothing. Use held-out cases.

**Mistake 2: only `contains` assertions.** `contains` is brittle and it does not measure quality. A rubric or a semantic check such as `similar` belongs next to it <Cite n={3} />.

**Mistake 3: only rubric assertions.** Every case then costs at least two model calls (the answer and the judge), the judge drifts, and the run is slow. Prefer a deterministic check when one exists.

**Mistake 4: no output recorded.** If the run does not save the outputs, you cannot debug the failures afterwards.

**Mistake 5: one provider only.** A suite that only runs the current model cannot tell you whether a cheaper model would pass.

**Mistake 6: a passing eval and no threshold.** "All tests passed" is not a quality bar. Set a `threshold`: a test fails when the combined score of its assertions is less than this number <Cite n={2} />. And do not over-read the number: Anthropic warns against overinterpreting the quantitative score of any eval <Cite n={4} />.

</Technical>
<Layman>

**Mistake 1: testing on the examples you tuned with.** If you test with the same examples you used to write the prompt, the test tells you nothing. Use new cases.

**Mistake 2: only `contains` checks.** A word check breaks easily and does not measure quality. Add a rubric or a meaning check such as `similar` next to it <Cite n={3} />.

**Mistake 3: only rubric checks.** Then every case needs at least two model calls, the judge can change its mind, and the run is slow. Use a rule check when one exists.

**Mistake 4: not saving the answers.** If the run does not keep the answers, you cannot find out later why a case failed.

**Mistake 5: only one model.** If you test only the current model, you cannot tell whether a cheaper one would also pass.

**Mistake 6: no pass mark.** "All tests passed" is not a quality bar. Set a `threshold`: the test fails when its combined score is below that number <Cite n={2} />. Also, do not read too much into one score; Anthropic warns about this <Cite n={4} />.

</Layman>

## What a tester can check

<Voices>
<Technical>

<Callout type="tip" title="Tutorial advice">

- Commit `promptfooconfig.yaml` next to the prompt it tests. The config and the prompt are one change, not two.
- Use `file://` for the prompt, the policy fixtures, and the rubric prompt. Inlined text in the config is impossible to diff cleanly.
- Save every run's output to a file and attach it to the pull request. The table is the evidence.
- Keep one case that is expected to fail, and check that it still fails. A suite where everything passes is a suite with no power.
- Run the eval before and after a prompt change, and put both tables in the pull request. One table alone shows nothing.
- Put the eval in CI with a threshold, not just in a developer's terminal. That is the CI/CD module later in this course.
</Callout>

## Key words

| Word | What it means |
| --- | --- |
| Eval | A test suite that measures a property of the output instead of one exact output |
| Promptfoo | A tool that runs prompts against providers and checks assertions on the results |
| Provider | The model an eval runs against |
| Assertion | One check applied to the output of a test case |
| Rubric | A written criterion that a judge model checks the output against |
| Model-graded assertion | An assertion that uses a model as the judge (Promptfoo calls these model-assisted) |
| Deterministic assertion | An assertion that checks the text with a rule, not a model |
| Test case | One set of variables and the assertions applied to them |
| Threshold | The score a test or an assertion must reach to pass |
