# Synthetic Data Generation with DSPy

The scarcest thing in AI testing is a good test set. You can generate one from the documents you already have.

<PageMeta />

## In plain words

<Voices>
<Technical>

**Synthetic data** is test data you generate rather than collect. For AI testing it solves the real problem: a hand-written eval set is small, biased towards what you already thought of, and expensive to grow.

Two tools do this, from opposite ends:

- **Giskard's quality scan** generates test scenarios from a knowledge base. Each generator probes one way an assistant goes wrong (hallucination, sycophancy, split or multi-topic questions, out-of-scope questions), and every scenario is tagged with the quality it tests and the component it stresses. It replaced the v2 RAGET tool <Cite n={3} /> <Cite n={4} />.
- **DSPy** optimizes a prompt program against a metric. You describe the task "write a question that this document answers", and it compiles a pipeline that does it well, so it can be used to build the question generator <Cite n={1} /> <Cite n={2} />.

The pipeline the two are usually combined into has four stages, and the third is the one that matters:

```text
source documents
   -> generate questions      the model writes them from each document
   -> generate answers        a second model answers them, using the document
   -> VERIFY the answers      is the answer supported by the document?
   -> golden dataset          only the questions that survived
```

The verification stage is what separates a useful synthetic dataset from a large pile of wrong test cases. An unverified synthetic dataset is a liability: it teaches the model to be confidently wrong and then tests you on it.

</Technical>

## How it works

<Voices>
<Technical>

**The generation step** is a prompt that asks a model to write questions a document answers, with a difficulty and a type. DSPy makes this reliable by optimising the prompt program against a metric, so the questions get better without you editing the prompt by hand each time <Cite n={2} />.

**The answer step** uses a second model that sees the document and answers the question. Two models is deliberate: the question writer and the answerer have different failure modes, and a single model answering its own question is much more likely to produce a confident, self-consistent, wrong pair.

**The verification step** is where the dataset is made trustworthy, and it has three checks:

```text
supported    is every claim in the answer in the document?
answerable   does the document actually contain the answer?
distinct     is this question different from the ones already in the set?
```

The third check is the one people forget, and without it a big generated dataset is mostly the same question forty times. Giskard's quality scan tags each scenario by kind, which gives you a natural way to see which kinds of failure your set already covers <Cite n={3} />.

**The last step** is a human sample. Not all of them: a few dozen, read by a person, to estimate the false rate of the verification. The verification is itself a model call, and a model that verifies answers is also fallible.

The DSPy side has one more thing worth using: the **optimizer**. It compiles a prompt program against your metric, so the question generator gets better at producing questions your verifier accepts, and the metric becomes part of the system rather than a separate script <Cite n={1} />.

</Technical>

## In practice

<Voices>
<Technical>

The generation prompt is the design, and it asks for the type and the difficulty:

```python
QUESTION_PROGRAM = """Write one question that the document below answers.
The question must:
- be answerable from the document alone
- name no fact that the document does not state
- differ from every other question in the set

Difficulty: {difficulty}
Type: {question_type}

Document:
{document}
"""
```

The verification is where the dataset is made safe, and the three checks are separate assertions:

```python
def test_the_generated_answer_is_supported_by_the_document(question, answer, document):
    claims = split_into_claims(answer)
    for claim in claims:
        assert claim in document, f"unsupported claim: {claim}"
```

```python
def test_the_generated_question_is_not_a_duplicate(question, existing_questions):
    embedding = embed(question)
    for other in existing_questions:
        assert cosine(embedding, embed(other)) < 0.95, (
            f"near-duplicate of: {other}"
        )
```

The duplicate check is the one that changes the dataset the most, and it needs an embedding rather than a string compare, because "How long is the return window?" and "What is the return period?" are the same question.

And the human sample, which measures the verifier itself:

```python
def test_the_verifier_agrees_with_a_human_on_a_sample(verified, human_reviewed):
    disagreements = [c for c in verified if c.id in human_reviewed
                      and c.verified != human_reviewed[c.id]]
    rate = len(disagreements) / len(human_reviewed)
    report.add("verifier_false_rate", rate)
    assert rate < 0.05, f"the verifier disagrees with humans {rate:.1%} of the time"
```

That last test is the one that makes the whole approach honest. The verifier is a model, and a model that checks answers is also fallible, so its error rate has to be measured rather than assumed.

The DSPy optimizer then improves the generator against that same metric:

```python
import dspy


class WriteQuestion(dspy.Signature):
    document: str = dspy.InputField()
    question: str = dspy.OutputField()


def verifier_metric(example, pred, trace=None):
    return verify(pred.question, example.document)  # True or False


program = dspy.ChainOfThought(WriteQuestion)
trainset = [dspy.Example(document=d).with_inputs("document") for d in verified_documents]
optimizer = dspy.BootstrapFewShot(metric=verifier_metric, max_bootstrapped_demos=8)
compiled = optimizer.compile(program, trainset=trainset)
```

Training the optimizer on the verified examples only is the point: the optimizer learns what a good question looks like from the questions that survived, not from the ones that were thrown away <Cite n={2} />.

</Technical>

```python

    return verify(pred.question, example.document)  # True or False


program = dspy.ChainOfThought(WriteQuestion)

compiled = optimizer.compile(program, trainset=trainset)
```

</Layman>

QUESTION_PROGRAM = """Write one question that the document below answers.

verification যেখানে dataset নিরাপদ হয়, আর তিনটা যাচাই আলাদা assertion:

```python
def test_the_generated_answer_is_supported_by_the_document(question, answer, document):
    claims = split_into_claims(answer)
    for claim in claims:
        assert claim in document, f"unsupported claim: {claim}"
```

```python
def test_the_generated_question_is_not_a_duplicate(question, existing_questions):
    embedding = embed(question)
    for other in existing_questions:
        assert cosine(embedding, embed(other)) < 0.95, (
            f"near-duplicate of: {other}"
        )
```

duplicate চেকটাই dataset-কে সবচেয়ে বেশি বদলায়, আর এতে string তুলনা নয় embedding লাগে, কারণ "How long is the return window?" আর "What is the return period?" একই প্রশ্ন।

আর মানুষের নমুনা, যেটা verifier-কেই মাপে:

```python
def test_the_verifier_agrees_with_a_human_on_a_sample(verified, human_reviewed):
    disagreements = [c for c in verified if c.id in human_reviewed
                      and c.verified != human_reviewed[c.id]]
    rate = len(disagreements) / len(human_reviewed)
    report.add("verifier_false_rate", rate)
    assert rate < 0.05, f"the verifier disagrees with humans {rate:.1%} of the time"
```

শেষ টেস্টটাই পুরো পদ্ধতিটাকে সৎ করে। verifier একটা model, আর উত্তর যাচাই করা model-ও ভুল হতে পারে, তাই তার error rate অনুমান না করে মাপতে হবে।

তারপর DSPy optimizer সেই একই metric-এর বিপরীতে generator-কে উন্নত করে:

```python
import dspy


class WriteQuestion(dspy.Signature):
    document: str = dspy.InputField()
    question: str = dspy.OutputField()


def verifier_metric(example, pred, trace=None):
    return verify(pred.question, example.document)  # True or False


program = dspy.ChainOfThought(WriteQuestion)
trainset = [dspy.Example(document=d).with_inputs("document") for d in verified_documents]
optimizer = dspy.BootstrapFewShot(metric=verifier_metric, max_bootstrapped_demos=8)
compiled = optimizer.compile(program, trainset=trainset)
```

শুধু যাচাই পাস করা উদাহরণে optimizer train করাটাই পয়েন্ট: optimizer শেখে ভালো প্রশ্ন কেমন হয়, আর যেগুলো ছুঁড়ে ফেলা হয়েছে সেগুলো থেকে নয় <Cite n={2} />।

## Common mistakes

<Voices>
<Technical>

**Mistake 1: no verification step.** An unverified synthetic dataset trains the model to be confidently wrong and then tests you on it.

**Mistake 2: one model writes the question and answers it.** Self-consistent and wrong at the same time is the worst combination.

**Mistake 3: no duplicate check.** A large generated set is often a few dozen questions repeated.

**Mistake 4: no human sample.** The verifier is a model too, and its error rate has to be measured.

**Mistake 5: using the generated set as the only eval.** A dataset written by a model tests for the failures that model has.

**Mistake 6: training the optimizer on unverified examples.** It learns from the questions you were going to throw away.

**Mistake 7: regenerating the set on every run.** The eval must be fixed, or two runs cannot be compared.

</Technical>
<Layman>

**Mistake 1: verification ধাপ নেই।** যাচাই না করা synthetic dataset model-কে আত্মবিশ্বাসী ভুল হতে শেখায়, আর তারপর সেটা দিয়ে আপনাকেই টেস্ট করে।

**Mistake 2: একই model প্রশ্ন লেখে আর উত্তরও দেয়।** self-consistent আর ভুল একসাথে হওয়াটাই সবচেয়ে খারাপ সমন্বয়।

**Mistake 3: duplicate চেক নেই।** বড় তৈরি set প্রায়ই কয়েক ডজন প্রশ্নের পুনরাবৃত্তি।

**Mistake 4: মানুষের নমুনা নেই।** verifier-ও একটা model, আর তার error rate মাপতে হবে।

**Mistake 5: তৈরি set-কেই একমাত্র eval হিসেবে ব্যবহার করা।** model-এর লেখা dataset ওই model-এর ব্যর্থতাগুলোর জন্যই টেস্ট করে।

**Mistake 6: যাচাই না করা উদাহরণে optimizer train করা।** এটা শেখে ফেলে যে প্রশ্নগুলো ছুঁড়ে ফেলা হবে।

**Mistake 7: প্রতিটা run-এ set আবার তৈরি করা।** eval-এর নির্দিষ্ট থাকতে হবে, নইলে দুটো run তুলনা যায় না।

## What a tester can check

<Voices>
<Technical>

<Callout type="tip" title="Tutorial advice">

This advice is the tutorial's own. It does not come from the sources.

- Commit the generated dataset. It is an asset, and regenerating it every time means every eval measures a different thing.
- Keep the generation prompt, the verifier prompt, and the models in version control next to the dataset. The dataset is meaningless without them.
- Log the verifier's decision for every case, not just the verdict. When a case is wrong later you need to know why it was accepted.
- Keep the difficulty label. The hard cases are the ones worth generating more of, and they are the ones you keep when you prune.
- Sample the generated set by hand every few months. The knowledge base changes and the questions drift out of date.
- Never let the synthetic set replace your hand-written one. Keep both, and compare the scores: a gap between them is a finding about the coverage.
</Callout>

</Technical>

## Key words

| Word | What it means |
| --- | --- |
| Synthetic data | Test data you generate rather than collect |
| Golden dataset | The fixed, versioned set of cases the eval runs against |
| Verification | Checking that a generated answer is supported by its source document |
| Answerable | Whether the document actually contains the answer to the question |
| Duplicate check | Rejecting a generated question that is too close to an existing one |
| DSPy | A framework that compiles and optimises prompt programs against a metric |
| Optimizer | The component that improves a prompt program using examples and a metric |
| Scenario tag | A label on a generated test scenario naming the quality it tests and the component it stresses |
