# Multi-Turn Conversation Testing

A chatbot that answers each question alone is a search box. The hard part is the conversation, and the conversation is where the state lives.

<PageMeta />

## In plain words

<Voices>
<Technical>

A multi-turn test has to check three things at once: that the **history** is sent, that the model **uses** it, and that the answer stays **relevant to the current turn**.

The **context window** is the limit on how much history fits. Every turn consumes tokens, so a long conversation eventually pushes the earliest turns out. The question "what did I say earlier?" then fails, and it fails silently, because nothing reports the truncation.

**Topic switching** is the second axis. A user asks about returns, then asks about their password, then asks "and what was the window?" The last question has no answer without the history, and the test has to decide whether the bot should carry the return context across the password question or not. Both behaviours are defensible; the product has to pick one and the test has to enforce it.

**Contradiction** is the third. The user says "my order number is 1001", then says "sorry, 1002". A good bot corrects the earlier value; a naive one answers about 1001.

The **reset** is the fourth. A user says "forget what I told you" or starts a new topic entirely, and the conversation history should be dropped. If the bot keeps the old order id, it acts on a stale order.

The measurement tools exist for this: DeepEval ships multi-turn metrics (Turn Relevancy, Role Adherence, Knowledge Retention, Conversation Completeness) <Cite n={1} />, and Ragas has a tutorial on evaluating multi-turn conversations <Cite n={2} />.

</Technical>

**Contradiction** তৃতীয়। ব্যবহারকারী বলে "আমার অর্ডার নম্বর 1001", তারপর বলে "sorry, 1002"। ভালো bot আগের মান শুধরায়; সরল bot 1001 নিয়েই উত্তর দেয়।

**Reset** চতুর্থ। ব্যবহারকারী বলে "আমি যা বলেছি ভুলে গেছো" বা নতুন topic শুরু করে, আর কথোপকথনের ইতিহাস বাদ দেওয়া উচিত। bot পুরোনো order id রাখলে সেটা stale order-এ কাজ করে।

## How it works

<Voices>
<Technical>

The conversation state has three parts, and each is separately testable:

```text
the message list    what is sent to the model, turn by turn
the summary        the compressed form of older turns, if the app uses one
the scratchpad      the facts extracted along the way, like an order id
```

The **message list** is the easiest to test and the easiest to get wrong. The assertion is on the request: after turn three, does the request contain three user messages and three assistant messages, in order, with the right roles? A chatbot that drops the assistant's own replies is a common bug and it is invisible in the UI, which only shows the user's bubbles. A test case holds the expected roles and the expected contents.

The **summary** is where the truncation shows. If the app summarises older turns, the summary has to keep the facts that matter, like the order id, and drop the small talk. The test writes a long conversation with one fact buried at the start and checks that the fact survives.

The **scratchpad** is the most useful and the least used. A well-built chatbot extracts the order id once and keeps it, instead of re-reading it from the transcript every turn. That makes the bot faster and more accurate, and the test can assert on the scratchpad directly.

**Contradiction handling** has a policy question and then a test. The policy: does a later correction override an earlier value? The test: give the contradicting value and check that the answer uses the new one.

**Reset** has two forms. The explicit one, where the user asks to forget. The implicit one, where the app detects a new conversation. Both need a test, and the implicit one is the one teams forget: a new conversation id should mean an empty history, and a test that reuses the id across two conversations finds that.

</Technical>

## In practice

<Voices>
<Technical>

The message-list test asserts on the request, because that is where the history actually lives:

```python
def test_the_history_is_sent_in_order(client, conversation):
    conversation.ask("My order number is 1001")
    conversation.ask("What is the return window?")
    conversation.ask("And for opened items?")

    last = client.requests[-1]
    roles = [m["role"] for m in last["messages"]]
    assert roles == ["user", "assistant", "user", "assistant", "user"], roles
    assert last["messages"][0]["content"] == "My order number is 1001"
```

The contradiction test, which needs the policy stated first:

```python
def test_a_later_correction_overrides_the_earlier_value(conversation):
    conversation.ask("My order number is 1001")
    conversation.ask("What is the status of my order?")
    conversation.ask("Sorry, the order number is 1002")

    answer = conversation.ask("What is the status of my order?")
    assert "1002" in answer
    assert "1001" not in answer, "the bot used the corrected-away order number"
```

The topic-switch test, which asserts the product's chosen policy:

```python
def test_the_return_context_survives_an_unrelated_question(conversation):
    conversation.ask("How long do I have to return a laptop?")
    conversation.ask("How do I reset my password?")
    answer = conversation.ask("How long do I have to return a laptop?")
    assert "30 day" in answer.lower(), "the earlier answer was lost"
```

The scratchpad test, which is the one that makes a chatbot fast and is almost never written:

```python
def test_the_order_id_is_extracted_once(conversation, scratchpad):
    conversation.ask("My order number is 1001")
    conversation.ask("And opened items?")
    assert scratchpad["order_id"] == "1001"
```

And the reset test, both forms:

```python
def test_an_explicit_reset_clears_the_history(conversation, client):
    conversation.ask("My order number is 1001")
    conversation.ask("Forget what I told you")
    conversation.ask("What is my order number?")
    last = client.requests[-1]
    assert "1001" not in str(last["messages"]), "the history survived the reset"
```

```python
def test_a_new_conversation_id_starts_with_no_history(client):
    client.ask(conversation_id="c1", message="My order number is 1001")
    client.ask(conversation_id="c2", message="What is my order number?")
    last = client.requests[-1]
    assert len(last["messages"]) == 1, "the second conversation inherited the history"
```

The last test catches the bug where the conversation id is generated once per session instead of once per conversation.

## Common mistakes

<Voices>
<Technical>

**Mistake 1: testing only the visible transcript.** The transcript is what the user sees; the request is what the model gets. They differ.

**Mistake 2: no policy for contradictions.** "Should the later value win?" is a product decision, and the test has to encode whichever answer you chose.

**Mistake 3: no long-conversation test.** The truncation bug only appears after the context window fills, which is the conversation nobody tests.

**Mistake 4: no reset test.** The stale order id after a reset acts on the wrong order.

**Mistake 5: reusing the conversation id across conversations.** That is a state leak, and it is invisible in a single-conversation test.

**Mistake 6: no evaluation of the conversation as a whole.** The per-turn answers can each be fine while the conversation is useless. DeepEval's multi-turn metrics, such as Conversation Completeness, exist for that <Cite n={1} />.

</Technical>
<Layman>

**Mistake 1: checking only the visible transcript.** The transcript is what the user sees. The request is what the model gets. They differ.

**Mistake 2: no policy for contradictions.** "Should the later value win?" is a product decision. The test must encode whichever answer you chose.

**Mistake 3: no long-conversation test.** The truncation bug only appears after the context window fills. Nobody tests that conversation.

**Mistake 4: no reset test.** After a reset, a stale order id means the bot acts on the wrong order.

**Mistake 5: reusing the conversation id across conversations.** This is a state leak. A single-conversation test cannot see it.

**Mistake 6: not judging the conversation as a whole.** Each answer can be fine while the conversation is useless. DeepEval's multi-turn metrics, such as Conversation Completeness, exist for that <Cite n={1} />.

</Layman>
<Bangla>

**Mistake 1: শুধু দৃশ্যমান transcript টেস্ট করা।** transcript হলো যা ব্যবহারকারী দেখে; request হলো যা model পায়। দুটো আলাদা।

**Mistake 2: contradiction-এর policy নেই।** "পরের মান কি জেতে?" একটা product সিদ্ধান্ত, আর টেস্টে আপনার বেছে নেওয়া উত্তরই encode করতে হবে।

**Mistake 3: লম্বা কথোপকথনের টেস্ট নেই।** truncation বাগ শুধু context window ভরার পরে দেখা যায়, আর সেই কথোপকথনটাই কেউ টেস্ট করে না।

**Mistake 4: reset টেস্ট নেই।** reset-এর পর stale order id ভুল order-এ কাজ করে।

**Mistake 5: কথোপকথনের মধ্যে conversation id পুনঃব্যবহার।** এটা state leak, আর একটি কথোপকথনের টেস্টে অদৃশ্য।

**Mistake 6: পুরো কথোপকথনের মূল্যায়ন নেই।** প্রতিটা টার্নের উত্তর আলাদা ঠিক থাকতে পারে আর পুরো কথোপকথন অকার্যকর হতে পারে। DeepEval-এর multi-turn metric, যেমন Conversation Completeness, ঠিক এর জন্যই আছে <Cite n={1} />।

## What a tester can check

<Voices>
<Technical>

<Callout type="tip" title="Tutorial advice">

This advice is the tutorial's own. It does not come from the sources.

- Assert on the request body, not on the transcript. The transcript can look perfect while the history is not being sent.
- Write the conversation policy down: does a later correction win, does a topic switch carry context, does a reset clear it. The tests are the policy.
- Keep one test with thirty turns. That is where the context window fills and where the summarisation either works or does not.
- Test the conversation id, not just the conversation. A reused id is a state leak between users.
- Evaluate the whole conversation as well as the turns. A chatbot that answers every turn well and never solves the problem is a bad chatbot.
- Log the token count of every turn in the test output. A conversation that grows the prompt by 500 tokens a turn has a problem before it has a bug.

## Key words

| Word | What it means |
| --- | --- |
| Multi-turn | A conversation with more than one exchange, where the history matters |
| Message list | The turns sent to the model, in order, with their roles |
| Summary | The compressed form of older turns, used when the history is too long |
| Scratchpad | The facts extracted along the way, such as an order id, kept separately |
| Truncation | Older turns falling out of the context window |
| Contradiction | The user giving a value that conflicts with an earlier one |
| Conversation reset | Clearing the history, either on request or on a new conversation |
| State leak | One conversation seeing another's state |
| Conversation-level metric | A score for the conversation as a whole, not one turn |
