# Advanced Capstone Presentation: Demo Day

Demo day is also a test of your test report. The audience will ask the question your dashboard cannot answer.

<PageMeta />

## In plain words

<Voices>
<Technical>

The course's final session for this module is a presentation to the cohort and guest reviewers, covering system architecture, test strategy, test results, vulnerabilities found, quality metrics, a live CI/CD pipeline demo, and the monitoring dashboard, followed by peer review and feedback <Cite n={1} />. Every one of those seven items is an artifact this module already built; the session is presenting them, not creating new ones.

The difference between this and the Phase 1 capstone's presentation is scope: the agent's routing decisions, the multi-source retrieval, the A/B framework, and the production monitoring all need their own slide or demo moment, because they are the parts of this capstone that the simpler Phase 1 project did not have to explain.

</Technical>

## How it works

<Voices>
<Technical>

A presentation built from this module's own artifacts, in the order the course lists them <Cite n={1} />:

```text
1. architecture        the multi-source + agent diagram from the setup session
2. test strategy       scope, risks, and gates, written down before testing began
3. test results        the Ragas four-metric scores, and the multi-turn results
4. vulnerabilities     the Giskard 40+ probe findings, by threat type and OWASP id
5. quality metrics     the live dashboard: hallucination rate, cost, latency P95
6. CI/CD demo          a real PR triggering the gate, shown live, not a screenshot
7. monitoring          the Phoenix/LangFuse dashboard, with a real trace opened
```

Peer review after the demo is where gaps surface that the presenter did not notice: a reviewer asking "what happens if two sources disagree" is testing the presentation the same way the test suite tested the app, and a presenter who built the suite in this module should be able to answer from a real test case, not a guess.

## In practice

<Voices>
<Technical>

A seven-slide outline, each slide backed by a real artifact rather than prose:

```text
slide 1  architecture diagram (image, exported from the setup session's docs)
slide 2  the test plan file, shown directly, not retyped
slide 3  a screenshot of the Ragas result table, all four metrics visible
slide 4  the Giskard findings table, grouped by threat type, failures first
slide 5  the live quality dashboard, opened in the browser during the talk
slide 6  a real pull request, opened live, showing the gate run and pass
slide 7  the Phoenix or LangFuse UI, with one real trace expanded
```

A short script for handling an unexpected peer-review question, since the goal is an honest answer grounded in a real test, not an improvised one:

```text
if you tested it: open the specific test file or trace and answer from it
if you did not test it: say so, and name which session's suite would cover it
```

<Callout type="tip" title="Tutorial advice">

This advice is the tutorial's own. It does not come from the sources.

- Rehearse the live demo parts (the PR trigger, the dashboard, the trace) beforehand on the actual environment, not just in slides.
- Prepare one answer in advance for "what is the worst thing you found"; reviewers ask it almost every time, and a real answer is more convincing than a generic one.
- Keep a laptop with the repo and a running instance ready during peer review, so a question can be answered by running something, not guessing.
</Callout>

## Common mistakes

<Voices>
<Technical>

**Mistake 1: a screenshot instead of a live demo.** A screenshot cannot answer a follow-up question; a running environment can.

**Mistake 2: presenting metrics without the gate thresholds next to them.** A number with no stated bar invites the audience to supply their own, which is rarely the generous one.

**Mistake 3: no prepared answer for "what is the worst thing you found".** Reviewers ask this almost every time; an unprepared answer undersells work that was actually done.

**Mistake 4: skipping the parts specific to this capstone.** The agent routing, the multi-source retrieval, and the A/B framework are what distinguish this project from the Phase 1 capstone; a presentation that only covers the shared parts undersells the harder work.

**Mistake 5: treating peer review as a formality.** A reviewer's question about an untested edge case is free QA; writing down what it found is worth more than defending the suite as already complete.

</Technical>
<Layman>

**Mistake ১: live demo-র বদলে একটা screenshot।** একটা screenshot একটা follow-up প্রশ্নের উত্তর দিতে পারে না; একটা চলমান environment পারে।

**Mistake ২: পাশে gate threshold ছাড়া metric উপস্থাপন করা।** বলা বার ছাড়া একটা সংখ্যা audience-কে তাদের নিজস্ব বার সরবরাহ করতে আমন্ত্রণ জানায়, যা খুব কমই উদার হয়।

**Mistake ৩: "আপনি যা পেয়েছেন তার মধ্যে সবচেয়ে খারাপটা কী"-এর জন্য কোনো প্রস্তুত উত্তর নেই।** Reviewer-রা প্রায় প্রতিবারই এটা জিজ্ঞেস করে; একটা অপ্রস্তুত উত্তর আসলে করা কাজকে কমিয়ে দেখায়।
