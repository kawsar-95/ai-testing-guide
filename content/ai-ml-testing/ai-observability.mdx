# AI Observability and Production Monitoring

An eval suite tells you what the model does on the questions you thought to ask. Observability tells you what it did on the ones you did not.

<PageMeta />

## In plain words

<Voices>
<Technical>

**Observability** is the practice of instrumenting a live system so that every call, its input, its output, and its timing, is recorded and queryable after the fact. For an AI application it answers a question an eval suite cannot: what is the model actually being asked in production, and how is it actually answering, on traffic nobody wrote a test case for.

**Arize Phoenix** is an open-source observability tool built specifically for LLM applications: it traces calls and runs evaluations on live traffic to find failures and regressions <Cite n={1} />. **LangFuse** does the same job with its own focus on tracing and prompt management, and both can sit alongside each other or replace one another depending on the stack <Cite n={2} />.

This page is the introduction: what a trace is, why it matters, and the first setup. The deeper version — specific alert thresholds, drift detection, and A/B comparison in production — is in the Phase 2 module on production observability, once the tools and the agent/RAG concepts that feed it are in place.

</Technical>
<Layman>

**Observability** means recording every call in a live system. You record the input, the output, and the timing. Later, you can search those records.

It also runs evaluations on live traffic to find failures and regressions <Cite n={1} />. **LangFuse** does the same job. It focuses on tracing and prompt management. You can run both together or swap one for the other, depending on your stack <Cite n={2} />.

This page is only the introduction. It covers what a trace is, why it matters, and the first setup. Alert thresholds, drift detection, and A/B comparison in production come later. They are in the Phase 2 module on production observability.

</Layman>
<Bangla>

**Observability** হলো একটা live সিস্টেমকে এমনভাবে instrument করার practice যাতে প্রতিটা call, তার input, output, আর timing, রেকর্ড হয় আর পরে query করা যায়। একটা AI application-এর জন্য এটা এমন একটা প্রশ্নের উত্তর দেয় যা eval suite দিতে পারে না: production-এ model-কে আসলে কী জিজ্ঞেস করা হচ্ছে, আর এটা আসলে কীভাবে উত্তর দিচ্ছে, এমন traffic-এ যার জন্য কেউ test case লেখেনি।

**Arize Phoenix** একটা open-source observability টুল, বিশেষভাবে LLM application-এর জন্য বানানো: এটা call trace করে আর live traffic-এ evaluation চালায় failure আর regression খুঁজে পেতে <Cite n={1} />। **LangFuse** একই কাজ করে নিজের tracing আর prompt management-এ focus দিয়ে, আর দুটোই একসাথে বসতে পারে বা স্ট্যাক অনুযায়ী একে অপরকে প্রতিস্থাপন করতে পারে <Cite n={2} />।

এই পেজটা ভূমিকা: trace কী, এটা কেন গুরুত্বপূর্ণ, আর প্রথম setup। গভীর সংস্করণ — নির্দিষ্ট alert threshold, drift detection, আর production-এ A/B তুলনা — Phase 2-এর production observability মডিউলে, একবার যে টুল আর agent/RAG ধারণা এটাকে খাওয়ায় সেগুলো জায়গায় থাকলে।

## How it works

<Voices>
<Technical>

A trace is the record of one call to the model, captured at the point the call happens:

```text
trace    one record: input, output, latency, token counts, model, timestamp
span     a sub-step inside a trace, e.g. one retrieval call within a RAG answer
session  a group of traces belonging to one conversation
```

Both Phoenix <Cite n={1} /> and LangFuse <Cite n={2} /> instrument an application by wrapping the calls it already makes, so adopting one does not mean rewriting the application: it means adding a decorator or a context manager around the existing model and retriever calls.

Once traces are flowing, the basic loop an observability setup supports is:

```text
collect traces -> sample a subset -> run an eval metric on the sample -> alert if it degrades
```

This is the same DeepEval- and Ragas-style metrics from the eval modules, run on live traffic instead of a fixed test set — the mechanism does not change, only the data source does.

</Technical>

## In practice

<Voices>
<Technical>

A minimal Phoenix setup that traces an existing OpenAI-style call <Cite n={1} />:

```python
import phoenix as px
from openinference.instrumentation.openai import OpenAIInstrumentor

px.launch_app()                 # starts the local Phoenix UI
OpenAIInstrumentor().instrument()  # traces every OpenAI call from here on

# existing application code, unmodified
answer = client.chat.completions.create(model="gpt-4o-mini", messages=messages)
```

Every call now shows up in the Phoenix UI with its input, output, latency, and token counts, with no change to `answer_question()` itself.

A minimal LangFuse setup, decorating the same kind of call <Cite n={2} />:

```python
from langfuse.decorators import observe

@observe()
def answer_question(question: str) -> str:
    return client.chat.completions.create(
        model="gpt-4o-mini",
        messages=[{"role": "user", "content": question}],
    ).choices[0].message.content
```

Both approaches collect the same shape of data. Choosing between them is usually about which one's UI, pricing, or self-hosting story fits the team, not about a difference in what gets captured.

<Callout type="tip" title="Tutorial advice">

This advice is the tutorial's own. It does not come from the sources.

- Turn on tracing before the first production user, not after the first incident. A trace you did not capture cannot be reviewed later.
- Tag every trace with the prompt version and model, the same discipline as the quality dashboard.
- Start by just looking at a sample of real traces by hand, before building any alert. The surprises in real traffic inform what is worth alerting on.
</Callout>

</Technical>

## Common mistakes

<Voices>
<Technical>

**Mistake 1: treating a clean eval run as proof production is fine.** The eval suite only covers the inputs someone thought to write; production traffic always finds the rest.

**Mistake 2: turning on tracing only after an incident.** The traces from before the tool was installed do not exist to review.

**Mistake 3: tracing without session grouping.** A pile of individual calls with no conversation boundary cannot show a multi-turn failure.

**Mistake 4: picking a tool before looking at either one's UI.** Phoenix and LangFuse capture similar data but present it differently; try both on a small slice of real traffic before committing <Cite n={1} /> <Cite n={2} />.

**Mistake 5: no link between a trace and the quality dashboard.** A trace tool and a metrics dashboard that cannot be cross-referenced leave a tester unable to go from "the metric dropped" to "here is the specific call that caused it".

</Technical>
<Layman>

**Mistake 1: thinking a clean eval run proves production is fine.** The eval suite only covers inputs someone thought to write. Production traffic always finds the rest.

**Mistake 2: turning on tracing only after an incident.** Traces from before you installed the tool do not exist. You cannot review them.

**Mistake 3: tracing without session grouping.** A pile of single calls has no conversation boundaries. It cannot show a failure that happens over several turns.

**Mistake 4: picking a tool before looking at either UI.** Phoenix and LangFuse capture similar data but show it differently. Try both on a small slice of real traffic before you commit <Cite n={1} /> <Cite n={2} />.

**Mistake 5: no link between a trace and the quality dashboard.** Sometimes the trace tool and the metrics dashboard cannot be cross-checked. Then a tester cannot go from "the metric dropped" to "here is the call that caused it".

</Layman>
<Bangla>

**ভুল ১: পরিষ্কার eval run-কে production ঠিক আছে তার প্রমাণ ভাবা।** eval suite শুধু সেই input কভার করে যা কেউ লেখার কথা ভেবেছিল; production traffic সবসময় বাকিটা খুঁজে পায়।

**ভুল ২: শুধু একটা incident-এর পরে tracing চালু করা।** টুল install হওয়ার আগের trace review করার জন্য থাকে না।

**ভুল ৩: session grouping ছাড়া tracing।** কথোপকথনের সীমানা ছাড়া পৃথক call-এর একটা স্তূপ একটা multi-turn ব্যর্থতা দেখাতে পারে না।

**ভুল ৪: কারো UI না দেখে একটা টুল বেছে নেওয়া।** Phoenix আর LangFuse একই রকম data ধরে কিন্তু আলাদাভাবে দেখায়; commit করার আগে real traffic-এর একটা ছোট অংশে দুটোই চেষ্টা করুন <Cite n={1} /> <Cite n={2} />।

**ভুল ৫: trace আর quality dashboard-এর মধ্যে কোনো লিংক নেই।** একটা trace টুল আর একটা metrics dashboard যা cross-reference করা যায় না, একজন টেস্টারকে "metric কমেছে" থেকে "এখানে নির্দিষ্ট call যা এটার কারণ"-এ যেতে অক্ষম রাখে।
