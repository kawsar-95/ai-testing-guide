# CI/CD Eval Pipelines

An eval suite that only runs on a laptop is a report. An eval suite that runs on every pull request is a gate.

<PageMeta />

## In plain words

<Voices>
<Technical>

The pipeline has three jobs, and they run in increasing cost order.

```text
on every push    the fast, deterministic checks: schema, format, prompt shape
on every PR      the eval suite with a threshold: a merge blocks below it
on a schedule    the expensive evals: the full dataset, the model comparison
```

The **gate** is the point. A gate is a threshold that fails the job, which fails the check, which blocks the merge. The threshold has to be a number the team agreed on before the first failure, and it has to be derived from the quality bar rather than from the current score, or the bar rises every time someone raises it.

The **PR report** is the second point. A failed gate with no explanation is a wall. The report has to name the failing cases, show the outputs, and say which metric moved. Promptfoo's GitHub Action posts a comment on the pull request with a link to the results <Cite n={1} />, and GitHub Actions is where the workflow itself lives <Cite n={2} />.

The **cost gate** is the third. An eval suite that costs more than the feature it protects is not sustainable, and a prompt change that quietly doubles the token count should fail the build like any other regression.

</Technical>

## How it works

<Voices>
<Technical>

The workflow file is a normal GitHub Actions workflow with the eval step added. The important detail is that the eval step **fails the job**, because a job that reports a failure without exiting non-zero does not block anything <Cite n={2} />.

```yaml
# .github/workflows/eval.yml
name: AI eval gate
on:
  pull_request:
    paths: ["app/ai/**", "prompts/**", "evals/**"]

jobs:
  eval:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: "22"
      - run: npm ci
      - name: Run the eval gate
        env:
          ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
        run: npx promptfoo eval --output results.json
```

The **paths** filter matters: without it, every pull request pays for the eval, and the team learns to ignore the gate.

The **threshold** is enforced by the assertions in the config rather than by a separate script, so the bar lives in one place next to the cases:

```yaml
defaultTest:
  assert:
    - type: llm-rubric
      value: The answer only uses the policy
      metric: faithfulness
      threshold: 0.9
```

The **cost gate** is a second check, and it is the one that stops a prompt change from quietly doubling the bill. Promptfoo's `cost` assertion fails a case whose inference cost is over a limit, and `latency` fails one slower than a number of milliseconds <Cite n={4} />:

```yaml
defaultTest:
  assert:
    - type: cost
      threshold: 0.01
    - type: latency
      threshold: 5000
```

And the **report**, which is what turns a red check into a fixable problem. Promptfoo's GitHub Action runs the eval when prompt files change and posts a comment on the pull request with a link to the results <Cite n={1} />.

The last piece is **flakiness control**. An eval that fails randomly will get ignored, and an ignored gate is worse than no gate. The controls are: run the model at a fixed temperature, average the score over several samples per case, and separate the flaky cases into their own suite that runs on a schedule instead of blocking the merge.

</Technical>

## In practice

<Voices>
<Technical>

The workflow runs the eval and fails on a threshold. Promptfoo's `eval` command returns exit code 100 when at least one test case fails or the pass rate is below `PROMPTFOO_PASS_RATE_THRESHOLD`, so the step itself is the gate <Cite n={3} />:

```yaml
      - name: Run the eval gate
        env:
          ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
        run: npx promptfoo eval --output results.json --no-cache
```

A non-zero exit fails the step, which fails the job, which blocks the merge once that check is required <Cite n={2} />.

The **report on the pull request** comes from Promptfoo's GitHub Action, which needs permission to post pull-request comments and posts a link to the results <Cite n={1} />:

```yaml
permissions:
  pull-requests: write

# ... in the job's steps:
      - uses: promptfoo/promptfoo-action@v1
        with:
          github-token: ${{ secrets.GITHUB_TOKEN }}
          prompts: prompts/**/*.json
          config: evals/promptfooconfig.yaml
```

The **cost gate** is an assertion in the same config, not a separate script <Cite n={4} />:

```yaml
defaultTest:
  assert:
    - type: cost
      threshold: 0.01
    - type: latency
      threshold: 5000
```

And the **flaky-case isolation**, which is what keeps the gate trusted:

```yaml
defaultTest:
  assert:
    - type: llm-rubric
      value: The answer only uses the policy
      metric: faithfulness
      threshold: 0.9
tests: file://evals/stable-cases.yaml
```

The stable cases run in the merge gate. The cases that flake run on the schedule, with the same assertions, so a genuinely flaky case is still measured. Nothing gets a permanent pass, and nothing random blocks a merge.

</Technical>

## Common mistakes

<Voices>
<Technical>

**Mistake 1: a gate with no threshold.** "The eval failed" without a number means the team argues about the bar instead of the quality .

**Mistake 2: the threshold set from the current score.** Then the bar silently rises every time somebody raises it.

**Mistake 3: running the eval on every push.** The cost is real and the team learns to ignore it.

**Mistake 4: no report on the pull request.** A red check with no output is a wall <Cite n={1} />.

**Mistake 5: no cost gate.** A prompt change that doubles the token count is a regression like any other.

**Mistake 6: a flaky gate.** A gate that fails randomly gets ignored, and an ignored gate is worse than no gate.

</Technical>
<Layman>

**Mistake 1: a gate with no threshold.** Saying "The eval failed" without a number makes the team argue about the bar instead of the quality.

**Mistake 2: the threshold set from the current score.** Then the bar silently rises every time somebody raises it.

**Mistake 3: running the eval on every push.** The cost is real. The team learns to ignore it.

**Mistake 4: no report on the pull request.** A red check with no output is a wall <Cite n={1} />.

**Mistake 5: no cost gate.** A prompt change that doubles the token count is a regression like any other.

**Mistake 6: a flaky gate.** A gate that fails randomly gets ignored. An ignored gate is worse than no gate.

</Layman>
<Bangla>

**Mistake ১: threshold ছাড়া gate।** সংখ্যা ছাড়া "eval ব্যর্থ" মানে দল মান নিয়ে ঝগড়া করে, মান নিয়ে নয়।

**Mistake ২: threshold বর্তমান স্কোর থেকে ঠিক করা।** তাহলে bar নীরবে প্রতিবার বাড়ে।

**Mistake ৩: প্রতিটা push-এ eval চালানো।** খরচ আসল, আর দল শেখে যায় উপেক্ষা করতে।

**Mistake ৪: pull request-এ report নেই।** output ছাড়া লাল চেক একটা দেয়াল <Cite n={1} />।

**Mistake ৫: cost gate নেই।** token সংখ্যা দ্বিগুণ করা prompt পরিবর্তন একটা regression-ই।

**Mistake ৬: flaky gate।** যে gate এলোমেলো ব্যর্থ হয় সেটা উপেক্ষা হয়, আর উপেক্ষিত gate কোনো gate-এর চেয়ে খারাপ।

</Bangla>

## What a tester can check

<Voices>
<Technical>

<Callout type="tip" title="Tutorial advice">

This advice is the tutorial's own. It does not come from the sources.

- Write the threshold down in the config next to the cases, with a comment explaining what it protects. A number nobody understands gets changed.
- Store the eval results as a build artifact. When the score drops three weeks later, the history is the only way to see what moved.
- Test the gate itself: open a pull request with a deliberately broken assertion and check that it blocks and that the comment explains why.
- Give the job a token budget of its own and alert when the eval spend itself goes up. The eval is a cost centre too.
- Put the eval behind the paths filter for the files that can change it. Every unrelated pull request should not pay for it.
- When you find a flaky case, move it to the scheduled suite in the same commit, so it does not get quietly deleted instead.
</Callout>

</Technical>

- threshold-টা config-এ কেসগুলোর পাশেই লিখুন, সাথে একটা comment দিয়ে ব্যাখ্যা করুন এটা কী রক্ষা করে। কেউ না বোঝা এমন সংখ্যা বদলে দেওয়া হয়।
- eval ফলাফল build artifact হিসেবে রাখুন। তিন সপ্তাহ পরে স্কোর কমলে ইতিহাসই একমাত্র উপায় বলতে পারে কী বদলেছে।
- gate-কেও টেস্ট করুন: ইচ্ছাকৃতভাবে ভাঙা assertion দিয়ে একটা pull request খুলে দেখুন সেটা আটকায় কি না আর comment ব্যাখ্যা করে কি না।
- job-কে নিজস্ব একটা token বাজেট দিন আর eval খরচ বাড়লে alert দিন। eval-ও একটা cost centre।
- eval-টা যেসব file বদলাতে পারে তার paths filter-এর পেছনে রাখুন। অপ্রাসঙ্গিক প্রতিটা pull request-এর জন্য এটা খরচ হওয়া উচিত নয়।
- flaky কেস পেলে একই commit-এ নির্ধারিত suite-এ সরান, যাতে সেটা চুপচাপ delete না হয়ে যায়।

## Key words

| Word | What it means |
| --- | --- |
| Quality gate | A threshold that fails the build, and so blocks the merge |
| Threshold | The score the eval must reach, agreed before the first failure |
| CI/CD | The pipeline that runs the checks on every change |
| Pull request report | The eval results written onto the pull request for the reviewer |
| Cost gate | A check that fails when a prompt change makes the calls too expensive |
| Flaky case | A test that fails at random and must be separated from the gate |
| Paths filter | The list of files that trigger the workflow |
| Build artifact | The stored eval results, which are the history of the score |
| Regression | A change that made the quality worse, which the gate is there to catch |
