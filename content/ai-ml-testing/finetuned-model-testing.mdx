# Fine-Tuned Model Testing

Fine-tuning changes a model on purpose. Testing it means measuring what got better and what got worse, because the second one is easy to miss.

<PageMeta />

## In plain words

<Voices>
<Technical>

A fine-tuned model is a base model whose weights were changed on a set of examples. The change is meant to make the model better at one thing: a specific format, a specific tone, a specific domain.

The testing problem is that **the base model was not broken**. It was general. So there is no failing test to write; there is a comparison to make. The comparison has three parts:

1. **The target task.** The fine-tune should improve here. This is the reason the fine-tune exists.
2. **The general capability.** The fine-tune should not damage it. The failure mode here is called **catastrophic forgetting**: the model becomes excellent at the target and loses abilities it had before. The research on this describes how the effect depends on how close the fine-tuning data is to the original training data <Cite n={1} />.
3. **The cost.** A fine-tuned model usually costs more per query than the base model it replaces, because the serving is specialised.

The evaluation design follows from the three parts. You need a **target dataset** that the fine-tune was not trained on, a **general dataset** that measures the abilities you care about, and you need to run both against both models. The eval must be designed before you look at any score, because a fine-tune almost always looks better on the data it was trained on and that comparison is meaningless <Cite n={2} />.

And the third part is the one teams skip: a fine-tune is justified when it makes the target task cheaper or better **enough** to pay for the lost general capability and the serving cost. That is a number, not a feeling.

</Technical>

## How it works

<Voices>
<Technical>

The evaluation runs the **same datasets against both models**, and the report has two columns plus the difference:

```text
dataset              base      fine-tuned   delta
target-task          0.72      0.94         +0.22
general-writing      0.88      0.91         +0.03
general-reasoning    0.81      0.74         -0.07
safety-refusal       0.95      0.96         +0.01
```

Read that table carefully. The target task improved a lot. The general reasoning dropped by seven points, and that is the line item that decides whether the fine-tune is worth it. A team that only reports the target task row will say yes.

The **general capability** dataset is the hard part to choose, and it is specific to your product. It is the set of questions your users ask that the fine-tune was not meant to change. If your bot handles support and the fine-tune is for tone, the general set is the support questions that need a detailed factual answer.

The **catastrophic forgetting** check has a specific shape: compare the two models on the general dataset, and the failing cases must be *the same cases that regressed*, not new random failures. If the fine-tuned model fails on cases the base model passed, the fine-tune damaged that ability.

The **cost** comparison is the third column of the decision:

```text
base model        1,100 tokens/query   quality 0.72   $X per 1k queries
fine-tuned model  1,150 tokens/query   quality 0.94   $Y per 1k queries
```

And a **format regression** test, which is the most common silent break: the fine-tune was meant to produce a specific format, and a change to the serving or the prompt template can break it while the weights stay the same.

The eval has to be designed before the comparison, and the comparison has to be repeatable, which means a fixed dataset and a fixed judge. A fine-tune that is evaluated on its own training data proves nothing <Cite n={2} />.

</Technical>

## In practice

<Voices>
<Technical>

The comparison test is the whole thing, and it runs the same cases through both models:

```python
# tests/ai/test_finetune_comparison.py
import pytest

from app.models import BASE_MODEL, FINE_TUNED_MODEL


def test_the_finetune_improves_the_target_task(base_eval, tuned_eval):
    assert tuned_eval.score("target-task") > base_eval.score("target-task") + 0.05
```

And the one that catches the damage:

```python
def test_the_finetune_does_not_break_the_general_ability(base_eval, tuned_eval):
    regressed = base_eval.passed_cases("general") - tuned_eval.passed_cases("general")
    assert not regressed, f"the fine-tune broke: {sorted(regressed)[:5]}"
```

The subtraction is the point. A set difference names exactly the cases that regressed, so the fix has a target.

The **format regression** test is separate, because it catches a different thing:

```python
def test_the_finetuned_model_still_returns_the_expected_format(tuned_eval):
    for case in FORMAT_CASES:
        output = tuned_eval.raw_output(case)
        assert output.startswith("<result>"), f"format broke: {output[:40]}"
        assert output.rstrip().endswith("</result>")
```

And the **cost** check, which turns the comparison into a decision:

```python
def test_the_finetune_pays_for_itself(report, base_eval, tuned_eval, prices):
    gain = tuned_eval.score("target-task") - base_eval.score("target-task")
    extra = prices.fine_tuned - prices.base
    report.add("quality_gain", "target", gain)
    report.add("cost_delta", "per_1k", extra)
    assert gain > 0, "the fine-tune did not improve the target task"
```

That last assertion is deliberately modest. It asserts the gain exists and records the cost; whether the trade is worth it is a product decision with both numbers in it.

For the **general capability** dataset, the test cases come from real questions, not from a benchmark, because the capability that matters is the one your users need <Cite n={3} />.

</Technical>

## Common mistakes

<Voices>
<Technical>

**Mistake 1: evaluating on the training data.** The fine-tune will win, and the comparison means nothing.

**Mistake 2: reporting only the target task.** The general capability drop is the number that decides whether the fine-tune was worth it <Cite n={1} />.

**Mistake 3: no held-out general dataset.** Without one, you cannot tell a forgetting problem from noise.

**Mistake 4: comparing different prompts.** Any difference may be the prompt, not the weights.

**Mistake 5: no format regression test.** The format the fine-tune was for can break from a serving change.

**Mistake 6: ignoring the cost.** A fine-tune that improves the score by two points and costs four times more is not obviously a win.

**Mistake 7: no repeatability.** The judge must be pinned and the dataset fixed, or the comparison moves on its own <Cite n={2} />.

</Technical>
<Layman>

**Mistake 1: training data-তে eval করা।** fine-tune জিতবেই, আর তুলনাটা অর্থহীন।

**Mistake 2: শুধু target task রিপোর্ট করা।** সাধারণ সক্ষমতার কমতি সেই সংখ্যা যেটা ঠিক করে fine-tune দাম উপযোগী ছিল কি না <Cite n={1} />।

**Mistake 3: held-out general dataset নেই।** ছাড়া সমস্যা আর noise-এর পার্থক্য বোঝা যায় না।

**Mistake 4: ভিন্ন prompt-এর তুলনা।** পার্থক্যটা weight-এর হতে পারে, prompt-এরও হতে পারে।

**Mistake 5: format regression টেস্ট নেই।** serving-এর পরিবর্তন fine-tune-এর বানানো format ভাঙতে পারে।

**Mistake 6: খরচ উপেক্ষা করা।** যে fine-tune স্কোর দুই পয়েন্ট বাড়ায় আর চারগুণ খরচ করে, সেটা স্পষ্ট জেত নয়।

**Mistake 7: পুনরাবৃত্তিযোগ্যতা নেই।** judge পিন করা আর dataset নির্দিষ্ট হতে হবে, নইলে তুলনা নিজেই নড়বে <Cite n={2} />।

</Layman>

## What a tester can check

<Voices>
<Technical>

<Callout type="tip" title="Tutorial advice">

This advice is the tutorial's own. It does not come from the sources.

- Keep the base model and the fine-tuned model behind the same interface, so the comparison runs the same code for both.
- Save the general capability dataset in the repo, with the cases you have seen regress. It is the most valuable artefact of the whole exercise.
- Report the difference, not the two numbers separately. The delta is what the reader acts on.
- Keep the judge model and the temperature pinned, and record them with every comparison. A judge change moves the score.
- Put the cost per thousand queries in the report next to the quality. Both or neither.
- When a general case regresses, write it down as a test before you fix the fine-tune. It becomes the guard for the next one.
- Re-run the comparison before every serving or prompt change. A fine-tune is evaluated against the whole system, not just the weights.
</Callout>

## Key words

| Word | What it means |
| --- | --- |
| Fine-tuning | Changing a model's weights on examples so it behaves differently |
| Base model | The general model the fine-tune starts from |
| Target task | The specific capability the fine-tune was meant to improve |
| General capability | The abilities the fine-tune was not meant to change, and might damage |
| Catastrophic forgetting | The model losing general abilities while gaining the target one |
| Held-out dataset | Data the model was not trained on, used for a fair comparison |
| Format regression | The fine-tuned output format breaking for a reason other than the weights |
| Cost per query | The serving cost of the fine-tuned model against the base |
