# Vector Database Fundamentals

A vector database stores vectors and finds the nearest ones. Everything else about it is a set of decisions about distance, filtering, and persistence.

<PageMeta />

## In plain words

<Voices>
<Technical>

A vector database does one thing: given a vector, find the stored vectors nearest to it. Everything else is a set of decisions about distance, filtering, and persistence.

**ChromaDB** runs embedded in your process, with a simple client API and a persistent directory on disk. It is the fast way to get a working index <Cite n={1} />. **Qdrant** is a vector search engine, usually run as a local or cloud service, whose docs cover similarity search, filtering, and hybrid queries <Cite n={2} />; filtering works best with payload indexes on the fields you filter on <Cite n={3} />. The two behave differently enough that the filter and persistence tests are worth running against both <Cite n={1} />.

The **similarity metric** decides what "nearest" means, and the choice is not cosmetic:

```text
cosine similarity    the angle between the vectors. Scale-independent.
dot product          the length times the cosine. Favours vectors with large magnitude.
euclidean distance   the straight-line distance. Sensitive to vector length.
```

Text embeddings are normally compared with **cosine similarity**, but the two databases do not share a default. Chroma's `space` defaults to `l2` (squared L2), with `cosine` and `ip` (inner product) as the other values <Cite n={5} />, and Qdrant makes you pick a distance (Cosine, Dot, Euclid, or Manhattan) when the collection is created <Cite n={6} />. Using euclidean on vectors meant for cosine works, but it ranks differently and can rank worse.

**Metadata filtering** is the other decision, and it is the one that changes how you design the schema. A filter like "only documents from 2026" can be applied before the search, after it, or during it. Applied before or during, it is faster and the result is exact. Applied after, the database searches everything and then throws most away, and the top-k you get back is not the true top-k of the filtered set.

</Technical>

## How it works

<Voices>
<Technical>

The insert-and-query cycle is the same in both databases, and the test is the same too: you know what you put in and what you expect back.

**Ingestion.** Every chunk becomes an id, a vector, and a metadata document. The metadata is what makes filtering possible later, so it is worth deciding early which fields you will filter on: the document id, the source file, the page number, the date, the language, the product, the version.

**Query.** A question is embedded with the same model that embedded the documents, and the database compares it against the stored vectors. Chroma's query interface takes the query text or an embedding plus the number of results and a filter <Cite n={4} />. Qdrant's search API does the same with its filter language <Cite n={3} />.

**The metric has to match the model.** An embedding model produces vectors whose length carries no information for ranking purposes, so cosine is the usual choice for text embeddings, and it is a setting you choose, not a default you can rely on. Setting the metric to euclidean on a model meant for cosine can give you results that are *consistent* and *wrong*: the same query returns the same neighbours every time, and the neighbours are not the semantically closest ones.

**The two databases differ in what they optimise.** Chroma is embedded and simple: one directory, one process, no separate server to run. Qdrant is a service: it has payload indexes and a combined filterable index that applies filters during the search <Cite n={3} />. The choice for a tester is mostly about whether you need to test the filter behaviour separately or not.

**The persistence question.** Chroma's persistent client writes to a directory; Qdrant persists to its own storage. Either way, the testable property is the same: **after a restart, the collection holds the same vectors and returns the same neighbours for the same query.** A vector database that loses its index on restart is a silent data-loss bug, and it shows up as "the chatbot suddenly stopped knowing things".

</Technical>

## In practice

<Voices>
<Technical>

Test the database as a component, with a small fixed corpus where you know the right answer for every query:

```python
# tests/ai/test_vector_db.py
import chromadb
import pytest

from app.knowledge import embed, index_documents

CORPUS = {
    "returns#chunk-1": "Unopened items can be returned within 30 days.",
    "returns#chunk-2": "Opened items cannot be returned.",
    "shipping#chunk-1": "We pay the return shipping for defects.",
}


@pytest.fixture
def collection(tmp_path):
    client = chromadb.PersistentClient(path=str(tmp_path))
    return index_documents(client.get_or_create_collection("docs"), CORPUS)
```

Then the tests that matter, in order of how often they catch something:

```python
def test_the_closest_chunk_is_the_right_one(collection):
    hits = collection.query(query_texts=["how long is the return window?"], n_results=1)
    assert hits["ids"][0][0] == "returns#chunk-1"
```

```python
def test_a_filter_excludes_the_other_documents(collection):
    hits = collection.query(
        query_texts=["return window"],
        n_results=3,
        where={"source": "returns"},
    )
    assert all(h.startswith("returns#") for h in hits["ids"][0])
```

```python
def test_the_query_is_deterministic(collection):
    first = collection.query(query_texts=["return window"], n_results=5)["ids"][0]
    second = collection.query(query_texts=["return window"], n_results=5)["ids"][0]
    assert first == second, "the same query returned different neighbours"
```

```python
def test_the_collection_survives_a_restart(tmp_path):
    client = chromadb.PersistentClient(path=str(tmp_path))
    collection = index_documents(client.get_or_create_collection("docs"), CORPUS)
    del collection, client

    reopened = chromadb.PersistentClient(path=str(tmp_path)).get_collection("docs")
    assert reopened.count() == len(CORPUS)
    hits = reopened.query(query_texts=["return window"], n_results=1)
    assert hits["ids"][0][0] == "returns#chunk-1"
```

The last one is the test that catches data loss, and it is the one teams skip because it needs a fresh process.

Then the **metric comparison**, which is the test that shows whether the space you chose is right for your model:

```python
@pytest.mark.parametrize("space", ["cosine", "l2", "ip"])
def test_each_space_ranks_the_right_chunk_first(tmp_path, space):
    client = chromadb.PersistentClient(path=str(tmp_path))
    collection = client.create_collection("docs", configuration={"hnsw": {"space": space}})
    index_documents(collection, CORPUS)
    hits = collection.query(query_texts=["how long is the return window?"], n_results=1)
    assert hits["ids"][0][0] == "returns#chunk-1", f"{space} ranked it wrong"
```

And the **Qdrant filter** test, which is where the two databases differ most:

```python
def test_qdrant_filters_inside_the_search(qdrant_client):
    hits = qdrant_client.query_points(
        collection_name="docs",
        query=embed("return window"),
        limit=3,
        query_filter=models.Filter(must=[models.FieldCondition(key="source", match=models.MatchValue(value="returns"))]),
    ).points
    assert all(h.payload["source"] == "returns" for h in hits)
```

That test is worth writing because Qdrant applies the filter during the search, through a combined filterable index <Cite n={3} />, and a filter applied after the search would return a different top-k.

```python
def test_the_collection_survives_a_restart(tmp_path):
    client = chromadb.PersistentClient(path=str(tmp_path))
    collection = index_documents(client.get_or_create_collection("docs"), CORPUS)
    del collection, client

    reopened = chromadb.PersistentClient(path=str(tmp_path)).get_collection("docs")
    assert reopened.count() == len(CORPUS)
    hits = reopened.query(query_texts=["return window"], n_results=1)
    assert hits["ids"][0][0] == "returns#chunk-1"
```

তারপর **metric তুলনা**, যেটা দেখায় আপনার বেছে নেওয়া space আপনার model-এর জন্য ঠিক কি না:

```python
@pytest.mark.parametrize("space", ["cosine", "l2", "ip"])
def test_each_space_ranks_the_right_chunk_first(tmp_path, space):
    client = chromadb.PersistentClient(path=str(tmp_path))
    collection = client.create_collection("docs", configuration={"hnsw": {"space": space}})
    index_documents(collection, CORPUS)
    hits = collection.query(query_texts=["how long is the return window?"], n_results=1)
    assert hits["ids"][0][0] == "returns#chunk-1", f"{space} ranked it wrong"
```

আর **Qdrant filter** টেস্ট, যেখানে দুটো database-এর সবচেয়ে বেশি পার্থক্য:

```python
def test_qdrant_filters_inside_the_search(qdrant_client):
    hits = qdrant_client.query_points(
        collection_name="docs",
        query=embed("return window"),
        limit=3,
        query_filter=models.Filter(must=[models.FieldCondition(key="source", match=models.MatchValue(value="returns"))]),
    ).points
    assert all(h.payload["source"] == "returns" for h in hits)
```

## Common mistakes

<Voices>
<Technical>

**Mistake 1: using euclidean because the docs mention it.** The metric has to match the model the vectors came from. Chroma's default space is l2, and text embeddings are normally compared with cosine, so set it deliberately <Cite n={5} />.

**Mistake 2: no filter test.** Filtering is where the two databases behave differently, and where a wrong top-k hides <Cite n={3} />.

**Mistake 3: no restart test.** A vector database that loses its index on restart loses data quietly.

**Mistake 4: filtering after the search.** The top-k you get is then the top-k of the unfiltered set, not of the filtered one.

**Mistake 5: no metadata schema.** Deciding which fields you filter on after the first production incident means a re-index of everything.

**Mistake 6: testing against a live corpus.** The test needs a fixed corpus where the right answer is known, so a failure is a failure and not a different day.

</Technical>

**Mistake ১: ডকুমেন্টে উল্লেখ আছে বলে euclidean ব্যবহার করা।** metric-কে model-এর সাথে মেলাতে হবে যার থেকে vector এসেছে। Chroma-র default space `l2`, আর text embedding সাধারণত cosine দিয়ে তুলনা করা হয়, তাই এটা ইচ্ছাকৃতভাবে সেট করুন <Cite n={5} />।

## What a tester can check

<Voices>
<Technical>

<Callout type="tip" title="Tutorial advice">

This advice is the tutorial's own. It does not come from the sources.

- Give every chunk a stable id built from the document id and the chunk index. The id is what every assertion refers to.
- Store the metadata you filter on in a fixed list, and test that every chunk has every field. A missing metadata field is an invisible filter bug.
- Run the same suite against Chroma and Qdrant if you use both. The contract you wrote should hold for both.
- Keep the restart test in the fast suite. It needs a temp directory, not a database.
- Test an empty collection. A query against nothing should return an empty result, not an error and not the whole collection.
- Test a query in a language the corpus does not contain. It is the cheapest way to see the embedding model's language coverage.
</Callout>

## Key words

| Word | What it means |
| --- | --- |
| Vector database | A store that finds the stored vectors nearest to a query vector |
| Cosine similarity | The angle between two vectors; the usual metric for text embeddings |
| Euclidean distance | The straight-line distance between vectors; sensitive to their length |
| Dot product | The length times the cosine; favours vectors with a large magnitude |
| Metadata filter | A condition on the stored records, applied during or after the search |
| Payload index | Qdrant's index that makes filtering part of the search |
| Persistent client | Chroma's mode that writes the collection to a directory on disk |
| Neighbour | One of the stored records the search returns |
| Determinism | The same query returning the same neighbours every time |
