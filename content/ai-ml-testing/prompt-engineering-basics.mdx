# Prompt Engineering Fundamentals

A prompt is not a question. It is a specification for an answer, and the difference shows in every test you write afterwards.

<PageMeta />

## In plain words

<Voices>
<Technical>

A prompt has four parts, and a good one has all four:

```text
1. role or context   who the model is and what situation it is in
2. the task           what to produce, in one sentence
3. the format         how the output must look
4. examples           one or two samples of the wanted result
```

The four-part list is the tutorial's own. Anthropic's prompt engineering overview points to the same kind of techniques, from clarity and examples to XML structuring, role prompting, and prompt chaining <Cite n={1} />.

Two techniques matter more than the rest. **Few-shot examples** show the pattern instead of describing it; in the tutorial's experience, two good examples often do more than a paragraph of instructions. **Chain-of-thought** asks the model to write the reasoning before the answer. The original paper found that this improved performance on arithmetic, commonsense, and symbolic reasoning tasks in large enough models <Cite n={2} />. The tester's version of this is simple: ask for the reasoning, check the reasoning, then check the answer.

The last point is the one that catches new teams. **Test every language you ship in, separately.** A model is not always equally good in every language, and an answer can be fluent and still wrong. This is the tutorial's own advice, not a finding of the sources. When the product serves non-English users, write the prompt and the eval dataset in that language too. An eval dataset in English cannot tell you that the Bengali path is broken.

</Technical>

## How it works

<Voices>
<Technical>

A model predicts each next token from the context it reads, and the prompt is part of that context. So a vague prompt does not produce a vague answer by accident: it produces the most likely answer given a vague context. This explanation, and the next two paragraphs, are the tutorial's own view.

This is why a **format** instruction tends to work well. If you ask for JSON, the most likely continuation is JSON, and the same holds for a numbered list. You are not only requesting a format; you are making the format the likely next text.

**Few-shot examples** push in the same direction, often harder than words do, because they show the exact pattern. That is also their risk: a badly chosen example teaches the wrong pattern, and the model can follow the example rather than the instruction.

**Chain-of-thought** adds an intermediate step: the model writes the reasoning, then the answer. The original paper reports gains on arithmetic, commonsense, and symbolic reasoning tasks <Cite n={2} />. A follow-up method, self-consistency, samples several reasoning paths and selects the most consistent answer; its paper reports large accuracy gains, at the cost of more model calls <Cite n={3} />.

The **language** effect is a separate axis. In the tutorial's view, quality can differ between languages, so each language needs its own check: a native-language prompt, native-language examples, and a native-language eval set.

Everything here is an input to the eval design. Anthropic's overview assumes, before any prompt engineering, a clear definition of the success criteria and a way to test against them empirically <Cite n={1} />. A prompt change is a change to the system under test, so it needs the same before-and-after measurement as any other change.

</Technical>

All of this feeds the test design. Anthropic's guide expects you to have clear success criteria, and a way to test against them, before you start tuning a prompt <Cite n={1} />. A prompt change is a change to the system, so measure it before and after, like any other change.

**Chain-of-thought** একটা মাঝের ধাপ যোগ করে: model আগে যুক্তি লেখে, তারপর উত্তর। মূল গবেষণায় হিসাব, সাধারণ বুদ্ধি আর প্রতীকী যুক্তির কাজে উন্নতির কথা আছে <Cite n={2} />। পরের একটা পদ্ধতি, self-consistency, কয়েকটা যুক্তির পথ নিয়ে সবচেয়ে সামঞ্জস্যপূর্ণ উত্তরটা বেছে নেয়; তার গবেষণায় নির্ভুলতা অনেক বাড়ার কথা আছে, তবে এতে model-কে বেশি বার ডাকতে হয় <Cite n={3} />।

**ভাষা** একটা আলাদা বিষয়। টিউটোরিয়ালের মতে, ভাষাভেদে মান আলাদা হতে পারে, তাই প্রতিটা ভাষার আলাদা যাচাই দরকার: সেই ভাষার prompt, সেই ভাষার উদাহরণ, আর সেই ভাষার eval set।

এসবই eval ডিজাইনের ইনপুট। Anthropic-এর গাইড ধরে নেয়, prompt নিয়ে কাজ শুরুর আগে আপনার সাফল্যের স্পষ্ট মানদণ্ড আর তা পরীক্ষা করে দেখার উপায় আছে <Cite n={1} />। prompt বদলানো মানে টেস্টের অধীন সিস্টেম বদলানো, তাই অন্য যেকোনো পরিবর্তনের মতো এরও আগে-পরে মাপ দরকার।

## In practice

<Voices>
<Technical>

Write the prompt as a template with the parts separated, so that the parts you vary in a test are visible:

```python
PROMPT = """You are a support agent for an online store.
Answer the question using only the policy below.
If the policy does not cover it, say so.
Reply in at most 3 sentences. Do not offer refunds.

Policy:
{policy}

Question: {question}
"""
```

Then measure the effect of each part separately, rather than changing the whole prompt at once. This is the experiment:

```python
VARIANTS = {
    "baseline": PROMPT,
    "with_example": PROMPT + "\n\nExample:\nQ: ...\nA: ...",
    "with_cot": PROMPT + "\n\nThink step by step, then answer.",
    "with_format": PROMPT + "\n\nReply as a JSON object with keys 'answer' and 'source'.",
}
```

Run each variant over the same dataset and compare the scores. That table is the evidence for the prompt change, and it goes in the pull request.

For the **language** effect, keep the dataset and the prompt in the same language and compare against the translated version:

```python
for language, dataset in [("en", EN_CASES), ("bn", BN_CASES)]:
    score = evaluate(dataset, prompt=prompt_for(language))
    print(language, score.hallucination_rate, score.faithfulness)
```

A large gap between the two is a product finding, not a bug to be filed and closed. It tells you which users the feature currently serves badly.

</Technical>

## Common mistakes

<Voices>
<Technical>

**Mistake 1: changing everything at once.** If the prompt, the model, and the dataset all change in one release, no result tells you which change helped. Change one thing and measure.

**Mistake 2: describing the format instead of showing it.** "Return JSON" is often weaker than one example of the JSON you want. This is the tutorial's own advice; Anthropic's overview lists examples among its core techniques <Cite n={1} />.

**Mistake 3: putting the instruction first and the question last.** For a long policy in between, the instruction at the top can get lost in a lot of context. In the tutorial's experience, it helps to put the instruction after the context, or to repeat it at the end.

**Mistake 4: few-shot examples that disagree with the instruction.** When they disagree, the model often follows the example. Pick examples that show exactly the rule.

**Mistake 5: evaluating in one language and shipping in another.** The eval cannot see a problem it never had data for.

**Mistake 6: keeping the reasoning but not checking it.** Chain-of-thought can raise the accuracy of the answer, and it also produces text that looks like reasoning. The paper itself notes that there is no guarantee that the reasoning path is correct, so the reasoning is a thing to assert on <Cite n={2} />.

</Technical>
<Layman>

**Mistake 1: changing everything at once.** If the prompt, the model, and the test set all change in one release, no result tells you which change helped. Change one thing, then measure.

**Mistake 2: describing the format instead of showing it.** "Return JSON" often works worse than one example of the JSON you want. This is the tutorial's advice; Anthropic's guide lists examples among its main techniques <Cite n={1} />.

**Mistake 3: instruction first, question last.** With a long policy in between, the instruction at the top can get lost. In the tutorial's experience, it helps to put the instruction after the policy, or to repeat it at the end.

**Mistake 4: examples that disagree with the instruction.** When they disagree, the model often copies the example. Pick examples that show exactly the rule.

**Mistake 5: testing in one language and shipping in another.** A test cannot find a problem it has no data for.

**Mistake 6: asking for the reasoning but not checking it.** Chain-of-thought can make the answer more accurate, and it also writes text that looks like reasoning. The paper itself says the reasoning is not guaranteed to be correct, so check the reasoning too <Cite n={2} />.

</Layman>

**ভুল ১: একসাথে সবকিছু বদলানো।** prompt, model আর dataset তিনটাই একসাথে বদলালে কোনো ফলাফলই বলবে না কোন পরিবর্তনে লাভ হয়েছে। একটা করে বদলে মাপুন।

**ভুল ২: format বর্ণনা করা, দেখানো নয়।** "JSON ফেরত দাও" লেখা প্রায়ই আপনি যে JSON চান তার একটা উদাহরণ দেখানোর চেয়ে কম কাজ করে। এটা টিউটোরিয়ালের পরামর্শ; Anthropic-এর গাইড উদাহরণকে মূল কৌশলগুলোর একটা হিসেবে তালিকায় রাখে <Cite n={1} />।

**ভুল ৩: নির্দেশনা প্রথমে, প্রশ্ন শেষে।** মাঝখানে লম্বা policy থাকলে শুরুর নির্দেশনা অনেক context-এর ভিড়ে হারিয়ে যেতে পারে। টিউটোরিয়ালের অভিজ্ঞতায়, context-এর পরে নির্দেশনা দিলে, অথবা শেষে আবার লিখলে কাজ হয়।

**ভুল ৪: few-shot উদাহরণ নির্দেশনার সাথে না মেলা।** দুটো না মিললে model প্রায়ই উদাহরণটাই অনুসরণ করে। এমন উদাহরণ বেছে নিন যেগুলো ঠিক নিয়মটাই দেখায়।

**ভুল ৫: এক ভাষায় eval, অন্য ভাষায় release।** যে সমস্যার data-ই ছিল না, eval সেটা দেখতে পায় না।

**ভুল ৬: যুক্তি রেখে দিয়ে যাচাই না করা।** chain-of-thought উত্তরের নির্ভুলতা বাড়াতে পারে, আর যুক্তির মতো দেখতে লেখাও তৈরি করে। গবেষণাপত্র নিজেই বলে যে যুক্তির পথ সঠিক হবে এমন কোনো নিশ্চয়তা নেই, তাই যুক্তিও assert করুন <Cite n={2} />।

<Callout type="tip" title="Tutorial advice">

This advice is the tutorial's own. It does not come from the sources.

- Keep the prompt in one file, versioned, and inject it into the app from there. A prompt copied into five code paths is five prompts to maintain.

- Keep one deliberately hard case in the dataset for every prompt you write. The easy cases stop being informative once the prompt is good.
- Test the prompt with the context filled by a user, not by your own tidy example. Real context has stray characters and irrelevant passages.

## Key words

| Word | What it means |
| --- | --- |
| Prompt | The instruction and context the model reads to produce an answer |
| Few-shot example | A sample of the wanted output, placed in the prompt |
| Chain-of-thought | Asking the model to write its reasoning before the answer |
| Self-consistency | Sampling several reasoning paths and taking the most common answer |
| Instruction | The part of the prompt that says what to do |
| Context | Everything the model can read: the system prompt, the history, the retrieved text, the question |
| Prompt drift | The behaviour of a prompt changing as the model or the context changes |
| Language parity | The feature behaving equally well in every language it ships in |
