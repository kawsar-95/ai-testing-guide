# CI/CD Integration and Capstone Presentation

A test suite that only runs on your laptop is a suite someone will forget to run.

<PageMeta />

## In plain words

<Voices>
<Technical>

The last technical step of the capstone is making the test pipeline run itself, on every pull request, without anyone remembering to trigger it. GitHub Actions is the CI platform that runs a defined job on a repository event such as a pull request <Cite n={1} />, and Promptfoo ships first-class support for running its evals inside that kind of pipeline <Cite n={2} />.

The job of the CI job is narrow: run the fast suites (the eval, the hallucination tests) on every PR as a required check, and run the slower ones (red team, Giskard scan, full UI suite) on a schedule or on demand, because they are too slow to block every single commit.

The presentation half of this session is not a technical artifact, but it has a technical dependency: the quality dashboard from the metrics module and the findings table from the test pipeline are what gets presented, not a narrative with no numbers behind it.

</Technical>

## How it works

<Voices>
<Technical>

The split between what blocks a merge and what runs on a schedule <Cite n={1} />:

```text
on every pull request (required check, blocks merge)
    Promptfoo eval
    DeepEval hallucination suite

on a schedule, or manually triggered (visible, not blocking)
    Promptfoo red team
    Giskard scan
    full Playwright suite
```

**Exit code.** `npx promptfoo eval` returns exit code 100 when at least one test case fails (or when the pass rate is below `PROMPTFOO_PASS_RATE_THRESHOLD`) <Cite n={3} />. Running it as a CI step is what lets the job fail and block a merge <Cite n={3} />.

**GitHub Action.** Promptfoo also ships a GitHub Action that, when prompt files change in a pull request, runs a before-and-after comparison and posts the results to the pull request <Cite n={2} />. It needs `github-token`, `prompts`, and `config` inputs and `pull-requests: write` permission <Cite n={2} />.

**PR comment.** The PR comment itself is the smallest version of the quality dashboard from the metrics module. It shows the same numbers and same gate logic, surfaced at the point a human actually makes the merge decision instead of a separate page they would need to remember to check.

</Technical>

## In practice

<Voices>
<Technical>

A workflow file with the required-vs-scheduled split <Cite n={1} /> <Cite n={2} />:

```yaml
# .github/workflows/capstone.yml
name: capstone checks
on:
  pull_request:
  schedule:
    - cron: "0 6 * * *"  # nightly, for the slow suites
jobs:
  fast-gate:
    if: github.event_name == 'pull_request'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npx promptfoo eval -c promptfooconfig.yaml   # exit code 100 on any failing test
      - run: python -m pytest tests/hallucination/
  nightly-slow-suite:
    if: github.event_name == 'schedule'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npx promptfoo redteam run --config redteam-config.yaml
      - run: python -m scripts.run_giskard_scan
      - run: python -m pytest tests/ui/
```

A short presentation outline built from the suite's own output, not written from memory:

```text
1. architecture        the diagram from capstone-project-setup
2. test strategy       the plan's scope, risks, and gates
3. results             the quality dashboard: current values vs. gates
4. vulnerabilities     the red team + Giskard findings table, by OWASP id
5. CI/CD               the PR comment from a real run, screenshotted
6. what broke          one real failure found during the capstone, and the fix
```

<Callout type="tip" title="Tutorial advice">

This advice is the tutorial's own. It does not come from the sources.

- Put the fast suite on `pull_request` as a required status check, not just a workflow that runs; a workflow that runs but is not required can still be merged past.
- Keep the nightly suite's results somewhere a reviewer finds without asking, such as a pinned issue or a status badge in the README.
- Present the one real failure you found and fixed during the capstone; it is more convincing than a suite that has always been green.
</Callout>

## Common mistakes

<Voices>
<Technical>

**Mistake 1: a workflow that runs but is not required.** GitHub only blocks a merge on checks explicitly marked required in branch protection <Cite n={1} />.

**Mistake 2: running the slow suites on every PR.** This either makes every PR wait ten minutes or teaches the team to ignore a check that is always still running when they want to merge.

**Mistake 3: no PR comment, only a pass/fail badge.** A reviewer who has to click into logs to see which assertion failed will eventually stop checking <Cite n={2} />.

**Mistake 4: presenting a suite that has never found anything.** It reads as untested, not as high quality; show the real failure that was found and fixed.

**Mistake 5: the presentation has no numbers from the actual dashboard.** A narrative description of quality is not evidence of it.

</Technical>
<Layman>

**Mistake 1: a workflow that runs but is not required.** GitHub blocks a merge only on checks marked required in branch protection <Cite n={1} />.

**Mistake 2: running the slow suites on every PR.** Every PR then waits ten minutes. Or the team learns to ignore a check that is still running when they want to merge.

**Mistake 3: no PR comment, only a pass/fail badge.** A reviewer must click into logs to see which assertion failed. Sooner or later, that reviewer stops checking <Cite n={2} />.

**Mistake 4: presenting a suite that has never found anything.** It looks untested, not high quality. Show the real failure that you found and fixed.

</Layman>

**ভুল ১: চলে কিন্তু required নয় এমন একটা workflow।** GitHub শুধু branch protection-এ স্পষ্টভাবে required চিহ্নিত check-এ merge ব্লক করে <Cite n={1} />।

**ভুল ২: প্রতিটা PR-এ ধীর suite চালানো।** এটা হয় প্রতিটা PR-কে দশ মিনিট অপেক্ষা করায় অথবা দলকে একটা check উপেক্ষা করতে শেখায় যা merge করতে চাওয়ার সময় সবসময় চলছে থাকে।

## Key words

| Word | What it means |
| --- | --- |
| Required check | A CI job marked in branch protection so a failure blocks the merge |
| Fast gate | The subset of tests fast enough to run on every pull request |
| Scheduled suite | Slower tests run nightly or on demand instead of on every commit |
| PR comment | A CI result posted directly on the pull request for the reviewer |
