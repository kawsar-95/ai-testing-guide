# RAG Test Automation at Scale: Synthetic Data and Regression

A knowledge base update is a deploy with no diff. The only way to know what it broke is to run the same questions through it, automatically, every time.

<PageMeta />

## In plain words

<Voices>
<Technical>

A hand-written RAG eval set of 20 or 50 questions covers what a tester thought to ask. **Giskard's quality scan** generates test scenarios automatically from the knowledge base itself, at a scale no one would write by hand: direct questions grounded in a document, multi-topic and history-dependent questions, sycophancy probes, and out-of-scope questions the documents never cover. It is the Giskard v3 successor of the v2 RAGET tool <Cite n={2} />, and each scenario is tagged with the component it is meant to assess (`llm`, `retrieval`, or `history`) <Cite n={1} />.

Automatic generation solves a coverage problem, but it creates a new one: a knowledge base changes constantly (a policy is updated, a document is added or removed), and a test set generated once goes stale. The fix is to treat the knowledge base like code: every update runs the regression suite, judged by the scan's LLM judge (you can add Ragas faithfulness and context metrics, as used elsewhere in the course, for a second opinion <Cite n={3} />), and a failing scenario blocks the update from going live, enforced the same way any other CI gate is enforced <Cite n={4} />.

</Technical>
<Layman>

A hand-written test set of 20 or 50 questions covers only what a tester thought to ask. **Giskard's quality scan** builds test scenarios by itself from the knowledge base. It makes far more than anyone would write by hand.

The scenarios include these kinds of questions:

- Direct questions based on one document.
- Questions that mix several topics, or depend on chat history.
- Sycophancy probes.
- Out-of-scope questions, which the documents never cover.

This is the Giskard v3 replacement for the v2 tool RAGET <Cite n={2} />. Each scenario is tagged with the part it is meant to test: `llm`, `retrieval`, or `history` <Cite n={1} />.

## How it works

<Voices>
<Technical>

The pipeline runs on every knowledge base change, not on a developer's schedule:

```text
1. knowledge base updates      a document is added, changed, or removed
2. quality_scan generates        scenarios (up to max_scenarios), component-tagged, from the new KB
3. the RAG pipeline answers      every generated question, through the real app
4. the scan's LLM judge scores    each answer pass or fail, grouped by component
5. compare to the threshold      if any scenario failed, block; if none, deploy
```

<Cite n={1} /> The scan's component tags matter for step 5: a failure tagged `retrieval` points somewhere different than one tagged `llm` or `history`. The tags describe what a scenario is designed to assess; they do not prove which internal component caused a failure, so use them to find patterns and then read the trace <Cite n={1} />.

The gate itself is the same shape as any other CI quality gate: a threshold on a score, wired to a pipeline step that can fail a build <Cite n={4} />. What is specific to RAG here is only what feeds the threshold — a scan generated from the current knowledge base instead of a fixed question list.

</Technical>

## In practice

<Voices>
<Technical>

Generate the scenarios and run them against the app with Giskard's quality scan <Cite n={1} />:

```python
from giskard.scan import KnowledgeBase, quality_scan

# support_agent is your wrapped app: async def support_agent(inputs: str) -> str
knowledge_base = KnowledgeBase.from_texts(faq_texts)  # a list of strings

async def run_scan():
    return await quality_scan(
        target=support_agent,
        description="A customer support chatbot answering from a return-policy knowledge base.",
        languages=["en"],
        knowledge_base=knowledge_base,
        max_scenarios=20,
        target_mode="singleturn",
    )
```

Gate the pipeline on the scan result <Cite n={1} />:

```python
import pytest

@pytest.mark.asyncio
async def test_the_knowledge_base_update_does_not_regress():
    result = await run_scan()
    # result.recommendation is a lead for a human to read, not a verdict
    assert result.failed_count == 0, result.recommendation
```

Wire it to run on every knowledge base change, not on a code change <Cite n={4} />:

```yaml
# .github/workflows/kb-regression.yml
on:
  push:
    paths: ["knowledge_base/**"]
jobs:
  regression:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: pip install "giskard[scan,openai]" pytest pytest-asyncio
      - run: python -m pytest tests/test_kb_regression.py
```

<Callout type="tip" title="Tutorial advice">

This advice is the tutorial's own. It does not come from the sources.

- Regenerate the question set on every run rather than reusing a stale one; a stale set tests the old knowledge base, not the new one.
- Keep the per-component results (`result.group_by("component")`), not just the overall pass rate, in the test output.
- Scope the trigger to the knowledge base's own path, so an unrelated code change does not spend minutes (and LLM API credits, since the scan calls an LLM to generate and to judge) for nothing.
</Callout>

</Technical>

## Common mistakes

<Voices>
<Technical>

**Mistake 1: generating the test set once and reusing it forever.** A regenerated set tests the current knowledge base; a stale one tests a knowledge base that no longer exists.

**Mistake 2: one overall number instead of per-component results.** A drop hidden inside one component group (for example `retrieval`) can be invisible in the overall pass rate <Cite n={1} />.

**Mistake 3: running the regression suite on a schedule instead of on the actual change.** A nightly run finds a regression up to 24 hours after it shipped; a push-triggered run finds it before it ships.

**Mistake 4: no threshold, just a report.** A faithfulness number with nothing gating on it does not stop a bad update <Cite n={3} /> <Cite n={4} />.

**Mistake 5: triggering the full suite on unrelated code changes.** Scope the trigger to the knowledge base's own files, not the whole repository.

</Technical>
<Layman>

**Mistake 2: one overall number instead of results for each component.** A drop inside one group, such as `retrieval`, can hide in the overall pass rate <Cite n={1} />.

</Layman>

## Key words

| Word | What it means |
| --- | --- |
| Giskard quality scan | A Giskard v3 scan that generates RAG test scenarios from a knowledge base (successor of v2 RAGET) |
| Component tag | A label on a generated scenario saying which part it stresses: llm, retrieval, or history |
| Regression suite | A test set re-run on every knowledge base change to catch what the update broke |
| Path-scoped trigger | A CI trigger limited to changes under a specific directory |
