# Capstone Test Pipeline: Eval, Red Team, and UI, Together

Every tool from this course earns its place here, on one app, at the same time.

<PageMeta />

## In plain words

<Voices>
<Technical>

The capstone's test pipeline is not a new technique; it is the whole course applied to one app at once:

```text
Promptfoo eval      20 test cases, assertions on the answer <Cite n={1} />
DeepEval            hallucination and faithfulness, as Pytest <Cite n={3} />
Promptfoo red team  prompt injection, PII, excessive agency <Cite n={4} />
Giskard scan        a second attack library, cross-checked against the first <Cite n={5} />
Playwright          the chat UI end to end <Cite n={6} />
LangFuse            every call traced, for when a test fails and needs a reason <Cite n={7} />
```

The point of running all six together is not redundancy. Each one tests a different layer: the eval and DeepEval suites test correctness, the red team and Giskard scan test security, Playwright tests the interface the user actually touches, and LangFuse is the record that makes a failure in any of the other five diagnosable rather than just reproducible.

</Technical>

## How it works

<Voices>
<Technical>

Running order matters: cheap and fast checks first, so an obvious break fails in seconds, not after a ten-minute red team run.

```text
1. Promptfoo eval       fast, deterministic assertions       seconds
2. DeepEval suite       LLM-judged metrics                   a minute or two
3. Playwright UI        the interface, against a running server   a minute
4. Promptfoo red team   generated adversarial prompts        several minutes
5. Giskard scan         a second, independent attack library  several minutes
```

LangFuse traces everything from step 1 onward <Cite n={7} />, so when step 4 or 5 finds something, the trace for that exact call — the prompt, the retrieved context, the model's answer — is one click away, instead of a re-run with extra logging bolted on.

The Promptfoo eval config and the red team config are two different files against the same target, because they serve different purposes: the eval config asserts correctness on expected inputs <Cite n={1} />, the red team config generates adversarial ones <Cite n={4} />.

</Technical>

## In practice

<Voices>
<Technical>

The eval config, 20 cases against the live endpoint <Cite n={1} /> <Cite n={2} />:

```yaml
# promptfooconfig.yaml
prompts: ["{{question}}"]
providers:
  - id: http://localhost:8000/ask
    config:
      method: POST
      headers:
        Content-Type: application/json
      body:
        question: "{{prompt}}"
      transformResponse: json.answer
tests: file://tests/capstone-eval-cases.yaml   # 20 rows of vars: question, expected_fact
defaultTest:
  assert:
    - type: contains
      value: "{{expected_fact}}"
```

A DeepEval hallucination test over the same endpoint <Cite n={3} />:

```python
from deepeval import assert_test
from deepeval.metrics import FaithfulnessMetric
from deepeval.test_case import LLMTestCase

def test_the_answer_is_faithful_to_the_retrieved_context(case):
    response = requests.post("http://localhost:8000/ask", json={"question": case["question"]}).json()
    assert_test(
        LLMTestCase(
            input=case["question"],
            actual_output=response["answer"],
            retrieval_context=response["context"],
        ),
        [FaithfulnessMetric(threshold=0.9)],
    )
```

The red team and the scan, as a two-tool gate <Cite n={4} /> <Cite n={5} />:

```bash
npx promptfoo redteam run --config redteam-config.yaml
python -m scripts.run_giskard_scan --target http://localhost:8000/ask
```

A Playwright UI test against the chat widget <Cite n={6} />:

```python
from playwright.sync_api import Page, expect

def test_sending_a_question_renders_an_answer(page: Page):
    page.goto("http://localhost:3000")
    page.locator("#chat-input").fill("What is your return policy?")
    page.locator("#send").click()
    expect(page.locator(".bot-message")).to_contain_text("30 day", timeout=10_000)
```

<Callout type="tip" title="Tutorial advice">

This advice is the tutorial's own. It does not come from the sources.

- Run the suites in cost order: assertions, then LLM-judged metrics, then the slower adversarial scans.
- Point every test at the same running instance of the app, so a LangFuse trace from a failure always has a matching call to inspect.
- Keep the 20 eval cases and the red team's generated cases in separate files; they have different owners and different update cadences.
</Callout>

## Common mistakes

<Voices>
<Technical>

**Mistake 1: running the slow scans first.** A broken endpoint should fail in the first few seconds of the eval suite, not after ten minutes of red teaming an app that was never going to pass it.

**Mistake 2: no shared target between the suites.** If the UI tests run against a different deployment than the eval suite, a passing eval and a failing UI test are not actually contradictory.

**Mistake 3: not tracing the eval and red team runs, only production traffic.** The traces from a test run are exactly the ones a tester needs when a test fails <Cite n={7} />.

**Mistake 4: one combined report instead of six.** Collapsing correctness, security, and UI findings into one pass/fail hides which layer actually broke.

**Mistake 5: skipping the Playwright suite because the eval suite passed.** An API that answers correctly can still render a broken loading state or drop the second half of a streamed response.

</Technical>
<Layman>

**Mistake ১: ধীর scan আগে চালানো।** একটা ভাঙা endpoint-এর eval suite-এর প্রথম কয়েক সেকেন্ডেই ব্যর্থ হওয়া উচিত, এমন একটা app-কে দশ মিনিট red team করার পরে নয় যেটা কখনো পাস করত না।

**Mistake ২: suite-গুলোর মধ্যে একটা ভাগাভাগি target নেই।** UI টেস্ট যদি eval suite-এর চেয়ে আলাদা deployment-এর বিপরীতে চলে, একটা পাস করা eval আর একটা ব্যর্থ UI test আসলে পরস্পরবিরোধী নয়।

**Mistake ৩: eval আর red team run trace না করা, শুধু production traffic।** একটা test run-এর trace ঠিক সেগুলোই যা একটা টেস্টারের দরকার যখন একটা test ব্যর্থ হয় <Cite n={7} />।

**Mistake ৪: ছয়টার বদলে একটা combined রিপোর্ট।** সঠিকতা, নিরাপত্তা, আর UI finding-কে একটা pass/fail-এ ভেঙে ফেলা লুকায় কোন layer আসলে ভেঙেছে।

**Mistake ৫: eval suite পাস করেছে বলে Playwright suite বাদ দেওয়া।** একটা API যা সঠিকভাবে উত্তর দেয় তারপরও একটা ভাঙা loading state render করতে পারে বা একটা streamed response-এর দ্বিতীয় অর্ধেক ফেলে দিতে পারে।

</Layman>
<Bangla>

**ভুল ১: ধীর scan আগে চালানো।** একটা ভাঙা endpoint-এর eval suite-এর প্রথম কয়েক সেকেন্ডেই ব্যর্থ হওয়া উচিত, এমন একটা app-কে দশ মিনিট red team করার পরে নয় যেটা কখনো পাস করত না।

**ভুল ৩: eval আর red team run trace না করা, শুধু production traffic।** একটা test run-এর trace ঠিক সেগুলোই যা একটা টেস্টারের দরকার যখন একটা test ব্যর্থ হয় <Cite n={7} />।

**ভুল ৫: eval suite পাস করেছে বলে Playwright suite বাদ দেওয়া।** একটা API যা সঠিকভাবে উত্তর দেয় তারপরও একটা ভাঙা loading state render করতে পারে বা একটা streamed response-এর দ্বিতীয় অর্ধেক ফেলে দিতে পারে।

## Key words

| Word | What it means |
| --- | --- |
| Test pipeline | The full set of suites run against one app: eval, hallucination, red team, scan, UI |
| Cost order | Running cheap, fast checks before slow, expensive ones |
| Shared target | Every test suite pointed at the same running instance of the app |
| Findings table | A combined report tagging each finding with the layer it belongs to |
| Trace | The recorded call that lets a test failure be diagnosed, not just reproduced |
