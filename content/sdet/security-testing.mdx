# Security Testing with Burp Suite

A functional test asks "does it work?". A security test asks "what happens when someone uses it in a way it was never meant to be used?". This page starts from the OWASP Top 10, then uses Burp Suite on a practice app to find two real flaws: an SQL injection and a broken access control.

## How it works

<Voices>
<Technical>

- **Broken access control.** Access control should keep users from acting outside their intended permissions <Cite n={2} />. One common failure is viewing or editing someone else's account by giving its unique identifier, which is called an insecure direct object reference (IDOR) <Cite n={2} />. An IDOR arises when an app uses user-supplied input to access objects directly <Cite n={14} />.
- **Injection.** An injection flaw sends untrusted input to an interpreter, such as a database, which then runs part of the input as commands <Cite n={3} />. SQL injection lets an attacker interfere with the queries that an app makes to its database <Cite n={13} />. In SQL, `--` starts a comment, so the rest of the query is ignored <Cite n={13} />.
- **Authentication failures.** An app is weak if it permits automated attacks such as credential stuffing, which tries a breached list of real usernames and passwords <Cite n={4} />.
- **The Proxy workflow.** In Burp, go to **Proxy > Intercept**, set the toggle to **Intercept on**, and click **Open Browser** <Cite n={6} />. That browser is preconfigured to work with Burp <Cite n={6} />. Each request is held, so that you can study it and even change it before you forward it <Cite n={6} />.
- **The Repeater workflow.** Right-click a request and select **Send to Repeater** <Cite n={8} />. Change it, click **Send**, and read the response <Cite n={8} />. Repeater is made for sending a request with varying parameter values, to test for input-based flaws <Cite n={7} />.

</Technical>
<Layman>

- **Broken access control.** Access control should stop users from acting outside what they are allowed to do <Cite n={2} />. A common failure: you give someone else's id, and you can see or change their account <Cite n={2} />. This is called an IDOR: the app uses your input to reach an object directly <Cite n={14} />.
- **Injection.** The app passes your input to something like a database, and the database runs part of it as a command <Cite n={3} />. SQL injection lets an attacker interfere with the queries that the app makes to its database <Cite n={13} />. In SQL, `--` starts a comment, so the rest of the query is ignored <Cite n={13} />.
- **Login attacks.** A login is weak if it allows automated attacks such as credential stuffing, which tries a breached list of real usernames and passwords <Cite n={4} />.
- **Using the Proxy.** In Burp, open **Proxy > Intercept**, switch **Intercept on**, and click **Open Browser** <Cite n={6} />. Each request then waits, so you can read or change it before you send it on <Cite n={6} />.
- **Using Repeater.** Right-click a request, choose **Send to Repeater**, change it, click **Send**, and read the answer <Cite n={8} />.

</Layman>
<Bangla>

- **Broken access control।** Access control-এর কাজ user-কে তাঁর নির্ধারিত অনুমতির বাইরে কাজ করতে না দেওয়া <Cite n={2} />। একটা সাধারণ ব্যর্থতা হলো কারও unique identifier দিয়ে তাঁর account দেখা বা বদলানো, যার নাম insecure direct object reference (IDOR) <Cite n={2} />। App যখন user-এর দেওয়া input দিয়ে সরাসরি object access করে, তখন IDOR তৈরি হয় <Cite n={14} />।
- **Injection।** Injection-এর ত্রুটিতে অবিশ্বস্ত input database-এর মতো কোনো interpreter-এ যায়, আর interpreter input-এর একটা অংশ command হিসেবে চালায় <Cite n={3} />। SQL injection attacker-কে app-এর database query-তে হস্তক্ষেপ করতে দেয় <Cite n={13} />। SQL-এ `--` comment শুরু করে, তাই query-র বাকি অংশ উপেক্ষা হয় <Cite n={13} />।
- **Authentication-এর ব্যর্থতা।** App দুর্বল, যদি এটা credential stuffing-এর মতো automated attack চলতে দেয়, যেখানে ফাঁস হওয়া আসল username আর password-এর তালিকা চেষ্টা করা হয় <Cite n={4} />।
- **Proxy-র কাজের ধারা।** Burp-এ **Proxy > Intercept**-এ গিয়ে toggle **Intercept on** করুন, আর **Open Browser**-এ ক্লিক করুন <Cite n={6} />। সেই browser Burp-এর সাথে কাজ করার জন্য আগে থেকেই সাজানো <Cite n={6} />। প্রতিটা request আটকে থাকে, যাতে forward করার আগে আপনি সেটা দেখতে, এমনকি বদলাতে পারেন <Cite n={6} />।
- **Repeater-এর কাজের ধারা।** একটা request-এ right-click করে **Send to Repeater** বেছে নিন <Cite n={8} />। বদলে **Send**-এ ক্লিক করে response পড়ুন <Cite n={8} />। Repeater বানানো হয়েছে বিভিন্ন parameter value দিয়ে request পাঠিয়ে input-নির্ভর ত্রুটি টেস্ট করার জন্য <Cite n={7} />।

## Try it

<Voices>
<Technical>

1. **Start the practice app.** With Docker, run `docker run --rm -p 127.0.0.1:3000:3000 bkimminich/juice-shop` <Cite n={11} />, and open `http://localhost:3000` <Cite n={11} /> in Burp's browser <Cite n={6} />.
2. **Catch the login request.** With **Intercept on**, log in with any email and password. Burp holds the request <Cite n={6} />: `POST /rest/user/login`, with a JSON body of `email` and `password`. Forward it; the app answers `401`.
3. **Inject.** Send the login request to Repeater <Cite n={8} />. Change the email to `' OR 1=1--`, keep any password, and click **Send** <Cite n={8} />. The answer is `200` with a login token: you are logged in as the first user, the admin. The `--` starts an SQL comment, which removes the password check from the `WHERE` clause <Cite n={13} />.
4. **Cross the access line.** Register a user of your own and log in. In the HTTP history of Burp Proxy <Cite n={6} />, find `GET /rest/basket/<id>`, the request for your own basket. Send it to Repeater <Cite n={8} />, change the id to `1`, and click **Send**. The answer is `200` with the basket of another user: an IDOR <Cite n={14} />.
5. **Without Burp.** The same login request works from a terminal:

```bash
curl -s -X POST http://localhost:3000/rest/user/login \
  -H 'Content-Type: application/json' \
  -d "{\"email\":\"' OR 1=1--\",\"password\":\"x\"}"
```

## How a tester uses it

<Voices>
<Technical>

- **Change every id.** For each request that carries an id, send it with the id of another user's record. Access control should enforce record ownership <Cite n={2} />, and everything except public resources should be denied by default <Cite n={2} />.
- **Feed every input to the interpreter.** An app is open to injection when user data is not validated, filtered, or sanitized <Cite n={3} />. Try the boolean conditions `OR 1=1` and `OR 1=2`, and compare the responses <Cite n={13} />.
- **Scale up with Intruder.** Intruder sends the same request over and over, with a different payload in predefined positions each time <Cite n={9} />.
- **Report the fix with the bug.** For SQL injection, the fix is to define the SQL structure apart from its data values and bind the values with parameterized queries <Cite n={16} />. For an IDOR, access control should enforce that the record belongs to the user <Cite n={2} />.
- **Follow a guide.** The OWASP Web Security Testing Guide project produces a cybersecurity testing resource for web application developers and security professionals <Cite n={15} />.

</Technical>
<Layman>

- **Change every id.** Send each request that carries an id with another user's id. Access control should check who owns each record <Cite n={2} />.
- **Try the tricky inputs.** An app is open to injection when user data is not validated, filtered, or sanitized <Cite n={3} />. Try `OR 1=1` and `OR 1=2`, and compare the answers <Cite n={13} />.
- **Scale up with Intruder.** Intruder sends the same request over and over, with a different payload each time <Cite n={9} />.
- **Report the fix too.** For SQL injection, the fix is to keep the SQL apart from the values and bind them with parameterized queries <Cite n={16} />. For an IDOR, access control should check that the record is the user's own <Cite n={2} />.
- **Follow a guide.** The OWASP Web Security Testing Guide is a testing resource for web developers and security people <Cite n={15} />.

</Layman>
<Bangla>

- **প্রতিটা id বদলান।** যে request-এ id থাকে, সেটা অন্য user-এর record-এর id দিয়ে পাঠান। Access control-এর উচিত record-এর মালিকানা নিশ্চিত করা <Cite n={2} />, আর public resource ছাড়া বাকি সবকিছু ডিফল্টভাবে নিষেধ রাখা <Cite n={2} />।
- **প্রতিটা input interpreter-এ পাঠিয়ে দেখুন।** User-এর ডেটা validate, filter বা sanitize না হলে app injection-এর জন্য খোলা <Cite n={3} />। `OR 1=1` আর `OR 1=2` boolean শর্ত দিয়ে চেষ্টা করুন, আর response দুটো তুলনা করুন <Cite n={13} />।
- **Intruder দিয়ে বড় পরিসরে।** Intruder একই request বারবার পাঠায়, প্রতিবার আগে থেকে ঠিক করা জায়গায় আলাদা payload বসিয়ে <Cite n={9} />।
- **Bug-এর সাথে সমাধানও লিখুন।** SQL injection-এর সমাধান হলো SQL-এর কাঠামো data value থেকে আলাদা রেখে parameterized query দিয়ে value bind করা <Cite n={16} />। IDOR-এর ক্ষেত্রে access control-এর উচিত record-টা user-এরই কি না, তা নিশ্চিত করা <Cite n={2} />।
- **একটা guide মেনে চলুন।** OWASP Web Security Testing Guide project web application developer আর security professional-দের জন্য একটা cybersecurity testing resource তৈরি করে <Cite n={15} />।

</Bangla>
</Voices>

## Common mistakes

<Voices>
<Technical>

- **Testing a target without permission.** Practise on targets that are made for it, such as Juice Shop <Cite n={10} />, the Web Security Academy labs <Cite n={12} />, or the deliberately vulnerable site of Burp's own tutorial <Cite n={6} />.
- **Trusting the screen.** Access control checks can be bypassed by modifying the URL or by an attack tool that modifies API requests <Cite n={2} />. Test the request, not only the screen.
- **Testing access only with one user.** An IDOR arises when an app uses user-supplied input to access objects directly <Cite n={14} />. Test it with two accounts: ask as one user for an object of the other.
- **Stopping at "the login works".** Also test whether the login permits automated attacks such as credential stuffing <Cite n={4} />.
- **Reporting `' OR 1=1--` as the bug.** The payload is only the proof. The flaw is user input that reaches the database as a command <Cite n={3} />.

</Technical>

- **স্ক্রিনে ভরসা করা।** URL বদলে, বা API request বদলানোর attack tool দিয়ে access control-এর চেক এড়ানো যায় <Cite n={2} />। শুধু স্ক্রিন নয়, request টেস্ট করুন।
- **একটা user দিয়েই access টেস্ট করা।** App যখন user-এর দেওয়া input দিয়ে সরাসরি object access করে, তখন IDOR তৈরি হয় <Cite n={14} />। দুটো account দিয়ে টেস্ট করুন: একজন user হিসেবে অন্যজনের object চান।
- **"Login কাজ করছে" বলে থেমে যাওয়া।** Login credential stuffing-এর মতো automated attack চলতে দেয় কি না, সেটাও টেস্ট করুন <Cite n={4} />।
- **`' OR 1=1--`-কেই bug হিসেবে report করা।** Payload শুধু প্রমাণ। আসল ত্রুটি হলো user-এর input, যা database-এ command হিসেবে পৌঁছায় <Cite n={3} />।

## What a tester can check

<Voices>
<Technical>

<Callout type="tip" title="Tutorial advice">
This list is the tutorial's own advice, not a fact from a source.

- **Permission.** Is there written permission and a written scope before any attack starts?
- **Two accounts.** Is every object id tried with the account of another user, for read, change, and delete?
- **Every input.** Is every field, header, and query parameter tried with injection payloads?
- **Login.** Is there a limit on wrong passwords, and does the app say the same thing for a wrong user and a wrong password?
- **Errors.** Do error answers hide stack traces, SQL, and server versions?
- **Retest.** After the fix, does the same request now fail, and does the normal use still work?
</Callout>

</Technical>
<Layman>

<Callout type="tip" title="Tutorial advice">
This list is the tutorial's own advice, not a fact from a source.

- **Permission.** Is there written permission and a scope before you start?
- **Two accounts.** Is every id tried with another user's account?
- **Every input.** Is every field tried with tricky inputs?
- **Login.** Is there a limit on wrong passwords?
- **Errors.** Do errors hide technical details?
- **Retest.** After the fix, does the attack fail and normal use still work?
</Callout>

</Layman>
<Bangla>

<Callout type="tip" title="Tutorial advice">
এই তালিকা টিউটোরিয়ালের নিজের পরামর্শ, কোনো source থেকে নেওয়া তথ্য নয়।

- **অনুমতি।** কোনো attack শুরুর আগে লিখিত অনুমতি আর লিখিত scope আছে কি?
- **দুটো account।** পড়া, বদলানো আর মোছার জন্য প্রতিটা object id কি অন্য user-এর account দিয়ে চেষ্টা করা হয়েছে?
- **প্রতিটা input।** প্রতিটা field, header আর query parameter কি injection payload দিয়ে চেষ্টা করা হয়েছে?
- **Login।** ভুল password-এর কোনো সীমা আছে কি, আর ভুল user আর ভুল password-এ app কি একই কথা বলে?
- **Error।** Error-এর উত্তর কি stack trace, SQL আর server-এর version লুকিয়ে রাখে?
- **আবার টেস্ট।** সমাধানের পরে একই request কি এখন ব্যর্থ হয়, আর স্বাভাবিক ব্যবহার কি এখনো কাজ করে?
</Callout>

## Key words

| Term | Meaning |
|---|---|
| OWASP Top 10 | An awareness document of the most critical security risks to web applications. |
| Broken access control | A user can act outside the permissions they should have. |
| IDOR | Insecure direct object reference: the app uses user-supplied input to access objects directly. |
| Injection | Untrusted input that an interpreter, such as a database, runs as a command. |
| SQL injection | Injection into the SQL queries of an app. |
| Credential stuffing | An automated attack with a breached list of real usernames and passwords. |
| Burp Proxy | Sits between the browser and the app, to intercept and change the traffic. |
| Burp Repeater | Changes a request and sends it again, as often as you like. |
| Burp Intruder | Sends one request many times, with a different payload each time. |
| Parameterized query | A query whose SQL structure is defined apart from its data values, which are bound in separately; the fix for SQL injection. |
| OWASP Juice Shop | An insecure web app made for security training. |
