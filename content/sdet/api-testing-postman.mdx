# API Testing with Postman

Before you automate an API test, send the request by hand and look at what comes back. This page explains the parts of an HTTP request and response, then uses Postman to send requests, write checks in JavaScript, run a whole collection, and run it again from the command line.

<PageMeta />

## What it is

<Voices>
<Technical>

**HTTP** is the foundation of any data exchange on the Web <Cite n={1} />. It is a client-server protocol: the client, usually a web browser, starts each request <Cite n={1} />. HTTP is stateless: two requests on the same connection have no link to each other <Cite n={1} />.

A request names a **method**, which says what the request is for <Cite n={2} />. The server answers with a **status code** in one of five classes <Cite n={3} />. On this page, API testing means sending these requests yourself and checking the responses, with no user interface in between.

**Postman** is an API client. You enter the request URL, select the method, and add values such as authorization, parameters, body data, and headers <Cite n={5} />. Then you test the response with JavaScript: `pm.test` defines a test with a name, and `pm.expect` makes an assertion <Cite n={7} />.

[Fundamentals](/fundamentals/) teaches how to design the test cases. When the checks work by hand, [API Automation with Playwright](/sdet/playwright-api/) turns them into code.

</Technical>

## How it works

<Voices>
<Technical>

**The method says what the request is for** <Cite n={2} />.

| Method | What it does |
|---|---|
| `GET` | Requests a representation of a resource. It should only retrieve data, and it should not contain request content <Cite n={2} />. |
| `POST` | Submits an entity to a resource, often with a change of state on the server <Cite n={2} />. |
| `PUT` | Replaces all current representations of the resource with the request content <Cite n={2} />. |
| `PATCH` | Applies partial modifications to a resource <Cite n={2} />. |
| `DELETE` | Deletes the resource <Cite n={2} />. |

**Some methods are idempotent.** A method is idempotent if one request has the same intended effect on the server as several identical requests <Cite n={4} />. Safe methods, `PUT`, and `DELETE` are idempotent. `POST` and `PATCH` are not guaranteed to be <Cite n={4} />. A client can safely retry a request that uses an idempotent method <Cite n={4} />.

**The status code says how it went.** There are five classes: informational (100–199), successful (200–299), redirection (300–399), client error (400–499), and server error (500–599) <Cite n={3} />. Five codes come up often:

- `201 Created`: the request made a new resource; typical after a `POST` <Cite n={3} />.
- `401 Unauthorized`: in meaning, unauthenticated. The client must authenticate itself <Cite n={3} />.
- `403 Forbidden`: the server knows who the client is, but the client has no access rights <Cite n={3} />.
- `404 Not Found`: the server cannot find the resource <Cite n={3} />.
- `500 Internal Server Error`: the server met a situation that it does not know how to handle <Cite n={3} />.

**Parameters and body.** Query parameters come after `?`, as key-value pairs joined by `&`, for example `?id=1&type=new` <Cite n={6} />. A path parameter is a placeholder after `:`, for example `/customer/:id` <Cite n={6} />. A body can be form data, URL-encoded, raw, or binary <Cite n={6} />.

</Technical>
<Layman>

**The method says what you want** <Cite n={2} />:

- `GET` reads something. It should only get data <Cite n={2} />.
- `POST` sends something to the server, and often changes data there <Cite n={2} />.
- `PUT` replaces the whole thing <Cite n={2} />.
- `PATCH` changes a part of it <Cite n={2} />.
- `DELETE` removes it <Cite n={2} />.

**Sending it again.** A method is idempotent if the intended effect of one request is the same as the effect of many of the same request <Cite n={4} />. Safe methods, `PUT`, and `DELETE` are idempotent. `POST` and `PATCH` may not be <Cite n={4} />. A client can safely send an idempotent request again <Cite n={4} />.

**The status code says how it went.** 200 to 299 means success. 400 to 499 is a client error, and 500 to 599 is a server error <Cite n={3} />.

- `201 Created`: something new was made, usually after a `POST` <Cite n={3} />.
- `401 Unauthorized`: you must prove who you are first <Cite n={3} />.
- `403 Forbidden`: the server knows who you are, but you may not do this <Cite n={3} />.
- `404 Not Found`: the server cannot find it <Cite n={3} />.
- `500 Internal Server Error`: the server hit a problem that it cannot handle <Cite n={3} />.

**Parameters and body.** Query parameters go after `?`, like `?id=1&type=new` <Cite n={6} />. A path parameter sits in the path after `:`, like `/customer/:id` <Cite n={6} />. The body can be form data, URL-encoded, raw, or binary <Cite n={6} />.

</Layman>
<Bangla>

**Method বলে request-টা কীসের জন্য** <Cite n={2} />:

- `GET` কোনো resource চায়। এটা শুধু data আনবে, আর এতে request content থাকা উচিত নয় <Cite n={2} />।
- `POST` resource-এ কিছু পাঠায়, প্রায়ই server-এ অবস্থা বদলায় <Cite n={2} />।
- `PUT` পুরো resource-টা request content দিয়ে বদলে দেয় <Cite n={2} />।
- `PATCH` resource-এর একটা অংশ বদলায় <Cite n={2} />।
- `DELETE` resource-টা মুছে দেয় <Cite n={2} />।

**কিছু method idempotent।** একটা request আর একই রকম অনেকগুলো request-এর উদ্দেশ্যমূলক ফল server-এ একই হলে method-টা idempotent <Cite n={4} />। Safe method, `PUT` আর `DELETE` idempotent। `POST` আর `PATCH` idempotent হবেই, এমন নিশ্চয়তা নেই <Cite n={4} />। Idempotent method-এর request client নিরাপদে আবার পাঠাতে পারে <Cite n={4} />।

**Status code বলে কী হলো।** পাঁচটা শ্রেণি: informational (100–199), successful (200–299), redirection (300–399), client error (400–499) আর server error (500–599) <Cite n={3} />। প্রায়ই দেখা যায় এমন পাঁচটা code:

- `201 Created`: request একটা নতুন resource তৈরি করেছে; সাধারণত `POST`-এর পর <Cite n={3} />।
- `401 Unauthorized`: অর্থের দিক থেকে unauthenticated; client-কে নিজের পরিচয় প্রমাণ করতে হবে <Cite n={3} />।
- `403 Forbidden`: server জানে client কে, কিন্তু client-এর access-এর অধিকার নেই <Cite n={3} />।
- `404 Not Found`: server resource-টা খুঁজে পায় না <Cite n={3} />।
- `500 Internal Server Error`: server এমন অবস্থায় পড়েছে, যেটা সে সামলাতে জানে না <Cite n={3} />।

**Parameter আর body।** Query parameter বসে `?`-এর পরে, `&` দিয়ে জোড়া key-value হিসেবে, যেমন `?id=1&type=new` <Cite n={6} />। Path parameter হলো path-এর ভেতরে `:`-এর পরের একটা placeholder, যেমন `/customer/:id` <Cite n={6} />। Body হতে পারে form data, URL-encoded, raw বা binary <Cite n={6} />।

</Bangla>
</Voices>

## Try it

<Voices>
<Technical>

1. **Send a request.** Open a new request in Postman and enter `https://postman-echo.com/get?course=sdet`. Select the `GET` method, then click Send <Cite n={13} />. The Echo service returns JSON with the details of the request that you sent <Cite n={13} />.
2. **Add two tests.** You can add tests to a request, a collection, or a folder <Cite n={7} />. Add this as the post-response script of the request:

```js
pm.test("Status code is 200", function () {
  pm.response.to.have.status(200);
});

pm.test("The query comes back", function () {
  const body = pm.response.json();
  pm.expect(body.args.course).to.eql("sdet");
});
```

`pm.response.to.have.status(200)` checks the status code, and `pm.response.json()` parses the JSON body <Cite n={8} />. Tests run after the response arrives, and their output appears in the Test Results tab <Cite n={7} />. Send the request again and read the two results.

3. **Use a variable.** Store `https://postman-echo.com` in a `base_url` variable, and write the URL as `{{base_url}}/get?course=sdet` <Cite n={9} />. When the URL changes, you change the variable once <Cite n={9} />.
4. **Run the collection.** Save the request in a collection. The Collection Runner sends the requests of a collection in the order you choose and logs the test results of each request <Cite n={10} />. It can also read iteration data from a data file <Cite n={10} />.
5. **Run it from a terminal.** Newman is Postman's command-line collection runner <Cite n={11} />. It needs Node.js 16 or later <Cite n={11} />. Export the collection as a JSON file, then run:

```bash
npm install -g newman
newman run my-collection.json
```

Newman will not receive updates or fixes, and Postman asks you to plan the move to the Postman CLI <Cite n={11} />. The Postman CLI runs a collection with `postman collection run` <Cite n={12} />.

</Technical>

## How a tester uses it

<Voices>
<Technical>

- **Check more than the status.** Postman's own examples check the status code, the response time, and the fields of the JSON body <Cite n={8} />. A response time check reads `pm.expect(pm.response.responseTime).to.be.below(200)` <Cite n={8} />.
- **Tell 401 from 403.** A `401` means the client must authenticate. A `403` means the server knows the client, but the client has no access rights <Cite n={3} />. Test both: a request with no token, and a request by a user who may not do the action.
- **Send a POST twice.** `POST` is not guaranteed to be idempotent <Cite n={4} />. Send the same `POST` again and check what the API does with the repeat.
- **One collection, several environments.** An environment groups one set of values, for example one for the production server and another for testing <Cite n={9} />. Environment variables scope the work to one environment, such as local development, testing, or production, and one environment is active at a time <Cite n={9} />.
- **Run it in CI.** By default, Newman exits with code 0 when the run completes without errors. With `--bail`, it stops and exits with code 1 when a test fails, so the CI tool can fail the build <Cite n={11} />.
- **Feed it data.** A data file gives the Collection Runner its iteration data, so the collection runs several times, with a different data set each time <Cite n={10} />.

</Technical>
<Layman>

- **Check more than the status.** Postman's examples check the status code, the time the answer took, and the fields of the JSON body <Cite n={8} />.
- **Know 401 from 403.** `401`: the client must prove who it is. `403`: the server knows the client, but it may not do this <Cite n={3} />. Test both: no token, and a user without the right.
- **Send a POST twice.** `POST` may not be idempotent <Cite n={4} />. Send the same `POST` again and see what the API does.
- **One collection, several environments.** An environment holds one set of values, like one for the live server and one for testing <Cite n={9} />. One environment is active at a time <Cite n={9} />.
- **Run it in CI.** By default, Newman ends with code 0 when the run has no errors. With `--bail`, it stops and ends with code 1 when a test fails, so CI can fail the build <Cite n={11} />.
- **Feed it data.** A data file lets the Collection Runner run the collection several times, with different data each time <Cite n={10} />.

<Bangla>

- **শুধু status নয়, আরও চেক করুন।** Postman-এর নিজের উদাহরণগুলো status code, response time আর JSON body-র field চেক করে <Cite n={8} />। Response time-এর চেক দেখতে এমন: `pm.expect(pm.response.responseTime).to.be.below(200)` <Cite n={8} />।
- **401 আর 403 আলাদা করুন।** `401` মানে client-কে নিজের পরিচয় প্রমাণ করতে হবে। `403` মানে server client-কে চেনে, কিন্তু তার access-এর অধিকার নেই <Cite n={3} />। দুটোই টেস্ট করুন: token ছাড়া একটা request, আর এমন user-এর request, যার কাজটা করার অনুমতি নেই।
- **একই POST দুবার পাঠান।** `POST` idempotent হবেই, এমন নিশ্চয়তা নেই <Cite n={4} />। একই `POST` আবার পাঠিয়ে দেখুন API সেটা নিয়ে কী করে।
- **এক collection, কয়েকটা environment।** একটা environment এক সেট value রাখে, যেমন production server-এর জন্য এক সেট আর টেস্টের জন্য আরেক সেট <Cite n={9} />। Environment variable কাজটাকে একটা environment-এ সীমিত রাখে, যেমন local development, testing বা production, আর একবারে একটাই environment active থাকে <Cite n={9} />।
- **CI-তে চালান।** ডিফল্টভাবে run কোনো error ছাড়া শেষ হলে Newman code 0 দিয়ে বের হয়। `--bail` দিলে কোনো টেস্ট fail করলেই থেমে code 1 দিয়ে বের হয়, যাতে CI tool build-কে fail করতে পারে <Cite n={11} />।
- **Data দিন।** একটা data file Collection Runner-কে iteration data দেয়, ফলে collection-টা কয়েকবার চলে, প্রতিবার আলাদা data set নিয়ে <Cite n={10} />।

</Bangla>
</Voices>

## Common mistakes

<Voices>
<Technical>

- **Expecting `200` from every success.** A create often answers `201 Created`, the typical response after a `POST` <Cite n={3} />. Check the exact code that the API promises.
- **Treating `401` and `403` as one case.** One means that the client is not authenticated; the other means that it has no access rights <Cite n={3} />.
- **Missing a `GET` that changes data.** A `GET` should only retrieve data <Cite n={2} />. If it changes data, report it.
- **Retrying a `POST` without a thought.** A client can safely retry an idempotent request, but `POST` is not guaranteed to be idempotent <Cite n={4} />.
- **The same URL typed into every request.** Store it in a variable, so that a change is made once <Cite n={9} />.
- **A new pipeline built on Newman.** Newman will not receive updates or fixes, and Postman asks you to plan to replace it with the Postman CLI in scripts and CI pipelines <Cite n={11} />.

</Technical>

## What a tester can check

<Voices>
<Technical>

<Callout type="tip" title="Tutorial advice">
This list is the tutorial's own advice, not a fact from a source.

- **Status codes.** Does each request check the exact status code, not only that it is a success?
- **The body.** Do the tests check the fields and the types of the JSON body, not only that it exists?
- **Error cases.** Is there a request for a missing field, a wrong type, no token, and a record of another user?
- **Repeats.** What does the API do when the same `POST` arrives twice?
- **Variables.** Are the URLs and tokens in variables and environments, not typed into the requests?
- **CI.** Does the collection run in CI, and does one failed test fail the build?
</Callout>

</Technical>

## Key words

| Term | Meaning |
|---|---|
| HTTP | A client-server protocol of the web; the client starts each request. |
| Method | What a request is for: `GET`, `POST`, `PUT`, `PATCH`, `DELETE`. |
| Status code | The result of a request, in one of five classes from 100 to 599. |
| Idempotent | One request has the same intended effect as several identical ones. |
| Query parameter | A key-value pair after `?` in the URL. |
| Path parameter | A placeholder in the path, such as `:id`. |
| Post-response script | JavaScript that runs after the response arrives, with `pm.test` and `pm.expect`. |
| Variable | A stored value, such as `{{base_url}}`, used across requests. |
| Environment | One set of variable values, for example for a test server. |
| Collection Runner | Runs the requests of a collection in order and logs the test results. |
| Newman | Postman's command-line collection runner; it gets no more updates or fixes. |
| Postman CLI | The command-line tool that Postman asks you to move to: `postman collection run`. |
