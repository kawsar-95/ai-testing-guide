# Hooks

A hook runs your own code at a fixed point in a Claude Code session, whatever Claude decides. This page shows how a hook gets its input, how it blocks an action, and four QA hooks: protect files, format after edits, run tests after edits, and log shell commands.

<PageMeta />

## What hooks are

<Voices>
<Technical>

Hooks are user-defined handlers that run automatically at specific points in the Claude Code lifecycle. A handler can be a shell command, an HTTP endpoint, an MCP tool call, an LLM prompt, or a subagent. <Cite n={1} />

- Some events happen once per session (`SessionStart`, `SessionEnd`), some once per turn (`UserPromptSubmit`, `Stop`), and some on every tool call (`PreToolUse`, `PostToolUse`). <Cite n={1} />
- If Claude skips a rule that must hold every time, move the rule into a hook. <Cite n={2} />

  </InfoCard>
  <InfoCard title="A hard rule in a hook" tone="good">

A `PreToolUse` hook that returns `permissionDecision: "deny"` blocks the tool, even in `bypassPermissions` mode. <Cite n={3} />

  </InfoCard>
</CardGrid>

<Layman>

A hook is your own handler. Claude Code runs it automatically at a fixed point in a session. A handler can be a shell command, an HTTP endpoint, an MCP tool call, an LLM prompt, or a subagent. <Cite n={1} />

## How a hook is built

<Voices>
<Technical>

A hook configuration has three levels: an event, a matcher group, and one or more handlers. <Cite n={1} /> This is the minimal structure: <Cite n={1} />

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          { "type": "command", "command": "./scripts/after-edit.sh" }
        ]
      }
    ]
  }
}
```

### Where hooks live

| Location | Scope |
|---|---|
| `~/.claude/settings.json` | All your projects <Cite n={1} /> |
| `.claude/settings.json` | One project. You can commit it. <Cite n={1} /> |
| `.claude/settings.local.json` | One project. Not shared. <Cite n={1} /> |
| Managed policy settings | The organization <Cite n={1} /> |
| Plugin `hooks/hooks.json` | Where the plugin is enabled <Cite n={1} /> |
| Skill frontmatter | The rest of the session after the skill is used <Cite n={1} /> |
| Subagent frontmatter | While that subagent runs <Cite n={1} /> |

- Hook entries from different settings levels merge. They do not replace each other. <Cite n={1} />
- All matching hooks run in parallel. If you define the same handler in more than one settings file, it runs once. <Cite n={1} />
- Claude Code watches the settings files and normally applies hook edits automatically. If it does not, restart the session. <Cite n={1} /> <Cite n={3} />

The [Settings & the .claude Folder](/configure/settings/) page explains the settings files.

### Matchers

The `matcher` selects which tool calls (or other event sources) trigger the hook. <Cite n={1} />

| Matcher | Matches |
|---|---|
| `"*"`, `""`, or no matcher | Everything <Cite n={1} /> |
| `Edit\|Write` or `Edit, Write` | Exactly `Edit` or `Write` <Cite n={1} /> |
| `Edit.*` | A regular expression. It also matches `NotebookEdit`. <Cite n={1} /> |
| `mcp__atlassian__.*` | Every tool of the MCP server named `atlassian` <Cite n={1} /> |

- A matcher with only letters, digits, `_`, `-`, spaces, `,`, and `|` is an exact name or a list of names. Any other character makes it a JavaScript regular expression. <Cite n={1} />
- Matchers are case-sensitive. <Cite n={3} />
- MCP tool names have the form `mcp__<server>__<tool>`. A bare `mcp__atlassian` matches nothing in a hook matcher. Add `__.*`. <Cite n={1} />
- For tool events, the matcher tests the tool name. For other events it tests something else, for example the session start source for `SessionStart`. A matcher on an event without matcher support is ignored. <Cite n={1} />

<Callout type="warning" title="Common mistake: matching only Write">

The old example on this page used the matcher `Write`. That misses every `Edit`. Use `Edit|Write` for file changes. <Cite n={1} />

</Callout>

</Technical>

You can put hooks in many places. `~/.claude/settings.json` is for all your projects. `.claude/settings.json` is for one project, and you can commit it. `.claude/settings.local.json` is for one project and is not shared. Hooks can also come from managed policy settings, a plugin, a skill, or a subagent. <Cite n={1} /> Hooks from different settings levels merge. They do not replace each other. </Layman>

একটি hook configuration-এর তিনটি স্তর আছে: একটি event, একটি matcher group এবং এক বা একাধিক handler। <Cite n={1} />

Hook অনেক জায়গায় রাখা যায়: `~/.claude/settings.json` (আপনার সব project), `.claude/settings.json` (একটি project, commit করা যায়) এবং `.claude/settings.local.json` (একটি project, share হয় না)। এছাড়া managed policy settings, plugin-এর `hooks/hooks.json`, skill frontmatter অথবা subagent frontmatter থেকেও hook আসতে পারে। <Cite n={1} /> বিভিন্ন settings level-এর hook একসাথে merge হয়, একটি অন্যটিকে replace করে না। মিলে যাওয়া সব hook parallel-এ চলে, আর একই handler একাধিক settings file-এ থাকলে একবারই চলে। <Cite n={1} /> Claude Code সাধারণত hook-এর পরিবর্তন নিজে থেকেই প্রয়োগ করে। না করলে session restart করুন। <Cite n={1} /> <Cite n={3} />

`matcher` ঠিক করে কোন tool call hook-টি চালাবে। `"*"`, `""` অথবা কোনো matcher না থাকলে সবকিছু মেলে। `Edit|Write` ঠিক `Edit` বা `Write`-কে মেলায়। অন্য character থাকলে, যেমন `Edit.*`-এ, matcher-টি একটি regular expression হয়ে যায়। MCP server-এর জন্য `mcp__atlassian__.*`-এর মতো রূপ ব্যবহার করুন। <Cite n={1} /> Matcher case-sensitive। <Cite n={3} /> File পরিবর্তনের জন্য শুধু `Write` নয়, `Edit|Write` ব্যবহার করুন। <Cite n={1} />

</Bangla>
</Voices>

## What your hook receives

<Voices>
<Technical>

A command hook gets the event data as JSON on stdin. An HTTP hook gets it as the body of a POST request. <Cite n={1} /> Example input for a `PreToolUse` hook on `Bash`, with only some fields: <Cite n={1} />

```json
{
  "session_id": "abc123",
  "cwd": "/home/user/payment-service",
  "permission_mode": "default",
  "hook_event_name": "PreToolUse",
  "tool_name": "Bash",
  "tool_input": { "command": "npm test" },
  "tool_use_id": "toolu_01ABC123..."
}
```

- Common fields include `session_id`, `transcript_path`, `cwd`, and `hook_event_name`. Most events also get `permission_mode`, but not all of them. Inside a subagent, the input also has `agent_id` and `agent_type`. <Cite n={1} />
- For `Write`, `tool_input` has `file_path` and `content`. For `Edit`, it has `file_path`, `old_string`, and `new_string`. <Cite n={1} />
- For `Write`, `Edit`, and `Read`, `tool_input.file_path` is always an absolute path. On Windows, it has backslashes. <Cite n={1} />
- A `PostToolUse` hook also gets `tool_response`. <Cite n={1} />

<Callout type="warning" title="Common mistake: $CLAUDE_FILE_PATH">

The docs define no `$CLAUDE_*` tool environment variables such as `CLAUDE_TOOL_NAME`, `CLAUDE_FILE_PATH`, or `CLAUDE_TOOL_INPUT`. <Cite n={1} /> <Cite n={3} /> <Cite n={4} /> Read the tool data from stdin, for example with `jq -r '.tool_input.file_path'`.

</Callout>

Hook scripts do get some environment variables: `CLAUDE_PROJECT_DIR`, `CLAUDE_EFFORT`, and for plugin hooks `CLAUDE_PLUGIN_ROOT` and `CLAUDE_PLUGIN_DATA`. <Cite n={1} /> <Cite n={4} />

- `CLAUDE_PROJECT_DIR` is the project root where the session started. It stays the same if Claude moves into a worktree. The `cwd` field in the JSON follows Claude. <Cite n={1} />
- Use it in script paths, in quotes: `"\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/protect-files.sh"`. <Cite n={3} />
- Make the script executable with `chmod +x`. <Cite n={3} />

</Technical>

## What your hook can answer

<Voices>
<Technical>

### Exit codes

| Exit code | Meaning | Effect |
|---|---|---|
| `0` | Success | For most events, stdout goes to the debug log, not to the transcript. <Cite n={1} /> |
| `2` | Blocking error | On `PreToolUse`, the tool call is blocked. Claude gets the stderr text as the reason. <Cite n={1} /> |
| Any other, including `1` | Non-blocking error | For most events, the action continues. The transcript shows the first line of stderr. <Cite n={1} /> |

<Callout type="danger" title="Exit 1 does not block">

Claude Code treats exit code 1 as a non-blocking error and continues the action, even though 1 is the usual Unix failure code. <Cite n={1} /> A hook that cannot start, for example because of a wrong path, is also a non-blocking error. The transcript shows a hook error notice with the interpreter's message. Watch for this notice on the first run of a policy hook. <Cite n={1} /> To make a failed hook block the action, set `"onFailure": "block"` on a `command` or `http` hook (Claude Code v2.1.295 or later). Then Claude Code blocks the action when the hook cannot start, exits with a code other than 0 or 2, or times out. <Cite n={1} /> Test each blocking hook with sample input.

</Callout>

- Exit code 2 wins over JSON output. Even `permissionDecision: "allow"` cannot override it. <Cite n={1} />
- On `UserPromptSubmit`, `UserPromptExpansion`, `SessionStart`, and `PostModelSwitch`, plain stdout on exit 0 becomes context for Claude. <Cite n={1} />
- Exit 2 on `PostToolUse` shows stderr to Claude, but the tool already ran. <Cite n={1} /> A `PostToolUse` hook cannot undo an action. <Cite n={3} />
- Exit 2 on `Stop` prevents Claude from stopping. On `UserPromptSubmit`, it blocks the prompt. <Cite n={1} />

### JSON output

For finer control, exit 0 and print one JSON object on stdout. Do not mix the JSON with other text. <Cite n={1} /> A `PreToolUse` hook puts its decision in `hookSpecificOutput`: <Cite n={1} />

```json
{
  "hookSpecificOutput": {
    "hookEventName": "PreToolUse",
    "permissionDecision": "deny",
    "permissionDecisionReason": "Database writes are not allowed"
  }
}
```

- `permissionDecision` takes `allow`, `deny`, `ask`, or `defer`. <Cite n={1} /> It must be inside `hookSpecificOutput`. At the top level, it is ignored. <Cite n={3} />
- If hooks disagree, `deny` wins over `defer`, `defer` over `ask`, and `ask` over `allow`. <Cite n={1} />
- `additionalContext` in `hookSpecificOutput` adds text to Claude's context as a system reminder, up to 10,000 characters. <Cite n={1} />
- `"continue": false` with a `stopReason` stops Claude completely. <Cite n={1} />

### Hooks and permission rules

- A hook that returns `deny` blocks the tool even in `bypassPermissions` mode and with `--dangerously-skip-permissions`. <Cite n={3} />
- A hook that returns `allow` does not bypass `deny` and `ask` rules from your settings. A blocking hook wins over `allow` rules. <Cite n={5} />
- Files that you add with `@` in a prompt fire no `PreToolUse` hook, not even one that matches `Read`. Use a `Read` deny rule for them. <Cite n={1} />

</Technical>

</Layman>
<Bangla>

Hook একটি exit code দিয়ে উত্তর দেয়। Exit code `0` মানে success। Exit code `2` হলো blocking error: `PreToolUse`-এ tool call block হয়, আর Claude stderr-এর লেখাটি কারণ হিসেবে পায়। `1`-সহ অন্য যেকোনো code হলো non-blocking error। বেশিরভাগ event-এ action চলতে থাকে। <Cite n={1} /> যে hook শুরুই হতে পারে না (যেমন ভুল path-এর কারণে), সেটিও block করে না। Failed hook দিয়ে action block করাতে একটি `command` বা `http` hook-এ `"onFailure": "block"` set করুন (Claude Code v2.1.295 বা পরের version)। <Cite n={1} /> প্রতিটি blocking hook sample input দিয়ে test করুন।

আরও সূক্ষ্ম নিয়ন্ত্রণের জন্য exit `0` দিন এবং stdout-এ একটি JSON object print করুন। একটি `PreToolUse` hook `permissionDecision` রাখে `hookSpecificOutput`-এর ভেতরে। এর মান হতে পারে `allow`, `deny`, `ask` অথবা `defer`। Hook-গুলো একমত না হলে `deny` জেতে। <Cite n={1} />

যে hook `deny` ফেরত দেয়, সেটি `bypassPermissions` mode-এও tool block করে। <Cite n={3} /> যে hook `allow` ফেরত দেয়, সেটি আপনার settings-এর `deny` এবং `ask` rule bypass করে না। <Cite n={5} />

</Bangla>
</Voices>

## Events

<Voices>
<Technical>

The hooks reference documents 33 events. <Cite n={1} /> These are the events that QA work uses most:

| Event | When it runs |
|---|---|
| `SessionStart` | When a session begins or resumes <Cite n={1} /> |
| `PreToolUse` | Before a tool call executes. It can block the call. <Cite n={1} /> |
| `PostToolUse` | After a tool call succeeds <Cite n={1} /> |
| `PostToolUseFailure` | After a tool call fails <Cite n={1} /> |
| `Stop` | When Claude finishes responding <Cite n={1} /> |
| `FileChanged` | Use it to catch a file that a Bash command or another process rewrote <Cite n={1} /> |

The full list is in the [Reference](#reference).

</Technical>

The hooks reference documents 33 events. <Cite n={1} /> QA work uses these events the most: <Cite n={1} />

- `SessionStart`: a session begins or resumes.

- `PostToolUse`: after a tool call succeeds.

</Layman>

Hooks reference-এ 33টি event-এর বর্ণনা আছে। <Cite n={1} /> QA কাজে এই event-গুলো সবচেয়ে বেশি লাগে: <Cite n={1} />

- `SessionStart`: session শুরু বা resume হলে।
- `PreToolUse`: tool call চলার আগে। এটি call-টি block করতে পারে।
- `PostToolUse`: tool call সফল হওয়ার পরে।
- `PostToolUseFailure`: tool call fail করার পরে।
- `Stop`: Claude উত্তর দেওয়া শেষ করলে।
- `FileChanged`: কোনো Bash command বা অন্য process যে file আবার লিখেছে, তা ধরতে।

পুরো তালিকা [Reference](#reference)-এ আছে।

## Hook types

<Voices>
<Technical>

| `type` | What it does |
|---|---|
| `command` | Runs a shell command with the event JSON on stdin <Cite n={1} /> |
| `http` | Sends the JSON as a POST to `url`. To block, it returns a 2xx response with decision JSON. A status code alone cannot block. <Cite n={1} /> |
| `mcp_tool` | Calls a tool on an MCP server, with `server`, `tool`, and `input` <Cite n={1} /> |
| `prompt` | Sends the input to a Claude model for a single-turn yes/no decision <Cite n={1} /> |
| `agent` | Starts a subagent with tools. Agent hooks are experimental. <Cite n={1} /> |

- `PreToolUse`, `PostToolUse`, `Stop`, and `UserPromptSubmit` are among the events that support all five types. `SessionStart` and `Setup` support only `command` and `mcp_tool`. <Cite n={1} />
- Default timeouts: 600 s for `command`, `http`, and `mcp_tool`; 30 s for `prompt`; 60 s for `agent`. <Cite n={1} /> On `UserPromptSubmit`, `PreModelSwitch`, and `PostModelSwitch`, the default for `command`, `http`, and `mcp_tool` is 30 s. On `MessageDisplay`, it is 10 s. <Cite n={1} />
- A `PreToolUse` hook of type `command`, `http`, or `mcp_tool` that times out does not block the tool call. <Cite n={1} />

</Technical>
<Layman>

A hook has one of five types: <Cite n={1} />

- `command` runs a shell command with the event JSON on stdin.
- `http` sends the JSON as a POST to `url`. To block, it must return a 2xx response with decision JSON. A status code alone cannot block.
- `mcp_tool` calls a tool on an MCP server.
- `prompt` sends the input to a Claude model for one yes or no decision.
- `agent` starts a subagent with tools. Agent hooks are experimental.

Not all events support all five types. For example, `SessionStart` supports only `command` and `mcp_tool`. <Cite n={1} /> The default timeout is 600 s for `command`, `http`, and `mcp_tool`, 30 s for `prompt`, and 60 s for `agent`. Some events have shorter defaults. <Cite n={1} /> If a `PreToolUse` hook of type `command`, `http`, or `mcp_tool` times out, the tool call is not blocked. <Cite n={1} />

</Layman>
<Bangla>

Hook-এর পাঁচটি type আছে: <Cite n={1} />

- `command`: event JSON stdin-এ দিয়ে একটি shell command চালায়।
- `http`: JSON-টি POST হিসেবে `url`-এ পাঠায়। Block করতে হলে এটিকে decision JSON-সহ একটি 2xx response ফেরত দিতে হয়। শুধু status code দিয়ে block হয় না।
- `mcp_tool`: একটি MCP server-এর একটি tool call করে।
- `prompt`: একবারের হ্যাঁ/না সিদ্ধান্তের জন্য input একটি Claude model-এ পাঠায়।
- `agent`: tool-সহ একটি subagent চালু করে। Agent hook এখনো experimental।

সব event পাঁচটি type-ই support করে না। যেমন, `SessionStart` শুধু `command` এবং `mcp_tool` support করে। <Cite n={1} /> Default timeout হলো `command`, `http` এবং `mcp_tool`-এর জন্য 600 s, `prompt`-এর জন্য 30 s, আর `agent`-এর জন্য 60 s। কিছু event-এ default আরও কম। <Cite n={1} /> `command`, `http` বা `mcp_tool` type-এর একটি `PreToolUse` hook timeout হলে tool call block হয় না। <Cite n={1} />

</Bangla>
</Voices>

## QA examples

<Voices>
<Technical>

### Block edits to .env and migrations

Example: save this script as `.claude/hooks/protect-files.sh` and run `chmod +x` on it. It is adapted from the protect-files example in the hooks guide, including its line that changes Windows backslashes to slashes. <Cite n={3} /> On Windows, `tool_input.file_path` has backslashes, and a check written with slashes never matches it. <Cite n={1} /> The `.env` pattern also matches names such as `.envrc`.

```bash
#!/bin/bash
# Example: block edits to .env files, migrations, and .git/
FILE_PATH=$(jq -r '.tool_input.file_path // empty')
# Change Windows backslashes to slashes so the patterns also match on Windows
FILE_PATH="${FILE_PATH//\\//}"

for pattern in ".env" "/migrations/" ".git/"; do
  if [[ "$FILE_PATH" == *"$pattern"* ]]; then
    echo "Blocked: $FILE_PATH matches the protected pattern $pattern" >&2
    exit 2
  fi
done
exit 0
```

Register it in `.claude/settings.json`:

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          {
            "type": "command",
            "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/protect-files.sh"
          }
        ]
      }
    ]
  }
}
```

Test it before you trust it. <Cite n={3} />

```bash
echo '{"tool_name":"Write","tool_input":{"file_path":"/repo/db/migrations/001.sql"}}' | .claude/hooks/protect-files.sh
echo $?   # 2, and the "Blocked" message on stderr
```

<Callout type="warning" title="Also add deny rules">

This hook sees only the `Edit` and `Write` tools. A `Bash` command can also change a file. `Read` and `Edit` deny rules cover Claude's file tools, the file commands that Claude Code recognizes in Bash (such as `cat`, `sed`, and `tee`), and redirections. They do not cover any script. For blocking at the operating system level, use the sandbox. <Cite n={5} /> Add rules such as `Read(./.env)` and `Edit(./.env)` to `permissions.deny`.

</Callout>

### Format after edits

The hooks guide runs Prettier on every file that Claude edits or writes: <Cite n={3} />

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          {
            "type": "command",
            "command": "jq -r '.tool_input.file_path' | xargs npx prettier --write"
          }
        ]
      }
    ]
  }
}
```

### Run tests after edits

`"async": true` runs a command hook in the background. An async hook cannot block. Its output reaches Claude on the next turn through `additionalContext` or `systemMessage`. <Cite n={1} />

Example: `.claude/hooks/run-tests-async.sh` runs the tests after Claude edits a test file and reports the result to Claude.

```bash
#!/bin/bash
# Example: run the tests after Claude edits a test file
FILE_PATH=$(jq -r '.tool_input.file_path // empty')

case "$FILE_PATH" in
  *.spec.ts|*.test.ts) ;;
  *) exit 0 ;;
esac

if npm test --silent > /dev/null 2>&1; then
  RESULT="Tests passed after the edit of $FILE_PATH"
else
  RESULT="Tests failed after the edit of $FILE_PATH. Run npm test to see the failures."
fi
jq -n --arg ctx "$RESULT" '{hookSpecificOutput: {hookEventName: "PostToolUse", additionalContext: $ctx}}'
```

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          {
            "type": "command",
            "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/run-tests-async.sh",
            "async": true
          }
        ]
      }
    ]
  }
}
```

A `PostToolUse` hook on `Edit|Write` does not run when a `Bash` command or a process outside Claude Code rewrites the file. Use `FileChanged` for that case. <Cite n={1} />

### Log shell commands

<Callout type="note" title="Example">

This audit-log hook is a tutorial example, not a docs example. It uses the `session_id` and `tool_input.command` fields of the `Bash` input. <Cite n={1} /> It was tested on Linux with `jq`. It is not tested on Windows.

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "command": "jq -r '[(now|todate), .session_id, .tool_input.command] | @tsv' >> \"$CLAUDE_PROJECT_DIR\"/.claude/bash-audit.log"
          }
        ]
      }
    ]
  }
}
```

Each line has the time, the session ID, and the command. Commands can contain secrets, so keep `bash-audit.log` out of git.

</Callout>

</Technical>
<Layman>

The first example hook blocks edits to `.env` files, migrations, and `.git/`. It is a `PreToolUse` script for `Edit|Write`. It reads the file path from stdin and exits with code `2` if the path matches a protected pattern. It changes Windows backslashes to slashes, so the check also matches on Windows. <Cite n={3} /> <Cite n={1} /> Test it before you trust it. <Cite n={3} /> This hook does not see `Bash` commands. `Read` and `Edit` deny rules also cover the file commands that Claude Code recognizes in Bash, but they do not cover any script. <Cite n={5} /> Add rules such as `Read(./.env)` and `Edit(./.env)` to `permissions.deny`.

The second hook runs Prettier on every file that Claude edits or writes. <Cite n={3} />

The third hook runs the tests in the background (`"async": true`) after Claude edits a test file. An async hook cannot block. Its output reaches Claude on the next turn. <Cite n={1} /> It does not run when a `Bash` command or another process rewrites the file. Use `FileChanged` for that case. <Cite n={1} />

The fourth hook is a tutorial example. It writes each shell command to `bash-audit.log`, with the time and the session ID. Commands can contain secrets, so keep this file out of git.

</Layman>
<Bangla>

এই section-এ QA কাজের জন্য চারটি উদাহরণ hook আছে।

প্রথম hook `.env` file, migrations এবং `.git/`-এ edit block করে। এটি `Edit|Write`-এর জন্য একটি `PreToolUse` script। এটি stdin থেকে file path পড়ে, আর path কোনো protected pattern-এর সাথে মিললে exit code `2` দেয়। এটি Windows-এর backslash-গুলোকে slash-এ বদলায়, তাই check-টি Windows-এও মেলে। <Cite n={3} /> <Cite n={1} /> বিশ্বাস করার আগে এটি test করুন। <Cite n={3} /> এই hook `Bash` command দেখে না। `Read` এবং `Edit` deny rule Claude Code-এর চেনা Bash file command-গুলোও cover করে, কিন্তু কোনো script cover করে না। <Cite n={5} /> তাই `permissions.deny`-তে `Read(./.env)` এবং `Edit(./.env)`-এর মতো rule যোগ করুন।

দ্বিতীয় hook Claude যে file edit বা write করে, তার প্রতিটিতে Prettier চালায়। <Cite n={3} />

তৃতীয় hook Claude একটি test file edit করার পরে background-এ (`"async": true`) test চালায়। Async hook block করতে পারে না। এর output Claude পরের turn-এ পায়। <Cite n={1} /> কোনো `Bash` command বা Claude Code-এর বাইরের কোনো process file আবার লিখলে এটি চলে না। সেজন্য `FileChanged` ব্যবহার করুন। <Cite n={1} />

চতুর্থ hook এই tutorial-এর নিজের উদাহরণ। এটি প্রতিটি shell command সময় আর session ID-সহ `bash-audit.log`-এ লেখে। Command-এ secret থাকতে পারে, তাই এই file git-এর বাইরে রাখুন।

## Debug and stay safe

<Voices>
<Technical>

### When a hook does not fire

1. Run `/hooks`. It opens a read-only browser of your hooks and shows where each one comes from. <Cite n={1} /> Check that the hook is under the correct event. <Cite n={3} />
2. Check the matcher. Matchers are case-sensitive. <Cite n={3} />
3. Pipe sample JSON into the script and check the exit code with `echo $?`. <Cite n={3} />
4. Start Claude Code with `claude --debug-file /tmp/claude.log`, or run `/debug` during a session. <Cite n={3} />

A `Stop` hook that blocks eight times in a row is overridden. Check the `stop_hook_active` input field and exit 0 early. <Cite n={3} />

### Trust and CI

<Callout type="danger" title="Hooks run with your permissions">

Command hooks run shell commands with your full user permissions. <Cite n={1} /> In an interactive session, hooks from settings files run only after you accept the workspace trust dialog. In a `-p` or SDK session, Claude Code treats the folder as trusted, so committed hooks run. <Cite n={1} /> Review `.claude/settings.json` in a repository that you did not write before you run Claude Code on it in CI.

</Callout>

The docs give these security practices for hook scripts: validate input, quote shell variables, block `..` in paths, use absolute paths, and skip sensitive files such as `.env`, `.git/`, and keys. <Cite n={1} />

- `"disableAllHooks": true` in settings turns hooks off. It cannot turn off managed hooks from user or project settings. <Cite n={1} />
- On Windows without Git Bash, the Bash tool is not registered, so a hook that matches only `Bash` never fires. Use the matcher `Bash|PowerShell` and `"shell": "powershell"`. <Cite n={1} />

</Callout>

</Technical>

### All 33 events

### More options

- `if` filters a tool event with permission-rule syntax, for example `"Bash(git *)"` or `"Edit(*.ts)"`. One rule per `if`. On other events, a hook with `if` never runs. <Cite n={1} /> `"Edit(src/**)"` matches only `src` in the working directory. Use `"Edit(**/src/**)"` for any depth (v2.1.214 or later). <Cite n={1} />
- Exec form: `command` plus an `args` list, for example `"command": "${CLAUDE_PROJECT_DIR}/.claude/hooks/check-style.sh", "args": []`. It needs no shell quotes. <Cite n={1} />
- `asyncRewake` runs the hook in the background and wakes Claude on exit code 2. <Cite n={1} />
- `PostToolUse` can replace the tool output with `updatedToolOutput`. <Cite n={1} />
- For an MCP tool, the `PreToolUse` input also has `mcp_server` with `name` and `source` (v2.1.274 or later). Base trust decisions on `source`, not on `name`. <Cite n={1} />
- `PreToolUse` top-level `decision` and `reason` are deprecated. Other events, such as `PostToolUse` and `Stop`, use a top-level `decision: "block"` with a `reason`. <Cite n={1} />
- Hooks in subagent frontmatter run only while the subagent runs. Hooks in skill frontmatter run for the rest of the session after the skill is used. `once: true` works only in skill frontmatter. <Cite n={1} />
- `SessionEnd` hooks share a time budget of 1.5 s. If your settings set a longer per-hook `timeout`, Claude Code raises the budget to match, up to 60 s. <Cite n={1} />
