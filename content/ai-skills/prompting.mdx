# Prompting

A prompt is the brief that you give an AI model. A clear brief gives you test cases, bug reports, and test data that you can use. A vague brief gives you text that you must write again. This page shows the parts of a good brief and how a tester uses them.

<PageMeta />

## In plain words

<Voices>
<Technical>

OpenAI defines prompt engineering as the work of writing effective instructions for a model <Cite n={1} />. Its guide also says that it is part art and part science to get the output you want <Cite n={1} />.

The Claude docs give a useful picture. Think of the model as a brilliant new employee who does not know your norms or your workflows <Cite n={2} />. A new colleague does good work when the brief says what to do, why, and in what form. A model is the same.

The docs also give a simple check. Hand your prompt to a colleague who knows little about the task, and let them try to do the work from it alone. If the colleague is confused, the model will be confused too <Cite n={2} />.

For a tester, prompting is the base skill. Every other skill in this module (context, research, agents, evals) starts with a clear brief. The site page [Prompting](/foundations/prompting/) shows the same ideas inside Claude Code.

## How it works

<Voices>
<Technical>

A good brief has a few parts. This order is the tutorial's own choice:

```text
Role       one sentence: who the model acts as
Context    the product, the users, and why the task matters
Task       what to do, as numbered steps
Examples   3 to 5 input -> output pairs
Format     table, JSON, Gherkin, or a fixed template
Limits     what to do when information is missing
```

**Role.** A role in the system prompt focuses the model's behavior and tone. Even one sentence helps <Cite n={2} />. In the OpenAI API, developer messages carry the rules and business logic of the system <Cite n={1} />.

**Context.** Say why an instruction matters. The reason gives the model more about your goal, so it can aim its answer <Cite n={2} />. The Gemini docs say that background tells the model the limits and the specifics of what you ask <Cite n={3} />.

**Task.** Clear and specific instructions are an effective way to steer a model <Cite n={3} />. Use numbered steps when the order or the completeness of the steps matters <Cite n={2} />.

**Examples.** A prompt with no examples is zero-shot. A prompt with a few examples is few-shot <Cite n={3} />. The Claude docs suggest 3 to 5 examples that are relevant and diverse, so that they cover edge cases. Put them in `<example>` tags <Cite n={2} />.

**Structure.** XML tags such as `<instructions>`, `<context>`, and `<input>` keep each kind of content apart, so the model misreads less <Cite n={2} />.

**Format.** You can tell the model the format of its response <Cite n={3} />.

**Limits.** Give the model explicit permission to say "I don't know". This can strongly cut false information <Cite n={4} />.

Expect to iterate. A prompt can need a few rounds before the answers are consistent <Cite n={3} />.

</Technical>

## How a tester uses it

<Voices>
<Technical>

**Test cases from a user story.** Put the story in `<requirement>` tags. Ask for boundary values and negative cases as a table with fixed columns: ID, step, data, expected result. Add 3 good cases from your own suite as examples, so the model copies your style <Cite n={2} />. The site page [Test Design](/foundations/test-design/) shows which techniques to ask for.

**Bug reports in one shape.** Give your bug template and one good report as an example. Then paste raw notes from an exploratory session and ask for one report for each issue. Ask for a numbered list of steps, because the order of the steps matters <Cite n={2} />.

**A second look at a test plan.** Paste the plan and ask what risks it misses. Allow the answer "not enough information" <Cite n={4} />, so the model does not invent gaps that are not there.

**Test data.** Ask for JSON with a fixed set of fields <Cite n={3} />. List the edge values that you want: empty strings, the maximum length, Unicode names, and dates on a leap day.

<Callout type="tip" title="Tutorial advice">
This is the tutorial's own advice. Keep your best prompts in the test repository, next to the tests that they helped to write. Give each prompt a short name and a date. When a prompt gives a bad result, fix the prompt in the file, not only in the chat, so the whole team gets the fix.
</Callout>

</Technical>
<Layman>

**Test cases from a user story.** Put the story in `<requirement>` tags. Ask for boundary values and negative cases in a table with fixed columns: ID, step, data, and expected result. Add 3 good cases from your own tests as examples. Then the model copies your style <Cite n={2} />.

**Bug reports in one shape.** Give your bug template and one good report as an example. Paste your rough notes from a test session. Ask for one report for each problem. Ask for numbered steps, because the order of the steps matters <Cite n={2} />.

**A second look at a test plan.** Paste the plan. Ask what risks it misses. Let the model answer "not enough information" <Cite n={4} />. Then it does not make up gaps.

**Test data.** Ask for JSON with a fixed set of fields <Cite n={3} />. Name the edge values that you want: empty text, the longest text, Unicode names, and leap-day dates.

This is the tutorial's own advice. Keep your best prompts in the test repository, next to the tests that they helped to write. Give each prompt a short name and a date. When a prompt gives a bad result, fix it in the file, not only in the chat. Then the whole team gets the fix.

</Layman>
<Bangla>

**User story থেকে test case.** Story-টা `<requirement>` ট্যাগে রাখুন। নির্দিষ্ট কলামসহ একটা টেবিলে boundary value আর negative case চান: ID, step, data, expected result। আপনার নিজের suite থেকে 3টা ভালো কেস উদাহরণ হিসেবে দিন। তাহলে মডেল আপনার ধরন অনুসরণ করে <Cite n={2} />।

**এক ধাঁচের bug report.** আপনার bug template আর একটা ভালো রিপোর্ট উদাহরণ হিসেবে দিন। তারপর exploratory session-এর কাঁচা নোট পেস্ট করুন। প্রতিটা সমস্যার জন্য একটা করে রিপোর্ট চান। ধাপগুলো সংখ্যা দিয়ে চান, কারণ ধাপের ক্রম গুরুত্বপূর্ণ <Cite n={2} />।

**Test plan-এ দ্বিতীয় চোখ।** Plan-টা পেস্ট করে জিজ্ঞেস করুন কোন ঝুঁকি বাদ পড়েছে। "not enough information" উত্তরের অনুমতি দিন <Cite n={4} />। তাহলে মডেল এমন ফাঁক বানাবে না যা আসলে নেই।

**Test data.** নির্দিষ্ট field-সহ JSON চান <Cite n={3} />। কোন edge value চান তা লিখে দিন: খালি string, সর্বোচ্চ দৈর্ঘ্য, Unicode নাম, আর leap day-এর তারিখ।

এটা টিউটোরিয়ালের নিজের পরামর্শ। আপনার সেরা prompt-গুলো test repository-তে রাখুন, যে টেস্ট লিখতে সেগুলো সাহায্য করেছে তার পাশে। প্রতিটা prompt-কে একটা ছোট নাম আর তারিখ দিন। কোনো prompt খারাপ ফল দিলে শুধু চ্যাটে নয়, ফাইলেই সেটা ঠিক করুন। তাহলে পুরো টিম সেই সংশোধন পায়।

## Common mistakes

<Voices>
<Technical>

**A one-line ask.** "Write tests for login" gives generic cases. Fix: say the output format and the constraints that you want <Cite n={2} />.

**A list of "don'ts" only.** Fix: say what the model must do in place of what it must not do <Cite n={2} />. "Use only the fields in the schema" works better than "don't invent fields".

**Examples that all look the same.** The model copies their pattern, also the parts that you did not mean. Fix: use diverse examples that cover edge cases <Cite n={2} />.

**Trust in the first answer.** A model can state wrong facts with confidence. Fix: ask the model to find a supporting quote for each claim, and to remove a claim that has no quote <Cite n={4} />. These steps reduce errors but do not remove them, so check every critical fact yourself <Cite n={4} />.

**No way to tell "good" from "bad".** Fix: before you tune a prompt, write clear success criteria and a way to test against them <Cite n={5} />. See [Checking AI Quality (Evals)](/ai-skills/ai-evals/). If an app depends on the prompt, OpenAI suggests pinning it to a specific model snapshot <Cite n={1} />.

</Technical>
<Layman>

**A one-line ask.** "Write tests for login" gives general cases. Fix: say the format and the limits that you want <Cite n={2} />.

**Only "don'ts".** Fix: say what the model must do, not what it must not do <Cite n={2} />. "Use only the fields in the schema" works better than "don't make up fields".

**Examples that all look the same.** The model copies their pattern, even the parts that you did not mean. Fix: use different examples that cover edge cases <Cite n={2} />.

**Trust in the first answer.** A model can say wrong facts in a sure voice. Fix: ask the model to find a quote for each claim, and to remove a claim with no quote <Cite n={4} />. This lowers the errors but does not remove all of them. So check every important fact yourself <Cite n={4} />.

**No way to tell good from bad.** Fix: before you change a prompt, write clear success rules and a way to test them <Cite n={5} />. If an app depends on the prompt, OpenAI suggests that you fix the app to one model snapshot <Cite n={1} />.

</Layman>
<Bangla>

**এক লাইনের অনুরোধ।** "Write tests for login" সাধারণ মানের কেস দেয়। সমাধান: কোন ফরম্যাট আর কোন সীমা চান তা বলুন <Cite n={2} />।

**শুধু "করো না"-র তালিকা।** সমাধান: মডেলকে কী করতে হবে তা বলুন, কী করবে না তা নয় <Cite n={2} />। "don't invent fields"-এর চেয়ে "Use only the fields in the schema" ভালো কাজ করে।

**সব উদাহরণ একই রকম।** মডেল তাদের ধাঁচ নকল করে, এমনকি যে অংশ আপনি বোঝাতে চাননি সেটাও। সমাধান: edge case ঢাকে এমন ভিন্ন ভিন্ন উদাহরণ দিন <Cite n={2} />।

**প্রথম উত্তরেই ভরসা।** মডেল আত্মবিশ্বাসের সাথে ভুল তথ্য বলতে পারে। সমাধান: প্রতিটা দাবির জন্য মডেলকে একটা সমর্থক উদ্ধৃতি খুঁজতে বলুন, আর উদ্ধৃতি না পেলে দাবিটা সরিয়ে দিতে বলুন <Cite n={4} />। এতে ভুল কমে, কিন্তু পুরো দূর হয় না। তাই প্রতিটা গুরুত্বপূর্ণ তথ্য নিজে যাচাই করুন <Cite n={4} />।

**ভালো আর খারাপ আলাদা করার উপায় নেই।** সমাধান: prompt বদলানোর আগে পরিষ্কার success criteria আর সেগুলো টেস্ট করার একটা উপায় লিখুন <Cite n={5} />। কোনো app যদি prompt-এর ওপর নির্ভর করে, OpenAI সেটাকে একটা নির্দিষ্ট model snapshot-এ বেঁধে রাখার পরামর্শ দেয় <Cite n={1} />।

## How to start

<Voices>
<Technical>

1. Pick one task that you do each week, for example test cases for a new story.
2. Write the brief with the six parts: role, context, task, examples, format, and limits.
3. Give the brief to a colleague first. If they are confused, the model will be too <Cite n={2} />.
4. Run it on three real stories. Note what is wrong in each answer, and change one part of the brief at a time. A few rounds are normal <Cite n={3} />.
5. Save the final prompt in your repository, and read [Context Engineering](/ai-skills/context-engineering/) next, so you stop pasting the same background each time.

</Technical>
