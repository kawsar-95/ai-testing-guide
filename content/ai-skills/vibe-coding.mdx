# Vibe Coding

Every QA team has a list of small tools that nobody has time to build: a form that makes test users, a page that shows flaky tests, a fake API for a service that is not ready. Vibe coding lets you build such a tool by describing it to an AI coding tool. Your testing skill is what makes the result safe to use.

<PageMeta />

## In plain words

<Voices>
<Technical>

**Vibe coding** is a way to go from an idea to working software by describing the result you want in plain language. The AI turns the description into an app that you can preview and change <Cite n={1} />. You still lead: the agent writes the code, and you judge if the result does its job <Cite n={1} />.

Several tools support this way of working:

- **Replit Agent** builds apps, designs, and slides from plain language <Cite n={2} />.
- **Lovable** is a full-stack platform that builds and deploys web apps from natural language <Cite n={3} />.
- **Cursor** has an agent that can finish coding tasks, run terminal commands, and edit code <Cite n={4} />.
- **Claude Code** is an AI agent that you use from your terminal <Cite n={5} />.

For a tester, the best first target is an **internal test tool**: something your team uses, with no customers and no production data. A small mistake there costs little, and you learn how the tools behave.

## How it works

<Voices>
<Technical>

Vibe coding is a short loop. You describe, the tool builds, you try it, and you describe the next change:

```text
describe the result --> AI writes and runs code --> preview
        ^                                             |
        |                                     you try the flow
        |                                             |
        +------ "the export button gives an empty file" <---+
```

Three safety nets keep the loop safe:

- **Checkpoints.** Replit Agent creates checkpoints while it works, and you can roll back to any of them <Cite n={2} />. Cursor saves snapshots of the code in an agent session, stored on your machine and separate from Git <Cite n={4} />. Claude Code saves a copy of a file before it edits it, and pressing `Esc` twice rewinds <Cite n={5} />.
- **Version control.** Lovable projects can sync to GitHub, GitLab, or Bitbucket <Cite n={3} />. A commit after each working step gives you a history that the whole team can see.
- **A check to run.** An agent stops when the work looks done. With no check, you become the test suite <Cite n={6} />. Give it a test command or an expected output, and ask for the command and its output as evidence <Cite n={6} />.

Claude Code checkpoints undo file changes only. Changes to a database, an API, or a deployment cannot be rolled back with a checkpoint <Cite n={5} />.

</Technical>

Vibe coding একটা ছোট লুপ। আপনি যা চান তা বর্ণনা করেন। টুলটা সেটা বানায়। আপনি চালিয়ে দেখেন। তারপর পরের পরিবর্তন বর্ণনা করেন, যেমন "the export button gives an empty file"।

- **Version control।** Lovable প্রজেক্ট GitHub, GitLab বা Bitbucket-এর সাথে sync করা যায় <Cite n={3} />। প্রতিটা কাজ-করা ধাপের পর একটা commit আপনাকে এমন একটা ইতিহাস দেয়, যা পুরো দল দেখতে পারে।
- **চালানোর মতো একটা চেক।** কাজ শেষ মনে হলেই এজেন্ট থামে। কোনো চেক না থাকলে আপনিই হয়ে যান test suite <Cite n={6} />। একটা টেস্ট কমান্ড বা প্রত্যাশিত আউটপুট দিন। প্রমাণ হিসেবে কমান্ড আর তার আউটপুট চেয়ে নিন <Cite n={6} />।

Claude Code-এর checkpoint শুধু ফাইলের পরিবর্তন ফেরায়। ডেটাবেস, API বা deployment-এর পরিবর্তন সে ফেরাতে পারে না <Cite n={5} />।

## How a tester uses it

<Voices>
<Technical>

**Internal test tools.** Good first projects: a form that creates test users through your API, a page that reads JUnit XML files and lists the tests that failed most often, or a mock server that returns fixed responses for a service that is not ready yet.

**A failing test first.** When you vibe code a fix or a helper, ask for a test that shows the problem before the fix. The Claude Code docs give a prompt of this kind: write a failing test that reproduces the bug, then fix it <Cite n={6} />.

**A spec before the build.** Talk through the tool first and save the result as `SPEC.md`. Then start a fresh session that builds from it <Cite n={6} />. The spec is also your test plan.

**Testing what others vibe coded.** Teams will ship more AI-built apps, and they need testers. The Replit guide says it plainly: do not only read what the agent says it changed, try the flow <Cite n={1} />.

<Callout type="tip" title="Tutorial advice">
This is the tutorial's own advice. Keep a vibe-coded tool internal until a developer reviews it. Look for three things first: secrets written into the code, input that is not checked, and actions that change shared test data.
</Callout>

</Technical>

**Internal test tool।** প্রথম প্রজেক্ট হিসেবে ভালো: আপনার API দিয়ে টেস্ট ইউজার বানানোর একটা ফর্ম, JUnit XML ফাইল পড়ে সবচেয়ে বেশি ফেইল করা টেস্টের তালিকা দেখানোর একটা পেজ, বা এখনো তৈরি হয়নি এমন একটা সার্ভিসের জন্য নির্দিষ্ট উত্তর দেওয়া একটা mock server।

**আগে একটা ফেইল করা টেস্ট।** কোনো fix বা helper vibe code করার সময়, fix-এর আগে সমস্যাটা দেখায় এমন একটা টেস্ট চান। Claude Code ডকস এমন একটা প্রম্পট দেয়: বাগটা দেখায় এমন একটা ফেইল করা টেস্ট লেখো, তারপর ঠিক করো <Cite n={6} />।

**বানানোর আগে একটা spec।** আগে টুলটা নিয়ে আলোচনা করুন, ফলাফল `SPEC.md` হিসেবে রাখুন। তারপর একটা নতুন session শুরু করুন যা সেখান থেকে বানায় <Cite n={6} />। Spec-টাই আপনার test plan।

**অন্যদের vibe code করা জিনিস টেস্ট করা।** দলগুলো AI দিয়ে বানানো আরও অ্যাপ ship করবে, আর তাদের টেস্টার দরকার। Replit গাইড সোজাসুজি বলে: এজেন্ট কী বদলেছে বলে শুধু তা পড়বেন না, flow-টা চালিয়ে দেখুন <Cite n={1} />।

এটা টিউটোরিয়ালের নিজের পরামর্শ। একজন ডেভেলপার রিভিউ না করা পর্যন্ত vibe code করা টুল internal রাখুন। আগে তিনটা জিনিস খুঁজুন: কোডে লেখা secret, যাচাই না করা ইনপুট, আর শেয়ার করা টেস্ট ডেটা বদলায় এমন অ্যাকশন।

## Common mistakes

<Voices>
<Technical>

- **Trusting the summary.** The agent's report of what it changed is not proof. Fix: try the flow yourself <Cite n={1} />.
- **No check to run.** Without one, the agent stops when the work looks done <Cite n={6} />. Fix: give a test command or an expected output, and ask for the output <Cite n={6} />.
- **Checkpoints instead of Git.** Cursor checkpoints are separate from Git <Cite n={4} />. Fix: commit each working step to a repository.
- **Testing against shared systems.** Claude Code checkpoints do not undo database, API, or deployment changes <Cite n={5} />. Fix: point the new tool at a test environment.
- **One giant prompt.** A whole app in one message gives a result that is hard to check. Fix: build one feature at a time, and try each one before the next.

## How to start

<Voices>
<Technical>

1. Pick one small internal tool that would save your team time each week.
2. Write five lines: who uses it, what it shows, what data it reads, what it must never do, and how you will know that it works.
3. Build it with one of the tools above, one feature at a time. Try each feature yourself <Cite n={1} />.
4. Commit after each working step, and keep the spec next to the code.
5. Ask a developer to review it before anyone outside the QA team uses it. To go deeper with Claude Code, read [Prompting](/foundations/prompting/) and [CLAUDE.md](/configure/claude-md/).

</Technical>
