# GitHub Actions

The Claude Code GitHub Action brings Claude into your pull requests and issues. This page shows how to set it up, how a tester asks `@claude` for missing tests, how to review the tests in every PR automatically, how to triage a flaky test with structured output, and how to keep cost and risk under control.

<PageMeta />

## What the Action does

<Voices>
<Technical>

Claude Code GitHub Actions is a GitHub Action, `anthropics/claude-code-action`, that runs Claude Code inside your repository's workflows. <Cite n={1} />

- Mention `@claude` in a pull request or issue comment, and Claude analyzes code, implements changes, and pushes commits. <Cite n={1} />
- Give the Action a prompt, and it runs on any GitHub event, for example to turn issues into pull requests. <Cite n={1} />
- The current major version is `v1`. Workflows use `anthropics/claude-code-action@v1`. <Cite n={1} /> <Cite n={2} />

Several products share the Claude Code name. Code Review gives automatic review on every pull request without a workflow file. This page covers the workflow integration only. <Cite n={1} />

### Two modes

The Action detects the mode from your workflow: <Cite n={1} />

| Mode | When | Where the result goes |
|---|---|---|
| Interactive | The workflow has no `prompt` input. Claude waits for the trigger phrase, `@claude` by default, in a comment, a review, or a new issue. | A comment on the issue or PR <Cite n={1} /> |
| Automation | The workflow has a `prompt` input. Claude runs without a mention. | The workflow run log, by default <Cite n={1} /> |

The [Headless & CI](/automate/headless/) page covers `claude -p`, which you can run in any CI system without this Action.

</Technical>

## Set it up

<Voices>
<Technical>

You need admin access to the repository for both setup paths. <Cite n={1} />

### Quick setup

Open `claude` in the repository and run `/install-github-app`. <Cite n={1} />

- The command needs the GitHub CLI, signed in with `gh auth login`. <Cite n={1} />
- It works only with github.com repositories. <Cite n={1} />
- Claude Code installs the Claude GitHub App and saves the credential as a repository secret: `ANTHROPIC_API_KEY` for an API key, or `CLAUDE_CODE_OAUTH_TOKEN` for a subscription token. <Cite n={1} />
- Claude Code then pushes a branch with the workflow files and opens GitHub in your browser with a pull request ready to create. Create and merge that pull request, and `@claude` works in the repository. <Cite n={1} />

### Manual setup

1. Install the [Claude GitHub App](https://github.com/apps/claude) on the repository. <Cite n={1} />
2. Add a secret: `ANTHROPIC_API_KEY` with a key from the Claude Console, or `CLAUDE_CODE_OAUTH_TOKEN` from `claude setup-token`. The token needs a Pro, Max, Team, or Enterprise plan. <Cite n={1} />
3. Copy `examples/claude.yml` from the Action's repository into `.github/workflows/`. <Cite n={1} />

In the workflow, pass the secret to the matching input: `anthropic_api_key` or `claude_code_oauth_token`. <Cite n={1} />

- The Action uses three permissions of the app: Contents, Issues, and Pull requests, each with read and write. <Cite n={1} />
- The app's full permission set is larger, because other Claude features share it. GitHub does not let you accept a subset. <Cite n={1} />
- For a secret that many repositories share, the docs advise a Console API key, because an OAuth token is tied to the subscription of one person. <Cite n={1} />
- Workload identity federation avoids a stored secret. It needs the `id-token: write` permission. <Cite n={1} />

</Technical>

## Respond to @claude in issues and PRs

<Voices>
<Technical>

The docs show this workflow for `@claude` mentions: <Cite n={1} />

```yaml
name: Claude Code
on:
  issue_comment:
    types: [created]
  pull_request_review_comment:
    types: [created]
jobs:
  claude:
    if: contains(github.event.comment.body, '@claude')
    runs-on: ubuntu-latest
    permissions:
      contents: write
      pull-requests: write
      issues: write
      id-token: write
      actions: read
    steps:
      - uses: actions/checkout@v6
        with:
          fetch-depth: 1
      - uses: anthropics/claude-code-action@v1
        with:
          anthropic_api_key: ${{ secrets.ANTHROPIC_API_KEY }}
```

- `id-token: write` is required for the default GitHub App authentication. <Cite n={1} />
- `actions: read` lets Claude read CI results on PRs. <Cite n={1} />
- `actions/checkout` gives Claude a local copy of the repository. <Cite n={1} />

Claude replies in a comment on the same issue or PR and updates it as it works. <Cite n={1} />

### Who can trigger a run

- On issue and PR events, the user who triggers the run must have write access to the repository. <Cite n={1} />
- The Action rejects a bot actor unless you list it in `allowed_bots`. <Cite n={1} />
- `allowed_non_write_users` bypasses the write-access check. To use it, you also pass your own `github_token` input. <Cite n={1} /> The security docs mark it as risky and advise it only for workflows with very limited permissions. <Cite n={3} />

### QA example: ask for missing tests

<Callout type="tip" title="Example">

These comments are example requests from a tester. The docs show the same form, such as `@claude fix the TypeError in the user dashboard component`. <Cite n={1} />

</Callout>

```text
@claude add unit tests for the changes in this PR. Follow the test conventions in CLAUDE.md. Cover the empty, maximum, and invalid inputs.
@claude explain why the checkout test failed in the last CI run and propose a fix.
```

- Put your test standards in `CLAUDE.md`. Claude follows its guidelines when it creates PRs and answers requests. <Cite n={1} /> See [CLAUDE.md & Memory](/configure/claude-md/).
- By default, Claude does not create a pull request. It commits to a new branch and gives a link to the PR creation page. A person creates the PR. <Cite n={3} />

## Review pull requests automatically

<Voices>
<Technical>

The docs show this workflow. It installs the `code-review` plugin and runs its skill when a PR is opened, updated, reopened, or marked ready for review: <Cite n={1} />

```yaml
name: Code Review
on:
  pull_request:
    types: [opened, synchronize, ready_for_review, reopened]
jobs:
  review:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      pull-requests: read
      issues: read
      id-token: write
    steps:
      - uses: actions/checkout@v6
        with:
          fetch-depth: 1
      - uses: anthropics/claude-code-action@v1
        with:
          anthropic_api_key: ${{ secrets.ANTHROPIC_API_KEY }}
          plugin_marketplaces: "https://github.com/anthropics/claude-code.git"
          plugins: "code-review@claude-code-plugins"
          prompt: "/code-review:code-review --comment ${{ github.repository }}/pull/${{ github.event.pull_request.number }}"
          claude_args: '--allowedTools "mcp__github_inline_comment__create_inline_comment"'
```

- With `--comment`, Claude posts the review on the PR: an inline comment for each issue, or one summary comment if it finds none. Without it, the findings stay in the run log. <Cite n={1} />
- Keep the `claude_args` line. The Action starts the MCP server for inline comments only when `--allowedTools` in `claude_args` names it. <Cite n={1} />
- Claude skips draft and closed PRs, PRs that it judges do not need a review, and PRs that already have a comment from Claude. <Cite n={1} />
- On public repositories, GitHub withholds secrets from runs that fork PRs trigger. The review runs only on PRs from branches in the same repository. <Cite n={1} />

### Run your own skill as the prompt

The `prompt` input accepts plain text or a skill: <Cite n={1} />

- For a skill in `.claude/skills/`, run `actions/checkout` before the Action step, then pass `/skill-name` as the `prompt`. <Cite n={1} />
- For a skill in a plugin, install it with `plugin_marketplaces` and `plugins`, then pass `/plugin-name:skill-name`. <Cite n={1} />
- For a plain-text prompt, Claude has no shell or GitHub API access until you grant tools with `--allowedTools` in `claude_args` or a `permissions.allow` rule in the `settings` input. A skill can use the tools that its `allowed-tools` frontmatter grants. <Cite n={1} />

### QA example: review the tests in every PR

<Callout type="tip" title="Example">

This workflow is the tutorial's example. It replaces the plugin in the docs workflow with a repository skill, `/review-tests`, that you write yourself. It uses only the inputs and arguments that the docs show. <Cite n={1} />

</Callout>

```yaml
name: Test Review
on:
  pull_request:
    types: [opened, synchronize, ready_for_review, reopened]
jobs:
  review-tests:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      pull-requests: read
      issues: read
      id-token: write
    steps:
      - uses: actions/checkout@v6
        with:
          fetch-depth: 1
      - uses: anthropics/claude-code-action@v1
        with:
          anthropic_api_key: ${{ secrets.ANTHROPIC_API_KEY }}
          prompt: "/review-tests"
          claude_args: |
            --max-turns 10
            --allowedTools "mcp__github_inline_comment__create_inline_comment"
```

Write the `review-tests` skill to check three things for each changed source file: is there a test, are the assertions strong enough to fail on a real bug, and does the test depend on timing or shared data that makes it flaky. The [Skills & Commands](/extend/skills/) page shows how to write a skill and its `allowed-tools`.

</Technical>

Tutorial-এর example-এ আপনার নিজের লেখা `/review-tests` skill চলে। Skill-টি প্রতিটি পরিবর্তিত source file-এর জন্য তিনটি জিনিস দেখে: test আছে কি না, assertion আসল bug-এ fail করার মতো শক্ত কি না, আর test timing বা shared data-র ওপর নির্ভর করে flaky হয় কি না।

</Bangla>

## Structured results and scheduled runs

<Voices>
<Technical>

### Triage a flaky test

Add `--json-schema` to `claude_args`, and the Action returns validated JSON in the step output `structured_output`, as one JSON string. <Cite n={4} /> The Action's usage docs show this flaky-test example: <Cite n={4} />

```yaml
- name: Detect flaky tests
  id: analyze
  uses: anthropics/claude-code-action@v1
  with:
    anthropic_api_key: ${{ secrets.ANTHROPIC_API_KEY }}
    prompt: |
      Check the CI logs and determine if this is a flaky test.
      Return: is_flaky (boolean), confidence (0-1), summary (string)
    claude_args: |
      --json-schema '{"type":"object","properties":{"is_flaky":{"type":"boolean"},"confidence":{"type":"number"},"summary":{"type":"string"}},"required":["is_flaky"]}'

- name: Retry if flaky
  if: fromJSON(steps.analyze.outputs.structured_output).is_flaky == true
  run: gh workflow run CI
```

A retry hides a flaky test. It does not fix it. Also record the `summary` in a flaky-test ticket, so the team fixes the cause.

### Run on a schedule

With a `prompt` input, the Action runs on any event, including a cron schedule. <Cite n={1} />

- GitHub runs scheduled workflows only from the default branch. <Cite n={1} />
- In public repositories, GitHub disables a schedule after 60 days without repository activity. <Cite n={1} />
- The docs example runs at `"0 9 * * *"` and gives Claude two GitHub MCP tools with `--allowedTools`. <Cite n={1} />

Example: a nightly prompt such as `Summarize yesterday's failed test runs and list the tests that failed more than once`, with only the tools that the prompt needs.

</Technical>

## Control cost and risk

<Voices>
<Technical>

<Callout type="danger" title="Never commit keys">

Never commit API keys or OAuth tokens to the repository. Store them as GitHub Secrets, for example `anthropic_api_key: ${{ secrets.ANTHROPIC_API_KEY }}`. Give the workflow only the permissions it needs, and review Claude's changes before you merge. <Cite n={1} />

</Callout>

### Cost

Each run uses GitHub Actions minutes and API tokens. If you authenticate with an OAuth token, runs use your Claude subscription instead of API billing. <Cite n={1} /> The docs list these controls: <Cite n={1} />

- Write specific `@claude` requests, so Claude needs fewer turns.
- Use issue templates to give context up front.
- Keep `CLAUDE.md` short, because Claude reads it on every run.
- Set `--max-turns` in `claude_args`.
- Set workflow-level timeouts.
- Use GitHub's concurrency controls to limit parallel runs.

### Risk

- On pull requests, the Action restores `.claude/`, `.mcp.json`, `.claude.json`, `.gitmodules`, `.ripgreprc`, `CLAUDE.md`, `CLAUDE.local.md`, and `.husky/` from the base branch before Claude starts. <Cite n={3} /> A PR cannot change those files to steer the run.
- `pull_request_target` and `workflow_run` run with the base repository's secrets. If you check out the PR head into the workspace before the Action, Claude works on that checkout. <Cite n={3} /> Do not do this for untrusted PRs.
- Hidden text in comments can carry instructions. The Action strips HTML comments, invisible characters, image alt text, hidden HTML attributes, and HTML entities, but new bypass techniques may appear. <Cite n={3} />
- On public repositories, `include_comments_by_actor` limits which users' comments go to Claude. <Cite n={3} />
- Claude's commits are unsigned by default. <Cite n={3} /> `show_full_output` is off by default for security reasons. Keep it off. <Cite n={3} />

</Technical>
<Layman>

Never commit API keys or OAuth tokens to the repository. Keep them in GitHub Secrets. Give the workflow only the permissions that it needs, and review Claude's changes before you merge. <Cite n={1} />

Each run uses GitHub Actions minutes and API tokens. With an OAuth token, runs use your Claude subscription, not API billing. To use less, write specific `@claude` requests, use issue templates, keep `CLAUDE.md` short, set `--max-turns`, set workflow timeouts, and limit parallel runs with GitHub's concurrency controls. <Cite n={1} />

</Layman>
<Bangla>

API key বা OAuth token কখনো repository-তে commit করবেন না। এগুলো GitHub Secrets-এ রাখুন। Workflow-কে শুধু দরকারি permission দিন, আর merge করার আগে Claude-এর পরিবর্তন review করুন। <Cite n={1} />

## Upgrade from beta and troubleshoot

<Voices>
<Technical>

To move a workflow from `@beta` to `@v1`: <Cite n={1} />

1. Change `@beta` to `@v1` in the `uses` line.
2. Remove the `mode` input. The Action detects the mode.
3. Replace `direct_prompt` with `prompt`.
4. Move `max_turns` and `model` into `claude_args`. Replace `custom_instructions` with `--append-system-prompt`.

The usage docs also list `allowed_tools` as deprecated. Use `--allowedTools` in `claude_args`. <Cite n={4} /> A tutorial that shows `direct_prompt:` or `allowed_tools:` inputs is out of date.

If Claude does not respond to `@claude`: <Cite n={1} />

- Check that the GitHub App is installed and workflows are on for the repository.
- Check that the API key or OAuth token is in the repository secrets.
- Write `@claude` as a complete word, not `/claude` or `@claude-bot`.
- Check that the user who comments has write access.

To use Amazon Bedrock, Google Cloud's Agent Platform, or Microsoft Foundry, set `use_bedrock`, `use_vertex`, or `use_foundry` to `"true"`, and authenticate through OIDC. <Cite n={1} />

</Technical>
