# Text Processing

This stage covers how text moves between commands and the small tools that search and reshape it. A tester needs it because logs, test reports, and CI output are plain text. A filter is a program that accepts text, transforms it, and prints the result. <Cite n={1} />

<PageMeta />

## Text Processing

Linux tools mostly handle plain text. A filter is a program that takes textual data and transforms it in one particular way. <Cite n={1} /> Each tool does one small job, and you join the tools to do a larger job. <Cite n={1} />

This stage has three groups of topics:

- How text moves: streams, redirects, pipes, and `tee`.
- Tools that pick lines and columns: `grep`, `awk`, and `cut`.
- Tools that order, count, and reshape lines: `sort`, `uniq`, and the commands that follow them.

The examples on this page create their own sample files. Run them in an empty scratch directory, as the first example does.

```bash
mkdir -p /tmp/text-demo && cd /tmp/text-demo || exit 1
printf '%s\n' 'ok login' 'fail login' 'ok search' 'fail login' > results.txt
grep fail results.txt | sort | uniq -c
```

```text
      2 fail login
```

<Callout type="tip" title="Why it matters for testing">
Tutorial's own advice: test logs, CSV exports, and API responses are all text. If you know a few filters, you can answer "how many tests failed, and which ones?" in one line, without a spreadsheet.
</Callout>

## Stdout, Stdin, and Stderr

A stream is a channel that carries bytes in one direction. Every program starts with three streams: one for input, one for normal output, and one for error and diagnostic messages. <Cite n={3} /> Their short names are `stdin`, `stdout`, and `stderr`. <Cite n={3} />

A file descriptor is a small number that stands for an open file or channel. The three streams use the numbers 0, 1, and 2. <Cite n={3} />

| Stream | Descriptor | Carries |
|---|---|---|
| `stdin` | 0 | Data fed into the program |
| `stdout` | 1 | Normal results of the program |
| `stderr` | 2 | Error messages |

Usually the terminal is behind all three streams. The shell can connect them to files or to other programs instead. <Cite n={2} /> <Cite n={4} /> The `stderr` stream is unbuffered. The `stdout` stream is line-buffered when it points to a terminal, which means it waits for a newline before it writes. <Cite n={3} />

In the next example, `ls` gets one good path and one bad path. The listing goes to the file. The error message still appears on the screen, because it uses `stderr`.

```bash
ls /does-not-exist /tmp > listing.txt
echo "exit status: $?"
```

```text
ls: cannot access '/does-not-exist': No such file or directory
exit status: 2
```

<Callout type="tip" title="Why it matters for testing">
Tutorial's own advice: a test tool can print failures on `stderr` and a summary on `stdout`. If you capture only one stream, you can miss the failures. Learn which stream your tool uses before you build a log filter.
</Callout>

## Redirects

A redirect changes where a command reads from or writes to. The shell sets it up before the command runs. <Cite n={5} /> The shell handles redirects from left to right. <Cite n={5} />

| Operator | Effect |
|---|---|
| `> file` | Send `stdout` to `file`. The shell creates the file, or empties it if it exists. <Cite n={5} /> |
| `>> file` | Append `stdout` to `file`. The shell creates the file if it is missing. <Cite n={5} /> |
| `< file` | Read `stdin` from `file`. <Cite n={5} /> |
| `2> file` | Send `stderr` (descriptor 2) to `file`. <Cite n={5} /> |
| `2>&1` | Make `stderr` a copy of `stdout`. <Cite n={5} /> |
| `&> file` | Send both streams to `file`. This is a Bash form. <Cite n={5} /> |

Order matters. `cmd > out.txt 2>&1` sends both streams to the file. `cmd 2>&1 > out.txt` sends only `stdout` to the file, because `stderr` was copied first. <Cite n={5} /> The POSIX text has no `&>`, so use `> file 2>&1` in scripts that run under `sh`. <Cite n={6} /> The special file `/dev/null` discards all data that you write to it. <Cite n={7} />

```bash
printf '%s\n' 'alpha' 'beta' > names.txt    # create or replace
echo 'gamma' >> names.txt                   # append
sort < names.txt                            # read stdin from the file
ls /no/such/dir 2> errors.txt               # keep only the error
ls /no/such/dir > all.txt 2>&1              # keep both streams
ls /no/such/dir 2> /dev/null                # hide the error
```

<Callout type="danger" title="Data loss: > empties the file first">
The shell empties the target file before the command starts. <Cite n={2} /> <Cite n={5} /> So `sort data.txt > data.txt` leaves `data.txt` empty, and the data is gone. Write to a new file, or use `>>` to add. In Bash, `set -C` stops `>` from replacing an existing file, and `>|` overrides it. <Cite n={8} />
</Callout>

<Callout type="tip" title="Why it matters for testing">
Tutorial's own advice: send test output to a new file for each run, for example `run-1.log`. Then an old log is never lost by mistake.
</Callout>

## Pipes

A pipe connects the `stdout` of one command to the `stdin` of the next command. You write it as `|`. <Cite n={9} /> A pipeline is a chain of commands joined by pipes. Each command reads the output of the one before it. <Cite n={9} />

The kernel provides the pipe as a one-way channel with a write end and a read end. <Cite n={10} /> The shell connects the pipe before it applies the redirects of the first command. <Cite n={9} />

Only `stdout` goes through the pipe. The `stderr` stream still goes to the terminal. In Bash, `|&` also sends `stderr` into the pipe. <Cite n={9} />

A pipeline returns the status of its last command. <Cite n={9} /> If the option `pipefail` is set, the status is that of the last command that failed, or 0 if all commands succeeded. <Cite n={8} /> Bash and the 2024 POSIX standard both define this option. <Cite n={6} /> Check that the shell of your CI runner supports it.

```bash
printf '%s\n' 'b 2' 'a 1' 'b 3' > pairs.txt
sort pairs.txt | cut -d ' ' -f1 | uniq      # prints a, then b
false | true; echo "$?"                      # prints 0
( set -o pipefail; false | true; echo "$?" ) # prints 1
```

<Callout type="tip" title="Why it matters for testing">
Tutorial's own advice: in a pipeline such as `pytest | tee test.log`, the status comes from `tee`, so a failing test run can look green. Turn on `pipefail` in CI scripts.
</Callout>

## Tee

The `tee` command copies `stdin` to each file you name, and also to `stdout`. <Cite n={11} /> You use it when you want to see the data and also save a copy. It creates a file that does not exist. It overwrites a file that exists, unless you use `-a`. <Cite n={11} />

```bash
printf '%s\n' 'run 1: ok' 'run 2: fail' | tee run.log
printf '%s\n' 'run 3: ok' | tee -a run.log
```

```text
run 1: ok
run 2: fail
run 3: ok
```

The first command replaces `run.log` and prints the two lines. The second command adds a third line and prints it.

`tee` also helps with root-owned files. Your shell sets up redirects, not `sudo`. <Cite n={5} /> So `sudo echo text > file` fails on a protected file. Run `tee` under `sudo` instead: `echo text | sudo tee -a file`.

GNU option: `-p` (long form `--output-error`) controls what `tee` does when a write fails. Other versions of `tee` may not have it. <Cite n={11} />

<Callout type="danger" title="Data loss: tee without -a overwrites">
Each `tee file` replaces the old content of `file`. <Cite n={11} /> Add `-a` to keep the old content. Tutorial's own advice: never give `tee` the name of a file that an earlier command in the same pipeline still reads.
</Callout>

<Callout type="tip" title="Why it matters for testing">
Tutorial's own advice: `make test 2>&1 | tee test.log` shows the output live and also keeps a log for the CI job. Turn on `pipefail` so a failed `make` still fails the job.
</Callout>

## grep

The `grep` command prints the lines that match a pattern. <Cite n={12} /> A regular expression is a pattern language that describes a set of strings. <Cite n={13} /> By default `grep` reads basic regular expressions. Use `-E` for extended ones, and `-F` to match fixed text. <Cite n={12} /> Quote the pattern, so that the shell does not change it. <Cite n={12} />

| Option | Effect |
|---|---|
| `-i` | Ignore case. <Cite n={12} /> |
| `-v` | Select the lines that do not match. <Cite n={12} /> |
| `-n` | Show the line number. <Cite n={12} /> |
| `-c` | Count the matching lines. <Cite n={12} /> |
| `-o` | Print only the matching part. <Cite n={12} /> |
| `-r` | Search all files under a directory. <Cite n={12} /> |
| `-q` | Print nothing. Use the exit status only. <Cite n={12} /> |
| `-A`, `-B`, `-C` | Add lines after, before, or around each match. <Cite n={12} /> |

`grep` returns 0 when it selects a line, 1 when it selects none, and 2 on an error. <Cite n={12} />

```bash
printf '%s\n' 'INFO start' 'ERROR db down' 'WARN slow' 'ERROR disk full' > app.log
grep -n ERROR app.log                       # 2:ERROR db down, 4:ERROR disk full
grep -c ERROR app.log                       # 2
grep -E 'WARN|ERROR' app.log                # three lines
grep -v INFO app.log                        # all lines except the INFO line
grep -q 'db down' app.log && echo found
```

GNU option: `-P` (Perl-style patterns) and `-H` are GNU options. Other versions of `grep` may lack them. <Cite n={12} />

<Callout type="tip" title="Why it matters for testing">
Tutorial's own advice: in a script, exit status 1 means "no match", not "failure". Treat only status 2 as an error. `grep -q ERROR app.log && exit 1` fails a CI step when the log has an error.
</Callout>

## awk

The `awk` language runs rules of the form `pattern { action }`. For each input line, awk checks the pattern and runs the action if it matches. <Cite n={14} /> A line is a record. <Cite n={15} /> A field is one piece of a record. By default, whitespace separates fields. <Cite n={16} />

You name a field with `$` and a number. `$1` is the first field, `$0` is the whole record, `NF` is the number of fields, and `$NF` is the last field. <Cite n={16} /> `NR` counts the records read so far. <Cite n={15} /> The variable `FS` holds the field separator. <Cite n={17} /> Option `-F` sets it, and `-v name=value` sets any variable. <Cite n={21} />

A pattern can be a regular expression between slashes, or a comparison. <Cite n={18} /> Input that looks like a number compares as a number, but a quoted string compares as text. <Cite n={19} /> A `BEGIN` or `END` rule runs before or after the input. <Cite n={20} />

```bash
printf '%s\n' 'login 120 ok' 'search 340 fail' 'login 95 ok' 'checkout 410 fail' > times.txt
awk '{ print $1 }' times.txt                          # first field
awk '$3 == "fail" { print $1, $2 }' times.txt         # failed rows
awk '$2 > 300' times.txt                              # slow rows
awk -v limit=300 '$2 > limit { print NR ": " $0 }' times.txt
awk '{ sum += $2 } END { print sum }' times.txt       # 965
```

To pass a shell variable into awk, use `-v`, as in the fourth line. This is easier than quoting the value into the program text. <Cite n={22} /> The examples use only basic awk features. The gawk manual also describes extras that other awk programs may lack.

<Callout type="tip" title="Why it matters for testing">
Tutorial's own advice: use awk when a log has aligned columns, such as a response time. It can filter by a number and sum a column in one command.
</Callout>

## cut

The `cut` command prints selected parts of each line. <Cite n={23} /> A delimiter is the character that separates fields. With `-f`, `cut` splits lines at a delimiter. The default delimiter is TAB, and `-d` sets another one. <Cite n={23} /> Fields, characters, and bytes are numbered from 1. <Cite n={23} />

A list names what to keep: `2`, `1,3`, `2-4`, `3-`, or `-2`. <Cite n={23} /> `cut` always prints the selected parts in the order of the input. So `-f3,1` prints field 1 first. <Cite n={23} /> A line without a delimiter is printed whole, unless you add `-s`. <Cite n={23} />

```bash
printf '%s\n' 'id,name,status' '1,login,pass' '2,search,fail' > cases.csv
cut -d, -f2 cases.csv                  # name, login, search
cut -d, -f1,3 cases.csv                # id,status / 1,pass / 2,fail
cut -d, -f2 --complement cases.csv     # all fields except the second
cut -c1-3 cases.csv                    # the first three characters
```

GNU option: `--complement` is a GNU extension. Other versions of `cut` may lack it. <Cite n={23} />

`cut` splits at every delimiter. It does not know about CSV quotes, so a quoted comma breaks the fields. For columns that are aligned with runs of blanks, or for a new field order, use awk. <Cite n={23} />

<Callout type="tip" title="Why it matters for testing">
Tutorial's own advice: use `cut -d, -f2` to take one column from a simple CSV of test data. For a CSV with quoted values, use a real CSV parser.
</Callout>

## sort

The `sort` command writes the lines of its input in sorted order. <Cite n={24} /> By default it compares whole lines, and the locale sets the order of characters. <Cite n={24} /> Set `LC_ALL=C` if the locale gives an order that you do not expect. <Cite n={24} />

| Option | Effect |
|---|---|
| `-n` | Compare numbers, not text. <Cite n={24} /> |
| `-r` | Reverse the order. <Cite n={24} /> |
| `-u` | Keep only the first of equal lines. <Cite n={24} /> |
| `-k 2,2` | Sort by the second field only. <Cite n={24} /> |
| `-t :` | Use `:` as the field separator. <Cite n={24} /> |
| `-c` | Check whether the input is sorted. Exit with status 1 if it is not. <Cite n={24} /> |

Write `-k 2,2n`, not `-k 2n`. The second form uses the rest of the line as the key. <Cite n={24} />

```bash
printf '%s\n' 'checkout 410' 'login 95' 'search 340' 'login 120' > timings.txt
sort timings.txt                  # text order: checkout, login 120, login 95, search
sort -k2,2n timings.txt           # number order: 95, 120, 340, 410
sort -k2,2nr timings.txt          # slowest first
sort -o sorted.txt timings.txt    # write the result to another file
```

GNU option: `-h` (human numbers such as 2K) and `-V` (version numbers) are GNU extras. Other versions of `sort` may lack them. <Cite n={24} />

<Callout type="danger" title="Data loss: sort -o to the input file">
`sort data.txt > data.txt` empties the file. <Cite n={5} /> The option `-o` can name the input file, because `sort` reads all input first. But a crash during the write can lose data, so output to a different file instead. <Cite n={24} />
</Callout>

<Callout type="tip" title="Why it matters for testing">
Tutorial's own advice: sort response times with `sort -n` to find the slowest ones. Sort two test result lists, and then compare them with `diff`.
</Callout>

## uniq

The `uniq` command removes repeated lines, but only lines that are next to each other. <Cite n={25} /> It does not find repeated lines that are far apart. So sort the input first, or use `sort -u`. <Cite n={25} />

| Option | Effect |
|---|---|
| `-c` | Put the number of occurrences before each line. <Cite n={25} /> |
| `-d` | Show each repeated line one time, and show no other line. <Cite n={25} /> |
| `-u` | Print only the lines that are not repeated. <Cite n={25} /> |
| `-i` | Ignore differences in case. <Cite n={25} /> |
| `-f N` | Skip the first N fields before the comparison. <Cite n={25} /> |

For plain lines, `sort -u` and `sort | uniq` give the same result. This is not true with every sort option. <Cite n={24} /> For example, `sort -n -u` checks only the leading number of each line. <Cite n={24} />

```bash
printf '%s\n' 'timeout' 'ok' 'timeout' 'ok' 'ok' 'error' > events.txt
uniq events.txt                           # nothing is removed: no equal neighbours
sort events.txt | uniq -c                 # 1 error, 3 ok, 2 timeout
sort events.txt | uniq -c | sort -rn      # most frequent first
sort events.txt | uniq -d                 # ok, timeout
```

<Callout type="tip" title="Why it matters for testing">
Tutorial's own advice: `sort | uniq -c | sort -rn` counts the most common error lines in a log. It shows which failure to fix first, and it can show a flaky test that fails again and again.
</Callout>

## wc

The `wc` command counts lines, words, and bytes. It reads the files you name, or `stdin` if you name none. <Cite n={26} /> A word is a run of non-blank characters. <Cite n={26} /> A line is counted by its newline character, so a last line without a newline is not counted. <Cite n={26} />

| Option | Counts |
|---|---|
| `-l` | Lines <Cite n={26} /> |
| `-w` | Words <Cite n={26} /> |
| `-c` | Bytes <Cite n={26} /> |
| `-m` | Characters, as the current locale reads them <Cite n={26} /> |
| `-L` | The width of the longest line <Cite n={26} /> |

The locale is the language and encoding setting of your shell. Bytes and characters can differ, because one character can use several bytes. In UTF-8, an accented letter takes two bytes. <Cite n={42} /> The output order is always lines, words, characters, bytes, longest line. <Cite n={26} />

```bash
printf '%s\n' 'login ok' 'search failed' 'logout ok' > run.log
wc run.log                         # 3 lines, 6 words, 33 bytes, then the name
wc -l < run.log                    # 3 (no file name: the input came from stdin)
grep failed run.log | wc -l        # 1
printf 'caf\303\251\n' | wc -c     # 6 bytes
printf 'caf\303\251\n' | wc -m     # 5 characters in a UTF-8 locale
```

GNU option: `--total=only` prints only the grand total for several files. `--total` is a GNU extension, so other versions of `wc` may lack it. <Cite n={26} />

<Callout type="tip" title="Why it matters for testing">
Tutorial's own advice: assert a count in a CI script, for example `[ "$(wc -l < results.txt)" -eq 3 ]`. A test that must produce three result lines then fails when it produces two. Also count matches with `grep ... | wc -l`. <Cite n={42} />
</Callout>

## head

The `head` command prints the first part of its input. The default is 10 lines. <Cite n={27} /> If you name several files, it prints a header line `==> name <==` before each one. <Cite n={27} /> Use `-q` to hide the headers and `-v` to always show them. <Cite n={27} />

`-n N` sets the number of lines. `-c N` sets the number of bytes. <Cite n={27} /> Both accept size suffixes, such as `K` for 1024 bytes. <Cite n={27} />

```bash
seq 15 > nums.txt
head nums.txt                   # lines 1 to 10
head -n 3 nums.txt              # 1, 2, 3
head -n -12 nums.txt            # all but the last 12 lines: 1, 2, 3
head -c 5 nums.txt              # the first 5 bytes
printf '%s\n' a b > letters.txt
head -n 1 nums.txt letters.txt  # one line of each file, with headers
```

GNU option: a minus sign before the number, as in `head -n -12`, prints all lines except the last 12. <Cite n={27} /> Other versions of `head` may reject it.

<Callout type="tip" title="Why it matters for testing">
Tutorial's own advice: use `head -n 1 results.csv` to check the header row of an export. Use `sort -k2,2nr timings.txt | head -n 3` to list the three slowest steps.
</Callout>

## tail

The `tail` command prints the last part of its input. The default is 10 lines. <Cite n={28} /> `-n N` sets the line count. <Cite n={28} /> A plus sign, as in `-n +2`, starts at line 2 and prints the rest. So `tail -n +2` removes a header line. <Cite n={28} />

With `-f`, `tail` keeps reading and prints new lines as the file grows. It never ends on its own. You must stop it yourself, for example with Ctrl-C. <Cite n={28} /> Log rotation is the case where a tool renames a full log and starts a new file with the same name. <Cite n={43} /> Plain `-f` follows the old file and misses the new one. `-F` follows the name and opens the file again. <Cite n={28} />

```bash
seq 15 > nums.txt
tail -n 2 nums.txt                        # 14, 15
printf '%s\n' 'id,name' '1,login' '2,search' > cases.csv
tail -n +2 cases.csv                      # the rows without the header
tail -F app.log                           # follow a log by name (Ctrl-C stops)
journalctl -f                             # follow the systemd journal
```

Many services write to the journal and not to a file in `/var/log`. For those, `journalctl -f` shows the newest entries and follows new ones. <Cite n={41} />

GNU option: `-F` and `--pid` are GNU forms. Other versions of `tail` may lack them. <Cite n={28} />

<Callout type="tip" title="Why it matters for testing">
Tutorial's own advice: a CI step that runs `tail -f` never ends and hangs the job. Add `--pid`, as in `./run-tests.sh > test.log 2>&1 &` and then `tail --pid=$! -f test.log`. `tail` then stops when the process ends. <Cite n={28} />
</Callout>

## nl

The `nl` command writes its input with line numbers. <Cite n={29} /> By default it numbers only non-empty lines. A line that gets no number does not use up a number. <Cite n={29} /> A plain text file counts as one section, because `nl` splits pages only at special marker lines. <Cite n={29} />

| Option | Effect |
|---|---|
| `-b a` | Number all lines. <Cite n={29} /> |
| `-b pREGEX` | Number only lines that match a basic regular expression. <Cite n={29} /> |
| `-w N` | Use N characters for the number. The default is 6. <Cite n={29} /> |
| `-s STR` | Put STR between the number and the text. The default is TAB. <Cite n={29} /> |
| `-v N` | Start at N. <Cite n={29} /> |
| `-i N` | Add N for each numbered line. <Cite n={29} /> |

```bash
printf '%s\n' alpha '' beta '' '' gamma > t.txt
nl t.txt                  # numbers 1 to 3: alpha, beta, gamma
nl -ba t.txt              # numbers 1 to 6: all lines, also the empty ones
nl -ba -w3 -s': ' t.txt   # "  1: alpha"
nl -b pb t.txt            # only the line that contains "b" gets a number
```

GNU option: the long names, such as `--body-numbering=a`, are GNU forms. Other versions of `nl` may have only the short options. <Cite n={29} />

<Callout type="tip" title="Why it matters for testing">
Tutorial's own advice: number a log excerpt with `nl -ba` before you paste it into a bug report. Then your team can say "see line 42" and everyone looks at the same line.
</Callout>

## paste

The `paste` command joins the lines of several files side by side. Line 1 of each file becomes one output line, and a delimiter separates the parts. The default delimiter is TAB. <Cite n={30} /> If one file is shorter, its column stays empty. <Cite n={30} />

`-d` sets the delimiter. Give it a list, and `paste` uses the characters in turn and starts again at the beginning. <Cite n={30} /> `-s` is serial mode: it pastes one file per output line. <Cite n={30} /> A `-` as a file name means `stdin`. Repeat it to take several lines from one stream. <Cite n={30} />

```bash
printf '%s\n' 1 2 3 > ids
printf '%s\n' login search logout > names
paste ids names              # 1 TAB login, and so on
paste -d, ids names          # 1,login / 2,search / 3,logout
paste -s -d, names           # login,search,logout
seq 6 | paste - - -          # 1 2 3 / 4 5 6, separated by TABs
```

GNU option: in the `-d` list, the escapes `\b`, `\f`, `\r`, and `\v` are GNU extensions. <Cite n={30} /> 
`paste` matches lines by position only. It does not look at the content. To match lines by a key, use `join`.

<Callout type="tip" title="Why it matters for testing">
Tutorial's own advice: build a small CSV of test data from two column files with `paste -d, ids names > cases.csv`. Use `paste -s -d, failed.txt` to turn a list of failed test names into one comma-separated argument for a rerun.
</Callout>

## join

The `join` command combines the lines of two files that have the same value in a key field. This is like a database join. <Cite n={31} /> By default, the key is the first field of each line. Blanks separate the fields. The output is the key, then the other fields of file 1, then those of file 2. <Cite n={31} />

Both files must be sorted on the key field. <Cite n={31} /> Sort them with `sort -k 1b,1`, and use the same locale for `sort` and `join`. The `C` locale avoids surprises. <Cite n={32} />

| Option | Effect |
|---|---|
| `-1 N`, `-2 N`, `-j N` | Choose the key field of file 1, of file 2, or of both. <Cite n={33} /> |
| `-t CHAR` | Use CHAR as the field separator. <Cite n={33} /> |
| `-a 1` | Also print the lines of file 1 that have no partner. <Cite n={33} /> |
| `-v 1` | Print only those lines. <Cite n={33} /> |
| `-e STR` with `-o auto` | Fill missing fields with STR. <Cite n={33} /> |

```bash
printf '%s\n' '1 login' '2 search' '4 admin' > cases
printf '%s\n' '3 fail' '1 pass' '2 pass' > results
LC_ALL=C sort -k 1b,1 cases > cases.s
LC_ALL=C sort -k 1b,1 results > results.s
LC_ALL=C join cases.s results.s                      # 1 login pass / 2 search pass
LC_ALL=C join -a 1 -e NONE -o auto cases.s results.s # adds: 4 admin NONE
LC_ALL=C join -v 1 cases.s results.s                 # 4 admin
```

GNU option: `--check-order` and `-o auto` are GNU options. Other versions of `join` may lack them. <Cite n={33} />

<Callout type="danger" title="Wrong results: unsorted input">
Unsorted input can give missing or wrong lines. `join` may not warn you. It diagnoses unsorted input only when some lines have no partner. <Cite n={33} /> Add `--check-order` to make it fail, and do not use the output of a failed run. <Cite n={33} />
</Callout>

<Callout type="tip" title="Why it matters for testing">
Tutorial's own advice: join a list of test case IDs with a list of results by ID. Then `join -v 1` shows the cases that have no result, which are the tests that never ran.
</Callout>

## split

The `split` command cuts a file into pieces. The default is 1000 lines per piece. <Cite n={34} /> The names are a prefix and a suffix: `x` plus `aa`, `ab`, and so on. <Cite n={34} /> If you join the pieces in name order, you get the original file. <Cite n={34} /> The last argument is your own prefix.

| Option | Effect |
|---|---|
| `-l N` | N lines in each piece. <Cite n={34} /> |
| `-b SIZE` | SIZE bytes in each piece. It can cut a line in two. <Cite n={34} /> |
| `-n l/N` | N pieces, without cutting lines. <Cite n={34} /> |
| `-d` | Digits in the suffix, not letters. <Cite n={34} /> |
| `--additional-suffix=.txt` | Add an extension to each name. <Cite n={34} /> |

```bash
mkdir -p /tmp/split-demo && cd /tmp/split-demo || exit 1
seq 25 > big.txt
split -l 10 big.txt part_                       # part_aa, part_ab, part_ac
wc -l part_*                                    # 10, 10, 5, and the total
cat part_* | cmp - big.txt && echo same         # the pieces rebuild the file
split -d -l 10 --additional-suffix=.txt big.txt chunk_   # chunk_00.txt, ...
```

GNU option: `-d`, `--additional-suffix`, and `-n` are GNU options. Other versions of `split` may lack them. For portable scripts, use letter suffixes with `-l` or `-b`.

<Callout type="danger" title="Many files, and old files replaced">
`split` writes all pieces into the current directory. Without a prefix, the names start with `x`. In our test, a second run with the same prefix replaced the earlier pieces without a warning. Tutorial's own advice: always give a prefix, and run `split` in an empty scratch directory.
</Callout>

<Callout type="tip" title="Why it matters for testing">
Tutorial's own advice: split a large test-data file with `split -n l/4` to get four files with whole lines. Give each parallel test worker one piece.
</Callout>

## tr

The `tr` command translates, squeezes, or deletes characters. It reads `stdin` and writes `stdout`. It takes no file names, so use `<` or a pipe. <Cite n={35} /> Its operands are lists of characters, not regular expressions. <Cite n={36} />

| Use | Command |
|---|---|
| Translate | `tr '[:lower:]' '[:upper:]'` <Cite n={37} /> |
| Delete | `tr -d '\r'` <Cite n={38} /> |
| Squeeze repeats | `tr -s ' '` <Cite n={38} /> |
| Keep only some characters | `tr -cd '0-9\n'` <Cite n={35} /> |

`-c` uses all characters that are not in the list. <Cite n={35} /> The escapes `\n` (newline), `\t` (tab), and `\r` (carriage return) work in the lists. <Cite n={36} />

```bash
printf 'Login OK\r\nSearch FAIL\r\n' > crlf.txt     # \r before each newline
tr -d '\r' < crlf.txt > lf.txt                      # remove the \r characters
echo 'Hello World' | tr '[:lower:]' '[:upper:]'     # HELLO WORLD
echo 'a   b    c' | tr -s ' '                       # a b c
echo 'order 42 / 17' | tr -cd '0-9\n'               # 4217
echo 'one two three' | tr ' ' '\n'                  # one, two, three on 3 lines
```

GNU option: classes such as `[:lower:]` are safer than ranges such as `a-z`, which are not portable outside the C locale. <Cite n={37} /> GNU `tr` works on single bytes. It does not treat a multibyte character, such as `ö`, as you may expect. `LC_ALL=C tr` runs it in a safe single-byte locale. <Cite n={36} /> Do not write `tr -d '[0-9]'`. It also deletes the brackets. Write `tr -d '0-9'`. <Cite n={36} />

<Callout type="danger" title="Data loss: tr output to its own input">
`tr ... < file > file` empties `file` before `tr` starts. <Cite n={5} /> Write to a new file, and then move it: `tr -d '\r' < f > f.new && mv f.new f`. Check `f.new` first.
</Callout>

<Callout type="tip" title="Why it matters for testing">
Tutorial's own advice: before you compare expected and actual output, remove carriage returns from both with `tr -d '\r'`. A file from a Windows tool then does not fail the comparison for an invisible character.
</Callout>

## expand

The `expand` command changes tab characters into spaces. It reads files, or `stdin`, and writes `stdout`. <Cite n={39} /> A tab does not stand for a fixed number of spaces. It moves the text to the next tab stop, which is a column that is a multiple of the tab width. The default width is 8. <Cite n={39} />

`-t N` sets the tab width to N. `-i` converts only the tabs at the start of a line. <Cite n={39} />

```bash
printf 'a\tb\tc\n\tindented\tx\n' > tabs.txt
expand tabs.txt                    # tab stops every 8 columns
expand -t 4 tabs.txt               # a   b   c, then 4 spaces, indented, ...
expand -i -t 4 tabs.txt            # only the leading tab changes
```

GNU option: a tab list can end with `/N`, the width of all later stops, as in `--tabs=2,4,/8`. This form is a GNU extension. <Cite n={39} />

<Callout type="danger" title="Data loss: expand output to its own input">
`expand f > f` empties `f` before `expand` starts. <Cite n={5} /> Write to a new file and then move it: `expand -t 4 f > f.new && mv f.new f`.
</Callout>

<Callout type="tip" title="Why it matters for testing">
Tutorial's own advice: tab-aligned reports look different in each viewer, because the tab width varies. Run `expand -t 8` on such a report before you paste it into a ticket or a CI log. The columns then stay aligned.
</Callout>

## unexpand

The `unexpand` command does the reverse of `expand`. It changes spaces into tab characters. <Cite n={40} /> By default it converts only the blanks at the start of a line. The tab stops are every 8 columns. <Cite n={40} /> So an indent of 4 spaces stays as it is, because it does not reach a tab stop.

`-t N` sets the tab width. It also turns on `-a`. <Cite n={40} /> With `-a`, `unexpand` converts any run of two or more blanks that ends at a tab stop, also after text. <Cite n={40} /> `--first-only` limits the work to leading blanks again. <Cite n={40} />

```bash
printf 'if x:\n    run()\nname    value\n' > code.txt
unexpand code.txt | tr -cd '\t' | wc -c                    # 0 tabs: 4 < 8 columns
unexpand -t 4 --first-only code.txt | tr -cd '\t' | wc -c  # 1 tab: the indent
unexpand -t 4 code.txt | tr -cd '\t' | wc -c               # 2 tabs: also the gap
```

The pipe `tr -cd '\t' | wc -c` counts the tab characters in the output.

GNU option: `--first-only` is a GNU option. Other versions of `unexpand` may lack it. <Cite n={40} />

<Callout type="danger" title="Data loss: unexpand output to its own input">
`unexpand f > f` empties `f` before `unexpand` starts. <Cite n={5} /> Write to a new file, and then move it. Use `-a` with care: it also changes spaces inside text, such as the gap between two columns.
</Callout>

<Callout type="tip" title="Why it matters for testing">
Tutorial's own advice: change indentation in a separate commit, so the diff of a test change stays easy to read. Use `unexpand --first-only -t 4` only when a project rule asks for tab indents.
</Callout>
