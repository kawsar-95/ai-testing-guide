# Text Processing

This stage covers how text moves between commands and the small tools that search and reshape it. A tester needs it because logs, test reports, and CI output are plain text. A filter is a program that accepts text, transforms it, and prints the result. <Cite n={1} />

<PageMeta />

## Text Processing

<Voices>
<Technical>

**Goal:** Count the failed tests in a small log with one line of small tools.

Linux tools mostly handle plain text. A filter is a program that takes textual data and transforms it in one particular way. <Cite n={1} /> Each tool does one small job, and you join the tools to do a larger job. <Cite n={1} />

**Try it:** make a small result file, pick the `fail` lines, sort them, and count each kind with `uniq -c`. The `|` sends the output of one command to the next command. <Cite n={2} />

```bash
(
  cd "$(mktemp -d)"   # make and enter a new, empty directory
  printf '%s\n' 'ok login' 'fail login' 'ok search' 'fail login' > results.txt   # one line per argument
  grep fail results.txt | sort | uniq -c
  #       2 fail login
)
```

<Callout type="tip" title="Why it matters for testing">

Tutorial's own advice: test logs, CSV exports, and API responses are all text. A few filters tell you which tests failed, in one line.

## Stdout, Stdin, and Stderr

<Voices>
<Technical>

**Goal:** See that error messages use `stderr`, so a plain `>` does not catch them.

Every program starts with three streams: one for input, one for normal output, and one for error messages. Their names are `stdin`, `stdout`, and `stderr`. <Cite n={3} /> Their file descriptors, the small numbers for open files, are 0, 1, and 2. <Cite n={3} /> Usually the terminal is behind all three. The shell can connect them to files or to other programs. <Cite n={2} /> <Cite n={4} />

**Try it:** list one file that exists and one that does not, and send `stdout` to a file with `>`. The error still shows on the screen. `$?` is the exit status of the last command, and 0 means success.

```bash
(
  cd "$(mktemp -d)"   # make and enter a new, empty directory
  touch a.txt         # make an empty file
  ls a.txt /does-not-exist > listing.txt
  # ls: cannot access '/does-not-exist': No such file or directory
  echo "exit status: $?"   # exit status: 2
  cat listing.txt          # a.txt
)
```

<Callout type="tip" title="Why it matters for testing">

Tutorial's own advice: a test tool can print failures on `stderr` and a summary on `stdout`. If you capture only one stream, you can miss the failures.

</Callout>

<details>
<summary>Go deeper</summary>

| Stream | Descriptor | Carries |
|---|---|---|
| `stdin` | 0 | Data fed into the program |
| `stdout` | 1 | Normal results of the program |
| `stderr` | 2 | Error and diagnostic messages |

- A stream is a channel that carries bytes in one direction. <Cite n={3} />
- The `stderr` stream is unbuffered: it writes at once. The `stdout` stream is line-buffered when it points to a terminal: it waits for a newline before it writes. <Cite n={3} />

Tutorial's own advice: learn which stream your test tool uses before you build a log filter.

</details>

</Technical>

## Redirects

<Voices>
<Technical>

**Goal:** Send output and errors to files, and add to a file without losing it.

A redirect changes where a command reads from or writes to. The shell sets it up before the command runs. <Cite n={5} /> `> file` sends `stdout` to a file, `>> file` appends to it, and `2> file` sends `stderr` to it. <Cite n={5} /> The shell empties the target of `>` before the command starts. So `sort data.txt > data.txt` leaves `data.txt` empty, and the data is gone. <Cite n={2} /> <Cite n={5} />

```bash
cmd > out.txt 2>&1
```

**Try it:** create a file with `>`, add a line with `>>`, and catch an error in a file with `2>&1` (make `stderr` a copy of `stdout`). <Cite n={5} />

```bash
(
  cd "$(mktemp -d)"   # make and enter a new, empty directory
  echo one > notes.txt              # create or replace
  echo two >> notes.txt             # append
  cat notes.txt                     # one, two
  ls /no/such/dir > all.txt 2>&1    # nothing shows on the screen
  cat all.txt
  # ls: cannot access '/no/such/dir': No such file or directory
)
```

<Callout type="tip" title="Why it matters for testing">

Tutorial's own advice: send the output of each test run to a new file, for example `run-1.log`. Then an old log is never lost by mistake.

</Callout>

<details>
<summary>Go deeper</summary>

| Operator | Effect |
|---|---|
| `> file` | Send `stdout` to `file`. The shell creates the file, or empties it if it exists. <Cite n={5} /> |
| `>> file` | Append `stdout` to `file`. The shell creates the file if it is missing. <Cite n={5} /> |
| `< file` | Read `stdin` from `file`. <Cite n={5} /> |
| `2> file` | Send `stderr` (descriptor 2) to `file`. <Cite n={5} /> |
| `2>&1` | Make `stderr` a copy of `stdout`. <Cite n={5} /> |
| `&> file` | Send both streams to `file`. This is a Bash form. <Cite n={5} /> |

- The shell handles redirects from left to right. So `cmd > out.txt 2>&1` sends both streams to the file, but `cmd 2>&1 > out.txt` sends only `stdout`. <Cite n={5} />
- The POSIX text has no `&>`. Use `> file 2>&1` in scripts that run under `sh`. <Cite n={6} />
- The special file `/dev/null` discards all data that you write to it, as in `ls /no/such/dir 2> /dev/null`. <Cite n={7} />
- In Bash, `set -C` stops `>` from replacing an existing file, and `>|` overrides it. <Cite n={8} />

</details>

</Technical>
<Layman>

**Goal:** Send output and errors to files, and add to a file without losing it.

## Pipes

<Voices>
<Technical>

**Goal:** Chain commands with `|`, and make the chain fail when one part fails.

A pipe connects the `stdout` of one command to the `stdin` of the next command. You write it as `|`. A pipeline is a chain of commands joined by pipes. <Cite n={9} /> Only `stdout` goes through the pipe. The `stderr` stream still goes to the terminal. <Cite n={9} /> A pipeline returns the status of its last command. <Cite n={9} /> If the option `pipefail` is set, it returns the status of the last command that failed. <Cite n={8} />

<FlowDiagram

## Tee

<Voices>
<Technical>

**Goal:** See the output on the screen and keep a copy in a file at the same time.

The `tee` command copies `stdin` to each file you name, and also to `stdout`. <Cite n={11} /> It creates a file that does not exist. <Cite n={11} /> Without `-a`, it overwrites a file that exists, and the old content is lost. <Cite n={11} />

```bash
make test 2>&1 | tee test.log
```

**Try it:** write one line with `tee`, add a second line with `tee -a` (append), and show the file.

```bash
(
  cd "$(mktemp -d)"   # make and enter a new, empty directory
  echo 'run 1: ok' | tee run.log       # prints: run 1: ok
  echo 'run 2: fail' | tee -a run.log  # prints: run 2: fail
  cat run.log
  # run 1: ok
  # run 2: fail
)
```

<Callout type="tip" title="Why it matters for testing">

Tutorial's own advice: `make test 2>&1 | tee test.log` shows the output live and keeps a log. Add `pipefail`, so a failed `make` fails the job.

</Callout>

<details>
<summary>Go deeper</summary>

- `tee` helps with root-owned files. Your shell sets up redirects, not `sudo`. <Cite n={5} /> So `sudo echo text > file` fails on a protected file. Use `echo text | sudo tee -a file` instead.
- GNU option: `-p` (long form `--output-error`) controls what `tee` does when a write fails. Other versions of `tee` may not have it. <Cite n={11} />
- Tutorial's own advice: never give `tee` the name of a file that an earlier command in the same pipeline still reads.

</details>

</Technical>

## grep

<Voices>
<Technical>

**Goal:** Find the lines that match a pattern, and read the result from the exit status.

The `grep` command prints the lines that match a pattern. <Cite n={12} /> The pattern is a regular expression: a short pattern that can match many different strings. <Cite n={12} /> Quote the pattern, so that the shell does not change it. <Cite n={12} /> `grep` returns 0 when it selects a line, 1 when it selects none, and 2 on an error. <Cite n={12} />

**Try it:** show the `ERROR` lines with their line numbers (`-n`). Then search with `-q` (print nothing) for a word that is not in the file, and search a file that does not exist.

```bash
(
  cd "$(mktemp -d)"   # make and enter a new, empty directory
  printf '%s\n' 'INFO start' 'ERROR db down' 'WARN slow' 'ERROR disk full' > app.log
  grep -n ERROR app.log
  # 2:ERROR db down
  # 4:ERROR disk full
  grep -q FATAL app.log; echo "$?"     # 1: no match
  grep ERROR no-such.log; echo "$?"    # 2: an error
  # grep: no-such.log: No such file or directory
)
```

<Callout type="tip" title="Why it matters for testing">

Tutorial's own advice: in a script, status 1 means "no match", not "failure". Status 2 is a real error, such as a missing file.

</Callout>

<details>
<summary>Go deeper</summary>

|---|---|
| `-i` | Ignore case. <Cite n={12} /> |
| `-v` | Select the lines that do not match. <Cite n={12} /> |
| `-c` | Count the matching lines. <Cite n={12} /> |
| `-o` | Print only the matching part. <Cite n={12} /> |
| `-r` | Search all files under a directory. <Cite n={12} /> |
| `-A`, `-B`, `-C` | Add lines after, before, or around each match. <Cite n={12} /> |

- GNU option: `-P` (Perl-style patterns) and `-H` are GNU options. Other versions of `grep` may lack them. <Cite n={12} />
- Tutorial's own advice: this line fails a CI step when the log has an error, or when `grep` cannot read the log: `grep -q ERROR app.log && exit 1; [ $? -eq 1 ] || exit 1`

</details>

## awk

<Voices>
<Technical>

**Goal:** Print chosen fields, filter rows by a number, and sum a column.

An `awk` program is a list of rules of the form `pattern { action }`. For each input line that matches the pattern, awk runs the action. <Cite n={14} /> A line is a record. <Cite n={15} /> A field is one piece of a record, and by default whitespace separates the fields. `$1` is the first field, and `$0` is the whole record. <Cite n={16} /> An `END` rule runs after the input. <Cite n={20} />

```bash
awk '{ print $1 }' times.txt
```

**Try it:** print the name and time of each row slower than 300 (the pattern `$2 > 300`). Then add up field 2 in a variable, and print the sum in an `END` rule.

```bash
(
  cd "$(mktemp -d)"   # make and enter a new, empty directory
  printf '%s\n' 'login 120 ok' 'search 340 fail' 'login 95 ok' 'checkout 410 fail' > times.txt
  awk '$2 > 300 { print $1, $2 }' times.txt
  # search 340
  # checkout 410
  awk '{ sum += $2 } END { print sum }' times.txt   # 965
)
```

<Callout type="tip" title="Why it matters for testing">

Tutorial's own advice: use awk on logs with aligned columns, such as response times. It filters by a number and sums a column in one command.

</Callout>

<details>
<summary>Go deeper</summary>

- `NF` is the number of fields, and `$NF` is the last field. <Cite n={16} /> `NR` counts the records read so far. <Cite n={15} />
- The variable `FS` holds the field separator. <Cite n={17} /> Option `-F` sets it, and `-v name=value` sets any variable. <Cite n={21} />
- A pattern can be a regular expression between slashes. <Cite n={18} /> It can also be a comparison. <Cite n={44} />
- Input that looks like a number compares as a number, but a quoted string compares as text. <Cite n={19} />
- A `BEGIN` rule runs before the input. <Cite n={20} />
- To pass a shell variable into awk, use `-v`, as in `awk -v limit=300 '$2 > limit { print NR ": " $0 }' times.txt`. This is easier than quoting the value into the program text. <Cite n={22} />
- The examples use only basic awk features. The gawk manual also describes extras that other awk programs may lack. <Cite n={21} />

</details>

## cut

<Voices>
<Technical>

**Goal:** Take one column out of a simple CSV file.

The `cut` command prints selected parts of each line. <Cite n={23} /> A delimiter is the character that separates fields. With `-f`, `cut` splits lines at a delimiter. The default delimiter is TAB, and `-d` sets another one. <Cite n={23} /> Fields are numbered from 1. <Cite n={23} />

**Try it:** take field 2 (`-f2`) of a small CSV, with a comma as the delimiter (`-d,`).

```bash
(
  cd "$(mktemp -d)"   # make and enter a new, empty directory
  printf '%s\n' 'id,name,status' '1,login,pass' '2,search,fail' > cases.csv
  cut -d, -f2 cases.csv
  # name
  # login
  # search
)
```

<Callout type="tip" title="Why it matters for testing">

Tutorial's own advice: use `cut -d, -f2` to take one column from a simple CSV of test data. For quoted values, use a real CSV parser.

</Callout>

<details>
<summary>Go deeper</summary>

- A list names what to keep: `2`, `1,3`, `2-4`, `3-`, or `-2`. <Cite n={23} />
- `cut` prints the selected parts in the order of the input. So `-f3,1` prints field 1 first. <Cite n={23} />
- A line without a delimiter is printed whole, unless you add `-s`. <Cite n={23} />
- `-c1-3` prints the first three characters. Characters and bytes are also numbered from 1. <Cite n={23} />
- GNU option: `--complement` prints all fields except the selected ones. Other versions of `cut` may lack it. <Cite n={23} />
- `cut` splits at every delimiter. It does not know about CSV quotes, so a quoted comma breaks the fields. For columns aligned with runs of blanks, or for a new field order, use awk. <Cite n={23} />

</details>

</Technical>

## sort

<Voices>
<Technical>

**Goal:** Sort lines as text and as numbers, and find the slowest step.

The `sort` command writes the lines of its input in sorted order. <Cite n={24} /> By default it compares whole lines as text. <Cite n={24} /> `-n` compares numbers, and `-k 2,2` sorts by the second field only. <Cite n={24} /> Do not send the output to the input file with `>`: the shell empties the file before `sort` reads it. <Cite n={5} />

**Try it:** sort a timing file as text, then by field 2 as numbers (`-k2,2n`). In text order, `120` comes before `95`, because `1` comes before `9`.

```bash
(
  cd "$(mktemp -d)"   # make and enter a new, empty directory
  printf '%s\n' 'checkout 410' 'login 95' 'search 340' 'login 120' > timings.txt
  sort timings.txt        # checkout 410, login 120, login 95, search 340
  sort -k2,2n timings.txt # login 95, login 120, search 340, checkout 410
)
```

<Callout type="tip" title="Why it matters for testing">

Tutorial's own advice: sort response times with `sort -n` to find the slowest ones. Sort two result lists, then compare them with `diff`.

</Callout>

<details>
<summary>Go deeper</summary>

The locale (the language and encoding setting of your shell) sets the order of characters. Set `LC_ALL=C` if the locale gives an order that you do not expect. <Cite n={24} />

| Option | Effect |
|---|---|
| `-r` | Reverse the order, as in `sort -k2,2nr` (slowest first). <Cite n={24} /> |
| `-u` | Keep only the first of equal lines. <Cite n={24} /> |
| `-t :` | Use `:` as the field separator. <Cite n={24} /> |
| `-c` | Check whether the input is sorted. Exit with status 1 if it is not. <Cite n={24} /> |
| `-o FILE` | Write the result to `FILE`. <Cite n={24} /> |

- Write `-k 2,2n`, not `-k 2n`. The second form uses the rest of the line as the key. <Cite n={24} />
- GNU option: `-h` (human numbers such as 2K) and `-V` (version numbers) are GNU extras. Other versions of `sort` may lack them. <Cite n={24} />
- `-o` can name the input file, because `sort` reads all input first. But a crash during the write can lose data, so write to a different file. <Cite n={24} />

</details>

- `-o` can name the input file, because `sort` reads all the input first. But a crash during the write can lose data, so write to a different file. <Cite n={24} />

</details>

</Layman>
<Bangla>

**লক্ষ্য:** Line-গুলো text হিসেবে আর সংখ্যা হিসেবে sort করুন, আর সবচেয়ে ধীর step খুঁজুন।

`sort` command input-এর line-গুলো সাজানো ক্রমে লেখে। <Cite n={24} /> Default হিসেবে এটি পুরো line text হিসেবে তুলনা করে। <Cite n={24} /> `-n` সংখ্যা তুলনা করে, আর `-k 2,2` শুধু দ্বিতীয় field দিয়ে সাজায়। <Cite n={24} /> সাবধান: `>` দিয়ে output input file-এ পাঠাবেন না। `sort` পড়ার আগেই shell file-টি খালি করে দেয়। <Cite n={5} />

**চেষ্টা করুন:** একটি timing file প্রথমে text হিসেবে sort করুন, তারপর field 2 অনুযায়ী সংখ্যা হিসেবে (`-k2,2n`)। Text ক্রমে `120` আসে `95`-এর আগে, কারণ `1` আসে `9`-এর আগে।

```bash
(

  printf '%s\n' 'checkout 410' 'login 95' 'search 340' 'login 120' > timings.txt
  sort timings.txt        # checkout 410, login 120, login 95, search 340
  sort -k2,2n timings.txt # login 95, login 120, search 340, checkout 410
)
```

</Callout>

<summary>আরও জানুন</summary>

## uniq

<Voices>
<Technical>

**Goal:** Count how often each line appears in a file.

The `uniq` command removes repeated lines, but only lines that are next to each other. <Cite n={25} /> It does not find repeated lines that are far apart. So sort the input first. <Cite n={25} /> `-c` puts the number of occurrences before each line. <Cite n={25} />

```bash
sort events.txt | uniq -c
```

**Try it:** `uniq` alone keeps 5 of the 6 lines, because only one pair of equal lines is next to each other. `wc -l` counts the lines. After `sort`, `uniq -c` counts each kind of line.

```bash
(
  cd "$(mktemp -d)"   # make and enter a new, empty directory
  printf '%s\n' 'timeout' 'ok' 'timeout' 'ok' 'ok' 'error' > events.txt
  uniq events.txt | wc -l      # 5
  sort events.txt | uniq -c
  #       1 error
  #       3 ok
  #       2 timeout
)
```

<Callout type="tip" title="Why it matters for testing">

Tutorial's own advice: `sort | uniq -c | sort -rn` lists the most common error lines first. It shows which failure to fix first.

</Callout>

<details>
<summary>Go deeper</summary>

| Option | Effect |
|---|---|
| `-d` | Show each repeated line one time, and show no other line. <Cite n={25} /> |
| `-u` | Print only the lines that are not repeated. <Cite n={25} /> |
| `-i` | Ignore differences in case. <Cite n={25} /> |
| `-f N` | Skip the first N fields before the comparison. <Cite n={25} /> |

- `sort -u` also removes repeated lines. <Cite n={25} /> For plain lines, `sort -u` and `sort | uniq` give the same result. This is not true with every sort option. <Cite n={24} />
- For example, `sort -n -u` checks only the leading number of each line. <Cite n={24} />
- Tutorial's own advice: the count can also show a flaky test that fails again and again.

</details>

## wc

<Voices>
<Technical>

**Goal:** Count the lines of a file, or of the output of a command.

The `wc` command counts lines, words, and bytes. It reads the files you name, or `stdin` if you name none. <Cite n={26} /> `-l` counts only lines. <Cite n={26} /> A line is counted by its newline character, so a last line without a newline is not counted. <Cite n={26} />

```bash
wc -l run.log
```

**Try it:** count all three, then the lines from `stdin` (`<`: no file name in the output), then the `failed` lines that `grep` finds.

```bash
(
  cd "$(mktemp -d)"   # make and enter a new, empty directory
  printf '%s\n' 'login ok' 'search failed' 'logout ok' > run.log
  wc run.log                     #  3  6 33 run.log  (lines, words, bytes)
  wc -l < run.log                # 3
  grep failed run.log | wc -l    # 1
)
```

<Callout type="tip" title="Why it matters for testing">

Tutorial's own advice: assert a count in CI, as in `[ "$(wc -l < results.txt)" -eq 3 ]`. Count matches with `grep ... | wc -l`. <Cite n={42} />

</Callout>

<details>
<summary>Go deeper</summary>

| Option | Counts |
|---|---|
| `-w` | Words. A word is a run of non-blank characters. <Cite n={26} /> |
| `-c` | Bytes <Cite n={26} /> |
| `-m` | Characters, as the current locale reads them <Cite n={26} /> |
| `-L` | The width of the longest line <Cite n={26} /> |

- Bytes and characters can differ. UTF-8 is a common text encoding that uses 1 to 4 bytes for each character, and a letter such as é takes two bytes. <Cite n={45} />
- So `printf 'caf\303\251\n' | wc -c` prints 6 (bytes), and `wc -m` prints 5 (characters) in a UTF-8 locale.
- The output order is always lines, words, characters, bytes, longest line. <Cite n={26} />
- GNU option: `--total=only` prints only the grand total for several files. `--total` is a GNU extension, so other versions of `wc` may lack it. <Cite n={26} />

</details>

## head

<Voices>
<Technical>

**Goal:** Print the first lines of a file.

The `head` command prints the first part of its input. The default is 10 lines. <Cite n={27} /> `-n N` sets the number of lines. <Cite n={27} />


**Try it:** make a file with the numbers 1 to 15 (`seq 15`, one per line). Count the lines that plain `head` prints, then print only 3 lines.

## tail

<Voices>
<Technical>

**Goal:** Print the last lines of a file, or all lines after a header.

The `tail` command prints the last part of its input. The default is 10 lines. <Cite n={28} /> `-n N` sets the line count. <Cite n={28} /> A plus sign, as in `-n +2`, starts at line 2 and prints the rest. So `tail -n +2` removes a header line. <Cite n={28} /> With `-f`, `tail` keeps reading and prints new lines as the file grows. It never ends on its own. <Cite n={28} />

**Try it:** print the last line of a small CSV, then all lines from line 2.

```bash
(
  cd "$(mktemp -d)"   # make and enter a new, empty directory
  printf '%s\n' 'id,name' '1,login' '2,search' > cases.csv
  tail -n 1 cases.csv    # 2,search
  tail -n +2 cases.csv   # 1,login, 2,search (no header)
)
```

<Callout type="tip" title="Why it matters for testing">

Tutorial's own advice: a CI step that runs `tail -f` never ends and hangs the job. Add `--pid`, so `tail` stops when that process ends. <Cite n={28} />

</Callout>

<details>
<summary>Go deeper</summary>

- Stop `tail -f` yourself, for example with Ctrl-C. <Cite n={28} />
- Log rotation is the case where a tool renames a full log and starts a new file with the same name. <Cite n={43} /> Plain `-f` follows the old file and misses the new one. `-F` follows the name and opens the file again. <Cite n={28} />
- The `--pid` form: `./run-tests.sh > test.log 2>&1 &` and then `tail --pid=$! -f test.log`. <Cite n={28} />
- A systemd host is a Linux system that uses systemd as its service manager. Its journal is the log store of systemd. It collects what a service writes to `stdout` and `stderr`, so some services have no file in `/var/log`. <Cite n={46} />
- `journalctl -f` shows the newest journal entries and follows new ones. <Cite n={41} /> A minimal container may have no `journalctl`.
- GNU option: `-F` and `--pid` are not in the POSIX standard, whose `tail` has only `-f`, `-c`, `-n`, and `-r`. <Cite n={48} /> Other versions of `tail` may lack them.

</details>

## nl

<Voices>
<Technical>

**Goal:** Number the lines of a file, also the empty ones.

The `nl` command writes its input with line numbers. <Cite n={29} /> By default it numbers only non-empty lines. <Cite n={29} /> `-b a` numbers all lines. <Cite n={29} />

**Try it:** number a file that has an empty line, first with the default, then with `-b a`. A TAB comes between each number and its text. <Cite n={29} />

```bash
(
  cd "$(mktemp -d)"   # make and enter a new, empty directory
  printf '%s\n' alpha '' beta > t.txt
  nl t.txt
  #      1  alpha
  #                  (the empty line gets no number)
  #      2  beta
  nl -b a t.txt
  #      1  alpha
  #      2
  #      3  beta
)
```

<Callout type="tip" title="Why it matters for testing">

Tutorial's own advice: number a log excerpt with `nl -b a` before you paste it into a bug report. Then your team can say "see line 42".

</Callout>

<details>
<summary>Go deeper</summary>

| Option | Effect |
|---|---|
| `-b pREGEX` | Number only lines that match a basic regular expression, as in `nl -b pb` (lines that contain `b`). <Cite n={29} /> |
| `-w N` | Use N characters for the number. The default is 6. <Cite n={29} /> |
| `-s STR` | Put STR between the number and the text. The default is TAB. <Cite n={29} /> |
| `-v N` | Start at N. <Cite n={29} /> |
| `-i N` | Add N for each numbered line. <Cite n={29} /> |

- A line that gets no number does not use up a number. <Cite n={29} />
- A plain text file counts as one section, because `nl` splits pages only at special marker lines. <Cite n={29} />
- Not every version of `nl` has the long names, such as `--body-numbering=a`. Use the short options in portable scripts. <Cite n={29} />

</details>

</Technical>

## paste

<Voices>
<Technical>

**Goal:** Join two column files side by side into one CSV.

The `paste` command joins the lines of several files side by side. Line 1 of each file becomes one output line, and a delimiter separates the parts. <Cite n={30} /> The default delimiter is TAB, and `-d` sets another one. <Cite n={30} /> `paste` matches lines by position only. It does not look at the content.

**Try it:** join a file of IDs and a file of names, with a comma as the delimiter (`-d,`).

```bash
(
  cd "$(mktemp -d)"   # make and enter a new, empty directory
  printf '%s\n' 1 2 3 > ids
  printf '%s\n' login search logout > names
  paste -d, ids names
  # 1,login
  # 2,search
  # 3,logout
)
```

<Callout type="tip" title="Why it matters for testing">

Tutorial's own advice: `paste -s -d, failed.txt` turns a list of failed test names into one comma-separated argument for a rerun.

</Callout>

<details>
<summary>Go deeper</summary>

- If one file is shorter, its column stays empty. <Cite n={30} />
- Give `-d` a list, and `paste` uses the characters in turn and starts again at the beginning. <Cite n={30} />
- `-s` is serial mode: it pastes one file per output line. So `paste -s -d, names` prints `login,search,logout`. <Cite n={30} />
- A `-` as a file name means `stdin`. Repeat it to take several lines from one stream: `seq 6 | paste - - -` prints `1 2 3` and `4 5 6`, separated by TABs. <Cite n={30} />
- GNU option: in the `-d` list, the escapes `\b`, `\f`, `\r`, and `\v` are GNU extensions. <Cite n={30} />
- To match lines by a key and not by position, use `join`.
- Tutorial's own advice: build a small CSV of test data with `paste -d, ids names > cases.csv`.

</details>

</Technical>

## join

<Voices>
<Technical>

**Goal:** Match the lines of two files by a key, and find the lines that have no partner.

The `join` command combines the lines of two files that have the same value in a key field. This is like a database join. <Cite n={31} /> By default, the key is the first field of each line. <Cite n={31} /> Both files must be sorted on the key field. <Cite n={31} /> Unsorted input can give missing or wrong lines, and `join` may not warn you. <Cite n={33} />

**Try it:** join test cases with results by ID. Then print with `-v 1` the lines of file 1 that have no partner. Both sample files are already sorted.

```bash
(
  cd "$(mktemp -d)"   # make and enter a new, empty directory
  printf '%s\n' '1 login' '2 search' '4 admin' > cases
  printf '%s\n' '1 pass' '2 pass' > results
  join cases results
  # 1 login pass
  # 2 search pass
  join -v 1 cases results   # 4 admin
)
```

<Callout type="tip" title="Why it matters for testing">

Tutorial's own advice: `join -v 1 cases results` shows the test cases that have no result. These are the tests that never ran.

</Callout>

<details>
<summary>Go deeper</summary>

- Blanks separate the fields. The output is the key, then the other fields of file 1, then those of file 2. <Cite n={31} />

## split

<Voices>
<Technical>

**Goal:** Cut a large file into pieces of N lines.

The `split` command cuts a file into pieces. The default is 1000 lines per piece, and `-l N` sets another number. <Cite n={34} /> The names are a prefix and a suffix: `x` plus `aa`, `ab`, and so on. <Cite n={34} /> The last argument is your own prefix. Run `split` in an empty directory: in our test, a second run with the same prefix replaced the old pieces without a warning.

**Try it:** split 25 numbers (`seq 25`, one per line) into pieces of 10 lines, and count the lines of each piece.

```bash
(
  cd "$(mktemp -d)"   # make and enter a new, empty directory
  seq 25 > big.txt
  split -l 10 big.txt part_
  wc -l part_*
  # 10 part_aa
  # 10 part_ab
  #  5 part_ac
  # 25 total
)
```

<Callout type="tip" title="Why it matters for testing">

Tutorial's own advice: `split -n l/4` gives four files of whole lines. Give each parallel test worker one piece.

</Callout>

<details>
<summary>Go deeper</summary>

| Option | Effect |
|---|---|
| `-b SIZE` | SIZE bytes in each piece. It can cut a line in two. <Cite n={34} /> |
| `-n l/N` | N pieces, without cutting lines. <Cite n={34} /> |
| `-d` | Digits in the suffix, not letters. <Cite n={34} /> |
| `--additional-suffix=.txt` | Add an extension to each name. <Cite n={34} /> |

- If you join the pieces in name order, you get the original file. <Cite n={34} /> So `cat part_* | cmp - big.txt` finds no difference.
- GNU option: `-d`, `--additional-suffix`, and `-n` are GNU options. Other versions of `split` may lack them. For portable scripts, use letter suffixes with `-l` or `-b`.
- `split` writes all pieces into the current directory. If the second run makes fewer pieces, old pieces stay behind.
- Tutorial's own advice: always give a prefix.

</details>

## tr

<Voices>
<Technical>

**Goal:** Delete or change characters, such as the `\r` at the end of the lines of a Windows file.

The `tr` command translates, squeezes, or deletes characters. It reads `stdin` and writes `stdout`. It takes no file names, so use `<` or a pipe. <Cite n={35} /> `-d` deletes the characters in a list. <Cite n={38} /> Do not write the output to the input file: `tr ... < file > file` empties `file` before `tr` starts. <Cite n={5} />

**Try it:** count the bytes of a line that ends in `\r\n` (carriage return, then newline). Remove the `\r` with `tr -d`, and count again. Then change lower case to upper case.

```bash
(
  cd "$(mktemp -d)"   # make and enter a new, empty directory
  printf 'Login OK\r\n' > crlf.txt
  wc -c < crlf.txt                  # 10
  tr -d '\r' < crlf.txt > lf.txt    # write to a new file
  wc -c < lf.txt                    # 9
  echo 'Hello World' | tr '[:lower:]' '[:upper:]'   # HELLO WORLD
)
```

<Callout type="tip" title="Why it matters for testing">

Tutorial's own advice: remove `\r` from expected and actual output with `tr -d '\r'` before you compare them.

</Callout>

<details>
<summary>Go deeper</summary>

The operands of `tr` are lists of characters, not regular expressions. <Cite n={36} />

| Use | Command |
|---|---|
| Translate | `tr '[:lower:]' '[:upper:]'` <Cite n={37} /> |
| Squeeze repeats | `tr -s ' '` turns `a   b` into `a b` <Cite n={38} /> |
| Keep only some characters | `tr -cd '0-9\n'` <Cite n={35} /> |

- `-c` uses all characters that are not in the list. <Cite n={35} />
- The escapes `\n` (newline), `\t` (tab), and `\r` (carriage return) work in the lists. <Cite n={36} />
- GNU option: classes such as `[:lower:]` are safer than ranges such as `a-z`, which are not portable outside the C locale. <Cite n={37} />
- GNU `tr` works on single bytes. It does not treat a multibyte character, such as `ö`, as you may expect. `LC_ALL=C tr` runs it in a safe single-byte locale. <Cite n={36} />
- Do not write `tr -d '[0-9]'`, because it also deletes the brackets. Write `tr -d '0-9'`. <Cite n={36} />
- To change a file in place, write to a new file, check it, and then move it: `tr -d '\r' < f > f.new && mv f.new f`.

</details>

</Technical>

## expand

<Voices>
<Technical>

**Goal:** Change tabs into spaces, so that columns look the same in every viewer.

The `expand` command changes tab characters into spaces. ## unexpand

<Voices>
<Technical>

**Goal:** Change the spaces at the start of a line into tabs.

The `unexpand` command does the reverse of `expand`. It changes spaces into tab characters. <Cite n={40} /> By default it converts only the blanks at the start of a line, and the tab stops are every 8 columns. <Cite n={40} /> `-t N` sets the tab width. <Cite n={40} /> Do not write the output to the input file: `unexpand f > f` empties `f` first. <Cite n={5} />

**Try it:** an indent of 4 spaces gives 0 tabs with the default width, because it does not reach a tab stop. With `-t 4`, it gives 1 tab. `tr -cd '\t'` deletes all characters except the tabs <Cite n={35} />, and `wc -c` counts them. <Cite n={26} />

```bash
(
  cd "$(mktemp -d)"   # make and enter a new, empty directory
  printf 'if x:\n    run()\n' > code.txt
  unexpand code.txt | tr -cd '\t' | wc -c        # 0
  unexpand -t 4 code.txt | tr -cd '\t' | wc -c   # 1
)
```

<Callout type="tip" title="Why it matters for testing">

Tutorial's own advice: change indentation in a separate commit, so that the diff of a test change stays easy to read.

</Callout>

<details>
<summary>Go deeper</summary>

- `-t N` also turns on `-a`. <Cite n={40} /> With `-a`, `unexpand` converts any run of two or more blanks that ends at a tab stop, also after text. <Cite n={40} />
- So `-a` also changes spaces inside text, such as the gap between two columns. Use it with care.
- `--first-only` limits the work to leading blanks again, as in `unexpand -t 4 --first-only`. <Cite n={40} />
- GNU option: `--first-only` is not in the POSIX standard, whose `unexpand` has only `-a` and `-t`. <Cite n={49} /> Other versions of `unexpand` may lack it.
- To change a file in place, write to a new file, and then move it.
- Tutorial's own advice: use `unexpand --first-only -t 4` only when a project rule asks for tab indents.

</details>
