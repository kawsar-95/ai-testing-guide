# Troubleshooting

This stage shows the first checks for a Linux server that misbehaves. <Cite n={1} /> They tell you who is on it, how loaded it is, whether memory or disk is full, and what the logs say. A tester needs these checks to attach evidence to a bug report. Every output on this page is an invented illustration. Hosts such as `web01` and the documentation address ranges `192.0.2.0/24`, `203.0.113.0/24`, and `198.51.100.0/24` stand in for real ones. <Cite n={48} />

<PageMeta />

## Server Review

<Voices>
<Technical>

Read before you change anything. A read-only look keeps the evidence intact. A maintenance checklist covers the same ground: logs, disk use, load, and open ports. <Cite n={2} /> Answer five questions in this order.

| Question | Command |
|---|---|
| What is this machine? | `uname -a` <Cite n={39} />, `cat /etc/os-release` <Cite n={40} /> |
| Who is on it? | `w`; its header also shows uptime and load |
| How busy is it? | `uptime`, `free -h`, `df -h` |
| What listens? | `ss -tuln`: TCP and UDP, listening only, numeric <Cite n={37} /> |
| What is broken? | `systemctl --failed` <Cite n={38} />, `journalctl -p err -b` <Cite n={21} /> |

`w` lists each user, the terminal, the login time, and the current command. <Cite n={41} /> If another person works on the host, ask before you test. A unit is a service or other object that systemd manages.

Tutorial's own advice: a minimal container image may lack some tools. `w`, `free`, `vmstat`, and `top` come from procps-ng, and `ss` comes from iproute2. `systemctl` and `journalctl` need a systemd host. `strace`, `ltrace`, and `lsof` are separate packages. Install what is missing before you start.

```bash
# First look. None of these commands changes the system.
uname -a                        # kernel release, host name, hardware
cat /etc/os-release             # distribution and version
uptime; w                       # boot age, load, logged-in users
df -h; free -h                  # disk and memory
ss -tuln                        # listening ports (-p adds the process; other users' processes need root)
systemctl --failed --no-pager   # units in the failed state
journalctl -p err -b --no-pager | tail -n 20   # last errors since boot (root or journal group sees all)
```

<Callout type="tip" title="Why it matters for testing">
Tutorial's own advice: run this list on the test environment before a run and again after a failure. Save both outputs with the bug report. A developer then sees the OS version, the failed units, and the disk state without asking you. Also compare a failing environment with a working one of the same distribution. <Cite n={7} />
</Callout>

</Technical>

## Uptime and Load

<Voices>
<Technical>

`uptime` prints the time, the time since boot, the user count, and the load averages (1, 5, 15 minutes). <Cite n={8} /> A load average is the mean number of processes that are runnable or in uninterruptible sleep. A runnable process uses a CPU or waits for one. An uninterruptible process waits for I/O. <Cite n={8} /> `uptime -s` prints the boot time. <Cite n={3} />

Load is not divided by CPUs: on four CPUs, a load of 1 means 75 % idle time. <Cite n={8} /> Compare the load with `nproc`; with a cgroup v2 CPU quota (a kernel limit on a process group), it can be lower than `nproc --all`. <Cite n={10} />

`/proc/loadavg` holds the same three numbers. <Cite n={9} /> In `vmstat`, `r` counts runnable processes, `b` blocked ones, and `wa` is I/O wait. `st` is time the hypervisor (the VM host software) took from the virtual machine. <Cite n={12} /> <Cite n={11} />

PSI (pressure stall information) is in `/proc/pressure/cpu`, `memory`, and `io`. `some` is the share of time when some tasks stall; `full`, when all non-idle tasks stall. `avg10`, `avg60`, `avg300` are percentages over 10, 60, 300 s; `total` is in microseconds. <Cite n={13} /> No file means PSI is off (tutorial's own note).

```bash
uptime                 # ... load average: 0.52, 0.48, 0.45   (illustration)
nproc                  # CPUs available to this process
cat /proc/loadavg      # three load numbers, then runnable/total and newest PID
vmstat 1 5             # r, b, wa, st columns; ignore the first line
cat /proc/pressure/io  # some avg10=... avg60=... avg300=... total=...
```

<Callout type="tip" title="Why it matters for testing">
Tutorial's own advice: before a load test, write down `nproc` and the load numbers. A load above the CPU count means tasks queue for a CPU or for I/O. High load with low CPU use can mean I/O waits: check `wa`, `b`, and `io` pressure. A high `st` can mean the host lent CPU time to others.
</Callout>

</Technical>
<Layman>

`uptime` shows the time, the time since boot, the number of users, and 3 load averages: for 1, 5, and 15 minutes <Cite n={8} />. The load average is the mean number of processes that use a CPU, wait for a CPU, or wait for I/O <Cite n={8} />. `uptime -s` shows the boot time <Cite n={3} />.

The load is not divided by the number of CPUs. On 4 CPUs, a load of 1 means 75 % idle time <Cite n={8} />. So compare the load with `nproc` <Cite n={10} />.

In `vmstat`, `r` counts the processes that can run, `b` counts the blocked ones, and `wa` is the I/O wait. `st` is the time that the VM host took from the virtual machine <Cite n={12} />.

The files in `/proc/pressure/` show how much time tasks stall for CPU, memory, or I/O <Cite n={13} />. If the files are not there, PSI is off (tutorial's own note).

Tutorial's own advice: before a load test, write down `nproc` and the load numbers. High load with low CPU use can mean I/O waits. Then check `wa`, `b`, and the `io` pressure.

</Layman>
<Bangla>

`uptime` সময়, boot থেকে কত সময় গেছে, user-এর সংখ্যা, আর load average (1, 5, 15 মিনিট) দেখায় <Cite n={8} />। Load average হলো সেই process-গুলোর গড় সংখ্যা, যেগুলো runnable অথবা uninterruptible sleep-এ আছে। Runnable process CPU ব্যবহার করে বা CPU-র জন্য অপেক্ষা করে; uninterruptible process I/O-র জন্য অপেক্ষা করে <Cite n={8} />। `uptime -s` boot-এর সময় দেখায় <Cite n={3} />। `/proc/loadavg`-এ একই তিনটি সংখ্যা থাকে <Cite n={9} />।

Load-কে CPU-র সংখ্যা দিয়ে ভাগ করা হয় না: 4টি CPU-তে load 1 মানে 75 % idle সময় <Cite n={8} />। তাই load-কে `nproc`-এর সাথে তুলনা করুন। cgroup v2 CPU quota থাকলে এটি `nproc --all`-এর চেয়ে কম হতে পারে <Cite n={10} />।

`vmstat`-এ `r` runnable process গোনে, `b` blocked process গোনে, আর `wa` হলো I/O wait। `st` হলো সেই সময়, যা hypervisor virtual machine থেকে নিয়ে নিয়েছে <Cite n={12} />।

PSI (pressure stall information) থাকে `/proc/pressure/cpu`, `memory`, আর `io`-তে। `some` হলো যে সময়ে কিছু task stall করে, তার অংশ; `full` হলো যে সময়ে সব non-idle task stall করে, তার অংশ <Cite n={13} />। File না থাকলে PSI বন্ধ আছে (tutorial-এর নিজের note)।

Tutorial-এর নিজের পরামর্শ: load test-এর আগে `nproc` আর load-এর সংখ্যাগুলো লিখে রাখুন। CPU ব্যবহার কম অথচ load বেশি হলে তা I/O wait হতে পারে। তখন `wa`, `b`, আর `io` pressure দেখুন।

</Bangla>
</Voices>

## Available Memory and Disk

<Voices>
<Technical>

`free -h` shows total, used, free, shared, buff/cache, and available memory. <Cite n={14} /> Page cache is file data that the kernel keeps in RAM to avoid disk reads. The kernel can reclaim it. <Cite n={20} /> So a small `free` value is normal. Read `available`, the estimate of memory for new programs without swapping. It comes from `MemAvailable`. <Cite n={15} /> Swap is disk space used when RAM runs short. In `vmstat`, `si` and `so` show memory moved from and to swap. <Cite n={12} />

`df -h` shows space per filesystem, `df -i` shows inode use, and `du -sh <dir>` totals one directory. <Cite n={16} /> <Cite n={17} /> An inode is the filesystem record of one file. Tutorial's own explanation: if `df` says full but `du` finds less, a process may hold a deleted file open. `lsof +L1` lists unlinked open files. <Cite n={18} />

When memory runs out and the kernel cannot reclaim enough, the OOM (out-of-memory) killer ends a task. <Cite n={20} /> A higher `/proc/<pid>/oom_score` makes a process more likely to be chosen. <Cite n={44} />

```bash
free -h                  # read the "available" column
df -h; df -i             # space and inodes per filesystem
du -xsk /var/* 2>/dev/null | sort -n | tail -n 5   # sizes in KiB; -x stays on one filesystem
lsof +L1                 # deleted but still open (run as root to see all users)
journalctl -k -b --no-pager | grep -i -E 'out of memory|oom-kill'   # kernel wording varies; needs root or journal group
```

<Callout type="danger" title="Do not tune memory on a production host">
Writing to `/proc/sys/vm/drop_caches` discards cached data and can cost much I/O and CPU. The kernel documentation advises it only for tests and debugging. <Cite n={19} /> Tutorial's own advice: do not run `sysctl -w` or `swapoff` on production while you diagnose.
</Callout>

<Callout type="tip" title="Why it matters for testing">
Tutorial's own advice: a full disk or an OOM kill can look like a flaky test. Run `df -h`, `df -i`, and `free -h` at the start and end of a CI job. Keep the output.
</Callout>

</Technical>

</Layman>
<Bangla>

`free -h` total, used, free, shared, buff/cache, আর available memory দেখায় <Cite n={14} />। Page cache হলো সেই file data, যা kernel disk read এড়াতে RAM-এ রাখে। Kernel এই memory আবার ফিরিয়ে নিতে পারে <Cite n={20} />। তাই `free`-এর মান ছোট হওয়া স্বাভাবিক। `available` column-টি পড়ুন। এটি swap ছাড়া নতুন program-এর জন্য কতটা memory আছে তার একটি অনুমান, যা `MemAvailable` থেকে আসে <Cite n={15} />। `vmstat`-এ `si` আর `so` দেখায়, কতটা memory swap থেকে আনা হলো আর swap-এ পাঠানো হলো <Cite n={12} />।

`df -h` প্রতিটি filesystem-এর জায়গা দেখায়, `df -i` inode-এর ব্যবহার দেখায়, আর `du -sh <dir>` একটি directory-র মোট আকার দেয় <Cite n={16} /> <Cite n={17} />। Inode হলো একটি file-এর filesystem record। Tutorial-এর নিজের ব্যাখ্যা: `df` disk full বললেও `du` কম পেলে, কোনো process হয়তো একটি deleted file খোলা রেখেছে। `lsof +L1` এমন unlinked open file দেখায় <Cite n={18} />।

Memory শেষ হলে আর kernel যথেষ্ট memory ফিরিয়ে নিতে না পারলে, OOM (out-of-memory) killer একটি task বন্ধ করে দেয় <Cite n={20} />। `/proc/<pid>/oom_score` যত বেশি, process-টি বাছাই হওয়ার সম্ভাবনা তত বেশি <Cite n={44} />।

`/proc/sys/vm/drop_caches`-এ লিখলে cached data মুছে যায়, এবং এতে অনেক I/O আর CPU খরচ হতে পারে। Kernel documentation এটি শুধু test আর debugging-এর জন্য পরামর্শ দেয় <Cite n={19} />। Tutorial-এর নিজের পরামর্শ: diagnose করার সময় production-এ `sysctl -w` বা `swapoff` চালাবেন না। একটি CI job-এর শুরুতে আর শেষে `df -h`, `df -i`, আর `free -h` চালিয়ে output রেখে দিন।

</Bangla>
</Voices>

## System Logs

<Voices>
<Technical>

Most plain-text logs live in `/var/log`. <Cite n={7} /> <Cite n={46} /> Many services log to the journal, the structured log store of `systemd-journald`. It collects kernel messages, `syslog(3)` calls, and service output. <Cite n={22} /> It writes to `/var/log/journal` if that directory exists, else to `/run/log/journal`, which is lost at reboot. <Cite n={22} /> `Storage=` in `journald.conf` changes this, and some distributions do not keep the journal. <Cite n={23} /> <Cite n={6} /> If `rsyslog` (the classic syslog service) runs, it writes text files <Cite n={43} />; RHEL uses `/var/log/messages` <Cite n={29} />, and Debian and Ubuntu use `/var/log/syslog`. <Cite n={26} /> <Cite n={45} />

Filters of `journalctl`: unit (`-u`), boot (`-b`), priority (`-p`), time (`--since`, `--until`), kernel (`-k`). <Cite n={21} /> Priorities run from `emerg` (0) to `debug` (7). `-p err` also shows the more severe levels. <Cite n={21} /> <Cite n={25} /> Only root and members of `systemd-journal`, `adm`, or `wheel` can read the whole journal. Others see only their own. <Cite n={21} /> Use `--utc` or `-o short-iso` for clear time zones. <Cite n={21} /> `dmesg` prints the kernel ring buffer (the kernel message log). <Cite n={27} /> Some systems need `CAP_SYSLOG` for it. A capability is one right of the root account. <Cite n={28} />

`logrotate` keeps old logs for a while, can compress them, and removes the oldest. <Cite n={24} />

```bash
journalctl -u myapp.service --since "-1h" -p warning --no-pager   # root or journal group
journalctl -k -b -p err --no-pager                  # kernel errors; root or journal group
journalctl -b -o short-iso --no-pager | head -n 5   # ISO time with zone offset
journalctl --disk-usage                             # space used by the journal
ls -l /var/log
```

<Callout type="danger" title="Never delete or truncate logs to free space">
Tutorial's own advice: on a production host, do not run `rm`, `truncate`, or `> file` on a log. Do not run `journalctl --vacuum-size` or `dmesg -c`. <Cite n={21} /> <Cite n={27} /> These commands destroy evidence.
</Callout>

<Callout type="tip" title="Why it matters for testing">
Tutorial's own advice: after a failed run, save the unit name, the time range with its time zone, and the priority filter.
</Callout>

</Technical>

## Authentication Logs

<Voices>
<Technical>

Authentication logs record logins and `sudo` use. With rsyslog, Debian and Ubuntu write them to `/var/log/auth.log`. <Cite n={4} /> <Cite n={45} /> RHEL and CentOS Stream write them to `/var/log/secure`. <Cite n={29} /> A facility is a syslog message category. The Debian file collects `auth` and `authpriv`; the CentOS file, only `authpriv`. Upstream `sshd` uses facility `AUTH`, but a distribution can change it. <Cite n={34} /> Check `SyslogFacility` in `/etc/ssh/sshd_config`; no active line means the default. Else read the journal: `journalctl -u ssh` on Ubuntu <Cite n={47} />, or `-u sshd` on RHEL (tutorial's own note; check `systemctl list-units '*ssh*'`).

`last` reads `/var/log/wtmp`, the record of logins. `lastb` reads `/var/log/btmp`, the record of bad logins. <Cite n={30} /> `--time-format iso` (util-linux) adds the time zone. <Cite n={30} /> Recent Debian and Ubuntu may lack them: install the package that provides `last` (tutorial's own note). With `pam_faillock` (see `/etc/security/faillock.conf`), `faillock --user alice` shows failed attempts. <Cite n={31} /> That module locks an account after more than `deny` consecutive failures. <Cite n={32} /> `faillog` is an older database, `/var/log/faillog`, and may be empty. <Cite n={33} />

Brute force means many password guesses. Signs: many failures from one address, many tries for `root`, many `invalid user` lines. <Cite n={5} /> <Cite n={4} />

```bash
sudo grep 'Failed password' /var/log/auth.log | tail -n 3   # needs root; Debian, Ubuntu
sudo grep 'Failed password' /var/log/secure | tail -n 3     # needs root; RHEL, CentOS
journalctl -u ssh --since today --no-pager | tail -n 3      # root or journal group; -u sshd on RHEL
last -n 5 --time-format iso                                 # if installed
sudo faillock --user alice                                  # needs root; only with pam_faillock
sudo lastb -n 5                                             # needs root; if installed
# Illustration: Failed password for invalid user alice from 203.0.113.7 port 51234 ssh2
```

</Callout>

## Troubleshooting

<Voices>
<Technical>

Reproduce the fault. Write down every symptom and error message. Check the logs. Compare with a working system. Write down the cause and the fix. <Cite n={7} /> Tutorial's own advice: change one thing at a time, and keep a rollback step for each change.

Work through the layers in order:

| Layer | Question | Read-only tool |
|---|---|---|
| Network | Does the port listen? | `ss -tuln` <Cite n={37} /> |
| Process | Does the unit run? | `systemctl status`, `ps` |
| Resource | CPU, memory, disk? | `uptime`, `free -h`, `df -h` |
| Config | What changed? | `diff` with a working host |
| Logs | What was said? | `journalctl`, `dmesg` |

`strace` records the system calls of a process. A syscall is a request from a program to the kernel. `-f` follows child processes (processes that the traced one starts), `-e trace=` limits the calls, and `-c` prints a summary. <Cite n={35} /> A traced process runs slower. <Cite n={35} /> Where Yama (a kernel module that limits tracing) is active, attaching with `-p` can need `CAP_SYS_PTRACE`, often root. <Cite n={42} /> `ltrace` traces library calls. <Cite n={36} />

```bash
strace -f -e trace=%file -o trace.txt myapp --check   # calls that take a file name (open, stat, ...)
grep ENOENT trace.txt | tail -n 5                     # "no such file" errors
strace -c -f myapp --check                            # summary of calls
lsof -p 1234                                          # open files of PID 1234

# Bug report bundle (the system part). Check the files for secrets first.
d=$(mktemp -d) || exit 1
{ date -u; uname -a; cat /etc/os-release; uptime; free -h; df -h; } > "$d/system.txt"
journalctl -u myapp.service --since "-30min" --no-pager > "$d/myapp.log"
echo "Bundle in $d"
```

<Callout type="danger" title="Do not change a production host while you diagnose">
Tutorial's own advice: do not run `kill -9`, restart a service, or attach `strace` on production without approval. A restart erases the state that you want to study. Escalate if you need root, see data loss, or see signs of an attack.
</Callout>

<Callout type="tip" title="Why it matters for testing">
Tutorial's own advice: attach a bug report bundle: OS and application versions, redacted configuration, the log window, and the steps. The script above collects the system part.
</Callout>

</Technical>
