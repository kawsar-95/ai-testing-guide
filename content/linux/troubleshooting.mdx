# Troubleshooting

This stage shows the first checks for a Linux server that misbehaves. <Cite n={1} /> They tell you who is on it, how loaded it is, whether memory or disk is full, and what the logs say. A tester needs these checks to attach evidence to a bug report. Every output on this page is an invented illustration. Hosts such as `web01` and the documentation address ranges `192.0.2.0/24`, `203.0.113.0/24`, and `198.51.100.0/24` stand in for real ones. <Cite n={48} />

## Server Review

<Voices>
<Technical>

**Goal:** Find out what the machine is and what is broken, with no change to the system.

Read before you change anything. A read-only look keeps the evidence intact. Answer five questions in this order: what is this machine, who is on it, how busy is it, what listens, and what is broken. `/etc/os-release` names the distribution and its version. <Cite n={40} /> `systemctl --failed` lists the units in the failed state. <Cite n={38} /> A unit is a service or other object that systemd manages.

```bash
systemctl --failed --no-pager
```

**Try it:** print the distribution, the kernel release (`uname -r`), and the count of failed units. <Cite n={39} /> `tail -n 1` keeps only the last line, the count. This needs a systemd host.

```bash
(
  grep '^PRETTY_NAME=' /etc/os-release       # PRETTY_NAME="Ubuntu 26.04.1 LTS"
  uname -r                                   # 7.0.0-38-generic
  systemctl --failed --no-pager | tail -n 1  # 1 loaded units listed.
)
# Your values differ. These come from one Ubuntu machine.
```

<Callout type="tip" title="Why it matters for testing">

Tutorial's own advice: run the five checks before a test run and again after a failure. Attach both outputs to the bug report.

</Callout>

| Question | Command |

- `w` lists each user, the terminal, the login time, and the current command. <Cite n={41} /> If another person works on the host, ask before you test.
- `ss -p` adds the process. The processes of other users need root.
- Without root or the journal group, `journalctl` shows only part of the log. <Cite n={21} />
- Tutorial's own advice: a minimal container image may lack some tools. `w`, `free`, `vmstat`, and `top` come from procps-ng, and `ss` comes from iproute2. `systemctl` and `journalctl` need a systemd host. `strace`, `ltrace`, and `lsof` are separate packages.
- A maintenance checklist covers logs, disk use, load, and open ports. <Cite n={2} />
- Compare a failing environment with a working one of the same distribution. <Cite n={7} />

## Uptime and Load

<Voices>
<Technical>

**Goal:** Read the load average and compare it with the CPU count.

`uptime` prints the time, the time since boot, the user count, and the load averages for 1, 5, and 15 minutes. <Cite n={8} /> A load average is the mean number of processes that are runnable or in uninterruptible sleep. <Cite n={8} /> The load is not divided by the CPU count: on four CPUs, a load of 1 means 75 % idle time. <Cite n={8} /> So compare the load with `nproc`, the CPU count. <Cite n={10} />

```bash
uptime
```

**Try it:** print the CPU count, the load, and three `vmstat` samples, 1 s apart. `cut` keeps the three load numbers of `/proc/loadavg`. <Cite n={9} /> The first `vmstat` line has averages since boot, so read the next lines. <Cite n={12} />

```bash
(
  nproc                              # 12
  cut -d ' ' -f 1-3 /proc/loadavg    # 9.54 4.59 2.03
  vmstat 1 3
)
# procs -----------memory---------- ---swap-- -----io---- -system-- -------cpu-------
#  r  b   swpd   free   buff  cache   si   so    bi    bo   in   cs us sy id wa st gu
#  4  0 1924740 649964  78812 2539404   73  676  2572  1426 5517    4  6  1 92  0  0  0
# 14  0 1924696 1085368  79584 2507308 6960    0 43980 115452 34908 47540 40 17 38  5  0  0
#  0  0 1924460 1109932  79728 2516892 3736    0  5452   888 29549 28971 35  8 55  1  0  0
# Stand-in numbers from one machine. Yours differ.
```

<Callout type="tip" title="Why it matters for testing">

Tutorial's own advice: write down `nproc` and the load before a load test. Then you can compare the numbers after it.

</Callout>

<details>
<summary>Go deeper</summary>

- A runnable process uses a CPU or waits for one. An uninterruptible process waits for I/O. <Cite n={8} />
- `uptime -s` prints the boot time. <Cite n={3} />
- With a cgroup v2 CPU quota (a kernel limit on a process group), `nproc` can be lower than `nproc --all`. <Cite n={10} />
- A load above the CPU count means tasks queue for a CPU or for I/O (tutorial's own note).
- `/proc/loadavg` holds the three load numbers, then runnable/total processes and the newest PID. <Cite n={9} />
- In `vmstat`, `r` counts runnable processes, `b` blocked ones, and `wa` is I/O wait. `st` is time that the hypervisor (the VM host software) took from the virtual machine. <Cite n={12} /> <Cite n={11} />
- PSI (pressure stall information) is in `/proc/pressure/cpu`, `memory`, and `io`. `some` is the share of time when some tasks stall; `full`, when all non-idle tasks stall. `avg10`, `avg60`, `avg300` are percentages over 10, 60, 300 s; `total` is in microseconds. <Cite n={13} /> No file means PSI is off (tutorial's own note).

```bash
cat /proc/pressure/io   # some avg10=... avg60=... avg300=... total=...
```

Tutorial's own advice: high load with low CPU use can mean I/O waits: check `wa`, `b`, and `io` pressure. A high `st` can mean the host lent CPU time to others.

</details>

<Bangla>

**লক্ষ্য:** Load average পড়ুন, আর CPU-র সংখ্যার সাথে তুলনা করুন।

`uptime` সময়, boot থেকে কত সময় গেছে, user-এর সংখ্যা, আর 1, 5, ও 15 মিনিটের load average দেখায়। <Cite n={8} /> Load average হলো সেই process-গুলোর গড় সংখ্যা, যেগুলো runnable অথবা uninterruptible sleep-এ আছে। <Cite n={8} /> Load-কে CPU-র সংখ্যা দিয়ে ভাগ করা হয় না: 4টি CPU-তে load 1 মানে 75 % idle সময়। <Cite n={8} /> তাই load-কে `nproc`-এর সাথে তুলনা করুন। এটি process-এর জন্য available CPU-র সংখ্যা। <Cite n={10} />

**চেষ্টা করুন:** CPU-র সংখ্যা, load, আর 1 s পরপর 3টি `vmstat` sample print করুন। `cut` `/proc/loadavg`-এর load-এর 3টি সংখ্যা রাখে। <Cite n={9} /> `vmstat`-এর প্রথম line-এ boot থেকে গড় থাকে, তাই পরের line-গুলো পড়ুন। <Cite n={12} />

```bash
(
  nproc                              # 12
  cut -d ' ' -f 1-3 /proc/loadavg    # 9.54 4.59 2.03
  vmstat 1 3
)
```

</Callout>

<details>
<summary>আরও জানুন</summary>

- Runnable process CPU ব্যবহার করে বা CPU-র জন্য অপেক্ষা করে। Uninterruptible process I/O-র জন্য অপেক্ষা করে। <Cite n={8} />
- `uptime -s` boot-এর সময় দেখায়। <Cite n={3} />
- cgroup v2 CPU quota থাকলে `nproc` `nproc --all`-এর চেয়ে কম হতে পারে। <Cite n={10} />

## Available Memory and Disk

<Voices>
<Technical>

**Goal:** Read the available memory, and find a deleted file that still uses disk space.

`free -h` shows the memory use. <Cite n={14} /> Page cache (file data in RAM) is memory that the kernel can reclaim. <Cite n={20} /> So a small `free` value is normal. Read `available`, the estimate of memory for new programs without swapping. <Cite n={15} /> If `df` says full but `du` finds less, a process may hold a deleted file open (tutorial's own explanation). `lsof +L1` lists such files. <Cite n={18} />

```bash
free -h
```

**Try it:** hold a file open with your own `sleep`, delete it, and find it with `lsof`. `$!` is the PID of your `sleep`. `-a` joins the two filters `+L1` and `-p` (process ID). <Cite n={18} />

```bash
(
  free -h | head -n 2                 # the header and the Mem line
  d=$(mktemp -d)                      # a new, empty directory
  echo data > "$d/big.log"
  sleep 30 < "$d/big.log" &           # your own process holds the file open
  rm "$d/big.log"
  lsof -a +L1 -p $! | tail -n 1
  kill $!                             # stop your own sleep
  rm -rf "$d"
)
#                total        used        free      shared  buff/cache   available
# Mem:            14Gi        11Gi       1.1Gi       393Mi       2.5Gi       2.8Gi
# sleep   12345 user    0r   REG   0,46        5     0 2182 /tmp/tmp.XXXXXXXXXX/big.log (deleted)
# The sizes, the PID, the user, and the directory name are stand-ins.
```

<Callout type="tip" title="Why it matters for testing">

Tutorial's own advice: a full disk can look like a flaky test. Run `df -h` and `free -h` at the start and end of a CI job.

</Callout>

<details>
<summary>Go deeper</summary>

- `free -h` shows total, used, free, shared, buff/cache, and available memory. <Cite n={14} /> Page cache avoids disk reads. <Cite n={20} />
- `available` comes from `MemAvailable` in `/proc/meminfo`. <Cite n={15} />
- Swap is disk space used when RAM runs short. In `vmstat`, `si` and `so` show memory moved from and to swap. <Cite n={12} />
- `df -h` shows space per filesystem, `df -i` shows inode use, and `du -sh <dir>` totals one directory. <Cite n={16} /> <Cite n={17} /> An inode is the filesystem record of one file.
- When memory runs out and the kernel cannot reclaim enough, the OOM (out-of-memory) killer ends a task. <Cite n={20} /> A higher `/proc/<pid>/oom_score` makes a process more likely to be chosen. <Cite n={44} />
- Do not tune memory on a production host. Writing to `/proc/sys/vm/drop_caches` discards cached data and can cost much I/O and CPU. The kernel documentation advises it only for tests and debugging. <Cite n={19} /> Tutorial's own advice: do not run `sysctl -w` or `swapoff` on production while you diagnose.

```bash
df -h; df -i             # space and inodes per filesystem
du -xsk /var/* 2>/dev/null | sort -n | tail -n 5   # sizes in KiB; -x stays on one filesystem
lsof +L1                 # all deleted but open files (run as root to see all users)
journalctl -k -b --no-pager | grep -i -E 'out of memory|oom-kill'   # kernel wording varies; needs root or journal group
```

Tutorial's own advice: an OOM kill can also look like a flaky test. Add `df -i` to the CI checks, and keep their output with the job log.

</details>

## System Logs

<Voices>
<Technical>

**Goal:** Read the kernel messages of this boot without root.

Many services log to the journal, the structured log store of `systemd-journald`. It collects kernel messages, `syslog(3)` calls, and service output. <Cite n={22} /> `journalctl` filters by unit (`-u`), boot (`-b`), priority (`-p`), time (`--since`, `--until`), and kernel (`-k`). <Cite n={21} /> Only root and members of `systemd-journal`, `adm`, or `wheel` can read the whole journal. Others see only their own messages. <Cite n={21} /> Tutorial's own advice: never delete or truncate a production log. It destroys evidence.

```bash
journalctl -u myapp.service --since "-1h" -p warning --no-pager
```

**Try it:** read the kernel log with `dmesg`, then with `journalctl -k`. Some systems need `CAP_SYSLOG` for `dmesg`, so it can fail for a normal user. <Cite n={28} /> `-n 1` shows the newest entry; `-o short-iso` adds the zone offset. <Cite n={21} />

```bash
(
  dmesg | tail -n 1      # dmesg: read kernel buffer failed: Operation not permitted
  journalctl -k -b -n 1 -o short-iso --no-pager
  # 2026-10-27T15:24:39+06:00 host kernel: <one kernel message>
  journalctl --disk-usage
  # Archived and active journals take up 1.5G in the file system.
)
# Run as a member of adm. The message, the host, and the size are stand-ins.
```

<Callout type="tip" title="Why it matters for testing">

Tutorial's own advice: after a failed run, save the unit name, the time range with its time zone, and the priority filter.

</Callout>

<summary>Go deeper</summary>

## Authentication Logs

<Voices>
<Technical>

**Goal:** Find the file that records logins on your system, and see who may read it.

Authentication logs record logins and `sudo` use. With rsyslog, Debian and Ubuntu write them to `/var/log/auth.log`. <Cite n={4} /> <Cite n={45} /> RHEL and CentOS Stream write them to `/var/log/secure`. <Cite n={29} /> `last` reads `/var/log/wtmp`, the record of logins. <Cite n={30} /> These logs hold user names and IP addresses. Only authorized administrators may read them. Never post them in a public ticket or chat.

```bash
last -n 5 --time-format iso
```

**Try it:** on Debian or Ubuntu, show the mode and group of `auth.log`, and your last two login records. `--time-format iso` adds the time zone. <Cite n={30} /> If `last` is not installed, the second command fails.

```bash
(
  ls -l /var/log/auth.log
  last -n 2 --time-format iso | head -n 2
)
# -rw-r----- 1 syslog adm 43222 Oct 27 15:30 /var/log/auth.log
# user     tty2                          2026-10-27T14:49:27+0600  - still logged in
# reboot   system boot  7.0.0-38-generic 2026-10-27T14:49:10+0600  - still running
# The size, the dates, and the user name are stand-ins.
```

<Callout type="tip" title="Why it matters for testing">

Tutorial's own advice: when a login test fails, find the cause in the log. Never lock the shared test account with bad-password loops.

</Callout>

<details>
<summary>Go deeper</summary>

- A facility is a syslog message category. The Debian file collects `auth` and `authpriv`; the CentOS file, only `authpriv`. Upstream `sshd` uses facility `AUTH`, but a distribution can change it. <Cite n={34} /> Check `SyslogFacility` in `/etc/ssh/sshd_config`; no active line means the default.
- The journal also has these lines: `journalctl -u ssh` on Ubuntu <Cite n={47} />, or `-u sshd` on RHEL (tutorial's own note; check `systemctl list-units '*ssh*'`).
- `lastb` reads `/var/log/btmp`, the record of bad logins. <Cite n={30} /> Recent Debian and Ubuntu may lack `last` and `lastb`: install the package that provides `last` (tutorial's own note).
- With `pam_faillock` (see `/etc/security/faillock.conf`), `faillock --user alice` shows failed attempts. <Cite n={31} /> That module locks an account after more than `deny` consecutive failures. <Cite n={32} /> `faillog` is an older database, `/var/log/faillog`, and may be empty. <Cite n={33} />
- Brute force means many password guesses. Signs: many failures from one address, many tries for `root`, many `invalid user` lines. <Cite n={5} /> <Cite n={4} />
- Before you share a line, replace names and addresses with `alice` and `203.0.113.7`.

```bash
sudo grep 'Failed password' /var/log/auth.log | tail -n 3   # needs root; Debian, Ubuntu
sudo grep 'Failed password' /var/log/secure | tail -n 3     # needs root; RHEL, CentOS
journalctl -u ssh --since today --no-pager | tail -n 3      # root or journal group; -u sshd on RHEL
# Illustration: Failed password for invalid user alice from 203.0.113.7 port 51234 ssh2
```

</details>

## Troubleshooting

<Voices>
<Technical>

**Goal:** Find the failed system call of a program with `strace`.

Reproduce the fault. Write down every symptom and error message. Check the logs. Compare with a working system. Write down the cause and the fix. <Cite n={7} /> `strace` records the system calls of a process. A system call is a request from a program to the kernel. <Cite n={35} /> Tutorial's own advice: on production, do not restart a service, run `kill -9`, or attach `strace` without approval. A restart erases the state under study.

```bash
strace -f -e trace=%file -o trace.txt myapp --check
```

**Try it:** trace `cat` on a missing file, then find the failed call. `-f` follows child processes, `-e trace=%file` keeps the calls with a file name, and `-o` writes to a file. <Cite n={35} /> `ENOENT` means "no such file".

```bash
(
  d=$(mktemp -d) && cd "$d"           # a new, empty directory
  strace -f -e trace=%file -o trace.txt cat missing.txt
  # cat: missing.txt: No such file or directory
  grep ENOENT trace.txt | grep missing
  # 12345 statx(AT_FDCWD, "missing.txt", AT_STATX_SYNC_AS_STAT, STATX_ALL, 0x7ffc9227c450) = -1 ENOENT (No such file or directory)
  cd / && rm -rf "$d"
)
# The PID and the address are stand-ins. The call name (here statx) can differ on your system.
```

<Callout type="tip" title="Why it matters for testing">

Tutorial's own advice: attach a bug report bundle: the versions, the redacted configuration, the log window, and the steps.

</Callout>

<details>
<summary>Go deeper</summary>

Work through the layers in order:

| Layer | Question | Read-only tool |
|---|---|---|
| Network | Does the port listen? | `ss -tuln` <Cite n={37} /> |
| Process | Does the unit run? | `systemctl status`, `ps` |
| Resource | CPU, memory, disk? | `uptime`, `free -h`, `df -h` |
| Config | What changed? | `diff` with a working host |
| Logs | What was said? | `journalctl`, `dmesg` |

- `strace -c` prints a summary of the calls. A traced process runs slower. <Cite n={35} />
- Where Yama (a kernel module that limits tracing) is active, attaching with `-p` can need `CAP_SYS_PTRACE`, often root. <Cite n={42} />
- `ltrace` traces library calls. <Cite n={36} /> `lsof -p 1234` lists the open files of PID 1234.
- Tutorial's own advice: change one thing at a time, and keep a rollback step for each change. Escalate if you need root, see data loss, or see signs of an attack.

```bash
journalctl -u myapp.service --since "-30min" --no-pager > "$d/myapp.log"
echo "Bundle in $d"
```
