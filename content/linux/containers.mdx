# Containers

A container is one or more Linux processes that the kernel isolates and limits. This stage explains containers, runtimes, Docker, and cgroups. A tester needs them because CI jobs often run inside containers and behave differently there. <Cite n={1} />

<PageMeta />

## Containerization

<Voices>
<Technical>

**Goal:** See the namespaces of a process, and make a new namespace with `unshare`.

A container is a group of processes that the kernel isolates from the host. <Cite n={21} /> <Cite n={7} /> A **namespace** gives a process its own view of one global resource, such as process IDs or the hostname. <Cite n={7} /> A **cgroup** limits and counts the resources of a group of processes. <Cite n={6} /> An **image** is a read-only package of an application and its files. <Cite n={2} /> <Cite n={21} />

```bash
ls -l /proc/self/ns
```

**Try it:** set a hostname in a new UTS (hostname) namespace. `--user --map-root-user` makes you root in a new user namespace, without `sudo`. <Cite n={10} /> It needs user namespaces: the per-user limit in `/proc/sys/user/max_user_namespaces` must allow one more. <Cite n={7} /> The hostname of your system does not change. <Cite n={7} />

```bash
(
  readlink /proc/self/ns/uts     # uts:[4026531838]
  unshare --user --map-root-user --uts sh -c 'hostname box1; readlink /proc/self/ns/uts; hostname'
  # uts:[4026533177]   a new number: a new namespace
  # box1
  hostname                       # your own hostname, not box1
)
# Your namespace numbers can differ.
```

<Callout type="tip" title="Why it matters for testing">

Tutorial's own advice: log `uname -r`, `cat /proc/self/cgroup`, and `ls -l /proc/self/ns` in each CI job. Compare them when a test fails only in CI.

</Callout>

<details>
<summary>Go deeper</summary>

`ls -l /proc/self/ns` shows one link for each namespace type, plus two `*_for_children` links. The same number means the same namespace. <Cite n={7} /> `unshare` builds new namespaces for one program by hand. <Cite n={10} />

| Namespace | Isolates |
|---|---|
| `cgroup` | the cgroup root |
| `ipc` | System V IPC |
| `mnt` | mount points |
| `net` | network devices and ports |
| `pid` | process IDs |
| `time` | the boot and monotonic clocks, not the wall clock |
| `user` | user and group IDs |
| `uts` | the hostname |

All rows: <Cite n={7} />

- A container shares the host kernel; a virtual machine (VM) runs its own. <Cite n={3} />
- The host kernel decides which features exist. <Cite n={41} /> `uname -r` prints the kernel release. <Cite n={45} /> On Docker Desktop, it is the kernel of its Linux VM. <Cite n={31} />
- By default, a container has no limit. It can use all the resources that the kernel scheduler allows. <Cite n={41} />
- Some views show host data: inside a container, `free` reports the swap of the host. <Cite n={41} />

Tutorial's own advice: two jobs on one host compete for CPU and memory, so a busy neighbour can make a timing test flaky.

</details>

</Technical>

## Container Runtime

<Voices>
<Technical>

**Goal:** Find which container engine and runtime a host has.

A **container runtime** starts and manages the container process. <Cite n={5} /> It sets up the namespaces and cgroups. <Cite n={2} /> <Cite n={5} /> A low-level runtime, such as `runc`, creates one container from an OCI bundle (a folder with `config.json` and a root filesystem). <Cite n={16} /> <Cite n={5} /> A high-level runtime, such as `containerd`, is a daemon (a background service) that also moves images and supervises containers. <Cite n={17} /> <Cite n={5} />

```bash
runc --version
```

**Try it:** list the container tools here and the `runc` version. `command -v` shows how the shell finds each tool (for a program, its path) and prints nothing for a tool that it cannot find. <Cite n={48} /> Both commands only read.

```bash
(
  command -v docker podman runc containerd
  # /usr/local/bin/docker
  # /usr/bin/runc
  # /usr/bin/containerd
  runc --version | head -n 1     # runc version 1.5.2
)
# Your paths and versions can differ. Here, podman is not installed.
```

<Callout type="tip" title="Why it matters for testing">

Tutorial's own advice: log the engine and runtime. A test that passes with Docker can fail with Podman or rootless, because file owners and privileges differ.

</Callout>

<details>
<summary>Go deeper</summary>

By default, Docker Engine starts containerd, which uses `runc` for most container work. <Cite n={46} /> <Cite n={47} /> <Cite n={5} /> The runtime acts as an intermediary between the container and the operating system. <Cite n={2} /> Two Open Container Initiative (OCI) standards matter:

- The image spec defines the image: a manifest, filesystem layers (sets of file changes), and a configuration. <Cite n={15} />
- The runtime spec defines the `config.json` file and the container lifecycle. <Cite n={13} /> Its Linux part names the namespaces, cgroups, and capabilities (small units of root power) to set. <Cite n={14} /> <Cite n={11} />

CRI-O is a runtime for Kubernetes, which needs a runtime with the Container Runtime Interface (CRI). <Cite n={18} /> <Cite n={4} />

| | Docker Engine | Podman |
|---|---|---|
| Daemon | `dockerd` is a long-running daemon <Cite n={22} /> | none <Cite n={19} /> |
| Root | The daemon needs root, unless rootless <Cite n={39} /> | A normal user can run containers <Cite n={19} /> |

**Rootless** means the runtime and containers run as a normal user, inside a user namespace (a private view of user IDs). <Cite n={40} /> Rootless setups need ID ranges in `/etc/subuid` and `/etc/subgid`. <Cite n={40} /> <Cite n={20} />

The runc README shows this flow. <Cite n={16} />

```bash
# Illustration, not run. Use only a test bundle directory, never a shared host:
#   runc spec                  # write a template config.json in the bundle directory
#   runc run mycontainerid     # start the container from the bundle; needs root (unless rootless)
```

</details>

## Cgroups

<Voices>
<Technical>

**Goal:** Find the cgroup of a process and read its limits.

`memory.max` caps memory, and `pids.max` caps tasks. The value `max` means no limit. <Cite n={12} />

```bash
cat /proc/self/cgroup
```

**Try it:** read two limit files of your cgroup. It needs cgroup v2: the first line starts with `0::`. The root cgroup (`0::/`) has no `memory.max` or `pids.max`. <Cite n={12} /> `cut -d: -f3` keeps the path after `0::`. <Cite n={49} />

```bash
(
  cat /proc/self/cgroup     # 0::/user.slice/user-1000.slice/user@1000.service/app.slice/<app>.scope
  cg=$(cut -d: -f3 /proc/self/cgroup)
  cat "/sys/fs/cgroup$cg/memory.max"   # max
  cat "/sys/fs/cgroup$cg/pids.max"     # 14581
)
# <app> stands for your own program. Your path and limits can differ.
```

<Callout type="danger" title="Do not kill the main process">

Tutorial's own advice: do not write into `/sys/fs/cgroup` on a shared host. A memory limit that is too low makes the OOM killer end processes. <Cite n={12} /> `kill -9` gives the usual main process of a container no time to clean up. <Cite n={8} /> `docker stop` sends SIGTERM first. <Cite n={28} />

</Callout>

<Callout type="tip" title="Why it matters for testing">

Tutorial's own advice: test with the limits of CI. A low memory limit shows as an OOM kill in `memory.events`, not as a test error. <Cite n={12} />

</Callout>

<details>
<summary>Go deeper</summary>

A cgroup puts processes in a hierarchy of groups with limits and counters. <Cite n={6} /> A **controller** manages one resource, such as `cpu`, `memory`, `io`, or `pids`. <Cite n={6} /> The interface is a file tree, usually at `/sys/fs/cgroup`. <Cite n={6} /> In cgroup v2, the entry in `/proc/self/cgroup` is `0::path`. If a v1 hierarchy is also in use, the file has more lines. <Cite n={12} />

| | cgroup v1 | cgroup v2 |
|---|---|---|
| Trees | One for each controller, or shared <Cite n={6} /> | One unified tree <Cite n={6} /> |
| I/O controller | `blkio` <Cite n={6} /> | `io` <Cite n={6} /> |
| Memory limit | `memory.limit_in_bytes` <Cite n={12} /> | `memory.max` <Cite n={12} /> |
| `/proc/self/cgroup` | `ID:controllers:path` <Cite n={6} /> | `0::path` <Cite n={6} /> |

- If a v2 cgroup reaches `memory.max` and cannot shrink, the OOM killer (the kernel's process killer) runs inside that cgroup. <Cite n={12} />
- `pids.max` counts tasks: processes and threads. <Cite n={12} /> `cpu.max` caps CPU time. A CPU limit shows as `nr_throttled` in `cpu.stat`. A `pids.max` limit makes `fork` (create a process) fail with `EAGAIN` (try again). <Cite n={12} />
- Docker sets cgroup limits with `--memory`, `--cpus`, and `--pids-limit`. <Cite n={41} /> <Cite n={24} />
- On cgroup v2, systemd uses `MemoryMax=`, and `systemd-run --scope` applies it to one command. <Cite n={42} /> <Cite n={43} /> `systemd-cgls` prints the cgroup tree. <Cite n={44} />
- A cgroup namespace makes `/proc/self/cgroup` show paths from its own root. <Cite n={9} />
- When the main process of a container ends, the kernel kills every other process in its PID namespace. <Cite n={8} />

```bash
systemd-cgls --no-pager | head -n 20    # the cgroup tree on a systemd host

#   (cgroup v2; --user uses your own service manager)
```
