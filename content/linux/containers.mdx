# Containers

A container is one or more Linux processes that the kernel isolates and limits. This stage explains containers, runtimes, Docker, and cgroups. A tester needs them because CI jobs often run inside containers and behave differently there. <Cite n={1} />

<PageMeta />

## Containerization

<Voices>
<Technical>

A container is a group of processes that the kernel isolates from the rest of the host. <Cite n={21} /> <Cite n={7} /> Three main parts build it. A **namespace** gives a process its own view of one global resource, such as process IDs, mounts, network devices, or the hostname. <Cite n={7} /> A **cgroup** (control group) limits and counts the resources of a group of processes. <Cite n={6} /> An **image** is a read-only package of the application and the files that it needs. <Cite n={2} /> <Cite n={21} /> The `unshare` command builds new namespaces for one program by hand. <Cite n={10} />

A container is not a virtual machine (VM). A VM runs its own kernel, the core of the operating system. A container shares the kernel of the host. <Cite n={3} /> So the host kernel decides which features exist. <Cite n={41} /> By default, a container has no limit and can use all the resources that the kernel scheduler allows. <Cite n={41} /> Some views show host data: inside a container, `free` reports the swap of the host. <Cite n={41} /> The time namespace isolates only the boot and monotonic clocks, not the wall clock. <Cite n={7} />

```bash
# Read-only. Run it on the host and inside a container, then compare.
uname -r                    # kernel release; a container shows the kernel that runs it
                            # (on Docker Desktop, the kernel of its Linux VM)
ls -l /proc/self/ns         # one link for each namespace type, plus two *_for_children links;
                            # the same number = the same namespace. The 8 types and what they isolate:
                            # cgroup (cgroup root), ipc (System V IPC), mnt (mount points),
                            # net (network devices, ports), pid (process IDs), time (boot and
                            # monotonic clocks), user (user and group IDs), uts (hostname)
readlink /proc/self/ns/pid  # for example pid:[4026531836] (an illustration)
cat /proc/self/cgroup       # the cgroup of this process
```

<Callout type="tip" title="Why it matters for testing">

Tutorial's own advice: log `uname -r` (it prints the kernel release <Cite n={45} />), `cat /proc/self/cgroup`, and `ls -l /proc/self/ns` at the start of each CI job. When a test fails only in CI, compare these values first. Two jobs on one host also compete for CPU and memory, so a busy neighbour can make a timing test flaky.

</Callout>

</Technical>

<Bangla>

Container হলো process-এর একটি group, যাকে kernel host-এর বাকি অংশ থেকে আলাদা করে রাখে <Cite n={21} /> <Cite n={7} />। তিনটি প্রধান অংশ দিয়ে container তৈরি হয়। **Namespace** একটি process-কে একটি global resource-এর নিজস্ব view দেয়, যেমন process ID, mount, network device, বা hostname <Cite n={7} />। **Cgroup** (control group) একদল process-এর resource সীমিত করে এবং তার হিসাব রাখে <Cite n={6} />। **Image** হলো application এবং তার দরকারি file-গুলোর একটি read-only package <Cite n={2} />। `unshare` command হাতে একটি program-এর জন্য নতুন namespace তৈরি করে <Cite n={10} />।

Tutorial-এর নিজস্ব পরামর্শ: প্রতিটি CI job-এর শুরুতে `uname -r`, `cat /proc/self/cgroup`, আর `ls -l /proc/self/ns` log করুন। কোনো test শুধু CI-তে fail করলে প্রথমে এই মানগুলো মিলিয়ে দেখুন। একই host-এ দুটি job CPU আর memory নিয়ে প্রতিযোগিতা করে, তাই একটি ব্যস্ত পাশের job একটি timing test-কে flaky করে দিতে পারে।

</Bangla>

## Container Runtime

<Voices>
<Technical>

A **container runtime** starts and manages the container process. <Cite n={5} /> It acts as an intermediary between the container and the operating system, and sets up namespaces and cgroups. <Cite n={2} /> <Cite n={5} />

Two Open Container Initiative (OCI) standards matter. The image spec defines the image: a manifest, filesystem layers (sets of file changes), and a configuration. <Cite n={15} /> The runtime spec defines the `config.json` file and the container lifecycle. <Cite n={13} /> Its Linux part names the namespaces, cgroups, and capabilities (small units of root power) to set. <Cite n={14} /> <Cite n={11} />

A low-level runtime, such as `runc`, creates one container from an OCI bundle (a folder with `config.json` and a root filesystem). <Cite n={16} /> <Cite n={5} /> A high-level runtime, such as `containerd`, is a daemon (a background service) that also moves images and supervises containers. <Cite n={17} /> <Cite n={5} /> By default, Docker Engine starts containerd, which uses `runc` for most container work. <Cite n={46} /> <Cite n={47} /> <Cite n={5} /> CRI-O is a runtime for Kubernetes, which needs a runtime with the Container Runtime Interface (CRI). <Cite n={18} /> <Cite n={4} />

| | Docker Engine | Podman |
|---|---|---|
| Daemon | `dockerd` is a long-running daemon <Cite n={22} /> | none <Cite n={19} /> |
| Root | The daemon needs root, unless rootless <Cite n={39} /> | A normal user can run containers <Cite n={19} /> |

**Rootless** means the runtime and containers run as a normal user, inside a user namespace (a private view of user IDs). <Cite n={40} /> Rootless setups need ID ranges in `/etc/subuid` and `/etc/subgid`. <Cite n={40} /> <Cite n={20} />

```bash
command -v docker podman runc containerd   # read-only: which of these tools exist here
# The runc README shows this flow. Do not run it on a shared host:
#   runc spec                  # write a template config.json in the bundle directory
#   runc run mycontainerid     # start the container from the bundle; needs root (unless rootless)
```

<Callout type="tip" title="Why it matters for testing">

Tutorial's own advice: log the engine and runtime, for example `docker version` or `podman --version`. A test that passes with Docker can fail with Podman or rootless, because file owners and privileges differ.

</Callout>

</Technical>
<Layman>

A **container runtime** starts and manages the container process <Cite n={5} />. It works between the container and the operating system, and sets up namespaces and cgroups <Cite n={2} /> <Cite n={5} />.

Two Open Container Initiative (OCI) standards are important. The image spec defines the image: a manifest, filesystem layers, and a configuration <Cite n={15} />. The runtime spec defines the `config.json` file and the container lifecycle <Cite n={13} />.

A low-level runtime, such as `runc`, makes one container from an OCI bundle <Cite n={16} /> <Cite n={5} />. A high-level runtime, such as `containerd`, is a background service. It also moves images and supervises containers <Cite n={17} /> <Cite n={5} />. By default, Docker Engine starts containerd, and containerd uses `runc` for most container work <Cite n={46} /> <Cite n={47} /> <Cite n={5} />.

Docker Engine has a long-running daemon, `dockerd` <Cite n={22} />. Podman has no daemon, and a normal user can run containers with it <Cite n={19} />. **Rootless** means that the runtime and the containers run as a normal user <Cite n={40} />.

Tutorial's own advice: log the engine and the runtime. A test that passes with Docker can fail with Podman or rootless, because file owners and privileges are different.

</Layman>
<Bangla>

**Container runtime** container process চালু করে এবং পরিচালনা করে <Cite n={5} />। এটি container আর operating system-এর মাঝে মধ্যস্থতাকারী হিসেবে কাজ করে, এবং namespace ও cgroup সেট করে <Cite n={2} /> <Cite n={5} />।

দুটি Open Container Initiative (OCI) standard গুরুত্বপূর্ণ। Image spec image-কে সংজ্ঞায়িত করে: একটি manifest, filesystem layer (file পরিবর্তনের সেট), এবং একটি configuration <Cite n={15} />। Runtime spec `config.json` file আর container lifecycle সংজ্ঞায়িত করে <Cite n={13} />। এর Linux অংশ বলে দেয় কোন namespace, cgroup, আর capability (root ক্ষমতার ছোট ছোট অংশ) সেট করতে হবে <Cite n={14} /> <Cite n={11} />।

`runc`-এর মতো low-level runtime একটি OCI bundle (`config.json` আর একটি root filesystem থাকা একটি folder) থেকে একটি container তৈরি করে <Cite n={16} /> <Cite n={5} />। `containerd`-এর মতো high-level runtime একটি daemon (background service), যা image আনা-নেওয়াও করে এবং container তত্ত্বাবধান করে <Cite n={17} /> <Cite n={5} />। Default হিসেবে Docker Engine containerd চালু করে, আর containerd বেশিরভাগ container-এর কাজে `runc` ব্যবহার করে <Cite n={46} /> <Cite n={47} /> <Cite n={5} />। CRI-O হলো Kubernetes-এর জন্য একটি runtime; Kubernetes-এর এমন runtime লাগে, যার Container Runtime Interface (CRI) আছে <Cite n={18} /> <Cite n={4} />।

Docker Engine-এর `dockerd` একটি long-running daemon <Cite n={22} />, আর rootless না হলে এই daemon-এর root লাগে <Cite n={39} />। Podman-এর কোনো daemon নেই, এবং একজন সাধারণ user এতে container চালাতে পারেন <Cite n={19} />। **Rootless** মানে runtime আর container একটি user namespace-এর ভেতরে সাধারণ user হিসেবে চলে <Cite n={40} />। এর জন্য `/etc/subuid` আর `/etc/subgid`-এ ID range লাগে <Cite n={40} /> <Cite n={20} />।

Tutorial-এর নিজস্ব পরামর্শ: engine আর runtime log করুন, যেমন `docker version` বা `podman --version`। Docker-এ pass করা একটি test Podman-এ বা rootless অবস্থায় fail করতে পারে, কারণ file owner আর privilege আলাদা হয়।

</Bangla>
</Voices>

## Docker

<Voices>
<Technical>

Docker Engine has a long-running daemon (`dockerd`) and the `docker` client. <Cite n={22} /> An **image** is a read-only template. A **container** is a runnable instance of it. <Cite n={21} /> Each Dockerfile instruction, such as `RUN` or `COPY`, adds a layer. <Cite n={21} /> <Cite n={23} /> 

A **volume** is storage that Docker manages. <Cite n={30} /> A **bind mount** shares a host path and is writable unless you add `ro`. <Cite n={31} /> `-p` publishes a port on all host interfaces, unless you give an address. <Cite n={24} /> On a user-defined network, containers reach each other by name. <Cite n={32} /> A tag can move, but a digest (the hash of the image) pins one exact image. <Cite n={35} /> `.dockerignore` keeps files out of the build context (files that the build can read). <Cite n={34} /> Compose starts several containers from one YAML file. <Cite n={36} /> Docker Desktop bundles the engine and runs its daemon in a Linux VM. <Cite n={37} /> <Cite n={31} />

`docker ps -a`, `logs`, `exec`, `stop`, and `rm` manage containers. <Cite n={25} /> <Cite n={26} /> <Cite n={27} /> By default, `stop` sends SIGTERM (ask to end), then SIGKILL (force end) after a timeout. <Cite n={28} /> <Cite n={29} />

```bash
# Illustration. registry.invalid is a name that cannot resolve: use your own image.
# Run it only where you may start containers. -p is HOST_IP:HOST_PORT:CONTAINER_PORT.
# Needs access to the Docker daemon, which runs as root unless it is rootless.
docker run -d --rm --name web1 -p 127.0.0.1:8080:80 registry.invalid/app:1.0
docker ps                    # CONTAINER ID 3f4e..., IMAGE registry.invalid/app:1.0, NAMES web1
docker logs --tail 20 web1   # the last 20 lines; add -f to follow
docker exec web1 ls /app     # one command in the running container
docker stop web1             # --rm removes the container after it stops
# Dockerfile lines: FROM alpine:<tag>@sha256:<digest>, COPY app /app, USER 1000, CMD ["/app/run"]
```

<Callout type="danger" title="Options that remove isolation or delete data">

Tutorial's own advice: avoid these options on a shared host:

- `--privileged`, `--pid host`, `--security-opt seccomp=unconfined`, and a mount of `/var/run/docker.sock` <Cite n={24} />
- `-v /:/host` <Cite n={39} />
- `--network host` <Cite n={32} />
- `docker rm -f` <Cite n={29} /> and `docker system prune -a` <Cite n={38} />, on things that you did not start

Run only trusted images. Set `USER` to avoid root. <Cite n={5} />

</Callout>

<Callout type="tip" title="Why it matters for testing">

Tutorial's own advice: pin the base image by digest. Publish ports on `127.0.0.1`: only the Docker host can reach them. <Cite n={33} /> Add `--rm` to remove finished containers. <Cite n={24} />

</Callout>

</Technical>
<Layman>

## Cgroups

<Voices>
<Technical>

A cgroup puts processes in a hierarchy of groups with limits and counters. <Cite n={6} /> A **controller** manages one resource: `cpu`, `memory`, `io` (`blkio` in v1), and `pids`. <Cite n={6} /> The interface is a file tree, usually at `/sys/fs/cgroup`. <Cite n={6} />

| | cgroup v1 | cgroup v2 |
|---|---|---|
| Trees | One for each controller, or shared <Cite n={6} /> | One unified tree <Cite n={6} /> |
| Memory limit | `memory.limit_in_bytes` <Cite n={12} /> | `memory.max` <Cite n={12} /> |
| `/proc/self/cgroup` | `ID:controllers:path` <Cite n={6} /> | `0::path` <Cite n={6} /> |

If a v2 cgroup reaches `memory.max` and cannot shrink, the OOM killer (the kernel's process killer) runs inside that cgroup. <Cite n={12} /> `cpu.max` caps CPU time and `pids.max` caps the number of tasks (processes and threads). <Cite n={12} /> Docker sets cgroup limits with `--memory`, `--cpus`, and `--pids-limit`. <Cite n={41} /> <Cite n={24} /> On cgroup v2, systemd uses `MemoryMax=`, and `systemd-run --scope` applies it to one command. <Cite n={42} /> <Cite n={43} /> `systemd-cgls` prints the cgroup tree. <Cite n={44} /> A cgroup namespace makes `/proc/self/cgroup` show paths from its own root. <Cite n={9} />

```bash
cat /proc/self/cgroup                   # v2: one line such as 0::/user.slice/... (an illustration)
systemd-cgls --no-pager | head -n 20    # the cgroup tree on a systemd host
# Documented, not run. Use a test host only:
#   docker run --memory=256m --cpus=0.5 --pids-limit=100 registry.invalid/app:1.0   # needs the Docker daemon
#   systemd-run --scope -p MemoryMax=256M ./suite.sh   # system scope: authentication or root
#   (cgroup v2; --user uses your own service manager)
```

<Callout type="danger" title="Do not change limits or kill the main process">

Tutorial's own advice: do not write into `/sys/fs/cgroup` on a shared host, because a wrong limit can kill services. `kill -9` gives the usual main process of a container no time to clean up. When it ends, the kernel kills every other process in its PID namespace. <Cite n={8} /> `docker stop` sends SIGTERM first. <Cite n={28} />

</Callout>

<Callout type="tip" title="Why it matters for testing">

Tutorial's own advice: test with the limits of CI. A low memory limit shows as an OOM kill in `memory.events`, not as a test error. A CPU limit shows as `nr_throttled` in `cpu.stat`. A `pids.max` limit makes `fork` (create a process) fail with `EAGAIN` (try again). <Cite n={12} />

</Callout>

</Technical>
