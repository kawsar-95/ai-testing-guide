# Disks and Filesystems

A disk is useless until you partition it, put a filesystem on it, and mount it. This stage covers that path, plus inodes, swap, and LVM. A tester needs it to find out why a CI runner is full, slow, or unable to boot. <Cite n={1} /> <Cite n={2} />

<PageMeta />

## Disks and Filesystems

A block device is a device that the kernel reads and writes in fixed-size blocks, such as a disk. A whole disk has a name like `/dev/sda`. A partition adds a number, as in `/dev/sda1`. <Cite n={15} /> A virtual disk may have another name, such as `/dev/xvdc`. <Cite n={9} /> `lsblk -N` lists only NVMe disks (a flash disk interface), and `lsblk -v` lists only virtio disks (virtual disks of a VM). <Cite n={14} />

A partition is a slice of a disk. The partition table records where each slice starts and ends, usually in sector 0. A sector is the unit in which a disk addresses its data. <Cite n={15} /> MBR (Master Boot Record, DOS) tables hold 4 primary partitions. One of them may be an extended partition that holds logical partitions. GPT (GUID Partition Table) is the modern standard, with checksums, UUIDs (unique IDs), and usually 128 partitions at most. <Cite n={15} /> MBR also limits a partition to 2 TB. <Cite n={2} />

A disk becomes usable in three steps: partition, make a filesystem, mount. <Cite n={8} /> `df` and `du` answer different questions. `df` reports the space of a whole filesystem. <Cite n={17} /> `du` adds up the space of the files below a path, so the two numbers can differ. `du -x` stays on one filesystem. <Cite n={18} /> `df -T` is a GNU option. <Cite n={17} />

```bash
lsblk -f                  # the tree: disks, partitions, filesystems, mount points
df -hT /                  # type and free space of the filesystem that holds /
du -xsh /var/log          # space used by the files below one path
```

<Callout type="tip" title="Why it matters for testing">

Tutorial's own advice: print `lsblk -f` and `df -hT` at the start of each CI job. When a test fails with "No space left on device", the log then shows which filesystem was full.

</Callout>

## Filesystems

A filesystem is the structure that stores file names, data, and metadata on a device. The kernel's virtual filesystem (VFS) layer sits above all types. <Cite n={4} /> `ext4` and `xfs` are journaling filesystems. `btrfs` is copy-on-write (changes go to new blocks), with snapshots and checksums. `vfat` is the FAT type. `tmpfs` keeps its files in memory. <Cite n={23} /> <Cite n={36} /> <Cite n={37} /> A journal is a log of metadata changes. After a crash, the kernel replays it to restore a consistent state. <Cite n={35} />

`/proc/filesystems` lists the types that the kernel supports. A `nodev` mark means that the type needs no block device. <Cite n={46} /> `stat -f` prints the block size and the number of inodes (file records) of a filesystem. <Cite n={25} /> Its type name can be vague, because `ext2`, `ext3`, and `ext4` share one type code. <Cite n={26} /> A block is the smallest unit that a filesystem allocates. <Cite n={3} /> The `overlay` filesystem stacks a writable layer on read-only layers. Docker uses it for container storage. <Cite n={39} /> <Cite n={50} />

`mkfs.<type>` builds a filesystem. Plain `mkfs` is a deprecated front end. <Cite n={32} />

<Callout type="danger" title="mkfs destroys the old data">

`mkfs` tools erase the start of the device, so the old filesystem is lost. <Cite n={30} /> Run `lsblk -f` first. Check the name and mount point. `mke2fs -n` and `wipefs -n` show a plan and change nothing. <Cite n={33} /> <Cite n={34} />

</Callout>

```bash
cat /proc/filesystems                       # the types that this kernel knows
findmnt -no FSTYPE /                        # the type of the root filesystem
stat -f -c 'block=%S free=%f inodes=%c' /   # GNU stat: block size, free blocks, inodes
# mkfs.ext4 -n /dev/sdX1                    # needs root; -n = dry run; sdX1 is a fake name
```

<Callout type="tip" title="Why it matters for testing">

Tutorial's own advice: test the full-disk case on purpose. Writes to `/dev/full` always fail with `ENOSPC`, "No space left on device". <Cite n={52} /> Run `echo x > /dev/full; echo $?` to see how your code reacts.

</Callout>

## Inodes

An inode is a record that holds the metadata of one file. It stores the device, the inode number, the type and mode, the link count, the owner, the size, and the timestamps. <Cite n={24} /> It does not store the file name. A directory entry links a name to an inode number. <Cite n={5} /> <Cite n={3} />

`ls -i` prints the inode number of each file. <Cite n={27} /> `stat` shows it with `%i`, and the link count with `%h`. <Cite n={25} /> A hard link is a second name for the same inode. `ln` makes a hard link by default. <Cite n={28} /> Inode numbers are unique only within one filesystem, so a hard link cannot cross filesystems. <Cite n={24} />

A filesystem can run out of inodes while it still has free space. This happens with very many small files. `df -i` shows the inode use. <Cite n={17} /> <Cite n={6} /> On `ext4`, the number of inodes is set when the filesystem is made. `mke2fs -i` sets the bytes per inode, and `-N` sets the count. <Cite n={33} /> A `tmpfs` has its own limit, `nr_inodes`. <Cite n={38} />

```bash
d=$(mktemp -d) || exit 1               # a fresh demo directory, safe to run twice
cd "$d" || exit 1
echo data > a.txt
ln a.txt b.txt                         # a second name for the same inode
ls -i a.txt b.txt                      # the same inode number twice
stat -c '%i inode, %h links' a.txt     # GNU stat -c
df -i .                                # inode use of this filesystem
rm -f a.txt b.txt; cd / && rmdir "$d"  # remove only the demo files
```

<Callout type="tip" title="Why it matters for testing">

Tutorial's own advice: a test that makes thousands of tiny files can fill the inodes and not the bytes. Add `df -i` to the failure report. Keep test data in one archive when you can.

</Callout>

## Mounts

A mount point is a directory where a filesystem is attached to the tree. A new mount hides the old contents of that directory. <Cite n={20} /> <Cite n={7} /> `findmnt` prints the mounts as a tree, and `findmnt --target /path` shows the filesystem of a path. <Cite n={19} /> `/proc/mounts` lists the mounts that the current process sees, in `fstab` format. <Cite n={47} />

`/etc/fstab` has one filesystem per line, with six fields. <Cite n={22} />

| Field | Meaning |
|---|---|
| 1 | Device, `UUID=`, or `LABEL=` |
| 2 | Mount point |
| 3 | Type |
| 4 | Options, such as `ro`, `noexec`, `nofail` |
| 5, 6 | `dump` backup flag; `fsck` (disk check) order |

`ro` mounts read-only. `noexec` blocks direct execution of programs. `nofail` hides the error when the device is absent. <Cite n={20} /> A bind mount shows a directory at a second place. <Cite n={20} /> A `tmpfs` mount lives in memory. <Cite n={38} /> Its size counts against the memory limit of a container. <Cite n={51} /> `umount` fails with "busy" when a process uses the filesystem. <Cite n={21} />

<Callout type="danger" title="Mount and unmount with care">

`umount -f` is for an unreachable NFS (network filesystem) share and may still hang. `umount -l` detaches a busy filesystem now and cleans up later. <Cite n={21} /> Find the user with `fuser -m` first. <Cite n={45} /> Run `findmnt --target /path` before you mount over a directory that has files.

</Callout>

```bash
findmnt --target /tmp -o TARGET,SOURCE,FSTYPE,OPTIONS   # which filesystem holds /tmp
# fuser -m /mnt/data                              # needs root for other users; who blocks umount?
# mount -t tmpfs -o size=256m tmpfs /mnt/fast     # needs root; a RAM-backed test directory
```

<Callout type="tip" title="Why it matters for testing">

Tutorial's own advice: put build and test scratch files on a `tmpfs` for speed. Set `size=` to cap the memory use.

</Callout>

## Adding Disks

Add a disk in a fixed order. Each step needs the result of the step before it.

1. Identify the new disk with `lsblk -f`. It shows no filesystem and no mount point. <Cite n={14} />
2. Partition it with `fdisk`. It edits the table in memory, `w` writes it, and `q` quits without saving. <Cite n={15} /> <Cite n={9} />
3. Make a filesystem with `mkfs.ext4` or another `mkfs.<type>`. <Cite n={8} /> <Cite n={32} />
4. Create a mount point and mount the partition. <Cite n={20} />
5. Read the UUID with `blkid` or `lsblk -f`. Device names follow the order of detection and can change. Use `UUID=` in `/etc/fstab`. <Cite n={16} /> <Cite n={22} />
6. Check `/etc/fstab` before a reboot. `findmnt --verify` is the recommended check, and the manual calls `mount -a` a bad way to check. <Cite n={19} /> <Cite n={20} />

`defaults` means the usual options. Add `nofail` for a disk that the boot does not need. <Cite n={22} />

```bash
lsblk -f                  # 1. read-only: the new disk has no FSTYPE and no MOUNTPOINTS
# All lines below need root. /dev/sdX is a fake name: replace it with your checked device.
# fdisk /dev/sdX          # 2. partition: n, then w to write
# mkfs.ext4 /dev/sdX1     # 3. make the filesystem (ERASES the partition)
# mkdir -p /mnt/data && mount /dev/sdX1 /mnt/data   # 4. mount
# blkid /dev/sdX1         # 5. read the UUID
# UUID=<uuid>  /mnt/data  ext4  defaults,nofail  0  2   # the line to add to /etc/fstab
findmnt --verify          # 6. read-only check of /etc/fstab
```

<Callout type="danger" title="The wrong device name destroys data">

`fdisk` rewrites the partition table, and `mkfs` erases the start of the partition. <Cite n={15} /> <Cite n={30} /> Both act on the device that you name. Without `nofail`, a failing `/etc/fstab` line can stop the boot. <Cite n={53} /> Check the name with `lsblk -f`, keep a backup, and test the file before you reboot.

</Callout>

<Callout type="tip" title="Why it matters for testing">

Tutorial's own advice: practice on a throw-away virtual machine with a spare virtual disk. Never practice on the disk of a shared runner.

</Callout>

## Swap

Swap is disk space that the kernel uses when memory is short. It can be a partition or a file. <Cite n={10} /> `swapon --show` lists the active swap areas. `free -h` shows memory and swap use. `/proc/swaps` has the same list. <Cite n={29} /> <Cite n={31} /> <Cite n={48} />

A new swap area needs two steps: `mkswap` prepares it, and `swapon` starts it. <Cite n={30} /> A swap file must not have holes (unwritten gaps). `cp` and `truncate` make files with holes, and `swapon` rejects them. The portable way to make the file is `dd` with `/dev/zero`. <Cite n={29} /> <Cite n={11} /> To keep swap after a reboot, add an entry of type `swap` to `/etc/fstab`. <Cite n={29} />

In the latest kernel docs, `vm.swappiness` takes 0 to 200, and the default is 60. Older kernels may allow a smaller range. A low value tells the kernel that swap IO is costly. <Cite n={40} /> When the kernel runs out of memory, the OOM killer ends a process. <Cite n={40} /> A higher `oom_score` means a more likely victim. <Cite n={49} />

```bash
swapon --show                  # active swap areas
free -h                        # memory and swap, human units
cat /proc/swaps                # the same areas, from the kernel
cat /proc/sys/vm/swappiness    # the current swappiness
cat /proc/self/oom_score       # the OOM score of this shell
```

<Callout type="danger" title="Swap commands can lose data">

`mkswap` erases the start of its target, so run it only on a checked partition or a new file. <Cite n={30} /> `swapoff` needs enough free memory to take the swapped pages back. Without it, `swapoff` fails with an out-of-memory status. <Cite n={29} />

</Callout>

<Callout type="tip" title="Why it matters for testing">

Tutorial's own advice: record `free -h` in the test logs. A runner with no swap may kill a test with the OOM killer, and a runner with swap may only run slowly. A container also counts `tmpfs` against its memory limit. <Cite n={51} />

</Callout>

## LVM

LVM (Logical Volume Manager) builds virtual block devices from physical devices. A physical volume (PV) is a disk or partition given to LVM. A volume group (VG) is a pool of PVs. A logical volume (LV) is a part of a VG that acts like a partition: you format it and mount it. <Cite n={41} /> <Cite n={13} /> An extent is the smallest unit of storage that LVM allocates. <Cite n={13} /> <Cite n={42} />

`pvs`, `vgs`, and `lvs` report on each layer. <Cite n={41} /> They only report.

`lvextend` grows an LV from the free extents of its VG. With `-r` it also resizes the filesystem. <Cite n={43} /> `ext4` can be resized online (mounted) or offline. <Cite n={35} /> A snapshot is a frozen image of an LV, for example for a backup. `lvcreate -s` makes one. <Cite n={42} /> The main gain is resizing without repartitioning. <Cite n={12} /> In this tutorial's view, the costs are one more layer to learn and a VG that can span several disks.

```bash
pvs                          # needs root and the lvm2 tools; physical volumes
vgs                          # volume groups
lvs                          # logical volumes
# All lines below need root. vg0 and data are example names.
# lvcreate -L 10G -n data vg0          # a new LV of 10 GiB
# lvextend -r -L +5G vg0/data          # grow the LV and its filesystem
# lvcreate -s -L 1G -n snap vg0/data   # a snapshot with 1 GiB for changes
```

<Callout type="danger" title="Resizing an LV can lose data">

`lvreduce` destroys the data in the removed area. Shrink the filesystem first, and back up before you try. <Cite n={44} /> `lvcreate` and `lvextend` take free extents from the VG, and `lvextend -r` changes a filesystem. <Cite n={42} /> <Cite n={43} /> Run `vgs` and `lvs` first. Check the names before any `lvreduce` or `lvremove`.

</Callout>

<Callout type="tip" title="Why it matters for testing">

Tutorial's own advice: take a snapshot before a destructive test run, so that you keep the data from before the test. Remove the snapshot afterwards, because it holds space.

</Callout>
