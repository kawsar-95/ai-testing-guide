# Processes

A process is a running program. This stage shows how to list processes, run them in the background, stop them with signals, set their priority, and limit what they use. A tester needs these skills because test runs start browsers, servers, and helper programs. When a run hangs, leaves stray processes, or fails with `Too many open files`, the process tools show the cause. <Cite n={1} />

<PageMeta />

## Process Management

<Voices>
<Technical>

**Goal:** Read the PID, the parent PID, and the state of a process.

A process is a program in execution. <Cite n={2} /> Each process has a PID (process ID), a unique number. <Cite n={31} /> Its PPID is the PID of its parent, the process that created it. <Cite n={31} /> In a shell, `$$` is the PID of the shell, and `$!` is the PID of the last background command. <Cite n={46} /> Linux shows each live process as a directory `/proc/PID`. <Cite n={3} /> The file `status` in it holds the name, the PID, the PPID, and a state letter. <Cite n={26} />

```bash
ps -o pid,ppid,args -p $$
```

**Try it:** start a `sleep` of your own in the background, read its `status` file, and stop it.

```bash
(                     # a subshell: your own shell does not change
  sleep 30 &          # a demo process of your own
  child=$!            # $!: the PID of the last background command
  sleep 1             # let the shell start sleep
  grep -E '^(Name|State|Pid|PPid):' /proc/"$child"/status
  kill "$child"; wait "$child"    # clean up
)
# Name:   sleep
# State:  S (sleeping)
# Pid:    34628
# PPid:   34627
# The PIDs are stand-ins. Your numbers differ.
```

<Callout type="tip" title="Why it matters for testing">

Tutorial's own advice: list the processes at the start and at the end of a CI job. A new process that is still alive after the suite is a leak.

</Callout>

<details>
<summary>Go deeper</summary>

- The PID and the PPID stay the same when the process starts a new program with `execve`. <Cite n={31} />
- A daemon is a background process that runs without a terminal, such as a web server. <Cite n={4} />
- The files in `/proc` are virtual: `ls -l` shows size 0, but they hold live data. <Cite n={5} />
- The tools of this page fall in three groups: monitor (`top`, `ps`), control (`bg`, `fg`, `kill`), and priority (`nice`, `renice`). <Cite n={2} />

The state letters in `status` <Cite n={26} /> <Cite n={25} />:

| Letter | State |
|---|---|
| `R` | Running |
| `S` | Sleeping |
| `D` | Waits on the disk |
| `T` | Stopped |
| `Z` | Zombie: the process ended, but it still waits for its parent |

Tutorial's own advice: save the output of `ps -eo pid,ppid,stat,etime,args` at the start and at the end of a CI job, and compare the two lists. A leaked process can break the next run on the same runner.

</details>

## Listing and Finding Processes

<Voices>
<Technical>

**Goal:** Find a process by its command line, and get its PID.

`ps` prints a snapshot of the processes. <Cite n={16} /> By default, it shows only your own processes on the current terminal. <Cite n={16} /> `ps -ef` shows all processes. <Cite n={16} /> `pgrep` prints the PIDs of the processes whose name matches a pattern (an extended regular expression). <Cite n={17} /> Its exit status (the number a command returns) is 0 for a match and 1 for no match. <Cite n={17} />

```bash
ps -ef
```

**Try it:** start a `sleep` of your own, find it with `pgrep`, then look for a name that does not exist. `-f` matches the whole command line, `-a` prints it, and `-x` demands an exact name. <Cite n={17} />

```bash
(                                # a subshell: your own shell does not change
  sleep 301 &
  pid=$!
  sleep 1                        # let the shell start sleep
  pgrep -a -f '^sleep 301$'      # ^ and $: the start and the end of the line
  pgrep -x no-such-program       # prints nothing
  echo "exit status: $?"         # $?: the exit status of the last command
  kill "$pid"; wait "$pid"       # clean up
)
# 34705 sleep 301
# exit status: 1
# 34705 is a stand-in PID.
```

<Callout type="tip" title="Why it matters for testing">

Tutorial's own advice: wait for a service with `pgrep -x NAME` and its exit status, not a fixed `sleep`. Also check its port.

</Callout>

<details>
<summary>Go deeper</summary>

- `ps aux` uses BSD options, written without a dash. The procps `ps` accepts both styles. <Cite n={16} /> Other systems, such as macOS or BusyBox, may differ: check their man page.
- Choose the columns with `-o` and the order with `--sort`. <Cite n={16} />
- Without `-f`, `pgrep` counts only the first 15 characters of the name. <Cite n={17} />
- `pidof` prints the PIDs of a named program. <Cite n={35} /> `pstree -p` draws the tree of processes with PIDs. <Cite n={33} /> `top -b -n 1` prints one frame for a log. <Cite n={32} />

```bash
ps aux --sort=-%mem | head -n 3              # BSD options: largest memory use first
ps -eo pid,ppid,stat,etime,args --sort=-etime | head -n 5   # chosen columns, oldest first
pidof sleep                                  # PIDs of all programs named sleep
pstree -p $$                                 # the tree below this shell
top -b -n 1 | head -n 12                     # one batch frame of top
```

Tutorial's own advice:

- In a minimal container, install `procps` (Debian, Ubuntu) or `procps-ng` (RHEL), and `psmisc`.
- Poll a fixed number of times, then stop. A fixed `sleep` makes tests slow or flaky.
- A process can exist before it listens on its port, so also check the port.
- On a shared runner, a short pattern such as `java` can match other jobs, so use `-x`.

</details>

**লক্ষ্য:** Command line দিয়ে একটি process খুঁজুন, আর তার PID নিন।

`ps` process-গুলোর একটি snapshot print করে। <Cite n={16} /> Default হিসেবে এটি শুধু current terminal-এ আপনার নিজের process-গুলো দেখায়। <Cite n={16} /> `ps -ef` সব process দেখায়। <Cite n={16} /> `pgrep` সেই process-গুলোর PID print করে, যাদের নাম একটি pattern (extended regular expression)-এর সাথে মেলে। <Cite n={17} /> মিল পেলে এর exit status 0, না পেলে 1। <Cite n={17} />

**চেষ্টা করুন:** নিজের একটি `sleep` চালু করুন, `pgrep` দিয়ে সেটি খুঁজুন, তারপর এমন একটি নাম খুঁজুন যা নেই। `-f` পুরো command line মেলায়, `-a` সেটি print করে, আর `-x` হুবহু নাম চায়। <Cite n={17} />

```bash
(                                # a subshell: your own shell does not change
  sleep 301 &
  pid=$!
  sleep 1                        # let the shell start sleep
  pgrep -a -f '^sleep 301$'      # ^ and $: the start and the end of the line
  pgrep -x no-such-program       # prints nothing
  echo "exit status: $?"         # $?: the exit status of the last command
  kill "$pid"; wait "$pid"       # clean up
)
# 34705 sleep 301
# exit status: 1
# 34705 is a stand-in PID.
```

<Callout type="tip" title="টেস্টিং-এ কেন দরকার">

Tutorial-এর নিজস্ব পরামর্শ: Fixed `sleep` দিয়ে অপেক্ষা করবেন না। `pgrep -x NAME` আর তার exit status দিয়ে অপেক্ষা করুন, port-ও check করুন।

</Callout>

## Background and Foreground Processes

<Voices>
<Technical>

**Goal:** Run a command in the background, and stop it by its PID.

A foreground process owns the terminal, and the shell waits for it. A background process runs while the shell accepts new commands. End a command with `&` to start it in the background. <Cite n={7} /> The shell does not wait for it, and the status of the `&` command is 0. <Cite n={47} /> Press Ctrl+Z to stop a foreground command. <Cite n={6} /> Then `bg` resumes it in the background, and `fg` brings it back to the foreground. <Cite n={41} />

```bash
sleep 60 &
```

**Try it:** start a `sleep` in the background, list it with `jobs -l`, and stop it by its PID. `-l` adds the PID to the list. <Cite n={41} />

```bash
(                          # a subshell: your own shell does not change
  sleep 60 &               # & starts it in the background
  pid=$!                   # $!: the PID of the last background command
  jobs -l                  # [1]+ 34718 Running    sleep 60 &
  kill "$pid"; wait "$pid" # clean up
  jobs -l                  # prints nothing: the job is gone
)
# 34718 is a stand-in PID.
```

<Callout type="tip" title="Why it matters for testing">

Tutorial's own advice: in CI, save the PID of a background helper from `$!`, send its output to a file, and stop it by that PID at the end.

</Callout>

<details>
<summary>Go deeper</summary>

- `%1` names job 1, for example `fg %1`. <Cite n={41} /> <Cite n={40} />
- In a script, use PIDs with `kill` and `wait`: job numbers may fail in `sh`. <Cite n={44} /> <Cite n={41} />
- A background job can die when the terminal closes, because Bash gets SIGHUP (the hangup signal) and resends it to its jobs. <Cite n={44} />

Three tools prevent this:

| Tool | What it does |
|---|---|
| `nohup` | Runs a command with hangup signals ignored. It appends the output to `nohup.out` when standard output is a terminal. <Cite n={45} /> |
| `disown -h` | Tells the shell not to send SIGHUP to a job. <Cite n={41} /> |
| `setsid` | Starts a program in its own session, a separate group of processes not tied to your terminal. <Cite n={36} /> |

```bash
nohup sleep 60 > nohup-demo.log 2>&1 &                  # survives a hangup
setsid sleep 60 > setsid-demo.log 2>&1 < /dev/null &    # own session
# Both demos end after 60 s. Then delete the two .log files.
```

Tutorial's own advice: check whether your CI system ends the processes of a step at its end before you rely on a background job between steps.

</details>

</Technical>

## Killing Processes

<Voices>
<Technical>

**Goal:** Stop a process of your own: SIGTERM first, and SIGKILL only if it still lives.

The command `kill` sends a signal, and it does not always kill. <Cite n={18} /> The default signal is SIGTERM, which a program can handle to clean up before it exits. <Cite n={18} /> SIGKILL cannot be caught, so the program cannot clean up. <Cite n={18} /> Send SIGTERM first, wait, and use SIGKILL only if the process lives. <Cite n={10} /> Signal 0 sends nothing, but checks that the PID exists and that you may signal it. <Cite n={18} /> Never run `kill -9 -1`: PID -1 means every process with a PID above 1 that you may signal. <Cite n={18} />

```bash
kill "$pid"
```

**Try it:** start a `sleep` of your own, send SIGTERM, and send SIGKILL only if it still lives.

```bash
(                                    # a subshell: your own shell does not change
  sleep 302 &                        # a demo target of your own
  pid=$!                             # $!: the PID of the last background command
  kill "$pid"                        # SIGTERM, the default signal
  sleep 1
  kill -0 "$pid" 2>/dev/null && kill -KILL "$pid"   # -0: only check; 2>/dev/null hides the error
  wait "$pid"                        # clean up
  kill -0 "$pid" 2>/dev/null || echo "process $pid is gone"
)
# process 33402 is gone
# 33402 is a stand-in PID.
```

<Callout type="tip" title="Why it matters for testing">

Tutorial's own advice: in teardown, stop only the PIDs that your job started. Do not run `pkill node` on a shared runner.

</Callout>

<details>
<summary>Go deeper</summary>

- Bash has a builtin `kill` (a command inside the shell), and the system has a separate program, often `/bin/kill`. <Cite n={9} />
- `pkill` signals the processes that `pgrep` lists. <Cite n={17} />
- `killall` signals every process that has a given name. On non-Linux systems, `killall name` may act differently. <Cite n={34} />

Safety rules. `kill -9` gives no clean-up. `killall` and `pkill` signal many processes at once, with no undo, and a wrong PID or pattern can stop the CI agent.

- Take the PID from `$!` or `pgrep -a`. The kernel can reuse a PID after a process exits. <Cite n={3} />
- Run `pgrep -a` with the same pattern before `pkill`.
- `-f` also matches the command line of a wrapper such as `sh -c 'pkill -f x'`. <Cite n={17} />

```bash
pgrep -a -f 'sleep 301'                # see which processes the pattern matches
# pkill -f 'sleep 301'                 # same match, only after you checked it
```

Tutorial's own advice: keep the PID of each process that your job starts in a variable or a file. Do not run `killall chrome` on a shared runner, because other jobs run there.

</details>

</Technical>

## Process Signals

<Voices>
<Technical>

**Goal:** Freeze, continue, and end a process with signals.

A signal is a short message that the kernel or another process sends to a process. Each signal has a name, a number, and a default action: `Term` (end the process), `Stop`, or `Cont` (continue). <Cite n={19} /> A process cannot catch, block, or ignore SIGKILL or SIGSTOP. <Cite n={19} /> In Bash, a process that a signal ended has an exit status of 128 plus the signal number, so SIGTERM (15) gives 143. <Cite n={49} /> <Cite n={19} />

```bash
kill -l
```

**Try it:** freeze your own `sleep` with SIGSTOP, continue it with SIGCONT, and end it with SIGTERM. A frozen process still holds its files and locks, so always continue or end it.

```bash
(                                                    # a subshell: your own shell does not change
  sleep 303 &
  pid=$!
  sleep 1                                            # let the shell start sleep
  kill -STOP "$pid"; ps -o pid,stat,args -p "$pid"   # STAT T: stopped
  kill -CONT "$pid"; ps -o pid,stat,args -p "$pid"   # STAT S: sleeping
  kill "$pid"; wait "$pid"                           # clean up
  echo "exit status: $?"                             # $?: the exit status of wait
)
#     PID STAT COMMAND
#   33424 T    sleep 303
#     PID STAT COMMAND
#   33424 S    sleep 303
# exit status: 143
# 33424 is a stand-in PID.
```

<Callout type="tip" title="Why it matters for testing">

Tutorial's own advice: add a `trap` for `INT` and `TERM` to a test-runner script. Without it, a cancelled CI job can leave helpers alive.

</Callout>

<details>
<summary>Go deeper</summary>

A process can use the default action, ignore the signal, or catch it with a handler (a function that runs when the signal arrives). <Cite n={19} /> `kill -l` lists the names (Bash also prints the numbers). <Cite n={18} /> <Cite n={8} />

| Signal | Number (x86, ARM) | Default | Meaning |
|---|---|---|---|
| `SIGHUP` | 1 | Term | Hangup; some daemons reload <Cite n={19} /> <Cite n={9} /> |
| `SIGINT` | 2 | Term | Ctrl+C <Cite n={19} /> <Cite n={11} /> |
| `SIGTERM` | 15 | Term | Polite stop <Cite n={19} /> |
| `SIGKILL` | 9 | Term | Forced stop <Cite n={19} /> |
| `SIGSTOP` | 19 | Stop | Freeze <Cite n={19} /> |
| `SIGTSTP` | 20 | Stop | Ctrl+Z <Cite n={19} /> <Cite n={48} /> |
| `SIGCONT` | 18 | Cont | Resume <Cite n={19} /> |

`trap` runs a command when the shell gets a signal, and the name `EXIT` runs it when the shell ends. <Cite n={43} /> It is part of the POSIX shell, so it works in `sh`. <Cite n={43} /> This script cleans up when it gets SIGTERM or SIGINT:

```bash
(
  cd "$(mktemp -d)"
  cat > trap-demo.sh <<'EOF'
#!/bin/sh
tmp=$(mktemp)
cleanup() { [ -n "$child" ] && kill "$child" 2>/dev/null; rm -f "$tmp"; echo "cleaned up"; exit 0; }
trap cleanup INT TERM
sleep 304 &
child=$!
wait "$child"
EOF
  sh trap-demo.sh & demo=$!
  sleep 1; kill -TERM "$demo"; wait "$demo"    # prints: cleaned up
  rm -f trap-demo.sh; cd ..; rmdir "$OLDPWD"
)
```

Tutorial's own advice: if a CI system cancels a job with a signal and the script has no trap, the helpers stay alive. Then the next run may fail on a busy port.

**Goal:** Freeze, continue, and end a process with signals.

A signal is a short message to a process from the kernel or from another process. Each signal has a name, a number, and a default action: `Term` (end the process), `Stop`, or `Cont` (continue). <Cite n={19} /> A process cannot catch, block, or ignore SIGKILL or SIGSTOP. <Cite n={19} /> In Bash, if a signal ends a process, the exit status is 128 plus the signal number. So SIGTERM (15) gives 143. <Cite n={49} /> <Cite n={19} />

**Try it:** freeze your own `sleep` with SIGSTOP, continue it with SIGCONT, and end it with SIGTERM. A frozen process still holds its files and locks, so always continue or end it.

```bash

  sleep 303 &
  pid=$!
  sleep 1                                            # let the shell start sleep
  kill -STOP "$pid"; ps -o pid,stat,args -p "$pid"   # STAT T: stopped
  kill -CONT "$pid"; ps -o pid,stat,args -p "$pid"   # STAT S: sleeping

)
#     PID STAT COMMAND
#   33424 T    sleep 303
#     PID STAT COMMAND
#   33424 S    sleep 303
# exit status: 143

```

## Process Priorities

<Voices>
<Technical>

**Goal:** Run a command with a lower CPU priority, and change it while it runs.

The scheduler is the part of the kernel that picks which process runs on a CPU. The niceness of a process tells the scheduler how much to favor it. On Linux it runs from -20 (most favor) to 19 (least favor), and the default is 0. <Cite n={38} /> <Cite n={20} /> <Cite n={12} /> A higher number means a nicer process, which takes less CPU when others compete. <Cite n={12} /> `nice -n 10 command` starts a command with 10 added to the niceness. <Cite n={20} /> `renice` changes a process that already runs. <Cite n={21} />

```bash
ps -o pid,ni,args -p $$
```

**Try it:** start your own `sleep` with niceness 10, then raise it to 15 with `renice`. The `NI` column of `ps` shows the niceness.

```bash
(                                # a subshell: your own shell does not change
  nice -n 10 sleep 60 &          # start sleep with niceness 10
  pid=$!
  sleep 1                        # let nice start sleep
  ps -o pid,ni,args -p "$pid"
  renice 15 -p "$pid"            # raise it to 15
  ps -o pid,ni,args -p "$pid"
  kill "$pid"; wait "$pid"       # clean up
)
#     PID  NI COMMAND
#   33506  10 sleep 60
# 33506 (process ID) old priority 10, new priority 15
#     PID  NI COMMAND
#   33506  15 sleep 60
# 33506 is a stand-in PID.
```

<Callout type="tip" title="Why it matters for testing">

Tutorial's own advice: before you raise a timeout, look in `top` for other jobs. Run heavy helper work under `nice -n 10`.

</Callout>

<details>
<summary>Go deeper</summary>

- With no command, `nice` prints the current niceness. <Cite n={20} />
- A normal user can only change their own processes, and can usually only raise the niceness, not lower it again. Negative values usually need root. <Cite n={21} />
- **Warning:** do not use negative niceness for tests. `nice -n -5` and `renice -5` usually need root and can starve the rest of the system. <Cite n={21} /> `renice -u USER` changes every process of a user. <Cite n={21} /> Practice only on a `sleep` that you started yourself.
- Note on `renice -n 5`: the util-linux tool sets the absolute value 5, but POSIX says relative. Write `renice 5 -p PID` to be clear. <Cite n={21} />
- `ionice` sets the priority of disk I/O, and class 3 is idle. Its man page describes the CFQ I/O scheduler, so check that your kernel honors it. <Cite n={22} />

```bash
nice -n 10 ionice -c 3 sleep 60 &         # CPU niceness 10 and idle I/O class
ionice -p $!                              # prints: idle
kill $!                                   # clean up
```

Tutorial's own advice: timeouts often fail because of CPU competition, not because the product is slow.

</details>

## Process Forking

<Voices>
<Technical>

**Goal:** See that a child gets its own PID, and that `exec` keeps that PID.

<details>
<summary>Go deeper</summary>

- Fork then `execve` is the classic way to start a new program. <Cite n={13} />
- The parent should call `wait` to collect the exit status of a child. <Cite n={25} />
- A child that ended but was not waited for is a zombie. It keeps only a table entry. <Cite n={25} />
- A signal cannot remove a zombie. The parent must wait, or end. Then `init` (PID 1) adopts the zombie and removes it. <Cite n={25} />
- An orphan is a running process whose parent has ended. <Cite n={4} /> The kernel gives it to the `init` process of its PID namespace, or to a subreaper (a volunteer adopter). <Cite n={39} /> A PID namespace is a separate set of PIDs, like in a container.
- `fork` fails with `EAGAIN` at a process limit like `RLIMIT_NPROC`. <Cite n={23} />

```bash

sh -c 'sleep 1 & exec sleep 30' &
parent=$!
sleep 2
ps -o pid,ppid,stat,args --ppid "$parent"           # the child shows Z and <defunct>
# Orphan: the shell ends at once; sleep 30 stays with a new parent.
orphan=$(sh -c 'sleep 30 > /dev/null 2>&1 & echo $!')
ps -o pid,ppid,stat,args -p "$orphan"               # PPID is now init or a subreaper
ps -eo pid,ppid,stat,args | awk '$3 ~ /^Z/'         # list all zombies on the host
kill "$parent" "$orphan"                            # clean up
```

<Callout type="tip" title="টেস্টিং-এ কেন দরকার">

Tutorial-এর নিজস্ব পরামর্শ: Test run-এর পরে zombie খুঁজুন। Container-এ PID 1 হিসেবে চলা test command হয়তো কখনো `wait` call করে না।

</Callout>

<details>
<summary>আরও জানুন</summary>

- প্রথমে fork, তারপর `execve`: এটিই নতুন program শুরু করার classic উপায়। <Cite n={13} />
- Child-এর exit status সংগ্রহ করতে parent-এর `wait` call করা উচিত। <Cite n={25} />
- যে child শেষ হয়েছে কিন্তু যার জন্য parent অপেক্ষা করেনি, সেটি zombie; এর শুধু একটি table entry থাকে। <Cite n={25} />
- Signal দিয়ে zombie সরানো যায় না। Parent-কে wait করতে হবে, অথবা শেষ হতে হবে; তখন `init` (PID 1) zombie-টিকে গ্রহণ করে সরিয়ে দেয়। <Cite n={25} />
- Orphan হলো এমন একটি চলমান process, যার parent শেষ হয়ে গেছে। <Cite n={4} /> Kernel এটিকে তার PID namespace-এর `init` process-কে দেয়, অথবা একটি subreaper-কে (যে process স্বেচ্ছায় দত্তক নেয়)। <Cite n={39} /> PID namespace হলো PID-এর একটি আলাদা set, যেমন একটি container-এ।
- `RLIMIT_NPROC`-এর মতো process limit-এ পৌঁছালে `fork` `EAGAIN` দিয়ে fail করে। <Cite n={23} />

Tutorial-এর নিজস্ব পরামর্শ: container-এ PID 1 কখনো `wait` না করলে zombie জমে যায়। <Cite n={39} /> আপনার test command-এর সামনে একটি ছোট init program রাখুন।

## Ulimits

<Voices>
<Technical>

**Goal:** Read the open-file limit, and see the error at the limit.

A resource limit caps what one process may use, such as open files or memory. <Cite n={29} /> Each limit has a soft value, which the kernel enforces, and a hard value, which is the ceiling for the soft value. <Cite n={29} /> `ulimit` is a shell builtin for the limits of the shell and its programs, and `-n` is the number of open file descriptors. <Cite n={42} /> Above that limit, `open` fails with `EMFILE`, shown as `Too many open files`. <Cite n={29} /> <Cite n={14} /> Never lower limits in your login shell: a low `ulimit -u` makes `fork` fail. <Cite n={29} />

```bash
ulimit -n
```

**Try it:** lower the limit to 20 in a subshell, and open a file until it fails.

```bash
(                          # a subshell: the low limit stays in it
  ulimit -n 20
  for i in $(seq 1 30); do
    exec {fd}</etc/passwd || { echo "open number $i failed"; break; }   # bash: open on a new descriptor
  done
)
ulimit -n                  # unchanged outside the subshell
# bash: redirection error: cannot duplicate fd: Too many open files
# bash: /etc/passwd: Too many open files
# open number 11 failed
# 524288
# The last number is the limit of the test machine. Yours can differ.
```

<Callout type="tip" title="Why it matters for testing">

Tutorial's own advice: when a suite fails with `Too many open files`, count the descriptors in `/proc/PID/fd` first. Fix the leak, then raise the limit. <Cite n={28} />

</Callout>

<details>
<summary>Go deeper</summary>

- A child inherits the limits. <Cite n={29} />
- A normal user can raise the soft limit up to the hard limit. A user can lower the hard limit, but not raise it. <Cite n={29} /> <Cite n={15} />
- `ulimit -a` prints all limits. <Cite n={42} /> <Cite n={14} /> A file descriptor is a number for an open file, socket, or pipe. `-u` is the number of processes. <Cite n={42} />
- `-S` and `-H` choose soft or hard. Without them, a change sets both. <Cite n={42} />
- For a running process, read `/proc/PID/limits`. <Cite n={27} />
- For a permanent value for logins, add a line `domain type item value` to `/etc/security/limits.conf`. <Cite n={30} /> Keep a second root session open while you edit it.
- A service that systemd starts takes its limits from its unit, such as `LimitNOFILE=` in `[Service]`. <Cite n={37} />

```bash
ulimit -Hn                               # hard limit of open files
grep 'open files' /proc/$$/limits        # the same data, from /proc
ls /proc/$$/fd | wc -l                   # descriptors that this shell has open now
```

Tutorial's own advice: print `ulimit -n` at the start of each CI job.

</details>

**লক্ষ্য:** Open file-এর limit পড়ুন, আর limit-এ পৌঁছালে কী error হয় দেখুন।

Resource limit ঠিক করে, একটি process সর্বোচ্চ কতটা ব্যবহার করতে পারবে, যেমন open file বা memory। <Cite n={29} /> প্রতিটি limit-এর একটি soft value থাকে, যা kernel প্রয়োগ করে, আর একটি hard value থাকে, যা soft value-এর ঊর্ধ্বসীমা। <Cite n={29} /> `ulimit` হলো shell আর তার program-গুলোর limit-এর জন্য একটি shell builtin, আর `-n` হলো open file descriptor-এর সংখ্যা। <Cite n={42} /> সেই limit পেরোলে `open` `EMFILE` দিয়ে fail করে, যা `Too many open files` হিসেবে দেখায়। <Cite n={29} /> <Cite n={14} /> নিজের login shell-এ কখনো limit কমাবেন না: কম `ulimit -u` থাকলে `fork` fail করে। <Cite n={29} />
