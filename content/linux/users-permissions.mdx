# Users and Permissions

This stage covers user accounts, groups, the root account, and file permissions. A tester needs it because many failures that read `Permission denied` are not product bugs. A CI runner (the machine that runs an automated job) may use the wrong account, or a fixture file may have the wrong owner. Test with the least privilege (the smallest set of rights) that works. <Cite n={1} />

<PageMeta />

## User Management

<Voices>
<Technical>

A Linux account is a line of data, not a folder. The file `/etc/passwd` holds one line for each account. It has seven colon-separated fields: name, password marker, UID, GID, comment, home directory, and login shell (the program that starts when the user logs in). <Cite n={2} /> The UID is the user ID, the number that the system uses to identify the account. The GID is the number of the primary group. UID 0 is the superuser, `root`. <Cite n={2} />

The name `passwd` misleads. On most systems it holds only an `x` in the password field. The password hash (the stored, one-way scramble of the password) lives in `/etc/shadow`. <Cite n={2} /> Regular users must not read that file. <Cite n={3} /> A hash that starts with `!` means that the password is locked. <Cite n={3} /> `getent` reads the account databases through the Name Service Switch libraries (the lookup layer of the system). <Cite n={15} />

```bash
id                              # your UID, primary GID, and groups
getent passwd "$USER"           # your line of the passwd database
ls -l /etc/passwd /etc/shadow   # the shadow file is not world-readable
```

<Callout type="tip" title="Why it matters for testing">

Tutorial's own advice: print `id` and `ls -ld .` at the start of a CI job. In a container, the UID of the runner often has no name. Files from the host can belong to a number that no account in the container uses. This mismatch causes many `Permission denied` errors.

</Callout>

</Technical>

## Users and Groups

<Voices>
<Technical>

A group is a named set of users. Admins use groups to give access to files and other resources. <Cite n={18} /> The file `/etc/group` has one line for each group: name, password field, GID, and a comma-separated list of members. <Cite n={4} /> Each account has one primary group, which is the GID in `/etc/passwd`. It can also join many supplementary groups (extra groups besides the primary one), which the member lists name. <Cite n={2} />

`id` prints the user, the primary group, and the supplementary groups. <Cite n={13} /> `groups` prints the same names as `id -Gn`. <Cite n={14} /> A session gets its groups at login. If an admin changes your groups later, `id` and `groups` still show the old list in that session. <Cite n={13} /> `id USER` reads the database again. <Cite n={13} /> `newgrp GROUP` changes the current group ID inside the session. It starts a new shell, and `exit` leaves it. <Cite n={12} /> <Cite n={39} /> `gpasswd -d USER GROUP` removes a member. <Cite n={11} /> `groupdel` cannot remove the primary group of an existing user. <Cite n={10} />

```bash
id                           # groups of this login session
id "$USER"                   # reads the group database again
groups                       # group names only, same as id -Gn
getent group "$(id -gn)"     # the /etc/group line of your primary group
newgrp qa                    # needs a group qa that lists you; starts a new shell
```

<Callout type="tip" title="Why it matters for testing">

Tutorial's own advice: test access control with two accounts, one inside the group and one outside it. The first must succeed. The second must get `Permission denied`. After a script changes a membership, start a new login, for example `sudo -iu USER`, before you test. <Cite n={21} /> An old session checks the old groups. A minimal container may lack `sudo`.

</Callout>

</Technical>

</Layman>

## Create, Update, and Delete Users

<Voices>
<Technical>

Three standard programs manage the life of an account. They need root, so run them as root or add `sudo`. `useradd` creates an account. `-m` makes the home directory and copies the files of `/etc/skel` into it. <Cite n={5} /> Without `-m`, the result depends on `CREATE_HOME` in `/etc/login.defs`. <Cite n={5} /> So pass `-m` or `-M` every time. A new account has a locked password until `passwd NAME` sets one. <Cite n={5} /> `groupadd NAME` makes a group. <Cite n={8} />

`usermod` changes an account. `-aG` adds supplementary groups, `-L` locks the password, and `-l` renames the login only. <Cite n={6} /> A locked password does not stop an SSH key login (a remote login with a key, not a password). To block the account, run `usermod --expiredate 1`. <Cite n={9} /> `userdel NAME` removes the account. `userdel -r` also removes the home directory and the mail spool (the file that holds the mail of the user). <Cite n={7} /> Debian and Ubuntu add `adduser`, a Debian front end for `useradd`. <Cite n={16} /> Use `useradd` in scripts that must run on every distribution.

```bash
sudo groupadd qa                                       # create a group first
sudo useradd -m -s /bin/bash -c "QA runner" qa-runner  # account with a home directory
sudo passwd qa-runner                                  # set a password (asks twice)
sudo usermod -aG qa qa-runner                          # -a keeps the old groups
sudo usermod -L qa-runner                              # lock the password
sudo userdel qa-runner                                 # remove the account, keep the home
```

<Callout type="danger">

`usermod -G` without `-a` replaces the whole list of supplementary groups. A user can lose `sudo` rights this way. <Cite n={6} /> <Cite n={17} /> `userdel -r` deletes the home directory with no undo. `userdel -f` skips safety checks and can leave the system in an inconsistent state. <Cite n={7} /> Use a disposable VM or container.

</Callout>

<Callout type="tip" title="Why it matters for testing">

Tutorial's own advice: create test users in a setup script and delete only the names that the script made. Do not pass `-p`: other users can see the password in the process list. <Cite n={5} />

</Callout>

</Technical>

তিনটি standard program একটি account-এর পুরো জীবনচক্র সামলায়। এগুলোর root দরকার, তাই root হিসেবে চালান অথবা `sudo` যোগ করুন। `useradd` একটি account তৈরি করে। `-m` দিলে এটি home directory বানায় এবং `/etc/skel`-এর file-গুলো সেখানে copy করে <Cite n={5} />। `-m` না দিলে ফলাফল নির্ভর করে `/etc/login.defs`-এর `CREATE_HOME`-এর ওপর <Cite n={5} />। তাই প্রতিবার `-m` অথবা `-M` দিন। `passwd NAME` password set না করা পর্যন্ত নতুন account-এর password locked থাকে <Cite n={5} />। `groupadd NAME` একটি group বানায় <Cite n={8} />।

`usermod` একটি account বদলায়। `-aG` supplementary group যোগ করে, `-L` password lock করে, আর `-l` শুধু login name বদলায় <Cite n={6} />। Password locked থাকলেও SSH key দিয়ে login বন্ধ হয় না। Account পুরোপুরি আটকাতে `usermod --expiredate 1` চালান <Cite n={9} />। `userdel NAME` account মুছে দেয়। `userdel -r` এর সাথে home directory এবং mail spool-ও (user-এর mail রাখার file) মুছে দেয় <Cite n={7} />। Debian এবং Ubuntu-তে `adduser` আছে, যা `useradd`-এর একটি Debian front end <Cite n={16} />। যে script সব distribution-এ চলতে হবে, সেখানে `useradd` ব্যবহার করুন।

সাবধান: `-a` ছাড়া `usermod -G` supplementary group-এর পুরো তালিকা বদলে দেয়, ফলে একজন user `sudo` অধিকার হারাতে পারেন <Cite n={6} />। `userdel -r` home directory মুছে দেয়, যা আর ফেরানো যায় না <Cite n={7} />। `-p` ব্যবহার করবেন না: process list-এ অন্য user-রা password দেখতে পারেন <Cite n={5} />।

</Bangla>

## Super User

<Voices>
<Technical>

The superuser is the account with UID 0, named `root`. <Cite n={2} /> Ubuntu disables the direct root login: it gives root a hash that matches no password. <Cite n={19} /> A Red Hat blog advises to lock root at install and to put admins in the `wheel` group. <Cite n={20} /> Ubuntu uses the `sudo` group for the same job. <Cite n={19} />

`sudo COMMAND` runs one command as root, or as another user with `-u`, if the sudoers policy allows it. <Cite n={21} /> `sudo -l` lists your rights. By default, sudo remembers your password for a few minutes in each terminal. The `timestamp_timeout` option of sudoers(5) sets the time. `-k` ends it, and `-n` fails instead of asking for input. <Cite n={21} /> Policies can log each attempt. <Cite n={21} />

Rules live in `/etc/sudoers` and in the files that its `@includedir` line reads, usually `/etc/sudoers.d`. The last matching rule wins. <Cite n={22} /> sudo skips file names that contain a `.` or end in `~`. <Cite n={22} /> `visudo` checks the syntax before it saves. <Cite n={23} />

```bash
id -u                                      # prints 0 only for root
sudo -l                                    # what may this account run through sudo?
sudo -n true && echo "sudo works without a password"
sudo visudo -f /etc/sudoers.d/qa-restart   # new drop-in file, syntax checked on save
# One narrow rule for that file (change the user, command, and path):
#   qa-runner ALL = (root) NOPASSWD: /usr/bin/systemctl restart myapp
sudo visudo -c                             # check /etc/sudoers and its includes
```

<Callout type="danger">

A syntax error in `/etc/sudoers` can stop sudo from working. You may then lose root access. <Cite n={22} /> Never edit the file with a plain editor. Use `visudo`. A rule with `NOPASSWD: ALL` gives full root to the user. <Cite n={22} /> Name exact commands with full paths.

</Callout>

<Callout type="tip" title="Why it matters for testing">

Tutorial's own advice: run the test suite as a normal user. Give a narrow rule only to the one setup step that needs root. Use `sudo -n` in CI, so a missing rule fails at once and does not wait for a password.

</Callout>

</Technical>

## File Permissions

<Voices>
<Technical>

Every file has an owner, a group, and mode bits (flags for access). Three classes use them: the owner (`u`), other members of the file's group (`g`), and everyone else (`o`). <Cite n={25} /> <Cite n={32} /> Each class can read (`r`), write (`w`), and execute (`x`). `ls -l` shows the file type first, then three `rwx` triplets. The type is `-` for a file, `d` for a directory, and `l` for a symbolic link (a file that points to another path). <Cite n={27} />

On a directory, `r` lists the names, `w` creates and removes entries, and `x` lets you reach the files inside. <Cite n={25} /> Write alone is not enough: removing a file also needs `x` on the directory. <Cite n={37} /> <Cite n={29} /> Octal mode (base 8 numbers) adds r=4, w=2, and x=1 for each class. So 640 means `rw-r-----`. <Cite n={26} />

Three special bits exist. Setuid (4000) runs a program with the effective user ID (the ID for permission checks) of the file owner. <Cite n={25} /> <Cite n={24} /> Setgid (2000) does the same for the group. On a directory, new files get the group of the directory. <Cite n={31} /> On a directory, the sticky bit (1000) lets unprivileged users remove or rename only their own files, or any file if they own the directory. <Cite n={25} /> `ls` shows these bits as `s` and `t`, or `S` and `T` when `x` is missing. <Cite n={27} />

```bash
touch report.txt                      # creates the file, or only updates its time
ls -l report.txt                      # -rw-rw-r-- (umask 002) or -rw-r--r-- (umask 022)

ls -l /usr/bin/passwd                 # -rwsr-xr-x: the s is the setuid bit
```

`stat -c` prints a chosen format. <Cite n={28} />

## Managing Permissions

<Voices>
<Technical>

`chmod` changes the mode. Use octal to set everything at once (`chmod 640 FILE`). Use symbolic form for one change (`chmod g-w FILE`). <Cite n={32} /> Only the owner of the file, or a privileged process, can change the mode. <Cite n={30} /> In `-R` runs, `X` gives execute permission only to directories and to files that are already executable. <Cite n={32} />

`chown OWNER:GROUP FILE` changes the owner and the group. `chgrp GROUP FILE` changes only the group. <Cite n={33} /> <Cite n={34} /> The umask (a mask that removes bits from the mode of new files) sets the default. A new file usually starts at 666, and the umask turns off its bits. So umask 022 gives 644. <Cite n={35} /> `umask` is a shell builtin (a command inside the shell). <Cite n={36} /> A subshell (a child copy of the shell) keeps the change local. <Cite n={38} />

```bash
mkdir -p shared-demo && touch shared-demo/run.sh
chmod 640 shared-demo/run.sh           # octal: owner rw-, group r--, others none
chmod u+x,g-w shared-demo/run.sh       # symbolic: add x for owner, remove w for group
chgrp "$(id -gn)" shared-demo/run.sh   # use a group that you belong to
chmod 2750 shared-demo                 # setgid directory: new files get its group
chmod -R g+rX,o-rwx shared-demo        # recursive, on a path that you made
(umask 077; touch private.txt)         # in a subshell: the file gets mode 600
ls -l shared-demo private.txt
```

<Callout type="danger">

`chmod -R 777` lets every user write every file in the tree. `chown -R` on a wrong path, such as `/etc`, can break the system. Check the path with `ls -ld` first. Do not combine `-R` with `-L`: it follows symbolic links and can change files outside the tree. <Cite n={30} /> Use `750` and `640` instead.

</Callout>

<Callout type="tip" title="Why it matters for testing">

Tutorial's own advice: give a shared artifact directory the mode `2770` and a group such as `qa`. Then all test users can write, and new files keep the group. Set `umask 077` in a script that writes secrets.

</Callout>

</Technical>

The middle panel at the bottom has the title "SUID Permission", but its command `chmod g+s directory_name` sets the setgid (set-group-ID) bit. On a directory, new files then get the group of the directory. <Cite n={32} /> <Cite n={31} />

A capital `S` or `T` is not an error. `S` means that the setuid or setgid bit is set and the matching execute bit is not set. `T` means that the sticky bit is set and the execute bit for others is not set. <Cite n={27} />

In the `rws` box, the `s` does not stand for execute alone. In the owner part, `s` means that the owner has execute permission and that the setuid bit is set. <Cite n={27} />

### Understanding Linux File Permissions

1. `Permission Types:`
   - `Read (r):` Permission to read the contents of the file. For directories, this allows listing files.
   - `Write (w):` Permission to modify the contents of the file. For directories, this allows creating or deleting files within the directory. Correction: on a directory, `w` works only together with `x` on that directory. <Cite n={43} /> <Cite n={37} />
   - `Execute (x):` Permission to execute the file as a program. For directories, this allows accessing files within the directory.

2. `User Classes:`
   - `Owner (u):` The user who owns the file.
   - `Group (g):` A group of users who have been granted access to the file.
   - `Others (o):` All other users who are not the owner or part of the group.

3. `Permission Representation:`
   - File permissions are displayed in a 10-character string when using the `ls -l` command. The format is:

     ```text
     -rwxrwxrwx
     ```

   - The first character indicates the file type (e.g., - for a regular file, d for a directory).
   - The next nine characters are divided into three sets of three:
     - First set (e.g., `rwx`): Owner permissions
     - Second set (e.g., `rwx`): Group permissions
     - Third set (e.g., `rwx`): Others permissions

For example, `-rwxr--r--` means:

- The file is a regular file (`-`).
- The owner has read, write, and execute permissions (`rwx`).
- The group has read permission (`r--`).
- Others have read permission (`r--`).

### Viewing Permissions

To view file permissions in Linux, use the `ls` command:

```bash
ls -l filename
```

### Modifying Permissions

You can change file permissions using the chmod command. There are two ways to specify permissions: symbolic mode and numeric mode.

1. `Symbolic Mode`

In symbolic mode, you use the following syntax:

```bash
chmod [u/g/o][+/-][r/w/x] filename
```

- `u` : user (owner)
- `g` : group
- `o` : others
- `+` : add permission
- `-` : remove permission
- `r` : read
- `w` : write
- `x` : execute

You can also use `a` (all users) and `=` (set exactly these permissions), join letters (`ug+rw`), or leave out the user letters (`+x`). The letters `s` and `t` also work. <Cite n={32} />

`Examples:`

- `Add execute permission for the owner:`

  ```bash
  chmod u+x filename
  ```

- `Remove read permission for others:`

  ```bash
  chmod o-r filename
  ```

- `Add write permission for the group:`

  ```bash
  chmod g+w filename
  ```

2. `Numeric Mode`

In numeric mode, permissions are represented by a three-digit octal number. Each permission type is represented by a specific number:

- Read (`r`) = `4`
- Write (`w`) = `2`
- Execute (`x`) = `1`

`To set permissions, add the numbers together:`

- `7` = read, write, execute (`4+2+1`)
- `6` = read, write (`4+2`)
- `5` = read, execute (`4+1`)
- `4` = read (`4`)
- `3` = write, execute (`2+1`)
- `2` = write (`2`)
- `1` = execute (`1`)
- `0` = no permissions

`Examples:`

- `Set permissions to read, write, and execute for the owner, and read and execute for group and others:`

  ```bash
  chmod 755 filename
  ```

- `Set permissions to read and write for the owner, and no permissions for group and others:`

  ```bash
  chmod 600 filename
  ```

### Special Permissions

In addition to standard permissions, Linux has special permissions:

- `Setuid (s):` When set on an executable file, the program runs with the permissions of the file owner.
- `Setgid (s):` When set on a directory, new files inherit the group of the directory, rather than the group of the user who created the file.
- `Sticky Bit (t):` When set on a directory, only the owner of a file can delete or rename it within that directory.

<Callout type="warning" title="Correction">

Setgid also works on an executable file. The program then runs with the group of the file. <Cite n={25} /> <Cite n={41} />

On a directory with the sticky bit, three kinds of user can delete or rename a file. They are the owner of the file, the owner of the directory, and a privileged process (for example root). <Cite n={41} /> <Cite n={32} />

On Linux, setuid and setgid do nothing on scripts, and nothing on a filesystem that is mounted `nosuid`. <Cite n={44} />

</Callout>

To set special permissions, use the chmod command with a 4 for setuid, 2 for setgid, and 1 for sticky bit:

<Callout type="warning" title="Correction">

The 4, 2, or 1 is the first digit of a four-digit octal mode. For example, `chmod 4755 file` sets setuid, `chmod 2755 directory` sets setgid, and `chmod 1777 directory` sets the sticky bit. <Cite n={32} />

</Callout>

- `Setuid:`

  ```bash
  chmod u+s filename
  ```

- `Setgid:`

  ```bash
  chmod g+s directoryname
  ```

- `Sticky Bit:`

  ```bash
  chmod +t directoryname
  ```

### Viewing and Modifying Ownership

You can view and change file ownership with the following commands:

- `View ownership:`

  ```bash
  ls -l filename
  ```

- `Change ownership:`

  ```bash
  chown new_owner:new_group filename
  ```

<Callout type="warning" title="Correction">

On Linux, only a privileged process (for example root) can change the owner of a file. A user without privilege can change only the group, and only to a group that the user belongs to. <Cite n={42} /> <Cite n={33} />

</Callout>

<Callout type="danger">

Setuid on a program makes it run with the user ID of the file owner. <Cite n={25} /> If root owns a compiled program, `chmod u+s` makes it run as root for every user. Mode 777 gives write permission to the owner, the group, and everyone else. <Cite n={32} /> Tutorial's own advice: set setuid only on a program that you trust, and do not use `chmod 777`. A `chown` on a wrong path changes the owner of that file. <Cite n={33} /> Tutorial's own advice: check the path with `ls -ld` first.

</Callout>

### Conclusion

Understanding and managing file permissions is crucial for security and proper functionality in Linux environments. By using the `ls` and `chmod` commands effectively, you can ensure that files and directories are accessible only to the appropriate users.

<Callout type="tip" title="Why it matters for testing">

Tutorial's own advice: after a test writes a key file, check its mode with `ls -l` or `stat -c %a` (a GNU option). <Cite n={28} /> If a test fails with `Permission denied`, find the missing bit and fix that bit. Do not use `chmod 777` to make the test pass: it hides the fault.

</Callout>
