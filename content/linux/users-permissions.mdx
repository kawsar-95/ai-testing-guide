# Users and Permissions

This stage covers user accounts, groups, the root account, and file permissions. A tester needs it because many failures that read `Permission denied` are not product bugs. A CI runner (the machine that runs an automated job) may use the wrong account, or a fixture file may have the wrong owner. Test with the least privilege (the smallest set of rights) that works. <Cite n={1} />

<PageMeta />

## User Management

<Voices>
<Technical>

**Goal:** Find your UID, GID, and login shell in the account database.

A Linux account is a line of data, not a folder. The file `/etc/passwd` has one line for each account, with seven colon-separated fields: name, password marker, UID, GID, comment, home directory, and login shell (the program that starts at login). <Cite n={2} /> The UID is the user ID. The GID is the number of the primary group. UID 0 is the superuser, `root`. <Cite n={2} /> `getent` reads the account databases through the Name Service Switch libraries (the lookup layer of the system). <Cite n={15} />

```bash
getent passwd root
```

**Try it:** print your IDs and your own account line. These commands only read. `id -un` prints your user name. <Cite n={13} />

```bash
id                          # uid=1000(user) gid=1000(staff) groups=1000(staff),27(sudo)
getent passwd "$(id -un)"   # user:x:1000:1000:User:/home/user:/bin/bash
ls -l /etc/passwd /etc/shadow
# -rw-r--r-- 1 root root   2978 Aug 30 13:21 /etc/passwd
# -rw-r----- 1 root shadow 1405 Aug 30 13:21 /etc/shadow
# Stand-ins: user, staff, and User replace your own names. Your groups differ.
```

<Callout type="tip" title="Why it matters for testing">

Tutorial's own advice: print `id` and `ls -ld .` at the start of a CI job. In a container, the UID of the runner often has no name.

</Callout>

<details>
<summary>Go deeper</summary>

- The name `passwd` misleads. On most systems, its password field holds only an `x`. <Cite n={2} />
- The password hash (the stored, one-way scramble of the password) lives in `/etc/shadow`. <Cite n={2} /> Regular users must not read that file. <Cite n={3} />
- A hash that starts with `!` means that the password is locked. <Cite n={3} />

Tutorial's own advice: in a container, files from the host can belong to a number that no account in the container uses. This mismatch causes many `Permission denied` errors.

</details>

</Technical>

## Users and Groups

<Voices>
<Technical>

**Goal:** List your groups and read the line of your primary group in `/etc/group`.

A group is a named set of users. The file `/etc/group` has one line for each group: name, password field, GID, and a comma-separated list of members. <Cite n={4} /> Each account has one primary group, which is the GID in `/etc/passwd`. It can also join many supplementary groups (extra groups). <Cite n={2} /> `id` prints the user, the primary group, and the supplementary groups. <Cite n={13} />

```bash
id
```

**Try it:** list your group names, and read the line of your primary group. These commands only read. `id -Gn` prints the group names only, and `groups` prints the same names. <Cite n={14} /> `id -gn` prints the name of the primary group. <Cite n={13} />

```bash
id -Gn                     # staff adm sudo users
groups                     # staff adm sudo users
getent group "$(id -gn)"   # staff:x:1000:
# Stand-in: staff replaces the name of your primary group. Your list differs.
```

<Callout type="tip" title="Why it matters for testing">

Tutorial's own advice: test access with two accounts, one in the group and one outside it. The first must succeed. The second must get `Permission denied`.

</Callout>

<details>
<summary>Go deeper</summary>

- Admins use groups to give access to files and other resources. <Cite n={18} />
- A session gets its groups at login. If an admin changes your groups later, `id` and `groups` still show the old list in that session. `id USER` reads the database again. <Cite n={13} />
- `newgrp GROUP` changes the current group ID inside the session. It starts a new shell, and `exit` leaves it. <Cite n={12} /> <Cite n={39} />
- `gpasswd -d USER GROUP` removes a member. <Cite n={11} /> `groupdel` cannot remove the primary group of an existing user. <Cite n={10} />

```bash
id "$USER"     # reads the group database again
newgrp qa      # needs a group qa that lists you; starts a new shell
```

Tutorial's own advice: after a script changes a membership, start a new login, for example `sudo -iu USER`, before you test. <Cite n={21} /> An old session checks the old groups. A minimal container may lack `sudo`.

</details>

</Technical>

<Bangla>

**লক্ষ্য:** আপনার group-গুলোর তালিকা দেখুন, আর `/etc/group`-এ আপনার primary group-এর লাইনটি পড়ুন।

Group হলো নাম দেওয়া একদল user। `/etc/group` file-এ প্রতিটি group-এর জন্য একটি লাইন থাকে: name, password field, GID, এবং comma দিয়ে আলাদা করা member-দের তালিকা। <Cite n={4} /> প্রতিটি account-এর একটি primary group থাকে, যা `/etc/passwd`-এর GID। Account-টি আরও অনেক supplementary group-এ (primary group-এর বাইরে অতিরিক্ত group) যোগ দিতে পারে। <Cite n={2} /> `id` user, primary group, এবং supplementary group-গুলো দেখায়। <Cite n={13} />

**চেষ্টা করুন:** আপনার group-এর নামগুলো দেখুন, আর আপনার primary group-এর লাইনটি পড়ুন। এই command-গুলো শুধু পড়ে। `id -Gn` শুধু group-এর নামগুলো print করে, আর `groups` একই নামগুলো print করে। <Cite n={14} /> `id -gn` primary group-এর নাম print করে। <Cite n={13} />

```bash
id -Gn                     # staff adm sudo users
groups                     # staff adm sudo users

```

</Callout>

<details>
<summary>আরও জানুন</summary>

- Admin-রা file এবং অন্যান্য resource-এ access দিতে group ব্যবহার করেন। <Cite n={18} />

## Super User

<Voices>
<Technical>

**Goal:** Check whether you are root, and find the admin group of your system.

The superuser is the account with UID 0, named `root`. <Cite n={2} /> Ubuntu disables the direct root login and uses the `sudo` group for admins. <Cite n={19} /> `sudo COMMAND` runs one command as root, if the sudoers policy allows it. `sudo -l` lists your rights. <Cite n={21} />

```bash
sudo -l
```

<Callout type="danger">

Edit sudoers only with `visudo`, which checks the syntax before it saves. <Cite n={23} /> A syntax error can stop sudo, and you can lose root access. A rule with `NOPASSWD: ALL` gives full root to the user. <Cite n={22} />

</Callout>

**Try it:** print your UID and the members of the `sudo` group. These commands only read.

```bash
id -u               # 1000 (only root gets 0)
getent group sudo   # sudo:x:27:user
# Stand-in: user replaces your login name.
```

<Callout type="tip" title="Why it matters for testing">

Tutorial's own advice: run the tests as a normal user. Use `sudo -n` in CI, so a missing rule fails at once.

</Callout>

<details>
<summary>Go deeper</summary>

- Ubuntu gives root a hash that matches no password. <Cite n={19} /> A Red Hat blog advises to lock root at install and to put admins in the `wheel` group. <Cite n={20} /> `getent group wheel` prints no line and exits with status 2 if the group does not exist. <Cite n={15} />
- `sudo -u USER` runs the command as another user. By default, sudo remembers your password for a few minutes in each terminal. The `timestamp_timeout` option of sudoers(5) sets the time. `-k` ends it, and `-n` fails instead of asking for input. Policies can log each attempt. <Cite n={21} />
- Rules live in `/etc/sudoers` and in the files that its `@includedir` line reads, usually `/etc/sudoers.d`. The last matching rule wins. sudo skips file names that contain a `.` or end in `~`. <Cite n={22} />

```bash
sudo visudo -f /etc/sudoers.d/qa-restart   # new drop-in file, syntax checked on save
# One narrow rule for that file (change the user, command, and path):
#   qa-runner ALL = (root) NOPASSWD: /usr/bin/systemctl restart myapp
sudo visudo -c                             # check /etc/sudoers and its includes
```

Tutorial's own advice: never edit `/etc/sudoers` with a plain editor. Name exact commands with full paths. Give a narrow rule only to the one setup step that needs root.

</details>

## File Permissions

<Voices>
<Technical>

**Goal:** Read a file mode in `rwx` form and in octal form.

Every file has an owner, a group, and mode bits (flags for access). Three classes use them: the owner (`u`), other members of the file's group (`g`), and everyone else (`o`). <Cite n={25} /> <Cite n={32} /> Each class can read (`r`), write (`w`), and execute (`x`). `ls -l` shows the file type first, then three `rwx` triplets. <Cite n={27} /> Octal mode (base 8 numbers) adds r=4, w=2, and x=1 for each class. So 640 means `rw-r-----`. <Cite n={26} />

```bash
ls -l report.txt
```

**Try it:** in a throw-away directory, give a file mode 640 and read the mode back. `stat -c` prints a chosen format, and `%a` is the octal mode. <Cite n={28} /> `stat -c` is a GNU option.

```bash
(
  cd "$(mktemp -d)" || exit   # make and enter a new, empty directory
  touch report.txt
  chmod 640 report.txt
  ls -l report.txt                      # -rw-r----- 1 user staff 0 Oct 27 15:32 report.txt
  stat -c '%A %a %U:%G %n' report.txt   # -rw-r----- 640 user:staff report.txt
  rm -r "$PWD"        # delete the throw-away directory
)
# Stand-ins: user and staff replace your user and group names.
```

<Callout type="tip" title="Why it matters for testing">

Tutorial's own advice: assert on modes in tests that write files. After a test writes a key file, check that `stat -c %a` prints `600` or `640`.

</Callout>

| Special bit | Effect |
|---|---|
| Setuid (4000) | Runs a program with the effective user ID (the ID for permission checks) of the file owner. <Cite n={25} /> <Cite n={24} /> |

| Sticky (1000) | On a directory, unprivileged users can remove or rename only their own files, or any file if they own the directory. <Cite n={25} /> |


প্রতিটি file-এর একজন owner, একটি group, এবং কিছু mode bit (access নিয়ন্ত্রণের flag) থাকে। তিনটি class এগুলো ব্যবহার করে: owner (`u`), file-এর group-এর অন্য member-রা (`g`), এবং বাকি সবাই (`o`)। <Cite n={25} /> প্রতিটি class read (`r`), write (`w`), এবং execute (`x`) করতে পারে। `ls -l` প্রথমে file-এর type দেখায়, তারপর তিনটি `rwx` সেট। <Cite n={27} /> Octal mode-এ (base 8 সংখ্যা) প্রতিটি class-এর জন্য r=4, w=2, এবং x=1 যোগ হয়। তাই 640 মানে `rw-r-----`। <Cite n={26} />

**চেষ্টা করুন:** একটি throw-away directory-তে একটি file-কে mode 640 দিন, আর mode-টি আবার পড়ুন। `stat -c` আপনার বেছে নেওয়া format-এ print করে, আর `%a` হলো octal mode। <Cite n={28} /> `stat -c` একটি GNU option।

```bash
(
  cd "$(mktemp -d)" || exit   # make and enter a new, empty directory
  touch report.txt
  chmod 640 report.txt
  ls -l report.txt                      # -rw-r----- 1 user staff 0 Oct 27 15:32 report.txt
  stat -c '%A %a %U:%G %n' report.txt   # -rw-r----- 640 user:staff report.txt
  rm -r "$PWD"        # delete the throw-away directory
)
```

</Callout>

- Directory-তে sticky bit (1000) সাধারণ user-দের শুধু নিজেদের file মুছতে বা নাম বদলাতে দেয়, অথবা directory-র owner হলে যেকোনো file। <Cite n={25} />

## Managing Permissions

<Voices>
<Technical>

**Goal:** Change modes with `chmod`, and set new-file modes with `umask`.

`chmod` changes the mode. Use octal to set everything at once (`chmod 640 FILE`). Use the symbolic form for one change (`chmod g-w FILE`). <Cite n={32} /> The umask removes bits from the mode of new files. A new file usually starts at 666, so umask 022 gives 644. <Cite n={35} />

```bash
chmod g-w report.txt
```

<Callout type="danger">

`chmod -R 777` lets every user write every file in the tree. <Cite n={32} /> `chown -R` on a wrong path, such as `/etc`, can break the system. Do not combine `-R` with `-L`: it follows symbolic links and can change files outside the tree. <Cite n={30} />

</Callout>

**Try it:** change a mode two ways, and make a private file. `umask` is a shell builtin. <Cite n={36} /> The parentheses run a subshell, so the change stays local. <Cite n={38} />

```bash
(
  cd "$(mktemp -d)" || exit      # make and enter a new, empty directory
  touch run.sh
  chmod 640 run.sh               # octal: owner rw-, group r--, others none
  chmod u+x,g-w run.sh           # symbolic: add x for the owner, remove w for the group
  umask 077; touch private.txt   # 077: new files get no bits for group and others
  stat -c '%A %a %n' run.sh private.txt
  # -rwxr----- 740 run.sh
  # -rw------- 600 private.txt
  rm -r "$PWD"                   # delete the throw-away directory
)
```

<Callout type="tip" title="Why it matters for testing">

Tutorial's own advice: set `umask 077` in a script that writes secrets.

</Callout>

### Understanding Linux File Permissions

1. `Permission Types:`
   - `Read (r):` Permission to read the contents of the file. For directories, this allows listing files.
   - `Write (w):` Permission to modify the contents of the file. For directories, this allows creating or deleting files within the directory. Correction: on a directory, `w` works only together with `x` on that directory. <Cite n={43} /> <Cite n={37} />
   - `Execute (x):` Permission to execute the file as a program. For directories, this allows accessing files within the directory.

2. `User Classes:`
   - `Owner (u):` The user who owns the file.
   - `Group (g):` A group of users who have been granted access to the file.
   - `Others (o):` All other users who are not the owner or part of the group.

3. `Permission Representation:`
   - File permissions are displayed in a 10-character string when using the `ls -l` command. The format is:

     ```text
     -rwxrwxrwx
     ```

   - The first character indicates the file type (e.g., - for a regular file, d for a directory).
   - The next nine characters are divided into three sets of three:
     - First set (e.g., `rwx`): Owner permissions
     - Second set (e.g., `rwx`): Group permissions
     - Third set (e.g., `rwx`): Others permissions

For example, `-rwxr--r--` means:

- The file is a regular file (`-`).
- The owner has read, write, and execute permissions (`rwx`).
- The group has read permission (`r--`).
- Others have read permission (`r--`).

### Viewing Permissions

To view file permissions in Linux, use the `ls` command:

```bash
ls -l filename
```

### Modifying Permissions

You can change file permissions using the chmod command. There are two ways to specify permissions: symbolic mode and numeric mode.

1. `Symbolic Mode`

In symbolic mode, you use the following syntax:

```bash
chmod [u/g/o][+/-][r/w/x] filename
```

- `u` : user (owner)
- `g` : group
- `o` : others
- `+` : add permission
- `-` : remove permission
- `r` : read
- `w` : write
- `x` : execute

You can also use `a` (all users) and `=` (set exactly these permissions), join letters (`ug+rw`), or leave out the user letters (`+x`). The letters `s` and `t` also work. <Cite n={32} />

`Examples:`

- `Add execute permission for the owner:`

  ```bash
  chmod u+x filename
  ```

- `Remove read permission for others:`

  ```bash
  chmod o-r filename
  ```

- `Add write permission for the group:`

  ```bash
  chmod g+w filename
  ```

2. `Numeric Mode`

In numeric mode, permissions are represented by a three-digit octal number. Each permission type is represented by a specific number:

- Read (`r`) = `4`
- Write (`w`) = `2`
- Execute (`x`) = `1`

`To set permissions, add the numbers together:`

- `7` = read, write, execute (`4+2+1`)
- `6` = read, write (`4+2`)
- `5` = read, execute (`4+1`)
- `4` = read (`4`)
- `3` = write, execute (`2+1`)
- `2` = write (`2`)
- `1` = execute (`1`)
- `0` = no permissions

`Examples:`

- `Set permissions to read, write, and execute for the owner, and read and execute for group and others:`

  ```bash
  chmod 755 filename
  ```

- `Set permissions to read and write for the owner, and no permissions for group and others:`

  ```bash
  chmod 600 filename
  ```

### Special Permissions

In addition to standard permissions, Linux has special permissions:

- `Setuid (s):` When set on an executable file, the program runs with the permissions of the file owner.
- `Setgid (s):` When set on a directory, new files inherit the group of the directory, rather than the group of the user who created the file.
- `Sticky Bit (t):` When set on a directory, only the owner of a file can delete or rename it within that directory.

<Callout type="warning" title="Correction">

Setgid also works on an executable file. The program then runs with the group of the file. <Cite n={25} /> <Cite n={41} />

On a directory with the sticky bit, three kinds of user can delete or rename a file. They are the owner of the file, the owner of the directory, and a privileged process (for example root). <Cite n={41} /> <Cite n={32} />

On Linux, setuid and setgid do nothing on scripts, and nothing on a filesystem that is mounted `nosuid`. <Cite n={44} />

</Callout>

To set special permissions, use the chmod command with a 4 for setuid, 2 for setgid, and 1 for sticky bit:

<Callout type="warning" title="Correction">

The 4, 2, or 1 is the first digit of a four-digit octal mode. For example, `chmod 4755 file` sets setuid, `chmod 2755 directory` sets setgid, and `chmod 1777 directory` sets the sticky bit. <Cite n={32} />

</Callout>

- `Setuid:`

  ```bash
  chmod u+s filename
  ```

- `Setgid:`

  ```bash
  chmod g+s directoryname
  ```

- `Sticky Bit:`

  ```bash
  chmod +t directoryname
  ```

### Viewing and Modifying Ownership

You can view and change file ownership with the following commands:

- `View ownership:`

  ```bash
  ls -l filename
  ```

- `Change ownership:`

  ```bash
  chown new_owner:new_group filename
  ```

<Callout type="warning" title="Correction">

On Linux, only a privileged process (for example root) can change the owner of a file. A user without privilege can change only the group, and only to a group that the user belongs to. <Cite n={42} /> <Cite n={33} />

</Callout>

<Callout type="danger">

Setuid on a program makes it run with the user ID of the file owner. <Cite n={25} /> If root owns a compiled program, `chmod u+s` makes it run as root for every user. Mode 777 gives write permission to the owner, the group, and everyone else. <Cite n={32} /> Tutorial's own advice: set setuid only on a program that you trust, and do not use `chmod 777`. A `chown` on a wrong path changes the owner of that file. <Cite n={33} /> Tutorial's own advice: check the path with `ls -ld` first.

</Callout>

### Conclusion

Understanding and managing file permissions is crucial for security and proper functionality in Linux environments. By using the `ls` and `chmod` commands effectively, you can ensure that files and directories are accessible only to the appropriate users.

<Callout type="tip" title="Why it matters for testing">

Tutorial's own advice: after a test writes a key file, check its mode with `ls -l` or `stat -c %a` (a GNU option). <Cite n={28} /> If a test fails with `Permission denied`, find the missing bit and fix that bit. Do not use `chmod 777` to make the test pass: it hides the fault.

</Callout>
