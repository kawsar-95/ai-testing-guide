# Boot and Services

A Linux machine starts in a chain of steps. On most distributions, systemd then runs the long-lived programs, called services, that your tests depend on. This stage shows the boot chain, the boot loader, and the daily `systemctl` and `journalctl` work. You create a service, start it, check it, and read its logs. A tester needs this to find out why a test host, a CI runner, or an application under test does not come up. <Cite n={1} />

<PageMeta />

## Booting Linux

Booting is a chain of hand-overs. Wikipedia groups it into four steps: system startup, boot loader, kernel, and init process. <Cite n={2} /> First the firmware (the program on the motherboard, called BIOS or UEFI) does basic hardware set-up and usually runs a boot loader. <Cite n={9} /> A BIOS machine starts boot code at the start of the first disk, the Master Boot Record (MBR). A UEFI machine starts a program from the EFI system partition (ESP). <Cite n={3} />

The boot loader loads the kernel (the core of the operating system) and an initramfs. <Cite n={9} /> The initramfs is a compressed archive that the kernel unpacks into memory. <Cite n={26} /> It works as a small file system that helps the kernel find the real root file system. <Cite n={9} /> <Cite n={27} /> The kernel then starts the first user-space process, with process ID 1 (PID 1). <Cite n={10} />

On a systemd distribution, PID 1 is systemd. It starts the units (managed objects) that `default.target` needs. <Cite n={11} /> A target is a named group of units. <Cite n={16} /> The default target is usually `multi-user.target` (text login) or `graphical.target` (desktop). <Cite n={9} />

`systemd-analyze` shows where the time goes. `time` splits it into kernel, initrd, and userspace. `blame` lists units by the time each took to start. `critical-chain` shows the units that delayed the target. <Cite n={17} /> `blame` can mislead, because a unit may only wait for another unit. <Cite n={17} />

```bash
# Needs a host where systemd runs as PID 1. A container may not have it.
cat /proc/cmdline               # the kernel command line of this boot
systemctl get-default           # the default target, for example multi-user.target
systemd-analyze time            # time in kernel, initrd, and userspace
systemd-analyze blame | head    # slowest units first
systemd-analyze critical-chain  # the chain of units that delayed the target
```

<Callout type="tip" title="Why it matters for testing">
Tutorial's own advice: a VM or CI runner that boots slowly can make the first tests fail. Save the output of `systemd-analyze critical-chain` as a job artifact.
</Callout>

## Boot Loaders

A boot loader is the program that the firmware starts to load the kernel. <Cite n={9} /> GRUB 2 is the boot loader of the GNU project, and GRUB Legacy is no longer developed. <Cite n={4} /> `systemd-boot` is a simple boot manager for UEFI firmware only. <Cite n={25} />

GRUB reads its menu from `grub.cfg`, usually in `/boot/grub`. The program `grub-mkconfig` generates this file, so do not edit it by hand. <Cite n={23} /> Change settings in `/etc/default/grub` instead, for example `GRUB_CMDLINE_LINUX` (extra kernel command-line words), and run the generator again. <Cite n={23} /> On Debian, `update-grub` runs it. <Cite n={30} /> Path and tool name can differ on other distributions. `systemd-boot` reads entry files from `/loader/entries/` on the ESP or the XBOOTLDR partition (an extra boot partition). The Boot Loader Specification defines their format. <Cite n={24} /> <Cite n={25} />

At the menu, the key `e` opens an editor for one entry. GRUB boots the edited entry with Ctrl-x. <Cite n={23} /> <Cite n={25} /> To reach a rescue shell, add `systemd.unit=rescue.target` to the kernel command line. The word `1` is a short form. <Cite n={11} /> <Cite n={20} />

```bash
cat /proc/cmdline    # the kernel command line of this boot
ls /boot             # boot files; GRUB usually keeps grub.cfg in /boot/grub
# Needs root. Do this on a throw-away VM only. Path and tool name are for Debian:
# grub-mkconfig -o /boot/grub/grub.cfg
```

<Callout type="danger" title="A wrong boot configuration can leave a machine unbootable">
Do not run `grub-install` or `grub-mkconfig -o`, or edit `/etc/default/grub`, on a machine that you cannot reach at its console. A broken boot loader can leave a remote machine unreachable. A rescue boot can cut the network. Use it only at the console of a VM. Use a VM snapshot for practice.
</Callout>

<Callout type="tip" title="Why it matters for testing">
Tutorial's own advice: keep one disposable VM for boot experiments. A VM that boots into `rescue.target` lets you test recovery steps.
</Callout>

## Service Management

Systemd manages the system with units. Each unit is an object, such as a service, a socket, a timer, or a target. Most units come from a configuration file. <Cite n={11} /> A service unit starts and controls a daemon (a program that runs in the background). <Cite n={11} /> A socket unit holds a socket (a channel that programs use to talk) and can start a service when traffic arrives. <Cite n={22} /> A timer unit starts another unit at set times. <Cite n={21} />

Unit files live in several directories. `/etc/systemd/system` holds units of the administrator. `/run/systemd/system` holds runtime units. `/usr/lib/systemd/system` holds units of the package manager. A unit file in an earlier directory overrides a file with the same name in a later one. <Cite n={13} /> A drop-in is a small `.conf` file in a `UNIT.d/` directory. It changes only some settings of a unit. <Cite n={13} />

`systemctl` is the main tool. `systemctl cat UNIT` prints the unit file and its drop-ins, so you see the real configuration. <Cite n={12} />

Other init systems exist. The older SysV init starts services with scripts in `/etc/init.d`. <Cite n={10} /> <Cite n={7} /> Systemd has largely replaced it. <Cite n={5} />

```bash
systemctl --version | head -n 1                    # the systemd version
systemctl cat systemd-journald.service             # unit file and drop-ins
systemctl list-unit-files --type=service | head    # installed service files
ls /etc/systemd/system                             # units of the administrator
```

<Callout type="tip" title="Why it matters for testing">
Tutorial's own advice: before you test a service, run `systemctl cat` on it. It shows the real command line, the user, and the drop-ins that a package or an image added. Two machines that behave differently often differ here.
</Callout>

## Creating Services

A service is a unit file that ends in `.service`. `[Unit]` describes the unit. `[Service]` says what to run. `[Install]` says which target pulls the unit in when you enable it. <Cite n={13} /> <Cite n={14} /> `Restart=on-failure` is the recommended choice for a long-running service. <Cite n={14} />

The first word of `ExecStart=` must be an absolute path or a plain file name. <Cite n={14} /> `User=` sets the user. A system service runs as root by default, and the user must exist at start. <Cite n={15} /> Tutorial's own advice: avoid root unless the program needs it.

A system service starts with only a few environment variables, not the ones of your shell. Set more with `Environment=`. <Cite n={15} /> With the default `Type=simple`, `systemctl start` reports success even when the program is missing. `Type=exec` reports the failure. <Cite n={14} />

Check the file with `systemd-analyze verify`. It warns about unknown keys and programs that it cannot find. <Cite n={17} /> `systemctl daemon-reload` then makes systemd read the unit files again. <Cite n={12} /> To change a vendor unit (a file from a package), use `systemctl edit UNIT`. It writes a drop-in and reloads. <Cite n={12} />

```bash
# myapp is an invented name; the paths are an illustration.
mkdir -p "$HOME/unit-test" || exit 1
cat > "$HOME/unit-test/myapp.service" <<'EOF'
[Unit]
Description=Example test API (illustration only)
After=network.target

[Service]
User=myapp
WorkingDirectory=/opt/myapp
Environment=APP_PORT=8080
ExecStart=/opt/myapp/bin/myapp --port ${APP_PORT}
Restart=on-failure
RestartSec=5

[Install]
WantedBy=multi-user.target
EOF
systemd-analyze verify "$HOME/unit-test/myapp.service"   # warns: myapp does not exist here
# Needs root, on a lab VM only. Administrators install units in /etc/systemd/system:
# cp "$HOME/unit-test/myapp.service" /etc/systemd/system/
# systemctl daemon-reload
```

<Callout type="danger" title="Test new units on a lab machine, not a remote one">
A wrong unit in `/etc/systemd/system` can change what starts at boot. `systemctl daemon-reload` makes systemd read all unit files at once. `systemctl revert` also deletes a copy of a vendor unit in `/etc`.
</Callout>

<Callout type="tip" title="Why it matters for testing">
Tutorial's own advice: for a test run, change one setting with a drop-in, such as `Environment=APP_ENV=test`. `systemctl revert UNIT` (needs root) removes your drop-ins. <Cite n={12} />
</Callout>

## Starting and Stopping Services

Starting and enabling are different actions. A unit can be enabled and stopped, or started and not enabled. <Cite n={12} /> `enable` only creates the symlinks (files that point to other files) that the `[Install]` section describes. `start` runs the program. <Cite n={12} /> With `enable`, `disable`, and `mask`, the option `--now` also starts or stops the unit. <Cite n={12} />

| Command | What it does |
|---|---|
| `start` | Starts the unit now |
| `stop` | Stops the unit now |
| `restart` | Stops, then starts; starts a stopped unit |
| `reload-or-restart` | Reloads the unit if it supports it, else restarts it |
| `enable` | Hooks the unit into boot, without starting it |
| `disable` | Removes those symlinks, without stopping the unit |
| `mask` | Links the unit to `/dev/null`, so nothing can start it |

<Cite n={12} /> If another unit can still trigger a stopped service, for example a socket, `stop` prints a warning. <Cite n={12} /> The option `--user` talks to your own user manager. <Cite n={12} /> That manager reads units from `~/.config/systemd/user` and other user directories, not from `/etc/systemd/system`. <Cite n={13} />

```bash
# Needs root for system units. Use a lab VM.
systemctl start myapp.service
systemctl restart myapp.service
systemctl enable --now myapp.service    # enable and start
systemctl disable --now myapp.service   # disable and stop
```

<Callout type="danger" title="Do not cut your own access">
`systemctl stop`, `disable`, and `mask` on the wrong unit can make a remote machine unreachable. Examples are `ssh` and the network service. `mask` blocks every start, also by dependencies. `systemctl isolate` stops all units outside the target. <Cite n={12} /> Check the unit name twice.
</Callout>

<Callout type="tip" title="Why it matters for testing">
Tutorial's own advice: `systemctl start` can return before the program is ready. For `simple` and `exec` units, systemd only waits until the process has started. <Cite n={14} /> In a test, wait until the port answers before you send requests.
</Callout>

## Checking Service Status

`systemctl status UNIT` shows the state of a unit and the newest lines of the journal (the log records that systemd keeps). By default it shows 10 lines. <Cite n={12} /> The `Loaded:` line shows the file path and whether the unit is enabled. The `Active:` line shows the state. The state `failed` means a crash, a non-zero exit, or a timeout. <Cite n={12} />

For scripts, use the `is-*` commands. They print one word and set the exit status (the number a command returns; 0 means success). `is-active` returns 0 for active, 3 for not active, and 4 for an unknown unit. <Cite n={12} /> `is-failed` is the other way round: it returns 0 when the unit has failed. <Cite n={12} /> `is-enabled` returns 0 also for `static` units, which cannot be enabled. <Cite n={12} /> The manual says that these codes map the states only roughly. Read the printed word when it matters. <Cite n={12} />

`systemctl list-units --failed` lists all failed units. `systemctl reset-failed` clears the failed state and the restart counter. <Cite n={12} /> The status shows only the newest run. Use `journalctl -u` for earlier runs and boots. <Cite n={12} />

```text
$ systemctl status myapp.service      # sample output: invented, trimmed
● myapp.service - Example test API (illustration only)
     Loaded: loaded (/etc/systemd/system/myapp.service; enabled; preset: enabled)
     Active: active (running) since Mon 2026-10-19 09:00:00 UTC; 5min ago
   Main PID: 1234 (myapp)
Oct 19 09:00:01 example-host myapp[1234]: listening on port 8080

$ systemctl is-active myapp.service; echo $?    # prints: active, then 0
$ systemctl is-failed myapp.service; echo $?    # prints: active, then 1
$ systemctl list-units --failed --no-pager
```

<Callout type="tip" title="Why it matters for testing">
Tutorial's own advice: in a CI script, run `systemctl is-active --quiet myapp.service` before the tests. If it fails, print `systemctl status` and the journal lines in the job log. A test then fails with a cause and not with "connection refused".
</Callout>

## Checking Service Logs

Systemd-journald collects the logs. It also takes the standard output and standard error of services. <Cite n={19} /> By default, the standard output of a service goes to the journal. <Cite n={15} /> So a service that prints to the screen needs no log file. `journalctl -u UNIT` shows the lines of one unit. <Cite n={18} /> `-b` limits the output to the current boot, and `-b -1` selects the boot before. <Cite n={18} /> <Cite n={8} />

| Option | Effect |
|---|---|
| `-n 50` | Last 50 entries |
| `-f` | Follows new entries until Ctrl-C |
| `--since "-1h"` | Entries from the last hour |
| `-p err` | Priority `err` and more important |

<Cite n={18} /> By default, the journal is on disk in `/var/log/journal` if that directory exists at boot. Otherwise it is in `/run/log/journal` and is lost at reboot. <Cite n={19} /> Root can read the journal. So can members of `systemd-journal`, `adm`, and `wheel`. <Cite n={18} /> A service can also write its own file, if its unit sets `StandardOutput=` to a file. <Cite n={15} /> The option `--no-pager` stops `journalctl` from using a pager (a program that shows text one screen at a time), which suits scripts. <Cite n={18} />

```bash
journalctl -u myapp.service -n 50 --no-pager          # last 50 lines of one unit
journalctl -u myapp.service -b -p err --no-pager      # errors since boot
journalctl -u myapp.service --since "-1h" -f          # last hour, then follow
journalctl -b -1 -p err --no-pager                    # errors of the previous boot
journalctl --list-boots                               # the boots in the journal
```

<Callout type="tip" title="Why it matters for testing">
Tutorial's own advice: attach `journalctl -u myapp.service -b --no-pager` to the CI report when a test fails. Read it before you share it. Journal lines can contain host names, user names, IP addresses, and tokens. Remove them first.
</Callout>

## Running Services

"Running" is a different question from "enabled". `systemctl list-units --type=service --state=running` lists the services that run now. <Cite n={6} /> <Cite n={12} /> `list-units` shows only active, failed, and pending units unless you add `--all`. <Cite n={12} /> `list-unit-files --state=enabled` lists the enabled unit files. <Cite n={6} /> <Cite n={12} /> A unit can be enabled but not running, or running but not enabled. Compare both lists.

Timers and sockets start work too. `list-timers` shows when each timer runs next and last. <Cite n={12} /> By default, a timer starts the service with the same name. <Cite n={21} /> `list-sockets` shows each socket unit and the unit that it activates. <Cite n={12} /> Socket activation lets systemd hold a port before the service starts. <Cite n={22} />

Check your own view of the machine too. `ss -tulpn` shows listening TCP and UDP ports with numeric values and the process. <Cite n={28} /> Use `sudo` to see the processes of other users. `ps xawf -eo pid,user,cgroup,args` shows which unit each process belongs to. <Cite n={11} /> `systemctl status PID` names the unit of a process. <Cite n={12} />

A container's main process is the `ENTRYPOINT` or `CMD` program, and Docker advises one service for each container. <Cite n={29} /> Tutorial's own note: many images start no systemd, so `systemctl` can fail there. A minimal image may also lack `ps`.

```bash
systemctl list-units --type=service --state=running --no-pager
systemctl list-unit-files --state=enabled --no-pager | head   # enabled unit files
systemctl list-timers --no-pager
systemctl list-sockets --no-pager
sudo ss -tulpn                              # needs root; ports and their process
ps xawf -eo pid,user,cgroup,args | head     # processes with their unit
```

<Callout type="tip" title="Why it matters for testing">
Tutorial's own advice: before a test run, save `systemctl list-units --type=service --state=running` and `sudo ss -tulpn`. An old instance or an unknown service on your test port is a common cause of "address already in use". The saved lists show it.
</Callout>
