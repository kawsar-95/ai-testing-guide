# Boot and Services

A Linux machine starts in a chain of steps. On most distributions, systemd then runs the long-lived programs, called services, that your tests depend on. This stage shows the boot chain, the boot loader, and the daily `systemctl` and `journalctl` work. You create a service, start it, check it, and read its logs. A tester needs this to find out why a test host, a CI runner, or an application under test does not come up. <Cite n={1} />

## Booting Linux

<Voices>
<Technical>

**Goal:** Name the boot steps, and find the default target and boot time of your machine.

Booting is a chain of hand-overs. <Cite n={2} /> First, the firmware on the motherboard (BIOS or UEFI) does basic hardware set-up and usually runs a boot loader. <Cite n={9} /> The boot loader loads the kernel and an initramfs, a small file system in memory. <Cite n={9} /> The kernel then starts the first user-space process, PID 1. <Cite n={10} /> On a systemd distribution, PID 1 is systemd. It starts the units that `default.target` needs. <Cite n={11} />

```bash
systemctl get-default
```

**Try it:** print the name of PID 1, the default target, and the boot time. This needs systemd as PID 1, which a container may not have. `systemd-analyze time` splits the time into kernel, initrd, and userspace. <Cite n={17} />

```bash
ps -p 1 -o comm=        # the name of process 1: systemd
systemctl get-default   # graphical.target
systemd-analyze time
# Startup finished in 6.2s (firmware) + 4.2s (loader) + 1.8s (kernel) + 4.7s (initrd) + 40.0s (userspace) = 56.9s
# graphical.target reached after 23.2s in userspace.
# The times are stand-ins. Your times and your target differ.
```

<Callout type="tip" title="Why it matters for testing">

Tutorial's own advice: a slow boot can fail the first tests. Save the output of `systemd-analyze critical-chain` as a job artifact.

</Callout>

<details>
<summary>Go deeper</summary>

- Wikipedia groups booting into four steps: system startup, boot loader, kernel, and init process. <Cite n={2} />
- A BIOS machine starts boot code at the start of the first disk, the Master Boot Record (MBR). A UEFI machine starts a program from the EFI system partition (ESP). <Cite n={3} />
- The initramfs is a compressed archive that the kernel unpacks into memory. <Cite n={26} /> It helps the kernel find the real root file system. <Cite n={9} /> <Cite n={27} />
- A target is a named group of units. <Cite n={16} /> The default target is usually `multi-user.target` (text login) or `graphical.target` (desktop). <Cite n={9} />
- `blame` lists units by the time each took to start. `critical-chain` shows the units that delayed the target. <Cite n={17} /> `blame` can mislead, because a unit may only wait for another unit. <Cite n={17} />

```bash
systemd-analyze blame | head    # slowest units first
systemd-analyze critical-chain  # the chain of units that delayed the target
```

</details>

## Boot Loaders

<Voices>
<Technical>

**Goal:** Read the kernel command line of this boot, and find the boot files.

A boot loader is the program that the firmware starts to load the kernel. <Cite n={9} /> GRUB 2 is the boot loader of the GNU project. <Cite n={4} /> GRUB reads its menu from `grub.cfg`, usually in `/boot/grub`. The program `grub-mkconfig` generates this file, so do not edit it by hand. <Cite n={23} />

```bash
cat /proc/cmdline
```

<Callout type="danger" title="A wrong boot configuration can leave a machine unbootable">

Do not run `grub-install` or `grub-mkconfig -o`, or edit `/etc/default/grub`, without console access. A broken boot loader or a rescue boot can lock you out of a remote machine.

</Callout>

**Try it:** print the kernel command line of this boot, and list the boot files. Both commands only read.

```bash
cat /proc/cmdline   # the kernel command line of this boot
# BOOT_IMAGE=/boot/vmlinuz-6.8.0-45-generic root=UUID=<uuid> ro quiet splash
ls /boot            # the boot files; GRUB keeps grub.cfg in /boot/grub
# config-6.8.0-45-generic  efi  grub  initrd.img-6.8.0-45-generic  vmlinuz-6.8.0-45-generic  ...
# Stand-ins: your kernel version and UUID differ. Ubuntu shown.
```

<Callout type="tip" title="Why it matters for testing">

Tutorial's own advice: practise on a disposable VM with a snapshot. Boot it into `rescue.target` to test recovery steps.

</Callout>

<details>
<summary>Go deeper</summary>

- GRUB Legacy is no longer developed. <Cite n={4} />
- To change GRUB settings, edit `/etc/default/grub`, for example `GRUB_CMDLINE_LINUX` (extra kernel command-line words), and run the generator again. <Cite n={23} /> On Debian, `update-grub` runs it. <Cite n={30} /> Path and tool name can differ on other distributions.
- `systemd-boot` is a simple boot manager for UEFI firmware only. <Cite n={25} /> It reads entry files from `/loader/entries/` on the ESP or the XBOOTLDR partition (an extra boot partition). The Boot Loader Specification defines their format. <Cite n={24} /> <Cite n={25} />
- At the menu, the key `e` opens an editor for one entry. GRUB boots the edited entry with Ctrl-x. <Cite n={23} /> <Cite n={25} />
- To reach a rescue shell, add `systemd.unit=rescue.target` to the kernel command line. The word `1` is a short form. <Cite n={11} /> <Cite n={20} /> A rescue boot can cut the network, so use it only at the console of a VM.

```bash
# Needs root. Do this on a throw-away VM only. Path and tool name are for Debian:
# grub-mkconfig -o /boot/grub/grub.cfg
```

</details>

## Creating Services

<Voices>
<Technical>

**Goal:** Write a service unit file, and check it with `systemd-analyze verify`.

A service is a unit file that ends in `.service`. `[Unit]` describes the unit. `[Service]` says what to run. `[Install]` says which target pulls the unit in when you enable it. <Cite n={13} /> <Cite n={14} /> The first word of `ExecStart=` must be an absolute path or a plain file name. <Cite n={14} /> `systemd-analyze verify` checks a unit file. It warns about unknown keys and programs that it cannot find. <Cite n={17} />

<Callout type="danger" title="Test new units on a lab machine, not a remote one">

A wrong unit in `/etc/systemd/system` can change what starts at boot.

</Callout>

**Try it:** in a throw-away directory, write a unit with a typo, and check it. Nothing is installed or started. `rm -r "$PWD"` deletes the directory.

```bash
(
  cd "$(mktemp -d)" || exit 1   # make and enter a new, empty directory
  cat > myapp.service <<'EOF'
[Unit]
Description=Example test API

[Service]
ExecStart=/usr/bin/sleep 60
Restrat=on-failure
EOF
  systemd-analyze verify ./myapp.service
  # /tmp/tmp.XXXXXXXXXX/myapp.service:6: Unknown key 'Restrat' in section [Service], ignoring.
  rm -r "$PWD"
)
# Your directory name differs from tmp.XXXXXXXXXX.
```

<Callout type="tip" title="Why it matters for testing">

Tutorial's own advice: for a test run, change one setting with a drop-in, such as `Environment=APP_ENV=test`.

</Callout>

<details>
<summary>Go deeper</summary>

- `Restart=on-failure` is the recommended choice for a long-running service. <Cite n={14} />
- `User=` sets the user. A system service runs as root by default, and the user must exist at start. <Cite n={15} /> Tutorial's own advice: avoid root unless the program needs it.
- A system service starts with only a few environment variables, not the ones of your shell. Set more with `Environment=`. <Cite n={15} />
- With the default `Type=simple`, `systemctl start` reports success even when the program is missing. `Type=exec` reports the failure. <Cite n={14} />
- `systemctl daemon-reload` makes systemd read all unit files again, at once. <Cite n={12} />
- To change a vendor unit (a file from a package), use `systemctl edit UNIT`. It writes a drop-in and reloads. <Cite n={12} /> `systemctl revert UNIT` (needs root) removes your drop-ins, and also deletes a copy of a vendor unit in `/etc`. <Cite n={12} />

A fuller example (`myapp` is an invented name; the paths are an illustration):

```ini
[Unit]
Description=Example test API (illustration only)
After=network.target

[Service]
User=myapp
WorkingDirectory=/opt/myapp
Environment=APP_PORT=8080
ExecStart=/opt/myapp/bin/myapp --port ${APP_PORT}
Restart=on-failure
RestartSec=5

[Install]
WantedBy=multi-user.target
```

```bash

# cp myapp.service /etc/systemd/system/
# systemctl daemon-reload
```

## Starting and Stopping Services

<Voices>
<Technical>

**Goal:** Tell a started unit from an enabled unit, and pick the right `systemctl` command.

Starting and enabling are different actions. `start` runs the program now. `enable` only creates the symlinks (files that point to other files) that the `[Install]` section describes. <Cite n={12} /> A unit can be enabled and stopped, or started and not enabled. <Cite n={12} />

```bash
systemctl enable --now myapp.service    # needs root: enable and start
```

<Callout type="danger" title="Do not cut your own access">

`systemctl stop`, `disable`, and `mask` on the wrong unit, such as `ssh` or the network service, can make a remote machine unreachable. Check the unit name twice.

</Callout>

**Try it:** ask systemd about the journal service. `is-enabled` and `is-active` only read. `static` means that the unit has no `[Install]` section, so you cannot enable it. <Cite n={12} />

```bash
systemctl is-enabled systemd-journald.service   # static
systemctl is-active systemd-journald.service    # active
```

<Callout type="tip" title="Why it matters for testing">

Tutorial's own advice: `systemctl start` can return before the program is ready. In a test, wait until the port answers.

</Callout>

<details>
<summary>Go deeper</summary>

| Command | What it does |
|---|---|
| `start` | Starts the unit now |
| `stop` | Stops the unit now |
| `restart` | Stops, then starts; starts a stopped unit |
| `reload-or-restart` | Reloads the unit if it supports it, else restarts it |
| `enable` | Hooks the unit into boot, without starting it |
| `disable` | Removes those symlinks, without stopping the unit |
| `mask` | Links the unit to `/dev/null`, so nothing can start it |

<Cite n={12} />

- With `enable`, `disable`, and `mask`, the option `--now` also starts or stops the unit. <Cite n={12} />
- If another unit can still trigger a stopped service, for example a socket, `stop` prints a warning. <Cite n={12} />
- `mask` blocks every start, also by dependencies. `systemctl isolate` stops all units outside the target. <Cite n={12} />
- The option `--user` talks to your own user manager. <Cite n={12} /> That manager reads units from `~/.config/systemd/user` and other user directories, not from `/etc/systemd/system`. <Cite n={13} />
- For `simple` and `exec` units, systemd only waits until the process has started. <Cite n={14} />

```bash
# Needs root for system units. Use a lab VM.
systemctl restart myapp.service
systemctl disable --now myapp.service   # disable and stop
```

</details>

</Technical>

একটি unit start করা আর enable করা আলাদা কাজ। `start` program-টি এখনই চালায়। `enable` শুধু সেই symlink-গুলো (যে file অন্য file-কে দেখায়) তৈরি করে, যা `[Install]` section বর্ণনা করে। <Cite n={12} /> একটি unit enabled কিন্তু stopped থাকতে পারে, আবার started কিন্তু enabled নয় এমনও হতে পারে। <Cite n={12} />

<Callout type="danger" title="নিজের access নিজে বন্ধ করবেন না">

ভুল unit-এ, যেমন `ssh` বা network service-এ, `systemctl stop`, `disable`, বা `mask` চালালে remote machine-এ পৌঁছানো না-ও যেতে পারে। Unit-এর নাম দুবার মিলিয়ে নিন।

</Callout>

**চেষ্টা করুন:** Journal service সম্পর্কে systemd-কে জিজ্ঞেস করুন। `is-enabled` আর `is-active` শুধু পড়ে। `static` মানে unit-টির কোনো `[Install]` section নেই, তাই এটি enable করা যায় না। <Cite n={12} />

```bash
systemctl is-enabled systemd-journald.service   # static
systemctl is-active systemd-journald.service    # active
```

<Callout type="tip" title="টেস্টিং-এ কেন দরকার">

Tutorial-এর নিজস্ব পরামর্শ: `systemctl start` program প্রস্তুত হওয়ার আগেই ফিরে আসতে পারে। Test-এ port সাড়া না দেওয়া পর্যন্ত অপেক্ষা করুন।

</Callout>

<details>
<summary>আরও জানুন</summary>

- `stop` unit-টি এখনই বন্ধ করে। `restart` বন্ধ করে আবার চালু করে, আর stopped unit-কে চালু করে। `reload-or-restart` unit সমর্থন করলে reload করে, নইলে restart করে। `disable` symlink-গুলো সরায়, কিন্তু unit বন্ধ করে না। `mask` unit-টিকে `/dev/null`-এর সাথে link করে, ফলে কেউ আর এটি চালু করতে পারে না। <Cite n={12} />
- `enable`, `disable`, এবং `mask`-এর সাথে `--now` option দিলে unit-টি start বা stop-ও হয়। <Cite n={12} />
- কোনো socket-এর মতো অন্য unit এখনও একটি stopped service-কে trigger করতে পারলে `stop` একটি warning দেখায়। <Cite n={12} />

- `simple` ও `exec` unit-এর ক্ষেত্রে systemd শুধু process চালু হওয়া পর্যন্ত অপেক্ষা করে। <Cite n={14} />

</details>

## Checking Service Status

<Voices>
<Technical>

**Goal:** Read the state of a service, and check it in a script.

`systemctl status UNIT` shows the state of a unit and the newest lines of the journal (the log records that systemd keeps). <Cite n={12} /> The `Loaded:` line shows the file path and whether the unit is enabled. The `Active:` line shows the state. <Cite n={12} /> For scripts, `is-active` prints one word and sets the exit status (the number a command returns; 0 means success). It returns 0 for active, 3 for not active, and 4 for an unknown unit. <Cite n={12} />

```bash
systemctl status systemd-journald.service
```

**Try it:** read two status lines, then test a real and an unknown unit. `grep -E` keeps the `Loaded:` and `Active:` lines. `$?` holds the last exit status.

```bash
systemctl status systemd-journald.service --no-pager | grep -E 'Loaded|Active'
#      Loaded: loaded (/usr/lib/systemd/system/systemd-journald.service; static)
#      Active: active (running) since Tue 2026-10-27 09:00:00 UTC; 41min ago
systemctl is-active systemd-journald.service; echo $?   # active, then 0
systemctl is-active no-such.service; echo $?            # inactive, then 4
# The date is a stand-in.
```

<Callout type="tip" title="Why it matters for testing">

Tutorial's own advice: in CI, run `systemctl is-active --quiet` before the tests. If it fails, print `systemctl status` in the job log.

</Callout>

<details>
<summary>Go deeper</summary>

- The state `failed` means a crash, a non-zero exit, or a timeout. <Cite n={12} />
- `is-failed` is the other way round: it returns 0 when the unit has failed. <Cite n={12} />
- `is-enabled` returns 0 also for `static` units, which cannot be enabled. <Cite n={12} />
- The manual says that these codes map the states only roughly. Read the printed word when it matters. <Cite n={12} />
- `systemctl list-units --failed` lists all failed units. `systemctl reset-failed` clears the failed state and the restart counter. <Cite n={12} />
- The status shows only the newest run. Use `journalctl -u` for earlier runs and boots. <Cite n={12} />
- Tutorial's own advice: with the status and the journal lines in the job log, a test fails with a cause and not with "connection refused".


## Checking Service Logs

<Voices>
<Technical>

**Goal:** Read the newest log lines of one service with `journalctl`.

Systemd-journald collects the logs. It also takes the standard output and standard error of services. <Cite n={19} /> By default, the standard output of a service goes to the journal. <Cite n={15} /> So a service that prints to the screen needs no log file. `journalctl -u UNIT` shows the lines of one unit. `-b` limits the output to the current boot. <Cite n={18} />

```bash
journalctl -u systemd-journald.service -b
```

**Try it:** print the last 3 lines of the journal service in this boot. `-n 3` sets the number of lines, and `--no-pager` prints all at once. Root and members of `systemd-journal`, `adm`, and `wheel` can read the system journal. <Cite n={18} />

```bash
journalctl -u systemd-journald.service -b -n 3 --no-pager
# Oct 27 09:00:40 example-host systemd-journald[465]: Forwarding to syslog missed 1131 messages.
# Each line: date and time, host, program[PID], message.
# The host name and the lines are stand-ins. Your lines differ.
```

<Callout type="tip" title="Why it matters for testing">

Tutorial's own advice: attach the journal of the failed unit to the CI report. Remove host names, user names, IP addresses, and tokens first.

</Callout>

<details>
<summary>Go deeper</summary>

| Option | Effect |
|---|---|
| `-n 50` | Last 50 entries |
| `-f` | Follows new entries until Ctrl-C |
| `--since "-1h"` | Entries from the last hour |
| `-p err` | Priority `err` and more important |
| `-b -1` | The boot before the current one |

<Cite n={18} /> <Cite n={8} />

- By default, the journal is on disk in `/var/log/journal` if that directory exists at boot. Otherwise it is in `/run/log/journal` and is lost at reboot. <Cite n={19} />
- A service can also write its own file, if its unit sets `StandardOutput=` to a file. <Cite n={15} />
- The option `--no-pager` stops `journalctl` from using a pager (a program that shows text one screen at a time), which suits scripts. <Cite n={18} />

```bash
journalctl -u myapp.service -b -p err --no-pager      # errors since boot
journalctl -u myapp.service --since "-1h" -f          # last hour, then follow
journalctl -b -1 -p err --no-pager                    # errors of the previous boot
journalctl --list-boots                               # the boots in the journal
```

</details>

## Running Services

<Voices>
<Technical>

**Goal:** List the services that run now, and compare them with the enabled ones.

"Running" is a different question from "enabled". `systemctl list-units --type=service --state=running` lists the services that run now. <Cite n={6} /> <Cite n={12} /> `list-unit-files` lists each unit file with its enablement state. <Cite n={12} /> A unit can be enabled but not running, or running but not enabled. Compare both lists.

```bash
systemctl list-unit-files --no-pager | awk '$2 == "enabled"' | head   # enabled unit files
```

**Try it:** list the first running services. `--no-pager` prints all at once, and `head -n 4` keeps the first 4 lines.

```bash
systemctl list-units --type=service --state=running --no-pager | head -n 4
#   UNIT                     LOAD   ACTIVE SUB     DESCRIPTION
#   accounts-daemon.service  loaded active running Accounts Service
#   avahi-daemon.service     loaded active running Avahi mDNS/DNS-SD Stack
#   bluetooth.service        loaded active running Bluetooth service
# Ubuntu desktop shown. Your list differs.
```

<Callout type="tip" title="Why it matters for testing">

Tutorial's own advice: save the running services and `sudo ss -tulpn` before a test run. They show an old instance that holds your test port.

</Callout>

<details>
<summary>Go deeper</summary>

- `list-units` shows only active, failed, and pending units unless you add `--all`. <Cite n={12} />
- `list-timers` shows when each timer runs next and last. <Cite n={12} /> By default, a timer starts the service with the same name. <Cite n={21} />
- `list-sockets` shows each socket unit and the unit that it activates. <Cite n={12} /> Socket activation lets systemd hold a port before the service starts. <Cite n={22} />

```bash
systemctl list-timers --no-pager
```

- `list-units` shows only active, failed, and pending units, unless you add `--all`. <Cite n={12} />
- `list-timers` shows when each timer runs next and last. `list-sockets` shows each socket unit and the unit that it activates. <Cite n={12} /> With socket activation, systemd can hold a port before the service starts. <Cite n={22} />
- `ss -tulpn` shows the listening TCP and UDP ports and the process of each. <Cite n={28} /> Use `sudo` to see the processes of other users. `systemctl status PID` tells you which unit a process belongs to. <Cite n={12} />
- Docker advises one service for each container. <Cite n={29} /> The tutorial's own note: many images start no systemd, so `systemctl` can fail there.

**লক্ষ্য:** এখন যে service-গুলো চলছে তাদের তালিকা দেখুন, আর enabled service-গুলোর সাথে মিলিয়ে নিন।

"Running" আর "enabled" দুটি আলাদা প্রশ্ন। `systemctl list-units --type=service --state=running` এখন যে service-গুলো চলছে তাদের তালিকা দেয়। <Cite n={6} /> <Cite n={12} /> `list-unit-files` প্রতিটি unit file ও তার enablement state দেখায়। <Cite n={12} /> একটি unit enabled কিন্তু running নয়, অথবা running কিন্তু enabled নয়, এমন হতে পারে। তাই দুটি তালিকা মিলিয়ে দেখুন।

**চেষ্টা করুন:** চলমান প্রথম service-গুলোর তালিকা দেখুন। `--no-pager` সব একবারে print করে, আর `head -n 4` প্রথম 4টি line রাখে।

```bash
systemctl list-units --type=service --state=running --no-pager | head -n 4
#   UNIT                     LOAD   ACTIVE SUB     DESCRIPTION
#   accounts-daemon.service  loaded active running Accounts Service
#   avahi-daemon.service     loaded active running Avahi mDNS/DNS-SD Stack
#   bluetooth.service        loaded active running Bluetooth service
# Ubuntu desktop shown. Your list differs.
```

Tutorial-এর নিজস্ব পরামর্শ: Test run-এর আগে চলমান service-গুলো আর `sudo ss -tulpn` save করুন। এতে test port ধরে রাখা পুরোনো instance দেখা যায়।

<summary>আরও জানুন</summary>

- `--all` না দিলে `list-units` শুধু active, failed, ও pending unit দেখায়। <Cite n={12} />
- `list-timers` দেখায় প্রতিটি timer পরের বার ও আগের বার কখন চলে। <Cite n={12} /> Default হিসেবে একটি timer একই নামের service চালু করে। <Cite n={21} />
- `list-sockets` প্রতিটি socket unit এবং সেটি কোন unit activate করে তা দেখায়। <Cite n={12} /> Socket activation-এ service চালু হওয়ার আগেই systemd একটি port ধরে রাখতে পারে। <Cite n={22} />
- `ss -tulpn` listening TCP ও UDP port, তাদের numeric মান, এবং process দেখায়। <Cite n={28} /> অন্য user-এর process দেখতে `sudo` ব্যবহার করুন।
- `ps xawf -eo pid,user,cgroup,args` দেখায় প্রতিটি process কোন unit-এর <Cite n={11} />, আর `systemctl status PID` একটি process-এর unit-এর নাম বলে। <Cite n={12} />
- একটি container-এর main process হলো `ENTRYPOINT` বা `CMD` program, এবং Docker প্রতিটি container-এ একটি service রাখার পরামর্শ দেয়। <Cite n={29} /> Tutorial-এর নিজস্ব note: অনেক image systemd চালু করে না, তাই সেখানে `systemctl` fail করতে পারে।

</details>
