# Shell Scripting

A shell script is a text file of commands that the shell runs for you. This stage covers how to write one, store values, write literal text, decide with conditions, repeat work with loops, and find faults. A tester needs these skills because CI jobs, test set-up, and log checks are often short shell scripts. <Cite n={1} /> <Cite n={3} />

<PageMeta />

## Shell Programming

<Voices>
<Technical>

**Goal:** Write a small script, run it, and read its exit status.

A shell script is a text file of commands. Bash runs it in a non-interactive shell. <Cite n={11} /> The first line is the shebang: `#!` and the path of an interpreter. The kernel reads it when it runs the file. The file needs the execute permission. <Cite n={41} /> `chmod +x` adds that permission. <Cite n={42} /> Every command ends with an exit status from 0 to 255. Zero means success. `$?` holds the last status. <Cite n={12} /> <Cite n={15} /> A script returns the status of its last command. <Cite n={38} />

```bash
chmod +x setup.sh
```

**Try it:** write a two-line script in a throw-away directory, run it twice, and print `$?` (the last exit status) after each run. <Cite n={15} /> The parentheses keep your shell unchanged.

```bash
(
  cd "$(mktemp -d)"   # make and enter a new, empty directory
  printf '%s\n' '#!/usr/bin/env bash' '[ "$1" = "ok" ]' > setup.sh
  chmod +x setup.sh
  ./setup.sh ok;  echo "status: $?"    # status: 0
  ./setup.sh bad; echo "status: $?"    # status: 1
  rm -r -- "$PWD"     # delete the throw-away directory
)
```

<Callout type="tip" title="Why it matters for testing">

Tutorial's own advice: in CI, check the exit status of a script, not its printed text. A status other than 0 is a fail.

</Callout>

<details>
<summary>Go deeper</summary>

- A shell is a program that passes your commands to the operating system. <Cite n={2} />
- `#!/usr/bin/env bash` finds the first `bash` in `PATH`. <Cite n={11} />
- `./setup.sh` runs the file in a child shell, so its variables vanish at the end. <Cite n={11} />
- `. ./setup.sh` (or `source`) runs the file in the current shell. Its variables stay in your shell. <Cite n={35} /> <Cite n={36} />
- POSIX defines the portable shell language. <Cite n={39} /> Debian policy lets a `sh` script in a Debian package assume POSIX plus a few extras. A package script that needs more must name its shell. <Cite n={40} />
- In a test with dash, `[[` and arrays gave errors.
- ShellCheck finds mistakes before a run. It reports through its exit status, so CI can run it. <Cite n={45} /> <Cite n={49} />

Tutorial's own advice: start each CI script with a shebang and run `shellcheck` on it in the pipeline. To find non-POSIX code, run the script under `dash` if installed, or give it a `#!/bin/sh` shebang so ShellCheck warns. <Cite n={45} />

</details>

## Variables

<Voices>
<Technical>

**Goal:** Store a value in a variable, read it safely, and give it a default.

A variable holds a value under a name. Assign it as `name=value`, with no spaces around `=`. <Cite n={13} /> Read it with `$name`, and quote the read: `"$name"`. An unquoted value is split at spaces and then treated as a glob, a filename pattern such as `*.txt`. <Cite n={46} /> <Cite n={32} /> `${name:-default}` gives a default when the variable is unset or empty. <Cite n={16} />

```bash
suite="smoke tests"
```

**Try it:** print a value with and without quotes, then read a variable with a default before and after you set it. `printf '[%s]\n'` prints each argument in brackets on its own line.

```bash
(
  suite="smoke tests"
  printf '[%s]\n' "$suite"              # [smoke tests]
  printf '[%s]\n' $suite                # [smoke]
                                        # [tests]
  unset TARGET_ENV
  echo "env: ${TARGET_ENV:-staging}"    # env: staging
  TARGET_ENV=qa
  echo "env: ${TARGET_ENV:-staging}"    # env: qa
)
```

<Callout type="tip" title="Why it matters for testing">

Tutorial's own advice: give settings a default, such as `${TARGET_ENV:-staging}`. Never print a variable that holds a token or a password into a CI log.

</Callout>

<details>
<summary>Go deeper</summary>

| Form | What it does |
|---|---|
| `${name:?message}` | Stops a script with an error if the variable is unset or empty. <Cite n={16} /> |
| `${#name}` | Gives the length of the value. <Cite n={16} /> |
| `$1`, `$2`, … | The arguments of a script (positional parameters). <Cite n={14} /> |
| `$#`, `$0`, `"$@"` | The count of the arguments, the name of the script, and each argument as one separate word. <Cite n={15} /> |
| `export name` | Adds the variable to the environment, the list of name-value pairs that child processes inherit. A plain variable lives in the current shell only. <Cite n={35} /> <Cite n={19} /> |
| `readonly name` | Blocks later changes with an error. <Cite n={4} /> <Cite n={35} /> |
| `$(command)` | Command substitution: the shell puts the output of the command in its place. <Cite n={17} /> |
| `urls=(a b)` | An array, a list of values. It works in bash, ksh, and zsh, but dash rejected it in a test. <Cite n={18} /> <Cite n={46} /> |

Tutorial's own advice: keep the base URL, browser, and environment name in variables with defaults. A CI job then overrides them without a script edit.

</details>

</Technical>

**লক্ষ্য:** একটি variable-এ value রাখুন, নিরাপদে পড়ুন, আর একটি default দিন।

## Literals

<Voices>
<Technical>

**Goal:** Use quotes to keep text exactly as you typed it.

A literal is text that the shell takes as written. Quoting switches off the special meaning of characters. Single quotes keep every character literal. <Cite n={21} /> Double quotes keep most characters literal, but `$`, the backtick, and `\` stay active. <Cite n={22} /> A backslash outside quotes makes the next character literal. <Cite n={20} />

```bash
echo 'cost: $5'
```

**Try it:** print the same variable in single quotes and in double quotes. Inside double quotes, `\$` keeps the `$` literal. <Cite n={22} />

```bash
(
  user=qa
  echo 'single: $user'    # single: $user
  echo "double: $user"    # double: qa
  echo "price: \$5"       # price: $5
)
```

<Callout type="tip" title="Why it matters for testing">

Tutorial's own advice: put `grep` patterns in single quotes, and write JSON test data with a quoted here-document, so the shell does not change them.

</Callout>

<details>
<summary>Go deeper</summary>

- A single quote cannot appear inside single quotes. <Cite n={21} /> To place one, close the string, add `\'`, and open it again: `'it'\''s'`. <Cite n={5} />
- `$'...'` decodes escapes such as `\n` and `\t`. <Cite n={23} /> The 2024 POSIX standard defines it, but dash did not decode it in a test. <Cite n={39} />
- A here-document gives several lines to a command as input. The word after `<<` is the end marker. If you quote the marker, nothing inside expands. Otherwise variables and `$(...)` expand. With `<<-`, the shell strips leading tabs. <Cite n={24} />
- `$((expression))` does arithmetic on whole numbers with C operators. <Cite n={26} /> <Cite n={25} /> A leading `0` means octal, and `0x` means hexadecimal. <Cite n={25} />
- The form `base#n` writes a number in another base. POSIX requires only decimal, octal, and hexadecimal constants, so other shells may reject `base#n`. Dash did in a test. <Cite n={25} /> <Cite n={39} />

```bash
cat <<'EOF'                          # quoted marker: prints the line as typed
{"user": "$USER"}
EOF
echo $((7 * 6 + 1)) $((10 / 3))      # 43 3
echo $((0x1F)) $((2#101)) $((010))   # 31 5 8
```

Tutorial's own advice: beware of leading zeros. `$((08))` is an error, because `08` is not a valid octal number.

</details>

</Technical>

## Conditionals

<Voices>
<Technical>

**Goal:** Run a command only when a test passes, with `if` and `[ ]`.

`if` runs a command and reads its exit status. Zero means true. Any other value means false. <Cite n={12} /> `elif` and `else` add more branches. <Cite n={27} /> `[ ... ]` is the `test` command, so it needs spaces around the brackets and around each operator. <Cite n={35} /> <Cite n={43} /> `-f` tests for a regular file, and `-d` tests for a directory. <Cite n={28} /> In `[ ]`, quote each variable. <Cite n={32} />

```bash
if [ -f "$path" ]; then echo "a file"; fi
```

**Try it:** make a file in a throw-away directory, print the exit status of two tests, and use one test in `if`.

```bash
(
  cd "$(mktemp -d)"   # make and enter a new, empty directory
  touch notes.txt
  [ -f notes.txt ]; echo "status: $?"   # status: 0  (a regular file)
  [ -d notes.txt ]; echo "status: $?"   # status: 1  (not a directory)
  if [ -f notes.txt ]; then echo "a file"; else echo "no file"; fi   # a file
  rm -r -- "$PWD"     # delete the throw-away directory
)
```

<Callout type="tip" title="Why it matters for testing">

Tutorial's own advice: check preconditions at the top of a script, such as `[ -d "$REPORT_DIR" ] || exit 1`, and print which check failed.

</Callout>

<details>
<summary>Go deeper</summary>

- The `if` command can be any program, such as `grep -q`. <Cite n={27} />
- `-e` tests that a path exists, and `-r` that it is readable. <Cite n={28} /> Numbers use `-eq -ne -lt -le -gt -ge`. Strings use `= !=`. <Cite n={7} /> <Cite n={28} /> Use a single `=` inside `[ ]` for portability. <Cite n={28} />
- An empty unquoted variable vanishes and leaves a broken test. <Cite n={32} />
- `[[ ... ]]` is a Bash keyword that POSIX leaves unspecified. <Cite n={27} /> <Cite n={39} /> It does not split words, it matches patterns with `==`, and `=~` matches a regular expression. In `[[ =~ ]]`, keep the pattern unquoted or in a variable: quotes make the match literal. <Cite n={27} />
- `&&` runs the next command only after success. `||` runs it only after failure. <Cite n={29} /> `a && b || c` is not if/else: `c` also runs when `b` fails.
- `cd "$dir" || exit 1` stops a script when `cd` fails. <Cite n={48} />
- `case` compares one word with patterns and ends each branch with `;;`. <Cite n={27} />

```bash
case "$name" in
  smoke*|sanity*) echo "short suite" ;;
  *)              echo "unknown suite" ;;
esac
```

Tutorial's own advice: a fast, clear failure is better in CI than a wrong result ten minutes later.

</details>

## Loops

<Voices>
<Technical>

**Goal:** Repeat a command for each file, also when a file name has a space.

A loop repeats commands. `for name in words; do ...; done` runs once for each word. `while` repeats as long as its test succeeds. `until` repeats as long as its test fails. <Cite n={30} /> <Cite n={8} /> Put `;` or a newline before `do`. <Cite n={9} /> <Cite n={30} /> To loop over files, use a glob, not `$(ls)`. The output of `ls` is split at spaces, so `my report.txt` becomes two words. <Cite n={47} />

```bash
for f in ./*.txt; do echo "file: $f"; done
```

**Try it:** make two files, one with a space in its name. Loop over them with a glob, then with `$(ls)` (the output of `ls` in its place). <Cite n={17} />

```bash
(
  cd "$(mktemp -d)"   # make and enter a new, empty directory
  touch "my report.txt" b.txt
  for f in ./*.txt; do echo "file: $f"; done
  # file: ./b.txt
  # file: ./my report.txt
  for f in $(ls); do echo "word: $f"; done
  # word: b.txt
  # word: my
  # word: report.txt
  rm -r -- "$PWD"     # delete the throw-away directory
)
```

<Callout type="tip" title="Why it matters for testing">

Tutorial's own advice: when `until` waits for a service, add a counter or a time limit. A dead service then fails the CI job fast.

</Callout>

<details>
<summary>Go deeper</summary>

- `until` is a `while` with the test reversed. <Cite n={30} /> <Cite n={8} />
- `break` leaves the loop, and `continue` starts the next round. <Cite n={35} />
- The C-style `for ((i=0; i<3; i++))` is a Bash form. Dash rejected it in a test. <Cite n={30} />
- If nothing matches, the glob stays as typed, so test with `[ -e "$f" ] || continue`. <Cite n={31} /> Use `--` before names that may start with a dash. <Cite n={6} />
- To read a file line by line, use `while IFS= read -r line; do ...; done < file`. `-r` keeps backslashes. <Cite n={36} /> An empty `IFS` keeps leading spaces. <Cite n={32} /> <Cite n={6} />
- Do not pipe into `while`. Each part of a pipeline runs in its own subshell, a child copy of the shell, so variables set in the loop are lost. <Cite n={33} /> Write `done < file` instead.

```bash
tries=0                                 # poll, but never forever
until [ -e ready.flag ] || [ "$tries" -ge 3 ]; do tries=$((tries + 1)); sleep 1; done
echo "tries: $tries"                    # tries: 3, if ready.flag never appears
```

</details>

</Technical>

**লক্ষ্য:** প্রতিটি file-এর জন্য একটি command বারবার চালান, file-এর নামে space থাকলেও।

Loop command-গুলো বারবার চালায়। `for name in words; do ...; done` প্রতিটি word-এর জন্য একবার চলে। `while` তার test সফল থাকা পর্যন্ত চলে। `until` test ব্যর্থ থাকা পর্যন্ত চলে। <Cite n={30} /> <Cite n={8} /> `do`-এর আগে `;` বা একটি নতুন লাইন দিন। <Cite n={9} /> <Cite n={30} /> File-এর উপর loop চালাতে `$(ls)` নয়, glob ব্যবহার করুন। `ls`-এর output space-এ ভাগ হয়, তাই `my report.txt` দুটি word হয়ে যায়। <Cite n={47} />

**চেষ্টা করুন:** দুটি file বানান, যার একটির নামে space আছে। প্রথমে glob দিয়ে, তারপর `$(ls)` (এর জায়গায় `ls`-এর output বসে) দিয়ে এগুলোর উপর loop চালান। <Cite n={17} />

```bash
(
  cd "$(mktemp -d)"   # make and enter a new, empty directory
  touch "my report.txt" b.txt
  for f in ./*.txt; do echo "file: $f"; done
  # file: ./b.txt
  # file: ./my report.txt
  for f in $(ls); do echo "word: $f"; done
  # word: b.txt
  # word: my
  # word: report.txt
  rm -r -- "$PWD"     # delete the throw-away directory
)
```

<Callout type="tip" title="টেস্টিং-এ কেন দরকার">

Tutorial-এর নিজস্ব পরামর্শ: service-এর জন্য `until` দিয়ে অপেক্ষা করলে একটি counter বা time limit দিন। তাহলে বন্ধ service-এ CI job দ্রুত fail করে।

</Callout>

<details>
<summary>আরও জানুন</summary>

- `until` হলো উল্টো test-সহ একটি `while`। <Cite n={30} /> <Cite n={8} /> `break` loop থেকে বের হয়, আর `continue` পরের round শুরু করে। <Cite n={35} />
- C-style `for ((i=0; i<3; i++))` একটি Bash form; একটি test-এ dash এটি reject করেছে। <Cite n={30} />
- কিছু match না করলে glob যেমন লেখা তেমনই থাকে, তাই `[ -e "$f" ] || continue` দিয়ে test করুন। <Cite n={31} /> যে নাম dash দিয়ে শুরু হতে পারে, তার আগে `--` দিন। <Cite n={6} />
- একটি file লাইন ধরে ধরে পড়তে `while IFS= read -r line` ব্যবহার করুন। `-r` backslash রেখে দেয়। <Cite n={36} /> Empty `IFS` শুরুর space রেখে দেয়। <Cite n={32} /> <Cite n={6} />
- `while`-এর ভেতরে pipe করবেন না। Pipeline-এর প্রতিটি অংশ নিজের subshell-এ চলে, তাই loop-এ set করা variable হারিয়ে যায়। <Cite n={33} /> এর বদলে `done < file` লিখুন।

## Debugging

<Voices>
<Technical>

**Goal:** Trace a script and stop it at the first failed command.

`bash -n script.sh` reports syntax errors and runs nothing. <Cite n={34} /> <Cite n={10} /> `bash -x script.sh` prints each command after expansion. `set -e` stops a script after a failed command. `set -u` makes an unset variable an error. `set -o pipefail` makes a pipeline fail when any part fails. <Cite n={34} /> Never run `rm -rf "$dir/"` with a variable that may be empty: the path can become `/`. Use `${dir:?}`, which stops the script if the variable is unset or empty. <Cite n={16} />

```bash
bash -x script.sh
```

**Try it:** write a script that fails in the middle, check its syntax, and trace it. `bash -x` writes each command with a `+` in front. <Cite n={37} />

```bash
(
  cd "$(mktemp -d)"   # make and enter a new, empty directory
  printf '%s\n' 'set -euo pipefail' 'echo "start"' 'false' 'echo "never reached"' > flaky.sh
  bash -n flaky.sh && echo "syntax ok"   # syntax ok
  bash -x flaky.sh; echo "status: $?"
  # + set -euo pipefail
  # + echo start
  # start
  # + false
  # status: 1
  rm -r -- "$PWD"     # delete the throw-away directory
)
```

<Callout type="tip" title="Why it matters for testing">

Tutorial's own advice: in CI, trace with `set -x` only around the failing step. A trace shows expanded values, so it can put tokens into the log.

</Callout>

<details>
<summary>Go deeper</summary>

- The `PS4` variable sets the prefix of each trace line. `BASH_SOURCE` and `LINENO` add the file and the line. Use single quotes, so `PS4` expands at each trace. <Cite n={37} />
- `set -e` ignores a failure in an `if` test. It also ignores failures before the last command of a `&&` or `||` list, and of a pipeline without `pipefail`. <Cite n={34} /> These options are aids, not guarantees.
- `trap 'cmd' ERR` runs a command when a command fails, with the same exceptions as `set -e`. `trap 'cmd' EXIT` runs when the shell exits, which suits clean-up. It does not run after SIGKILL, which no trap can catch. <Cite n={35} /> <Cite n={50} />
- `ERR` is not a POSIX condition: POSIX lists `EXIT` and signals. <Cite n={39} />
- `echo "x=$x" >&2` prints to the error stream. <Cite n={24} />
- `mktemp -d` makes a temporary directory. <Cite n={44} />
- ShellCheck finds quoting, `$(ls)`, and `cd` mistakes. <Cite n={45} /> <Cite n={46} /> <Cite n={47} /> <Cite n={48} />

```bash
# the top of a script: a temporary directory that the EXIT trap deletes
tmp=$(mktemp -d)
trap 'rm -rf -- "${tmp:?}"' EXIT
trap 'echo "failed at line $LINENO, status $?" >&2' ERR   # ERR: not a POSIX condition
PS4='+ ${BASH_SOURCE##*/}:${LINENO}: '                    # with bash -x: + file:line: command
```

</details>

**লক্ষ্য:** একটি script trace করুন, আর প্রথম fail করা command-এ সেটি থামান।

`bash -n script.sh` syntax error জানায় এবং কিছুই চালায় না। <Cite n={34} /> <Cite n={10} /> `bash -x script.sh` expansion-এর পর প্রতিটি command print করে। `set -e` একটি command fail করলে script থামায়। `set -u` একটি unset variable-কে error বানায়। `set -o pipefail` দিলে pipeline-এর যেকোনো অংশ fail করলে pipeline fail করে। <Cite n={34} /> যে variable empty হতে পারে, তা দিয়ে কখনো `rm -rf "$dir/"` চালাবেন না: path-টি `/` হয়ে যেতে পারে। `${dir:?}` ব্যবহার করুন, যা variable unset বা empty হলে script থামায়। <Cite n={16} />
