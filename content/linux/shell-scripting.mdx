# Shell Scripting

A shell script is a text file of commands that the shell runs for you. This stage covers how to write one, store values, write literal text, decide with conditions, repeat work with loops, and find faults. A tester needs these skills because CI jobs, test set-up, and log checks are often short shell scripts. <Cite n={1} /> <Cite n={3} />

<PageMeta />

## Shell Programming

A shell is a program that passes your commands to the operating system. <Cite n={2} /> A shell script is a text file of such commands. Bash runs it in a non-interactive shell, with no person at the prompt. <Cite n={11} />

The first line is the shebang, `#!` plus the path of an interpreter. The kernel reads it when it runs the file. The file needs the execute permission. <Cite n={41} /> `chmod +x` adds that permission. <Cite n={42} /> `#!/usr/bin/env bash` finds the first `bash` in `PATH`. <Cite n={11} />

`./setup.sh` runs the file in a child shell, so its variables vanish at the end. <Cite n={11} /> `. ./setup.sh` (or `source`) runs it in the current shell. <Cite n={35} /> <Cite n={36} /> Every command ends with an exit status from 0 to 255. Zero means success. `$?` holds the last status. <Cite n={12} /> <Cite n={15} /> A script returns the status of its last command. <Cite n={38} />

```bash
cd "$(mktemp -d)" || exit 1          # a scratch directory: the examples create files here
cat > setup.sh <<'EOF'
#!/usr/bin/env bash
GREETING="hello from setup.sh"
echo "args: $#"
[ "$1" = "ok" ]               # the last command sets the exit status
EOF
chmod +x setup.sh             # the execute permission lets the kernel run it

./setup.sh ok;  echo "status: $?"
./setup.sh bad; echo "status: $?"
echo "after run: ${GREETING:-unset}"
. ./setup.sh                  # source it: it runs in the current shell
echo "after source: ${GREETING:-unset}"
if command -v shellcheck >/dev/null; then shellcheck setup.sh; fi

# Output:
#   args: 1
#   status: 0
#   args: 1
#   status: 1
#   after run: unset
#   args: 0
#   after source: hello from setup.sh
```

POSIX defines the portable shell language. <Cite n={39} /> Debian policy lets a `sh` script in a Debian package assume POSIX plus a few extras. A package script that needs more must name its shell. <Cite n={40} /> In a test with dash, `[[` and arrays gave errors. ShellCheck finds mistakes before a run and reports through its exit status, so CI can run it. <Cite n={45} /> <Cite n={49} />

<Callout type="tip" title="Why it matters for testing">
Tutorial's own advice: start each CI script with a shebang and run `shellcheck` on it in the pipeline. Check the exit status, not the printed text. To find non-POSIX code, run the script under `dash` if installed, or give it a `#!/bin/sh` shebang so ShellCheck warns. <Cite n={45} />
</Callout>

## Variables

A variable holds a value under a name. Assign it as `name=value`, with no spaces around `=`. <Cite n={13} /> Read it with `$name`, and quote the read: `"$name"`. An unquoted value is split at spaces and then treated as a glob, a filename pattern such as `*.txt`. <Cite n={46} /> <Cite n={32} />

Parameter expansion changes a value as the shell reads it. `${name:-default}` gives a default when the variable is unset or empty. `${name:?message}` stops a script with an error in that case. `${#name}` gives the length. <Cite n={16} />

Script arguments arrive as positional parameters `$1`, `$2`, and so on. <Cite n={14} /> `$#` is their count, and `$0` is the name of the script. `"$@"` gives each argument as one separate word. <Cite n={15} />

A shell variable lives in the current shell only. `export` adds it to the environment, the list of name-value pairs that child processes inherit. <Cite n={35} /> <Cite n={19} /> `readonly` blocks later changes with an error. <Cite n={4} /> <Cite n={35} /> `$(command)` is command substitution: it is replaced by the output of the command. <Cite n={17} /> An array is a list of values. It works in bash, ksh, and zsh, but dash rejected it in a test. <Cite n={18} /> <Cite n={46} />

```bash
suite="smoke tests"                    # no spaces around =
echo "suite: $suite"
echo "env: ${TARGET_ENV:-staging}"     # a default if unset or empty

set -- alpha "beta gamma"              # fake two script arguments
echo "count: $#, first: $1"
for arg in "$@"; do echo "arg: $arg"; done

export TARGET_ENV=qa                   # child processes see it
bash -c 'echo "child sees: $TARGET_ENV"'
readonly BASE_URL="https://example.test"
( BASE_URL=other ) 2>&1 || echo "BASE_URL is read-only"

stamp=$(date +%F)                      # command substitution
echo "the date has ${#stamp} characters"
urls=("$BASE_URL/login" "$BASE_URL/cart")   # array: dash rejected this in our test
echo "${#urls[@]} urls, last: ${urls[1]}"
```

<Callout type="tip" title="Why it matters for testing">
Tutorial's own advice: keep the base URL, browser, and environment name in variables with defaults, such as `${TARGET_ENV:-staging}`. A CI job then overrides them without a script edit. Never print variables that hold tokens or passwords into the job log.
</Callout>

## Literals

A literal is text that the shell takes as written. Quoting switches off the special meaning of characters. Single quotes keep every character literal, and a single quote cannot appear inside them. <Cite n={21} /> To place one, close the string, add `\'`, and open it again. <Cite n={5} /> Double quotes keep most characters literal, but `$`, the backtick, and `\` stay active. <Cite n={22} /> A backslash outside quotes makes the next character literal. <Cite n={20} />

`$'...'` decodes escapes such as `\n` and `\t`. <Cite n={23} /> The 2024 POSIX standard defines it, but dash did not decode it in a test. <Cite n={39} />

A here-document gives several lines to a command as input. The word after `<<` is the end marker. If you quote the marker, nothing inside expands. Otherwise variables and `$(...)` expand. With `<<-`, the shell strips leading tabs, so you can indent the text. <Cite n={24} />

Number literals are plain digits. `$((expression))` does arithmetic on whole numbers with C operators. <Cite n={26} /> <Cite n={25} /> A leading `0` means octal, and `0x` means hexadecimal. <Cite n={25} /> The form `base#n` writes a number in another base. POSIX requires only decimal, octal, and hexadecimal constants, so other shells may reject `base#n`. Dash did in a test. <Cite n={25} /> <Cite n={39} />

```bash
cd "$(mktemp -d)" || exit 1          # a scratch directory: the examples create files here
user="qa"
echo 'single: $user stays $(whoami)'    # nothing expands
echo "double: $user and \$5 and \"quoted\""
echo "it's" 'say "hi"' it\'s            # three ways to place a quote
printf '%s\n' $'tab:\there\nnew line'    # decodes escapes

cat <<EOF > report.txt                   # > replaces report.txt: a file this demo owns
user is $user
EOF
cat <<'EOF' >> report.txt
literal: $HOME and \n stay as typed
EOF
cat report.txt

echo $((7 * 6 + 1)) $((10 / 3)) $((10 % 3))   # whole numbers only
echo $((0x1F)) $((2#101)) $((010))            # hex, base 2 (not required by POSIX), octal
```

<Callout type="tip" title="Why it matters for testing">
Tutorial's own advice: write test data such as JSON bodies with a quoted here-document, so the file holds exactly what you typed. Put `grep` patterns in single quotes. Beware of leading zeros: `$((08))` is an error, because `08` is not a valid octal number.
</Callout>

## Conditionals

`if` runs a command and reads its exit status. Zero means true. Any other value means false. <Cite n={12} /> The command can be any program, such as `grep -q`. `elif` and `else` add more branches. <Cite n={27} />

Two forms compare values. `[ ... ]` is the `test` command, so it needs spaces around the brackets and around each operator. <Cite n={35} /> <Cite n={43} /> `[[ ... ]]` is a Bash keyword that POSIX leaves unspecified. <Cite n={27} /> <Cite n={39} /> It does not split words, it matches patterns with `==`, and `=~` matches a regular expression. <Cite n={27} /> In `[[ =~ ]]`, keep the pattern unquoted or in a variable: quotes make the match literal. <Cite n={27} /> Use a single `=` inside `[ ]` for portability. <Cite n={28} />

File tests: `-f` regular file, `-d` directory, `-e` exists, `-r` readable. <Cite n={28} /> Numbers use `-eq -ne -lt -le -gt -ge`. Strings use `= !=`. <Cite n={7} /> <Cite n={28} /> In `[ ]`, quote each variable. An empty unquoted variable vanishes and leaves a broken test. <Cite n={32} />

`&&` runs the next command only after success. `||` runs it only after failure. <Cite n={29} /> `a && b || c` is not if/else: `c` also runs when `b` fails. `cd "$dir" || exit 1` stops a script when `cd` fails. <Cite n={48} /> `case` compares one word with patterns and ends each branch with `;;`. <Cite n={27} />

```bash
cd "$(mktemp -d)" || exit 1          # a scratch directory: the examples create files here
path=notes.txt count=12 name="smoke test"
printf 'ok\n' > "$path"               # the demo creates its own file

if [ -d "$path" ]; then
  echo "directory"
elif [ -f "$path" ] && [ -r "$path" ]; then
  echo "readable file"
else
  echo "missing or not a file"
fi

[ "$count" -ge 10 ] && echo "count: 10 or more"
[ "$name" = "smoke test" ] && echo "same name"
[[ $name == smoke* ]] && echo "pattern match"   # POSIX leaves [[ unspecified
if grep -q '^root:' /etc/passwd; then echo "if tests any command"; fi

case "$name" in
  smoke*|sanity*) echo "short suite" ;;
  *)              echo "unknown suite" ;;
esac

true && false || echo "runs although the middle command failed"
```

<Callout type="tip" title="Why it matters for testing">
Tutorial's own advice: check preconditions at the top of a script, for example `[ -d "$REPORT_DIR" ] || exit 1`, and print which check failed. A fast, clear failure is better in CI than a wrong result ten minutes later.
</Callout>

## Loops

A loop repeats commands. `for name in words; do ...; done` runs once for each word. `while` repeats as long as its test succeeds. `until` repeats as long as it fails, so it is a `while` with the test reversed. <Cite n={30} /> <Cite n={8} /> Put `;` or a newline before `do`. <Cite n={9} /> <Cite n={30} /> `break` leaves the loop, and `continue` starts the next round. <Cite n={35} /> The C-style `for ((i=0; i<3; i++))` is a Bash form; dash rejected it in a test. <Cite n={30} />

To loop over files, use a glob, not `$(ls)`. The output of `ls` is split at spaces, so `my report.txt` becomes two words. <Cite n={47} /> If nothing matches, the glob stays as typed, so test with `[ -e "$f" ] || continue`. <Cite n={31} /> Use `--` before names that may start with a dash. <Cite n={6} />

To read a file line by line, use `while IFS= read -r line`. `-r` keeps backslashes. <Cite n={36} /> An empty `IFS` keeps leading spaces. <Cite n={32} /> <Cite n={6} /> Do not pipe into `while`. Each part of a pipeline runs in its own subshell, a child copy of the shell, so variables set in the loop are lost. <Cite n={33} /> Write `done < file` instead.

```bash
cd "$(mktemp -d)" || exit 1          # a scratch directory: the examples create files here
touch -- "my report.txt" "-odd.txt"     # a space in one name, a dash in the other
for f in ./*.txt; do                    # a glob: safe for odd names
  [ -e "$f" ] || continue               # no match: the glob stays as typed
  echo "file: $f"
done

printf '%s\n' "first" "  indented \\ line" "last" > lines.dat
while IFS= read -r line; do             # keeps spaces and backslashes
  printf '[%s]\n' "$line"
done < lines.dat

total=0
for n in 1 2 3 4 5; do
  [ "$n" -eq 2 ] && continue            # skip this round
  [ "$n" -eq 5 ] && break               # leave the loop
  total=$((total + n))
done
echo "total: $total"

tries=0                                 # poll, but never forever
until [ -e ready.flag ] || [ "$tries" -ge 3 ]; do tries=$((tries + 1)); sleep 1; done
echo "tries: $tries"
```

<Callout type="tip" title="Why it matters for testing">
Tutorial's own advice: use `until` to wait for a service, and always add a counter or a time limit. A dead service then fails the CI job fast instead of hanging it.
</Callout>

## Debugging

`bash -n script.sh` reads a script, reports syntax errors, and runs nothing. <Cite n={34} /> <Cite n={10} /> `bash -x script.sh` prints each command after expansion. <Cite n={34} /> The `PS4` variable sets the prefix of each trace line, and `BASH_SOURCE` and `LINENO` add file and line. Use single quotes, so `PS4` expands at each trace. <Cite n={37} />

`set -e` stops a script after a failed command. It ignores a failure in an `if` test. It also ignores failures before the last command of a `&&` or `||` list, and of a pipeline without `pipefail`. `set -o pipefail` makes a pipeline fail when any part fails. `set -u` makes an unset variable an error. <Cite n={34} /> These are aids, not guarantees.

A trap runs a command on an event. `trap 'cmd' ERR` fires when a command fails, with the same exceptions as `set -e`. `trap 'cmd' EXIT` fires when the shell exits, which suits clean-up, but not after SIGKILL, which no trap can catch. <Cite n={35} /> <Cite n={50} /> `ERR` is not a POSIX condition: POSIX lists `EXIT` and signals. <Cite n={39} /> Print to the error stream with `echo "x=$x" >&2`. <Cite n={24} /> ShellCheck finds quoting, `$(ls)`, and `cd` mistakes. <Cite n={45} /> <Cite n={46} /> <Cite n={47} /> <Cite n={48} />

```bash
cd "$(mktemp -d)" || exit 1          # a scratch directory: the examples create files here
cat > flaky.sh <<'EOF'                  # creates flaky.sh in the scratch directory
#!/usr/bin/env bash
set -euo pipefail
tmp=$(mktemp -d)
trap 'rm -rf -- "${tmp:?}"' EXIT
trap 'echo "failed at line $LINENO, status $?" >&2' ERR   # ERR: not a POSIX condition
echo "start" > "$tmp/log.txt"
grep -c "missing" "$tmp/log.txt"        # exits 1: no match
echo "never reached"
EOF
bash -n flaky.sh && echo "syntax ok"
bash flaky.sh; echo "status: $?"
PS4='+ ${BASH_SOURCE##*/}:${LINENO}: ' bash -x flaky.sh 2>&1 | tail -5

# Output (the temporary path differs on each run):
#   syntax ok
#   0
#   failed at line 7, status 1
#   status: 1
#   + flaky.sh:7: grep -c missing /tmp/tmp.XXXXXXXXXX/log.txt
#   0
#   ++ flaky.sh:7: echo 'failed at line 7, status 1'
#   failed at line 7, status 1
#   + flaky.sh:1: rm -rf -- /tmp/tmp.XXXXXXXXXX
```

<Callout type="danger">
Never run `rm -rf "$dir/"` with a variable that may be empty: the path can become `/`. Use `${dir:?}`, which stops the script if it is unset or empty. <Cite n={16} /> `mktemp -d` makes the directory. <Cite n={44} />
</Callout>

<Callout type="tip" title="Why it matters for testing">
Tutorial's own advice: in CI, trace with `set -x` only around the failing step. A trace shows expanded values, so it can put tokens into the job log.
</Callout>
