# Shell Basics

This stage covers the shell, the first commands you type in it, and the layout of the system around you. A tester needs it because each CI log, test runner, and server check starts at a shell prompt, and many failures come from a wrong directory, a missing command, or a wrong variable.

<PageMeta />

## Shell Basics

The shell is a program. It takes the commands that you type and gives them to the operating system. <Cite n={11} /> On most Linux systems the shell is bash. Bash is a newer shell that builds on the old Bourne shell. <Cite n={1} /> <Cite n={11} /> Other shells exist, for example ksh, tcsh, and zsh. <Cite n={11} />

A terminal is not a shell. The terminal is the program that opens a window for you. <Cite n={11} /> The shell is the program inside it that reads your commands. <Cite n={12} />

Bash reads different startup files in different modes. <Cite n={1} />

- A login shell reads `/etc/profile`. Then it reads the first file that it finds of `~/.bash_profile`, `~/.bash_login`, and `~/.profile`.
- A `bash` that you start by hand at the prompt reads `~/.bashrc`, if it is interactive and was not started as a login shell. A script that you run with `bash script.sh` does not read this file.
- A non-interactive shell, for example a script, reads the file that `BASH_ENV` names.

```bash
echo "$SHELL"   # the login shell of your user
echo "$-"       # contains i in an interactive shell
bash --version
```

`SHELL` holds the absolute path of the login shell of the user. <Cite n={7} /> Bash puts `i` in `$-` when the shell is interactive. <Cite n={1} />

<Callout type="tip" title="Why it matters for testing">

Tutorial's own advice: a CI job often runs a non-interactive shell, so it does not read `~/.bashrc`. If a command works in your terminal but fails in the job, print `$-` and `$PATH` at the start of the job. Then compare them with your terminal.

</Callout>

## Basic Commands

Three commands are the base of all navigation. `pwd` prints the absolute path of the current directory. <Cite n={1} /> `cd` changes the current directory. <Cite n={1} /> `ls` lists the entries of a directory. If you give no path, it lists the current directory. <Cite n={2} />

`ls` hides the names that start with a dot. Add `-a` to show them. <Cite n={2} /> These options are the most useful:

| Option | Effect |
|---|---|
| `-l` | Long format. <Cite n={2} /> |
| `-a` | Do not ignore entries that start with a dot. <Cite n={2} /> |
| `-h` | With `-l`, print sizes such as 1K, 234M, 2G. <Cite n={2} /> |
| `-t` | Sort by time, newest first. <Cite n={2} /> |
| `-r` | Reverse the sort order. <Cite n={2} /> |

```bash
pwd
ls -l
ls -lah /var/log
ls -ltr          # oldest first, newest last
```

Without an argument, `cd` goes to the directory in `HOME`. <Cite n={1} />

<Callout type="tip" title="Why it matters for testing">

Tutorial's own advice: before a step that fails in a pipeline, print `pwd` and `ls -la`. A flaky test often depends on a working directory or on a file that is not there yet. `ls -ltr` puts the newest report or log at the end of the list, so you find it fast.

</Callout>

## Navigation Basics

An absolute path starts with `/`, the root of the file tree. A relative path starts from the current directory. <Cite n={13} /> In a path, `.` is the current directory and `..` is the parent directory. <Cite n={13} />

Bash gives you three shortcuts:

- `~` expands to the value of `HOME`. <Cite n={1} />
- `cd -` goes back to the directory in `OLDPWD`, the previous working directory. <Cite n={1} />
- `cd` with no argument goes to your home directory. <Cite n={14} />

```bash
cd /usr/local/bin
cd ..          # now in /usr/local
cd ~           # your home directory
cd -           # back in /usr/local
pwd -P         # print the path without symbolic links
```

By default, `cd` follows symbolic links logically (`-L`). The option `-P` makes `cd` use the physical directory structure. <Cite n={1} /> The option `-P` of `pwd` prints a path with no symbolic links. <Cite n={1} />

<Callout type="tip" title="Why it matters for testing">

Tutorial's own advice: use absolute paths in test scripts, or set the directory at the top with `cd "$(dirname "$0")"`. A relative path works only from the directory where you started the test. A CI runner often starts in another one.

</Callout>

## Command Help

The system holds its own documentation. Use the tool that fits the command.

- `man name` shows the manual page of a program. <Cite n={4} />
- `help name` shows help for a bash builtin such as `cd`. <Cite n={1} />
- `name --help` prints a short usage text. `ls` and `pwd` accept it. <Cite n={2} /> <Cite n={3} /> Many other commands do, but the rule is not fixed. <Cite n={16} />
- `tldr name` shows short examples. The tldr-pages project is a community collection that is simpler than a man page. <Cite n={17} />

The manual has numbered sections. Section 1 holds programs, section 5 holds file formats, section 7 holds conventions, and section 8 holds administration commands. <Cite n={4} /> Use `man -k word` to search the short descriptions. Use `man -f name` to print the short description of a page. <Cite n={4} /> The `help` builtin has `-d` for a short description and `-s` for the usage line only. <Cite n={1} /> <Cite n={15} />

```bash
man ls
man 5 passwd      # section 5: the file format
man -k printf
help -s cd
ls --help
type -t cd        # builtin
```

<Callout type="tip" title="Why it matters for testing">

Tutorial's own advice: read the help on the machine that runs your tests, not on your laptop. The options of a tool can differ between versions and images. Then copy the exact flag into your script.

</Callout>

## Command Path

When a command name has no slash, bash looks in a fixed order: a shell function, then a builtin, then the directories of `PATH`. <Cite n={1} /> `PATH` is a list of directories with a colon between them. The shell searches the list from the first to the last. <Cite n={7} /> Bash remembers the full path of a command it found. `hash -r` clears this memory. <Cite n={1} /> If bash finds no command, it prints an error and returns exit status 127. <Cite n={1} />

```bash
echo "$PATH" | tr ':' '\n'
type -a ls                   # all places where ls is found
command -v python3           # the one that would run
whereis ls                   # binary, source, and manual files
export PATH="$HOME/bin:$PATH"
hash -r
```

`whereis` shows where the program, the source, and the manual page of a command are. <Cite n={5} /> To keep a `PATH` change, put the `export` line in `~/.bashrc`. <Cite n={18} />

<Callout type="warning" title="Common mistake: an empty entry in PATH">

A zero-length entry in `PATH` means the current directory. You get it from two colons in a row, or from a colon at the start or the end. <Cite n={1} /> POSIX says that an application must use an explicit `.` for this, and the legacy form is deprecated. <Cite n={7} /> Do not write `PATH="$PATH:"`.

</Callout>

<Callout type="tip" title="Why it matters for testing">

Tutorial's own advice: "command not found" with status 127 in a CI step usually means that `PATH` has no directory for the tool. Print `$PATH` and run `command -v tool` at the start of the job. Because the first match wins, an old copy of a tool in an early directory can hide the new one.

</Callout>

## Directory Hierarchy

All files sit under one root, `/`. The absolute path of each file goes through the root. <Cite n={19} /> The Filesystem Hierarchy Standard (FHS) defines what the main directories hold. <Cite n={10} /> The root filesystem must be enough to boot, restore, recover, and repair the system. <Cite n={10} />

| Path | What it holds |
|---|---|
| `/etc` | Configuration files for this machine. <Cite n={6} /> |
| `/home` | The home directories of users. <Cite n={6} /> |
| `/root` | The home directory of the root user. <Cite n={6} /> |
| `/usr/bin` | The main directory for executable programs. <Cite n={6} /> |
| `/usr/local` | Programs that are local to the site. <Cite n={6} /> |
| `/var` | Data that grows and shrinks while the system runs, for example logs and spool files. <Cite n={6} /> |
| `/tmp` | Temporary files. The system may delete them without notice. <Cite n={6} /> |
| `/dev` | Special files that refer to devices. <Cite n={6} /> |
| `/proc` | Information about running processes and the kernel. <Cite n={6} /> |
| `/opt` | Add-on application packages. <Cite n={6} /> |

```bash
ls /
ls -ld /tmp /var /etc
man 7 hier        # the full list
```

<Callout type="tip" title="Why it matters for testing">

Tutorial's own advice: do not keep test evidence in `/tmp`. The system may delete it. Copy reports and logs to a folder that your CI job saves. When a service under test fails, look in `/var/log` for its logs <Cite n={6} /> and in `/etc` for its configuration.

</Callout>

## Environment Variables

The environment is a list of strings in the form `name=value`. A new program gets it at start. A child process gets a copy of the environment of its parent. <Cite n={7} /> The name is case-sensitive. <Cite n={7} />

A normal assignment makes a shell variable. A child process does not see it. The `export` command marks the name for the environment of later commands. <Cite n={1} /> <Cite n={21} /> `unset` removes a variable. <Cite n={1} />

```bash
printenv HOME
API_URL=http://localhost:8080
bash -c 'echo "[$API_URL]"'    # prints []
export API_URL
bash -c 'echo "[$API_URL]"'    # prints [http://localhost:8080]
API_URL=http://staging.example.test bash -c 'echo "$API_URL"'   # one command only
unset API_URL
env -i HOME=/tmp printenv      # a clean environment
```

`printenv` prints the named variables, or all of them. <Cite n={9} /> The form `NAME=value command` sets a variable only for that command. <Cite n={7} /> With `env -i`, a command starts with an empty environment. <Cite n={8} /> To keep a variable for each login, add it to `~/.bash_profile`. <Cite n={20} /> Common names are `HOME`, `PATH`, `PWD`, `SHELL`, `USER`, `LANG`, and `TMPDIR`. <Cite n={7} />

<Callout type="tip" title="Why it matters for testing">

Tutorial's own advice: a test that reads a URL, a token, or `LANG` from the environment can behave differently on a laptop and on a runner. Run it with `env -i` and set only the variables that you need. Do not run `printenv` in a shared CI log, because it can print secrets.

</Callout>
