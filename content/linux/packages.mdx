# Packages

A package manager installs, upgrades, and removes software for you. This stage explains packages and repositories, how to find, install, upgrade, and list packages, and how Snap differs. A tester needs it because every test machine, container image, and CI runner is built from packages. <Cite n={1} /> <Cite n={2} />

<PageMeta />

## Package Management

<Voices>
<Technical>

A package is an archive with programs, configuration files, and metadata such as the version and the dependencies. <Cite n={2} /> A dependency is another package that must be installed with it. A conflicting dependency is a package that must not be installed with it. <Cite n={6} /> A package manager installs, upgrades, and removes packages and solves the dependencies. <Cite n={2} />

Each family has a low-level tool and a high-level tool. The low-level tool works on single package files. The high-level tool also downloads packages from repositories, with their dependencies. <Cite n={18} /> <Cite n={4} /> APT adds features on top of `dpkg`. <Cite n={18} />

| Family | Low-level | High-level | File |
|---|---|---|---|
| Debian, Ubuntu | `dpkg` <Cite n={7} /> | `apt` <Cite n={9} /> | `.deb` <Cite n={18} /> |
| RHEL, Fedora | `rpm` <Cite n={26} /> | `dnf` <Cite n={25} /> | `.rpm` <Cite n={26} /> |

`dpkg` cannot fetch a package or its dependencies. <Cite n={18} /> Do daily work with the high-level tool, so that you do not list the dependencies yourself. `rpm` can install, query, verify, and erase single packages. <Cite n={26} /> `dnf install` also installs the dependencies. <Cite n={21} /> `apt-cache depends` shows what a package needs. <Cite n={11} /> `dpkg-query -W` shows the installed version. <Cite n={8} />

```bash
dpkg-query -W bash        # Debian, Ubuntu: the installed version of one package
apt-cache depends bash    # Debian, Ubuntu: what that package needs
rpm -q bash               # RHEL, Fedora: is it installed? Run the lines of your family.
```

<Callout type="tip" title="Why it matters for testing">

Tutorial's own advice: put the package manager and the package versions in each test report. A failure on one runner often comes from another version of a dependency. Name the family of each test image, so that setup scripts call the right tool.

</Callout>

</Technical>

## Package Repositories

<Voices>
<Technical>

A repository is a server that holds packages and their metadata. <Cite n={3} /> A mirror is a copy of a repository on another server.

Debian and Ubuntu read `/etc/apt/sources.list` and the files in `/etc/apt/sources.list.d/`. In current APT, the one-line `.list` format is deprecated. The deb822 `.sources` format uses `Field: value` stanzas, with fields such as `Types` and `URIs`. <Cite n={14} /> Ubuntu releases before 24.04 LTS use `sources.list`. <Cite n={18} /> Debian has the components `main`, `contrib`, and `non-free`. <Cite n={14} /> Ubuntu adds `universe`, without official support. <Cite n={18} />

RHEL and Fedora use `*.repo` files in `/etc/yum.repos.d`. A repository has a `baseurl`, `mirrorlist`, or `metalink`, plus `gpgcheck` and `gpgkey`. <Cite n={22} /> The DNF default of `gpgcheck` is off, so set it. <Cite n={22} />

A GPG signature proves who published a file. A keyring is a file of the public keys that check it. APT checks the signature of the `Release` file, which lists the checksums of the repository files. <Cite n={13} /> `Signed-By` limits a repository to the keys that you name. <Cite n={14} /> A PPA is an apt repository of one user or team, hosted by Launchpad. <Cite n={20} />

```bash
ls /etc/apt/sources.list.d/    # Debian, Ubuntu: one file per source
apt-cache policy | head -n 12  # the sources that apt uses
ls /etc/yum.repos.d/           # RHEL, Fedora
dnf repolist                   # RHEL, Fedora: the enabled repositories
```

<Callout type="danger" title="A new repository or key can run code as root">

A third-party package runs maintainer scripts, its install-time scripts, as root. <Cite n={17} /> A trusted archive means a trusted maintainer, not safe code. <Cite n={13} /> Check the key fingerprint with the publisher. Keep the key in `/etc/apt/keyrings` and use `Signed-By`, not the deprecated `apt-key add`. <Cite n={14} /> <Cite n={15} /> Never pipe `curl` into `sudo sh`.

</Callout>

<Callout type="tip" title="Why it matters for testing">

Tutorial's own advice: log `sources.list` and `sources.list.d` in each test run. Extra repositories explain package differences.

</Callout>

</Technical>

## Finding and Installing Packages

<Voices>
<Technical>

APT searches a local index, which `apt update` refreshes. <Cite n={10} /> `apt search` looks in package names and descriptions. <Cite n={11} /> `apt show` prints dependencies, sizes, and sources. <Cite n={9} /> `apt-cache policy` without a name lists the sources and their priorities. With a name, it shows how apt picks that package. <Cite n={11} /> `apt install` also installs the dependencies. <Cite n={10} /> `apt-file search` finds the package that contains a file. It is a separate package, and `apt-file update` must run first. <Cite n={16} />

DNF has `dnf search`, `dnf info`, and `dnf install`. <Cite n={21} /> `dnf search` matches names and summaries, and ignores case. <Cite n={21} /> `dnf provides /path/to/file` finds the package that holds a file, installed or not. <Cite n={21} /> It also accepts a command name, such as `zless`. <Cite n={21} /> DNF 5 keeps these commands. <Cite n={25} />

To pin a version, write `apt install pkg=version`, or `pkg/release` for a release. <Cite n={9} /> With DNF, add it to the name, as in `dnf install tito-0.5.6-1.fc22`. <Cite n={21} />

`apt` is made for people, and its behavior may change between versions. Scripts should call `apt-get`. <Cite n={9} /> <Cite n={18} />

```bash
apt-cache search --names-only '^jq$'   # search the local index
apt show jq                            # details, with dependencies
apt-cache policy jq                    # which source supplies it
apt-get -s install jq                  # -s: simulate only, nothing changes
dnf provides /usr/bin/jq               # RHEL, Fedora: which package has this file
sudo dnf install --assumeno jq         # needs root; RHEL, Fedora: show the plan, answer no
```

<Callout type="danger" title="Install runs code as root">

`sudo apt install jq` and `sudo dnf install jq` change the system. A package script runs as root. <Cite n={17} /> Simulate first, as above. <Cite n={10} /> Install only from repositories that you trust.

</Callout>

<Callout type="tip" title="Why it matters for testing">

Tutorial's own advice: pin the version of a tool in a test image, for example `jq=<version>`. This does not pin its dependencies. An old version may leave the repository, so keep a local copy or a package snapshot for long-lived images.

</Callout>

</Technical>

## Installing, Removing, and Upgrading Packages

<Voices>
<Technical>

Update and upgrade are two steps. `apt update` only refreshes the package index. <Cite n={10} /> `apt upgrade` installs newer versions but never removes a package. <Cite n={9} /> `apt full-upgrade` may remove packages. <Cite n={9} /> `dnf upgrade` updates each package to its latest version. <Cite n={21} /> In DNF 4, `dnf check-update` returns exit status 100 if upgrades exist. <Cite n={21} /> An exit status is the number that a command returns. DNF 5 names the check `dnf check-upgrade`. <Cite n={37} />

`remove` keeps the configuration files. `purge` deletes them but not your home data. <Cite n={9} /> `autoremove` deletes dependencies that nobody needs now. List them first with `apt-get -s autoremove`. <Cite n={17} /> `dnf remove` also removes the packages that depend on the target. <Cite n={21} />

`apt-mark hold` stops the automatic install, upgrade, and removal of one package. <Cite n={12} /> DNF has the versionlock plugin. <Cite n={23} />

On Ubuntu Server, the default `unattended-upgrades` package installs security updates. Reboot is off by default. <Cite n={19} /> `unattended-upgrade --dry-run` only simulates a run. <Cite n={27} /> `dnf-automatic.timer` follows `/etc/dnf/automatic.conf`, whose defaults download and apply nothing. The install timer unit applies updates. <Cite n={24} />

```bash
apt-get -s upgrade       # preview: what an upgrade would change
apt-get -s autoremove    # preview: what autoremove would delete
apt-mark showhold        # which packages are held
dnf check-update         # DNF 4: list upgrades; exit status 100 means some exist (DNF 5: check-upgrade)
sudo unattended-upgrade --dry-run   # needs root and the unattended-upgrades package: simulate a run
```

<Callout type="danger" title="These commands change or delete software">

`apt remove`, `apt purge`, `apt autoremove`, and `dnf remove` delete packages. `-y` answers every prompt with yes. <Cite n={10} /> `-y` runs a command without prompts, so a script on a disposable container or CI runner needs it. On a shared machine, do not use `-y` or `apt upgrade`. <Cite n={10} />

</Callout>

<Callout type="tip" title="Why it matters for testing">

Tutorial's own advice: on a CI runner, run `apt-get update`, then `apt-get install -y` with named packages and fixed versions. Automatic upgrades can change a package during a test run. Turn them off or log them. <Cite n={19} />

</Callout>

</Technical>

## Listing Installed Packages

<Voices>
<Technical>

`dpkg -l` lists packages. The first two letters, `ii`, mean wanted (install) and installed. Quote a pattern, as in `'libc6*'`. <Cite n={8} /> `apt list --installed` lists them too. <Cite n={9} /> On RHEL and Fedora, use `rpm -qa` or `dnf list --installed`. <Cite n={26} /> <Cite n={21} />

To find the owner of a file, use `dpkg -S` or `rpm -qf`. <Cite n={8} /> <Cite n={26} /> `dpkg -S` cannot see files that maintainer scripts (install-time scripts) create. <Cite n={8} /> `dpkg -L` lists the files of a package. <Cite n={7} />

APT marks a package as manual if you asked for it and as automatic if it came as a dependency. `apt-mark showmanual` lists the manual ones. <Cite n={12} />

For scripts, use `dpkg-query -W -f`, which sets the output format. The `dpkg -l` layout is for people. The default output of `dpkg-query -W` is the package name and the version, separated by a tab. <Cite n={8} /> `rpm -qi` shows the details of a package, and `rpm -ql` lists its files. <Cite n={26} /> `dpkg -s` shows the status of a package. <Cite n={7} />

```bash
dpkg-query -W -f='${binary:Package}=${Version}\n' | sort > packages.txt   # creates packages.txt here
wc -l < packages.txt                # how many packages
dpkg -S /etc/host.conf              # which package owns this file
apt-mark showmanual | head -n 3     # packages that someone asked for
rpm -qa | sort | head -n 3          # RHEL, Fedora
rpm -qf "$(command -v bash)"        # RHEL, Fedora: owner of bash
```

<Callout type="tip" title="Why it matters for testing">

Tutorial's own advice: save the package list as an artifact of every test run or image build. Compare two lists with `diff` to explain why a test passes on one machine and fails on another. The list also records the dependencies. An old version may leave the repository, so for long-lived images keep a local copy or a package snapshot.

</Callout>

</Technical>

## Snap

<Voices>
<Technical>

A snap is a self-contained app package. It bundles the app with its libraries. <Cite n={5} /> The `snapd` daemon, a background service, installs, confines, and updates snaps. <Cite n={34} /> It must run before you can install a snap, and some distributions need you to install it. <Cite n={36} />

```bash
snap list                 # installed snaps, with channel and notes
snap find "media player"  # search the Snap Store
snap info vlc             # details and channels
snap refresh --time       # when snaps refresh
ls /snap/bin | head -n 3  # the commands of snaps (on your PATH)
```

`sudo snap install` and `sudo snap remove` add and delete snaps. <Cite n={35} /> A channel is `track/risk/branch`, and the branch is optional. The risk levels are `stable`, `candidate`, `beta`, and `edge`. The default is `stable`. <Cite n={29} /> Confinement is the isolation of an app from the system. A `strict` snap cannot reach files, network, or other resources without an interface. A `classic` snap has full access, like a normal package, and needs `--classic`. <Cite n={28} /> <Cite n={31} />

By default, snaps refresh four times a day. `snap refresh --hold=24h firefox` pauses one snap. <Cite n={30} /> The commands are links in `/snap/bin`. <Cite n={33} /> Data is under `/var/snap` and `~/snap`. <Cite n={32} />

<Callout type="danger" title="Remove can delete data">

`snap remove --purge` removes a snap without a snapshot of its data. <Cite n={35} /> A `classic` snap has no sandbox. <Cite n={31} /> Install it only from a publisher that you trust.

</Callout>

<Callout type="tip" title="Why it matters for testing">

Tutorial's own advice: pin the channel with `--channel=` and hold the refresh during a test run. An auto-refresh can change the app version in the middle of a test. If a snapped tool cannot read a test file, check the confinement first. <Cite n={28} />

</Callout>

</Technical>
