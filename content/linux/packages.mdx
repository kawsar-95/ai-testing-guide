# Packages

A package manager installs, upgrades, and removes software for you. This stage explains packages and repositories, how to find, install, upgrade, and list packages, and how Snap differs. A tester needs it because every test machine, container image, and CI runner is built from packages. <Cite n={1} /> <Cite n={2} />

## Package Management

<Voices>
<Technical>

**Goal:** Read the name, the version, and the dependencies of a package file.

A package is an archive with programs, configuration files, and metadata such as the version and the dependencies. <Cite n={2} /> A dependency is another package that must be installed with it. <Cite n={6} /> A package manager installs, upgrades, and removes packages and solves the dependencies. <Cite n={2} /> `dpkg-query -W` shows the installed version of a package. <Cite n={8} />

```bash
dpkg-query -W bash    # Debian, Ubuntu: the installed version of bash
```

**Try it:** on Debian or Ubuntu, build a tiny `.deb` file in a throw-away directory and read its metadata. `dpkg -b` builds a package from a directory, and `dpkg -f` prints fields of its metadata. <Cite n={7} /> `> /dev/null 2>&1` hides the build messages. The parentheses keep your shell unchanged.

```bash
(
  d="$(mktemp -d)" && cd "$d"   # make and enter a new, empty directory
  mkdir -p demo/DEBIAN demo/usr/bin
  printf '#!/bin/sh\necho hello\n' > demo/usr/bin/demo-hello
  printf 'Package: demo-hello\nVersion: 1.0\nArchitecture: all\nMaintainer: Example <user@example.com>\nDepends: bash\nDescription: a demo package\n' > demo/DEBIAN/control
  dpkg -b demo demo.deb > /dev/null 2>&1
  dpkg -f demo.deb Package Version Depends
  # Package: demo-hello
  # Version: 1.0
  # Depends: bash
  rm -r "$d"                    # delete the throw-away directory
)
```

<Callout type="tip" title="Why it matters for testing">

Tutorial's own advice: put the package versions in each test report. A failure on one runner often comes from another version of a dependency.

</Callout>

<details>
<summary>Go deeper</summary>

- A conflicting dependency is a package that must not be installed with it. <Cite n={6} />
- Each family has a low-level tool for single package files and a high-level tool that also downloads packages and their dependencies from repositories. <Cite n={18} /> <Cite n={4} /> APT adds features on top of `dpkg`. <Cite n={18} />
- `dpkg` cannot fetch a package or its dependencies. <Cite n={18} /> `rpm` can install, query, verify, and erase single packages. <Cite n={26} /> `dnf install` also installs the dependencies. <Cite n={21} />
- `apt-cache depends` shows what a package needs. <Cite n={11} />

| Family | Low-level | High-level | File |
|---|---|---|---|
| Debian, Ubuntu | `dpkg` <Cite n={7} /> | `apt` <Cite n={9} /> | `.deb` <Cite n={18} /> |
| RHEL, Fedora | `rpm` <Cite n={26} /> | `dnf` <Cite n={25} /> | `.rpm` <Cite n={26} /> |

```bash
apt-cache depends bash    # Debian, Ubuntu: what that package needs
rpm -q bash               # RHEL, Fedora: is it installed?
```

Tutorial's own advice: do daily work with the high-level tool, so that you do not list the dependencies yourself. Name the family of each test image, so that setup scripts call the right tool.

</details>

## Package Repositories

<Voices>
<Technical>

**Goal:** Find the repositories that APT uses and the key that signs each one.

A repository is a server that holds packages and their metadata. <Cite n={3} /> Debian and Ubuntu read `/etc/apt/sources.list` and the files in `/etc/apt/sources.list.d/`. The deb822 `.sources` format uses `Field: value` stanzas, such as `URIs`. `Signed-By` limits a repository to the keys that you name. <Cite n={14} /> RHEL and Fedora use `*.repo` files in `/etc/yum.repos.d`. <Cite n={22} /> A third-party package runs its install-time scripts as root, so add only a repository that you trust. <Cite n={17} />

```bash
apt-cache policy | head -n 12   # Debian, Ubuntu: the sources that apt uses
```

**Try it:** print the address and the key file of each repository. This run is on Ubuntu 26.04, which has the file `ubuntu.sources`. On another system, pick a `.sources` file in `/etc/apt/sources.list.d/`. `grep -E` prints the lines that start with these field names.

```bash
grep -E '^(URIs|Signed-By):' /etc/apt/sources.list.d/ubuntu.sources
# URIs: http://archive.ubuntu.com/ubuntu/
# Signed-By: /usr/share/keyrings/ubuntu-archive-keyring.gpg
# URIs: http://security.ubuntu.com/ubuntu/
# Signed-By: /usr/share/keyrings/ubuntu-archive-keyring.gpg
```

<Callout type="tip" title="Why it matters for testing">

Tutorial's own advice: log `sources.list` and `sources.list.d` in each test run. Extra repositories explain package differences.

</Callout>

<details>
<summary>Go deeper</summary>

- A mirror is a copy of a repository on another server.
- In current APT, the one-line `.list` format is deprecated. Other deb822 fields are `Types` and `Suites`. <Cite n={14} /> Ubuntu releases before 24.04 LTS use `sources.list`. <Cite n={18} />
- Debian has the components `main`, `contrib`, and `non-free`. <Cite n={14} /> Ubuntu adds `universe`, without official support. <Cite n={18} />
- A `.repo` repository has a `baseurl`, `mirrorlist`, or `metalink`, plus `gpgcheck` and `gpgkey`. The DNF default of `gpgcheck` is off, so set it. <Cite n={22} />
- A GPG signature proves who published a file. A keyring is a file of the public keys that check it. APT checks the signature of the `Release` file, which lists the checksums of the repository files. <Cite n={13} />
- A PPA is an apt repository of one user or team, hosted by Launchpad. <Cite n={20} />

```bash
ls /etc/apt/sources.list.d/    # Debian, Ubuntu: one file per source
ls /etc/yum.repos.d/           # RHEL, Fedora
dnf repolist                   # RHEL, Fedora: the enabled repositories
```

Before you add a repository or a key:

- A trusted archive means a trusted maintainer, not safe code. <Cite n={13} />
- Check the key fingerprint with the publisher. Keep the key in `/etc/apt/keyrings` and use `Signed-By`, not the deprecated `apt-key add`. <Cite n={14} /> <Cite n={15} />
- Tutorial's own advice: never pipe `curl` into `sudo sh`.

</details>

</Technical>

## Finding and Installing Packages

<Voices>
<Technical>

**Goal:** Find a package and preview its install, with no change to the system.

APT searches a local index, which `apt update` refreshes. <Cite n={10} /> `apt search` looks in package names and descriptions. With a name, `apt-cache policy` shows how apt picks that package. <Cite n={11} /> `apt install` also installs the dependencies. <Cite n={10} /> An install changes the system, and a package script runs as root. <Cite n={17} /> So simulate first: `apt-get -s` shows what would happen and changes nothing. <Cite n={10} />

```bash
apt show jq    # Debian, Ubuntu: details, with dependencies
```

**Try it:** on Debian or Ubuntu, check a package that is not installed, then simulate its install. This run uses `cowsay`. `grep '^Inst'` keeps only the lines that start with `Inst`.

```bash
apt-cache policy cowsay | head -n 3
# cowsay:
#   Installed: (none)
#   Candidate: 3.03+dfsg2-8build1
apt-get -s install cowsay | grep '^Inst'
# Inst cowsay (3.03+dfsg2-8build1 Ubuntu:26.04/resolute [all])
# Your versions differ.
```

<Callout type="tip" title="Why it matters for testing">

Tutorial's own advice: pin the version of a tool in a test image, for example `jq=<version>`. This does not pin its dependencies.

</Callout>

<details>
<summary>Go deeper</summary>

- `apt show` prints dependencies, sizes, and sources. <Cite n={9} /> `apt-cache policy` without a name lists the sources and their priorities. <Cite n={11} />
- `apt-file search` finds the package that contains a file. It is a separate package, and `apt-file update` must run first. <Cite n={16} />
- DNF has `dnf search`, `dnf info`, and `dnf install`. `dnf search` matches names and summaries, and ignores case. <Cite n={21} />
- `dnf provides /path/to/file` finds the package that holds a file, installed or not. It also accepts a command name, such as `zless`. <Cite n={21} /> DNF 5 keeps these commands. <Cite n={25} />
- To pin a version, write `apt install pkg=version`, or `pkg/release` for a release. <Cite n={9} /> With DNF, add it to the name, as in `dnf install tito-0.5.6-1.fc22`. <Cite n={21} />
- `apt` is made for people, and its behavior may change between versions. Scripts should call `apt-get`. <Cite n={9} /> <Cite n={18} />

```bash

dnf provides /usr/bin/jq               # RHEL, Fedora: which package has this file
sudo dnf install --assumeno jq         # needs root; RHEL, Fedora: show the plan, answer no
```

Tutorial's own advice: install only from repositories that you trust. An old version may leave the repository, so keep a local copy or a package snapshot for long-lived images.

## Installing, Removing, and Upgrading Packages

<Voices>
<Technical>

**Goal:** Preview an upgrade and a cleanup before you run them.

Update and upgrade are two steps. `apt update` only refreshes the package index. <Cite n={10} /> `apt upgrade` installs newer versions but never removes a package. `remove` deletes a package and keeps its configuration files. `purge` deletes them too. <Cite n={9} /> These commands change or delete software. `-y` answers every prompt with yes, so do not use it on a shared machine. Preview a change with `-s` first. <Cite n={10} />

```bash
apt-get -s upgrade    # Debian, Ubuntu: preview what an upgrade would change
```

**Try it:** on Debian or Ubuntu, print the summary line of a simulated upgrade and of a simulated `autoremove`, which deletes dependencies that nobody needs now. <Cite n={17} /> `grep` keeps only the summary line. Nothing changes.

```bash
apt-get -s upgrade | grep 'not upgraded'
# 5 upgraded, 0 newly installed, 0 to remove and 18 not upgraded.
apt-get -s autoremove | grep 'not upgraded'
# 0 upgraded, 0 newly installed, 7 to remove and 23 not upgraded.
# Your numbers differ.
```

<Callout type="tip" title="Why it matters for testing">

Tutorial's own advice: on a CI runner, install named packages with fixed versions. Turn off automatic upgrades during a test run, or log them.

</Callout>

<details>
<summary>Go deeper</summary>

- `apt full-upgrade` may remove packages. <Cite n={9} /> `dnf upgrade` updates each package to its latest version. <Cite n={21} />
- An exit status is the number that a command returns. In DNF 4, `dnf check-update` returns exit status 100 if upgrades exist. <Cite n={21} /> DNF 5 names the check `dnf check-upgrade`. <Cite n={37} />
- `purge` does not delete your home data. <Cite n={9} /> `dnf remove` also removes the packages that depend on the target. <Cite n={21} />
- `apt-mark hold` stops the automatic install, upgrade, and removal of one package. <Cite n={12} /> DNF has the versionlock plugin. <Cite n={23} />
- On Ubuntu Server, the default `unattended-upgrades` package installs security updates. Reboot is off by default. <Cite n={19} /> `unattended-upgrade --dry-run` only simulates a run. <Cite n={27} />
- `dnf-automatic.timer` follows `/etc/dnf/automatic.conf`, whose defaults download and apply nothing. The install timer unit applies updates. <Cite n={24} />
- `-y` runs a command without prompts, so a script on a disposable container or CI runner needs it. <Cite n={10} />

```bash
apt-mark showhold        # which packages are held
dnf check-update         # DNF 4: list upgrades; exit status 100 means some exist (DNF 5: check-upgrade)
sudo unattended-upgrade --dry-run   # needs root and the unattended-upgrades package: simulate a run
```

Tutorial's own advice: on a CI runner, run `apt-get update`, then `apt-get install -y` with named packages and fixed versions. Automatic upgrades can change a package during a test run. <Cite n={19} />

</details>

## Listing Installed Packages

<Voices>
<Technical>

**Goal:** Save the list of installed packages, so that you can compare two machines.

`dpkg -l` lists packages. The first two letters, `ii`, mean wanted (install) and installed. <Cite n={8} /> On RHEL and Fedora, use `rpm -qa`. <Cite n={26} /> For scripts, use `dpkg-query -W -f`, which sets the output format. The `dpkg -l` layout is for people. `dpkg -S` finds the package that owns a file. <Cite n={8} />

```bash
dpkg -l bash    # Debian, Ubuntu: one line, starts with ii
```

**Try it:** on Debian or Ubuntu, save the list in a throw-away directory, count it, and find two entries. `${binary:Package}=${Version}` writes the name, `=`, and the version. <Cite n={8} />

```bash
(
  d="$(mktemp -d)" && cd "$d"   # make and enter a new, empty directory
  dpkg-query -W -f='${binary:Package}=${Version}\n' | sort > packages.txt
  wc -l < packages.txt          # 2051 (your count differs)
  grep '^bash=' packages.txt    # bash=5.3-2ubuntu1
  dpkg -S /etc/host.conf        # base-files: /etc/host.conf
  rm -r "$d"                    # delete the throw-away directory
)
```

<Callout type="tip" title="Why it matters for testing">

Tutorial's own advice: save the package list with each test run. Compare two lists with `diff` to see why a test fails on only one machine.

</Callout>

<details>
<summary>Go deeper</summary>

- Quote a pattern, as in `'libc6*'`. <Cite n={8} /> `apt list --installed` lists packages too. <Cite n={9} /> `dnf list --installed` works on RHEL and Fedora. <Cite n={21} />
- `rpm -qf` finds the owner of a file. <Cite n={26} /> `dpkg -S` cannot see files that maintainer scripts (install-time scripts) create. <Cite n={8} />
- `dpkg -L` lists the files of a package. `dpkg -s` shows the status of a package. <Cite n={7} />
- APT marks a package as manual if you asked for it and as automatic if it came as a dependency. `apt-mark showmanual` lists the manual ones. <Cite n={12} />
- The default output of `dpkg-query -W` is the package name and the version, separated by a tab. <Cite n={8} />
- `rpm -qi` shows the details of a package, and `rpm -ql` lists its files. <Cite n={26} />

```bash
apt-mark showmanual | head -n 3     # packages that someone asked for
rpm -qa | sort | head -n 3          # RHEL, Fedora
rpm -qf "$(command -v bash)"        # RHEL, Fedora: owner of bash
```

`dpkg -l` package-গুলোর তালিকা দেখায়। প্রথম দুটি অক্ষর `ii` মানে package-টি wanted (install) এবং installed। <Cite n={8} /> RHEL ও Fedora-তে `rpm -qa` ব্যবহার করুন। <Cite n={26} /> Script-এর জন্য `dpkg-query -W -f` ব্যবহার করুন, যা output format ঠিক করে দেয়। `dpkg -l`-এর layout মানুষের পড়ার জন্য। `dpkg -S` খুঁজে বের করে একটি file কোন package-এর। <Cite n={8} />

**চেষ্টা করুন:** Debian বা Ubuntu-তে একটি throw-away directory-তে তালিকাটি save করুন, গুনুন, আর দুটি entry খুঁজুন। `${binary:Package}=${Version}` নাম, `=`, আর version লেখে। <Cite n={8} />

```bash
(
  d="$(mktemp -d)" && cd "$d"   # make and enter a new, empty directory
  dpkg-query -W -f='${binary:Package}=${Version}\n' | sort > packages.txt
  wc -l < packages.txt          # 2051 (your count differs)
  grep '^bash=' packages.txt    # bash=5.3-2ubuntu1
  dpkg -S /etc/host.conf        # base-files: /etc/host.conf
  rm -r "$d"                    # delete the throw-away directory
)
```

<Callout type="tip" title="টেস্টিং-এ কেন দরকার">

Tutorial-এর নিজস্ব পরামর্শ: প্রতিটি test run-এ package list save করুন। Test শুধু এক machine-এ fail করলে দুটি list `diff` দিয়ে মিলিয়ে দেখুন।

</Callout>

<details>
<summary>আরও জানুন</summary>

- `apt list --installed`-ও তালিকা দেখায়। <Cite n={9} /> RHEL ও Fedora-তে `dnf list --installed`-ও কাজ করে। <Cite n={21} />
- একটি file কোন package-এর, তা জানতে `rpm -qf`-ও ব্যবহার করা যায়। <Cite n={26} /> Maintainer script (install-time script) যে file তৈরি করে, `dpkg -S` তা দেখতে পায় না। <Cite n={8} />
- `dpkg -L` একটি package-এর file-গুলোর তালিকা দেয়। <Cite n={7} />
- আপনি নিজে চাইলে APT একটি package-কে manual হিসেবে mark করে, আর dependency হিসেবে এলে automatic হিসেবে। `apt-mark showmanual` manual package-গুলোর তালিকা দেয়। <Cite n={12} />

</details>

## Snap

<Voices>
<Technical>

**Goal:** See which channel a snap follows and when snaps refresh.

A snap is a self-contained app package. It bundles the app with its libraries. <Cite n={5} /> The `snapd` daemon, a background service, installs, confines, and updates snaps. <Cite n={34} /> A channel is `track/risk/branch`. The default risk is `stable`. <Cite n={29} /> By default, snaps refresh four times a day. <Cite n={30} /> Be careful: `snap remove --purge` removes a snap without a snapshot of its data. <Cite n={35} />

```bash
snap list    # installed snaps, with channel and notes
```

**Try it:** list the `snapd` snap and print the refresh timer. You need a system with `snapd`, such as Ubuntu. <Cite n={36} /> The `Tracking` column shows the channel. `/4` in the timer means four refreshes over the day. <Cite n={30} />

```bash
snap list snapd
# Name   Version  Rev    Tracking       Publisher    Notes
# snapd  2.77.1   28254  latest/stable  canonical**  snapd
snap refresh --time
# timer: 00:00~24:00/4
# last: today at <time>
# next: today at <time>
# Your version, Rev, and times differ.
```

<Callout type="tip" title="Why it matters for testing">

Tutorial's own advice: pin the channel with `--channel=` and hold the refresh during a test run. A refresh can change the app in a test.

</Callout>

<details>
<summary>Go deeper</summary>

- `snapd` must run before you can install a snap, and some distributions need you to install it. <Cite n={36} />
- `snap find` searches the Snap Store, and `snap info` shows details and channels. `sudo snap install` and `sudo snap remove` add and delete snaps. <Cite n={35} />
- The branch of a channel is optional. The risk levels are `stable`, `candidate`, `beta`, and `edge`. <Cite n={29} />
- Confinement is the isolation of an app from the system. A `strict` snap cannot reach files, network, or other resources without an interface. A `classic` snap has full access, like a normal package, and needs `--classic`. <Cite n={28} /> <Cite n={31} />
- A `classic` snap has no sandbox. <Cite n={31} /> Install it only from a publisher that you trust.
- `snap refresh --hold=24h firefox` pauses one snap. <Cite n={30} /> The commands are links in `/snap/bin`. <Cite n={33} /> Data is under `/var/snap` and `~/snap`. <Cite n={32} />

```bash
snap find "media player"  # search the Snap Store
snap info vlc             # details and channels
ls /snap/bin | head -n 3  # the commands of snaps (on your PATH)
```

Tutorial's own advice: if a snapped tool cannot read a test file, check the confinement first. <Cite n={28} />

</details>
