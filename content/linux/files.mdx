# Working with Files

This stage covers the commands that create, copy, move, edit, link, and archive files. A tester needs them because every test run makes files: logs, reports, screenshots, and fixtures (fixed test data). One wrong command can destroy that data, so each section names the risk.

<PageMeta />

## Working with Files

Every file on a Linux filesystem has an inode. An inode is a record of the metadata of the file, such as its owner, size, and timestamps. <Cite n={1} /> The name of a file is a hard link: a reference to that inode number. <Cite n={2} />

Two commands show this data. `ls -l` lists files in the long format. <Cite n={3} /> `stat` prints the full status, and `-c` chooses the fields. <Cite n={4} />

```bash
ls -li report.txt      # -i adds the inode number
stat report.txt
stat -c '%n: %s bytes, %h hard links, inode %i' report.txt
```

The code `%s` is the size in bytes, `%h` is the number of hard links, and `%i` is the inode number. <Cite n={4} /> `rm` has no recycle bin, so treat each removal as final. <Cite n={5} />

<Callout type="tip" title="Why it matters for testing">

Tutorial's own advice: after a test run, use `stat` to check the size and the modification time of each output file. A report of 0 bytes often means that the step crashed before it wrote any data. In a CI log, one `ls -l` of the artifact folder is a cheap check.

</Callout>

## Creating Files and Directories

`touch` creates an empty file when the name does not exist. If the file exists, `touch` only updates its access and modification times. <Cite n={6} /> The option `-c` stops `touch` from creating a file, and `-d` sets a chosen time. <Cite n={6} />

`mkdir` makes a directory and reports an error if the directory exists, unless you add `-p`. <Cite n={7} /> With `-p`, `mkdir` also makes the missing parent directories. <Cite n={7} />

```bash
touch notes.txt
touch -d '2026-01-15T10:00:00' old.log   # set a chosen time
mkdir -p results/2026/run1
echo "first line" > hello.txt
cat > draft.txt                          # type text, then press Ctrl+D
```

A redirection with `>` also makes a file. <Cite n={8} /> The command `cat > file` reads your text until you press Ctrl+D. <Cite n={9} /> To remove things, `rm` deletes files, and it needs `-r` for a directory. <Cite n={10} /> `rmdir` removes only empty directories. <Cite n={9} />

<Callout type="danger" title="Deletion and redirection lose data">

`rm -r` deletes a directory and all of its contents. `-f` never prompts. <Cite n={10} /> The `>` operator cuts an existing file to zero size. <Cite n={8} /> Run `ls` on the path first. Use `rm -I` to get one prompt before a recursive removal. <Cite n={10} />

</Callout>

<Callout type="tip" title="Why it matters for testing">

Tutorial's own advice: start each test setup with `mkdir -p`. It succeeds when the folder exists, so a second run of the job does not fail. Use `touch -d` to build files with an old time when you test code that depends on the age of a file.

</Callout>

## Copying and Renaming

`cp` makes a copy that is independent of the original. <Cite n={11} /> It copies a directory only with `-r`. <Cite n={11} /> If the last argument is a directory, `cp` puts each source inside it. <Cite n={11} /> To rename a file, use `mv` with a new name. <Cite n={12} />

By default, `cp` replaces an existing destination file without a prompt. <Cite n={11} /> `mv` does the same. <Cite n={13} /> These options change that:

| Option | Effect |
|---|---|
| `-i` | Ask before each overwrite. <Cite n={11} /> |
| `-n` | Skip a file that exists. <Cite n={11} /> |
| `-p` | Keep the mode, owner, and times. <Cite n={11} /> |
| `-a` | Archive mode: copy a tree and keep as much as possible. <Cite n={11} /> |
| `-v` | Print what happens. <Cite n={11} /> |

The manual marks `-n` as deprecated, because its exit status differs from other platforms. In newer versions, `--update=none` also skips existing files. <Cite n={11} />

```bash
cp config.yml config.yml.bak
mkdir -p /tmp/archive
cp -i report.txt /tmp/archive/
cp -a fixtures /tmp/fixtures-copy   # copy a tree, keep modes and times
mv draft.txt final.txt              # rename
```

<Callout type="danger" title="Overwriting is silent">

`cp` and `mv` destroy the old content of a destination file at once. Add `-i` to get a prompt, or `-n` to keep the old file. Run `ls` on the destination first. <Cite n={11} />

</Callout>

<Callout type="tip" title="Why it matters for testing">

Tutorial's own advice: copy a fixture before a test changes it, and compare the two files afterwards. Use `cp -p` or `cp -a`, so that the copy keeps the mode and times of the original.

</Callout>

## Moving Files and Directories

`mv` moves a file or directory. If the last argument is a directory, `mv` moves each source into it. <Cite n={12} /> A shell pattern such as `*.log` moves many files in one command. <Cite n={13} /> To rename a directory, use a new name. If that name exists, the directory moves inside it. <Cite n={13} />

On one filesystem, `mv` usually only renames the entry. <Cite n={12} /> Between two filesystems (separate storage areas that are mounted at different paths), `mv` copies like `cp -a` and then removes the original. <Cite n={12} /> If a copy fails, `mv` removes the partial copy. A move of many directories can stop halfway. <Cite n={12} />

```bash
mkdir -p logs archive
mv build/app.log logs/
mv *.log logs/                       # the shell expands the pattern
mv -t archive/ run1.log run2.log     # target directory first
mv -i old-name.txt new-name.txt
mv --no-copy big-dir /mnt/other/     # example path: fail if a copy is needed
```

The option `--no-copy` makes `mv` fail instead of copy. <Cite n={12} />

<Callout type="danger" title="A move can overwrite">

Without `-i` or `-n`, `mv` replaces a writable destination file and gives no warning. <Cite n={13} /> The old content is lost. Check the destination with `ls` first.

</Callout>

<Callout type="tip" title="Why it matters for testing">

Tutorial's own advice: a CI workspace and `/tmp` can be on different filesystems. A `mv` between them is a slow copy. Use `--no-copy` when your job needs a fast rename, so that a surprise copy fails the job early.

</Callout>

## Editing Files

You edit a text file in a terminal with a text editor. Vi, Vim, Nano, and Emacs are the common ones. <Cite n={14} /> A terminal editor such as Vim needs no X session and works over SSH. <Cite n={15} /> You need it for files such as the config files in `/etc`. <Cite n={14} />

For a small change, you may need no editor. The `>>` operator adds text to the end of a file and makes the file if it does not exist. <Cite n={8} /> A here document (text that follows the command, up to a delimiter line) feeds many lines to a command. <Cite n={8} />

```bash
cp -p app.conf app.conf.bak            # back up first (app.conf must exist)
echo "retries=3" >> app.conf           # append one line
cat > new.conf <<'EOF'
retries=3
timeout=30
EOF
```

<Callout type="danger" title="One character separates append from erase">

`>` replaces the whole content of a file. `>>` adds to the end. <Cite n={8} /> A typo of `>` for `>>` erases your config. Make a backup with `cp -p` first.

</Callout>

<Callout type="tip" title="Why it matters for testing">

Tutorial's own advice: a script cannot drive a full-screen editor, so a CI step must write files with redirection. Keep editors for work on a live host. A minimal container may have no nano or Vim, so install one or use redirection.

</Callout>

## Nano

Nano is a small editor with no modes: every key types text, except the Control and Meta keys. <Cite n={16} /> The caret `^` stands for Ctrl, and `M-` stands for Alt. <Cite n={14} /> Nano shows the main shortcuts on two lines at the bottom. <Cite n={16} /> It is the default editor in Ubuntu and many other distributions. <Cite n={14} />

| Keys | Action |
|---|---|
| `^O` | Open the Write-Out menu, to save the file. <Cite n={16} /> |
| `^X` | Exit. Nano asks whether to save changed text. <Cite n={17} /> |
| `^K` and `^U` | Cut a line, and paste it. <Cite n={16} /> |
| `^W` | Search. <Cite n={16} /> |
| `^G` | Open the built-in help. <Cite n={16} /> |

At the save prompt, `Y` saves, `N` discards, and `C` cancels. <Cite n={14} /> The title bar shows "Modified" when the buffer (the text in memory) has unsaved changes. <Cite n={16} />

```bash
nano report.txt
nano +42 app.log        # open at line 42
nano -l config.yml      # show line numbers
nano -v config.yml      # view only
```

Nano can open a file at a line, with `+LINE` before the name. <Cite n={16} /> The option `-l` shows line numbers, and `-v` is read-only mode. <Cite n={16} />

<Callout type="tip" title="Why it matters for testing">

Tutorial's own advice: when an error names line 42, open the file with `nano -l +42 file`. Use `-v` to read a shared config without a risk of a change. The manual says that `-v` does not replace correct file permissions. <Cite n={16} />

</Callout>

## Vim

Vim is a modal editor: the same key does a different job in each mode. <Cite n={18} /> In Normal mode, the keys you type are commands. In Insert mode, they are text. <Cite n={18} /> Vim starts in Normal mode. Press `i` to enter Insert mode and `Esc` to return. <Cite n={18} /> If you lose track of the mode, press `Esc`, sometimes twice. <Cite n={18} /> A `:` key opens Command-line mode for one-line commands. <Cite n={19} />

Vim reads the file into a buffer, changes the buffer, and writes it back. <Cite n={20} /> The buffer is the copy in memory. The file changes only when you write.

| Keys | Action |
|---|---|
| `i`, `Esc` | Start Insert mode, and leave it. <Cite n={18} /> |
| `:w` | Write the buffer to the file. <Cite n={20} /> |
| `:wq`, `ZZ` | Write and quit. <Cite n={20} /> |
| `:q!` | Quit and drop all changes. <Cite n={18} /> |
| `dd`, `u`, `Ctrl-R` | Delete a line, undo, redo. <Cite n={18} /> |
| `/text` | Search for text. <Cite n={21} /> |
| `:help` | Open the help. <Cite n={21} /> |

`:q` alone fails with error E37 when you have unsaved changes. <Cite n={18} /> The `vimtutor` command is a lesson that teaches by doing. <Cite n={18} /> VIM Adventures is a browser game that teaches Vim commands. <Cite n={22} />

<Callout type="warning" title="No backup and no way back">

Vim makes no backup file unless you set it up. After `ZZ`, there is no turning back. <Cite n={18} /> `:q!` drops every change since the last write.

</Callout>

<Callout type="tip" title="Why it matters for testing">

Tutorial's own advice: a remote host or a container may offer only `vi`. Learn a small survival set (`i`, `Esc`, `:wq`, `:q!`, `dd`, `u`), so that you can fix one file there.

</Callout>

## Soft and Hard Links

A hard link is another name for a file. The link and the original share one inode, so they are the same file. <Cite n={23} /> A hard link cannot point to a directory. It cannot cross a filesystem either, because inode numbers are unique only inside one filesystem. <Cite n={2} /> The inode keeps a link count. <Cite n={1} /> The data stays while at least one name remains. <Cite n={24} />

A symbolic link (symlink) is a special file that holds the path of another file. <Cite n={2} /> It can point to a directory and cross filesystems. <Cite n={2} /> Its target may be missing. Then the link is dangling. <Cite n={2} /> A relative symlink resolves from the directory that holds the link, not from your current directory. <Cite n={23} />

```bash
touch data.txt
ln data.txt data-hard.txt            # hard link: ln TARGET LINK_NAME
mkdir -p releases/v2
ln -s releases/v2 current            # symlink named current
ls -li data.txt data-hard.txt        # same inode number in column 1
stat -c '%h' data.txt                # link count
```

`-s` makes a symlink, and `-r` with `-s` makes the path relative to the link. <Cite n={23} /> `ls -i` prints the inode number, and two names with one number are hard links. <Cite n={3} /> <Cite n={24} /> `stat` with `%h` prints the link count. <Cite n={4} />

<Callout type="danger" title="ln -f removes the destination">

`-f` removes an existing destination file before `ln` makes the link. <Cite n={23} /> A wrong link name can destroy a real file. Run `ls -l` on the name first.

</Callout>

<Callout type="tip" title="Why it matters for testing">

Tutorial's own advice: use a symlink such as `current` to switch between builds without a change to the paths in your tests. If a test reports a missing file, run `ls -l` and look for a link whose target is gone.

</Callout>

## Archiving and Compressing

An archive is one file that holds many files. Compression makes data smaller. `tar` makes archives, and `gzip` compresses. <Cite n={25} /> <Cite n={26} /> With `-z`, `tar` passes the archive through `gzip`. <Cite n={25} />

| Option | Meaning |
|---|---|
| `-c`, `-x`, `-t` | Create, extract, or list an archive. <Cite n={25} /> |
| `-f FILE` | The name of the archive. <Cite n={25} /> |
| `-C DIR` | Change to `DIR` before the work. <Cite n={25} /> |

```bash
tar -czf results.tar.gz results/         # create
tar -tzf results.tar.gz                  # list only
mkdir -p /tmp/unpack
tar -xzf results.tar.gz -C /tmp/unpack   # extract into a chosen directory
gzip -k app.log                          # compress, keep the original
gzip -d old-run.log.gz                   # decompress an existing .gz file
```

`gzip` replaces each file with a `.gz` file, and `-k` keeps the original. <Cite n={26} /> ZIP is another format: it packs and compresses in one step. <Cite n={27} /> Use `unzip` for a ZIP file with many members. <Cite n={26} />

<Callout type="danger" title="Check the paths before you extract">

Extraction can overwrite files that exist. Extract an unknown archive into a new empty directory. <Cite n={28} /> It is often unsafe to extract names that are absolute or start with `../`. <Cite n={28} /> List with `-t` first. `tar -c` also erases an existing archive of the same name. <Cite n={28} />

</Callout>

<Callout type="tip" title="Why it matters for testing">

Tutorial's own advice: pack the logs and reports of a CI run into one `.tar.gz` for upload. In a later step, run `tar -tzf` on it to prove that it holds the files you expect.

</Callout>
