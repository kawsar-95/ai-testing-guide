# White-Box Techniques

Design tests from the code: statement, branch, and condition coverage.

<PageMeta />

## Why White-Box Testing Matters

<Version of="notes">

White Box testing technique is generally a testing technique which can be applied by writing test cases based on coding logic.

We can say it **glassbox testing** or **clearbox** testing technique.

**Why whitebox testing is important?**

- **Understand code logic:** SDET can identify hidden bugs inside conditions, loops, validations, and business rules.
- **Design better test cases:** Code understanding helps cover positive, negative, edge, and branch scenarios more effectively.
- **Improve automation quality:** SDET can write stronger API, integration, and E2E automation by understanding the internal flow.
- **Find root cause faster:** When a test fails, SDET can debug logs, code, database, and API responses instead of only reporting "it failed."
- **Test backend and integration properly:** Many bugs happen between UI, API, database, queue, cache, and third-party services. White-box knowledge helps detect them.
- **Support developers better:** SDET can explain defects with technical evidence, possible root cause, and clear reproduction steps.
- **Reduce production risk:** Internal code-path coverage reduces the chance of hidden logic defects going to production.

**Types of whitebox testing:**

1. **Statement Testing:** Checks whether each important line or statement of code is executed at least once.
2. **Branch / Decision Testing:** Checks whether each decision point, like `if-else`, covers both true and false outcomes.
3. **Condition Testing:** Checks individual conditions inside complex logic, especially when multiple conditions are combined.
4. **Unit Testing:** Tests a single function, method, class, or component in isolation to verify its internal logic.
5. **Integration Testing:** Tests how multiple modules, APIs, services, database, or components work together internally.

<Callout type="warning">

ISTQB counts every executable statement in statement testing, not only the important ones. Switch to the ISTQB version at the top of the page to see the ISTQB definition.

</Callout>

<Callout type="warning">

ISTQB covers only statement testing and branch testing as white-box techniques in its Foundation syllabus, so condition testing is outside that syllabus. Switch to the ISTQB version at the top of the page to see the ISTQB definition.

</Callout>

<Callout type="warning">

ISTQB treats unit testing and integration testing as test levels, not as types of white-box testing. Switch to the ISTQB version at the top of the page to see the ISTQB definition.

</Callout>

</Version>

<Version of="istqb">

White-box testing derives tests from the internal structure of a component or system. <Cite n={1} /> The glossary calls it a test approach that is based on that structure. <Cite n={2} /> The syllabus gives code, architecture, work flows, and data flows as examples of the structure. <Cite n={1} /> The glossary lists clear-box testing, glass-box testing, and structural testing as synonyms. <Cite n={2} />

The syllabus also calls these techniques structure-based techniques. <Cite n={1} /> The test cases depend on how the software is designed. So you can create them only after the design or the code exists. <Cite n={1} />

| | Black-box | White-box |
|---|---|---|
| Test basis | The specified behavior, without the internal structure <Cite n={1} /> | The internal structure and processing <Cite n={1} /> |
| Other name | Specification-based <Cite n={1} /> | Structure-based <Cite n={1} /> |
| Main objective | Check the behavior against the specification <Cite n={1} /> | Cover the structure to an acceptable level <Cite n={1} /> |
| If the code changes but the behavior stays | The test cases stay useful <Cite n={1} /> | The test cases depend on the design <Cite n={1} /> |

**The value of white-box testing**

- **Strength.** The tests take the whole implementation into account. So they can find defects even when the specification is vague, outdated, or incomplete. <Cite n={1} />
- **Weakness.** If the software does not implement a requirement, white-box testing may miss that defect of omission. <Cite n={1} />
- **Static use.** You can apply white-box techniques without running the code, for example in dry runs of code. They suit code that is not ready to run, and pseudocode. <Cite n={1} />
- **A measure of coverage.** Black-box testing alone gives no measure of the real code coverage. White-box coverage is an objective measure. It also shows which extra tests to add. <Cite n={1} />

**The techniques in the syllabus**

The syllabus covers two white-box techniques: statement testing and branch testing. <Cite n={1} /> It says other white-box techniques exist, for example for safety-critical systems. It does not discuss them. <Cite n={1} />

White-box testing is also one of four test types: functional, non-functional, black-box, and white-box. You can apply each test type at every test level. <Cite n={1} />

| Name in the notes | ISTQB view |
|---|---|
| Statement testing | A white-box technique of the syllabus. <Cite n={1} /> |
| Branch / decision testing | Branch testing is a white-box technique of the syllabus. <Cite n={1} /> |
| Condition testing | Not in the syllabus. See the Condition Testing topic. |
| Unit testing | A test level. The syllabus gives "unit testing" as another name for component testing. <Cite n={1} /> |
| Integration testing | A test level. The syllabus splits it into component integration testing and system integration testing. <Cite n={1} /> |

So unit tests and integration tests are not kinds of white-box testing. They are test levels, and you can design their tests with white-box techniques.

</Version>

## Statement Coverage

<Version of="notes">

**Example 1:**

```js
function findSqrt(number){
    if(number>0){
        return Math.sqrt(number)
    }
    return -1
}
console.log(findSqrt(-36))
```

**Example 2:**

```js
let age=18;
if(age>=0){
    if(age>=18 && age<=100){
        console.log("Voter");
    }
    else if(age>100){
        console.log("You are not allowed to give vote")
    }
    else{
        console.log("Not voter")
    }
}
else{
    console.log("Age can not be negative")
}
```

**Statement coverage Rules for find out minimum test case**

**For nested conditions**

`statement coverage = Number of else + 1`

**For un-nested conditions**

- `statement coverage = 2` (When else are there)
- `statement coverage = 1` (When no else are there)

<Callout type="warning">

This rule gives 1 test for `findSqrt`, `calculateDiscount`, and `login`, but 100 % ISTQB statement coverage needs 2, 3, and 3 tests, because each early `return` works like an `else`. Switch to the ISTQB version at the top of the page to see the ISTQB definition.

</Callout>

Note 1: **100% statement coverage cannot guarantee bug free software**

```java
public static double division(int x, int y){
   return x/y;
}
```

</Version>

<Version of="istqb">

In statement testing, the coverage items are the executable statements. <Cite n={1} /> The glossary defines statement coverage as the coverage of executable source statements. <Cite n={3} />

You measure the coverage as a percentage. Divide the number of statements that the tests execute by the number of executable statements in the code. <Cite n={1} />

```text
statement coverage = executed statements / executable statements x 100 %
```

At 100 % statement coverage, every executable statement has run at least once. So each statement that holds a defect has run, and the run may cause a failure that shows the defect. <Cite n={1} />

100 % statement coverage has two limits. <Cite n={1} />

- A defect that depends on data can stay hidden. A division by zero is an example: it fails only when the denominator is zero.
- It does not show that the tests exercised all the decision logic. Some branches can stay unexercised.

<Callout type="tip" title="The tutorial's own method: find the minimum number of tests by reasoning">

This method is the tutorial's own advice. The syllabus gives no rule to count tests.

1. List the executable statements of the code.
2. Find statements that cannot run in the same test. The two returns of an `if` that ends in `return` are an example.
3. If k statements exclude each other, you need at least k tests.
4. Pick k tests that also reach every other statement. Then k is the minimum.

</Callout>

**Sample 1: findSqrt**

```js
function findSqrt(number){
    if(number>0){
        return Math.sqrt(number)
    }
    return -1
}
console.log(findSqrt(-36))
```

The function has three executable statements: the `if`, `return Math.sqrt(number)`, and `return -1`. The first `return` ends the function. So the two returns never run in the same call. You need at least 2 tests.

| Test | `number` | Statements that run | Statement coverage |
|---|---|---|---|
| 1 | -36 | the `if`, `return -1` | 2 of 3 (67 %) |
| 2 | 5 | the `if`, `return Math.sqrt(number)` | 2 of 3 (67 %) |
| 1 and 2 | | all three | 3 of 3 (100 %) |

The minimum is 2 tests. The call `findSqrt(-36)` in the sample is test 1 alone. It leaves `return Math.sqrt(number)` unexercised.

**Sample 2: the voter check**

```js
let age=18;
if(age>=0){
    if(age>=18 && age<=100){
        console.log("Voter");
    }
    else if(age>100){
        console.log("You are not allowed to give vote")
    }
    else{
        console.log("Not voter")
    }
}
else{
    console.log("Age can not be negative")
}
```

The code has 8 executable statements: the `let` line, three `if` statements (the `else if` counts as an `if`), and four `console.log` calls. As written, the sample sets `age` to 18, so it runs only the first path: 4 of 8 statements (50 %). To run the other paths, change the value of `age` for each run.

| Test | `age` | Path | New statements that run |
|---|---|---|---|
| 1 | 18 | outer `if` true, voter `if` true | the `let` line, the outer `if`, the voter `if`, `"Voter"` |
| 2 | 101 | voter `if` false, `age>100` true | the `age>100` `if`, `"You are not allowed to give vote"` |
| 3 | 10 | voter `if` false, `age>100` false | `"Not voter"` |
| 4 | -1 | outer `if` false | `"Age can not be negative"` |

The four tests reach 8 of 8 statements (100 %). The four `console.log` calls exclude each other, because one run prints one message. So 4 tests is the minimum.

**Sample 3: the division**

```java
public static double division(int x, int y){
   return x/y;
}
```

The method has one executable statement. One test, for example `division(6, 3)`, reaches 100 % statement coverage. That test does not find the defect, because the method fails only when `y` is 0. <Cite n={1} />

**Check the rules of the notes**

The "My notes" version gives two rules to count tests. For nested conditions: the number of `else` plus 1. For un-nested conditions: 2 if there are `else` parts, and 1 if there are none.

| Sample | Rule that applies | Rule gives | Minimum by reasoning | Result |
|---|---|---|---|---|
| `findSqrt` | un-nested, no `else` | 1 | 2 | Wrong |
| The voter check | nested, 3 `else` parts (the outer `else`, the `else if`, the last `else`) | 4 | 4 | Right |
| `division` | un-nested, no `else` | 1 | 1 | Right |

<Callout type="warning">

This check is the tutorial's own. The syllabus gives no rule to count tests. The notes' rule gives 1 test for `findSqrt`, but `findSqrt` needs 2. The `return` inside the `if` ends the function, so `return -1` runs only when the `if` is false. To use the rule, count each early `return` like an `else`, and treat the code as nested. Then the nested rule gives 1 + 1 = 2.

</Callout>

</Version>

## Branch Coverage

<Version of="notes">

Note 2: **100% statement coverage cannot guarantee 100% decision/branch coverage**

**Example 1:**

```java
public static int makePositive(int number){
   if(number<0){
       number=number*(-1);
   }
   return number;
}
```

**Example 2:**

```js
function phoneCall(phoneNumber = "999") {
  return `Calling ${phoneNumber}...`;
}

console.log(phoneCall("01712345678"));
// Output: Calling 01712345678...

console.log(phoneCall());
// Output: Calling 999...
```

**Branch coverage Rules for find out minimum test case**

For nested, Branch coverage (count of if+1)

**For un-nested conditions**

`DC=2` always

<Callout type="warning">

The rule "DC=2 always" gives 2 tests for `division`, `calculateDiscount`, and `login`, but 100 % ISTQB branch coverage needs 1, 3, and 3 tests. Switch to the ISTQB version at the top of the page to see the ISTQB definition.

</Callout>

</Version>

<Version of="istqb">

A branch moves control from one node of the control flow graph to another. The move is unconditional (straight-line code) or conditional (a decision outcome). <Cite n={1} /> The glossary defines branch coverage as the coverage of the branches of a control flow graph. <Cite n={4} />

Conditional branches are typically the true or false outcome of an `if...then` decision. They can also be an outcome of a `switch/case` statement, or the choice to exit or continue a loop. <Cite n={1} />

You measure the coverage as a percentage. Divide the number of branches that the tests exercise by the total number of branches. <Cite n={1} />

```text
branch coverage = exercised branches / all branches x 100 %
```

At 100 % branch coverage, the tests exercise all branches, both unconditional and conditional. <Cite n={1} /> This still may not find a defect that needs a specific path through the code. <Cite n={1} />

Branch coverage subsumes statement coverage. Any set of tests that reaches 100 % branch coverage also reaches 100 % statement coverage. The reverse is not true. <Cite n={1} />

The glossary also defines decision coverage as the coverage of decision outcomes. <Cite n={5} /> The examples below count the true and the false outcome of each decision. This is the tutorial's own choice. If you also count the unconditional branches, the percentages change, but the minimum number of tests for these samples stays the same.

**Sample 4: makePositive**

```java
public static int makePositive(int number){
   if(number<0){
       number=number*(-1);
   }
   return number;
}
```

| Test | `number` | Decision outcome | Statement coverage | Decision outcomes covered |
|---|---|---|---|---|
| 1 | -5 | true | 3 of 3 (100 %) | 1 of 2 (50 %) |
| 2 | 5 | false | 2 of 3 (67 %) | 1 of 2 (50 %) |
| 1 and 2 | | both | 3 of 3 (100 %) | 2 of 2 (100 %) |

Test 1 alone reaches 100 % statement coverage, but only 50 % of the decision outcomes. This is the case that the syllabus describes: statement coverage can be full while branch coverage is not. <Cite n={1} /> The true and the false outcome exclude each other in one run. So the minimum is 2 tests.

**Sample 5: phoneCall**

```js
function phoneCall(phoneNumber = "999") {
  return `Calling ${phoneNumber}...`;
}

console.log(phoneCall("01712345678"));
// Output: Calling 01712345678...

console.log(phoneCall());
// Output: Calling 999...
```

The function has one executable statement, the `return`. One call reaches 100 % statement coverage.

The syllabus names `if`, `switch/case`, and loops as typical decisions. <Cite n={1} /> A default value is not on that list. This tutorial counts it as a decision, because the code takes a different path when the caller gives no argument. That reading is the tutorial's own. With it, the function has 2 paths, and the two `console.log` calls of the sample are the minimum set of 2 tests.

**Sample 2 again: the voter check**

The voter check from the previous topic has 3 decisions with 6 outcomes. The four tests of that topic cover all of them.

| Test | `age` | Outer `if` (`age>=0`) | Voter `if` | `age>100` `if` |
|---|---|---|---|---|
| 1 | 18 | true | true | not reached |
| 2 | 101 | true | false | true |
| 3 | 10 | true | false | false |
| 4 | -1 | false | not reached | not reached |

The outcomes "outer `if` false", "voter `if` true", "`age>100` true", and "`age>100` false" exclude each other. Each one ends the run with a different message. So the minimum is 4 tests.

**Check the rules of the notes**

The "My notes" version gives two rules to count tests. For nested conditions: the number of `if` plus 1. For un-nested conditions: always 2.

| Sample | Rule that applies | Rule gives | Minimum by reasoning | Result |
|---|---|---|---|---|
| `findSqrt` | un-nested | 2 | 2 | Right |
| The voter check | nested, 3 `if` parts (the `if`, the inner `if`, the `else if`) | 4 | 4 | Right |
| `makePositive` | un-nested | 2 | 2 | Right |
| `phoneCall` | un-nested, with the default value as a decision | 2 | 2 | Right |
| `division` | un-nested | 2 | 1 | Wrong |

<Callout type="warning">

This check is the tutorial's own. The rule "DC=2 always" gives 2 tests for `division`. But `division` has no decision, so it has only unconditional branches. One test reaches 100 % branch coverage. The rule fits only code that has at least one decision. The Unit Testing and Integration Testing in Code topics show two more samples where the rule fails.

</Callout>

</Version>

## Condition Testing

<Version of="notes">

**Condition Testing:** Checks individual conditions inside complex logic, especially when multiple conditions are combined.

<Callout type="warning">

ISTQB does not include condition testing in its Foundation syllabus, which covers only statement testing and branch testing as white-box techniques. Switch to the ISTQB version at the top of the page to see the ISTQB definition.

</Callout>

</Version>

<Version of="istqb">

The Foundation syllabus does not cover condition testing. Its section on white-box techniques names only statement testing and branch testing. <Cite n={1} />

The glossary does define the term. Condition testing is a white-box technique in which the test conditions are outcomes of atomic conditions. <Cite n={6} /> The glossary shows the term only for a specialist syllabus (Automotive Software Tester), not for the Foundation syllabus. <Cite n={6} /> An atomic condition is a condition that has no logical operators. <Cite n={7} />

In `age>=18 && age<=100`, the operator `&&` joins two atomic conditions: `age>=18` and `age<=100`. Each atomic condition has two outcomes, true and false.

<Callout type="note" title="The tutorial's own explanation">

The worked examples below are the tutorial's own analysis, not ISTQB text. In JavaScript, `&&` and `||` skip the right side when the left side already gives the result. A skipped condition has no outcome in that test. The tables mark it "not evaluated".

</Callout>

**The voter check**

The voter check has four atomic conditions: `age>=0`, `age>=18`, `age<=100`, and `age>100`. The four statement tests of the Statement Coverage topic cover all 8 outcomes.

| Test | `age` | `age>=0` | `age>=18` | `age<=100` | `age>100` |
|---|---|---|---|---|---|
| 1 | 18 | true | true | true | not evaluated |
| 2 | 101 | true | true | false | true |
| 3 | 10 | true | false | not evaluated | false |
| 4 | -1 | false | not evaluated | not evaluated | not evaluated |

The outcomes "`age>=0` false", "`age>=18` false", "`age<=100` true", and "`age>100` true" need four different ranges of `age`. So 4 tests is the minimum. For this sample, condition outcomes need no more tests than branches.

**A case where branch coverage is not enough**

The second `if` of `calculateDiscount` (the full function is in the Unit Testing topic) has a compound decision.

```js
if (discountPercent < 0 || discountPercent > 100) {
  return "Invalid discount";
}
```

Two values of `discountPercent` give 100 % decision coverage for this `if`: one value that makes it true, and one that makes it false. But 2 values leave one atomic outcome unexercised.

| `discountPercent` | `discountPercent < 0` | `discountPercent > 100` | Decision |
|---|---|---|---|
| 120 | false | true | true |
| 10 | false | false | false |
| -5 | true | not evaluated | true |

The values 120 and 10 reach 2 of 2 decision outcomes, but only 3 of 4 atomic outcomes. The outcome "`discountPercent < 0` true" needs a third value such as -5. A defect in the check for a negative discount can hide from a test set that has 100 % branch coverage.

</Version>

## Unit Testing

<Version of="notes">

**Unit testing** ensures to pass a function with several datasets.

```js
function calculateDiscount(price, discountPercent) {
  if (price <= 0) {
    return "Invalid price";
  }

  if (discountPercent < 0 || discountPercent > 100) {
    return "Invalid discount";
  }

  const discountAmount = (price * discountPercent) / 100;
  return price - discountAmount;
}
```

Example unit test cases:

```js
console.log(calculateDiscount(1000, 10));
// Expected output: 900

console.log(calculateDiscount(500, 20));
// Expected output: 400

console.log(calculateDiscount(0, 10));
// Expected output: Invalid price

console.log(calculateDiscount(1000, 120));
// Expected output: Invalid discount
```

</Version>

<Version of="istqb">

The syllabus calls this level component testing, also known as unit testing. It tests components in isolation. <Cite n={1} /> It often needs special support, for example a test harness or a unit test framework. <Cite n={1} /> Developers normally run it in their development environments. <Cite n={1} />

The glossary defines unit testing as a test level that evaluates the smallest part of code that you can test in isolation. <Cite n={8} />

Unit testing is a level, not a technique. You choose the techniques. You can apply white-box testing at any test level, and so you can design unit tests from the statements and branches of the code. <Cite n={1} />

**Sample 6: calculateDiscount**

```js
function calculateDiscount(price, discountPercent) {
  if (price <= 0) {
    return "Invalid price";
  }

  if (discountPercent < 0 || discountPercent > 100) {
    return "Invalid discount";
  }

  const discountAmount = (price * discountPercent) / 100;
  return price - discountAmount;
}
```

The function has 6 executable statements, 4 decision outcomes (2 for each `if`), and 3 atomic conditions (6 outcomes). The three `return` statements exclude each other.

The notes give 4 unit test cases. This table shows what each one reaches.

| Test | Call | Expected | Statements (of 6) | Decision outcomes (of 4) | Atomic outcomes (of 6) |
|---|---|---|---|---|---|
| 1 | `calculateDiscount(1000, 10)` | 900 | 4 | 2 | 3 |
| 2 | `calculateDiscount(500, 20)` | 400 | 4 (no new) | 2 (no new) | 3 (no new) |
| 3 | `calculateDiscount(0, 10)` | Invalid price | 2 | 1 | 1 |
| 4 | `calculateDiscount(1000, 120)` | Invalid discount | 3 | 2 | 3 |
| All four | | | 6 of 6 (100 %) | 4 of 4 (100 %) | 5 of 6 (83 %) |

The four tests reach 100 % statement coverage and 100 % decision outcome coverage. Test 2 adds no coverage. No test makes `discountPercent < 0` true, so the atomic outcomes stay at 5 of 6.

**The minimum test sets (by reasoning)**

The "My notes" version gives two rules to count tests.

| Coverage | Minimum | Why | Example set |
|---|---|---|---|
| Statement | 3 | The three `return` statements exclude each other. | `(0, 10)`, `(1000, 120)`, `(1000, 10)` |
| Branch (decision outcomes) | 3 | The outcomes "first `if` true", "second `if` true", and "second `if` false" exclude each other. | the same three |
| Atomic condition outcomes | 4 | Add a value below 0. A test with `discountPercent < 0` true skips `discountPercent > 100`, so the false outcome of that condition needs another test. | the three above and `(1000, -5)` |

<Callout type="warning">

This check is the tutorial's own. The notes' rule for un-nested code gives 1 test for statement coverage and 2 tests for branch coverage, but `calculateDiscount` needs 3 for each. The two `if` statements are in a row, but each ends in `return`, so each one works like an `else`. Count each early `return` like an `else`, and treat the code as nested. Then the nested rules match: for statements, 2 `else` plus 1 give 3. For branches, 2 `if` plus 1 give 3.

</Callout>

White-box tests may miss a requirement that the code does not implement. <Cite n={1} />

<Callout type="tip" title="The tutorial's own advice">

Coverage shows which code the tests run. It does not show that the expected results are right. Add black-box tests to the white-box tests. Use [boundary value analysis](/fundamentals/black-box/#boundary-value-analysis). For this function, test `price` 0 and 1, and `discountPercent` -1, 0, 100, and 101. These values find a wrong operator, for example `<` coded instead of `<=`.

</Callout>

</Version>

## Integration Testing in Code

<Version of="notes">

**Integration Testing** means testing whether two or more modules, components, APIs, services, or systems work together correctly.

Here is a simple **integration testing example with code**.

Suppose we have two modules:

1. `userService` → finds user from database
2. `authService` → uses `userService` to login user

**1. User Service**

```js
// userService.js

const users = [
  {
    id: 1,
    email: "user@example.com",
    password: "123456",
  },
];

function findUserByEmail(email) {
  return users.find((user) => user.email === email);
}

module.exports = { findUserByEmail };
```

**2. Auth Service**

```js
// authService.js

const { findUserByEmail } = require("./userService");

function login(email, password) {
  const user = findUserByEmail(email);

  if (!user) {
    return "User not found";
  }

  if (user.password !== password) {
    return "Invalid password";
  }

  return "Login successful";
}

module.exports = { login };
```

**3. Integration Test**

```js
// auth.integration.test.js

const { login } = require("./authService");

test("should login successfully with valid email and password", () => {
  const result = login("user@example.com", "123456");

  expect(result).toBe("Login successful");
});

test("should return invalid password for wrong password", () => {
  const result = login("user@example.com", "wrongpass");

  expect(result).toBe("Invalid password");
});

test("should return user not found for unknown email", () => {
  const result = login("unknown@test.com", "123456");

  expect(result).toBe("User not found");
});
```

<Version of="istqb">

Component integration testing focuses on the interfaces and the interactions between components. <Cite n={1} /> The glossary defines it as the integration testing of components. <Cite n={9} /> It depends heavily on the integration strategy: bottom-up, top-down, or big-bang. <Cite n={1} />

System integration testing is a different level. It tests the interfaces that connect your system to other systems and to external services. <Cite n={1} /> It needs suitable test environments. They should preferably resemble the operational environment. <Cite n={1} />

| What you connect | ISTQB level |
|---|---|
| Two modules or classes of one program | Component integration testing <Cite n={1} /> |
| Your system and another system or an external service | System integration testing <Cite n={1} /> |

**Sample 7: userService and authService**

```js
// userService.js

const users = [
  {
    id: 1,
    email: "user@example.com",
    password: "123456",
  },
];

function findUserByEmail(email) {
  return users.find((user) => user.email === email);
}

module.exports = { findUserByEmail };
```

```js
// authService.js

const { findUserByEmail } = require("./userService");

function login(email, password) {
  const user = findUserByEmail(email);

  if (!user) {
    return "User not found";
  }

  if (user.password !== password) {
    return "Invalid password";
  }

  return "Login successful";
}

module.exports = { login };
```

```js
// auth.integration.test.js

const { login } = require("./authService");

test("should login successfully with valid email and password", () => {
  const result = login("user@example.com", "123456");

  expect(result).toBe("Login successful");
});

test("should return invalid password for wrong password", () => {
  const result = login("user@example.com", "wrongpass");

  expect(result).toBe("Invalid password");
});

test("should return user not found for unknown email", () => {
  const result = login("unknown@test.com", "123456");

  expect(result).toBe("User not found");
});
```

The two modules run in one program, and the user list is an array in memory. So this sample is a component integration test. It would be a system integration test if `findUserByEmail` called another system, for example an external user directory service.

**The white-box view of the sample**

The three tests follow the three exits of `login`. The function has 6 executable statements and 4 decision outcomes.

The "My notes" version gives two rules to count tests.

| Test | Call | Result | Statements (of 6) | Decision outcomes (of 4) |
|---|---|---|---|---|
| 1 | `login("user@example.com", "123456")` | Login successful | 4 | 2 |
| 2 | `login("user@example.com", "wrongpass")` | Invalid password | 4 | 2 |
| 3 | `login("unknown@test.com", "123456")` | User not found | 3 | 1 |
| All three | | | 6 of 6 (100 %) | 4 of 4 (100 %) |

The three `return` statements exclude each other. So the minimum is 3 tests for statement coverage and for branch coverage. The three tests of the notes are this minimum set. They also use both results of the interface between the modules: a user is found, and no user is found.

<Callout type="warning">

This check is the tutorial's own. The notes' rule for un-nested code gives 1 test for statement coverage and 2 tests for branch coverage, but `login` needs 3 for each. Both `if` statements end in `return`, so each one works like an `else`. Count each early `return` like an `else`, and treat the code as nested. Then the nested rules match: 2 plus 1 give 3 for statements and for branches.

</Callout>

## White-Box Review Checklist

<Version of="notes">

- Is the business logic implemented correctly?
- Are all conditions (if/else, switch cases, loops) properly covered?
- Has boundary value testing (minimum/maximum limits) been performed?
- Are null, empty, and undefined cases handled properly?
- Is proper exception handling implemented?
- Does the system handle invalid input without crashing?
- Is data validation applied?
- Are error messages meaningful and user-friendly?

</Version>

<Version of="istqb">

You can use white-box techniques without running the code. The syllabus names dry runs of code as an example. <Cite n={1} /> Source code is one of the work products that static testing can examine. <Cite n={1} /> Static testing finds defects directly. It may more easily find defects on paths that tests rarely execute or can hardly reach. <Cite n={1} />

In a review, each reviewer works alone first. A reviewer may use a technique such as checklist-based reviewing. <Cite n={1} /> So a code review checklist is a checklist for static testing.

The syllabus gives rules for the checklists of checklist-based testing. <Cite n={1} />

- Leave out items that a tool can check automatically, items that suit entry or exit criteria better, and items that are too general.
- Items are often questions. A reviewer can check each item separately and directly.
- Update the checklist from defect analysis, and keep it short.

<Callout type="note" title="The tutorial's own review of the checklist">

This tutorial uses the same rules for a review checklist. The table is the tutorial's own check of the notes' list against those rules.

| Item of the notes | Check |
|---|---|
| Is the business logic implemented correctly? | Too general. Write one question for each business rule. |
| Are all conditions (if/else, switch cases, loops) properly covered? | A coverage tool can measure this. Use the tool instead. |
| Has boundary value testing (minimum/maximum limits) been performed? | Fine. One direct question. |
| Are null, empty, and undefined cases handled properly? | Fine. One direct question. |
| Is proper exception handling implemented? | Fine, if the team agrees what "proper" means. |
| Does the system handle invalid input without crashing? | Fine. Test one invalid input for each field. |
| Is data validation applied? | Fine. One direct question. |
| Are error messages meaningful and user-friendly? | Fine, if the team agrees what "meaningful" means. |
