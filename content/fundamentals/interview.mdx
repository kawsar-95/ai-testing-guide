## What is software testing, and why is it important?

<Voices>
<Technical>

Software testing is a set of activities. They find defects and judge the quality of software work products. <Cite n={1} /> Failing software can cost money, time, or reputation, and it can even cause injury or death. <Cite n={1} /> Testing lowers the risk of failure in operation. <Cite n={1} /> It also gives managers facts for decisions, such as the release decision. <Cite n={1} />

[Read more](/fundamentals/basics/#what-is-software-testing)

</Technical>
<Layman>

Software testing is a set of activities. These activities find defects and judge the quality of software work products <Cite n={1} />. When software fails, it can cost money, time, or a good name. It can even cause injury or death <Cite n={1} />. Testing lowers the risk that the software fails in operation <Cite n={1} />. Testing also gives managers facts for their decisions, for example the decision to release <Cite n={1} />.

</Layman>
<Bangla>

Software testing হলো কয়েকটি কাজের একটি সেট। এই কাজগুলো defect খুঁজে বের করে এবং software work product-এর quality যাচাই করে <Cite n={1} />। Software fail করলে টাকা, সময় বা সুনামের ক্ষতি হতে পারে, এমনকি মানুষ আহত হতে বা মারা যেতে পারে <Cite n={1} />। Testing operation-এর সময় failure-এর ঝুঁকি কমায় <Cite n={1} />। এটি manager-দের সিদ্ধান্ত নেওয়ার জন্য তথ্যও দেয়, যেমন release-এর সিদ্ধান্ত <Cite n={1} />।

</Bangla>
</Voices>

## What is the main objective of software testing?

<Technical>

The syllabus gives a list of typical test objectives, not one main objective. <Cite n={1} /> Finding defects and causing failures is only one of the nine. <Cite n={1} /> The others include reducing the risk of poor quality, verifying requirements, informing stakeholders, building confidence, and validating the test object. <Cite n={1} /> The objectives change with the context, for example with the test level, the risks, and the life cycle in use. <Cite n={1} />

[Read more](/fundamentals/basics/#testing-objectives)

</Technical>
<Layman>

The syllabus does not give one main objective. It gives a list of typical test objectives <Cite n={1} />. The list has nine objectives. To find defects and cause failures is only one of them <Cite n={1} />. Some of the others are: reduce the risk of poor quality, verify the requirements, inform the stakeholders, build confidence, and validate the test object <Cite n={1} />. The objectives change with the context. For example, they change with the test level, the risks, and the life cycle that the team uses <Cite n={1} />.

</Layman>
<Bangla>

Syllabus একটি main objective দেয় না; এটি typical test objective-গুলোর একটি তালিকা দেয় <Cite n={1} />। তালিকায় নয়টি objective আছে, আর defect খুঁজে পাওয়া ও failure ঘটানো তার মধ্যে মাত্র একটি <Cite n={1} />। বাকিগুলোর মধ্যে আছে: খারাপ quality-র ঝুঁকি কমানো, requirement verify করা, stakeholder-দের জানানো, confidence তৈরি করা, এবং test object validate করা <Cite n={1} />। Context অনুযায়ী objective বদলায়, যেমন test level, ঝুঁকি, এবং ব্যবহৃত life cycle অনুযায়ী <Cite n={1} />।

</Bangla>
</Voices>

## What is the difference between verification and validation?

<Voices>
<Technical>

Testing involves both verification and validation. <Cite n={1} /> Verification checks whether the system meets the specified requirements. <Cite n={1} /> Validation checks whether the system meets the needs of users and other stakeholders in its operational environment. <Cite n={1} /> A system can pass verification and still fail validation, because testing every requirement does not ensure that users are satisfied. <Cite n={1} /> The glossary agrees: verification confirms that a work product fulfills its specification, and validation confirms that it fits what a stakeholder needs. <Cite n={2} /> <Cite n={3} />

[Read more](/fundamentals/basics/#what-is-software-testing)

</Technical>
<Layman>

Testing includes both verification and validation <Cite n={1} />. Verification checks if the system meets the specified requirements <Cite n={1} />. Validation checks if the system meets the needs of the users and other stakeholders in the environment where they use it <Cite n={1} />. A system can pass verification and still fail validation. The reason is that a test of every requirement does not make sure that the users are satisfied <Cite n={1} />. The glossary says the same. Verification confirms that a work product fulfills its specification. Validation confirms that it fits what a stakeholder needs <Cite n={2} /> <Cite n={3} />.

</Layman>
<Bangla>

Testing-এ verification এবং validation দুটোই থাকে <Cite n={1} />। Verification যাচাই করে system specified requirement পূরণ করে কি না <Cite n={1} />। Validation যাচাই করে system তার operational environment-এ user ও অন্যান্য stakeholder-দের প্রয়োজন মেটায় কি না <Cite n={1} />। একটি system verification pass করেও validation-এ fail করতে পারে, কারণ প্রতিটি requirement test করলেই user সন্তুষ্ট হবেন, এমন নিশ্চয়তা নেই <Cite n={1} />। Glossary-ও একই কথা বলে: verification নিশ্চিত করে যে একটি work product তার specification পূরণ করে, আর validation নিশ্চিত করে যে এটি stakeholder-এর প্রয়োজনের সাথে মেলে <Cite n={2} /> <Cite n={3} />।

</Bangla>
</Voices>

## What is the difference between QA and QC?

<Voices>
<Technical>

QA is process-oriented and preventive, and it covers how the team develops and tests the product. <Cite n={1} /> Testing is product-oriented and corrective, and it is a major form of quality control (QC). <Cite n={1} /> The glossary defines QA as activities that give confidence that quality requirements will be met, and QC as activities that evaluate quality. <Cite n={4} /> <Cite n={5} /> QA is the responsibility of everyone on the project, not only of the testers. <Cite n={1} />

[Read more](/fundamentals/basics/#qa-vs-qc)

</Technical>
<Layman>

QA looks at the process, and it is preventive. It covers how the team develops and tests the product <Cite n={1} />. Testing looks at the product, and it is corrective. Testing is a major form of quality control (QC) <Cite n={1} />. The glossary defines QA as activities that give confidence that the quality requirements will be met. It defines QC as activities that evaluate quality <Cite n={4} /> <Cite n={5} />. QA is the job of everyone on the project, not only of the testers <Cite n={1} />.

</Layman>
<Bangla>

QA process-oriented এবং preventive; team কীভাবে product develop ও test করে, তা এর আওতায় পড়ে <Cite n={1} />। Testing product-oriented এবং corrective, আর এটি quality control (QC)-এর একটি প্রধান রূপ <Cite n={1} />। Glossary অনুযায়ী QA হলো এমন কাজ, যা quality requirement পূরণ হবে বলে আস্থা দেয়, আর QC হলো এমন কাজ, যা quality মূল্যায়ন করে <Cite n={4} /> <Cite n={5} />। QA শুধু tester-দের নয়, project-এর সবার দায়িত্ব <Cite n={1} />।

</Bangla>
</Voices>

## What is the difference between static testing and dynamic testing?

<Voices>
<Technical>

Static testing checks a test item without running it, for example in a review or with static analysis. <Cite n={1} /> <Cite n={6} /> Dynamic testing runs the test item. <Cite n={7} /> Dynamic testing causes a failure, and later analysis of the failure finds the defect, but static testing finds the defect directly. <Cite n={1} /> The two kinds complement each other, because each one finds some defect types that the other one misses. <Cite n={1} />

[Read more](/fundamentals/test-types/#static-testing)

</Technical>
<Layman>

Static testing checks a test item but does not run it. Two examples are a review and static analysis <Cite n={1} /> <Cite n={6} />. Dynamic testing runs the test item <Cite n={7} />. Dynamic testing causes a failure, and a later analysis of the failure finds the defect. Static testing finds the defect directly <Cite n={1} />. The two kinds help each other. Each kind finds some types of defects that the other kind misses <Cite n={1} />.

</Layman>
<Bangla>

Static testing একটি test item চালানো ছাড়াই যাচাই করে, যেমন review বা static analysis-এর মাধ্যমে <Cite n={1} /> <Cite n={6} />। Dynamic testing test item চালিয়ে দেখে <Cite n={7} />। Dynamic testing একটি failure ঘটায়, এবং পরে সেই failure বিশ্লেষণ করে defect পাওয়া যায়; কিন্তু static testing সরাসরি defect খুঁজে পায় <Cite n={1} />। দুই ধরনের testing একে অপরের পরিপূরক, কারণ প্রতিটি এমন কিছু defect type খুঁজে পায়, যা অন্যটি পায় না <Cite n={1} />।

</Bangla>
</Voices>

## What is the difference between functional and non-functional testing?

<Voices>
<Technical>

Functional testing checks the functions that the component or system must have, which describe what the test object does. <Cite n={1} /> Non-functional testing checks other attributes and shows how well the test object behaves. <Cite n={1} /> The syllabus uses the ISO/IEC 25010 list of non-functional characteristics: performance efficiency, compatibility, usability, reliability, security, maintainability, portability, and safety. <Cite n={1} /> Testers can apply both kinds of testing at all test levels. <Cite n={1} />

[Read more](/fundamentals/test-types/#non-functional-testing)

</Technical>
<Layman>

Functional testing checks the functions that the component or system must have. These functions describe what the test object does <Cite n={1} />. Non-functional testing checks other attributes. It shows how well the test object behaves <Cite n={1} />. The syllabus uses the ISO/IEC 25010 list of non-functional characteristics: performance efficiency, compatibility, usability, reliability, security, maintainability, portability, and safety <Cite n={1} />. Testers can use both kinds of testing at all test levels <Cite n={1} />.

</Layman>
<Bangla>

Functional testing যাচাই করে component বা system-এর যে function থাকা দরকার, সেগুলো; এই function-গুলো বলে test object কী করে <Cite n={1} />। Non-functional testing অন্য attribute-গুলো যাচাই করে এবং দেখায় test object কতটা ভালোভাবে আচরণ করে <Cite n={1} />। Syllabus non-functional characteristic-এর জন্য ISO/IEC 25010-এর তালিকা ব্যবহার করে: performance efficiency, compatibility, usability, reliability, security, maintainability, portability, এবং safety <Cite n={1} />। Tester-রা সব test level-এ দুই ধরনের testing-ই করতে পারেন <Cite n={1} />।

</Bangla>
</Voices>

## What is the difference between smoke testing and sanity testing?

<Voices>
<Technical>

The glossary defines smoke testing as a test type that builds confidence that the test object is fit for the testing that the team plans. <Cite n={8} /> The syllabus uses only the form "smoke tests". It gives "all smoke tests have passed" as an example of an entry criterion. <Cite n={1} />

The ISTQB syllabus and glossary do not define sanity testing.

<Callout type="note" title="The tutorial's own explanation">

Teams often use "sanity testing" for a quick check that one bug fix or one small change works. A smoke test is wider: it checks that the main functions of a new build work before deeper testing starts. Agree on the meaning with your team before you use the names.

</Callout>

[Read more](/fundamentals/test-types/#smoke-sanity-and-feature-testing)

</Technical>
<Layman>

The glossary defines smoke testing as a test type. It builds confidence that the test object is fit for the testing that the team plans <Cite n={8} />. The syllabus uses only the words "smoke tests". It gives "all smoke tests have passed" as an example of an entry criterion <Cite n={1} />.

The ISTQB syllabus and glossary do not define sanity testing. The next part is the tutorial's own explanation. Teams often use "sanity testing" for a quick check that one bug fix or one small change works. A smoke test is wider. It checks that the main functions of a new build work before deeper testing starts. Agree on the meaning with your team before you use the names.

</Layman>
<Bangla>

Glossary smoke testing-কে এমন একটি test type হিসেবে সংজ্ঞায়িত করে, যা আস্থা দেয় যে test object পরিকল্পিত testing-এর জন্য উপযুক্ত <Cite n={8} />। Syllabus শুধু "smoke tests" শব্দটি ব্যবহার করে, এবং entry criterion-এর একটি উদাহরণ হিসেবে "all smoke tests have passed" দেয় <Cite n={1} />।

ISTQB syllabus ও glossary sanity testing সংজ্ঞায়িত করে না। নিচের অংশটি tutorial-এর নিজের ব্যাখ্যা। Team-গুলো প্রায়ই "sanity testing" বলতে বোঝায় একটি bug fix বা একটি ছোট পরিবর্তন কাজ করছে কি না, তার দ্রুত check। Smoke test-এর চেয়ে বিস্তৃত: গভীর testing শুরুর আগে এটি দেখে নতুন build-এর প্রধান function-গুলো কাজ করছে কি না। নাম দুটি ব্যবহারের আগে আপনার team-এর সাথে অর্থ নিয়ে একমত হয়ে নিন।

</Bangla>
</Voices>

## What is regression testing, and when should we perform it?

<Voices>
<Technical>

Regression testing confirms that a change has caused no adverse consequences, also for a fix that already passed confirmation testing. <Cite n={1} /> The glossary says it detects defects that a change introduced or uncovered in areas of the software that did not change. <Cite n={9} /> Perform it after each change, for example a new feature or a defect fix. <Cite n={1} /> First do an impact analysis, because it shows which parts the change could affect. <Cite n={1} /> Regression suites grow with each release, so they suit automation and the CI pipeline. <Cite n={1} />

[Read more](/fundamentals/test-types/#regression-testing)

</Technical>
<Layman>

Regression testing confirms that a change did not cause bad results. This is also true for a fix that already passed confirmation testing <Cite n={1} />. The glossary says that it finds defects in the parts of the software that did not change. The change put these defects in, or the change uncovered them <Cite n={9} />. Do regression testing after each change, for example a new feature or a defect fix <Cite n={1} />. First do an impact analysis, because it shows which parts the change could affect <Cite n={1} />. The regression suites grow with each release. So they are good for automation and for the CI pipeline <Cite n={1} />.

</Layman>
<Bangla>

## What is retesting, and how is it different from regression testing?

<Voices>
<Technical>

Retesting is confirmation testing, and the glossary lists "retesting" as another name for it. <Cite n={10} /> It confirms that the original defect is fixed, for example by running the tests that failed because of the defect. <Cite n={1} /> Regression testing asks a different question. It checks for adverse consequences of the change, including the fix. <Cite n={1} />

| Point | Retesting (confirmation testing) | Regression testing |
|---|---|---|
| Question | Is the original defect fixed? <Cite n={1} /> | Did the change cause an adverse consequence? <Cite n={1} /> |
| Scope | The fixed defect <Cite n={1} /> | The same component, other components, and connected systems <Cite n={1} /> |

[Read more](/fundamentals/test-types/#regression-testing)

</Technical>
<Layman>

For example, you run again the tests that failed because of the defect <Cite n={1} />. Regression testing asks a different question. It checks if the change, and the fix too, caused bad results <Cite n={1} />. The scope is also different. Retesting covers the fixed defect. Regression testing covers the same component, other components, and connected systems <Cite n={1} />.

</Layman>
<Bangla>

## What will you do if a developer says, "This is not a bug"?

<Voices>
<Technical>

## How do you decide what to test first when time is limited?

<Voices>
<Technical>
