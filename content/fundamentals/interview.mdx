# Interview Questions

50 common manual testing interview questions with short answers.

<PageMeta />

## What is software testing, and why is it important?

Software testing is a set of activities. They find defects and judge the quality of software work products. <Cite n={1} /> Failing software can cost money, time, or reputation, and it can even cause injury or death. <Cite n={1} /> Testing lowers the risk of failure in operation. <Cite n={1} /> It also gives managers facts for decisions, such as the release decision. <Cite n={1} />

[Read more](/fundamentals/basics/#what-is-software-testing)

## What is the main objective of software testing?

The syllabus gives a list of typical test objectives, not one main objective. <Cite n={1} /> Finding defects and causing failures is only one of the nine. <Cite n={1} /> The others include reducing the risk of poor quality, verifying requirements, informing stakeholders, building confidence, and validating the test object. <Cite n={1} /> The objectives change with the context, for example with the test level, the risks, and the life cycle in use. <Cite n={1} />

[Read more](/fundamentals/basics/#testing-objectives)

## What is the difference between verification and validation?

Testing involves both verification and validation. <Cite n={1} /> Verification checks whether the system meets the specified requirements. <Cite n={1} /> Validation checks whether the system meets the needs of users and other stakeholders in its operational environment. <Cite n={1} /> A system can pass verification and still fail validation, because testing every requirement does not ensure that users are satisfied. <Cite n={1} /> The glossary agrees: verification confirms that a work product fulfills its specification, and validation confirms that it fits what a stakeholder needs. <Cite n={2} /> <Cite n={3} />

[Read more](/fundamentals/basics/#what-is-software-testing)

## What is the difference between QA and QC?

QA is process-oriented and preventive, and it covers how the team develops and tests the product. <Cite n={1} /> Testing is product-oriented and corrective, and it is a major form of quality control (QC). <Cite n={1} /> The glossary defines QA as activities that give confidence that quality requirements will be met, and QC as activities that evaluate quality. <Cite n={4} /> <Cite n={5} /> QA is the responsibility of everyone on the project, not only of the testers. <Cite n={1} />

[Read more](/fundamentals/basics/#qa-vs-qc)

## What is the difference between static testing and dynamic testing?

Static testing checks a test item without running it, for example in a review or with static analysis. <Cite n={1} /> <Cite n={6} /> Dynamic testing runs the test item. <Cite n={7} /> Dynamic testing causes a failure, and later analysis of the failure finds the defect, but static testing finds the defect directly. <Cite n={1} /> The two kinds complement each other, because each one finds some defect types that the other one misses. <Cite n={1} />

[Read more](/fundamentals/test-types/#static-testing)

## What is the difference between functional and non-functional testing?

Functional testing checks the functions that the component or system must have, which describe what the test object does. <Cite n={1} /> Non-functional testing checks other attributes and shows how well the test object behaves. <Cite n={1} /> The syllabus uses the ISO/IEC 25010 list of non-functional characteristics: performance efficiency, compatibility, usability, reliability, security, maintainability, portability, and safety. <Cite n={1} /> Testers can apply both kinds of testing at all test levels. <Cite n={1} />

[Read more](/fundamentals/test-types/#non-functional-testing)

## What is the difference between smoke testing and sanity testing?

The glossary defines smoke testing as a test type that builds confidence that the test object is fit for the testing that the team plans. <Cite n={8} /> The syllabus uses only the form "smoke tests". It gives "all smoke tests have passed" as an example of an entry criterion. <Cite n={1} />

The ISTQB syllabus and glossary do not define sanity testing.

<Callout type="note" title="The tutorial's own explanation">

Teams often use "sanity testing" for a quick check that one bug fix or one small change works. A smoke test is wider: it checks that the main functions of a new build work before deeper testing starts. Agree on the meaning with your team before you use the names.

</Callout>

[Read more](/fundamentals/test-types/#smoke-sanity-and-feature-testing)

## What is regression testing, and when should we perform it?

Regression testing confirms that a change has caused no adverse consequences, also for a fix that already passed confirmation testing. <Cite n={1} /> The glossary says it detects defects that a change introduced or uncovered in areas of the software that did not change. <Cite n={9} /> Perform it after each change, for example a new feature or a defect fix. <Cite n={1} /> First do an impact analysis, because it shows which parts the change could affect. <Cite n={1} /> Regression suites grow with each release, so they suit automation and the CI pipeline. <Cite n={1} />

[Read more](/fundamentals/test-types/#regression-testing)

## What is retesting, and how is it different from regression testing?

Retesting is confirmation testing, and the glossary lists "retesting" as another name for it. <Cite n={10} /> It confirms that the original defect is fixed, for example by running the tests that failed because of the defect. <Cite n={1} /> Regression testing asks a different question. It checks for adverse consequences of the change, including the fix. <Cite n={1} />

| Point | Retesting (confirmation testing) | Regression testing |
|---|---|---|
| Question | Is the original defect fixed? <Cite n={1} /> | Did the change cause an adverse consequence? <Cite n={1} /> |
| Scope | The fixed defect <Cite n={1} /> | The same component, other components, and connected systems <Cite n={1} /> |

[Read more](/fundamentals/test-types/#regression-testing)

## What is exploratory testing? Give an example.

In exploratory testing, the tester designs, runs, and evaluates tests at the same time, and learns about the test object while testing. <Cite n={1} /> It is useful when the specifications are few or poor, or when time is short. <Cite n={1} /> Session-based testing adds a structure: a time box, a test charter, and a debriefing. <Cite n={1} />

<Callout type="tip" title="Example (the tutorial's own)">

A tester has 60 minutes and the charter "Explore the checkout with unusual cart contents". The tester tries an empty cart, a very large quantity, and a removed item. The tester notes each question and each result. A short debriefing follows. This example is not from ISTQB.

</Callout>

[Read more](/fundamentals/experience-based/#exploratory-testing)

## What is ad-hoc testing? How is it different from exploratory testing?

The glossary defines ad hoc testing as informal testing that skips test analysis and test design. <Cite n={11} /> The syllabus does not use the term. <Cite n={1} /> Exploratory testing is different, because the tester designs the tests during the session while learning about the test object. <Cite n={1} /> It can use time boxes, charters, and debriefings. <Cite n={1} /> So the difference is the design and the structure.

[Read more](/fundamentals/test-types/#exploratory-and-ad-hoc-testing)

## What is acceptance testing? Who performs it?

Acceptance testing focuses on validation and on showing that the system is ready for deployment. This means that the system fulfills the business needs of the user. <Cite n={1} /> The glossary says it determines whether to accept the system. <Cite n={12} />

Ideally, the intended users perform it. <Cite n={1} /> The syllabus names six main forms: user acceptance testing, operational acceptance testing, contractual acceptance testing, regulatory acceptance testing, alpha testing, and beta testing. <Cite n={1} />

[Read more](/fundamentals/levels/#acceptance-testing)

## What is UAT? Why is it important?

User acceptance testing (UAT) is one main form of acceptance testing. <Cite n={1} /> The glossary defines it as acceptance testing that determines whether the intended users accept the system. <Cite n={13} />

It matters because acceptance testing is about validation. A system that meets all its specified requirements can still fail the needs of its users. <Cite n={1} /> In the test quadrants, UAT belongs to Q3: business facing, and critiquing the product. <Cite n={1} />

[Read more](/fundamentals/levels/#acceptance-testing)

## What is alpha testing and beta testing?

Alpha testing and beta testing are both forms of acceptance testing. <Cite n={1} /> The difference is the place.

| Form | Where it happens | Who tests |
|---|---|---|
| Alpha testing | In the test environment of the developer <Cite n={14} /> | Roles outside the development organization <Cite n={14} /> |
| Beta testing | At an external site, not in the test environment of the developer <Cite n={15} /> | Roles outside the development organization <Cite n={15} /> |

[Read more](/fundamentals/test-types/#alpha-beta-and-ab-testing)

## What is compatibility testing? Give examples.

ISTQB does not define "compatibility testing" as a term, but compatibility is a non-functional quality characteristic in the syllabus. <Cite n={1} /> The glossary defines compatibility as the degree to which a system can exchange information with other systems. It also covers how well a system does its own functions while it shares the same hardware or software environment. <Cite n={16} /> It also defines cross-browser compatibility as how well a web application works across different browsers. <Cite n={17} /> Cross-device testing finds out whether a system works correctly across its intended devices. <Cite n={18} />

<Callout type="note" title="The tutorial's own explanation">

Compatibility testing means testing the compatibility characteristic. The glossary has no entry with this name.

</Callout>

<Callout type="tip" title="Examples (the tutorial's own)">

Open the same web page in Chrome, Firefox, and Safari. Run the same app on an old and a new Android version. Check that a layout works on a phone, a tablet, and a desktop screen. These examples are not from ISTQB.

</Callout>

[Read more](/fundamentals/test-types/#non-functional-testing)

## What is usability testing? Give examples.

The glossary defines usability testing as testing that evaluates how well specified users can use the system. It looks at effectiveness, efficiency, and user satisfaction in a set context. <Cite n={19} /> Usability is also one of the non-functional quality characteristics in the syllabus. <Cite n={1} /> Non-functional tests sometimes need a special environment, such as a usability lab. <Cite n={1} />

<Callout type="tip" title="Examples (the tutorial's own)">

Ask a new user to find the checkout button without help. Check that an error message tells the user what to do next. Check that a user can finish the sign-up form with the keyboard only. These examples are not from ISTQB.

</Callout>

[Read more](/fundamentals/test-types/#non-functional-testing)

## What is a test plan? What does it usually contain?

A test plan describes the test objectives, the resources, and the processes of one test project. <Cite n={1} /> The glossary calls it documentation of the objectives, the means, and the schedule. <Cite n={20} /> It also shows that testing follows the test policy and the test strategy, or it explains why testing differs. <Cite n={1} />

The syllabus lists seven typical parts. They are the context of testing, assumptions and constraints, stakeholders, communication, a risk register, the test approach, and the budget and schedule. <Cite n={1} />

[Read more](/fundamentals/planning/#test-plan)

## What is a test strategy? How is it different from a test plan?

The glossary describes a test strategy as a way to perform testing so that it reaches the test objectives in the given circumstances. <Cite n={21} /> The syllabus uses the term but does not define it. <Cite n={1} /> A test plan covers one test project, and it must show that testing follows the existing test strategy or explain why it does not. <Cite n={1} /> The test approach is one part of the plan, and the glossary defines it as the way of implementing test tasks. <Cite n={1} /> <Cite n={22} /> So the plan follows the strategy for one project.

[Read more](/fundamentals/planning/#test-plan-vs-test-strategy)

## What is test estimation? How do you estimate testing effort?

The glossary defines test estimation as an approximation of some aspects of testing. <Cite n={23} /> The syllabus describes four techniques: ratios from earlier projects, extrapolation from the current project, Wideband Delphi, and three-point estimation. <Cite n={1} /> Three-point estimation takes three values, a (optimistic), m (likely), and b (pessimistic): `E = (a + 4m + b) / 6`. <Cite n={1} /> For a = 6, m = 9, and b = 18 person-hours, the estimate is 10 ± 2 person-hours. <Cite n={1} /> Tell the stakeholders that every estimate rests on assumptions and has some error. <Cite n={1} />

[Read more](/fundamentals/planning/#test-effort-estimation)

## What are entry criteria and exit criteria in testing?

Entry criteria are the conditions to start a task officially, and exit criteria are the conditions to finish it officially. <Cite n={24} /> <Cite n={25} /> A team should define both for each test level. <Cite n={1} /> Typical entry criteria are available resources, available testware, and an initial quality level of the test object, for example "all smoke tests pass". <Cite n={1} /> Typical exit criteria are measures of thoroughness, such as coverage and the number of unresolved defects, and yes-or-no checks, such as "the planned tests ran". <Cite n={1} /> In Agile teams, the exit criteria are often the Definition of Done. <Cite n={1} />

[Read more](/fundamentals/test-cases-bugs/#entry-and-exit-criteria)

## What is a test scenario? Give an example.

The ISTQB syllabus and glossary do not define "test scenario". The glossary does define a test condition as a testable aspect of a component or system that the team intends to test. <Cite n={26} />

<Callout type="note" title="The tutorial's own explanation">

A test scenario is a short statement of what to test, for one feature or area. Many teams write it as one line, such as "Verify that a registered user can log in". One scenario leads to several test cases. A scenario is close to the ISTQB idea of a test condition.

</Callout>

[Read more](/fundamentals/test-cases-bugs/#test-case)

## What is a test case? What are the key fields of a test case?

The glossary defines a test case as a set of five things: preconditions, inputs, actions where they apply, expected results, and postconditions. Testers derive it from test conditions. <Cite n={27} /> The syllabus gives no list of test case fields, so each team picks its own layout.

<Callout type="note" title="The tutorial's own explanation">

A common test case sheet has these fields: test case ID, test scenario or module, prerequisites, title, steps, test data, expected result, actual result, status, and remarks. The first seven fields describe the test. The last three record one run of the test. The list is common practice, not an ISTQB rule.

</Callout>

[Read more](/fundamentals/test-cases-bugs/#test-case)

## What is the difference between test scenario and test case?

ISTQB defines the test case. <Cite n={27} /> It does not define the test scenario.

<Callout type="note" title="The tutorial's own explanation">

A test scenario says what to test. A test case says exactly how: the steps, the data, and the expected result. Example: the scenario "Verify login" leads to three cases. They log in with a valid password, a wrong password, and an empty password. A scenario is close to the ISTQB idea of a test condition.

</Callout>

[Read more](/fundamentals/test-cases-bugs/#test-case)

## What is test data? Why is it important?

The glossary defines test data as the data that a team needs to run a test. <Cite n={28} /> Test design defines the test data requirements, and test implementation creates or gets the test data. <Cite n={1} /> A defect report names the test data in use, so that others can reproduce the failure. <Cite n={1} /> If a team repeats the same tests for a long time, it may need to change the test data, because tests wear out. <Cite n={1} />

[Read more](/fundamentals/lifecycles/#testing-activities)

## What is Requirement Traceability Matrix, RTM?

The ISTQB syllabus and glossary do not define "requirements traceability matrix". The glossary defines traceability as the ability to set up explicit relationships between related work products. <Cite n={29} /> A traceability matrix correlates such items to find out the coverage that the tests reach. <Cite n={30} /> The syllabus uses traceability to link the test basis, the testware, the test results, and the defects. <Cite n={1} /> It shows whether the test cases cover the requirements, and it helps with impact analysis and audits. <Cite n={1} />

<Callout type="note" title="The tutorial's own explanation">

An RTM is a traceability matrix with the requirements in the rows and the test case IDs next to them. A requirement without a test case is a coverage gap.

</Callout>

[Read more](/fundamentals/test-cases-bugs/#requirement-traceability-matrix-rtm)

## How do you write test cases from requirements?

Test analysis studies the test basis, such as the requirements, and defines test conditions. <Cite n={1} /> Test design then turns the test conditions into test cases. <Cite n={1} /> Test techniques, such as equivalence partitioning and boundary value analysis, help in both steps. <Cite n={1} /> For a user story, write the positive test cases first, which confirm the expected behavior, and then the negative test cases. <Cite n={1} /> Keep traceability from each test case to its requirement. <Cite n={1} />

[Read more](/fundamentals/black-box/#test-techniques-overview)

## Write test cases for a checkout/payment flow, excluding payment gateway technical details.

This answer covers the steps of the user. It leaves out the technical details of the payment gateway. Assume that the lowest allowed order total is 10.00.

| Type | Test case title |
|---|---|
| Positive | Pay with a valid card and see the order confirmation |
| Positive | Apply a valid coupon and see the new total |
| Positive | Choose a saved address and finish the order |

## What is a bug or defect?

A defect is an imperfection in a work product: it does not meet its requirements, or it impairs the intended use. <Cite n={31} /> A "bug" is the same thing. The glossary lists "bug" as a synonym of "defect", and the syllabus writes "defects (faults, bugs)". <Cite n={31} /> <Cite n={1} /> The chain is: a human makes an error, the error produces a defect, and the defect may cause a failure. <Cite n={1} /> A defect can cause a failure only when the code runs, and some defects never cause one. <Cite n={1} />

[Read more](/fundamentals/defects-principles/#error-defect-bug-and-failure)

## What are the important fields in a bug report?

A defect report documents the occurrence, nature, and status of a defect. <Cite n={32} /> The syllabus lists the typical fields. They are a unique identifier, a title, the date, organization, and author, and the test object and test environment. They also include the context, a description with steps and evidence, the expected and actual results, severity, priority, status, and references. <Cite n={1} />

A defect tool can fill some fields on its own, such as the identifier, the date, the author, and the first status. <Cite n={1} />

[Read more](/fundamentals/test-cases-bugs/#bug-report)

## How do you write a good bug title?

The syllabus says the title of a defect report holds a short summary of the anomaly. <Cite n={1} /> The callout below gives the tutorial's own advice for the wording.

<Callout type="tip" title="The tutorial's own advice">

A good title says what fails, where, and under which condition. Write "Checkout: the Pay button stays disabled after a valid card is entered". Do not write "Payment bug" or "It does not work". A clear title helps the team to find duplicates and to set the priority. This advice is not an ISTQB rule.

</Callout>

## What is the difference between severity and priority?

Severity is the degree of impact that a defect has. <Cite n={33} /> Priority is the level of importance that the team gives to the task of fixing it. <Cite n={34} /> A defect report has a separate field for each value. <Cite n={1} /> The defect management process has rules to classify defects, and all involved stakeholders must follow it. <Cite n={1} />

<Callout type="note" title="The tutorial's own explanation">

Severity says how bad the impact is. Priority says how important it is to fix the defect. The two values are separate, so a defect can have any mix of them.

</Callout>

## Explain the bug life cycle.

The ISTQB syllabus and glossary do not define "bug life cycle". The syllabus gives example defect statuses: open, closed, rejected, deferred, duplicate, re-opened, waiting to be fixed, and awaiting confirmation testing. <Cite n={1} /> The glossary has a defect workflow, which is a model of the states of a defect, including the responsibilities. <Cite n={35} /> The workflow typically has four activities: log the anomaly, analyze and classify it, decide on a response, and close the report. <Cite n={1} />

<Callout type="note" title="The tutorial's own explanation">

A common life cycle has these states: New, Open, Fixed, Retest, and Closed. A bug can also go to Rejected (it is not a defect) or Deferred (the team fixes it later). It can go to Reopen if the failure still occurs after the fix. Each team changes the states to fit its tool.

</Callout>

## What will you do if a developer says, "This is not a bug"?

<Callout type="note" title="About questions 46 to 50">

The answers to questions 46 to 50 are the tutorial's own practical advice. Where a sentence has a citation, it states an ISTQB fact. The rest is not an ISTQB rule.

</Callout>

A reported anomaly may be a real defect or something else, such as a false-positive result or a change request. <Cite n={1} /> Stay calm and check the facts: read the requirement again, reproduce the issue, and collect evidence such as the steps, a screenshot, and the logs. Show the expected result and the actual result side by side. If the requirement is unclear, ask the product owner or the business analyst to decide. Do not argue about who is right.

[Read more](/fundamentals/test-cases-bugs/#bug-report)

## What will you do if requirements are unclear or incomplete?

Do not guess: a static review of the requirements finds ambiguities, omissions, and contradictions before any code exists. <Cite n={1} /> Write each unclear point as a question, ask the product owner or the business analyst, and keep the written answer. Record every assumption that you must make, because a test plan has a part for assumptions and constraints. <Cite n={1} /> Share the questions with the team before you write the test cases.

[Read more](/fundamentals/test-types/#static-testing)

## How do you decide what to test first when time is limited?

Exhaustive testing is not possible, so testers focus the effort with test techniques, test case prioritization, and risk-based testing. <Cite n={1} /> In risk-based prioritization, the test cases that cover the most important risks run first. <Cite n={1} /> Test first the functions that the business needs most, such as login and payment. Test the areas that changed most, and the modules where defects cluster, because a few components usually hold most of the defects. <Cite n={1} /> Tell the stakeholders what you will not test.

[Read more](/fundamentals/defects-principles/#exhaustive-testing-is-impossible)

## If a feature works on your machine but fails on the client's machine, how will you investigate?

First get the exact steps, the build or version, and any logs or screenshots from the client. A defect report needs the test object, the test environment, and a description that allows reproduction. <Cite n={1} /> Then compare the two environments: the operating system, the browser or app version, the settings, the data, the permissions, and the network. Try to reproduce the failure in an environment that matches the client's. If you can reproduce it, give the steps and the environment to the developer, because reproduction is the first step of debugging. <Cite n={1} />

[Read more](/fundamentals/test-cases-bugs/#bug-report)

## A user reports that they cannot log in, but you cannot reproduce the issue. What will you do?

Some defects cause a failure only in specific circumstances, so the aim is to find those circumstances. <Cite n={1} /> Ask the user for the steps, the time, the device, the browser, the exact error message, and a screenshot, but never for the password. Check the server logs for that time, and try the same account state, such as a locked account, an expired password, or a new device. If you still cannot reproduce it, report it with all the facts that you have, and watch for new reports. A defect report needs enough information for others to resolve the issue. <Cite n={1} />
