# Planning and Estimation

Plan the testing, set the strategy, estimate the effort, and write acceptance criteria.

<PageMeta />

## Test Plan

<Voices>
<Technical>

<Version of="notes">

A **test plan** is a document that explains **what we will test, why we will test, how we will test, who will test, and when testing will be completed**.

It helps the QA team and stakeholders understand the full testing process before starting the test project.

**Test planning includes:**

**1. Testing Context**

This explains the basic background of testing. It includes:

- What will be tested
- What will not be tested
- Test objectives
- Project limitations
- Requirement documents or test basis

**2. Assumptions and Constraints**

This explains what we are assuming and what limitations we have. Example:

- The test environment will be ready on time
- Developers will fix critical bugs quickly
- Testing must be completed within 2 weeks
- Limited testers or limited devices are available

**3. Stakeholders**

This explains who is involved in the testing project and what their responsibilities are. Example: QA team, Developers, Project manager, Product owner, Business team, Client. It may also include whether new testers need to be hired or trained.

**4. Communication**

This explains how the team will communicate during testing. Example: Daily standup meeting, Bug reporting process, Test summary report, Email or Slack updates, Weekly QA status meeting.

**5. Risk Register**

This lists possible risks that can affect the product or the testing process. Example:

- Important feature may fail
- Test environment may not be stable
- Requirement may change frequently
- Testing time may be too short
- Critical bugs may be found near release

**6. Test Approach**

This explains how testing will be performed. It includes:

- Test levels, such as unit, integration, system, and acceptance testing
- Test types, such as functional, regression, performance, security, and usability testing
- Test techniques, such as boundary value analysis, equivalence partitioning, and exploratory testing
- Test deliverables, such as test cases, bug reports, and test summary reports
- Entry criteria and exit criteria
- Test data requirements
- Test environment requirements
- Metrics to be collected
- Level of tester independence

**7. Resource, Budget, and Schedule**

This explains what resources are needed and when testing activities will happen. It includes: Number of testers needed, Required tools, Required devices, Required budget, Testing timeline, Test execution schedule, Release deadline.

**In simple words:**

A test plan answers these questions:

- What will we test?
- Why will we test?
- How will we test?
- Who will test?
- When will testing start and finish?
- What risks may affect testing?
- What resources are needed?
- What conditions must be met before release?

So, a test plan works like a roadmap for the complete testing process.

</Version>

<Version of="istqb">

A test plan describes the test objectives, the resources, and the processes of one test project. <Cite n={1} /> The glossary says a test plan is documentation of the objectives, the means, and the schedule. <Cite n={2} />

**Purpose of a test plan**

A test plan has four jobs. <Cite n={1} />

- It records the means and the schedule to reach the test objectives.
- It helps to make sure that the test activities meet the agreed criteria.
- It is a way to communicate with the team and the stakeholders.
- It shows that testing follows the test policy and the test strategy, or it explains why testing differs from them.

The work of making the plan is also useful. The tester must think about risks, schedules, people, tools, costs, and effort before testing starts. <Cite n={1} />

**Typical content**

The syllabus lists seven typical parts of a test plan. <Cite n={1} />

| Part | Examples the syllabus gives |
|---|---|
| Context of testing | Test scope, test objectives, test basis |
| Assumptions and constraints | No examples in the syllabus |
| Stakeholders | Roles, responsibilities, relevance to testing, hiring needs, training needs |
| Communication | Forms and frequency of communication, document templates |
| Risk register | Product risks and project risks |
| Test approach | Test levels, test types, test techniques, test deliverables, entry and exit criteria, independence of testing, metrics, test data, test environment, deviations from the test policy and strategy |
| Budget and schedule | No examples in the syllabus |

The standard ISO/IEC/IEEE 29119-3 gives more detail about the content of a test plan. <Cite n={1} />

**Planning in Agile teams**

Iterative life cycles have two kinds of planning: release planning and iteration planning. Release planning is the basis for the test approach and test plan of all iterations. <Cite n={1} />

| Planning | What the tester does |
|---|---|
| Release planning | Helps to write testable user stories and acceptance criteria. Joins the risk analysis. Estimates the test effort of the stories. Chooses the test approach. Plans the testing of the release. <Cite n={1} /> |
| Iteration planning | Joins the detailed risk analysis of the stories. Checks the testability of the stories. Splits stories into tasks, mainly test tasks. Estimates the effort of each test task. <Cite n={1} /> |

<Callout type="tip" title="The tutorial's own advice">

Treat a plan as a short working document. Write the seven parts first, and add detail only when the team needs it. Entry criteria and exit criteria have their own topic in [Test Cases, Bugs and Completion](/fundamentals/test-cases-bugs/). This advice is not from the ISTQB syllabus.

</Callout>

## Test Strategy

<Voices>
<Technical>

<Version of="notes">

A **test strategy** is a high-level guideline that explains **how testing will be performed across a project, product, or organization**.

It defines the overall testing direction, approach, standards, tools, responsibilities, risk management, and quality expectations.

**Example:** For an eCommerce project, the test strategy may include:

- Performing API testing first, then UI testing
- Using Playwright for automation
- Giving high priority to payment, login, and order flows
- Running performance testing before release

**In simple terms:** **Test Strategy = The big-picture approach for how testing will be done**

</Version>

<Version of="istqb">

The glossary defines a test strategy as a description of how to perform testing to reach the test objectives under given circumstances. <Cite n={3} />

The syllabus uses the term but does not define it. It says that a test plan must show that testing follows the existing test strategy, or explain why it does not. <Cite n={1} /> It also says that the context of a project affects the test strategy. <Cite n={1} />

**Organizational test strategy**

The glossary has a second term for the organization-wide case. An organizational test strategy describes the generic requirements for testing, and how to test, inside an organization. <Cite n={4} />

**Test approach**

The glossary defines a test approach as the manner of implementing test tasks. <Cite n={5} /> The test approach is one part of the test plan. <Cite n={1} />

One example in the syllabus is risk-based testing. In this approach, the team selects, prioritizes, and manages the test activities with the results of risk analysis and risk control. <Cite n={1} />

| Term | Short meaning | Source |
|---|---|---|
| Test strategy | How to test to reach the test objectives under given circumstances | <Cite n={3} /> |
| Organizational test strategy | The generic testing requirements and methods of one organization | <Cite n={4} /> |
| Test approach | The manner of implementing the test tasks, written in the test plan | <Cite n={5} /> <Cite n={1} /> |

<Callout type="note" title="The tutorial's own example">

For an eCommerce project, a strategy can say that the team tests the API before the UI. It can also say that payment and login get the most attention. This example comes from the notes and is not from the ISTQB sources.

</Callout>

## Test Plan vs Test Strategy

<Voices>
<Technical>

<Version of="notes">

| Aspect | Test Plan | Test Strategy |
| --- | --- | --- |
| Definition | A Test Plan is a **detailed document** that outlines the scope, objectives, resources, schedule, and approach for a specific testing project. It provides a roadmap for the testing process. | A Test Strategy is a **high-level document** that defines the overall approach, testing objectives, and methods to be employed for multiple testing projects within an organization. It sets a long-term direction for testing. |
| Scope | It focuses on the specifics of a **single testing project**, including the features, functionalities, and components to be tested. | It has a **broader scope**, covering testing across various projects or products. It provides guidelines for consistent testing practices. |
| Level of Detail | A Test Plan is **highly detailed and project-specific**. It includes specifics about test cases, test data, test environment, and test schedules. | A Test Strategy is **less detailed** and focuses on high-level principles and **guidelines**. It doesn't delve into the specifics of individual projects. |
| Audience | It is **primarily for the testing team, project stakeholders**, and anyone directly involved in the specific testing project. | It is intended for a **wider audience**, including management, stakeholders, and teams involved in **multiple projects.** |
| Change Frequency | Test Plans may **change frequently** as project requirements and scope evolve. | Test Strategies change **less frequently** and are more stable, as they provide a long-term approach to testing practices. |

<Callout type="warning">

The notes' table says a test strategy covers many projects, but the ISTQB glossary defines "test strategy" without that limit and uses "organizational test strategy" for the organization-wide meaning. Switch to the ISTQB version at the top of the page to see the ISTQB definition.

</Callout>

</Version>

<Version of="istqb">

ISTQB v4 uses the terms test plan, test strategy, and test approach. <Cite n={1} /> The next table compares the plan and the strategy.

| Aspect | Test plan | Test strategy |
|---|---|---|
| Meaning | The objectives, resources, and processes of a test project <Cite n={1} /> | A description of how to test to reach the objectives under given circumstances <Cite n={3} /> |
| Scope | One test project <Cite n={1} /> | No fixed scope in the general term <Cite n={3} />. The organization-wide form is the organizational test strategy <Cite n={4} />. |
| Content | The seven typical parts, which include the test approach <Cite n={1} /> | The syllabus does not list its content. For the organizational test strategy, the glossary names the generic testing requirements of an organization <Cite n={4} />. |
| Relation | Must show that testing follows the existing strategy, or explain the deviation <Cite n={1} /> | The existing reference that the plan follows <Cite n={1} /> |

**How the three terms fit together**

- The strategy is a description of how to test. <Cite n={3} />
- The test approach is the way a team implements the test tasks in a project. <Cite n={5} />
- The test plan holds the test approach, and it can list the deviations from the policy and the strategy. <Cite n={1} />
- Release planning is the basis for both the test approach and the test plan. <Cite n={1} />

<Callout type="tip" title="The tutorial's own advice">

Teams use the words strategy, approach, and plan in different ways. When you join a team, ask how it uses each word and which documents it keeps. This advice is not from the ISTQB syllabus.

</Callout>

</Version>

## Test Effort Estimation

<Voices>
<Technical>

<Version of="notes">

**1. Estimation Based on Ratios**

This technique uses data from previous similar projects to estimate testing effort.

**Example:** In previous projects, your company found that: **Development effort : Testing effort = 3 : 2**. Now, if the current project development effort is **600 person-days**, then testing effort can be estimated as: **Testing effort = 400 person-days**. So, if development takes 3 parts, testing usually takes 2 parts.

**2. Extrapolation**

This technique estimates future testing effort based on the progress of the current project.

**Example:** Suppose in the first sprint, QA tested **5 features in 10 days**. Now, the project has **20 similar features**. So, estimated testing effort: **5 features = 10 days**, **20 features = 40 days**. This is useful when the team starts testing and then predicts the remaining effort based on early progress.

**3. Wideband Delphi**

In this technique, multiple experts estimate individually. Then they discuss differences and agree on a final estimate.

**Example:** For testing a payment feature: Tester 1 estimates: 3 days; Tester 2 estimates: 5 days; Tester 3 estimates: 4 days. They discuss the assumptions, risks, and complexity. Finally, they agree: **Final estimate = 4 days**. This is useful when expert judgment is needed.

**4. Three-Point Estimation**

This technique uses three estimates: **Optimistic:** Best-case estimate; **Most likely:** Normal estimate; **Pessimistic:** Worst-case estimate.

Formula: **E = (Optimistic + 4 × Most likely + Pessimistic) / 6**

**Example:** For testing checkout functionality: Optimistic estimate = 2 days; Most likely estimate = 4 days; Pessimistic estimate = 8 days. So, **E = (2 + 4×4 + 8) / 6 = (2 + 16 + 8) / 6 = 26 / 6 = 4.3 days**. So, the estimated testing effort is around **4 to 5 days**.

**In simple terms**

- **Ratio-based estimation:** Estimate using past project ratios.
- **Extrapolation:** Estimate based on current progress.
- **Wideband Delphi:** Experts discuss and agree on an estimate.
- **Three-point estimation:** Estimate using best-case, normal-case, and worst-case values.

</Version>

<Version of="istqb">

Test effort estimation predicts how much test work the team needs to meet the test objectives of a project. <Cite n={1} /> The glossary calls a test estimation an approximation of some aspect of testing. <Cite n={6} />

Two points apply to every estimate. <Cite n={1} />

- Tell the stakeholders that the estimate rests on assumptions.
- Tell them that every estimate has some error.

Small tasks are usually estimated more accurately than large tasks. So a large task can be split into small tasks, and the team can estimate each one. <Cite n={1} />

| Technique | Kind | Input |
|---|---|---|

| Extrapolation | Metrics-based | Measures from the current project |
| Wideband Delphi | Expert-based, iterative | Estimates of several experts |
| Three-point estimation | Expert-based | Three estimates of an expert: best, most likely, worst |

**Estimation based on ratios**

The team collects figures from earlier projects and derives standard ratios. The organization's own ratios are usually the best source. <Cite n={1} />

Example: the development-to-test ratio of an earlier project is 3:2. The new project needs 600 person-days of development. One part is 600 / 3 = 200 person-days. The test effort is 2 × 200 = 400 person-days. <Cite n={1} />

**Extrapolation**

The team measures the work as early as possible in the current project. With enough data, it approximates the remaining effort, usually with a mathematical model. The technique suits iterative life cycles. <Cite n={1} />

Example from the syllabus: the estimate for the next iteration is the average effort of the last three iterations. <Cite n={1} /> With the tutorial's own numbers 8, 10, and 12 person-days, the estimate is (8 + 10 + 12) / 3 = 10 person-days.

The notes use a straight-line model. Five features took 10 days, so one feature takes 10 / 5 = 2 days. Twenty similar features need 20 × 2 = 40 days.

**Wideband Delphi**

This technique is iterative and expert-based. <Cite n={1} /> The glossary says it uses the collective wisdom of the team members. <Cite n={7} />

1. Each expert estimates the effort alone.
2. The team collects the estimates.
3. If an estimate is outside the agreed range, the experts discuss their estimates.
4. Each expert estimates again alone, using the feedback.
5. The team repeats steps 2 to 4 until it reaches consensus. <Cite n={1} />

Planning Poker is a variant that Agile teams often use. The experts show cards with numbers that stand for the effort size. <Cite n={1} />

**Three-point estimation**

Each expert gives three values: the most optimistic estimate (a), the most likely estimate (m), and the most pessimistic estimate (b). E is the weighted average of the three values. <Cite n={1} /> <Cite n={8} />

The syllabus gives the most popular version of the formula. It also gives a formula for the measurement error, which it calls SD. <Cite n={1} />

```text
E  = (a + 4 × m + b) / 6
SD = (b − a) / 6
```

Syllabus example: a = 6, m = 9, and b = 18 person-hours. Then E = (6 + 36 + 18) / 6 = 10 and SD = (18 − 6) / 6 = 2. The final estimate is 10 ± 2 person-hours, which is between 8 and 12 person-hours. <Cite n={1} />

The checkout example from the notes uses a = 2, m = 4, and b = 8 days.

| Step | Calculation | Result |
|---|---|---|
| Estimate | E = (2 + 4 × 4 + 8) / 6 = (2 + 16 + 8) / 6 = 26 / 6 | 4.33 days |
| Error | SD = (8 − 2) / 6 | 1 day |
| Range | 4.33 ± 1 | About 3.3 to 5.3 days |

The notes round the result to "around 4 to 5 days". The SD shows the range more exactly.

Give the estimate and its range together, for example "4.3 ± 1 days". Then the stakeholders see the uncertainty. This advice is not from the ISTQB syllabus.

## Acceptance Criteria

<Voices>
<Technical>

<Version of="notes">

Acceptance criteria (AC) are the conditions that a software product must meet to be accepted by a user, a customer, or other systems. They are unique for each user story and define the feature behavior from the end-user's perspective.

2 ways can be written:

1. Scenario oriented
2. Rule oriented

<Callout type="warning">

The notes say there are 2 ways to write acceptance criteria, but the syllabus calls them the two most common formats and also allows a custom format. Switch to the ISTQB version at the top of the page to see the ISTQB definition.

</Callout>

**Scenario Oriented**

- It is approached through the Given/When/Then (GWT) sequence that looks like this:
    - Given some precondition
    - When I do some action
    - Then I expect some result
- This approach was inherited from behavior-driven development (BDD) and provides a consistent structure that helps testers define when to begin and end testing a particular feature.

**Scenario Oriented: Example**

```gherkin
Feature: User should Login to access the portal
  As a new user
  I want to log in to the website
  So that the user can login successfully

Scenario #1: Successful Log in to the website
  Given A user visit the website
  When the user clicks Sign-in
  And enters a valid email <email> and password <password>
  And clicks Sign-in/submit button
  Then the user should be successfully logged into the site

Scenario #2: Unsuccessful Log in to the website
  Given A user visit the website
  When the user enters an invalid email <email> and password <password>
  And clicks Sign-in/submit button
  Then the user should get a warning message
```

**Rule oriented: Example**

This type of acceptance criteria objectives are same as the scenario oriented. But the writing styles are different. It is written by bullet point verification list or tabulated form of input output mapping.

For example regarding a send money transaction:

1. Sender should have enough balance
2. After successful transaction sender balance should be deducted with corresponding service fee
3. Sender and receiver should get SMS
4. Sender transaction list should be updated.

**Rule oriented** AC-এর উদ্দেশ্য একই, শুধু লেখার ধরন আলাদা: bullet point-এর verification list, অথবা input-output mapping-এর table। Send money transaction-এর উদাহরণ: sender-এর যথেষ্ট balance থাকতে হবে; সফল transaction-এর পর sender-এর balance থেকে সংশ্লিষ্ট service fee-সহ কাটা হবে; sender ও receiver SMS পাবেন; sender-এর transaction list update হবে।
