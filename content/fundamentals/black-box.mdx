# Black-Box Techniques

Design tests from the specification: partitions, boundaries, decision tables, and states.

<PageMeta />

## Test Techniques Overview

<Version of="notes">

**Test Techniques are called as Test methods.**

There are mainly 3 types of test techniques:

**1. Blackbox or specification based testing:**

Testing the software based on requirements without knowing the internal code structure.

**Example**: For a login page, tester checks whether valid username/password allows login and invalid credentials show an error.

**2. Whitebox or clearbox or structural or glassbox testing**

Testing the software by understanding the internal code, logic, conditions, loops, and structure.

**Example**: Developer/tester checks the login function code to verify all `if-else` conditions for valid user, invalid password, blocked user, and empty fields are tested.

**3. Experienced based testing:**

Testing based on tester's experience, intuition, domain knowledge, and past defect patterns.

**Example**: Tester checks if the password field accepts spaces, copy-paste, emojis, very long input, or SQL injection because similar bugs were found before.

**Blackbox Testing Methods**

Black-box test techniques, also called **specification-based** techniques, focus on the specified behavior of the software, not its internal structure. This means test cases don't depend on how the software is built. If the behavior remains the same, the test cases are still useful even if the implementation changes.

Blackbox has 4 types of test techniques:
1. Equivalence Partitioning
2. Boundary Value Analysis (BVA)
3. Decision Table Testing
4. State Transition Testing

</Version>

<Version of="istqb">

Testers use test techniques in two activities. <Cite n={1} /> In test analysis, a technique helps to decide what to test. <Cite n={1} /> In test design, it helps to decide how to test. <Cite n={1} /> A technique gives the tester a systematic way to build a set of test cases that is small but enough. <Cite n={1} /> The glossary describes a test technique as a procedure that defines test conditions, designs test cases, and specifies test data. <Cite n={2} />

The syllabus sorts test techniques into three groups. <Cite n={1} />

| Group | Based on | Other name | What follows |
|---|---|---|---|
| Black-box | The specified behavior of the test object, without its internal structure <Cite n={1} /> | Specification-based <Cite n={1} /> | After a change of the implementation, the test cases still work if the required behavior is the same. <Cite n={1} /> |
| White-box | The internal structure and processing of the test object <Cite n={1} /> | Structure-based <Cite n={1} /> | Testers can create the test cases only after the design or the implementation exists. <Cite n={1} /> |
| Experience-based | The knowledge and experience of the testers <Cite n={1} /> | None given | The results depend heavily on the skill of the tester. The group complements the other two. <Cite n={1} /> |

The syllabus names four black-box techniques: equivalence partitioning, boundary value analysis, decision table testing, and state transition testing. <Cite n={1} /> The next topics cover them in this order.

The ISTQB syllabus and glossary do not define the term "test method".

<Callout type="note" title="The tutorial's own explanation">

The notes use "test method" as another name for "test technique". ISTQB uses "test technique". Use that name when you talk about ISTQB.

</Callout>

</Version>

## Equivalence Partitioning

<Version of="notes">

**Scenario:** A software system accepts birthday of members only from 18 to 100 years.

| Invalid | valid | invalid |
| --- | --- | --- |
| &lt;18 | 18-100 | &gt;100 |

</Version>

<Version of="istqb">

Equivalence partitioning (EP) divides data into partitions. <Cite n={1} /> It expects the test object to process all elements of one partition in the same way. <Cite n={1} /> If a test with one value of a partition finds a defect, a test with any other value of that partition should find it too. <Cite n={1} /> So one test for each partition is enough. <Cite n={1} /> The glossary says the same: one representative member of each partition is exercised. <Cite n={3} />

You can find partitions for any data element of the test object. <Cite n={1} /> Examples are inputs, outputs, internal values, interface parameters, configuration items, and values that depend on time. <Cite n={1} /> The partitions must not overlap. <Cite n={1} /> Each partition must contain at least one value. <Cite n={1} />

A valid partition holds valid values. An invalid partition holds invalid values. <Cite n={1} /> Teams and organizations can define "valid" and "invalid" in different ways. <Cite n={1} />

The coverage items of EP are the partitions. <Cite n={1} /> To reach 100% coverage, the test cases must exercise every identified partition, the invalid ones too. <Cite n={1} /> The coverage is the number of partitions that at least one test case exercises, divided by the number of identified partitions. <Cite n={1} />

**Worked answer for the 18 to 100 example.** The rules above come from the syllabus. The numbers below are the tutorial's own working. Assume that the age is a whole number.

| Partition | Values | Valid or invalid | Test value |
|---|---|---|---|
| 1 | 17 or less | Invalid | 10 |
| 2 | 18 to 100 | Valid | 50 |
| 3 | 101 or more | Invalid | 120 |

- The example has 3 partitions.
- The 3 test values 10, 50, and 120 exercise 3 partitions.
- The coverage is 3 / 3 = 100%.
- If the tester uses only the value 50, the coverage is 1 / 3 = 33.3%.
- If the tester uses the values 10 and 50, the coverage is 2 / 3 = 66.7%.

<Callout type="tip" title="The tutorial's own advice">

The two invalid partitions can hide more cases. If the specification treats negative numbers or text in a different way, add one partition for each way.

</Callout>

</Version>

## Boundary Value Analysis

<Version of="notes">

2 types of BVA:
1. **2BVA: 17,18,100,101 (min-1, min, max, max+1)**
2. **3BVA: 17,18,19,99,100,101 (min-1, min, min+1, max-1, max, max+1)**

<Callout type="warning">

The 3BVA line takes only 18 and 100 as boundary values, but ISTQB also counts 17 and 101 as boundary values, so 3-value BVA has 8 values and not 6. Switch to the ISTQB version at the top of the page to see the ISTQB definition.

</Callout>

</Version>

<Version of="istqb">

Boundary value analysis (BVA) exercises the boundaries of equivalence partitions. <Cite n={1} /> The glossary says the test conditions are boundary values. <Cite n={4} /> BVA works only for ordered partitions. <Cite n={1} /> The minimum and the maximum of a partition are its boundary values. <Cite n={1} /> If two elements belong to one partition, all elements between them belong to it too. <Cite n={1} />

Developers make more errors at boundaries. <Cite n={1} /> BVA finds boundaries that are misplaced above or below the intended position, and boundaries that are missing. <Cite n={1} />

The syllabus covers two versions of BVA. They differ in the number of coverage items for each boundary. <Cite n={1} />

| Version | Coverage items for each boundary | Coverage is |
|---|---|---|
| 2-value | The boundary value and its closest neighbor in the adjacent partition <Cite n={1} /> | Boundary values exercised, divided by boundary values identified <Cite n={1} /> |
| 3-value | The boundary value and both of its neighbors <Cite n={1} /> | Boundary values and neighbors exercised, divided by all identified boundary values and neighbors <Cite n={1} /> |

In 3-value BVA, some coverage items can be values that are not boundary values. <Cite n={1} /> 3-value BVA is more rigorous than 2-value BVA. <Cite n={1} />

The syllabus gives an example. The decision "if (x ≤ 10)" is wrongly coded as "if (x = 10)". The 2-value test data x = 10 and x = 11 cannot find the defect. The 3-value test data x = 9 is likely to find it. <Cite n={1} />

**Worked answer for the 18 to 100 example.** The rules come from the syllabus. The numbers are the tutorial's own working. The three partitions are "17 or less", "18 to 100", and "101 or more". The partition "17 or less" has no stated lower end, so only its maximum 17 is a boundary value.

The boundary values are 17 (maximum of the first partition), 18 and 100 (minimum and maximum of the second), and 101 (minimum of the third). That is 4 boundary values.

| Boundary value | 2-value test values | 3-value test values |
|---|---|---|
| 17 | 17, 18 | 16, 17, 18 |
| 18 | 17, 18 | 17, 18, 19 |
| 100 | 100, 101 | 99, 100, 101 |
| 101 | 100, 101 | 100, 101, 102 |

- 2-value BVA lists 4 × 2 = 8 values. Each value appears twice, so 8 / 2 = 4 different values: 17, 18, 100, and 101.
- 3-value BVA lists 4 × 3 = 12 values. The values 17, 18, 100, and 101 appear twice each. So 12 − 4 = 8 different values remain: 16, 17, 18, 19, 99, 100, 101, and 102.
- If the tester runs only the 4 values of the 2-value set, the 3-value coverage is 4 / 8 = 50%.
- The 2BVA list of the notes has the same 4 values. The 3BVA list of the notes has 6 values and leaves out 16 and 102.

</Version>

## Equivalence Partitioning in a Complex Case

<Version of="notes">

A bank offers Gold and Premium savings accounts for 1 and 3 years for each plan. The Gold savings account offers 5% interest for 1 year and 7% interest for 3 years, while the Premium savings account offers 7% interest for 1 year and 9% interest for 3 years. To avail of the Gold savings account, one must deposit a minimum of 1 lakh taka, and to avail of the Premium savings account, a deposit of 3 lakh taka is required.

A person deposited 1 lakh taka to purchase a Gold savings account for 3 years, and after 6 months, he deposited an additional 3 lakh taka to purchase a Premium savings account for 1 year.

How many test cases are covered by this scenario, expressed as a percentage?

<Callout type="warning">

ISTQB measures the coverage of equivalence partitioning as the partitions exercised divided by the partitions identified, not as "test cases covered". Switch to the ISTQB version at the top of the page to see the ISTQB definition.

</Callout>

</Version>

<Version of="istqb">

Many test items have more than one input, so they have more than one set of partitions. <Cite n={1} /> A test case then covers partitions from different sets. <Cite n={1} /> The simplest coverage criterion for this case is Each Choice coverage. <Cite n={1} /> Each Choice coverage needs test cases that exercise each partition of each set at least once. <Cite n={1} /> It does not look at combinations of partitions. <Cite n={1} />

**Worked answer for the bank example.** The rules above come from the syllabus. The sets of partitions and all numbers below are the tutorial's own working. The notes do not state the expected answer.

The rates of interest are outputs. The inputs are the plan, the tenure, and the deposit.

| Set | Partitions |
|---|---|
| Plan | Gold; Premium |
| Tenure | 1 year; 3 years |
| Deposit compared with the minimum of the plan | Below the minimum (invalid); at or above the minimum (valid) |

The scenario has two purchases. Purchase 1 is Gold, 3 years, 1 lakh taka. Purchase 2 is Premium, 1 year, 3 lakh taka.

| Partition | Exercised by the scenario |
|---|---|
| Gold | Yes, purchase 1 |
| Premium | Yes, purchase 2 |
| 1 year | Yes, purchase 2 |
| 3 years | Yes, purchase 1 |
| Deposit at or above the minimum | Yes: 100,000 ≥ 100,000 (purchase 1) and 300,000 ≥ 300,000 (purchase 2) |
| Deposit below the minimum | No |

- Total partitions: 2 + 2 + 2 = 6.
- Exercised partitions: 5.
- Coverage of all 6 partitions: 5 / 6 = 83.3%.
- Each Choice coverage of plan and tenure only: 4 / 4 = 100%.

Now count the combinations of plan and tenure. This count is not a coverage criterion of the CTFL syllabus. The syllabus gives Each Choice as the simplest criterion and names no criterion for all combinations. <Cite n={1} />

| Combination | Expected rate | In the scenario |
|---|---|---|
| Gold, 1 year | 5% | No |
| Gold, 3 years | 7% | Yes |
| Premium, 1 year | 7% | Yes |
| Premium, 3 years | 9% | No |

- Combinations: 2 × 2 = 4.
- Combinations in the scenario: 2.
- Coverage of the combinations: 2 / 4 = 50%.

The scenario checks the rate 7% two times. It never checks the rates 5% and 9%. A defect in those two combinations stays hidden.

The deposits 1 lakh and 3 lakh sit exactly on the minimum of each plan. This is a boundary value. The scenario does not test the value just below it, so it cannot find a wrong minimum. If the amounts are whole taka, those values are 99,999 and 299,999.

If your test case means "a combination of plan and tenure", the answer to the question of the notes is 2 / 4 = 50%. If it means "a partition", the answer is 5 / 6 = 83.3% for all six partitions. This is the tutorial's own reading.

</Version>

## Decision Table Testing

<Version of="notes">

**Decision Table Testing:**

**Scenario**: You have to test a login page.

| Conditions | T1 | T2 | T3 | T4 |
| --- | --- | --- | --- | --- |
| Email | T | T | F | F |
| Password | T | F | T | F |
| Output | x |  | - | N/A |

<Callout type="warning">

The Output row uses "-" and "N/A", which the ISTQB syllabus defines only for conditions, so rules T3 and T4 do not show if the action occurs. Switch to the ISTQB version at the top of the page to see the ISTQB definition.

</Callout>

</Version>

<Version of="istqb">

Decision tables test requirements that say how different combinations of conditions give different outcomes. <Cite n={1} /> A decision table is an effective way to record complex logic, such as business rules. <Cite n={1} /> The glossary says the test conditions are the combinations of conditions and the resulting actions in the table. <Cite n={5} />

The conditions and the actions of the system form the rows of the table. <Cite n={1} /> Each column is a decision rule. <Cite n={1} /> A rule is a unique combination of conditions with its actions. <Cite n={1} /> A limited-entry table shows the values as true or false. <Cite n={1} /> An extended-entry table can also use many values, such as ranges or partitions. <Cite n={1} />

| Notation | Used for | Meaning |
|---|---|---|
| T | Condition | The condition is satisfied. <Cite n={1} /> |
| F | Condition | The condition is not satisfied. <Cite n={1} /> |
| – | Condition | The condition does not change the outcome. <Cite n={1} /> |
| N/A | Condition | The condition is infeasible for this rule. <Cite n={1} /> |
| X | Action | The action occurs. <Cite n={1} /> |
| Blank | Action | The action does not occur. <Cite n={1} /> |

A full decision table has a column for every combination of conditions. <Cite n={1} /> You can delete the columns with infeasible combinations. <Cite n={1} /> You can also merge columns in which some conditions do not change the outcome. <Cite n={1} /> The syllabus does not cover minimization algorithms. <Cite n={1} />

The coverage items are the columns with feasible combinations. <Cite n={1} /> The coverage is the number of exercised columns, divided by the number of feasible columns. <Cite n={1} />

The technique finds all combinations of conditions in a systematic way. <Cite n={1} /> It also helps to find gaps and contradictions in the requirements. <Cite n={1} /> The number of rules grows exponentially as you add conditions. <Cite n={1} /> For many conditions, use a minimized table or a risk-based approach. <Cite n={1} />

**The login example, in the tutorial's own version.** The table in the notes has a gap and a notation problem. The syllabus defines "–" and "N/A" for conditions only. <Cite n={1} /> "N/A" marks an infeasible rule. <Cite n={1} /> All four rules of this table are feasible. Rules T3 and T4 also show no action, so the table does not say if the user logs in. The table below gives each rule an action. It assumes that a failed login shows an error message. The syllabus does not give this table.

| | Rule 1 | Rule 2 | Rule 3 | Rule 4 |
|---|---|---|---|---|
| Condition: email is correct | T | T | F | F |
| Condition: password is correct | T | F | T | F |
| Action: user logs in | X | | | |
| Action: error message is shown | | X | X | X |

- The table has 2 conditions, so it has 2 × 2 = 4 combinations and 4 rules.
- All 4 combinations are feasible.
- 4 test cases, one for each rule, give 4 / 4 = 100% coverage.

Suppose a wrong email always gives the same error, whatever the password is. Then the password is irrelevant for Rules 3 and 4. Merge them into one rule: email F, password "–".

| | Rule 1 | Rule 2 | Rule 3 (merged) |
|---|---|---|---|
| Condition: email is correct | T | T | F |
| Condition: password is correct | T | F | – |
| Action: user logs in | X | | |
| Action: error message is shown | | X | X |

- The minimized table has 3 rules, so 3 test cases give 3 / 3 = 100% coverage.
- A table with 3 conditions has 2 × 2 × 2 = 8 rules.

</Version>

## State Transition Testing

<Version of="notes">

**State Transition** is a test design technique where we test how a system moves from one state to another based on specific actions, inputs, or events.

<MdxImage src="/images/fundamentals/state-transition-pin.png" alt="State diagram of a PIN entry. Start leads to 1st Try. Incorrect PIN leads from 1st Try to 2nd Try and from 2nd Try to 3rd Try. Correct PIN from each try leads to Access Granted. Incorrect PIN from the 3rd Try leads to Account Blocked." />

Example: In a login system, a user account may move through different states:

`Active → Locked → Unlocked`

</Version>

<Version of="istqb">

A state diagram shows the possible states of a system and its valid state transitions. <Cite n={1} /> An event starts a transition. <Cite n={1} /> A guard condition can qualify the event. <Cite n={1} /> The model assumes that transitions are instantaneous. <Cite n={1} /> A transition can cause the software to take an action. <Cite n={1} /> The common label is `event [guard condition] / action`. <Cite n={1} /> You can omit the guard condition and the action if they do not exist or do not matter to the tester. <Cite n={1} /> The glossary says the test conditions are state transitions or sequences of them. <Cite n={6} />

<PinStateDiagram />

A state table models the same behavior as a state diagram. <Cite n={1} /> Its rows are the states. Its columns are the events, with their guard conditions if any. <Cite n={1} /> Each cell holds the target state and the resulting actions, if any. <Cite n={1} /> An empty cell is an invalid transition, so the state table shows invalid transitions and the state diagram does not. <Cite n={1} />

A test case is usually a sequence of events. The events cause state changes in a row, and actions when needed. <Cite n={1} /> One test case usually covers several transitions. <Cite n={1} />

| Coverage criterion | Coverage items | Coverage is |
|---|---|---|
| All states | The states <Cite n={1} /> | Exercised states, divided by all states <Cite n={1} /> |
| Valid transitions (0-switch) | The single valid transitions <Cite n={1} /> | Exercised valid transitions, divided by all valid transitions <Cite n={1} /> |
| All transitions | All transitions of the state table, valid and invalid <Cite n={1} /> | Valid and invalid transitions exercised or attempted, divided by all transitions <Cite n={1} /> |

Valid transitions coverage is stronger than all states coverage. <Cite n={1} /> Test cases can reach all states without exercising all transitions. <Cite n={1} /> Valid transitions coverage is the most used criterion. <Cite n={1} /> Full valid transitions coverage gives full all states coverage. <Cite n={1} /> Full all transitions coverage gives both. It should be a minimum for mission-critical and safety-critical software. <Cite n={1} />

To test invalid transitions, test only one invalid transition in a test case. This avoids defect masking. <Cite n={1} />

**Worked answer for the PIN example.** The rules above come from the syllabus. The counts below are the tutorial's own working, read from the diagram above. This tutorial takes Start as the initial marker, not as a state.

The states are 1st try, 2nd try, 3rd try, Access granted, and Account blocked. The events are "correct PIN" and "incorrect PIN". The state table is below. The two end states have no outgoing transitions, so their cells are empty.

| State | Correct PIN | Incorrect PIN |
|---|---|---|
| 1st try | Access granted | 2nd try |
| 2nd try | Access granted | 3rd try |
| 3rd try | Access granted | Account blocked |
| Access granted | | |
| Account blocked | | |

- States: 5.
- Valid transitions: 6 (the 6 filled cells).
- All cells: 5 states × 2 events = 10.
- Invalid transitions: 10 − 6 = 4 (the 4 empty cells).

These four test cases reach full valid transitions coverage.

| Test case | Events | Valid transitions exercised |
|---|---|---|
| A | Correct | 1st try → Access granted |
| B | Incorrect, correct | 1st try → 2nd try; 2nd try → Access granted |
| C | Incorrect, incorrect, correct | 1st try → 2nd try; 2nd try → 3rd try; 3rd try → Access granted |
| D | Incorrect, incorrect, incorrect | 1st try → 2nd try; 2nd try → 3rd try; 3rd try → Account blocked |

- Valid transitions coverage with A to D: 6 / 6 = 100%.
- All states coverage needs fewer tests. Test case C exercises 4 states: 1st try, 2nd try, 3rd try, and Access granted. That is 4 / 5 = 80%.
- Test cases C and D together exercise all 5 states: 5 / 5 = 100%.
- All transitions coverage with A to D: 6 / 10 = 60%.
- The 4 invalid transitions need 4 more test cases, one invalid transition in each. A plan with 4 + 4 = 8 test cases gives 10 / 10 = 100%.

</Version>
