# Experience-Based Techniques

Use your experience: error guessing, exploratory testing, and checklists.

<PageMeta />

## Error Guessing

<Voices>
<Technical>

<Version of="notes">

3 types of experienced based testing techniques
1. Error guessing
2. Exploratory testing
3. Checklist-based testing

Error guessing is a technique used to **anticipate** the occurrence of errors, defects, and failures, based on the tester's knowledge, including:
1. How the application has worked in the past
2. The types of errors the developers tend to make and the types of defects that result from these errors
3. The types of failures that have occurred in other, similar applications

Testers need to make a list of possible errors, defects, and failures, and then create tests that can find these issues or even make them happen.

**Error factors:**

Mistakes, issues, and problems in software can be linked to various things like:
1. **Input problems, like not accepting correct input or having the wrong or missing parameters.**
2. **Output issues, such as producing the wrong format or result.**
3. **Logic errors, which could involve missing cases or using the wrong operators.**
4. **Computation problems, like working with the wrong numbers or making incorrect calculations.**
5. **Interface-related troubles, such as parameter mismatches or incompatible types.**
6. **Data issues, including incorrect starting values or using the wrong data types.**

</Version>

ISTQB sorts test techniques into three groups: black-box, white-box, and experience-based. <Cite n={1} /> Experience-based techniques use the knowledge and experience of the tester to design and build test cases. <Cite n={1} /> Their results depend heavily on the skill of the tester. <Cite n={1} /> They can find defects that black-box and white-box techniques miss, so they complement those techniques. <Cite n={1} /> The syllabus names three experience-based techniques: error guessing, exploratory testing, and checklist-based testing. <Cite n={1} />

Error guessing is a technique that anticipates errors, defects, and failures from what the tester knows. <Cite n={1} /> The glossary says the test conditions come from knowledge of past failures or failure modes. <Cite n={2} />

The tester draws on three kinds of knowledge. <Cite n={1} />

- How the application behaved in the past.
- The errors that developers tend to make, and the defects that these errors cause.
- The failures that happened in other, similar applications.

The syllabus groups the errors, defects, and failures into six areas. <Cite n={1} />

| Area | Example of a problem |
|---|---|
| Input | The application refuses a correct input, or a parameter is wrong or missing. |
| Output | The format is wrong, or the result is wrong. |
| Logic | A case is missing, or an operator is wrong. |
| Computation | An operand is wrong, or the calculation is wrong. |
| Interfaces | The parameters do not match, or the types are not compatible. |
| Data | A start value is wrong, or the data type is wrong. |

A fault attack is one way to do error guessing. <Cite n={1} /> The tester creates or collects a list of possible errors, defects, and failures. <Cite n={1} /> Then the tester designs tests that find the defects, expose them, or cause the failures. <Cite n={1} /> The tester can build the list from experience, from data about past defects and failures, or from general knowledge of the causes of software failure. <Cite n={1} />

This example is the tutorial's own. It is not from ISTQB. Your team found a bug in an earlier release: the login form accepted a password of only spaces. This is a failure from the past. Add "password of only spaces" to your list of possible failures. Then run it on the new release and on other forms, such as the sign-up form.

## Exploratory Testing

<Voices>
<Technical>

<Version of="notes">

**Exploratory testing** is a way of testing where the tester **learns, designs, and runs** tests at the same time to understand the test subject better. Often, it's done in a **time-limited session** with specific goals called a **test charter**. After testing, **the tester shares** what they found with others.

The tester explores areas that haven't been tested yet and may use a simple sheet to note down what they did and discovered. Simple notes and findings are essential in this type of testing.

**Lightweight documentation are the crucial part of exploratory testing.**

</Version>

<Version of="istqb">

In exploratory testing, the tester designs, runs, and evaluates tests at the same time. <Cite n={1} /> The tester learns about the test object while doing this. <Cite n={1} /> The glossary describes it as a test approach where tests are designed and run dynamically. <Cite n={3} /> The tester uses personal knowledge, the exploration of the test item, and earlier test results. <Cite n={3} />

Exploratory testing has three aims. <Cite n={1} />

- Learn more about the test object.
- Explore the test object deeper with focused tests.
- Create tests for areas that nobody tested yet.

The syllabus describes session-based testing as a way to give structure to exploratory testing. <Cite n={1} />

| Part of a session | What it is |
|---|---|
| Time box | The session has a fixed length. <Cite n={1} /> |
| Test charter | The charter holds the test objectives and guides the session. <Cite n={1} /> The glossary calls it a mission statement for the session. <Cite n={4} /> |
| Test session sheet | The tester notes the steps taken and the discoveries made. <Cite n={1} /> |
| Debriefing | After the session, the tester and the interested stakeholders discuss the results. <Cite n={1} /> |

In a session, the test objectives can serve as high-level test conditions. <Cite n={1} /> The tester identifies coverage items and exercises them during the session. <Cite n={1} />

Exploratory testing helps when the specification is poor or missing, or when time is short. <Cite n={1} /> It also complements more formal test techniques. <Cite n={1} /> It works better if the tester is experienced, knows the domain, and has strong skills such as analysis, curiosity, and creativity. <Cite n={1} /> The tester can use other techniques during exploratory testing, for example equivalence partitioning. <Cite n={1} />

<Callout type="tip" title="Example charter (the tutorial's own)">

This example is the tutorial's own. It is not from ISTQB. A charter can be one sentence: "Explore the password reset flow with expired and reused links to find defects in error handling." Set a time box of 60 minutes. Write short notes during the session. Share the notes in the debriefing.

</Callout>

</Version>

## Checklist-Based Testing

<Voices>
<Technical>

<Version of="notes">

In **exploratory testing**, testers do not follow detailed step-by-step test cases. They explore the software using their experience, curiosity, and domain knowledge. So a checklist helps them stay focused and avoid missing important areas.

**Example checklist for exploratory testing of a login page. Often this is considered as test title.**

- Verify that valid users can log in successfully.
- Verify that users cannot log in with an invalid password.
- Verify that proper validation appears when email or password is empty.
- Verify that locked or blocked users cannot log in.
- Verify that the password visibility icon works properly.
- Verify that the remember me option works as expected.
- Verify that the forgot password link redirects users to the correct page.
- Verify that proper error messages appear for invalid login scenarios.
- Verify that session or token behavior works correctly after login.
- Verify that login works properly across different browsers and devices.

**Written format of Checklist:**

| SL | Checklist | Yes | No |
| --- | --- | --- | --- |
| 1 | Can a user register and login successfully? | ☐ | ☐ |
| 2 | Does product search and filtering work correctly? | ☐ | ☐ |
| 3 | Can users add items to cart and update quantity properly? | ☐ | ☐ |
| 4 | Does the checkout and payment process complete successfully? | ☐ | ☐ |
| 5 | Is order confirmation shown and email received? | ☐ | ☐ |
| 6 | Is the password securely stored (hashed)? | ☐ | ☐ |
| 7 | Is unauthorized access to user data restricted? | ☐ | ☐ |
| 8 | Does the website load within acceptable time (&lt;3 sec)? | ☐ | ☐ |
| 9 | Can the system handle multiple users without crashing? | ☐ | ☐ |
| 10 | Is payment data securely transmitted using HTTPS? | ☐ | ☐ |

<Callout type="warning">

ISTQB says a checklist should not contain items that a tool can check, such as items 8 and 10, or items that are too general, such as items 1, 4, and 9. Switch to the ISTQB version at the top of the page to see the ISTQB definition.

</Callout>

</Version>

<Version of="istqb">

In checklist-based testing, the tester designs, builds, and runs tests that cover the test conditions of a checklist. <Cite n={1} /> The glossary calls it an experience-based technique whose test cases exercise the items of a checklist. <Cite n={5} />

A tester can build a checklist from three things. <Cite n={1} />

- Experience.
- Knowledge about what is important for the user.
- An understanding of why and how software fails.

The syllabus gives guidance for the content of a checklist. <Cite n={1} />

| Guidance | Meaning |
|---|---|
| Make each item checkable on its own. | You should be able to check each item separately and directly. <Cite n={1} /> |
| Leave out items that a tool can check. | A checklist should not contain items that you can check automatically. <Cite n={1} /> |
| Leave out entry and exit criteria. | A checklist should not contain items that suit entry criteria or exit criteria better. <Cite n={1} /> |
| Leave out general items. | A checklist should not contain items that are too general. <Cite n={1} /> |

Checklist items are often questions. <Cite n={1} /> An item can refer to a requirement, a property of the graphical interface, a quality characteristic, or another test condition. <Cite n={1} /> A checklist can support functional and non-functional testing. <Cite n={1} />

A checklist needs care over time. Some entries become less effective, because developers learn to avoid the same errors. <Cite n={1} /> Add entries for new defects of high severity. <Cite n={1} /> Update the checklist from defect analysis, and do not let it grow too long. <Cite n={1} />

If detailed test cases are missing, a checklist gives guidelines and some consistency. <Cite n={1} /> A high-level checklist leads to more variety between test runs. <Cite n={1} /> This can give more coverage, but less repeatability. <Cite n={1} />

<Callout type="note" title="The tutorial's own advice">

This advice is the tutorial's own. It is not from ISTQB. Apply the guidance above to the owner's written-format table:

- Item 8 ("load within acceptable time") is a check for a performance tool. Put it in an automated test.
- Item 10 ("HTTPS") is also a check for an automated test or a scan.
- Item 9 ("multiple users without crashing") is too general. Name the number of users and the action.
- Items 1 and 4 are too general. Split them into one question for each step, for example "Does the sign-up form show an error for an email that is already in use?"

</Callout>

Rules for the content <Cite n={1} />:

- You can check each item on its own and directly.
- Leave out items that a tool can check.
- Leave out items that fit entry or exit criteria better.
- Leave out items that are too general.

A checklist can support functional and non-functional testing <Cite n={1} />. Some items lose effect, because developers learn to avoid the same errors. Add items for new defects of high severity, and do not let the list grow too long <Cite n={1} />.

A high-level checklist gives more variety between test runs. It can give more coverage but less repeatability <Cite n={1} />.

## White-Box Checklist

<Voices>
<Technical>

<Version of="notes">

- Is each important code statement executed by at least one test?
- Are all major `if-else` or decision outcomes tested properly?
- Are individual conditions inside complex logic tested correctly?
- Are boundary values handled correctly in the code?
- Are null, undefined, empty, and invalid values handled safely?
- Are default and optional parameter values tested properly?
- Are exceptions and error-handling blocks tested correctly?
- Are important business rules implemented correctly in the code logic?
- Are service, controller, repository, API, and database layers interacting correctly?
- Are security checks like authentication, authorization, token validation, and permission checks implemented correctly?

**White-box testing is not just about code coverage — it is about verifying internal logic, hidden conditions, business rules, error handling, and system behavior from inside the code.**

</Version>

<Version of="istqb">

This topic uses the term "generic white-box checklist". The ISTQB syllabus and glossary do not define this term.

<Callout type="note" title="The tutorial's own explanation">

A generic white-box checklist is a list of questions that a tester or a reviewer asks about the code. The list in the owner's notes is the tutorial's own. It is not from ISTQB.

ISTQB does define the two parts of the idea. A white-box technique uses the internal structure and processing of the test object. <Cite n={1} /> Checklist-based testing designs the test cases from the items of a checklist. <Cite n={5} />

Two questions of the list match the white-box techniques of the syllabus. The syllabus names only two such techniques: statement testing and branch testing. <Cite n={1} />

| Question of the list | Link to the syllabus |
|---|---|
| Is each important statement executed by at least one test? | Statement coverage is the number of statements that the tests exercise, divided by the number of executable statements. <Cite n={1} /> |

White-box testing also has a limit. It may miss a defect of omission, where the code does not implement a requirement. <Cite n={1} />
