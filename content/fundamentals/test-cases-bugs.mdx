# Test Cases, Bugs and Completion

Write test cases and bug reports, triage bugs, and close the testing.

<PageMeta />

## Test Case

<Version of="notes">

A test case is a set of actions performed on a system to determine if it satisfies software requirements and functions correctly.

<Callout type="warning">

The notes define a test case as actions that testers perform, but the ISTQB glossary defines it as a set of preconditions, inputs, actions, expected results, and postconditions. Switch to the ISTQB version at the top of the page to see the ISTQB definition.

</Callout>

Test case should have following fields:

1. Test case Id
2. Test scenario/module
3. Prerequisites
4. Test case title
5. Test steps
6. Test data
7. Expected Result
8. Actual Result
9. Test Result/Status
10. Remarks

Test Case example:

<MdxImage src="/images/fundamentals/test-case-template.png" alt="A test case template in a spreadsheet. A header block holds the test scenario id, the creator, the reviewer, and the test date. Below it is a table with the columns Test Case Id, Test Scenario, Test Case Title, Prerequisites, Steps/Actions, Test Data, Expected Result, Actual Result, Status, and Remarks." />

</Version>

<Version of="istqb">

A test case is a piece of testware <Cite n={1} />.

The glossary defines a test case as a set of preconditions, inputs, actions (where applicable), expected results, and postconditions. Testers develop it from test conditions <Cite n={2} />.

| Activity | What happens to test cases |
|---|---|
| Test design | The tester elaborates test conditions into test cases <Cite n={1} /> |
| Test implementation | The tester can organize test cases into test procedures. Procedures are often assembled into test suites <Cite n={1} /> |
| Test execution | The tester runs the tests, compares actual results with expected results, and logs the results <Cite n={1} /> |

A test log is a chronological record of relevant details about test execution <Cite n={3} />. So the actual result and the pass or fail status belong to one test run. They do not belong to the definition of the test case.

The syllabus gives no list of test case fields <Cite n={1} />. Each team picks its own layout.

<Callout type="note" title="The tutorial's own explanation">

The common layout of a test case sheet has the fields below. The last column compares each field with the parts of the ISTQB definition. This comparison is the tutorial's own.

| Field | What it holds | Part of the ISTQB definition |
|---|---|---|
| Test case ID | A unique label for the test case | None (a label) |
| Test scenario or module | The feature or area that the test case belongs to | None (grouping) |
| Prerequisites | The state that must exist before the first step | Preconditions |
| Title | One line that says what the test case checks | None (a label) |
| Steps | The actions, in order | Actions |
| Test data | The values that the steps enter | Inputs |
| Expected result | What the system must do or show | Expected results |
| Actual result | What the system did in this run | None (execution record) |
| Status | Pass, fail, or not executed | None (execution record) |
| Remarks | Free notes, such as a defect ID | None (execution record) |

The field list has no field for postconditions. Add one if a step leaves data or a state behind that the next test must know.

</Callout>

</Version>

## Bug Report

<Version of="notes">

During test execution, if a tester identifies a discrepancy between the expected result and the actual result, it is considered an anomaly or issue. The tester then communicates this finding with the developer or project manager and documents it in a report, typically referred to as a 'bug report' or 'defect report'.

Bug report has following fields:

1. Status (Open/Fixed/Closed)
2. Issue Id (automatically)
3. Issue title
4. Issue Type (bug/improvement)
5. Issue description (detail about the issue)
6. Steps to reproduce
7. Priority
8. Severity
9. Environment
10. Sprint
11. Version
12. Date
13. Assign to
14. Attachment

</Version>

<Version of="istqb">

During test execution, the tester compares actual results with expected results. The tester analyzes each anomaly to find its likely cause, and then reports the anomaly <Cite n={1} />. The glossary defines an anomaly as a condition that deviates from expectation <Cite n={4} />.

A defect report documents the occurrence, nature, and status of a defect <Cite n={5} />. "Bug report" is another name for it <Cite n={5} />.

A reported anomaly may turn out to be a real defect or something else. For example, it can be a false-positive result or a change request. The team finds out while it handles the report <Cite n={1} />.

Defect management is the process of recognizing, recording, classifying, investigating, fixing, and disposing of defects <Cite n={6} />. A typical defect report has three objectives <Cite n={1} />:

- It gives the people who resolve the defect enough information to fix it.
- It gives a way to track the quality of the work product.
- It gives ideas to improve the development and test process.

A defect report from dynamic testing typically has the fields below <Cite n={1} />. The last column shows the matching field of the owner's notes.

| ISTQB field | What it holds | Field in the notes |
|---|---|---|
| Unique identifier | A unique ID for the report | Issue Id |
| Title | A short summary of the anomaly | Issue title |
| Date, organization, author | When the anomaly was seen, who reported it, and the author's role | Date |
| Test object and test environment | What was tested, and where | Environment, Version |
| Context | The test case being run, the test activity, the SDLC phase, and the technique, checklist, or test data in use | No matching field |
| Description | The failure, the steps that found it, and evidence such as logs, database dumps, screenshots, or recordings | Issue description, Steps to reproduce, Attachment |
| Expected and actual results | What the tester expected and what happened | No separate field |
| Severity | The degree of impact on stakeholder interests or on requirements | Severity |
| Priority | The priority to fix the defect | Priority |
| Status | For example open, deferred, or closed | Status |
| References | For example the test case | No matching field |

The notes also list Issue Type, Sprint, and Assign to. The syllabus does not list these three fields <Cite n={1} />.

The glossary defines severity as the degree of impact that a defect has on development, testing, or operation <Cite n={7} />. It defines priority as the level of importance assigned to a task according to specific criteria <Cite n={8} />.

Defect management tools can fill some fields on their own, such as the identifier, the date, the author, and the first status <Cite n={1} />. The standard ISO/IEC/IEEE 29119-3 has templates and examples of defect reports. It calls them incident reports <Cite n={1} />.

<Callout type="tip" title="The tutorial's own advice">

Report one defect in each report. Write the steps so that a developer can repeat the failure without asking you. Name the build and the environment. This is the tutorial's own advice, not an ISTQB rule.

</Callout>

</Version>

## Bug Life Cycle

<Version of="notes">

<MdxImage src="/images/fundamentals/bug-life-cycle.png" alt="The bug life cycle. A bug moves from New to Open, then Fixed, then Retest, then Closed. A New bug can go to Rejected. An Open bug can go to Deferred. A bug that fails the retest goes to Reopen, and then back to Fixed." />

</Version>

<Version of="istqb">

The ISTQB syllabus and glossary do not define this term.

The syllabus lists eight example defect statuses: closed, rejected, open, deferred, duplicate, re-opened, waiting to be fixed, and awaiting confirmation testing <Cite n={1} />. It gives them as examples and shows no fixed diagram <Cite n={1} />.

The glossary has a close term. A defect workflow is the state transition model of a defect life cycle, including responsibilities <Cite n={9} />. The glossary gives no list of states for it <Cite n={9} />.

The workflow usually has four kinds of activity <Cite n={1} />:

1. Log the reported anomaly.
2. Analyze and classify it.
3. Decide on a response, such as fix it or keep it as it is.
4. Close the defect report.

After a fix, the tester runs confirmation testing. It checks that the failure caused by that defect does not occur again <Cite n={10} />. The glossary lists "retesting" as another name for it <Cite n={10} />.

<Callout type="note" title="The tutorial's own explanation">

The diagram shows the life cycle that is common in practice and in the owner's notes. ISTQB does not define these states. A team changes the states and their names to fit its defect tool.

| State | Meaning | Next state | Closest ISTQB example status |
|---|---|---|---|
| New | A tester logged the bug. Nobody has reviewed it yet. | Open or Rejected | None |
| Open | The team accepted the bug and gave it to a developer. | Fixed or Deferred | Open, or waiting to be fixed |
| Rejected | The team decided that it is not a defect. | End | Rejected |
| Deferred | The team accepted the bug but will fix it in a later release. | Not shown in the diagram. Often Open, when the team schedules it | Deferred |
| Fixed | The developer says the fix is done and is in a build. | Retest | Awaiting confirmation testing |
| Retest | The tester runs the failed test again on the new build. | Closed or Reopen | None. This is the confirmation testing itself. |
| Reopen | The failure still occurs after the fix. | Fixed | Re-opened |
| Closed | The fix is confirmed. | End | Closed |

The ISTQB example "duplicate" has no state in this diagram.

</Callout>

</Version>

## Bug Triage

<Version of="notes">

Bug triage is a process in software development and testing where identified bugs or issues are evaluated, categorized, and prioritized to determine their importance and order in which they should be addressed.

In bug triage we categorized the issue by applying priority and severity

1. Priority (High/Medium/Low): It means how fast the issue should resolve
2. Severity (Critical/Major/Minor): It means how much its impact on the system

Often Critical/Major severity are pointed as High severity and Minor severity are pointed as low severity.

**Bug Triage States**

Based on the High and Low factors, bug has 4 states:

**1. High Priority, High Severity**

**Meaning:** The bug seriously breaks the system and must be fixed immediately.

**Example:** In an eCommerce website, users cannot complete payment after placing an order.

**2. High Priority, Low Severity**

**Meaning:** The bug is not technically serious, but it is important for business or user impression.

**Example:** The company logo is missing from the homepage during a big marketing campaign.

**3. Low Priority, High Severity**

**Meaning:** The bug is serious, but it happens rarely or in a less important area.

**Example:** The application crashes only when an admin uploads a 500MB file, but the allowed file size is 10MB.

**4. Low Priority, Low Severity**

**Meaning:** The bug has very small impact and does not need urgent fixing.

**Example:** A minor spelling mistake appears in the footer text.

</Version>

<Version of="istqb">

The ISTQB syllabus and glossary do not define this term.

They do define the two values that a triage uses. Severity is the degree of impact that a defect has on development, testing, or operation <Cite n={7} />. Priority is the level of importance assigned to a task according to specific criteria <Cite n={8} />.

A defect report has a field for severity and a separate field for priority <Cite n={1} />. The defect management process includes rules to classify defects, and all involved stakeholders must follow them <Cite n={1} />. The syllabus sets no scale of levels for either value <Cite n={1} />.

<Callout type="note" title="The tutorial's own explanation">

In daily work, bug triage is a review of new bugs. The team reads each bug, sets its severity and priority, and decides the order of the fixes. Many teams do this in a short regular meeting. The scales in the notes, such as Critical, Major, and Minor, are common team conventions and not ISTQB levels.

Severity says how bad the impact is. Priority says how soon to fix it. The two values are separate, so a bug can have any combination.

| Priority | Severity | How to read it | Example |
|---|---|---|---|
| High | High | Fix it now. The product is broken in a way that matters. | No user can pay at checkout. |
| High | Low | Fix it soon, because of business or image. The technical impact is small. | The wrong company logo shows on launch day. |
| Low | High | Plan the fix. The impact is large but it rarely happens. | The app crashes when an admin imports a file 50 times the size limit. |
| Low | Low | Fix it when there is time. | A spelling mistake sits in the footer. |

</Callout>

</Version>

## Entry and Exit Criteria

<Version of="notes">

**Entry criteria** are conditions that must be met before starting an activity. If they aren't met, the activity can become more difficult, time-consuming, expensive, and risky.

**Examples:**

- Requirements are reviewed and approved
- Test environment is set up and accessible

**Exit criteria** define what needs to be achieved to consider an activity finished. These criteria are specific to the goals of the testing.

**Examples:**

- All critical test cases are executed and passed
- No high or critical defects remain open

</Version>

<Version of="istqb">

The glossary defines entry criteria as the conditions for officially starting a task <Cite n={11} />. It defines exit criteria as the conditions for officially completing a task <Cite n={12} />.

The syllabus says a team should define both for each test level. They differ with the test objectives <Cite n={1} />. If the team does not meet the entry criteria, the activity likely becomes harder, slower, costlier, and riskier <Cite n={1} />.

Typical entry criteria fall into three groups <Cite n={1} />:

- Resources are available: people, tools, environments, test data, budget, and time.
- Testware is available: the test basis, testable requirements, user stories, and test cases.
- The test object has an initial quality level. For example, all smoke tests pass.

Typical exit criteria fall into two groups <Cite n={1} />:

- Measures of thoroughness: the level of coverage, the number of unresolved defects, the defect density, and the number of failed test cases.
- Yes or no criteria: the planned tests ran, static testing is done, all defects found are reported, or all regression tests are automated.

| | Entry criteria | Exit criteria |
|---|---|---|
| Question they answer | Can we start? | Can we stop? |
| Name in Agile | Definition of Ready, for a user story <Cite n={1} /> | Definition of Done <Cite n={1} /> |

A team can also treat a lack of time or budget as a valid exit criterion. The stakeholders must first review the risk of release with less testing and accept it <Cite n={1} />.

</Version>

## Test Completion

<Version of="notes">

Test completion gathers data from finished test activities to compile experience, test materials, and any other relevant information. Test completion activities occur at project milestones such as:

1. When a test level is completed
2. An agile iteration is finished
3. A test project is completed or cancelled
4. A software system is released
5. A maintenance release is completed

</Version>

<Version of="istqb">

The glossary defines test completion as an activity with three results. It makes testware available for later use. It leaves test environments in a satisfactory condition. It tells stakeholders the results of testing <Cite n={13} />. "Test closure" is another name for it <Cite n={13} />.

Test completion usually happens at a project milestone. Examples are a release, the end of an iteration, and the completion of a test level <Cite n={1} />. The tasks are <Cite n={1} />:

1. Create a change request or a product backlog item for each unresolved defect.
2. Find testware that may be useful later, and archive it or hand it over to the right teams.
3. Shut down the test environment to an agreed state.
4. Analyze the test activities to find lessons learned and improvements.
5. Create a test completion report and send it to the stakeholders.

Test completion produces a completion report, change requests, documented lessons learned, and action items. The action items are for improving later projects or iterations. <Cite n={1} />

A test completion report evaluates the test items against the exit criteria <Cite n={14} />. It is prepared during test completion. That is when a project, a test level, or a test type is complete, and ideally when its exit criteria are met. The report uses the test progress reports and other data <Cite n={1} />. A typical report has these parts <Cite n={1} />:

| Part | What it holds |
|---|---|
| Test summary | A short account of the testing |
| Evaluation | The quality of the testing and of the product, measured against the test objectives and exit criteria of the test plan |
| Deviations | Differences from the plan in schedule, duration, and effort |
| Impediments | The things that blocked testing, and the workarounds |
| Metrics | Test metrics taken from the progress reports |
| Open items | Unmitigated risks and defects that stay unfixed |
| Lessons learned | What the team learned that matters for testing |

A completion report follows a set template and appears once. A progress report to the same team is often frequent and informal <Cite n={1} />.

</Version>

## Requirement Traceability Matrix (RTM)

<Version of="notes">

**Requirement Traceability Matrix (RTM)** is a document/table that maps each **requirement** with its related **test cases**.

It helps the QA team confirm that **every requirement is covered by testing**.

**In simple terms**

**RTM = Requirement coverage tracking document**

It answers:

- Which requirement is tested?
- Which test case covers that requirement?
- Has the test case passed or failed?
- Is any requirement missing test coverage?

Example:

<MdxImage src="/images/fundamentals/rtm-example.png" alt="A requirements traceability matrix for an online flight booking application. Business requirement BR_1, the reservation module, has functional requirements FR_1 to FR_3 for one-way, round-trip, and multi-city booking. Each has high priority and two test cases, TC#001 to TC#006. Business requirement BR_2, the payment module, has FR_4 for credit card and FR_5 for debit card with high priority, and FR_6 for reward points with medium priority. They have test cases TC#007 to TC#011." />

</Version>

<Version of="istqb">

The ISTQB syllabus and glossary do not define this term.

They do define two wider terms. Traceability is the ability to establish explicit relationships between related work products or items within work products <Cite n={15} />. A traceability matrix is a matrix that correlates such items to determine the coverage achieved <Cite n={16} />.

The syllabus tells testers to keep traceability through the whole test process. It links four kinds of item <Cite n={1} />:

- the elements of the test basis
- the testware for those elements, such as test conditions, risks, and test cases
- the test results
- the defects

Trace test cases to requirements to check that the test cases cover each requirement <Cite n={1} />. Tracing test results to risks can show how much residual risk a test object has <Cite n={1} />.

Good traceability also gives these benefits <Cite n={1} />:

- It supports the evaluation of coverage. This is most useful when the test basis has measurable coverage criteria.
- It makes it possible to find the impact of a change.
- It makes audits easier and helps meet IT governance criteria.
- It makes progress and completion reports easier to understand, because they show the status of test basis elements.

<Callout type="note" title="The tutorial's own explanation">

An RTM is a traceability matrix with requirements in the rows and test cases in the cells. A requirement with an empty test case cell has no coverage. That is a gap to close.

| Requirement | Test cases | Last result |
|---|---|---|
| R1: A user can log in with a valid email and password | TC-001, TC-002 | Passed |
| R2: A user sees an error after three failed logins | TC-003 | Failed |
| R3: A user can reset a password | None | Not covered |

Add a column for the defect ID if you also want to trace defects, as the list above shows.

</Callout>

</Version>
