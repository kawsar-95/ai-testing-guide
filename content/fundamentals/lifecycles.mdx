# SDLC, STLC and Agile

How testing fits into the software life cycle and into Agile teams.

<PageMeta />

## Software Testing Life Cycle (STLC)

<Voices>
<Technical>

<Version of="notes">

<MdxImage src="/images/fundamentals/stlc-phases.png" alt="Six boxes in a staircase: Requirement Analysis, Test Planning, Test Case Development, Test Environment Setup, Test Execution, Test Closure" />

**STLC** is a structured process that defines the **step-by-step activities involved in software testing** from requirement analysis to test closure.

It ensures testing is **planned, systematic, and measurable**, rather than random execution.

<Callout type="warning">

The notes describe the STLC as seven fixed phases from requirement analysis to test closure, but the ISTQB syllabus does not define an STLC and lists seven groups of test activities that are often done in parallel or repeated. Switch to the ISTQB version at the top of the page to see the ISTQB definition.

</Callout>

**Phases of STLC**

**1. Requirement Analysis**

**What happens:** Understand what needs to be tested from requirements or user stories.

**Example:** For a login system, QA identifies requirements like valid login, invalid login, password rules, etc.

**2. Test Planning**

**What happens:** Define strategy, scope, resources, and timeline.

**Example:** Decide to use Selenium for automation and Postman for API testing, and set regression scope.

**3. Test Case Design (Test Development)**

**What happens:** Write test cases and prepare test data.

**Example:**

- Valid login test case
- Invalid password test case
- SQL test data for user table

**4. Test Environment Setup**

**What happens:** Prepare the system where testing will be executed.

**Example:** QA environment deployed with database, APIs, and frontend connected.

**5. Test Execution**

**What happens:** Run test cases and record results.

**Example:** Execute login test → compare expected vs actual result.

**6. Defect Reporting & Tracking**

**What happens:** Log bugs and track fixes.

**Example:** Report "Login fails for valid user" in Jira and assign to developer.

**7. Test Closure**

**What happens:** Evaluate testing completion and prepare summary report.

**Example:** Final report shows 95% test cases passed, 5% bugs fixed or deferred.

**Simple Summary**

STLC =

> *Requirement → Planning → Test Design → Setup → Execution → Bug Reporting → Closure*

</Version>

STLC means "software testing life cycle". Teams use it as a name for the stages of testing, in order. Each team uses its own list of stages, so you will see lists of six, seven, or more. ISTQB uses the term "test process" for the same idea.

## Testing Activities

<Voices>
<Technical>

<Version of="notes">

**1. Test Planning**

Define **objectives, scope, strategy, resources, schedule, and risks**.

Example: Decide to test an e-commerce app using UI + API automation with Playwright + Postman.

**2. Test Monitoring & Control**

Track progress against the plan and take corrective actions.

Example: If API testing is delayed, redistribute effort or adjust timeline.

**3. Test Analysis (What to test?)**

Analyze requirements/test basis and derive **test conditions / acceptance criteria / testable items**, including risks.

Example: From "Login feature", derive conditions like valid login, invalid credentials, locked account, security checks.

**4. Test Design (How to test?)**

Convert test conditions into **test cases, test data, test coverage approach, and test design techniques**.

Example:

- Decide boundary value tests for password length
- Decide equivalence partitioning for input validation
- Design data sets and coverage strategy

**5. Test Implementation**

Prepare execution-ready assets (**testware**).

- Organize test cases into suites
- Create automation scripts/manual procedures
- Set up test environment

Example: Build Playwright framework and configure staging environment.

**6. Test Execution**

Run tests and compare **actual vs expected results**, log defects, and analyze failures.

Example: API returns 500 instead of 200 → defect logged.

**7. Test Closure**

Complete testing cycle and finalize reporting.

- Close defects and testware
- Archive artifacts
- Prepare test summary report
- Collect lessons learned

Example: Release report with pass/fail metrics and known issues.

</Version>

<Version of="istqb">

The syllabus groups the work of testing into seven activities. <Cite n={1} /> The table lists each activity, its purpose, and its main tasks.

| Activity | Purpose | Main tasks |
|---|---|---|
| Test planning | Decide the test objectives and the approach. | Define the objectives. Select an approach that fits the constraints. <Cite n={1} /> |
| Test monitoring and test control | Keep testing on track. | Check all test activities and compare actual progress with the plan (monitoring). Take the actions that meet the objectives (control). <Cite n={1} /> |
| Test analysis | Decide what to test. | Analyze the test basis. Define and prioritize test conditions with their risks. Look for defects in the test basis. <Cite n={1} /> |
| Test design | Decide how to test. | Turn test conditions into test cases and other testware. Find coverage items. Define test data needs and design the test environment. <Cite n={1} /> |
| Test implementation | Get ready to run the tests. | Create test data, test procedures, test suites, and scripts. Set the execution schedule. Build and verify the test environment. <Cite n={1} /> |
| Test execution | Run the tests. | Run the tests by the schedule, manually or with tools. Compare actual and expected results. Log the results. Analyze anomalies. <Cite n={1} /> |
| Test completion | Close the testing at a milestone. | Create change requests or backlog items for unresolved defects. Archive useful testware. Shut down the environment. Collect lessons learned. Send a completion report. <Cite n={1} /> |

Test analysis decides what to test. It states this in coverage criteria that you can measure. <Cite n={1} /> Test design decides how to test. <Cite n={1} />

Test completion usually happens at project milestones. Examples are a release, the end of an iteration, or the end of a test level. <Cite n={1} />

The activities create testware as output work products. <Cite n={1} /> The context of the project changes how a team does the activities. Stakeholders, team skills, time, budget, and the development life cycle all have an effect. <Cite n={1} />

<Callout type="tip" title="The tutorial's own advice">

In a small Agile team, one meeting can cover test analysis and test design for a user story. The activities still exist. Only the size and the paperwork change. This advice is the tutorial's own, not a syllabus statement.

</Callout>

## Software Development Life Cycle (SDLC)

<Voices>
<Technical>

<Version of="notes">

The Software Development Life Cycle (SDLC) refers to a methodology with clearly defined processes for creating high-quality software.

<Callout type="warning">

The notes call the SDLC a methodology, but the ISTQB glossary defines it as the activities done in each development phase and how they relate to one another. Switch to the ISTQB version at the top of the page to see the ISTQB definition.

</Callout>

SDLC Phases are:

**1. Requirement Gathering & Analysis**

Collect and analyze business/user requirements.

**Output:** SRS (Software Requirement Specification)

Example: Define features like login, payment, user roles.

**2. System Design (architectural/UI/UX)**

Convert requirements into system UI, UX and system architecture and design.

**Output:** HLD (High-Level Design: System architecture (services + components)), LLD (Low-Level Design: Internal design of a component (API, logic, DB schema))

Example: Decide database schema, API structure, system flow.

**3. Implementation (Coding/Development)**

Develop the actual software based on design documents.

**Output:** Source code

Example: Backend APIs in Node.js, frontend in React.

**4. Testing**

Verify the system meets requirements and is defect-free.

<Callout type="warning">

The notes say testing verifies that the system is defect-free, but the ISTQB syllabus says testing cannot prove that there are no defects. Switch to the ISTQB version at the top of the page to see the ISTQB definition.

</Callout>

**Output:** Test reports, bug reports

Example: API testing, UI testing, regression testing.

**5. Deployment**

Release the software to production or live environment.

**Output:** Live system

Example: Deploy application on AWS, VPS, or cloud platform.

**6. Maintenance**

Fix issues and improve the system after release.

**Output:** Updates, patches, enhancements

Example: Bug fixes, performance improvements, new feature updates.

<Callout type="warning">

The notes show testing as one phase after coding, but the ISTQB syllabus says every development activity has a matching test activity. Switch to the ISTQB version at the top of the page to see the ISTQB definition.

## SDLC Models

<Version of="notes">

**1. Sequential Model**

In a sequential model, development follows a fixed step-by-step flow, such as:

**Requirement → Design → Development → Testing → Deployment**

Testers usually get involved in requirement review, test analysis, and test design early. However, because executable code is developed in later phases, **dynamic testing** usually starts late.

**Example:** Waterfall, V-Model

**Simple idea:** Testing preparation can start early, but actual execution starts after development.

**2. Iterative / Incremental Model**

In iterative and incremental models, the system is developed in repeated cycles. Each cycle may deliver a working prototype or product increment.

This allows both:

- **Static testing**: reviewing requirements, design, test cases
- **Dynamic testing**: executing the working software

Because increments are delivered frequently, teams need fast feedback and strong regression testing.

**Example:** Spiral model, Prototyping, RAD

**Simple idea:** Build, test, improve, and deliver step by step.

**3. Agile Methodology**

Agile is a flexible and collaborative SDLC approach where software is developed in short cycles with frequent customer feedback.

It combines both **iterative** and **incremental** development. Cross-functional teams work together to deliver working software quickly and adapt to changing requirements.

**Example:** Scrum, Kanban

**Simple idea:** Build small, test continuously, get feedback, and improve fast.

**Activities of Agile:**

1. **Define the project**: The team, along with the customer, defines the project's goals, objectives, and requirements.
2. **Create a backlog**: A backlog is a prioritized list of tasks that need to be completed. The customer, product owner, and the team work together to create the backlog.
3. **Plan the sprint**: The team plans the sprint by selecting the highest-priority tasks from the backlog and determining how much work can be completed in the upcoming sprint.
4. **Execute the sprint**: The team works on completing the tasks planned for the sprint, with daily meetings to check progress and address any issues.
5. **Review and demo**: At the end of the sprint, the team demonstrates the completed work to the customer and gets feedback.
6. **Retrospect**: The team retrospects on the sprint, discussing what went well, what didn't, and what can be improved for the next sprint.
7. **Repeat**: The process is repeated for each sprint until the project is completed. The product is incrementally developed and delivered to the customer in small chunks.
8. **Continuous improvement**: Agile methodologies focus on continuous improvement. The team reflects on its progress and makes adjustments as necessary to improve processes, tools, and communication for the next sprint.

Agile-এর activity-গুলো:

1. **Define the project:** team ও customer মিলে project-এর goal, objective ও requirement ঠিক করে।
2. **Create a backlog:** customer, product owner ও team মিলে শেষ করতে হবে এমন task-এর priority অনুযায়ী সাজানো তালিকা তৈরি করে।
3. **Plan the sprint:** team backlog থেকে সবচেয়ে বেশি priority-র task বাছাই করে এবং আসন্ন sprint-এ কতটা কাজ শেষ করা যাবে তা ঠিক করে।
4. **Execute the sprint:** team sprint-এর task-গুলো শেষ করে; প্রতিদিন meeting করে অগ্রগতি দেখে এবং সমস্যা মেটায়।
5. **Review and demo:** sprint-এর শেষে team customer-কে শেষ হওয়া কাজ দেখায় এবং feedback নেয়।
6. **Retrospect:** কী ভালো হয়েছে, কী হয়নি এবং পরের sprint-এ কী উন্নত করা যায়, team তা আলোচনা করে।
7. **Repeat:** project শেষ না হওয়া পর্যন্ত প্রতিটি sprint-এ এটি চলে। Product ছোট ছোট অংশে customer-এর কাছে যায়।
8. **Continuous improvement:** team নিজের অগ্রগতি দেখে পরের sprint-এর জন্য process, tool ও communication উন্নত করে।

## ATDD, TDD and BDD

<Voices>
<Technical>

<Version of="notes">

**Acceptance Test-Driven Development (ATDD)**

- Derives tests from acceptance criteria as part of the system design process
- Tests are written before the part of the application is developed to satisfy the tests

**Test-Driven Development (TDD):**

- Directs the coding through test cases (instead of extensive software design)
- Tests are written first, then the code is written to satisfy the tests, and then the tests and code are refactored

**Behavior-Driven Development (BDD):**

- Expresses the desired behavior of an application with test cases written in a simple form of natural language, which is easy to understand by stakeholders usually using the Given/When/Then format.
- Test cases are then automatically translated into executable tests

For all these approaches, automated tests can be kept to maintain code quality during future changes or improvements

For real development practice:

> ***ATDD-style thinking is more common before development**, where requirements are broken into acceptance criteria.*

</Version>

<Version of="istqb">

The syllabus calls TDD, ATDD, and BDD similar approaches. In all three, tests direct the development. <Cite n={1} /> The team defines the tests before it writes the code. So all three follow the principle of early testing and shift left. They support an iterative model. <Cite n={1} />

| Approach | What it does | What the tests look like |
|---|---|---|
| TDD | Test cases, not an extensive software design, guide the coding. <Cite n={1} /> The glossary says the team develops and automates the test cases first. <Cite n={7} /> | Automated tests of the code, written before the code. |
| ATDD | The team gets the tests from the acceptance criteria while it designs the system. <Cite n={1} /> The glossary says it is a collaborative test-first approach. It defines the acceptance tests in the domain language of the stakeholders. <Cite n={8} /> | Acceptance tests that the stakeholders understand. |
| BDD | Describes the desired behavior of the application with test cases in simple natural language. <Cite n={1} /> The glossary says the team focuses on the behavior that the customer expects. This behavior is the basis for testing. <Cite n={9} /> | Usually the Given/When/Then format. |

**TDD in three steps.** The team first writes a test. Then it writes the code that passes the test. Then it refactors the tests and the code. <Cite n={1} />

**ATDD in practice.** The first step is a specification workshop. The team discusses and writes the user story and its acceptance criteria. <Cite n={1} /> Team members with different views, such as customers, developers, and testers, create the test cases. <Cite n={1} /> The first test cases are positive. Then the team does negative testing. Last, it covers non-functional quality characteristics such as performance efficiency and usability. <Cite n={1} />

**BDD in practice.** The team writes test cases in a format that stakeholders can read. Then it translates the test cases into executable tests. <Cite n={1} />

<Callout type="tip" title="The tutorial's own example">

A Given/When/Then test case for a login page can read as follows. This example is the tutorial's own, not a syllabus example.

```text
Given a registered user at the login page
When the user enters the correct email and password
Then the user sees the dashboard
```

</Callout>

For all three approaches, the tests can stay as automated tests. They protect the code quality when the code changes later. <Cite n={1} /> Shift left means that testing starts earlier. It does not mean that the team can neglect testing later in the SDLC. <Cite n={1} />

</Version>

**Acceptance Test-Driven Development (ATDD):**

- System design process-এর অংশ হিসেবে acceptance criteria থেকে test তৈরি হয়।
- Application-এর যে অংশ test-গুলো পূরণ করবে, সেই অংশ develop করার আগেই test লেখা হয়।

**Test-Driven Development (TDD):**

- বিস্তারিত software design-এর বদলে test case দিয়ে coding পরিচালনা করা হয়।
- আগে test লেখা হয়, তারপর test পূরণ করতে code লেখা হয়, তারপর test ও code refactor করা হয়।

**Behavior-Driven Development (BDD):**

- Application-এর কাঙ্ক্ষিত behavior সহজ natural language-এ লেখা test case দিয়ে প্রকাশ করা হয়, যা stakeholder-রা সহজে বোঝেন। সাধারণত Given/When/Then format ব্যবহার হয়।

এই তিনটি approach-এই automated test রেখে দেওয়া যায়, যাতে ভবিষ্যতের পরিবর্তন বা উন্নতির সময় code quality ঠিক থাকে।

বাস্তব development-এ ATDD-ধাঁচের চিন্তা development-এর আগে বেশি দেখা যায়, যখন requirement-কে acceptance criteria-তে ভাগ করা হয়।
