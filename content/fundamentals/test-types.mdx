# Test Types

Static and dynamic testing, and the common functional and non-functional test types.

<PageMeta />

## Testing Classification

<Version of="notes">

</Version>

<Version of="istqb">

The syllabus groups test techniques into three kinds: black-box, white-box, and experience-based. <Cite n={1} /> It also addresses four test types: functional, non-functional, black-box, and white-box. <Cite n={1} />

The glossary defines manual testing as a test activity that people perform by hand. <Cite n={2} /> It defines test automation as the conversion of test activities to automated operation. <Cite n={3} />

The glossary defines static testing and dynamic testing as two test approaches. Static testing does not execute the test item. <Cite n={4} /> Dynamic testing does. <Cite n={5} />

## Static Testing

<Version of="notes">

**Static testing** is a type of testing where the software is tested **without executing the code or application**.

In static testing, testers, developers, business analysts, or other team members review documents, requirements, designs, test cases, or source code to find defects early.

**Use Cases of Static Testing:**
1. Requirement Review
2. Design Review
3. Test Case Review
4. Code Review
5. API Specification Review
6. User Story / Acceptance Criteria Review

</Version>

<Version of="istqb">

Static testing checks a test item without running it. <Cite n={4} /> People examine work products by hand, for example in a review. <Cite n={1} /> A tool can also help to examine work products. This is static analysis. <Cite n={1} />

The objectives of static testing include better quality and the detection of defects. <Cite n={1} /> They also include an assessment of readability, completeness, correctness, testability, and consistency. <Cite n={1} />

Almost any work product can be examined by static testing. <Cite n={1} /> The syllabus gives these examples:

- Requirement specification documents
- Source code
- Test plans and test cases
- Product backlog items
- Test charters
- Project documentation, contracts, and models

A review works on any work product that people can read and understand. <Cite n={1} /> Static analysis needs a work product with a structure, such as code or a model. <Cite n={1} />

Static testing finds defects in the earliest phases of the software development life cycle. <Cite n={1} /> It also finds defects that dynamic testing cannot find, such as unreachable code or defects in documents. <Cite n={1} />

Reviews can cost much to run. Still, the total project cost is usually lower with reviews, because late defect fixing takes more time and effort. <Cite n={1} />

The syllabus lists these defect types that are easier or cheaper to find with static testing. <Cite n={1} />

| Area | Example |
|---|---|
| Requirements | Inconsistencies, ambiguities, contradictions, omissions |
| Design | Inefficient database structures, poor modularization |
| Code | Variables with undefined values, unreachable or duplicated code |
| Standards | Names that do not follow the coding standard |
| Interfaces | Parameters with the wrong number, type, or order |
| Security | Specific vulnerabilities such as buffer overflows |
| Test basis | A missing test for an acceptance criterion |

<Callout type="tip" title="Advice (the tutorial's own)">

This advice is the tutorial's own. It is not from ISTQB. When you get a new user story, read it before you write any test. Mark each word that is unclear or that you cannot test.

</Callout>

</Version>

## Dynamic Testing

<Version of="notes">

**Dynamic testing** is performed when the developed software or product is executed and tested by the tester. In this testing, the tester runs the application, gives input, checks output, and verifies whether the system behaves as expected.

2 types of dynamic testing:
1. **Functional testing:** Testing functionality of a feature
2. **Non-Functional testing**: Testing performance, security, UI/UX etc.

<Callout type="warning">

The notes split dynamic testing into two types, but ISTQB does not divide dynamic testing into types. Switch to the ISTQB version at the top of the page to see the ISTQB definition.

</Callout>

</Version>

<Version of="istqb">

Dynamic testing runs the test item. <Cite n={5} /> It causes failures. Analysis of each failure then finds the defect behind it. <Cite n={1} />

Static testing and dynamic testing complement each other. <Cite n={1} /> Some defect types only one of them can find. <Cite n={1} />

| Point | Static testing | Dynamic testing |
|---|---|---|
| How it finds defects | It finds the defect directly. <Cite n={1} /> | It causes a failure. Analysis of the failure shows the defect. <Cite n={1} /> |
| Work products | It works on non-executable work products. <Cite n={1} /> | It works only on executable work products. <Cite n={1} /> |
| Hard-to-reach code | It can find defects on rarely executed paths more easily. <Cite n={1} /> | It reaches such paths less easily. <Cite n={1} /> |
| Quality characteristics | It measures those that do not depend on running code, such as maintainability. <Cite n={1} /> | It measures those that depend on running code, such as performance efficiency. <Cite n={1} /> |

In sequential life cycle models the code comes late. So dynamic testing usually cannot start early in those models. <Cite n={1} />

Functional testing is one of the four test types. It checks the functions that the component or system must have. The functions describe what the test object should do. <Cite n={1} /> The glossary calls it a test type that determines the functional suitability of a test object. <Cite n={6} />

The main objective of functional testing is to check functional completeness, functional correctness, and functional appropriateness. <Cite n={1} /> All four test types can be applied at all test levels. <Cite n={1} />

</Version>

## Smoke, Sanity and Feature Testing

<Version of="notes">

**Functional Testing**

**1. Feature Testing**

**Explanation:** Feature testing verifies whether a specific feature works according to its requirements.

**Example:** For a login feature, test whether users can log in with valid credentials. Also test invalid password, empty fields, and proper error messages.

**2. Sanity Testing**

**Explanation:** Sanity testing is a quick check to verify whether a specific bug fix or small change works properly.

**Example:** If a login bug is fixed, test only the login flow quickly. No need to test the full application unless the fix affects other areas.

**3. Smoke Testing**

**Explanation:** Smoke testing checks whether the basic and critical functionalities of the application are working.

**Example:** After a new build, test login, dashboard loading, user creation, and logout. If any critical flow fails, the build is rejected for detailed testing.

</Version>

<Version of="istqb">

**Smoke testing.** The glossary defines smoke testing as a test type. Smoke testing gives enough confidence that a test object is ready for planned testing. <Cite n={7} /> The syllabus uses only the form "smoke tests". It gives "all smoke tests have passed" as an example of an entry criterion. <Cite n={1} /> It also places smoke tests in quadrant Q4, with the technology-facing tests that critique the product. <Cite n={1} />

**Sanity testing.** The ISTQB syllabus and glossary do not define this term.

In this tutorial's view, the nearest ISTQB term is confirmation testing. The glossary defines it as change-related testing after a defect fix. It confirms that the failure caused by that defect does not occur again. <Cite n={8} />

<Callout type="note" title="The tutorial's own explanation">

Teams often use "sanity testing" for a quick check that one bug fix or one small change works. Agree on the meaning with your team before you use the name.

</Callout>

**Feature testing.** The glossary has an entry with this name, but it has a different meaning. It is a test type that finds out whether the training data of an AI model has a suitable set of features. <Cite n={9} />

The syllabus does not use the term "feature testing". <Cite n={1} /> In this tutorial's view, the nearest ISTQB term for checking a feature against its requirements is functional testing. <Cite n={6} />

<Callout type="note" title="The tutorial's own explanation">

In most teams, "feature testing" means this: check one feature against its requirements, including valid and invalid input and error messages. In ISTQB words, this is functional testing of one feature.

</Callout>

| Name | ISTQB status | Nearest ISTQB term (the tutorial's view) |
|---|---|---|
| Smoke testing | Defined in the glossary. <Cite n={7} /> | Smoke testing itself |
| Sanity testing | Not defined | Confirmation testing <Cite n={8} /> |
| Feature testing | Defined in the glossary with an AI meaning only. <Cite n={9} /> | Functional testing <Cite n={6} /> |

</Version>

## Regression Testing

<Version of="notes">

**4. Regression Testing**

**Explanation:** Regression testing ensures that new changes did not break existing working features.

**Example:** After adding a payment feature, test existing login, registration, product search, and checkout flows. This confirms old features still work after the new update.

</Version>

<Version of="istqb">

Regression testing confirms that a change has caused no adverse consequences. This includes a fix that already passed confirmation testing. <Cite n={1} /> The glossary defines it as change-related testing. It detects whether defects were introduced or uncovered in unchanged areas of the software. <Cite n={10} />

The adverse consequences can affect the changed component, other components in the system, or other connected systems. <Cite n={1} /> Regression testing can also relate to the environment. <Cite n={1} />

Do an impact analysis first. It shows which parts of the software the change could affect. This sets the extent of the regression testing. <Cite n={1} />

Regression test suites run many times, and they usually grow with each iteration or release. <Cite n={1} /> This makes regression testing a good candidate for automation. <Cite n={1} /> Where a team uses CI, it is good practice to include automated regression tests. <Cite n={1} />

Teams need confirmation testing, regression testing, or both on all test levels when they fix defects or make changes. <Cite n={1} />

| Point | Confirmation testing | Regression testing |
|---|---|---|
| Question | Is the original defect fixed? <Cite n={1} /> | Did the change cause any adverse consequence? <Cite n={1} /> |
| Typical tests | The tests that failed because of the defect, or new tests that cover the fix <Cite n={1} /> | The regression suite, sized by the impact analysis <Cite n={1} /> |
| Scope | The fixed defect <Cite n={1} /> | The same component, other components, and connected systems <Cite n={1} /> |

Maintenance testing also covers regression. After a change to an operational system, testers check the change and look for regressions in the parts that did not change. Most of the system is usually in this group. <Cite n={1} />

</Version>

## Exploratory and Ad-hoc Testing

<Version of="notes">

**5. Exploratory Testing**

**Explanation:** Exploratory testing is an experience-based testing approach where testers learn, design, and execute tests at the same time.

**Example:** A tester explores an e-commerce checkout flow without predefined test cases. During exploration, the tester may find hidden bugs in coupon, payment, address, or order confirmation flows.

**6. Ad-hoc Testing**

**Explanation:** Ad-hoc testing is informal testing done without a planned test case or structured approach.

**Example:** A tester randomly checks a form by entering unusual values. The goal is to quickly find defects using intuition and experience.

</Version>

<Version of="istqb">

In exploratory testing, the tester designs, executes, and evaluates tests at the same time, while learning about the test object. <Cite n={1} /> The glossary defines it as a test approach. The tester designs and runs tests from knowledge, exploration of the test item, and earlier test results. <Cite n={11} />

Exploratory testing has three uses. <Cite n={1} />

- Learn more about the test object.
- Explore the test object more deeply with focused tests.
- Create tests for untested areas.

Exploratory testing is useful when the specifications are few or poor, or when time is short. <Cite n={1} /> It also complements more formal test techniques. <Cite n={1} /> It works better when the tester has experience and domain knowledge. <Cite n={1} /> The tester can use other techniques inside it, such as equivalence partitioning. <Cite n={1} />

Session-based testing gives exploratory testing a structure. <Cite n={1} /> The tester works in a defined time box and uses a test charter with test objectives. A debriefing usually follows the session. <Cite n={1} />

The glossary defines ad hoc testing as informal testing that is done without test analysis and test design. <Cite n={12} /> The syllabus does not use the term "ad hoc testing". <Cite n={1} />

| Point | Exploratory testing | Ad hoc testing |
|---|---|---|
| Test design | The tester designs tests during the session, while learning. <Cite n={1} /> | None. The testing has no test analysis and no test design. <Cite n={12} /> |
| Structure | It can use time boxes, charters, and debriefings. <Cite n={1} /> | It is informal. <Cite n={12} /> |

</Version>

## Monkey and Gorilla Testing

<Version of="notes">

**7. Monkey Testing / Random Testing**

**Explanation:** Monkey testing is random testing where the tester gives random inputs or performs random actions to check system stability.

**Example:** A tester randomly clicks buttons, enters random text, and navigates pages quickly. This helps identify crashes, unexpected errors, or broken UI behavior.

**8. Gorilla Testing**

**Explanation:** Gorilla testing deeply tests one specific module or feature again and again with many scenarios.

**Example:** A tester repeatedly tests only the payment module with valid cards, invalid cards, expired cards, failed payments, and network issues. The goal is to make that single module highly stable.

</Version>

<Version of="istqb">

**Monkey testing.** The ISTQB syllabus and glossary do not define this term.

The glossary has a related term, random testing. It is a black-box test technique in which input values are randomly generated. <Cite n={13} />

<Callout type="note" title="The tutorial's own explanation">

Teams use "monkey testing" for random inputs or random actions, to look for crashes and unexpected errors. Random input can find failures that a planned test misses. It does not check that the system gives the correct result. In ISTQB random testing, the input values are randomly generated.

</Callout>

**Gorilla testing.** The ISTQB syllabus and glossary do not define this term.

<Callout type="note" title="The tutorial's own explanation">

Teams use "gorilla testing" for testing one module or feature many times with many scenarios, so that this one part becomes very stable. The meaning is not the same in every team. Agree on it before you use the name.

</Callout>

</Version>

## Alpha, Beta and A/B Testing

<Version of="notes">

**9. Alpha Testing**

**Explanation:** Alpha testing is internal testing performed before releasing the product to real external users.

**Example:** The company's QA team and internal employees test a new LMS system before public launch. They report bugs, usability issues, and missing requirements.

<Callout type="warning">

The notes list alpha and beta testing under functional testing, but the syllabus names them as forms of acceptance testing, which is a test level. Switch to the ISTQB version at the top of the page to see the ISTQB definition.

</Callout>

<Callout type="warning">

The notes say the company's QA team tests in alpha testing, but ISTQB says alpha testing is done by roles outside the development organization. Switch to the ISTQB version at the top of the page to see the ISTQB definition.

</Callout>

**10. Beta Testing**

**Explanation:** Beta testing is performed by selected real users before the final public release.

**Example:** A course platform is released to 100 selected students before launching for everyone. Their feedback helps identify real-world issues, usability problems, and performance gaps.

**11. A/B Testing**

**Explanation:** A/B testing compares two different versions of a feature or design to see which performs better.

**Example:** Version A has a blue "Enroll Now" button, and Version B has a green "Join Now" button. The team measures which version gets more clicks or conversions.

</Version>

<Version of="istqb">

Alpha testing and beta testing are forms of acceptance testing. <Cite n={1} /> The other main forms are user acceptance testing, operational acceptance testing, contractual acceptance testing, and regulatory acceptance testing. <Cite n={1} />

Acceptance testing focuses on validation and on showing readiness for deployment. <Cite n={1} /> Ideally, the intended users do it. <Cite n={1} />

| Form | Where it happens | Who tests |
|---|---|---|
| Alpha testing | In the test environment of the developer <Cite n={14} /> | Roles outside the development organization <Cite n={14} /> |
| Beta testing | At an external site, not in the test environment of the developer <Cite n={15} /> | Roles outside the development organization <Cite n={15} /> |

A/B testing is a different idea. The glossary defines it as a test approach. Two variants of a test object are evaluated statistically. The result shows which variant performs better for the chosen characteristics. <Cite n={16} /> The syllabus does not mention A/B testing. <Cite n={1} />

<Callout type="tip" title="Example (the tutorial's own)">

This example is the tutorial's own. It is not from ISTQB. A shop has two versions of a sign-up button. The system shows version A to half of the visitors and version B to the other half. The team compares the sign-up rate of the two groups.

</Callout>

</Version>

## Non-Functional Testing

<Version of="notes">

**1. Performance Testing**

Performance testing checks how fast, stable, and scalable the system is under different user loads.

**Example:** For an e-commerce website, test whether 1,000 users can browse products and place orders at the same time without slow response or server crash.

**2. Security Testing**

Security testing checks whether the system is protected from unauthorized access, data leaks, and common attacks.

**Example:** For a login API, test whether users can access another user's profile by changing the user ID in the request URL or token.

**3. Usability Testing**

**Clarification:** Usability testing checks whether the application is easy, clear, and comfortable for real users to use.

For a registration form, check whether users can easily understand required fields, validation messages, and the final submit process.

**4. Cross Browser / Device Testing**

**Clarification:** Cross browser and device testing checks whether the application works correctly across different browsers, screen sizes, and devices.

Test the same checkout page on Chrome, Firefox, Safari, Android mobile, iPhone, tablet, and desktop to ensure layout and functionality remain consistent.

**5. Benchmark Testing**

Benchmark testing compares the system's performance against a standard, previous version, competitor product, or expected target.

**Example:** If the current login API response time is 800ms, benchmark testing may check whether the optimized version improves it to the target response time of 300ms.

</Version>

<Version of="istqb">

Non-functional testing evaluates attributes other than the functions of a component or system. It tests how well the system behaves. <Cite n={1} /> The glossary defines it as a test type that checks compliance with non-functional requirements. <Cite n={17} />

The ISO/IEC 25010 standard classifies the non-functional quality characteristics. The syllabus lists eight. <Cite n={1} />

- Performance efficiency
- Compatibility
- Usability (also called interaction capability)
- Reliability
- Security
- Maintainability
- Portability (also called flexibility)
- Safety

Non-functional testing sometimes starts early in the life cycle, for example in reviews or component testing. <Cite n={1} /> Many non-functional tests reuse functional tests. They check a constraint while the function runs, such as the time that the function takes. <Cite n={1} /> Late discovery of non-functional defects can be a serious threat to a project. <Cite n={1} /> Some tests need a special environment, such as a usability lab. <Cite n={1} />

The table links each topic of the notes to ISTQB.

| Topic in the notes | ISTQB |
|---|---|
| Performance testing | The glossary defines it as a test type that determines the performance efficiency of a component or system. <Cite n={18} /> |
| Security testing | The glossary defines it as a test type that determines the security of a component or system. <Cite n={19} /> |
| Usability testing | The glossary defines it as testing that evaluates how well specified users can use the system, with effectiveness, efficiency, and satisfaction. <Cite n={20} /> |
| Cross-browser testing | The glossary defines cross-browser compatibility as how well a web application works across different browsers. <Cite n={21} /> |
| Cross-device testing | The glossary defines it as a test type that finds out whether a component or system performs correctly across its intended devices. <Cite n={22} /> |
| Benchmark testing | Not defined |

**Benchmark testing.** The ISTQB syllabus and glossary do not define this term.

<Callout type="note" title="The tutorial's own explanation">

Teams use "benchmark testing" to compare the performance of a system with a standard, an earlier version, a competitor, or a target. It is close to performance testing. Teams often call cross-browser and cross-device testing compatibility testing. In ISO/IEC 25010 terms, they can also touch portability.

</Callout>

</Version>
