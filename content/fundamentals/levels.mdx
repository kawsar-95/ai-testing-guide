# Test Levels, Pyramid and Quadrants

The test levels, and two models that help you balance them.

<PageMeta />

## Test Levels

<Version of="notes">

**Test level** means a specific stage of testing in the software development life cycle where testing is performed with a specific objective. They are connected to other activities in the software development life cycle (SDLC).

There are mainly 4 types of Test level that are:

<MdxImage src="/images/fundamentals/test-levels.png" alt="Four stacked bars, from the bottom up: Unit Testing, Integration Testing, System Testing, Acceptance Testing" />

1. Unit/Component testing
2. Integration Testing
3. System Testing
4. Acceptance Testing

<Callout type="warning">

The notes list four test levels, but the ISTQB syllabus describes five, because it splits integration testing into component integration testing and system integration testing. Switch to the ISTQB version at the top of the page to see the ISTQB definition.

</Callout>

</Version>

<Version of="istqb">

The ISTQB syllabus describes five test levels <Cite n={1} />. Each level is one instance of the test process. It runs at a given phase of development, from single components to complete systems <Cite n={1} />. The glossary gives the same idea: a test level is a specific instantiation of a test process <Cite n={2} />.

<TestLevelsDiagram />

| Level | Focus |
|---|---|
| Component testing | Components in isolation. Another name is unit testing. <Cite n={1} /> |
| Component integration testing | The interfaces and interactions between components. <Cite n={1} /> |
| System testing | The overall behavior and capabilities of a whole system or product. <Cite n={1} /> |
| System integration testing | Interfaces between the system under test and outside systems or services. <Cite n={1} /> |
| Acceptance testing | Validation, and proof that the system is ready for deployment. <Cite n={1} /> |

**How to tell the levels apart**

The syllabus names these attributes, and says the list is not complete. They keep the test activities of two levels from overlapping <Cite n={1} />.

- The test object
- The test objectives
- The test basis
- The defects and failures
- The approach and the responsibilities

**Why the levels matter**

Each level has its own test objectives. This lets the team test as fully as needed and avoid repeated tests <Cite n={1} />. Test types are not tied to one level. You can apply functional, non-functional, black-box, and white-box testing at every level. The focus differs at each level <Cite n={1} />.

**Levels and time**

In a sequential life cycle model, the exit criteria of one level are often part of the entry criteria of the next level. In some iterative models this does not apply. Levels can overlap in time <Cite n={1} />.

<Callout type="tip" title="The tutorial's own advice">

When you find a failure, note the level where you found it. Then ask whether a lower level could have found the defect earlier. This advice is the tutorial's own. It is not from the syllabus.

</Callout>

</Version>

## Component Testing

<Version of="notes">

**Component Testing: This level of testing focuses on evaluating individual components or units of a software system to ensure they work correctly in isolation.**

</Version>

<Version of="istqb">

Component testing focuses on components in isolation. Its other name is unit testing <Cite n={1} />. It often needs extra help, for example a test harness or a unit test framework <Cite n={1} />. Developers normally run it in their own development environments <Cite n={1} />.

The glossary defines the two terms with a small difference. Component testing is a test level for individual hardware or software components <Cite n={3} />. Unit testing is a test level for the smallest part of code that you can test in isolation <Cite n={4} />.

Component testing can also check non-functional quality. For example, a team can start non-functional testing early, as part of component testing <Cite n={1} />. In the test quadrants, component tests belong to Q1. They should be automated and run in the CI process <Cite n={1} />.

</Version>

## Integration Testing

<Version of="notes">

Integration testing has been divided into 2 types:

<MdxImage src="/images/fundamentals/test-levels-integration.png" alt="Five stacked shapes, from the bottom up: Component Testing, Component Integration Testing, System Testing, System Integration Testing, Acceptance Testing" />

1. Component Integration Testing
2. System Integration Testing

**Component Integration Testing: It involves testing the interactions and interfaces between different components to ensure they integrate seamlessly.**

**System Integration Testing: It's the testing of interactions and interfaces between different systems or modules to ensure that the overall system functions as expected.**

<Callout type="warning">

The notes say system integration testing covers "modules", but the ISTQB syllabus says it focuses on the interfaces with other systems and external services, and the ISTQB glossary makes module integration testing a synonym of component integration testing. Switch to the ISTQB version at the top of the page to see the ISTQB definition.

</Callout>

</Version>

<Version of="istqb">

The glossary defines integration testing as a test level that focuses on interactions between components or systems <Cite n={5} />. The syllabus splits this work into two levels <Cite n={1} />.

| | Component integration testing | System integration testing |
|---|---|---|
| What it tests | The interfaces and interactions between components <Cite n={1} /> | Interfaces between the system under test and outside systems or services <Cite n={1} /> |
| Glossary meaning | The integration testing of components <Cite n={6} /> | A test level for the integration of systems <Cite n={7} /> |
| Main dependency | The integration strategy: bottom-up, top-down, or big-bang <Cite n={1} /> | A test environment that is close to the operational environment <Cite n={1} /> |

Component integration testing is also called unit integration testing <Cite n={1} />. The glossary lists module integration testing as a synonym <Cite n={6} />. Component integration tests belong to Q1 of the test quadrants <Cite n={1} />.

<Callout type="note" title="The tutorial's own explanation">

The syllabus names the three integration strategies but does not explain them here. In a bottom-up strategy, you integrate the lowest components first. In a top-down strategy, you start from the top and replace missing lower parts with stubs. In big-bang, you join all components at once. This explanation is the tutorial's own, and it is not cited.

</Callout>

</Version>

## System Testing

<Version of="notes">

**System Testing: This level of testing evaluates the entire software system as a whole to verify that it meets its specified requirements and functions correctly.**

</Version>

<Version of="istqb">

System testing looks at how a complete system or product behaves and what it can do <Cite n={1} />. The glossary says it verifies that a system as a whole meets its specified requirements <Cite n={8} />.

- It often includes functional tests of end-to-end tasks <Cite n={1} />.
- It often includes non-functional tests of quality characteristics <Cite n={1} />.
- An independent test team may run it <Cite n={1} />.
- It relates to the specifications of the system <Cite n={1} />.

Some non-functional characteristics, such as usability, are best tested on a full system, in a test environment that represents real use. You can also use simulations of subsystems <Cite n={1} />.

</Version>

## Acceptance Testing

<Version of="notes">

**Acceptance Testing: This is the final testing phase where the software is tested by stakeholder to ensure that it meets the business or end-users' requirements and is ready for deployment.**

</Version>

<Version of="istqb">

Acceptance testing focuses on validation and on showing that the system is ready for deployment. This means the system fulfills the business needs of the user. Ideally the intended users run it <Cite n={1} />. The glossary says it determines whether to accept the system <Cite n={9} />.

The syllabus lists six main forms of acceptance testing <Cite n={1} />.

| Form | Meaning |
|---|---|
| User acceptance testing (UAT) | Determines if the intended users accept the system <Cite n={10} /> |
| Operational acceptance testing | Determines whether the organization that operates the system can accept it <Cite n={11} /> |
| Contractual acceptance testing | Named in the syllabus <Cite n={1} />. The glossary has no entry for this form. |
| Regulatory acceptance testing | Determines the compliance of a test object <Cite n={12} /> |
| Alpha testing | Acceptance testing in the developer's test environment, by roles outside the development organization <Cite n={13} /> |
| Beta testing | Acceptance testing at an external site, by roles outside the development organization <Cite n={14} /> |

In the test quadrants, user acceptance testing belongs to Q3 <Cite n={1} />.

</Version>

## The Test Pyramid

<Version of="notes">

The test pyramid is a model that helps with test automation and allocation of testing efforts. It shows that there are different types of tests with varying levels of granularity.

<MdxImage src="/images/fundamentals/test-pyramid.png" alt="A pyramid with three layers, from the bottom up: Unit, Integration, End to end" />

1. The bottom layer consists of small, isolated, and fast tests that check specific functionality. You need many of these tests for good coverage.
2. The top layer includes high-level, end-to-end tests that are slower and cover larger functionality. The higher the layer, the broader and more complex the tests.
3. There are variations in the number and names of layers in different models. For instance, one model has three layers: **unit tests, service tests, and UI tests.**
4. Another model uses **unit tests, integration tests, and end-to-end tests**. Other testing levels can also be employed.

</Version>

<Version of="istqb">

The test pyramid is a model that shows that tests have different granularity. It helps the team with test automation and with test effort allocation <Cite n={1} />. The glossary describes it as a model of the amount of testing per level, with more tests at the bottom than at the top <Cite n={15} />.

<TestPyramidDiagram />

Each layer is a group of tests. A test in a higher layer has a lower granularity and less isolation. It also takes longer to run <Cite n={1} />.

| Layer | Tests | How many |
|---|---|---|
| Bottom | Small, isolated, and fast. They check a small piece of functionality. | Usually many, to reach reasonable coverage <Cite n={1} /> |
| Top | Complex, high-level, end-to-end. They are slower and check a large piece of functionality. | Usually only a few <Cite n={1} /> |

The number and the names of the layers can differ. The syllabus gives two examples <Cite n={1} />.

| Model | Layers, bottom to top |
|---|---|
| The original pyramid (2009) | Unit tests, service tests, UI tests |
| A popular variant | Unit (component) tests, integration (component integration) tests, end-to-end tests |

You can also build a pyramid from other test levels <Cite n={1} />.

<Callout type="tip" title="The tutorial's own advice">

Use the pyramid as a check on your automation. If most of your automated tests are at the top, the suite will be slow. Move checks to a lower layer where you can. This advice is the tutorial's own. It is not from the syllabus.

</Callout>

</Version>

## The Test Quadrants

<Version of="notes">

Testing quadrant **group the test levels** with the appropriate test types, activities, test techniques and work products in the Agile software development.

In this model, tests can be **business facing or technology facing**.

Tests can also **support the team** or **critique the product**

<MdxImage src="/images/fundamentals/test-quadrants.png" alt="Four boxes: Technology facing and Business facing on top, Support the team and Critique the product below, with arrows from the top boxes to the lower boxes" />

**The combination of these two viewpoints determines the four quadrants:**

**Quadrant Q1** - *Technology Facing, Support the Team*:
- Contains: Component and component integration tests
- Characteristics: **Automated**, included in CI process

**Quadrant Q2** - *Business Facing, Support the Team*:
- Contains: Functional tests, user story tests, user experience prototypes, API testing
- Characteristics: Checks acceptance criteria, **manual or automated**

**Quadrant Q3** - *Business Facing, Critique the Product*:
- Contains: Exploratory testing, usability testing, user acceptance testing
- Characteristics: User-oriented, **often manual**

**Quadrant Q4** - *Technology Facing, Critique the Product*:
- Contains: Smoke tests, sanity test, regression test, system testing, non-functional tests (excluding usability tests)
- Characteristics: **Often automated**

<Callout type="warning">

The notes put sanity, regression, and system testing in Q4, but the ISTQB syllabus lists only smoke tests there, plus the non-functional tests other than usability tests. Switch to the ISTQB version at the top of the page to see the ISTQB definition.

</Callout>

</Version>

<Version of="istqb">

The syllabus credits the testing quadrants to their original author. They group the test levels with the right work products, test techniques, activities, and test types in Agile development <Cite n={1} />. The glossary calls them a classification model with four quadrants <Cite n={16} />.

The model has two axes <Cite n={1} />.

- A test is business facing or technology facing.
- A test supports the team (it guides the development) or critiques the product (it measures behavior against expectations).

<TestQuadrantsDiagram />

| Quadrant | Viewpoint | Contains | Notes |
|---|---|---|---|
| Q1 | Technology facing, supports the team | Component tests and component integration tests <Cite n={1} /> | Should be automated and run in the CI process |
| Q2 | Business facing, supports the team | API testing, examples, functional tests, simulations, user experience prototypes, user story tests <Cite n={1} /> | Check the acceptance criteria. Manual or automated |
| Q3 | Business facing, critiques the product | Exploratory testing, usability testing, user acceptance testing <Cite n={1} /> | User-oriented. Often manual |
| Q4 | Technology facing, critiques the product | Smoke tests, plus non-functional tests other than usability tests <Cite n={1} /> | Often automated |

**What the model is for**

The model helps test management to see that the SDLC has all the appropriate test types and test levels <Cite n={1} />. It also gives you a way to describe the test types to all stakeholders, such as developers, testers, and business representatives <Cite n={1} />.

**Smoke tests, sanity tests, regression tests, and system testing**

The syllabus puts only smoke tests and non-functional tests in Q4. It does not list sanity tests, regression tests, or system testing there <Cite n={1} />. The glossary defines smoke testing as a test type that gives enough confidence that a test object is ready for planned testing <Cite n={17} />. Sanity testing is not an ISTQB term. The ISTQB syllabus and glossary do not define this term.

<Callout type="note" title="The tutorial's own explanation">

Many teams use "sanity test" for a short check that one change or one fix works. Teams use the name in different ways. This explanation is the tutorial's own, and it is not cited.

</Callout>

</Version>
