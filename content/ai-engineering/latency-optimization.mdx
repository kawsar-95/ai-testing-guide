# Latency Optimization

A user waits for a chatbot the way a customer waits in a shop queue. A long wait with nothing happening feels broken. Latency optimization makes the answer come sooner, or makes the wait feel shorter, without making the answer worse.

<PageMeta />

## In plain words

<Voices>
<Technical>

**Latency** is the time that the model takes to read a prompt and produce an output. A bigger model, a more complex prompt, and the infrastructure behind the API can all make it longer <Cite n={1} />.

Two numbers are common <Cite n={1} />:

- **Baseline latency**: the time to process the prompt and produce the full response.
- **Time to first token (TTFT)**: the time from sending the prompt to the first token of the answer. It matters most with streaming.

The Claude docs advise to make the prompt work well first, and only then reduce latency. If you cut latency too early, you may never see the best quality that the task can reach <Cite n={1} />.

</Technical>

## How it works

<Voices>
<Technical>

### 1. A faster model and fewer output tokens

A smaller, faster model answers sooner. For speed-critical apps, the Claude docs point to Claude Haiku 5.5 <Cite n={1} />. Output length matters more than input length. The OpenAI guide gives a rule of thumb: half the output tokens may give about half the latency, but half the prompt may give only 1–5 % <Cite n={5} />. Ask for a short answer, and set `max_tokens` as a hard limit <Cite n={1} />.

### 2. Streaming

With `"stream": true`, the API sends the answer in pieces as server-sent events <Cite n={3} />. The user sees the output in real time, so the app feels much more responsive <Cite n={1} />.

```python
import anthropic

client = anthropic.Anthropic()  # reads ANTHROPIC_API_KEY

with client.messages.stream(
    model="claude-haiku-5-5",
    max_tokens=512,
    messages=[{"role": "user", "content": "Summarize this bug report: ..."}],
) as stream:
    for text in stream.text_stream:
        print(text, end="", flush=True)
```

### 3. Prompt caching

Prompt caching lets the API reuse a prefix of the prompt that a recent request already processed. This cuts processing time and cost <Cite n={2} />. The prefix covers `tools`, then `system`, then `messages`, up to the block with `cache_control` <Cite n={2} />. By default a cache entry lives 5 minutes, and each use refreshes it <Cite n={2} />. A prompt that is shorter than the minimum for the model (512 tokens for Claude Haiku 5.5) is not cached, and the API returns no error <Cite n={2} />.

### 4. Parallel calls

If two steps do not depend on each other, run them at the same time <Cite n={5} />. The Python SDK has `AsyncAnthropic` for async calls <Cite n={6} />. If the steps must run in order, the OpenAI guide suggests fewer, combined requests, because each request adds a round trip <Cite n={5} />.

### 5. Batching: the opposite trade

The Message Batches API runs many requests in the background at 50 % lower cost. Most batches finish within 1 hour, but a batch can take up to 24 hours <Cite n={4} />. It suits tasks that do not need an immediate response <Cite n={4} />. Use it only for work that can wait, such as a nightly evaluation run <Cite n={4} />.

</Technical>

## A real-life example

<Voices>
<Technical>

An HR policy assistant answers employee questions. Each request sends a 6,000-token policy handbook in the system prompt, then the question. Users wait 9 seconds and see a spinner the whole time.

The team makes three changes:

1. **Streaming.** The answer appears word by word, so the first text shows within about a second <Cite n={3} /><Cite n={5} />.
2. **Caching.** The handbook is the same in every request, so it becomes a cached prefix with `cache_control`. The question stays after it, because a cache hit needs the same prefix <Cite n={2} />.
3. **Parallel work.** The input screen and the main answer start at the same time. If the screen flags the question, the app cancels the answer. The OpenAI guide calls this speculative execution <Cite n={5} />.

The weekly report on all answers moves to the Message Batches API, because nobody waits for it <Cite n={4} />.

</Technical>

## Common mistakes

<Voices>
<Technical>

- **Optimizing before the prompt works.** You may lose quality that you never measured <Cite n={1} />.
- **Shortening the prompt and expecting a big gain.** Output tokens drive most of the latency <Cite n={5} />.
- **Putting changing text before the cached part.** A timestamp or a user name at the start changes the prefix, so the cache never hits <Cite n={2} />.
- **Not checking that caching works.** If `cache_creation_input_tokens` and `cache_read_input_tokens` are both 0, the prompt was not cached <Cite n={2} />.
- **Using `max_tokens` as a style tool.** At the limit, the answer stops mid-sentence or mid-word <Cite n={1} />.
- **Using batches for interactive features.** A batch can take up to 24 hours <Cite n={4} />.

</Technical>
<Layman>

- **Optimizing before the prompt works.** You may lose quality that you never measured <Cite n={1} />.

- **Putting changing text before the cached part.** A timestamp or a user name at the start changes the prefix. So the cache never hits <Cite n={2} />.
- **Not checking that caching works.** Sometimes `cache_creation_input_tokens` and `cache_read_input_tokens` are both 0. Then the prompt was not cached <Cite n={2} />.
- **Using `max_tokens` to control style.** At the limit, the answer stops in the middle of a sentence or a word <Cite n={1} />.
- **Using batches for interactive features.** A batch can take up to 24 hours <Cite n={4} />.

</Layman>
<Bangla>

- **প্রম্পট কাজ করার আগেই অপ্টিমাইজ করা।** আপনি এমন মান হারাতে পারেন যা কখনো মাপেননি <Cite n={1} />।
- **প্রম্পট ছোট করে বড় লাভ আশা করা।** লেটেন্সির বেশিরভাগ আসে আউটপুট টোকেন থেকে <Cite n={5} />।
- **ক্যাশ করা অংশের আগে বদলানো টেক্সট রাখা।** শুরুতে একটা টাইমস্ট্যাম্প বা ইউজারের নাম প্রিফিক্স বদলে দেয়। তাই ক্যাশ কখনো হিট করে না <Cite n={2} />।
- **ক্যাশিং কাজ করছে কি না না দেখা।** কখনো `cache_creation_input_tokens` ও `cache_read_input_tokens` দুটোই 0 হয়। তখন প্রম্পট ক্যাশ হয়নি <Cite n={2} />।
- **স্টাইল নিয়ন্ত্রণে `max_tokens` ব্যবহার করা।** সীমায় পৌঁছালে উত্তর একটা বাক্য বা শব্দের মাঝে থেমে যায় <Cite n={1} />।
- **ইন্টারঅ্যাক্টিভ ফিচারে ব্যাচ ব্যবহার করা।** একটা ব্যাচে 24 ঘণ্টা পর্যন্ত লাগতে পারে <Cite n={4} />।

## What a tester can check

<Voices>
<Technical>

<Callout type="tip" title="Tutorial advice">
These test ideas are the tutorial's own advice.

- **Measure two numbers.** Record time to first token and total time for a fixed set of prompts. Report the median and the slowest 5 %, not only the average.
- **Compare before and after.** Run the same set before and after each latency change. Check that answer quality did not drop.
- **Prove the cache.** Send the same long prompt twice within 5 minutes. Check that the second response shows `cache_read_input_tokens` above 0.
- **Break the stream.** Cut the network in the middle of a streamed answer. Check that the UI shows a clear message and does not keep half an answer as final.
- **Load test.** Send many requests at once. Check that parallel calls do not hit rate limits and turn into slow retries.
</Callout>

</Technical>

These test ideas are the tutorial's own advice.

- **Measure two numbers.** Record the time to the first token and the total time for a fixed set of prompts. Report the median and the slowest 5 %, not only the average.
- **Compare before and after.** Run the same set before and after each latency change. Check that the quality of the answers did not drop.
- **Prove the cache.** Send the same long prompt twice within 5 minutes. Check that the second response shows `cache_read_input_tokens` above 0.
- **Break the stream.** Cut the network in the middle of a streamed answer. Check that the UI shows a clear message. Check that it does not keep half an answer as final.
- **Load test.** Send many requests at once. Check that parallel calls do not hit rate limits and turn into slow retries.

## Key words

| Term | Meaning |
|---|---|
| Latency | How long the model needs to read a prompt and write its output <Cite n={1} /> |
| Time to first token (TTFT) | The time from sending the prompt to the first token of the answer <Cite n={1} /> |
| Streaming | Sending the answer in pieces as server-sent events <Cite n={3} /> |
| Prompt caching | Reusing a prompt prefix that a recent request already processed <Cite n={2} /> |
| Message Batches API | Running many requests in the background at a lower cost <Cite n={4} /> |
| Speculative execution | Starting a later step before an earlier check ends, and cancelling it if the check fails <Cite n={5} /> |
| `AsyncAnthropic` | The async client of the Claude Python SDK <Cite n={6} /> |
