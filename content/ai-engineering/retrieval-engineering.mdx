# Retrieval Engineering

A good test search finds the one bug report you need among 10,000, even when you remember only an error code or a vague description. Retrieval engineering is the work that makes a RAG app find the right chunks: it mixes keyword and meaning search, sorts the results again, and filters out what the user must not see.

<PageMeta />

## In plain words

<Voices>
<Technical>

In a RAG app, the model can answer only from the chunks that **retrieval** gives it. If the right chunk is not found, the answer is wrong or empty, even with a strong model.

Two kinds of search find different things:

- **Embedding (vector) search** finds chunks with a similar meaning, but it can miss exact matches <Cite n={1} />.
- **BM25** is a keyword ranking function. It is good for exact words, such as IDs and technical terms <Cite n={1} />.

Anthropic's example: for the query "Error code TS-999", an embedding search can return pages about error codes in general and skip the page for "TS-999" itself. BM25 searches for that exact string <Cite n={1} />.

Retrieval engineering combines both kinds, reranks the results, and filters them by **metadata**.

</Technical>

## How it works

<Voices>
<Technical>

### Hybrid search and rank fusion

**Hybrid search** runs a vector search and a keyword (BM25) search, then fuses the two result lists <Cite n={3} />. Anthropic's flow: find top chunks with BM25, find top chunks with embeddings, then combine and deduplicate them with rank fusion <Cite n={1} />.

**Reciprocal rank fusion** (RRF) is a common fusion method. It needs no tuning, and the two scores do not need to be related <Cite n={2} />. Each document gets `1 / (k + rank)` from each list it is in, and the sums give the final order <Cite n={2} />. In Elasticsearch, `rank_constant` (the `k`) defaults to 60 <Cite n={2} />.

```python
def rrf(result_lists, k=60):
    scores = {}
    for results in result_lists:
        for rank, doc_id in enumerate(results, start=1):
            scores[doc_id] = scores.get(doc_id, 0.0) + 1.0 / (k + rank)
    return sorted(scores, key=scores.get, reverse=True)

rrf([["a", "b", "c"], ["c", "a", "d"]])  # -> ['a', 'c', 'b', 'd']
```

Some stores let you weight the two sides. In Weaviate, `alpha=1` is pure vector search and `alpha=0` is pure keyword search <Cite n={3} />.

### Reranking

The first search is fast but rough. A **reranker** is a second model that scores each result for relevance to the query and gives back a better order <Cite n={5} />. Anthropic retrieved the top 150 chunks, reranked them, and passed the top 20 to the model <Cite n={1} />. Embeddings, BM25, contextual chunks, and a reranker together cut failed retrievals by 67% in their tests <Cite n={1} />. The cost: reranking adds a step at run time, so it adds latency <Cite n={1} />.

### Metadata filters

A filter limits the search by fields that the embedding cannot express, such as stock, location, or price range <Cite n={4} />. In Qdrant, `must` works like AND, `should` like OR, and `must_not` excludes matches <Cite n={4} />:

```json
{ "filter": { "must": [
  { "key": "country", "match": { "value": "BD" } },
  { "key": "audience", "match": { "value": "staff" } }
] } }
```

Qdrant suggests a payload index on each field that you filter on <Cite n={4} />.

### Other knobs

- **Top-K.** OpenAI file search returns 10 results by default and up to 50 with `max_num_results` <Cite n={6} />. Anthropic found that 20 chunks worked better than 10 or 5 <Cite n={1} />.
- **Score threshold.** A higher `score_threshold` keeps only more relevant chunks, but can drop useful ones <Cite n={6} />.
- **Query rewriting.** With `rewrite_query=true`, OpenAI rewrites the query into a better search form <Cite n={6} />.

</Technical>

## A real-life example

<Voices>
<Technical>

A support chatbot answers questions from the product docs. Users often paste error codes.

1. **Before:** vector search only, top 5. For "What does error E-4012 mean?", the bot returns a general page about error handling. The exact page for E-4012 is at rank 9.
2. **Add BM25 and RRF.** The keyword list has the E-4012 page at rank 1, so the fused list puts it near the top <Cite n={1} /> <Cite n={2} />.
3. **Add a reranker.** The app retrieves 50 chunks, reranks them, and keeps the top 10. Retrieve wide, then rerank, is the two-stage pattern of Pinecone and Anthropic <Cite n={5} /> <Cite n={1} />.
4. **Add a filter.** Each chunk has a `product_version` field. A user on version 3 gets only version 3 chunks <Cite n={4} />.

The team measures each change with a fixed set of 100 questions and the known right chunk for each. Anthropic uses a similar measure: the share of relevant chunks that do not appear in the top 20 <Cite n={1} />.

</Technical>

## Common mistakes

<Voices>
<Technical>

- **Vector search alone for exact terms.** It can miss IDs, codes, and product names <Cite n={1} />.
- **Adding raw scores from two searches.** BM25 and vector search give different kinds of relevance scores. Rank fusion uses the rank, not the raw score, so the two scores do not have to be related <Cite n={2} />.
- **Reranking too many chunks.** More chunks give better quality, but more latency and cost <Cite n={1} />.
- **A score threshold set too high.** It drops useful chunks <Cite n={6} />.
- **Filtering after the search.** Tutorial's own view: if you search first and filter the top 10 later, the right chunk can be lost. Filter inside the search query.
- **Tuning by feel.** Each change should be measured on a fixed question set. Anthropic advises experiments on your own use case <Cite n={1} />.

</Technical>

## What a tester can check

<Voices>
<Technical>

<Callout type="tip" title="Tutorial advice">
These checks are the tutorial's own advice.

- **Build a golden set.** Write 50 to 100 real questions, each with the ID of the chunk that must be found. Run it after every change.
- **Measure recall at K.** For each question, check if the right chunk is in the top K. Report the failure rate, not only a few good examples.
- **Test exact strings.** Ask with error codes, ticket IDs, and product names. Keyword search must find them.
- **Test synonyms.** Ask the same question with other words. Vector search must still find the chunk.
- **Test the filters as access control.** Ask as a user from group A for a chunk of group B. It must never come back, in any position.
- **Time each stage.** Log the time of search, rerank, and generation, so a slow reranker is visible.
</Callout>

</Technical>

এই চেকগুলো টিউটোরিয়ালের নিজের পরামর্শ।

- **একটা গোল্ডেন সেট বানান।** 50 থেকে 100টা আসল প্রশ্ন লিখুন। প্রতিটার জন্য সেই চাংকের ID লিখে রাখুন, যেটা সার্চকে খুঁজে পেতেই হবে। প্রতিটা পরিবর্তনের পর সেটটা চালান।
- **Recall at K মাপুন।** প্রতিটা প্রশ্নে দেখুন সঠিক চাংক সেরা K-তে আছে কি না। ব্যর্থতার হার জানান, শুধু কয়েকটা ভালো উদাহরণ নয়।
- **হুবহু টেক্সট টেস্ট করুন।** এরর কোড, টিকিট ID আর প্রোডাক্টের নাম দিয়ে প্রশ্ন করুন। কিওয়ার্ড সার্চকে এগুলো খুঁজে পেতেই হবে।
- **অন্য শব্দ টেস্ট করুন।** একই প্রশ্ন ভিন্ন শব্দে করুন। ভেক্টর সার্চকে তবুও চাংকটা খুঁজে পেতে হবে।
- **ফিল্টারকে অ্যাক্সেস কন্ট্রোল হিসেবে টেস্ট করুন।** গ্রুপ A-এর ইউজার হিসেবে গ্রুপ B-এর একটা চাংক চান। সেটা কোনো অবস্থানেই ফিরে আসা চলবে না।
- **প্রতিটা ধাপের সময় মাপুন।** সার্চ, রির‍্যাঙ্ক আর উত্তরের সময় লগ করুন। তখন ধীর reranker সহজে চোখে পড়ে।

## Key words

| Term | Meaning |
|---|---|
| BM25 | A keyword ranking function that finds exact word and phrase matches <Cite n={1} /> |
| Hybrid search | A search that fuses vector search results with keyword search results <Cite n={3} /> |
| RRF | Reciprocal rank fusion: each list adds `1 / (k + rank)` to a document's score <Cite n={2} /> |
| Alpha | In Weaviate, the weight between keyword search (0) and vector search (1) <Cite n={3} /> |
| Reranker | A second model that scores the first results against the query and reorders them <Cite n={5} /> |
| Metadata filter | A condition on stored fields that limits which chunks a search can return <Cite n={4} /> |
| Top-K | The number of results that the search returns <Cite n={6} /> |
