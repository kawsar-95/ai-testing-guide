# Vector Databases

A normal database finds rows where a field equals a value. A vector database finds rows that are close in meaning to a question, even when they share no words. It is the search engine behind most RAG systems.

<PageMeta />

## In plain words

<Voices>
<Technical>

An **embedding** is a list of floating-point numbers (a **vector**) that an embedding model makes from a text. The distance between two vectors shows how related the texts are: a small distance means closely related, a large distance means not related <Cite n={1} />. Each vector is a point in a space with many dimensions, and points that are close together have a similar meaning <Cite n={3} />.

A **vector database** stores these vectors, often with an ID and extra data (**metadata**), and finds the stored vectors that are nearest to a query vector. This is called semantic search, nearest neighbor search, or vector search <Cite n={3} />.

You can use a dedicated product, such as Pinecone or Qdrant, or an extension of a normal database, such as pgvector for PostgreSQL <Cite n={2} /> <Cite n={3} /> <Cite n={4} />.

</Technical>

## How it works

<Voices>
<Technical>

### 1. Make embeddings

You send each text to an embedding model. For example, OpenAI's `text-embedding-3-small` returns a vector of 1536 numbers by default <Cite n={1} />. Anthropic does not make its own embedding model; its docs point to other providers, such as Voyage AI <Cite n={7} />.

### 2. Store them

In pgvector, a vector is a column type. The number in brackets is the dimension <Cite n={2} />:

```sql
CREATE EXTENSION vector;
CREATE TABLE chunks (id bigserial PRIMARY KEY, body text, embedding vector(1536));
```

In Qdrant, every vector in one **collection** must have the same dimension and use one distance metric <Cite n={4} />. In Pinecone, a **namespace** is a partition of an index, and each query reads only one namespace <Cite n={3} />.

### 3. Search by distance

| Metric | pgvector operator <Cite n={2} /> |
|---|---|
| L2 (Euclidean) distance | `<->` |
| Negative inner product | `<#>` |
| Cosine distance | `<=>` |

```sql
SELECT id, body FROM chunks ORDER BY embedding <=> '[0.01, -0.02, ...]' LIMIT 5;
```

OpenAI recommends cosine similarity for its embeddings. Its vectors have length 1, so cosine similarity and Euclidean distance give the same order <Cite n={1} />.

### 4. Exact or approximate

Without an index, pgvector does an **exact** nearest neighbor search, with perfect recall <Cite n={2} />. An index makes the search **approximate**: faster, but with some loss of recall, so the results can change after you add it <Cite n={2} />.

**HNSW** is a common index type. It builds a graph with many layers <Cite n={5} /> <Cite n={2} />. In pgvector, a higher `hnsw.ef_search` gives better recall but slower queries <Cite n={2} />. **IVFFlat** splits the vectors into lists. It builds faster and uses less memory than HNSW, but it has a worse speed-recall trade-off <Cite n={2} />.

### 5. Filters

With an approximate index, pgvector applies a `WHERE` filter after the index scan. With the default `ef_search` of 40 and a filter that matches 10% of rows, only about 4 rows come back <Cite n={2} />. Since version 0.8.0, **iterative index scans** read more of the index until enough rows match <Cite n={2} />.

</Technical>

<Bangla>

প্রথমে এমবেডিং বানান। প্রতিটা টেক্সট একটা এমবেডিং মডেলে পাঠান। যেমন OpenAI-এর `text-embedding-3-small` ডিফল্টভাবে ১৫৩৬টা সংখ্যার একটা ভেক্টর দেয় <Cite n={1} />। Anthropic নিজের কোনো এমবেডিং মডেল বানায় না। এর ডক অন্য প্রোভাইডার দেখায়, যেমন Voyage AI <Cite n={7} />।

দ্বিতীয়ত, এগুলো রাখুন। pgvector-এ ভেক্টর একটা কলাম টাইপ, যেমন `vector(1536)`। সংখ্যাটা হলো ডাইমেনশন <Cite n={2} />। Qdrant-এ একটা **collection**-এর প্রতিটা ভেক্টরের ডাইমেনশন একই হতে হবে, আর একটাই দূরত্বের মাপ (metric) ব্যবহার করতে হবে <Cite n={4} />। Pinecone-এ **namespace** হলো একটা ইনডেক্সের একটা ভাগ। প্রতিটা কুয়েরি শুধু একটা namespace পড়ে <Cite n={3} />।

তৃতীয়ত, দূরত্ব দিয়ে সার্চ করুন। pgvector-এর ৩টা মূল অপারেটর আছে <Cite n={2} />। `<->` হলো L2 (সরল রেখার) দূরত্ব। `<#>` হলো নেগেটিভ inner product। `<=>` হলো cosine দূরত্ব। কুয়েরি সারিগুলো দূরত্ব অনুযায়ী সাজিয়ে প্রথম ৫টা নেয়। Technical লেখায় SQL আছে।

OpenAI তার এমবেডিং-এর জন্য cosine similarity-র পরামর্শ দেয়। এর ভেক্টরের দৈর্ঘ্য ১। তাই cosine similarity আর সরল রেখার দূরত্ব একই ক্রম দেয় <Cite n={1} />।

চতুর্থত, exact নাকি approximate সার্চ, তা বাছুন। ইনডেক্স ছাড়া pgvector প্রতিটা সারি দেখে। এটা **exact** সার্চ, আর এটা প্রতিটা আসল মিল খুঁজে পায় <Cite n={2} />। একটা ইনডেক্স সার্চকে **approximate** করে। এটা দ্রুত, কিন্তু কিছু মিল বাদ পড়তে পারে। তাই ইনডেক্স যোগ করার পর ফল বদলাতে পারে <Cite n={2} />।

**HNSW** একটা প্রচলিত ইনডেক্স টাইপ। এটা অনেক স্তরের একটা গ্রাফ বানায় <Cite n={5} /> <Cite n={2} />। pgvector-এ `hnsw.ef_search` বেশি দিলে বেশি আসল মিল পাওয়া যায়, কিন্তু কুয়েরি ধীর হয় <Cite n={2} />। **IVFFlat** ভেক্টরগুলোকে কয়েকটা তালিকায় ভাগ করে। HNSW-এর চেয়ে এটা দ্রুত তৈরি হয় আর কম মেমরি নেয়। কিন্তু গতি আর মিলের ভারসাম্যে এটা দুর্বল <Cite n={2} />।

শেষে, ফিল্টার। approximate ইনডেক্সে pgvector ইনডেক্স সার্চের পরে `WHERE` ফিল্টার বসায়। ডিফল্ট `ef_search` ৪০ আর একটা ফিল্টার যা ১০% সারির সাথে মেলে, ধরুন। তাহলে গড়ে মাত্র ৪টা সারি ফেরত আসে <Cite n={2} />। ভার্সন 0.8.0 থেকে **iterative index scans** যথেষ্ট সারি না মেলা পর্যন্ত ইনডেক্সের আরও অংশ পড়ে <Cite n={2} />।

## A real-life example

<Voices>
<Technical>

A support team stores 200,000 help-center chunks in PostgreSQL with pgvector, so the vectors live next to the rest of the app data <Cite n={2} />. Each row also has a `product` column.

With no index, a search takes 2 seconds. The team adds an HNSW index, and the search takes 30 ms. Two problems show up in testing:

1. **Different results.** Some queries now return a slightly different top 5. This is expected: the index makes the search approximate and trades recall for speed <Cite n={2} />. The team measures recall against exact search on 100 test queries and raises `hnsw.ef_search` until recall is good enough <Cite n={2} />.
2. **Too few results.** A query filtered to one small product returns only 1 or 2 rows, not 5. The filter runs after the index scan <Cite n={2} />. The team turns on iterative index scans <Cite n={2} />.

They also learn that the customers of different companies must never share one search space. They split the data, as OWASP recommends for shared vector stores <Cite n={6} />.

</Technical>

একটা সাপোর্ট টিম pgvector দিয়ে PostgreSQL-এ হেল্প সেন্টারের ২,০০,০০০টা চাঙ্ক রাখে। তাই ভেক্টরগুলো অ্যাপের বাকি ডেটার পাশেই থাকে <Cite n={2} />। প্রতিটা সারিতে একটা `product` কলামও আছে।

ইনডেক্স ছাড়া একটা সার্চে ২ সেকেন্ড লাগে। টিম একটা HNSW ইনডেক্স যোগ করে। এখন সার্চে ৩০ ms লাগে। টেস্টে ২টা সমস্যা ধরা পড়ে:

1. **ভিন্ন ফল।** কিছু কুয়েরি এখন একটু ভিন্ন প্রথম ৫টা ফল দেয়। এটা প্রত্যাশিত। ইনডেক্স সার্চকে approximate করে। গতির জন্য কিছু মিল ছেড়ে দেয় <Cite n={2} />। টিম ১০০টা টেস্ট কুয়েরিতে exact সার্চের সাথে ফল তুলনা করে। ফল যথেষ্ট ভালো না হওয়া পর্যন্ত তারা `hnsw.ef_search` বাড়ায় <Cite n={2} />।
2. **খুব কম ফল।** একটা ছোট প্রোডাক্টে ফিল্টার করা কুয়েরি ৫টার বদলে মাত্র ১ বা ২টা সারি দেয়। ফিল্টার চলে ইনডেক্স সার্চের পরে <Cite n={2} />। টিম iterative index scans চালু করে <Cite n={2} />।

তারা এটাও শেখে যে আলাদা কোম্পানির কাস্টমাররা কখনো একটা সার্চের জায়গা শেয়ার করবেন না। শেয়ার্ড ভেক্টর স্টোরের জন্য OWASP যেমন বলে, তারা ডেটা ভাগ করে রাখে <Cite n={6} />।

## Common mistakes

<Voices>
<Technical>

- **Mixed dimensions or models.** All vectors in one collection must have the same dimension <Cite n={4} />. In the tutorial's own view, the query and the documents must also come from the same embedding model, or the distances mean nothing.
- **Expecting exact results from an approximate index.** Results can change after you add an index <Cite n={2} />.
- **The wrong distance operator.** In pgvector, you add an index for each distance function that you use, such as `vector_cosine_ops` for cosine distance. To use the index, the query must `ORDER BY` a distance operator, not an expression, in ascending order <Cite n={2} />.
- **Filters that return too little.** With an approximate index, a selective filter can leave very few rows <Cite n={2} />.
- **Only semantic search.** Vector search finds similar meaning. For exact product names, IDs, and codes, full-text (BM25) search is often better <Cite n={3} />.
- **No tenant isolation.** If many groups share one vector store, data can leak between them. Use permission-aware stores and strict partitions <Cite n={6} />. A Pinecone namespace is one way to isolate each customer <Cite n={3} />.

</Technical>
<Layman>

- **Mixed dimensions or models.** All vectors in one collection must have the same dimension <Cite n={4} />. In the tutorial's own view, the question and the documents must also come from the same embedding model. If not, the distances mean nothing.
- **Expecting exact results from an approximate index.** Results can change after you add an index <Cite n={2} />.
- **The wrong distance operator.** In pgvector, you add an index for each distance function that you use, such as `vector_cosine_ops` for cosine distance. To use the index, the query must `ORDER BY` a distance operator, not an expression, in ascending order <Cite n={2} />.
- **Filters that return too little.** With an approximate index, a strict filter can leave very few rows <Cite n={2} />.
- **Only meaning-based search.** Vector search finds similar meaning. For exact product names, IDs, and codes, full-text (BM25) search is often better <Cite n={3} />.
- **No customer isolation.** If many groups share one vector store, data can leak between them. Use stores that check permissions, and strict partitions <Cite n={6} />. A Pinecone namespace is one way to keep each customer apart <Cite n={3} />.

</Layman>

- **মেশানো ডাইমেনশন বা মডেল।** একটা collection-এর সব ভেক্টরের ডাইমেনশন একই হতে হবে <Cite n={4} />। টিউটোরিয়ালের নিজের মতে, প্রশ্ন আর ডকুমেন্টও একই এমবেডিং মডেল থেকে আসতে হবে। না হলে দূরত্বের কোনো মানে থাকে না।
- **approximate ইনডেক্স থেকে exact ফল আশা করা।** ইনডেক্স যোগ করার পর ফল বদলাতে পারে <Cite n={2} />।
- **ভুল দূরত্বের অপারেটর।** pgvector-এ আপনি যে প্রতিটা দূরত্বের ফাংশন ব্যবহার করেন, তার জন্য একটা করে ইনডেক্স যোগ করতে হয়, যেমন cosine দূরত্বের জন্য `vector_cosine_ops`। ইনডেক্সটা কাজে লাগাতে কুয়েরিকে একটা দূরত্বের অপারেটর দিয়ে (কোনো expression দিয়ে নয়) ছোট থেকে বড় ক্রমে `ORDER BY` করতে হবে <Cite n={2} />।
- **খুব কম ফল দেওয়া ফিল্টার।** approximate ইনডেক্সে একটা কড়া ফিল্টার খুব কম সারি রাখতে পারে <Cite n={2} />।
- **শুধু অর্থভিত্তিক সার্চ।** ভেক্টর সার্চ কাছাকাছি অর্থ খোঁজে। হুবহু প্রোডাক্টের নাম, ID আর কোডের জন্য full-text (BM25) সার্চ প্রায়ই ভালো <Cite n={3} />।
- **কাস্টমার আলাদা না রাখা।** অনেক গ্রুপ একটা ভেক্টর স্টোর শেয়ার করলে তাদের মধ্যে ডেটা ফাঁস হতে পারে। পারমিশন যাচাই করে এমন স্টোর আর কড়া পার্টিশন ব্যবহার করুন <Cite n={6} />। প্রতিটা কাস্টমারকে আলাদা রাখার একটা উপায় হলো Pinecone namespace <Cite n={3} />।

## What a tester can check

<Voices>
<Technical>

<Callout type="tip" title="Tutorial advice">
These test ideas are the tutorial's own advice.

- **Measure recall.** For 50 to 100 queries, compare the top 10 of the indexed search with the top 10 of an exact search. Track the share that matches.
- **Known neighbors.** Insert a near-copy of a document. A query with that text must return both near the top.
- **Dimension check.** Try to insert a vector with the wrong length. The database must reject it.
- **Filter plus limit.** Filter to a rare value and ask for 10 results. Check that you get 10 when 10 exist.
- **Delete and update.** Delete or change a document. It must not come back in search results.
- **Tenant isolation.** As customer A, search for text that only customer B has. Nothing from B must come back.
- **Load test.** Measure the query time at the expected number of vectors and requests, not on a small test set.
</Callout>

## Key words

| Term | Meaning |
|---|---|
| Embedding | A vector of numbers that a model makes from a text; distance shows relatedness <Cite n={1} /> |
| Vector database | A store that finds the vectors nearest to a query vector <Cite n={3} /> |
| Dimension | The number of values in a vector, for example 1536 <Cite n={1} /> |
| Cosine distance | One of the distance metrics, written `<=>` in pgvector <Cite n={2} /> |
| Exact search | A search that compares every vector, with perfect recall <Cite n={2} /> |
| Approximate search (ANN) | A faster search with an index that can miss some neighbors <Cite n={2} /> |
| HNSW | An index that builds a graph with many layers <Cite n={5} /> |
| Namespace | A partition of a Pinecone index; each query reads one <Cite n={3} /> |
