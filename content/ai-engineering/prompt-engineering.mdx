# Prompt Engineering

A new team member does good work when you tell them the goal, give them the facts, and show them one finished example. A language model is the same. Prompt engineering is the skill of writing that brief well, and then testing it.

<PageMeta />

## In plain words

<Voices>
<Technical>

A **prompt** is the text that you send to a language model: the instructions, the data, and the question. **Prompt engineering** is the work of writing these instructions so that the model gives the output you need, again and again <Cite n={3} />.

Anthropic gives a useful picture: treat the model like a very capable new employee who does not know your rules or your workflow. The more exactly you say what you want, the better the result <Cite n={2} />.

Prompt engineering starts before the first prompt. You need a clear definition of success, a way to test against it, and a first draft to improve <Cite n={1} />. Not every problem is a prompt problem. For example, a different model can sometimes fix latency or cost more easily than a new prompt <Cite n={1} />.

</Technical>

## How it works

<Voices>
<Technical>

### The parts of a good prompt

OpenAI suggests that a developer message often has these parts, usually in this order <Cite n={3} />:

| Part | What it gives the model |
|---|---|
| Identity | The purpose, the style, and the high-level goals |
| Instructions | The rules: what to do and what never to do |
| Examples | Sample inputs with the output you want |
| Context | Extra data the model needs, such as private documents. It is often best near the end. |

### Techniques that help

- **Be clear and direct.** Say the output format and the limits. Use a numbered list when the order of the steps matters <Cite n={2} />. A quick check: give the prompt to a colleague with little context. If the colleague is confused, the model will be too <Cite n={2} />.
- **Give the reason.** An instruction with its reason helps the model aim its answer, and the model can apply the reason to new cases <Cite n={2} />.
- **Show examples.** A prompt with a few examples is a **few-shot** prompt. A prompt with none is a **zero-shot** prompt <Cite n={4} />. Anthropic suggests 3 to 5 examples that are relevant and varied, inside `<example>` tags <Cite n={2} />. Keep the same format in all examples <Cite n={4} />.
- **Mark the parts.** XML tags such as `<instructions>`, `<context>`, and `<input>` keep the parts of a long prompt apart <Cite n={2} />. Markdown headings also work. Pick one style and keep it <Cite n={4} />.
- **Say what to do, not what to avoid.** "Write flowing paragraphs" works better than "Do not use Markdown" <Cite n={2} />.
- **Put long documents first.** For inputs of about 20,000 tokens or more, put the documents near the top and the question at the end <Cite n={2} />.
- **Set a role.** One sentence in the system prompt can set the focus and the tone <Cite n={2} />.

This request sets a role in the `system` field and sends one user message <Cite n={2} />:

```python
import anthropic

client = anthropic.Anthropic()

message = client.messages.create(
    model="claude-opus-5-5",
    max_tokens=1024,
    system="You are a senior QA engineer. You write short, exact test cases.",
    messages=[
        {"role": "user", "content": "<feature>Password reset by email</feature>\nWrite 5 test cases as a Markdown table: ID, Steps, Expected result."}
    ],
)
print(message.content)
```

### Same prompt, different model

Different models, and even different snapshots of one model family, can answer the same prompt in different ways. OpenAI recommends that you pin production apps to a fixed model snapshot, and that you build evals that measure how prompts behave <Cite n={3} />.

</Technical>

<Bangla>

OpenAI বলে, একটা ভালো নির্দেশনা মেসেজে সাধারণত এই ক্রমে ৪টা অংশ থাকে <Cite n={3} />। **Identity** দেয় উদ্দেশ্য, স্টাইল, আর লক্ষ্য। **Instructions** দেয় নিয়ম: কী করতে হবে আর কী কখনো করা যাবে না। **Examples** দেখায় নমুনা ইনপুট আর আপনি যে আউটপুট চান। **Context** দেয় বাড়তি ডেটা, যেমন প্রাইভেট ডকুমেন্ট। এটা প্রায়ই শেষের দিকে রাখা ভালো।

কিছু কৌশল কাজে দেয়:

- **পরিষ্কার ও সরাসরি লিখুন।** ফরম্যাট আর সীমা বলে দিন। ধাপের ক্রম জরুরি হলে নম্বর দেওয়া তালিকা ব্যবহার করুন <Cite n={2} />। একটা পরীক্ষা: কাজটা কম জানে এমন একজন সহকর্মীকে প্রম্পটটা দিন। সে বিভ্রান্ত হলে মডেলও হবে <Cite n={2} />।
- **কারণ বলুন।** একটা নিয়ম কেন আছে তা বলুন। তাহলে মডেল উত্তর ভালোভাবে লক্ষ্যে রাখে, আর কারণটা নতুন ক্ষেত্রেও খাটায় <Cite n={2} />।
- **উদাহরণ দেখান।** কয়েকটা উদাহরণ সহ প্রম্পট হলো **few-shot** প্রম্পট। কোনো উদাহরণ ছাড়া প্রম্পট হলো **zero-shot** প্রম্পট <Cite n={4} />। Anthropic বলে `<example>` ট্যাগের ভেতরে ৩ থেকে ৫টা প্রাসঙ্গিক ও বৈচিত্র্যময় উদাহরণ দিতে <Cite n={2} />। সব উদাহরণে একই ফরম্যাট রাখুন <Cite n={4} />।
- **অংশগুলো চিহ্নিত করুন।** `<instructions>` আর `<context>` এর মতো ট্যাগ লম্বা প্রম্পটের অংশগুলো আলাদা রাখে <Cite n={2} />। Markdown হেডিংও কাজ করে। একটা স্টাইল বেছে নিয়ে সেটাই রাখুন <Cite n={4} />।
- **কী করতে হবে বলুন।** "Do not use Markdown" এর চেয়ে "Write flowing paragraphs" ভালো কাজ করে <Cite n={2} />।
- **লম্বা ডকুমেন্ট আগে দিন।** খুব লম্বা ইনপুটে (প্রায় ২০,০০০ টোকেন বা বেশি) ডকুমেন্ট উপরে আর প্রশ্ন শেষে রাখুন <Cite n={2} />।
- **একটা রোল (role) দিন।** সিস্টেম প্রম্পটে একটা বাক্যই ফোকাস আর টোন ঠিক করতে পারে <Cite n={2} />। Technical লেখার কোড উদাহরণ এটা `system` ফিল্ড দিয়ে করে।

একই প্রম্পটে ভিন্ন মডেল ভিন্নভাবে উত্তর দিতে পারে। একই মডেলের ভিন্ন ভার্সনও এটা করতে পারে। OpenAI দুটো জিনিস বলে। প্রোডাকশন অ্যাপকে একটা নির্দিষ্ট মডেল ভার্সনে পিন (pin) করুন। আপনার প্রম্পট কেমন আচরণ করে তা মাপতে টেস্ট (evals) বানান <Cite n={3} />।

## A real-life example

<Voices>
<Technical>

A QA team builds a small tool that turns a user story into test cases. The first prompt is one line: "Write test cases for this story." The output changes every run: sometimes a list, sometimes a table, sometimes with no negative cases.

The team rewrites the prompt with the parts above <Cite n={3} />:

```text
You are a senior QA engineer for a banking web app.

<instructions>
1. Read the user story in <story>.
2. Write positive, negative, and boundary test cases.
3. Return only a Markdown table with the columns ID, Type, Steps, Expected result.
Testers paste this table into the test management tool, so keep exactly these columns.
</instructions>

<example>
| ID | Type | Steps | Expected result |
|---|---|---|---|
| TC-01 | Negative | Enter an amount of 0 and select Send | The app shows "Enter an amount above 0" |
</example>

<story>
{{USER_STORY}}
</story>
```

The prompt now has a role, numbered steps, the reason for the format, one example, and tags around the data <Cite n={2} />. The team keeps 20 stories with known good outputs, and runs them again after each prompt change. This is the eval that the success criteria need <Cite n={1} />.

</Technical>

A QA team builds a small tool. It turns a user story into test cases. The first prompt is one line: "Write test cases for this story." The output changes on every run. Sometimes it is a list. Sometimes it is a table. Sometimes it has no negative cases.

## Common mistakes

<Voices>
<Technical>

- **A vague task.** "Make a dashboard" gives a basic result. If you want more than the minimum, ask for it in words <Cite n={2} />.
- **Only "do not" rules.** A list of bans tells the model what to avoid, but not what to write. Say the format you want <Cite n={2} />.
- **Examples in different formats.** The model copies the format of the examples, so mixed formats give mixed output <Cite n={4} />.
- **User text mixed with instructions.** Text from a user, a web page, or a file can change the behavior of the model. This is **prompt injection**, and it can be direct (from the user) or indirect (from outside content) <Cite n={5} />. Mark the outside text clearly as untrusted, and check the output format with code <Cite n={5} />. Clear prompts lower the risk, but they do not remove it <Cite n={5} />.
- **No tests after a change.** A new model snapshot can change the behavior of the same prompt <Cite n={3} />. Without evals, you do not see the change.

</Technical>

- **শুধু "করো না" নিয়ম।** নিষেধের তালিকা বলে কী এড়াতে হবে। কী লিখতে হবে তা বলে না। আপনি যে ফরম্যাট চান তা বলুন <Cite n={2} />।
- **ভিন্ন ফরম্যাটের উদাহরণ।** মডেল উদাহরণের ফরম্যাট নকল করে। মেশানো ফরম্যাট মেশানো আউটপুট দেয় <Cite n={4} />।
- **ইউজারের টেক্সট নির্দেশনার সাথে মেশানো।** ইউজার, ওয়েব পেজ, বা ফাইলের টেক্সট মডেলের আচরণ বদলে দিতে পারে। এটা **প্রম্পট ইনজেকশন** (prompt injection)। এটা সরাসরি (ইউজার থেকে) বা পরোক্ষ (বাইরের কনটেন্ট থেকে) হতে পারে <Cite n={5} />। বাইরের টেক্সটকে পরিষ্কারভাবে অবিশ্বস্ত হিসেবে চিহ্নিত করুন। কোড দিয়ে আউটপুট ফরম্যাট চেক করুন <Cite n={5} />। পরিষ্কার প্রম্পট ঝুঁকি কমায়, কিন্তু পুরো দূর করে না <Cite n={5} />।
- **বদলের পর কোনো টেস্ট নেই।** নতুন মডেল ভার্সন একই প্রম্পটের আচরণ বদলে দিতে পারে <Cite n={3} />। টেস্ট না থাকলে আপনি বদলটা দেখতে পান না।

</Bangla>
</Voices>

## What a tester can check

<Voices>
<Technical>

<Callout type="tip" title="Tutorial advice">
These test ideas are the tutorial's own advice.

- **Keep a golden set.** Save 10 to 30 real inputs with outputs that a person approved. Run them after every prompt change and every model change.
- **Run each input more than once.** The same prompt can give different answers. Run each case 3 to 5 times and compare.
- **Check the format with code.** If the prompt asks for a table or JSON, parse it in the test. Do not trust the eye.
- **Try hostile input.** Put "ignore the instructions above" inside the user story or the uploaded file. The output must keep the same role and format.
- **Test the edges.** Send an empty input, a very long input, and an input in another language.
- **Version the prompt.** Keep the prompt in the repo, next to its tests, so a review shows each change.
</Callout>

## Key words

| Term | Meaning |
|---|---|
| Prompt | The text you send to a model: instructions, data, and the question <Cite n={3} /> |
| System prompt | Instructions in a separate field, used for the role and the rules <Cite n={2} /> |
| Few-shot prompt | A prompt with a few examples of input and output <Cite n={4} /> |
| Zero-shot prompt | A prompt with no examples <Cite n={4} /> |
| XML tags | Labels such as `<context>` that mark the parts of a prompt <Cite n={2} /> |
| Prompt injection | Input that changes the behavior of the model in a way you did not intend <Cite n={5} /> |
| Model snapshot | One fixed version of a model, which you can pin <Cite n={3} /> |
