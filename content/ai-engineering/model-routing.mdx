# Model Routing

A hospital does not send every patient to the top surgeon. A nurse looks at each case first and sends it to the right person. Model routing does the same for AI requests: a small rule or a small model looks at each request and picks the model that should answer it.

## In plain words

<Voices>
<Technical>

A provider sells several models. A stronger model costs more, and a cheaper model is less capable <Cite n={4} />. In its 2023 review of commercial LLM APIs such as GPT-4 and ChatGPT, the FrugalGPT paper found fees that differed by up to two orders of magnitude <Cite n={5} />.

The Claude docs name three things to weigh when you pick a model: capability, speed, and cost <Cite n={1} />. **Model routing** makes that choice for each request, not once for the whole app. A **router** sends easy requests to a fast, cheap model and hard requests to a strong model <Cite n={4} />.

Research shows that routing can cut cost. In the 2024 RouteLLM paper, routers that chose between GPT-4 and Mixtral-8x7B cut cost by more than 2 times in some cases on public benchmarks such as MT Bench and MMLU, with no loss in answer quality <Cite n={4} />.

</Technical>

## How it works

<Voices>
<Technical>

### Know the options

The Claude models overview compares the current models <Cite n={2} />:

| Model | API id | Latency (relative) | Price per million tokens (input / output) |
|---|---|---|---|
| Claude Opus 5.5 | `claude-opus-5-5` | Moderate | $4 / $20 |
| Claude Sonnet 5.5 | `claude-sonnet-5-5` | Fast | $2 / $10 |
| Claude Haiku 5.5 | `claude-haiku-5-5` | Fastest | from $0.10 / from $0.50 |

The docs list Haiku 5.5 for the lowest latency and price, for example real-time apps and high-volume work <Cite n={1} />.

### Three ways to route

1. **Rules.** Code looks at the request (its type, its length, the user plan) and picks a model. The router is cheap and easy to test.
2. **A learned router.** A small model predicts which model will answer well. RouteLLM trains such routers on human preference data <Cite n={4} />.
3. **A cascade.** Try the cheap model first. If the answer fails a check, send the request to a stronger model. FrugalGPT is a cascade that learns which models to use for which queries <Cite n={5} />. Anthropic describes a related policy: give each task a first try at a low setting, then repeat only the failed tasks at a higher setting <Cite n={3} />. This works only when you have a reliable failure signal, and each failure costs extra time <Cite n={3} />.

Tutorial's own view: start with rules. Add a learned router only when the rules leave clear savings on the table.

```python
def pick_model(request_type: str, text: str) -> str:
    # Rule-based router: easy, short requests go to the fast model.
    if request_type in {"faq", "classify"} and len(text) < 2000:
        return "claude-haiku-5-5"
    if request_type == "code_review":
        return "claude-opus-5-5"
    return "claude-sonnet-5-5"
```

### Compare the right number

Anthropic advises to compare models on the cost of a completed task, not the cost of a token <Cite n={3} />. A failed task still costs its tokens, then the retry <Cite n={3} />. So a cheap model that fails often can cost more in total.

</Technical>

রাউট করার তিনটা উপায় আছে:

1. **নিয়ম।** কোড রিকুয়েস্ট দেখে: তার ধরন, তার দৈর্ঘ্য, বা ইউজারের প্ল্যান। তারপর একটা মডেল বাছাই করে। এই রাউটার সস্তা এবং টেস্ট করা সহজ।

Technical টেক্সটে একটা ছোট Python উদাহরণ আছে। ছোট FAQ ও classify রিকুয়েস্ট Haiku-তে যায়। কোড রিভিউ Opus-এ যায়। বাকি সব রিকুয়েস্ট Sonnet-এ যায়।

## A real-life example

<Voices>
<Technical>

A support chatbot answers about 50,000 questions a day. At first, every question goes to the strongest model. The team adds a rule router:

- Order status and password-reset questions go to Claude Haiku 5.5. These are high-volume, simple tasks, the use case that the docs give for Haiku <Cite n={1} />.
- Refund disputes and complaints go to Claude Opus 5.5.
- If the Haiku answer fails a check (for example, it does not name an order number), the request goes again to Opus. This is a cascade <Cite n={5} />.

A tester then compares both setups on the same 500 real questions. The team looks at the cost per solved question, not the cost per token <Cite n={3} />.

</Technical>

## Common mistakes

<Voices>
<Technical>

- **Comparing price per token only.** You pay for completed tasks, so compare cost per task <Cite n={3} />.
- **Testing on easy cases only.** Anthropic advises to price models on the 10 % of tasks that are hardest, not on a typical task <Cite n={3} />.
- **A cascade with a weak check.** A checker that passes bad work lets the failures through <Cite n={3} />.
- **Never checking the router again.** Anthropic advises to check a model pairing again at every model release <Cite n={3} />.
- **Choosing without your own data.** The docs say that a good evaluation set, with your real prompts and data, is the most important step <Cite n={1} />.

</Technical>
<Layman>

- **Comparing price per token only.** You pay for finished tasks. So compare the cost for each task <Cite n={3} />.
- **Testing on easy cases only.** Anthropic says to price models on the 10 % of tasks that are hardest. Do not use only a typical task <Cite n={3} />.
- **A cascade with a weak check.** A checker that passes bad work lets the failures through <Cite n={3} />.
- **Never checking the router again.** Anthropic says to check a pair of models again at every new model release <Cite n={3} />.
- **Choosing without your own data.** The docs say that a good test set is the most important step. It uses your real prompts and data <Cite n={1} />.

</Layman>
<Bangla>

- **শুধু প্রতি টোকেনের দাম তুলনা করা।** আপনি শেষ হওয়া কাজের দাম দেন। তাই প্রতিটা কাজের খরচ তুলনা করুন <Cite n={3} />।
- **শুধু সহজ কেসে টেস্ট করা।** Anthropic বলে, আপনার সবচেয়ে কঠিন 10 % কাজে মডেলের দাম তুলনা করুন। শুধু সাধারণ কাজ ব্যবহার করবেন না <Cite n={3} />।
- **দুর্বল চেকসহ ক্যাসকেড।** যে চেকার খারাপ কাজ পাস করায়, সে ব্যর্থতাগুলো ঢুকতে দেয় <Cite n={3} />।
- **রাউটার আর কখনো না দেখা।** Anthropic বলে, প্রতিটা নতুন মডেল রিলিজে মডেলের জোড়া আবার দেখুন <Cite n={3} />।
- **নিজের ডেটা ছাড়া বাছাই করা।** ডকস বলে, একটা ভালো টেস্ট সেট সবচেয়ে জরুরি ধাপ। এতে আপনার আসল প্রম্পট ও ডেটা থাকে <Cite n={1} />।

## What a tester can check

<Voices>
<Technical>

<Callout type="tip" title="Tutorial advice">
These test ideas are the tutorial's own advice.

- **Router unit tests.** For each rule, give one input on each side of the limit (for example 1,999 and 2,001 characters). Check the chosen model.
- **Log the choice.** Check that each request logs the model that answered it, so that you can compare cost and quality later.
- **Same set, two setups.** Run one fixed question set through the router and through the strong model alone. Compare pass rate and cost per solved question.
- **Escalation path.** Force the cheap model to fail the check. Check that the request goes to the strong model and the user gets one answer, not two.
- **Fallback when a model is missing.** Point the router at a model id that does not exist in a test setup. Check that the app gives a clear error.
</Callout>

</Technical>
