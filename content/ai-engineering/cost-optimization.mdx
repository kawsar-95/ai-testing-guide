# Cost Optimization

An AI feature has a meter that runs on every request. A prompt that is a little too long, sent a million times, becomes a large bill. Cost optimization finds the tokens that do no work and stops paying for them, without making the answers worse.

<PageMeta />

## In plain words

<Voices>
<Technical>

The Claude API bills by **tokens**: input tokens that you send, and output tokens that the model writes. Prices are in USD per million tokens (MTok) <Cite n={1} />. Output tokens cost more than input tokens. For Claude Sonnet 5.5, input is $2 / MTok and output is $10 / MTok <Cite n={1} />.

So the cost of one request depends on three things: the model, the number of input tokens, and the number of output tokens. **Cost optimization** works on all three, with these levers:

- a smaller model for simple work,
- prompt caching for text that repeats,
- batches for work that can wait,
- limits on tokens and spend.

Anthropic advises to judge the result by the cost of a completed task, not the price of a token <Cite n={5} />.

</Technical>

- সহজ কাজের জন্য ছোট মডেল,
- বারবার আসা টেক্সটের জন্য প্রম্পট ক্যাশিং,

## How it works

<Voices>
<Technical>

### Prices of the current models

| Model | Input / MTok | Output / MTok | Cache hit / MTok |
|---|---|---|---|
| Claude Opus 5.5 | $4 | $20 | $0.20 |
| Claude Sonnet 5.5 | $2 | $10 | $0.10 |
| Claude Haiku 5.5 (prompt up to 100,000 tokens) | $0.10 | $0.50 | $0.01 |

All prices are from the Claude pricing page <Cite n={1} />. Claude Haiku 5.5 has higher prices for a prompt over 100,000 tokens <Cite n={1} />.

### Lever 1: prompt caching

A cache write costs more than normal input: 1.25 times the base input price for a 5-minute cache, and 2 times for a 1-hour cache <Cite n={2} />. A cache read costs much less: 0.1 times the base input price on most models, and 0.05 times on Claude Opus 5.5 and Claude Sonnet 5.5 <Cite n={2} />. So a long system prompt that every request repeats is the first thing to cache.

### Lever 2: batches

The Batch API gives a 50 % discount on input and output tokens <Cite n={1} />. The work runs asynchronously, so use it only when nobody waits for the answer <Cite n={3} />. The caching multipliers stack with the batch discount <Cite n={2} />.

### Lever 3: count and cap tokens

The token counting endpoint returns the number of input tokens of a message before you send it <Cite n={4} />. Use it to find prompts that grew too large. The API ID of Claude Sonnet 5.5 is `claude-sonnet-5-5` <Cite n={7} />.

```python
import anthropic

client = anthropic.Anthropic()
count = client.messages.count_tokens(
    model="claude-sonnet-5-5",
    system="You write test cases from user stories.",
    messages=[{"role": "user", "content": "Story: a user resets a password."}],
)
print(count.input_tokens)
```

Every tool definition that you attach is input on every turn <Cite n={5} />. `max_tokens` limits the length of one response. The model cannot see it, so a lower value does not make the model save tokens. A cut-off response is still billed <Cite n={5} />.

### Lever 4: spend limits

The Start, Build, and Scale usage tiers each have a monthly spend cap. You can set your own lower limit for the organization <Cite n={6} />. This is the last safety net if a bug sends too many requests.

</Technical>

আপনার যোগ করা প্রতিটা টুলের সংজ্ঞা প্রতিটা টার্নে ইনপুট হিসেবে যায় <Cite n={5} />। `max_tokens` একটা রেসপন্সের দৈর্ঘ্য সীমিত করে। মডেল এটা দেখতে পায় না। তাই কম মান দিলে মডেল কম টোকেন ব্যবহার করে না। কেটে যাওয়া রেসপন্সেরও বিল হয় <Cite n={5} />।

## A real-life example

<Voices>
<Technical>

A team runs a test-case generator on Claude Sonnet 5.5. It gets 10,000 requests a day. Each request has 3,000 input tokens (2,500 of them are the same system prompt) and 500 output tokens. The numbers below are the tutorial's own calculation, with the prices above <Cite n={1} />:

```text
Before:
  input   10,000 x 3,000 = 30 M tokens x $2.00  = $60.00
  output  10,000 x   500 =  5 M tokens x $10.00 = $50.00
  total per day                                 = $110.00

After caching the 2,500-token system prompt (cache hit $0.10 / MTok):
  cached  10,000 x 2,500 = 25 M tokens x $0.10  =  $2.50
  input   10,000 x   500 =  5 M tokens x $2.00  = $10.00
  output  (no change)                           = $50.00
  total per day (plus a few cache writes)       = about $62.50
```

The output is now the largest part of the bill. The team asks for shorter test cases, and moves the nightly regression run of 2,000 stories to the Batch API, at 50 % off <Cite n={1} /><Cite n={3} />.

</Technical>

## Common mistakes

<Voices>
<Technical>

- **Comparing token prices only.** A failed task still bills its tokens and then the retry, so compare cost per completed task <Cite n={5} />.
- **Caching a prompt that is too short.** A prompt below the minimum length for the model is not cached, and the API returns no error <Cite n={2} />.
- **Trusting a low `max_tokens` to save money.** The model does not see the cap, and cut-off answers are still billed <Cite n={5} />.
- **Attaching every tool to every request.** Each definition is input on every turn <Cite n={5} />.
- **No spend limit.** Without your own limit, only the tier cap stops a runaway job <Cite n={6} />.

</Technical>
<Layman>

- **Comparing token prices only.** A failed task still costs its tokens. Then the retry costs more. So compare the cost of each finished task <Cite n={5} />.
- **Caching a prompt that is too short.** A prompt below the minimum length for the model is not cached. The API returns no error <Cite n={2} />.
- **Trusting a low `max_tokens` to save money.** The model does not see the limit. Answers that were cut off are still billed <Cite n={5} />.
- **Attaching every tool to every request.** Each tool definition is input on every turn <Cite n={5} />.
- **No spend limit.** Without your own limit, only the tier cap stops a job that runs out of control <Cite n={6} />.

</Layman>
<Bangla>

- **শুধু টোকেনের দাম তুলনা করা।** একটা ব্যর্থ কাজেও তার টোকেনের বিল হয়। তারপর রিট্রাইয়ের খরচ যোগ হয়। তাই প্রতিটা শেষ হওয়া কাজের খরচ তুলনা করুন <Cite n={5} />।
- **খুব ছোট প্রম্পট ক্যাশ করা।** মডেলের ন্যূনতম দৈর্ঘ্যের চেয়ে ছোট প্রম্পট ক্যাশ হয় না। API কোনো এরর দেয় না <Cite n={2} />।
- **টাকা বাঁচাতে কম `max_tokens`-এ ভরসা করা।** মডেল সীমাটা দেখে না। কেটে যাওয়া উত্তরেরও বিল হয় <Cite n={5} />।
- **প্রতিটা রিকুয়েস্টে সব টুল যোগ করা।** প্রতিটা টুলের সংজ্ঞা প্রতিটা টার্নে ইনপুট হিসেবে যায় <Cite n={5} />।
- **খরচের কোনো সীমা না থাকা।** নিজের সীমা না থাকলে নিয়ন্ত্রণের বাইরে চলে যাওয়া একটা কাজ শুধু tier-এর সীমাই থামায় <Cite n={6} />।

</Bangla>

## What a tester can check

<Voices>
<Technical>

<Callout type="tip" title="Tutorial advice">
These test ideas are the tutorial's own advice.

- **Cost per test run.** Log the `usage` of every call in your AI test suite. Report the cost of each run, and flag a run that costs much more than the last one.
- **Prompt size gate.** In CI, count the tokens of each prompt template. Fail the build when a template grows past an agreed budget.
- **Cache hit rate.** In a staging run, check how many requests show `cache_read_input_tokens` above 0. A low rate means the cached prefix changes between requests.
- **Runaway loop.** Make an agent loop forever in a test setup. Check that a step limit or a spend limit stops it.
- **Same quality, lower cost.** After each cost change, run the evaluation set again. Check that the pass rate did not drop.
</Callout>

</Technical>

- **Cache hit rate.** In a staging run, check how many requests show `cache_read_input_tokens` above 0. A low rate means that the cached prefix changes between requests.
- **A loop that never ends.** In a test setup, make an agent loop forever. Check that a step limit or a spend limit stops it.
- **Same quality, lower cost.** After each cost change, run the evaluation set again. Check that the pass rate did not drop.
