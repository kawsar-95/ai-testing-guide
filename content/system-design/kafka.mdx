# How Apache Kafka Works

Apache Kafka moves data between the programs of a company. One program writes an event, such as "a user paid for an order", and many other programs read it, now or days later. <Cite n={1} /> It is hard to build because Kafka must take in huge amounts of data, keep it in order, never lose it, and keep working when machines fail.

## The problem in plain words

<Voices>
<Technical>

A large company runs hundreds of services. Each service makes data that other services need. LinkedIn had this problem, and it built Kafka in 2010 to solve it. <Cite n={1} /> In 2011, Kafka became open source and went to the Apache Software Foundation. <Cite n={1} />

Without a central system, each pair of services needs its own data pipe, called a pipeline. When the number of services is N, the number of pipes grows like N times N. <Cite n={1} /> Kafka puts one central store in the middle. A writer sends its data to Kafka one time. Each reader takes the data from Kafka when it needs it. <Cite n={1} />

The article quotes an estimate by Confluent: more than 70 % of Fortune 500 companies use Kafka. <Cite n={1} /> Kafka was built for the case where many systems read the same message, so a cluster often reads several times more data than it writes. <Cite n={1} />

## The big picture

<Voices>
<Technical>

```text
[Producer: checkout app] --write--> [Kafka cluster: 3 or more brokers]
                                      topic "payments"
                                        partition 0: leader on broker 1, copies on 2 and 3
                                        partition 1: leader on broker 2, copies on 1 and 3
                                        partition 2: leader on broker 3, copies on 1 and 2
                                          ^
                                          |  choose leaders, watch broker health
                                     [Controllers (KRaft)]

[Kafka cluster] --read--> [Consumer group "fraud-check"]  consumer A, consumer B
[Kafka cluster] --read--> [Consumer group "accounting"]   consumer C
```

A producer writes an event to a topic, and Kafka puts it in one partition. Each partition has copies on three brokers. The controllers watch the brokers and choose a leader for each partition. Each consumer group reads the whole topic, and the members of one group split the partitions between them.

</Technical>

## The log: a notebook you can only add to

<Voices>
<Technical>

Think of a ship's logbook. The crew adds each line at the bottom, never erases a line, and numbers each line.

Kafka is built on the same idea, called a log. A new record goes only at the end. Nobody changes or deletes a single record. <Cite n={1} /> Each record gets a number called an offset. The offset always grows, so it shows the order of the records. <Cite n={1} />

Why this design? A hard disk is fast when it reads or writes one long run of data. It is slow when it must jump to many places. <Cite n={1} /> A log always writes at the end, so the disk works in its fast mode. To add a record takes the same short time, however long the log is, and needs no lock. <Cite n={1} />

A record is a key and a value, plus extra data such as the offset and a timestamp. The key is optional. <Cite n={1} /> Kafka sees the key and the value only as raw bytes, with no type. <Cite n={1} /> The producer turns its objects into bytes, which is called serialization. The consumer does the reverse. <Cite n={1} />

<Callout type="note">

Kafka clients do not use HTTP. They speak Kafka's own protocol over TCP, so you need a Kafka client library, such as the Java producer and consumer classes. <Cite n={1} />

</Callout>

</Technical>

## Topics and partitions: shelves and drawers

<Voices>
<Technical>

Think of a library. Each subject has its own shelf. A very busy shelf is split into several drawers, so several librarians can work on it at the same time.

In Kafka, the shelf is a topic. A topic is a named stream of related records, like a table in a database. A cluster often has hundreds or thousands of topics. <Cite n={1} /> One machine cannot hold or serve a very big topic. So Kafka splits each topic into one or more partitions, and each partition is a separate log. <Cite n={1} /> This kind of split is called sharding.

A Kafka server is a broker, and all the brokers together are a cluster. A normal setup has three brokers or more. <Cite n={1} /> To grow, you add brokers. Each partition is a separate log, so the limit of the scale is the number of brokers that you can add. <Cite n={1} /> The article says that nothing in theory stops a cluster that takes 50 GiB/s of writes from growing to 100 GiB/s. <Cite n={1} />

</Technical>

## Copies, leaders, and controllers

<Voices>
<Technical>

Think of a kitchen. Only the head chef writes in the order book, and two assistants copy it. If the head chef gets sick, the manager names a new one.

Each partition has copies on several brokers. A setting called the replication factor sets the number of copies, and three is the usual value. <Cite n={1} /> Each copy is a replica. With three replicas, one broken disk does not lose data. <Cite n={1} />

One replica is the leader. Only the leader accepts new writes, and the followers copy from it. Reads can come from the leader or from a follower. <Cite n={1} />

Special brokers called controllers choose the leaders. A cluster usually has three controllers, and only one is active at a time. <Cite n={1} /> Every broker sends a heartbeat, a short "I am alive" message, to the active controller. If a broker sends no heartbeat for 6 seconds, the controller fences it, which means it shuts that broker out. The controller then gives that broker's partitions new leaders. <Cite n={1} />

The controllers write each cluster decision to a special log, the `__cluster_metadata` topic. Every broker reads this log and replays it to build the same picture of the cluster. <Cite n={1} /> The controllers elect their own active leader with KRaft, a Kafka version of the Raft voting method. A change is final only when a majority of the controllers have stored it. <Cite n={1} /> Older Kafka versions used a separate system, ZooKeeper, for this job. <Cite n={1} />

</Technical>

Controller নামের বিশেষ broker-গুলো leader বেছে নেয়। একটি cluster-এ সাধারণত তিনটি controller থাকে, এবং একসময়ে শুধু একটি active থাকে। <Cite n={1} /> প্রতিটি broker active controller-কে heartbeat পাঠায়, অর্থাৎ একটি ছোট "আমি সচল আছি" message। কোনো broker 6 সেকেন্ড heartbeat না পাঠালে controller সেটিকে fence করে, অর্থাৎ বাইরে রাখে। তারপর controller সেই broker-এর partition-গুলোর জন্য নতুন leader ঠিক করে। <Cite n={1} />

Controller-গুলো cluster-এর প্রতিটি সিদ্ধান্ত একটি বিশেষ log-এ লেখে, `__cluster_metadata` topic-এ। প্রতিটি broker এই log পড়ে replay করে, যাতে সবাই cluster-এর একই ছবি পায়। <Cite n={1} /> Controller-গুলো KRaft দিয়ে নিজেদের active leader নির্বাচন করে। KRaft হলো Raft voting পদ্ধতির Kafka সংস্করণ। বেশিরভাগ controller কোনো পরিবর্তন store করলে তবেই তা চূড়ান্ত হয়। <Cite n={1} /> পুরোনো Kafka version-এ এই কাজের জন্য ZooKeeper নামের আলাদা system ব্যবহার হতো। <Cite n={1} />

## Consumer groups and offsets: sharing the reading

<Voices>
<Technical>

Think of postal workers who share mail bags. Each worker notes the last letter done, so another worker can continue if one leaves.

A consumer group is a set of consumer programs that work as one team. <Cite n={1} /> Inside a group, only one consumer reads a partition at a time. This keeps the order correct without locks. <Cite n={1} /> Different groups read the same topic separately, each at its own speed. <Cite n={1} />

You can add or remove consumers while the group runs. To read faster, add consumers to the group. To give the same data to a new application, start a new group. <Cite n={1} />

The consumers of a group do not talk to each other. A broker called the group coordinator makes the decisions, and the consumers send it heartbeats. <Cite n={1} /> Each consumer saves its progress, the offset it has read up to, in a special topic called `__consumer_offsets`. This save is called a commit. <Cite n={1} /> If a consumer crashes, it or another consumer starts again from the last commit. <Cite n={1} />

</Technical>

<Bangla>

ডাকের থলে ভাগ করে নেওয়া ডাককর্মীদের কথা ভাবুন। প্রত্যেকে শেষ কোন চিঠির কাজ করেছেন তা লিখে রাখেন, যাতে কেউ চলে গেলে অন্যজন সেখান থেকে চালিয়ে যেতে পারেন।

Consumer group হলো কিছু consumer program-এর একটি দল, যারা এক team হিসেবে কাজ করে। <Cite n={1} /> একটি group-এর ভেতরে একসময়ে শুধু একটি consumer একটি partition পড়ে। এতে lock ছাড়াই ক্রম ঠিক থাকে। <Cite n={1} /> আলাদা group-গুলো একই topic আলাদাভাবে, নিজের গতিতে পড়ে। <Cite n={1} />

## Retention and tiered storage: how long data stays

<Voices>
<Technical>

Think of a security camera that keeps the last 7 days of video, watched or not.

Some other message systems delete a message after a client reads it. Kafka does not. It keeps each message for a fixed time, often 7 days, and then deletes it. <Cite n={1} /> So a team can replay old data, for example after it fixes a bug in a consumer. <Cite n={1} />

Big clusters store a lot. At 1 GB/s of writes, 7 days of retention, and three copies, a cluster holds about 1,772 TB. <Cite n={1} /> Tiered storage solves this. Kafka copies older data to a cloud object store such as Amazon S3. After a set time, for example 12 hours, the brokers delete their local copy. <Cite n={1} /> Consumers still read old data with the same API. The reads are a little slower, because the broker gets the data from S3. <Cite n={1} /> The article says that this makes the storage of large data more than 10 times cheaper. <Cite n={1} />

</Technical>

## Exactly once: no lost and no double messages

<Voices>
<Technical>

Think of a bank that stamps a number on each cheque. If the same cheque comes in twice, the bank pays it only one time.

If a network loses a reply, the producer sends the message again, and that can make a duplicate. Kafka gives each message of a producer a growing number. If the same message comes again, the broker keeps only one copy. <Cite n={1} /> This property is called idempotency: to do an action twice has the same effect as to do it once.

Kafka also has transactions. A producer can write many messages to several topics and partitions. Then all of them are committed, or all of them are aborted. <Cite n={1} /> Consumers can be set to skip the messages of transactions that did not commit. <Cite n={1} /> When the input and the output are both in Kafka, this gives exactly-once processing. <Cite n={1} /> Duplicates can still come from outside systems, for example a web service that crashes after its write and gets a retry. <Cite n={1} />

</Technical>

## Key words

| Word | Plain meaning |
|---|---|
| Event (record, message) | One fact that a program writes, such as "order 42 was paid" |
| Producer | A program that writes events to Kafka |
| Consumer | A program that reads events from Kafka |
| Broker | One Kafka server |
| Topic | A named stream of related events, like a table |
| Partition | One slice of a topic, stored as its own log |
| Offset | The number of an event inside a partition |
| Replica | One copy of a partition on one broker |
| Consumer group | A team of consumers that share the partitions of a topic |
| Retention | How long Kafka keeps events before it deletes them |

## What a tester can learn

<Voices>
<Technical>

<Callout type="tip" title="Tutorial advice">

These ideas are the tutorial's own advice.

- Stop one broker during a test run. Check that producers and consumers continue, and that no event is lost.
- Kill a consumer before it commits its offset. Check that the next consumer processes the events again, and that your code handles the same event twice without harm.
- Send events to one partition and check that they arrive in order. Do not expect one order across different partitions.
- Send a message twice on purpose and check that the downstream result, such as a balance, changes only one time.
- Measure consumer lag, the gap between the newest offset and the committed offset, under peak load.
- Send a message with a broken shape, such as a missing field. Check that the consumer rejects it and does not crash.
</Callout>
