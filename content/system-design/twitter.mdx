# How Twitter Works

When you open Twitter (now X), you see a long list of tweets that loads fast and grows as you scroll. This page covers the part that runs in your browser: the front end of the timeline. The hard part is to keep a huge, always-changing list fast and correct, even on a slow phone or a weak network.

## The big picture

<Voices>
<Technical>

```text
[You] --> [View: timeline page, tweet page, composer]
               ^                    |
     redraw    |                    |  your action (like, post)
               |                    v
          [Store: tweets, users, timeline, kept in memory]
                                    |
                                    v
          [Data access: requests, retries, paging, caching]
                                    |
                                    v  HTTP
          [Server: timeline, tweets, likes, media]
```

The view draws what is in the store. When you act, the store changes first, and the data access layer sends the change to the server. Data that comes back goes through the data access layer into the store, and the view draws again <Cite n={1} />.

## Where the page is built

<Voices>
<Technical>

Think of a restaurant. It can serve a plated meal that is ready to eat, or a meal kit that you cook at home. A plated meal is faster to start, and a kit gives you more control.

| Approach | What happens | Good | Bad |
|---|---|---|---|
| Server-side rendering (SSR) | The server builds the full HTML page | Fast first paint, good for search engines | Needs more server resources |
| Client-side rendering (CSR) | The server sends a small HTML shell and JavaScript; the browser fetches data and draws | Very interactive after load | Slow first load, weak for search engines |
| Hybrid | The server draws the first page, the browser handles updates | A fast first page and fast updates | The article names none. Tutorial's view: the first page still costs server resources |

The table follows the article, except the last cell <Cite n={1} />. With SSR, the browser later "hydrates" the page: it attaches the code that makes buttons work <Cite n={1} />. The article thinks Twitter likely uses CSR. Timelines are personal, so SSR helps speed more than search, and the timeline fetch is already fast <Cite n={1} />.

The second choice is how you move between pages. A single-page application (SPA) loads one HTML page and then changes its content with JavaScript, with no full reload. A multi-page application (MPA) loads a new HTML page for each route <Cite n={1} />. For Twitter, an SPA is the better fit <Cite n={1} />. When you click a tweet in the timeline, its text and images are already in memory, so the tweet page opens at once. Only the replies must load <Cite n={1} />.

</Technical>

## The store keeps one copy of everything

<Voices>
<Technical>

Think of the contact list on your phone. Your chat apps show the name from your contacts. If you change a name one time, every chat shows the new name.

The store is the single source of truth in the browser. It keeps the timeline, the tweets, the users, and the text you are typing in memory <Cite n={1} />. It uses normalization: each item is stored exactly one time, and other items point to it by its ID <Cite n={1} />. A tweet does not hold a full copy of its author. It holds the ID of the author. So when a user changes an avatar, the store updates one entry, and every tweet by that user shows the new picture <Cite n={1} />.

| Item | What it holds |
|---|---|
| Tweet | Text, author ID, times, like and retweet counts, media |
| User | Name, username, picture, verified status, "you follow them" flag |
| Timeline | An ordered list of tweet IDs and the paging details |

The table follows the article <Cite n={1} />. The work to normalize data can happen on the server or in the browser. The article says that, as of 2025, Twitter normalizes the timeline on its servers, so the browser gets a small, ready-made payload <Cite n={1} />.

</Technical>

## The API between browser and server

<Voices>
<Technical>

```text
GET  /timeline?count=10&cursor=abc   a page of tweets, with paging details
GET  /tweets/{id}                    one tweet
POST /tweets                         create a tweet
POST /media/upload                   upload an image, get back a media ID
POST /tweets/{id}/like               like a tweet
POST /tweets/{id}/retweet            retweet a tweet
```

The list follows the article <Cite n={1} />. A request must not carry the user ID as proof of who the user is, because an attacker can fake it. It gets back an ID and puts that ID in the new tweet <Cite n={1} />.

## Making a long timeline fast

<Voices>
<Technical>

Think of a theatre stage. Only the actors in the current scene stand on it. The rest wait backstage until they are needed.

- **Code splitting.** The app downloads only the JavaScript for the current view <Cite n={1} />. Code for each tweet type, the emoji picker, or the tweet detail page loads only when the app needs it <Cite n={1} />.
- **List virtualization.** The app draws only the tweets in view. Empty blocks keep the scrollbar the right size, and tweets that leave the screen are removed or reused <Cite n={1} />.
- **Lazy media.** Images load only when they come near the screen. The app asks for an image size that fits the device and can show a blurred preview first <Cite n={1} />.

The page must also say clearly when it is busy or broken. Twitter shows one loading spinner. The article suggests gray "skeleton" blocks in the shape of tweets, so the layout does not jump <Cite n={1} />. If the feed fails to load, Twitter shows a short message and a Retry button, not a blank page <Cite n={1} />.

</Technical>

- **List virtualization।** App শুধু দেখা যাওয়া tweet-গুলো আঁকে। ফাঁকা block-গুলো scrollbar-এর size ঠিক রাখে, আর screen থেকে সরে যাওয়া tweet-গুলো সরিয়ে ফেলা হয় বা আবার ব্যবহার করা হয় <Cite n={1} />।
- **Lazy media।** Image শুধু screen-এর কাছে এলে load হয়। App device-এর সাথে মানানসই image size চায়, এবং প্রথমে একটি ঝাপসা preview দেখাতে পারে <Cite n={1} />।

Page busy বা broken হলে সেটিও পরিষ্কারভাবে দেখাতে হবে। Twitter একটি loading spinner দেখায়। Article tweet-এর আকারে ধূসর "skeleton" block-এর পরামর্শ দেয়, যাতে layout লাফিয়ে না সরে <Cite n={1} />। Feed load না হলে Twitter ফাঁকা page-এর বদলে একটি ছোট message আর একটি Retry button দেখায় <Cite n={1} />।

## Loading more tweets: offset or cursor

<Voices>
<Technical>

Think of a long book. You can say "start at line 200", or you can put a bookmark after the last line you read. If someone adds lines at the top, "line 200" now points to a different line. The bookmark still works.

| Method | Request | Problem or benefit |
|---|---|---|
| Offset | `?offset=20&limit=10` | New tweets shift the positions, so items repeat or go missing; big offsets are slow |
| Cursor | "the next 10 after tweet X" | Stable when data changes; works for newer and older tweets |

The table follows the article <Cite n={1} />. A cursor is a unique value, often a tweet ID or a timestamp, that marks the edge of a page <Cite n={1} />. The article picks cursor paging for Twitter, because new tweets arrive all the time and old ones can be deleted or ranked again <Cite n={1} />.

</Technical>
<Layman>

Think of a long book. You can say "start at line 200", or you can put a bookmark after the last line that you read. If someone adds lines at the top, "line 200" now points to a different line. The bookmark still works.

- **Offset** paging sends a request such as `?offset=20&limit=10`. New tweets move the positions, so items repeat or go missing. Big offsets are slow <Cite n={1} />.
- **Cursor** paging asks for "the next 10 after tweet X". It stays stable when the data changes. It works for newer and older tweets <Cite n={1} />.

A cursor is a unique value, often a tweet ID or a timestamp. It marks the edge of a page <Cite n={1} />. The article picks cursor paging for Twitter, because new tweets arrive all the time, and old tweets can be deleted or ranked again <Cite n={1} />.

</Layman>
<Bangla>

একটি লম্বা বইয়ের কথা ভাবুন। আপনি বলতে পারেন "line 200 থেকে শুরু করুন", অথবা শেষ যে line পড়েছেন তার পরে একটি bookmark রাখতে পারেন। কেউ উপরে নতুন line যোগ করলে "line 200" এখন অন্য একটি line-কে দেখায়, কিন্তু bookmark তবুও ঠিক কাজ করে।

- **Offset** paging `?offset=20&limit=10`-এর মতো request পাঠায়। নতুন tweet এলে position সরে যায়, তাই item repeat হয় বা হারিয়ে যায়; বড় offset ধীর <Cite n={1} />।
- **Cursor** paging চায় "tweet X-এর পরের 10টি"। Data বদলালেও এটি stable থাকে, এবং নতুন ও পুরোনো দুই ধরনের tweet-এর জন্যই কাজ করে <Cite n={1} />।

Cursor হলো একটি unique value, প্রায়ই একটি tweet ID বা একটি timestamp, যা একটি page-এর সীমা চিহ্নিত করে <Cite n={1} />। Article Twitter-এর জন্য cursor paging বেছে নেয়, কারণ সবসময় নতুন tweet আসে, আর পুরোনো tweet delete হতে পারে বা আবার rank হতে পারে <Cite n={1} />।

## Key words

| Word | Plain meaning |
|---|---|
| Front end | The part of an app that runs on your device and draws the screen |
| SSR / CSR | Build the page on the server, or build it in the browser |
| SPA | A web app that loads one page and then changes its content without a reload |
| Store | The memory in the browser that holds all app data, one copy of each item |
| Normalization | Store each item one time and point to it by ID |
| API | The fixed set of requests that the browser can send to the server |
| Optimistic update | Change the screen first, confirm with the server after |
| Virtualization | Draw only the items that are on screen |
| Lazy loading | Load a file only when it is about to be needed |
| Cursor | A bookmark value that tells the server where the next page starts |

## What a tester can learn

<Voices>
<Technical>

<Callout type="tip" title="Tutorial advice">
These ideas are the tutorial's own advice.

- Like a tweet while the network is offline or the server returns an error. Check that the heart and the count roll back and that the user sees a message.
- Show the same tweet in two places, for example the timeline and the tweet page. Like it in one place and check the other.
- Post new tweets from another account while you scroll. Check that no tweet shows twice and that no tweet is missing.
- Throttle the network. Check the loading state, the error state, and that Retry works.
- Send a request with the user ID of another account in the body. The server must use the session cookie, not that ID.
- Scroll through hundreds of tweets. Check that memory and the number of page elements stay stable.
</Callout>

- শত শত tweet scroll করুন। দেখুন, memory আর page element-এর সংখ্যা stable থাকে কি না।
