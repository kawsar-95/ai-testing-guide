# How Spotify Works

A music app lets you tap a song and hear it almost at once, on a fast home network or a weak mobile signal. Behind that tap, the app must find one song among millions, check that you may play it, and send the sound in small parts without gaps. This page explains one article that designs a Spotify-like service for a job interview.<Cite n={1} /> The article describes one way to build this. It is not the exact system that Spotify runs. The second half of the article is for paid subscribers only, so this page covers the free part: the sizes, the main parts, and what happens when you press play.

## The big picture

<Voices>
<Technical>

```text
[Mobile app] --> [Load balancer] --> [API servers] --> [SQL database]
     |                                    |             (song details)
     |                                    v
     |                          creates a signed URL
     |                                    |
     |  <------------- signed URL --------+
     |
     +--- fetch audio in chunks ---> [CDN] --> [Blob storage]
                                                (audio files)
```

The app asks the API servers for a song, through a load balancer. The API servers check the user, read the song details from a database, and return a signed URL.<Cite n={1} /> The app then downloads the sound itself straight from blob storage or a CDN, not through the API servers.<Cite n={1} />

## Where the songs live

<Voices>
<Technical>

Think of a huge warehouse with numbered shelves. You do not need to know how the building works. You only need the shelf address. Blob storage, also called object storage, works this way. It keeps large files, such as audio, and gives each file an address.

The article suggests a service like AWS S3 for all audio files.<Cite n={1} /> It arranges the files in folders by artist, then album, then song.<Cite n={1} /> Blob storage can grow almost without limit, keeps files safe, and costs little for large files.<Cite n={1} /> The design copies the files to several regions, so a fault in one place does not lose them.<Cite n={1} />

There is a cost. Blob storage is slower to answer than a local disk, and sending data out of it can be expensive.<Cite n={1} /> The article names a distributed file system, the Hadoop Distributed File System (HDFS), as an option. It still prefers blob storage, because it is a more managed service and is reliable for most cases.<Cite n={1} />

The app also keeps recently played songs on the phone, so a replay starts faster.<Cite n={1} />

## Load balancer and API servers

<Voices>
<Technical>

Think of a host at the door of a restaurant. The host sends each new guest to a table with a free waiter, and closes a table when its waiter is sick. A load balancer does this for requests.

The article's load balancer shares requests among many API servers. It can send them in turn (round-robin) or to the server with the fewest open connections.<Cite n={1} /> It checks each server every 30 seconds and stops sending traffic to a server that fails the check.<Cite n={1} /> This matters most when a big album comes out and traffic jumps.<Cite n={1} /> It also lets the team deploy new code without downtime.<Cite n={1} />

The API servers are stateless. That means they keep no user data between requests, so any server can answer any request.<Cite n={1} /> They check a JWT, which is a signed login token, and they read song details from the database.<Cite n={1} /> They also protect themselves in three ways:<Cite n={1} />

- A circuit breaker stops calls to a failing service, so one failure does not spread to others.
- A connection pool reuses open database connections and does not open a new one for each request.
- A fallback gives a simple answer for features that are not critical when a service they need is down.

</Technical>

## What happens when you press play

<Voices>
<Technical>

The article lists the read path step by step.<Cite n={1} />

1. The app sends `GET /songs/{id}`.
2. The API server checks the JWT.
3. The API server reads the song details from the SQL database.
4. The API server creates a signed URL for the audio file.
5. The app downloads the audio in chunks with range requests. A range request asks for only one part of a file.
6. From time to time, the app sends `POST /songs/{id}/play` to record plays and listening time.

For step 5, the article uses HTTP streaming standards called HLS or DASH. They give smooth playback, switch bitrate on their own, and work on many devices.<Cite n={1} />

The app also plans for failure. It retries API calls that fail.<Cite n={1} /> If the network drops, it pauses the song until the connection comes back.<Cite n={1} />

</Technical>

6. মাঝে মাঝে app `POST /songs/{id}/play` পাঠায়, যাতে play এবং listening time record হয়।

ধাপ 5-এর জন্য article HLS বা DASH নামের HTTP streaming standard ব্যবহার করে। এগুলো smooth playback দেয়, নিজে থেকে bitrate বদলায় এবং অনেক device-এ কাজ করে।<Cite n={1} />

App failure-এর জন্যও প্রস্তুত থাকে। কোনো API call fail করলে app আবার চেষ্টা করে।<Cite n={1} /> Network চলে গেলে connection ফিরে না আসা পর্যন্ত app song-টি pause রাখে।<Cite n={1} />

## Key words

| Word | Plain meaning |
|---|---|
| Bitrate | The amount of data for each second of sound. A higher bitrate gives better sound. |
| Adaptive streaming | Changing the quality of the sound during playback to match the speed of the network |
| Rebuffering | A pause in playback while the app waits for more sound data |
| Blob storage | A store for large files, where each file has an address |
| CDN | Servers in many cities that keep copies of popular files close to users |
| Signed URL | A link to one file that works only for a short time |
| Load balancer | A server that shares incoming requests among many servers |
| Stateless server | A server that keeps no user data between requests, so any copy can answer |
| Circuit breaker | A switch that stops calls to a failing service for a while |
| Metadata | Facts about a song, such as title, artist, and length, but not the sound itself |
