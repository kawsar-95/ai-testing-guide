# Requirement Analysis & Acceptance Criteria

Before you write a single test, read the requirement as a tester. This page shows how to bring a Jira story or a GitHub issue into Claude, find what is vague or missing, list the risks, and write acceptance criteria that a whole team can check. A question that you ask now costs one message. The same gap found after release costs a bug, a fix, and a retest.

<PageMeta />

## Why requirements come first

<Voices>
<Technical>

A requirement is the first thing that you test, and you test it without running any code.

**The ISTQB terms.**

- **Test basis**: the body of knowledge used as the basis for test analysis and test design. <Cite n={2} /> On this page, the test basis is the story and its issue.
- **Requirement**: a provision that contains criteria to be fulfilled. <Cite n={3} />
- **Testability**: the degree to which test conditions can be set up, and tests can show whether those conditions are met. <Cite n={4} />
- **Test condition**: a testable aspect of a component or system that is intended to be tested. <Cite n={5} />

**What the syllabus says.** Test analysis examines the test basis to find testable features. <Cite n={1} /> It also checks the test basis for defects and assesses its testability. <Cite n={1} /> Its outputs include test conditions, such as acceptance criteria, and defect reports about the test basis. <Cite n={1} />

**Reviews are static testing.** In static testing, the software under test does not need to be executed. <Cite n={1} /> Requirement documents and product backlog items can be reviewed. <Cite n={1} /> Static testing can find defects in the earliest phases of the lifecycle. <Cite n={1} /> Typical requirement defects are inconsistencies, ambiguities, contradictions, omissions, inaccuracies, and duplications. <Cite n={1} />

**The tester's role.** Reviews help make sure that user stories are complete, understandable, and have testable acceptance criteria. <Cite n={1} /> Testers ask the right questions to explore, challenge, and improve the stories. <Cite n={1} /> Teams use criteria such as a Definition of Ready for this. <Cite n={1} />

<Callout type="tip" title="The tutorial's advice">

Claude makes the review fast, but it does not replace the conversation with the product owner. Use Claude to prepare good questions. Let people answer them. The [Fundamentals basics](/fundamentals/basics/) chapter covers static testing in more depth.

</Callout>

</Technical>
<Layman>

You can test a requirement without running any code. You read it and look for problems.

Some words to know:

- The **test basis** is the knowledge you use as the base for analyzing and designing tests. <Cite n={2} /> On this page, it is the story and its issue.
- A **requirement** is a statement that contains criteria to be fulfilled. <Cite n={3} />
- **Testability** means: can you set up test conditions, and can a test show if they are met? <Cite n={4} />
- A **test condition** is one thing in the system that you intend to test. <Cite n={5} />

Test analysis looks at the test basis and finds what to test. It also looks for defects in the test basis. <Cite n={1} /> This kind of review is static testing: the software does not need to run. <Cite n={1} /> It can find defects in the earliest phases. Typical defects in requirements are gaps, vague words, and parts that disagree. <Cite n={1} />

Testers ask questions to make a story clear and testable. <Cite n={1} />

The tutorial's advice: Claude helps you prepare the questions. People still answer them.

</Layman>
<Bangla>

কোনো code চলার আগেই আপনি requirement test করতে পারেন। এটি পড়ে সমস্যা খোঁজাই সেই test।

ISTQB-এর কয়েকটি শব্দ:

- **Test basis** হলো সেই জ্ঞানের ভান্ডার, যার ওপর test analysis আর test design দাঁড়ায়। <Cite n={2} /> এই পেজে test basis হলো story আর তার issue।
- **Requirement** হলো এমন একটি শর্ত, যাতে পূরণ করার মতো criteria থাকে। <Cite n={3} />
- **Testability** মানে কতটা সহজে test condition ঠিক করা যায়, আর test দিয়ে দেখা যায় সেগুলো পূরণ হলো কি না। <Cite n={4} />
- **Test condition** হলো component বা system-এর এমন একটি testable দিক, যা test করার কথা। <Cite n={5} />

Syllabus বলে, test analysis test basis বিশ্লেষণ করে testable feature খোঁজে, আর test basis-এর defect ও testability-ও যাচাই করে। <Cite n={1} /> এর ফলাফলের মধ্যে আছে acceptance criteria-র মতো test condition, আর test basis-এর defect report। <Cite n={1} />

Review হলো static testing: এখানে software চালানোর দরকার হয় না। <Cite n={1} /> Requirement document আর product backlog item review করা যায়, আর এতে lifecycle-এর একদম শুরুর ধাপেই defect ধরা পড়তে পারে। <Cite n={1} /> Requirement-এর সাধারণ defect হলো অসংগতি, অস্পষ্টতা, পরস্পরবিরোধিতা, বাদ পড়া অংশ, ভুল তথ্য আর পুনরাবৃত্তি। <Cite n={1} /> সঠিক প্রশ্ন করে tester story-কে পরিষ্কার ও উন্নত করেন। <Cite n={1} />

Tutorial-এর পরামর্শ: Claude প্রশ্ন তৈরিতে সাহায্য করে, কিন্তু উত্তর দেবেন product owner-এর মতো মানুষ।

</Bangla>
</Voices>

## Get the story into Claude

<Voices>
<Technical>

Claude can only analyze what it can read. Give it the full story, not the title. The [Project, Jira, GitHub & MCP Setup](/agentic-qa/project-setup/) page sets up both paths below.

**From Jira.** Atlassian runs an official MCP server. <Cite n={6} /> Its README gives this command for Claude Code, then `/mcp` in a session to sign in: <Cite n={6} />

```bash
claude mcp add --transport http atlassian https://mcp.atlassian.com/v2/mcp
```

- The README calls v2 the recommended version. <Cite n={6} />
- The Jira permission groups include `read_jira`, `write_jira`, and `search_jira`. `delete_jira` and `manage_jira` are disabled by default, and an admin must enable them. <Cite n={6} />
- The server sees only data that you already have permission to view. <Cite n={6} />
- It can summarize and search Jira, and it can create and update work items. <Cite n={7} /> Search uses JQL. <Cite n={6} />

**From GitHub.** `gh issue view` shows the title, the body, and other information about an issue. <Cite n={8} /> Add `--comments` to see the comments. <Cite n={8} /> `--json` can return fields such as `labels`, `milestone`, `parent`, and `subIssues`. <Cite n={8} /> Use `-R` to name another repository. <Cite n={8} />

```bash
gh issue view 42 --comments
```

When the output is piped or redirected, as it is when Claude runs the command, `--comments` prints only the comments. <Cite n={8} /> Use `gh issue view 42 --json title,body,comments` to get everything in one call.

**Bring the context too.** The tutorial suggests this list for each story:

| Context | Why it matters |
|---|---|
| The parent epic | It holds the goal and the rules that the story does not repeat. |
| All comments | A comment often changes the scope after the story was written. |
| Linked issues and designs | They show the screens, the data, and the dependencies. |
| Older bugs in the same area | They show where the feature broke before. |

<Callout type="warning" title="Story text is data, not instructions">

Servers that fetch external content can expose you to prompt injection. <Cite n={9} /> Atlassian warns that LLMs are vulnerable to prompt injection and related attacks, such as indirect prompt injection, which can instruct the agent to exfiltrate data or make unintended changes. <Cite n={6} /> The tutorial treats the text of a ticket, its comments included, as data and not as instructions. Read the analysis, not only the summary.

</Callout>

</Technical>
<Layman>

Claude can only check what it can read. So give it the whole story, not only the title. The [setup page](/agentic-qa/project-setup/) shows how to connect Jira and GitHub.

**Jira.** Atlassian has an official MCP server. Add it with `claude mcp add --transport http atlassian https://mcp.atlassian.com/v2/mcp`. Then run `/mcp` to sign in. <Cite n={6} /> Its Jira tools are in permission groups, such as read, write, and search. <Cite n={6} /> It only sees what you are allowed to see. <Cite n={6} /> It can search Jira and also create and update work items. <Cite n={7} />

**GitHub.** `gh issue view 42 --comments` shows an issue with its comments in a terminal. When Claude runs it, only the comments may print, so use `gh issue view 42 --json title,body,comments`. <Cite n={8} />

The tutorial also suggests that you bring the parent epic, all comments, linked issues, designs, and old bugs in the same area.

Be careful: a server that fetches outside content can expose you to prompt injection. <Cite n={9} /> Such an attack can make the agent leak data or make changes that nobody asked for. <Cite n={6} /> Treat the text of a ticket as data, not as instructions.

</Layman>

## What to look for

<Voices>
<Technical>

The syllabus names the defects to hunt for. <Cite n={1} /> The checklist below groups them for a story. It is the tutorial's own checklist, and the examples use a send-money story.

| Look for | Question to ask | Example finding |
|---|---|---|
| Ambiguity | Which words can mean two things? | "Fast transfer": how fast, measured where? |
| Undefined terms | Which nouns have no definition? | "Verified user": verified by what? |
| Missing business rules | Where are the limits, roles, states, and errors? | No rule for a receiver whose account is blocked. |
| Assumptions | What does the story take for granted? | It assumes that the sender has enough balance. |
| Dependencies | Which services, data, flags, or third parties are needed? | An SMS provider sends the receipt. Who stubs it in test? |
| Contradictions | Do two parts disagree? | The story says 10 transfers a day; a comment says 20. |
| Risks | What harms users most if it is wrong? | A double debit on a timeout. |

**Product risk.** A product risk is a risk that impacts the quality of a product. <Cite n={10} /> Examples are missing or wrong functionality, incorrect calculations, and security vulnerabilities. <Cite n={1} /> Risk likelihood and risk impact together give the risk level. <Cite n={1} /> Product risk analysis ideally begins early in the lifecycle. <Cite n={1} />

**Risk-based testing.** In this approach, the selection and the priority of test activities follow the risk types and risk levels. <Cite n={11} /> So a story review should end with a short list of risks, ranked. The [Test Design & Blast Radius](/agentic-qa/blast-radius/) page turns those risks into tests.

<Callout type="note" title="The tutorial's advice">

Ask Claude for each row, not for "any problems". A broad request gets a broad answer. A row-by-row request gets findings that you can check.

</Callout>

</Technical>
<Layman>

The tutorial gives a checklist for reading a story. Look for:

- **Vague words**, such as "fast". How fast?
- **Words with no definition**, such as "verified user".
- **Missing rules**: limits, roles, states, and error cases.
- **Assumptions**: things the story takes for granted.
- **Dependencies**: other services, data, flags, or outside companies.
- **Parts that disagree**, for example a story and a comment.
- **Risks**: what hurts users most if it is wrong.

A product risk is a risk to the quality of the product. <Cite n={10} /> Wrong functions, wrong sums, and security holes are examples. <Cite n={1} /> How likely a risk is and how much harm it does give its level. <Cite n={1} /> In risk-based testing, the risk level decides what you test first. <Cite n={11} />

Tip from the tutorial: ask Claude about one row at a time.

</Layman>
<Bangla>

Syllabus বলে দেয় কোন defect খুঁজতে হবে। <Cite n={1} /> নিচের checklist tutorial-এর নিজের, আর উদাহরণগুলো একটি send-money story থেকে:

- **অস্পষ্টতা:** কোন শব্দের দুই রকম মানে হতে পারে? যেমন "fast transfer"।
- **সংজ্ঞাহীন শব্দ:** যেমন "verified user", কী দিয়ে verified?
- **বাদ পড়া business rule:** limit, role, state আর error case কোথায়? যেমন blocked receiver-এর জন্য কোনো rule নেই।
- **Assumption:** story কী ধরে নিচ্ছে? যেমন sender-এর যথেষ্ট balance আছে।
- **Dependency:** কোন service, data, flag বা third party লাগবে? যেমন receipt পাঠানোর SMS provider।
- **পরস্পরবিরোধিতা:** story বলছে দিনে 10টি transfer, comment বলছে 20টি।
- **ঝুঁকি:** timeout-এ দুবার debit হলে কী হবে?

Product risk হলো এমন ঝুঁকি, যা product-এর quality-কে প্রভাবিত করে। <Cite n={10} /> ভুল functionality, ভুল হিসাব আর security vulnerability এর উদাহরণ। <Cite n={1} /> Risk likelihood আর risk impact মিলে risk level ঠিক হয়, আর product risk analysis শুরুতেই হওয়া ভালো। <Cite n={1} /> Risk-based testing-এ test activity বাছাই আর অগ্রাধিকার risk level অনুযায়ী হয়। <Cite n={11} />

Tutorial-এর পরামর্শ: "কোনো সমস্যা আছে?" না বলে Claude-কে প্রতিটি সারি ধরে প্রশ্ন করুন।

</Bangla>
</Voices>

## A repeatable analysis

<Voices>
<Technical>

The docs suggest a skill when you keep pasting the same instructions, checklist, or multi-step procedure into chat. A skill is a `SKILL.md` file with instructions, and you run it with `/skill-name`. <Cite n={12} /> The tutorial uses a skill so that every analysis asks for the same sections.

- A project skill lives in `.claude/skills/<skill-name>/SKILL.md`. Commit it so the team gets it too. <Cite n={12} />
- `disable-model-invocation: true` stops Claude from loading the skill on its own, so it runs only when you type its name. <Cite n={12} />
- `argument-hint` shows the expected argument during autocomplete, and `$ARGUMENTS` holds what you pass. <Cite n={12} />
- `allowed-tools` lets Claude use the listed tools without asking during that turn. <Cite n={12} /> Do not list a tool that writes to Jira or GitHub there.

**Run it read-only.** Plan mode tells Claude to research and propose changes without making them. <Cite n={13} /> Claude reads files and can run shell commands to explore, but it does not edit your source. <Cite n={13} /> Enter it with `Shift+Tab`, with `/plan` before one prompt, or with `claude --permission-mode plan`. <Cite n={13} />

Here is an example skill. It is the tutorial's own template, saved as `.claude/skills/analyze-story/SKILL.md`:

```markdown
---
name: analyze-story
description: Analyze one Jira story or GitHub issue for test readiness.
argument-hint: [issue-key-or-number]
disable-model-invocation: true
---

Read $ARGUMENTS with its comments, parent, and linked issues.
Do not change any ticket.

Write exactly these sections:
1. Summary: user, goal, and business value, in 3 lines.
2. Questions for the product owner (numbered).
3. Assumptions: each one marked ASSUMPTION.
4. Risks: likelihood and impact (high, medium, low).
5. Test conditions: one line each, positive and negative.

For every finding, quote the story text behind it.
If no text supports a finding, mark it as a guess.
```

The test conditions feed the [Test Design & Blast Radius](/agentic-qa/blast-radius/) page. The [Skills](/extend/skills/) page explains skills in depth.

</Technical>
<Layman>

Make a skill when you keep pasting the same instructions into chat. A skill is a `SKILL.md` file with instructions. You run it with `/skill-name`. <Cite n={12} /> The tutorial uses one so that every analysis asks for the same sections.

- Put a project skill in `.claude/skills/<skill-name>/SKILL.md` and commit it. Then your team gets it too. <Cite n={12} />
- `disable-model-invocation: true` means the skill runs only when you call it. <Cite n={12} />
- `$ARGUMENTS` holds the text that you pass. <Cite n={12} />

Run the analysis in plan mode. In plan mode, Claude researches and suggests, but it does not edit your source. <Cite n={13} /> Press `Shift+Tab`, or start with `claude --permission-mode plan`. <Cite n={13} />

The tutorial's example skill asks for five parts: a summary, questions, assumptions, risks, and test conditions. It also asks Claude to quote the story text behind each finding. A finding with no quote is marked as a guess.

</Layman>

## Acceptance criteria

<Voices>
<Technical>

**Definitions.** Acceptance criteria are the criteria that a work product must satisfy to be accepted by the stakeholders. <Cite n={14} /> A user story is a short narrative of a need from a user's perspective, with the expected benefit. <Cite n={15} />

**The 3 Cs.** The syllabus gives three aspects of a user story: <Cite n={1} />

- **Card**: the medium that describes the story, such as an entry on an electronic board.
- **Conversation**: how the software will be used.
- **Confirmation**: the acceptance criteria.

The common story format is "As a [role], I want [goal], so that I can [business value]", followed by the acceptance criteria. <Cite n={1} />

**INVEST.** Good stories are Independent, Negotiable, Valuable, Estimable, Small, and Testable. <Cite n={1} /> If a stakeholder does not know how to test a story, the story may not be clear enough. <Cite n={1} />

**What criteria do.** Acceptance criteria may be viewed as the test conditions that the tests exercise. <Cite n={1} /> They describe both positive and negative scenarios. <Cite n={1} />

| Format | What it looks like <Cite n={1} /> |
|---|---|
| Scenario-oriented | Given/When/Then, as used in BDD |
| Rule-oriented | A bullet-point verification list, or a table of inputs and outputs |

A custom format is fine if the criteria are well-defined and unambiguous. <Cite n={1} />

**ATDD.** Acceptance test-driven development is a collaboration-based, test-first approach. It defines acceptance tests in the stakeholders' domain language. <Cite n={16} />

- It starts with a specification workshop. The team resolves incompleteness and ambiguities in the story there. <Cite n={1} />
- The first test cases are positive. Negative tests come next, then non-functional ones. <Cite n={1} />
- The test cases cover the story and do not go beyond it. <Cite n={1} />

The [Lifecycles](/fundamentals/lifecycles/) chapter compares ATDD and BDD.

</Technical>
<Layman>

**Acceptance criteria** are the conditions that work must meet before the stakeholders accept it. <Cite n={14} /> A **user story** is a short text about what a user needs and why. <Cite n={15} />

A story has three parts, the "3 Cs": <Cite n={1} />

- **Card**: where the story is written, such as a board.
- **Conversation**: the talk about how the software will be used.
- **Confirmation**: the acceptance criteria.

A good story is Independent, Negotiable, Valuable, Estimable, Small, and Testable. People call this INVEST. <Cite n={1} /> If a stakeholder does not know how to test a story, it may not be clear enough. <Cite n={1} />

You can write criteria in two common ways. One way is scenarios, with Given, When, and Then. The other way is rules: a list or a table. <Cite n={1} /> Criteria describe both good paths and error paths. <Cite n={1} />

**ATDD** means the team writes the acceptance tests first, together, in the business language. <Cite n={16} /> It starts with a workshop that clears up gaps in the story. <Cite n={1} />

</Layman>
<Bangla>

**Acceptance criteria** হলো সেই criteria, যা পূরণ করলে stakeholder-রা কাজটি গ্রহণ করেন। <Cite n={14} /> **User story** হলো user-এর দৃষ্টিকোণ থেকে একটি প্রয়োজন আর তার প্রত্যাশিত সুবিধার ছোট বর্ণনা। <Cite n={15} />

Syllabus অনুযায়ী user story-র তিনটি দিক, "3 Cs": <Cite n={1} />

- **Card:** যেখানে story লেখা থাকে, যেমন electronic board-এর একটি entry।
- **Conversation:** software কীভাবে ব্যবহার হবে, তার আলোচনা।
- **Confirmation:** acceptance criteria।

সাধারণ format হলো "As a [role], I want [goal], so that I can [business value]", তারপর acceptance criteria। <Cite n={1} /> ভালো story হয় INVEST: Independent, Negotiable, Valuable, Estimable, Small আর Testable। কোনো stakeholder story test করার উপায় না জানলে story হয়তো যথেষ্ট পরিষ্কার নয়। <Cite n={1} />

Acceptance criteria-কে test condition হিসেবে দেখা যায়, আর এতে positive ও negative দুই ধরনের scenario থাকে। <Cite n={1} /> লেখার দুটি সাধারণ format: scenario-oriented (Given/When/Then) আর rule-oriented (bullet list বা input-output table)। Criteria স্পষ্ট আর দ্ব্যর্থহীন হলে custom format-ও চলে। <Cite n={1} />

**ATDD** হলো একটি collaboration-ভিত্তিক test-first approach, যা stakeholder-দের ভাষায় acceptance test লেখে। <Cite n={16} /> এটি শুরু হয় একটি specification workshop দিয়ে, যেখানে story-র অসম্পূর্ণতা আর অস্পষ্টতা দূর হয়। প্রথমে positive test, তারপর negative, তারপর non-functional test। <Cite n={1} />

</Bangla>
</Voices>

## A worked example: send money

<Voices>
<Technical>

**The Gherkin keywords.** Each step starts with `Given`, `When`, `Then`, `And`, or `But`. <Cite n={17} />

- `Given` describes the initial context, `When` an event or an action, and `Then` an expected outcome. <Cite n={17} />
- `Rule` represents one business rule and groups its scenarios. <Cite n={17} /> `Scenario` is a synonym of `Example`. <Cite n={17} />
- `Scenario Outline` runs the same scenario with different values from an `Examples` table. <Cite n={17} />
- Cucumber recommends 3 to 5 steps per example. <Cite n={17} /> An outcome should be on an observable output, and examples should not assume a technology or a user interface. <Cite n={17} />

<Callout type="note" title="Where these facts come from">

The rules below come from the business requirements document (BRD) in `dmoney-web-react/README.md` of the dMoney practice repository. They have no cites, because a cite links to an official source.

</Callout>

The dMoney requirements say that send money needs two different, active Customer accounts. The minimum amount is 10 BDT, the fee is a flat 5 BDT, and the sender needs a balance of at least the amount plus 5. Daily and monthly limits are checked first: 5,000 Tk and 10 transactions a day.

The story and the criteria below are the tutorial's own example, written from those rules.

```gherkin
Feature: Send money
  As a customer, I want to send money to another customer,
  so that I can pay people without cash.

  Rule: The amount is at least 10 BDT

    Scenario Outline: Amount at the minimum boundary
      Given my balance is 100 BDT
      When I send <amount> BDT to another active customer
      Then I see "<result>"

      Examples:
        | amount | result                    |
        | 9      | Minimum amount is 10 tk   |
        | 10     | Send money successful     |

  Rule: The sender cannot send to the same account

    Scenario: Sender enters own phone number
      Given my balance is 100 BDT
      When I send 50 BDT to my own phone number
      Then the transfer is rejected
      And my balance is still 100 BDT
```

**The same rules, rule-oriented:**

| Rule | Input | Expected |
|---|---|---|
| Fee | Send 100 BDT | Sender is debited 105 BDT |
| Balance | Balance 104 BDT, send 100 BDT | Rejected, no debit |
| Daily count | 11th transfer today | Rejected by the daily limit |

</Technical>
<Layman>

In Gherkin, each step starts with Given, When, Then, And, or But. <Cite n={17} /> Given is the starting situation. When is the action. Then is the result that you expect. <Cite n={17} /> A Rule groups the scenarios of one business rule. <Cite n={17} /> A Scenario Outline runs one scenario with many values from a table. <Cite n={17} /> Cucumber suggests 3 to 5 steps per example. The result should be an observable output. <Cite n={17} />

The rules for the example come from the dMoney practice repo. Send money needs two different, active Customer accounts. The minimum is 10 BDT. The fee is 5 BDT. The sender needs the amount plus 5 in the account. Daily and monthly limits are checked first.

The tutorial's example story has two rules. The first checks the minimum: 9 BDT fails and 10 BDT works. The second checks that you cannot send money to yourself. The same rules also fit in a table of inputs and expected results.

</Layman>
<Bangla>

Gherkin-এ প্রতিটি step শুরু হয় `Given`, `When`, `Then`, `And` বা `But` দিয়ে। <Cite n={17} /> `Given` শুরুর অবস্থা, `When` একটি event বা action, আর `Then` প্রত্যাশিত ফলাফল বর্ণনা করে। <Cite n={17} /> `Rule` একটি business rule-এর scenario-গুলো একসাথে রাখে, আর `Scenario Outline` একটি `Examples` table থেকে ভিন্ন ভিন্ন মান নিয়ে একই scenario বারবার চালায়। <Cite n={17} /> Cucumber প্রতিটি example-এ 3 থেকে 5টি step রাখতে বলে, আর ফলাফল হওয়া উচিত বাইরে থেকে দেখা যায় এমন কিছু। <Cite n={17} />

উদাহরণের rule-গুলো dMoney practice repo-র `dmoney-web-react/README.md`-এর BRD থেকে নেওয়া। Send money-র জন্য দুটি আলাদা, active Customer account লাগে। সর্বনিম্ন amount 10 BDT, fee নির্দিষ্ট (flat) 5 BDT, আর sender-এর balance কমপক্ষে amount যোগ 5 হতে হবে। Daily আর monthly limit আগে যাচাই হয়: দিনে 5,000 Tk আর 10টি transaction।

Tutorial-এর উদাহরণে দুটি rule আছে। প্রথমটি minimum boundary যাচাই করে: 9 BDT fail করে, 10 BDT সফল হয়। দ্বিতীয়টি দেখে যে নিজের account-এ টাকা পাঠানো যায় না, আর balance বদলায় না। একই rule একটি input-output table-এও লেখা যায়।

## Is the story ready for test?

<Voices>
<Technical>

Teams check stories against criteria such as a Definition of Ready. <Cite n={1} /> The checklist below is the tutorial's own. Run it after the analysis, before any test design.

<Callout type="tip" title="The tutorial's checklist">

- The story names the user, the goal, and the business value.
- Every vague word has a number or a definition.
- Each business rule has at least one acceptance criterion.
- The criteria cover both positive and negative scenarios.
- The limits, roles, states, and error messages are written down.
- Each dependency has an owner and a test double or a test environment.
- Every assumption is confirmed by the product owner, or listed as open.
- The top risks are ranked.
- Each criterion can pass or fail on something that a user or a system can observe.

</Callout>

**When the story is not testable.** INVEST lists Testable as a property of a good story. <Cite n={1} /> If a story fails the checklist, do not fill the gaps with guesses. The tutorial suggests this order:

1. Send the open questions back to the product owner, numbered, with the quote that each one is about.
2. Mark the story as blocked for test design, or agree on which part can start.
3. Keep the assumptions in the ticket, so that a later reader sees what was guessed.
4. Run the analysis again when the answers arrive.

<Callout type="warning" title="The tutorial's advice: do not let Claude fill the gap">

An answer can read well even when the story is silent. A plausible limit that nobody approved is still a guess. The skill above asks Claude to mark such findings, so you can see them.

</Callout>

</Technical>
<Layman>

Teams often check a story against a list, such as a Definition of Ready. <Cite n={1} /> The tutorial gives its own list:

- The story names the user, the goal, and the value.
- Each vague word has a number or a definition.
- Each business rule has at least one criterion.
- The criteria cover good paths and error paths.
- Limits, roles, states, and error messages are written down.
- Each dependency has an owner and a way to test it.
- The product owner confirmed each assumption, or it is listed as open.
- The top risks are ranked.
- Each criterion can pass or fail on something you can see.

A good story is testable. <Cite n={1} /> If it is not, do not guess. Send the questions back to the product owner. Mark the story as blocked, or agree on what can start. Keep the assumptions in the ticket. Run the analysis again when the answers come.

The tutorial's advice: an answer can read well even when the story says nothing. A guess is still a guess.

</Layman>
<Bangla>

Team-গুলো Definition of Ready-এর মতো criteria দিয়ে story যাচাই করে। <Cite n={1} /> নিচের checklist tutorial-এর নিজের। Analysis-এর পরে, test design-এর আগে এটি চালান:

- Story-তে user, goal আর business value আছে।
- প্রতিটি অস্পষ্ট শব্দের একটি সংখ্যা বা সংজ্ঞা আছে।
- প্রতিটি business rule-এর অন্তত একটি acceptance criterion আছে।
- Criteria-তে positive ও negative দুই ধরনের scenario আছে।
- Limit, role, state আর error message লেখা আছে।
- প্রতিটি dependency-র একজন owner আর test করার উপায় আছে।
- প্রতিটি assumption product owner নিশ্চিত করেছেন, নয়তো open হিসেবে লেখা আছে।
- প্রধান risk-গুলো ক্রম অনুযায়ী সাজানো।
- প্রতিটি criterion দেখা যায় এমন কিছুর ওপর pass বা fail করে।

INVEST অনুযায়ী ভালো story testable হয়। <Cite n={1} /> Story checklist-এ fail করলে অনুমান দিয়ে ফাঁক পূরণ করবেন না। প্রশ্নগুলো quote-সহ product owner-এর কাছে ফেরত পাঠান, story-কে test design-এর জন্য blocked রাখুন বা কোন অংশ শুরু করা যায় তা ঠিক করুন, assumption-গুলো ticket-এ রাখুন, আর উত্তর এলে analysis আবার চালান।

Tutorial-এর পরামর্শ: story চুপ থাকলেও উত্তর পড়তে ভালো লাগতে পারে। কেউ অনুমোদন না দেওয়া একটি limit তবুও একটি অনুমান।

## Write back only after approval

<Voices>
<Technical>

The questions and the criteria belong in the ticket, where the team can see them. But a write to Jira or GitHub is visible to everyone, so a person approves it first.

**Make Claude ask.** Ask rules prompt for confirmation when Claude tries to use a tool. <Cite n={18} /> Rules are evaluated in order: deny, then ask, then allow. <Cite n={18} /> A matching ask rule prompts even when a more specific allow rule also matches. <Cite n={18} /> To match every tool of an MCP server, write `mcp__<server>__*`. <Cite n={18} />

The `permissions` object of a settings file takes `allow`, `ask`, and `deny` arrays. <Cite n={20} /> Example `.claude/settings.json`, the tutorial's own, for a server named `atlassian`:

```json
{
  "permissions": {
    "ask": [
      "mcp__atlassian__*",
      "Bash(gh issue comment *)"
    ]
  }
}
```

This asks before every Atlassian tool call, reads included. That is slower, but safe.

**Least privilege.** MCP clients can act on all connected Atlassian products with your permissions, and Atlassian advises least privilege. <Cite n={7} /> Organization admins grant or revoke access at the permission-group level. <Cite n={6} /> The tutorial suggests that a read-only analysis gets only the read and search groups.

<Callout type="warning" title="Before you post">

The next command posts a comment that the whole team sees. Read the file first, and post to a test issue the first time.

</Callout>

`gh issue comment` adds a comment to a GitHub issue, and `--body-file` reads the text from a file. <Cite n={19} />

```bash
gh issue comment 42 --body-file analysis/42-questions.md
```

The tutorial suggests one comment that holds the numbered questions, the open assumptions, and the draft criteria. Keep the draft label until the product owner agrees. The [Case Study PR review](/case-study/pr-review/) shows criteria from issues used to review a fix.

</Technical>
<Layman>

Questions and criteria belong in the ticket, where the team sees them. Everyone can see a post, so a person approves it first.

An ask rule makes Claude stop and ask before it uses a tool. <Cite n={18} /> Claude Code checks deny rules first, then ask rules, then allow rules. <Cite n={18} /> So an ask rule wins over an allow rule. <Cite n={18} /> `mcp__<server>__*` covers every tool of one MCP server. <Cite n={18} /> The tutorial's example settings file asks before each Atlassian tool and before `gh issue comment`.

MCP clients can act with your permissions, and Atlassian advises giving only the access that is needed. <Cite n={7} /> Admins give access per permission group. <Cite n={6} /> For reading only, the tutorial suggests leaving out the `write_jira` group.

Before you post, read the text. `gh issue comment 42 --body-file analysis/42-questions.md` posts the text of a file as a comment. <Cite n={19} /> Try it on a test issue first.

</Layman>
<Bangla>

প্রশ্ন আর criteria ticket-এই থাকা উচিত, যেখানে team দেখতে পায়। কিন্তু Jira বা GitHub-এ লেখা সবাই দেখে, তাই আগে একজন মানুষ অনুমোদন দেবেন।

Ask rule থাকলে কোনো tool ব্যবহারের আগে Claude নিশ্চিতকরণ চায়। <Cite n={18} /> Rule যাচাই হয় এই ক্রমে: deny, তারপর ask, তারপর allow। তাই আরও নির্দিষ্ট allow rule মিললেও ask rule prompt দেখায়। <Cite n={18} /> একটি MCP server-এর সব tool ধরতে `mcp__<server>__*` লিখুন। <Cite n={18} /> Tutorial-এর উদাহরণ `.claude/settings.json` প্রতিটি Atlassian tool আর `gh issue comment`-এর আগে অনুমতি চায়।

MCP client আপনার permission নিয়ে সব connected Atlassian product-এ কাজ করতে পারে, আর Atlassian least privilege-এর পরামর্শ দেয়। <Cite n={7} /> Admin permission group ধরে access দেন বা সরান। <Cite n={6} /> Tutorial-এর পরামর্শ: শুধু পড়ার কাজে `write_jira` group দেবেন না।

পোস্ট করার আগে text পড়ে নিন। `gh issue comment` একটি GitHub issue-এ comment যোগ করে, আর `--body-file` একটি file থেকে text পড়ে। <Cite n={19} /> প্রথমবার একটি test issue-তে চেষ্টা করুন।

</Bangla>
</Voices>

   For a GitHub issue, give its number. Claude can read it with `gh issue view 42 --json title,body,comments`. <Cite n={8} />
5. **Check the output.** Expect five sections. Every finding should quote the story, or be marked as a guess. Open the ticket and compare three quotes with the real text.
6. **Turn it into criteria.** Ask for two formats:

   ```text
   Write acceptance criteria for this story: one Gherkin Rule per business rule,
   then the same rules as a table of input and expected result.
   Include negative scenarios. Do not add a rule that the story does not state.
   ```

7. **Review.** Run "Is the story ready for test?" on the result. Mark each line pass or fail.
8. **Post only with approval.** Save the questions to a file. Show them to the product owner, then post with `gh issue comment` and `--body-file`. <Cite n={19} />

**How to check the result.** Each Gherkin step starts with a Gherkin keyword. <Cite n={17} /> Each criterion has a positive or a negative label. Each open question has a quote.

## Common mistakes

<Voices>
<Technical>

| Mistake | Fix |
|---|---|
| Analyzing from the title or the key alone | Fetch the full story with its comments: `gh issue view 42 --json title,body,comments`, or the Jira MCP server. <Cite n={8} /> <Cite n={6} /> |
| Accepting Claude's guesses as rules | Ask for a quote behind each finding, and mark the rest as assumptions (the tutorial's advice). |
| Only positive criteria | Acceptance criteria describe both positive and negative scenarios. <Cite n={1} /> |
| Criteria that go beyond the story | Test cases must cover the story and should not go beyond it. <Cite n={1} /> Move extra ideas to a new question. |
| Then steps that check the database | An outcome should be on an observable output. <Cite n={17} /> |
| Posting to the ticket without review | Add ask rules for the write tools. <Cite n={18} /> A person reads every comment first (the tutorial's advice). |
| Giving the analysis write access | Plan mode does not edit your source. <Cite n={13} /> Use least privilege for the Atlassian connection. <Cite n={7} /> |

</Technical>
<Layman>

- **Reading only the title.** Fetch the whole story with its comments. <Cite n={8} /> <Cite n={6} />
- **Trusting Claude's guesses.** Ask for a quote behind each finding. Mark the rest as assumptions. This is the tutorial's advice.
- **Only happy paths.** Criteria cover good paths and error paths. <Cite n={1} />
- **Going beyond the story.** Tests cover the story, not more. <Cite n={1} /> Turn extra ideas into questions.
- **Checking the database in Then steps.** The result should be an observable output. <Cite n={17} />
- **Posting without review.** Use ask rules. <Cite n={18} /> A person reads each post first.
- **Too much access.** Plan mode does not edit your source. <Cite n={13} /> Give the Atlassian connection only the access it needs. <Cite n={7} />

</Layman>
<Bangla>

- **শুধু title বা key দেখে analysis:** comment-সহ পুরো story আনুন, `gh issue view 42 --json title,body,comments` দিয়ে, অথবা Jira MCP server দিয়ে। <Cite n={8} /> <Cite n={6} />
- **Claude-এর অনুমানকে rule ধরে নেওয়া:** প্রতিটি finding-এর পেছনে quote চান, বাকিগুলো assumption হিসেবে চিহ্নিত করুন (tutorial-এর পরামর্শ)।
- **শুধু positive criteria:** acceptance criteria-তে positive ও negative দুই ধরনের scenario থাকে। <Cite n={1} />
- **Story-র বাইরে যাওয়া:** test case story-কে cover করবে, তার বাইরে যাবে না। <Cite n={1} /> বাড়তি ধারণাকে প্রশ্ন বানান।
- **Then step-এ database যাচাই:** ফলাফল হওয়া উচিত বাইরে থেকে দেখা যায় এমন কিছু। <Cite n={17} />
- **Review ছাড়া ticket-এ post:** write tool-এর জন্য ask rule দিন। <Cite n={18} /> আগে একজন মানুষ প্রতিটি comment পড়বেন।
- **Analysis-কে write access দেওয়া:** plan mode source edit করে না। <Cite n={13} /> Atlassian connection-এ least privilege রাখুন। <Cite n={7} />

## Key words

| Term | Meaning |
|---|---|
| Test basis | The body of knowledge used as the basis for test analysis and test design |
| Requirement | A provision that contains criteria to be fulfilled |
| Testability | How well test conditions can be set up, and tests can show whether they are met |
| Test condition | A testable aspect of a component or system that is intended to be tested |
| Static testing | Testing in which the software under test does not need to be executed, for example a review of a story |
| Product risk | A risk that impacts the quality of a product |
| Acceptance criteria | The criteria that a work product must satisfy to be accepted by the stakeholders |
| User story | A short narrative of a need from a user's perspective, with the expected benefit |
| 3 Cs | Card, Conversation, and Confirmation: the three aspects of a user story |
| INVEST | Independent, Negotiable, Valuable, Estimable, Small, and Testable |
| ATDD | A collaboration-based, test-first approach that defines acceptance tests in the stakeholders' language |
| Plan mode | A Claude Code permission mode in which Claude researches and proposes, but does not edit source |
