# Test Execution & Bug Investigation

An agent can run your test cases in a real browser, call the API, and read the database. That saves time, but only if you can trust what it reports. This page shows how to pick a browser tool, check each result in three layers, keep evidence, find the cause of a failure, and write the results and the defect reports in a fixed shape that a person approves.

<PageMeta />

## Choose a browser tool for the agent

<Voices>
<Technical>

Three tools let Claude drive a browser. Each one fits a different job.

| Tool | What it is | Good for |
|---|---|---|
| agent-browser | A native Rust CLI. The agent drives the browser one shell command at a time. <Cite n={1} /> | Running written test cases step by step, with short calls |
| Playwright MCP | An MCP server. Claude works with pages through structured accessibility snapshots, not screenshots. <Cite n={2} /> | Long exploratory sessions that keep the browser state |
| Claude in Chrome | Claude Code connected to the Claude in Chrome extension in your own browser. <Cite n={3} /> | Debugging by hand, in a visible window |

**Context cost.** The Playwright MCP README says a CLI with skills is more token-efficient than MCP. It says MCP suits exploratory automation and long-running autonomous workflows. <Cite n={2} />

**Your login.** Claude in Chrome shares the login state of your browser. Its actions run in a visible Chrome window. <Cite n={3} /> It pauses at a login page or a CAPTCHA and asks you to handle it. <Cite n={3} />

**Limits of Claude in Chrome.** It works with Google Chrome and Microsoft Edge, and it is not supported in WSL. <Cite n={3} /> It needs a `/login` sign-in. With an API key or a long-lived token, Claude Code keeps it off. <Cite n={3} /> `claude setup-token` makes the long-lived token for CI and scripts, <Cite n={22} /> so a CI job that signs in with that token or an API key cannot use Claude in Chrome.

<Callout type="tip" title="The tutorial's advice">

Use agent-browser or Playwright MCP to run test cases. Use Claude in Chrome when you debug one failure with your own eyes. Never point any of them at production. The [Browser Testing with Playwright](/automate/playwright/) page sets up Playwright MCP in detail.

</Callout>

</Technical>

## Drive the browser with agent-browser

<Voices>
<Technical>

**Install.** The README gives two commands. The second one downloads Chrome for Testing the first time. <Cite n={1} />

```bash
npm install -g agent-browser
agent-browser install
```

**The loop.** `snapshot` returns the page as compact text, with a ref such as `@e1` for each element. The agent acts on a ref, reads the page again, and repeats. <Cite n={1} /> The browser stays open between commands. <Cite n={1} /> The README's quick start looks like this: <Cite n={1} />

```bash
agent-browser open example.com
agent-browser snapshot -i       # interactive elements, each with a ref
agent-browser click @e1         # act on a ref from that snapshot
agent-browser get url           # check the result
agent-browser close
```

**Rules that matter for testing:**

- A ref describes the page at the time of the snapshot. After a navigation or a DOM change, take a new snapshot. <Cite n={1} />
- A click fails, and does not report success, when the target is hidden, disabled, outside the viewport, or covered. <Cite n={1} /> A failed click is a finding, not noise.
- Each `--session` gets its own daemon and browser. <Cite n={1} /> Use one session per test user.

**Commands for evidence.** The capture group has `screenshot`, `pdf`, `record`, `download`, and `diff`. The debug group has `console` and `errors`. The page state group has `network`. <Cite n={1} />

**Teach the agent.** `agent-browser skills get core` prints the core loop and common workflows for the installed version. <Cite n={1} /> `agent-browser mcp` starts an MCP server over stdio, for an MCP client. <Cite n={1} />

</Technical>
<Layman>

You install agent-browser with `npm install -g agent-browser`. Then `agent-browser install` downloads a test copy of Chrome. <Cite n={1} />

The agent works in a loop. `snapshot` gives the page as short text. Each element gets a label, called a ref, such as `@e1`. The agent clicks a ref, reads the page again, and repeats. The browser stays open between commands. <Cite n={1} />

Three rules help in testing:

- A ref is only good for the page it came from. After the page changes, take a new snapshot. <Cite n={1} />
- A click fails if the target is hidden, disabled, off screen, or covered. <Cite n={1} /> Treat that as a finding.
- Each `--session` has its own browser. <Cite n={1} /> Use one session for each test user.

For evidence, use `screenshot`, `record`, `console`, `errors`, and `network`. <Cite n={1} /> `agent-browser skills get core` teaches the agent the basic loop. <Cite n={1} />

</Layman>
<Bangla>

`npm install -g agent-browser` দিয়ে install করুন। তারপর `agent-browser install` প্রথমবার Chrome for Testing download করে। <Cite n={1} />

Agent একটি loop-এ কাজ করে। `snapshot` page-টিকে ছোট text হিসেবে দেয়, আর প্রতিটি element-কে `@e1`-এর মতো একটি ref দেয়। Agent একটি ref-এ কাজ করে, page আবার পড়ে, তারপর আবার করে। Command-এর মাঝে browser খোলা থাকে। <Cite n={1} />

Testing-এর জন্য তিনটি নিয়ম:

- Ref শুধু snapshot নেওয়ার সময়ের page-এর জন্য ঠিক। Navigation বা DOM change-এর পরে নতুন snapshot নিন। <Cite n={1} />
- Target hidden, disabled, viewport-এর বাইরে বা ঢাকা থাকলে click fail করে। <Cite n={1} /> এটিকে finding হিসেবে ধরুন।
- প্রতিটি `--session`-এর নিজের daemon আর browser আছে। <Cite n={1} /> প্রতিটি test user-এর জন্য আলাদা session নিন।

Evidence-এর জন্য `screenshot`, `record`, `console`, `errors` আর `network` ব্যবহার করুন। <Cite n={1} /> `agent-browser skills get core` agent-কে মূল loop শেখায়। <Cite n={1} />

</Bangla>

## Check the result in three layers

<Voices>
<Technical>

A green screen does not prove that the data is right. The tutorial suggests three checks for each test case that changes data:

1. **UI.** Read the visible result from a fresh snapshot.
2. **API.** Call the endpoint that returns the same data, and compare.
3. **Database.** Run one read-only query, and compare again.

**The test environment.** ISTQB defines a test environment as an environment containing hardware, instrumentation, simulators, software tools, and other support elements needed to perform a test. <Cite n={4} /> Name it in the prompt, for example `https://staging.example.com`. Never let the agent run against production.

**Test data.** ISTQB defines test data as data needed for test execution. <Cite n={5} /> The tutorial suggests this order: create the data before the run, use only test accounts, and remove or reset the data after the run. Write each step down, so a person can repeat it.

**API checks.** Playwright Test has a built-in `request` fixture. It respects options such as `baseURL` and `extraHTTPHeaders`. <Cite n={6} /> The tutorial also uses a plain `curl` call for a quick check.

**Database checks.** Give the agent read-only access. One example is the MySQL MCP server:

- `MCP_PERMISSIONS=list,read,utility` keeps only the list, read, and utility tools. <Cite n={7} />
- `MCP_REQUIRE_READONLY_DB_USER=true` makes the server fail at startup if the MySQL user can write. <Cite n={7} />
- Every tool reports `readOnlyHint` and `destructiveHint`. <Cite n={7} />

<Callout type="warning" title="The tutorial's rule">

Use a database user that can only read, in a test environment. Keep the password in an environment variable such as `${DB_PASSWORD}`, never in a prompt or a report.

</Callout>

</Technical>
<Layman>

A good screen does not prove the data is right. The tutorial suggests three checks:

1. **UI.** Read the result on the page.
2. **API.** Ask the server for the same data.
3. **Database.** Read the stored row and compare.

ISTQB calls the place where you test the test environment. It has the hardware, instrumentation, simulators, software tools, and other support elements that a test needs. <Cite n={4} /> Tell the agent its address, such as `https://staging.example.com`. Never test on production.

Test data is the data a test run needs. <Cite n={5} /> The tutorial suggests: make the data first, use test accounts only, and clean up after.

For the API, Playwright Test has a `request` fixture. It uses your settings such as `baseURL`. <Cite n={6} /> The tutorial also uses `curl` for a quick check.

For the database, give read-only access. The MySQL MCP server can keep only the list, read, and utility tools with `MCP_PERMISSIONS=list,read,utility`. It can also refuse to start if its database user can write. <Cite n={7} /> Keep the password in a variable such as `${DB_PASSWORD}`.

</Layman>
<Bangla>

Screen-এ সফল দেখালেই data ঠিক, তা প্রমাণ হয় না। Tutorial তিনটি check-এর পরামর্শ দেয়:

1. **UI.** নতুন snapshot থেকে দৃশ্যমান result পড়ুন।
2. **API.** একই data ফেরত দেয় এমন endpoint call করে মিলিয়ে দেখুন।
3. **Database.** একটি read-only query চালিয়ে আবার মিলিয়ে দেখুন।

ISTQB-এর মতে test environment হলো test চালাতে যে hardware, instrumentation, simulator, software tool আর অন্যান্য সহায়ক উপাদান লাগে। <Cite n={4} /> Prompt-এ environment-এর নাম দিন, যেমন `https://staging.example.com`। Production-এ কখনো চালাবেন না।

ISTQB-এর মতে test data হলো test execution-এর জন্য দরকারি data। <Cite n={5} /> Tutorial-এর পরামর্শ: run-এর আগে data তৈরি করুন, শুধু test account ব্যবহার করুন, আর run-এর পরে data মুছে বা reset করে দিন।

API check-এর জন্য Playwright Test-এ built-in `request` fixture আছে, যেটি `baseURL` আর `extraHTTPHeaders` মেনে চলে। <Cite n={6} /> দ্রুত check-এর জন্য tutorial `curl`-ও ব্যবহার করে।

Database-এ agent-কে শুধু read-only access দিন। MySQL MCP server-এ `MCP_PERMISSIONS=list,read,utility` শুধু list, read আর utility tool রাখে। `MCP_REQUIRE_READONLY_DB_USER=true` থাকলে MySQL user write করতে পারলে server চালু হয় না। <Cite n={7} /> Password `${DB_PASSWORD}`-এর মতো environment variable-এ রাখুন, prompt বা report-এ নয়।

</Bangla>
</Voices>

## Collect evidence

<Voices>
<Technical>

The CTFL syllabus says a defect report holds the test steps and any relevant test logs, database dumps, screenshots, or recordings. <Cite n={8} /> So collect them while the test runs, not later.

| Evidence | How to get it |
|---|---|
| Screenshot or recording | agent-browser `screenshot` and `record` <Cite n={1} />. Playwright MCP `browser_take_screenshot`. <Cite n={2} /> |
| Console log | agent-browser `console` and `errors` <Cite n={1} />. Playwright MCP `browser_console_messages`, with a `level` and a `filename` to save it. <Cite n={2} /> |
| Network log | agent-browser `network` <Cite n={1} />. Playwright MCP `browser_network_requests`, with a `filter` regexp and a `filename`. <Cite n={2} /> |
| Database result | The query and its rows, from a read-only user |
| Run facts | The time, the environment URL, the build or commit, and the test user role |

**Where files go.** Playwright MCP `--output-dir` sets the folder for files that get an automatic name, such as a screenshot with no file name. <Cite n={2} /> `--isolated` keeps the browser profile in memory, not on disk. <Cite n={2} /> The tutorial suggests one folder per run, for example `evidence/<run-id>/<test-id>/`.

**Keep secrets out.** Playwright MCP `--redact-url-params` replaces the values of named URL parameters with `<redacted>` in tool responses. <Cite n={2} /> A Claude in Chrome GIF captures everything visible, including account details on logged-in pages. Review it before you share it outside your team. <Cite n={3} />

**Ask for focus.** The Claude in Chrome docs say to tell Claude what console patterns to look for, because logs can be verbose. <Cite n={3} />

<Callout type="tip" title="The tutorial's checklist">

Before you close a test case, check that each piece of evidence has the test id, a time, and the build. Remove tokens, passwords, and personal data from logs and screenshots.

</Callout>

</Technical>

Check it before you share it outside your team. <Cite n={3} />

</Layman>

## Investigate a failure

<Voices>
<Technical>

In test execution, actual results are compared with expected results. The results are logged, and anomalies are analyzed to find their likely causes. <Cite n={8} /> Use the ISTQB words, so the team means the same thing:

| Term | ISTQB meaning |
|---|---|
| Failure | An event in which a component or system does not meet its requirements within specified limits during its execution <Cite n={9} /> |
| Defect | An imperfection or deficiency in a work product. "Bug" is a synonym. <Cite n={10} /> |
| False-positive result | A defect is reported, but no such defect exists in the test object <Cite n={11} /> |
| False-negative result | The test fails to find a defect that is present <Cite n={12} /> |
| Root cause analysis | The process used to find the root cause of a defect <Cite n={13} /> |

The syllabus also says a reported anomaly may turn out to be a real defect or something else. <Cite n={8} /> So the tutorial asks you to check each finding before you report it.

**The tutorial's method** for one failure:

1. **Reproduce.** Run the steps again in a fresh session. Cut every step that is not needed.
2. **Isolate the layer.** Ask where the result first goes wrong.
3. **Find the cause.** Read the logs and the code. Ask Claude to explain, not to fix.
4. **Decide.** Defect, false positive, or a problem with the environment or the test.

| If this is true | The layer is probably |
|---|---|
| The API returns the right data, but the page shows it wrong | UI |
| The API returns wrong data, or the wrong status | API or business logic |
| The API and the page agree, but the stored row is wrong | Data |
| The same steps pass on another environment | Environment |
| A manual run passes, and the agent run fails | The test or the agent |

</Technical>
<Layman>

When a test runs, you compare what happened with what should happen. You log the result. Then you look for the likely cause of anything odd. <Cite n={8} />

- A **defect** is a fault in a work product. "Bug" means the same. <Cite n={10} />
- A **false-positive result** reports a defect that is not there. <Cite n={11} />
- A **false-negative result** misses a defect that is there. <Cite n={12} />

- **Failure**: একটি ঘটনা, যেখানে execution-এর সময় component বা system নির্দিষ্ট সীমার মধ্যে তার requirement পূরণ করে না। <Cite n={9} />
- **Defect**: একটি work product-এর ত্রুটি। "Bug" এর সমার্থক। <Cite n={10} />
- **False-positive result**: defect report হয়েছে, কিন্তু test object-এ এমন কোনো defect নেই। <Cite n={11} />

<Voices>

## Guardrails while tests run

<Voices>
<Technical>

The tutorial's concern: a test agent can see the code, so when a test fails, it may try to "fix" the app so that the test passes. Block that with permission rules and a hook. See [Hooks](/extend/hooks/) for more.

**Permission rules.** Rules are evaluated in order: deny, then ask, then allow. The first match decides. <Cite n={20} /> Ask rules prompt for confirmation. <Cite n={20} /> File edits are checked against `Edit(path)` rules, and an `Edit` rule also covers `Write`. <Cite n={20} /> Bash rules match the whole command text, with `*` for any text. <Cite n={20} /> `mcp__<server>__*` matches every tool of one MCP server. <Cite n={20} />

The `permissions` object of a settings file takes `allow`, `ask`, and `deny` arrays. <Cite n={23} /> Example `.claude/settings.json` for a test run (the paths and the `jira` server name are examples):

```json
{
  "permissions": {
    "deny": ["Edit(/src/**)", "Edit(/api/**)"],
    "ask": ["Bash(gh issue create *)", "mcp__jira__*"]
  }
}
```

**A hook.** A `PreToolUse` hook runs before a tool call and can block it. Exit code 2 blocks the action. <Cite n={21} /> The hooks guide shows a script that a `PreToolUse` hook in `.claude/settings.json` runs before each `Edit` or `Write` call. It exits 2 for a protected path. <Cite n={21} /> Hook decisions do not bypass deny and ask rules. <Cite n={20} />

**Shell commands.** The hooks guide warns that Claude can still change protected files with shell commands. <Cite n={21} /> So keep the deny rules too, and do not allow broad Bash patterns during a test run.

<Callout type="warning" title="The tutorial's rule">

During execution, the agent reads code and runs tests. It does not edit application code, write to the database, or file a defect without your approval. If a fix is needed, that is a separate task with a separate review.

</Callout>

</Technical>

1. Pick five test cases, for example on a deposit.
2. Add the deny and ask rules from the section above.
3. Ask Claude to run them with agent-browser. Ask it to check the page, the API, and one read-only database query. Ask it to save a screenshot, the console errors, and the network log for each case.
4. Open the evidence folder. Check one balance yourself.
5. Ask Claude to repeat one failure in a fresh session and name the layer.
6. Draft one defect report with the template. Search for a copy first with `gh issue list --search`. <Cite n={15} /> Read and approve it before `gh issue create` files it. <Cite n={16} />

You are done when the results file has five rows with a status and evidence, and the report has steps, results, and evidence. No file may hold a password or a token.

## Common mistakes

<Voices>
<Technical>

1. **Trusting the UI alone.** The page says "Success", but the stored data is wrong. Fix: check the UI, the API, and the database for each case (the tutorial's advice).
2. **Reusing old refs.** A ref describes the page at the time of its snapshot. <Cite n={1} /> Fix: take a new snapshot after each navigation or DOM change.
3. **Reporting a false positive.** A reported anomaly may turn out to be something other than a real defect. <Cite n={8} /> Fix: reproduce it in a fresh session before you draft a report.
4. **Letting the agent fix the app.** A changed app hides the defect. Fix: deny `Edit` on the application folders. Remember that the hooks guide says shell commands can still change files. <Cite n={21} />
5. **Secrets in the evidence.** A Chrome GIF captures account details on logged-in pages. <Cite n={3} /> Fix: use test accounts, `--redact-url-params` in Playwright MCP <Cite n={2} />, and read each file before you share it.
6. **Filing without review.** A filed issue reaches the whole team at once. Fix: an ask rule for the filing tool <Cite n={20} />, and a duplicate search first. <Cite n={15} />
7. **A database user that can write.** Fix: a read-only user, and `MCP_REQUIRE_READONLY_DB_USER=true` on the MySQL MCP server. <Cite n={7} />

</Technical>
<Layman>

1. **Trusting the page alone.** It may say "Success" while the data is wrong. The tutorial says: check the page, the API, and the database.
2. **Using an old ref.** A ref is only good for its snapshot. <Cite n={1} /> Take a new snapshot after the page changes.
3. **Reporting a false alarm.** A problem may not be a real defect. <Cite n={8} /> Repeat it in a fresh session first.
4. **Letting the agent fix the app.** That hides the bug. Deny edits to the app folders. Shell commands can still change files, so keep the deny rules. <Cite n={21} />
5. **Secrets in the evidence.** A Chrome GIF shows account details on logged-in pages. <Cite n={3} /> Use test accounts and hide URL secrets with `--redact-url-params`. <Cite n={2} />
6. **Filing without review.** Add an ask rule for the filing tool. <Cite n={20} /> Search for a copy first. <Cite n={15} />
7. **A database user that can write.** Use a read-only user. The MySQL MCP server can refuse to start with a user that can write. <Cite n={7} />

</Layman>

1. **শুধু UI-তে বিশ্বাস করা।** Page "Success" দেখায়, কিন্তু data ভুল। সমাধান: প্রতিটি case-এ UI, API আর database check করুন (tutorial-এর পরামর্শ)।

7. **Write করতে পারে এমন database user।** সমাধান: read-only user, আর MySQL MCP server-এ `MCP_REQUIRE_READONLY_DB_USER=true`। <Cite n={7} />

## Key words

| Term | Meaning |
|---|---|
| Failure | An event in which a component or system does not meet its requirements within specified limits during its execution |
| Defect | An imperfection or deficiency in a work product; "bug" is a synonym |
| False-positive result | A result that reports a defect that does not exist in the test object |
| False-negative result | A result that misses a defect that is present in the test object |
| Root cause analysis | The process used to find the root cause of a defect |
| Test environment | An environment containing hardware, instrumentation, simulators, software tools, and other support elements needed to perform a test |
| Test data | Data needed for test execution |
| Test log | A chronological record of relevant details about test execution |
| Defect report | Documentation of the occurrence, nature, and status of a defect |
| Ref | The id, such as `@e1`, that an agent-browser snapshot gives each element; valid only for that snapshot |
| Ask rule | A permission rule that makes Claude Code ask for confirmation before a tool call |
