An agent can only test what it can reach. This page sets up a real practice project, then connects Claude Code to the three systems that a tester uses every day: the issue tracker, the test database, and the code host. The tutorial gives each connection only the access that the work needs.

## Install and run dMoney

<Voices>
<Technical>

**Prerequisites.** Node.js 20.x or newer, npm, and MySQL 8.x or a compatible MariaDB. You need a Stripe test account only for the bank cash-in feature. SMTP is optional, because the API also prints OTPs to its console. If a step needs a tool that you do not have, read along and come back later.

**1. Clone and create the database.** Clone the repository, then create the database:

```sql
CREATE DATABASE dmoneydb;
```

**2. Restore the dump.** Import `sql_scripts/local-dmoneydb-202604201925.sql` into `dmoneydb` with any MySQL client. The dump was exported on Windows, so its table names are lowercase. On Linux, follow the README's rename step before the import. Restoring is optional: with an empty `dmoneydb`, the API creates the tables and seeds the test accounts on first start.

**3. Configure the API.** In `dmoney-transaction-api/`, copy `.env.example` to both `.env` and `.env.dev`. `db.js` reads `.env.dev`, and the rest of the code reads `.env`. Set the same database values in both files:

```bash
DB_HOST=localhost
DB_NAME=dmoneydb
DB_USER=<your-mysql-user>
DB_PASSWORD=<your-mysql-password>
```

**4. Start the API.** Run `npm install`, then `npm run dev` (nodemon). The API listens on `PORT`, default 5000. Check it with `GET http://localhost:5000/`.

**5. Configure and start the web app.** In `dmoney-web-react/`, copy `.env.example` to `.env`. Set `NEXT_PUBLIC_API_URL`, `NEXT_PUBLIC_SECRET_KEY`, and `NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY` from the README and your own Stripe test account. Run `npm install` and `npm run dev`. The app opens at `http://localhost:3000`.

**6. Find the test accounts.** They are in the "Test accounts" section of the README and in `dmoney-transaction-api/endpoints.md`. For an Agent, Customer, or Merchant login, the OTP shows in the API console.

<Callout type="warning" title="The tutorial's advice">

The README and the env files hold practice values. Keep your own `.env` files out of git, and never paste their values into a prompt, a ticket, or a page. This page shows only placeholders such as `<your-mysql-password>`.

</Callout>

</Technical>

## MCP scopes and .mcp.json

<Voices>
<Technical>

MCP (Model Context Protocol) is an open-source standard for connecting AI applications to external systems. <Cite n={1} /> Claude Code adds servers with `claude mcp add`. <Cite n={2} />

```bash
# A remote server
claude mcp add --transport http <name> <url>
# A local stdio server: everything after -- goes to the server
claude mcp add [options] <name> -- <command> [args...]
```

The scope decides where the server is stored and who gets it: <Cite n={2} />

| Scope | Flag | Stored in | Who gets it |
|---|---|---|---|
| Local (default) | `--scope local` | `~/.claude.json` | You, in this project only <Cite n={2} /> |
| Project | `--scope project` | `.mcp.json` in the project root | Everyone, through version control <Cite n={2} /> |
| User | `--scope user` | `~/.claude.json` | You, in all your projects <Cite n={2} /> |

- `--scope project` creates or updates `.mcp.json`. <Cite n={2} />
- In an interactive session, Claude Code asks you to approve each `.mcp.json` server before it uses it. `claude mcp reset-project-choices` resets your choices. <Cite n={2} /> In a `claude -p` run, it loads them without asking. <Cite n={2} />
- Verify that you trust each server before you connect it. <Cite n={2} />

### Keep secrets out of git

`.mcp.json` expands `${VAR}` and `${VAR:-default}` in `command`, `args`, `env`, `url`, and `headers`. <Cite n={2} /> So the team commits the file, and each tester keeps the secret in the shell.

- An unset variable with no default does not stop the config. `claude mcp list` shows a missing-variable warning. <Cite n={2} />
- An empty string counts as set, so `${VAR:-default}` then gives the empty string. <Cite n={2} />

The dMoney `.mcp.json` puts the database password in `${DMONEY_DB_PASS:-}`. The default is empty, so with the variable unset the server tries an empty password.

The [MCP Servers](/extend/mcp/) page covers transports, OAuth, and trust in more detail.

</Technical>
<Layman>

MCP (Model Context Protocol) is an open standard. It connects AI apps to other systems. <Cite n={1} /> You add a server to Claude Code with `claude mcp add`. <Cite n={2} />

The scope says who gets the server: <Cite n={2} />

- **Local** is the default. Only you get it, in this project only.
- **Project** writes the server to `.mcp.json` in the project folder. Everyone who clones the repository gets it.
- **User** is for you, in all your projects.

In a normal, interactive session, Claude Code asks you to approve each server from `.mcp.json` before it uses it. A `claude -p` run does not ask. <Cite n={2} /> Trust a server before you connect it. <Cite n={2} />

Do not write a password into `.mcp.json`. Write `${VAR}` instead. Claude Code fills in the value of the environment variable (a value that you set in your shell). <Cite n={2} /> If the variable is missing and has no default, `claude mcp list` warns you. An empty value still counts as set. <Cite n={2} />

The dMoney file uses `${DMONEY_DB_PASS:-}`. Its default is empty, so an unset variable gives an empty password.

</Layman>

## Check servers, sign in, and watch the context

<Voices>
<Technical>

**Check from the shell.** `claude mcp list` shows a health status next to each server, such as `✔ Connected`, `! Needs authentication`, or `✘ Failed to connect`. <Cite n={2} /> A `.mcp.json` server that you have not approved yet shows `⏸ Pending approval`. <Cite n={2} /> To check one server, run `claude mcp get <name>`. <Cite n={2} />

```bash
claude mcp list
claude mcp get jira
```

**Check and sign in from a session.** `/mcp` manages server connections and OAuth sign-in. It also takes `reconnect`, `enable`, and `disable`. <Cite n={3} /> Claude Code supports OAuth 2.0 for remote servers. <Cite n={2} /> A `claude -p` run cannot do the OAuth flow, so sign in first from an interactive session: `/mcp` in the session, or `claude mcp login <name>` in the shell. <Cite n={2} />

**Context cost.** Tool search is on by default. It defers tool definitions until Claude needs them, so only tool names and server instructions load at session start. <Cite n={2} /> Large tool results still cost context. Claude Code warns when an MCP tool output exceeds 10,000 tokens, and it limits output to 25,000 tokens by default. `MAX_MCP_OUTPUT_TOKENS` changes the limit. <Cite n={2} />

`/context` shows the current context usage as a colored grid. <Cite n={3} /> Run it after you connect a server, and again after a large query.

<Callout type="tip" title="The tutorial's advice">

Ask for small results. Add a limit to a Jira search and to a SQL query, and ask for the columns that you need. A short result keeps room in the context for the test work.

</Callout>

</Technical>
<Layman>

Inside a session, `/mcp` manages the connections and the sign-in. <Cite n={3} /> Sign-in uses OAuth. <Cite n={2} /> A `claude -p` run cannot sign in, so sign in from a normal session first. <Cite n={2} />

Claude's context is limited. Tool search is on by default. Claude loads only the tool names and server instructions at the start, and the full tool details when it needs them. <Cite n={2} /> Big tool results still take space. Claude Code warns above 10,000 tokens. <Cite n={2} /> `/context` shows how full the context is. <Cite n={3} />

The tutorial's advice: ask for small results, with a limit.

</Layman>

## Jira through the Atlassian MCP server

<Voices>

## The test database through MySQL MCP

<Voices>
<Technical>

The dMoney `.mcp.json` runs the MySQL MCP server `@berthojoris/mcp-mysql-server@1.43.2` with the permission list `list,read,utility,create,update,delete,execute`. The README of dMoney lists only `playwright` and `jira` as the project servers, and it describes a separate user-level `dmoneydb` server as read-only. It does not describe this project server, whose list includes write actions. The [What to Fix in the Setup](/case-study/lessons/) page records this finding.

**What the permissions mean.** The server takes the connection string, then a permission list, then an optional category list. <Cite n={7} />

| Permission | Allows |
|---|---|
| `list` | Listing databases, tables, and schemas <Cite n={7} /> |
| `read` | SELECT queries <Cite n={7} /> |
| `utility` | Connection tests and diagnostics <Cite n={7} /> |
| `create`, `update`, `delete` | INSERT, UPDATE, and DELETE of records <Cite n={7} /> |
| `execute` | Custom INSERT and UPDATE SQL <Cite n={7} /> |
| `ddl` | CREATE, ALTER, and DROP of tables <Cite n={7} /> |

Since v1.44.0, a server with no permissions and no categories enables only `list,read,utility`. <Cite n={7} /> dMoney pins 1.43.2, and it passes its own list, so that default does not help it.

**A read-only version.** This example keeps the dMoney entry, pins version 1.46.0, and lists only the read permissions. It takes the user and the password from your shell:

```json
{
  "mcpServers": {
    "dmoney-db": {
      "type": "stdio",
      "command": "npx",
      "args": [
        "-y",
        "@berthojoris/mcp-mysql-server@1.46.0",
        "mysql://${DMONEY_DB_USER}:${DMONEY_DB_PASS}@localhost:3306/dmoneydb",
        "list,read,utility"
      ]
    }
  }
}
```

- Versions 1.43.3 and 1.43.4 tightened the permission checks. For example, `EXPLAIN ANALYZE` runs the statement it wraps (MySQL 8.0.18 and later), so since v1.43.4 it needs that statement's permission. <Cite n={7} /> The tutorial suggests a version with these changes, such as 1.46.0, for a read-only setup.
- From v1.44.0, `WITH` (CTE) queries are supported, and in read queries they need `execute`, so a read-only list cannot run them. <Cite n={7} /> Write the query without `WITH`.
- `MCP_REQUIRE_READONLY_DB_USER=true` makes the server fail at startup if the MySQL user can write. <Cite n={7} />
- Ask Claude to call `list_all_tools` first. It returns the enabled tools and the active permission profile. <Cite n={7} />

<Callout type="danger" title="The tutorial's advice: a SELECT-only user">

The permission list is the first lock. A database user that has only the SELECT privilege is the second. Create one for Claude, and point the server at it. Never connect Claude to a production database.

</Callout>

</Technical>
<Layman>

## GitHub through the gh CLI

<Voices>
<Technical>

GitHub CLI (`gh`) is GitHub on the command line, for macOS, Windows, and Linux. <Cite n={8} /> The README lists Homebrew for macOS, Debian, Ubuntu, and RPM packages for Linux, and WinGet for Windows. GitHub-hosted runners have it pre-installed. <Cite n={8} />

**Sign in.** `gh auth login` uses a web browser flow by default and stores the token in the system credential store. <Cite n={9} /> `--with-token` reads a classic token from standard input. For a fine-grained token, the manual favours `GH_TOKEN`. <Cite n={9} />

**Read commands** (safe to allow):

| Command | What it shows |
|---|---|
| `gh issue view 7 --comments` | The title, body, and other data of an issue, with its comments <Cite n={10} /> |
| `gh issue list --state all --label bug` | Issues filtered by state and label. The default is open issues only. <Cite n={11} /> |
| `gh pr view 8` | The title, body, and other data of a pull request <Cite n={12} /> |
| `gh pr diff 8 --name-only` | The changes of a pull request, here only the file names <Cite n={13} /> |

**Write commands** (ask first): `gh issue create --title ...` creates an issue. <Cite n={14} /> `gh pr create --draft` creates a pull request as a draft. <Cite n={15} />

**Let Claude use gh through Bash.** Claude Code evaluates rules in this order: deny, then ask, then allow. <Cite n={16} /> Put the `*` after the subcommand: `Bash(git *)` allows every git command. <Cite n={16} /> A trailing ` *` also matches the bare command. <Cite n={16} /> The `permissions` object of a settings file takes `allow`, `ask`, and `deny` arrays. <Cite n={20} /> This example, the tutorial's own, lets Claude read without a prompt and asks before each write:

```json
{
  "permissions": {
    "allow": [
      "Bash(gh issue view *)",
      "Bash(gh issue list *)",
      "Bash(gh pr view *)",
      "Bash(gh pr diff *)"
    ],
    "ask": [
      "Bash(gh issue create *)",
      "Bash(gh pr create *)"
    ]
  }
}
```

An ask rule applies when any subcommand matches it, also inside a chained command. <Cite n={16} />

</Technical>

## Common mistakes

<Voices>
<Technical>

| Mistake | Fix |
|---|---|
| A password written into `.mcp.json` and committed | Use `${VAR}` in `args`, `env`, `url`, or `headers`, and set the value in your shell. <Cite n={2} /> |
| An empty default such as `${DMONEY_DB_PASS:-}` hides a missing value | Leave out the default, so `claude mcp list` warns when the variable is unset. An empty value counts as set. <Cite n={2} /> |
| A database server with write permissions | Use `list,read,utility` <Cite n={7} />, and, as the tutorial advises, a SELECT-only database user. See [What to Fix in the Setup](/case-study/lessons/). |
| The old Atlassian SSE endpoint `/v1/sse` | It is not supported after 30 June 2026. Use `https://mcp.atlassian.com/v2/mcp`. <Cite n={4} /> |
| Jira tools missing in a `claude -p` run | Sign in first from an interactive session with `/mcp` or `claude mcp login <name>`. <Cite n={2} /> |
| `Bash(gh *)` in `allow` | It allows every `gh` command, writes too. Put the `*` after the subcommand. <Cite n={16} /> |
| One server under two names | The tutorial's advice: keep the server names of `.mcp.json` (`jira`, `dmoney-db`) in the skills, agents, and rules, so `mcp__jira` matches. <Cite n={16} /> |

</Technical>

## Key words

| Term | Meaning |
|---|---|
| MCP | An open-source standard for connecting AI applications to external systems |
| Scope | Where Claude Code stores an MCP server and who gets it: local (default), project, or user |
| `.mcp.json` | The file in the project root that holds the project-scoped servers. Claude Code asks you to approve them in an interactive session. |
| Variable expansion | `${VAR}` and `${VAR:-default}` in `.mcp.json`, so secrets stay in your shell and out of git |
| `/mcp` | The session command that manages MCP connections and OAuth sign-in |
| Tool search | Loads only tool names and server instructions at start, and the full definitions when Claude needs them |
| Atlassian MCP Server | Atlassian's cloud-based MCP server. It connects your Atlassian Cloud site to compatible external tools and acts with your existing permissions. |
| JQL | The Jira Query Language, which `searchJiraIssuesUsingJql` uses to search Jira work items |
| Permission list | The MySQL MCP argument that sets what Claude may do. `list,read,utility` is read-only. |
| `gh` | GitHub CLI: GitHub on the command line, with read commands such as `gh issue view` and write commands such as `gh pr create` |
| Permission rule | An allow, ask, or deny entry in settings. Claude Code checks deny, then ask, then allow. |
| `CLAUDE.md` | The notes file of a project. In a subdirectory, it loads when Claude works on a file there. |
