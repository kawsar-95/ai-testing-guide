# Test Design & Blast Radius

A change rarely breaks only the lines that it touches. This page shows how to work with Claude to find what a change can affect, which this tutorial calls its blast radius, and how to turn acceptance criteria and that impact map into scenarios and structured test cases. You learn which tools trace callers and dependents, which scenario categories a money transfer needs, and how to check what Claude writes before you trust it.

## From acceptance criteria to test cases

<Voices>
<Technical>

The ISTQB test process gives one activity to each question. <Cite n={1} />

- **Test analysis** answers "what to test?". It analyzes the test basis to find testable features. It defines test conditions and prioritizes them by risk. <Cite n={1} />
- **Test design** answers "how to test?". It turns test conditions into test cases and other testware, such as test charters. <Cite n={1} />
- Test design also defines the test data requirements and designs the test environment. <Cite n={1} />

A **test condition** is "a testable aspect of a component or system that is intended to be tested". <Cite n={2} /> The syllabus names acceptance criteria as an example of a test condition. <Cite n={1} /> A **test case** is a set of preconditions, inputs, actions, expected results, and postconditions, developed from test conditions. <Cite n={3} />

So the chain on this page has three steps. The example column is the tutorial's own.

| Step | What it is | Example for a money transfer |
|---|---|---|
| Acceptance criterion | A test condition <Cite n={1} /> | "A customer cannot send more than the daily limit." |
| Scenario | The tutorial's word for one situation to test | Send an amount that crosses the daily limit |
| Test case | Preconditions, inputs, actions, expected results, postconditions <Cite n={3} /> | The used amount, the exact amount sent, the steps, the status, and both balances |

This page does not repeat the techniques. [Test Design with Claude](/foundations/test-design/) and [Black-Box Techniques](/fundamentals/black-box/) explain them. [Requirement Analysis & Acceptance Criteria](/agentic-qa/requirements/) shows how to get good criteria. This page adds the question that a code change brings: what else can break?

</Technical>
<Layman>

Testers answer two questions before they write tests. <Cite n={1} />

- **Test analysis** finds out what to test. You read the test basis and list the things to check. You rank them by risk.
- **Test design** finds out how to test. You turn each thing to check into test cases.

A **test condition** is one thing in the system that you intend to test. <Cite n={2} /> An acceptance criterion is one example. <Cite n={1} /> A **test case** gives the starting state, the inputs, the actions, the expected results, and the end state. <Cite n={3} />

This page follows one chain: a criterion, then a scenario (one situation to test), then a test case. The test techniques are on [Test Design with Claude](/foundations/test-design/). This page adds one question: when the code changes, what else can break?

</Layman>
<Bangla>

ISTQB test process-এ দুটি প্রশ্নের জন্য দুটি আলাদা কাজ আছে। <Cite n={1} />

- **Test analysis** উত্তর দেয় "কী test করবেন?"। এটি test basis বিশ্লেষণ করে testable feature খুঁজে বের করে, test condition ঠিক করে এবং risk অনুযায়ী সেগুলোর অগ্রাধিকার দেয়।
- **Test design** উত্তর দেয় "কীভাবে test করবেন?"। এটি test condition-কে test case ও অন্যান্য testware-এ (যেমন test charter) রূপ দেয়। এটি test data-র প্রয়োজন এবং test environment-ও ঠিক করে।

**Test condition** হলো কোনো component বা system-এর এমন একটি দিক, যা test করার উদ্দেশ্য আছে। <Cite n={2} /> Syllabus acceptance criteria-কে test condition-এর একটি উদাহরণ বলে। <Cite n={1} /> **Test case** হলো precondition, input, action, expected result এবং postcondition-এর একটি সেট, যা test condition থেকে তৈরি হয়। <Cite n={3} />

এই পেজের ধারা তিন ধাপের: acceptance criterion, তারপর scenario (test করার একটি পরিস্থিতি, tutorial-এর নিজের শব্দ), তারপর test case। Technique-গুলো এখানে আবার বলা হয়নি; সেগুলো [Test Design with Claude](/foundations/test-design/) পেজে আছে। এই পেজ একটি নতুন প্রশ্ন যোগ করে: code বদলালে আর কী ভাঙতে পারে?

</Bangla>
</Voices>

## Blast radius is impact analysis

<Voices>
<Technical>

This tutorial uses "blast radius" for the result of an impact analysis on one change.

- **Impact analysis** is "the identification of all work products affected by a change, including an estimate of the resources needed to accomplish the change". <Cite n={4} />
- **Regression testing** is change-related testing that detects whether defects have been introduced or uncovered in unchanged areas of the software. <Cite n={5} />
- A change can harm the same component, other components in the same system, or other connected systems. The syllabus advises an impact analysis first, to find the extent of the regression testing. <Cite n={1} />

**Maintenance testing** is the same idea for a system in operation. Its scope typically depends on the risk of the change, the size of the system, and the size of the change. <Cite n={1} /> It checks the change and looks for regressions in the unchanged parts, which are usually most of the system. <Cite n={1} /> Its triggers include modifications such as hot fixes, upgrades or migrations of the environment, and retirement. When data from another application is migrated into the system, data conversion can need tests. <Cite n={1} />

<Callout type="tip" title="The tutorial's impact map">

Ask Claude to sort every finding into three rings. Each row names its evidence as `file:line`.

```markdown
## Impact map: <PR or commit>
| Ring | Item | Evidence (file:line) | Entry point (endpoint or page) | Risk |
|---|---|---|---|---|
| Directly changed | Symbols and files in the diff | | | |
| Indirectly affected | Callers, importers, and readers of a changed item | | | |
| Unchanged but risky | Shares data, a lock, a config, or a rule; no traced call | | | |

### Assumptions
- A-1: <what Claude could not prove from the code>

### Unresolved
- <dynamic calls, string-built paths, anything the trace could not follow>
```

</Callout>

[Test Types](/fundamentals/test-types/) explains change-related testing. [From Issue to Reviewed PR](/case-study/pr-review/) shows a real blast-radius report.

</Technical>
<Layman>

The tutorial uses "blast radius" for the result of an impact analysis on one change. In **impact analysis**, you find every work product that a change affects, and you estimate the resources that the change needs. <Cite n={4} />

**Regression testing** checks that a change did not add or uncover defects in the parts that did not change. <Cite n={5} /> A change can harm its own component, other components, or other connected systems. So the syllabus advises: do the impact analysis first, then decide how much regression testing you need. <Cite n={1} />

For a live system, this is **maintenance testing**. Its size typically depends on the risk of the change, the size of the system, and the size of the change. Most of the system usually stays unchanged. When data from another application moves into the system, data conversion can need tests. <Cite n={1} />

The tutorial suggests an impact map with three rings. The first ring is what the diff changed. The second ring is what calls or reads the changed parts. The third ring did not change, but it shares data, a lock, a setting, or a rule with the change. Each row names the file and the line that proves it.

</Layman>
<Bangla>

একটি change-এর impact analysis-এর ফলাফলকে tutorial "blast radius" নাম দেয়।

- ISTQB অনুযায়ী **impact analysis** হলো একটি change যেসব work product-কে প্রভাবিত করে, সেগুলো সব খুঁজে বের করা, এবং change-টি করতে কত resource লাগবে তার একটি হিসাব। <Cite n={4} />
- **Regression testing** হলো change-সম্পর্কিত testing, যা দেখে software-এর অপরিবর্তিত অংশে কোনো defect ঢুকেছে বা প্রকাশ পেয়েছে কি না। <Cite n={5} />
- একটি change একই component, একই system-এর অন্য component, এমনকি যুক্ত অন্য system-এরও ক্ষতি করতে পারে। তাই syllabus আগে impact analysis করে regression testing-এর পরিধি ঠিক করার পরামর্শ দেয়। <Cite n={1} />

চালু system-এ এটিই **maintenance testing**। এর পরিধি সাধারণত নির্ভর করে change-এর risk, system-এর আকার এবং change-এর আকারের ওপর। এটি change যাচাই করে এবং অপরিবর্তিত অংশে regression খোঁজে, যা সাধারণত system-এর বেশিরভাগ অংশ। Hot fix, environment-এর upgrade বা migration এবং retirement এর trigger। অন্য application-এর data system-এ migrate করা হলে data conversion test লাগতে পারে। <Cite n={1} />

Tutorial-এর পরামর্শ: Claude-কে প্রতিটি finding তিনটি ring-এ সাজাতে বলুন — সরাসরি পরিবর্তিত, পরোক্ষভাবে প্রভাবিত, এবং অপরিবর্তিত কিন্তু ঝুঁকিপূর্ণ। প্রতিটি row-তে প্রমাণ হিসেবে `file:line` থাকবে। যা code থেকে প্রমাণ করা যায়নি, তা Assumptions বা Unresolved অংশে যাবে।

</Bangla>
</Voices>

## Get the change

<Voices>
<Technical>

Impact analysis starts from the exact change, not from the ticket title. For a pull request, the GitHub CLI gives you the change.

- `gh pr diff` views the changes in a pull request. With no argument, it uses the pull request of the current branch. <Cite n={6} />
- `--name-only` displays only the names of the changed files. `--exclude` removes files that match a glob pattern, and you can repeat it. <Cite n={6} />
- `gh pr view --json <fields>` prints JSON. Its fields include `files`, `changedFiles`, and `closingIssuesReferences`. <Cite n={7} />
- `-R` or `--repo` selects another repository in the `OWNER/REPO` format. <Cite n={6} />

An example for pull request 8 of a repository:

```bash
gh pr diff 8 --name-only --exclude '*.generated.*'
gh pr view 8 --json files,closingIssuesReferences
gh pr diff 8 --exclude '*.generated.*'
```

`closingIssuesReferences` is the list of issues that may be closed by the pull request. <Cite n={23} /> Those issues hold the acceptance criteria that the test cases trace to.

<Callout type="tip" title="The tutorial's advice">

If the branch has no pull request yet, ask Claude to compare the branch with its merge base on `main`, and to include staged, unstaged, and untracked files. The dMoney `blast-radius` skill collects all four sources. It is read-only: "never edit, stage, stash, or commit".

</Callout>

</Technical>
<Layman>

Start from the real change, not from the ticket title. For a pull request, the GitHub CLI shows the change.

- `gh pr diff` shows the changes in a pull request. Without an argument, it uses the pull request of your current branch.
- `--name-only` shows only the names of the changed files. `--exclude` hides files that match a pattern.
- `--repo` picks another repository. <Cite n={6} />

`gh pr view --json` prints details as JSON. The fields include `files` and `closingIssuesReferences`. <Cite n={7} /> `closingIssuesReferences` lists the issues that the pull request may close. <Cite n={23} /> Those issues hold the acceptance criteria.

The tutorial suggests: if the branch has no pull request yet, ask Claude to compare it with `main`. Include files that are staged, unstaged, and untracked. The dMoney skill does this, and it never edits, stages, or commits.

</Layman>
<Bangla>

Impact analysis শুরু হয় আসল change থেকে, ticket-এর title থেকে নয়। Pull request-এর জন্য GitHub CLI change-টি দেখায়।

- `gh pr diff` একটি pull request-এর change দেখায়। কোনো argument না দিলে এটি current branch-এর pull request নেয়।
- `--name-only` শুধু পরিবর্তিত file-এর নাম দেখায়। `--exclude` একটি glob pattern-এর সাথে মেলে এমন file বাদ দেয়, আর এটি একাধিকবার দেওয়া যায়।
- `-R` বা `--repo` দিয়ে অন্য repository বেছে নিতে পারেন। <Cite n={6} />

`gh pr view --json` JSON আকারে তথ্য দেয়। এর field-এর মধ্যে আছে `files`, `changedFiles` এবং `closingIssuesReferences`। <Cite n={7} /> `closingIssuesReferences` হলো সেই issue-গুলোর তালিকা, যেগুলো pull request-টি বন্ধ করতে পারে। <Cite n={23} /> ওই issue-গুলোতে acceptance criteria থাকে।

Tutorial-এর পরামর্শ: branch-এর এখনও pull request না থাকলে Claude-কে `main`-এর merge base-এর সাথে তুলনা করতে বলুন, এবং staged, unstaged ও untracked file-ও ধরতে বলুন। dMoney-এর `blast-radius` skill চারটি উৎসই নেয়, এবং এটি read-only।

</Bangla>
</Voices>

## Trace callers and dependents

<Voices>
<Technical>

The second ring needs the callers, importers, and readers of each changed symbol. Four ways to find them:

| Way | What it gives Claude | Limits |
|---|---|---|
| Text search | Every line that names the file or the symbol | Comments and same-name matches need a filter (the tutorial's note) |
| Code intelligence plugin | An `LSP` tool that finds all references, traces call hierarchies, and finds implementations <Cite n={9} /> | Inactive until you install a plugin for your language <Cite n={9} />; not started in cloud sessions <Cite n={8} /> |
| Serena | An MCP server with symbol-level tools, such as "find referencing symbols" <Cite n={10} /> | Uses language servers by default, for over 40 languages <Cite n={10} /> |
| graphify | A Claude Code skill that builds a knowledge graph; code goes through tree-sitter and a call-graph pass <Cite n={11} /> | Rebuild it after a change (the tutorial's note); `graphify hook install` rebuilds it after every commit <Cite n={11} /> |

**Code intelligence.** A plugin lets Claude find definitions and references by symbol instead of by text search. <Cite n={8} /> The plugin does not include the language server: install the binary first, then the plugin. <Cite n={8} /> For TypeScript and JavaScript: <Cite n={8} />

```text
/plugin install typescript-lsp@claude-plugins-official
```

The `LSP` tool is read-only. <Cite n={8} />

**graphify edges.** Every edge is tagged `EXTRACTED`, `INFERRED`, or `AMBIGUOUS`, so you know what was found and what was guessed. <Cite n={11} /> Treat an `INFERRED` edge as an assumption until you open the code.

**Explore.** Claude delegates to the built-in Explore subagent when it needs to search or understand a codebase without making changes. <Cite n={12} />

**dMoney example.** The `blast-radius` skill counts fan-in: what depends on a symbol. Its report for PR #8 names `checkCustomerLimits` as the changed symbol with the highest fan-in: "3 callers → 3 endpoints → 5 pages". That is why Payment and Withdraw are in the report as "Medium (regression only)", although their own code did not change.

</Technical>
<Layman>

The second ring needs everything that calls, imports, or reads a changed part. You can find it in four ways:

- **Text search** finds every line with the name. It also finds comments and other things with the same name, so you must filter the results.
- **A code intelligence plugin** gives Claude an `LSP` tool. It finds all references and traces call chains. <Cite n={9} /> It finds them by symbol, not by text. <Cite n={8} /> It does nothing until you install a plugin for your language. <Cite n={9} /> Install the language server first, then the plugin. <Cite n={8} /> The tool only reads.
- **Serena** is an MCP server with symbol tools, such as "find referencing symbols". <Cite n={10} />
- **graphify** is a Claude Code skill that builds a knowledge graph. Each link in the graph is marked as found, guessed, or unclear. <Cite n={11} /> Check a guessed link in the code before you trust it.

Claude can also hand the search to its built-in Explore helper, which searches without changing anything. <Cite n={12} />

In dMoney, the report for PR #8 found that, of the changed symbols, `checkCustomerLimits` had the most dependents: 3 callers, 3 endpoints, and 5 pages. So Payment and Withdraw needed regression tests, although their own code did not change.

</Layman>
<Bangla>

দ্বিতীয় ring-এর জন্য প্রতিটি পরিবর্তিত symbol-এর caller, importer ও reader খুঁজতে হয়। চারটি উপায় আছে:

- **Text search** নাম আছে এমন প্রতিটি line খুঁজে দেয়। তবে comment ও একই নামের অন্য জিনিসও আসে, তাই ফলাফল ছেঁকে নিতে হয়।

## Scenario categories for a money transfer

<Voices>
<Technical>

Cover each acceptance criterion and each impact ring with these six categories. The examples for a money transfer are the tutorial's own.

| Category | What it proves | Example for a transfer |
|---|---|---|
| Positive | The intended use works | Send a valid amount to another customer; both balances change by the right amounts |
| Negative | A test type that uses the system in a way that it is not intended <Cite n={14} /> | Send to your own account; send `0`; send text as the amount |
| Boundary | Boundary value analysis, a black-box test technique: the test conditions are boundary values <Cite n={15} /> | The amounts just below, at, and just above the daily limit from the criterion |
| Integration | Interactions between components or systems <Cite n={13} /> | The transfer writes the ledger rows, and the statement page shows them |
| Regression | No new defects in unchanged areas <Cite n={5} /> | Payment and withdraw, which share the limit check |
| Adversarial | Abuse and misuse of the business logic <Cite n={16} /> | Skip a step, repeat a one-time action, or send parallel requests |

**Adversarial cases come from OWASP.** Business logic testing asks testers to develop abuse and misuse cases. <Cite n={16} /> A vulnerability scanner cannot detect this type of flaw. <Cite n={16} /> Ideas to adapt:

- Go from step 1 straight to step 3 of a flow. <Cite n={16} />
- Use a function more times than allowed, such as a one-time discount. <Cite n={18} />
- Check that all checks run on the back end and cannot be bypassed. <Cite n={17} />
- Use one card at several places very quickly to exceed a limit. <Cite n={17} /> For a transfer, that is parallel requests against one daily limit.

<Callout type="warning" title="Test only where you are allowed to">

Run adversarial and parallel-request tests only on a test environment that you are allowed to test, with test accounts. This is the tutorial's advice.

</Callout>

</Technical>

## Structured test cases

<Voices>
<Technical>

A structured test case has the ISTQB parts: preconditions, inputs, actions, expected results, and postconditions. <Cite n={3} /> Add two more fields: a trace link and a priority.

- **Traceability** is the ability to establish explicit relationships between related work products. <Cite n={19} /> Tracing test cases to requirements shows that the requirements are covered. Good traceability also makes it possible to determine the impact of changes. <Cite n={1} />
- **Risk-based testing** selects, prioritizes, manages, and uses test activities and resources based on risk types and risk levels. <Cite n={20} /> The risk level comes from two factors: the likelihood of the risk and its impact. <Cite n={1} />
- With risk-based prioritization, the test cases that cover the most important risks run first. If a high-priority case depends on a low-priority case, the low-priority case must run first. <Cite n={1} />

A template, the tutorial's own:

```markdown
### TC-007: Verify transfer that crosses the daily limit
- Traces to: AC-3 (daily limit) · Impact ring: directly changed
- Category: Boundary · Priority: High (moves money)
- Preconditions: Customer A has used <limit minus 10> today and has enough balance; Customer B exists
- Inputs: amount = 11, to = Customer B
- Actions:
  1. Sign in as Customer A on https://staging.example.com
  2. Send 11 to Customer B
- Expected results: the limit error from AC-3; no new ledger row
- Postconditions: the balances of A and B are unchanged
- Evidence: <the file:line of the limit check, from the impact map>
```

The dMoney `test-design` skill adds a title rule: a title starts with "Verify" and does not give away the expected result. Its self-check asks that "every requirement highlight is covered by ≥ 1 test case".

[Test Levels, Pyramid and Quadrants](/fundamentals/levels/) shows where each case runs. [Design, Execute, Fix, Retest](/case-study/test-and-retest/) shows cases like these in use.

</Technical>
<Layman>

A good test case has the five ISTQB parts: the starting state, the inputs, the actions, the expected results, and the end state. <Cite n={3} /> The tutorial adds two fields:

- **A trace link.** Traceability means a clear link between related work products. <Cite n={19} /> A link from each test case to its requirement shows what is covered. It also helps you see what a later change affects. <Cite n={1} />
- **A priority.** Risk-based testing picks and orders tests by risk. <Cite n={20} /> The risk level comes from how likely the problem is and how much harm it does. Tests for the biggest risks run first. If an important test depends on a less important test, the less important test runs first. <Cite n={1} />

The tutorial gives a template. It has the test case ID and title, the criterion it traces to, the ring, the category, the priority, the starting state, the inputs, the steps, the expected results, the end state, and the file and line that proves the impact.

## Common mistakes

<Voices>
<Technical>

- **Testing only the diff.** A change can harm other components and connected systems. <Cite n={1} /> Fix: add a regression case for each entry point in the second ring.
- **Trusting a dependent that nothing proves.** A path or a caller can be invented, and a graph edge can be `INFERRED`. <Cite n={11} /> Fix: ask for `file:line` on every row and open it. This is the tutorial's advice.
- **Relying on text search alone.** It returns comments and same-name matches. Fix: use the `LSP` tool to find all references and trace call hierarchies. <Cite n={9} /> List dynamic calls under Unresolved.
- **Guessing boundary values.** Fix: take each limit from a criterion or the code. Put an unknown limit under Open questions. This is the tutorial's advice.
- **Test cases with no trace or priority.** Fix: trace each case to a criterion, and run the cases for the most important risks first. <Cite n={1} />
- **Letting the writer review its own work.** Fix: use a fresh, read-only reviewer subagent. <Cite n={12} /> <Cite n={22} />
- **Exploring data with write access.** Fix: a read-only database user on a test environment. This is the tutorial's advice.

</Technical>
<Layman>

- **You test only the changed lines.** A change can harm other parts and other systems. <Cite n={1} /> Add regression tests for the second ring.
- **You trust a link that nothing proves.** A graph can guess a link. <Cite n={11} /> The tutorial says: ask for the file and line, and open it.
- **You use only text search.** It also finds comments and other names. Use the `LSP` tool to find all references. <Cite n={9} />
- **You guess the edge values.** The tutorial says: take each limit from a criterion or the code, or list it under Open questions.
- **Your test cases have no link or priority.** Link each case to a criterion, and run the biggest risks first. <Cite n={1} />
- **The writer checks its own work.** Use a fresh reviewer that can only read. <Cite n={12} /> <Cite n={22} />
- **Claude can write to the database.** The tutorial says: use a read-only user on a test environment.

</Layman>
<Bangla>

- **শুধু diff test করা।** একটি change অন্য component ও যুক্ত system-এরও ক্ষতি করতে পারে। <Cite n={1} /> সমাধান: দ্বিতীয় ring-এর প্রতিটি entry point-এর জন্য regression case যোগ করুন।
- **প্রমাণহীন dependent-এ ভরসা করা।** Path বা caller বানানো হতে পারে, আর graph edge `INFERRED` হতে পারে। <Cite n={11} /> সমাধান (tutorial-এর পরামর্শ): প্রতিটি row-তে `file:line` চান এবং খুলে দেখুন।
- **শুধু text search-এ নির্ভর করা।** এতে comment ও একই নামের জিনিসও আসে। সমাধান: সব reference ও call hierarchy-র জন্য `LSP` tool ব্যবহার করুন। <Cite n={9} />
- **Boundary value অনুমান করা।** সমাধান (tutorial-এর পরামর্শ): প্রতিটি limit criterion বা code থেকে নিন; অজানা হলে Open questions-এ রাখুন।
- **Trace ও priority ছাড়া test case।** সমাধান: প্রতিটি case-কে criterion-এর সাথে যুক্ত করুন, আর সবচেয়ে গুরুত্বপূর্ণ risk-এর case আগে চালান। <Cite n={1} />
- **লেখক নিজেই নিজের কাজ review করা।** সমাধান: fresh, read-only reviewer subagent। <Cite n={12} /> <Cite n={22} />
- **Write access নিয়ে data explore করা।** সমাধান (tutorial-এর পরামর্শ): test environment-এ read-only database user।

</Bangla>

## Key words

| Term | Meaning |
|---|---|
| Blast radius | The tutorial's name for the result of an impact analysis on one change |
| Impact analysis | Finding all work products that a change affects, with an estimate of the resources that the change needs |
| Impact map | The tutorial's three rings: directly changed, indirectly affected, and unchanged but risky, each row with `file:line` evidence |
| Regression testing | Change-related testing that looks for defects introduced or uncovered in unchanged areas |
| Maintenance testing | Testing a change to an operational system, including regressions in its unchanged parts |
| Test condition | A testable aspect of a component or system that is intended to be tested, such as an acceptance criterion |
| Test case | Preconditions, inputs, actions, expected results, and postconditions, developed from test conditions |
| Traceability | The ability to establish explicit relationships between related work products |
| Risk-based testing | Selecting, prioritizing, and managing test activities by risk types and risk levels |
| Negative testing | Using a component or system in a way that it is not intended |
| Boundary value analysis | A black-box technique whose test conditions are boundary values |
| Fan-in | What depends on a symbol |
