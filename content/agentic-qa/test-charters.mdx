# Exploring Features with Test Charters

Many features reach a tester with a thin ticket, an old wiki page, or no requirement at all. This page shows how to test such a feature: explore it with Claude without changing anything, plan the work as short test charters, and turn what you find into expected results, hidden business rules, questions, and suspected defects. Each rule keeps its evidence, so a stakeholder can confirm it before it becomes the basis of a test.

<PageMeta />

## The oracle problem

<Voices>
<Technical>

A test compares an actual result with an expected result. When there is no spec, you must first find the expected result.

- A **test oracle** is a source to determine an expected result. <Cite n={1} />
- The **test oracle problem** is the challenge of deciding whether a test passed or failed for given inputs and state. <Cite n={2} />
- Exploratory testing is useful when there are few or inadequate specifications, or significant time pressure. <Cite n={3} />

### Where expected behavior can come from

The list below is the tutorial's own. Use more than one source for each rule.

| Source | What it tells you | Watch out for |
|---|---|---|
| Current behavior | What the system does now | It can be a bug that nobody reported |
| Code | Validations, limits, fees, error messages | It says what was built, not what was meant |
| API docs | The request and response contract | Docs can be older than the code |
| Database constraints | Types, `NOT NULL`, enums, unique keys, seed rules | Data rules can differ from code rules |
| Similar features | Rules that a sibling flow applies | The two flows can differ on purpose |
| User docs and help text | What users were told | Marketing text is not a rule |
| Stakeholders | The intent | Memory is not always correct |

<Callout type="warning" title="The tutorial's advice: the code is not the spec">

When Claude reads the code, it can describe the current behavior very fast. That makes it easy to turn every line into an expected result. Then each test passes, and each bug in the code becomes a "rule". Treat a rule that only the code supports as a question, not as an expected result.

</Callout>

</Technical>
<Layman>

A test compares what happens with what should happen. With no spec, you must first find out what should happen.

- A **test oracle** is any source that tells you the expected result. <Cite n={1} />
- The **test oracle problem** is the hard part: deciding if a test passed or failed. <Cite n={2} />
- Exploratory testing helps when specs are missing or weak, or when time is short. <Cite n={3} />

The tutorial lists places to look for expected behavior. These are the current behavior, the code, the API docs, and the database rules. Similar features, user help text, and stakeholders help too. Each source has a weak spot. Current behavior can be a bug. Code shows what was built, not what was meant. Docs can be out of date.

The tutorial warns about one trap. Claude reads code fast. So it is tempting to copy each line of code into an expected result. Then every test passes, and every bug becomes a "rule". If only the code supports a rule, treat it as a question.

</Layman>
<Bangla>

একটি test আসল ফলাফলকে প্রত্যাশিত ফলাফলের সাথে মেলায়। Spec না থাকলে আগে আপনাকে প্রত্যাশিত ফলাফলটি খুঁজে বের করতে হবে।

- **Test oracle** হলো এমন একটি উৎস, যা থেকে প্রত্যাশিত ফলাফল ঠিক করা যায়। <Cite n={1} />
- **Test oracle problem** হলো নির্দিষ্ট input আর state-এর জন্য একটি test pass করল না fail করল, তা ঠিক করার চ্যালেঞ্জ। <Cite n={2} />
- Specification কম বা অপর্যাপ্ত হলে, অথবা সময়ের চাপ বেশি থাকলে exploratory testing কাজে লাগে। <Cite n={3} />

Tutorial-এর নিজের তালিকায় প্রত্যাশিত আচরণের উৎসগুলো হলো: বর্তমান আচরণ, code, API docs, database constraint, একই রকম অন্য feature, user docs আর stakeholder। প্রতিটি উৎসের দুর্বলতা আছে। বর্তমান আচরণ নিজেই একটি bug হতে পারে। Code বলে কী বানানো হয়েছে, কী বোঝানো হয়েছিল তা নয়। Docs code-এর চেয়ে পুরোনো হতে পারে।

Tutorial-এর পরামর্শ: code-কে spec ভাববেন না। Claude খুব দ্রুত code পড়ে বর্তমান আচরণ বলে দিতে পারে। তখন code-এর প্রতিটি লাইনকে expected result বানিয়ে ফেলা সহজ। এতে সব test pass করে, আর code-এর প্রতিটি bug একটি "rule" হয়ে যায়। যে rule-কে শুধু code সমর্থন করে, সেটিকে প্রশ্ন হিসেবে রাখুন।

</Bangla>

## Exploratory testing and test charters

<Voices>
<Technical>

The ISTQB terms give the session its shape.

| Term | What ISTQB says |
|---|---|
| Exploratory testing | Tests are designed, executed, and evaluated at the same time, while the tester learns about the test object. <Cite n={3} /> The glossary adds that the design is dynamic and uses the tester's knowledge, exploration of the test item, and previous results. <Cite n={4} /> |
| Session-based testing | An approach in which test activities are planned as test sessions. <Cite n={5} /> The exploratory testing happens within a defined time box. <Cite n={3} /> |
| Test charter | A mission statement that guides an exploratory test session. <Cite n={6} /> It contains the test objectives. <Cite n={3} /> |
| Test session | An uninterrupted period of time spent executing tests. <Cite n={7} /> |
| Debriefing | Usually follows the session: the tester and the interested stakeholders discuss the results. <Cite n={3} /> |
| Test session sheet | The tester may use it to record the steps followed and the discoveries made. <Cite n={3} /> |

More points from the syllabus:

- Test objectives may be treated as high-level test conditions. <Cite n={3} />
- Exploratory testing can use other test techniques, for example equivalence partitioning. <Cite n={3} />
- It is more effective when the tester is experienced and has domain knowledge. <Cite n={3} />
- It also complements more formal test techniques. <Cite n={3} />

Claude does not replace the tester here. The tutorial asks Claude to read code and data and to draft notes. You keep the judgment about what is a problem.

<Callout type="tip" title="Related pages">

[Experience-based Techniques](/fundamentals/experience-based/) covers exploratory testing in the Fundamentals module. [Test and Retest](/case-study/test-and-retest/) shows charters that a skill wrote for one pull request.

</Callout>

</Technical>
<Layman>

ISTQB gives names to each part of a session:

- **Exploratory testing**: you design, run, and judge tests at the same time, while you learn the product. <Cite n={3} /> You choose the next test from what you know and what you just saw. <Cite n={4} />
- **Session-based testing**: you plan the work as test sessions. <Cite n={5} /> Each session has a fixed length, called a time box. <Cite n={3} />
- **Test charter**: a mission statement that guides one session. <Cite n={6} /> It holds the test objectives. <Cite n={3} />
- **Test session**: a period of testing with no breaks. <Cite n={7} />
- **Debriefing**: usually a talk after the session. You and interested people discuss what you found. <Cite n={3} />
- **Test session sheet**: you may use it to note the steps you took and what you found. <Cite n={3} />

You can also use other techniques inside a session, such as equivalence partitioning. Experience and domain knowledge make the session better. <Cite n={3} />

Claude does not replace you. The tutorial asks it to read code and data and to draft notes. You decide what is a problem.

</Layman>
<Bangla>

ISTQB-এর term-গুলো session-কে একটি কাঠামো দেয়:

- **Exploratory testing**: tester test object সম্পর্কে শিখতে শিখতে একই সময়ে test design, execute আর evaluate করেন। <Cite n={3} /> Glossary বলে, tester-এর জ্ঞান, exploration আর আগের ফলাফল থেকে test তৈরি হয়। <Cite n={4} />
- **Session-based testing**: test-এর কাজ test session হিসেবে পরিকল্পনা করা হয়। <Cite n={5} /> Exploratory testing একটি নির্দিষ্ট time box-এর মধ্যে হয়। <Cite n={3} />
- **Test charter**: একটি mission statement, যা একটি exploratory test session-কে পথ দেখায়। <Cite n={6} /> এতে test objective থাকে। <Cite n={3} />
- **Test session**: test চালানোর জন্য বিরতিহীন একটি সময়। <Cite n={7} />
- **Debriefing**: সাধারণত session-এর পরে হয়। Tester আর আগ্রহী stakeholder-রা ফলাফল নিয়ে আলোচনা করেন। <Cite n={3} />
- **Test session sheet**: এতে tester নেওয়া step আর পাওয়া discovery লিখে রাখতে পারেন। <Cite n={3} />

এখানে Claude tester-এর জায়গা নেয় না। Tutorial Claude-কে দিয়ে code আর data পড়ায় এবং note-এর খসড়া লেখায়। কোনটি সমস্যা, সেই বিচার আপনার।

## Explore the code read-only with Claude

<Voices>
<Technical>

Start every exploration so that Claude cannot change the project.

**Plan mode.** In plan mode, Claude reads files, runs shell commands to explore, and writes a plan, but does not edit your source. <Cite n={8} /> Press `Shift+Tab`, prefix one prompt with `/plan`, or start the session in plan mode: <Cite n={8} />

```bash
claude --permission-mode plan
```

Plan mode blocks edits, not every command. When auto mode is available, a classifier reviews shell commands during planning, and approved commands run. <Cite n={8} /> Without auto mode, commands outside the built-in read-only set ask for approval. <Cite n={8} /> A `POST` request is still a write to the system under test, so read each command before you approve it.

**The Explore subagent.** Explore is a built-in, read-only agent for searching and analyzing codebases. <Cite n={9} />

- Its tools are read-only. Write and Edit are denied. <Cite n={9} />
- Claude gives it a thoroughness level: quick, medium, or very thorough. <Cite n={9} />
- Its results stay out of your main conversation context. <Cite n={9} />
- It starts without your CLAUDE.md files and the git status snapshot. <Cite n={9} /> Put the domain words that it needs in your prompt.

**Read the request path.** The tutorial suggests that you follow one request from the outside in: the route, the middleware (authentication, roles), the controller (validation, rules, error messages), and the model or table that stores the result. An example prompt:

```text
Use the Explore agent, very thorough. Map the request path of the cash out
feature: the route, the middleware, the controller, the services it calls,
and the tables it reads and writes. For each validation, give the file, the
line, the condition, the HTTP status, and the message. Do not change any file.
```

[A Tour of the Codebase](/case-study/codebase-tour/) shows how the practice app is organized.

</Technical>
<Layman>

Start each exploration in a way that Claude cannot change the project.

**Plan mode.** In plan mode, Claude reads files, runs shell commands to explore, and writes a plan. It does not edit your source. <Cite n={8} /> Press `Shift+Tab`, start a prompt with `/plan`, or run `claude --permission-mode plan`. <Cite n={8} />

Plan mode stops edits, not every command. Some shell commands can still run after a check or your approval. <Cite n={8} /> A `POST` request still changes the system under test. So read each command before you approve it.

**The Explore subagent.** Explore is a built-in helper that only reads code. It cannot write or edit files. <Cite n={9} /> Claude tells it how deep to search: quick, medium, or very thorough. Its results do not fill your main conversation. It starts without your CLAUDE.md files. <Cite n={9} /> So put the business words it needs in your prompt.

**Follow one request.** The tutorial suggests that you trace one request from the outside in. Start at the route. Then read the login and role checks. Then read the controller with its checks and error messages. End at the table that stores the result. Ask Claude for the file and line of each check.

</Layman>

প্রতিটি exploration এমনভাবে শুরু করুন, যাতে Claude project-এ কিছু বদলাতে না পারে।

**Plan mode:** Plan mode-এ Claude file পড়ে, explore করতে shell command চালায় এবং একটি plan লেখে, কিন্তু আপনার source edit করে না। <Cite n={8} /> `Shift+Tab` চাপুন, একটি prompt-এর শুরুতে `/plan` দিন, অথবা `claude --permission-mode plan` দিয়ে session শুরু করুন। <Cite n={8} />

**Request path পড়ুন:** Tutorial-এর পরামর্শ হলো, একটি request বাইরে থেকে ভেতরে অনুসরণ করুন: route, middleware (authentication, role), controller (validation, rule, error message), আর যে model বা table ফলাফল রাখে। প্রতিটি check-এর file আর line নম্বর Claude-এর কাছে চান।

## Probe the API, the database, and the UI

<Voices>
<Technical>

After the code, look at the running system. Use a test environment and test accounts only.

**The API.** Start from the repo's own endpoint docs. The tutorial sends requests with `curl`, or with Playwright: it can send requests to the server directly from Node.js without loading a page, through `APIRequestContext`. <Cite n={10} /> A read request (`GET`) is safe. A `POST` creates data, so it belongs in the session plan, not in a quick check.

**The database.** A database MCP server such as the MySQL one can list databases, tables, and schemas, and run SELECT queries. <Cite n={12} /> Give it read access only.

- A project-scoped server lives in `.mcp.json` at the project root. <Cite n={11} /> Claude Code asks for approval in interactive sessions before it uses such a server. <Cite n={11} />
- `.mcp.json` can reference environment variables as `${VAR}` in `command`, `args`, `env`, `url`, and `headers`. <Cite n={11} />
- The MySQL MCP server takes a connection string and a permission list. `list` lists databases, tables, and schemas. `read` allows `SELECT` queries. <Cite n={12} /> `create`, `update`, and `delete` change records. <Cite n={12} />
- Since v1.44.0, with no permissions and no categories, it enables only `list`, `read`, and `utility`. <Cite n={12} />
- `MCP_REQUIRE_READONLY_DB_USER=true` makes startup fail if the MySQL user can write. <Cite n={12} />

An example entry, with a read-only database user:

```json
{
  "mcpServers": {
    "app-db-readonly": {
      "type": "stdio",
      "command": "npx",
      "args": [
        "-y",
        "@berthojoris/mcp-mysql-server",
        "mysql://qa_reader:${DB_PASSWORD}@localhost:3306/appdb",
        "list,read,utility"
      ],
      "env": { "MCP_REQUIRE_READONLY_DB_USER": "true" }
    }
  }
}
```

**The UI.** Pick one browser tool:

- Playwright MCP works with web pages through structured accessibility snapshots. <Cite n={13} />
- agent-browser is a CLI that an agent drives one command at a time. `snapshot` returns the page as text with a ref such as `@e1` for each element. <Cite n={14} /> After navigation or a DOM change, take a new snapshot before you use refs again. <Cite n={14} />
- Claude in Chrome can read console errors and DOM state. <Cite n={15} /> It shares your browser login state, so it can reach any site you are signed in to. <Cite n={15} />

[Browser Testing with Playwright](/automate/playwright/) compares the browser tools. [Project, Jira, GitHub & MCP Setup](/agentic-qa/project-setup/) sets up the servers.

</Technical>

Code দেখার পরে চলমান system দেখুন। শুধু test environment আর test account ব্যবহার করুন।

**Database:** একটি database MCP server database, table আর schema-র তালিকা দেখাতে এবং SELECT query চালাতে পারে। <Cite n={12} /> একে শুধু read access দিন। Project-scoped server project root-এর `.mcp.json`-এ থাকে, আর interactive session-এ ব্যবহারের আগে Claude Code approval চায়। `.mcp.json`-এ environment variable `${VAR}` আকারে লেখা যায়। <Cite n={11} /> MySQL MCP server একটি permission list নেয়। `list` আর `read` শুধু দেখে, `create`, `update` আর `delete` record বদলায়। কোনো permission বা category না দিলে v1.44.0 থেকে এটি শুধু `list`, `read` আর `utility` চালু করে। `MCP_REQUIRE_READONLY_DB_USER=true` দিলে MySQL user write করতে পারলে server চালুই হয় না। <Cite n={12} />

**UI:** একটি browser tool বাছুন:

- Playwright MCP structured accessibility snapshot দিয়ে web page-এ কাজ করে। <Cite n={13} />

- Claude in Chrome console error আর DOM state পড়তে পারে। এটি আপনার browser-এর login state শেয়ার করে, তাই আপনি যেসব site-এ sign in করা আছেন, সেখানে ঢুকতে পারে। <Cite n={15} />

## Write the charters

<Voices>
<Technical>

A charter is a test design work product, like a test case. <Cite n={3} /> It is a mission for one session, not a script. <Cite n={6} /> The dMoney practice repo has a `test-charter` skill that writes each mission as "Explore … with … to discover …".

<Callout type="tip" title="The tutorial's charter template">

```markdown
## CH-<n>: <short title>
Mission:    Explore <area> with <data, tools, techniques>
            to discover <the information or risk>
Time box:   45 min
Risk:       <what can go wrong, and who is hurt>
Entry:      <page, endpoint, table>
Oracles:    <how you will know that something is wrong>
Setup:      <accounts, roles, balances, environment>
Out of scope: <what this session does not cover>
Trace:      <ticket, question, or rule ID>
```

</Callout>

### Three example charters for a money-transfer app

These three charters are the tutorial's own examples.

| ID | Mission | Oracles |
|---|---|---|
| CH-1 Cash out amounts and fees | Explore cash out with amounts below, at, and above the minimum, decimals, and large values, through the API, to discover the minimum, the fee rule, and the rounding. | The fee rule in the database; the ledger rows of the transaction; the balance before and after. |
| CH-2 Cash out roles and account states | Explore cash out with each sender role, each receiver role, an inactive account, and a sender that is not the token owner, to discover who may cash out to whom, and which status and message each case returns. | The role checks in the controller; the same checks in a sibling flow such as send money. |
| CH-3 Daily limit under repeated cash outs | Explore repeated and parallel cash outs close to the daily limit, to discover how the limit counts the fee and whether two requests can pass the limit together. | The limit table; the sum of the day's debits; the error message. |

Each charter covers one risk. Each fits one time box. The oracles are things you can check, not "works correctly".

</Technical>

## Derive expected behavior and hidden rules

<Voices>
<Technical>

A hidden rule is a business rule that the system applies but no document states. Record each one with its evidence and a confidence.

<Callout type="note" title="The tutorial's advice: evidence and confidence">

- **Evidence**: a file and line, a query result, a request and response, or an observed screen.
- **High**: two independent sources agree, for example the code and the seed data.
- **Medium**: one source only.
- **Low**: inferred from a name or a comment.
- **Status**: every rule starts as "to confirm". Only a stakeholder's answer makes it an expected result.

</Callout>

### Example: cash out in dMoney

<Callout type="note" title="Where these facts come from">

The dMoney facts below come from the files of the public practice repo at commit 51db34a. They have no cites, because a cite links to an official source.

</Callout>

The cash out endpoint is `POST /transaction/withdraw`, behind `authenticateJWT` (`routes/transaction.route.js:20`).

| Rule | Evidence | Confidence |
|---|---|---|
| R1: The minimum cash out is 10 Tk. | `withdraw.controller.js:23` falls back to 10; the seed rule has `min_txn_amount` 10.00 | High |
| R2: The fee is 1%, at least 5 Tk, paid by the customer. | Seed rule "System takes 1% (min 5 BDT) from payer"; the debit is amount plus fee (`withdraw.controller.js:113`) | High |
| R3: The agent gets 2.5% on top, charged to the platform. | Seed rule (`create_commission_table.js:75`); the agent credit is amount plus commission (`withdraw.controller.js:124`) | Medium |
| R4: Customers only: daily 5,000 Tk and 10 transactions; the check counts amount plus fee. | `create_transaction_limits.js:4-6`; `withdraw.controller.js:93` | Medium |
| R5: The receiver must be an Agent. | `withdraw.controller.js:57-59` | High |
| R6: No balance returns HTTP 208 "Insufficient balance". | `withdraw.controller.js:153-155` | Medium |

Two rules raise questions:

- **R3**: no account is debited for the commission. Who funds it? That is a question for the business, not an expected result.

## Practice

<Voices>
<Technical>

<Callout type="note" title="The tutorial's exercise">

This exercise is the tutorial's own. Run one 45-minute charter on the cash out feature of the dMoney practice app, or on a similar feature of your own project. [A Tour of the Codebase](/case-study/codebase-tour/) describes the app. Use a local copy with test data only.

</Callout>

1. **Start read-only.** Open the project and start Claude Code in plan mode. <Cite n={8} />

   ```bash
   claude --permission-mode plan
   ```

2. **Map the request path.** Give the Explore prompt from "Explore the code read-only with Claude". Expect a list of checks with file, line, status, and message. Check two of them in the files yourself.

   ```text
   Show the schema of the tables that the cash out flow uses, with their
   constraints and enum values. Show the seed rows of the fee and limit
   tables. Use SELECT queries only.
   ```

4. **Write the charter.** Ask Claude for CH-1 with the template on this page. Cut anything that reads like a script.

5. **Run the session.** Set a 45-minute timer. Ask Claude to propose each request before it runs. Approve each `POST` yourself, and only against the local test database.

6. **Debrief.** Ask Claude to draft the session notes, the rules table, the questions, three test cases for the High rules, and the suspected defects.

**Check the result.** Each rule has evidence and a confidence. Each test case traces to a rule. Each "to confirm" rule is in the questions list, not in an expected result.

**ফলাফল যাচাই:** প্রতিটি rule-এর evidence আর confidence আছে। প্রতিটি test case একটি rule-এ trace করে। প্রতিটি "to confirm" rule প্রশ্নের তালিকায় আছে, expected result-এ নয়।

</Bangla>
</Voices>

## Key words

| Term | Meaning |
|---|---|
| Test oracle | A source to determine an expected result. |
| Test oracle problem | The challenge of deciding whether a test passed or failed for given inputs and state. |
| Exploratory testing | Testing in which tests are designed, executed, and evaluated at the same time, while the tester learns about the test object. |
| Session-based testing | An approach in which test activities are planned as test sessions, each within a time box. |
| Test charter | A mission statement that guides an exploratory test session. It holds the test objectives. |
| Test session | An uninterrupted period of time spent executing tests. |
| Debriefing | The discussion of the session results between the tester and the interested stakeholders. |
| Test log | A chronological record of relevant details about test execution. |
| Plan mode | A permission mode in which Claude reads files, runs shell commands to explore, and writes a plan, but does not edit your source. |
| Explore subagent | A built-in, read-only Claude Code agent for searching and analyzing codebases. |
| Hidden rule | A business rule that the system applies but no document states. Record it with evidence and a confidence, and confirm it with a stakeholder. |
