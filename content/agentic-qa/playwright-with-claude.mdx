# Playwright Automation with Claude

Asking Claude for a Playwright test is easy. Knowing whether the test is right is the hard part. This page teaches Playwright Test itself: the setup, the test structure, browser contexts, locators, assertions, fixtures, and the debug tools. Then it shows how to use Claude to create, explain, debug, and refactor tests, and how to review each generated test before you trust it. If you know the tool, you can see when Claude is wrong.

## Install and configure Playwright Test

<Voices>
<Technical>

**Install.** One command starts a new project or adds Playwright to an existing one: <Cite n={1} />

```bash
npm init playwright@latest
```

The command asks four questions: <Cite n={1} />

- TypeScript or JavaScript. The default is TypeScript.
- The tests folder. The default is `tests`, or `e2e` if `tests` already exists.
- Whether to add a GitHub Actions workflow.
- Whether to install the Playwright browsers. The default is yes.

You can run it again later. It does not overwrite existing tests. <Cite n={1} />

**What it creates.** Playwright downloads the browser binaries and writes `playwright.config.ts`, `package.json`, a lock file, and `tests/example.spec.ts`. <Cite n={1} />

**Browsers and system.** Playwright supports Chromium, WebKit, and Firefox on Windows, Linux, and macOS. <Cite n={1} /> It needs Node.js 22.x, 24.x, or 26.x (the latest of each). <Cite n={1} /> By default, tests run headless and in parallel across Chromium, Firefox, and WebKit. <Cite n={1} />

**Version.** The newest entry in the release notes, read on 2026-11-15, is version 1.65. <Cite n={2} /> Check your version with `npx playwright --version`. Update with `npm install -D @playwright/test@latest`, then `npx playwright install --with-deps`. <Cite n={1} />

**Configure.** `playwright.config.ts` holds the target browsers, timeouts, retries, projects, and reporters. <Cite n={1} /> These keys are common: <Cite n={3} />

| Key | Example value from the docs |
|---|---|
| `testDir` | `'tests'` |
| `fullyParallel` | `true` |
| `forbidOnly` | `!!process.env.CI` |
| `retries` | `process.env.CI ? 2 : 0` |
| `use.baseURL` | `'http://localhost:3000'` |

## Write and run a test

<Voices>
<Technical>

**Structure.** A test file imports `test` and `expect` from `@playwright/test`. <Cite n={4} /> A test performs actions and asserts the state against expectations. <Cite n={4} />

- `test.describe` groups tests. <Cite n={4} />
- `test.beforeEach` and `test.afterEach` run before and after each test. <Cite n={4} />
- `test.beforeAll` and `test.afterAll` run once per worker. <Cite n={4} />
- The `page` fixture gives each test a fresh page. <Cite n={4} />
- `page.goto()` waits for the page to reach the load state. <Cite n={4} />

The example below is the tutorial's own. It follows the pattern of the docs:

```ts
import { test, expect } from '@playwright/test';

test.describe('login page', () => {
  test.beforeEach(async ({ page }) => {
    await page.goto('https://staging.example.com/login');
  });

  test('shows an error for a wrong password', async ({ page }) => {
    await page.getByLabel('Email').fill('qa-user@example.com');
    await page.getByLabel('Password').fill('wrong-password');
    await page.getByRole('button', { name: 'Sign in' }).click();
    await expect(page.getByText('Invalid email or password')).toBeVisible();
  });
});
```

**Run.** These commands come from the docs: <Cite n={5} />

| Command | What it does |
|---|---|
| `npx playwright test` | Runs all tests, headless |
| `npx playwright test --headed` | Shows the browser window |
| `npx playwright test --ui` | Opens UI mode |
| `npx playwright test --project webkit` | Runs one project only |
| `npx playwright test login.spec.ts` | Runs one file |
| `npx playwright test -g "wrong password"` | Runs the tests with that title |
| `npx playwright test --last-failed` | Runs only the tests that failed last time |
| `npx playwright show-report` | Opens the HTML report |

The HTML report opens by itself if some tests failed. <Cite n={5} />

**Projects.** A project is a group of tests with the same configuration. <Cite n={6} /> Use one project for each browser, or run the same tests logged in and logged out. <Cite n={6} />

</Technical>

## Browser, context, page, and fixtures

<Voices>
<Technical>

**Three layers.** Playwright can create multiple browser contexts in one scenario, and a page belongs to a context. <Cite n={7} />

- A browser context is like an incognito profile. Contexts are fast to create and fully isolated, even in one browser. <Cite n={7} />
- Playwright creates a context for each test and gives a default page in it. <Cite n={7} />
- So each test has its own local storage, session storage, and cookies. <Cite n={7} /> This isolation prevents cascading test failures. <Cite n={7} />
- One test can create several contexts, for example an admin and a user in a chat flow. <Cite n={7} />

**Fixtures.** A fixture sets up the environment for a test: everything it needs and nothing else. Fixtures are isolated between tests. <Cite n={8} />

| Built-in fixture | What it gives |
|---|---|
| `page` | An isolated page for this test <Cite n={8} /> |
| `context` | The isolated context that the page belongs to <Cite n={8} /> |
| `browser` | The browser, shared across tests to save resources <Cite n={8} /> |
| `browserName` | `chromium`, `firefox`, or `webkit` <Cite n={8} /> |
| `request` | An isolated `APIRequestContext` for API calls <Cite n={8} /> |

**Custom fixtures.** `test.extend()` creates a new `test` object with your own fixture. <Cite n={8} /> The code before `await use()` is the setup. The code after it is the teardown. <Cite n={8} /> Playwright sets up only the fixtures that a test uses. <Cite n={8} />

The example below is the tutorial's own. It gives each test a `loginPage` page object:

```ts
import { test as base } from '@playwright/test';
import { LoginPage } from './pages/LoginPage';

export const test = base.extend<{ loginPage: LoginPage }>({
  loginPage: async ({ page }, use) => {
    const loginPage = new LoginPage(page);
    await loginPage.goto();
    await use(loginPage);
  },
});
export { expect } from '@playwright/test';
```

A test then asks for it by name: `test('...', async ({ loginPage }) => { ... })`.

</Technical>
<Layman>

Think of three layers. A browser can run several browser contexts. A context is like an incognito profile. A page belongs to a context. <Cite n={7} />

Playwright makes a new context for each test. <Cite n={7} /> So each test has its own cookies and storage. A test that fails does not leave a mess for the next test. One test can also open two contexts, for example an admin and a user who chat. <Cite n={7} />

A fixture is something that a test needs, ready before the test starts. <Cite n={8} /> `page` is a fixture. Others are `context`, `browser`, `browserName`, and `request`. <Cite n={8} />

You can make your own fixture with `test.extend()`. <Cite n={8} /> The code before `await use()` prepares it. The code after `await use()` cleans up. <Cite n={8} /> Playwright prepares only the fixtures that a test asks for. <Cite n={8} />

</Layman>
<Bangla>

তিনটি স্তর মনে রাখুন: browser, browser context আর page। Browser context একটি incognito profile-এর মতো। একই browser-এর ভেতরেও প্রতিটি context পুরোপুরি আলাদা। <Cite n={7} />

Playwright প্রতিটি test-এর জন্য একটি নতুন context আর তার ভেতরে একটি default page তৈরি করে। <Cite n={7} /> তাই প্রতিটি test-এর নিজের local storage, session storage আর cookie থাকে। একটি test-এ একাধিক context-ও বানানো যায়, যেমন chat flow-তে একজন admin আর একজন user। <Cite n={7} />

Fixture হলো test-এর environment: test-এর যা দরকার ঠিক ততটুকু। Fixture এক test থেকে আরেক test-এ আলাদা থাকে। <Cite n={8} /> Built-in fixture হলো `page`, `context`, `browser` (সব test-এ shared), `browserName` আর `request`। <Cite n={8} />

নিজের fixture বানাতে `test.extend()` ব্যবহার করুন। <Cite n={8} /> `await use()`-এর আগের code হলো setup, পরের code হলো teardown। <Cite n={8} /> যে fixture কোনো test চায়, Playwright শুধু সেটিই set up করে। <Cite n={8} /> Technical panel-এর `loginPage` fixture-টি tutorial-এর নিজের উদাহরণ।

</Bangla>
</Voices>

## Locators that survive change

<Voices>
<Technical>

A locator is a way to find an element on the page at any moment. Each time an action uses it, Playwright finds an up-to-date element. <Cite n={9} />

**The recommended built-in locators,** in the order that the docs list them: <Cite n={9} />

| Locator | Finds an element by |
|---|---|
| `getByRole()` | Its accessibility role and name, for example a button named "Sign in" |
| `getByText()` | Its text content |
| `getByLabel()` | The text of the label of a form control |
| `getByPlaceholder()` | The placeholder of an input |
| `getByAltText()` | The text alternative of an image |
| `getByTitle()` | Its `title` attribute |
| `getByTestId()` | Its `data-testid` attribute (you can configure another one) |

**Priority.** The docs recommend role locators first, because they are closest to how users and assistive technology see the page. <Cite n={9} /> Use text locators for non-interactive elements such as `div` and `span`. <Cite n={9} /> Test ids are the most resilient, but they are not user facing. <Cite n={9} /> To use another attribute, set `testIdAttribute` in `use` of the config. <Cite n={9} />

**Chaining and filtering.** Chain locators to narrow the search to one part of the page. <Cite n={10} />

```ts
await page
  .getByRole('listitem')
  .filter({ hasText: 'Product 2' })
  .getByRole('button', { name: 'Add to cart' })
  .click();
```

**Strictness.** Locators are strict. An action throws an error if more than one element matches. <Cite n={9} /> `first()`, `last()`, and `nth()` turn this off, but the docs do not recommend them: when the page changes, Playwright can click an element that you did not intend. <Cite n={9} />

**Why CSS and XPath break.** Selectors tied to the DOM structure break when the DOM changes. <Cite n={9} /> A selector on CSS classes breaks when a designer changes a class. <Cite n={10} /> The docs do not recommend CSS or XPath. <Cite n={9} />

```ts
// Brittle: tied to the DOM
await page.locator('#tsf > div:nth-child(2) > div.A8SBwf > input').click();
// Resilient: what the user sees
await page.getByRole('button', { name: 'submit' }).click();
```

Codegen also picks locators in this order: role, text, then test id. <Cite n={11} />

</Technical>
<Layman>

A locator tells Playwright how to find an element, such as a button or a text box. Playwright looks for the element again each time it acts. <Cite n={9} />

The docs list these built-in locators, and they recommend `getByRole()` first: <Cite n={9} />

- `getByRole()` finds an element by what it is and its name, like "the button named Sign in". The docs recommend it first, because users see the page this way.
- `getByText()` finds an element by its text. Use it for text that you do not click.
- `getByLabel()` finds a form field by its label.
- `getByTestId()` finds an element by its test id. It is very stable, but users do not see it.

You can chain locators. For example, first find a list item, then the button inside it. <Cite n={10} />

Locators are strict. If two elements match, the action fails with an error. <Cite n={9} /> The docs do not recommend `nth()` for this. The page can change, and then Playwright can click the wrong element. <Cite n={9} />

Long CSS or XPath paths follow the structure of the HTML. They break when the HTML changes. <Cite n={9} />

</Layman>
<Bangla>

Locator হলো page-এ কোনো element খোঁজার উপায়। প্রতিটি action-এর সময় Playwright element-টি নতুন করে খোঁজে। <Cite n={9} />

Docs যে built-in locator-গুলো recommend করে: `getByRole()`, `getByText()`, `getByLabel()`, `getByPlaceholder()`, `getByAltText()`, `getByTitle()` আর `getByTestId()`। <Cite n={9} /> সবার আগে role locator ব্যবহার করুন, কারণ user আর assistive technology page-কে এভাবেই দেখে। <Cite n={9} /> `div` বা `span`-এর মতো non-interactive element-এর জন্য text locator ব্যবহার করুন। <Cite n={9} /> Test id সবচেয়ে টেকসই, কিন্তু user এটি দেখে না। <Cite n={9} />

Locator chain করে page-এর একটি অংশে খোঁজা সীমিত করা যায়, আর `filter({ hasText })` দিয়ে বাছাই করা যায়। <Cite n={10} />

Locator strict: একাধিক element মিললে action error দেয়। <Cite n={9} /> `first()`, `last()` বা `nth()` দিয়ে এটি এড়ানো যায়, কিন্তু docs এগুলো recommend করে না, কারণ page বদলালে Playwright ভুল element-এ click করতে পারে। <Cite n={9} />

DOM structure-এর সাথে বাঁধা CSS বা XPath, DOM বদলালেই ভেঙে যায়। <Cite n={9} /> Designer একটি CSS class বদলালেও test ভাঙে। <Cite n={10} /> Codegen-ও role, text আর test id-কে আগে রাখে। <Cite n={11} />

</Bangla>
</Voices>

## Assertions and auto-waiting

<Voices>
<Technical>

**Auto-waiting before actions.** Before an action, Playwright runs actionability checks and waits until they pass. If they do not pass within the timeout, the action fails with a `TimeoutError`. <Cite n={12} /> For `click()`, the element must: <Cite n={12} />

- resolve to exactly one element,
- be visible and stable (not animating),
- receive events (no overlay on top of it),
- be enabled and not inert.

The `force` option turns off the non-essential checks. <Cite n={12} /> So you do not need manual waits. <Cite n={4} />

**Web-first assertions.** An auto-retrying assertion checks the page again and again until the condition is true or the assertion timeout ends. <Cite n={13} /> These assertions are async, so you must `await` them. <Cite n={13} />

| Kind | Examples | Waits? |
|---|---|---|
| Auto-retrying | `toBeVisible()`, `toHaveText()`, `toHaveURL()`, `toHaveCount()`, `toHaveValue()` | Yes <Cite n={13} /> |
| Non-retrying | `toBe()`, `toEqual()`, `toBeTruthy()`, `toContain()` | No. They can make a test flaky. <Cite n={13} /> |

For a complex check that must retry, use `expect.poll` or `expect.toPass`. <Cite n={13} /> A soft assertion (`expect.soft`) does not stop the test, but it marks the test as failed. <Cite n={13} />

**The wrong way and the right way:** <Cite n={10} />

```ts
// Does not wait: checks once and returns
expect(await page.getByText('welcome').isVisible()).toBe(true);
// Waits and retries until the text is visible
await expect(page.getByText('welcome')).toBeVisible();
```

**Timeouts.** The defaults are 5 seconds for each assertion <Cite n={13} /> and 30 seconds for each test. <Cite n={14} />

<Callout type="tip" title="The tutorial's advice">

Treat a fixed sleep, such as `page.waitForTimeout(3000)`, as a smell in a generated test. It makes the test slow when the app is fast and flaky when the app is slow. Wait for the state that the user sees with a web-first assertion instead. If a test needs more time, find out why before you raise a timeout.

</Callout>

</Technical>
<Layman>

Before Playwright clicks, it waits. It checks that the element is there, visible, still, not covered, and enabled. <Cite n={12} /> If this takes too long, the action fails with a timeout error. <Cite n={12} /> So you do not need to add your own waits. <Cite n={4} />

An assertion is a check, like "the welcome text is visible". Web-first assertions try again and again until the check is true or time runs out. <Cite n={13} /> Always put `await` before them. <Cite n={13} />

Some checks do not wait, like `toBe()` and `toEqual()`. They check one time only. This can make a test flaky. <Cite n={13} />

Do not write `expect(await page.getByText('welcome').isVisible()).toBe(true)`. It does not wait. Write `await expect(page.getByText('welcome')).toBeVisible()`. <Cite n={10} />

An assertion waits 5 seconds by default. <Cite n={13} /> A test times out after 30 seconds by default. <Cite n={14} />

The tutorial's advice: a fixed sleep in a test is a warning sign. Wait for what the user sees instead.

</Layman>
<Bangla>

কোনো action-এর আগে Playwright actionability check চালায় এবং সেগুলো pass করা পর্যন্ত অপেক্ষা করে। সময়ের মধ্যে pass না করলে action `TimeoutError` দিয়ে fail করে। <Cite n={12} /> `click()`-এর জন্য element-কে ঠিক একটি হতে হবে, visible, stable, enabled আর not inert হতে হবে, এবং event গ্রহণ করতে হবে। <Cite n={12} /> তাই নিজে থেকে manual wait যোগ করার দরকার নেই। <Cite n={4} />

Web-first assertion শর্তটি সত্য না হওয়া বা timeout শেষ না হওয়া পর্যন্ত বারবার check করে। এগুলো async, তাই অবশ্যই `await` দিন। <Cite n={13} /> `toBe()`, `toEqual()`-এর মতো non-retrying assertion অপেক্ষা করে না, তাই test flaky হতে পারে। <Cite n={13} />

ভুল উপায়: `expect(await page.getByText('welcome').isVisible()).toBe(true)`, কারণ এটি একবার দেখেই ফেরত আসে। সঠিক উপায়: `await expect(page.getByText('welcome')).toBeVisible()`। <Cite n={10} />

Default timeout হলো প্রতিটি assertion-এর জন্য 5 সেকেন্ড <Cite n={13} /> আর প্রতিটি test-এর জন্য 30 সেকেন্ড। <Cite n={14} />

Tutorial-এর পরামর্শ: generated test-এ `page.waitForTimeout(3000)`-এর মতো fixed sleep দেখলে সন্দেহ করুন। এর বদলে user যা দেখে, সেই অবস্থার জন্য web-first assertion দিয়ে অপেক্ষা করুন।

</Bangla>
</Voices>

## Debug a failing test

<Voices>
<Technical>

This section covers four debug tools: UI mode, the trace viewer, the Inspector, and codegen. Learn them before you ask Claude to fix a test, so you can check its fix.

**UI mode** (`npx playwright test --ui`). You explore, run, and debug tests with time travel and a watch mode. <Cite n={15} /> The pick locator button shows the locator for each element of the DOM snapshot. <Cite n={15} />

**Trace viewer.** A trace records each action of a test. <Cite n={16} />

| Command or setting | What it does |
|---|---|
| `npx playwright test --trace on` | Records a trace for each test, during development <Cite n={16} /> |
| `trace: 'on-first-retry'` | Records a trace only on the first retry, for CI <Cite n={16} /> |
| `trace: 'retain-on-failure'` | Records each test, but keeps only the traces of failed tests <Cite n={16} /> |
| `npx playwright show-trace path/to/trace.zip` | Opens a saved trace <Cite n={16} /> |

`trace: 'on'` for every test is not recommended, because it is performance heavy. <Cite n={16} /> In the Actions tab, you see the locator and the duration of each action, with Before and After snapshots. <Cite n={16} /> The trace viewer loads the trace in your browser and sends no data out. <Cite n={16} />

**Inspector** (`--debug`). It opens the Playwright Inspector and a headed browser, with the default timeout set to 0. <Cite n={17} /> To debug one test, give the file and the line: `npx playwright test example.spec.ts:10 --debug`. <Cite n={5} /> Add `page.pause()` to stop at one point. <Cite n={17} />

**Codegen** (`npx playwright codegen <url>`). It records your actions as test code. <Cite n={11} /> From the toolbar, you can add three assertions: visibility, text, and value. <Cite n={11} /> `--save-storage` saves cookies, localStorage, and IndexedDB data at the end of the session. <Cite n={11} />

<Callout type="tip" title="The tutorial's advice">

Codegen code is a first draft. It records what you clicked, and it adds only the assertions that you choose. Add the checks that matter for the requirement before you keep the test.

</Callout>

</Technical>
<Layman>

## Review a generated test

<Voices>
<Technical>

<Callout type="note" title="The tutorial's checklist">

Use this checklist on every test that Claude writes or changes. Each row names the Playwright behavior that it protects.

</Callout>

| Check | Why it matters |
|---|---|
| Each test has at least one assertion on what the user sees. | A test with no assertion passes when the feature is broken. |
| Each web-first assertion has `await` before `expect`. | Retrying assertions are async and must be awaited. <Cite n={13} /> A lint rule, `@typescript-eslint/no-floating-promises`, finds a missing `await`. <Cite n={10} /> |
| No `isVisible()` inside a plain `expect`. | That pattern checks once and does not wait. <Cite n={10} /> |
| No fixed sleep such as `waitForTimeout`. | Playwright already waits before actions and in web-first assertions. <Cite n={4} /> |
| Locators use role, label, text, or test id. No long CSS or XPath chain. | DOM-tied selectors break when the DOM changes. <Cite n={9} /> |
| No `nth()`, `first()`, or `last()` without a reason in a comment. | They can click an element that you did not intend. <Cite n={9} /> |
| No `force: true` without a reason. | It turns off non-essential actionability checks. <Cite n={12} /> |
| The test does not depend on another test or on run order. | Each test gets its own context. <Cite n={7} /> |
| No password, token, or real user data in the code. | Use environment variables and test accounts. |
| The assertion can fail. | Break the expected value on purpose and watch the test fail. |
| Claude showed the command and its output. | A claim of success alone tells you very little. <Cite n={20} /> |

Read the diff yourself before you merge. If a change to a test makes an expected value weaker, ask why, and check the requirement.

</Technical>

## Common mistakes

<Voices>
<Technical>

| Mistake | Fix |
|---|---|
| You accept a generated test because Claude says it passes. | Ask for the command and its output. A claim of success alone tells you very little. <Cite n={20} /> |
| The test uses a fixed sleep to "fix" a flaky step. | Remove it. Use a web-first assertion on the state that the user sees. Playwright waits before each action. <Cite n={4} /> |
| The assertion does not wait or cannot fail: `expect(await locator.isVisible()).toBe(true)` checks once and does not wait, <Cite n={10} /> and a check on a value that the test set itself cannot fail. | Use an auto-retrying assertion with `await`. <Cite n={10} /> Then break the expected value on purpose and watch the test fail (the tutorial's advice). |
| Claude picks a long CSS or XPath selector from the source code. | Give Claude the live page with Playwright MCP or the Playwright CLI. <Cite n={18} /> Prefer role locators. <Cite n={9} /> |
| A strict mode error is "fixed" with `nth()` or `first()`. | Make the locator unique with a filter or a chain. <Cite n={9} /> |
| Traces are `on` for every test in CI. | Use `on-first-retry` or `retain-on-failure`. `on` is performance heavy. <Cite n={16} /> |
| A refactor quietly changes an expected value. | Ask Claude not to change assertions, and read the diff yourself (the tutorial's advice). |

</Technical>
<Layman>

- **You trust "it passes".** Ask Claude for the command and the output. <Cite n={20} />
- **A fixed sleep hides a flaky step.** Remove it. Wait for what the user sees. Playwright already waits before each action. <Cite n={4} />
- **A weak check.** `expect(await locator.isVisible()).toBe(true)` checks once and does not wait, and a check on a value that the test set itself cannot fail. Use a web-first check with `await`. <Cite n={10} /> Then break it on purpose and see it fail.
- **Claude guesses a long CSS path.** Let Claude see the real page with Playwright MCP. <Cite n={18} /> Use role locators first. <Cite n={9} />
- **Two elements match, and the test uses `nth()`.** Make the locator unique instead. <Cite n={9} />
- **Traces are on for every test in CI.** That is heavy. Use `on-first-retry` or `retain-on-failure`. <Cite n={16} />
- **A refactor changes a check.** Tell Claude not to change checks. Read the diff yourself.

</Layman>
<Bangla>

- **"Pass করেছে" কথায় বিশ্বাস করা।** Claude-এর কাছে command আর output চান। <Cite n={20} />
- **Flaky ধাপ ঢাকতে fixed sleep।** এটি সরিয়ে দিন। User যা দেখে, তার জন্য web-first assertion দিয়ে অপেক্ষা করুন। Playwright প্রতিটি action-এর আগে নিজেই অপেক্ষা করে। <Cite n={4} />
- **দুর্বল assertion।** `expect(await locator.isVisible()).toBe(true)` একবার দেখেই ফেরত আসে, অপেক্ষা করে না। আর test নিজে যে value বসিয়েছে, তার check কখনো fail করে না। `await` সহ auto-retrying assertion ব্যবহার করুন। <Cite n={10} /> তারপর ইচ্ছা করে ভুল value দিয়ে fail হতে দেখুন।
- **Source code থেকে লম্বা CSS বা XPath।** Playwright MCP দিয়ে Claude-কে চলমান page দেখান। <Cite n={18} /> Role locator আগে ব্যবহার করুন। <Cite n={9} />
- **Strict mode error `nth()` দিয়ে "ঠিক" করা।** Filter বা chain দিয়ে locator-কে unique করুন। <Cite n={9} />
- **CI-তে প্রতিটি test-এ trace `on`।** এটি ভারী। `on-first-retry` বা `retain-on-failure` ব্যবহার করুন। <Cite n={16} />
- **Refactor-এ চুপচাপ expected value বদলানো।** Claude-কে assertion না বদলাতে বলুন এবং diff নিজে পড়ুন।

</Bangla>

## Key words

| Term | Meaning |
|---|---|
| Playwright Test | The Playwright test framework that this page teaches: `test`, `expect`, and fixtures. |
| Browser context | An isolated, incognito-like profile. Playwright creates one for each test. |
| Fixture | The environment that a test needs, such as `page`. You add your own with `test.extend()`. |
| Locator | A way to find an element on the page at the moment of each action. |
| Role locator | `getByRole()`: finds an element by its accessibility role and name. The docs recommend it first. |
| Strictness | An action on a locator throws an error if more than one element matches. |
| Actionability checks | The checks that Playwright waits for before an action, such as visible, stable, and enabled. |
| Web-first assertion | An `await expect(...)` that retries until the condition is true or the timeout ends. |
| Trace viewer | A tool that shows each recorded action of a test, with its locator and snapshots. |
| UI mode | `--ui`: run, watch, and debug tests with time travel. |
| Codegen | `npx playwright codegen`: records your actions in the browser as test code. |
| Playwright MCP | A tool that you add to Claude Code with `claude mcp add`. It reads the page through accessibility snapshots. |
