# Single Server Architecture

Think of a small corner shop where one person takes the orders, cooks, cleans, and keeps the money box. The shop is cheap to run and easy to understand. But when a bus full of customers arrives, the line goes out the door. And if that one person is sick, the shop closes. A single server is that shop.

<PageMeta />

## In plain words

<Voices>
<Technical>

Single server architecture means that the main parts of an application run on one server. Often this server is a VPS. A VPS is a virtual private server, also called a virtual machine <Cite n={1} />. For example, an Amazon Lightsail instance is a VPS, and you choose an operating system image when you create it <Cite n={1} />.

One machine runs all of these parts:

- **A web server**, such as Nginx. It receives the requests from browsers. Nginx can serve files such as images and static HTML pages <Cite n={2} />. It can also work as a proxy: it receives requests, passes them to another server, and sends the responses back to the clients <Cite n={2} />.
- **The backend application**, for example a Node.js app with the business logic.
- **The database**, for example MySQL.
- **File storage**: the uploaded files, on the local disk.
- **Logs**: the record of what the app did.
- **Background processes**, such as scheduled jobs (cron jobs) and email sending.

This setup is common and practical for small applications, MVPs (minimum viable products: the first small version of a product), internal tools, portfolio websites, small LMS platforms, and launches with low traffic. Google Cloud says that a single-zone design suits workloads that can tolerate downtime <Cite n={3} />.

The big risk is that the server is a **single point of failure (SPOF)**. If a part of the system depends on one single resource, a failure of that resource can affect the whole system <Cite n={3} />. Google Cloud gives this example: if the application runs on a single VM and the VM crashes, the entire stack is effectively unavailable <Cite n={3} />.

All parts also share the same CPU, RAM, disk, and network. So one busy part can slow down all the others. And every resource has an upper limit <Cite n={6} />.

</Technical>

<Bangla>

Single server architecture মানে হলো, একটি application-এর মূল অংশগুলো একটি server-এ চলে। প্রায়ই এই server একটি VPS। VPS মানে virtual private server, যাকে virtual machine-ও বলা হয় <Cite n={1} />। যেমন, একটি Amazon Lightsail instance একটি VPS, এবং এটি তৈরি করার সময় আপনি একটি operating system image বেছে নেন <Cite n={1} />।

একটি machine এই সব অংশ চালায়:

- **Web server**, যেমন Nginx। এটি browser থেকে request গ্রহণ করে। Nginx image আর static HTML page-এর মতো file serve করতে পারে <Cite n={2} />। এটি proxy হিসেবেও কাজ করতে পারে: request নিয়ে অন্য server-এ পাঠায়, তারপর response-গুলো client-এর কাছে ফেরত পাঠায় <Cite n={2} />।
- **Backend application**, যেমন business logic সহ একটি Node.js app।
- **Database**, যেমন MySQL।
- **File storage**: upload করা file-গুলো, local disk-এ।
- **Logs**: app কী করেছে, তার রেকর্ড।
- **Background process**, যেমন scheduled job (cron job) আর email পাঠানো।

ছোট application, MVP (একটি product-এর প্রথম ছোট version), internal tool, portfolio website, ছোট LMS platform, আর কম traffic-এর launch-এর জন্য এই setup প্রচলিত ও কার্যকর। Google Cloud বলে, যে workload downtime সহ্য করতে পারে, তার জন্য single-zone design উপযুক্ত <Cite n={3} />।

বড় ঝুঁকি হলো, server-টি একটি **single point of failure (SPOF)**। Google Cloud-এর উদাহরণ: application একটিমাত্র VM-এ চললে এবং সেই VM crash করলে, পুরো stack কার্যত unavailable হয়ে যায় <Cite n={3} />। সব অংশ একই CPU, RAM, disk আর network ভাগ করে নেয়, তাই একটি ব্যস্ত অংশ বাকি সবগুলোকে ধীর করে দিতে পারে। আর প্রতিটি resource-এর একটি সর্বোচ্চ সীমা আছে <Cite n={6} />।

## When you need it

<Voices>
<Technical>

- The project is new and has few users.
- The traffic is low and easy to predict.
- The budget is small.
- The team is small.
- A fast launch is more important than a complex scaling design.
- High availability (the system stays up when one part fails) is not required yet.

</Technical>
<Layman>

A single server is a good choice in these cases:

- The project is new and has few users.
- The traffic is low and easy to predict.
- The budget is small.
- The team is small.
- A fast launch is more important than a complex scaling design.
- You do not need high availability yet. High availability means that the system stays up when one part fails.

</Layman>
<Bangla>

নিচের অবস্থাগুলোতে single server একটি ভালো পছন্দ:

- Project নতুন, আর user কম।
- Traffic কম এবং সহজে অনুমান করা যায়।
- Budget ছোট।
- Team ছোট।
- জটিল scaling design-এর চেয়ে দ্রুত launch বেশি গুরুত্বপূর্ণ।
- এখনো high availability দরকার নেই। High availability মানে, একটি অংশ fail করলেও system চালু থাকে।

</Bangla>
</Voices>

## A real-life example

<Voices>
<Technical>

A small training institute runs Nginx, a Node.js backend, a MySQL database, the uploaded files, and the logs on one VPS. For 200 to 500 students, this is cheap, simple, and easy to debug. There is one machine to check and one folder of logs to read.

Then 5,000 to 10,000 visitors come at the same time. The CPU and the RAM become full. The database slows down. File downloads become slow, because large downloads and logins now fight for the same CPU, disk, and network. In the worst case, the whole system goes down, and every feature stops at the same time.

</Technical>
<Layman>

A small training institute runs Nginx, a Node.js backend, a MySQL database, the uploaded files, and the logs on one VPS. For 200 to 500 students, this setup is cheap, simple, and easy to debug. The team checks one machine and reads one folder of logs.

File downloads become slow, because large downloads and logins use the same CPU, disk, and network. In the worst case, the whole system goes down, and every feature stops at the same time.

</Layman>
<Bangla>

একটি ছোট training institute একটি VPS-এ Nginx, একটি Node.js backend, একটি MySQL database, upload করা file-গুলো আর log চালায়। 200 থেকে 500 জন শিক্ষার্থীর জন্য এটি সস্তা, সহজ, আর debug করাও সহজ। দেখার জন্য একটি machine, আর পড়ার জন্য log-এর একটি folder।

তারপর একই সময়ে 5,000 থেকে 10,000 visitor আসে। CPU আর RAM ভরে যায়। Database ধীর হয়ে যায়। File download-ও ধীর হয়ে যায়, কারণ বড় download আর login এখন একই CPU, disk আর network নিয়ে লড়াই করে। সবচেয়ে খারাপ ক্ষেত্রে পুরো system বন্ধ হয়ে যায়, আর প্রতিটি feature একসাথে থেমে যায়।

## Common mistakes

<Voices>
<Technical>

- **Running production without a backup.** A failed disk or a bad command can delete everything. AWS lists "Assuming that a backup exists" as a common anti-pattern <Cite n={5} />. Restore your backups from time to time and check that the data is complete and not corrupted <Cite n={5} />.
- **Keeping the uploaded files and the database on the same server with no backup.** If that one disk fails, you lose both at the same time.
- **Not monitoring disk usage.** Logs and uploads grow every day. When the disk is full, the database and the app can stop writing. Monitoring should warn early, for example: "It looks like your database will fill its hard drive in 4 hours" <Cite n={4} />.
- **Assuming that one server can handle very large traffic forever.** Every resource has a limit <Cite n={6} />. See [Vertical Scaling](/architecture/vertical-scaling/) for the first step past it.
- **Making everything tightly coupled.** For example, the code saves files to a fixed local folder and reads them from the same place. A later move to more servers or to object storage then needs many code changes. Separate components let you isolate failures <Cite n={6} />.

</Technical>
<Layman>

- **No backup in production.** A failed disk or a bad command can delete everything. AWS lists "Assuming that a backup exists" as a common anti-pattern <Cite n={5} />. Restore your backups from time to time, and make sure that the data is complete and not corrupted <Cite n={5} />.
- **The uploaded files and the database are on one server, with no backup.** If that disk fails, you lose both.
- **Nobody monitors the disk usage.** Logs and uploads grow every day. When the disk is full, the database and the app can stop writing. Monitoring should warn early, for example: "It looks like your database will fill its hard drive in 4 hours" <Cite n={4} />.
- **You think that one server can handle very large traffic forever.** Every resource has a limit <Cite n={6} />. See [Vertical Scaling](/architecture/vertical-scaling/).
- **Everything is tightly coupled.** For example, the code saves files to a fixed local folder and reads them from there. A later move to more servers or to object storage then needs many code changes. Separate components let you isolate failures <Cite n={6} />.

</Layman>
<Bangla>

এই সাধারণ ভুলগুলোর দিকে খেয়াল রাখুন:

- **Backup ছাড়া production চালানো।** একটি নষ্ট disk বা একটি ভুল command সবকিছু মুছে দিতে পারে। AWS "Assuming that a backup exists"-কে একটি সাধারণ anti-pattern হিসেবে তালিকায় রেখেছে <Cite n={5} />। মাঝে মাঝে আপনার backup restore করুন, এবং দেখুন data সম্পূর্ণ আছে আর corrupted নয় <Cite n={5} />।
- **Upload করা file আর database একই server-এ, কোনো backup ছাড়া।** সেই একটি disk fail করলে আপনি দুটোই একসাথে হারাবেন।
- **Disk usage monitor না করা।** Log আর upload প্রতিদিন বাড়ে। Disk ভরে গেলে database আর app লেখা বন্ধ করে দিতে পারে। Monitoring-এর উচিত আগেভাগে সতর্ক করা, যেমন: "It looks like your database will fill its hard drive in 4 hours" <Cite n={4} />।
- **ধরে নেওয়া যে একটি server চিরকাল খুব বেশি traffic সামলাতে পারবে।** প্রতিটি resource-এর একটি সীমা আছে <Cite n={6} />। সেই সীমা পার হওয়ার প্রথম ধাপের জন্য [Vertical Scaling](/architecture/vertical-scaling/) পাতাটি দেখুন।
- **সবকিছু tightly coupled করে ফেলা।** যেমন, code একটি নির্দিষ্ট local folder-এ file save করে এবং সেখান থেকেই পড়ে। পরে একাধিক server বা object storage-এ যেতে হলে অনেক code পরিবর্তন করতে হয়। Component-গুলো আলাদা থাকলে failure আলাদা করে রাখা যায় <Cite n={6} />।

</Bangla>
</Voices>

## What a tester can check

<Voices>
<Technical>

<Callout type="tip" title="Tutorial advice">
These test ideas are the tutorial's own advice.

- In a test environment, restart the server. Check that the web server, the app, the database, and the background jobs all start again without manual work.
- Fill the disk close to its limit in a test environment. Check what happens to uploads, logs, and database writes, and check that an alert fires first.
- Run a small load test while a large file download runs. Watch the login response time.
- Ask for the backup schedule. Then restore a backup to a clean server and check that the data and the uploaded files are complete.
- Check that log files rotate (old logs are compressed or deleted), so that they do not fill the disk.
- Check that the database port is not open to the public internet, because the database runs on the same machine as the public web server.
</Callout>

</Technical>
<Layman>

These test ideas are the tutorial's own advice.

- In a test environment, restart the server. Check that the web server, the app, the database, and the background jobs all start again with no manual work.
- In a test environment, fill the disk close to its limit. Check what happens to uploads, logs, and database writes. Check that an alert fires first.
- Run a small load test during a large file download. Watch the login response time.
- Ask for the backup schedule. Then restore a backup to a clean server. Check that the data and the uploaded files are complete.
- Check that the log files rotate, so that they do not fill the disk. Rotation means that old logs are compressed or deleted.
- Check that the database port is not open to the public internet. The database runs on the same machine as the public web server.

</Layman>
<Bangla>

নিচের test ধারণাগুলো এই tutorial-এর নিজস্ব পরামর্শ।

- একটি test environment-এ server restart করুন। দেখুন, web server, app, database আর background job-গুলো হাতে কিছু না করেই আবার চালু হয় কি না।
- একটি test environment-এ disk প্রায় তার সীমা পর্যন্ত ভরে ফেলুন। Upload, log আর database write-এর কী হয়, তা দেখুন। আর দেখুন, তার আগে একটি alert আসে কি না।
- একটি বড় file download চলার সময় একটি ছোট load test চালান। Login-এর response time লক্ষ করুন।
- Backup schedule জেনে নিন। তারপর একটি পরিষ্কার server-এ একটি backup restore করুন, এবং দেখুন data আর upload করা file-গুলো সম্পূর্ণ আছে কি না।
- দেখুন, log file-গুলো rotate হয় কি না (পুরনো log compress বা delete হয়), যাতে সেগুলো disk ভরে না ফেলে।
- দেখুন, database port public internet-এর জন্য খোলা নেই। কারণ database আর public web server একই machine-এ চলে।

## Key words

| Word | Meaning |
|---|---|
| Server | A computer that answers requests from other computers |
| VPS | Virtual private server, also called a virtual machine <Cite n={1} /> |
| Web server | The program that receives HTTP requests and serves files, such as Nginx |
| Proxy | A server that receives requests, passes them to another server, and returns the responses |
| SPOF | Single point of failure: one part whose failure stops the whole system |
| MVP | Minimum viable product: the first small version of a product |
| Backup | A copy of the data that you can restore after a loss |
| Saturation | How "full" a resource is, such as CPU, RAM, or disk <Cite n={4} /> |
| Tightly coupled | Parts that depend on each other so much that you cannot change one without the other. Decoupled parts can change without an effect on the others <Cite n={6} />. |
