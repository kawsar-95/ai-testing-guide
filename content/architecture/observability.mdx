# Monitoring and Observability

Think of a car dashboard. The warning light tells you that something is wrong with the engine. That is monitoring. The mechanic who plugs in a reader and finds that one sensor failed at 80 km/h is doing observability. You need both: the light to know that there is a problem, and the reader to know why.

## In plain words

<Voices>
<Technical>

**Monitoring** means to collect, process, and show live numbers about a system, such as request counts, error counts, and processing times <Cite n={2} />. Google's SRE book says monitoring must answer two questions: what is broken, and why <Cite n={2} />. Monitoring tells you that the system is not healthy.

**Observability** lets you understand a system from the outside, by asking it questions. It helps you answer "Why is this happening?" <Cite n={1} />. For this, the application must send out three kinds of signals: logs, metrics, and traces <Cite n={1} />.

| Signal | What it is | What it tells you |
|---|---|---|
| Log | A message with a timestamp that a service writes <Cite n={1} /> | What happened |
| Metric | A number collected over a period of time, such as error rate, CPU use, or request rate <Cite n={1} /> | How much, or how often |
| Trace | The path of one request through many services <Cite n={1} /> | Where the request spent its time |

A trace is made of spans. A span is one unit of work, such as one database call <Cite n={1} />. For example, one page load can pass through an API gateway, a backend service, and a database. Each step is a span, and together they make one trace <Cite n={1} />.

Logs alone often miss context, such as where the code was called from. They become much more useful when they are linked to a trace <Cite n={1} />. That link is a shared ID. The W3C Trace Context standard defines HTTP headers that carry an ID for each request from service to service <Cite n={9} />.

### The numbers to watch

Google's SRE book names four golden signals: latency, traffic, errors, and saturation <Cite n={2} />. In everyday terms:

- **RPS** (requests per second): the traffic. For a web service, the SRE book says traffic is usually HTTP requests per second <Cite n={2} />.
- **Error rate**: the share of requests that fail. A failure can also be a `200 OK` with the wrong content <Cite n={2} />.
- **p95 and p99 latency**: 95 % or 99 % of requests are faster than this time. Averages hide slow requests. The SRE book gives an example: with an average of 100 ms, 1 % of requests can still take 5 s <Cite n={2} />.
- **Queue length, slow database queries, and replication lag**: signs that a part behind the API is falling behind.
- **CPU, RAM, and disk use**: how full the servers are. The SRE book calls this saturation: how "full" your service is <Cite n={2} />.

</Technical>
<Layman>

**Monitoring** means to collect, process, and show live numbers about a system, such as request counts, error counts, and processing times <Cite n={2} />. It tells you that the system is not healthy. Google's SRE book says that monitoring must answer two questions: what is broken, and why <Cite n={2} />.

**Observability** lets you understand a system from the outside. You ask the system questions, such as "Why is this happening?" <Cite n={1} />. For this, the application must send out three kinds of signals <Cite n={1} />:

- **Logs**: messages with a timestamp. They tell you what happened.
- **Metrics**: numbers collected over time, such as the error rate. They tell you how much or how often.
- **Traces**: the path of one request through many services. A trace is made of spans. Each span is one unit of work, such as one database call.

A shared ID links the logs to a trace. The W3C Trace Context standard defines HTTP headers that carry this ID from service to service <Cite n={9} />.

Google's SRE book names four golden signals: latency, traffic, errors, and saturation <Cite n={2} />. Watch p95 and p99 latency too, because averages hide slow requests <Cite n={2} />.

</Layman>
<Bangla>

**Monitoring** মানে একটি system সম্পর্কে live সংখ্যা সংগ্রহ করা, process করা এবং দেখানো, যেমন request-এর সংখ্যা, error-এর সংখ্যা এবং processing time <Cite n={2} />। Google-এর SRE book বলে, monitoring-কে দুটি প্রশ্নের উত্তর দিতে হবে: কী নষ্ট হয়েছে, এবং কেন <Cite n={2} />। Monitoring আপনাকে জানায় যে system healthy নয়।

**Observability** আপনাকে বাইরে থেকে প্রশ্ন করে একটি system বুঝতে সাহায্য করে। এটি "এটি কেন হচ্ছে?" প্রশ্নের উত্তর দিতে সাহায্য করে <Cite n={1} />। এর জন্য application-কে তিন ধরনের signal পাঠাতে হয়: log, metric এবং trace <Cite n={1} />।

- **Log**: একটি service-এর লেখা timestamp-সহ একটি message। এটি বলে কী ঘটেছে।
- **Metric**: একটি সময়ের মধ্যে সংগ্রহ করা একটি সংখ্যা, যেমন error rate, CPU use বা request rate। এটি বলে কতটা বা কতবার।
- **Trace**: অনেক service-এর মধ্য দিয়ে একটি request-এর পথ। এটি বলে request কোথায় সময় নিয়েছে। একটি trace কয়েকটি span দিয়ে তৈরি। একটি span হলো কাজের একটি একক, যেমন একটি database call।

শুধু log-এ প্রায়ই context থাকে না। Log-কে একটি trace-এর সাথে যুক্ত করলে log অনেক বেশি কাজে লাগে <Cite n={1} />। এই যোগসূত্র হলো একটি shared ID। W3C Trace Context standard এমন HTTP header নির্ধারণ করে, যা প্রতিটি request-এর একটি ID এক service থেকে আরেক service-এ নিয়ে যায় <Cite n={9} />।

Google-এর SRE book চারটি golden signal-এর কথা বলে: latency, traffic, errors এবং saturation <Cite n={2} />। p95 আর p99 latency-ও দেখুন, কারণ average ধীর request-গুলোকে আড়াল করে। যেমন, average 100 ms হলেও 1 % request 5 s নিতে পারে <Cite n={2} />।

</Bangla>
</Voices>

## When you need it

<Voices>
<Technical>

- A production system is running.
- There are critical flows: payment, login, order, or enrollment.
- The system uses more than one service or server.
- The system depends on a queue, a cache, or an external API.
- The team must find the cause of an incident fast.
- There is an uptime target or an SLA (service level agreement, a promise to customers).

</Technical>
<Layman>

You need monitoring and observability in these cases:

- A production system is running.
- The system has critical flows, such as payment, login, order, or enrollment.
- The system uses more than one service or server.
- The system depends on a queue, a cache, or an external API.
- The team must find the cause of an incident fast.
- There is an uptime target or an SLA. An SLA (service level agreement) is a promise to customers.

</Layman>
<Bangla>

নিচের যেকোনো অবস্থায় আপনার monitoring আর observability দরকার:

- একটি production system চলছে।
- System-এ গুরুত্বপূর্ণ flow আছে: payment, login, order বা enrollment।
- System একাধিক service বা server ব্যবহার করে।
- System একটি queue, একটি cache বা একটি external API-এর উপর নির্ভর করে।
- Team-কে দ্রুত একটি incident-এর কারণ খুঁজে বের করতে হবে।
- একটি uptime target বা একটি SLA আছে। SLA (service level agreement) হলো customer-দের কাছে দেওয়া একটি প্রতিশ্রুতি।

</Bangla>
</Voices>

## A real-life example

<Voices>
<Technical>

Students say that login in the LMS is slow. Without observability, developers guess and read code at random.

With observability, the team sees the problem in steps:

1. **Metrics** show that login p95 latency went up from 300 ms to 3 s.
2. **Logs** show timeouts from the SMS provider that sends the login code.
3. **A trace** of one slow login shows that the call to the SMS provider takes 2.5 s.

Now the cause is clear, and nobody had to guess.

</Technical>
<Layman>

Students say that login in the LMS is slow. Without observability, the developers guess and read code at random.

With observability, the team finds the problem in steps:

1. The **metrics** show that the login p95 latency went up from 300 ms to 3 s.
2. The **logs** show timeouts from the SMS provider. This provider sends the login code.
3. A **trace** of one slow login shows that the call to the SMS provider takes 2.5 s.

Now the cause is clear. Nobody had to guess.

</Layman>
<Bangla>

ধরুন, শিক্ষার্থীরা বলছেন যে LMS-এ login ধীর। Observability না থাকলে developer-রা অনুমান করেন এবং এলোমেলোভাবে code পড়েন।

Observability থাকলে team ধাপে ধাপে সমস্যাটি দেখতে পায়:

1. **Metric** দেখায় যে login-এর p95 latency 300 ms থেকে বেড়ে 3 s হয়েছে।
2. **Log** দেখায় যে login code পাঠানো SMS provider থেকে timeout আসছে।
3. একটি ধীর login-এর **trace** দেখায় যে SMS provider-কে করা call-টি 2.5 s নেয়।

এখন কারণটি পরিষ্কার, আর কাউকে অনুমান করতে হয়নি।

</Bangla>
</Voices>

## Common tools

<Voices>
<Technical>

The tool names below come from common practice. They are examples, not a recommendation.

| Area | Popular tools |
|---|---|
| Logs | ELK Stack / Elastic Stack, Grafana Loki, Splunk, Datadog Logs, AWS CloudWatch Logs |
| Metrics | Prometheus, Grafana, Datadog, New Relic, AWS CloudWatch |
| Traces / APM | Jaeger, Zipkin, OpenTelemetry, Datadog APM, New Relic APM |
| Alerting | Alertmanager, Grafana Alerting, PagerDuty, Opsgenie, AWS CloudWatch Alarms |
| Cloud monitoring | AWS CloudWatch, Google Cloud Monitoring, Azure Monitor |

APM means application performance monitoring. What some of these tools do, in one line each:

- **Prometheus** is an open-source monitoring and alerting toolkit. It stores metrics as time series, which are values with a timestamp <Cite n={3} />.
- **Alertmanager** removes duplicate alerts, groups them, and sends them to a receiver such as email, PagerDuty, or OpsGenie <Cite n={4} />.
- **Grafana Loki** is an open-source logging stack. It indexes only the labels of the logs, not the full text <Cite n={5} />.
- **Grafana** lets you query, show, and alert on metrics, logs, and traces <Cite n={6} />.
- **Jaeger** is an open-source distributed tracing platform <Cite n={7} />.
- **OpenTelemetry** is the way to add the code that sends out the signals <Cite n={1} />.
- **AWS CloudWatch** monitors AWS resources and apps. Its alarms watch metrics against limits that you set <Cite n={8} />.

</Technical>

## Common mistakes

<Voices>
<Technical>

- **Logs with no context.** "Error occurred" with no user, no request, and no step is noise.
- **No request ID or correlation ID.** Without one shared ID, you cannot join the log lines of one request across services. The W3C Trace Context standard exists to carry an ID that identifies each request from service to service <Cite n={9} />.
- **Only CPU alerts.** CPU can be fine while payments fail. Watch business signals too, such as failed payments per minute.
- **Metrics but no useful alert.** Google's SRE book says every page to a human should be actionable <Cite n={2} />.
- **Microservices with no traces.** When a request crosses ten services, logs alone cannot show where the time went.

</Technical>
<Layman>

Look out for these common mistakes:

- **Logs with no context.** A log line such as "Error occurred" with no user, no request, and no step is only noise.
- **No request ID or correlation ID.** Without one shared ID, you cannot join the log lines of one request across services. The W3C Trace Context standard exists to carry an ID that identifies each request from service to service <Cite n={9} />.
- **Only CPU alerts.** The CPU can be fine while payments fail. Also watch business signals, such as failed payments per minute.
- **Metrics but no useful alert.** Google's SRE book says that every page to a human should be actionable <Cite n={2} />.
- **Microservices with no traces.** When a request goes through ten services, logs alone cannot show where the time went.

</Layman>
<Bangla>

এই সাধারণ ভুলগুলোর দিকে খেয়াল রাখুন:

- **Context ছাড়া log।** User, request বা step ছাড়া "Error occurred"-এর মতো একটি log শুধু noise।
- **কোনো request ID বা correlation ID নেই।** একটি shared ID ছাড়া আপনি বিভিন্ন service জুড়ে একটি request-এর log line-গুলো জোড়া লাগাতে পারবেন না। W3C Trace Context standard ঠিক এই কাজের জন্য আছে: এটি এমন একটি ID বহন করে, যা এক service থেকে আরেক service-এ প্রতিটি request-কে চিহ্নিত করে <Cite n={9} />।
- **শুধু CPU alert।** CPU ঠিক থাকলেও payment fail করতে পারে। Business signal-ও দেখুন, যেমন প্রতি মিনিটে fail হওয়া payment-এর সংখ্যা।
- **Metric আছে, কিন্তু কাজের alert নেই।** Google-এর SRE book বলে, একজন মানুষের কাছে যাওয়া প্রতিটি page actionable হওয়া উচিত <Cite n={2} />।
- **Trace ছাড়া microservices।** একটি request দশটি service পার হলে শুধু log দেখে বোঝা যায় না সময় কোথায় গেল।

</Bangla>

## What a tester can check

<Voices>
<Technical>

<Callout type="tip" title="Tutorial advice">
These test ideas are the tutorial's own advice.

- **Log content.** Run a payment and a failed login. Check that each log line has a timestamp, a request ID, the user ID, and the step. Check that no password, OTP, or card number is in the logs.
- **Request ID end to end.** Send one request with a known ID. Find it in the gateway, the service, and the worker logs.
- **Alert fires.** In a test environment, make a dependency slow or make payments fail. Check that the right alert fires within the promised time, and that it says what to do.
- **Trace is complete.** Open the trace of one checkout. Check that each service and each external call shows up as a span.
- **Performance tests report p95 and p99.** Do not accept a report that shows only the average.
</Callout>

</Technical>
<Layman>

These test ideas are the tutorial's own advice.

- **Log content.** Run a payment and a failed login. Make sure that each log line has a timestamp, a request ID, the user ID, and the step. Make sure that the logs contain no password, OTP, or card number.
- **Request ID end to end.** Send one request with a known ID. Find this ID in the gateway logs, the service logs, and the worker logs.
- **Alert fires.** In a test environment, make a dependency slow, or make payments fail. Make sure that the correct alert fires within the promised time. Make sure that the alert says what to do.
- **Trace is complete.** Open the trace of one checkout. Make sure that each service and each external call shows as a span.
- **Performance tests report p95 and p99.** Do not accept a report that shows only the average.

</Layman>

নিচের test ধারণাগুলো এই tutorial-এর নিজস্ব পরামর্শ।

- **Log-এর content।** একটি payment আর একটি failed login চালান। দেখুন, প্রতিটি log line-এ একটি timestamp, একটি request ID, user ID এবং step আছে কি না। দেখুন, log-এ কোনো password, OTP বা card number নেই।

- **Alert চালু হয়।** একটি test environment-এ একটি dependency ধীর করুন বা payment fail করান। দেখুন, ঠিক alert-টি প্রতিশ্রুত সময়ের মধ্যে আসে কি না, এবং alert-টি বলে কি না কী করতে হবে।
- **Trace সম্পূর্ণ।** একটি checkout-এর trace খুলুন। দেখুন, প্রতিটি service এবং প্রতিটি external call একটি span হিসেবে দেখা যায় কি না।

## Key words

| Word | Meaning |
|---|---|
| Monitoring | Collecting and showing live numbers that tell you if a system is healthy |
| Observability | The power to find out why a system behaves as it does, from its signals |
| Log | A timestamped message about one event |
| Metric | A number measured over time, such as requests per second |
| Trace | The path of one request through all the services it touches |
| Span | One step inside a trace, such as one database call |
| p95 latency | The time that 95 % of requests are faster than |
| Saturation | How full a resource is, such as CPU or a queue |
| Correlation ID | One ID that follows a request through every service |
| SLA | A promise to customers about uptime or speed |
