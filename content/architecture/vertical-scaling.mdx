# Vertical Scaling

Your family grows, and your small car is now too small. So you sell it and buy a bigger car. The trip is more comfortable, and you change nothing else in your life. But you still have only one car. If it breaks down, nobody goes anywhere. And there is a biggest car that you can buy. Vertical scaling is the bigger car.

<PageMeta />

## In plain words

<Voices>
<Technical>

**Vertical scaling**, also called **scaling up**, means that you change the capacity of a resource <Cite n={1} />. You make the same machine more powerful. For example, you move the application to a larger virtual machine size <Cite n={1} />. In practice, you add more CPU, more RAM, a faster disk, or a bigger database instance. Microsoft describes it as adding compute capacity to existing resources <Cite n={2} />.

In this tutorial's view, it is often the first practical scaling step, because the code and the architecture can stay the same. Microsoft says vertical scaling is useful when more processing power or memory in a single instance helps the workload <Cite n={2} />. It is also a good fit when the work is not easy to divide, or when the app architecture does not support horizontal scaling <Cite n={2} />. Horizontal scaling means adding more instances of a resource <Cite n={1} />; see [Horizontal Scaling](/architecture/horizontal-scaling/).

Vertical scaling has four limits:

- **Downtime.** A resize often makes the system temporarily unavailable while it is redeployed <Cite n={1} />.
- **A ceiling.** Every resource has an upper scale limit <Cite n={2} />.
- **Cost.** Larger and more powerful resources can cost more <Cite n={2} />.
- **Still one machine.** If the application runs on a single VM and that VM crashes, the whole system is effectively unavailable. That VM is a single point of failure (SPOF) <Cite n={3} />. Horizontal scaling gives better resiliency, because the work is spread across more servers <Cite n={2} />.

A bigger machine also does not fix every slow system. Adding resources does not guarantee better performance <Cite n={1} />. Find the bottleneck (the one part that limits the speed) before you add capacity. A database, for example, can limit throughput even when you add more compute <Cite n={1} />.

</Technical>

<Bangla>

Vertical scaling-কে scaling up-ও বলা হয়। এর অর্থ হলো একটি resource-এর capacity বদলানো <Cite n={1} />। অর্থাৎ আপনি একই machine-কে আরও শক্তিশালী করেন, যেমন application-টিকে একটি বড় virtual machine size-এ সরিয়ে নেন <Cite n={1} />। বাস্তবে আপনি আরও CPU, আরও RAM, দ্রুততর disk, অথবা বড় database instance যোগ করেন।

এই tutorial-এর মতে, এটি প্রায়ই প্রথম ব্যবহারিক scaling ধাপ, কারণ code আর architecture একই রাখা যায়। Microsoft বলে, একটি instance-এ বেশি processing power বা memory workload-কে সাহায্য করলে vertical scaling কাজে লাগে <Cite n={2} />। কাজ সহজে ভাগ করা না গেলে, অথবা app architecture horizontal scaling support না করলেও এটি ভালো বিকল্প <Cite n={2} />। Horizontal scaling মানে একটি resource-এর আরও instance যোগ করা <Cite n={1} />।

Vertical scaling-এর চারটি সীমা আছে:

- **Downtime।** Resize করলে system প্রায়ই সাময়িকভাবে unavailable থাকে, যতক্ষণ এটি আবার deploy হয় <Cite n={1} />।
- **একটি ceiling।** প্রতিটি resource-এর একটি সর্বোচ্চ scale limit আছে <Cite n={2} />।
- **খরচ।** বড় ও বেশি শক্তিশালী resource-এর খরচ বেশি হতে পারে <Cite n={2} />।
- **এখনও একটিই machine।** Application একটি VM-এ চললে এবং সেই VM crash করলে পুরো system কার্যত unavailable হয়ে যায়। সেই VM একটি single point of failure (SPOF) <Cite n={3} />।

বেশি resource যোগ করলেই ভালো performance নিশ্চিত হয় না <Cite n={1} />। Capacity যোগ করার আগে bottleneck, অর্থাৎ যে অংশটি গতি সীমিত করে, খুঁজে বের করুন। যেমন, বেশি compute যোগ করলেও একটি database throughput সীমিত রাখতে পারে <Cite n={1} />।

</Bangla>
</Voices>

## When you need it

<Voices>
<Technical>

- You want to keep the architecture simple.
- You need a quick performance improvement.
- The bottleneck is mainly CPU, RAM, disk I/O (reading from and writing to the disk), or the size of the database instance.
- The traffic grows at a moderate rate.
- The team is not ready yet to run a system with many servers.

To know which resource is the bottleneck, measure saturation. Google's SRE book says to watch the resource that is most constrained: memory in a memory-constrained system, I/O in an I/O-constrained system <Cite n={4} />. Many systems become slow before they reach 100% use <Cite n={4} />. So a CPU at 85% can already mean slow pages.

</Technical>
<Layman>

You need vertical scaling in these cases:

- You want to keep the architecture simple.
- You need a quick performance improvement.
- The bottleneck is mainly CPU, RAM, disk I/O (reading from and writing to the disk), or the size of the database instance.
- The traffic grows at a moderate rate.
- The team is not ready yet to run a system with many servers.

To know which resource is the bottleneck, measure saturation. Watch the resource that limits the system most: memory when memory is the limit, I/O when I/O is the limit <Cite n={4} />. Many systems become slow before they reach 100% use <Cite n={4} />. So a CPU at 85% can already mean slow pages.

</Layman>
<Bangla>

নিচের অবস্থাগুলোতে vertical scaling কাজে লাগে:

- আপনি architecture সহজ রাখতে চান।
- আপনার performance-এর দ্রুত উন্নতি দরকার।
- Bottleneck মূলত CPU, RAM, disk I/O (disk থেকে পড়া ও disk-এ লেখা), অথবা database instance-এর size।
- Traffic মাঝারি হারে বাড়ছে।
- Team এখনও অনেক server-এর একটি system চালানোর জন্য প্রস্তুত নয়।

কোন resource bottleneck, তা জানতে saturation মাপুন। Google-এর SRE book বলে, যে resource সবচেয়ে বেশি সীমিত, সেটির দিকে নজর রাখুন: memory-সীমিত system-এ memory, I/O-সীমিত system-এ I/O <Cite n={4} />। অনেক system 100% ব্যবহারে পৌঁছানোর আগেই ধীর হয়ে যায় <Cite n={4} />। তাই CPU 85%-এ থাকলেও page ধীর হতে পারে।

</Bangla>
</Voices>

## A real-life example

<Voices>
<Technical>

During an admission campaign, the LMS server CPU reaches 95%, and the RAM is almost full. As a quick fix, the team upgrades the VPS from 2 CPU and 4 GB RAM to 8 CPU and 16 GB RAM. (A VPS is a virtual private server, also called a virtual machine <Cite n={6} />.)

The response time improves. But the server is still a single point of failure. If that server goes down, the full system goes down.

Two more things can go wrong. First, the resize itself can need a restart, so the team must do it outside the busy hours. Second, if the real cause was one slow database query, the bigger server only hides the problem until traffic grows again.

</Technical>
<Layman>

During an admission campaign, the CPU of the LMS server reaches 95%, and the RAM is almost full. As a quick fix, the team upgrades the VPS from 2 CPU and 4 GB RAM to 8 CPU and 16 GB RAM. A VPS is a virtual private server, also called a virtual machine <Cite n={6} />.

The response time improves. But the server is still a single point of failure. If that server goes down, the full system goes down.

Two more problems can occur. First, the resize can need a restart. So the team must do it outside the busy hours. Second, maybe the real cause was one slow database query. Then the bigger server only hides the problem until the traffic grows again.

</Layman>
<Bangla>

একটি admission campaign চলার সময় LMS server-এর CPU 95%-এ পৌঁছায়, আর RAM প্রায় পূর্ণ হয়ে যায়। দ্রুত সমাধান হিসেবে team VPS-টি 2 CPU ও 4 GB RAM থেকে 8 CPU ও 16 GB RAM-এ upgrade করে। VPS হলো virtual private server, যাকে virtual machine-ও বলা হয় <Cite n={6} />।

Response time ভালো হয়। কিন্তু server-টি এখনও একটি single point of failure। সেই server বন্ধ হলে পুরো system বন্ধ হয়ে যায়।

আরও দুটি সমস্যা হতে পারে। প্রথমত, resize-এর জন্য restart লাগতে পারে, তাই team-কে এটি ব্যস্ত সময়ের বাইরে করতে হবে। দ্বিতীয়ত, আসল কারণ যদি একটি ধীর database query হয়, তাহলে বড় server শুধু সমস্যাটি আড়াল করে, যতক্ষণ না traffic আবার বাড়ে।

</Bangla>
</Voices>

## Common mistakes

<Voices>
<Technical>

- **Upgrading the server without measuring the real bottleneck.** If the database waits for the disk, more CPU does not help.
- **Thinking that vertical scaling gives high availability.** It does not. There is still one machine, and when it stops, everything stops.
- **Upgrading the server but not fixing slow database queries.** MySQL has a slow query log for this. It records SQL statements that take more than `long_query_time` seconds <Cite n={5} />, and these queries are candidates for optimization <Cite n={5} />. The log is disabled by default <Cite n={5} />, so the team must turn it on.
- **Ignoring backup, monitoring, and alerting.** A bigger server fails in the same ways as a small one.
- **Thinking that one machine can scale forever.** Every resource has a limit <Cite n={2} />. Plan the next step before you reach it.
- **Resizing during peak traffic.** The resize can make the system unavailable for a short time <Cite n={1} />.

</Technical>
<Layman>

Look out for these common mistakes:

- **You upgrade the server, but you do not measure the real bottleneck.** If the database waits for the disk, more CPU does not help.
- **You think that vertical scaling gives high availability.** It does not. There is still one machine. When it stops, everything stops.
- **You upgrade the server, but you do not fix slow database queries.** MySQL has a slow query log for this. It records the SQL statements that take more than `long_query_time` seconds <Cite n={5} />. These queries are candidates for optimization <Cite n={5} />. The log is disabled by default <Cite n={5} />, so the team must turn it on.
- **You ignore backup, monitoring, and alerting.** A bigger server fails in the same ways as a small one.
- **You think that one machine can scale forever.** Every resource has a limit <Cite n={2} />. Plan the next step before you reach it.
- **You resize during peak traffic.** The resize can make the system unavailable for a short time <Cite n={1} />.

</Layman>
<Bangla>

এই সাধারণ ভুলগুলোর দিকে খেয়াল রাখুন:

- **আসল bottleneck না মেপেই server upgrade করা।** Database যদি disk-এর জন্য অপেক্ষা করে, তাহলে বেশি CPU কোনো সাহায্য করে না।
- **ভাবা যে vertical scaling high availability দেয়।** দেয় না। এখনও একটিই machine থাকে, আর সেটি থামলে সবকিছু থেমে যায়।
- **Server upgrade করা, কিন্তু ধীর database query ঠিক না করা।** এর জন্য MySQL-এ একটি slow query log আছে। এটি সেই SQL statement-গুলো record করে, যেগুলোতে `long_query_time` সেকেন্ডের বেশি সময় লাগে <Cite n={5} />, আর এই query-গুলো optimization-এর জন্য উপযুক্ত <Cite n={5} />। Log-টি default হিসেবে disabled থাকে <Cite n={5} />, তাই team-কে এটি চালু করতে হবে।
- **Backup, monitoring আর alerting উপেক্ষা করা।** একটি বড় server-ও ছোট server-এর মতো একইভাবে fail করে।
- **ভাবা যে একটি machine চিরকাল scale করতে পারে।** প্রতিটি resource-এর একটি limit আছে <Cite n={2} />। সেখানে পৌঁছানোর আগেই পরের ধাপের পরিকল্পনা করুন।
- **Peak traffic-এর সময় resize করা।** Resize-এর ফলে system অল্প সময়ের জন্য unavailable হতে পারে <Cite n={1} />।

</Bangla>
</Voices>

## What a tester can check

<Voices>
<Technical>

<Callout type="tip" title="Tutorial advice">
These test ideas are the tutorial's own advice.

- Run the same load test before and after the upgrade. Compare the 95th percentile response time and the error rate. Without a "before" number, nobody can prove that the upgrade helped.
- During the load test, watch CPU, RAM, disk I/O, and database connections. Find the resource that becomes full first.
- After a load test, read the slow query log (or ask the team for it). Report the slowest queries.
- Test the resize window in a test environment. Check what users see, and check if sessions and background jobs survive the restart.
- Push the load past the new limit. Record the new breaking point, so that the team knows how much room is left.
- Stop the server in a test environment. Check that the monitoring alert fires, because the server is still a single point of failure.
</Callout>

</Technical>

These test ideas are the tutorial's own advice.

- Run the same load test before and after the upgrade. Compare the 95th percentile response time and the error rate. Without a "before" number, nobody can prove that the upgrade helped.

<Bangla>

নিচের test ধারণাগুলো এই tutorial-এর নিজস্ব পরামর্শ।

- Upgrade-এর আগে ও পরে একই load test চালান। 95th percentile response time আর error rate তুলনা করুন। "আগের" কোনো সংখ্যা না থাকলে কেউ প্রমাণ করতে পারবে না যে upgrade কাজে লেগেছে।
- Load test চলার সময় CPU, RAM, disk I/O আর database connection-গুলোর দিকে নজর রাখুন। কোন resource সবার আগে পূর্ণ হয়, তা খুঁজে বের করুন।
- Load test-এর পরে slow query log পড়ুন (অথবা team-এর কাছে চেয়ে নিন)। সবচেয়ে ধীর query-গুলো report করুন।
- একটি test environment-এ resize window test করুন। User-রা কী দেখেন, তা দেখুন, এবং session ও background job-গুলো restart-এর পরেও টিকে থাকে কি না, তা যাচাই করুন।
- নতুন limit ছাড়িয়ে যাওয়া পর্যন্ত load বাড়ান। নতুন breaking point record করুন, যাতে team জানে আর কতটা জায়গা বাকি আছে।
- একটি test environment-এ server বন্ধ করুন। Alert trigger হয় কি না, তা যাচাই করুন, কারণ server-টি এখনও একটি single point of failure।

## Key words

| Word | Meaning |
|---|---|
| Vertical scaling (scale up) | Make one machine more powerful: more CPU, RAM, or a faster disk |
| Horizontal scaling (scale out) | Add more machines that share the work |
| Bottleneck | The one part that limits the speed of the whole system |
| Saturation | How "full" a resource is, such as CPU, RAM, or disk <Cite n={4} /> |
| Disk I/O | Reading data from the disk and writing data to it |
| Instance size | The amount of CPU and RAM that a virtual machine or database instance has |
| SPOF | Single point of failure: one part whose failure stops the whole system |
| Slow query log | A MySQL log of the SQL statements that take too long |
| Baseline | A measurement before a change, used to compare with the result after the change |
