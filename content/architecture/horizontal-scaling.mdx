# Horizontal Scaling

Think of a supermarket on a busy Saturday. One cashier cannot serve a long queue, so the shop opens more checkout counters, and each new customer goes to a free counter. Horizontal scaling does the same for software. You run the same application on more servers, and you share the traffic between them. This page tells you what horizontal scaling fixes, what it does not fix, and what a tester can check.

<PageMeta />

## In plain words

<Voices>
<Technical>

Horizontal scaling, also called scaling out, means that you add more instances of a resource. An instance is one running copy of the application, for example one app server. Scaling in is the opposite: you remove instances when the demand goes down <Cite n={1} />. [Vertical scaling](/architecture/vertical-scaling/) is different. It makes one machine bigger, for example a larger virtual machine <Cite n={1} />.

With horizontal scaling, the same code runs on two, three, or more app servers. A [load balancer](/architecture/load-balancer/) receives the requests and spreads them across the servers. It sends traffic only to the servers that are healthy <Cite n={5} />.

More servers give more capacity. They can also make the system more reliable <Cite n={2} />. AWS advises you to replace one large resource with many small ones, so that one failure has a smaller effect on the whole system <Cite n={3} />. If one app server stops, the other servers continue to serve users.

But scaling out does not fix every problem. If the database is the slow part, more web servers do not help <Cite n={2} />. Microsoft tells you to check the capacity of the data stores separately, because their scaling limits can differ from the limits of the app servers <Cite n={1} />. Also, the old servers can continue to serve requests while new servers start. But this depends on the application design, on how the traffic is routed, and on the safe removal of servers <Cite n={1} />.

</Technical>

Horizontal scaling, or scaling out, means that you add more instances. An instance is one running copy of the app, for example one app server. Scaling in removes instances when the demand goes down <Cite n={1} />. [Vertical scaling](/architecture/vertical-scaling/) makes one machine bigger <Cite n={1} />.

But this depends on the app design, the traffic routing, and the safe removal of servers <Cite n={1} />.

</Layman>
<Bangla>

Horizontal scaling-কে scaling out-ও বলা হয়। এর মানে হলো একটি resource-এর আরও instance যোগ করা। একটি instance হলো application-এর একটি চলমান copy, যেমন একটি app server। Scaling in হলো এর উল্টো: demand কমে গেলে আপনি instance সরিয়ে নেন <Cite n={1} />। [Vertical scaling](/architecture/vertical-scaling/) আলাদা জিনিস। এটি একটি machine-কেই বড় করে, যেমন একটি বড় virtual machine <Cite n={1} />।

Horizontal scaling-এ একই code দুই, তিন বা তার বেশি app server-এ চলে। একটি [load balancer](/architecture/load-balancer/) request-গুলো গ্রহণ করে এবং server-গুলোর মধ্যে ভাগ করে দেয়। এটি শুধু healthy server-এ traffic পাঠায় <Cite n={5} />।

বেশি server মানে বেশি capacity। এতে system আরও reliable-ও হতে পারে <Cite n={2} />। AWS পরামর্শ দেয়, একটি বড় resource-এর বদলে অনেকগুলো ছোট resource ব্যবহার করুন, যাতে একটি failure পুরো system-এ কম প্রভাব ফেলে <Cite n={3} />। একটি app server থেমে গেলেও বাকি server-গুলো user-দের service দিতে থাকে।

তবে scaling out সব সমস্যার সমাধান করে না। Database যদি ধীর অংশ হয়, তাহলে বেশি web server কোনো সাহায্য করে না <Cite n={2} />। Microsoft বলে, data store-গুলোর capacity আলাদাভাবে যাচাই করুন, কারণ তাদের scaling limit app server-এর limit থেকে আলাদা হতে পারে <Cite n={1} />। নতুন server চালু হওয়ার সময় পুরনো server-গুলো request সামলাতে পারে। কিন্তু এটি নির্ভর করে application design, traffic কীভাবে route হয়, এবং server নিরাপদে সরানোর ওপর <Cite n={1} />।

</Bangla>
</Voices>

## When you need it

<Voices>
<Technical>

- One server cannot handle the traffic.
- The service must continue when one server crashes. This is high availability: the system stays usable when a part fails.
- The application can be stateless. This means that any server can handle any request <Cite n={2} />. See [Stateless Service](/architecture/stateless-service/).
- The traffic peaks are predictable. For a regular load, you can scale out on a schedule, for example during business hours <Cite n={2} />.
- You need deployments with zero downtime. A rolling update replaces the old instances with new ones step by step. This lets the update happen with zero downtime <Cite n={4} />.

</Technical>
<Layman>

You need horizontal scaling in these cases:

- One server cannot handle the traffic.
- The service must continue when one server crashes. This is called high availability: the system stays usable when a part fails.
- The app can be stateless. This means that any server can handle any request <Cite n={2} />. See [Stateless Service](/architecture/stateless-service/).
- You can predict the traffic peaks. For a regular load, you can scale out on a schedule, for example during business hours <Cite n={2} />.
- You need deployments with zero downtime. A rolling update replaces the old instances with new ones, step by step. This lets the update happen with zero downtime <Cite n={4} />.

</Layman>
<Bangla>

নিচের অবস্থাগুলোতে আপনার horizontal scaling দরকার:

- একটি server traffic সামলাতে পারছে না।
- একটি server crash করলেও service চালু থাকতে হবে। একে high availability বলে: কোনো একটি অংশ fail করলেও system ব্যবহারযোগ্য থাকে।
- Application-টি stateless হতে পারে। এর মানে, যেকোনো server যেকোনো request সামলাতে পারে <Cite n={2} />। [Stateless Service](/architecture/stateless-service/) পাতাটি দেখুন।
- Traffic কখন বাড়বে, তা আগে থেকে বোঝা যায়। নিয়মিত load-এর জন্য আপনি একটি schedule ধরে scale out করতে পারেন, যেমন অফিস চলার সময় <Cite n={2} />।
- আপনার zero downtime-এ deployment দরকার। একটি rolling update পুরনো instance-গুলোকে ধাপে ধাপে নতুন instance দিয়ে বদলে দেয়। এতে update-টি zero downtime-এ হওয়া সম্ভব হয় <Cite n={4} />।

</Bangla>
</Voices>

## A real-life example

<Voices>
<Technical>

On admission day, thousands of students try to log in to the LMS (Learning Management System) at the same time. One server gets overloaded. Pages load slowly, and some requests fail.

The team runs three app servers and puts a load balancer in front of them. The load balancer shares the logins between the three servers. Then App Server 2 crashes. The load balancer sends the traffic to App Server 1 and App Server 3, and the students can still log in.

</Technical>
<Layman>

On admission day, thousands of students try to log in to the LMS (Learning Management System) at the same time. One server gets too much load. Pages load slowly, and some requests fail.

The team runs three app servers and puts a load balancer in front of them. The load balancer shares the logins between the three servers.

Then App Server 2 crashes. The load balancer sends the traffic to App Server 1 and App Server 3. The students can still log in.

</Layman>
<Bangla>

ভর্তির দিনে হাজার হাজার শিক্ষার্থী একই সময়ে LMS (Learning Management System)-এ log in করার চেষ্টা করে। একটি server-এর ওপর অতিরিক্ত load পড়ে। Page ধীরে load হয়, আর কিছু request fail করে।

Team তিনটি app server চালায় এবং সেগুলোর সামনে একটি load balancer বসায়। Load balancer log in-গুলো তিনটি server-এর মধ্যে ভাগ করে দেয়।

এরপর App Server 2 crash করে। Load balancer তখন traffic App Server 1 আর App Server 3-এ পাঠায়, আর শিক্ষার্থীরা তখনও log in করতে পারে।

</Bangla>
</Voices>

## Common mistakes

<Voices>
<Technical>

- **"More app servers make the full system scalable."** The database can still be the bottleneck. Three app servers that wait for one slow database are not faster than one.
- **The session is in local memory.** A student logs in on Server 1, and the next request goes to Server 2. Server 2 does not know the student, so the student seems logged out. Microsoft names session state in memory as a cause of "stickiness", and stickiness limits scale-out <Cite n={2} />.
- **Uploaded files are on the local disk.** A file that is on Server 1 is not on Server 2. Use shared [object storage](/architecture/object-storage/).
- **No central logs.** One user's request can touch three servers. If each server keeps its own log file, you cannot follow the request from start to end.
- **The configuration is not the same on all servers.** If one server has an old setting, a bug shows on only one request in three. Such a bug is hard to reproduce.
- **Servers are removed without care.** When the system scales in, the app must handle the removal. Microsoft gives ways to do this: shut down cleanly, and put work items on a queue so that another instance can pick up the unfinished work <Cite n={2} />.

</Technical>
<Layman>

- **"More app servers make the full system scalable."** The database can still be the slowest part. Three app servers that wait for it are not faster than one.
- **The session is in local memory.** A student logs in on Server 1. The next request goes to Server 2, which does not know the student. The student seems logged out. Microsoft names session state in memory as a cause of "stickiness", which limits scale-out <Cite n={2} />.
- **Uploaded files are on the local disk.** A file on Server 1 is not on Server 2. Use shared [object storage](/architecture/object-storage/).
- **No central logs.** One request can touch three servers. With a log file on each server, you cannot follow the full request.
- **The configuration is different on one server.** Then a bug shows on only one request in three. It is hard to reproduce.
- **Servers are removed without care.** At scale-in, the app must handle the removal. Microsoft says: shut down cleanly, and put work items on a queue, so that another instance can do the unfinished work <Cite n={2} />.

</Layman>
<Bangla>

এই সাধারণ ভুলগুলোর দিকে খেয়াল রাখুন:

- **"বেশি app server মানেই পুরো system scalable।"** Database তখনও bottleneck থাকতে পারে। একটি ধীর database-এর জন্য অপেক্ষা করা তিনটি app server একটির চেয়ে দ্রুত নয়।
- **Session local memory-তে থাকে।** একজন শিক্ষার্থী Server 1-এ log in করে, আর পরের request যায় Server 2-এ। Server 2 শিক্ষার্থীকে চেনে না, তাই মনে হয় সে log out হয়ে গেছে। Microsoft memory-তে রাখা session state-কে "stickiness"-এর একটি কারণ বলে, আর stickiness scale-out সীমিত করে <Cite n={2} />।
- **Upload করা file local disk-এ থাকে।** Server 1-এর file Server 2-এ থাকে না। Shared [object storage](/architecture/object-storage/) ব্যবহার করুন।
- **Central log নেই।** একজন user-এর একটি request তিনটি server ছুঁয়ে যেতে পারে। প্রতিটি server যদি নিজের log file রাখে, তাহলে আপনি request-টি শুরু থেকে শেষ পর্যন্ত অনুসরণ করতে পারবেন না।
- **সব server-এ configuration এক নয়।** একটি server-এ পুরনো setting থাকলে bug প্রতি তিনটি request-এর মধ্যে মাত্র একটিতে দেখা যায়। এমন bug reproduce করা কঠিন।
- **Server সাবধানে সরানো হয় না।** System scale in করার সময় app-কে server সরানোর বিষয়টি সামলাতে হবে। Microsoft-এর উপায় বলে: পরিষ্কারভাবে shut down করুন, এবং work item-গুলো একটি queue-তে রাখুন, যাতে অন্য একটি instance অসমাপ্ত কাজটি তুলে নিতে পারে <Cite n={2} />।

</Bangla>
</Voices>

## What a tester can check

<Voices>
<Technical>

<Callout type="tip" title="Tutorial advice">
These test ideas are the tutorial's own advice.

- **Kill one server under load.** Run a load test, then stop one app server. Check the error rate, and check that users stay logged in.
- **Session across servers.** Log in, then send many requests. Use the logs or a response header to see that different servers answered. The user must stay logged in.
- **Same build, same config.** Call a version or health endpoint many times. Each server must report the same build number and the same configuration.
- **Files across servers.** Upload a file, then download it many times. Every server must return the file.
- **Scaling curve.** Run the same load test with 1, 2, and 3 servers. If the throughput does not go up, look for the bottleneck, often the database.
- **Deploy during traffic.** Run a rolling deployment while a load test runs. Count the failed requests.
</Callout>

</Technical>
<Layman>

These test ideas are the tutorial's own advice.

- **Kill one server under load.** Run a load test, then stop one app server. Check the error rate. Make sure that users stay logged in.
- **Session across servers.** Log in, then send many requests. Use the logs or a response header to see that different servers answered. The user must stay logged in.
- **Same build, same config.** Call a version or health endpoint many times. Each server must report the same build number and the same configuration.
- **Files across servers.** Upload a file, then download it many times. Every server must return the file.
- **Scaling curve.** Run the same load test with 1, 2, and 3 servers. If the throughput does not go up, look for the slowest part. Often it is the database.

</Layman>
<Bangla>

নিচের test ধারণাগুলো এই tutorial-এর নিজস্ব পরামর্শ।

- **Load-এর মধ্যে একটি server বন্ধ করুন।** একটি load test চালান, তারপর একটি app server বন্ধ করুন। Error rate দেখুন, এবং user-রা log in অবস্থায় থাকে কি না, তা যাচাই করুন।
- **Server-এর মধ্যে session।** Log in করুন, তারপর অনেক request পাঠান। Log বা একটি response header দেখে নিশ্চিত হন যে আলাদা আলাদা server উত্তর দিয়েছে। User-কে log in অবস্থায় থাকতে হবে।
- **একই build, একই config।** একটি version বা health endpoint অনেকবার call করুন। প্রতিটি server-কে একই build number আর একই configuration জানাতে হবে।
- **Server-এর মধ্যে file।** একটি file upload করুন, তারপর অনেকবার download করুন। প্রতিটি server-কে file-টি ফেরত দিতে হবে।
- **Scaling curve।** 1, 2 এবং 3টি server দিয়ে একই load test চালান। Throughput না বাড়লে bottleneck খুঁজুন, প্রায়ই সেটি database।
- **Traffic-এর মধ্যে deploy।** Load test চলার সময় একটি rolling deployment চালান। Fail হওয়া request-গুলো গুনুন।

</Bangla>

## Key words

| Word | Meaning |
|---|---|
| Instance | One running copy of the application, for example one app server |
| Scale out / scale in | Add instances / remove instances |
| Scale up | Make one machine bigger (vertical scaling) |
| Load balancer | A component that spreads requests across several servers |
| High availability | The system stays usable when one part fails |
| Bottleneck | The slowest part, which limits the whole system |
| Stickiness | All requests from one client always go to the same server |
| Rolling update | A deployment that replaces old instances with new ones step by step |
