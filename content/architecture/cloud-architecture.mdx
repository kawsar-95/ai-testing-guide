# Basic Cloud Architecture

A VPS is like owning one car. You drive it, fill the tank, and fix it when it breaks. Cloud architecture is more like a city transport system. Buses, trains, and taxis are run by others, and you plan how to connect them for your trip. In the cloud, you do not run every part yourself. You choose managed services and design how they work together.

<PageMeta />

## In plain words

**Cloud computing** is the on-demand delivery of IT resources over the internet, with pay-as-you-go pricing <Cite n={1} />. You do not buy and keep your own servers. You rent computing power, storage, and databases from a cloud provider when you need them <Cite n={1} />. You can also make these resources bigger or smaller as your needs change <Cite n={1} />.

**Cloud architecture** is the plan for how your application uses these services. A basic plan connects compute, a database, storage, the network, security, monitoring, backups, and scaling. This page uses AWS names as the example. Other clouds have the same building blocks under other names.

A **managed service** is a service where the provider does part of the work for you. Who does what depends on the service you choose <Cite n={3} />. On a plain virtual server, such as Amazon EC2, you must manage the operating system, its updates, and its security patches <Cite n={3} />. A managed database, such as Amazon RDS, handles backups, software patching, failure detection, and recovery for you <Cite n={4} />. That is the main difference from a VPS: on a VPS, you do almost all of this work yourself.

The common building blocks are:

| Block | What it does | AWS example |
|---|---|---|
| Private network | A logically isolated virtual network that you define <Cite n={5} /> | Amazon VPC |
| Compute that scales | Adds or removes servers when demand goes up or down <Cite n={7} />, and replaces broken ones <Cite n={7} /> | EC2 Auto Scaling |
| Managed database | Runs the database and its backups for you <Cite n={4} /> | Amazon RDS |
| Monitoring | Watches resources and applications in real time <Cite n={8} />, and sends an alarm when a metric crosses a limit <Cite n={8} /> | Amazon CloudWatch |
| Secrets store | Gives credentials to the app at run time, so they are not in the code <Cite n={9} /> | AWS Secrets Manager |

The AWS Well-Architected Framework names six pillars of a good design: operational excellence, security, reliability, performance efficiency, cost optimization, and sustainability <Cite n={2} />.

## When you need it

- The system must scale and stay reliable.
- You need a managed database, object storage, a CDN, and monitoring.
- You need backups, security controls, and automated deployment.
- Traffic is hard to predict.
- The team wants less server maintenance work.

## A real-life example

A practical cloud setup for an LMS (learning management system) can include:

- App servers or containers for the backend, behind a [load balancer](/architecture/load-balancer/).
- A managed MySQL database for students, courses, and payments.
- [Object storage](/architecture/object-storage/) for videos and certificates, with a [CDN](/architecture/cdn/) for static files.
- Redis for cache, sessions, and rate limits.
- Monitoring for logs and alerts.
- DNS, so `lms.example.com` points to the load balancer.

Each part does one job. If the video traffic grows, the CDN and the storage grow. The database does not need to change.

## Common mistakes

- **Keeping all resources in a public network.** A public subnet has a direct route to the internet. A private subnet does not <Cite n={6} />. AWS recommends private subnets to protect resources <Cite n={6} />. Put the database and app servers in private subnets, and expose only the load balancer.
- **Hardcoding secrets in the code repository.** Anyone who can read the repository can then read the database password. A secrets service removes the need for hard-coded credentials <Cite n={9} />.
- **Using managed services without understanding backup and monitoring.** "Managed" does not mean "nothing to do." For example, you still choose how to back up: you can turn on automated backups, or make your own backup snapshots <Cite n={4} />. AWS also says to test backups with a real recovery <Cite n={10} />.
- **Not watching cloud cost.** With pay-as-you-go pricing, a forgotten test server keeps costing money while it runs. AWS Budgets can alert you on actual spend and on forecasted spend <Cite n={11} />.
- **Not separating production and staging.** If a test script runs against production, real students can lose data. AWS suggests separate accounts for production and non-production, so their resources and data stay apart <Cite n={12} />.

## What a tester can check

<Callout type="tip" title="Tutorial advice">
These test ideas are the tutorial's own advice.

- **Network exposure.** Try to connect to the database host and the app servers directly from the internet. Only the load balancer or the CDN must answer.
- **Secrets in code.** Search the repository and the built frontend files for passwords, API keys, and tokens. Check that the app still starts when the secret comes from the secrets store.
- **Restore drill.** Ask the team to restore last night's backup into a test environment. Check that the data is complete and that the app works on it.
- **Environment mix-up.** Check that staging uses its own database, storage bucket, and keys. A file uploaded in staging must never appear in production.
- **Scaling and alarms.** Run a load test. Check that new servers start, that alarms fire, and that the alert reaches a person.
</Callout>

## Key words

| Word | Meaning |
|---|---|
| Cloud computing | Renting IT resources over the internet and paying for what you use |
| VPS | Virtual private server: one rented server that you manage yourself |
| Managed service | A cloud service where the provider runs part of the work, such as patching or backups |
| VPC | Virtual private cloud: your own isolated network in the cloud |
| Public subnet | A part of the network with a direct route to the internet |
| Private subnet | A part of the network with no direct route to the internet |
| Auto scaling | Adding or removing servers automatically when demand changes |
| Secret | A password, key, or token that the app needs and nobody else must see |
| Staging | A copy of the system for tests, separate from production |
