# Kubernetes Operations

This page is about keeping an app healthy once it runs on Kubernetes: probes that restart a container or hold it back from traffic, memory and CPU requests and limits, Jobs that run a task to the end, and autoscaling, with a practice run on the local cluster of [Kubernetes Basics](/devops/kubernetes-basics/).

<PageMeta />

## What it is

<Voices>
<Technical>

**Probes.** Many applications running for long periods of time eventually transition to broken states, and cannot recover except by being restarted; Kubernetes provides liveness probes to detect and remedy such situations <Cite n={1} />. There are three kinds of probe <Cite n={4} />:

| Probe | What it does |
|---|---|
| Liveness | Determines when to restart a container |
| Readiness | Determines when a container is ready to accept traffic |
| Startup | Verifies whether the application within a container is started |

**Requests and limits.** When you specify the resource request for containers in a Pod, the kube-scheduler uses this information to decide which node to place the Pod on <Cite n={3} />. When you specify a resource limit for a container, the kubelet enforces those limits so that the running container is not allowed to use more of that resource than the limit you set <Cite n={3} />.

**Jobs.** A Job creates one or more Pods and will continue to retry execution of the Pods until a specified number of them successfully terminate <Cite n={8} />.

**Autoscaling.** A HorizontalPodAutoscaler automatically updates a workload resource, such as a Deployment or StatefulSet, with the aim of automatically scaling capacity to match demand <Cite n={2} />. Horizontal scaling means that the response to increased load is to deploy more Pods <Cite n={2} />.

</Technical>

## How it works

<Voices>
<Technical>

**How a probe decides.** These fields control a probe <Cite n={4} />:

| Field | Meaning | Default |
|---|---|---|
| `initialDelaySeconds` | Number of seconds after the container has started before startup, liveness or readiness probes are initiated | 0 |
| `periodSeconds` | How often (in seconds) to perform the probe | 10 |
| `timeoutSeconds` | Number of seconds after which the probe times out | 1 |
| `failureThreshold` | After a probe fails this many times in a row, Kubernetes considers that the overall check has failed | 3 |

For a startup or liveness probe, if at least `failureThreshold` probes have failed, Kubernetes treats the container as unhealthy and triggers a restart for that specific container <Cite n={4} />. The kubelet honors the `terminationGracePeriodSeconds` setting for that container <Cite n={4} />. The default is to inherit the Pod-level value (30 seconds if not specified), and when both a Pod-level and a probe-level value are set, the kubelet uses the probe-level value <Cite n={4} />. If a startup probe is configured, Kubernetes does not execute liveness or readiness probes until the startup probe succeeds <Cite n={4} />. Liveness probes do not wait for readiness probes to succeed <Cite n={4} />.

**Readiness decides the traffic.** Readiness probes run on the container during its whole lifecycle <Cite n={4} />. For a failed readiness probe, the kubelet continues running the container that failed checks, and also continues to run more probes; because the check failed, the kubelet sets the Ready condition on the Pod to false <Cite n={4} />. In an EndpointSlice, the serving condition indicates that the endpoint should be used as a target for Service traffic, and for an endpoint backed by a Pod, it maps to the Pod's Ready condition; the ready condition is essentially a shortcut for checking "serving and not terminating" <Cite n={5} />.

**How limits are enforced.** If the node where a Pod is running has enough of a resource available, it's possible (and allowed) for a container to use more resource than its request for that resource specifies <Cite n={3} />. CPU limits are enforced by CPU throttling <Cite n={3} />, and container runtimes don't terminate Pods or containers for excessive CPU usage <Cite n={3} />. If the container tries to allocate more memory than its limit, the Linux kernel out-of-memory subsystem activates and, typically, intervenes by stopping one of the processes in the container that tried to allocate memory; if that process is the container's PID 1, and the container is marked as restartable, Kubernetes restarts the container <Cite n={3} />.

**Quality of Service classes.** Kubernetes classifies the Pods that you run and allocates each Pod into a specific quality of service (QoS) class <Cite n={7} />. The classes are Guaranteed, Burstable, and BestEffort <Cite n={7} />:

| Class | When |
|---|---|
| Guaranteed | Every container has a memory limit and request, and a CPU limit and request, and each limit equals its request |
| Burstable | The Pod is not Guaranteed, and at least one container has a memory or CPU request or limit |
| BestEffort | No container has a memory or CPU limit or request |

The kubelet prefers to evict BestEffort Pods if the node comes under resource pressure <Cite n={7} />.

**Jobs retry, then fail.** `.spec.backoffLimit` sets the number of retries before considering a Job as failed, and it is set by default to 6 <Cite n={8} />. Failed Pods are recreated by the Job controller with an exponential back-off delay (10s, 20s, 40s ...) capped at ten minutes <Cite n={8} />. A Job has two terminal states: on success, the Job condition `Complete`; on failure, the Job condition `Failed` <Cite n={8} />. Once a Job reaches `activeDeadlineSeconds`, all of its running Pods are terminated, and the Job status becomes `Failed` with the reason `DeadlineExceeded` <Cite n={8} />.

**The autoscaler.** The HorizontalPodAutoscaler controller runs intermittently, and the default interval is 15 seconds <Cite n={2} />. It computes the desired number of replicas as `ceil(currentReplicas × currentMetricValue / desiredMetricValue)`: for example, if the current metric value is 200m and the desired value is 100m, the number of replicas will be doubled <Cite n={2} />. If some of the Pod's containers do not have the relevant resource request set, CPU utilization for the Pod will not be defined, and the autoscaler will not take any action for that metric <Cite n={2} />. For scaling up there is no stabilization window, and by default 4 pods or 100% of the currently running replicas may at most be added every 15 seconds <Cite n={2} />. Scale-downs wait for a stabilization window, which defaults to 5 minutes <Cite n={2} />.

**Where the numbers come from.** metrics-server is a cluster addon component that collects and aggregates resource metrics pulled from each kubelet, and the API server serves the Metrics API for use by HPA, VPA, and the `kubectl top` command <Cite n={10} />.

In step 5 of the tutorial's run below, the autoscaler grew a Deployment from 1 to 10 Pods. This diagram is the tutorial's own picture of that loop; metrics-server collects the metrics from each kubelet <Cite n={10} />, and once during each period, the controller manager queries the resource utilization against the metrics specified in each HorizontalPodAutoscaler definition <Cite n={2} />:

```text
kubelet ──▶ metrics-server ──▶ Metrics API
                                   │ read by the HPA controller every 15 s
                                   ▼
            HorizontalPodAutoscaler php-apache (target: 50% of the CPU request)
                                   │ desired = ceil(current × used / target)
                                   ▼
            Deployment php-apache: 1 → 4 → 5 → 10 replicas
```

**Probe কীভাবে সিদ্ধান্ত নেয়।** এই field-গুলো একটা probe নিয়ন্ত্রণ করে <Cite n={4} />:

| Field | অর্থ | Default |
|---|---|---|
| `initialDelaySeconds` | container চালু হওয়ার কত সেকেন্ড পরে startup, liveness বা readiness probe শুরু হবে | 0 |
| `periodSeconds` | কত ঘন ঘন (সেকেন্ডে) probe চালানো হবে | 10 |
| `timeoutSeconds` | কত সেকেন্ড পরে probe time out হবে | 1 |
| `failureThreshold` | পরপর এতবার probe ব্যর্থ হলে Kubernetes পুরো check-কে ব্যর্থ ধরে | 3 |

startup বা liveness probe-এর ক্ষেত্রে অন্তত `failureThreshold`-সংখ্যক probe ব্যর্থ হলে Kubernetes container-টাকে unhealthy ধরে আর ঠিক সেই container restart করায় <Cite n={4} />। kubelet সেই container-এর `terminationGracePeriodSeconds` setting মেনে চলে <Cite n={4} />। default হলো Pod-level মান inherit করা (না দিলে 30 সেকেন্ড), আর Pod-level ও probe-level দুটো মানই দেওয়া থাকলে kubelet probe-level মানটা ব্যবহার করে <Cite n={4} />। startup probe থাকলে সেটা সফল না হওয়া পর্যন্ত Kubernetes কোনো liveness বা readiness probe চালায় না <Cite n={4} />। liveness probe readiness probe সফল হওয়ার জন্য অপেক্ষা করে না <Cite n={4} />।

**Readiness traffic ঠিক করে।** readiness probe container-এর পুরো জীবনকাল জুড়ে চলে <Cite n={4} />। readiness probe ব্যর্থ হলে kubelet ব্যর্থ container-টা চালিয়ে যায় এবং আরও probe চালিয়ে যায়; check ব্যর্থ হয়েছে বলে kubelet Pod-এর Ready condition false করে <Cite n={4} />। একটা EndpointSlice-এ serving condition বলে endpoint-টাকে Service traffic-এর লক্ষ্য হিসেবে ব্যবহার করা উচিত কি না, আর Pod-এর endpoint-এর ক্ষেত্রে এটা Pod-এর Ready condition অনুসরণ করে; ready condition মূলত "serving এবং terminating নয়" যাচাইয়ের একটা সংক্ষিপ্ত রূপ <Cite n={5} />।

**Limit কীভাবে প্রয়োগ হয়।** Pod যে node-এ চলছে সেখানে যথেষ্ট resource থাকলে একটা container তার request-এর চেয়ে বেশি resource ব্যবহার করতে পারে, আর এটা অনুমোদিত <Cite n={3} />। CPU limit প্রয়োগ হয় CPU throttling দিয়ে <Cite n={3} />, আর বেশি CPU ব্যবহারের জন্য container runtime কোনো Pod বা container বন্ধ করে না <Cite n={3} />। container তার limit-এর বেশি memory নিতে চাইলে Linux kernel-এর out-of-memory subsystem সক্রিয় হয়, আর সাধারণত container-এর যে process memory চেয়েছিল, তাদের একটাকে থামিয়ে দেয়; সেই process container-এর PID 1 হলে আর container restart-যোগ্য হলে Kubernetes container-টা restart করে <Cite n={3} />।

**Quality of Service class।** Kubernetes আপনার চালানো Pod-গুলোকে classify করে আর প্রতিটা Pod-কে একটা নির্দিষ্ট quality of service (QoS) class-এ রাখে <Cite n={7} />। class-গুলো হলো Guaranteed, Burstable আর BestEffort <Cite n={7} />:

| Class | কখন |
|---|---|
| Guaranteed | প্রতিটা container-এর memory limit ও request আর CPU limit ও request আছে, আর প্রতিটা limit তার request-এর সমান |
| Burstable | Pod Guaranteed নয়, আর অন্তত একটা container-এর memory বা CPU request বা limit আছে |
| BestEffort | কোনো container-এর memory বা CPU limit বা request নেই |

node-এ resource-এর চাপ পড়লে kubelet BestEffort Pod evict করতে পছন্দ করে <Cite n={7} />।

**Job আবার চেষ্টা করে, তারপর ব্যর্থ হয়।** `.spec.backoffLimit` ঠিক করে একটা Job-কে ব্যর্থ ধরার আগে কতবার আবার চেষ্টা হবে, আর এর default 6 <Cite n={8} />। Job controller ব্যর্থ Pod-গুলো exponential back-off delay (10s, 20s, 40s ...) দিয়ে আবার তৈরি করে, সর্বোচ্চ দশ মিনিট <Cite n={8} />। একটা Job-এর দুটো শেষ অবস্থা আছে: সফল হলে Job condition `Complete`; ব্যর্থ হলে Job condition `Failed` <Cite n={8} />। একটা Job `activeDeadlineSeconds`-এ পৌঁছালে তার সব চলমান Pod বন্ধ হয়, আর Job-এর status `DeadlineExceeded` reason-সহ `Failed` হয় <Cite n={8} />।

**Autoscaler।** HorizontalPodAutoscaler controller বিরতি দিয়ে চলে, আর default interval 15 সেকেন্ড <Cite n={2} />। এটা কাঙ্ক্ষিত replica-সংখ্যা হিসাব করে `ceil(currentReplicas × currentMetricValue / desiredMetricValue)` দিয়ে: যেমন বর্তমান metric মান 200m আর কাঙ্ক্ষিত মান 100m হলে replica-সংখ্যা দ্বিগুণ হবে <Cite n={2} />। Pod-এর কিছু container-এ সংশ্লিষ্ট resource request না থাকলে Pod-এর CPU utilization নির্ধারিত হয় না, আর autoscaler সেই metric-এর জন্য কিছুই করে না <Cite n={2} />। scale up-এর কোনো stabilization window নেই, আর default-এ প্রতি 15 সেকেন্ডে সর্বোচ্চ 4টা pod বা চলমান replica-র 100% যোগ হতে পারে <Cite n={2} />। scale down একটা stabilization window-এর জন্য অপেক্ষা করে, যার default 5 মিনিট <Cite n={2} />।

**সংখ্যাগুলো কোথা থেকে আসে।** metrics-server একটা cluster addon component, যা প্রতিটা kubelet থেকে resource metric সংগ্রহ ও একত্র করে, আর API server HPA, VPA আর `kubectl top` command-এর জন্য Metrics API দেয় <Cite n={10} />।

নিচে টিউটোরিয়ালের run-এর ধাপ ৫-এ autoscaler একটা Deployment-কে 1 থেকে 10টা Pod-এ বাড়িয়েছে। এই diagram সেই loop-এর টিউটোরিয়ালের নিজের ছবি; metrics-server প্রতিটা kubelet থেকে metric সংগ্রহ করে <Cite n={10} />, আর প্রতিটা period-এ একবার controller manager প্রতিটা HorizontalPodAutoscaler definition-এ উল্লেখ করা metric-এর বিপরীতে resource utilization জিজ্ঞেস করে <Cite n={2} />:

```text
kubelet ──▶ metrics-server ──▶ Metrics API
                                   │ read by the HPA controller every 15 s
                                   ▼
            HorizontalPodAutoscaler php-apache (target: 50% of the CPU request)
                                   │ desired = ceil(current × used / target)
                                   ▼
            Deployment php-apache: 1 → 4 → 5 → 10 replicas
```

**১. Liveness probe-কে একটা container restart করতে দেখুন।** docs-এর উদাহরণ `exec-liveness.yaml` একটা file `/tmp/healthy` তৈরি করে আর 30 সেকেন্ড পরে মুছে দেয়; এর probe প্রথম probe-এর আগে 5 সেকেন্ড অপেক্ষা করে, তারপর প্রতি 5 সেকেন্ডে `cat /tmp/healthy` চালায় <Cite n={1} />। run file-টাতে namespace যোগ করেছে:

```yaml

    test: liveness
  name: liveness-exec
  namespace: ops-lab

    image: registry.k8s.io/busybox:1.27.2
    args:
    - /bin/sh
    - -c
    - touch /tmp/healthy; sleep 30; rm -f /tmp/healthy; sleep 600

      exec:
        command:
        - cat
        - /tmp/healthy
```

## How a tester uses it

<Voices>
<Technical>

**Wait for ready, not for running.** For a failed readiness probe, the kubelet continues running the container and sets the Ready condition on the Pod to false <Cite n={4} />. In step 2, both Pods were `Running` and `0/1` ready. `kubectl wait --for=condition=Ready` waits for the Ready condition <Cite n={14} />.

**Count the restarts.** If at least `failureThreshold` liveness probes have failed, Kubernetes restarts the container <Cite n={4} />, and a container that goes over its memory limit can be stopped by the out-of-memory subsystem and restarted <Cite n={3} />. A Pod can look healthy between the restarts: in step 3, the Pod was `Running` with one restart, and its last state was `OOMKilled`.

**Read the result of a test Job from its condition.** A Job ends with the condition `Complete` or `Failed` <Cite n={8} />, and `kubectl wait` waits for a specific condition on one or many resources <Cite n={14} />, so a pipeline can wait for one of the two. `.spec.backoffLimit` is the number of retries before considering a Job as failed, 6 by default <Cite n={8} />: in step 4, the failing tests ran three times with `backoffLimit: 2`.

**Load test with the autoscaler in mind.** If a container has no request for the resource, CPU utilization will not be defined, and the autoscaler will not take any action for that metric <Cite n={2} />. The controller runs every 15 seconds by default, and scale-downs wait for a stabilization window of 5 minutes by default <Cite n={2} />. In step 5, the autoscaler grew the Deployment from 1 to 10 replicas within about 90 seconds of load.

**Know where the numbers come from.** metrics-server serves the numbers of the autoscaler and of `kubectl top` <Cite n={10} />, and pod metrics may be unavailable for a few minutes since pod creation <Cite n={12} />.

</Technical>
<Layman>

**Wait for ready, not for running.** When a readiness probe fails, the kubelet keeps the container running, and sets the Ready condition of the Pod to false <Cite n={4} />. In step 2, both Pods were `Running` and `0/1` ready. `kubectl wait --for=condition=Ready` waits for the Ready condition <Cite n={14} />.

**Count the restarts.** Once `failureThreshold` liveness probes have failed, Kubernetes restarts the container <Cite n={4} />, and a container that uses more memory than its limit can be stopped by the out-of-memory system and restarted <Cite n={3} />. A Pod can look healthy between restarts: in step 3, the Pod was `Running` with one restart, and its last state was `OOMKilled`.

**Read the result of a test Job from its condition.** A Job ends with the condition `Complete` or `Failed` <Cite n={8} />, and `kubectl wait` waits until one or more resources reach a condition <Cite n={14} />, so a pipeline can wait for one of the two. `.spec.backoffLimit` is how many retries happen before the Job counts as failed, 6 by default <Cite n={8} />: in step 4, the failing tests ran three times with `backoffLimit: 2`.

**Load test with the autoscaler in mind.** If a container sets no request for the resource, the Pod has no CPU utilization, and the autoscaler does nothing for that metric <Cite n={2} />. The controller runs every 15 seconds by default, and scaling down waits for a stabilization window, 5 minutes by default <Cite n={2} />. In step 5, the autoscaler grew the Deployment from 1 to 10 replicas within about 90 seconds of load.

**Know where the numbers come from.** metrics-server gives the numbers to the autoscaler and to `kubectl top` <Cite n={10} />, and pod metrics may be missing for a few minutes after a Pod is made <Cite n={12} />.

</Layman>
<Bangla>

**Running নয়, ready-র জন্য অপেক্ষা করুন।** readiness probe ব্যর্থ হলে kubelet container চালিয়ে যায়, আর Pod-এর Ready condition false করে <Cite n={4} />। ধাপ ২-এ দুটো Pod-ই `Running` আর `0/1` ready ছিল। `kubectl wait --for=condition=Ready` Ready condition-এর জন্য অপেক্ষা করে <Cite n={14} />।

**Restart গুনুন।** অন্তত `failureThreshold`-সংখ্যক liveness probe ব্যর্থ হলে Kubernetes container restart করে <Cite n={4} />, আর memory limit পার হওয়া container-কে out-of-memory subsystem থামিয়ে দিতে পারে, তারপর সেটা restart হয় <Cite n={3} />। দুই restart-এর মাঝে একটা Pod সুস্থ দেখাতে পারে: ধাপ ৩-এ Pod একটা restart-সহ `Running` ছিল, আর তার শেষ state ছিল `OOMKilled`।

**Test Job-এর ফল তার condition থেকে পড়ুন।** একটা Job `Complete` বা `Failed` condition নিয়ে শেষ হয় <Cite n={8} />, আর `kubectl wait` এক বা একাধিক resource-এর একটা নির্দিষ্ট condition-এর জন্য অপেক্ষা করে <Cite n={14} />, তাই একটা pipeline এ দুটোর একটার জন্য অপেক্ষা করতে পারে। `.spec.backoffLimit` হলো Job-কে ব্যর্থ ধরার আগে কতবার আবার চেষ্টা হবে, default 6 <Cite n={8} />: ধাপ ৪-এ `backoffLimit: 2` দিয়ে ব্যর্থ test-গুলো তিনবার চলেছে।

**Autoscaler মাথায় রেখে load test করুন।** container-এ resource-এর request না থাকলে CPU utilization নির্ধারিত হয় না, আর autoscaler সেই metric-এর জন্য কিছুই করে না <Cite n={2} />। controller default-এ প্রতি 15 সেকেন্ডে চলে, আর scale down default-এ 5 মিনিটের stabilization window-এর জন্য অপেক্ষা করে <Cite n={2} />। ধাপ ৫-এ load-এর প্রায় 90 সেকেন্ডের মধ্যে autoscaler Deployment-কে 1 থেকে 10টা replica-তে বাড়িয়েছে।

**সংখ্যাগুলো কোথা থেকে আসে, জানুন।** metrics-server autoscaler আর `kubectl top`-এর সংখ্যা দেয় <Cite n={10} />, আর pod তৈরির পরে কয়েক মিনিট pod metric পাওয়া না-ও যেতে পারে <Cite n={12} />।

</Bangla>
</Voices>

## Common mistakes

<Voices>
<Technical>

- **A liveness probe that does more than it should.** Liveness probes must be configured carefully to ensure that they truly indicate unrecoverable application failure, for example a deadlock; incorrect implementation of liveness probes can lead to cascading failures <Cite n={4} />.
- **No resource request on a Pod that should scale.** CPU utilization for the Pod will not be defined, and the autoscaler will not take any action for that metric <Cite n={2} />.
- **Reading `Running` as ready.** A Pod whose readiness probe fails keeps running, with its Ready condition false <Cite n={4} />.
- **Keeping the default retries for a test Job.** The `.spec.backoffLimit` is set by default to 6 <Cite n={8} />, and failed Pods are recreated with an exponential back-off delay (10s, 20s, 40s ...) capped at ten minutes <Cite n={8} />. In step 4, `backoffLimit: 2` was followed by three Pods, and the Job became `Failed` after 33 seconds.
- **Checking the autoscaler right after the deploy.** Pod metrics may be unavailable for a few minutes since pod creation <Cite n={12} />.
- **Using `--kubelet-insecure-tls` outside a test cluster.** It does not verify the CA of serving certificates presented by Kubelets, and it is for testing purposes only <Cite n={11} />.

</Technical>
<Layman>

- **A liveness probe that does more than it should.** Liveness probes must be set up carefully, so that they really show a failure that the app cannot recover from, such as a deadlock; a wrong liveness probe can lead to failures that spread <Cite n={4} />.
- **No resource request on a Pod that should scale.** The Pod then has no CPU utilization, and the autoscaler does nothing for that metric <Cite n={2} />.
- **Reading `Running` as ready.** A Pod whose readiness probe fails keeps running, with its Ready condition false <Cite n={4} />.
- **Keeping the default retries for a test Job.** `.spec.backoffLimit` is 6 by default <Cite n={8} />, and the Job controller recreates failed Pods with a growing delay (10s, 20s, 40s ...) that is capped at ten minutes <Cite n={8} />. In step 4, `backoffLimit: 2` was followed by three Pods, and the Job became `Failed` after 33 seconds.
- **Checking the autoscaler right after the deploy.** Pod metrics may be missing for a few minutes after a Pod is made <Cite n={12} />.
- **Using `--kubelet-insecure-tls` outside a test cluster.** It skips checking the CA of the kubelets' serving certificates, and it is for testing only <Cite n={11} />.

</Layman>
<Bangla>

- **যে liveness probe যতটা উচিত তার বেশি করে।** liveness probe সাবধানে configure করতে হবে, যাতে সেটা সত্যিই এমন failure বোঝায় যা থেকে application ফিরতে পারে না, যেমন একটা deadlock; ভুলভাবে বানানো liveness probe cascading failure ঘটাতে পারে <Cite n={4} />।
- **Scale হওয়ার কথা এমন Pod-এ resource request নেই।** তখন Pod-এর CPU utilization নির্ধারিত হয় না, আর autoscaler সেই metric-এর জন্য কিছুই করে না <Cite n={2} />।
- **`Running`-কে ready ভাবা।** readiness probe ব্যর্থ হওয়া একটা Pod চলতে থাকে, তার Ready condition false থাকে <Cite n={4} />।
- **Test Job-এ default retry রেখে দেওয়া।** `.spec.backoffLimit`-এর default 6 <Cite n={8} />, আর ব্যর্থ Pod-কে Job controller exponential back-off delay দিয়ে (10s, 20s, 40s ...) আবার তৈরি করে, যা ten minutes-এ সীমিত <Cite n={8} />। ধাপ ৪-এ `backoffLimit: 2`-এর পরে তিনটা Pod হয়েছে, আর Job 33 সেকেন্ড পরে `Failed` হয়েছে।
- **Deploy-এর ঠিক পরেই autoscaler যাচাই করা।** pod তৈরির পরে কয়েক মিনিট pod metric পাওয়া না-ও যেতে পারে <Cite n={12} />।
- **Test cluster-এর বাইরে `--kubelet-insecure-tls` ব্যবহার করা।** এটা kubelet-এর দেখানো serving certificate-এর CA যাচাই করে না, আর এটা শুধু testing-এর জন্য <Cite n={11} />।

</Bangla>
</Voices>

## What a tester can check

<Voices>
<Technical>

<Callout type="tip" title="Tutorial advice">
This list is the tutorial's own advice for a tester whose app runs on Kubernetes.

- Before a test sends traffic, wait for the Pods to be ready, not only running.
- Check what each liveness probe tests, and that it does not fail when a dependency is slow.
- After a test run, check the restart counts and the last state of the containers; a restart with `OOMKilled` is a finding.
- Check that every container that should scale has a CPU request.
- Run a test suite as a Job with a small `backoffLimit`, read the result from its condition, and report how often it was retried.
- In a load test, wait for the metrics before the first check of the autoscaler, and watch the scale-down too.

This list is the tutorial's own advice for a tester whose app runs on Kubernetes.

## Key words

| Term | Meaning |
|---|---|
| Liveness probe | Determines when to restart a container |
| Readiness probe | Determines when a container is ready to accept traffic |
| Startup probe | Verifies whether the application in a container has started; holds back the other probes until then |
| `failureThreshold` | How many failures in a row make the check fail; 3 by default |
| Resource request | What the scheduler uses to place a Pod on a node |
| Resource limit | What the kubelet does not let a running container go over |
| `OOMKilled` | The last state of the container in step 3 after it went over its memory limit; exit code 137 in the run |
| QoS class | `Guaranteed`, `Burstable`, or `BestEffort`, from the requests and limits of a Pod |
| Job | Runs Pods until a set number of them end with success, or until it fails |
| `backoffLimit` | The number of retries before a Job counts as failed; 6 by default |
| HorizontalPodAutoscaler | Scales a workload resource to match demand; more load is answered with more Pods |
| metrics-server | The cluster add-on that collects resource metrics from the kubelets for the Metrics API |
| `kubectl top` | Shows metrics for the nodes; in the run it also showed the CPU use of Pods |
