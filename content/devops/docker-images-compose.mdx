# Docker Images and Compose

This page explains how a test environment is built and started: how a Dockerfile builds an image, why the order of its instructions matters, and how Docker Compose starts an application and the services that it needs from one file, with a practice run of Docker's own Compose Quickstart. It builds on [Docker Basics](/devops/docker-basics/); [Docker in Practice](/devops/docker-in-practice/) goes deeper into volumes and networks.

<PageMeta />

## What it is

<Voices>
<Technical>

**Dockerfile.** A Dockerfile is a text document that contains all the commands a user could call on the command line to assemble an image <Cite n={1} />. Docker runs instructions in a Dockerfile in order <Cite n={1} />. A Dockerfile must begin with a `FROM` instruction <Cite n={1} />.

**`docker build`.** `docker build` is an alias of `docker buildx build`, which starts a build using BuildKit <Cite n={2} />. Its `-t` (`--tag`) option sets the image identifier, in the format `[registry/]repository[:tag]` <Cite n={2} />.

**Docker Compose.** Docker Compose is a tool for defining and running multi-container applications <Cite n={9} />. It manages services, networks, and volumes in a single YAML configuration file <Cite n={9} />. With a single command, you create and start all the services from your configuration file <Cite n={9} />. The default path for a Compose file is `compose.yaml` (preferred) or `compose.yml` in the working directory <Cite n={10} />. Compose works in all environments: production, staging, development, testing, as well as CI workflows <Cite n={9} />.

**Bake.** Bake is a feature of Docker Buildx that lets you define your build configuration using a declarative file, as opposed to specifying a complex CLI expression <Cite n={18} />. It also lets you run multiple builds concurrently with a single invocation <Cite n={18} />. A Bake file can be written in HCL or JSON format, and Bake can also build directly from a Docker Compose file <Cite n={18} />.

| Tool | Reads | Command |
|---|---|---|
| Docker build | A `Dockerfile` <Cite n={1} /> | `docker build` <Cite n={2} /> |
| Docker Compose | A `compose.yaml` <Cite n={10} /> | `docker compose up` <Cite n={11} /> |
| Bake | A Bake file in HCL or JSON, or a Compose file <Cite n={18} /> | `docker buildx bake` <Cite n={18} /> |

</Technical>

## How it works

<Voices>
<Technical>

**The instructions of a Dockerfile.** These are the instructions of the Dockerfile in the practice run below:

| Instruction | What it does |
|---|---|
| `FROM` | Specifies the base image from which you are building <Cite n={1} /> |
| `WORKDIR` | Sets the working directory for any `RUN`, `CMD`, `ENTRYPOINT`, `COPY` and `ADD` instructions that follow it <Cite n={1} /> |
| `ENV` | Sets the environment variable `<key>` to the value `<value>` <Cite n={1} /> |
| `RUN` | Executes any commands to create a new layer on top of the current image <Cite n={1} /> |
| `COPY` | Copies new files or directories from `<src>` and adds them to the filesystem of the image at the path `<dest>` <Cite n={1} /> |
| `EXPOSE` | Doesn't actually publish the port. It is documentation about which ports are intended to be published <Cite n={1} /> |
| `CMD` | Provides defaults for an executing container. If you list more than one `CMD`, only the last one takes effect <Cite n={1} /> |

**The build context.** The build context is the set of files that your build can access <Cite n={3} />. Docker sends everything in your project directory to the daemon when it builds an image <Cite n={11} />. A `.dockerignore` file is a newline-separated list of patterns similar to the file globs of Unix shells <Cite n={3} />. It keeps unneeded files out of the build context <Cite n={11} />.

**The build cache.** If a layer changes, all other layers that come after it are also affected <Cite n={4} />. So make expensive steps appear near the beginning of the Dockerfile, and steps that change often near the end <Cite n={5} />. Docker's own example: copy the package management files first, then install the dependencies, and only then copy the project source code, which is subject to frequent change <Cite n={5} />.

**Multi-stage builds.** With multi-stage builds, you use multiple `FROM` statements in your Dockerfile <Cite n={6} />. You can selectively copy artifacts from one stage to another, leaving behind everything you don't want in the final image <Cite n={6} />.

**How Compose starts services.** By default, Compose sets up a single network for your app <Cite n={14} />. Each container for a service joins that network, and it is reachable by other containers on it and discoverable by its service name <Cite n={14} />. Compose always starts and stops containers in dependency order <Cite n={13} />. But on startup, Compose does not wait until a container is "ready", only until it's running <Cite n={13} />. To wait for a dependency, use the `condition` attribute: with `service_healthy`, the dependency must be "healthy", as defined with `healthcheck`, before the dependent service starts <Cite n={13} />.

This diagram is the tutorial's own picture of the practice run below:

```text
compose.yaml ── docker compose up ──> network: compose-demo_default
                                         │
                 redis (image: redis:alpine)   healthcheck: redis-cli ping
                    ▲  becomes healthy
                    │  depends_on: condition: service_healthy
                 web (build: .)   port 8000 on the host ──> 5000 in the container
                 redis keeps its data in the named volume redis-data
```

| `COPY` | `<src>` থেকে নতুন file বা directory copy করে image-এর filesystem-এ `<dest>` path-এ যোগ করে <Cite n={1} /> |

**Build cache।** একটা layer বদলালে তার পরের সব layer-ও প্রভাবিত হয় <Cite n={4} />। তাই ব্যয়বহুল ধাপ Dockerfile-এর শুরুর দিকে রাখুন, আর ঘনঘন বদলায় এমন ধাপ শেষের দিকে <Cite n={5} />। Docker-এর নিজের উদাহরণ: আগে package management file copy করুন, তারপর dependency install করুন, আর একদম শেষে project-এর source code copy করুন, যেটা ঘনঘন বদলায় <Cite n={5} />।

**Multi-stage build।** multi-stage build-এ Dockerfile-এ একাধিক `FROM` statement থাকে <Cite n={6} />। এক stage থেকে আরেক stage-এ বেছে বেছে artifact copy করা যায়, আর final image-এ যা চান না তা পেছনে রেখে আসা যায় <Cite n={6} />।

## Try it

<Voices>
<Technical>

This practice run is Docker's Compose Quickstart: a small Flask web app that counts visits in Redis <Cite n={11} />. It needs Docker Compose <Cite n={11} />. The tutorial ran it on 2026-11-16 with Docker Engine 29.9.3 and Docker Compose v5.5.1 on Linux. It leaves out the Quickstart's Compose Watch step and its step on multiple Compose files.

**1. Make the project.** Create a folder and the app <Cite n={11} />:

```bash
mkdir compose-demo
cd compose-demo
```

`app.py` reads its Redis connection details from environment variables, with defaults <Cite n={11} />:

```python
import os
import redis
from flask import Flask

app = Flask(__name__)
cache = redis.Redis(
    host=os.getenv("REDIS_HOST", "redis"),
    port=int(os.getenv("REDIS_PORT", "6379")),
)

@app.route("/")
def hello():
    count = cache.incr("hits")
    return f"Hello from Docker! I have been seen {count} time(s).\n"
```

`requirements.txt` lists the two Python packages <Cite n={11} />:

```text
flask
redis
```

**2. Write the Dockerfile.** This is the Quickstart's `Dockerfile`, without its comments <Cite n={11} />. Name the file `Dockerfile` with no extension: some editors add `.txt` automatically, which causes the build to fail <Cite n={11} />.

```dockerfile
# syntax=docker/dockerfile:1
FROM python:3.12-alpine
WORKDIR /code
ENV FLASK_APP=app.py
ENV FLASK_RUN_HOST=0.0.0.0
RUN apk add --no-cache gcc musl-dev linux-headers
COPY requirements.txt .
RUN pip install -r requirements.txt
COPY . .
EXPOSE 5000
CMD ["flask", "run", "--debug"]
```

Note the order: `requirements.txt` is copied and installed before the rest of the code is copied.

**3. Keep settings and secrets apart.** A `.env` file holds configuration values, and Compose reads it automatically for interpolation in your `compose.yaml` <Cite n={11} />. The `.dockerignore` keeps the `.env` file, which may contain secrets, and cached Python bytecode out of the build context <Cite n={11} />:

```text
# .env
APP_PORT=8000
REDIS_HOST=redis
REDIS_PORT=6379
```

```text
# .dockerignore
.env
*.pyc
__pycache__
redis-data
```

**4. Write `compose.yaml`.** This is the Quickstart's file with its health check and its named volume, without the `develop.watch` block <Cite n={11} />:

```yaml
services:
  web:
    build: .
    ports:
      - "${APP_PORT}:5000"
    environment:
      - REDIS_HOST=${REDIS_HOST}
      - REDIS_PORT=${REDIS_PORT}
    depends_on:
      redis:
        condition: service_healthy
  redis:
    image: redis:alpine
    volumes:
      - redis-data:/data
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 5s
      timeout: 3s
      retries: 5
      start_period: 10s

volumes:
  redis-data:
```

The `web` service uses an image built from the Dockerfile in the current directory, and maps port 8000 on the host to port 5000 in the container <Cite n={11} />. **test করার জন্য একটা নতুন image build করুন।** `--pull` flag Docker-কে base image-এর নতুন version খুঁজে download করতে বাধ্য করে <Cite n={8} />। `--no-cache` flag build cache বন্ধ করে, ফলে Docker সব layer শুরু থেকে আবার build করে <Cite n={8} />। Docker-এর উদাহরণে দুটোই আছে <Cite n={8} />:

```bash
docker build --pull --no-cache -t my-image:my-tag .
```

**Bake-এ build আর test।** Bake-এর documentation-এ test আর lint check চালানো, আর build artifact export করার মতো workflow-এর তালিকা আছে <Cite n={18} />।

</Bangla>
</Voices>

## Common mistakes

<Voices>
<Technical>

- **Trusting `depends_on` alone.** With the short syntax, Compose does not wait for dependency services to be "healthy" before starting a dependent service <Cite n={12} />. If an application starts before its database, it may not find a database able to handle its SQL statements <Cite n={13} />. Add a `healthcheck` and `condition: service_healthy` <Cite n={13} />.
- **Unquoted ports.** `HOST:CONTAINER` should always be specified as a quoted string, to avoid conflicts with the YAML base-60 float <Cite n={12} />.
- **Ports open to everyone.** If you do not specify a host IP (such as `127.0.0.1`), Docker binds to all interfaces (`0.0.0.0`), bypassing host firewall rules <Cite n={12} />. A short-syntax example with a host IP is `"127.0.0.1:8001:8001"` <Cite n={12} />.
- **Secrets in build arguments or `ENV`.** Build arguments and environment variables are inappropriate for passing secrets to your build, because they persist in the final image <Cite n={7} />.
- **Copying all the source before installing dependencies.** Then updating any file causes a reinstall of all dependencies every time you build the image <Cite n={5} />.
- **Expecting `docker compose down` to clear the data.** Named volumes stay unless you add `-v` <Cite n={16} />. Anonymous volumes are not removed by default either <Cite n={16} />.
- **Trusting a tag in `FROM`.** Image tags are mutable: a publisher can update a tag to point to a new image <Cite n={8} />. Pinning to a digest guarantees the same image version <Cite n={8} />.

</Technical>
<Layman>

## What a tester can check

<Voices>
<Technical>

<Callout type="tip" title="Tutorial advice">
This list is the tutorial's own advice for a tester on a team that uses Dockerfiles and Compose.

- Ask for a `healthcheck` on each service that the tests depend on, and for `condition: service_healthy` in `depends_on`.
- In CI, start the stack with `docker compose up --wait` before the tests run.
- Give each parallel test environment its own project name.
- Ask that base images in `FROM` are pinned, and record the digest of the image under test.
- Check that `.dockerignore` keeps `.env` files and other secrets out of the build context.
- Use `docker compose down -v` only when you mean to delete the test data.
- Attach the output of `docker compose config` to a bug report about the environment.
</Callout>

</Technical>

## Key words

| Term | Meaning |
|---|---|
| Dockerfile | A text document with all the commands a user could call on the command line to assemble an image |
| `docker build` | An alias of `docker buildx build`, which starts a build using BuildKit |
| Build context | The set of files that your build can access |
| `.dockerignore` | A newline-separated list of patterns that keeps files out of the build context |
| Build cache | If a layer changes, all other layers that come after it are also affected, so the order of the instructions matters |
| Multi-stage build | A Dockerfile with multiple `FROM` statements that copies only the artifacts it needs into the final image |
| Docker Compose | A tool for defining and running multi-container applications |
| `compose.yaml` | The default Compose file in the working directory |
| Service | An entry under `services` in `compose.yaml`, such as `web` or `redis`; its containers are discoverable by the service name |
| `healthcheck` | How Compose tests whether a service is healthy, such as `redis-cli ping` |
| `condition: service_healthy` | Starts a dependent service only after the dependency is healthy |
| Project name | The name that lets the same `compose.yaml` run twice on the same infrastructure |
| Named volume | Storage that keeps data between `compose down` and `compose up` |
| Bake | A feature of Docker Buildx that defines builds in a declarative file |
