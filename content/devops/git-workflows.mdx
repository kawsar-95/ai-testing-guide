# Git Workflows

This page is about the Git commands that a tester meets after the basics. It starts with how teams keep branches at levels of stability. Then it explains rebase, cherry-pick, stash, worktrees, and `git bisect`, with a practice run that finds a known bad commit twice. It builds on [Git Basics](/devops/git-basics/).

<PageMeta />

## What it is

<Voices>
<Technical>

Git has a command for each of these jobs. `git rebase` reapplies commits on top of another base tip <Cite n={1} />. `git stash` stashes the changes in a dirty working directory away <Cite n={2} />. `git worktree` manages multiple working trees attached to the same repository, so you can check out more than one branch at a time <Cite n={3} />. `git bisect` uses binary search to find the commit that introduced a bug <Cite n={4} />. `git cherry-pick` applies the changes introduced by some existing commits <Cite n={5} />.

| Command | A typical use |
|---|---|
| `git rebase` | A cleaner history: the log of a rebased branch looks linear <Cite n={6} /> |
| `git stash` | You want to switch branches, but you don't want to commit half-done work <Cite n={7} /> |
| `git worktree` | More than one branch checked out at a time <Cite n={3} /> |
| `git bisect` | Dozens or hundreds of commits since the code last worked, and you don't know what broke it <Cite n={8} /> |
| `git cherry-pick` | Backporting a fix to a maintenance branch for an older release <Cite n={5} /> |
| `git blame` | Which revision and author last modified each line of a file <Cite n={11} /> |

</Technical>

| Command | A typical use |

## How it works

<Voices>
<Technical>

**Branches at levels of stability.** Git makes it easy to keep several **long-running branches** that are always open, for different stages of the development cycle <Cite n={9} />. Many Git developers keep only entirely stable code in their `master` branch, possibly only code that has been or will be released <Cite n={9} />. A parallel branch named `develop` or `next` is where they work or test stability; when it gets to a stable state, it can be merged into `master` <Cite n={9} />. A **topic branch** is a short-lived branch for a single feature or related work <Cite n={9} />. Topic branches are pulled into `develop` when they are ready, to make sure that they pass all the tests and don't introduce bugs <Cite n={9} />.

```text
master    o--------------------o------   only stable code
           \                  /
develop     o---o---o---o---o---o-----   tested here, merged up when stable
                 \     /
topic             o---o                 one feature, merged when ready
```

**Merge or rebase.** There are two main ways to integrate changes from one branch into another: the merge and the rebase <Cite n={6} />. A merge performs a three-way merge between the two latest branch snapshots and their most recent common ancestor, creating a new snapshot and commit <Cite n={6} />. A rebase takes all the changes that were committed on one branch and replays them on a different branch <Cite n={6} />. There is no difference in the end product, but rebasing makes for a cleaner history <Cite n={6} />. When you rebase, you abandon existing commits and create new ones that are similar but different <Cite n={6} />:

```text
before:   A---B---C          main
               \
                D---E        feature

merge:    A---B---C-------M  main      M is a new merge commit
               \         /
                D-------E

rebase:   A---B---C---D'---E'  feature   D' and E' are new commits
```

**Cherry-pick.** Given one or more existing commits, `git cherry-pick` applies the change each one introduces, recording a new commit for each <Cite n={5} />. It requires your working tree to be clean <Cite n={5} />. With `-x`, it appends a line that says "(cherry picked from commit …)" to the original commit message <Cite n={5} />. This is done only for cherry-picks without conflicts <Cite n={5} />.

**Stash.** Stashing takes the dirty state of your working directory, your modified tracked files and staged changes, and saves it on a stack of unfinished changes <Cite n={7} />. You can reapply it at any time, even on a different branch <Cite n={7} />. `git stash list` shows the stashes, `git stash apply` reapplies one, and `git stash pop` applies a stash and then immediately drops it from the stack <Cite n={7} />.

**Worktree.** A repository can support multiple working trees, so that you can check out more than one branch at a time <Cite n={3} />. Each one that `git worktree add` creates is a **linked worktree**; the one that `git init` or `git clone` prepared is the **main worktree** <Cite n={3} />.

**Bisect.** You give `git bisect` a "bad" commit that is known to contain the bug, and a "good" commit that is known to be before the bug <Cite n={4} />. Git picks a commit between the two and asks you whether it is good or bad <Cite n={4} />. It keeps narrowing the range until it finds the exact commit that introduced the change <Cite n={4} />:

```text
good                                         bad
 1 ---- 2 ---- 3 ---- 4 ---- 5 ---- 6 ---- 7 ---- 8
                      ^ test 4: good   -> the bug came after 4
                                    ^ test 6: bad   -> 5 or 6
                             ^ test 5: good   -> 6 is the first bad commit
```

With `git bisect run <cmd>`, a command does the marking for you <Cite n={4} />. Its exit code decides <Cite n={4} />:

| Exit code | Meaning for bisect |
|---|---|
| 0 | Good (old) <Cite n={4} /> |
| 1 to 127, except 125 | Bad (new) <Cite n={4} /> |
| 125 | This commit cannot be tested <Cite n={4} /> |
| Any other code | Bisect stops <Cite n={4} /> |

</Technical>
<Layman>

**Branches at levels of stability.** Git makes it easy to keep several **long-running branches** that are always open, for different stages of the work <Cite n={9} />. Many Git developers keep only fully stable code in their `master` branch, maybe only code that has been or will be released <Cite n={9} />. A second branch, called `develop` or `next`, is where they work or test that things are stable. When it is stable, it can be merged into `master` <Cite n={9} />. A **topic branch** is a short-lived branch for one feature or one piece of related work <Cite n={9} />. When a topic branch is ready, it goes into `develop`, to make sure that it passes all the tests and brings no bugs <Cite n={9} />.

```text
master    o--------------------o------   only stable code
           \                  /
develop     o---o---o---o---o---o-----   tested here, merged up when stable
                 \     /
topic             o---o                 one feature, merged when ready
```

**Merge or rebase.** Git has two main ways to bring changes from one branch into another: merge and rebase <Cite n={6} />. A merge does a three-way merge: it combines the two newest snapshots, using the commit where the branches split, into a new snapshot and a new commit <Cite n={6} />. A rebase takes all the changes made on one branch and plays them again on another branch <Cite n={6} />. The end result is the same, but the history is tidier <Cite n={6} />. When you rebase, you drop the old commits and make new ones that are similar but different <Cite n={6} />:

```text
before:   A---B---C          main
               \
                D---E        feature

merge:    A---B---C-------M  main      M is a new merge commit
               \         /
                D-------E

rebase:   A---B---C---D'---E'  feature   D' and E' are new commits
```

**Cherry-pick.** `git cherry-pick` takes the change of each commit that you give it, and saves it as a new commit <Cite n={5} />. Your working tree must be clean first <Cite n={5} />. With `-x`, it adds the line "(cherry picked from commit …)" to the commit message <Cite n={5} />. It does this only when the cherry-pick has no conflicts <Cite n={5} />.

**Stash.** A stash takes your unfinished changes, both changed tracked files and staged changes, and puts them on a stack <Cite n={7} />. You can put them back at any time, even on another branch <Cite n={7} />. `git stash list` shows the stashes. `git stash apply` puts one back. `git stash pop` puts one back and then removes it from the stack <Cite n={7} />.

**Worktree.** One repository can have several working trees, so you can check out more than one branch at a time <Cite n={3} />. Each one that `git worktree add` makes is a **linked worktree**. The one that `git init` or `git clone` made is the **main worktree** <Cite n={3} />.

**Bisect.** You tell `git bisect` one "bad" commit that has the bug, and one "good" commit from before the bug <Cite n={4} />. Git picks a commit in between and asks you if it is good or bad <Cite n={4} />. It keeps cutting the range until it finds the exact commit that brought the change <Cite n={4} />:

```text
good                                         bad
 1 ---- 2 ---- 3 ---- 4 ---- 5 ---- 6 ---- 7 ---- 8
                      ^ test 4: good   -> the bug came after 4
                                    ^ test 6: bad   -> 5 or 6
                             ^ test 5: good   -> 6 is the first bad commit
```

With `git bisect run <cmd>`, a command marks each commit for you <Cite n={4} />. Its exit code decides <Cite n={4} />:

| Exit code | Meaning for bisect |
|---|---|
| 0 | Good (old) <Cite n={4} /> |
| 1 to 127, except 125 | Bad (new) <Cite n={4} /> |
| 125 | This commit cannot be tested <Cite n={4} /> |
| Any other code | Bisect stops <Cite n={4} /> |

</Layman>
<Bangla>

**stability-র স্তর অনুযায়ী branch।** Git-এ সবসময় খোলা থাকা কয়েকটা **long-running branch** রাখা সহজ, development cycle-এর বিভিন্ন ধাপের জন্য <Cite n={9} />। অনেক Git developer তাদের `master` branch-এ শুধু পুরোপুরি stable code রাখেন, হয়তো শুধু সেই code যা release হয়েছে বা হবে <Cite n={9} />। `develop` বা `next` নামের একটা সমান্তরাল branch-এ তারা কাজ করেন বা stability test করেন; সেটা stable অবস্থায় পৌঁছালে `master`-এ merge করা যায় <Cite n={9} />। **topic branch** হলো একটা নির্দিষ্ট feature বা সম্পর্কিত কাজের জন্য স্বল্পস্থায়ী branch <Cite n={9} />। topic branch প্রস্তুত হলে `develop`-এ আনা হয়, যাতে নিশ্চিত হওয়া যায় এটা সব test পাস করে আর কোনো bug আনে না <Cite n={9} />।

```text
master    o--------------------o------   only stable code
           \                  /
develop     o---o---o---o---o---o-----   tested here, merged up when stable
                 \     /
topic             o---o                 one feature, merged when ready
```

**Merge নাকি rebase।** এক branch-এর change আরেক branch-এ আনার দুটো প্রধান উপায় আছে: merge আর rebase <Cite n={6} />। merge দুই branch-এর সর্বশেষ দুটো snapshot আর তাদের সবচেয়ে কাছের common ancestor নিয়ে three-way merge করে, একটা নতুন snapshot আর commit বানায় <Cite n={6} />। rebase এক branch-এ commit হওয়া সব change নিয়ে আরেকটা branch-এর ওপর আবার চালায় <Cite n={6} />। শেষ ফলাফলে কোনো পার্থক্য নেই, কিন্তু rebase history-কে পরিষ্কার রাখে <Cite n={6} />। rebase করলে আপনি পুরোনো commit বাদ দিয়ে একই রকম কিন্তু আলাদা নতুন commit বানান <Cite n={6} />:

```text
before:   A---B---C          main
               \
                D---E        feature

merge:    A---B---C-------M  main      M is a new merge commit
               \         /
                D-------E

rebase:   A---B---C---D'---E'  feature   D' and E' are new commits
```

**Cherry-pick।** এক বা একাধিক existing commit দিলে `git cherry-pick` প্রতিটার আনা change প্রয়োগ করে, প্রতিটার জন্য একটা নতুন commit রেকর্ড করে <Cite n={5} />। এর জন্য আপনার working tree পরিষ্কার থাকতে হয় <Cite n={5} />। `-x` দিলে এটা মূল commit message-এর শেষে "(cherry picked from commit …)" লাইনটা যোগ করে <Cite n={5} />। এটা শুধু conflict ছাড়া cherry-pick-এর বেলায় হয় <Cite n={5} />।

**Stash।** stash আপনার working directory-র অগোছালো অবস্থা, মানে বদলানো tracked ফাইল আর staged change, নিয়ে অসমাপ্ত change-এর একটা stack-এ রাখে <Cite n={7} />। যেকোনো সময় আবার প্রয়োগ করা যায়, এমনকি অন্য branch-এও <Cite n={7} />। `git stash list` stash-গুলো দেখায়, `git stash apply` একটা আবার প্রয়োগ করে, আর `git stash pop` প্রয়োগ করে সাথে সাথে stack থেকে মুছে দেয় <Cite n={7} />।

**Worktree।** একটা repository একাধিক working tree রাখতে পারে, যাতে একসাথে একাধিক branch check out করা যায় <Cite n={3} />। `git worktree add` যেটা বানায় সেটা **linked worktree**; `git init` বা `git clone` যেটা বানিয়েছিল সেটা **main worktree** <Cite n={3} />।

**Bisect।** আপনি `git bisect`-কে একটা "bad" commit দেন, যাতে bug আছে বলে জানা, আর একটা "good" commit দেন, যেটা bug-এর আগের বলে জানা <Cite n={4} />। Git দুটোর মাঝের একটা commit বেছে নিয়ে জিজ্ঞেস করে সেটা good নাকি bad <Cite n={4} />। যতক্ষণ না ঠিক কোন commit change-টা এনেছে তা পায়, ততক্ষণ এটা পরিসর ছোট করতে থাকে <Cite n={4} />:

```text
good                                         bad
 1 ---- 2 ---- 3 ---- 4 ---- 5 ---- 6 ---- 7 ---- 8
                      ^ test 4: good   -> the bug came after 4
                                    ^ test 6: bad   -> 5 or 6
                             ^ test 5: good   -> 6 is the first bad commit
```

`git bisect run <cmd>` দিলে একটা command আপনার হয়ে প্রতিটা commit চিহ্নিত করে <Cite n={4} />। এর exit code সিদ্ধান্ত নেয় <Cite n={4} />:

| Exit code | bisect-এর কাছে মানে |
|---|---|
| 0 | Good (old) <Cite n={4} /> |
| 1 থেকে 127, 125 বাদে | Bad (new) <Cite n={4} /> |
| 125 | এই commit test করা যায় না <Cite n={4} /> |
| অন্য যেকোনো code | bisect থেমে যায় <Cite n={4} /> |

</Bangla>

## Try it

<Voices>
<Technical>

This practice run needs only Git and a bash shell. You make a repository with a known bug, find the bug's commit twice, and then use a stash and a worktree.

**1. Make a practice repository.** This script is the tutorial's own. It makes eight commits. Commit 6 changes the total from 100 to 110: that is the "bug". It uses only basic commands: `git init` makes a repository with a `.git` subdirectory <Cite n={13} />, `git add` stages files, `git commit -m` records a commit with an inline message <Cite n={14} />, and `git log --oneline` prints each commit on a single line <Cite n={12} />.

```bash
mkdir bisect-practice && cd bisect-practice
git init
for i in 1 2 3 4 5 6 7 8; do
  if [ "$i" -lt 6 ]; then echo "total=100" > price.txt; else echo "total=110" > price.txt; fi
  echo "change $i" >> notes.txt
  git add price.txt notes.txt
  git commit -m "Change $i"
done
git log --oneline
```

**2. Find the bad commit by hand.** Start a session, mark the current commit as bad, and mark the oldest one as good <Cite n={4} />. Git then checks out a commit in between <Cite n={4} />. Read `price.txt`: if it says `total=100`, run `git bisect good`, otherwise `git bisect bad`. Repeat until Git prints the first bad commit <Cite n={4} />. Then `git bisect reset` returns you to the commit that you had before <Cite n={4} />.

```bash
git bisect start
git bisect bad
git bisect good HEAD~7
cat price.txt
git bisect good    # or: git bisect bad
git bisect reset
```

**3. ## How a tester uses it

<Voices>
<Technical>

**Find the commit that broke a test.** When you don't know what is breaking, and there have been dozens or hundreds of commits since the code last worked, use `git bisect` <Cite n={8} />. If you have a script that exits 0 when the project is good and non-0 when it is bad, you can fully automate it <Cite n={8} />. You can also run whatever you have that runs automated tests for you <Cite n={8} />.

**Find the change to one line.** If a method in your code is buggy, `git blame` can show which commit introduced that line <Cite n={8} />. It annotates each line of a file with information from the revision that last modified it <Cite n={11} />.

**Trace a fix to a release branch.** A cherry-picked fix is a new commit on the release branch <Cite n={5} />. When a fix moves between two publicly visible branches, such as a backport to a maintenance branch, the `-x` line can be useful <Cite n={5} />. It names the commit that the change came from <Cite n={5} />.

**Test two branches side by side.** With linked worktrees, you can check out more than one branch at a time <Cite n={3} />. To work on an existing branch in a new worktree, use `git worktree add <path> <branch>` <Cite n={3} />.

**Pause your own work.** When your work is in a messy state and you want to switch branches for a bit to work on something else, stash your half-done changes instead of committing them <Cite n={7} />. You can reapply them later, even on a different branch <Cite n={7} />.

**Know which commits you tested.** After a rebase, the branch is made of new commits <Cite n={6} />.

</Technical>

## Common mistakes

<Voices>
<Technical>

- **Rebasing shared commits.** Do not rebase commits that exist outside your repository and that people may have based work on <Cite n={6} />. Rebase local changes before you push, but never rebase anything that you have pushed somewhere <Cite n={6} />.
- **Forgetting `git bisect reset`.** After a bisect session, it cleans up the bisection state and returns you to the original `HEAD` <Cite n={4} />.
- **A bisect script with the wrong exit code.** Any exit code other than 0 to 127 aborts the bisect <Cite n={4} />. A program that ends with `exit(-1)` leaves the code 255 <Cite n={4} />. For a commit that cannot be tested, exit with 125 <Cite n={4} />.
- **Skipping the wrong commit.** If you skip a commit next to the one that you are looking for, Git cannot tell exactly which of those commits was the first bad one <Cite n={4} />.
- **Losing new files in a stash.** By default, `git stash` stashes only modified and staged tracked files <Cite n={7} />. Add `-u` (`--include-untracked`) to include untracked files <Cite n={7} />.
- **Deleting a worktree folder by hand.** Use `git worktree remove` <Cite n={3} />. If the folder is already gone, `git worktree prune` removes the worktree information that is left <Cite n={3} />.
- **Cherry-picking into a dirty tree.** `git cherry-pick` requires a clean working tree <Cite n={5} />.

</Technical>

- Before you bisect with a test, run it a few times on the bad commit and on the good one. A flaky test marks commits wrongly.
- For `git bisect run`, use a command that runs only the failing test.
- Put the hash and the title of the first bad commit in the bug report.
- Ask if fixes on release branches are cherry-picked with `-x`, so that you can follow them.
- After a branch is rebased, run its tests again, because its commits are new.
- Ask which branch has only stable code, and which branch is for testing.
- Keep half-done test work in a stash or a worktree, not in a half-done commit on a shared branch.
</Callout>

এই তালিকা টিউটোরিয়ালের নিজের পরামর্শ, এই command-গুলো ব্যবহার করা একজন tester-এর জন্য।

- একটা test দিয়ে bisect করার আগে সেটা bad আর good commit-এ কয়েকবার চালান। flaky test commit-কে ভুল চিহ্নিত করে।
- `git bisect run`-এ এমন command দিন, যেটা শুধু ফেল করা test-টা চালায়।
- first bad commit-এর hash আর title bug report-এ লিখুন।
- জিজ্ঞেস করুন release branch-এর fix `-x` দিয়ে cherry-pick করা হয় কি না, যাতে সেগুলো খুঁজে পাওয়া যায়।
- একটা branch rebase হলে তার test আবার চালান, কারণ তার commit-গুলো নতুন।
- জিজ্ঞেস করুন কোন branch-এ শুধু stable code থাকে, আর কোনটা test-এর জন্য।
- অর্ধেক করা test-এর কাজ stash বা worktree-তে রাখুন, shared branch-এ অর্ধেক করা commit হিসেবে নয়।

## Key words

| Term | Meaning |
|---|---|
| Long-running branch | A branch that stays open, such as `master` for stable code or `develop` for testing stability |
| Topic branch | A short-lived branch for a single feature or related work |
| Rebase | Replaying the changes of one branch on another branch, as new commits |
| Cherry-pick | Applying the change of an existing commit as a new commit |
| `-x` | The cherry-pick option that adds "(cherry picked from commit …)" to the message of a cherry-pick without conflicts |
| Stash | A stack of unfinished changes that you can reapply later |
| Linked worktree | An extra working tree made by `git worktree add` |
| Main worktree | The working tree that `git init` or `git clone` prepared |
| Bisect | A binary search for the commit that introduced a change |
| Good (old) / bad (new) | A good commit is known to be before the bug, and a bad one contains it; for `git bisect run`, exit code 0 means good |
| `git bisect run` | Bisect with a command whose exit code marks each commit |
| Exit code 125 | Tells bisect that a commit cannot be tested |
| `git blame` | Shows the revision and author that last modified each line |
