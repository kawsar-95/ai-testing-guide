# CNCF Projects: Build and Deliver

This page covers the CNCF and three of its projects for building and delivering software: Helm, Backstage, and Cloud Native Buildpacks. The practice run lints, renders, and tests a Helm chart, validates Backstage catalog files, and builds an image with a buildpack. It needs no Kubernetes cluster and no cloud account, and one step uses Docker. It comes after [Monitoring and Observability](/devops/monitoring-observability/) and before [CNCF Projects: Runtime, Scheduling, and Data](/devops/cncf-runtime-data/).

<Technical>

**The CNCF and its stages.** The Cloud Native Computing Foundation (CNCF) hosts critical components of the global technology infrastructure <Cite n={1} />. CNCF is part of the nonprofit Linux Foundation <Cite n={1} />. The CNCF has a Technical Oversight Committee (TOC) <Cite n={3} />. The TOC defines 4 stages of the project lifecycle <Cite n={3} />. Sandbox projects are experimental or innovative projects early in their development <Cite n={3} />. Incubation projects are gaining adoption, with a focus on improving stability and maturity <Cite n={3} />. Graduated projects are highly mature, robust projects whose adopters have demonstrated their production-readiness by deploying them to production environments <Cite n={3} />. Archived projects are inactive or low activity projects that the TOC no longer supports, or does not recommend for use, for reasons that depend on the project <Cite n={3} />. The CNCF says that graduated and incubating projects are considered stable and are used successfully in production environments <Cite n={2} />.

**The three projects.** Helm is the package manager for Kubernetes <Cite n={7} />. The CNCF page says that Helm was accepted on June 1, 2018 at the Incubating maturity level, and moved to the Graduated maturity level on May 1, 2020 <Cite n={4} />. Backstage is an open source framework for building developer portals <Cite n={26} />. It was accepted on September 8, 2020, and moved to the Incubating maturity level on March 15, 2022 <Cite n={5} />. Cloud Native Buildpacks transform your application source code into images that can run on any cloud <Cite n={6} />. Buildpacks was accepted on October 3, 2018, moved to the Incubating maturity level on November 18, 2020, and then moved to the Graduated maturity level on July 17, 2026 <Cite n={6} />. The tutorial read these three CNCF pages on 2026-11-19. A maturity level can change, so read the pages again when it matters.

**Helm: chart, release, repository, values.** A chart is a Helm package that contains information sufficient for installing a set of Kubernetes resources into a Kubernetes cluster <Cite n={7} />. Charts contain a `Chart.yaml` file as well as templates, default values (`values.yaml`), and dependencies <Cite n={7} />. When a chart is installed, the Helm library creates a release to track that installation <Cite n={7} />. A single chart may be installed many times into the same cluster, and create many different releases <Cite n={7} />. Helm charts may be stored on dedicated HTTP servers called chart repositories <Cite n={7} />. Values provide a way to override template defaults with your own information <Cite n={7} />.

**Backstage: the software catalog.** The Backstage Software Catalog is a centralized system that keeps track of ownership and metadata for all the software in your ecosystem <Cite n={27} />. The catalog is built around metadata YAML files that are stored together with the code, and then harvested and visualized in Backstage <Cite n={27} />. Out of the box, Backstage also includes Software Templates and TechDocs <Cite n={26} />.

**Cloud Native Buildpacks.** A buildpack is software that transforms application source code into runnable artifacts by analyzing the code and determining the best way to build it <Cite n={34} />. A builder is an OCI image that contains an ordered combination of buildpacks, a build-time base image, a lifecycle binary, and a reference to a runtime base image <Cite n={35} />. A platform orchestrates builds by invoking the lifecycle binary together with buildpacks and app source code to produce a runnable OCI image <Cite n={36} />. The Pack CLI is one such platform <Cite n={36} />. The tutorial uses `pack` for that reason.

## How it works

<Voices>
<Technical>

**The files of a chart.** A chart is a collection of files that describe a related set of Kubernetes resources <Cite n={8} />. Charts are created as files laid out in a particular directory tree <Cite n={8} />. The `helm create` command creates a chart directory along with the common files and directories used in a chart <Cite n={9} />. Its example tree has `Chart.yaml`, with information about your chart, `values.yaml`, with the default values for your templates, `charts/`, with the charts that this chart depends on, and `templates/`, with the template files <Cite n={9} />. Every chart must have a `Chart.yaml` file <Cite n={7} />. Charts are versioned according to the SemVer 2 spec, and a version number is required on every chart <Cite n={7} />. A chart archive is a tarred and gzipped (and optionally signed) chart <Cite n={7} />.

**Values and templates.** Values provide a way to override template defaults with your own information <Cite n={7} />. A chart developer may expose configuration that can be overridden at installation time <Cite n={7} />. The order of specificity is this: `values.yaml` is the default, a parent chart's `values.yaml` can override it, a user-supplied values file can override that, and `--set` parameters can override that <Cite n={19} />. You can give the `--values` or `-f` flag more than once, and the last, right-most file gets the priority <Cite n={12} />. To force a string value, use `--set-string` <Cite n={12} />. **Lint and the values schema.** To lint a chart is to validate that it follows the conventions and requirements of the Helm chart standard <Cite n={7} />. `helm lint` takes a path to a chart and runs a series of tests to verify that the chart is well-formed <Cite n={10} />. **Releases, revisions, and rollback.** After a first `helm install`, a release has release number 1 <Cite n={7} />. Each time a release is upgraded or rolled back, the release number is incremented <Cite n={7} />. Since release history is stored, a release can be rolled back to a previous release number with the `helm rollback` command <Cite n={7} />. **Tests and hooks.** A test in a Helm chart lives under the `templates/` directory <Cite n={17} />. The tests to run are defined in the chart that was installed <Cite n={16} />. Hooks work like regular templates, but they have special annotations that cause Helm to use them differently <Cite n={18} />. **Packages, signing, and sharing.** `helm package` packages a chart into a versioned chart archive file <Cite n={13} />. The docs list `experimental` as an experiment or early, non-production component <Cite n={28} />. They list `production` as an established, owned, maintained component <Cite n={28} />.

**Kinds and references.** Components are individual pieces of software <Cite n={29} />. APIs are the boundaries between different components <Cite n={29} />. **The life of an entity.** The catalog is a hub where entities are ingested from various authoritative sources and held in a database, subject to automated processing, and then presented through an API <Cite n={30} />. Engineers write their documentation in Markdown files that live together with their code <Cite n={33} />. With little configuration, they get a doc site in Backstage <Cite n={33} />.

**The lifecycle.** The lifecycle orchestrates buildpacks, then assembles the resulting artifacts into an OCI image <Cite n={37} />. An image build requires 5 lifecycle phases <Cite n={37} />. They are the detect, analyze, restore, build, and export binaries <Cite n={45} />. The analyzer, restorer, and exporter need access to an image repository, either an OCI registry or a Docker-compliant daemon <Cite n={37} />. For security hardening, these phases run in separate containers to avoid exposing sensitive data to buildpacks <Cite n={37} />. The detector and builder invoke buildpacks <Cite n={37} />. For security hardening, both the lifecycle and buildpacks run as non-root users when doing this work <Cite n={37} />. When a builder is trusted, all 5 lifecycle phases can be run in the same container, with the creator binary <Cite n={37} />.

**Detect.** The detector finds an ordered group of buildpacks to use during the build phase <Cite n={38} />. It reads `order.toml`, and looks for the first group that passes the detection process <Cite n={38} />. If all of the groups fail, the detection process fails <Cite n={38} />. To pass, the detect scripts of all required buildpacks must pass successfully, which means that the exit code is zero <Cite n={38} />. The detector should also be able to create a build plan with all of the requirements of the group's buildpacks <Cite n={38} />. The first group that passes both steps is written to `group.toml`, and its build plan is written to `plan.toml` <Cite n={38} />.

**The two executables of a buildpack.** A component buildpack is a buildpack that contains `/bin/detect` and `/bin/build` executables <Cite n={41} />. The `pack buildpack new` command generates the basic scaffolding of a buildpack repository <Cite n={42} />. It creates a `buildpack.toml` and two executable bash scripts, `bin/detect` and `bin/build` <Cite n={42} />. The spec gives the exit status of `/bin/detect` as pass (0), fail (100), or error (1-99, 101+) <Cite n={41} />. The spec gives the exit status of `/bin/build` as success (0) or failure (1+) <Cite n={41} />. The `CNB_LAYERS_DIR` variable holds the absolute path of the buildpack layers directory <Cite n={41} />. A build can write a `launch.toml` file with app metadata into that directory <Cite n={41} />. The positional arguments to the detect and build executables were deprecated in Buildpack API 0.8, and the lifecycle provides their values as environment variables <Cite n={41} />.

**Layers.** A layer is a set of filesystem changes packaged according to the OCI Image Specification <Cite n={41} />. A layer directory is a directory created by a component buildpack that contains build and/or runtime dependencies <Cite n={41} />. The spec names three layer types <Cite n={41} />. A launch layer is added as a layer in the exported OCI image <Cite n={41} />. A cache layer is saved to the cache, and its contents may be restored on the next build <Cite n={41} />. A build layer has child directories whose paths are added to the environment for subsequent buildpacks in the same build <Cite n={41} />. In the example output of the Buildpacks docs, the layers of the buildpack `example/node-engine` are in `/layers/example_node-engine` <Cite n={47} />.

**Builders, platforms, and trust.** `pack build` uses Cloud Native Buildpacks to create a runnable app image from source code <Cite n={43} />. It requires an image name <Cite n={43} />. It defaults to the current directory, and you can use `--path` to specify another source code directory <Cite n={43} />. It requires a builder, which can be given with `--builder` or can be set with the `set-default-builder` command <Cite n={43} />. The `--buildpack` flag accepts a path to a buildpack directory, among other forms <Cite n={43} />. `pack inspect` shows information about a built app image <Cite n={44} />. From pack version 0.11.0 onward, `pack` can identify builders that should be considered trusted <Cite n={45} />. If `pack` does not trust a builder, it continues to execute five separate lifecycle binaries <Cite n={45} />. The docs say that this choice strikes a balance between security and performance <Cite n={45} />.

**The privilege behind the trust.** If `pack` does not trust a builder, it runs the more privileged phases using a published lifecycle image, if one is available <Cite n={45} />. The analyze, restore, and export phases need higher levels of privilege or access to sensitive data that the detect and build phases do not need <Cite n={45} />. **Rebase, reproducibility, and the SBOM.** The rebaser places application layers atop a new version of the runtime base image <Cite n={39} />. The Cloud Native Buildpacks project aims to create “Reproducible Builds” of container images <Cite n={40} />. Given the same inputs, two builds should produce the same outputs <Cite n={40} />. A Software Bill-of-Materials (SBOM) lists all the software components included in an image <Cite n={46} />. Buildpacks can populate SBOM information about the dependencies they have provided <Cite n={46} />. The `pack sbom download` command downloads the app layer containing the SBOM files to `./layers/sbom/...` on your local filesystem <Cite n={46} />.

**chart-এর file।** chart হলো একগুচ্ছ file, যা একটা সম্পর্কিত Kubernetes resource-এর সেট বর্ণনা করে <Cite n={8} />। chart বানানো হয় একটা নির্দিষ্ট directory tree-তে সাজানো file দিয়ে <Cite n={8} />। `helm create` command একটা chart directory বানায়, সঙ্গে chart-এ ব্যবহৃত সাধারণ file আর directory-ও <Cite n={9} />। তার উদাহরণ tree-তে আছে `Chart.yaml` (chart-এর তথ্য), `values.yaml` (template-এর default value), `charts/` (এই chart যেসব chart-এর ওপর নির্ভর করে) আর `templates/` (template file) <Cite n={9} />। প্রতিটা chart-এ একটা `Chart.yaml` file থাকতেই হয় <Cite n={7} />। chart-এর version দেওয়া হয় SemVer 2 spec অনুযায়ী, আর প্রতিটা chart-এ একটা version number লাগে <Cite n={7} />। chart archive হলো একটা tar আর gzip করা (আর ইচ্ছে হলে signed) chart <Cite n={7} />।

**value আর template।** value দেয় template-এর default বদলানোর একটা উপায়, আপনার নিজের তথ্য দিয়ে <Cite n={7} />। chart-এর developer এমন configuration সামনে রাখতে পারেন, যা install-এর সময় বদলানো যায় <Cite n={7} />। কোনটা কার ওপরে, তার ক্রম এই: `values.yaml` হলো default, parent chart-এর `values.yaml` তাকে বদলাতে পারে, user-এর দেওয়া values file সেটাকে বদলাতে পারে, আর `--set` parameter সেটাকেও বদলাতে পারে <Cite n={19} />। `--values` বা `-f` flag একাধিকবার দেওয়া যায়, আর শেষের, ডানদিকের file-টা অগ্রাধিকার পায় <Cite n={12} />। একটা মানকে string করতে চাইলে `--set-string` ব্যবহার করুন <Cite n={12} />। chart best practice বলে, variable-এর নাম ছোট হাতের অক্ষর দিয়ে শুরু হওয়া উচিত, আর শব্দগুলো camelcase দিয়ে আলাদা করা উচিত <Cite n={20} />। তারা আরও বলে, বেশির ভাগ ক্ষেত্রে nested-এর চেয়ে flat বেছে নেওয়া উচিত <Cite n={20} />।

**cluster ছাড়া render করা।** `helm template` chart-এর template স্থানীয়ভাবে render করে আর output দেখায় <Cite n={11} />। যে মান সাধারণত cluster-এর ভেতর থেকে খুঁজে বা এনে নেওয়া হতো, তা স্থানীয়ভাবে নকল করা হয় <Cite n={11} />। chart ঠিক আছে কি না, তা server-এর দিক থেকে পরীক্ষা করার কিছুই করা হয় না, যেমন কোনো API সমর্থিত কি না <Cite n={11} />। `--dry-run=client` flag কাজটার অনুকরণ করে শুধু client-এর দিকে, আর cluster-এর সঙ্গে যোগাযোগ এড়ায় <Cite n={11} />। `--dry-run=server` flag কাজটার অনুকরণ আর যাচাই করে server-এ, আর cluster-এর সঙ্গে যোগাযোগ লাগে <Cite n={11} />। `helm install` command একটা chart archive install করে <Cite n={12} />। তার argument হতে হবে একটা chart reference, একটা packaged chart-এর path, একটা খোলা chart directory-র path, বা একটা URL <Cite n={12} />।

**lint আর values schema।** একটা chart lint করা মানে যাচাই করা যে সে Helm chart standard-এর রীতি আর শর্ত মেনে চলছে <Cite n={7} />। `helm lint` একটা chart-এর path নেয় আর কয়েকটা test চালিয়ে দেখে chart ঠিকঠাক গড়া কি না <Cite n={10} />। যা chart-কে install-এ ব্যর্থ করবে, সেসবের জন্য সে `[ERROR]` বার্তা দেয় <Cite n={10} />। যা রীতি বা সুপারিশ ভাঙে, সেসবের জন্য সে `[WARNING]` বার্তা দেয় <Cite n={10} />। chart-এর maintainer `values.schema.json` file-এ একটা schema ঠিক করে value-গুলোর কাঠামো বেঁধে দিতে পারেন <Cite n={8} />। schema লেখা হয় JSON Schema হিসেবে <Cite n={8} />। `helm install`, `helm upgrade`, `helm lint` বা `helm template` চালালে এই যাচাই হয় <Cite n={8} />।

**release, revision আর rollback।** প্রথম `helm install`-এর পর একটা release-এর release number হয় 1 <Cite n={7} />। একটা release upgrade বা rollback হলে প্রতিবার release number একটা করে বাড়ে <Cite n={7} />। release-এর ইতিহাস রাখা হয় বলে একটা release-কে আগের কোনো release number-এ rollback করা যায়, `helm rollback` command দিয়ে <Cite n={7} />। rollback করা release একটা নতুন release number পায় <Cite n={7} />। `helm rollback` নেয় একটা release-এর নাম আর একটা revision number <Cite n={14} />। revision বাদ দিলে বা 0 দিলে সে আগের release-এ ফিরে যায় <Cite n={14} />। revision number দেখতে চালান `helm history RELEASE` <Cite n={14} />। `helm history` ডিফল্টভাবে সর্বোচ্চ ২৫৬টা revision ফেরত দেয় <Cite n={15} />। ডিফল্টভাবে release-এর তথ্য রাখা হয় release-এর namespace-এর Secret-এ <Cite n={21} />। `HELM_DRIVER` environment variable অন্য একটা backend বেছে নিতে পারে <Cite n={21} />।

**test আর hook।** Helm chart-এর একটা test থাকে `templates/` directory-র ভেতরে <Cite n={17} />। সেটা একটা workload definition, সাধারণত Pod বা Job, যা একটা container আর তার চালানোর একটা command ঠিক করে <Cite n={17} />। test সফল ধরা হতে হলে container-এর সফলভাবে (exit 0 দিয়ে) শেষ হওয়া উচিত <Cite n={17} />। definition-এ test hook annotation `helm.sh/hook: test` থাকতেই হয় <Cite n={17} />। `helm test` command একটা release-এর test চালায় <Cite n={16} />। তার argument একটা deployed release-এর নাম <Cite n={16} />। চালানোর test-গুলো ঠিক করা থাকে install করা chart-এ <Cite n={16} />। hook সাধারণ template-এর মতোই কাজ করে, কিন্তু তাদের বিশেষ annotation থাকে, যার ফলে Helm তাদের আলাদাভাবে ব্যবহার করে <Cite n={18} />। install lifecycle-এর জন্য Helm দুটো hook ঠিক করে: `pre-install` আর `post-install` <Cite n={18} />।

**package, signing আর ভাগ করা।** `helm package` একটা chart-কে একটা version-যুক্ত chart archive file-এ package করে <Cite n={13} />। path দিলে সে সেই path-এ একটা chart খোঁজে, যাতে একটা `Chart.yaml` file থাকতে হবে <Cite n={13} />। version-যুক্ত chart archive Helm package repository ব্যবহার করে <Cite n={13} />। chart-এ signature দিতে `--sign` flag ব্যবহার করুন <Cite n={13} />। Helm-এর provenance tool আছে, যা chart-এর ব্যবহারকারীকে package-এর অখণ্ডতা (integrity) আর উৎস যাচাই করতে সাহায্য করে <Cite n={22} />। provenance file তৈরি হয় package করার সময়, আর একাধিক command তা যাচাই করতে পারে, বিশেষ করে `helm install --verify` <Cite n={22} />। chart repository হলো একটা HTTP server, যাতে থাকে একটা `index.yaml` file আর ইচ্ছে হলে কিছু packaged chart <Cite n={24} />। Helm docs chart package রাখতে আর ভাগ করতে OCI সমর্থন করে এমন container registry ব্যবহারের সুপারিশ করে <Cite n={23} />।

**catalog descriptor।** Backstage docs একটা catalog descriptor file-এর নাম `catalog-info.yaml` রাখার সুপারিশ করে <Cite n={28} />। descriptor file YAML, যাতে মানুষ সেটা সহজে সামলাতে পারে <Cite n={28} />। `kind` হলো যে উঁচু স্তরের entity type বর্ণনা করা হচ্ছে, সেটা <Cite n={28} />। `apiVersion` হলো specification format-এর সেই version, যার বিপরীতে entity লেখা হয়েছে <Cite n={28} />। একটা নাম হতে হবে kind অনুযায়ী অনন্য, একটা নির্দিষ্ট namespace-এর মধ্যে, যেকোনো সময়ে <Cite n={28} />। ডিফল্টভাবে একটা নাম হলো ১ থেকে ৬৩ অক্ষরের একটা string, যা গড়া অক্ষর আর অঙ্কের ক্রম দিয়ে, যাদের আলাদা করতে পারে `-`, `_` বা `.` <Cite n={28} />। নামের নিয়ম বদলানো যায় <Cite n={28} />। একটা Component-এর জন্য `spec.type`, `spec.lifecycle` আর `spec.owner` প্রতিটাই বাধ্যতামূলক <Cite n={28} />।

**owner আর lifecycle।** Backstage-এ একটা component-এর owner হলো সেই একক entity, সাধারণত একটা team, যে component-টার চূড়ান্ত দায় বহন করে আর তা বানানো ও সামলানোর অধিকার ও সামর্থ্য রাখে <Cite n={28} />। কিছু ভুল হলে বা নতুন feature চাইলে owner-ই যোগাযোগের মানুষ <Cite n={28} />। software catalog যেকোনো lifecycle মান নেয়, কিন্তু একটা প্রতিষ্ঠানের উচিত সেগুলোর একটা ঠিকঠাক শ্রেণিবিন্যাস দাঁড় করাতে খুব যত্ন নেওয়া <Cite n={28} />। docs `experimental`-কে বলে একটা পরীক্ষা বা শুরুর দিকের, production নয় এমন component <Cite n={28} />। তারা `production`-কে বলে একটা প্রতিষ্ঠিত, মালিকানাযুক্ত, রক্ষণাবেক্ষণ করা component <Cite n={28} />।

**kind আর reference।** component হলো আলাদা আলাদা software-এর টুকরো <Cite n={29} />। API হলো আলাদা component-এর মধ্যেকার সীমানা <Cite n={29} />। resource হলো একটা component চালাতে দরকারি বাস্তব বা ভার্চুয়াল অবকাঠামো <Cite n={29} />। user বর্ণনা করে একজন মানুষকে, যেমন একজন কর্মী, ঠিকাদার বা অনুরূপ কেউ <Cite n={29} />। group বর্ণনা করে একটা সাংগঠনিক entity-কে, যেমন একটা team, একটা business unit বা আগ্রহের ভিত্তিতে গড়া আলগা একটা দল <Cite n={29} />। catalog-এর প্রতিটা entity অনন্যভাবে চেনা যায় তার kind, namespace আর name-এর তিনটা মান দিয়ে <Cite n={31} />। একটা string reference এক থেকে তিনটা অংশ দিয়ে গড়া, এই নির্দিষ্ট ক্রমে, কোনো বাড়তি encoding ছাড়া: ইচ্ছে হলে kind আর তার পর একটা কোলন, ইচ্ছে হলে namespace আর তার পর একটা সামনের slash, আর name <Cite n={31} />।

**একটা entity-র জীবন।** catalog একটা কেন্দ্র, যেখানে entity বিভিন্ন নির্ভরযোগ্য উৎস থেকে ঢোকে (ingest) আর একটা database-এ থাকে, স্বয়ংক্রিয় processing-এর মধ্য দিয়ে যায়, আর তারপর একটা API দিয়ে দেখানো হয় <Cite n={30} />। ingestion হলো যেখানে entity provider বাইরের উৎস থেকে কাঁচা entity data আনে আর database-এ বসায় <Cite n={30} />। processing-এ policy আর processor ঢুকে আসা data-র ওপর ক্রমাগত কাজ করে <Cite n={30} />। policy entity-র আকার নিয়ে প্রাথমিক নিয়ম ঠিক করে <Cite n={30} />। processor কাঁচা entity data যাচাই করে, বিশ্লেষণ করে আর বদলে তার চূড়ান্ত রূপ দেয় <Cite n={30} />। stitching-এ processor-রা যে সব data ছেড়েছে, তা জোড়া লেগে চূড়ান্ত output entity হয় <Cite n={30} />। একটা entity catalog API দিয়ে দেখা যায় না, যতক্ষণ না সে শেষ ধাপ পেরিয়ে চূড়ান্ত entity-দের মধ্যে এসে পৌঁছায় <Cite n={30} />।

**software template আর TechDocs।** ডিফল্টভাবে Software Templates code-এর কাঠামো load করতে পারে, কিছু variable বসাতে পারে, আর তারপর সেই template GitHub বা GitLab-এর মতো জায়গায় publish করতে পারে <Cite n={32} />। TechDocs হলো Spotify-র নিজস্ব docs-like-code সমাধান, যা সরাসরি Backstage-এর ভেতরে বানানো <Cite n={33} />। engineer-রা তাদের documentation লেখেন Markdown file-এ, যা তাদের code-এর সঙ্গেই থাকে <Cite n={33} />। সামান্য configuration দিয়ে তারা Backstage-এ একটা doc site পান <Cite n={33} />।

**lifecycle।** lifecycle buildpack-গুলোকে চালায়, তারপর পাওয়া artifact-গুলো জুড়ে একটা OCI image বানায় <Cite n={37} />। একটা image build-এ ৫টা lifecycle phase লাগে <Cite n={37} />। সেগুলো হলো detect, analyze, restore, build আর export binary <Cite n={45} />। analyzer, restorer আর exporter-এর একটা image repository-তে ঢোকার সুযোগ লাগে, হয় একটা OCI registry, নয় একটা Docker-সামঞ্জস্যপূর্ণ daemon <Cite n={37} />। নিরাপত্তা শক্ত করতে এই phase-গুলো আলাদা আলাদা container-এ চলে, যাতে সংবেদনশীল data buildpack-গুলোর সামনে না পড়ে <Cite n={37} />। detector আর builder buildpack-গুলোকে চালায় <Cite n={37} />। নিরাপত্তা শক্ত করতে এই কাজ করার সময় lifecycle আর buildpack দুটোই non-root user হিসেবে চলে <Cite n={37} />। কোনো builder trusted হলে ৫টা lifecycle phase-ই একই container-এ চলতে পারে, creator binary দিয়ে <Cite n={37} />।

**detect।** detector build phase-এ ব্যবহারের জন্য buildpack-এর একটা ক্রমানুসারে সাজানো group খুঁজে বের করে <Cite n={38} />। সে `order.toml` পড়ে, আর প্রথম যে group detection পার হয়, তাকে খোঁজে <Cite n={38} />। সব group ব্যর্থ হলে detection ব্যর্থ হয় <Cite n={38} />। পার হতে হলে সব দরকারি (required) buildpack-এর detect script সফলভাবে পার হতে হবে, অর্থাৎ exit code শূন্য হতে হবে <Cite n={38} />। detector-এরও উচিত group-এর buildpack-গুলোর সব চাহিদা নিয়ে একটা build plan বানাতে পারা <Cite n={38} />। যে প্রথম group দুটো ধাপই পার হয়, তাকে `group.toml`-এ লেখা হয়, আর তার build plan `plan.toml`-এ লেখা হয় <Cite n={38} />।

**একটা buildpack-এর দুটো executable।** component buildpack হলো এমন buildpack, যাতে `/bin/detect` আর `/bin/build` executable আছে <Cite n={41} />। `pack buildpack new` command একটা buildpack repository-র মৌলিক কাঠামো বানায় <Cite n={42} />। সে একটা `buildpack.toml` আর দুটো executable bash script, `bin/detect` আর `bin/build`, বানায় <Cite n={42} />। spec `/bin/detect`-এর exit status দেয় এভাবে: pass (0), fail (100) বা error (1-99, 101+) <Cite n={41} />। spec `/bin/build`-এর exit status দেয় এভাবে: success (0) বা failure (1+) <Cite n={41} />। `CNB_LAYERS_DIR` variable-এ থাকে buildpack-এর layers directory-র পূর্ণ path <Cite n={41} />। build সেই directory-তে app-এর metadata সহ একটা `launch.toml` file লিখতে পারে <Cite n={41} />। detect আর build executable-এর positional argument Buildpack API 0.8-এ deprecated হয়েছে, আর lifecycle তাদের মান environment variable হিসেবে দেয় <Cite n={41} />।

**layer।** layer হলো একগুচ্ছ filesystem পরিবর্তন, OCI Image Specification অনুযায়ী package করা <Cite n={41} />। layer directory হলো একটা component buildpack-এর বানানো directory, যাতে build আর/বা runtime-এর dependency থাকে <Cite n={41} />। spec তিন ধরনের layer-এর নাম দেয় <Cite n={41} />। launch layer রপ্তানি করা OCI image-এ একটা layer হিসেবে যোগ হয় <Cite n={41} />। cache layer cache-এ রাখা হয়, আর তার ভেতরের জিনিস পরের build-এ ফিরিয়ে আনা হতে পারে <Cite n={41} />। build layer-এ থাকে child directory, যাদের path একই build-এর পরের buildpack-গুলোর জন্য environment-এ যোগ হয় <Cite n={41} />। Buildpacks docs-এর উদাহরণ output-এ `example/node-engine` buildpack-এর layer আছে `/layers/example_node-engine`-এ <Cite n={47} />।

**builder, platform আর বিশ্বাস।** `pack build` Cloud Native Buildpacks ব্যবহার করে source code থেকে একটা চালানো যায় এমন app image বানায় <Cite n={43} />। তার একটা image name লাগে <Cite n={43} />। সে ডিফল্টভাবে current directory ধরে, আর `--path` দিয়ে আপনি অন্য একটা source code directory দিতে পারেন <Cite n={43} />। তার একটা builder লাগে, যা `--builder` দিয়ে দেওয়া যায় বা `set-default-builder` command দিয়ে ঠিক করা যায় <Cite n={43} />। `--buildpack` flag আরও কয়েক রকমের সঙ্গে একটা buildpack directory-র path নেয় <Cite n={43} />। `pack inspect` একটা বানানো app image-এর তথ্য দেখায় <Cite n={44} />। pack version 0.11.0 থেকে `pack` এমন builder চিনতে পারে, যাকে trusted ধরা উচিত <Cite n={45} />। `pack` কোনো builder-কে trusted ধরলে `pack build` creator নামের একটা একক lifecycle binary ব্যবহার করে <Cite n={45} />। `pack` কোনো builder-কে বিশ্বাস না করলে সে পাঁচটা আলাদা lifecycle binary চালিয়ে যায় <Cite n={45} />। docs বলে, এই বাছাই নিরাপত্তা আর গতির মধ্যে একটা ভারসাম্য আনে <Cite n={45} />।

**বিশ্বাসের পেছনের সুবিধা-অসুবিধা।** `pack` কোনো builder-কে বিশ্বাস না করলে সে বেশি সুবিধাপ্রাপ্ত phase-গুলো চালায় একটা প্রকাশিত lifecycle image দিয়ে, যদি তেমন একটা পাওয়া যায় <Cite n={45} />। analyze, restore আর export phase-এর দরকার বেশি উঁচু স্তরের সুবিধা বা সংবেদনশীল data-য় ঢোকার সুযোগ, যা detect আর build phase-এর লাগে না <Cite n={45} />। `pack` কোনো অবিশ্বস্ত builder-এর সঙ্গে creator ব্যবহার করলে প্রতিটা buildpack-এর `bin/detect` আর `bin/build` চলত এমন একটা container-এ, যেখানে বাড়তি সুবিধা বা registry credential-এ ঢোকার সুযোগ আছে <Cite n={45} />।

**rebase, পুনরাবৃত্তিযোগ্যতা আর SBOM।** rebaser application layer-গুলোকে runtime base image-এর একটা নতুন version-এর ওপর বসায় <Cite n={39} />। Cloud Native Buildpacks project container image-এর “Reproducible Builds” বানানোর লক্ষ্য রাখে <Cite n={40} />। একই input পেলে দুটো build-এর একই output দেওয়া উচিত <Cite n={40} />। Software Bill-of-Materials (SBOM) একটা image-এ থাকা সব software component-এর তালিকা <Cite n={46} />। buildpack তাদের দেওয়া dependency নিয়ে SBOM তথ্য ভরতে পারে <Cite n={46} />। `pack sbom download` command SBOM file সহ app layer-টা আপনার স্থানীয় filesystem-এর `./layers/sbom/...`-এ download করে <Cite n={46} />।

```javascript
// validate.mjs FILE...: check each Component descriptor with the validators of @backstage/catalog-model.
// It is the tutorial's own script.
import { readFileSync } from 'node:fs';
import { parseAllDocuments } from 'yaml';
import { componentEntityV1alpha1Validator, makeValidator } from '@backstage/catalog-model';

const names = makeValidator();
let failed = 0;
for (const file of process.argv.slice(2)) {
  for (const doc of parseAllDocuments(readFileSync(file, 'utf8'))) {
    const entity = doc.toJS();
    const problems = [];
    try {
      const applies = await componentEntityV1alpha1Validator.check(entity);
      if (!applies) problems.push('the Component validator does not apply to this entity');
    } catch (error) {
      problems.push(`kind check: ${error.message}`);
    }
    const name = entity?.metadata?.name;
    if (!names.isValidEntityName(name)) problems.push(`metadata.name ${JSON.stringify(name)} is not a valid entity name`);
    if (problems.length) failed++;
    console.log(`${problems.length ? 'FAIL' : 'PASS'} ${file}${problems.map((p) => `\n     ${p}`).join('')}`);
  }
}
process.exit(failed ? 1 : 0);
```

```javascript
// validate.mjs FILE...: check each Component descriptor with the validators of @backstage/catalog-model.
// It is the tutorial's own script.
import { readFileSync } from 'node:fs';
import { parseAllDocuments } from 'yaml';
import { componentEntityV1alpha1Validator, makeValidator } from '@backstage/catalog-model';

const names = makeValidator();
let failed = 0;
for (const file of process.argv.slice(2)) {
  for (const doc of parseAllDocuments(readFileSync(file, 'utf8'))) {
    const entity = doc.toJS();
    const problems = [];
    try {
      const applies = await componentEntityV1alpha1Validator.check(entity);
      if (!applies) problems.push('the Component validator does not apply to this entity');
    } catch (error) {
      problems.push(`kind check: ${error.message}`);
    }
    const name = entity?.metadata?.name;
    if (!names.isValidEntityName(name)) problems.push(`metadata.name ${JSON.stringify(name)} is not a valid entity name`);
    if (problems.length) failed++;
    console.log(`${problems.length ? 'FAIL' : 'PASS'} ${file}${problems.map((p) => `\n     ${p}`).join('')}`);
  }
}
process.exit(failed ? 1 : 0);
```

```javascript
// validate.mjs FILE...: check each Component descriptor with the validators of @backstage/catalog-model.
// It is the tutorial's own script.
import { readFileSync } from 'node:fs';
import { parseAllDocuments } from 'yaml';
import { componentEntityV1alpha1Validator, makeValidator } from '@backstage/catalog-model';

const names = makeValidator();
let failed = 0;
for (const file of process.argv.slice(2)) {
  for (const doc of parseAllDocuments(readFileSync(file, 'utf8'))) {
    const entity = doc.toJS();
    const problems = [];
    try {
      const applies = await componentEntityV1alpha1Validator.check(entity);
      if (!applies) problems.push('the Component validator does not apply to this entity');
    } catch (error) {
      problems.push(`kind check: ${error.message}`);
    }
    const name = entity?.metadata?.name;
    if (!names.isValidEntityName(name)) problems.push(`metadata.name ${JSON.stringify(name)} is not a valid entity name`);
    if (problems.length) failed++;
    console.log(`${problems.length ? 'FAIL' : 'PASS'} ${file}${problems.map((p) => `\n     ${p}`).join('')}`);
  }
}
process.exit(failed ? 1 : 0);
```

**Chart changes before any cluster.** `helm lint` runs a series of tests to verify that a chart is well-formed <Cite n={10} />. **Values.** The order of specificity of values is this: `values.yaml` is the default, a parent chart's `values.yaml` can override it, a user-supplied values file can override that, and `--set` parameters can override that <Cite n={19} />. To delete a key from the default values, you can override the value of the key with `null`, and Helm then removes the key from the merged values <Cite n={19} />. The chart best practices say that in most cases flat should be favored over nested <Cite n={20} />. They also say that for optimal safety a nested value must be checked at every level <Cite n={20} />.

A rolled back release receives a new release number <Cite n={7} />. By default, release information is stored in Secrets in the namespace of the release <Cite n={21} />. `helm test` runs the tests for a deployed release <Cite n={16} />. The container of a test should exit with 0 for the test to be considered a success <Cite n={17} />.

Integrity is established by comparing a chart to a provenance record <Cite n={22} />. A provenance contains a cryptographic hash of the chart archive file, the `Chart.yaml` data, and a signature block <Cite n={7} />. Provenance records are stored in provenance files, alongside a packaged chart <Cite n={22} />. For a chart named `myapp-1.2.3.tgz`, the provenance file is `myapp-1.2.3.tgz.prov` <Cite n={22} />. The tutorial did not sign a chart.

**Who owns a service.** The Backstage Software Catalog keeps track of ownership and metadata for all the software in your ecosystem <Cite n={27} />. It makes all the software in your company, and who owns it, discoverable <Cite n={27} />. The owner of a component is the point of contact if something goes wrong <Cite n={28} />. The docs list `experimental`, `production`, and `deprecated` among the well-known lifecycle values <Cite n={28} />. Each entity is uniquely identified by its kind, namespace, and name <Cite n={31} />. An entity is not visible through the catalog API until it has passed through the last process <Cite n={30} />. In step 7, the tutorial's script rejected a file with no owner and a file with a bad name.

The rebaser places application layers atop a new version of the runtime base image <Cite n={39} />. The output of the run said `Rebasable: true`. A Software Bill-of-Materials (SBOM) lists all the software components included in an image <Cite n={46} />. The `pack sbom download` command downloads the app layer containing the SBOM files <Cite n={46} />. The formats that are supported are CycloneDX, Syft, and Spdx <Cite n={46} />. The tutorial did not run `pack sbom download` or `pack rebase`. The project aims to create reproducible builds of container images <Cite n={40} />. In step 9, the second build reused every layer and printed the same image ID as the first build. If `pack` does not trust a builder, it runs the more privileged phases using a published lifecycle image, if one is available <Cite n={45} />.

**Images that a buildpack made.** `pack inspect` shows information about a built app image <Cite n={44} />. In step 9 it listed the stack, the run image, the buildpack `qa/hello-buildpack` with the version `1.0.0`, and the default `web` process. The rebaser places application layers atop a new version of the runtime base image <Cite n={39} />. The output of the run said `Rebasable: true`. A Software Bill-of-Materials (SBOM) lists all the software components included in an image <Cite n={46} />. The `pack sbom download` command downloads the app layer containing the SBOM files <Cite n={46} />. The formats that are supported are CycloneDX, Syft, and Spdx <Cite n={46} />. The tutorial did not run `pack sbom download` or `pack rebase`. The project aims to create reproducible builds of container images <Cite n={40} />. In step 9, the second build reused every layer and printed the same image ID as the first build. If `pack` does not trust a builder, it runs the more privileged phases using a published lifecycle image, if one is available <Cite n={45} />.

**cluster-এর আগে chart-এর পরিবর্তন।** `helm lint` কয়েকটা test চালিয়ে দেখে একটা chart ঠিকঠাক গড়া কি না <Cite n={10} />। টিউটোরিয়ালের run-এর ৪ নম্বর ধাপে একটা মান schema ভাঙলে সে exit status 1 দিয়ে শেষ হয়েছে। `helm template` chart-এর template স্থানীয়ভাবে render করে আর output দেখায় <Cite n={11} />। ৩ নম্বর ধাপে output-এ default value দিয়ে ছিল `replicas: 1`, আর `--set replicaCount=3` দিয়ে `replicas: 3`। render করা manifest হলো text, আর টিউটোরিয়ালের `render_test.sh` ৫ নম্বর ধাপে `grep` দিয়ে তা পড়ে। `values.schema.json`-এর schema যাচাই হয় যখন `helm lint` বা `helm template` চলে <Cite n={8} />। এই যাচাইয়ের সীমা আছে। `helm template` chart ঠিক আছে কি না তা server-এর দিক থেকে পরীক্ষা করার কিছুই করে না, যেমন কোনো API সমর্থিত কি না <Cite n={11} />।

**value।** value-র অগ্রাধিকারের ক্রম এই: `values.yaml` হলো default, parent chart-এর `values.yaml` তাকে বদলাতে পারে, user-এর দেওয়া values file সেটাকে বদলাতে পারে, আর `--set` parameter সেটাকেও বদলাতে পারে <Cite n={19} />। `-f` flag একাধিকবার দিলে শেষের, ডানদিকের file-টা অগ্রাধিকার পায় <Cite n={12} />। ৩ নম্বর ধাপে একটা `--set` Deployment-এর replica-সংখ্যা 1 থেকে 3 করে দিয়েছে। default value থেকে একটা key মুছতে চাইলে আপনি সেই key-র মান `null` দিয়ে বদলে দিতে পারেন, আর তখন Helm মিলিত value থেকে key-টা সরিয়ে দেয় <Cite n={19} />। chart best practice বলে, বেশির ভাগ ক্ষেত্রে nested-এর চেয়ে flat বেছে নেওয়া উচিত <Cite n={20} />। তারা আরও বলে, সবচেয়ে নিরাপদ হতে একটা nested value-র প্রতিটা স্তরে যাচাই করতে হয় <Cite n={20} />।

**test environment-এর release।** একটা release-এর revision number দেখতে চালান `helm history RELEASE` <Cite n={14} />। command-টা ইতিহাসের release-সেট একটা সাজানো সারণি (table) হিসেবে ছাপে <Cite n={15} />। একটা release-এর status-এ থাকে তার অবস্থা, তার revision, সে যেসব resource দিয়ে গড়া তার তালিকা, আর শেষ test suite চালানোর বিবরণ, যদি প্রযোজ্য হয় <Cite n={48} />। rollback করা release একটা নতুন release number পায় <Cite n={7} />। ডিফল্টভাবে release-এর তথ্য রাখা হয় release-এর namespace-এর Secret-এ <Cite n={21} />। `helm test` একটা deployed release-এর test চালায় <Cite n={16} />। একটা test সফল ধরা হতে হলে তার container-এর 0 দিয়ে শেষ হওয়া উচিত <Cite n={17} />।

**আপনি কী deploy করছেন।** chart repository হলো একটা HTTP server, যাতে থাকে একটা `index.yaml` file আর ইচ্ছে হলে কিছু packaged chart <Cite n={24} />। একটা OCI-ভিত্তিক registry-তে শূন্য বা তার বেশি Helm repository থাকতে পারে, আর সেই repository-গুলোর প্রতিটায় শূন্য বা তার বেশি packaged Helm chart থাকতে পারে <Cite n={23} />। অখণ্ডতা (integrity) প্রতিষ্ঠিত হয় একটা chart-কে একটা provenance record-এর সঙ্গে মিলিয়ে <Cite n={22} />। provenance-এ থাকে chart archive file-এর একটা ক্রিপ্টোগ্রাফিক hash, `Chart.yaml`-এর data আর একটা signature block <Cite n={7} />। provenance record রাখা হয় provenance file-এ, একটা packaged chart-এর পাশে <Cite n={22} />। `myapp-1.2.3.tgz` নামের chart-এর provenance file হলো `myapp-1.2.3.tgz.prov` <Cite n={22} />। টিউটোরিয়াল কোনো chart-এ signature দেয়নি।

**একটা service-এর মালিক কে।** Backstage Software Catalog আপনার ecosystem-এর সব software-এর মালিকানা আর metadata-র হিসাব রাখে <Cite n={27} />। সে আপনার কোম্পানির সব software, আর তার মালিক কে, তা খুঁজে পাওয়ার মতো করে <Cite n={27} />। কিছু ভুল হলে একটা component-এর owner-ই যোগাযোগের মানুষ <Cite n={28} />। docs পরিচিত lifecycle মানের মধ্যে `experimental`, `production` আর `deprecated`-এর নাম দেয় <Cite n={28} />। প্রতিটা entity অনন্যভাবে চেনা যায় তার kind, namespace আর name দিয়ে <Cite n={31} />। একটা entity catalog API দিয়ে দেখা যায় না, যতক্ষণ না সে শেষ ধাপ পেরিয়ে আসে <Cite n={30} />। ৭ নম্বর ধাপে টিউটোরিয়ালের script owner-বিহীন একটা file আর খারাপ নামের একটা file বাতিল করেছে।

**buildpack-এর বানানো image।** `pack inspect` একটা বানানো app image-এর তথ্য দেখায় <Cite n={44} />। ৯ নম্বর ধাপে সে stack, run image, `qa/hello-buildpack` buildpack-এর version `1.0.0`, আর default `web` process দেখিয়েছে। rebaser application layer-গুলোকে runtime base image-এর একটা নতুন version-এর ওপর বসায় <Cite n={39} />। run-এর output বলেছে `Rebasable: true`। Software Bill-of-Materials (SBOM) একটা image-এ থাকা সব software component-এর তালিকা <Cite n={46} />। `pack sbom download` command SBOM file সহ app layer download করে <Cite n={46} />। সমর্থিত format হলো CycloneDX, Syft আর Spdx <Cite n={46} />। টিউটোরিয়াল `pack sbom download` বা `pack rebase` চালায়নি। project container image-এর পুনরাবৃত্তিযোগ্য (reproducible) build বানানোর লক্ষ্য রাখে <Cite n={40} />। ৯ নম্বর ধাপে দ্বিতীয় build প্রতিটা layer আবার ব্যবহার করেছে আর প্রথম build-এর মতো একই image ID ছাপিয়েছে। `pack` কোনো builder-কে বিশ্বাস না করলে সে বেশি সুবিধাপ্রাপ্ত phase-গুলো চালায় একটা প্রকাশিত lifecycle image দিয়ে, যদি তেমন একটা পাওয়া যায় <Cite n={45} />।

## Common mistakes

<Voices>
<Technical>

- **Reading a passing `helm template` as a test of the cluster.** `helm template` fakes any value that it would normally look up in a cluster <Cite n={11} />. It does none of the server-side testing of chart validity <Cite n={11} />. A server-side dry run needs cluster connectivity <Cite n={11} />. The tutorial's run had no cluster, so it ran only the client-side dry run.
- **Ignoring the level of a lint message.** `helm lint` emits `[ERROR]` messages for things that will cause the chart to fail installation <Cite n={10} />. It emits `[WARNING]` messages for issues that break with convention or recommendation <Cite n={10} />. In step 2, the run printed an `[INFO]` line, and the chart passed with `0 chart(s) failed`. In step 4, an `[ERROR]` made `helm lint` fail with exit status 1.
- **Mixing up a chart, a release, and a revision.** A single chart may be installed many times into the same cluster, and create many different releases <Cite n={7} />. Each time a release is upgraded or rolled back, the release number is incremented <Cite n={7} />. A rolled back release receives a new release number, and not the old one <Cite n={7} />.
- **Setting a value in the wrong layer.** A `--set` parameter can override a user-supplied values file. That file can override the `values.yaml` of a parent chart. That one can override the default `values.yaml` <Cite n={19} />. If you give `-f` more than once, the right-most file gets the priority <Cite n={12} />. To force a string value, use `--set-string` <Cite n={12} />. In step 4, the schema rejected `replicaCount=abc` with `got string, want integer`.
- **Installing a binary or an image without checking where it came from.** The Helm docs say that you should always verify the authenticity of Helm binaries before installing <Cite n={25} />. Helm has provenance tools which help chart users verify the integrity and origin of a package <Cite n={22} />. Suppose `pack` used the creator with an untrusted builder <Cite n={45} />. Then the `bin/detect` and `bin/build` of each buildpack would run within a container that has heightened privileges or access to registry credentials <Cite n={45} />. The checksum check of the tutorial's `pack` install shows that the archive is whole. It does not show who built it.
- **Expecting a catalog entity at once, or with any name.** An entity is not visible through the catalog API until it has passed through the last process <Cite n={30} />. By default, a name is a string of 1 to 63 characters <Cite n={28} />. By default, it is made of sequences of letters and digits, possibly separated by `-`, `_`, or `.` <Cite n={28} />. In step 7, the name `qa demo` failed this check.
- **Copying a buildpack scaffold without reading its API level.** The `bin/build` that `pack buildpack new` wrote in the run reads its layers directory from `$1`. The spec deprecated the positional arguments to the detect and build executables in Buildpack API 0.8 <Cite n={41} />. The exit status of `/bin/detect` is pass (0), fail (100), or error (1-99, 101+) <Cite n={41} />. So a detect script that exits with 1 reports an error. It does not report a failed detection.

- **কোথা থেকে এসেছে তা না দেখেই binary বা image install করা।** Helm docs বলে, install করার আগে আপনার সবসময় Helm binary-র খাঁটিত্ব যাচাই করা উচিত <Cite n={25} />। Helm-এর provenance tool আছে, যা chart-এর ব্যবহারকারীকে package-এর অখণ্ডতা আর উৎস যাচাই করতে সাহায্য করে <Cite n={22} />। ধরুন `pack` একটা অবিশ্বস্ত builder-এর সঙ্গে creator ব্যবহার করল <Cite n={45} />। তাহলে প্রতিটা buildpack-এর `bin/detect` আর `bin/build` চলত এমন একটা container-এ, যেখানে বাড়তি সুবিধা বা registry credential-এ ঢোকার সুযোগ আছে <Cite n={45} />। টিউটোরিয়ালের `pack` install-এর checksum যাচাই দেখায় archive-টা অক্ষত। কে সেটা বানিয়েছে তা সে দেখায় না।
- **একটা catalog entity সঙ্গে সঙ্গে আশা করা, বা যেকোনো নাম দেওয়া।** একটা entity catalog API দিয়ে দেখা যায় না, যতক্ষণ না সে শেষ ধাপ পেরিয়ে আসে <Cite n={30} />। ডিফল্টভাবে একটা নাম হলো ১ থেকে ৬৩ অক্ষরের একটা string <Cite n={28} />। ডিফল্টভাবে সেটা গড়া অক্ষর আর অঙ্কের ক্রম দিয়ে, যাদের আলাদা করতে পারে `-`, `_` বা `.` <Cite n={28} />। ৭ নম্বর ধাপে `qa demo` নামটা এই যাচাইয়ে ব্যর্থ হয়েছে।
- **API স্তর না পড়েই buildpack scaffold কপি করা।** run-এ `pack buildpack new`-এর লেখা `bin/build` তার layers directory পড়ে `$1` থেকে। spec বলে, detect আর build executable-এর positional argument Buildpack API 0.8-এ deprecated হয়েছে <Cite n={41} />। `/bin/detect`-এর exit status হলো pass (0), fail (100) বা error (1-99, 101+) <Cite n={41} />। তাই যে detect script 1 দিয়ে শেষ হয়, সে error জানায়। সে ব্যর্থ detection জানায় না।

## What a tester can check

<Voices>
<Technical>

<Callout type="tip" title="Tutorial advice">
This list is the tutorial's own advice for a tester who works with Helm, Backstage, and buildpacks.

- Run `helm lint` and `helm template` on every change to a chart, and fail the build on a non-zero exit status.
- Give the chart a `values.schema.json`, and test it with one good and one bad set of values.
- Write render tests for the things that your team must never ship, such as a `latest` tag or a missing resource limit, and run them on the output of `helm template`.
- Say in the test report that `helm template` and a client-side dry run did not talk to a cluster, and run `helm test` against a deployed release as well.
- Keep the output of `helm history` and `helm status` in the report of a test run, so that the revision under test is on record.
- Verify the signature of a downloaded `helm` binary, and say in the report when you could check only a checksum.
- Check every catalog descriptor in the pull request with a script such as `validate.mjs`, so that a missing owner or a bad name fails before the merge.
- Look at the owner and the lifecycle of a service in the catalog first when you triage a defect.
- Build the image in CI with the same builder every time, and compare the image IDs of two builds of the same commit.
- Download the SBOM of an image that you test, and keep it with the report.
</Callout>

## Key words

| Term | Meaning |
|---|---|
| Graduated | Graduated projects are highly mature, robust projects whose adopters have demonstrated their production-readiness by deploying them to production environments |
| Chart | A chart is a Helm package that contains information sufficient for installing a set of Kubernetes resources into a Kubernetes cluster |
| Release | When a chart is installed, the Helm library creates a release to track that installation |
| Values | Values provide a way to override template defaults with your own information |
| Lint | To lint a chart is to validate that it follows the conventions and requirements of the Helm chart standard |
| Chart archive | A chart archive is a tarred and gzipped (and optionally signed) chart |
| Hook | Hooks work like regular templates, but they have special annotations that cause Helm to use them differently |
| Provenance | Helm has provenance tools which help chart users verify the integrity and origin of a package |
| OCI-based registry | An OCI-based registry can contain zero or more Helm repositories, and each of those repositories can contain zero or more packaged Helm charts |
| Software Catalog | The Backstage Software Catalog is a centralized system that keeps track of ownership and metadata for all the software in your ecosystem |
| Entity | Each entity in the catalog is uniquely identified by the triplet of its kind, namespace, and name |
| Owner | the owner of a component is the singular entity, commonly a team, that bears ultimate responsibility for the component and has the authority and capability to develop and maintain it |
| Buildpack | A buildpack is software that transforms application source code into runnable artifacts by analyzing the code and determining the best way to build it |
| Builder | A builder is an OCI image that contains an ordered combination of buildpacks, a build-time base image, a lifecycle binary, and a reference to a runtime base image |
| Platform | A platform orchestrates builds by invoking the lifecycle binary together with buildpacks and app source code to produce a runnable OCI image |
| Lifecycle | The lifecycle orchestrates buildpacks, then assembles the resulting artifacts into an OCI image |
| Layer | A layer is a set of filesystem changes packaged according to the OCI Image Specification |
| Rebase | The rebaser places application layers atop a new version of the runtime base image |
| SBOM | A Software Bill-of-Materials (SBOM) lists all the software components included in an image |
