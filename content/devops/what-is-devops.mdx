# What Is DevOps?

In DevOps, testing is not only a phase at the end. Testers work alongside developers through the whole delivery. This page explains what DevOps is, the practices that it uses, how DORA measures delivery, and where a tester fits. The other pages of this module go deeper into each practice.

## What it is

<Voices>
<Technical>

DevOps is the combination of cultural philosophies, practices, and tools that increases an organization's ability to deliver applications and services at high velocity <Cite n={1} />. DevOps combines development (Dev) and operations (Ops) to unite people, process, and technology in application planning, development, delivery, and operations <Cite n={2} />. DevOps enables coordination and collaboration between formerly siloed roles like development, IT operations, quality engineering, and security <Cite n={2} />.

**No more silos.** Under a DevOps model, development and operations teams are no longer "siloed" <Cite n={1} />. Sometimes the two teams are merged into a single team. Its engineers work across the entire application lifecycle, from development and test to deployment to operations <Cite n={1} />.

**Quality and security join in.** In some DevOps models, quality assurance and security teams may also become more tightly integrated with development and operations, throughout the application lifecycle <Cite n={1} />. When security is the focus of everyone on a DevOps team, this is sometimes called **DevSecOps** <Cite n={1} />.

**What changes for testing.** DORA is a research program, led by a global team of researchers at Google <Cite n={7} />. Its page on test automation compares the traditional way with what it recommends:

| | Traditionally | What DORA recommends |
|---|---|---|
| How the system is checked | Manual testing and code inspection <Cite n={4} /> | Fast, reliable suites of automated tests, run in the continuous delivery pipeline <Cite n={4} /> |
| When | In a separate phase after "dev complete" <Cite n={4} /> | Throughout the delivery process, with manual activities such as exploratory testing too <Cite n={4} /> |
| Feedback for developers | A long wait after "dev complete" <Cite n={4} /> | Most of their work is validated in minutes, instead of days or weeks <Cite n={4} /> |

"Tester" is a role here, not necessarily a full-time job <Cite n={4} />.

</Technical>
<Layman>

DevOps is a mix of ways of thinking, ways of working, and tools. It helps an organization deliver applications and services at high speed <Cite n={1} />. DevOps joins development (Dev) and operations (Ops). It brings people, process, and technology together in application planning, development, delivery, and operations <Cite n={2} />. Roles such as development, IT operations, quality engineering, and security used to work apart. DevOps lets them coordinate and work together <Cite n={2} />.

**No more silos.** In DevOps, the development team and the operations team stop working apart <Cite n={1} />. Sometimes the two become one team. Its engineers work on the whole life of the application: development, test, deployment, and operations <Cite n={1} />.

**Quality and security join in.** In some DevOps teams, quality assurance and security people may also work closely with development and operations, all through the life of the application <Cite n={1} />. When security is the focus of everyone on the team, people sometimes call it **DevSecOps** <Cite n={1} />.

**What changes for testing.** DORA is a research program, led by a team of researchers at Google <Cite n={7} />. Its page on test automation compares the old way with what it recommends:

| | The old way | What DORA recommends |
|---|---|---|
| How the system is checked | People test by hand and read the code <Cite n={4} /> | Fast, reliable sets of automated tests run in the delivery pipeline <Cite n={4} /> |
| When | In a separate phase, after "dev complete" <Cite n={4} /> | All through delivery, and people still do manual work such as exploratory testing <Cite n={4} /> |
| Feedback for developers | A long wait after "dev complete" <Cite n={4} /> | Most of their work is checked in minutes, not days or weeks <Cite n={4} /> |

Here "tester" is a role. It is not always a full-time job <Cite n={4} />.

</Layman>

**quality আর security-ও যুক্ত হয়।** কিছু DevOps model-এ quality assurance আর security টিমও development ও operations-এর সাথে, application-এর পুরো lifecycle জুড়ে, আরও ঘনিষ্ঠভাবে যুক্ত হতে পারে <Cite n={1} />। যখন DevOps টিমের সবার মনোযোগ security-তে থাকে, তখন একে কখনো কখনো **DevSecOps** বলা হয় <Cite n={1} />।

| | প্রচলিত পদ্ধতি | DORA-র সুপারিশ |
|---|---|---|
| system কীভাবে যাচাই হয় | হাতে করা testing আর code inspection <Cite n={4} /> | continuous delivery pipeline-এ চলা দ্রুত, নির্ভরযোগ্য automated test suite <Cite n={4} /> |
| কখন | "dev complete"-এর পরে একটা আলাদা phase-এ <Cite n={4} /> | পুরো delivery process জুড়ে, সাথে exploratory testing-এর মতো manual কাজও <Cite n={4} /> |
| developer-দের feedback | "dev complete"-এর পরে লম্বা অপেক্ষা <Cite n={4} /> | বেশিরভাগ কাজ দিন বা সপ্তাহ নয়, কয়েক মিনিটে যাচাই হয় <Cite n={4} /> |

এখানে "tester" একটা ভূমিকা, সবসময় full-time চাকরি নয় <Cite n={4} />।

## How it works

<Voices>
<Technical>

**The lifecycle.** DevOps influences the application lifecycle through its planning, development, delivery, and operations phases <Cite n={2} />. Each phase relies on the other phases, and the phases are not role-specific <Cite n={2} />. A DevOps culture involves all roles in each phase to some extent <Cite n={2} />.

```text
   plan  ---->  develop  ---->  deliver  ---->  operate
    ^                                              |
    +--- insights for future development cycles ---+
```

Monitoring closes the loop. Its insights help the team mitigate issues in real time, and see how to improve the application in future development cycles <Cite n={2} />.

**The practices.** Most DevOps practices are accomplished with proper tooling <Cite n={1} />. The main ones, and where this module covers them:

| Practice | What it is | In this module |
|---|---|---|
| Small, frequent updates | Frequent but small updates make each deployment less risky. The team can find the last deployment that caused an error <Cite n={1} /> | [CI/CD Pipelines](/devops/ci-cd/) |
| Version control | Managing code in versions: tracking revisions and change history, so that code is easy to review and recover <Cite n={2} /> | [Git Basics](/devops/git-basics/), [Git Workflows](/devops/git-workflows/) |
| Continuous integration | Developers regularly merge their changes into a central repository. Automated builds and tests then run <Cite n={1} /> | [CI/CD Pipelines](/devops/ci-cd/) |
| Continuous delivery | Code changes are automatically built, tested, and prepared for a release to production <Cite n={1} /> | [CI/CD Pipelines](/devops/ci-cd/), [GitOps](/devops/gitops/) |
| Infrastructure as code | Infrastructure is provisioned and managed with code and software development techniques, such as version control and continuous integration <Cite n={1} /> | [Terraform](/devops/terraform-iac/) |
| Configuration management | Managing the state of resources in a system, including servers, virtual machines, and databases <Cite n={2} /> | [Ansible](/devops/ansible/) |
| Continuous monitoring | Full, real-time visibility into the performance and health of the entire application stack <Cite n={2} /> | [Monitoring and Observability](/devops/monitoring-observability/) |

**How delivery is measured.** DORA identified five software delivery performance metrics <Cite n={3} />. Three measure throughput: how many changes can move through the system over a period of time. Two measure instability: how well the deployments go <Cite n={3} />.

| Metric | Group | What it measures |
|---|---|---|
| Change lead time | Throughput | The time for a change to go from committed to version control to deployed in production <Cite n={3} /> |
| Deployment frequency | Throughput | The number of deployments over a given period, or the time between deployments <Cite n={3} /> |
| Failed deployment recovery time | Throughput | The time to recover from a deployment that fails and requires immediate intervention <Cite n={3} /> |
| Change fail rate | Instability | The ratio of deployments that require immediate intervention after the deployment, likely a rollback or a hotfix <Cite n={3} /> |
| Deployment rework rate | Instability | The ratio of deployments that are unplanned but happen as a result of an incident in production <Cite n={3} /> |

DORA's research has repeatedly shown that speed and stability are not tradeoffs <Cite n={3} />. Top performers do well across all five metrics, and low performers do poorly <Cite n={3} />. The metrics are best suited for measuring one application or service at a time <Cite n={3} />.

</Technical>

## Try it

<Voices>
<Technical>

This exercise needs no tools, only the delivery data of one team. Use your own team's data, or the made-up month below.

**1. Pick one service.** The DORA metrics are best suited for one application or service at a time <Cite n={3} />.

**2. Map how one change reaches production.** Write down each step from commit to production: who does it, how long it waits, and which tests run. Mapping out the delivery process may help a team talk about its friction points <Cite n={3} />. A map can look like this. It is an invented example:

```text
commit -> review -> CI: unit tests -> deploy to staging -> manual regression -> approval -> production
         waits 6h      runs 10 min        runs 30 min          takes 1 day        waits 1 day
```

**3. Work out the five metrics.** Here is an invented month of one service:

| Deployment | Day | Commit to production | What happened |
|---|---|---|---|
| 1 | 2 | 2 days | Fine |
| 2 | 5 | 1 day | Failed. Rolled back after 3 hours |
| 3 | 9 | 3 days | Fine |
| 4 | 12 | 1 day | Failed. Deployment 5 fixed it after 1 hour |
| 5 | 12 | 1 hour | Unplanned hotfix for the failure of deployment 4 |
| 6 | 16 | 2 days | Fine |
| 7 | 19 | 1 day | Fine |
| 8 | 23 | 2 days | Fine |
| 9 | 26 | 1 day | Fine |
| 10 | 30 | 2 days | Fine |

Apply the definitions of DORA <Cite n={3} />:

- **Deployment frequency:** 10 deployments in 30 days.
- **Change lead time:** from 1 hour to 3 days. Most changes take 1 or 2 days.
- **Change fail rate:** 2 deployments (2 and 4) needed immediate intervention, so 2 of 10, or 20%.
- **Deployment rework rate:** 1 deployment (5) was unplanned and came from an incident, so 1 of 10, or 10%.
- **Failed deployment recovery time:** 3 hours and 1 hour.

**4. Find the bottleneck.** In the map of step 2, the manual regression run and the wait for approval take the most time. DORA suggests that the whole team commits to an improvement in the most significant constraint or bottleneck <Cite n={3} />.

**5. Take the DORA Quick Check.** A team can set a baseline for an application with the DORA Quick Check, and later use it again to check its progress <Cite n={3} />.

## How a tester uses it

<Voices>
<Technical>

The key to building quality into software is fast feedback on the impact of changes, throughout the software delivery lifecycle <Cite n={4} />. Here is where a tester helps.

**Work alongside developers.** DORA's research finds that teams do better when testers work alongside developers throughout development and delivery <Cite n={4} />. It is a good practice to pair testers with developers to create and evolve the suites of automated tests <Cite n={4} />.

**Bring the user's view.** Testers have a unique perspective on the system, because they understand how users interact with it <Cite n={4} />. They play an essential role in exploratory testing and usability testing, and they help to curate the test suites <Cite n={4} />.

**Keep feedback fast.** Developers should get feedback from automated tests in less than ten minutes, both on their workstations and from the continuous integration system <Cite n={4} />. Faster unit tests run before slower acceptance tests, and both run before any manual testing <Cite n={4} />.

**Shift testing left.** The goal of shifting testing left is to move quality upstream, by doing testing tasks earlier in the pipeline <Cite n={6} />. A team can choose where in the DevOps process each test runs <Cite n={6} />. Microsoft's guide uses a test taxonomy: it classifies tests by their dependencies and the time they take to run <Cite n={6} />:

| Level | What it tests | Example rule |
|---|---|---|
| L0, L1 | Unit tests: only the code in the assembly under test <Cite n={6} /> | |
| L2 | Functional tests that may also need other dependencies, like SQL or the file system <Cite n={6} /> | Developers run them before they commit <Cite n={6} /> |
| L3 | Functional tests against testable service deployments <Cite n={6} /> | A pull request fails if they fail <Cite n={6} /> |
| L4 | A restricted class of integration tests that run against production <Cite n={6} /> | A deployment may be blocked if they fail <Cite n={6} /> |

**Turn each bug into a faster test.** When you find an error in an acceptance test or during exploratory testing, add a unit test, so that the error is caught faster, earlier, and cheaper next time <Cite n={4} />.

**Plan the test data.** All kinds of tests need test data, manual and automated <Cite n={5} />. Good test data lets you validate common or high-value user journeys, test edge cases, reproduce defects, and simulate errors <Cite n={5} />. DORA's analysis shows that successful teams follow three principles: enough test data is available to run full automated test suites, it can be acquired on demand, and it does not limit the automated tests that the team can run <Cite n={5} />.

## Common mistakes

<Voices>
<Technical>

- **Tolerating unreliable tests.** Tests should be reliable: when the tests pass, you should be confident that the software is releasable, and a test failure should indicate a real defect <Cite n={4} />. In particular, don't tolerate flaky tests <Cite n={4} />.
- **A big suite that nobody trusts.** Ten tests that are reliable, fast, and trustworthy are much better than hundreds of tests that are hard to maintain and that nobody trusts <Cite n={4} />. If a suite is expensive to maintain and unreliable, don't be afraid to prune it <Cite n={4} />.
- **Manual regression as the only gate.** Manual regression testing is time-consuming and expensive, which makes it a bottleneck <Cite n={4} />. People are poor at repetitive tasks like manual regression tests <Cite n={4} />.
- **UI tests that break on every UI change.** Use the page object pattern to decouple your tests from the system under test <Cite n={4} />.
- **The wrong mix of tests.** Having the wrong proportion of unit and acceptance tests is a common pitfall <Cite n={4} />. A design goal of an automated test suite is to find errors as early as possible <Cite n={4} />.
- **Copying production data for tests.** Copying production data introduces risk, because it might contain sensitive information <Cite n={5} />. A full copy of the production database, instead of the relevant parts, is a common pitfall <Cite n={5} />.
- **Making a metric the goal.** A broad goal such as "every application must deploy multiple times per day by year's end" makes it more likely that teams game the metrics <Cite n={3} />.
- **Comparing very different applications.** Comparing the metrics of, for example, a mobile app and a mainframe system can be misleading <Cite n={3} />.

</Technical>
<Layman>

- **Living with unreliable tests.** Tests should be reliable. When the tests pass, you should trust that the software is ready to release. When a test fails, it should mean a real bug <Cite n={4} />. In particular, do not live with flaky tests <Cite n={4} />.
- **A big set of tests that nobody trusts.** Ten tests that are reliable, fast, and trusted are much better than hundreds that are hard to keep up and that nobody trusts <Cite n={4} />. If a set of tests costs a lot to keep up and is not reliable, do not be afraid to cut it down <Cite n={4} />.

- **metric-কেই লক্ষ্য বানানো।** "বছর শেষে প্রতিটা application-কে দিনে কয়েকবার deploy করতে হবে"-এর মতো বড় লক্ষ্য দিলে টিমগুলো metric নিয়ে কারসাজি করার সম্ভাবনা বাড়ে <Cite n={3} />।
- **খুব আলাদা application-এর তুলনা।** যেমন একটা mobile app আর একটা mainframe system-এর metric তুলনা করলে ভুল ধারণা হতে পারে <Cite n={3} />।

## Key words

| Term | Meaning |
|---|---|
| DevOps | Cultural philosophies, practices, and tools that help an organization deliver applications and services at high velocity |
| Siloed roles | Roles such as development, IT operations, quality engineering, and security, which DevOps brings together |
| DevSecOps | DevOps where security is the focus of everyone on the team |
| Continuous integration | Developers regularly merge changes into a central repository, and automated builds and tests run |
| Continuous delivery | Code changes are automatically built, tested, and prepared for a release to production |
| Infrastructure as code | Infrastructure provisioned and managed with code |
| Configuration management | Managing the state of servers, virtual machines, databases, and other resources |
| Continuous monitoring | Real-time visibility into the performance and health of the application stack |
| DORA | A research program on software delivery, led by researchers at Google |
| Throughput | How many changes can move through the system over a period of time |
| Instability | How well the deployments go |
| Change lead time | Time from commit to deployed in production |
| Deployment frequency | Deployments over a period, or the time between them |
| Change fail rate | The ratio of deployments that require immediate intervention |
| Deployment rework rate | The ratio of unplanned deployments caused by an incident in production |
| Failed deployment recovery time | Time to recover from a failed deployment |
| Shift left | Moving testing tasks earlier in the pipeline |
| Flaky test | An unreliable test; DORA's advice is not to tolerate flaky tests |
| Test data | The data that manual and automated tests need |
