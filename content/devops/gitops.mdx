# GitOps

This page explains GitOps for a tester: the four OpenGitOps principles, how Argo CD and Flux keep a cluster in line with a Git repository, what that means for the version that you test and for changes made by hand, and where smoke tests fit. It builds on [CI/CD Pipelines](/devops/ci-cd/); the Kubernetes pages of this module explain the cluster side.

<PageMeta />

## What it is

<Voices>
<Technical>

OpenGitOps is a set of open-source standards, best practices, and community-focused education that helps organizations adopt a structured, standardized approach to implementing GitOps <Cite n={1} />. Flux describes GitOps as a way of managing infrastructure and applications so that the whole system is described declaratively and version controlled, with an automated process that makes the deployed environment match the state in one or more Git repositories <Cite n={4} />.

**The four principles.** OpenGitOps names four principles <Cite n={1} />:

| Principle | What it says |
|---|---|
| Declarative | A system managed by GitOps must have its desired state expressed declaratively <Cite n={1} /> |
| Versioned and Immutable | Desired state is stored in a way that enforces immutability, versioning and retains a complete version history <Cite n={1} /> |
| Pulled Automatically | Software agents automatically pull the desired state declarations from the source <Cite n={1} /> |
| Continuously Reconciled | Software agents continuously observe actual system state and attempt to apply the desired state <Cite n={1} /> |

**Two tools.** Two GitOps tools for Kubernetes are Argo CD, a declarative, GitOps continuous delivery tool <Cite n={2} />, and Flux, a tool for keeping Kubernetes clusters in sync with sources of configuration (like Git repositories) <Cite n={3} />.

</Technical>

## How it works

<Voices>
<Technical>

**The loop.** Argo CD uses Git repositories as the source of truth for the desired application state <Cite n={2} />. It is a Kubernetes controller that continuously monitors running applications and compares the live state with the desired target state in the Git repository <Cite n={2} />. An application whose live state deviates from the target state is **OutOfSync** <Cite n={2} />. Argo CD reports and visualizes the differences, and it can sync the live state back to the desired state automatically or manually <Cite n={2} />.

**No push to the cluster.** With automated sync, CI/CD pipelines no longer need direct access to the Argo CD API server to deploy <Cite n={6} />. Instead, the pipeline commits and pushes the changed manifests to the Git repository that Argo CD tracks <Cite n={6} />.

Flux, too, keeps Kubernetes clusters in sync with sources of configuration, like Git repositories <Cite n={3} />. Here is the whole loop of Argo CD <Cite n={2} />, with a pipeline that pushes to Git <Cite n={6} />:

```text
you or a CI pipeline --- commit and push --->  Git repository  (desired state)
                                                     ^
                                                     |  watch and compare
                                         Argo CD, in the cluster
                                                     |
                                                     v  sync when OutOfSync
                                              Kubernetes cluster  (live state)
```

**Three settings that matter.**

| Setting | Default | What it does |
|---|---|---|
| Automated sync | Off: a new application shows `Sync Policy: <none>` <Cite n={5} />. Turn it on with `argocd app set <APPNAME> --sync-policy automated` <Cite n={6} /> | Syncs an application when Argo CD detects differences between the manifests in Git and the live state <Cite n={6} /> |
| Self-heal | Off | Starts an automated sync when the live cluster's state deviates from the state in Git. Without it, changes made to the live cluster do not trigger an automated sync <Cite n={6} /> |
| Prune | Off | Deletes resources that are no longer defined in Git. By default, as a safety mechanism, automated sync does not delete them <Cite n={6} /> |

**Hooks.** Sync phases and hooks decide when resources are applied, such as before or after the main sync operation <Cite n={7} />. The `argocd.argoproj.io/hook` annotation assigns a resource to a phase <Cite n={7} />:

| Hook | When it runs |
|---|---|
| `PreSync` | Before the manifests are applied <Cite n={7} /> |
| `Sync` | After all `PreSync` hooks succeeded, at the same time as the manifests are applied <Cite n={7} /> |
| `PostSync` | After all `Sync` hooks succeeded, the application succeeded, and all resources are Healthy <Cite n={7} /> |
| `SyncFail` | When the sync operation fails <Cite n={7} /> |

Hooks can be any kind of Kubernetes resource, but they tend to be a Pod, a Job, or an Argo Workflow <Cite n={7} />.

**Flux.** In Flux, a **Source** defines where the repository with the desired state is, and how to get it, such as credentials and version selectors <Cite n={4} />. Examples are `GitRepository`, `OCIRepository`, `HelmRepository`, and `Bucket` <Cite n={4} />. A **Kustomization** is a set of Kubernetes resources that Flux reconciles in the cluster <Cite n={4} />. **Reconciliation** means making sure that a given state matches a desired state that is declared somewhere, such as a Git repository <Cite n={4} />.

</Technical>

**চক্রটা।** Argo CD Git repository-কে application-এর desired state-এর source of truth হিসেবে ব্যবহার করে <Cite n={2} />। এটা একটা Kubernetes controller, যেটা চলমান application-গুলো ক্রমাগত দেখে আর live state-কে Git repository-তে লেখা desired target state-এর সাথে তুলনা করে <Cite n={2} />। যে application-এর live state target state থেকে সরে যায়, সেটা **OutOfSync** <Cite n={2} />। Argo CD পার্থক্যগুলো রিপোর্ট করে ও দেখায়, আর live state-কে automatically বা manually আবার desired state-এ sync করতে পারে <Cite n={2} />।

**cluster-এ push নয়।** automated sync থাকলে deploy করার জন্য CI/CD pipeline-এর Argo CD API server-এ সরাসরি access লাগে না <Cite n={6} />। তার বদলে pipeline বদলানো manifest Argo CD যে Git repository track করে সেখানে commit আর push করে <Cite n={6} />।

Flux-ও Kubernetes cluster-কে configuration-এর source-এর (যেমন Git repository) সাথে sync-এ রাখে <Cite n={3} />। এই হলো Argo CD-র পুরো চক্র <Cite n={2} />, Git-এ push করা একটা pipeline-সহ <Cite n={6} />:

```text
you or a CI pipeline --- commit and push --->  Git repository  (desired state)
                                                     ^
                                                     |  watch and compare
                                         Argo CD, in the cluster
                                                     |
                                                     v  sync when OutOfSync
                                              Kubernetes cluster  (live state)
```

**তিনটা গুরুত্বপূর্ণ setting।**

| Setting | Default | কী করে |
|---|---|---|
| Automated sync | বন্ধ: নতুন application-এ `Sync Policy: <none>` দেখায় <Cite n={5} />। চালু করতে `argocd app set <APPNAME> --sync-policy automated` <Cite n={6} /> | Git-এর manifest আর live state-এ পার্থক্য পেলে Argo CD application sync করে <Cite n={6} /> |
| Self-heal | বন্ধ | live cluster-এর state Git-এর state থেকে সরে গেলে automated sync শুরু করে। এটা না থাকলে live cluster-এ করা change automated sync চালু করে না <Cite n={6} /> |
| Prune | বন্ধ | Git-এ আর নেই এমন resource মুছে দেয়। default-ভাবে, নিরাপত্তার জন্য, automated sync এগুলো মোছে না <Cite n={6} /> |

**Hook।** sync phase আর hook ঠিক করে resource কখন apply হবে, যেমন মূল sync-এর আগে বা পরে <Cite n={7} />। `argocd.argoproj.io/hook` annotation একটা resource-কে একটা phase-এ রাখে <Cite n={7} />:

| Hook | কখন চলে |
|---|---|
| `PreSync` | manifest apply হওয়ার আগে <Cite n={7} /> |
| `Sync` | সব `PreSync` hook সফল হওয়ার পর, manifest apply হওয়ার সাথে একই সময়ে <Cite n={7} /> |
| `PostSync` | সব `Sync` hook সফল হওয়ার পর, application সফল হলে, আর সব resource Healthy হলে <Cite n={7} /> |
| `SyncFail` | sync operation ফেল করলে <Cite n={7} /> |

hook যেকোনো ধরনের Kubernetes resource হতে পারে, তবে সাধারণত Pod, Job বা Argo Workflow হয় <Cite n={7} />।

**Flux।** Flux-এ **Source** বলে desired state-ওয়ালা repository কোথায়, আর সেটা পেতে কী লাগে, যেমন credential আর version selector <Cite n={4} />। উদাহরণ: `GitRepository`, `OCIRepository`, `HelmRepository` আর `Bucket` <Cite n={4} />। **Kustomization** হলো Kubernetes resource-এর একটা সেট, যেটা Flux cluster-এ reconcile করে <Cite n={4} />। **Reconciliation** মানে নিশ্চিত করা যে একটা state কোথাও (যেমন একটা Git repository-তে) declaratively লেখা desired state-এর সাথে মেলে <Cite n={4} />।

## Try it

<Voices>
<Technical>

This walk-through follows the Argo CD Getting Started guide <Cite n={5} />. It needs a Kubernetes cluster. On a local computer, kind or minikube can run one <Cite n={8} />; kind requires Docker or Podman <Cite n={8} />. You also need the `kubectl` command-line tool and a kubeconfig file (by default `~/.kube/config`) <Cite n={5} />. If you cannot run a cluster yet, read along.

**1. Install Argo CD.** This creates the `argocd` namespace, where all the Argo CD services and application resources live <Cite n={5} />:

```bash
kubectl create namespace argocd
kubectl apply -n argocd --server-side --force-conflicts -f https://raw.githubusercontent.com/argoproj/argo-cd/stable/manifests/install.yaml
```

**2. Install the CLI.** Download the latest version from the Argo CD releases on GitHub, or use Homebrew <Cite n={5} />:

```bash
brew install argocd
```

**3. Log in.** Set the default namespace of `kubectl` to `argocd`, then use `argocd login --core` <Cite n={5} />:

```bash
kubectl config set-context --current --namespace=argocd
argocd login --core
```

**4. Create an application from a Git repository.** Argo CD's example repository has a guestbook application <Cite n={5} />:

```bash
argocd app create guestbook --repo https://github.com/argoproj/argocd-example-apps.git --path guestbook --dest-server https://kubernetes.default.svc --dest-namespace default
argocd app get guestbook
```

The application starts as **OutOfSync**, because it is not deployed yet and no Kubernetes resources were created <Cite n={5} />.

**5. Sync it.** `argocd app sync guestbook` gets the manifests from the repository and runs a `kubectl apply` of them <Cite n={5} />. Then you can see the application's resources, logs, events, and health status <Cite n={5} />.

```bash
argocd app sync guestbook
argocd app get guestbook
```

**6. Optional: open the web UI.** `kubectl port-forward` connects to the API server without exposing the service, and the API server can then be accessed at `https://localhost:8080` <Cite n={5} />. To use the UI, open that address in a browser and log in <Cite n={5} />. The initial password of the `admin` user is shown by `argocd admin initial-password -n argocd` <Cite n={5} />. The default installation has a self-signed certificate <Cite n={5} />.

```bash
kubectl port-forward svc/argocd-server -n argocd 8080:443
argocd admin initial-password -n argocd
```

</Technical>


**৪. একটা Git repository থেকে application বানান।** Argo CD-র উদাহরণ repository-তে একটা guestbook application আছে <Cite n={5} />:

```bash
argocd app create guestbook --repo https://github.com/argoproj/argocd-example-apps.git --path guestbook --dest-server https://kubernetes.default.svc --dest-namespace default
argocd app get guestbook
```

application শুরুতে **OutOfSync** থাকে, কারণ এটা এখনো deploy হয়নি আর কোনো Kubernetes resource তৈরি হয়নি <Cite n={5} />।

**৫. sync করুন।** `argocd app sync guestbook` repository থেকে manifest এনে সেগুলোর `kubectl apply` চালায় <Cite n={5} />। তারপর application-এর resource, log, event আর health status দেখা যায় <Cite n={5} />।

```bash
argocd app sync guestbook
argocd app get guestbook
```

**৬. চাইলে web UI খুলুন।** `kubectl port-forward` service বাইরে না খুলেই API server-এ যুক্ত করে, আর তখন API server পাওয়া যায় `https://localhost:8080`-এ <Cite n={5} />। UI ব্যবহার করতে browser-এ ওই address খুলে login করুন <Cite n={5} />। `admin` user-এর প্রথম password দেখায় `argocd admin initial-password -n argocd` <Cite n={5} />। default installation-এ একটা self-signed certificate থাকে <Cite n={5} />।

```bash
kubectl port-forward svc/argocd-server -n argocd 8080:443
argocd admin initial-password -n argocd
```

## How a tester uses it

<Voices>
<Technical>

**Run smoke tests after each sync.** You can run smoke tests as `PostSync` hooks <Cite n={7} />. If they succeed, you know that the application passed the validation; if they fail, the whole deployment is marked as failed, and Argo CD can notify you <Cite n={7} />. In the same way, an essential check can run as a `PreSync` hook: if it fails, the whole sync stops, and the deployment does not happen <Cite n={7} />.

Hooks tend to be a Pod, a Job, or an Argo Workflow <Cite n={7} />. This Job has the shape of the Argo CD example; the image and the command are placeholders for your own test runner. With `hook-delete-policy: HookSucceeded`, the hook resource is deleted when the sync succeeds <Cite n={7} />.

```yaml
apiVersion: batch/v1
kind: Job
metadata:
  generateName: smoke-test-
  annotations:
    argocd.argoproj.io/hook: PostSync
    argocd.argoproj.io/hook-delete-policy: HookSucceeded
spec:
  template:
    spec:
      containers:
        - name: smoke-test
          image: <your-test-image>
          command: ["<your-smoke-test-command>"]
      restartPolicy: Never
  backoffLimit: 2
```

**Know what is deployed.** Git is the source of truth for the desired state <Cite n={2} />. The feature list of Argo CD includes audit trails for application events and API calls <Cite n={2} />. It can roll back to any application configuration that is committed in the Git repository <Cite n={2} />.

**See drift.** Argo CD detects and shows configuration drift automatically <Cite n={2} />. If a test environment does not match Git, it is OutOfSync <Cite n={2} />.

**Treat a change to an environment like code.** Desired state is stored in a way that enforces immutability and versioning, and it keeps a complete version history <Cite n={1} />. The tutorial's advice: review a change to the desired state of a test environment the way you review code.

## Common mistakes

<Voices>
<Technical>

- **Changing a test environment by hand.** With self-heal, Argo CD syncs the cluster back when its state deviates from Git <Cite n={6} />. Without self-heal, such a change does not trigger a sync <Cite n={6} />, and the application shows as OutOfSync <Cite n={2} />. Change the Git repository instead.
- **Expecting deleted manifests to disappear.** By default, automated sync does not delete resources that are no longer defined in Git <Cite n={6} />. A manual sync with pruning can always delete them <Cite n={6} />.
- **Waiting for a retry of a failed sync.** Automated sync tries once for each combination of commit and application parameters, and it does not try again when the last attempt against the same commit and parameters failed <Cite n={6} />. Push the fix as a new commit, or set a retry policy: Argo CD can retry a failed sync with exponential backoff <Cite n={6} />.
- **Planning a rollback with automated sync on.** Rollback cannot be performed against an application with automated sync enabled <Cite n={6} />.
- **Expecting hooks in a selective sync.** Hooks do not run during a selective sync operation <Cite n={7} />.
- **Leaving the initial admin secret.** Delete the `argocd-initial-admin-secret` from the Argo CD namespace once you have changed the password <Cite n={5} />.

</Technical>
<Layman>

- **Changing a test environment by hand.** With self-heal, Argo CD changes the cluster back when it no longer matches Git <Cite n={6} />. Without self-heal, such a change does not trigger a sync <Cite n={6} />, and the application shows as OutOfSync <Cite n={2} />. Change the Git repository instead.
- **Expecting deleted files to make things disappear.** By default, automated sync does not delete things that are no longer in Git <Cite n={6} />. A manual sync with pruning can always delete them <Cite n={6} />.
- **Waiting for a failed sync to try again.** Automated sync tries once for each commit and set of application parameters. It does not try again when the last try with the same commit and parameters failed <Cite n={6} />. Push the fix as a new commit, or set a retry policy: Argo CD can retry a failed sync, and wait longer each time <Cite n={6} />.
- **Planning a rollback with automated sync on.** You cannot roll back an application while automated sync is on <Cite n={6} />.
- **Expecting hooks in a selective sync.** Hooks do not run during a selective sync <Cite n={7} />.
- **Leaving the first admin password secret.** Delete the `argocd-initial-admin-secret` from the Argo CD namespace after you change the password <Cite n={5} />.

</Layman>
<Bangla>

- **হাতে test environment বদলানো।** self-heal থাকলে cluster-এর state Git থেকে সরে গেলে Argo CD আবার sync করে ফিরিয়ে আনে <Cite n={6} />। self-heal না থাকলে এমন change sync চালু করে না <Cite n={6} />, আর application OutOfSync দেখায় <Cite n={2} />। তার বদলে Git repository বদলান।
- **মুছে ফেলা manifest-এর জিনিস চলে যাবে ভাবা।** default-ভাবে automated sync Git-এ আর নেই এমন resource মোছে না <Cite n={6} />। pruning-সহ একটা manual sync সবসময় এগুলো মুছতে পারে <Cite n={6} />।
- **ফেল করা sync আবার চেষ্টা হবে ভেবে অপেক্ষা করা।** automated sync প্রতিটা commit আর application parameter-এর জোড়ার জন্য একবার চেষ্টা করে, আর একই commit ও parameter-এ আগের চেষ্টা ফেল করলে আবার চেষ্টা করে না <Cite n={6} />। fix-টা নতুন commit হিসেবে push করুন, অথবা একটা retry policy দিন: Argo CD exponential backoff দিয়ে ফেল করা sync আবার চেষ্টা করতে পারে <Cite n={6} />।
- **automated sync চালু রেখে rollback-এর পরিকল্পনা।** automated sync চালু থাকা application-এ rollback করা যায় না <Cite n={6} />।
- **selective sync-এ hook আশা করা।** selective sync operation-এ hook চলে না <Cite n={7} />।
- **initial admin secret রেখে দেওয়া।** password বদলানোর পর Argo CD namespace থেকে `argocd-initial-admin-secret` মুছে দিন <Cite n={5} />।

## Key words

| Term | Meaning |
|---|---|
| GitOps | Managing a system that is described declaratively and version controlled, with an automated process that makes it match Git |
| Desired state | What the system should be, as declared in the source, such as Git |
| Live state | The state of the running application, which Argo CD compares with the desired target state |
| Reconciliation | Making sure that a given state matches the declared desired state |
| OutOfSync | The live state deviates from the target state in Git |
| Sync | Making the live state match the desired state |
| Automated sync | Argo CD syncs by itself when Git and the cluster differ |
| Self-heal | Starting an automated sync when the live cluster deviates from Git |
| Prune | Deleting resources that are no longer defined in Git |
| Hook | A resource that runs in a sync phase: `PreSync`, `Sync`, `PostSync`, or `SyncFail` |
| Argo CD | A declarative, GitOps continuous delivery tool for Kubernetes |
| Flux | A tool that keeps Kubernetes clusters in sync with sources of configuration |
| Source (Flux) | Where the desired state is, and how to get it |
| Kustomization (Flux) | A set of Kubernetes resources that Flux reconciles |
