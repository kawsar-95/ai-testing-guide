# Monitoring and Observability

This page covers monitoring and observability: the three signals (metrics, logs, and traces), Prometheus and its rules, Alertmanager, Loki, and the trace context that OpenTelemetry passes between services. The practice run starts a small web app and the tools on your own machine. It needs no cloud account and no Docker. It comes after [Ansible](/devops/ansible/) and before [CNCF Projects: Build and Deliver](/devops/cncf-build-deliver/).

## What it is

<Voices>
<Technical>

**Observability.** Observability lets you understand a system from the outside by letting you ask questions about that system without knowing its inner workings <Cite n={1} />. To ask those questions about your system, your application must be properly instrumented <Cite n={1} />. That is, the application code must emit signals such as traces, metrics, and logs <Cite n={1} />. Telemetry refers to data emitted from a system and its behavior <Cite n={1} />. OpenTelemetry is the mechanism by which application code is instrumented to help make a system observable <Cite n={1} />.

**Monitoring.** The Google SRE book describes monitoring as collecting, processing, aggregating, and displaying real-time quantitative data about a system, such as query counts and types, error counts and types, processing times, and server lifetimes <Cite n={7} />. White-box monitoring is based on metrics exposed by the internals of the system <Cite n={7} />. Black-box monitoring is testing externally visible behavior as a user would see it <Cite n={7} />.

**The three signals.** Metrics are aggregations over a period of time of numeric data about your infrastructure or application <Cite n={1} />. A log is a timestamped message emitted by services or other components <Cite n={1} />. A span represents a single unit of work or operation <Cite n={1} />. A trace is made of one or more spans <Cite n={1} />. The first span represents the root span <Cite n={1} />. A distributed trace records the path taken by a single request as it propagates through multiple services in an architecture <Cite n={1} />.

**The tools of this page.** Prometheus is an open-source systems monitoring and alerting toolkit <Cite n={8} />. It collects and stores its metrics as time series data <Cite n={8} />. The Alertmanager handles alerts sent by client applications such as the Prometheus server <Cite n={23} />. Loki is a horizontally-scalable, highly-available, multi-tenant log aggregation system inspired by Prometheus <Cite n={31} />. Unlike other logging systems, Loki does not index the contents of the logs <Cite n={31} />. OpenTelemetry is open source, and vendor- and tool-agnostic <Cite n={2} />. It is not an observability backend itself <Cite n={2} />.

## How it works

<Voices>
<Technical>

**The pieces of Prometheus.** The Prometheus ecosystem consists of multiple components, many of which are optional <Cite n={8} />. The main Prometheus server scrapes and stores time series data <Cite n={8} />. Client libraries instrument application code <Cite n={8} />. An alertmanager handles alerts <Cite n={8} />. Prometheus scrapes metrics from instrumented jobs <Cite n={8} />. It stores all scraped samples locally and runs rules over this data to either aggregate and record new time series from existing data or generate alerts <Cite n={8} />. Grafana or other API consumers can be used to visualize the collected data <Cite n={8} />. Time series collection happens via a pull model over HTTP <Cite n={8} />.

**The data model.** Prometheus stores its data as time series <Cite n={8} />. Every time series is uniquely identified by its metric name and optional key-value pairs called labels <Cite n={9} />. Besides stored time series, Prometheus may generate temporary derived time series as the result of queries <Cite n={9} />.

**Jobs, instances, and `up`.** In Prometheus terms, an endpoint you can scrape is called an instance, usually corresponding to a single process <Cite n={11} />. A collection of instances with the same purpose is called a job <Cite n={11} />. When Prometheus scrapes a target, it attaches some labels automatically to the scraped time series <Cite n={11} />. The `job` label holds the configured job name that the target belongs to <Cite n={11} />. The `instance` label holds the host and port part of the target's URL that was scraped <Cite n={11} />. For each instance scrape, Prometheus stores a sample in the `up` series <Cite n={11} />. Its value is 1 if the instance is healthy, that is, reachable, or 0 if the scrape failed <Cite n={11} />. The `up` series is useful for instance availability monitoring <Cite n={11} />.

**Metric types.** The Prometheus instrumentation libraries offer four core metric types <Cite n={10} />. A counter is a cumulative metric that represents a single monotonically increasing counter whose value can only increase or be reset to zero on restart <Cite n={10} />. Do not use a counter to expose a value that can decrease <Cite n={10} />. A gauge is a metric that represents a single numerical value that can arbitrarily go up and down <Cite n={10} />. A histogram records observations by counting them in configurable buckets <Cite n={10} />. It also provides a sum of all observed values <Cite n={10} />. A classic histogram consists of multiple time series of simple float samples <Cite n={10} />. They are the cumulative bucket counters, the sum, and the count <Cite n={10} />. Similar to a histogram, a summary samples observations <Cite n={10} />.

**Histogram or summary.** Summaries calculate streaming φ-quantiles within the instrumented program and expose them directly <Cite n={20} />. Histograms expose bucketed observation counts, and the calculation of quantiles happens on the Prometheus server using the `histogram_quantile()` function <Cite n={20} />. For a summary, other φ-quantiles and sliding windows cannot be calculated later <Cite n={20} />.

**Names and labels.** Metric names should have a single-word application prefix <Cite n={18} />. They should have a suffix that describes the unit, in plural form <Cite n={18} />. Every unique combination of key-value label pairs represents a new time series, which can dramatically increase the amount of data stored <Cite n={18} />. Do not use labels to store dimensions with high cardinality, such as user IDs, email addresses, or other unbounded sets of values <Cite n={18} />.

**Instrumentation.** For monitoring purposes, services can generally be broken down into three types: online-serving, offline-processing, and batch jobs <Cite n={19} />. Online-serving systems should be monitored on both the client and server side <Cite n={19} />. If the two sides see different behaviors, that is very useful information for debugging <Cite n={19} />. Time series that are not present until something happens are difficult to deal with <Cite n={19} />. To avoid this, export a default value such as 0 for any time series you know may exist in advance <Cite n={19} />.

**The text format.** As of Prometheus version 2.0, all processes that expose metrics to Prometheus must use a text format, by default <Cite n={17} />. Lines with a # as the first non-whitespace character are comments <Cite n={17} />. They are ignored unless the first token after # is either HELP or TYPE <Cite n={17} />. If the token is TYPE, exactly two more tokens are expected <Cite n={17} />. The first is the metric name, and the second is either counter, gauge, histogram, summary, or untyped <Cite n={17} />. The remaining lines describe samples, one per line <Cite n={17} />.

**PromQL.** Prometheus provides a functional query language called PromQL that lets the user select and aggregate time series data in real time <Cite n={12} />. A query request can be an instant query, evaluated at one point in time, or a range query at equally-spaced steps between a start and an end time <Cite n={12} />. An instant vector is a set of time series containing a single sample for each time series, all sharing the same timestamp <Cite n={12} />. A range vector is a set of time series containing a range of data points over time for each time series <Cite n={12} />. Instant vector selectors allow the selection of a set of time series and a single sample value for each at a given timestamp <Cite n={12} />. You can filter the series further with a comma-separated list of label matchers in curly braces <Cite n={12} />. By convention, time series that contain float counters have a name ending in `_total` <Cite n={12} />. Between an instant vector and a scalar, a comparison operator is applied to every sample, and the elements for which the comparison is false get dropped from the result <Cite n={40} />.

**`rate`, aggregation, and quantiles.** `rate(v range-vector)` calculates the per-second average rate of increase of the time series in the range vector <Cite n={13} />. Breaks in monotonicity, such as counter resets due to target restarts, are automatically adjusted for <Cite n={13} />. The `rate` function should only be used with counters <Cite n={13} />. Applying it to gauge floats will most likely produce a nonsensical result, but the query will be processed without complaints <Cite n={12} />. When you combine `rate()` with an aggregation operator such as `sum()`, always take a `rate()` first, then aggregate <Cite n={13} />. Otherwise `rate()` cannot detect counter resets when your target restarts <Cite n={13} />. `histogram_quantile(φ scalar, b instant-vector)` calculates the φ-quantile from a classic histogram or from a native histogram <Cite n={13} />. The page says to use the `rate()` function to specify the time window for the quantile calculation <Cite n={13} />. For classic histograms, the `le` label has to be included in the `by` clause <Cite n={13} />.

**Recording rules and alerting rules.** Recording rules allow you to precompute frequently needed or computationally expensive expressions and save their result as a new set of time series <Cite n={14} />. Recording and alerting rules exist in a rule group <Cite n={14} />. Rules within a group are run sequentially at a regular interval, with the same evaluation time <Cite n={14} />. The names of recording rules must be valid metric names <Cite n={14} />. For an alerting rule, all resultant time series of the expression become pending or firing alerts <Cite n={14} />. Alerts are considered firing once they have been returned for this long <Cite n={14} />. Alerts which have not yet fired for long enough are considered pending <Cite n={14} />. The labels clause allows specifying a set of additional labels to be attached to the alert <Cite n={15} />. The annotations clause specifies a set of informational labels that can be used to store longer additional information such as alert descriptions or runbook links <Cite n={15} />. For pending and firing alerts, Prometheus also stores synthetic time series of the form `ALERTS` <Cite n={15} />. Prometheus's alerting rules are good at figuring what is broken right now, but they are not a fully-fledged notification solution <Cite n={15} />.

**Alertmanager.** Alerting with Prometheus is separated into two parts <Cite n={22} />. Alerting rules in Prometheus servers send alerts to an Alertmanager <Cite n={22} />. The Alertmanager takes care of deduplicating, grouping, and routing them to the correct receiver integration <Cite n={23} />. Grouping categorizes alerts of similar nature into a single notification <Cite n={23} />. Inhibition is a concept of suppressing notifications for certain alerts if certain other alerts are already firing <Cite n={23} />. Silences are a straightforward way to simply mute alerts for a given time <Cite n={23} />. A silence is configured based on matchers, just like the routing tree <Cite n={23} />. Every alert enters the routing tree at the configured top-level route, which must match all alerts <Cite n={24} />. It then traverses the child nodes <Cite n={24} />. If `continue` is set to false, it stops after the first matching child <Cite n={24} />. If an alert does not match any children of a node, the alert is handled based on the configuration parameters of the current node <Cite n={24} />. Most optional parameters of a route are inherited from its parent node if not set <Cite n={24} />. The `amtool` command is a cli tool for interacting with the Alertmanager API <Cite n={25} />. It is bundled with all releases of Alertmanager <Cite n={25} />. The configuration page says that you can use `amtool` to validate that a configuration file is compatible with UTF-8 strict mode before enabling it in the server <Cite n={24} />. For that check, you do not need a running Alertmanager server <Cite n={24} />.

**What to alert on.** Aim to have as few alerts as possible, by alerting on symptoms that are associated with end-user pain rather than trying to catch every possible way that pain could be caused <Cite n={21} />. To summarize: keep alerting simple, alert on symptoms, have good consoles to allow pinpointing causes, and avoid having pages where there is nothing to do <Cite n={21} />. For error rates, page on user-visible errors <Cite n={21} />. The Google SRE book says that the four golden signals of monitoring are latency, traffic, errors, and saturation <Cite n={7} />. If you can only measure four metrics of your user-facing system, focus on these four <Cite n={7} />. Errors are the rate of requests that fail, either explicitly, implicitly, or by policy <Cite n={7} />. It is important to distinguish between the latency of successful requests and the latency of failed requests <Cite n={7} />.

**Loki and its labels.** Loki differs from Prometheus by focusing on logs instead of metrics, and collecting logs via push, instead of pull <Cite n={31} />. **The pieces of Prometheus.** The Prometheus ecosystem consists of multiple components, many of which are optional <Cite n={8} />. The main Prometheus server scrapes and stores time series data <Cite n={8} />. Client libraries instrument application code <Cite n={8} />. An alertmanager handles alerts <Cite n={8} />. Prometheus scrapes metrics from instrumented jobs <Cite n={8} />. It stores all scraped samples locally and runs rules over this data to either aggregate and record new time series from existing data or generate alerts <Cite n={8} />. Grafana or other API consumers can be used to visualize the collected data <Cite n={8} />. Time series collection happens via a pull model over HTTP <Cite n={8} />.

**The data model.** Prometheus stores its data as time series <Cite n={8} />. Every time series is uniquely identified by its metric name and optional key-value pairs called labels <Cite n={9} />. Besides stored time series, Prometheus may generate temporary derived time series as the result of queries <Cite n={9} />.

**Jobs, instances, and `up`.** In Prometheus terms, an endpoint you can scrape is called an instance, usually corresponding to a single process <Cite n={11} />. A collection of instances with the same purpose is called a job <Cite n={11} />. When Prometheus scrapes a target, it attaches some labels automatically to the scraped time series <Cite n={11} />. The `job` label holds the configured job name that the target belongs to <Cite n={11} />. The `instance` label holds the host and port part of the target's URL that was scraped <Cite n={11} />. For each instance scrape, Prometheus stores a sample in the `up` series <Cite n={11} />. Its value is 1 if the instance is healthy, that is, reachable, or 0 if the scrape failed <Cite n={11} />. The `up` series is useful for instance availability monitoring <Cite n={11} />.

**Metric types.** The Prometheus instrumentation libraries offer four core metric types <Cite n={10} />. A counter is a cumulative metric that represents a single monotonically increasing counter whose value can only increase or be reset to zero on restart <Cite n={10} />. Do not use a counter to expose a value that can decrease <Cite n={10} />. A gauge is a metric that represents a single numerical value that can arbitrarily go up and down <Cite n={10} />. A histogram records observations by counting them in configurable buckets <Cite n={10} />. It also provides a sum of all observed values <Cite n={10} />. A classic histogram consists of multiple time series of simple float samples <Cite n={10} />. They are the cumulative bucket counters, the sum, and the count <Cite n={10} />. Similar to a histogram, a summary samples observations <Cite n={10} />.

**Histogram or summary.** Summaries calculate streaming φ-quantiles within the instrumented program and expose them directly <Cite n={20} />. Histograms expose bucketed observation counts, and the calculation of quantiles happens on the Prometheus server using the `histogram_quantile()` function <Cite n={20} />. For a summary, other φ-quantiles and sliding windows cannot be calculated later <Cite n={20} />.

**Names and labels.** Metric names should have a single-word application prefix <Cite n={18} />. They should have a suffix that describes the unit, in plural form <Cite n={18} />. Every unique combination of key-value label pairs represents a new time series, which can dramatically increase the amount of data stored <Cite n={18} />. Do not use labels to store dimensions with high cardinality, such as user IDs, email addresses, or other unbounded sets of values <Cite n={18} />.

**Instrumentation.** For monitoring purposes, services can generally be broken down into three types: online-serving, offline-processing, and batch jobs <Cite n={19} />. Online-serving systems should be monitored on both the client and server side <Cite n={19} />. If the two sides see different behaviors, that is very useful information for debugging <Cite n={19} />. Time series that are not present until something happens are difficult to deal with <Cite n={19} />. To avoid this, export a default value such as 0 for any time series you know may exist in advance <Cite n={19} />.

**The text format.** As of Prometheus version 2.0, all processes that expose metrics to Prometheus must use a text format, by default <Cite n={17} />. Lines with a # as the first non-whitespace character are comments <Cite n={17} />. They are ignored unless the first token after # is either HELP or TYPE <Cite n={17} />. If the token is TYPE, exactly two more tokens are expected <Cite n={17} />. The first is the metric name, and the second is either counter, gauge, histogram, summary, or untyped <Cite n={17} />. The remaining lines describe samples, one per line <Cite n={17} />.

**PromQL.** Prometheus provides a functional query language called PromQL that lets the user select and aggregate time series data in real time <Cite n={12} />. A query request can be an instant query, evaluated at one point in time, or a range query at equally-spaced steps between a start and an end time <Cite n={12} />. An instant vector is a set of time series containing a single sample for each time series, all sharing the same timestamp <Cite n={12} />. A range vector is a set of time series containing a range of data points over time for each time series <Cite n={12} />. Instant vector selectors allow the selection of a set of time series and a single sample value for each at a given timestamp <Cite n={12} />. You can filter the series further with a comma-separated list of label matchers in curly braces <Cite n={12} />. By convention, time series that contain float counters have a name ending in `_total` <Cite n={12} />. **`rate`, aggregation, and quantiles.** `rate(v range-vector)` calculates the per-second average rate of increase of the time series in the range vector <Cite n={13} />. **Metric-এর ধরন।** Prometheus instrumentation library চারটা মূল metric type দেয় <Cite n={10} />। counter হলো একটা জমা হওয়া metric, যা একটাই একঘেয়েভাবে বাড়তে থাকা counter বোঝায়, যার মান শুধু বাড়তে পারে বা restart-এ শূন্যে ফিরতে পারে <Cite n={10} />। যে মান কমতে পারে, তা দেখাতে counter ব্যবহার করবেন না <Cite n={10} />। gauge হলো এমন metric, যা একটাই সংখ্যাগত মান বোঝায়, আর সেই মান ইচ্ছেমতো ওঠানামা করতে পারে <Cite n={10} />। histogram পর্যবেক্ষণ গোনে, সেগুলোকে বদলানো যায় এমন bucket-এ ফেলে <Cite n={10} />। সে পর্যবেক্ষণ করা সব মানের যোগফলও দেয় <Cite n={10} />। একটা classic histogram সরল float sample-এর একাধিক time series দিয়ে তৈরি <Cite n={10} />। সেগুলো হলো জমা হওয়া bucket counter, যোগফল আর গণনা <Cite n={10} />। histogram-এর মতোই, একটা summary পর্যবেক্ষণ নমুনা হিসেবে নেয় <Cite n={10} />।

**Histogram না summary।** summary instrumented program-এর ভেতরেই streaming φ-quantile হিসাব করে আর সরাসরি প্রকাশ করে <Cite n={20} />। histogram bucket করা পর্যবেক্ষণ-সংখ্যা প্রকাশ করে, আর quantile-এর হিসাব হয় Prometheus server-এ, `histogram_quantile()` function দিয়ে <Cite n={20} />। একটা summary-র ক্ষেত্রে অন্য φ-quantile আর sliding window পরে হিসাব করা যায় না <Cite n={20} />।

**Name আর label।** metric-এর নামে application-এর একটা এক-শব্দের prefix থাকা উচিত <Cite n={18} />। নামে একটা suffix থাকা উচিত, যা unit বর্ণনা করে, বহুবচনে <Cite n={18} />। key-value label জোড়ার প্রতিটা অনন্য সমন্বয় একটা নতুন time series বোঝায়, যা জমানো data-র পরিমাণ নাটকীয়ভাবে বাড়িয়ে দিতে পারে <Cite n={18} />। high cardinality-র dimension রাখতে label ব্যবহার করবেন না, যেমন user ID, email address, বা অন্য সীমাহীন মানের সেট <Cite n={18} />।

**Instrumentation।** monitoring-এর জন্য service-কে সাধারণত তিন ধরনে ভাগ করা যায়: online-serving, offline-processing আর batch job <Cite n={19} />। online-serving system-কে client আর server দুই দিকেই monitor করা উচিত <Cite n={19} />। দুই দিক আলাদা আচরণ দেখলে সেটা debugging-এর জন্য খুবই কাজের তথ্য <Cite n={19} />। যে time series কিছু ঘটার আগে থাকে না, তা সামলানো কঠিন <Cite n={19} />। এটা এড়াতে, যে time series আগে থেকেই থাকতে পারে বলে আপনি জানেন, তার জন্য 0-র মতো একটা default মান export করুন <Cite n={19} />।

**Text format।** Prometheus version 2.0 থেকে, Prometheus-এ metric প্রকাশ করা সব process-কে ডিফল্টভাবে একটা text format ব্যবহার করতেই হয় <Cite n={17} />। যে লাইনের প্রথম non-whitespace অক্ষর #, সে লাইন comment <Cite n={17} />। # -এর পরের প্রথম token HELP বা TYPE না হলে সেগুলো উপেক্ষা করা হয় <Cite n={17} />। token TYPE হলে ঠিক আরও দুটো token আশা করা হয় <Cite n={17} />। প্রথমটা metric-এর নাম, আর দ্বিতীয়টা counter, gauge, histogram, summary বা untyped-এর একটা <Cite n={17} />। বাকি লাইনগুলো sample বর্ণনা করে, প্রতি লাইনে একটা <Cite n={17} />।

**PromQL।** Prometheus একটা functional query language দেয়, যার নাম PromQL, আর যা ব্যবহারকারীকে real time-এ time series data বেছে নিতে ও একত্র করতে দেয় <Cite n={12} />। একটা query অনুরোধ হতে পারে instant query, যা একটা এক মুহূর্তে মূল্যায়ন হয়, বা range query, যা শুরু আর শেষ সময়ের মধ্যে সমান ব্যবধানের ধাপে চলে <Cite n={12} />। একটা instant vector হলো time series-এর একটা সেট, যাতে প্রতিটা time series-এ একটাই sample থাকে, আর সবার timestamp এক <Cite n={12} />। একটা range vector হলো time series-এর একটা সেট, যাতে প্রতিটা time series-এর জন্য সময় জুড়ে একটা data point-এর পরিসর থাকে <Cite n={12} />। Instant vector selector একটা নির্দিষ্ট timestamp-এ time series-এর একটা সেট আর প্রতিটার একটা sample মান বেছে নিতে দেয় <Cite n={12} />। আপনি curly brace-এর ভেতরে কমা দিয়ে আলাদা করা label matcher-এর একটা তালিকা জুড়ে series আরও ছেঁকে নিতে পারেন <Cite n={12} />। প্রচলিত রীতি অনুযায়ী, float counter ধরে রাখা time series-এর নাম `_total` দিয়ে শেষ হয় <Cite n={12} />। একটা instant vector আর একটা scalar-এর মধ্যে comparison operator প্রতিটা sample-এ প্রয়োগ হয়, আর যে element-এর তুলনার ফল false, সেগুলো result থেকে বাদ পড়ে <Cite n={40} />।

**`rate`, aggregation আর quantile।** `rate(v range-vector)` range vector-এর time series-এর প্রতি সেকেন্ডের গড় বৃদ্ধির হার হিসাব করে <Cite n={13} />। monotonicity-র ভাঙন, যেমন target restart-এর কারণে counter reset, নিজে থেকেই সমন্বয় করা হয় <Cite n={13} />। `rate` function শুধু counter-এর সঙ্গে ব্যবহার করা উচিত <Cite n={13} />। gauge float-এ এটা প্রয়োগ করলে খুব সম্ভব অর্থহীন ফল আসবে, কিন্তু query কোনো অভিযোগ ছাড়াই চলবে <Cite n={12} />। `rate()`-কে `sum()`-এর মতো aggregation operator-এর সঙ্গে মেলালে সবসময় আগে `rate()` নিন, তারপর aggregate করুন <Cite n={13} />। নইলে target restart হলে `rate()` counter reset ধরতে পারে না <Cite n={13} />। `histogram_quantile(φ scalar, b instant-vector)` একটা classic histogram বা native histogram থেকে φ-quantile হিসাব করে <Cite n={13} />। page বলে quantile হিসাবের সময়-জানালা ঠিক করতে `rate()` function ব্যবহার করতে <Cite n={13} />। classic histogram-এর ক্ষেত্রে `le` label-কে `by` clause-এ রাখতে হয় <Cite n={13} />।

**Recording rule আর alerting rule।** Recording rule আপনাকে প্রায়ই লাগে বা হিসাব করতে ভারী এমন expression আগে থেকে হিসাব করে তার ফল time series-এর একটা নতুন সেট হিসেবে রাখতে দেয় <Cite n={14} />। Recording আর alerting rule একটা rule group-এ থাকে <Cite n={14} />। একটা group-এর rule একই মূল্যায়ন-সময়ে, নিয়মিত ব্যবধানে, পরপর চলে <Cite n={14} />। recording rule-এর নাম অবশ্যই বৈধ metric name হতে হবে <Cite n={14} />। একটা alerting rule-এর expression-এর সব ফল time series pending বা firing alert হয়ে যায় <Cite n={14} />। alert firing ধরা হয়, একবার সেগুলো এই সময় ধরে ফেরত এলে <Cite n={14} />। যে alert এখনও যথেষ্ট সময় ধরে ফেরত আসেনি, সেগুলো pending ধরা হয় <Cite n={14} />। labels clause alert-এ জোড়া যাবে এমন অতিরিক্ত label-এর একটা সেট ঠিক করতে দেয় <Cite n={15} />। annotations clause তথ্যমূলক label-এর একটা সেট ঠিক করে, যা alert-এর বিবরণ বা runbook link-এর মতো দীর্ঘ অতিরিক্ত তথ্য রাখতে ব্যবহার করা যায় <Cite n={15} />। pending আর firing alert-এর জন্য Prometheus `ALERTS` আকারের কৃত্রিম time series-ও রাখে <Cite n={15} />। Prometheus-এর alerting rule এখন কী ভেঙেছে তা বের করতে ভালো, কিন্তু সেগুলো পূর্ণাঙ্গ notification সমাধান নয় <Cite n={15} />।

**Alertmanager।** Prometheus-এর alerting দুই ভাগে বিভক্ত <Cite n={22} />। Prometheus server-এর alerting rule একটা Alertmanager-এর কাছে alert পাঠায় <Cite n={22} />। Alertmanager সেই alert-গুলোর deduplication, grouping আর সঠিক receiver integration-এ routing সামলায় <Cite n={23} />। Grouping একই ধরনের alert-কে একটা notification-এ আনে <Cite n={23} />। Inhibition হলো কিছু alert আগে থেকেই firing থাকলে অন্য কিছু alert-এর notification চেপে দেওয়ার ধারণা <Cite n={23} />। Silence হলো কিছু সময়ের জন্য alert চুপ করিয়ে দেওয়ার সরল উপায় <Cite n={23} />। একটা silence ঠিক হয় matcher দিয়ে, routing tree-র মতোই <Cite n={23} />। প্রতিটা alert routing tree-তে ঢোকে সবচেয়ে ওপরের route দিয়ে, যাকে অবশ্যই সব alert-এর সঙ্গে মিলতে হবে <Cite n={24} />। তারপর সে child node-গুলো ঘুরে দেখে <Cite n={24} />। `continue` false হলে সে প্রথম মিলে যাওয়া child-এর পর থামে <Cite n={24} />। কোনো alert একটা node-এর কোনো child-এর সঙ্গে না মিললে alert-টা সামলানো হয় বর্তমান node-এর configuration parameter অনুযায়ী <Cite n={24} />। একটা route-এর বেশির ভাগ ঐচ্ছিক parameter, সেট না করলে, তার parent node থেকে পাওয়া যায় <Cite n={24} />। `amtool` হলো Alertmanager API-র সঙ্গে কাজ করার একটা cli tool <Cite n={25} />। এটা Alertmanager-এর সব release-এর সঙ্গে আসে <Cite n={25} />। configuration page বলে, server-এ চালু করার আগে একটা configuration file UTF-8 strict mode-এর সঙ্গে সামঞ্জস্যপূর্ণ কি না যাচাই করতে আপনি `amtool` ব্যবহার করতে পারেন <Cite n={24} />। সেই যাচাইয়ের জন্য একটা চালু Alertmanager server লাগে না <Cite n={24} />।

**কীসের ওপর alert দেবেন।** যত কম সম্ভব alert রাখার লক্ষ্য রাখুন, শেষ-ব্যবহারকারীর কষ্টের সঙ্গে জড়িত লক্ষণের ওপর alert দিয়ে, সেই কষ্ট যত উপায়ে হতে পারে তার সবটা ধরার চেষ্টা না করে <Cite n={21} />। সারসংক্ষেপে: alerting সরল রাখুন, লক্ষণের ওপর alert দিন, কারণ চিহ্নিত করতে ভালো console রাখুন, আর এমন page এড়ান যেখানে করার কিছু নেই <Cite n={21} />। error rate-এর ক্ষেত্রে ব্যবহারকারীর চোখে পড়ে এমন error-এ page করুন <Cite n={21} />। Google-এর SRE book বলে, monitoring-এর চারটা golden signal হলো latency, traffic, error আর saturation <Cite n={7} />। আপনার ব্যবহারকারীমুখী system-এর শুধু চারটা metric মাপতে পারলে এই চারটার ওপর মনোযোগ দিন <Cite n={7} />। Error হলো যে অনুরোধ ব্যর্থ হয় তার হার, প্রকাশ্যে, অপ্রকাশ্যে বা নীতির কারণে <Cite n={7} />। সফল অনুরোধের latency আর ব্যর্থ অনুরোধের latency আলাদা করে দেখা গুরুত্বপূর্ণ <Cite n={7} />।

**Loki আর তার label।** Loki Prometheus থেকে আলাদা, কারণ সে metric-এর বদলে log-এর ওপর মনোযোগ দেয়, আর log সংগ্রহ করে pull-এর বদলে push-এ <Cite n={31} />। Label Loki-কে log বার্তা সাজাতে আর log stream-এ একত্র করতে দেয় <Cite n={32} />। stream-এ আগে থেকে একটা `service_name` label থাকলে Loki সেটাই সরাসরি ব্যবহার করে <Cite n={32} />। নইলে Loki একটা label-তালিকা থেকে ক্রমানুসারে প্রথম ফাঁকা-নয় এমন মান খোঁজে <Cite n={32} />। তালিকার কোনো label না মিললে `unknown_service` মান বসানো হয় <Cite n={32} />। region, cluster, server, application, namespace আর environment-এর মতো জিনিসের জন্য label ব্যবহার করুন <Cite n={33} />। label-মানের অনেক বেশি সমন্বয় মানে অনেক বেশি stream <Cite n={33} />। Loki-তে এর শাস্তি হলো একটা বড় index আর store-এ ছোট chunk, যা আসলে performance কমিয়ে দিতে পারে <Cite n={33} />। সেই সমস্যা এড়াতে, কোনো কিছুর জন্য label লাগবে বলে নিশ্চিত না হওয়া পর্যন্ত label যোগ করবেন না <Cite n={33} />।

**LogQL।** সব LogQL query-তে একটা log stream selector থাকে <Cite n={34} />। ঐচ্ছিকভাবে log stream selector-এর পরে একটা log pipeline থাকতে পারে <Cite n={34} />। log pipeline হলো stage expression-এর একটা সেট, যা একটার পর একটা জোড়া লাগে আর বেছে নেওয়া log stream-এ প্রয়োগ হয় <Cite n={34} />। log stream selector ঠিক করা হয় এক বা একাধিক কমা দিয়ে আলাদা করা key-value জোড়া দিয়ে <Cite n={34} />। label matching operator হলো `=` (হুবহু সমান), `!=` (সমান নয়), `=~` (regex মেলে) আর `!~` (regex মেলে না) <Cite n={34} />। line filter expression মিলে যাওয়া log stream-এর একত্র করা log-এর ওপর একটা distributed grep চালায় <Cite n={34} />। সে log লাইনের বিষয়বস্তুতে খোঁজে, আর case-sensitive expression-এর সঙ্গে না মেলা লাইন বাদ দেয় <Cite n={34} />। label filter expression মূল আর বের করা label ব্যবহার করে log লাইন ছেঁকে নিতে দেয় <Cite n={34} />। metric query log query-র ফলে একটা function প্রয়োগ করে log query-কে বাড়ায় <Cite n={35} />। `count_over_time(log-range)` দেওয়া পরিসরের মধ্যে প্রতিটা log stream-এর entry গোনে <Cite n={35} />।

**1. Start a small web app, and read its metrics.** The app is the tutorial's own, written for this lesson. It uses only the standard library. It counts its requests by path and status code, times each request, and writes one log line per request. The path `/` answers 200, `/slow` answers 200 after 0.3 s, `/fail` answers 500, and any other path answers 404. Save this as `app.py`:

```python
"""A tiny web app for the practice run: it counts and times its own requests and shows them at /metrics.

  python3 app.py PORT LOGFILE

The routes are /, /slow (sleeps 0.3 s), /fail (answers 500), /metrics, and anything else (404). It uses only the
standard library. The metrics are written in the text format of Prometheus, and each request is also logged as one
line of key=value pairs.
"""
import http.server
import sys
import threading
import time
from collections import Counter

BUCKETS = (0.05, 0.1, 0.25, 0.5, 1.0)
LOCK = threading.Lock()
REQUESTS = Counter()  # (path, code) -> number of requests
BUCKET_COUNTS = [0] * (len(BUCKETS) + 1)  # observations per bucket (the last one is above 1.0)
STATE = {"sum": 0.0, "count": 0, "in_flight": 0}
PORT, LOGFILE = int(sys.argv[1]), sys.argv[2]
LOG = open(LOGFILE, "a", buffering=1, encoding="utf-8")


def render():
    lines = ["# HELP app_requests_total Requests handled, by path and status code.", "# TYPE app_requests_total counter"]
    for (path, code), n in sorted(REQUESTS.items()):
        lines.append(f'app_requests_total{{path="{path}",code="{code}"}} {n}')
    lines += ["# HELP app_in_flight_requests Requests that are being handled now.", "# TYPE app_in_flight_requests gauge",
              f"app_in_flight_requests {STATE['in_flight']}",
              "# HELP app_request_duration_seconds Time to handle a request.", "# TYPE app_request_duration_seconds histogram"]
    cumulative = 0
    for bound, n in zip(BUCKETS, BUCKET_COUNTS):
        cumulative += n
        lines.append(f'app_request_duration_seconds_bucket{{le="{bound}"}} {cumulative}')
    lines += [f'app_request_duration_seconds_bucket{{le="+Inf"}} {STATE["count"]}',
              f'app_request_duration_seconds_sum {STATE["sum"]:.6f}', f'app_request_duration_seconds_count {STATE["count"]}']
    return "\n".join(lines) + "\n"


class Handler(http.server.BaseHTTPRequestHandler):
    def log_message(self, *args):
        pass

    def reply(self, code, body, ctype="text/plain; charset=utf-8"):
        data = body.encode()
        self.send_response(code)
        self.send_header("Content-Type", ctype)
        self.send_header("Content-Length", str(len(data)))
        self.end_headers()
        self.wfile.write(data)

    def do_GET(self):
        if self.path == "/metrics":
            with LOCK:
                self.reply(200, render(), "text/plain; version=0.0.4; charset=utf-8")
            return
        started = time.time()
        with LOCK:
            STATE["in_flight"] += 1
        if self.path == "/slow":
            time.sleep(0.3)
        code = {"/": 200, "/slow": 200, "/fail": 500}.get(self.path, 404)
        self.reply(code, f"{code}\n")
        took = time.time() - started
        with LOCK:
            STATE["in_flight"] -= 1
            REQUESTS[(self.path if code != 404 else "other", code)] += 1
            STATE["sum"] += took
            STATE["count"] += 1
            BUCKET_COUNTS[next((i for i, b in enumerate(BUCKETS) if took <= b), len(BUCKETS))] += 1
        level = "error" if code >= 500 else "info"
        now = time.time()
        stamp = time.strftime("%Y-%m-%dT%H:%M:%S", time.gmtime(now)) + f".{int(now % 1 * 1000):03d}Z"
        LOG.write(f"ts={stamp} level={level} path={self.path} code={code} duration_ms={took * 1000:.0f}\n")


http.server.ThreadingHTTPServer(("127.0.0.1", PORT), Handler).serve_forever()
```

```python
"""Send the lines of an app log to Loki, as one stream with the label job="app".

  python3 push.py app.log http://127.0.0.1:13100
Each line starts with ts=<UTC time with milliseconds>. That time becomes the timestamp of the entry in Loki.
"""
import datetime
import json
import re
import sys
import urllib.request

path, base = sys.argv[1], sys.argv[2]
values = []
for line in open(path, encoding="utf-8").read().splitlines():
    stamp = re.match(r"ts=(\S+)", line).group(1)
    when = datetime.datetime.fromisoformat(stamp)
    values.append([str(int(when.timestamp() * 1000) * 1_000_000), line])
body = json.dumps({"streams": [{"stream": {"job": "app"}, "values": values}]}).encode()
request = urllib.request.Request(base + "/loki/api/v1/push", data=body, headers={"Content-Type": "application/json"})
with urllib.request.urlopen(request) as response:
    print(f"pushed {len(values)} lines, HTTP status {response.status}")
```

The same page says to use instrumentation libraries to propagate context <Cite n={4} />. The function `one_line` and the five checks are the tutorial's own. Save the script as `otel_demo.py`:

```python
"""Trace context propagation with the OpenTelemetry Python SDK: two "services" in one process.

The dictionary `headers` stands in for the HTTP request between them. Each span is printed on one line when it ends.
"""
import json
import re

from opentelemetry import trace
from opentelemetry.sdk.trace import TracerProvider
from opentelemetry.sdk.trace.export import ConsoleSpanExporter, SimpleSpanProcessor
from opentelemetry.trace.propagation.tracecontext import TraceContextTextMapPropagator

SPANS = []


def one_line(span):
    d = json.loads(span.to_json())
    row = {"name": d["name"], "trace_id": d["context"]["trace_id"], "span_id": d["context"]["span_id"], "parent_id": d["parent_id"]}
    SPANS.append(row)
    return json.dumps(row) + "\n"


provider = TracerProvider()
provider.add_span_processor(SimpleSpanProcessor(ConsoleSpanExporter(formatter=one_line)))
trace.set_tracer_provider(provider)
tracer = trace.get_tracer("practice")
propagator = TraceContextTextMapPropagator()


def service_b(headers):
    context = propagator.extract(carrier=headers)
    with tracer.start_as_current_span("service-b handles the request", context=context):
        pass


print("case 1: service A sends the traceparent header")
with tracer.start_as_current_span("service-a calls service-b"):
    headers = {}
    propagator.inject(headers)
    print("traceparent:", headers["traceparent"])
    service_b(headers)

print("case 2: the header is lost on the way")
with tracer.start_as_current_span("service-a calls service-b, no header"):
    service_b({})

b1, a1, b2, a2 = SPANS  # a span is printed when it ends, so each service-b span comes before its service-a span
print("check 1: header has the form 00-<32 hex>-<16 hex>-<2 hex>:", bool(re.fullmatch(r"00-[0-9a-f]{32}-[0-9a-f]{16}-[0-9a-f]{2}", headers["traceparent"])))
print("check 2: case 1, both spans share one trace id:", a1["trace_id"] == b1["trace_id"])
print("check 3: case 1, the parent of the service-b span is the service-a span:", b1["parent_id"] == a1["span_id"])
print("check 4: case 2, the trace ids differ:", a2["trace_id"] != b2["trace_id"])
print("check 5: case 2, the service-b span has no parent:", b2["parent_id"] is None)
```

**1. Start a small web app, and read its metrics.** The app is the tutorial's own, written for this lesson. It uses only the standard library. It counts its requests by path and status code, times each request, and writes one log line per request. The path `/` answers 200, `/slow` answers 200 after 0.3 s, `/fail` answers 500, and any other path answers 404. Save this as `app.py`:

```python
"""A tiny web app for the practice run: it counts and times its own requests and shows them at /metrics.

  python3 app.py PORT LOGFILE

The routes are /, /slow (sleeps 0.3 s), /fail (answers 500), /metrics, and anything else (404). It uses only the
standard library. The metrics are written in the text format of Prometheus, and each request is also logged as one
line of key=value pairs.
"""
import http.server
import sys
import threading
import time
from collections import Counter

BUCKETS = (0.05, 0.1, 0.25, 0.5, 1.0)
LOCK = threading.Lock()
REQUESTS = Counter()  # (path, code) -> number of requests
BUCKET_COUNTS = [0] * (len(BUCKETS) + 1)  # observations per bucket (the last one is above 1.0)
STATE = {"sum": 0.0, "count": 0, "in_flight": 0}
PORT, LOGFILE = int(sys.argv[1]), sys.argv[2]
LOG = open(LOGFILE, "a", buffering=1, encoding="utf-8")


def render():
    lines = ["# HELP app_requests_total Requests handled, by path and status code.", "# TYPE app_requests_total counter"]
    for (path, code), n in sorted(REQUESTS.items()):
        lines.append(f'app_requests_total{{path="{path}",code="{code}"}} {n}')
    lines += ["# HELP app_in_flight_requests Requests that are being handled now.", "# TYPE app_in_flight_requests gauge",
              f"app_in_flight_requests {STATE['in_flight']}",
              "# HELP app_request_duration_seconds Time to handle a request.", "# TYPE app_request_duration_seconds histogram"]
    cumulative = 0
    for bound, n in zip(BUCKETS, BUCKET_COUNTS):
        cumulative += n
        lines.append(f'app_request_duration_seconds_bucket{{le="{bound}"}} {cumulative}')
    lines += [f'app_request_duration_seconds_bucket{{le="+Inf"}} {STATE["count"]}',
              f'app_request_duration_seconds_sum {STATE["sum"]:.6f}', f'app_request_duration_seconds_count {STATE["count"]}']
    return "\n".join(lines) + "\n"


class Handler(http.server.BaseHTTPRequestHandler):
    def log_message(self, *args):
        pass

    def reply(self, code, body, ctype="text/plain; charset=utf-8"):
        data = body.encode()
        self.send_response(code)
        self.send_header("Content-Type", ctype)
        self.send_header("Content-Length", str(len(data)))
        self.end_headers()
        self.wfile.write(data)

    def do_GET(self):
        if self.path == "/metrics":
            with LOCK:
                self.reply(200, render(), "text/plain; version=0.0.4; charset=utf-8")
            return
        started = time.time()
        with LOCK:
            STATE["in_flight"] += 1
        if self.path == "/slow":
            time.sleep(0.3)
        code = {"/": 200, "/slow": 200, "/fail": 500}.get(self.path, 404)
        self.reply(code, f"{code}\n")
        took = time.time() - started
        with LOCK:
            STATE["in_flight"] -= 1
            REQUESTS[(self.path if code != 404 else "other", code)] += 1
            STATE["sum"] += took
            STATE["count"] += 1
            BUCKET_COUNTS[next((i for i, b in enumerate(BUCKETS) if took <= b), len(BUCKETS))] += 1
        level = "error" if code >= 500 else "info"
        now = time.time()
        stamp = time.strftime("%Y-%m-%dT%H:%M:%S", time.gmtime(now)) + f".{int(now % 1 * 1000):03d}Z"
        LOG.write(f"ts={stamp} level={level} path={self.path} code={code} duration_ms={took * 1000:.0f}\n")


http.server.ThreadingHTTPServer(("127.0.0.1", PORT), Handler).serve_forever()
```

```python
"""Send the lines of an app log to Loki, as one stream with the label job="app".

  python3 push.py app.log http://127.0.0.1:13100
Each line starts with ts=<UTC time with milliseconds>. That time becomes the timestamp of the entry in Loki.
"""
import datetime
import json
import re
import sys
import urllib.request

path, base = sys.argv[1], sys.argv[2]
values = []
for line in open(path, encoding="utf-8").read().splitlines():
    stamp = re.match(r"ts=(\S+)", line).group(1)
    when = datetime.datetime.fromisoformat(stamp)
    values.append([str(int(when.timestamp() * 1000) * 1_000_000), line])
body = json.dumps({"streams": [{"stream": {"job": "app"}, "values": values}]}).encode()
request = urllib.request.Request(base + "/loki/api/v1/push", data=body, headers={"Content-Type": "application/json"})
with urllib.request.urlopen(request) as response:
    print(f"pushed {len(values)} lines, HTTP status {response.status}")
```

**8. Pass a trace context from one service to another.** The script has two services in one process, `service-a` and `service-b`. The dictionary `headers` stands in for the HTTP request between them, so no network is used. The script uses the `ConsoleSpanExporter` of the SDK, which is included in the `opentelemetry-sdk` package <Cite n={5} />. It passes the context by hand, as the Python docs show <Cite n={4} />. The same page says to use instrumentation libraries to propagate context <Cite n={4} />. The function `one_line` and the five checks are the tutorial's own. Save the script as `otel_demo.py`:

```python
"""Trace context propagation with the OpenTelemetry Python SDK: two "services" in one process.

The dictionary `headers` stands in for the HTTP request between them. Each span is printed on one line when it ends.
"""
import json
import re

from opentelemetry import trace
from opentelemetry.sdk.trace import TracerProvider
from opentelemetry.sdk.trace.export import ConsoleSpanExporter, SimpleSpanProcessor
from opentelemetry.trace.propagation.tracecontext import TraceContextTextMapPropagator

SPANS = []


def one_line(span):
    d = json.loads(span.to_json())
    row = {"name": d["name"], "trace_id": d["context"]["trace_id"], "span_id": d["context"]["span_id"], "parent_id": d["parent_id"]}
    SPANS.append(row)
    return json.dumps(row) + "\n"


provider = TracerProvider()
provider.add_span_processor(SimpleSpanProcessor(ConsoleSpanExporter(formatter=one_line)))
trace.set_tracer_provider(provider)
tracer = trace.get_tracer("practice")
propagator = TraceContextTextMapPropagator()


def service_b(headers):
    context = propagator.extract(carrier=headers)
    with tracer.start_as_current_span("service-b handles the request", context=context):
        pass


print("case 1: service A sends the traceparent header")
with tracer.start_as_current_span("service-a calls service-b"):
    headers = {}
    propagator.inject(headers)
    print("traceparent:", headers["traceparent"])
    service_b(headers)

print("case 2: the header is lost on the way")
with tracer.start_as_current_span("service-a calls service-b, no header"):
    service_b({})

b1, a1, b2, a2 = SPANS  # a span is printed when it ends, so each service-b span comes before its service-a span
print("check 1: header has the form 00-<32 hex>-<16 hex>-<2 hex>:", bool(re.fullmatch(r"00-[0-9a-f]{32}-[0-9a-f]{16}-[0-9a-f]{2}", headers["traceparent"])))
print("check 2: case 1, both spans share one trace id:", a1["trace_id"] == b1["trace_id"])
print("check 3: case 1, the parent of the service-b span is the service-a span:", b1["parent_id"] == a1["span_id"])
print("check 4: case 2, the trace ids differ:", a2["trace_id"] != b2["trace_id"])
print("check 5: case 2, the service-b span has no parent:", b2["parent_id"] is None)
```

```python
  python3 app.py PORT LOGFILE

The routes are /, /slow (sleeps 0.3 s), /fail (answers 500), /metrics, and anything else (404). It uses only the
standard library. The metrics are written in the text format of Prometheus, and each request is also logged as one
line of key=value pairs.
"""

import sys
import threading
import time
from collections import Counter

BUCKETS = (0.05, 0.1, 0.25, 0.5, 1.0)
LOCK = threading.Lock()
REQUESTS = Counter()  # (path, code) -> number of requests
BUCKET_COUNTS = [0] * (len(BUCKETS) + 1)  # observations per bucket (the last one is above 1.0)
STATE = {"sum": 0.0, "count": 0, "in_flight": 0}
PORT, LOGFILE = int(sys.argv[1]), sys.argv[2]
LOG = open(LOGFILE, "a", buffering=1, encoding="utf-8")


def render():
    lines = ["# HELP app_requests_total Requests handled, by path and status code.", "# TYPE app_requests_total counter"]
    for (path, code), n in sorted(REQUESTS.items()):
        lines.append(f'app_requests_total{{path="{path}",code="{code}"}} {n}')
    lines += ["# HELP app_in_flight_requests Requests that are being handled now.", "# TYPE app_in_flight_requests gauge",
              f"app_in_flight_requests {STATE['in_flight']}",
              "# HELP app_request_duration_seconds Time to handle a request.", "# TYPE app_request_duration_seconds histogram"]
    cumulative = 0
    for bound, n in zip(BUCKETS, BUCKET_COUNTS):
        cumulative += n
        lines.append(f'app_request_duration_seconds_bucket{{le="{bound}"}} {cumulative}')
    lines += [f'app_request_duration_seconds_bucket{{le="+Inf"}} {STATE["count"]}',
              f'app_request_duration_seconds_sum {STATE["sum"]:.6f}', f'app_request_duration_seconds_count {STATE["count"]}']
    return "\n".join(lines) + "\n"


class Handler(http.server.BaseHTTPRequestHandler):
    def log_message(self, *args):
        pass

    def reply(self, code, body, ctype="text/plain; charset=utf-8"):
        data = body.encode()
        self.send_response(code)
        self.send_header("Content-Type", ctype)
        self.send_header("Content-Length", str(len(data)))
        self.end_headers()
        self.wfile.write(data)

    def do_GET(self):
        if self.path == "/metrics":
            with LOCK:
                self.reply(200, render(), "text/plain; version=0.0.4; charset=utf-8")
            return
        started = time.time()
        with LOCK:
            STATE["in_flight"] += 1
        if self.path == "/slow":
            time.sleep(0.3)
        code = {"/": 200, "/slow": 200, "/fail": 500}.get(self.path, 404)
        self.reply(code, f"{code}\n")
        took = time.time() - started
        with LOCK:
            STATE["in_flight"] -= 1
            REQUESTS[(self.path if code != 404 else "other", code)] += 1
            STATE["sum"] += took
            STATE["count"] += 1
            BUCKET_COUNTS[next((i for i, b in enumerate(BUCKETS) if took <= b), len(BUCKETS))] += 1
        level = "error" if code >= 500 else "info"
        now = time.time()
        stamp = time.strftime("%Y-%m-%dT%H:%M:%S", time.gmtime(now)) + f".{int(now % 1 * 1000):03d}Z"
        LOG.write(f"ts={stamp} level={level} path={self.path} code={code} duration_ms={took * 1000:.0f}\n")


http.server.ThreadingHTTPServer(("127.0.0.1", PORT), Handler).serve_forever()
```

- টিউটোরিয়াল ওই query-তে `rate()` রাখেনি, তাই উত্তর app চালু হওয়ার পর থেকে নয়টা অনুরোধ জুড়ে। docs quantile হিসাবের সময়-জানালা ঠিক করতে `rate()` function ব্যবহার করে <Cite n={13} />। এটা টিউটোরিয়ালের নিজের সিদ্ধান্ত, যাতে সংখ্যাটা আবার পাওয়া যায়।

```python
"""Send the lines of an app log to Loki, as one stream with the label job="app".

  python3 push.py app.log http://127.0.0.1:13100
Each line starts with ts=<UTC time with milliseconds>. That time becomes the timestamp of the entry in Loki.
"""
import datetime
import json
import re
import sys
import urllib.request

path, base = sys.argv[1], sys.argv[2]
values = []
for line in open(path, encoding="utf-8").read().splitlines():
    stamp = re.match(r"ts=(\S+)", line).group(1)
    when = datetime.datetime.fromisoformat(stamp)
    values.append([str(int(when.timestamp() * 1000) * 1_000_000), line])
body = json.dumps({"streams": [{"stream": {"job": "app"}, "values": values}]}).encode()
request = urllib.request.Request(base + "/loki/api/v1/push", data=body, headers={"Content-Type": "application/json"})
with urllib.request.urlopen(request) as response:
    print(f"pushed {len(values)} lines, HTTP status {response.status}")
```

```bash
# a helper that prints the result and leaves out the "stats" field of the response

curl -s localhost:13100/loki/api/v1/labels; echo
lq query_range '{job="app"} |= "code=500"' --data-urlencode limit=2
lq query 'sum by (path) (count_over_time({job="app"} | logfmt | code >= 500 [1h]))'
```

**৮. এক service থেকে আরেক service-এ trace context পাঠান।** script-এ একটা process-এ দুটো service আছে, `service-a` আর `service-b`। `headers` dictionary তাদের মধ্যের HTTP অনুরোধের জায়গা নেয়, তাই কোনো network ব্যবহার হয় না। script SDK-র `ConsoleSpanExporter` ব্যবহার করে, যা `opentelemetry-sdk` package-এর সঙ্গেই আসে <Cite n={5} />। সে context হাতে করে পাঠায়, Python docs যেমন দেখায় <Cite n={4} />। একই page বলে context propagate করতে instrumentation library ব্যবহার করতে <Cite n={4} />। `one_line` function আর পাঁচটা check টিউটোরিয়ালের নিজের। script `otel_demo.py` নামে save করুন:

```python
"""Trace context propagation with the OpenTelemetry Python SDK: two "services" in one process.

The dictionary `headers` stands in for the HTTP request between them. Each span is printed on one line when it ends.
"""
import json
import re

from opentelemetry import trace
from opentelemetry.sdk.trace import TracerProvider
from opentelemetry.sdk.trace.export import ConsoleSpanExporter, SimpleSpanProcessor
from opentelemetry.trace.propagation.tracecontext import TraceContextTextMapPropagator

SPANS = []


def one_line(span):
    d = json.loads(span.to_json())
    row = {"name": d["name"], "trace_id": d["context"]["trace_id"], "span_id": d["context"]["span_id"], "parent_id": d["parent_id"]}
    SPANS.append(row)
    return json.dumps(row) + "\n"


provider = TracerProvider()
provider.add_span_processor(SimpleSpanProcessor(ConsoleSpanExporter(formatter=one_line)))
trace.set_tracer_provider(provider)
tracer = trace.get_tracer("practice")
propagator = TraceContextTextMapPropagator()


def service_b(headers):
    context = propagator.extract(carrier=headers)
    with tracer.start_as_current_span("service-b handles the request", context=context):
        pass


print("case 1: service A sends the traceparent header")
with tracer.start_as_current_span("service-a calls service-b"):
    headers = {}
    propagator.inject(headers)
    print("traceparent:", headers["traceparent"])
    service_b(headers)

print("case 2: the header is lost on the way")
with tracer.start_as_current_span("service-a calls service-b, no header"):
    service_b({})

b1, a1, b2, a2 = SPANS  # a span is printed when it ends, so each service-b span comes before its service-a span
print("check 1: header has the form 00-<32 hex>-<16 hex>-<2 hex>:", bool(re.fullmatch(r"00-[0-9a-f]{32}-[0-9a-f]{16}-[0-9a-f]{2}", headers["traceparent"])))
print("check 2: case 1, both spans share one trace id:", a1["trace_id"] == b1["trace_id"])
print("check 3: case 1, the parent of the service-b span is the service-a span:", b1["parent_id"] == a1["span_id"])
print("check 4: case 2, the trace ids differ:", a2["trace_id"] != b2["trace_id"])
print("check 5: case 2, the service-b span has no parent:", b2["parent_id"] is None)
```

## Common mistakes

<Voices>
<Technical>

- **Using `rate()` on a gauge.** The `rate` function should only be used with counters <Cite n={13} />. Applied to gauge floats, it will most likely produce a nonsensical result, but the query will be processed without complaints <Cite n={12} />.
- **Aggregating before `rate()`.** When you combine `rate()` with an aggregation operator such as `sum()`, always take a `rate()` first, then aggregate <Cite n={13} />. Otherwise `rate()` cannot detect counter resets when your target restarts <Cite n={13} />. The recording rule of step 2 takes the `rate()` first.
- **Using a counter for a value that can decrease.** Do not use a counter to expose a value that can decrease <Cite n={10} />. The docs give an example: do not use a counter for the number of currently running processes, and use a gauge instead <Cite n={10} />.
- **Aggregating the quantiles of a summary.** The page on histograms says that Prometheus implements pre-calculated quantiles as a metric type called summary <Cite n={20} />. It adds that you cannot recalculate the quantiles later for another time window or another percentile, and that you cannot aggregate quantiles <Cite n={20} />.
- **Putting unbounded values in labels.** Do not use labels to store dimensions with high cardinality, such as user IDs, email addresses, or other unbounded sets of values <Cite n={18} />. In Loki, the penalties of too many streams are a large index and small chunks in the store <Cite n={33} />.
- **Reading `pending` as `firing`.** Alerts which have not yet fired for long enough are considered pending <Cite n={14} />. In step 6, `AppHighErrorRatio` was `pending` first.
- **Thinking that a silence resolves an alert.** If an alert matches an active silence, no notifications will be sent out for that alert <Cite n={23} />. In step 6, Prometheus still reported the silenced alert as `firing`.
- **Reading `up` as the health of the application.** The value of `up` says whether the scrape worked <Cite n={11} />. In step 6, the alert on the error ratio fired while `AppDown` did not.
- **Counting only the explicit errors.** The SRE book counts an HTTP 200 success response, coupled with the wrong content, as an error, implicitly <Cite n={7} />. The rule `AppHighErrorRatio` counts only the status codes from 500 to 599, so it would not see such a response.
- **Mixing the latency of successes and failures.** It is important to distinguish between the latency of successful requests and the latency of failed requests <Cite n={7} />. The histogram of the tutorial's app has no label for the status code, so it mixes them.
- **Trusting only a green `promtool check`.** The command `promtool check rules` checks if the rule files are valid or not, and `promtool test rules` runs unit tests for rules <Cite n={26} />. They are two commands for two jobs.
- **Forgetting a series that does not exist yet.** Time series that are not present until something happens are difficult to deal with <Cite n={19} />. The docs say to export a default value such as 0 for any time series that you know may exist in advance <Cite n={19} />.
- **Sending a timestamp to Loki as a number.** The push endpoint needs the timestamp as a string, and it returns a 400 error otherwise <Cite n={36} />.
- **Expecting a line filter to ignore case.** The line filter expression discards the lines that do not match the case-sensitive expression <Cite n={34} />.
- **Losing the trace header on a hop.** When no traceparent header is received, the vendor creates a new trace-id and parent-id that represents the current request <Cite n={6} />. Case 2 of step 8 shows two traces where one was expected.
- **Reading the trace flags as a number.** The flags are a bit field, and you cannot interpret them by decoding the hex value and looking at the resulting number <Cite n={6} />. The value in step 8 was `03`.
- **Leaving a port open to the network.** In the tutorial's run, the gRPC port of Loki listened on all addresses. Run step 7 on a machine and a network that you trust.

</Technical>

- **যে মান কমতে পারে তার জন্য counter ব্যবহার করা।** যে মান কমতে পারে তা দেখাতে counter ব্যবহার করবেন না <Cite n={10} />। docs একটা উদাহরণ দেয়: এখন চলছে এমন process-এর সংখ্যার জন্য counter ব্যবহার করবেন না, বদলে gauge ব্যবহার করুন <Cite n={10} />।
- **summary-র quantile aggregate করা।** histogram-সংক্রান্ত page বলে, Prometheus আগে-হিসাব-করা quantile প্রয়োগ করে summary নামের একটা metric type হিসেবে <Cite n={20} />। সে আরও বলে, আপনি অন্য সময়-জানালা বা অন্য percentile-এর জন্য পরে quantile আবার হিসাব করতে পারবেন না, আর quantile aggregate করতে পারবেন না <Cite n={20} />।
- **label-এ সীমাহীন মান রাখা।** user ID, email address বা অন্য সীমাহীন মানের মতো high cardinality-র dimension রাখতে label ব্যবহার করবেন না <Cite n={18} />। Loki-তে অনেক বেশি stream-এর শাস্তি হলো একটা বড় index আর store-এ ছোট chunk <Cite n={33} />।
- **`pending`-কে `firing` পড়া।** যে alert এখনও যথেষ্ট সময় ধরে ফেরত আসেনি, সেগুলো pending ধরা হয় <Cite n={14} />। ৬ নম্বর ধাপে `AppHighErrorRatio` প্রথমে `pending` ছিল।
- **ভাবা যে silence একটা alert মিটিয়ে দেয়।** একটা alert সক্রিয় silence-এর সঙ্গে মিললে সেই alert-এর জন্য কোনো notification পাঠানো হবে না <Cite n={23} />। ৬ নম্বর ধাপে Prometheus তখনও silence করা alert-টাকে `firing` জানিয়েছে।
- **`up`-কে application-এর সুস্থতা পড়া।** `up`-এর মান বলে scrape কাজ করেছে কি না <Cite n={11} />। ৬ নম্বর ধাপে error ratio-র alert firing হয়েছে, কিন্তু `AppDown` হয়নি।
- **শুধু প্রকাশ্য error গোনা।** SRE book ভুল বিষয়বস্তুসহ একটা HTTP 200 সাফল্যের response-কেও অপ্রকাশ্য error ধরে <Cite n={7} />। `AppHighErrorRatio` rule শুধু 500 থেকে 599 status code গোনে, তাই সে এমন response দেখবে না।
- **সফল আর ব্যর্থ অনুরোধের latency মিশিয়ে ফেলা।** সফল অনুরোধের latency আর ব্যর্থ অনুরোধের latency আলাদা করে দেখা গুরুত্বপূর্ণ <Cite n={7} />। টিউটোরিয়ালের app-এর histogram-এ status code-এর label নেই, তাই সে দুটোকে মিশিয়ে ফেলে।
- **শুধু সবুজ `promtool check`-এর ওপর ভরসা করা।** `promtool check rules` command দেখে rule file বৈধ কি না, আর `promtool test rules` rule-এর unit test চালায় <Cite n={26} />। দুটো কাজের জন্য দুটো command।
- **এখনও নেই এমন series ভুলে যাওয়া।** যে time series কিছু ঘটার আগে থাকে না, তা সামলানো কঠিন <Cite n={19} />। docs বলে, যে time series আগে থেকেই থাকতে পারে বলে আপনি জানেন, তার জন্য 0-র মতো একটা default মান export করতে <Cite n={19} />।
- **Loki-তে timestamp সংখ্যা হিসেবে পাঠানো।** push endpoint-এর timestamp string হিসেবে লাগে, নইলে সে 400 error ফেরত দেয় <Cite n={36} />।
- **line filter case উপেক্ষা করবে বলে ধরে নেওয়া।** line filter expression case-sensitive expression-এর সঙ্গে না মেলা লাইন বাদ দেয় <Cite n={34} />।
- **এক hop-এ trace header হারানো।** কোনো traceparent header না এলে vendor একটা নতুন trace-id আর parent-id বানায়, যা বর্তমান অনুরোধ বোঝায় <Cite n={6} />। ৮ নম্বর ধাপের case 2 একটা trace আশা করা জায়গায় দুটো trace দেখায়।
- **trace flags-কে সংখ্যা হিসেবে পড়া।** flags একটা bit field, আর আপনি hex মান decode করে ফলের সংখ্যা দেখে সেগুলো বুঝতে পারেন না <Cite n={6} />। ৮ নম্বর ধাপে মান ছিল `03`।
- **network-এর জন্য একটা port খোলা রাখা।** টিউটোরিয়ালের run-এ Loki-র gRPC port সব address-এ শুনেছে। ৭ নম্বর ধাপ এমন machine আর network-এ চালান, যাকে আপনি বিশ্বাস করেন।

## What a tester can check

<Voices>
<Technical>

<Callout type="tip" title="Tutorial advice">
This list is the tutorial's own advice for a tester who works with monitoring and observability tools.

- Run `promtool check config`, `promtool check rules`, and `promtool test rules` on every change to the rule files, and fail the build on a non-zero exit status.
- Write two unit tests for each alert: one that must fire, and one that must not fire, with an empty `exp_alerts`.
- Test the routing with `amtool config routes test` for each `severity` and each receiver that matters.
- After a test run, read the counters and compare the difference with what the test sent, not the value.
- Look at `up` for every target before you trust a graph.
- Wait for the state that you expect, `pending` or `firing`, with a poll and a time limit.
- Look at the labels of every new metric, and refuse ids, user input, and other unbounded values.
- Count the failures in two places, the metric and the log, and compare the two numbers.
- Look at the latency of the failed requests and the latency of the successful requests apart.
- For one request, look for the same trace id in every service, and test one case where the header is lost.
- Keep secrets, personal data, and tokens out of logs, labels, and span attributes.
- Run a local Loki or Prometheus on a machine and a network that you trust, and look at which ports it opens.
- Record the date, the versions, and the exact commands with each result.
</Callout>

## Key words

| Term | Meaning |
|---|---|
| Observability | Observability lets you understand a system from the outside by letting you ask questions about that system without knowing its inner workings |
| Instrumentation | To ask those questions about your system, your application must be properly instrumented |
| Telemetry | Telemetry refers to data emitted from a system and its behavior |
| Metric | Metrics are aggregations over a period of time of numeric data about your infrastructure or application |
| Log | A log is a timestamped message emitted by services or other components |
| Span | A span represents a single unit of work or operation |
| Trace | A trace is made of one or more spans |
| Time series | Every time series is uniquely identified by its metric name and optional key-value pairs called labels |
| Label | optional key-value pairs called labels |
| Instance | an endpoint you can scrape is called an instance, usually corresponding to a single process |
| Job | A collection of instances with the same purpose is called a job |
| up | Its value is 1 if the instance is healthy, that is, reachable, or 0 if the scrape failed |
| Counter | A counter is a cumulative metric that represents a single monotonically increasing counter whose value can only increase or be reset to zero on restart |
| Gauge | A gauge is a metric that represents a single numerical value that can arbitrarily go up and down |
| Histogram | A histogram records observations by counting them in configurable buckets |
| Summary | Similar to a histogram, a summary samples observations |
| PromQL | Prometheus provides a functional query language called PromQL that lets the user select and aggregate time series data in real time |
| Instant vector | An instant vector is a set of time series containing a single sample for each time series, all sharing the same timestamp |
| Range vector | A range vector is a set of time series containing a range of data points over time for each time series |
| Recording rule | Recording rules allow you to precompute frequently needed or computationally expensive expressions and save their result as a new set of time series |
| Pending | Alerts which have not yet fired for long enough are considered pending |
| Firing | Alerts are considered firing once they have been returned for this long |
| Alertmanager | The Alertmanager takes care of deduplicating, grouping, and routing them to the correct receiver integration |
| Grouping | Grouping categorizes alerts of similar nature into a single notification |
| Inhibition | Inhibition is a concept of suppressing notifications for certain alerts if certain other alerts are already firing |
| Silence | Silences are a straightforward way to simply mute alerts for a given time |
| Routing tree | Every alert enters the routing tree at the configured top-level route, which must match all alerts |
| promtool | You can use promtool to test your rules |
| amtool | a cli tool for interacting with the Alertmanager API |
| Loki | Loki is a horizontally-scalable, highly-available, multi-tenant log aggregation system inspired by Prometheus |
| Log stream | Labels allow Loki to organize and group together log messages into log streams |
| LogQL | All LogQL queries contain a log stream selector |
| Context propagation | Propagation is the mechanism that moves context between services and processes |
| traceparent | HTTP header field identifies the incoming request in a tracing system |
| Golden signals | the four golden signals of monitoring are latency, traffic, errors, and saturation |
| Cardinality | Do not use labels to store dimensions with high cardinality, such as user IDs, email addresses, or other unbounded sets of values |
