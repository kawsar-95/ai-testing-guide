# Kubernetes Architecture

This page is about the parts of a Kubernetes cluster: the control plane, the nodes, and etcd, how they work together to place and run Pods, and how custom resources and Operators extend the API, with a practice run that looks at each part of the local cluster of [Kubernetes Basics](/devops/kubernetes-basics/).

<PageMeta />

## What it is

<Voices>
<Technical>

**A cluster.** A Kubernetes cluster consists of a control plane plus a set of worker machines, called nodes, that run containerized applications <Cite n={1} />. Every cluster needs at least one worker node in order to run Pods <Cite n={1} />. The control plane manages the worker nodes and the Pods in the cluster <Cite n={1} />. In production environments, the control plane usually runs across multiple computers and a cluster usually runs multiple nodes, providing fault-tolerance and high availability <Cite n={1} />.

**The control plane.**

| Component | What it does |
|---|---|
| kube-apiserver | Exposes the Kubernetes API; the API server is the front end for the Kubernetes control plane <Cite n={1} /> |
| etcd | A consistent and highly-available key value store used as Kubernetes' backing store for all cluster data <Cite n={1} /> |
| kube-scheduler | Watches for newly created Pods with no assigned node, and selects a node for them to run on <Cite n={1} /> |
| kube-controller-manager | Runs controller processes <Cite n={1} /> |
| cloud-controller-manager | Embeds cloud-specific control logic, and lets you link your cluster into your cloud provider's API <Cite n={1} /> |

**The node components.** The components on a node include the kubelet, a container runtime, and the kube-proxy <Cite n={3} />.

| Component | What it does |
|---|---|
| kubelet | An agent that runs on each node in the cluster; it makes sure that containers are running in a Pod <Cite n={1} /> |
| kube-proxy (optional) | A network proxy that runs on each node, implementing part of the Kubernetes Service concept <Cite n={1} /> |
| Container runtime | Manages the execution and lifecycle of containers; Kubernetes supports container runtimes such as containerd, CRI-O, and any other implementation of the Kubernetes CRI <Cite n={1} /> |

**Add-ons.** All Kubernetes clusters should have cluster DNS, as many examples rely on it <Cite n={1} />. Namespaced resources for addons belong within the `kube-system` namespace <Cite n={1} />.

**Extending the API.** A custom resource is an extension of the Kubernetes API that is not necessarily available in a default Kubernetes installation <Cite n={12} />. Operators are software extensions to Kubernetes that make use of custom resources to manage applications and their components <Cite n={2} />. Operators follow Kubernetes principles, notably the control loop <Cite n={2} />.

</Technical>

## How it works

<Voices>
<Technical>

**The API server is the front end.** kube-apiserver exposes the Kubernetes API, and the API server is the front end for the control plane <Cite n={1} />. kube-apiserver is designed to scale horizontally: it scales by deploying more instances <Cite n={1} />.

**etcd keeps the state.** All Kubernetes objects are stored in etcd <Cite n={14} />. etcd is a leader-based distributed system <Cite n={14} />.

**The scheduler places Pods.** kube-scheduler is the default scheduler for Kubernetes and runs as part of the control plane <Cite n={6} />. It selects an optimal node to run newly created or not yet scheduled Pods <Cite n={6} />. It selects a node in a 2-step operation: filtering finds the set of Nodes where it's feasible to schedule the Pod, and scoring ranks the remaining nodes to choose the most suitable Pod placement <Cite n={6} />. If none of the nodes are suitable, the Pod remains unscheduled until the scheduler is able to place it <Cite n={6} />. With the `nodeSelector` field of a Pod, you list the node labels that you want the target node to have, and Kubernetes only schedules the Pod onto nodes that have each of the labels you specify <Cite n={7} />.

**The controllers react.** kube-controller-manager runs controller processes: logically, each controller is a separate process, but they are all compiled into a single binary and run in a single process <Cite n={1} />. One of them, the Node controller, is responsible for noticing and responding when nodes go down <Cite n={1} />.

**The kubelet runs the Pods, and reports.** The kubelet takes a set of PodSpecs and ensures that the containers described in those PodSpecs are running and healthy <Cite n={1} />. Heartbeats, sent by Kubernetes nodes, help your cluster determine the availability of each node <Cite n={3} />. For nodes there are two forms of heartbeats: updates to the `.status` of a Node, and Lease objects within the `kube-node-lease` namespace <Cite n={3} />. Every kubelet heartbeat is an update request to its Lease object, updating the `spec.renewTime` field of the Lease <Cite n={5} />. Four of the conditions of a node <Cite n={4} />:

| Condition | Meaning |
|---|---|
| `Ready` | `True` if the node is healthy and ready to accept Pods; `False` if it is not healthy and is not accepting Pods; `Unknown` if the node controller has not heard from the node in the last `node-monitor-grace-period` (default is 50 seconds) |
| `DiskPressure` | `True` if pressure exists on the disk size, that is, if the disk capacity is low |
| `MemoryPressure` | `True` if pressure exists on the node memory, that is, if the node memory is low |
| `PIDPressure` | `True` if pressure exists on the processes, that is, if there are too many processes on the node |

**Static Pods.** The control plane components can be deployed as static Pods, managed by the kubelet on specific nodes; this is a common approach used by tools like kubeadm <Cite n={1} />. Static Pods are managed directly by the kubelet daemon on a specific node, without the API server observing them <Cite n={9} />. The kubelet watches each static Pod and restarts it if it fails <Cite n={9} />. The `staticPodPath` field of the kubelet configuration file names a directory; the kubelet periodically scans it and creates or deletes static Pods as YAML or JSON files appear or disappear there <Cite n={10} />. The kubelet automatically tries to create a mirror Pod on the API server for each static Pod: the Pods are visible on the API server, but cannot be controlled from there <Cite n={9} />. Their names are suffixed with the node hostname with a leading hyphen, and they have the `kubernetes.io/config.mirror` annotation <Cite n={9} />.

**Who runs the control plane.** Cloud providers often abstract away the control plane, managing its components as part of their service offering <Cite n={1} />. If you are running Kubernetes on your own premises, or in a learning environment inside your own PC, the cluster does not have a cloud controller manager <Cite n={1} />.

**The API can grow.** When you create a CustomResourceDefinition, a new RESTful API endpoint is created for its objects <Cite n={13} />. On their own, custom resources let you store and retrieve structured data; when you combine a custom resource with a custom controller, custom resources provide a true declarative API <Cite n={12} />.

**The API server is the front door.** kube-apiserver offers the Kubernetes API, and it is the front door of the control plane <Cite n={1} />. It is built to grow sideways: you run more copies of it <Cite n={1} />.

**etcd keeps the state.** Every Kubernetes object is stored in etcd <Cite n={14} />. etcd is a distributed system with a leader <Cite n={14} />.

**The scheduler places Pods.** kube-scheduler is the default scheduler of Kubernetes, and it runs as part of the control plane <Cite n={6} />. It picks the best node for each new Pod, or for a Pod that has no node yet <Cite n={6} />. | `DiskPressure` | `True` if the disk is running out of space |
| `MemoryPressure` | `True` if the node is running out of memory |

**Who runs the control plane.** Cloud providers often hide the control plane and run its parts as part of their service <Cite n={1} />. If you run Kubernetes on your own machines, or to learn on your own PC, the cluster has no cloud controller manager <Cite n={1} />.

**The API can grow.** When you create a CustomResourceDefinition, the API gets a new endpoint for its objects <Cite n={13} />. On their own, custom resources let you store data and get it back; with a custom controller, they become a true declarative API <Cite n={12} />.

<Bangla>

**API server হলো front end।** kube-apiserver Kubernetes API expose করে, আর API server হলো control plane-এর front end <Cite n={1} />। kube-apiserver horizontally scale করার জন্য বানানো: আরও instance deploy করে এটা scale করে <Cite n={1} />।

**etcd state ধরে রাখে।** সব Kubernetes object etcd-তে store করা থাকে <Cite n={14} />। etcd একটা leader-based distributed system <Cite n={14} />।

**Scheduler Pod বসায়।** kube-scheduler হলো Kubernetes-এর default scheduler, আর এটা control plane-এর অংশ হিসেবে চলে <Cite n={6} />। নতুন তৈরি হওয়া বা এখনো schedule না হওয়া Pod চালানোর জন্য এটা একটা optimal node বেছে নেয় <Cite n={6} />। এটা দুই ধাপে node বাছে: filtering সেই Node-গুলো খুঁজে বের করে যেখানে Pod schedule করা সম্ভব, আর scoring বাকি node-গুলোকে র‍্যাঙ্ক করে সবচেয়ে উপযুক্ত জায়গা বেছে নেয় <Cite n={6} />। কোনো node উপযুক্ত না হলে, scheduler বসাতে না পারা পর্যন্ত Pod unscheduled থাকে <Cite n={6} />। Pod-এর `nodeSelector` field-এ আপনি target node-এ যে node label চান তা লেখেন, আর Kubernetes Pod-কে কেবল সেই node-এ schedule করে, যেখানে আপনার দেওয়া প্রতিটা label আছে <Cite n={7} />।

**Controller সাড়া দেয়।** kube-controller-manager controller process চালায়: যুক্তির দিক থেকে প্রতিটা controller আলাদা process, কিন্তু সবগুলো একটা binary-তে compile হয়ে একটা process-এ চলে <Cite n={1} />। এদের একটা, Node controller, node বন্ধ হয়ে গেলে তা খেয়াল করে সাড়া দেয় <Cite n={1} />।

**kubelet Pod চালায়, আর খবর দেয়।** kubelet কিছু PodSpec নেয়, আর নিশ্চিত করে যে ওই PodSpec-এ বর্ণিত container-গুলো চলছে আর healthy <Cite n={1} />। Kubernetes node-এর পাঠানো heartbeat cluster-কে প্রতিটা node-এর availability বুঝতে সাহায্য করে <Cite n={3} />। node-এর heartbeat দুই রকম: Node-এর `.status`-এর আপডেট, আর `kube-node-lease` namespace-এর Lease object <Cite n={3} />। kubelet-এর প্রতিটা heartbeat তার Lease object-এর একটা update request, যা Lease-এর `spec.renewTime` field আপডেট করে <Cite n={5} />। একটা node-এর চারটা condition <Cite n={4} />:

| Condition | অর্থ |
|---|---|
| `Ready` | node healthy আর Pod নিতে প্রস্তুত হলে `True`; healthy না হলে আর Pod না নিলে `False`; শেষ `node-monitor-grace-period`-এ (default 50 সেকেন্ড) node controller node-এর কোনো খবর না পেলে `Unknown` |
| `DiskPressure` | disk size-এ চাপ থাকলে, মানে disk capacity কম হলে `True` |
| `MemoryPressure` | node memory-তে চাপ থাকলে, মানে node memory কম হলে `True` |
| `PIDPressure` | process-এ চাপ থাকলে, মানে node-এ অনেক বেশি process থাকলে `True` |

**Static Pod।** control plane component-গুলো static Pod হিসেবে deploy করা যায়, যা নির্দিষ্ট node-এ kubelet পরিচালনা করে; kubeadm-এর মতো tool এই পদ্ধতি প্রায়ই ব্যবহার করে <Cite n={1} />। Static Pod নির্দিষ্ট একটা node-এর kubelet daemon সরাসরি পরিচালনা করে, API server সেগুলো observe করে না <Cite n={9} />। kubelet প্রতিটা static Pod-এর দিকে নজর রাখে, আর ফেল করলে restart করে <Cite n={9} />। kubelet configuration file-এর `staticPodPath` field একটা directory-র নাম দেয়; kubelet নিয়মিত সেটা scan করে, আর সেখানে YAML বা JSON file আসলে বা চলে গেলে static Pod তৈরি করে বা মুছে দেয় <Cite n={10} />। প্রতিটা static Pod-এর জন্য kubelet নিজে থেকে API server-এ একটা mirror Pod তৈরির চেষ্টা করে: Pod-গুলো API server-এ দেখা যায়, কিন্তু সেখান থেকে নিয়ন্ত্রণ করা যায় না <Cite n={9} />। তাদের নামের শেষে একটা hyphen আর node-এর hostname যোগ হয়, আর তাদের `kubernetes.io/config.mirror` annotation থাকে <Cite n={9} />।

**Control plane কে চালায়।** cloud provider-রা প্রায়ই control plane আড়াল করে রাখে, আর তার component-গুলো তাদের service-এর অংশ হিসেবে পরিচালনা করে <Cite n={1} />। আপনি নিজের premises-এ, বা নিজের PC-র ভেতরে একটা learning environment-এ Kubernetes চালালে cluster-এ কোনো cloud controller manager থাকে না <Cite n={1} />।

**API বাড়তে পারে।** একটা CustomResourceDefinition তৈরি করলে তার object-গুলোর জন্য একটা নতুন RESTful API endpoint তৈরি হয় <Cite n={13} />। custom resource নিজে থেকে structured data store আর retrieve করতে দেয়; একটা custom resource-কে একটা custom controller-এর সাথে মেলালে custom resource একটা সত্যিকারের declarative API দেয় <Cite n={12} />।

**Check the cluster before the tests.** Machines that check the health of the API server should rely on the HTTP status code: a status code 200 indicates that the API server is healthy, live, or ready, depending on the endpoint <Cite n={11} />. **When a Pod stays Pending, ask the scheduler.** If none of the nodes are suitable, the Pod remains unscheduled until the scheduler is able to place it <Cite n={6} />. In step 5, the `FailedScheduling` Event named the rule that the node did not meet.

**Watch the nodes.** A node is `Unknown` when the node controller has not heard from it in the last `node-monitor-grace-period`, and `DiskPressure`, `MemoryPressure`, or `PIDPressure` is `True` when the disk capacity is low, the node memory is low, or there are too many processes on the node <Cite n={4} />.

**Know what you cannot see.** Cloud providers often abstract away the control plane, managing its components as part of their service offering <Cite n={1} />. On such a cluster, ask what the provider shows of it.

**Back up before you break things.** If your cluster uses etcd as its backing store, make sure you have a back up plan for the data <Cite n={1} />. Periodically backing up the etcd cluster data is important to recover Kubernetes clusters under disaster scenarios <Cite n={14} />. `etcdctl snapshot save` creates a snapshot, as in step 7 <Cite n={14} />.

**Test the Operator, not only its resource.** When you combine a custom resource with a custom controller, custom resources provide a true declarative API <Cite n={12} />. In step 6, the API accepted the CronTab object, and no Pod ran. Among the things that you can use an Operator to automate are deploying an application on demand, taking and restoring backups of that application's state, and simulating failure in all or part of your cluster to test its resilience <Cite n={2} />.

</Technical>

## Common mistakes

<Voices>
<Technical>

- **A backup file next to a static Pod manifest.** The kubelet processes all files not starting with a dot in the static Pod directory; there is no filtering by file extension <Cite n={10} />. If you copy `kube-apiserver.yaml` to `kube-apiserver.yaml.backup`, the kubelet will read both files and attempt to create a static Pod from each <Cite n={10} />.
- **Deleting a mirror Pod to restart a component.** If you use kubectl to delete the mirror Pod from the API server, the kubelet doesn't remove the static Pod <Cite n={10} />.
- **Reading the verbose health output in a script.** The `verbose` output is not intended to be consumed by a machine; machines should rely on the HTTP status code <Cite n={11} />.
- **Using `/healthz`.** The `healthz` endpoint is deprecated (since Kubernetes v1.16); use the more specific `livez` and `readyz` endpoints instead <Cite n={11} />.
- **Deleting a CustomResourceDefinition in a test clean-up.** The server will uninstall the RESTful API endpoint and delete all custom objects stored in it <Cite n={13} />.
- **Leaving a test label on a node.** Kubernetes only schedules a Pod onto nodes that have each of the labels of its `nodeSelector` <Cite n={7} />. A `-` after the name of a label removes it <Cite n={16} />.

</Technical>
<Layman>

- **A backup file next to a static Pod manifest.** The kubelet reads every file in the static Pod folder whose name does not start with a dot, whatever its extension <Cite n={10} />. If you copy `kube-apiserver.yaml` to `kube-apiserver.yaml.backup`, the kubelet reads both and tries to make a static Pod from each <Cite n={10} />.
- **Deleting a mirror Pod to restart a component.** If you delete the mirror Pod with kubectl, the kubelet does not remove the static Pod <Cite n={10} />.
- **Reading the verbose health output in a script.** The `verbose` output is not for programs; they should look at the HTTP status code <Cite n={11} />.
- **Using `/healthz`.** The `healthz` endpoint is deprecated (since Kubernetes v1.16); use `livez` and `readyz` <Cite n={11} />.
- **Deleting a CustomResourceDefinition in a test clean-up.** The server removes the endpoint and deletes all the custom objects stored in it <Cite n={13} />.
- **Leaving a test label on a node.** Kubernetes only places a Pod on a node that has each label of its `nodeSelector` <Cite n={7} />. A `-` after the name of a label removes it <Cite n={16} />.

</Layman>
<Bangla>

- **Static Pod manifest-এর পাশে backup file।** kubelet static Pod directory-র এমন সব file process করে, যাদের নাম dot দিয়ে শুরু হয় না; file extension দিয়ে কোনো বাছাই হয় না <Cite n={10} />। `kube-apiserver.yaml`-কে `kube-apiserver.yaml.backup`-এ copy করলে kubelet দুটো file-ই পড়বে, আর প্রতিটা থেকে একটা static Pod তৈরির চেষ্টা করবে <Cite n={10} />।
- **Component restart করতে mirror Pod মোছা।** kubectl দিয়ে API server থেকে mirror Pod মুছলে kubelet static Pod সরায় না <Cite n={10} />।
- **Script-এ verbose health output পড়া।** `verbose` output কোনো machine-এর ব্যবহারের জন্য নয়; machine-গুলোর HTTP status code-এর ওপর নির্ভর করা উচিত <Cite n={11} />।
- **`/healthz` ব্যবহার করা।** `healthz` endpoint deprecated (Kubernetes v1.16 থেকে); এর বদলে আরও নির্দিষ্ট `livez` আর `readyz` endpoint ব্যবহার করুন <Cite n={11} />।
- **Test clean-up-এ CustomResourceDefinition মোছা।** server RESTful API endpoint uninstall করবে, আর তাতে store করা সব custom object মুছে দেবে <Cite n={13} />।
- **Node-এ test-এর label রেখে দেওয়া।** Kubernetes একটা Pod-কে কেবল সেই node-এ schedule করে, যেখানে তার `nodeSelector`-এর প্রতিটা label আছে <Cite n={7} />। label-এর নামের পরে একটা `-` দিলে label-টা সরে যায় <Cite n={16} />।

</Bangla>
</Voices>

## What a tester can check

<Voices>
<Technical>

<Callout type="tip" title="Tutorial advice">

## Key words

| Term | Meaning |
|---|---|
| Control plane | Manages the worker nodes and the Pods in the cluster |
| Node | A worker machine that runs containerized applications |
| kube-apiserver | Exposes the Kubernetes API; the front end for the control plane |
| etcd | The consistent and highly-available key value store that is Kubernetes' backing store for all cluster data |
| kube-scheduler | Selects a node for each newly created Pod with no assigned node |
| kube-controller-manager | Runs the controller processes, compiled into a single binary |
| kubelet | The agent on each node that makes sure that containers are running in a Pod |
| kube-proxy | An optional network proxy on each node that implements part of the Service concept |
| Static Pod | A Pod managed directly by the kubelet on a specific node, without the API server observing it |
| Mirror Pod | The Pod that the kubelet creates on the API server for a static Pod; visible there, but not controlled from there |
| Lease | An object that carries a node's heartbeat, or makes sure that only one instance of a component is running |
| Node condition | A status of a node, such as `Ready`, `DiskPressure`, `MemoryPressure`, or `PIDPressure` |
| `livez`, `readyz` | API server endpoints that indicate its current status; `healthz` is deprecated |
| Custom resource | An extension of the Kubernetes API that is not necessarily in a default installation |
| CustomResourceDefinition | Creates a new API endpoint for a custom resource; deleting it deletes all its objects |
| Operator | A software extension that uses custom resources to manage an application and its components |
