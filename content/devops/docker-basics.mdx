# Docker Basics

This page explains Docker for a tester: what containers, images, and registries are, how the Docker client and daemon run a container, and the first commands, with a practice run that you can repeat on your own machine. It ends with the ways that a tester uses containers. [Docker Images and Compose](/devops/docker-images-compose/) builds on it.

<PageMeta />

## What it is

<Voices>
<Technical>

Docker is an open platform for developing, shipping, and running applications <Cite n={1} />. Docker provides the ability to package and run an application in a loosely isolated environment called a container <Cite n={1} />. Containers are lightweight and contain everything needed to run the application, so you don't need to rely on what's installed on the host <Cite n={1} />.

**Three words to know.**

| Word | What it is |
|---|---|
| Container | A runnable instance of an image <Cite n={1} />. Simply put, containers are isolated processes for each of your app's components <Cite n={2} /> |
| Image | A standardized package that includes all of the files, binaries, libraries, and configurations to run a container <Cite n={3} /> |
| Registry | A centralized location for storing and sharing your container images. Docker Hub is a public registry that anyone can use and is the default registry <Cite n={4} /> |

**Why a tester cares.** In Docker's own example, developers use Docker to push their applications into a test environment and run automated and manual tests <Cite n={1} />. When they find bugs, they fix them and redeploy to the test environment for testing and validation <Cite n={1} />. You can share containers and be sure that everyone you share with gets the same container that works in the same way <Cite n={1} />.

**Containers and virtual machines.** A virtual machine (VM) is an entire operating system with its own kernel, hardware drivers, programs, and applications <Cite n={2} />. A container is simply an isolated process with all of the files it needs to run <Cite n={2} />. If you run multiple containers, they all share the same kernel, so you can run more applications on less infrastructure <Cite n={2} />. The two are often used together: in a cloud, the machines are typically VMs, and a VM with a container runtime can run multiple containerized applications <Cite n={2} />.

</Technical>

## How it works

<Voices>
<Technical>

**Client and daemon.** Docker uses a client-server architecture <Cite n={1} />. When you use commands such as `docker run`, the Docker client (`docker`) sends these commands to the Docker daemon (`dockerd`), which carries them out <Cite n={1} />. The daemon listens for Docker API requests and manages Docker objects such as images, containers, networks, and volumes <Cite n={1} />. The client and daemon communicate using a REST API, over UNIX sockets or a network interface <Cite n={1} />. When you use `docker pull` or `docker run`, Docker pulls the required images from your configured registry <Cite n={1} />.

This diagram is the tutorial's own summary of those sentences:

```text
you ── docker run ──> Docker client (docker)
                            │  REST API
                            ▼
                     Docker daemon (dockerd) ── pull ──> registry (Docker Hub by default)
                            │
              manages images, containers, networks, volumes
```

**What `docker run` does.** Docker's overview follows `docker run -i -t ubuntu /bin/bash` step by step <Cite n={1} />:

1. If you don't have the `ubuntu` image locally, Docker pulls it from your configured registry <Cite n={1} />.
2. Docker creates a new container <Cite n={1} />.
3. Docker allocates a read-write filesystem to the container, as its final layer <Cite n={1} />.
4. Docker creates a network interface to connect the container to the default network, which includes assigning an IP address to the container <Cite n={1} />.
5. Docker starts the container and executes `/bin/bash` <Cite n={1} />.
6. When you run `exit`, the container stops but isn't removed. You can start it again or remove it <Cite n={1} />.

**Images are made of layers.** Images are immutable: once an image is created, it can't be modified <Cite n={3} />. Container images are composed of layers, and each layer represents a set of file system changes <Cite n={3} />. Each instruction in a Dockerfile creates a layer in the image <Cite n={1} />. When you change the Dockerfile and rebuild the image, only those layers which have changed are rebuilt <Cite n={1} />.

**The container's own layer.** By default, all files created inside a container are stored on a writable container layer that sits on top of the read-only, immutable image layers <Cite n={5} />. Data written to the container layer doesn't persist when the container is destroyed <Cite n={5} />. [Docker in Practice](/devops/docker-in-practice/) shows how volumes keep data.

**Isolation.** Docker uses a technology called namespaces to provide the isolated workspace called the container <Cite n={1} />. Each aspect of a container runs in a separate namespace, and its access is limited to that namespace <Cite n={1} />.

**Ports.** All ports of containers on bridge networks are accessible from the Docker host and other containers connected to the same network <Cite n={6} />. They are not accessible from outside the host <Cite n={6} />. The `--publish` or `-p` flag makes a port available outside the host: `-p 8080:80` maps port 8080 on the Docker host to TCP port 80 in the container <Cite n={6} />.

</Technical>

**Port।** bridge network-এ থাকা container-এর সব port Docker host আর একই network-এ যুক্ত অন্য container থেকে পাওয়া যায় <Cite n={6} />। host-এর বাইরে থেকে এগুলো পাওয়া যায় না <Cite n={6} />। `--publish` বা `-p` flag একটা port host-এর বাইরে খুলে দেয়: `-p 8080:80` Docker host-এর port 8080-কে container-এর TCP port 80-এর সাথে map করে <Cite n={6} />।

## Try it

<Voices>
<Technical>

This practice run needs only Docker. Docker Desktop delivers all Docker tools to a Mac, a Windows computer, or a Linux computer <Cite n={7} />. On Ubuntu, you can also install Docker Engine <Cite n={8} />. The tutorial ran these steps on 2026-11-16 with Docker Engine 29.9.3 on Linux. Your IDs, sizes, and times will differ.

**1. Check the install.** Run the `hello-world` image <Cite n={8} />. The command downloads a test image and runs it in a container; the container prints a confirmation message and exits <Cite n={8} />. After you install Docker Engine on Ubuntu, the `docker` group exists but contains no users, so you need `sudo` to run Docker commands until you follow the post-installation steps for Linux <Cite n={8} />.

```bash
docker run hello-world
```

The start of the output, from the tutorial's run:

```text
Hello from Docker!
This message shows that your installation appears to be working correctly.
```

**2. Pull an image and look at its layers.** `docker pull` downloads an image from a registry <Cite n={9} />. If no tag is provided, Docker Engine uses the `:latest` tag as a default <Cite n={9} />. `docker image ls` lists the images on your system, and `docker image history` lists the layers of an image <Cite n={3} />:

```bash
docker pull docker/welcome-to-docker
docker image ls
docker image history docker/welcome-to-docker
```

Docker prints the digest of the image after the pull has finished <Cite n={9} />. In the tutorial's run, the newest layer of the history copied `/app/build` to `/usr/share/nginx/html` (Docker's own example has the same line <Cite n={3} />):

```text
IMAGE          CREATED         CREATED BY                                      SIZE
c4d56c24da4f   15 months ago   COPY /app/build /usr/share/nginx/html # buil…   1.65MB
```

**3. Run it.** `-d` runs the container in the background and prints the container ID <Cite n={10} />. `--name` assigns a name to the container <Cite n={10} />. With the localhost IP address in the publish flag, only the Docker host can access the published port <Cite n={6} />:

```bash
docker run -d -p 127.0.0.1:8080:80 --name welcome docker/welcome-to-docker
```

Then visit `http://localhost:8080` in your browser <Cite n={2} />.

**4. Look inside.** `docker ps` shows the running containers <Cite n={2} />. `docker logs` fetches the logs of a container <Cite n={12} />. `docker exec` executes a command in a running container <Cite n={13} />:

```bash
docker ps
docker logs welcome
docker exec welcome ls /usr/share/nginx/html
```

From the tutorial's run, `docker ps` showed the port mapping, and `ls` listed these files:

```text
CONTAINER ID   IMAGE                      ...   STATUS         PORTS                    NAMES
a35d70cab22a   docker/welcome-to-docker   ...   Up 2 seconds   127.0.0.1:8080->80/tcp   welcome

50x.html
asset-manifest.json
favicon.ico
index.html
robots.txt
static
```

**5. Stop and remove it.** `docker stop` stops one or more running containers <Cite n={14} />. By default, `docker ps` shows just running containers; `-a` shows all containers <Cite n={11} />. `docker rm` removes one or more containers <Cite n={15} />. ```


## How a tester uses it

<Voices>
<Technical>

**Start the dependencies of a test.** Testcontainers is an open source library for providing throwaway, lightweight instances of databases, message brokers, web browsers, or just about anything that can run in a Docker container <Cite n={18} />. You define your test dependencies as code; when you run your tests, containers are created and then deleted <Cite n={18} />. The project says that your tests will always start with a known state <Cite n={18} />.

**Run browser tests in a container.** Playwright publishes a Docker image that includes the Playwright browsers and browser system dependencies <Cite n={19} />. The Playwright package is not included in the image and should be installed separately <Cite n={19} />. The image is intended to be used for testing and development purposes only <Cite n={19} />. For end-to-end tests on trusted websites, Playwright's example starts a shell in the image <Cite n={19} />:

```bash
docker run -it --rm --ipc=host mcr.microsoft.com/playwright:v1.64.1-noble /bin/bash
```

Using `--ipc=host` is recommended when using Chromium <Cite n={19} />. [CI/CD Pipelines](/devops/ci-cd/) shows a pipeline that runs Playwright tests.

That lets you pin an image to that version and guarantee that the image you're using is always the same <Cite n={9} />. `docker image ls --digests` shows the digests of your images <Cite n={16} />.

**Collect evidence for a bug report.** `docker logs --timestamps` adds an RFC3339Nano timestamp to each log entry <Cite n={12} />. The `--since` option shows only the container logs generated after a given date, or a relative time such as `42m` for 42 minutes <Cite n={12} />. `docker inspect` returns low-level information on Docker objects, and by default it renders the results in a JSON array <Cite n={17} />.

**Throw a test environment away.** Data written to the container layer doesn't persist when the container is destroyed <Cite n={5} />. Each run of `docker run --rm` starts a new container from the image, and the container is removed when it exits <Cite n={10} />.

## Common mistakes

<Voices>
<Technical>

- **Keeping test data in the container.** Data written to the container layer doesn't persist when the container is destroyed <Cite n={5} />. Keep data that must survive in a volume ([Docker in Practice](/devops/docker-in-practice/)).
- **Publishing a port to everyone.** Publishing container ports is insecure by default: a published port becomes available not only to the Docker host, but to the outside world as well <Cite n={6} />. Include `127.0.0.1` in the publish flag, so that only the Docker host can access the port <Cite n={6} />.
- **Relying on a tag alone.** If no tag is provided, Docker Engine uses the `:latest` tag as a default <Cite n={9} />, and `ubuntu:24.04` pulls the latest version of the Ubuntu 24.04 image <Cite n={9} />. Pull by digest when you need the same image every time <Cite n={9} />.
- **A Playwright image that does not match the project.** If the Playwright version in your Docker image does not match the version in your project or tests, Playwright will be unable to locate browser executables <Cite n={19} />.
- **Looking for a stopped container with `docker ps`.** `docker ps` shows only running containers; add `-a` to list all containers <Cite n={2} />.
- **Expecting a slow shutdown to finish.** If the container does not exit after the timeout elapses, it's forcibly killed with a `SIGKILL` signal <Cite n={14} />. `--timeout` sets the number of seconds to wait <Cite n={14} />.

</Technical>
<Layman>

- **Keeping test data in the container.** When the container is destroyed, the data in its own layer is gone <Cite n={5} />. Keep data that must stay in a volume ([Docker in Practice](/devops/docker-in-practice/)).

- **Relying on a tag alone.** If you give no tag, Docker uses `:latest` <Cite n={9} />, and `ubuntu:24.04` gets the latest version of the Ubuntu 24.04 image <Cite n={9} />. Pull by digest when you need the same image every time <Cite n={9} />.
- **A Playwright image that does not match the project.** If the Playwright version in the image is not the version in your project, Playwright cannot find the browsers <Cite n={19} />.
- **Looking for a stopped container with `docker ps`.** `docker ps` shows only running containers; add `-a` to see them all <Cite n={2} />.
- **Expecting a slow shutdown to finish.** If the container has not stopped when the wait time is over, Docker kills it with a `SIGKILL` signal <Cite n={14} />. `--timeout` sets how many seconds to wait <Cite n={14} />.

## Key words

| Term | Meaning |
|---|---|
| Docker | An open platform for developing, shipping, and running applications |
| Container | A runnable instance of an image: an isolated process with all of the files it needs to run |
| Image | A standardized package with all of the files, binaries, libraries, and configurations to run a container |
| Layer | A set of file system changes; an image is composed of layers |
| Writable container layer | Where the files created inside a container are stored; its data doesn't persist when the container is destroyed |
| Registry | A centralized location for storing and sharing container images |
| Docker Hub | A public registry that anyone can use, and the default registry |
| Docker daemon (`dockerd`) | Listens for Docker API requests and manages images, containers, networks, and volumes |
| Docker client (`docker`) | Sends commands such as `docker run` to the daemon |
| Tag (`:latest`) | `:latest` is the tag that Docker Engine uses as a default when no tag is provided |
| Digest | Pulling by digest specifies exactly which version of an image to pull |
| Publish (`-p`) | Makes a container port available outside the host, as in `-p 8080:80` |
| Namespaces | The technology that Docker uses to provide the isolated workspace called the container |
