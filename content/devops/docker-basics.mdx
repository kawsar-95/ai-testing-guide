# Docker Basics

This page explains Docker for a tester: what containers, images, and registries are, how the Docker client and daemon run a container, and the first commands, with a practice run that you can repeat on your own machine. It ends with the ways that a tester uses containers. [Docker Images and Compose](/devops/docker-images-compose/) builds on it.

## What it is

<Voices>
<Technical>

Docker Engine is an open source containerization technology for building and containerizing your applications <Cite n={1} />. A container is an ordinary process on your computer, such as a Node.js server, that runs in isolation <Cite n={2} />. Because everything the app needs is inside, a container doesn't depend on what is installed on your machine <Cite n={2} />.

**Three words to know.**

| Word | What it is |
|---|---|
| Container | An ordinary process on your computer, such as a Node.js server, that runs in isolation <Cite n={2} />. Its files come from an image <Cite n={2} /> |
| Image | A package of everything a container needs to start: the operating system files, the language runtime, the app's dependencies and code, and settings such as which command to run <Cite n={2} /> |
| Registry | A service that stores images so anyone with access can pull them <Cite n={2} />. Docker Hub (docker.io) is Docker's public registry and the default one <Cite n={2} />. Docker Hub provides a container registry for storing, managing, and sharing Docker images <Cite n={4} /> |

**Why a tester cares.** Docker's guide says that each difference between machines is a chance for the app to work on one machine and fail on another <Cite n={2} />. Ten containers started from the same image start from exactly the same files, today or next month <Cite n={2} />. Delete a container and nothing else on your machine changes <Cite n={2} />.

**Containers and virtual machines.** A virtual machine (VM) also isolates software, but it does so by pretending to be a whole computer <Cite n={2} />. Every VM boots its own complete operating system, including its own kernel, the core of the operating system that talks to the hardware <Cite n={2} />. A container is still a process, so every container on a machine shares that machine's kernel <Cite n={2} />. There is no operating system to boot, which is why a container starts in about a second and why one machine can run many of them <Cite n={2} />. The trade-off is that a VM's isolation is stronger: containers that share a kernel are separated by that kernel, while VMs are separated by the hardware boundary the hypervisor creates <Cite n={2} />. In practice, you'll often use both <Cite n={2} />. Cloud servers are usually VMs that run many containers each <Cite n={2} />.

## How it works

<Voices>
<Technical>

**Client and daemon.** Docker Engine acts as a client-server application <Cite n={1} />. It has a server with a long-running daemon process, `dockerd` <Cite n={1} />. It has APIs, which specify interfaces that programs can use to talk to and instruct the Docker daemon <Cite n={1} />. It has a command line interface (CLI) client, `docker` <Cite n={1} />. The CLI uses Docker APIs to control or interact with the Docker daemon through scripting or direct CLI commands <Cite n={1} />. The daemon creates and manages Docker objects, such as images, containers, networks, and volumes <Cite n={1} />. The Docker Engine API is a RESTful API accessed by an HTTP client such as wget or curl, or the HTTP library which is part of most modern programming languages <Cite n={21} />. The REST API endpoint (used by the Docker CLI to communicate with the Docker daemon) now uses a Unix socket instead of a TCP socket bound on 127.0.0.1 <Cite n={20} />. You can also expose the REST API over HTTP if you explicitly decide to do so <Cite n={20} />.

**Pulling images.** `docker pull` downloads an image from a registry without running it <Cite n={2} />. `docker run` pulls the image it needs if it isn't on your machine yet <Cite n={2} />. If you don't name a registry, Docker uses Docker Hub <Cite n={2} />.

This diagram is the tutorial's own summary of the sentences above about the client, the daemon, and pulling images:

```text
you ── docker run ──> Docker client (docker)
                            │  REST API
                            ▼
                     Docker daemon (dockerd) ── pull ──> registry (Docker Hub by default)
                            │
              manages images, containers, networks, volumes
```

**What `docker run` does.** The `docker run` command runs a command in a new container, pulling the image if needed and starting the container <Cite n={10} />. The list below is what the Docker pages say about it. The order is the tutorial's own:

1. With `--pull`, the value `missing` is the default: it pulls the image if it was not found in the image cache, or uses the cached image otherwise <Cite n={10} />.
2. When a container starts, it uses the image's layers as they are and adds one thin writable layer of its own on top <Cite n={2} />.
3. When you start Docker, a default bridge network (also called bridge) is created automatically, and newly-started containers connect to it unless otherwise specified <Cite n={23} />.
4. A stopped container isn't gone: its configuration and its writable layer are kept <Cite n={22} />.
5. You can restart a stopped container with all its previous changes intact using `docker start` <Cite n={10} />.

**Images are made of layers.** Images are immutable: once built, an image never changes <Cite n={2} />. An image isn't one big file; it's an ordered stack of layers, each one a set of filesystem changes: files added, changed, or deleted <Cite n={3} />. Each Dockerfile instruction that changes files produces one layer, and once a layer is created, it never changes <Cite n={3} />. Docker reuses a layer from an earlier build only when nothing it depends on has changed <Cite n={3} />.

**The container's own layer.** By default, all files created inside a container are stored on a writable container layer that sits on top of the read-only, immutable image layers <Cite n={5} />. Data written to the container layer doesn't persist when the container is destroyed <Cite n={5} />. [Docker in Practice](/devops/docker-in-practice/) shows how volumes keep data.

**Isolation.** When you start a container with `docker run`, behind the scenes Docker creates a set of namespaces and control groups for the container <Cite n={20} />. Namespaces provide the first and most straightforward form of isolation <Cite n={20} />. Processes running within a container cannot see, and even less affect, processes running in another container, or in the host system <Cite n={20} />.

**Ports.** All ports of containers on bridge networks are accessible from the Docker host and other containers connected to the same network <Cite n={6} />. They are not accessible from outside the host <Cite n={6} />. The `--publish` or `-p` flag makes a port available outside the host: `-p 8080:80` maps port 8080 on the Docker host to TCP port 80 in the container <Cite n={6} />.

</Technical>

**`docker run` কী করে।** `docker run` command একটা নতুন container-এ একটা command চালায়, দরকার হলে image pull করে এবং container চালু করে <Cite n={10} />। নিচের তালিকা Docker-এর page এ-বিষয়ে যা বলে তা-ই। ক্রমটা টিউটোরিয়ালের নিজের:

1. `--pull`-এর মান `missing` হলো default: image, image cache-এ না পাওয়া গেলে Docker সেটা pull করে, নইলে cache-এ থাকা image ব্যবহার করে <Cite n={10} />।
2. একটা container চালু হলে সেটা image-এর layer যেমন আছে তেমনই ব্যবহার করে, আর নিজের একটা পাতলা writable layer ওপরে যোগ করে <Cite n={2} />।
3. আপনি Docker চালু করলে একটা default bridge network (যাকে bridge-ও বলে) নিজে থেকেই তৈরি হয়, আর নতুন চালু হওয়া container অন্য কিছু ঠিক করা না থাকলে সেটায় যুক্ত হয় <Cite n={23} />।
4. থেমে যাওয়া একটা container হারিয়ে যায় না: তার configuration আর তার writable layer রাখা থাকে <Cite n={22} />।
5. `docker start` দিয়ে আপনি থেমে যাওয়া একটা container তার আগের সব পরিবর্তন অক্ষত রেখে আবার চালু করতে পারেন <Cite n={10} />।

**Image layer দিয়ে তৈরি।** image immutable: একবার তৈরি হলে আর কখনো বদলায় না <Cite n={2} />। image একটা বড় file নয়; সেটা layer-এর একটা ক্রমবদ্ধ স্তূপ, যার প্রতিটা layer file system-এর একসেট পরিবর্তন: file যোগ, বদল বা মোছা <Cite n={3} />। file বদলায় এমন প্রতিটা Dockerfile instruction একটা করে layer তৈরি করে, আর একটা layer তৈরি হওয়ার পর সেটা আর কখনো বদলায় না <Cite n={3} />। আগের build-এর একটা layer Docker শুধু তখনই আবার ব্যবহার করে, যখন সেটা যার ওপর নির্ভর করে তার কিছুই বদলায়নি <Cite n={3} />।

**Container-এর নিজের layer।** default-ভাবে container-এর ভেতরে তৈরি সব file একটা writable container layer-এ থাকে, যেটা image-এর read-only, immutable layer-গুলোর ওপরে বসে <Cite n={5} />। container ধ্বংস হলে container layer-এ লেখা data থাকে না <Cite n={5} />। volume কীভাবে data রাখে, তা [Docker in Practice](/devops/docker-in-practice/) পেজে আছে।

**আলাদা রাখা (isolation)।** আপনি `docker run` দিয়ে একটা container চালু করলে Docker পর্দার আড়ালে container-এর জন্য namespace আর control group-এর একটা সেট তৈরি করে <Cite n={20} />। namespace হলো isolation-এর প্রথম ও সবচেয়ে সরাসরি রূপ <Cite n={20} />। একটা container-এর ভেতরে চলা process অন্য container বা host system-এর process দেখতেই পারে না, প্রভাব ফেলা তো দূরের কথা <Cite n={20} />।

**Port।** bridge network-এ থাকা container-এর সব port Docker host আর একই network-এ যুক্ত অন্য container থেকে পাওয়া যায় <Cite n={6} />। host-এর বাইরে থেকে এগুলো পাওয়া যায় না <Cite n={6} />। `--publish` বা `-p` flag একটা port host-এর বাইরে খুলে দেয়: `-p 8080:80` Docker host-এর port 8080-কে container-এর TCP port 80-এর সাথে map করে <Cite n={6} />।

## How a tester uses it

<Voices>
<Technical>

**Start the dependencies of a test.** Testcontainers is an open source library for providing throwaway, lightweight instances of databases, message brokers, web browsers, or just about anything that can run in a Docker container <Cite n={18} />. You define your test dependencies as code; when you run your tests, containers are created and then deleted <Cite n={18} />. The project says that your tests will always start with a known state <Cite n={18} />.

**Run browser tests in a container.** Playwright publishes a Docker image that includes the Playwright browsers and browser system dependencies <Cite n={19} />. The Playwright package is not included in the image and should be installed separately <Cite n={19} />. The image is intended to be used for testing and development purposes only <Cite n={19} />. For end-to-end tests on trusted websites, Playwright's example starts a shell in the image <Cite n={19} />:

```bash
docker run -it --rm --ipc=host mcr.microsoft.com/playwright:v1.64.1-noble /bin/bash
```

Using `--ipc=host` is recommended when using Chromium <Cite n={19} />. [CI/CD Pipelines](/devops/ci-cd/) shows a pipeline that runs Playwright tests.

**Know which image you tested.** `docker pull ubuntu:24.04` pulls the latest version of the Ubuntu 24.04 image <Cite n={9} />. When you pull an image by digest, you specify exactly which version of an image to pull <Cite n={9} />. That lets you pin an image to that version and guarantee that the image you're using is always the same <Cite n={9} />. `docker image ls --digests` shows the digests of your images <Cite n={16} />.

**Collect evidence for a bug report.** `docker logs --timestamps` adds an RFC3339Nano timestamp to each log entry <Cite n={12} />. The `--since` option shows only the container logs generated after a given date, or a relative time such as `42m` for 42 minutes <Cite n={12} />. `docker inspect` returns low-level information on Docker objects, and by default it renders the results in a JSON array <Cite n={17} />.

**Throw a test environment away.** Data written to the container layer doesn't persist when the container is destroyed <Cite n={5} />. Each run of `docker run --rm` starts a new container from the image, and the container is removed when it exits <Cite n={10} />.


Chromium ব্যবহার করলে `--ipc=host` দেওয়ার পরামর্শ দেওয়া হয় <Cite n={19} />। Playwright test চালানো একটা pipeline [CI/CD Pipelines](/devops/ci-cd/) পেজে আছে।

**কোন image test করেছেন, জানুন।** `docker pull ubuntu:24.04` Ubuntu 24.04 image-এর সর্বশেষ version pull করে <Cite n={9} />। digest দিয়ে image pull করলে আপনি ঠিক কোন version চান, সেটা নির্দিষ্ট করেন <Cite n={9} />। এতে image সেই version-এ pin হয়, আর নিশ্চিত হয় যে আপনি সবসময় একই image ব্যবহার করছেন <Cite n={9} />। `docker image ls --digests` আপনার image-গুলোর digest দেখায় <Cite n={16} />।

**bug report-এর প্রমাণ জোগাড় করুন।** `docker logs --timestamps` প্রতিটা log entry-তে একটা RFC3339Nano timestamp যোগ করে <Cite n={12} />। `--since` option শুধু একটা নির্দিষ্ট সময়ের পরে তৈরি log দেখায়, অথবা `42m`-এর মতো আপেক্ষিক সময় (42 মিনিট) <Cite n={12} />। `docker inspect` Docker object-এর low-level তথ্য দেয়, আর default-ভাবে ফল একটা JSON array-তে দেখায় <Cite n={17} />।

**test environment ফেলে দিন।** container ধ্বংস হলে container layer-এ লেখা data থাকে না <Cite n={5} />। প্রতিবার `docker run --rm` image থেকে একটা নতুন container শুরু করে, আর container বেরিয়ে গেলে সেটা মুছে যায় <Cite n={10} />।

</Bangla>
</Voices>

## Common mistakes

<Voices>
<Technical>

- **Keeping test data in the container.** Data written to the container layer doesn't persist when the container is destroyed <Cite n={5} />. Keep data that must survive in a volume ([Docker in Practice](/devops/docker-in-practice/)).
- **Publishing a port to everyone.** Publishing container ports is insecure by default: a published port becomes available not only to the Docker host, but to the outside world as well <Cite n={6} />. Include `127.0.0.1` in the publish flag, so that only the Docker host can access the port <Cite n={6} />.
- **Relying on a tag alone.** If no tag is provided, Docker Engine uses the `:latest` tag as a default <Cite n={9} />, and `ubuntu:24.04` pulls the latest version of the Ubuntu 24.04 image <Cite n={9} />. Pull by digest when you need the same image every time <Cite n={9} />.
- **A Playwright image that does not match the project.** If the Playwright version in your Docker image does not match the version in your project or tests, Playwright will be unable to locate browser executables <Cite n={19} />.
- **Looking for a stopped container with `docker ps`.** `docker ps` shows only running containers; `docker ps -a` shows all of them <Cite n={22} />.
- **Expecting a slow shutdown to finish.** If the container does not exit after the timeout elapses, it's forcibly killed with a `SIGKILL` signal <Cite n={14} />. `--timeout` sets the number of seconds to wait <Cite n={14} />.

</Technical>
<Layman>

- **Keeping test data in the container.** When the container is destroyed, the data in its own layer is gone <Cite n={5} />. Keep data that must stay in a volume ([Docker in Practice](/devops/docker-in-practice/)).
- **Opening a port to everyone.** Publishing a port is not safe by default: the port is open not only to the Docker host, but to the outside world too <Cite n={6} />. Put `127.0.0.1` in the publish flag, so that only the Docker host can reach the port <Cite n={6} />.
- **Relying on a tag alone.** If you give no tag, Docker uses `:latest` <Cite n={9} />, and `ubuntu:24.04` gets the latest version of the Ubuntu 24.04 image <Cite n={9} />. Pull by digest when you need the same image every time <Cite n={9} />.
- **A Playwright image that does not match the project.** If the Playwright version in the image is not the version in your project, Playwright cannot find the browsers <Cite n={19} />.
- **Looking for a stopped container with `docker ps`.** `docker ps` shows only running containers; `docker ps -a` shows all of them <Cite n={22} />.
- **Expecting a slow shutdown to finish.** If the container has not stopped when the wait time is over, Docker kills it with a `SIGKILL` signal <Cite n={14} />. `--timeout` sets how many seconds to wait <Cite n={14} />.

</Layman>
<Bangla>

- **container-এ test data রাখা।** container ধ্বংস হলে container layer-এ লেখা data থাকে না <Cite n={5} />। যে data থাকতে হবে, তা একটা volume-এ রাখুন ([Docker in Practice](/devops/docker-in-practice/))।
- **সবার জন্য port publish করা।** container port publish করা default-ভাবে অনিরাপদ: publish করা port শুধু Docker host-এর জন্য নয়, বাইরের দুনিয়ার জন্যও খুলে যায় <Cite n={6} />। publish flag-এ `127.0.0.1` দিন, যাতে শুধু Docker host-ই port-এ পৌঁছাতে পারে <Cite n={6} />।
- **শুধু tag-এর ওপর ভরসা করা।** কোনো tag না দিলে Docker Engine default হিসেবে `:latest` tag ব্যবহার করে <Cite n={9} />, আর `ubuntu:24.04` Ubuntu 24.04 image-এর সর্বশেষ version pull করে <Cite n={9} />। প্রতিবার একই image দরকার হলে digest দিয়ে pull করুন <Cite n={9} />।
- **project-এর সাথে না মেলা Playwright image।** Docker image-এর Playwright version আপনার project বা test-এর version-এর সাথে না মিললে Playwright browser executable খুঁজে পাবে না <Cite n={19} />।
- **`docker ps` দিয়ে থেমে যাওয়া container খোঁজা।** `docker ps` শুধু চলমান container দেখায়; `docker ps -a` সবগুলো দেখায় <Cite n={22} />।
- **ধীর shutdown শেষ হবে ভাবা।** timeout শেষ হওয়ার পরও container বেরিয়ে না গেলে `SIGKILL` signal দিয়ে জোর করে বন্ধ করা হয় <Cite n={14} />। `--timeout` কত সেকেন্ড অপেক্ষা করবে, তা ঠিক করে <Cite n={14} />।

## What a tester can check

<Voices>
<Technical>

<Callout type="tip" title="Tutorial advice">
This list is the tutorial's own advice for a tester on a team that uses Docker.

- Ask which image, tag, and digest each test environment runs, and put them in your bug reports.
- Ask whether the databases and services that your tests need run in containers with fixed versions.
- On a shared machine, publish test ports to `127.0.0.1` only.
- Use `--rm` for throwaway runs, so that stopped containers do not pile up.
- Save `docker logs --timestamps` for the time window of a failure.
- Keep the version of the Playwright image equal to the Playwright version of the project.
</Callout>

## Key words

| Term | Meaning |
|---|---|
| Docker Engine | An open source containerization technology for building and containerizing your applications |
| Container | An ordinary process on your computer, such as a Node.js server, that runs in isolation; its files come from an image |
| Image | A package of everything a container needs to start; the operating system files, the language runtime, the app's dependencies and code, and settings such as which command to run |
| Layer | A set of filesystem changes; files added, changed, or deleted; an image is an ordered stack of layers |
| Writable container layer | Where the files created inside a container are stored; its data doesn't persist when the container is destroyed |
| Registry | A service that stores images so anyone with access can pull them |
| Docker Hub | Docker's public registry and the default one |
| Docker daemon (`dockerd`) | A server with a long-running daemon process; the daemon creates and manages Docker objects, such as images, containers, networks, and volumes |
| Docker client (`docker`) | A command line interface (CLI) client; the CLI uses Docker APIs to control or interact with the Docker daemon |
| Tag (`:latest`) | `:latest` is the tag that Docker Engine uses as a default when no tag is provided |
| Digest | Pulling by digest specifies exactly which version of an image to pull |
| Publish (`-p`) | Makes a container port available outside the host, as in `-p 8080:80` |
| Namespaces | Docker creates a set of namespaces and control groups for the container; namespaces provide the first and most straightforward form of isolation |
