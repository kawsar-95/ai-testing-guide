# CNCF Projects: Runtime, Scheduling, and Data

This page covers the CNCF and two of its projects, containerd and Rook, and where the Kubernetes scheduler fits between them. The practice run starts containerd as a normal user, renders the Rook Helm charts, and uses a short-lived kind cluster (Docker, no cloud account) to watch the scheduler. It follows [CNCF Projects: Build and Deliver](/devops/cncf-build-deliver/) and precedes [CNCF Projects: Networking, Security, and Observability](/devops/cncf-network-security-observability/).

<Technical>

**The CNCF and its stages.** The Cloud Native Computing Foundation (CNCF) hosts critical components of the global technology infrastructure <Cite n={1} />. CNCF is part of the nonprofit Linux Foundation <Cite n={1} />. Its Technical Oversight Committee (TOC) defines 4 stages of the project lifecycle <Cite n={3} />. The CNCF projects page says that graduated and incubating projects are considered stable and are used successfully in production environments <Cite n={2} />. The TOC describes Incubation projects as projects gaining adoption, focusing on improving stability and maturity <Cite n={3} />. It describes Graduated projects as highly mature, robust projects whose adopters have demonstrated their production-readiness by their deployment to production environments <Cite n={3} />.

**The two projects.** The CNCF page says that containerd was accepted on March 29, 2017 at the Incubating maturity level <Cite n={4} />. containerd moved to the Graduated maturity level on February 28, 2019 <Cite n={4} />. The CNCF Rook page says that Rook was accepted on January 29, 2018 <Cite n={5} />. Rook moved to the Incubating maturity level on September 25, 2018 <Cite n={5} />. Rook moved to the Graduated maturity level on October 7, 2020 <Cite n={5} />. The project pages call containerd an open and reliable container runtime <Cite n={4} />, and Rook storage orchestration for Kubernetes <Cite n={5} />.

**containerd: the daemon on the node.** containerd calls itself an industry-standard container runtime with an emphasis on simplicity, robustness and portability <Cite n={6} />. The README says that it is available as a daemon for Linux and Windows <Cite n={7} />. The daemon can manage the complete container lifecycle of its host system <Cite n={7} />. The README also says that containerd is designed to be embedded into a larger system, rather than being used directly by developers or end-users <Cite n={7} />.

**Where containerd sits.** The Kubernetes docs say that you need a working container runtime on each Node, so that the kubelet can launch Pods and their containers <Cite n={20} />. The Container Runtime Interface (CRI) is the main protocol for the communication between the kubelet and the container runtime <Cite n={20} />. The containerd docs say that containerd has built-in support for the CRI <Cite n={8} />. They say that containerd operates on the same node as the kubelet, and that its cri plugin handles all CRI service requests from the kubelet <Cite n={15} />.

**Scheduling: who picks the node.** kube-scheduler is the default scheduler for Kubernetes, and it runs as part of the control plane <Cite n={23} />. A scheduler watches for newly created Pods that have no Node assigned <Cite n={23} />. It finds the feasible Nodes for a Pod, scores them, and picks a Node with the highest score <Cite n={23} />.

**Rook: Ceph storage run by an operator.** Rook is an open source cloud-native storage orchestrator <Cite n={30} />. Ceph is a distributed storage system that provides file, block and object storage <Cite n={30} />. Rook automates deployment and management of Ceph to provide self-managing, self-scaling, and self-healing storage services <Cite n={30} />. The Rook operator does this by building on Kubernetes resources to deploy, configure, provision, scale, upgrade, and monitor Ceph <Cite n={30} />.

**Custom resources and operators.** A custom resource is an extension of the Kubernetes API that is not necessarily available in a default Kubernetes installation <Cite n={24} />. The CustomResourceDefinition API resource allows you to define custom resources <Cite n={24} />. Operators are clients of the Kubernetes API that act as controllers for a Custom Resource <Cite n={26} />. The most common way to deploy an operator is to add the Custom Resource Definition and its associated Controller to your cluster <Cite n={26} />. The Rook glossary says that the CephCluster CRD is used by Rook to allow creation and customization of storage clusters <Cite n={31} />.

## How it works

<Voices>
<Technical>

**Plugins and a smart client.** containerd supports extending its functionality using most of its defined interfaces <Cite n={10} />. This includes using a customized runtime, snapshotter, content store, and even adding gRPC interfaces <Cite n={10} />. containerd uses plugins internally, so that its internal implementations are decoupled, stable, and treated equally with external plugins <Cite n={10} />. To see all the plugins, use `ctr plugins ls` <Cite n={10} />. In the output, you can see all the plugins, also those that did not load successfully <Cite n={10} />. containerd has a smart client architecture, meaning that any functionality that the daemon does not require is done by the client <Cite n={10} />. That includes most high level interactions, such as creating a container's specification, interacting with an image registry, and loading an image from tar <Cite n={10} />.

**Namespaces.** containerd offers a fully namespaced API, so that multiple consumers can use a single containerd instance without conflicting with one another <Cite n={9} />. Underlying image content is still shared via content addresses, but image names and metadata are separate per namespace <Cite n={9} />. The docs call namespaces an administrative construct that is not meant to be used as a security feature <Cite n={9} />. They add that it is trivial for clients to switch namespaces <Cite n={9} />. If you do not provide a namespace, `ctr` client commands use the default namespace, which is named "default" <Cite n={9} />. The `--namespace` or `-n` flag of `ctr` changes it <Cite n={9} />.

**The command line tools.** The containerd docs list several command line projects for interacting with containerd <Cite n={8} />. The `ctr` tool is bundled together with containerd, and the docs note that it is solely made for debugging containerd <Cite n={8} />. The docs say that the `nerdctl` tool provides a stable and human-friendly user experience <Cite n={8} />. The Kubernetes docs say that `crictl` is a command-line interface for CRI-compatible container runtimes <Cite n={22} />. You can use it to inspect and debug container runtimes and applications on a Kubernetes node <Cite n={22} />.

**Content flow: registry, content store, snapshots.** Content exists in several areas in the containerd lifecycle <Cite n={12} />. They are an OCI registry, the containerd content store, and snapshots <Cite n={12} />. To create a container, the image and all its content must be loaded into the local content store <Cite n={12} />. **Plugin আর smart client।** containerd তার বেশিরভাগ interface দিয়ে নিজের কার্যক্ষমতা বাড়ানোর সুযোগ দেয় <Cite n={10} />। এর মধ্যে আছে নিজের মতো runtime, snapshotter, content store ব্যবহার করা, এমনকি নতুন gRPC interface যোগ করা <Cite n={10} />। containerd ভেতরেও plugin ব্যবহার করে, যাতে তার ভেতরের implementation আলাদা, স্থিতিশীল আর বাইরের plugin-এর সমান গণ্য হয় <Cite n={10} />। সব plugin দেখতে `ctr plugins ls` ব্যবহার করুন <Cite n={10} />। output-এ সব plugin দেখা যায়, যেগুলো সফলভাবে load হয়নি সেগুলোও <Cite n={10} />। containerd-এর architecture হলো smart client, অর্থাৎ daemon-এর যা না হলেই চলে, সেই কাজ client করে <Cite n={10} />। তার মধ্যে আছে বেশিরভাগ উঁচু স্তরের (high level) কাজ, যেমন container-এর specification বানানো, image registry-র সঙ্গে কথা বলা আর tar থেকে image load করা <Cite n={10} />।

**Namespace।** containerd একটা পুরোপুরি namespace-যুক্ত API দেয়, যাতে অনেক consumer একটা containerd instance ব্যবহার করতে পারে, একে অপরের সঙ্গে সংঘর্ষ না বাধিয়ে <Cite n={9} />। image-এর ভেতরের content এখনও content address দিয়ে ভাগ করা থাকে, কিন্তু image-এর নাম আর metadata প্রতিটা namespace-এ আলাদা <Cite n={9} />। docs namespace-কে বলে একটা প্রশাসনিক কাঠামো, যা security feature হিসেবে ব্যবহারের জন্য নয় <Cite n={9} />। তারা যোগ করে, client-এর পক্ষে namespace বদলানো সহজ <Cite n={9} />। আপনি namespace না দিলে `ctr` client command সব "default" নামের default namespace ব্যবহার করে <Cite n={9} />। `ctr`-এর `--namespace` বা `-n` flag সেটা বদলায় <Cite n={9} />।

**Command line tool।** containerd docs containerd-এর সঙ্গে কাজ করার কয়েকটা command line project-এর তালিকা দেয় <Cite n={8} />। `ctr` tool containerd-এর সঙ্গেই আসে, আর docs উল্লেখ করে, সে কেবল containerd debug করার জন্য বানানো <Cite n={8} />। docs বলে, `nerdctl` tool একটা স্থিতিশীল আর মানুষের জন্য সুবিধাজনক অভিজ্ঞতা দেয় <Cite n={8} />। Kubernetes docs বলে, `crictl` হলো CRI-সামঞ্জস্যপূর্ণ container runtime-এর জন্য একটা command-line interface <Cite n={22} />। আপনি তাকে দিয়ে একটা Kubernetes node-এর container runtime আর application পরীক্ষা ও debug করতে পারেন <Cite n={22} />।

**Content flow: registry, content store, snapshot।** containerd-এর জীবনচক্রে content কয়েকটা জায়গায় থাকে <Cite n={12} />। সেগুলো হলো একটা OCI registry, containerd-এর content store আর snapshot <Cite n={12} />। container বানাতে হলে image আর তার সব content আগে স্থানীয় content store-এ load করতে হবে <Cite n={12} />। তারপর layer-গুলো পড়ে একটা filesystem-এ প্রয়োগ করতে হবে, যাতে একটা committed snapshot তৈরি হয় <Cite n={12} />। এই প্রক্রিয়ার নাম unpacking <Cite n={12} />। শেষ layer-এর ওপর একটা পরিবর্তনযোগ্য, mount করা যায় এমন filesystem, অর্থাৎ active snapshot, বানাতে হবে <Cite n={12} />। তখন সেই active snapshot-কে root filesystem করে একটা container তৈরি করা যায় <Cite n={12} />।

**image আসলে কী।** content-flow doc বলে, একটা image হলো descriptor নামের একটা JSON document দিয়ে গড়া <Cite n={12} />। একটা descriptor-এ সবসময় mediaType নামের একটা উপাদান থাকে, যা বলে সে কোন ধরনের <Cite n={12} />। mediaType হয় manifest, নয় index <Cite n={12} />। OCI spec বলে, একটা image manifest একটা নির্দিষ্ট architecture আর operating system-এর একটা container image-এর জন্য একটা configuration আর একগুচ্ছ layer দেয় <Cite n={18} />। image index-এ নির্দিষ্ট platform-এর manifest-এর তালিকা থাকে <Cite n={19} />। index-এর উদ্দেশ্য হলো লক্ষ্য platform-এর সঙ্গে মেলে এমন manifest বেছে নেওয়া <Cite n={12} />। একটা layer-এর DiffID হলো layer-এর uncompressed tar archive-এর digest <Cite n={17} />। spec সতর্ক করে, DiffID-কে layer digest-এর সঙ্গে গুলিয়ে ফেলা চলবে না, যেগুলো প্রায়ই manifest-এ উল্লেখ করা হয় <Cite n={17} />।

**Content store আর snapshotter।** content store-এ content load হলে সেটা registry যেভাবে রাখে, প্রায় সেভাবেই রাখা হয় <Cite n={12} />। প্রতিটা অংশ এমন একটা file-এ থাকে, যার নাম তার hash <Cite n={12} />। Snapshotter container filesystem-এর snapshot পরিচালনা করে <Cite n={11} />। overlayfs snapshotter হলো default, আর সে Docker-এর "overlay2" storage driver-এর মতো <Cite n={11} />। native snapshotter হলো file কপি করার একটা driver, Docker-এর "vfs" driver-এর মতো <Cite n={11} />। কোন snapshotter আছে, তা `ctr plugins ls` বা `nerdctl info` চালিয়ে দেখা যায় <Cite n={11} />।

**Runtime আর CRI plugin।** containerd একাধিক container runtime সমর্থন করে, আর প্রতিটা container আলাদা runtime দিয়ে চালানো যায় <Cite n={10} />। সে v2 runtime-কে system-এর binary হিসেবে চালায়, যেগুলো shim process শুরু করতে ব্যবহার হয় <Cite n={10} />। README বলে, Linux আর Windows container-এর বেশিরভাগ কাজ runc এবং/অথবা OS-নির্দিষ্ট library দিয়ে সামলানো হয় <Cite n={7} />। CRI plugin kubelet-এর request সামলায়, আর CNI দিয়ে pod-এর networking পরিচালনা করে, যা আরেকটা CNCF project <Cite n={15} />। kubelet একটা pod বানালে plugin pod-এর network namespace বানায় আর CNI দিয়ে সেটা সাজায় <Cite n={15} />। তারপর সে একটা বিশেষ pause container, অর্থাৎ sandbox container, বানায় <Cite n={15} />। পরে node-এ application image না থাকলে সে সেটা pull করে <Cite n={15} />।

**kubelet কী চায়।** kubelet gRPC দিয়ে container runtime-এর সঙ্গে যুক্ত হওয়ার সময় client হিসেবে কাজ করে <Cite n={20} />। Kubernetes v1.26 আর তার পরের সংস্করণে kubelet চায়, container runtime যেন v1 CRI API সমর্থন করে <Cite n={20} />। কোনো container runtime v1 API সমর্থন না করলে kubelet node register করবে না <Cite n={20} />। control group-এর সঙ্গে যোগাযোগের জন্য kubelet আর container runtime-এর একটা cgroup driver লাগে <Cite n={21} />। docs বলে, দুটোই একই cgroup driver ব্যবহার করবে আর একইভাবে সাজানো থাকবে, এটা অত্যন্ত জরুরি <Cite n={21} />। containerd-এর configuration-এ docs runc runtime-এর option-এ `SystemdCgroup = true` দেখায় <Cite n={21} />। তারা বলে, cgroup v2 ব্যবহার করলে systemd cgroup driver সুপারিশ করা হয় <Cite n={21} />।

**Garbage collection আর registry।** containerd-এর garbage collector একটা background goroutine-এ schedule হয়, আর কয়েকটা সাজানো যায় এমন বিষয়ের ওপর ভিত্তি করে চলে <Cite n={13} />। কোনো resource সরানোর সময় client একটা garbage collection-ও চাইতে পারে <Cite n={13} />। garbage collection শেষ না হওয়া পর্যন্ত service ফিরে আসে না <Cite n={13} />। এটা এখন image আর lease সরানোর সময় সমর্থিত <Cite n={13} />। registry-র জন্য containerd একটা configuration directory থেকে প্রতিটা registry host-এর জন্য ঐচ্ছিক `hosts.toml` file পড়ে <Cite n={16} />। কোনো host registry host namespace থেকে আলাদা হলে, যেমন একটা mirror, containerd request-এ registry host namespace-কে `ns` নামের query parameter হিসেবে জুড়ে দেয় <Cite n={16} />।

**root ছাড়া চালানো।** containerd docs বলে, একজন non-root user user_namespaces(7) ব্যবহার করে containerd চালাতে পারে <Cite n={14} />। তারা RootlessKit-কে এমন একটা tool হিসেবে বলে, যা একটা user namespace, একটা mount namespace আর ঐচ্ছিকভাবে একটা network namespace সাজাতে পারে <Cite n={14} />। তারা বলে, আপনাকে নিজের path-সহ একটা `config.toml` দিতে হবে <Cite n={14} />। তারা আরও বলে, `ctr`-এর মতো client-কে daemon-এর namespace-এর ভেতরে চলতে হবে <Cite n={14} />। নিচের practice run কোনো user namespace সাজায় না, আর টিউটোরিয়াল বলে দেয় তাতে কী বদলায়।

**scheduler কীভাবে ঠিক করে।** Kubernetes-এ scheduling মানে Pod-গুলোকে Node-এর সঙ্গে মেলানো, যাতে kubelet সেগুলো চালাতে পারে <Cite n={23} />। scheduler যে Pod-ই খুঁজে পায়, তার জন্য সবচেয়ে ভালো Node খোঁজার দায়িত্ব তার <Cite n={23} />। কোনো node উপযুক্ত না হলে scheduler Pod-টা বসাতে পারা পর্যন্ত pod-টা unscheduled থাকে <Cite n={23} />। তারপর scheduler তার সিদ্ধান্ত API server-কে জানায় binding নামের একটা প্রক্রিয়ায় <Cite n={23} />। Kubernetes নির্দিষ্ট Pod কোথায় schedule করবে তা বাছার একটা উপায় হিসেবে আপনি `nodeSelector` field ব্যবহার করতে পারেন, যা node-এর label-এর সঙ্গে মেলায় <Cite n={41} />। একটা `nodeSelector` কেবল সেই node বাছে, যাতে দেওয়া সব label আছে <Cite n={41} />। Kubernetes একটা cluster-এর সব node-এ একটা প্রমিত label-সেটও বসায় <Cite n={41} />। Affinity আর anti-affinity আপনি যে ধরনের শর্ত দিতে পারেন তা বাড়ায় <Cite n={41} />। আপনি এমন একটা rule-কে নরম বা পছন্দের বলে দিতে পারেন <Cite n={41} />। নরম rule থাকলে মেলে এমন node না পেলেও scheduler Pod-টা schedule করে <Cite n={41} />।

**দুটো Helm chart।** Rook docs একটা Ceph Operator Helm chart-এর কথা বলে, যা Kubernetes-এ Ceph cluster তৈরি, সাজানো আর পরিচালনার জন্য Rook install করে <Cite n={34} />। chart একটা rook-ceph-operator deployment চালু করে <Cite n={34} />। docs তিনটা ধাপ বলে: Helm chart install করা, CSI যাতে volume provision আর mount করতে পারে সেজন্য Ceph-CSI drivers chart install করা, আর একটা Rook cluster তৈরি করা <Cite n={34} />। দ্বিতীয় chart, Ceph Cluster chart, হলো template-এর একটা সরল প্যাকেজ, যা ঐচ্ছিকভাবে Rook resource তৈরি করে <Cite n={35} />। সেই resource হলো CephCluster, CephFilesystem আর CephObjectStore custom resource, storage class, dashboard-এর জন্য একটা ingress আর একটা toolbox <Cite n={35} />। default value একটা করে block pool, filesystem আর object store বানায়, তাদের storage class-সহ <Cite n={35} />।

**CRD আর operator।** operator chart-এ একটা `crds.enabled` setting আছে। সে বলে, Helm chart-এর CRD তৈরি আর হালনাগাদ করা উচিত কি না <Cite n={34} />। এটা false হলে CRD-গুলো আলাদাভাবে `deploy/examples/crds.yaml` দিয়ে পরিচালনা করতে হবে <Cite n={34} />। docs সতর্ক করে, এটা কেবল প্রথম deployment-এর সময় ঠিক করুন, আর পরে বন্ধ করলে cluster ধ্বংস হয়ে যেতে পারে <Cite n={34} />। quickstart-ও CRD দিয়ে শুরু করে: `kubectl create -f crds.yaml -f common.yaml -f csi-operator.yaml`, তারপর `kubectl create -f operator.yaml` <Cite n={32} />। সে বলে, Kubernetes v1.32 থেকে v1.37 পর্যন্ত সংস্করণ সমর্থিত <Cite n={32} />।

**CephCluster কী বলে।** CephCluster CRD docs বলে, `count` কতগুলো mon চালু হবে তা ঠিক করে <Cite n={36} />। সংখ্যাটা ১ থেকে ৯-এর মধ্যে হতে হবে <Cite n={36} />। তারা বলে, সুপারিশ করা মান সাধারণত ৩ <Cite n={36} />। সর্বোচ্চ availability-র জন্য mon-এর সংখ্যা বিজোড় দেওয়া উচিত <Cite n={36} />। quorum ধরে রাখতে mon-এর সংখ্যাগরিষ্ঠকে চালু থাকতে হবে <Cite n={36} />। `dataDirHostPath` হলো host-এর সেই path, যেখানে প্রতিটা service-এর config আর data রাখা উচিত <Cite n={36} />। docs সতর্ক করে, test-এর ক্ষেত্রে একটা cluster মুছে একই host-এ নতুন cluster চালু করলে সেই path মুছে ফেলতে হবে <Cite n={36} />। না হলে আগের cluster-এর পুরনো key আর config থেকে যায়, আর নতুন mon চালু হতে ব্যর্থ হবে <Cite n={36} />।

**Ceph-এর শব্দ আর node-এর পূর্বশর্ত।** Rook glossary Ceph-এর কয়েকটা শব্দের নাম বলে: Ceph Monitor (MON), Ceph Manager (MGR), Ceph Metadata Server (MDS), Object Storage Device (OSD), RADOS Block Device (RBD) আর Ceph Object Gateway (RGW) <Cite n={31} />। Ceph storage cluster সাজাতে এই স্থানীয় storage-এর অন্তত একটা লাগে: raw device, raw partition, LVM logical volume, অথবা block mode-এর storage class থেকে পাওয়া persistent volume <Cite n={33} />। raw device-এ কোনো partition বা formatted filesystem থাকে না, আর raw partition ও LVM logical volume-এ কোনো formatted filesystem থাকে না <Cite n={33} />। পরীক্ষা করতে `lsblk -f` চালান: FSTYPE ঘর ফাঁকা না হলে সেই device-এর ওপর একটা filesystem আছে <Cite n={33} />। সব storage node-এ একটা চালু udev daemon লাগে <Cite n={33} />। Ceph-এর জন্য RBD module-সহ বানানো একটা Linux kernel লাগে <Cite n={33} />। আপনি Ceph shared file system (CephFS) থেকে RWX volume বানালে সুপারিশ করা সর্বনিম্ন kernel সংস্করণ ৪.১৭ <Cite n={33} />।

- `containerd config default` এই সংস্করণের default ছাপিয়েছে। সেগুলো হলো `overlayfs` snapshotter, sandbox image `registry.k8s.io/pause:3.10.2`, default runtime-এর নাম `runc`, runtime type `io.containerd.runc.v2` আর `SystemdCgroup = false`।
- runc-এর সঙ্গে systemd cgroup driver ব্যবহার করতে Kubernetes docs `SystemdCgroup = true` বসাতে বলে <Cite n={21} />। তারা বলে, kubelet আর container runtime একই cgroup driver ব্যবহার করবে, এটা অত্যন্ত জরুরি <Cite n={21} />। ১৪ নম্বর ধাপ একটা kind cluster-এর node-এ দুটো setting-ই পড়ে।

## How a tester uses it

<Voices>
<Technical>

**Read the runtime of a node.** In step 10, `kubectl get nodes -o wide` showed `containerd://2.3.4` for the node of the kind cluster. The docs say that you need a working container runtime on each Node, so that the kubelet can launch Pods and their containers <Cite n={20} />. For Kubernetes v1.26 and later, the kubelet requires that the container runtime supports the v1 CRI API <Cite n={20} />. If a container runtime does not support the v1 API, the kubelet will not register the node <Cite n={20} />. A tester can write the runtime and its version in every test report. The tutorial's machine had containerd 2.4.2, and the node of the kind cluster had containerd 2.3.4.

**Match the cgroup drivers.** The kubelet and the container runtime need a cgroup driver to interface with control groups <Cite n={21} />. The cgroupfs driver is the default cgroup driver in the kubelet <Cite n={21} />. The systemd cgroup driver is recommended if you use cgroup v2 <Cite n={21} />. It is critical that both use the same driver <Cite n={21} />. In step 14, the node of the kind cluster had `SystemdCgroup = true` in its containerd file and `cgroupDriver: systemd` in its kubelet file. The default configuration of containerd 2.4.2 in step 3 had `SystemdCgroup = false`. A tester can compare the two settings on every node of a test cluster.

**Find an image on a node.** `crictl` is a command-line interface for CRI-compatible container runtimes <Cite n={22} />. You can use it to inspect and debug container runtimes and applications on a Kubernetes node <Cite n={22} />. The docs note that the `ctr` tool is solely made for debugging containerd <Cite n={8} />. If you do not provide a namespace, `ctr` client commands use the namespace `default` <Cite n={9} />. In step 14, the node held its images in the namespace `k8s.io`, and `default` was not in the list. In step 6, the namespace `other` listed 0 images while `qa` listed 1. A tester who looks in the wrong namespace sees no image.

**Compare digests.** Each component of an image is stored in a file whose name is the hash of it <Cite n={12} />. In step 5, all 42 files of the content store had names equal to the SHA-256 of their content. An image index contains a list of manifests for specific platforms <Cite n={19} />. A manifest provides a configuration and a set of layers for a single container image for a specific architecture and operating system <Cite n={18} />. A tester can write down the digest of the index and the digest of the manifest of the platform under test. DiffIDs are not to be confused with layer digests, which are often referenced in the manifest <Cite n={17} />. In step 5, the DiffID and the name of the layer file were two different values. The tutorial pinned no digest for `hello-world`.

**Disk use and removal.** In step 6, two namespaces listed the same 42 blobs, and the store held 42 files. A tester who adds up the blobs of each namespace counts the same files twice. The docs say that the garbage collector is scheduled on a background goroutine, and that it runs based on a number of configurable factors <Cite n={13} />. In step 7, the store held 0 files after `ctr -n qa images rm --sync`. One line of step 7 differed between two runs of the tutorial. A test that checks the disk after an image removal can use `--sync`, as step 7 did. The tutorial did not test a check that waits and polls.

**Registries and mirrors.** containerd reads an optional `hosts.toml` file for each registry host, from a configuration directory <Cite n={16} />. If a host differs from the registry host namespace, such as a mirror, containerd appends the registry host namespace to requests as a query parameter called `ns` <Cite n={16} />. The tutorial set no `hosts.toml`, and steps 4, 6, and 8 used Docker Hub directly. A tester who works behind a mirror can read the `hosts.toml` of the node first.

**Read why a Pod is pending.** A scheduler watches for newly created Pods that have no Node assigned <Cite n={23} />. **একটা storage node পরীক্ষা করুন।** Ceph storage cluster সাজাতে এই স্থানীয় storage-এর অন্তত একটা লাগে: raw device, raw partition, LVM logical volume, অথবা block mode-এর storage class থেকে পাওয়া persistent volume <Cite n={33} />। Rook কোনো device-কে অনুপলব্ধ ঠিক করলে (তাতে বিদ্যমান partition বা formatted filesystem আছে), Rook সেই device ব্যবহার করা এড়িয়ে যাবে <Cite n={38} />। কোনো device এড়ানো হয়েছে কি না দেখতে, যে node-এ device এড়ানো হয়েছে সেই node-এর OSD preparation log দেখুন <Cite n={38} />। ১৫ নম্বর ধাপ prerequisites page-এর পরীক্ষাগুলো টিউটোরিয়ালের machine-এ চালিয়েছে। প্রতিটা partition-এ filesystem ছিল। `rbd` module ছিল, কিন্তু load করা ছিল না। একটা `systemd-udevd` process চলছিল। kernel ছিল 7.0.0-43-generic।

**Ceph কখন চলে।** Rook toolbox হলো একটা container, যাতে rook debug আর test করার সাধারণ tool আছে <Cite n={37} />। তার উদাহরণ command হলো `ceph status`, `ceph osd status`, `ceph df` আর `rados df` <Cite n={37} />। docs PVC pending থেকে যাওয়ার দুটো সাধারণ কারণ তালিকাভুক্ত করে। cluster-এ কোনো OSD নেই, অথবা CSI provisioner pod চলছে না বা request-এর উত্তর দিচ্ছে না <Cite n={38} />। একটা test cluster-এ মাত্র একটা OSD লাগে <Cite n={38} />। production storage class-এর উদাহরণে তিনটা OSD থাকতে হতো <Cite n={38} />। টিউটোরিয়াল কোনো operator চালায়নি, আর এগুলোর কোনোটাই চালায়নি।

## Common mistakes

<Voices>
<Technical>

- **Treating a containerd namespace as a security boundary.** The docs call namespaces an administrative construct that is not meant to be used as a security feature <Cite n={9} />. They add that it is trivial for clients to switch namespaces <Cite n={9} />. In step 6, the option `-n other` was enough to read another namespace.
- **Looking in the wrong namespace.** If you do not provide a namespace, `ctr` client commands use `default` <Cite n={9} />. The node of step 14 had only `k8s.io`. The namespace `other` of step 6 had 0 images.
- **Counting disk space per namespace, or expecting it back at once.** In step 6, two namespaces listed the same 42 blobs, and the store held 42 files. The garbage collector is scheduled on a background goroutine <Cite n={13} />. Step 7 used `--sync`.
- **Letting the kubelet and the runtime disagree on the cgroup driver.** It is critical that they use the same driver <Cite n={21} />. The default configuration of containerd 2.4.2 has `SystemdCgroup = false` (step 3), and the node of step 14 had `SystemdCgroup = true`. Do not assume the default.
- **Reading an accepted custom resource as a working cluster.** In step 13, the API server created the `CephCluster`, and `PHASE`, `MESSAGE`, and `HEALTH` stayed empty. The Rook operator deploys, configures, provisions, scales, upgrades, and monitors Ceph by building on Kubernetes resources <Cite n={30} />. The tutorial's cluster had no operator.
- **Trusting `kubectl explain` for limits.** In step 12, `kubectl explain cephcluster.spec.mon.count` printed `count <integer>` and one line of text, and no range. The range is in the CRD, `"minimum": 0` and `"maximum": 9`, and the Rook docs say that the number must be between 1 and 9 <Cite n={36} />.
- **Turning off `crds.enabled` later.** The chart docs warn that it should only be set during first deployment, and that if it is later disabled the cluster may be destroyed <Cite n={34} />. The tutorial did not install the operator chart, so it did not test this.
- **Reusing the hosts of a deleted test cluster.** The docs warn that for test scenarios, if you delete a cluster and start a new cluster on the same hosts, the path used by `dataDirHostPath` must be deleted <Cite n={36} />. Otherwise, stale keys and other config remain, and the new mons fail to start <Cite n={36} />. The tutorial did not test this.
- **Choosing the number of mons without a reason.** For highest availability, an odd number of mons should be specified <Cite n={36} />. For higher durability in case of mon loss, an even number can be specified although availability may be lower <Cite n={36} />. To maintain quorum, a majority of mons must be up <Cite n={36} />.
- **Offering Rook a disk that has a filesystem.** Rook skips a device that has existing partitions or a formatted filesystem <Cite n={38} />. In step 15, every partition of the tutorial's machine had a filesystem.
- **Debugging a Pending Pod on the node.** The scheduler matches Pods to Nodes so that the kubelet can run them <Cite n={23} />. In step 11, the Pod was `Pending` with the reason `Unschedulable` until the node got the label. The tutorial's advice is to read the events of the Pod first.

## What a tester can check

<Voices>
<Technical>

<Callout type="tip" title="Tutorial advice">
This list is the tutorial's own advice for a tester who works with containerd, the Kubernetes scheduler, and Rook.

- Write the container runtime and its version in every test report, from `kubectl get nodes -o wide`.
- Compare the cgroup driver of the kubelet and of containerd on each node, and do not rely on the default of either.
- Look for images with `crictl` on a node, and give the namespace `k8s.io` to `ctr` there.
- Compare image digests, not tags, when you say that two environments run the same image.
- Use `ctr images rm --sync` in a test that checks free disk space after a removal.
- Read `kubectl get events --field-selector reason=FailedScheduling` before you look at a node when a Pod stays `Pending`.
- Run `kubectl apply --dry-run=server` on every custom resource file in a pull request, against the CRDs of the target version.
- Test the edges of a CRD schema with one bad file for each rule: a wrong type, a value over the maximum, an unknown field, and a change of an immutable field.
- Compare the limits that the docs give with the limits of the CRD schema, and report a gap.
- Check each storage node against the Rook prerequisites before you install the operator: no filesystem on the devices, the `rbd` module, a udev daemon, and the kernel version.
- Keep the output of `kubectl get cephcluster` and `ceph status` in the report. An accepted custom resource is not a healthy cluster.
</Callout>

## Key words

| Term | Meaning |
|---|---|
| Graduated | highly mature, robust projects whose adopters have demonstrated their production-readiness by their deployment to production environments |
| Incubation | projects gaining adoption, focusing on improving stability and maturity |
| containerd | an industry-standard container runtime with an emphasis on simplicity, robustness and portability |
| CRI | the main protocol for the communication between the kubelet and the container runtime |
| Namespace | an administrative construct that is not meant to be used as a security feature |
| Snapshotter | Snapshotters manage the snapshots of the container filesystems |
| Unpacking | The layers must then be read and applied to a filesystem, which creates a committed snapshot |
| Image index | An image index contains a list of manifests for specific platforms |
| DiffID | A layer DiffID is the digest over the layer's uncompressed tar archive |
| Garbage collector | scheduled on a background goroutine, and it runs based on a number of configurable factors |
| kube-scheduler | the default scheduler for Kubernetes, and it runs as part of the control plane |
| nodeSelector | A nodeSelector only selects nodes with all the specified labels |
| Custom resource | an extension of the Kubernetes API that is not necessarily available in a default Kubernetes installation |
