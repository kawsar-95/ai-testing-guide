# Ansible

This page covers Ansible: its inventory, its playbooks and modules, check mode, handlers, tests, ansible-lint, and Ansible Vault. The practice run applies two playbooks to your own machine. It needs no remote host and no cloud account. It comes after [Terraform and Infrastructure as Code](/devops/terraform-iac/) and before [Monitoring and Observability](/devops/monitoring-observability/).

<PageMeta />

## What it is

<Voices>
<Technical>

**Ansible.** Ansible provides open-source automation that reduces complexity and runs everywhere <Cite n={1} />. Ansible uses simple, human-readable scripts called playbooks to automate your tasks <Cite n={1} />. You declare the desired state of a local or remote system in your playbook <Cite n={1} />. Ansible ensures that the system remains in that state <Cite n={1} />. Some of its common use cases are to eliminate repetition and simplify workflows, to manage and maintain system configuration, to continuously deploy complex software, and to perform zero-downtime rolling updates <Cite n={1} />.

**The design.** Ansible is designed around an agent-less architecture <Cite n={1} />. Its playbooks use straightforward YAML syntax for code that reads like documentation <Cite n={1} />. Ansible is also decentralized, and it uses SSH with existing OS credentials to access remote machines <Cite n={1} />. Ansible does not change anything when the system is in the state that the playbook describes, even if the playbook runs many times <Cite n={1} />.

**The parts.** Ansible automates the management of remote systems and controls their desired state <Cite n={2} />. Most Ansible environments have three main components <Cite n={2} />. The control node is a system on which Ansible is installed <Cite n={2} />. You run Ansible commands such as ansible or ansible-inventory on a control node <Cite n={2} />. The inventory is a list of managed nodes that are logically organized <Cite n={2} />. A managed node is a remote system, or host, that Ansible controls <Cite n={2} />.

You install Ansible on a single host, which is the control node <Cite n={5} />. From the control node, Ansible can manage machines remotely with SSH, Powershell remoting, and numerous other transports, with no databases or daemons required <Cite n={5} />. The control node can be nearly any UNIX-like machine with Python installed <Cite n={5} />.

**The packages.** Ansible's community packages are distributed in two ways <Cite n={5} />. The `ansible-core` package is a minimalist language and runtime package that contains a set of built-in modules and plugins <Cite n={5} />. The `ansible` package is a much larger "batteries included" package <Cite n={5} />. It adds a community-curated selection of Ansible Collections <Cite n={5} />. The docs install the minimal package for the current user with `python3 -m pip install --user ansible-core` <Cite n={5} />.

## How it works

<Voices>
<Technical>

**The inventory.** Ansible automates tasks on managed nodes, or hosts, by using a list or group of lists known as inventory <Cite n={6} />. Your inventory defines the managed nodes you automate and the variables associated with those hosts <Cite n={6} />. You can also specify groups <Cite n={6} />. The most common formats are INI and YAML, because Ansible includes built-in support for them <Cite n={6} />. You can pass another inventory source at the command line with `-i` <Cite n={6} />. Even if you define no groups, Ansible creates two default groups, `all` and `ungrouped` <Cite n={6} />. The `all` group contains every host <Cite n={6} />. The `ungrouped` group contains all hosts that do not belong to any other group <Cite n={6} />.

To build an inventory file, you add a new `[myhosts]` group <Cite n={3} />. You specify the IP address or fully qualified domain name (FQDN) of each host system <Cite n={3} />. The docs check an inventory with `ansible-inventory -i inventory.ini --list` <Cite n={3} />, and they ping a group with `ansible myhosts -m ping -i inventory.ini` <Cite n={3} />. With an inventory file, Ansible can manage a large number of hosts with a single command <Cite n={3} />.

A host does not need a remote connection. The `local` connection plugin allows Ansible to execute tasks on the controller instead of on a remote host <Cite n={7} />. Most Ansible modules that run in a POSIX environment need a Python interpreter on the target host <Cite n={8} />. Unless you configure it, Ansible tries to discover one the first time that it runs a Python module for that host <Cite n={8} />. The `ansible_python_interpreter` variable specifies the target host Python path <Cite n={6} />. The default value `auto` searches the configurable list of common Python interpreter paths <Cite n={8} />. It issues a warning that future installation of another Python interpreter could alter the one chosen <Cite n={8} />. The value `auto_silent` does not issue warnings <Cite n={8} />.

**Playbooks, plays, tasks, and modules.** Playbooks are automation blueprints, in YAML format, that Ansible uses to deploy and configure managed nodes <Cite n={4} />. A playbook is a list of plays that define the order in which Ansible performs operations, from top to bottom, to achieve an overall goal <Cite n={4} />. A play is an ordered list of tasks that maps to managed nodes in an inventory <Cite n={4} />. A task is a reference to a single module that defines the operations that Ansible performs <Cite n={4} />. A module is a unit of code or binary that Ansible runs on managed nodes <Cite n={4} />. Each task calls an Ansible module <Cite n={10} />. You express playbooks in YAML with a minimum of syntax <Cite n={10} />.

A playbook runs in order from top to bottom <Cite n={10} />. At a minimum, each play defines the managed nodes to target, using a pattern, and at least one task to execute <Cite n={10} />. By default, Ansible executes each task in order, one at a time, against all machines that the host pattern matches <Cite n={10} />. For Ansible 2.10 and later, you should use the fully-qualified collection name (FQCN) in your playbooks <Cite n={10} />. The tips page says to use fully qualified collection names to avoid ambiguity in which collection to search for the correct module or plugin for each task <Cite n={29} />. The tips page also says to always name plays, tasks, and blocks <Cite n={29} />, and to always mention the state of a module <Cite n={29} />.

To run a playbook, use the `ansible-playbook` command <Cite n={10} />. When you run a playbook, Ansible returns the name lines of your plays and tasks <Cite n={10} />. It also returns whether each task has succeeded or failed on each machine, and whether each task has made a change on each machine <Cite n={10} />. At the bottom, it gives a summary of the nodes that were targeted and how they performed <Cite n={10} />. The `ansible-playbook` command can verify a playbook with `--check`, `--diff`, `--list-hosts`, `--list-tasks`, and `--syntax-check` <Cite n={10} />. `--syntax-check` performs a syntax check on the playbook, but does not execute it <Cite n={20} />. `--list-tasks` lists all tasks that would be executed <Cite n={20} />. `--list-hosts` outputs a list of matching hosts, and does not execute anything else <Cite n={20} />.

**The modules of the tutorial.** The `file` module sets attributes of files, directories, or symlinks and their targets <Cite n={21} />. With `state: directory`, the target is a directory, and if needed all intermediate subdirectories are created, using the supplied permissions <Cite n={21} />. Modes are octal numbers, and for consistent results, you should quote octal numbers so that Ansible receives a string <Cite n={21} />. The `copy` module copies a file or a directory structure from the local or remote machine to a location on the remote machine <Cite n={22} />. When you use `content` instead of `src`, it sets the contents of a file directly to the given value <Cite n={22} />. It works only when `dest` is a file, and it creates the file if it does not exist <Cite n={22} />. For the `template` module, templates are processed by the Jinja2 templating language <Cite n={23} />. Its `src` is the path of a Jinja2 formatted template on the Ansible controller <Cite n={23} />. Its `dest` is the location to render the template to on the remote machine <Cite n={23} />. The `slurp` module works like `fetch`, and it is used for fetching a base64-encoded blob containing the data in a remote file <Cite n={24} />. The `assert` module asserts that given expressions are true, with an optional custom message <Cite n={25} />. Its `that` option is a list of string expressions of the same form that you can pass to the `when` statement <Cite n={25} />.

Ansible modules normally return a data structure that you can register into a variable <Cite n={18} />. The key `changed` is a boolean indicating if the task had to make changes to the target or delegated host <Cite n={18} />. The key `failed` is a boolean that indicates if the task was failed or not <Cite n={18} />. The key `diff` holds information on differences between previous and current state <Cite n={18} />.

**Desired state and idempotence.** Most Ansible modules check whether the desired final state has already been achieved, and they exit without performing any actions if it has <Cite n={10} />. Modules that behave this way are idempotent <Cite n={10} />. An operation is idempotent if the result of performing it once is exactly the same as the result of performing it repeatedly without any intervening actions <Cite n={19} />. Not all playbooks and not all modules behave this way <Cite n={10} />.

The `shell` and `command` modules run arbitrary commands, and they do not naturally detect if a change has occurred <Cite n={35} />. **inventory।** Ansible managed node বা host-এর ওপর কাজ automate করে inventory নামে পরিচিত একটা তালিকা বা তালিকার গুচ্ছ ব্যবহার করে <Cite n={6} />। আপনার inventory ঠিক করে আপনি কোন managed node automate করেন, আর সেই host-গুলোর সঙ্গে যুক্ত variable <Cite n={6} />। আপনি group-ও ঠিক করতে পারেন <Cite n={6} />। সবচেয়ে প্রচলিত format INI আর YAML, কারণ Ansible-এ এগুলোর জন্য built-in সমর্থন আছে <Cite n={6} />। আপনি command line-এ `-i` দিয়ে অন্য inventory source দিতে পারেন <Cite n={6} />। আপনি কোনো group না বানালেও Ansible দুটো default group বানায়, `all` আর `ungrouped` <Cite n={6} />। `all` group-এ প্রতিটা host আছে <Cite n={6} />। `ungrouped` group-এ আছে সেই সব host, যারা অন্য কোনো group-এর নয় <Cite n={6} />।

একটা inventory file বানাতে আপনি একটা নতুন `[myhosts]` group যোগ করেন <Cite n={3} />। আপনি প্রতিটা host system-এর IP address বা fully qualified domain name (FQDN) ঠিক করেন <Cite n={3} />। docs একটা inventory যাচাই করে `ansible-inventory -i inventory.ini --list` দিয়ে <Cite n={3} />, আর একটা group ping করে `ansible myhosts -m ping -i inventory.ini` দিয়ে <Cite n={3} />। একটা inventory file দিয়ে Ansible একটাই command-এ বহু host পরিচালনা করতে পারে <Cite n={3} />।

একটা host-এর জন্য দূরের connection লাগে না। `local` connection plugin Ansible-কে দূরের host-এর বদলে controller-এ task চালাতে দেয় <Cite n={7} />। POSIX পরিবেশে চলা বেশির ভাগ Ansible module-এর জন্য target host-এ একটা Python interpreter লাগে <Cite n={8} />। আপনি ঠিক না করলে Ansible সেই host-এর জন্য প্রথম Python module চালানোর সময় একটা খুঁজে নিতে চেষ্টা করে <Cite n={8} />। `ansible_python_interpreter` variable একটা target host-এর Python path ঠিক করে <Cite n={6} />। default মান `auto` সাধারণ Python interpreter path-এর কনফিগার করা যায় এমন তালিকায় খোঁজে <Cite n={8} />। সে একটা সতর্কবার্তা দেয় যে ভবিষ্যতে আরেকটা Python interpreter install হলে বেছে নেওয়াটা বদলে যেতে পারে <Cite n={8} />। `auto_silent` মান কোনো সতর্কবার্তা দেয় না <Cite n={8} />।

**playbook, play, task আর module।** playbook হলো YAML format-এর automation blueprint, যা Ansible managed node deploy ও configure করতে ব্যবহার করে <Cite n={4} />। একটা playbook হলো play-এর একটা তালিকা, যা ঠিক করে একটা সামগ্রিক লক্ষ্যে পৌঁছাতে Ansible উপর থেকে নিচে কোন ক্রমে কাজ করবে <Cite n={4} />। একটা play হলো task-এর একটা ক্রমানুসারে তালিকা, যা একটা inventory-র managed node-এর সঙ্গে মেলানো <Cite n={4} />। একটা task হলো একটা একক module-এর রেফারেন্স, যা ঠিক করে Ansible কী কী কাজ করবে <Cite n={4} />। একটা module হলো এক টুকরো code বা binary, যা Ansible managed node-এ চালায় <Cite n={4} />। প্রতিটা task একটা Ansible module ডাকে <Cite n={10} />। আপনি playbook লেখেন YAML-এ, ন্যূনতম syntax দিয়ে <Cite n={10} />।

একটা playbook উপর থেকে নিচে ক্রমানুসারে চলে <Cite n={10} />। ন্যূনতমভাবে প্রতিটা play ঠিক করে, একটা pattern দিয়ে কোন managed node লক্ষ্য, আর অন্তত একটা task <Cite n={10} />। by default Ansible প্রতিটা task ক্রমানুসারে, একবারে একটা করে, host pattern-এর সঙ্গে মেলা সব মেশিনে চালায় <Cite n={10} />। Ansible 2.10 আর তার পরে আপনার playbook-এ fully-qualified collection name (FQCN) ব্যবহার করা উচিত <Cite n={10} />। tips page বলে, প্রতিটা task-এর সঠিক module বা plugin কোন collection-এ খুঁজতে হবে সেই অস্পষ্টতা এড়াতে fully qualified collection name ব্যবহার করতে <Cite n={29} />। tips page আরও বলে, সবসময় play, task আর block-এর নাম দিতে <Cite n={29} />, আর একটা module-এর state উল্লেখ করতে <Cite n={29} />।

একটা playbook চালাতে ব্যবহার করুন `ansible-playbook` command <Cite n={10} />। একটা playbook চালালে Ansible আপনার play আর task-এর নামের লাইন ফেরত দেয় <Cite n={10} />। সে এও ফেরত দেয় প্রতিটা মেশিনে প্রতিটা task সফল হয়েছে না ব্যর্থ, আর প্রতিটা মেশিনে প্রতিটা task কোনো পরিবর্তন করেছে কি না <Cite n={10} />। শেষে সে দেয় কোন node লক্ষ্য ছিল আর সেগুলো কেমন করেছে, তার একটা সারাংশ <Cite n={10} />। `ansible-playbook` command একটা playbook যাচাই করতে পারে `--check`, `--diff`, `--list-hosts`, `--list-tasks` আর `--syntax-check` দিয়ে <Cite n={10} />। `--syntax-check` playbook-এর syntax যাচাই করে, কিন্তু সেটা চালায় না <Cite n={20} />। `--list-tasks` যে সব task চালানো হতো তার তালিকা দেয় <Cite n={20} />। `--list-hosts` মেলা host-এর তালিকা দেয়, আর আর কিছু চালায় না <Cite n={20} />।

**টিউটোরিয়ালের module-গুলো।** `file` module file, directory বা symlink আর তাদের লক্ষ্যের attribute ঠিক করে <Cite n={21} />। `state: directory` দিলে লক্ষ্যটা একটা directory, আর দরকার হলে মাঝের সব subdirectory দেওয়া permission দিয়ে তৈরি হয় <Cite n={21} />। mode হলো octal সংখ্যা, আর সঙ্গতিপূর্ণ ফলের জন্য সেগুলো quote করা উচিত <Cite n={21} />। `copy` module একটা file বা directory-র কাঠামো স্থানীয় বা দূরের মেশিন থেকে দূরের মেশিনের একটা জায়গায় কপি করে <Cite n={22} />। `src`-এর বদলে `content` ব্যবহার করলে এটা একটা file-এর content সরাসরি দেওয়া মানে বসায় <Cite n={22} />। এটা কাজ করে শুধু `dest` একটা file হলে, আর file না থাকলে সেটা তৈরি করে <Cite n={22} />। `template` module-এর ক্ষেত্রে template প্রক্রিয়া করা হয় Jinja2 templating language দিয়ে <Cite n={23} />। এর `src` হলো Ansible controller-এ থাকা একটা Jinja2 format-এর template-এর path <Cite n={23} />। এর `dest` হলো দূরের মেশিনে সেই জায়গা, যেখানে template render হবে <Cite n={23} />। `slurp` module `fetch`-এর মতো কাজ করে, আর একটা দূরের file-এর data ধরা base64-encoded blob আনে <Cite n={24} />। `assert` module যাচাই করে দেওয়া expression-গুলো সত্য কি না, সঙ্গে ঐচ্ছিক custom বার্তা <Cite n={25} />। এর `that` option হলো একই ধরনের string expression-এর একটা তালিকা, যা আপনি `when` statement-এ দিতে পারেন <Cite n={25} />।

Ansible module সাধারণত একটা data structure ফেরত দেয়, যা আপনি একটা variable-এ register করতে পারেন <Cite n={18} />। `changed` key একটা boolean, যা বলে task-টাকে লক্ষ্যে পরিবর্তন করতে হয়েছে কি না <Cite n={18} />। `failed` key একটা boolean, যা বলে task ব্যর্থ হয়েছে কি না <Cite n={18} />। `diff` key আগের আর বর্তমান state-এর পার্থক্যের তথ্য ধরে <Cite n={18} />।

**কাঙ্ক্ষিত অবস্থা আর idempotence।** বেশির ভাগ Ansible module যাচাই করে কাঙ্ক্ষিত চূড়ান্ত অবস্থা আগেই অর্জিত হয়েছে কি না, আর হয়ে থাকলে কোনো কাজ না করেই exit করে <Cite n={10} />। যে module এভাবে আচরণ করে, তারা idempotent <Cite n={10} />। একটা operation idempotent, যদি সেটা একবার করার ফল ঠিক তা-ই হয়, যা মাঝখানে কিছু না করে বারবার করলে হয় <Cite n={19} />। সব playbook আর সব module এভাবে আচরণ করে না <Cite n={10} />।

`shell` আর `command` module যেকোনো command চালায়, আর তারা স্বাভাবিকভাবে ধরতে পারে না কোনো পরিবর্তন হয়েছে কি না <Cite n={35} />। `changed_when` দিয়ে আপনি ঠিক করেন, কখন একটা task একটা দূরের node বদলেছে <Cite n={16} />। এটা আপনাকে return code বা output-এর ভিত্তিতে ঠিক করতে দেয়, পরিবর্তন statistic-এ জানানো উচিত কি না, আর handler চালু করা উচিত কি না <Cite n={16} />। `failed_when` দিয়ে আপনি ঠিক করেন প্রতিটা task-এ ব্যর্থতার মানে কী <Cite n={16} />।

**variable, fact আর template।** Ansible বিভিন্ন system-এর পার্থক্য সামলাতে variable ব্যবহার করে <Cite n={11} />। আপনি variable ঠিক করতে পারেন আপনার playbook-এ, inventory-তে, পুনর্ব্যবহারযোগ্য file বা role-এ, অথবা command line-এ <Cite n={11} />। আপনি একটা run-এর সময়ও variable বানাতে পারেন, একটা task-এর ফেরত দেওয়া মান একটা নতুন variable হিসেবে register করে <Cite n={11} />। Ansible গতিশীল expression আর variable ও fact-এ প্রবেশ সম্ভব করতে Jinja2 templating ব্যবহার করে <Cite n={12} />। আপনি template module দিয়ে templating ব্যবহার করতে পারেন <Cite n={12} />। fact হলো দূরের node সম্পর্কে আবিষ্কার করা জিনিস <Cite n={19} />। Ansible সেগুলো আবিষ্কার করে play চালানোর সময়, দূরের node-এ ভেতরের `setup` module চালিয়ে <Cite n={19} />। দরকার না হলে সময় বাঁচাতে fact সংগ্রহ বন্ধ করা যায় <Cite n={19} />।

**handler।** কখনও কখনও আপনি চান একটা task শুধু তখনই চলুক, যখন একটা মেশিনে কোনো পরিবর্তন হয় <Cite n={13} />। handler হলো এমন task, যা শুধু notify করা হলে চলে <Cite n={13} />। একটা task এক বা একাধিক handler চালাতে বলে `notify` keyword দিয়ে <Cite n={13} />। keyword-টা handler-এর নামের এমন একটা তালিকা নেয়, যাদের task বদলালে notify করা হয় <Cite n={13} />। একই handler বহুবার notify করলে সেটা একবারই চলে <Cite n={13} />। handler চলে `handlers` section-এর ক্রমে, `notify` তালিকার ক্রমে নয় <Cite n={13} />। docs-এর উদাহরণে handler Apache restart করে play-এর সব task শেষ হওয়ার পর <Cite n={13} />। `meta: flush_handlers` task play-এর সেই বিন্দুতে notify হয়ে থাকা সব handler চালু করে <Cite n={13} />। `--force-handlers` option কোনো task ব্যর্থ হলেও handler চালায় <Cite n={20} />।

**check mode আর diff mode।** Ansible-এ task যাচাইয়ের দুটো mode আছে: check mode আর diff mode <Cite n={15} />। check mode-এ Ansible দূরের system-এ কোনো পরিবর্তন না করে চলে <Cite n={15} />। যে module check mode সমর্থন করে, তারা জানায় তারা কোন পরিবর্তন করত <Cite n={15} />। যে module check mode সমর্থন করে না, তারা কিছু জানায় না আর কিছু করে না <Cite n={15} />। diff mode-এ Ansible আগে-পরের তুলনা দেয় <Cite n={15} />। check mode শুধু একটা simulation <Cite n={15} />। registered variable-ভিত্তিক conditional ব্যবহার করা task-এর জন্য এটা কোনো output দেয় না <Cite n={15} />। `--diff` option একা বা `--check`-এর সঙ্গে ব্যবহার করা যায় <Cite n={15} />। `--diff` সংবেদনশীল তথ্য প্রকাশ করতে পারে বলে আপনি একটা task-এর জন্য `diff: false` দিয়ে সেটা বন্ধ করতে পারেন <Cite n={15} />। playbook `--check` দিয়ে ডাকা হলেও একটা task-কে স্বাভাবিক mode-এ চালাতে `check_mode: false` দিন <Cite n={15} />।

**error আর block।** Ansible কোনো command থেকে শূন্য নয় এমন return code বা কোনো module থেকে ব্যর্থতা পেলে by default সেই host-এ চালানো বন্ধ করে দেয়, আর অন্য host-এ চালিয়ে যায় <Cite n={16} />। ব্যর্থতা সত্ত্বেও চালিয়ে যেতে আপনি `ignore_errors` ব্যবহার করতে পারেন <Cite n={16} />। এই directive কাজ করে শুধু যখন task চলতে পারে আর `failed` মান ফেরত দেয় <Cite n={16} />। এটা undefined variable error, connection ব্যর্থতা, execution সমস্যা বা syntax error উপেক্ষা করায় না <Cite n={16} />। block task-কে যুক্তিসঙ্গত দলে ভাগ করে <Cite n={17} />। এগুলো task-এর error সামলানোর উপায়ও দেয়, যা অনেক programming language-এর exception handling-এর মতো <Cite n={17} />। rescue block ঠিক করে, একটা block-এর আগের কোনো task ব্যর্থ হলে কোন task চলবে <Cite n={17} />। `always` section-এর task চলে, আগের block-এর task-এর অবস্থা যা-ই হোক <Cite n={17} />। অবৈধ task সংজ্ঞা আর অগম্য host-এর কারণে হওয়া error `rescue` বা `always` section চালু করে না <Cite n={17} />।

**role।** role আপনাকে একটা পরিচিত file কাঠামোর ভিত্তিতে সম্পর্কিত vars, file, task, handler আর অন্য Ansible জিনিস স্বয়ংক্রিয়ভাবে load করতে দেয় <Cite n={14} />। আপনি content role-এ ভাগ করে নিলে সহজেই সেগুলো পুনর্ব্যবহার করতে আর অন্য ব্যবহারকারীদের সঙ্গে ভাগ করতে পারেন <Cite n={14} />। একটা role-এর `tasks/main.yml` file হলো task-এর একটা তালিকা, যা role play-কে চালানোর জন্য দেয় <Cite n={14} />।

**Vault আর project-এর রীতি।** Ansible vault পাসওয়ার্ডের মতো সংবেদনশীল data encrypt ও পরিচালনা করার একটা উপায় দেয় <Cite n={26} />। আপনি Ansible Vault দিয়ে দুই ধরনের content encrypt করতে পারেন: variable আর file <Cite n={27} />। একটা বিদ্যমান file encrypt করতে ব্যবহার করুন `ansible-vault encrypt` command <Cite n={27} />। একটা encrypted file edit না করে তার content দেখতে ব্যবহার করুন `ansible-vault view` command <Cite n={27} />। একটা file-এ রাখা vault password ব্যবহার করে এমন একটা playbook চালানোর সময় আপনি `--vault-password-file` flag-এ file-টা দেন <Cite n={44} />। tips page বলে, সংবেদনশীল বা গোপন variable Ansible Vault দিয়ে encrypt করা উচিত <Cite n={29} />।

tips page বলে, আপনার playbook, role, inventory আর variable file version control-এ রাখতে <Cite n={29} />। এটা বলে, আপনি আলাদা inventory file বা directory ব্যবহার করে production-কে development, test আর staging পরিবেশ থেকে আলাদা রাখতে পারেন <Cite n={29} />। একটা inventory-তে production আর development দুটোই থাকলে সেটা যারা ব্যবহার করেন সেই developer-রা production-এর secret-এ প্রবেশ করতে পারতেন <Cite n={29} />।

**test আর lint।** Ansible তৈরি fail-fast আর ক্রমানুসারে চলা system হিসেবে, তাই playbook-এর ভেতরেই সরাসরি test বসানো সহজ <Cite n={28} />। Ansible resource হলো কাঙ্ক্ষিত অবস্থার মডেল, তাই service চালু আছে বা package install করা আছে কি না test করার দরকার হওয়া উচিত নয় <Cite n={28} />। `assert` module নানা ধরনের সত্যতা যাচাই করা খুব সহজ করে <Cite n={28} />। আপনার Ansible configuration যে file-এর অস্তিত্ব ঘোষণামূলকভাবে ঠিক করে না, তা test করার দরকার হলে `stat` module দারুণ পছন্দ <Cite n={28} />। command-এর return code যাচাই করার দরকার নেই, কারণ Ansible সেগুলো আপনা থেকেই যাচাই করে <Cite n={28} />। check mode একটা drift test হিসেবে কাজ করতে পারে: `--check` দিলে Ansible জানায়, তার ধারণা অনুযায়ী system-কে কাঙ্ক্ষিত অবস্থায় আনতে তাকে কোনো পরিবর্তন করতে হতো কি না <Cite n={28} />। আপনি production webservice হলে একটা integration test battery আপনার QA team-এর লেখা উচিত <Cite n={28} />। সেটা সাধারণত আপনার playbook-এর ভেতরে বসানো হয় না <Cite n={28} />। playbook-এ কিছু মৌলিক health check রাখা অর্থবহ <Cite n={28} />।

Ansible Lint হলো playbook, role আর collection lint করার একটা command-line tool <Cite n={31} />। এর মূল লক্ষ্য প্রমাণিত অভ্যাস, pattern আর আচরণ উৎসাহিত করা, আর এমন সাধারণ ফাঁদ এড়ানো, যা সহজেই bug ঘটাতে বা code রক্ষণাবেক্ষণ কঠিন করতে পারে <Cite n={31} />। playbook page বলে, একটা playbook চালানোর আগে আপনি এটা দিয়ে বিস্তারিত, Ansible-নির্দিষ্ট মতামত পেতে পারেন <Cite n={10} />। profile নিয়মের কঠোরতা ধাপে ধাপে বাড়ায় <Cite n={32} />। `min` profile নিশ্চিত করে যে Ansible content load করতে পারে <Cite n={32} />। `basic` profile সাধারণ coding সমস্যা ঠেকায় আর মান ধরনের style ও formatting চাপায়, আর এটা `min` profile-কে বাড়ায় <Cite n={32} />। `--profile` option ঠিক করে কোন rules profile ব্যবহার করা হবে <Cite n={33} />। `--strict` option warning আর error দুটোতেই শূন্য নয় এমন exit code ফেরত দেয় <Cite n={33} />। `-f` option output format ঠিক করে, যা `brief`, `full`, `md`, `json`, `codeclimate`, `quiet`, `pep8` আর `sarif`-এর একটা <Cite n={33} />। `--project-dir` option হলো project বা repository-র অবস্থান, যা configuration file-এর অবস্থানের ভিত্তিতে স্বয়ংক্রিয়ভাবে ধরা হয় <Cite n={33} />। `--offline` option requirements.yml-এর installation আর schema refresh বন্ধ করে <Cite n={33} />। docs বলে, project-স্থানীয় `.ansible` আর `.cache` folder `.gitignore`-এ যোগ করা উচিত <Cite n={33} />।

`name[play]` rule বলে সব play-এর নাম থাকা উচিত <Cite n={34} />। `name[missing]` rule বলে সব task-এর নাম থাকা উচিত <Cite n={34} />। `name[casing]` rule বলে যেসব ভাষা এটা সমর্থন করে, সেগুলোর জন্য সব নাম বড় হাতের অক্ষর দিয়ে শুরু হওয়া উচিত <Cite n={34} />। `no-changed-when` rule যাচাই করে task ফলাফল বা condition দিয়ে পরিবর্তন জানায় কি না <Cite n={35} />। `risky-file-permissions` rule চালু হয় এমন নানা module-এ, যা এমন permission সহ নতুন file বানাতে পারে, যা বেশি খোলা বা অনির্ভরযোগ্য হতে পারে <Cite n={36} />।

Molecule হলো একটা Ansible testing framework, যা Ansible collection, playbook আর role তৈরি ও test করার জন্য বানানো <Cite n={37} />। এটা নমনীয় testing workflow দিতে inventory, playbook আর collection-এর মতো স্ট্যান্ডার্ড Ansible বৈশিষ্ট্য কাজে লাগায় <Cite n={37} />।

```yaml
- name: Check the settings file
  hosts: app
  gather_facts: false
  vars:

The example of the `slurp` module uses the expression `{{ mounts['content'] | b64decode }}` to decode the content <Cite n={24} />. The first two expressions of the test do the same with `settings.content`, and check that the text holds `env=qa` and `base_url=http://localhost:8080`. The third checks the mode. **3. Write a playbook, and run it twice.** Save this as `site.yml`:

```yaml
- name: Write the settings of the test environment
  hosts: app
  gather_facts: false
  vars:
    env_name: qa
    base_url: http://localhost:8080
    out_dir: "{{ playbook_dir }}/out"
  tasks:
    - name: Create the output folder
      ansible.builtin.file:
        path: "{{ out_dir }}"
        state: directory
        mode: "0755"

    - name: Write the settings file
      ansible.builtin.template:
        src: settings.env.j2
        dest: "{{ out_dir }}/{{ env_name }}.env"
        mode: "0644"
      notify: Record the change

  handlers:
    - name: Record the change
      ansible.builtin.copy:
        content: "settings changed\n"
        dest: "{{ out_dir }}/changed.log"
        mode: "0644"
```

Save this as `settings.env.j2`, in a folder named `templates`, next to `site.yml`:

```text
env={{ env_name }}
base_url={{ base_url }}
```

The play has two tasks and one handler:

- `hosts: app` makes the play target the group `app`. The keyword `hosts` is a list of groups, hosts, or host patterns that translate into the targets of the play <Cite n={45} />.
- The section `vars` holds three variables for the play <Cite n={45} />. The variable `playbook_dir` is the path to the directory of the current playbook <Cite n={43} />. So the playbook writes into a folder `out` next to itself.
- The keyword `gather_facts` is a boolean that controls if the play will automatically run the `setup` task to gather facts for the hosts <Cite n={45} />. The tutorial sets `gather_facts: false`, because the playbook uses no facts. The output has no `Gathering Facts` task.
- The `file` task creates the folder `out`. With `state: directory`, the target is a directory, and Ansible creates any missing parent folders <Cite n={21} />. The mode is `"0755"`, in quotes, because you should quote octal numbers so that Ansible receives a string <Cite n={21} />.
- The `template` task renders `templates/settings.env.j2` into `out/qa.env`. The `src` is the path of a Jinja2 formatted template on the controller <Cite n={23} />, and `dest` is the location to render it to on the remote machine <Cite n={23} />. The template holds two Jinja2 expressions, `{{ env_name }}` and `{{ base_url }}`. Ansible uses Jinja2 templating to enable dynamic expressions and access to variables and facts <Cite n={12} />. In the layout of a role, the folder `templates/` holds files for use with the template resource, and templates end in `.j2` <Cite n={14} />. The tutorial uses the same names next to a playbook that is not a role, and the run shows that Ansible found the file.
- `notify: Record the change` names the handler. The keyword `notify` is a list of handlers to notify when the task returns a `changed=True` status <Cite n={45} />. The `handlers` section holds tasks that do not run normally, only when notified after each section of tasks is complete <Cite n={45} />. The handler writes the text `settings changed` into `out/changed.log` with the `copy` module. When you use `content` instead of `src`, it sets the contents of a file directly to the given value <Cite n={22} />.
- Every play, task, and handler has a name, and every module has its full name, `ansible.builtin.<module>`. The tips page says to always name plays, tasks, and blocks <Cite n={29} />, and to use fully qualified collection names <Cite n={29} />.

**6. Write a test with `assert`.** Save this as `check.yml`:

```yaml
- name: Check the settings file
  hosts: app
  gather_facts: false
  vars:
    out_dir: "{{ playbook_dir }}/out"
  tasks:
    - name: Read the settings file
      ansible.builtin.slurp:
        src: "{{ out_dir }}/qa.env"
      register: settings

    - name: Look at the settings file
      ansible.builtin.stat:
        path: "{{ out_dir }}/qa.env"
      register: settings_stat

    - name: Check that the file holds the settings of the qa environment
      ansible.builtin.assert:
        that:
          - "'env=qa' in (settings.content | b64decode)"
          - "'base_url=http://localhost:8080' in (settings.content | b64decode)"
          - settings_stat.stat.mode == '0644'
        success_msg: The settings are what the test expects.
        fail_msg: The settings are not what the test expects.
```

The playbook changes nothing. It has three tasks:

- The `slurp` task reads `out/qa.env`. The module is used for fetching a base64-encoded blob containing the data in a remote file <Cite n={24} />. The keyword `register` is the name of the variable that will contain the task status and the module return data <Cite n={45} />. So `settings` holds the result of the `slurp` task.
- The `stat` task registers the status of the file in `settings_stat`. The module retrieves facts for a file, similar to the Linux/Unix `stat` command <Cite n={40} />. Its return value `mode` holds the Unix permissions of the file in octal representation as a string <Cite n={40} />. So the test compares it with the string `'0644'`.
- The `assert` task has three expressions in `that`. The option `that` is a list of string expressions of the same form that can be passed to the `when` statement <Cite n={25} />. The example of the `slurp` module uses the expression `{{ mounts['content'] | b64decode }}` to decode the content <Cite n={24} />. The first two expressions of the test do the same with `settings.content`, and check that the text holds `env=qa` and `base_url=http://localhost:8080`. The third checks the mode. The option `success_msg` is the customized message used for a successful assertion, and `fail_msg` is the customized message used for a failing assertion <Cite n={25} />.

- `gather_facts` keyword একটা boolean, যা ঠিক করে play আপনা থেকে hosts-এর fact সংগ্রহ করতে `setup` task চালাবে কি না <Cite n={45} />। টিউটোরিয়াল `gather_facts: false` দিয়েছে, কারণ playbook কোনো fact ব্যবহার করে না। output-এ কোনো `Gathering Facts` task নেই।
- `file` task `out` folder বানায়। `state: directory` দিলে লক্ষ্যটা একটা directory, আর Ansible যেকোনো অনুপস্থিত parent folder বানায় <Cite n={21} />। mode `"0755"`, quote-সহ, কারণ octal সংখ্যা quote করা উচিত, যাতে Ansible একটা string পায় <Cite n={21} />।
- `template` task `templates/settings.env.j2`-কে render করে `out/qa.env`-এ। `src` হলো controller-এ থাকা একটা Jinja2 format-এর template-এর path <Cite n={23} />, আর `dest` হলো যেখানে সেটা render হবে সেই জায়গা <Cite n={23} />। template-এ দুটো Jinja2 expression আছে, `{{ env_name }}` আর `{{ base_url }}`। Ansible গতিশীল expression আর variable ও fact-এ প্রবেশ সম্ভব করতে Jinja2 templating ব্যবহার করে <Cite n={12} />। একটা role-এর কাঠামোয় `templates/` folder template resource-এর জন্য file ধরে, আর template-এর নাম `.j2` দিয়ে শেষ হয় <Cite n={14} />। টিউটোরিয়াল একই নাম ব্যবহার করেছে এমন একটা playbook-এর পাশে, যা role নয়, আর run দেখায় Ansible file-টা পেয়েছে।
- `notify: Record the change` handler-এর নাম দেয়। `notify` keyword হলো সেই handler-এর তালিকা, যাদের task `changed=True` status ফেরত দিলে notify করা হয় <Cite n={45} />। `handlers` section-এ এমন task থাকে, যা স্বাভাবিকভাবে চলে না, চলে শুধু task-এর প্রতিটা section শেষ হওয়ার পর notify করা হলে <Cite n={45} />। handler `copy` module দিয়ে `out/changed.log`-এ `settings changed` লেখে। `src`-এর বদলে `content` ব্যবহার করলে এটা একটা file-এর content সরাসরি দেওয়া মানে বসায় <Cite n={22} />।
- প্রতিটা play, task আর handler-এর একটা নাম আছে, আর প্রতিটা module-এর পুরো নাম আছে, `ansible.builtin.<module>`। tips page বলে সবসময় play, task আর block-এর নাম দিতে <Cite n={29} />, আর fully qualified collection name ব্যবহার করতে <Cite n={29} />।

**৬. `assert` দিয়ে একটা test লিখুন।** এটা `check.yml` নামে save করুন:

```yaml
- name: Check the settings file
  hosts: app
  gather_facts: false
  vars:
    out_dir: "{{ playbook_dir }}/out"
  tasks:
    - name: Read the settings file
      ansible.builtin.slurp:
        src: "{{ out_dir }}/qa.env"
      register: settings

    - name: Look at the settings file
      ansible.builtin.stat:
        path: "{{ out_dir }}/qa.env"
      register: settings_stat

    - name: Check that the file holds the settings of the qa environment
      ansible.builtin.assert:
        that:
          - "'env=qa' in (settings.content | b64decode)"
          - "'base_url=http://localhost:8080' in (settings.content | b64decode)"
          - settings_stat.stat.mode == '0644'
        success_msg: The settings are what the test expects.
        fail_msg: The settings are not what the test expects.
```

playbook কিছুই বদলায় না। এতে তিনটা task আছে:

- `slurp` task `out/qa.env` পড়ে। module একটা দূরের file-এর data ধরা base64-encoded blob আনতে ব্যবহার করা হয় <Cite n={24} />। `register` keyword হলো সেই variable-এর নাম, যাতে task-এর status আর module-এর ফেরত দেওয়া data থাকবে <Cite n={45} />। তাই `settings`-এ `slurp` task-এর ফল আছে।
- `stat` task file-এর status `settings_stat`-এ register করে। module একটা file-এর facts আনে, Linux/Unix-এর `stat` command-এর মতো <Cite n={40} />। এর `mode` ফেরত-মান file-এর Unix permission ধরে, octal রূপে একটা string হিসেবে <Cite n={40} />। তাই test সেটাকে `'0644'` string-এর সঙ্গে মেলায়।
- `assert` task-এর `that`-এ তিনটা expression আছে। `that` option হলো একই ধরনের string expression-এর একটা তালিকা, যা `when` statement-এ দেওয়া যায় <Cite n={25} />। `slurp` module-এর উদাহরণ content decode করতে `{{ mounts['content'] | b64decode }}` expression ব্যবহার করে <Cite n={24} />। test-এর প্রথম দুটো expression `settings.content`-এর সঙ্গে একই কাজ করে, আর যাচাই করে text-এ `env=qa` আর `base_url=http://localhost:8080` আছে। তৃতীয়টা mode যাচাই করে। `success_msg` option হলো সফল assertion-এর বার্তা, আর `fail_msg` হলো ব্যর্থ assertion-এর বার্তা <Cite n={25} />।

- ansible-lint ইনস্টল করা role ও collection সহ cache বানায় runtime cache directory-র নিচে, যা offline না হলে সাধারণত `{project}/.ansible` <Cite n={33} />। সে নিজে থেকে cache পরিষ্কার করে না <Cite n={33} />। টিউটোরিয়ালের run খালি home folder-এ একটা file রেখে গেছে, যা এই section-এর শুরুর অংশে বর্ণিত।

**৮. Vault দিয়ে একটা secret encrypt করুন।** চালান:

```bash
printf 'made-up-vault-password\n' > vault-pass.txt
printf 'db_password: made-up-db-password\n' > secrets.yml
ansible-vault encrypt secrets.yml --vault-password-file vault-pass.txt
head -n 2 secrets.yml
grep -c 'made-up-db-password' secrets.yml
ansible-vault view secrets.yml --vault-password-file vault-pass.txt
```

```text

db_password: made-up-db-password
```

এই ধাপের password আর secret টিউটোরিয়ালের জন্য বানানো।

- `ansible-vault` হলো Ansible data file-এর জন্য একটা encryption/decryption utility <Cite n={41} />। প্রথম দুটো লাইন password file, `vault-pass.txt`, আর data file, `secrets.yml`, লেখে। একটা vault password file-এ রাখতে, আপনি file-এর একটাই লাইনে password-টা একটা string হিসেবে লেখেন <Cite n={44} />। docs আরও বলে, file-এর permission উপযুক্ত কি না নিশ্চিত করতে, আর password file source control-এ যোগ না করতে <Cite n={44} />। টিউটোরিয়াল তার file-এর permission বদলায়নি, যে file শুধু run-এর অস্থায়ী folder-এ থাকে।
- একটা বিদ্যমান file encrypt করতে আপনি `ansible-vault encrypt` command ব্যবহার করেন <Cite n={27} />। `--vault-password-file` option একটা vault password file নেয় <Cite n={41} />। এই run-এ command কিছু ছাপেনি।
- `head -n 2 secrets.yml` ছেপেছে header লাইন, `$ANSIBLE_VAULT;1.1;AES256`, আর hex অঙ্কের একটা লাইন। docs `$ANSIBLE_VAULT;1.1;AES256` header সহ encrypted content-এর একটা উদাহরণ দেখায় <Cite n={27} />।
- `grep -c` ছেপেছে `0`, তাই encrypted file-এর কোনো লাইনে `made-up-db-password` লেখাটা নেই।
- `ansible-vault view` ছেপেছে `db_password: made-up-db-password`। একটা encrypted file edit না করে তার content দেখতে আপনি `ansible-vault view` command ব্যবহার করতে পারেন <Cite n={27} />। Ansible Vault দুই ধরনের content encrypt করতে পারে, variable আর file <Cite n={27} />। এই ধাপ একটা file encrypt করেছে।

## How a tester uses it

<Voices>
<Technical>

- **Test the result, and not the tool.** Ansible resources are models of desired state, so it should not be necessary to test that services are started or that packages are installed <Cite n={28} />. The `assert` module makes it very easy to validate various kinds of truth <Cite n={28} />. In step 6, the test read the file that the playbook wrote, and it checked its text and its mode.
- **Use `stat` for what the configuration does not set.** If you need to test for the existence of files that your Ansible configuration does not set declaratively, the `stat` module is a great choice <Cite n={28} />. Its return value `mode` holds the Unix permissions of the file in octal representation as a string <Cite n={40} />.
- **Do not test what Ansible tests.** There is no need to check the return codes of commands, because Ansible checks them automatically <Cite n={28} />.
- **Run a playbook twice, and read the second recap.** Most Ansible modules exit without performing any actions if the desired final state has already been achieved <Cite n={10} />. In step 3, the second run reported `changed=0`. Not all playbooks and not all modules behave this way <Cite n={10} />. A second run that reports changes is a finding.
- **Use check mode as a drift test, and know its limits.** With `--check`, Ansible reports if it thinks it would have had to make any changes to bring the system into a desired state <Cite n={28} />. In step 5, it found the hand edit. Check mode is just a simulation <Cite n={15} />. Modules that do not support it report nothing and do nothing <Cite n={15} />. Ordinarily, scripts and commands do not run in check mode <Cite n={28} />. A check does not generate output for tasks that use conditionals based on registered variables <Cite n={15} />.
- **Read the diff, and mind the secrets in it.** In diff mode, Ansible provides before-and-after comparisons <Cite n={15} />. Because `--diff` can reveal sensitive information, you can disable it for a task with `diff: false` <Cite n={15} />.
- **Lint before you run.** You can use ansible-lint for detailed, Ansible-specific feedback on your playbooks before you execute them <Cite n={10} />. The option `--strict` returns a non-zero exit code on warnings as well as errors <Cite n={33} />. In step 7, the exit status was 0 for the two good files and 2 for the bad file.
- **Use the cheap checks first.** `--syntax-check` performs a syntax check on the playbook, but does not execute it <Cite n={20} />. `--list-hosts` outputs a list of matching hosts, and it does not execute anything else <Cite n={20} />. `--list-tasks` lists all tasks that would be executed <Cite n={20} />. In step 3, the tutorial ran `--syntax-check` and `--list-tasks` before the real run.
- **Keep secrets in Vault, and keep the password out of Git.** The tips page says that you should encrypt sensitive or secret variables with Ansible Vault <Cite n={29} />. The docs say not to add password files to source control <Cite n={44} />. Step 8 shows that the encrypted file does not hold the plain text, and that `ansible-vault view` shows it again.
- **Keep the environments apart.** You can keep your production environment separate from development, test, and staging environments by using separate inventory files or directories for each environment <Cite n={29} />. If an inventory contains both production and development environments, developers using that inventory would be able to access production secrets <Cite n={29} />.
- **Use the right tool for the right test.** Molecule is an Ansible testing framework designed for developing and testing Ansible collections, playbooks, and roles <Cite n={37} />. An integration test battery, such as Selenium tests or automated API tests, should be written by your QA team if you are a production webservice <Cite n={28} />. It would usually not be embedded into your playbooks <Cite n={28} />. It does make sense to include some basic health checks into your playbooks <Cite n={28} />.

- **একটা playbook দুবার চালান, আর দ্বিতীয় সারাংশ পড়ুন।** বেশির ভাগ Ansible module কাঙ্ক্ষিত চূড়ান্ত অবস্থা আগেই অর্জিত হয়ে থাকলে কোনো কাজ না করেই exit করে <Cite n={10} />। ৩ নম্বর ধাপে দ্বিতীয় run জানিয়েছে `changed=0`। সব playbook আর সব module এভাবে আচরণ করে না <Cite n={10} />। যে দ্বিতীয় run পরিবর্তন জানায়, সেটা একটা আবিষ্কার।
- **check mode drift test হিসেবে ব্যবহার করুন, আর তার সীমা জানুন।** `--check` দিলে system-কে কাঙ্ক্ষিত অবস্থায় আনতে Ansible-কে কোনো পরিবর্তন করতে হতো বলে তার ধারণা হলে, সে তা জানায় <Cite n={28} />। ৫ নম্বর ধাপে সেটা হাতে করা edit ধরেছে। check mode শুধু একটা simulation <Cite n={15} />। যে module এটা সমর্থন করে না, তারা কিছু জানায় না আর কিছু করে না <Cite n={15} />। সাধারণত script আর command check mode-এ চলে না <Cite n={28} />। registered variable-ভিত্তিক conditional ব্যবহার করা task-এর জন্য check কোনো output দেয় না <Cite n={15} />।
- **diff পড়ুন, আর তার ভেতরের secret-এর দিকে নজর রাখুন।** diff mode আগে-পরের তুলনা দেয় <Cite n={15} />। `--diff` সংবেদনশীল তথ্য প্রকাশ করতে পারে বলে আপনি একটা task-এর জন্য `diff: false` দিয়ে সেটা বন্ধ করতে পারেন <Cite n={15} />।
- **চালানোর আগে lint করুন।** একটা playbook চালানোর আগে আপনি ansible-lint দিয়ে বিস্তারিত, Ansible-নির্দিষ্ট মতামত পেতে পারেন <Cite n={10} />। `--strict` option warning আর error দুটোতেই শূন্য নয় এমন exit code ফেরত দেয় <Cite n={33} />। ৭ নম্বর ধাপে দুটো ভালো file-এর exit status ছিল ০, আর খারাপ file-এর ২।
- **সস্তা যাচাই আগে করুন।** `--syntax-check` playbook চালায় না <Cite n={20} />। `--list-hosts` মেলা host-এর তালিকা দেয়, আর আর কিছু চালায় না <Cite n={20} />। `--list-tasks` যে সব task চালানো হতো তার তালিকা দেয় <Cite n={20} />। ৩ নম্বর ধাপে টিউটোরিয়াল আসল run-এর আগে `--syntax-check` আর `--list-tasks` চালিয়েছে।
- **secret রাখুন Vault-এ, আর password রাখুন Git-এর বাইরে।** tips page বলে, সংবেদনশীল বা গোপন variable Ansible Vault দিয়ে encrypt করা উচিত <Cite n={29} />। docs বলে, password file source control-এ যোগ না করতে <Cite n={44} />। ৮ নম্বর ধাপ দেখায় encrypted file-এ plain text নেই, আর `ansible-vault view` সেটা আবার দেখায়।
- **পরিবেশগুলো আলাদা রাখুন।** আপনি প্রতিটা পরিবেশের জন্য আলাদা inventory file বা directory ব্যবহার করে আপনার production পরিবেশকে development, test আর staging পরিবেশ থেকে আলাদা রাখতে পারেন <Cite n={29} />। একটা inventory-তে production আর development দুটোই থাকলে সেটা যারা ব্যবহার করেন সেই developer-রা production-এর secret-এ প্রবেশ করতে পারতেন <Cite n={29} />।
- **ঠিক test-এর জন্য ঠিক tool ব্যবহার করুন।** Molecule হলো একটা Ansible testing framework, যা Ansible collection, playbook আর role তৈরি ও test করার জন্য বানানো <Cite n={37} />। Selenium test বা automated API test-এর মতো একটা integration test battery আপনি production webservice হলে আপনার QA team-এর লেখা উচিত <Cite n={28} />। সেটা সাধারণত আপনার playbook-এর ভেতরে বসানো হয় না <Cite n={28} />। playbook-এ কিছু মৌলিক health check রাখা অর্থবহ <Cite n={28} />।

## Common mistakes

<Voices>
<Technical>

- **Reading `ping` as a network test.** The `ping` module always returns `pong` on successful contact <Cite n={39} />. It does not make sense in playbooks, but it is useful from `/usr/bin/ansible` to verify the ability to log in and that a usable Python is configured <Cite n={39} />.
- **Running `shell` or `command` without `changed_when`.** You should always use the `changed_when` clause on tasks that do not naturally detect if a change has occurred <Cite n={35} />. Some of the most common examples are the `shell` and `command` modules, which run arbitrary commands <Cite n={35} />. The rule `no-changed-when` of ansible-lint checks that tasks return changes to results or conditions <Cite n={35} />. Step 7 shows it.
- **Treating check mode as a full preview.** Check mode is just a simulation <Cite n={15} />. Modules that do not support check mode report nothing and do nothing <Cite n={15} />. Ordinarily, scripts and commands do not run in check mode <Cite n={28} />. A task with `check_mode: false` runs in normal mode and makes changes to the system, even when the playbook is called with `--check` <Cite n={15} />.
- **Reading the exit status of a check as the result.** In steps 4 and 5, the exit status of `--check` was 0, although the check reported a change. The tutorial looked at the recap instead.
- **Reading `ok` as "the task did not run".** In steps 4 and 5, the handler ran and printed `ok`, because its `copy` task found nothing to change.
- **Expecting a handler to run at once, or after a failure.** Handlers run in the order of the `handlers` section, and not in the order of the `notify` list <Cite n={13} />. Notifying the same handler multiple times results in executing the handler only once, regardless of how many tasks notify it <Cite n={13} />. The `meta: flush_handlers` task triggers the handlers that have been notified at that point in the play <Cite n={13} />. The option `--force-handlers` runs handlers even if a task fails <Cite n={20} />. Step 3 shows that `--list-tasks` does not list handlers.
- **Using `ignore_errors` to hide a failure.** The directive only works when the task can run and returns a value of failed <Cite n={16} />. It does not make Ansible ignore undefined variable errors, connection failures, execution issues, or syntax errors <Cite n={16} />.
- **Leaving a file mode unquoted.** For consistent results, quote octal numbers, so that Ansible receives a string <Cite n={21} />.
- **Leaving plays and tasks without names.** In its output, Ansible shows you the name of each named entity it runs <Cite n={29} />. The rule `name[play]` says that all plays should be named, and `name[missing]` says that all tasks should be named <Cite n={34} />. Step 7 shows both.
- **Using the short name of a module.** For Ansible 2.10 and later, you should use the fully-qualified collection name (FQCN) in your playbooks <Cite n={10} />.
- **Testing what Ansible already tests.** There is no need to check the return codes of commands, because Ansible checks them automatically <Cite n={28} />.
- **Treating a clean lint as a test of the result.** The playbooks page describes ansible-lint as feedback on your playbooks before you execute them <Cite n={10} />. In step 7, `site.yml` met the `production` profile, and steps 3 and 5 showed what the playbook does to the file.
- **Putting a vault password file in Git.** The docs say not to add password files to source control <Cite n={44} />.
- **Leaving `--diff` on for a secret.** Because `--diff` can reveal sensitive information, you can disable it for a task with `diff: false` <Cite n={15} />.
- **Mixing production and development in one inventory.** If an inventory contains both, developers who use it would be able to access production secrets <Cite n={29} />.
- **Not knowing where the tools write.** The setting `ANSIBLE_HOME` is the default root path for Ansible config files on the controller, and its default is `~/.ansible` <Cite n={30} />. The setting `remote_tmp` is the temporary directory to use on targets when executing tasks, and its default is `~/.ansible/tmp` <Cite n={9} />. In the tutorial's run, the empty home folder held the file `~/.cache/ansible-lint/latest.json` after the steps. Use an empty `HOME` for a practice run. Look into a folder before you delete it, because the docs say not to delete shared `~/.ansible` or `ANSIBLE_HOME` directories when they contain installed roles or collections <Cite n={33} />.

- **vault password file Git-এ রাখা।** docs বলে, password file source control-এ যোগ না করতে <Cite n={44} />।
- **secret-এর জন্য `--diff` চালু রাখা।** `--diff` সংবেদনশীল তথ্য প্রকাশ করতে পারে বলে আপনি একটা task-এর জন্য `diff: false` দিয়ে সেটা বন্ধ করতে পারেন <Cite n={15} />।
- **একটা inventory-তে production আর development মেশানো।** একটা inventory-তে দুটোই থাকলে সেটা যারা ব্যবহার করেন সেই developer-রা production-এর secret-এ প্রবেশ করতে পারতেন <Cite n={29} />।
- **tool-গুলো কোথায় লেখে তা না জানা।** `ANSIBLE_HOME` setting হলো controller-এ Ansible config file-এর default root path, আর এর default `~/.ansible` <Cite n={30} />। `remote_tmp` setting হলো target-এ task চালানোর সময় ব্যবহারের অস্থায়ী directory, আর এর default `~/.ansible/tmp` <Cite n={9} />। টিউটোরিয়ালের run-এ ধাপগুলোর পর খালি home folder-এ ছিল `~/.cache/ansible-lint/latest.json` file। practice run-এর জন্য একটা খালি `HOME` ব্যবহার করুন। কোনো folder মোছার আগে ভেতরে দেখুন, কারণ docs বলে, shared `~/.ansible` বা `ANSIBLE_HOME` directory-তে ইনস্টল করা role বা collection থাকলে সেগুলো না মুছতে <Cite n={33} />।

<Callout type="tip" title="Tutorial advice">
This list is the tutorial's own advice for a tester who works with Ansible.

- Run `ansible-playbook --syntax-check` and `ansible-lint` on every pull request, and fail the build on a non-zero exit status.
- Run a playbook twice on a clean machine, and expect `changed=0` in the second run.
- Run `--check --diff` against a system before you deploy, and read the diff, and not only the exit status.
- Count the changes in the recap of a check run, and fail the test when the count is above 0 for a system that must not drift.
- Write a test playbook with `assert`, and write one failing variant of it, to prove that the test can fail.
- Name every play and task, and use the full name of every module, so that a failure points to a name that you can read.
- Set `changed_when` on every `command` and `shell` task.
- Keep vault passwords, vault password files, and decrypted output out of Git, bug reports, and chat messages.
- Use `diff: false` on tasks that handle secrets.
- Use made-up values and a throwaway folder for a practice run, and use an empty `HOME`.
- Use a separate inventory for each environment, and give a tester only the inventory of the test environment.
- Keep the date, the versions of ansible-core and ansible-lint, and the exact commands with every test result.

## Key words

| Term | Meaning |
|---|---|
| Agent-less | Ansible is designed around an agent-less architecture |
| Desired state | You declare the desired state of a local or remote system in your playbook |
| Control node | A system on which Ansible is installed |
| Managed node | A remote system, or host, that Ansible controls |
| Inventory | A list of managed nodes that are logically organized |
| Playbook | Playbooks are automation blueprints, in YAML format, that Ansible uses to deploy and configure managed nodes |
| Play | An ordered list of tasks that maps to managed nodes in an inventory |
| Task | A reference to a single module that defines the operations that Ansible performs |
| Module | A unit of code or binary that Ansible runs on managed nodes |
| Ad hoc command | An ad hoc command uses the /usr/bin/ansible command-line tool to automate a single task on one or more managed nodes |
| Idempotent | An operation is idempotent if the result of performing it once is exactly the same as the result of performing it repeatedly without any intervening actions |
| Variable | Ansible uses variables to manage differences between systems |
| Fact | Facts are things that are discovered about remote nodes |
| Template | Templates are processed by the Jinja2 templating language |
| Handler | Handlers are tasks that only run when notified |
| Block | Blocks create logical groups of tasks |
| Role | Roles let you automatically load related vars, files, tasks, handlers, and other Ansible artifacts based on a known file structure |
| Check mode | In check mode, Ansible runs without making any changes on remote systems |
| Diff mode | In diff mode, Ansible provides before-and-after comparisons |
| Ansible Vault | Ansible vault provides a way to encrypt and manage sensitive data such as passwords |
| Ansible Lint | Ansible Lint is a command-line tool for linting playbooks, roles and collections |
| Profile | Profiles gradually increase the strictness of the rules |
| Molecule | Molecule is an Ansible testing framework designed for developing and testing Ansible collections, playbooks, and roles |
