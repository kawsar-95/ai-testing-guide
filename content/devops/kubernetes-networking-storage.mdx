# Kubernetes Networking and Storage

This page is about how Pods are reached over the network, through Services and DNS names, and how data is kept when a Pod goes away, through volumes, with a practice run on the local cluster of [Kubernetes Basics](/devops/kubernetes-basics/).

<PageMeta />

## What it is

<Voices>
<Technical>

**Pods come and go.** If you use a Deployment to run your app, that Deployment can create and destroy Pods dynamically <Cite n={1} />. Each Pod gets its own IP address, and the set of Pods running in one moment in time could be different from the set of Pods running that application a moment later <Cite n={1} />.

**The Pod network.** Each pod in a cluster gets its own unique cluster-wide IP address <Cite n={4} />. All pods can communicate with all other pods, whether they are on the same node or on different nodes, directly, without the use of proxies or address translation (NAT) <Cite n={4} />.

**A Service.** In Kubernetes, a Service is a method for exposing a network application that is running as one or more Pods in your cluster <Cite n={1} />. The set of Pods targeted by a Service is usually determined by a selector that you define <Cite n={1} />. Kubernetes creates DNS records for Services and Pods <Cite n={2} />. You can contact Services with consistent DNS names instead of IP addresses <Cite n={2} />.

**Traffic from outside.** Ingress exposes HTTP and HTTPS routes from outside the cluster to services within the cluster <Cite n={7} />. The Kubernetes project recommends using Gateway instead of Ingress, and the Ingress API has been frozen <Cite n={7} />. Gateway API is a family of API kinds that provide dynamic infrastructure provisioning and advanced traffic routing <Cite n={8} />.

**Storage.** On-disk files in a container are ephemeral <Cite n={3} />. One problem occurs when a container crashes or is stopped; the container state is not saved, so all of the files that were created or modified during the lifetime of the container are lost <Cite n={3} />. After a crash, kubelet restarts the container with a clean state <Cite n={3} />. Another problem occurs when multiple containers are running in a Pod and need to share files <Cite n={3} />. The Kubernetes volume abstraction can help you to solve both of these problems <Cite n={3} />. At its core, a volume is a directory, possibly with some data in it, which is accessible to the containers in a Pod <Cite n={3} />.

| Object | What it is |
|---|---|
| Ephemeral volume, such as `emptyDir` | Has a lifetime linked to a specific Pod; `emptyDir` is empty scratch space that is initialized when the Pod is assigned to a node, and is deleted when the Pod is removed from that node <Cite n={3} /> |
| PersistentVolume (PV) | A piece of storage in the cluster that has been provisioned by an administrator or dynamically provisioned using Storage Classes <Cite n={9} /> |
| PersistentVolumeClaim (PVC) | A request for storage by a user <Cite n={9} /> |
| StorageClass | A way for administrators to describe the classes of storage they offer <Cite n={10} /> |

When a Pod ceases to exist, Kubernetes destroys ephemeral volumes; however, Kubernetes does not destroy persistent volumes <Cite n={3} />.

</Technical>
<Layman>

**Pods come and go.** If a Deployment runs your app, it can make and remove Pods on the fly <Cite n={1} />. Each Pod gets its own IP address, and the Pods that run the app now may not be the same Pods that run it a moment later <Cite n={1} />.

**The Pod network.** Each Pod in a cluster gets its own IP address, unique in the whole cluster <Cite n={4} />. Every Pod can talk to every other Pod, on the same node or on another node, directly, without a proxy and without address translation (NAT) <Cite n={4} />.

**A Service.** A Service is a way to expose a network application that runs as one or more Pods in your cluster <Cite n={1} />. The Pods of a Service are usually picked by a selector that you write <Cite n={1} />. Kubernetes creates DNS records for Services and Pods <Cite n={2} />. So you can reach a Service by a name that stays the same, instead of by an IP address <Cite n={2} />.

**Traffic from outside.** An Ingress exposes HTTP and HTTPS routes from outside the cluster to Services inside it <Cite n={7} />. The Kubernetes project recommends Gateway instead of Ingress, and the Ingress API is frozen <Cite n={7} />. Gateway API is a family of API kinds that set up infrastructure on demand and route traffic in advanced ways <Cite n={8} />.

**Storage.** Files that a container keeps on its disk are ephemeral: they do not last <Cite n={3} />. Problem one: when a container crashes or is stopped, its state is not saved, and all the files that it made or changed while it ran are lost <Cite n={3} />. After a crash, the kubelet restarts the container with a clean state <Cite n={3} />. Problem two: several containers run in one Pod and need to share files <Cite n={3} />. The Kubernetes volume abstraction can help you solve both problems <Cite n={3} />. At its core, a volume is a folder, maybe with some data in it, that the containers in a Pod can use <Cite n={3} />.

| Object | What it is |
|---|---|
| Ephemeral volume, such as `emptyDir` | Lives as long as one Pod; `emptyDir` is empty scratch space, made when the Pod is placed on a node and deleted when the Pod is removed from that node <Cite n={3} /> |
| PersistentVolume (PV) | A piece of storage in the cluster, set up by an administrator, or set up on demand through a StorageClass <Cite n={9} /> |
| PersistentVolumeClaim (PVC) | A user's request for storage <Cite n={9} /> |
| StorageClass | A way for administrators to describe the kinds of storage that they offer <Cite n={10} /> |

When a Pod stops existing, Kubernetes destroys its ephemeral volumes, but it does not destroy persistent volumes <Cite n={3} />.

## How it works

<Voices>
<Technical>

**A Service gets an address and a list of Pods.** Kubernetes assigns a Service an IP address, the cluster IP, that is used by the virtual IP address mechanism <Cite n={1} />. The controller for that Service continuously scans for Pods that match its selector, and then makes any necessary updates to the set of EndpointSlices for the Service <Cite n={1} />. EndpointSlices track the IP addresses of backend endpoints; they are normally associated with a Service, and the backend endpoints typically represent Pods <Cite n={5} />. A Service can map any incoming port to a `targetPort`; by default, the `targetPort` is set to the same value as the `port` field <Cite n={1} />.

**kube-proxy sends the traffic.** Each instance of kube-proxy watches the Kubernetes control plane for the addition and removal of Service and EndpointSlice objects <Cite n={6} />. For each Service, kube-proxy calls appropriate APIs, depending on the kube-proxy mode, to configure the node to capture traffic to the Service's clusterIP and port, and redirect that traffic to one of the Service's endpoints <Cite n={6} />. If you do not choose a mode explicitly, kube-proxy uses the recommended default: in Kubernetes 1.37, this is iptables, but a future version of Kubernetes will change the default to nftables <Cite n={6} />. In iptables mode, each change may wait up to the full `minSyncPeriod` before it is processed, so the rules can be out of sync with the API server for that time; the default value of `minSyncPeriod` is 1s <Cite n={6} />.

**Four types of Service** <Cite n={1} />:

| Type | What it does |
|---|---|
| `ClusterIP` | Exposes the Service on a cluster-internal IP, which makes it only reachable from within the cluster; this is the default type |
| `NodePort` | Exposes the Service on each Node's IP at a static port, the NodePort; the control plane allocates the port from a range, by default 30000-32767 |
| `LoadBalancer` | Exposes the Service externally using an external load balancer; Kubernetes does not directly offer a load balancing component |
| `ExternalName` | Maps the Service to the contents of the `externalName` field, for example a hostname; no proxying of any kind is set up |

To implement a Service of type `LoadBalancer`, Kubernetes typically starts off by making the changes that are equivalent to requesting a Service of type `NodePort`; the cloud-controller-manager then configures the external load balancer to forward traffic to that node port <Cite n={1} />.

**DNS names.** A normal Service is assigned DNS A and/or AAAA records with a name of the form `my-svc.my-namespace.svc.cluster-domain.example`, which resolves to the cluster IP of the Service <Cite n={2} />. DNS queries that don't specify a namespace are limited to the Pod's namespace, and you access Services in other namespaces by specifying the namespace in the DNS query <Cite n={2} />. DNS queries may be expanded using the Pod's `/etc/resolv.conf`, which the kubelet configures for each Pod; the values of its `search` option are used to expand queries <Cite n={2} />.

**Storage is claimed, then bound.** A control loop in the control plane watches for new PVCs, finds a matching PV if possible, and binds them together <Cite n={9} />. A PVC to PV binding is a one-to-one mapping <Cite n={9} />, and claims will remain unbound indefinitely if a matching volume does not exist <Cite n={9} />. An administrator can specify a default StorageClass that applies to any PVCs that don't request a specific class <Cite n={10} />. The `WaitForFirstConsumer` mode delays the binding and provisioning of a PersistentVolume until a Pod using the PersistentVolumeClaim is created <Cite n={10} />. Pods access storage by using the claim as a volume, and claims must exist in the same namespace as the Pod using the claim <Cite n={9} />.

**Access modes** <Cite n={9} />:

| Access mode | Meaning |
|---|---|
| `ReadWriteOnce` | The volume can be mounted as read-write by a single node; it can still allow multiple Pods to access the volume when the Pods are running on the same node |
| `ReadOnlyMany` | The volume can be mounted as read-only by many nodes |
| `ReadWriteMany` | The volume can be mounted as read-write by many nodes |
| `ReadWriteOncePod` | The volume can be mounted as read-write by a single Pod |

**What happens to the data.** When a user is done with their volume, they can delete the PVC objects, and the reclaim policy of a PersistentVolume tells the cluster what to do with the volume after it has been released of its claim <Cite n={9} />. Volumes that were dynamically provisioned inherit the reclaim policy of their StorageClass, which defaults to `Delete` <Cite n={9} />. For volume plugins that support it, `Delete` removes both the PersistentVolume object from Kubernetes and the associated storage asset in the external infrastructure <Cite n={9} />. With `Retain`, the PersistentVolume still exists when the PersistentVolumeClaim is deleted, and the volume is considered "released" <Cite n={9} />.

|---|---|

| `ReadOnlyMany` | Many nodes can mount the volume to read only |
| `ReadWriteMany` | Many nodes can mount the volume to read and write |
| `ReadWriteOncePod` | One Pod can mount the volume to read and write |

Where the volume plugin supports it, `Delete` removes both the PersistentVolume object and the real storage behind it <Cite n={9} />. With `Retain`, the PersistentVolume is still there after the claim is deleted, and the volume counts as "released" <Cite n={9} />.

**Service একটা address আর Pod-এর একটা তালিকা পায়।** Kubernetes একটা Service-কে একটা IP address দেয়, cluster IP, যা virtual IP address mechanism ব্যবহার করে <Cite n={1} />। সেই Service-এর controller ক্রমাগত তার selector-এর সাথে মেলে এমন Pod খোঁজে, তারপর Service-এর EndpointSlice-গুলোতে দরকারি update করে <Cite n={1} />। EndpointSlice backend endpoint-গুলোর IP address track করে; এগুলো সাধারণত একটা Service-এর সাথে যুক্ত থাকে, আর backend endpoint-গুলো সাধারণত Pod <Cite n={5} />। একটা Service যেকোনো incoming port-কে একটা `targetPort`-এ map করতে পারে; default-এ `targetPort` `port` field-এর সমান মান পায় <Cite n={1} />।

**kube-proxy traffic পাঠায়।** প্রতিটা kube-proxy Kubernetes control plane-এ Service আর EndpointSlice object যোগ হওয়া আর সরে যাওয়ার দিকে নজর রাখে <Cite n={6} />। প্রতিটা Service-এর জন্য kube-proxy তার mode অনুযায়ী উপযুক্ত API call করে, যাতে node Service-এর clusterIP আর port-এর traffic ধরে, আর সেই traffic Service-এর একটা endpoint-এ পাঠায় <Cite n={6} />। আপনি স্পষ্ট করে mode বেছে না নিলে kube-proxy recommended default ব্যবহার করে: Kubernetes 1.37-এ এটা iptables, তবে Kubernetes-এর পরের কোনো version default বদলে nftables করবে <Cite n={6} />। iptables mode-এ প্রতিটা পরিবর্তন process হওয়ার আগে পুরো `minSyncPeriod` পর্যন্ত অপেক্ষা করতে পারে, তাই সেই সময়টুকু rule-গুলো API server-এর সাথে মেলে না থাকতে পারে; `minSyncPeriod`-এর default মান 1s <Cite n={6} />।

**Service-এর চার type** <Cite n={1} />:

| Type | কী করে |
|---|---|
| `ClusterIP` | Service-কে cluster-এর ভেতরের একটা IP-তে প্রকাশ করে, ফলে শুধু cluster-এর ভেতর থেকে পৌঁছানো যায়; এটাই default type |
| `NodePort` | Service-কে প্রতিটা Node-এর IP-তে একটা স্থির port-এ প্রকাশ করে, NodePort; control plane port-টা একটা range থেকে দেয়, default 30000-32767 |
| `LoadBalancer` | একটা external load balancer দিয়ে Service-কে বাইরে প্রকাশ করে; Kubernetes নিজে সরাসরি কোনো load balancing component দেয় না |
| `ExternalName` | Service-কে `externalName` field-এর মানে map করে, যেমন একটা hostname; কোনো ধরনের proxying হয় না |

`LoadBalancer` type-এর Service তৈরিতে Kubernetes সাধারণত শুরুতে `NodePort` type-এর Service চাওয়ার সমান পরিবর্তনগুলো করে; তারপর cloud-controller-manager external load balancer-কে সেই node port-এ traffic পাঠাতে configure করে <Cite n={1} />।

**DNS নাম।** একটা সাধারণ Service `my-svc.my-namespace.svc.cluster-domain.example` ধরনের নামে DNS A এবং/বা AAAA record পায়, যা Service-এর cluster IP-তে resolve হয় <Cite n={2} />। যে DNS query namespace বলে না, তা Pod-এর নিজের namespace-এ সীমিত থাকে; অন্য namespace-এর Service-এ পৌঁছাতে DNS query-তে namespace দিন <Cite n={2} />। DNS query Pod-এর `/etc/resolv.conf` দিয়ে বাড়ানো (expand) হতে পারে, যা kubelet প্রতিটা Pod-এর জন্য configure করে; এর `search` option-এর মানগুলো দিয়ে query expand হয় <Cite n={2} />।

**Storage আগে claim, তারপর bind।** control plane-এর একটা control loop নতুন PVC-র দিকে নজর রাখে, সম্ভব হলে মেলে এমন একটা PV খুঁজে বের করে, আর দুটোকে bind করে <Cite n={9} />। PVC আর PV-র binding এক-এক (one-to-one) <Cite n={9} />, আর মেলে এমন volume না থাকলে claim অনির্দিষ্টকাল unbound থাকে <Cite n={9} />। একজন administrator একটা default StorageClass ঠিক করে দিতে পারেন, যা নির্দিষ্ট class না চাওয়া সব PVC-তে খাটে <Cite n={10} />। `WaitForFirstConsumer` mode PersistentVolume-এর binding আর provisioning পিছিয়ে দেয়, যতক্ষণ না PersistentVolumeClaim ব্যবহার করা একটা Pod তৈরি হয় <Cite n={10} />। Pod claim-কে volume হিসেবে ব্যবহার করে storage পায়, আর claim-কে Pod-এর একই namespace-এ থাকতে হয় <Cite n={9} />।

**Access mode** <Cite n={9} />:

| Access mode | অর্থ |
|---|---|
| `ReadWriteOnce` | একটা node volume-টা read-write হিসেবে mount করতে পারে; Pod-গুলো একই node-এ চললে একাধিক Pod তখনও volume-টা ব্যবহার করতে পারে |
| `ReadOnlyMany` | অনেক node volume-টা read-only হিসেবে mount করতে পারে |
| `ReadWriteMany` | অনেক node volume-টা read-write হিসেবে mount করতে পারে |
| `ReadWriteOncePod` | একটা Pod volume-টা read-write হিসেবে mount করতে পারে |

**Data-র কী হয়।** volume-এর কাজ শেষ হলে user PVC object মুছতে পারেন, আর claim থেকে ছাড়া পাওয়ার পর volume নিয়ে কী করতে হবে, তা PersistentVolume-এর reclaim policy cluster-কে বলে <Cite n={9} />। dynamically তৈরি volume তার StorageClass-এর reclaim policy পায়, যার default `Delete` <Cite n={9} />। যে volume plugin এটা support করে, তাতে `Delete` Kubernetes থেকে PersistentVolume object আর external infrastructure-এর সংশ্লিষ্ট storage asset, দুটোই সরিয়ে দেয় <Cite n={9} />। `Retain`-এ PersistentVolumeClaim মোছার পরও PersistentVolume থেকে যায়, আর volume-টাকে "released" ধরা হয় <Cite n={9} />।

**6. Clean up.** `kubectl delete namespaces` deletes a namespace, and this deletes everything under the namespace <Cite n={14} />. `--timeout` is the length of time to wait before giving up on a delete <Cite n={20} />:

**৫. Pod চলে গেলেও data রাখুন।** type দিয়ে আর নাম ছাড়া `kubectl get` ওই type-এর সব resource দেখায়, আর type একবচন, বহুবচন বা সংক্ষিপ্ত রূপে দেওয়া যায় <Cite n={23} />:



cluster-এ একটা class ছিল, `standard`, default হিসেবে চিহ্নিত, reclaim policy `Delete` আর binding mode `WaitForFirstConsumer`। এই claim, `net-pvc.yaml`, কোনো class বলে না, তাই default class এতে খাটে <Cite n={10} />:

```yaml
apiVersion: v1

  accessModes:
  - ReadWriteOnce
  resources:
    requests:
```


`WaitForFirstConsumer` PersistentVolume-এর binding আর provisioning পিছিয়ে দেয়, যতক্ষণ না PersistentVolumeClaim ব্যবহার করা একটা Pod তৈরি হয় <Cite n={10} />। Pod claim-কে volume হিসেবে ব্যবহার করে storage পায় <Cite n={9} />। এই Pod, `net-writer.yaml`, volume-এ একটা লাইন লেখে:

```yaml
apiVersion: v1

  name: writer
  namespace: net-lab
spec:
  restartPolicy: Never
  containers:
  - name: writer
    image: busybox:1.28
    command: ["sh", "-c", "echo 'run 1: 12 passed' > /data/result.txt"]
    volumeMounts:
    - name: data
      mountPath: /data
  volumes:
  - name: data
    persistentVolumeClaim:
      claimName: data
```

`net-reader.yaml` একই file, নাম `reader` আর command `cat /data/result.txt`। `kubectl wait` reference `--for=jsonpath='{.status.phase}'=Running` দিয়ে একটা field-এর জন্য অপেক্ষা করে <Cite n={18} />:

```bash
kubectl apply -f net-writer.yaml

kubectl get pvc data -n net-lab
kubectl get pv
```

run-এ claim এখন একটা নতুন volume-এ `Bound`:

```text

```

```text

```

volume-টা তার StorageClass-এর reclaim policy `Delete` পেয়েছে <Cite n={9} />। তারপর run writer মুছে একটা নতুন Pod দিয়ে file-টা পড়েছে। `kubectl delete` resource আর নাম দিয়ে resource মোছে <Cite n={20} />, আর `kubectl logs` একটা Pod-এর log দেখায় <Cite n={21} />:


```text

```

যে Pod file-টা লিখেছিল, সেটা আর ছিল না, আর একটা নতুন Pod file-টা পড়েছে: persistent volume কোনো একক Pod-এর আয়ুর পরেও টিকে থাকে <Cite n={3} />।

<Technical>

**Test the way clients call the app.** One of the most common ways that clients consume a Service is through a DNS name <Cite n={11} />. From a test Pod in another namespace, use a namespace-qualified name such as `web.net-lab`: DNS queries that don't specify a namespace are limited to the Pod's namespace <Cite n={2} />.

**When a Service gives no response, go down the list.** Debug Services asks, among other questions: Does the Service exist? Does the Service work by DNS name? Does the Service have any EndpointSlices? Are the Pods working? <Cite n={11} /> To check the Pods alone, you can bypass the Service mechanism and go straight to the Pods <Cite n={11} />. In step 3, the Service existed and had a cluster IP, and its EndpointSlice was empty.

**Know what a port forward tests.** With a Service name, `kubectl port-forward` selects a matching Pod to forward to <Cite n={13} />. A test through it reaches that Pod, and the docs open a separate terminal for it, because it does not return <Cite n={13} />.

**Check that data outlives a Pod.** For any kind of volume in a given Pod, data is preserved across container restarts, and persistent volumes exist beyond the lifetime of any individual Pod <Cite n={3} />. Step 5 tested this: one Pod wrote a file, and a new Pod read it after the first was deleted.

**Know what clean-up deletes.** Deleting a namespace deletes everything under the namespace <Cite n={14} />. For volume plugins that support the `Delete` reclaim policy, deletion also removes the associated storage asset in the external infrastructure <Cite n={9} />. With `Retain`, the PersistentVolume still exists when the PersistentVolumeClaim is deleted <Cite n={9} />.

Pod-গুলো কি কাজ করছে? <Cite n={11} /> শুধু Pod-গুলো যাচাই করতে Service mechanism এড়িয়ে সরাসরি Pod-এ যেতে পারেন <Cite n={11} />। ধাপ ৩-এ Service ছিল, তার cluster IP ছিল, আর তার EndpointSlice খালি ছিল।

**পরিবর্তনের পরে একটু দেরি আশা করুন।** iptables mode-এ প্রতিটা পরিবর্তন process হওয়ার আগে পুরো `minSyncPeriod` পর্যন্ত অপেক্ষা করতে পারে; default 1s <Cite n={6} />। ধাপ ৪-এ একটা নতুন NodePort-এ প্রথম request ব্যর্থ হয়েছে, আর ২ সেকেন্ড পরে একই request কাজ করেছে।

**Port forward কী test করে, জানুন।** Service-এর নাম দিলে `kubectl port-forward` forward করার জন্য মেলে এমন একটা Pod বেছে নেয় <Cite n={13} />। এর মধ্য দিয়ে একটা test সেই Pod-এ পৌঁছায়, আর docs এর জন্য আলাদা terminal খোলে, কারণ এটা ফেরত আসে না <Cite n={13} />।

**Data একটা Pod-এর পরেও টেকে কি না, যাচাই করুন।** একটা Pod-এর যেকোনো ধরনের volume-এ container restart হলেও data থেকে যায়, আর persistent volume কোনো একক Pod-এর আয়ুর পরেও টিকে থাকে <Cite n={3} />। ধাপ ৫ এটা test করেছে: একটা Pod একটা file লিখেছে, আর প্রথমটা মোছার পরে একটা নতুন Pod সেটা পড়েছে।

**Clean-up কী মোছে, জানুন।** একটা namespace মুছলে namespace-এর ভেতরের সবকিছু মুছে যায় <Cite n={14} />। যে volume plugin `Delete` reclaim policy support করে, তাতে মোছার সময় external infrastructure-এর সংশ্লিষ্ট storage asset-ও সরে যায় <Cite n={9} />। `Retain`-এ PersistentVolumeClaim মোছার পরও PersistentVolume থেকে যায় <Cite n={9} />।

</Bangla>
</Voices>

## Common mistakes

<Voices>
<Technical>

- **A typo in the selector.** If the ENDPOINTS column is `<none>`, check that the selector of the Service selects for the labels on your Pods; a common mistake is to have a typo <Cite n={11} />. In step 3, the request was refused.
- **A short DNS name across namespaces.** DNS queries that don't specify a namespace are limited to the Pod's namespace <Cite n={2} />.
- **Waiting for an external IP on a local cluster.** Kubernetes does not directly offer a load balancing component; you must provide one, or you can integrate your Kubernetes cluster with a cloud provider <Cite n={1} />. kind's guide uses Cloud Provider KIND for this <Cite n={22} />.
- **Reading a `Pending` claim as a failure, or a fault as normal.** With `WaitForFirstConsumer`, the binding and provisioning wait until a Pod using the claim is created <Cite n={10} />. But claims will remain unbound indefinitely if a matching volume does not exist <Cite n={9} />, so read the Events of the claim.
- **Keeping test data in the files of a container.** After a crash, kubelet restarts the container with a clean state <Cite n={3} />.
- **Starting new work on Ingress.** The Kubernetes project recommends using Gateway instead of Ingress, and the Ingress API has been frozen <Cite n={7} />.

</Technical>

## What a tester can check

<Voices>
<Technical>

<Callout type="tip" title="Tutorial advice">
This list is the tutorial's own advice for a tester whose app runs on Kubernetes.

- For each Service, check that its EndpointSlices list the Pods that you expect; an empty list points to the selector or the labels.
- Call a Service by its DNS name from a test Pod, and use the name with the namespace across namespaces.
- After a test creates or changes a Service, poll it until it answers, with a time limit, before the first real check.
- Test a NodePort or LoadBalancer Service from outside the cluster, and find out first whether the cluster can provide a load balancer at all.
- Use a port forward for a quick look at one Pod, not to test how a Service spreads the requests.
- Delete the Pod that wrote some data, and check that a new Pod reads the same data.
- Before a test deletes a namespace, check the reclaim policy of its volumes, so that no data that is needed later is deleted.
</Callout>

## Key words

| Term | Meaning |
|---|---|
| Service | Exposes a network application that runs as one or more Pods, usually picked by a selector |
| Cluster IP | The IP address that Kubernetes assigns to a Service, used by the virtual IP address mechanism |
| EndpointSlice | Tracks the IP addresses of the backend endpoints of a Service, typically Pods |
| Selector | The labels that pick the Pods of a Service |
| kube-proxy | Watches Services and EndpointSlices, and configures each node to send Service traffic to an endpoint |
| `ClusterIP`, `NodePort`, `LoadBalancer`, `ExternalName` | The four types of Service; `ClusterIP` is the default |
| Service DNS name | `my-svc.my-namespace.svc.cluster-domain.example`; resolves to the cluster IP |
| Port forward | `kubectl port-forward`: forwards a local port to a matching Pod |
| Ingress | Exposes HTTP and HTTPS routes from outside the cluster to Services; frozen, and Gateway is recommended instead |
| Gateway API | A family of API kinds for dynamic infrastructure provisioning and advanced traffic routing |
| Volume | A directory, possibly with some data in it, that the containers in a Pod can use |
| `emptyDir` | Empty scratch space that lives as long as the Pod stays on its node |
| PersistentVolume (PV) | A piece of storage in the cluster, provisioned by an administrator or dynamically through a StorageClass |
| PersistentVolumeClaim (PVC) | A request for storage by a user |
| StorageClass | Describes a class of storage; can make volumes on demand |
| `WaitForFirstConsumer` | Delays binding and provisioning until a Pod that uses the claim is created |
| Access mode | `ReadWriteOnce`, `ReadOnlyMany`, `ReadWriteMany`, or `ReadWriteOncePod` |
| Reclaim policy | What the cluster does with a volume after its claim is deleted, such as `Delete` or `Retain` |
