# Git Basics

Your test code, your test plans, and your team's pipeline files live in Git. To test a branch, read what a change did, or name the exact version that has a bug, you need a few Git ideas and a short list of commands. This page gives you both, and a practice run on your own laptop.

<PageMeta />

## What it is

<Voices>
<Technical>

The major difference between Git and any other version control system (VCS) is the way that Git thinks about its data <Cite n={1} />. It thinks of its data as a series of **snapshots** of a miniature filesystem: each time you commit, Git takes a picture of what all your files look like at that moment <Cite n={1} />. A **merge** joins two or more development histories together <Cite n={2} />.

**Nearly every operation is local.** Most operations need only local files and resources, and the entire history of the project is on your local disk <Cite n={1} />.

**Everything is checksummed.** Git refers to each stored item by its checksum, a SHA-1 hash: a 40-character string of hexadecimal characters <Cite n={1} />.

A file in a Git project is in one of three states <Cite n={1} />:

| State | Meaning |
|---|---|
| Modified | You changed the file, but you have not committed it yet |
| Staged | You marked the modified file to go into your next commit |
| Committed | The data is safely stored in your local database |

The three states match the three sections of a Git project <Cite n={1} />:

- The **working tree** is a single checkout of one version of the project. Its files are placed on disk for you to use or modify <Cite n={1} />.
- The **staging area** is a file, generally in your Git directory, that stores information about what will go into your next commit. Its technical name is the **index** <Cite n={1} />.
- The **Git directory** is where Git stores the metadata and object database of your project. It is what is copied when you clone a repository <Cite n={1} />.

`git add` stages files <Cite n={4} />. A commit takes the files as they are in the staging area, and stores that snapshot permanently in the Git directory <Cite n={1} />. In a repository that `git init` made, the Git directory is a subdirectory named `.git` <Cite n={16} />:

```text
working tree  ---- git add ---->  staging area  ---- git commit ---->  Git directory (.git)
 (modified)                        (staged)                             (committed)
```

On GitHub, a **pull request** is a proposal to merge code changes into a project, so that people can discuss and review the changes before they are merged <Cite n={13} />.

</Technical>

## How it works

<Voices>
<Technical>

**Branches.** A branch in Git is a lightweight movable pointer to a commit <Cite n={5} />. The default branch name in Git is `master`, and every time you commit, the branch pointer moves forward automatically <Cite n={5} />. The `init.defaultBranch` setting changes the name for new repositories, and Git 3.0 will change the default to `main` <Cite n={17} />. A special pointer called `HEAD` points to the local branch you are currently on <Cite n={5} />.

**Switching.** `git switch <branch>` switches to a branch: the working tree and the index are updated to match it, and new commits are added to its tip <Cite n={9} />. `git switch -c <new-branch>` creates a new branch, then switches to it <Cite n={9} />.

**Merging.** There are two kinds of merge <Cite n={6} />:

- **Fast-forward.** If the commit that you merge is directly ahead of the commit you are on, there is no divergent work. Git just moves the pointer forward.
- **Three-way merge.** If the branches diverged, Git uses the two branch tips and their common ancestor. It creates a new **merge commit**, which has more than one parent.

**Conflicts.** If you changed the same part of the same file differently in the two branches, Git cannot merge them cleanly <Cite n={6} />. It pauses the merge and adds conflict-resolution markers to the file <Cite n={6} />. The part above `=======` is the version in `HEAD`, and the part below it is the version of the other branch <Cite n={6} />. You resolve it, run `git add` on each file to mark it as resolved, then run `git commit` <Cite n={6} />.

**Remotes.** A remote repository is a version of your project that is hosted on the Internet or a network <Cite n={7} />. `origin` is the default name that Git gives to the server you cloned from <Cite n={7} />.

```text
your laptop                               the server: the remote "origin"
local repository  <-- git fetch / git pull --  remote repository
local repository  --------- git push -------->  remote repository
```

- `git fetch` only downloads the data. It does not merge it with your work or modify what you are working on <Cite n={7} />.
- `git pull` runs `git fetch`, then integrates the remote branch into your current branch <Cite n={10} />.
- `git push <remote> <branch>` shares your work <Cite n={7} />. If someone pushed before you, your push is rejected: you fetch their work and incorporate it first <Cite n={7} />.

</Technical>

<Bangla>

**Branch।** Git-এ branch হলো একটা commit-এর দিকে নির্দেশ করা একটা হালকা, সরানো যায় এমন pointer <Cite n={5} />। Git-এ default branch-এর নাম `master`, আর প্রতিবার commit করলে branch pointer নিজে নিজেই সামনে এগোয় <Cite n={5} />। `init.defaultBranch` সেটিং নতুন repository-র নাম বদলায়, আর Git 3.0 default বদলে `main` করবে <Cite n={17} />। `HEAD` নামের একটা বিশেষ pointer দেখায় আপনি এখন কোন local branch-এ আছেন <Cite n={5} />।

**Switch করা।** `git switch <branch>` একটা branch-এ নিয়ে যায়: working tree আর index সেই branch-এর মতো হয়ে যায়, আর নতুন commit সেই branch-এর মাথায় যোগ হয় <Cite n={9} />। `git switch -c <new-branch>` একটা নতুন branch বানায়, তারপর সেখানে যায় <Cite n={9} />।

**Merge।** merge দুই রকম <Cite n={6} />:

- **Fast-forward।** আপনি যে commit merge করছেন সেটা যদি আপনার এখনকার commit-এর ঠিক সামনে থাকে, তাহলে আলাদা হয়ে যাওয়া কোনো কাজ নেই। Git শুধু pointer সামনে সরিয়ে দেয়।
- **Three-way merge।** branch দুটো আলাদা হয়ে গেলে Git দুটো branch-এর মাথা আর তাদের common ancestor ব্যবহার করে। এটা একটা নতুন **merge commit** বানায়, যার একাধিক parent থাকে।

**Conflict।** দুই branch-এ একই ফাইলের একই অংশ আলাদাভাবে বদলালে Git পরিষ্কারভাবে merge করতে পারে না <Cite n={6} />। এটা merge থামিয়ে দেয় আর ফাইলে conflict-resolution marker বসায় <Cite n={6} />। `=======`-এর ওপরের অংশ `HEAD`-এর version, আর নিচের অংশ অন্য branch-এর version <Cite n={6} />। আপনি সমাধান করেন, প্রতিটা ফাইলে `git add` চালিয়ে resolved চিহ্নিত করেন, তারপর `git commit` চালান <Cite n={6} />।

**Remote।** remote repository হলো Internet বা network-এ রাখা আপনার project-এর একটা version <Cite n={7} />। যে server থেকে clone করেছেন, Git তার default নাম দেয় `origin` <Cite n={7} />।

```text
your laptop                               the server: the remote "origin"
local repository  <-- git fetch / git pull --  remote repository
local repository  --------- git push -------->  remote repository
```

- `git fetch` শুধু data download করে। এটা আপনার কাজের সাথে merge করে না, আর আপনি যা নিয়ে কাজ করছেন তা বদলায় না <Cite n={7} />।
- `git pull` প্রথমে `git fetch` চালায়, তারপর remote branch-কে আপনার current branch-এ যোগ করে <Cite n={10} />।
- `git push <remote> <branch>` আপনার কাজ share করে <Cite n={7} />। আপনার আগে কেউ push করে থাকলে আপনার push reject হয়: আগে তাদের কাজ fetch করে নিজের কাজে মেলাতে হয় <Cite n={7} />।

## Try it

<Voices>
<Technical>

This practice run makes a small repository, a branch, and a merge conflict on purpose. Use an empty folder.

**1. Tell Git who you are.** Do this once. Every commit uses this information <Cite n={3} />:

```bash
git config --global user.name "Your Name"
git config --global user.email you@example.com
```

**2. Start a repository and commit a file.** You obtain a Git repository in one of two ways: turn a local directory into one, or clone an existing one <Cite n={16} />. Here you do the first. `git init -b main` starts a repository whose first branch is `main` <Cite n={15} />. Create `checklist.txt` with one line, `Login: a valid user can sign in`. Then check the state, stage the file, and commit it <Cite n={4} />. `git log --oneline` shows each commit on one line, with the first few characters of its hash <Cite n={8} />.

```bash
git init -b main
git status
git add checklist.txt
git commit -m "Add the login checklist"
git log --oneline
```

**3. Change the same line on two branches.** `git switch -c` creates a branch and switches to it, and `git switch <branch>` switches back <Cite n={9} />. `git commit -a` stages every file that is already tracked, then commits <Cite n={4} />.

```bash
git switch -c fix-checklist
# edit the line to: Login: a valid user can sign in with email
git commit -a -m "Say how the user signs in"
git switch main
# edit the line to: Login: a valid user can sign in and sign out
git commit -a -m "Add sign out"
```

**4. Merge, and see the conflict.** Git stops with "Automatic merge failed; fix conflicts and then commit the result", and `git status` lists the unmerged file <Cite n={6} />.

```bash
git merge fix-checklist
git status
```

The file now has the markers <Cite n={6} />:

```text
<<<<<<< HEAD
Login: a valid user can sign in and sign out
=======
Login: a valid user can sign in with email
>>>>>>> fix-checklist
```

**5. Resolve it.** Edit the file to the text that you want, and remove the `<<<<<<<`, `=======`, and `>>>>>>>` lines. Then mark it as resolved and finish the merge commit <Cite n={6} />. `--graph` draws the branch and merge history <Cite n={8} />.

```bash
git add checklist.txt
git commit
git log --oneline --graph
```

**6. Put it on GitHub.** Create an empty repository on GitHub, with no README, license, or gitignore file, to avoid errors <Cite n={15} />. Copy its URL, then add the remote, check it, and push <Cite n={15} />:

```bash
git remote add origin REMOTE-URL
git remote -v
git push -u origin main
```

</Technical>

**3. Change the same line on two branches.** `git switch -c` makes a branch and moves you to it. `git switch <branch>` moves you back <Cite n={9} />. `git commit -a` stages every file that Git already tracks, then commits <Cite n={4} />.

```bash
git switch -c fix-checklist
# edit the line to: Login: a valid user can sign in with email
git commit -a -m "Say how the user signs in"
git switch main
# edit the line to: Login: a valid user can sign in and sign out
git commit -a -m "Add sign out"
```

**4. Merge, and see the conflict.** Git stops with "Automatic merge failed; fix conflicts and then commit the result". `git status` lists the file that is not merged <Cite n={6} />.

```bash
git merge fix-checklist
git status
```

The file now has markers <Cite n={6} />:

```text
<<<<<<< HEAD
Login: a valid user can sign in and sign out
=======
Login: a valid user can sign in with email
>>>>>>> fix-checklist
```

**5. Fix it.** Change the file to the text that you want, and delete the `<<<<<<<`, `=======`, and `>>>>>>>` lines. Then mark it as fixed and finish the merge commit <Cite n={6} />. `--graph` draws the branches and the merge <Cite n={8} />.

```bash
git add checklist.txt
git commit
git log --oneline --graph
```

**6. Put it on GitHub.** Make an empty repository on GitHub. Do not add a README, license, or gitignore file, to avoid errors <Cite n={15} />. Copy its URL. Then add the remote, check it, and push <Cite n={15} />:

```bash
git remote add origin REMOTE-URL
git remote -v
git push -u origin main
```

</Layman>
<Bangla>

এই practice-এ আপনি একটা ছোট repository, একটা branch আর ইচ্ছা করে একটা merge conflict বানাবেন। একটা খালি ফোল্ডার ব্যবহার করুন।

**১. Git-কে আপনার পরিচয় দিন।** এটা একবারই করতে হয়। প্রতিটা commit এই তথ্য ব্যবহার করে <Cite n={3} />:

```bash
git config --global user.name "Your Name"
git config --global user.email you@example.com
```

**২. repository শুরু করে একটা ফাইল commit করুন।** Git repository দুইভাবে পাওয়া যায়: একটা local directory-কে repository বানিয়ে, অথবা আগে থেকে থাকা একটা repository clone করে <Cite n={16} />। এখানে আপনি প্রথমটা করবেন। `git init -b main` এমন একটা repository শুরু করে, যার প্রথম branch `main` <Cite n={15} />। `checklist.txt` নামে একটা ফাইল বানান, তাতে এক লাইন লিখুন: `Login: a valid user can sign in`। তারপর state দেখুন, ফাইলটা stage করুন আর commit করুন <Cite n={4} />। `git log --oneline` প্রতিটা commit এক লাইনে দেখায়, hash-এর প্রথম কয়েকটা অক্ষরসহ <Cite n={8} />।

```bash

git add checklist.txt
git commit -m "Add the login checklist"
git log --oneline
```

**৩. দুই branch-এ একই লাইন বদলান।** `git switch -c` একটা branch বানিয়ে সেখানে নিয়ে যায়, আর `git switch <branch>` আবার ফিরিয়ে আনে <Cite n={9} />। `git commit -a` আগে থেকে track হওয়া সব ফাইল stage করে, তারপর commit করে <Cite n={4} />।

```bash

git commit -a -m "Say how the user signs in"
git switch main
# edit the line to: Login: a valid user can sign in and sign out
git commit -a -m "Add sign out"
```

**৪. merge করুন, conflict দেখুন।** Git "Automatic merge failed; fix conflicts and then commit the result" বলে থেমে যায়, আর `git status` merge না হওয়া ফাইলটা দেখায় <Cite n={6} />।

```bash

git status
```

ফাইলে এখন marker আছে <Cite n={6} />:

```text

Login: a valid user can sign in and sign out
=======
Login: a valid user can sign in with email
>>>>>>> fix-checklist
```

**৫. সমাধান করুন।** ফাইলটা আপনার পছন্দের লেখায় বদলান, আর `<<<<<<<`, `=======` ও `>>>>>>>` লাইনগুলো মুছে দিন। তারপর resolved চিহ্নিত করে merge commit শেষ করুন <Cite n={6} />। `--graph` branch আর merge-এর history আঁকে <Cite n={8} />।

```bash

git commit
git log --oneline --graph
```

## How a tester uses it

<Voices>
<Technical>

**Test a pull request on your machine.** Anyone can work with an open pull request to continue working on it or to test it <Cite n={14} />. Find its ID number, the digits after its title <Cite n={14} />. Then fetch it into a new local branch and switch to it <Cite n={14} />, and run your tests:

```bash
git fetch origin pull/ID/head:BRANCH_NAME
git switch BRANCH_NAME
```

**Read what changed.** A pull request has tabs: **Commits** shows how the branch changed over time, **Checks** shows the automated tests, builds, and other validations, and **Files changed** shows the diff <Cite n={13} />. On your machine, `git log -p` shows the patch of each commit, and `git log --stat` lists the changed files and the number of added and removed lines <Cite n={8} />. `git diff` shows what you changed but did not stage yet, and `git diff --staged` shows what goes into your next commit <Cite n={4} />.

**Name the exact version.** `git log` lists each commit with its SHA-1 checksum <Cite n={8} />. Put it, or the short form that `git log --oneline` shows, in the bug report <Cite n={8} />. A branch name does not say exactly what you tested, because the branch pointer moves forward with every commit <Cite n={5} />.

**Keep test output out of the repository.** A `.gitignore` file lists patterns of intentionally untracked files that Git should ignore <Cite n={12} />. They are usually generated files, such as log files or files that your build produces <Cite n={4} />. The tutorial's advice: list test reports, screenshots, and videos in `.gitignore` too.

## Common mistakes

<Voices>
<Technical>

- **Adding a tracked file to `.gitignore`.** Files that Git already tracks are not affected by `.gitignore` <Cite n={12} />. Run `git rm --cached` on the file to stop tracking it, then add it to `.gitignore` <Cite n={12} />.
- **`git push --force` on a shared branch.** It disables the check that stops a push of a branch that is not an ancestor of the commit being pushed, and it can cause the remote repository to lose commits <Cite n={11} />.
- **Testing old code.** `git fetch` downloads, but it does not change your work <Cite n={7} />. Run `git pull`, which fetches and then integrates the remote branch, before you test <Cite n={10} />.
- **Committing what you did not stage.** A commit records the snapshot in your staging area, not every change in your working tree <Cite n={4} />. `git status` is the main tool to see which files are in which state <Cite n={4} />.
- **No name and email.** Every commit uses them, and they are immutably baked into the commits that you create <Cite n={3} />.
- **Leaving conflict markers in a file.** In a resolved file, the `<<<<<<<`, `=======`, and `>>>>>>>` lines are completely removed <Cite n={6} />. Check the file before you run `git add`, because staging the file marks it as resolved in Git <Cite n={6} />.

</Technical>
<Layman>

- **Adding a tracked file to `.gitignore`.** `.gitignore` does not affect files that Git already tracks <Cite n={12} />. Run `git rm --cached` on the file to stop tracking it, then add it to `.gitignore` <Cite n={12} />.
- **`git push --force` on a shared branch.** It turns off a safety check, and the remote repository can lose commits <Cite n={11} />.
- **Testing old code.** `git fetch` downloads, but it does not change your work <Cite n={7} />. Run `git pull` before you test. It fetches and then adds the remote changes to your branch <Cite n={10} />.
- **Committing what you did not stage.** A commit saves what is in your staging area, not every change in your files <Cite n={4} />. `git status` is the main tool to see which files are in which state <Cite n={4} />.
- **No name and email.** Every commit uses them, and they stay in your commits for good <Cite n={3} />.
- **Leaving conflict markers in a file.** A fixed file has no `<<<<<<<`, `=======`, or `>>>>>>>` lines left <Cite n={6} />. Check the file before you run `git add`. Staging the file tells Git that the conflict is fixed <Cite n={6} />.

</Layman>
<Bangla>

- **track হওয়া ফাইল `.gitignore`-এ যোগ করা।** Git আগে থেকেই যেসব ফাইল track করে, `.gitignore` সেগুলোর ওপর কাজ করে না <Cite n={12} />। ফাইলটার tracking বন্ধ করতে `git rm --cached` চালান, তারপর `.gitignore`-এ যোগ করুন <Cite n={12} />।
- **shared branch-এ `git push --force`।** এটা সেই check বন্ধ করে দেয় যেটা push হওয়া commit-এর ancestor নয় এমন branch update আটকায়, আর এতে remote repository commit হারাতে পারে <Cite n={11} />।
- **পুরোনো code test করা।** `git fetch` download করে, কিন্তু আপনার কাজ বদলায় না <Cite n={7} />। test করার আগে `git pull` চালান, যেটা fetch করে তারপর remote branch যোগ করে <Cite n={10} />।
- **stage না করা জিনিস commit হবে ভাবা।** commit রেকর্ড করে staging area-র snapshot, working tree-র সব change নয় <Cite n={4} />। কোন ফাইল কোন state-এ আছে তা দেখার প্রধান tool হলো `git status` <Cite n={4} />।
- **নাম আর email না দেওয়া।** প্রতিটা commit এগুলো ব্যবহার করে, আর আপনার বানানো commit-এ এগুলো স্থায়ীভাবে বসে যায় <Cite n={3} />।
- **ফাইলে conflict marker রেখে দেওয়া।** সমাধান করা ফাইল থেকে `<<<<<<<`, `=======` আর `>>>>>>>` লাইন পুরোপুরি মুছে ফেলা হয় <Cite n={6} />। `git add` চালানোর আগে ফাইলটা দেখে নিন, কারণ ফাইল stage করলেই Git সেটাকে resolved ধরে নেয় <Cite n={6} />।

## Key words

| Term | Meaning |
|---|---|
| Repository | A project under Git: you make one with `git init` or clone one, and its whole history is on your disk |
| Commit | A snapshot of the files, stored in the Git directory |
| SHA-1 hash | The 40-character checksum by which Git refers to a stored item, such as a commit |
| Working tree | A single checkout of one version of the project, on disk for you to use or modify |
| Staging area (index) | A file that stores what will go into your next commit |
| Branch | A movable pointer to a commit |
| HEAD | The pointer to the branch you are on |
| Merge | Joining two or more development histories |
| Fast-forward | A merge that only moves the pointer forward |
| Merge commit | A commit with more than one parent, made by a three-way merge |
| Merge conflict | The same part of a file changed differently on two branches |
| Remote | A version of the project on the Internet or a network |
| origin | The default name of the remote that you cloned from |
| fetch / pull / push | Download / download and integrate / share your commits |
| Pull request | A proposal on GitHub to merge changes, with review and checks |
| `.gitignore` | A file of patterns of files that Git should not track |
