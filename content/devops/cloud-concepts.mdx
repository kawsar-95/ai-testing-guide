# Cloud Concepts

It comes before the four AWS pages, which start with [AWS Compute and Storage](/devops/aws-compute-storage/).

## What it is

<Voices>
<Technical>

**Cloud computing.** Cloud computing is the on-demand delivery of IT resources over the Internet with pay-as-you-go pricing <Cite n={1} />. Instead of buying, owning, and maintaining physical data centers and servers, you can access services such as computing power, storage, and databases on an as-needed basis from a cloud provider like Amazon Web Services (AWS) <Cite n={1} />.

NIST describes cloud computing as a model for on-demand network access to a shared pool of configurable computing resources <Cite n={3} />. The resources can be rapidly provisioned and released with minimal management effort or service provider interaction <Cite n={3} />. The model has five essential characteristics, three service models, and four deployment models <Cite n={3} />.

**The three service types.** The three main types of cloud computing are Infrastructure as a Service, Platform as a Service, and Software as a Service <Cite n={1} />. AWS notes that definitions vary from company to company <Cite n={2} />.

| Type | What the provider gives you |
|---|---|
| IaaS (Infrastructure as a Service) | The basic building blocks for cloud IT: typically networking features, computers (virtual or on dedicated hardware), and data storage space <Cite n={2} /> |
| PaaS (Platform as a Service) | It removes the need to manage the underlying infrastructure (usually hardware and operating systems), so that you can focus on the deployment and management of your applications <Cite n={2} /> |
| SaaS (Software as a Service) | Software applications that are run and managed by the vendor; web-based email is a common example <Cite n={2} /> |

**Where the app runs.** A cloud-based application is fully deployed in the cloud, and all parts of it run there <Cite n={2} />. A hybrid deployment connects cloud-based resources with existing resources that are not in the cloud <Cite n={2} />. The most common hybrid method connects the cloud with existing on-premises infrastructure <Cite n={2} />.

**Why teams use it.** AWS names four benefits <Cite n={1} />:

- **Agility.** You can quickly spin up resources as you need them <Cite n={1} />.
- **Elasticity.** You can access as much or as little capacity as you need, and scale up and down as required with only a few minutes' notice <Cite n={4} />.
- **Cost savings.** The cloud allows you to trade fixed expenses (such as data centers and physical servers) for variable expenses, and to pay for IT only as you consume it <Cite n={1} />.
- **Deploy globally in minutes.** With the cloud, you can expand to new geographic regions and deploy globally in minutes <Cite n={1} />.

**Regions and Availability Zones.** AWS has the concept of a Region: a physical location around the world where AWS clusters data centers <Cite n={5} />. Each group of logical data centers is an Availability Zone (AZ) <Cite n={5} />. Each AWS Region consists of a minimum of three isolated and physically separate AZs within a geographic area <Cite n={5} />. An AZ is one or more discrete data centers with redundant power, networking, and connectivity in an AWS Region <Cite n={5} />. AZs let customers run production applications and databases that are more highly available, fault tolerant, and scalable than would be possible from a single data center <Cite n={5} />.

**Shared responsibility.** Building and operating workloads in the cloud is a shared responsibility between AWS and you <Cite n={6} />. AWS operates, manages, and controls the components from the host operating system and virtualization layer down to the physical security of the facilities in which the services run <Cite n={6} />. You assume responsibility for the guest operating system (including updates and security patches), other associated application software, and the configuration of the AWS-provided resources you use <Cite n={6} />. This split is commonly called responsibility of the cloud versus in the cloud <Cite n={6} />.

**The twelve-factor app.** The twelve-factor app is a methodology for building software-as-a-service apps <Cite n={15} /> that:

- use declarative formats for setup automation, to minimize time and cost for new developers joining the project <Cite n={15} />;
- have a clean contract with the underlying operating system, offering maximum portability between execution environments <Cite n={15} />;
- are suitable for deployment on modern cloud platforms, obviating the need for servers and systems administration <Cite n={15} />;
- minimize divergence between development and production, enabling continuous deployment for maximum agility <Cite n={15} />;
- and can scale up without significant changes to tooling, architecture, or development practices <Cite n={15} />.

The methodology can be applied to apps written in any programming language, and which use any combination of backing services <Cite n={15} />.

**The Well-Architected pillars.** The AWS Well-Architected Framework names six pillars: operational excellence, security, reliability, performance efficiency, cost optimization, and sustainability <Cite n={8} />. The reliability pillar is about making a workload perform its intended function correctly and consistently, and recover from failures with minimal impact <Cite n={8} />. Each pillar is organized into capabilities, or groupings of related best practices that share a common objective <Cite n={8} />.

</Technical>

**Cloud computing।** cloud computing-এ আপনি প্রয়োজনের সময় ইন্টারনেটের মাধ্যমে IT resource পান। আপনি pay-as-you-go পদ্ধতিতে দাম দেন <Cite n={1} />। physical data center আর server কেনা, নিজের মালিকানায় রাখা ও রক্ষণাবেক্ষণ করার দরকার নেই। computing power, storage আর database-এর মতো service আপনি প্রয়োজন মতো পান, Amazon Web Services (AWS)-এর মতো একটা cloud provider থেকে <Cite n={1} />।

NIST বলে, cloud computing হলো একটা model, যাতে configure করা যায় এমন computing resource-এর একটা shared pool-এ আপনি চাহিদা অনুযায়ী network দিয়ে প্রবেশাধিকার পান <Cite n={3} />। resource দ্রুত চালু আর ছেড়ে দেওয়া যায়, খুব কম management-এর কাজে বা provider-এর সঙ্গে যোগাযোগে <Cite n={3} />। এই model-এ পাঁচটা essential characteristic, তিনটা service model আর চারটা deployment model আছে <Cite n={3} />।

**তিন ধরনের service।** cloud computing-এর তিনটা main type হলো Infrastructure as a Service, Platform as a Service আর Software as a Service <Cite n={1} />। AWS বলে, সংজ্ঞা এক company থেকে আরেক company-তে আলাদা হয় <Cite n={2} />।

| ধরন | provider আপনাকে কী দেয় |
|---|---|
| IaaS (Infrastructure as a Service) | cloud IT-এর মৌলিক building block। সাধারণত networking feature, computer (virtual বা dedicated hardware) আর data রাখার জায়গা পাওয়া যায় <Cite n={2} /> |
| PaaS (Platform as a Service) | নিচের infrastructure (সাধারণত hardware আর operating system) আপনাকে চালাতে হয় না। আপনি app deploy আর পরিচালনায় মন দিতে পারেন <Cite n={2} /> |
| SaaS (Software as a Service) | software application, যা vendor চালায় ও পরিচালনা করে। web-based email একটা সাধারণ উদাহরণ <Cite n={2} /> |

**app কোথায় চলে।** cloud-based application পুরোপুরি cloud-এ deploy করা হয়, আর তার সব অংশ cloud-এ চলে <Cite n={2} />। hybrid deployment cloud-এর resource-কে এমন বিদ্যমান resource-এর সঙ্গে যুক্ত করে, যা cloud-এ নেই <Cite n={2} />। সবচেয়ে প্রচলিত hybrid পদ্ধতিতে cloud যুক্ত হয় বিদ্যমান on-premises infrastructure-এর সঙ্গে <Cite n={2} />।

**কেন দলগুলো এটা ব্যবহার করে।** AWS চারটা সুবিধার নাম বলে <Cite n={1} />:

- **Agility।** আপনার দরকারি resource আপনি দ্রুত চালু করতে পারেন <Cite n={1} />।
- **Elasticity।** আপনার যতটা capacity দরকার, ততটাই পান, কম হোক বা বেশি। প্রয়োজন মতো scale up আর scale down করা যায়, মাত্র কয়েক minute-এর নোটিশে <Cite n={4} />।
- **Cost savings।** স্থির খরচ (যেমন data center আর physical server) বদলে পরিবর্তনশীল খরচ নেওয়া যায়। আপনি IT-র জন্য শুধু যতটা ব্যবহার করেন, ততটার দাম দেন <Cite n={1} />।
- **Deploy globally in minutes।** আপনি নতুন geographic region-এ ছড়িয়ে পড়তে আর কয়েক minute-এ সারা বিশ্বে deploy করতে পারেন <Cite n={1} />।

**Region আর Availability Zone।** AWS-এ Region নামে একটা ধারণা আছে। Region হলো পৃথিবীর একটা physical জায়গা, যেখানে AWS তার data center জড়ো করে <Cite n={5} />। logical data center-এর প্রতিটা দলকে বলে Availability Zone (AZ) <Cite n={5} />। প্রতিটা AWS Region-এ অন্তত তিনটা AZ থাকে। সেগুলো একটা geographic এলাকার মধ্যে আলাদা ও physically পৃথক <Cite n={5} />। একটা AZ হলো একটা Region-এর এক বা একাধিক আলাদা data center, যাতে redundant power, networking আর connectivity আছে <Cite n={5} />। AZ থাকলে customer এমন production application ও database চালাতে পারে, যা একটামাত্র data center থেকে সম্ভব হতো না, এত বেশি highly available, fault tolerant আর scalable <Cite n={5} />।

**ভাগ করা দায়িত্ব।** cloud-এ workload তৈরি ও চালানো AWS আর আপনার মধ্যে ভাগ করা দায়িত্ব <Cite n={6} />। AWS host operating system আর virtualization layer থেকে শুরু করে service যে facility-তে চলে তার physical নিরাপত্তা পর্যন্ত সব অংশ চালায়, পরিচালনা করে ও নিয়ন্ত্রণ করে <Cite n={6} />। guest operating system (update আর security patch-সহ), অন্য সংশ্লিষ্ট application software, আর আপনার ব্যবহার করা AWS-এর দেওয়া resource-এর configuration-এর দায়িত্ব আপনার <Cite n={6} />। এই ভাগকে সাধারণত বলা হয় responsibility of the cloud versus in the cloud <Cite n={6} />।

**twelve-factor app।** twelve-factor app হলো software-as-a-service app বানানোর একটা পদ্ধতি <Cite n={15} />। এমন app:

- setup automate করতে declarative format ব্যবহার করে, যাতে প্রজেক্টে নতুন developer-দের জন্য সময় ও খরচ কম লাগে <Cite n={15} />;
- underlying operating system-এর সঙ্গে একটা পরিষ্কার contract রাখে, তাই এক execution environment থেকে আরেকটায় সহজে নেওয়া যায় <Cite n={15} />;
- আধুনিক cloud platform-এ deploy করার উপযোগী, তাই server আর systems administration লাগে না <Cite n={15} />;
- development আর production-কে আলাদা হয়ে যেতে দেয় না, যাতে continuous deployment সম্ভব হয় <Cite n={15} />;
- এবং tooling, architecture বা development practice-এ বড় বদল ছাড়াই scale up করতে পারে <Cite n={15} />।

এই পদ্ধতি যেকোনো programming language-এ লেখা app-এর জন্য, আর backing service-এর যেকোনো সমন্বয়ের সঙ্গে ব্যবহার করা যায় <Cite n={15} />।

**Well-Architected-এর pillar।** AWS Well-Architected Framework ছয়টা pillar-এর নাম বলে: operational excellence, security, reliability, performance efficiency, cost optimization আর sustainability <Cite n={8} />। reliability pillar-এর কাজ হলো একটা workload যেন তার উদ্দিষ্ট কাজ সঠিকভাবে ও ধারাবাহিকভাবে করে, আর ব্যর্থতা থেকে ন্যূনতম প্রভাবে সেরে ওঠে <Cite n={8} />। প্রতিটা pillar capability-তে ভাগ করা। capability হলো সম্পর্কিত best practice-এর একটা দল, যাদের একটা অভিন্ন লক্ষ্য আছে <Cite n={8} />।

## How it works

<Voices>
<Technical>

**How the pieces sit.** The diagram is the tutorial's own sketch, not an AWS drawing:

```text
AWS Cloud
└── Region                    a physical location
    ├── Availability Zone A   one or more discrete data centers
    ├── Availability Zone B   (each AZ has its own power, cooling,
```

<Voices>
<Technical>

- **Test environments on demand.** AWS lists software development and testing among the uses of the cloud <Cite n={1} />. In a cloud computing environment, new IT resources are only a click away. That reduces the time to make resources available to developers from weeks to just minutes <Cite n={4} />.
- **One build, many environments.** The codebase is the same across all deploys, although different versions may be active in each deploy <Cite n={16} />. A release is a build combined with the config of a deploy, and every release should always have a unique release ID <Cite n={20} />. A release cannot be mutated once it is created <Cite n={20} />.
- **Config instead of code changes.** Config includes resource handles to the database and other backing services, and per-deploy values such as the canonical hostname <Cite n={18} />. A deploy should be able to swap a local MySQL database for one managed by a third party, such as Amazon RDS, without any changes to the app's code <Cite n={19} />. Only the resource handle in the config needs to change <Cite n={19} />.
- **Parity makes a test result mean something.** Differences between backing services mean that tiny incompatibilities crop up, causing code that worked and passed tests in development or staging to fail in production <Cite n={25} />. All deploys should use the same type and version of each backing service <Cite n={25} />. AWS's guidance on scalability and performance tests asks for a test environment that closely mirrors production, so that results predict real behavior <Cite n={10} />.
- **Load tests with a pass or fail.** Start from service-level objectives (SLOs) <Cite n={10} />. An SLO states a target for a measurable output such as throughput, a latency percentile, or an error rate <Cite n={10} />. SLOs give every load test a clear pass or fail outcome <Cite n={10} />. Load tests run as part of the delivery pipeline catch performance regressions before release <Cite n={10} />.
- **Test failure, not only function.** A workload designed for resilience is not the same as a workload proven to be resilient <Cite n={9} />. Testing closes the gap between the resilience that you designed and the resilience that you actually have <Cite n={9} />. ## Common mistakes

<Voices>
<Technical>

- **Config in the code.** Apps sometimes store config as constants in the code, and that is a violation of twelve-factor <Cite n={18} />. A litmus test is whether the codebase could be made open source at any moment without compromising any credentials <Cite n={18} />. Store config in environment variables instead <Cite n={18} />.
- **Config grouped as named environments.** Grouping config by environment name does not scale cleanly <Cite n={18} />. New names such as staging or qa are needed as deploys are created, and the result is a combinatorial explosion of config <Cite n={18} />. In a twelve-factor app, env vars are granular controls, independently managed for each deploy <Cite n={18} />.
- **A different backing service in test.** The twelve-factor developer resists the urge to use different backing services between development and production, even when adapters theoretically abstract away any differences <Cite n={25} />. Using SQLite locally and PostgreSQL in production is the docs' example <Cite n={25} />.
- **State in the process or on disk.** Sticky sessions are a violation of twelve-factor and should never be used or relied upon <Cite n={21} />. Session state data is a good candidate for a datastore that offers time-expiration, such as Memcached or Redis <Cite n={21} />.
- **Log files written by the app.** A twelve-factor app should not attempt to write to or manage logfiles <Cite n={26} />. Each running process writes its event stream, unbuffered, to stdout instead <Cite n={26} />.
- **Leaving security to AWS.** Customers assume responsibility for the guest operating system, including updates and security patches <Cite n={6} />. For an EC2 instance, the customer is also responsible for the application software and utilities that they install, and for the configuration of the AWS-provided firewall, called a security group <Cite n={7} />.
- **A test environment that does not match production.** A common anti-pattern is to test against environments that do not match production in size or configuration <Cite n={10} />.
- **One load test, with no pass or fail.** Two anti-patterns of load testing are a one-time activity that is not part of the delivery pipeline <Cite n={10} />, and undefined performance requirements, so that tests have no pass or fail criteria <Cite n={10} />.
- **Resilience that is designed, but never tested.** Teams design for resilience but never verify how the whole workload behaves when faults occur <Cite n={11} />. Teams document recovery procedures but never exercise them <Cite n={12} />. A game day that involves only engineers tests the technology but misses the coordination, decision-making, and communication that are required in real incidents <Cite n={12} />.
- **A DDoS test from EC2.** Volumetric network-based DDoS simulations are explicitly prohibited from the Amazon EC2 platform <Cite n={14} />. Tests that purposefully attempt to overwhelm the target with flooding attacks are not network stress tests <Cite n={14} />. A customer is responsible for any damages to AWS or other AWS customers that are caused by their testing <Cite n={13} />.

<Technical>

<Callout type="tip" title="Tutorial advice">
This list is the tutorial's own advice for a tester whose app runs in the cloud.

- Ask where each environment gets its config, and who can change it.
- Ask which release each test environment runs, and write it in the test report.
- Compare the backing services of test and production: the same type, and the same version.
- Restart a process in the middle of a test, and check that nothing that matters is lost.
- Find out where the logs of each environment go, and how long they are kept.
- Ask who patches the operating system, and who owns the firewall rules, on each machine.
- Before a load or security test on AWS, read the AWS testing policies, and ask AWS for approval when a policy requires it.
- Ask for the SLOs before you design a load test, and write the pass or fail line from them.
- Ask when the team last made a failure happen on purpose, and what it learned.
- Delete the test resources when a run ends, and look at what the account is billed for.

<Callout type="tip" title="Tutorial advice">
This list is the tutorial's own advice for a tester whose app runs in the cloud.

- Ask where each environment gets its config, and who can change it.
- Ask which release each test environment runs, and write it in the test report.
- Compare the backing services of test and production. They should be the same type and the same version.
- Restart a process in the middle of a test, and check that nothing important is lost.
- Find out where the logs of each environment go, and how long they are kept.
- Ask who patches the operating system on each machine, and who owns its firewall rules.
- Before a load or security test on AWS, read the AWS testing policies. Ask AWS for approval when a policy requires it.
- Ask for the SLOs before you design a load test. Write the pass or fail line from them.
- Ask when the team last made a failure happen on purpose, and what it learned.
- Delete the test resources when a run ends, and look at what the account is billed for.
</Callout>

## Key words

| Term | Meaning |
|---|---|
| Cloud computing | The on-demand delivery of IT resources over the Internet with pay-as-you-go pricing |
| IaaS | Infrastructure as a Service: the basic building blocks for cloud IT, typically networking features, computers, and data storage space |
| PaaS | Platform as a Service: it removes the need to manage the underlying infrastructure, so that you focus on your applications |
| SaaS | Software as a Service: software applications that are run and managed by the vendor |
| Region | A physical location around the world where AWS clusters data centers |
| Availability Zone (AZ) | One or more discrete data centers with redundant power, networking, and connectivity in an AWS Region |
| Shared responsibility | Building and operating workloads in the cloud is shared between AWS and you; commonly called responsibility of the cloud versus in the cloud |
| Guest operating system | The operating system whose updates and security patches the customer is responsible for on EC2 |
| Twelve-factor app | A methodology for building software-as-a-service apps |
| Deploy | A running instance of the app |
| Config | Everything that is likely to vary between deploys; the twelve-factor app stores it in environment variables |
| Backing service | Any service the app consumes over the network as part of its normal operation |
| Build, release, run | The three stages that turn a codebase into a running deploy |
| Release | A build combined with the config of a deploy; it should always have a unique release ID and cannot be mutated once it is created |
| Stateless process | Twelve-factor processes are stateless and share-nothing; data that needs to persist goes into a stateful backing service |
| `SIGTERM` | The signal that a process manager sends; a twelve-factor process shuts down gracefully when it receives it |
| Event stream | The stream of events that each running process writes, unbuffered, to stdout |
| SLO | A service-level objective: a target for a measurable output such as throughput, a latency percentile, or an error rate |
| Chaos engineering | Injecting controlled faults into a system to verify that it withstands and recovers from real-world disruptions |
| Game day | A scheduled exercise where a team responds to a simulated failure in a production-like environment |
