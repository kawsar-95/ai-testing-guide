# CI/CD Pipelines

You write the tests. This page shows how a CI/CD pipeline runs them for the whole team. It explains continuous integration, continuous delivery, and continuous deployment, and the parts of a pipeline in GitHub Actions and Jenkins. Then you put a Playwright test suite into a pipeline, and use it as a gate, a schedule, and a record.

<PageMeta />

## What it is

<Voices>
<Technical>

**Continuous integration (CI)** is a software practice that requires frequently committing code to a shared repository <Cite n={3} />. Each commit can be built and tested, to make sure that it doesn't introduce errors <Cite n={3} />. The tests can include code linters, security checks, code coverage, functional tests, and other custom checks <Cite n={3} />.

**Continuous delivery** expands upon CI. Every code change is built, tested, and then pushed to a non-production testing or staging environment <Cite n={4} />. Done well, the team always has a deployment-ready build artifact that has passed through a standardized test process <Cite n={4} />.

**Continuous deployment** differs from continuous delivery in one thing. The difference is a manual approval to update production: with continuous deployment, production happens automatically, without explicit approval <Cite n={4} />.

| Practice | What happens to each change | Release to production |
|---|---|---|
| Continuous integration | Committed often, then built and tested <Cite n={3} /> | — |
| Continuous delivery | Also pushed to a testing or staging environment <Cite n={4} /> | After a manual approval <Cite n={4} /> |
| Continuous deployment | Also pushed to a testing or staging environment <Cite n={4} /> | Automatic, with no approval <Cite n={4} /> |

A **pipeline** is this process as automation. Jenkins describes a continuous delivery pipeline as "an automated expression of your process for getting software from version control right through to your users and customers" <Cite n={5} />. Two common tools run pipelines:

- **Jenkins** is a self-contained, open source automation server for tasks related to building, testing, and delivering or deploying software <Cite n={1} />.
- **GitHub Actions** is a continuous integration and continuous delivery (CI/CD) platform that lets you automate your build, test, and deployment pipeline <Cite n={2} />.

</Technical>

## How it works

<Voices>
<Technical>

A GitHub Actions pipeline has these parts <Cite n={2} />:

| Part | What it is |
|---|---|
| Workflow | A configurable automated process that runs one or more jobs. It is a YAML file in the `.github/workflows` directory of the repository. |
| Event | A specific activity in a repository that triggers a workflow run, such as a pushed commit or a new pull request. A workflow can also run on a schedule, through the REST API, or manually. |
| Job | A set of steps that runs on the same runner. |
| Step | A shell script or an action. Steps are executed in order and depend on each other. |
| Action | A pre-defined, reusable set of jobs or code that performs a specific task. |
| Runner | A server that runs your workflows. Each runner can run a single job at a time. |

An example with two jobs. The file name and the job names are made up:

```text
push or pull request                 (the event)
        |
        v
.github/workflows/tests.yml          (the workflow)
        |
        +--> job "unit"  on a runner:  step -> step -> step
        |
        +--> job "e2e"   on a runner:  step -> step -> step
        |
        v
the result of the tests, shown in the pull request
```

By default, jobs have no dependencies and run in parallel <Cite n={2} />. A job that depends on another job waits for that job to complete <Cite n={2} />. A **matrix** runs the same job several times, each with a different combination of variables, like operating systems or language versions <Cite n={2} />.

GitHub provides Ubuntu Linux, Microsoft Windows, and macOS runners, and each workflow run executes in a fresh, newly-provisioned virtual machine <Cite n={2} />. GitHub runs your CI tests and shows the results of each test in the pull request <Cite n={3} />. When all CI tests in a workflow pass, the change is ready to be reviewed or merged <Cite n={3} />.

**Jenkins** uses other names for the same ideas. A Jenkins Pipeline is written in a text file called a `Jenkinsfile`, which can be committed to the project's source control repository <Cite n={5} />. A **stage** is a distinct subset of tasks, such as "Build", "Test", and "Deploy" <Cite n={5} />. A **step** is a single task, such as `sh 'make'` to run a shell command <Cite n={5} />. A **node** is a machine of the Jenkins environment that can execute a Pipeline <Cite n={5} />. This is a basic three-stage pipeline in the Declarative syntax <Cite n={6} />:

```groovy
pipeline {
    agent any
    stages {
        stage('Build') {
            steps {
                echo 'Building..'
            }
        }
        stage('Test') {
            steps {
                echo 'Testing..'
            }
        }
        stage('Deploy') {
            steps {
                echo 'Deploying....'
            }
        }
    }
}
```

## Try it

<Voices>
<Technical>

This walk-through puts a Playwright test suite into GitHub Actions. It follows the Playwright guide <Cite n={7} />.

<Callout type="note" title="Cost">
Standard GitHub-hosted runners in public repositories are free <Cite n={10} />. In a private repository, runner time draws from the monthly included compute usage of your plan <Cite n={10} />.
</Callout>

**1. Create the project.** Run the command below. When it offers to add a GitHub Actions workflow, say yes. It creates `.github/workflows/playwright.yml`, which runs your tests on each push and pull request into the `main` or `master` branch <Cite n={7} />.

```bash
npm init playwright@latest
```

**2. Read the workflow.** This is the file that it creates <Cite n={7} />:

```yaml
name: Playwright Tests
on:
  push:
    branches: [ main, master ]
  pull_request:
    branches: [ main, master ]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
    - uses: actions/checkout@v6
    - uses: actions/setup-node@v6
      with:
        node-version: lts/*
    - name: Install dependencies
      run: npm ci
    - name: Install Playwright Browsers
      run: npx playwright install --with-deps
    - name: Run Playwright tests
      run: npx playwright test
    - uses: actions/upload-artifact@v5
      if: ${{ !cancelled() }}
      with:
        name: playwright-report
        path: playwright-report/
        retention-days: 30
```

- The steps clone your repository, install Node.js, install the npm dependencies, install the Playwright browsers, run the tests, and upload the HTML report <Cite n={7} />.
- `runs-on` defines the type of machine that runs the job, by a workflow label such as `ubuntu-latest` <Cite n={13} />.
- `npm ci` is the install command for automated environments such as test platforms and continuous integration <Cite n={9} />. It never writes to `package.json` or the lock file <Cite n={9} />.
- `if: ${{ !cancelled() }}` keeps the report of a failed run. A step with no status function gets the default check `success()`, which returns true when all previous steps have succeeded <Cite n={8} />. `cancelled()` is true if the workflow was canceled <Cite n={8} />. So the upload runs after failed tests too.

**3. Push it.** Create a repository on GitHub and push your code to it. First initialize a Git repository with `git init`, so that you can add, commit, and push <Cite n={7} />. The commands are on the [Git Basics](/devops/git-basics/) page.

**4. Watch the run.** Open the **Actions** tab to see whether your tests passed or failed <Cite n={7} />. Click the run, then **Run Playwright tests**, to see the error messages, what was expected and what was received, and the call log <Cite n={7} />.

**5. Open the report.** In the **Artifacts** section, click `playwright-report` to download the report as a zip file <Cite n={7} />. Extract it, then serve it with this command, because opening the file directly does not work as expected <Cite n={7} />:

```bash
npx playwright show-report name-of-my-extracted-playwright-report
```

- `if: ${{ !cancelled() }}` keeps the report when tests fail. A step with no status function gets the default check `success()`. It is true when all earlier steps passed <Cite n={8} />. `cancelled()` is true when the run was canceled <Cite n={8} />. So the report uploads after failed tests too.

**3. Push it.** Make a repository on GitHub and push your code. First run `git init`, so that you can add, commit, and push <Cite n={7} />. The [Git Basics](/devops/git-basics/) page shows the commands.

**4. Watch the run.** Open the **Actions** tab. It shows if your tests passed or failed <Cite n={7} />. Click the run, then **Run Playwright tests**. You see the error messages, the expected and the received values, and the call log <Cite n={7} />.

**5. Open the report.** Under **Artifacts**, click `playwright-report`. It downloads as a zip file <Cite n={7} />. Unzip it and open it with this command. Opening the file directly does not work well <Cite n={7} />:

```bash
npx playwright show-report name-of-my-extracted-playwright-report
```

</Layman>
<Bangla>

এখানে আপনি একটা Playwright test suite-কে GitHub Actions-এ বসাবেন। ধাপগুলো Playwright-এর guide অনুসরণ করে <Cite n={7} />।

<Callout type="note" title="খরচ">
public repository-তে standard GitHub-hosted runner বিনামূল্যে <Cite n={10} />। private repository-তে runner-এর সময় আপনার plan-এর মাসিক included compute usage থেকে কাটা যায় <Cite n={10} />।
</Callout>

**১. project বানান।** নিচের command চালান। এটা GitHub Actions workflow যোগ করতে চাইলে yes দিন। এটা `.github/workflows/playwright.yml` বানায়, যেটা `main` বা `master` branch-এ প্রতিটা push আর pull request-এ আপনার test চালায় <Cite n={7} />।

```bash
npm init playwright@latest
```

**২. workflow পড়ুন।** এটাই সেই ফাইল <Cite n={7} />:

```yaml
name: Playwright Tests
on:
  push:
    branches: [ main, master ]
  pull_request:
    branches: [ main, master ]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
    - uses: actions/checkout@v6
    - uses: actions/setup-node@v6
      with:
        node-version: lts/*
    - name: Install dependencies
      run: npm ci
    - name: Install Playwright Browsers
      run: npx playwright install --with-deps
    - name: Run Playwright tests
      run: npx playwright test
    - uses: actions/upload-artifact@v5
      if: ${{ !cancelled() }}
      with:
        name: playwright-report
        path: playwright-report/
        retention-days: 30
```

- step-গুলো আপনার repository clone করে, Node.js install করে, npm dependency install করে, Playwright browser install করে, test চালায়, আর HTML report upload করে <Cite n={7} />।
- `runs-on` ঠিক করে কোন ধরনের machine job চালাবে, `ubuntu-latest`-এর মতো একটা workflow label দিয়ে <Cite n={13} />।
- `npm ci` হলো test platform আর continuous integration-এর মতো automated environment-এর install command <Cite n={9} />। এটা কখনো `package.json` বা lock ফাইলে লেখে না <Cite n={9} />।
- `if: ${{ !cancelled() }}` ফেল হওয়া run-এর report রেখে দেয়। কোনো status function না থাকলে step-এ default check `success()` বসে, যেটা true হয় যখন আগের সব step সফল হয়েছে <Cite n={8} />। workflow cancel হলে `cancelled()` true হয় <Cite n={8} />। তাই test ফেল করলেও report upload হয়।

**৩. push করুন।** GitHub-এ একটা repository বানিয়ে আপনার code push করুন। আগে `git init` দিয়ে একটা Git repository শুরু করুন, যাতে add, commit আর push করা যায় <Cite n={7} />। command-গুলো [Git Basics](/devops/git-basics/) পেজে আছে।

**৪. run দেখুন।** **Actions** tab খুলুন: test পাস করল না ফেল করল, সেখানে দেখা যায় <Cite n={7} />। run-এ ক্লিক করুন, তারপর **Run Playwright tests**-এ। সেখানে error message, কী আশা করা হয়েছিল আর কী পাওয়া গেছে, আর call log দেখা যায় <Cite n={7} />।

**৫. report খুলুন।** **Artifacts** অংশে `playwright-report`-এ ক্লিক করলে report একটা zip ফাইল হিসেবে download হয় <Cite n={7} />। unzip করে এই command দিয়ে খুলুন, কারণ ফাইলটা সরাসরি খুললে ঠিকমতো কাজ করে না <Cite n={7} />:

```bash
npx playwright show-report name-of-my-extracted-playwright-report
```

## How a tester uses it

<Voices>
<Technical>

A pipeline turns a test suite into a gate, a schedule, and a record.

**A merge gate.** A branch protection rule can require status checks. Then all required status checks must pass before collaborators can merge changes into the protected branch <Cite n={11} />. Make your test job one of them, and a red test blocks the merge.

**A schedule.** A slow suite, such as a full regression run, can run on a timer with the `schedule` event <Cite n={12} />. It uses POSIX cron syntax: five fields for the minute, hour, day of the month, month, and day of the week <Cite n={12} />. By default, scheduled workflows run in UTC, on the latest commit on the default branch, and the shortest interval is once every 5 minutes <Cite n={12} />. This example runs at 5:30 AM in the America/New_York timezone, Monday through Friday. Without the `timezone` line, it would run at 5:30 UTC <Cite n={12} />:

```yaml
on:
  schedule:
    - cron: '30 5 * * 1-5'
      timezone: "America/New_York"
```

**More environments.** A matrix runs the same test job on several operating systems or language versions <Cite n={2} />.

**A record.** The output of building and testing often produces files that you can use to debug test failures <Cite n={14} />. You can use the `upload-artifact` action to upload them, and `retention-days` sets how long one artifact is kept, within the limit of the repository, organization, or enterprise <Cite n={14} />. In Jenkins, the `junit` step records JUnit XML test reports <Cite n={6} />. Based on the recorded reports, Jenkins can show historical trends <Cite n={6} />. In the handbook's example that runs `sh 'make check || true'`, failed tests mark the Pipeline "unstable", shown as a yellow ball in the web UI <Cite n={6} />. A Declarative Pipeline can also record the reports in a `post` section with the condition `always` <Cite n={6} />:

```groovy
pipeline {
    agent any
    stages {
        stage('Test') {
            steps {
                sh 'make check'
            }
        }
    }
    post {
        always {
            junit '**/target/*.xml'
        }
    }
}
```

**A release gate.** Continuous delivery has a manual approval before production <Cite n={4} />. In GitHub Actions, an environment can require approval before a job proceeds <Cite n={17} />. Before a release, a continuous delivery pipeline can run more than unit tests: UI testing, load testing, integration testing, and API reliability testing <Cite n={4} />.

Go deeper on this site: [Browser Testing with Playwright](/automate/playwright/), [k6 in CI](/k6/k6-in-ci/), and [GitHub Actions](/automate/github-actions/) for Claude Code in a workflow.

## Common mistakes

<Voices>
<Technical>

- **The report uploads only when tests pass.** A step with no status function gets the default check `success()`, which returns true when all previous steps have succeeded <Cite n={8} />. Fix: give the upload step `if: ${{ !cancelled() }}`, as the Playwright workflow does <Cite n={7} />.
- **`npm install` in the pipeline.** `npm ci` is meant for automated environments such as continuous integration <Cite n={9} />. If the dependencies in the lock file do not match `package.json`, `npm ci` exits with an error instead of updating the lock file <Cite n={9} />. The run then fails on the real problem.
- **No time limit.** By default, a job can run 360 minutes before GitHub cancels it <Cite n={13} />. Set `timeout-minutes` on the job <Cite n={13} />. For Playwright, the guide sets `globalTimeout` in the config instead, so that the reporters still produce a report <Cite n={7} />.
- **A password in the YAML file.** Store it as a secret of the organization, repository, or environment <Cite n={15} />. A workflow can read a secret only if it names it, and GitHub redacts secrets that are printed to the logs, but the redaction is not guaranteed <Cite n={15} />.
- **A third-party action pinned to a tag.** A tag can be moved or deleted if a bad actor gains access to the repository of the action <Cite n={16} />. Pin it to a full-length commit SHA <Cite n={16} />.
- **A scheduled run that should test a branch.** Scheduled workflows run on the latest commit on the default branch <Cite n={12} />.
- **A job that never runs.** If a job fails or is skipped, every job that `needs` it is skipped, unless a condition lets it continue <Cite n={13} />.

</Technical>

- সাম্প্রতিক তিনটা pull request খুলুন। দেখুন প্রতিটায় test চলেছে কি না, আর একটা ফেল হওয়া test merge আটকেছে কি না।
- একটা branch-এ ইচ্ছা করে একটা test ভাঙুন। দেখুন run লাল হয় কি না, আর দুই-তিন ক্লিকে ফেল হওয়া test, তার log আর report-এ পৌঁছানো যায় কি না।
- জিজ্ঞেস করুন কোন suite শুধু schedule-এ চলে, আর পরদিন সকালে তার ফল কে পড়ে।
- জিজ্ঞেস করুন flaky test নিয়ে টিম কী করে: একটা ticket খোলে, নাকি পাস না হওয়া পর্যন্ত আবার চালায়।
- দেখুন প্রতিটা test job-এর সময়ের সীমা আছে কি না, আর test ফেল করলে report upload হয় কি না।
- workflow ফাইলে password, token আর key-সহ URL খুঁজুন।
- matrix-এর version-গুলো আপনার user-রা যে version চালান, তার সাথে মিলিয়ে দেখুন।

## Key words

| Term | Meaning |
|---|---|
| Continuous integration (CI) | Committing code often to a shared repository, and building and testing each commit |
| Continuous delivery | Every change is built, tested, and pushed to a testing or staging environment; a person approves production |
| Continuous deployment | The same, but production updates happen automatically, with no approval |
| Pipeline | The automated path of a change from version control to the users |
| Workflow | A GitHub Actions YAML file in `.github/workflows` that runs one or more jobs |
| Event | The activity that starts a workflow, such as a push, a pull request, or a schedule |
| Job | A set of steps that runs on the same runner |
| Step | One shell script or one action |
| Action | A reusable building block that performs a task in a workflow |
| Runner | The server that runs a job |
| Matrix | One job run several times, with a different combination of variables each time |
| Artifact | A file that a run keeps, such as a test report |
| Required status check | A check that must pass before a merge into a protected branch |
| Jenkinsfile | The text file that defines a Jenkins Pipeline |
| Stage | A named subset of tasks in a Jenkins Pipeline, such as Build, Test, or Deploy |
