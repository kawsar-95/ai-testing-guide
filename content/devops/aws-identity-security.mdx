# AWS Identity and Security

This page is about who may use AWS resources and how keys and secrets are kept. It covers IAM identities, credentials, and policies, then AWS KMS and AWS Secrets Manager. The practice run models two ideas on your own machine and needs no AWS account. It comes after [AWS Networking and Delivery](/devops/aws-networking/) and before [AWS Databases and Serverless](/devops/aws-data-serverless/).

## What it is

<Voices>
<Technical>

**AWS IAM.** AWS Identity and Access Management (IAM) is a web service that helps you securely control access to AWS resources <Cite n={1} />. You use IAM to control who is authenticated (signed in) and authorized (has permissions) to use resources <Cite n={1} />. There is no charge to use IAM <Cite n={2} />.

**Identities.** When you create an AWS account, you begin with one sign-in identity called the AWS account root user that has complete access to all AWS services and resources <Cite n={1} />. An IAM role is an IAM identity that you can create in your account that has specific permissions <Cite n={4} />. A role is intended to be assumable by anyone who needs it <Cite n={4} />. A role does not have standard long-term credentials such as a password or access keys associated with it <Cite n={4} />. When you assume a role, it provides you with temporary security credentials for your role session <Cite n={4} />.

**Policies.** A policy is an object in AWS that, when associated with an identity or resource, defines their permissions <Cite n={9} />. AWS evaluates these policies when an IAM principal (user or role) makes a request <Cite n={9} />. Permissions in the policies determine whether the request is allowed or denied <Cite n={9} />.

**AWS KMS.** AWS Key Management Service (AWS KMS) is an AWS managed service that makes it easy for you to create and control the keys used to encrypt and sign your data <Cite n={17} />. KMS keys are created, managed, used, and deleted entirely within AWS KMS <Cite n={17} />. They never leave the service unencrypted <Cite n={17} />.

**AWS Secrets Manager.** AWS Secrets Manager helps you manage, retrieve, and rotate database credentials, application credentials, OAuth tokens, API keys, and other secrets throughout their lifecycles <Cite n={24} />. You replace hard-coded credentials with a runtime call to the Secrets Manager service to retrieve credentials dynamically when you need them <Cite n={24} />. For AWS credentials, AWS recommends AWS Identity and Access Management <Cite n={24} />. For encryption keys, it recommends AWS Key Management Service <Cite n={24} />.

## How it works

<Voices>
<Technical>

**Sign-in, the root user, and MFA.** Authentication is provided by matching the sign-in credentials to a principal trusted by the AWS account <Cite n={1} />. AWS strongly recommends that you don't use the root user for everyday tasks <Cite n={1} />. Use the root user only to perform the tasks that require root-level permissions <Cite n={7} />. You cannot attach identity-based policies to the root user <Cite n={9} />. MFA is enforced for root users by default <Cite n={7} />. Adding it requires customer action during the initial account creation or as prompted during sign-in <Cite n={7} />.

MFA requires users to provide unique authentication from an AWS supported MFA mechanism in addition to their sign-in credentials <Cite n={8} />. Your AWS account root user and IAM users can register up to eight MFA devices of any type <Cite n={8} />. You only need one MFA device to sign in to the AWS Management Console or create a session through the AWS CLI <Cite n={8} />. AWS recommends phishing-resistant MFA such as passkeys and security keys whenever possible <Cite n={8} />.

**Access keys and temporary credentials.** Access keys are long-term credentials for an IAM user or the AWS account root user <Cite n={6} />. You must use both the access key ID and secret access key together to authenticate your requests <Cite n={6} />. The secret access key can be retrieved only at the time you create it <Cite n={6} />. You can have a maximum of two access keys per user <Cite n={6} />. As a best practice, use temporary security credentials (such as IAM roles) instead of creating long-term credentials like access keys <Cite n={6} />.

Access keys or credential information stored in the shared AWS credentials file are stored in plaintext <Cite n={6} />. Do NOT put access keys or credential information in your application files <Cite n={6} />. Do NOT include files that contain access keys or credential information in your project area <Cite n={6} />.

You can use AWS STS to create and provide trusted users with temporary security credentials <Cite n={5} />. Temporary security credentials are short-term, as the name implies <Cite n={5} />. They can be configured to last for anywhere from a few minutes to several hours <Cite n={5} />. After the credentials expire, AWS no longer recognizes them <Cite n={5} />. They are not stored with the user but are generated dynamically when requested <Cite n={5} />.

**Roles for workloads.** When you're building on an AWS compute service, such as Amazon EC2 or Lambda, AWS delivers the temporary credentials of an IAM role to that compute resource <Cite n={3} />. Applications written using an AWS SDK will discover and use these temporary credentials <Cite n={3} />. When you launch an Amazon EC2 instance, you specify an IAM role to associate with the instance <Cite n={16} />. Applications that run on the instance can then use the role-supplied temporary credentials to sign API requests <Cite n={16} />. Only one role can be assigned to an Amazon EC2 instance at a time <Cite n={16} />. All applications on the instance share the same role and permissions <Cite n={16} />.

IAM, like many other AWS services, is eventually consistent <Cite n={1} />. AWS recommends that you do not include IAM changes in the critical, high-availability code paths of your application <Cite n={1} />. Be sure to verify that the changes have been propagated before production workflows depend on them <Cite n={1} />.

**Policy types.** Identity-based policies are JSON permissions policy documents that control what actions an identity can perform, on which resources, and under what conditions <Cite n={9} />. You attach managed and inline policies to IAM identities <Cite n={9} />. Managed policies are standalone identity-based policies that you can attach to multiple users, groups, and roles <Cite n={9} />. Inline policies are policies that you add directly to a single user, group, or role <Cite n={9} />. They are deleted when you delete the identity <Cite n={9} />.

Resource-based policies are JSON policy documents that you attach to a resource such as an Amazon S3 bucket <Cite n={9} />. They grant the specified principal permission to perform specific actions on that resource <Cite n={9} />. Resource-based policies are inline policies <Cite n={9} />. There are no managed resource-based policies <Cite n={9} />. Trust policies define which principal entities can assume the role <Cite n={9} />.

A permissions boundary sets the maximum permissions that an identity-based policy can grant to an IAM entity <Cite n={9} />. With a boundary, the entity can perform only the actions that both its identity-based policies and its boundary allow <Cite n={9} />.

**Policy statements.** Each statement includes information about a single permission <Cite n={9} />. If a policy includes multiple statements, AWS applies a logical OR across the statements <Cite n={9} />. If multiple policies apply to a request, AWS applies a logical OR across all of those policies <Cite n={9} />. These are the main elements:

- `Effect`: use `Allow` or `Deny` to indicate whether the policy allows or denies access <Cite n={9} />.
- `Action`: a list of actions that the policy allows or denies <Cite n={9} />.
- `Resource`: an IAM permissions policy must specify a list of resources to which the actions apply <Cite n={9} />.
- `Principal`: in a resource-based policy, you must indicate the account, user, role, or AWS STS federated user principal <Cite n={9} />. In an identity-based policy, you cannot include this element <Cite n={9} />.
- `Condition`: it specifies the circumstances under which the policy grants permission <Cite n={9} />.

Policies are expressed in JSON <Cite n={10} />. Action names can include wildcards <Cite n={10} />. AWS recommends the latest `2012-10-17` version of the policy language <Cite n={9} />. If you try to define multiple permissions in a single statement, your policy might not grant the access that you expect <Cite n={9} />.

**How AWS decides.** By default, all requests are implicitly denied, except for the AWS account root user, which has full access <Cite n={12} />. A request must be explicitly allowed by a policy or set of policies to be allowed <Cite n={12} />. An explicit deny overrides an explicit allow <Cite n={12} />.

AWS looks in all applicable policies for a `Deny` statement that applies to the request <Cite n={12} />. This is called an explicit deny <Cite n={12} />. If it finds even one explicit deny that applies, the final decision is Deny <Cite n={12} />. If there is no explicit deny, the evaluation continues <Cite n={12} />.

Within one account, the identity-based and the resource-based policies both count. AWS evaluates all the permissions granted by the policies for at least one `Allow` <Cite n={11} />. If one of the two allows the request and the other doesn't, the request is still allowed <Cite n={11} />. For most resources, you only need an explicit `Allow` in one of them <Cite n={12} />. IAM role trust policies and KMS key policies are exceptions <Cite n={12} />. If a permissions boundary does not allow the requested action, the request is implicitly denied <Cite n={12} />.

**A worked example.** The page for a single account shows a user named Carlos and two policies <Cite n={11} />. The `DenyS3Logs` statement denies Carlos access to any S3 bucket with `log` in its name <Cite n={11} />. When Carlos saves a file in the logs bucket, AWS first checks for a `Deny` statement that applies to the request <Cite n={11} />. It finds one <Cite n={11} />. Carlos is denied access <Cite n={11} />. When he saves the file in his own bucket, AWS checks for a `Deny` statement and does not find one <Cite n={11} />. Both the identity-based policy and the resource-based policy allow the request <Cite n={11} />. Therefore, AWS allows the request <Cite n={11} />. If either of them explicitly denied the request, it would have been denied <Cite n={11} />.

**Least privilege and checks.** When you set permissions with IAM policies, grant only the permissions required to perform a task <Cite n={3} />. As your use case matures, you can work to reduce the permissions that you grant to work toward least privilege <Cite n={3} />. AWS managed policies might not grant least-privilege permissions for your specific use cases <Cite n={3} />. IAM provides last accessed information to help you identify what you no longer need <Cite n={3} />. You can specify conditions under which a policy statement is in effect <Cite n={3} />.

IAM Access Analyzer external access analyzers help identify resources that are shared with an external entity <Cite n={15} />. It generates IAM policies based on access activity in your AWS CloudTrail logs <Cite n={15} />. AWS automatically examines the policies that you create or edit in the console to ensure that they comply with the IAM policy grammar <Cite n={14} />. It also verifies that your ARNs are formatted properly and action names and condition keys are correct <Cite n={14} />.

**The policy simulator.** With the IAM policy simulator, you can test identity-based policies, IAM permissions boundaries, service control policies (SCPs), and resource-based policies that you provide <Cite n={13} />. You simulate how AWS would evaluate a request, without sending a real request to any AWS service <Cite n={13} />. Each simulation returns a binary authorization outcome for every action and resource you test <Cite n={13} />. In Custom mode, you test one or more policies that you write or paste in <Cite n={13} />. They are simulated on their own and are not saved to your account <Cite n={13} />. The simulator results can differ from your live AWS environment <Cite n={13} />. AWS recommends that you check your policies against your live environment after testing <Cite n={13} />.

**KMS keys and data keys.** When you encrypt data, you need to protect your encryption key <Cite n={17} />. If you encrypt your key, you need to protect its encryption key <Cite n={17} />. Eventually, you must protect the highest level encryption key, known as a root key <Cite n={17} />. Envelope encryption is the practice of encrypting plaintext data with a data key, and then encrypting the data key under another key <Cite n={19} />. Eventually, one key must remain in plaintext so you can decrypt the keys and your data <Cite n={19} />. This top-level plaintext key encryption key is known as the root key <Cite n={19} />. To use a KMS key, you must call AWS KMS <Cite n={19} />.

Data keys are symmetric keys you can use to encrypt data <Cite n={20} />. Data keys are returned to you for use outside of AWS KMS <Cite n={20} />. AWS KMS returns a plaintext data key for immediate use (optional) and an encrypted copy of the data key <Cite n={20} />. When you are ready to decrypt the data, you first ask AWS KMS to decrypt the encrypted data key <Cite n={20} />. AWS KMS does not store, manage, or track your data keys <Cite n={20} />. To create a data key, call the `GenerateDataKey` operation <Cite n={20} />. You can re-encrypt only the data keys instead of re-encrypting the raw data <Cite n={19} />.

**KMS key types, rotation, and deletion.** The KMS keys that you create are customer managed keys <Cite n={18} />. IAM, অন্য অনেক AWS service-এর মতোই, eventually consistent <Cite n={1} />। AWS সুপারিশ করে, আপনার application-এর জরুরি, high-availability code path-এ IAM-এর এমন পরিবর্তন রাখবেন না <Cite n={1} />। production workflow এই পরিবর্তনের ওপর নির্ভর করার আগে নিশ্চিত হয়ে নিন যে পরিবর্তনগুলো ছড়িয়ে গেছে <Cite n={1} />।

**Policy-র ধরন।** Identity-based policy হলো JSON permissions policy document, যা ঠিক করে একটা identity কোন action করতে পারবে, কোন resource-এ আর কোন শর্তে <Cite n={9} />। আপনি managed আর inline policy IAM identity-তে attach করেন <Cite n={9} />। Managed policy হলো আলাদা (standalone) identity-based policy, যা আপনি একাধিক user, group আর role-এ attach করতে পারেন <Cite n={9} />। Inline policy হলো এমন policy, যা আপনি সরাসরি একটা user, group বা role-এ যোগ করেন <Cite n={9} />। identity মুছলে সেগুলোও মুছে যায় <Cite n={9} />।

Resource-based policy হলো JSON policy document, যা আপনি Amazon S3 bucket-এর মতো একটা resource-এ attach করেন <Cite n={9} />। সেগুলো নির্দিষ্ট করা principal-কে ওই resource-এ নির্দিষ্ট action করার permission দেয় <Cite n={9} />। Resource-based policy হলো inline policy <Cite n={9} />। managed resource-based policy নেই <Cite n={9} />। Trust policy ঠিক করে কোন principal entity role-টা assume করতে পারবে <Cite n={9} />।

Permissions boundary একটা IAM entity-কে identity-based policy সর্বোচ্চ কোন permission দিতে পারে, তা ঠিক করে <Cite n={9} />। boundary থাকলে entity শুধু সেই action করতে পারে, যা তার identity-based policy আর boundary দুটোই অনুমতি দেয় <Cite n={9} />।

**Policy statement।** প্রতিটা statement একটা মাত্র permission-এর তথ্য রাখে <Cite n={9} />। একটা policy-তে একাধিক statement থাকলে AWS evaluate করার সময় statement-গুলোর ওপর logical OR প্রয়োগ করে <Cite n={9} />। একটা request-এ একাধিক policy প্রযোজ্য হলে AWS সেই সব policy-র ওপর logical OR প্রয়োগ করে <Cite n={9} />। প্রধান element-গুলো:

- `Effect`: policy অনুমতি দেয় না আটকায়, তা বোঝাতে `Allow` বা `Deny` ব্যবহার করুন <Cite n={9} />।
- `Action`: policy যে action-গুলোর অনুমতি দেয় বা আটকায়, তার তালিকা <Cite n={9} />।
- `Resource`: একটা IAM permissions policy-তে এমন resource-এর তালিকা দিতে হয়, যেগুলোর ওপর action প্রযোজ্য <Cite n={9} />।
- `Principal`: একটা resource-based policy-তে account, user, role বা AWS STS federated user principal ঠিক করে দিতে হয় <Cite n={9} />। identity-based policy-তে এই element রাখা যায় না <Cite n={9} />।
- `Condition`: এটা ঠিক করে policy কোন পরিস্থিতিতে permission দেয় <Cite n={9} />।

Policy JSON-এ লেখা হয় <Cite n={10} />। Action-এর নামে wildcard থাকতে পারে <Cite n={10} />। AWS policy language-এর সর্বশেষ `2012-10-17` version ব্যবহারের সুপারিশ করে <Cite n={9} />। একটা statement-এ একাধিক permission ঠিক করতে গেলে আপনার policy আপনার প্রত্যাশিত access নাও দিতে পারে <Cite n={9} />।

**AWS কীভাবে সিদ্ধান্ত নেয়।** By default সব request implicitly denied হয়, শুধু AWS account root user বাদে, যার পূর্ণ প্রবেশাধিকার আছে <Cite n={12} />। একটা request অনুমতি পেতে হলে কোনো policy বা policy-র সেট তাকে স্পষ্টভাবে অনুমতি দিতে হয় <Cite n={12} />। explicit deny explicit allow-কে বাতিল করে দেয় <Cite n={12} />।

AWS সব প্রযোজ্য policy-তে খোঁজে, এমন একটা `Deny` statement আছে কি না যা request-টার ওপর প্রযোজ্য <Cite n={12} />। একে বলা হয় explicit deny <Cite n={12} />। প্রযোজ্য একটা explicit deny পেলেও চূড়ান্ত সিদ্ধান্ত হয় Deny <Cite n={12} />। কোনো explicit deny না থাকলে evaluation এগিয়ে চলে <Cite n={12} />।

একটা account-এর ভেতরে identity-based আর resource-based policy দুটোই গণনায় আসে। AWS policy-গুলোর দেওয়া সব permission দেখে, অন্তত একটা `Allow`-এর জন্য <Cite n={11} />। দুটোর একটা request-টা অনুমতি দিলে আর অন্যটা না দিলেও request অনুমতি পায় <Cite n={11} />। বেশির ভাগ resource-এর জন্য এর যেকোনো একটাতে একটা explicit `Allow`-ই যথেষ্ট <Cite n={12} />। IAM role trust policy আর KMS key policy এর ব্যতিক্রম <Cite n={12} />। একটা permissions boundary চাওয়া action-এর অনুমতি না দিলে request implicitly denied হয় <Cite n={12} />।

**একটা কাজের উদাহরণ।** একটা account-এর ভেতরের request-এর page-এ Carlos নামের একজন user আর দুটো policy দেখানো আছে <Cite n={11} />। `DenyS3Logs` statement Carlos-কে এমন যেকোনো S3 bucket-এ প্রবেশ করতে বাধা দেয়, যার নামে `log` আছে <Cite n={11} />। Carlos logs bucket-এ একটা file save করলে AWS আগে এমন একটা `Deny` statement খোঁজে, যা request-টার ওপর প্রযোজ্য <Cite n={11} />। সে একটা পায় <Cite n={11} />। Carlos-এর প্রবেশ আটকানো হয় <Cite n={11} />। সে নিজের bucket-এ file save করলে AWS একটা `Deny` statement খোঁজে আর পায় না <Cite n={11} />। identity-based policy আর resource-based policy দুটোই request-টা অনুমতি দেয় <Cite n={11} />। তাই AWS request-টা অনুমতি দেয় <Cite n={11} />। এর কোনোটা request-টা explicit deny করলে সেটা আটকানো হতো <Cite n={11} />।

**Least privilege আর যাচাই।** IAM policy দিয়ে permission ঠিক করার সময় কাজটা করার জন্য যতটুকু permission দরকার, শুধু ততটুকুই দিন <Cite n={3} />। আপনার ব্যবহারের ক্ষেত্র পরিণত হলে আপনি দেওয়া permission কমিয়ে least privilege-এর দিকে এগোতে পারেন <Cite n={3} />। AWS managed policy আপনার নির্দিষ্ট ব্যবহারের জন্য least-privilege permission নাও দিতে পারে <Cite n={3} />। IAM last accessed তথ্য দেয়, যাতে আপনি কী আর দরকার নেই তা শনাক্ত করতে পারেন <Cite n={3} />। আপনি এমন শর্ত ঠিক করতে পারেন, যে শর্তে একটা policy statement কার্যকর থাকে <Cite n={3} />।

IAM Access Analyzer-এর external access analyzer এমন resource শনাক্ত করতে সাহায্য করে, যা কোনো বাইরের সত্তার সঙ্গে ভাগ করা <Cite n={15} />। এটা আপনার AWS CloudTrail log-এর access activity থেকে IAM policy তৈরি করে <Cite n={15} />। আপনি console-এ যে policy বানান বা সম্পাদনা করেন, AWS স্বয়ংক্রিয়ভাবে সেগুলো পরীক্ষা করে দেখে, IAM policy grammar মানা হচ্ছে কি না <Cite n={14} />। এটা আরও যাচাই করে যে আপনার ARN ঠিকভাবে লেখা আর action-এর নাম ও condition key সঠিক <Cite n={14} />।

**Policy simulator।** IAM policy simulator দিয়ে আপনি আপনার দেওয়া identity-based policy, IAM permissions boundary, service control policy (SCP) আর resource-based policy test করতে পারেন <Cite n={13} />। কোনো AWS service-এ আসল request না পাঠিয়ে আপনি দেখে নেন AWS একটা request কীভাবে evaluate করত <Cite n={13} />। প্রতিটা simulation আপনার test করা প্রতিটা action ও resource-এর জন্য একটা দুই-মানের authorization ফল দেয় <Cite n={13} />। Custom mode-এ আপনি আপনার লেখা বা paste করা এক বা একাধিক policy test করেন <Cite n={13} />। সেগুলো আলাদাভাবে simulate হয়, আপনার account-এ save হয় না <Cite n={13} />। simulator-এর ফল আপনার live AWS environment-এর থেকে আলাদা হতে পারে <Cite n={13} />। AWS সুপারিশ করে, test করার পর আপনার policy আপনার live environment-এ যাচাই করুন <Cite n={13} />।

**KMS key আর data key।** আপনি data encrypt করলে আপনার encryption key-কে সুরক্ষিত রাখতে হয় <Cite n={17} />। আপনি আপনার key encrypt করলে তার encryption key-কে সুরক্ষিত রাখতে হয় <Cite n={17} />। শেষমেশ আপনাকে সবচেয়ে ওপরের স্তরের encryption key-কে সুরক্ষিত রাখতে হয়, যার নাম root key <Cite n={17} />। Envelope encryption হলো plaintext data-কে একটা data key দিয়ে encrypt করা, তারপর সেই data key-কে অন্য একটা key দিয়ে encrypt করার চর্চা <Cite n={19} />। শেষমেশ একটা key plaintext-এ থেকে যেতে হয়, যাতে আপনি key আর আপনার data decrypt করতে পারেন <Cite n={19} />। এই সবচেয়ে ওপরের plaintext key encryption key-এর নাম root key <Cite n={19} />। একটা KMS key ব্যবহার করতে আপনাকে AWS KMS-কে call করতে হয় <Cite n={19} />।

Data key হলো symmetric key, যা দিয়ে আপনি data encrypt করতে পারেন <Cite n={20} />। Data key আপনাকে ফেরত দেওয়া হয়, AWS KMS-এর বাইরে ব্যবহারের জন্য <Cite n={20} />। AWS KMS একটা plaintext data key (সঙ্গে সঙ্গে ব্যবহারের জন্য, ঐচ্ছিক) আর data key-র একটা encrypted copy ফেরত দেয় <Cite n={20} />। আপনি data decrypt করতে তৈরি হলে আগে AWS KMS-কে encrypted data key decrypt করতে বলেন <Cite n={20} />। AWS KMS আপনার data key জমা রাখে না, পরিচালনা করে না, আর হিসাবও রাখে না <Cite n={20} />। একটা data key বানাতে `GenerateDataKey` operation call করুন <Cite n={20} />। কাঁচা data বারবার re-encrypt করার বদলে আপনি শুধু data key-গুলো re-encrypt করতে পারেন <Cite n={19} />।

**KMS key-র ধরন, rotation আর মুছে ফেলা।** আপনার বানানো KMS key-গুলো customer managed key <Cite n={18} />। আপনার account-এ একটা customer managed key রাখার জন্য মাসিক খরচ আছে <Cite n={18} />। একটা customer managed key-র জন্য আপনি তার key policy রাখতে ও বদলাতে, সেটা enable ও disable করতে, তার cryptographic material rotate করতে আর সেটা মুছে ফেলার জন্য schedule করতে পারেন <Cite n={18} />। AWS managed key-র কোনো property আপনি বদলাতে, সেগুলো rotate করতে, তাদের key policy বদলাতে বা মুছে ফেলার জন্য schedule করতে পারেন না <Cite n={18} />। সব AWS managed key প্রতি বছর স্বয়ংক্রিয়ভাবে rotate হয় <Cite n={18} />।

By default, আপনি একটা KMS key-র জন্য automatic key rotation চালু করলে AWS KMS প্রতি বছর সেটার জন্য নতুন cryptographic material তৈরি করে <Cite n={21} />। এক্ষুনি rotation শুরু করতে আপনি on-demand rotation করতে পারেন <Cite n={21} />। আপনি rotate হওয়া KMS key দিয়ে ciphertext decrypt করলে AWS KMS সেই key material ব্যবহার করে, যা দিয়ে ciphertext encrypt হয়েছিল <Cite n={21} />। আপনি rotate হওয়া KMS key code বদলানো ছাড়াই application-এ নিরাপদে ব্যবহার করতে পারেন <Cite n={21} />। KMS key একই logical resource থাকে, তার key material যতবারই বদলাক <Cite n={21} />। Key rotation KMS key যে data রক্ষা করে, তার ওপর কোনো প্রভাব ফেলে না <Cite n={21} />। এটা KMS key-র বানানো data key rotate করে না, আর কোনো data re-encrypt করে না <Cite n={21} />। Key rotation একটা ফাঁস হওয়া data key-র প্রভাব কমায় না <Cite n={21} />।

একটা AWS KMS key মুছে ফেলা ধ্বংসাত্মক আর সম্ভাব্য বিপজ্জনক <Cite n={22} />। এটা key material আর KMS key-র সঙ্গে যুক্ত সব metadata মুছে দেয়, আর এটা ফেরানো যায় না <Cite n={22} />। একটা KMS key মুছে গেলে সেই KMS key-র অধীনে encrypt হওয়া data আপনি আর decrypt করতে পারেন না <Cite n={22} />। AWS KMS ৭ – ৩০ দিনের একটা অপেক্ষার সময় দাবি করে <Cite n={22} />। default অপেক্ষার সময় ৩০ দিন <Cite n={22} />। মুছে ফেলার অপেক্ষায় থাকা KMS key কোনো cryptographic operation-এ ব্যবহার করা যায় না <Cite n={22} />। KMS key ফিরিয়ে আনতে আপনি অপেক্ষার সময় শেষ হওয়ার আগে মুছে ফেলা বাতিল করতে পারেন <Cite n={22} />। আপনি নিশ্চিত না হলে KMS key মুছে ফেলার বদলে disable করার কথা ভাবুন <Cite n={22} />। মুছে ফেলার জন্য schedule করা customer managed KMS key-র জন্য কোনো খরচ নেই <Cite n={23} />।

**Secrets Manager: secret, key আর rotation।** একটা secret হতে পারে একটা password, একটা credential-এর সেট, একটা OAuth token বা অন্য গোপন তথ্য, যা আপনি encrypt করা রূপে রাখেন <Cite n={25} />। আপনি একটা secret-এ ৬৫৫৩৬ byte পর্যন্ত রাখতে পারেন <Cite n={25} />। একটা secret বানাতে আপনার `SecretsManagerReadWrite` managed policy-র দেওয়া permission লাগে <Cite n={25} />। Secrets Manager secret-গুলো জমা অবস্থায় encrypt করে, এমন encryption key দিয়ে, যা আপনার মালিকানায় আর AWS KMS-এ রাখা <Cite n={27} />। আপনি একটা secret retrieve করলে Secrets Manager সেটা decrypt করে TLS দিয়ে নিরাপদে আপনার local environment-এ পাঠায় <Cite n={27} />। বেশির ভাগ ক্ষেত্রে AWS managed key `aws/secretsmanager` বেছে নিন <Cite n={25} />। এই key ব্যবহারের জন্য কোনো খরচ নেই <Cite n={25} />। আপনি আপনার secret encrypt করতে নিজের KMS key বানালে AWS আপনার কাছ থেকে বর্তমান AWS KMS হারে খরচ নেয় <Cite n={24} />।

Secrets Manager দিয়ে আপনি আপনার secret-এর জন্য একটা স্বয়ংক্রিয় rotation-এর সূচি ঠিক করতে পারেন <Cite n={24} />। credential rotate করতে আর আপনার application হালনাগাদ করা এবং application client-এ পরিবর্তন deploy করা লাগে না <Cite n={24} />। আপনি প্রতি চার ঘণ্টায়ও স্বয়ংক্রিয় rotation চালু করতে পারেন <Cite n={27} />। Secrets Manager rotation-এর দুটো কৌশল দেয়: Single user আর Alternating users <Cite n={27} />। আপনি অনেক দিন secret না বদলালে সেগুলো ফাঁস হওয়ার সম্ভাবনা বাড়ে <Cite n={27} />। আপনি স্বয়ংক্রিয় rotation চালু করলে (managed rotation বাদে) rotation function-এর জন্য বর্তমান Lambda হারে খরচ হয় <Cite n={24} />।

**Secrets Manager: মুছে ফেলা আর সামলানো।** Secrets Manager secret সঙ্গে সঙ্গে মুছে ফেলে না <Cite n={26} />। সে secret-টাকে সঙ্গে সঙ্গে অপ্রবেশযোগ্য করে দেয় আর কমপক্ষে সাত দিনের একটা recovery window-এর পর মুছে ফেলার জন্য schedule করে <Cite n={26} />। recovery window শেষ না হওয়া পর্যন্ত আপনি আগে মুছে ফেলা একটা secret ফিরিয়ে আনতে পারেন <Cite n={26} />। মুছে ফেলার জন্য চিহ্নিত secret-এর জন্য কোনো খরচ নেই <Cite n={26} />। আপনি একটা secret-এর একটা version সরাসরি মুছতে পারেন না <Cite n={26} />। কোনো application এখনো একটা secret ব্যবহার করে কি না তা না জানলে আপনি recovery window-এর সময় চেষ্টা করা access-এর জন্য একটা Amazon CloudWatch alarm বানাতে পারেন <Cite n={26} />। recovery window ছাড়া একটা secret মুছলে সেটা আর ফেরানো যায় না <Cite n={26} />।

Secrets Manager ব্যবহার করলে আপনি শুধু যা ব্যবহার করেন তার জন্য দাম দেন, কোনো ন্যূনতম বা setup খরচ ছাড়া <Cite n={24} />। বেশির ভাগ command shell-এ এমন সুবিধা আছে, যা আপনার secret ঝুঁকিতে ফেলতে পারে, যেমন logging আর সর্বশেষ দেওয়া command দেখার সুযোগ <Cite n={27} />। আপনার secret-এ প্রবেশ নিয়ন্ত্রণ করা IAM policy statement-এ সবচেয়ে কম সুবিধার (least privileged) নীতি ব্যবহার করুন <Cite n={27} />। আপনার secret সবচেয়ে কার্যকরভাবে ব্যবহার করতে সেগুলো cache করুন আর শুধু দরকারে হালনাগাদ করুন <Cite n={27} />।

**1. Model the policy decision with Python.** This is the tutorial's own code. It is a model of the rules that the AWS pages describe. It is not the AWS engine. It reads JSON policies with `json.loads`, which deserializes a JSON document to a Python object <Cite n={32} />. The two policies are those of the single-account example of AWS <Cite n={11} />, with one change. The identity policy of the tutorial lists two of the four actions of the `AllowS3ListRead` statement, and leaves out `s3:GetAccountPublicAccessBlock` and `s3:ListAccessPoints` <Cite n={11} />. Save this file as `policy_model.py`:

```python
import json
import re


def wild(pattern):
    """IAM-style wildcards: * is any run of characters, ? is one character."""
    return re.compile("^" + "".join(".*" if c == "*" else "." if c == "?" else re.escape(c) for c in pattern) + "$")


def as_list(value):
    return [value] if isinstance(value, str) else list(value)


def applies(statement, principal, action, resource, from_resource_policy):
    if from_resource_policy and principal not in as_list(statement.get("Principal", {}).get("AWS", [])):
        return False
    return (any(wild(a).match(action) for a in as_list(statement["Action"]))
            and any(wild(r).match(resource) for r in as_list(statement["Resource"])))


def decide(principal, action, resource, identity_policies, resource_policy=None):
    statements = [(s, False) for doc in identity_policies for s in doc["Statement"]]
    if resource_policy:
        statements += [(s, True) for s in resource_policy["Statement"]]
    allowed = False
    for statement, from_resource_policy in statements:
        if not applies(statement, principal, action, resource, from_resource_policy):
            continue
        if statement["Effect"] == "Deny":
            return "Deny (explicit deny: %s)" % statement.get("Sid", "no Sid")
        allowed = True
    return "Allow" if allowed else "Deny (implicit deny)"


CARLOS = "arn:aws:iam::123456789012:user/carlossalazar"
HOME, LOGS = "amzn-s3-demo-bucket-carlossalazar", "amzn-s3-demo-bucket-carlossalazar-logs"
identity = json.loads("""{"Version": "2012-10-17", "Statement": [
  {"Sid": "AllowS3ListRead", "Effect": "Allow", "Action": ["s3:GetBucketLocation", "s3:ListAllMyBuckets"], "Resource": "arn:aws:s3:::*"},
  {"Sid": "AllowS3Self", "Effect": "Allow", "Action": "s3:*", "Resource": ["arn:aws:s3:::%s/*", "arn:aws:s3:::%s"]},
  {"Sid": "DenyS3Logs", "Effect": "Deny", "Action": "s3:*", "Resource": "arn:aws:s3:::*log*"}]}""" % (HOME, HOME))
bucket = json.loads("""{"Version": "2012-10-17", "Statement": [
  {"Effect": "Allow", "Principal": {"AWS": "%s"}, "Action": "s3:*", "Resource": ["arn:aws:s3:::%s/*", "arn:aws:s3:::%s"]}]}""" % (CARLOS, HOME, HOME))
bucket_deny = json.loads(json.dumps(bucket))
bucket_deny["Statement"].append({"Sid": "DenyCarlos", "Effect": "Deny", "Principal": {"AWS": CARLOS}, "Action": "s3:*", "Resource": "arn:aws:s3:::%s/*" % HOME})

put = "s3:PutObject"
cases = [
    ("Carlos saves a file in the logs bucket", CARLOS, "arn:aws:s3:::%s/notes.txt" % LOGS, [identity], bucket),
    ("Carlos saves a file in his own bucket", CARLOS, "arn:aws:s3:::%s/notes.txt" % HOME, [identity], bucket),
    ("Carlos saves a file in another bucket", CARLOS, "arn:aws:s3:::amzn-s3-demo-bucket-other/notes.txt", [identity], bucket),
    ("Someone else saves in Carlos's bucket", "arn:aws:iam::123456789012:user/someoneelse", "arn:aws:s3:::%s/notes.txt" % HOME, [], bucket),
    ("Own bucket, identity policy only", CARLOS, "arn:aws:s3:::%s/notes.txt" % HOME, [identity], None),
    ("Own bucket, bucket policy only", CARLOS, "arn:aws:s3:::%s/notes.txt" % HOME, [], bucket),
    ("Own bucket, bucket policy adds a Deny", CARLOS, "arn:aws:s3:::%s/notes.txt" % HOME, [identity], bucket_deny),
]
for label, principal, resource, identity_policies, resource_policy in cases:
    print("%-40s %s" % (label + ":", decide(principal, put, resource, identity_policies, resource_policy)))
```

**2. Model a key hierarchy with OpenSSL.** This is the tutorial's own model of the key hierarchy that the AWS pages describe. It does not call AWS KMS. It follows envelope encryption, which is the practice of encrypting plaintext data with a data key, and then encrypting the data key under another key <Cite n={19} />. The root key of the model is a random value that stands in for a KMS key. In AWS KMS, KMS keys are created, managed, used, and deleted entirely within AWS KMS <Cite n={17} />.

`openssl rand` generates random bytes with a cryptographically secure pseudo random number generator <Cite n={31} />, and `-hex` shows the output as a hex string <Cite n={31} />. For `openssl enc`, the key given with `-K` must be a string of hex digits, and if only the key is specified, the IV must be given with `-iv` <Cite n={30} />. The option `-d` decrypts the input <Cite n={30} />. Using AES-256 in CBC mode is the tutorial's own choice. The command lists AES in CBC mode <Cite n={30} />. It does not support authenticated encryption modes like CCM and GCM <Cite n={30} />. So the model cannot tell whether a file was changed. Do not use it for real data.

Save this file as `envelope.sh`. It keeps the root keys and the data key in shell variables and never writes them to a file:

```bash
set -eu
mkdir envelope-demo && cd envelope-demo
ROOT_A=$(openssl rand -hex 32)          # stands in for a KMS key
DATA=$(openssl rand -hex 32)            # the data key
IV1=$(openssl rand -hex 16); IV2=$(openssl rand -hex 16); IV3=$(openssl rand -hex 16)
printf 'tester note: nothing secret here\n' > message.txt

# 1. seal the message with the data key, and the data key with the root key
openssl enc -aes-256-cbc -K "$DATA" -iv "$IV1" -in message.txt -out message.enc
printf '%s' "$DATA" | openssl enc -aes-256-cbc -K "$ROOT_A" -iv "$IV2" -out datakey.enc
unset DATA
rm message.txt
echo "1. envelope: message.enc $(wc -c < message.enc) bytes, datakey.enc $(wc -c < datakey.enc) bytes"

# 2. open it: the root key opens the data key, and the data key opens the message
DATA=$(openssl enc -d -aes-256-cbc -K "$ROOT_A" -iv "$IV2" -in datakey.enc)
echo "2. opened: $(openssl enc -d -aes-256-cbc -K "$DATA" -iv "$IV1" -in message.enc)"

# 3. "rotate": wrap the same data key under a new root key; message.enc is not touched
BEFORE=$(sha256sum < message.enc)
ROOT_B=$(openssl rand -hex 32)
printf '%s' "$DATA" | openssl enc -aes-256-cbc -K "$ROOT_B" -iv "$IV3" -out datakey.enc
unset DATA ROOT_A
if [ "$BEFORE" = "$(sha256sum < message.enc)" ]; then echo "3. message.enc is the same file after the re-wrap"; else echo "3. message.enc CHANGED"; fi
DATA=$(openssl enc -d -aes-256-cbc -K "$ROOT_B" -iv "$IV3" -in datakey.enc)
echo "3. opened with the new root key: $(openssl enc -d -aes-256-cbc -K "$DATA" -iv "$IV1" -in message.enc)"

# 4. "delete" the root key: it was never written to a file, so nothing is left that opens datakey.enc
unset DATA ROOT_B
echo "4. no root key is left; files in the folder: $(ls | tr '\n' ' ')"
```

Run it:

```bash
bash envelope.sh
```

Output of the tutorial's run:

```text
1. envelope: message.enc 48 bytes, datakey.enc 80 bytes
2. opened: tester note: nothing secret here
3. message.enc is the same file after the re-wrap
3. opened with the new root key: tester note: nothing secret here
4. no root key is left; files in the folder: datakey.enc message.enc 
```

- Line 1: the envelope is two files, the sealed message and the sealed data key. AWS says that you can safely store the encrypted data key alongside the encrypted data <Cite n={19} />. The model keeps the three IVs in shell variables and does not store them with the files.
- Line 2: the root key opens the data key, and the data key opens the message. The recipient first decrypts the encrypted key and then decrypts the message <Cite n={19} />. With AWS KMS, you first ask AWS KMS to decrypt the encrypted data key <Cite n={20} />.
- Line 3: the script wraps the same data key under a new root key. The message file is the same file after the re-wrap. AWS says that you can re-encrypt only the data keys instead of re-encrypting the raw data <Cite n={19} />. This is not a model of KMS key rotation. When you use a rotated KMS key to decrypt, AWS KMS uses the key material that was used to encrypt <Cite n={21} />, and the model drops the old root key. What both share is that key rotation does not re-encrypt any data <Cite n={21} />.
- Line 4: no root key is left. AWS says that after a KMS key is deleted, you can no longer decrypt the data that was encrypted under it <Cite n={22} />. The model has no waiting period and no way to cancel. AWS KMS requires a waiting period of 7 – 30 days <Cite n={22} />, and you can cancel key deletion before it ends <Cite n={22} />. The tutorial did not try to open `datakey.enc` after step 4, so its output does not show that the data is unrecoverable.

```python
import json
import re


def wild(pattern):
    """IAM-style wildcards: * is any run of characters, ? is one character."""
    return re.compile("^" + "".join(".*" if c == "*" else "." if c == "?" else re.escape(c) for c in pattern) + "$")


def as_list(value):
    return [value] if isinstance(value, str) else list(value)


def applies(statement, principal, action, resource, from_resource_policy):
    if from_resource_policy and principal not in as_list(statement.get("Principal", {}).get("AWS", [])):
        return False
    return (any(wild(a).match(action) for a in as_list(statement["Action"]))
            and any(wild(r).match(resource) for r in as_list(statement["Resource"])))


def decide(principal, action, resource, identity_policies, resource_policy=None):
    statements = [(s, False) for doc in identity_policies for s in doc["Statement"]]
    if resource_policy:
        statements += [(s, True) for s in resource_policy["Statement"]]
    allowed = False
    for statement, from_resource_policy in statements:
        if not applies(statement, principal, action, resource, from_resource_policy):
            continue
        if statement["Effect"] == "Deny":
            return "Deny (explicit deny: %s)" % statement.get("Sid", "no Sid")
        allowed = True
    return "Allow" if allowed else "Deny (implicit deny)"


CARLOS = "arn:aws:iam::123456789012:user/carlossalazar"
HOME, LOGS = "amzn-s3-demo-bucket-carlossalazar", "amzn-s3-demo-bucket-carlossalazar-logs"

put = "s3:PutObject"

**2. Model a key hierarchy with OpenSSL.** This is the tutorial's own model of the key hierarchy that the AWS pages describe. It does not call AWS KMS. It follows envelope encryption, which is the practice of encrypting plaintext data with a data key, and then encrypting the data key under another key <Cite n={19} />. The root key of the model is a random value that stands in for a KMS key. In AWS KMS, KMS keys are created, managed, used, and deleted entirely within AWS KMS <Cite n={17} />.

`openssl rand` generates random bytes with a cryptographically secure pseudo random number generator <Cite n={31} />, and `-hex` shows the output as a hex string <Cite n={31} />. For `openssl enc`, the key given with `-K` must be a string of hex digits, and if only the key is specified, the IV must be given with `-iv` <Cite n={30} />. The option `-d` decrypts the input <Cite n={30} />. Using AES-256 in CBC mode is the tutorial's own choice. The command lists AES in CBC mode <Cite n={30} />. It does not support authenticated encryption modes like CCM and GCM <Cite n={30} />. So the model cannot tell whether a file was changed. Do not use it for real data.

Save this file as `envelope.sh`. It keeps the root keys and the data key in shell variables and never writes them to a file:

```bash
set -eu
mkdir envelope-demo && cd envelope-demo
ROOT_A=$(openssl rand -hex 32)          # stands in for a KMS key
DATA=$(openssl rand -hex 32)            # the data key
IV1=$(openssl rand -hex 16); IV2=$(openssl rand -hex 16); IV3=$(openssl rand -hex 16)
printf 'tester note: nothing secret here\n' > message.txt

# 1. seal the message with the data key, and the data key with the root key
openssl enc -aes-256-cbc -K "$DATA" -iv "$IV1" -in message.txt -out message.enc
printf '%s' "$DATA" | openssl enc -aes-256-cbc -K "$ROOT_A" -iv "$IV2" -out datakey.enc
unset DATA
rm message.txt
echo "1. envelope: message.enc $(wc -c < message.enc) bytes, datakey.enc $(wc -c < datakey.enc) bytes"

# 2. open it: the root key opens the data key, and the data key opens the message
DATA=$(openssl enc -d -aes-256-cbc -K "$ROOT_A" -iv "$IV2" -in datakey.enc)
echo "2. opened: $(openssl enc -d -aes-256-cbc -K "$DATA" -iv "$IV1" -in message.enc)"

# 3. "rotate": wrap the same data key under a new root key; message.enc is not touched
BEFORE=$(sha256sum < message.enc)
ROOT_B=$(openssl rand -hex 32)
printf '%s' "$DATA" | openssl enc -aes-256-cbc -K "$ROOT_B" -iv "$IV3" -out datakey.enc
unset DATA ROOT_A
if [ "$BEFORE" = "$(sha256sum < message.enc)" ]; then echo "3. message.enc is the same file after the re-wrap"; else echo "3. message.enc CHANGED"; fi
DATA=$(openssl enc -d -aes-256-cbc -K "$ROOT_B" -iv "$IV3" -in datakey.enc)
echo "3. opened with the new root key: $(openssl enc -d -aes-256-cbc -K "$DATA" -iv "$IV1" -in message.enc)"

# 4. "delete" the root key: it was never written to a file, so nothing is left that opens datakey.enc
unset DATA ROOT_B
echo "4. no root key is left; files in the folder: $(ls | tr '\n' ' ')"

Python দিয়ে policy-র সিদ্ধান্তের model বানান।** এটা টিউটোরিয়ালের নিজের code। AWS-এর page যে নিয়মগুলো বলে, এটা তার একটা model। এটা AWS-এর engine নয়। এটা `json.loads` দিয়ে JSON policy পড়ে, যা একটা JSON document-কে Python object-এ বদলায় <Cite n={32} />। দুটো policy AWS-এর একটা account-এর ভেতরের উদাহরণের policy-ই <Cite n={11} />, তবে একটা বদল আছে। টিউটোরিয়ালের identity policy-তে `AllowS3ListRead` statement-এর চারটা action-এর মধ্যে দুটো আছে, আর `s3:GetAccountPublicAccessBlock` ও `s3:ListAccessPoints` বাদ দেওয়া হয়েছে <Cite n={11} />। এই file-টা `policy_model.py` নামে save করুন:

```python
import json
import re


def wild(pattern):
    """IAM-style wildcards: * is any run of characters, ? is one character."""
    return re.compile("^" + "".join(".*" if c == "*" else "." if c == "?" else re.escape(c) for c in pattern) + "$")


def as_list(value):
    return [value] if isinstance(value, str) else list(value)


def applies(statement, principal, action, resource, from_resource_policy):
    if from_resource_policy and principal not in as_list(statement.get("Principal", {}).get("AWS", [])):
        return False
    return (any(wild(a).match(action) for a in as_list(statement["Action"]))
            and any(wild(r).match(resource) for r in as_list(statement["Resource"])))


def decide(principal, action, resource, identity_policies, resource_policy=None):
    statements = [(s, False) for doc in identity_policies for s in doc["Statement"]]
    if resource_policy:
        statements += [(s, True) for s in resource_policy["Statement"]]
    allowed = False
    for statement, from_resource_policy in statements:
        if not applies(statement, principal, action, resource, from_resource_policy):
            continue
        if statement["Effect"] == "Deny":
            return "Deny (explicit deny: %s)" % statement.get("Sid", "no Sid")
        allowed = True
    return "Allow" if allowed else "Deny (implicit deny)"


CARLOS = "arn:aws:iam::123456789012:user/carlossalazar"
HOME, LOGS = "amzn-s3-demo-bucket-carlossalazar", "amzn-s3-demo-bucket-carlossalazar-logs"
identity = json.loads("""{"Version": "2012-10-17", "Statement": [
  {"Sid": "AllowS3ListRead", "Effect": "Allow", "Action": ["s3:GetBucketLocation", "s3:ListAllMyBuckets"], "Resource": "arn:aws:s3:::*"},
  {"Sid": "AllowS3Self", "Effect": "Allow", "Action": "s3:*", "Resource": ["arn:aws:s3:::%s/*", "arn:aws:s3:::%s"]},
  {"Sid": "DenyS3Logs", "Effect": "Deny", "Action": "s3:*", "Resource": "arn:aws:s3:::*log*"}]}""" % (HOME, HOME))
bucket = json.loads("""{"Version": "2012-10-17", "Statement": [
  {"Effect": "Allow", "Principal": {"AWS": "%s"}, "Action": "s3:*", "Resource": ["arn:aws:s3:::%s/*", "arn:aws:s3:::%s"]}]}""" % (CARLOS, HOME, HOME))
bucket_deny = json.loads(json.dumps(bucket))
bucket_deny["Statement"].append({"Sid": "DenyCarlos", "Effect": "Deny", "Principal": {"AWS": CARLOS}, "Action": "s3:*", "Resource": "arn:aws:s3:::%s/*" % HOME})

put = "s3:PutObject"
cases = [
    ("Carlos saves a file in the logs bucket", CARLOS, "arn:aws:s3:::%s/notes.txt" % LOGS, [identity], bucket),
    ("Carlos saves a file in his own bucket", CARLOS, "arn:aws:s3:::%s/notes.txt" % HOME, [identity], bucket),
    ("Carlos saves a file in another bucket", CARLOS, "arn:aws:s3:::amzn-s3-demo-bucket-other/notes.txt", [identity], bucket),
    ("Someone else saves in Carlos's bucket", "arn:aws:iam::123456789012:user/someoneelse", "arn:aws:s3:::%s/notes.txt" % HOME, [], bucket),
    ("Own bucket, identity policy only", CARLOS, "arn:aws:s3:::%s/notes.txt" % HOME, [identity], None),
    ("Own bucket, bucket policy only", CARLOS, "arn:aws:s3:::%s/notes.txt" % HOME, [], bucket),
    ("Own bucket, bucket policy adds a Deny", CARLOS, "arn:aws:s3:::%s/notes.txt" % HOME, [identity], bucket_deny),
]
for label, principal, resource, identity_policies, resource_policy in cases:
    print("%-40s %s" % (label + ":", decide(principal, put, resource, identity_policies, resource_policy)))
```

প্রতিটা লাইন AWS-এর page পাশে রেখে পড়ুন:

- Logs bucket: AWS আগে এমন একটা `Deny` statement খোঁজে, যা request-টার ওপর প্রযোজ্য, একটা পায়, আর Carlos-এর প্রবেশ আটকানো হয় <Cite n={11} />।
- তার নিজের bucket: identity-based policy আর resource-based policy দুটোই request-টা অনুমতি দেয়, তাই AWS সেটা অনুমতি দেয় <Cite n={11} />।
- অন্য bucket: by default সব request implicitly denied <Cite n={12} />।
- অন্য কেউ: bucket policy ঠিক করে, শুধু `carlossalazar` user-ই bucket-টায় প্রবেশ করতে পারবে <Cite n={11} />। model-এ অন্য user-এর কোনো identity-based policy নেই।
- শুধু identity policy, আর শুধু bucket policy: দুটোর একটা request-টা অনুমতি দিলে আর অন্যটা না দিলেও request অনুমতি পায় <Cite n={11} />।
- bucket policy-তে একটা `Deny`: explicit deny explicit allow-কে বাতিল করে দেয় <Cite n={12} />। page বলে, কোনো একটা policy request-টা explicit deny করলে সেটা আটকানো হতো <Cite n={11} />।

প্রথম দুই লাইনের জন্য, যা page-এর উদাহরণ, model সেই উত্তরই দিয়েছে, যা page-এর লেখায় আছে। বাকি পাঁচটা request টিউটোরিয়ালের নিজের, আর টিউটোরিয়াল সেগুলোর প্রত্যাশিত উত্তর ভেবেছে উদ্ধৃত বাক্য থেকে, AWS থেকে নয়।

model অনেক কিছু বাদ রাখে। এটা `Condition`, `NotAction` বা `NotResource` পড়ে না। এটা একটা bucket policy-র `Principal`-এ শুধু একটা IAM user ARN নেয়। এতে নেই permissions boundary, service control policy, resource control policy, session policy, root user বা অন্য account থেকে আসা request। AWS একটা request-এর ওপর প্রযোজ্য এই সব ধরনের policy evaluate করে <Cite n={12} />।

**২. OpenSSL দিয়ে একটা key hierarchy-র model বানান।** AWS-এর page যে key hierarchy বলে, এটা তার টিউটোরিয়ালের নিজের model। এটা AWS KMS-কে call করে না। এটা envelope encryption মেনে চলে, যা হলো plaintext data-কে একটা data key দিয়ে encrypt করা, তারপর সেই data key-কে অন্য একটা key দিয়ে encrypt করার চর্চা <Cite n={19} />। model-এর root key একটা এলোমেলো মান, যা একটা KMS key-র জায়গা নেয়। AWS KMS-এ KMS key পুরোপুরি AWS KMS-এর ভেতরেই তৈরি, পরিচালিত, ব্যবহৃত ও মুছে ফেলা হয় <Cite n={17} />।

`openssl rand` একটা cryptographically secure pseudo random number generator দিয়ে এলোমেলো byte বানায় <Cite n={31} />, আর `-hex` output-কে hex string হিসেবে দেখায় <Cite n={31} />। `openssl enc`-এর জন্য `-K` দিয়ে দেওয়া key শুধু hex digit-এর একটা string হতে হয়, আর শুধু key দিলে IV দিতে হয় `-iv` দিয়ে <Cite n={30} />। `-d` option input decrypt করে <Cite n={30} />। AES-256 CBC mode-এ ব্যবহার করা টিউটোরিয়ালের নিজের পছন্দ। command-টা CBC mode-এ AES-এর তালিকা দেয় <Cite n={30} />। এটা CCM বা GCM-এর মতো authenticated encryption mode সমর্থন করে না <Cite n={30} />। তাই model বলতে পারে না কোনো file বদলেছে কি না। আসল data-র জন্য এটা ব্যবহার করবেন না।

এই file-টা `envelope.sh` নামে save করুন। এটা root key আর data key shell variable-এ রাখে, কখনো file-এ লেখে না:

```bash
set -eu
mkdir envelope-demo && cd envelope-demo
ROOT_A=$(openssl rand -hex 32)          # stands in for a KMS key
DATA=$(openssl rand -hex 32)            # the data key
IV1=$(openssl rand -hex 16); IV2=$(openssl rand -hex 16); IV3=$(openssl rand -hex 16)
printf 'tester note: nothing secret here\n' > message.txt

# 1. seal the message with the data key, and the data key with the root key
openssl enc -aes-256-cbc -K "$DATA" -iv "$IV1" -in message.txt -out message.enc
printf '%s' "$DATA" | openssl enc -aes-256-cbc -K "$ROOT_A" -iv "$IV2" -out datakey.enc
unset DATA
rm message.txt
echo "1. envelope: message.enc $(wc -c < message.enc) bytes, datakey.enc $(wc -c < datakey.enc) bytes"

# 2. open it: the root key opens the data key, and the data key opens the message
DATA=$(openssl enc -d -aes-256-cbc -K "$ROOT_A" -iv "$IV2" -in datakey.enc)
echo "2. opened: $(openssl enc -d -aes-256-cbc -K "$DATA" -iv "$IV1" -in message.enc)"

# 3. "rotate": wrap the same data key under a new root key; message.enc is not touched
BEFORE=$(sha256sum < message.enc)
ROOT_B=$(openssl rand -hex 32)
printf '%s' "$DATA" | openssl enc -aes-256-cbc -K "$ROOT_B" -iv "$IV3" -out datakey.enc
unset DATA ROOT_A
if [ "$BEFORE" = "$(sha256sum < message.enc)" ]; then echo "3. message.enc is the same file after the re-wrap"; else echo "3. message.enc CHANGED"; fi
DATA=$(openssl enc -d -aes-256-cbc -K "$ROOT_B" -iv "$IV3" -in datakey.enc)
echo "3. opened with the new root key: $(openssl enc -d -aes-256-cbc -K "$DATA" -iv "$IV1" -in message.enc)"

# 4. "delete" the root key: it was never written to a file, so nothing is left that opens datakey.enc
unset DATA ROOT_B
echo "4. no root key is left; files in the folder: $(ls | tr '\n' ' ')"
```

- ১ নম্বর লাইন: envelope হলো দুটো file, সিল করা message আর সিল করা data key। AWS বলে, encrypted data key আপনি encrypted data-র পাশেই নিরাপদে রাখতে পারেন <Cite n={19} />। model তিনটা IV shell variable-এ রাখে, file-গুলোর সঙ্গে জমা রাখে না।
- ২ নম্বর লাইন: root key data key খোলে, আর data key message খোলে। যে গ্রহণ করে, সে আগে encrypted key decrypt করে, তারপর message decrypt করে <Cite n={19} />। AWS KMS দিয়ে আপনি আগে AWS KMS-কে encrypted data key decrypt করতে বলেন <Cite n={20} />।
- ৩ নম্বর লাইন: script একই data key-কে একটা নতুন root key দিয়ে মুড়ে দেয়। re-wrap-এর পর message file একই file থাকে। AWS বলে, কাঁচা data re-encrypt করার বদলে আপনি শুধু data key-গুলো re-encrypt করতে পারেন <Cite n={19} />। এটা KMS key rotation-এর model নয়। আপনি rotate হওয়া KMS key দিয়ে decrypt করলে AWS KMS সেই key material ব্যবহার করে, যা দিয়ে encrypt হয়েছিল <Cite n={21} />, আর model পুরোনো root key ফেলে দেয়। দুটোর মিল এটুকুই যে key rotation কোনো data re-encrypt করে না <Cite n={21} />।
- ৪ নম্বর লাইন: কোনো root key বাকি নেই। AWS বলে, একটা KMS key মুছে গেলে তার অধীনে encrypt হওয়া data আপনি আর decrypt করতে পারেন না <Cite n={22} />। model-এ কোনো অপেক্ষার সময় নেই আর বাতিল করার উপায়ও নেই। AWS KMS ৭ – ৩০ দিনের অপেক্ষার সময় দাবি করে <Cite n={22} />, আর সেটা শেষ হওয়ার আগে আপনি মুছে ফেলা বাতিল করতে পারেন <Cite n={22} />। টিউটোরিয়াল ৪ নম্বর ধাপের পর `datakey.enc` খোলার চেষ্টা করেনি, তাই এর output দেখায় না যে data ফেরানো যায় না।

**৩. তিনটা command-এর parameter template ছাপুন।** নিচের command প্রথমে AWS Compute and Storage-এর ২ নম্বর ধাপের মতোই তিনটা environment variable সেট করে। এগুলো বেছে নেওয়া টিউটোরিয়ালের নিজের পছন্দ। `AWS_CONFIG_FILE` আর `AWS_SHARED_CREDENTIALS_FILE` configuration profile আর access key রাখার file-এর নাম দেয়, আর `AWS_EC2_METADATA_DISABLED` EC2 instance metadata service (IMDS)-এর ব্যবহার বন্ধ করে <Cite n={29} />। `--generate-cli-skeleton` option একটা parameter template তৈরি করে দেখায়, যা আপনি নিজের মতো করে বদলে একটা command-এর input হিসেবে ব্যবহার করতে পারেন <Cite n={28} />। তিনটা command টিউটোরিয়ালের নিজের পছন্দ, ছাঁকনিও তাই। এতে থাকা চারটা space ভেতরের (nested) নাম বাদ রাখে।

```bash
export AWS_CONFIG_FILE=/dev/null AWS_SHARED_CREDENTIALS_FILE=/dev/null AWS_EC2_METADATA_DISABLED=true
for command in "iam create-role" "secretsmanager create-secret" "kms schedule-key-deletion"; do
  echo "== aws $command"
  aws $command --generate-cli-skeleton | grep -E '^    "'
done
```

**৪. পাশাপাশি পড়ুন: একটা EC2 instance-কে role দেওয়া।** এটা AWS-এর নিজের page। টিউটোরিয়াল এটা চালায়নি। **খরচের সতর্কতা।** IAM, IAM Identity Center আর AWS STS আপনার AWS account-এর এমন feature, যা বাড়তি খরচ ছাড়া দেওয়া হয় <Cite n={1} />। আপনি তখনই শুধু খরচ করেন, যখন আপনার IAM user বা AWS STS-এর অস্থায়ী security credential দিয়ে অন্য AWS service ব্যবহার করেন <Cite n={1} />। আপনি যে instance চালু করেন, তার বিল হয় [AWS Compute and Storage](/devops/aws-compute-storage/)-এ যেভাবে বলা আছে।

1. একজন administrator `Get-pics` service role বানায় আর role-টা EC2 instance-এ attach করে <Cite n={16} />।
2. role-এ থাকে একটা permissions policy, যা নির্দিষ্ট S3 bucket-এ শুধু পড়ার প্রবেশাধিকার দেয় <Cite n={16} />। এতে একটা trust policy-ও থাকে, যা EC2 instance-কে role assume করে অস্থায়ী credential retrieve করতে দেয় <Cite n={16} />।
3. একজন developer একটা EC2 instance চালু করে আর role-টা সেই instance-এ দেয় <Cite n={16} />। role সহ instance চালু করতে developer-এর EC2 instance চালু করার permission আর IAM role পাস করার permission লাগে <Cite n={16} />।
4. আপনি IAM console ব্যবহার করলে instance profile আপনার হয়ে পরিচালিত হয় <Cite n={16} />। আপনি AWS CLI বা API ব্যবহার করলে instance profile বানানো আর তাতে role দেওয়া আলাদা ধাপে করতে হয় <Cite n={16} />।
5. application চলার সময় সে EC2 instance metadata থেকে অস্থায়ী security credential পায় <Cite n={16} />। application সেগুলো cache করলে প্রতি ঘণ্টায়, বা চলমান সেটের মেয়াদ শেষ হওয়ার অন্তত ১৫ মিনিট আগে, তার একটা নতুন সেট নেওয়া উচিত <Cite n={16} />।

**৫. পাশাপাশি পড়ুন: একটা secret রাখা।** এটা AWS-এর নিজের page। টিউটোরিয়াল এটা চালায়নি। **খরচের সতর্কতা।** Secrets Manager ব্যবহার করলে আপনি শুধু যা ব্যবহার করেন তার জন্য দাম দেন, কোনো ন্যূনতম বা setup খরচ ছাড়া <Cite n={24} />। আপনি আপনার secret encrypt করতে নিজের KMS key বানালে AWS আপনার কাছ থেকে বর্তমান AWS KMS হারে খরচ নেয় <Cite n={24} />। Secrets Manager একটা secret সঙ্গে সঙ্গে মোছে না, মোছে কমপক্ষে সাত দিনের একটা recovery window-এর পর <Cite n={26} />। মুছে ফেলার জন্য চিহ্নিত secret-এর জন্য কোনো খরচ নেই <Cite n={26} />।

1. Secrets Manager console খুলুন আর Store a new secret বেছে নিন <Cite n={25} />।
2. API key, access token বা database-এর নয় এমন credential রাখতে Other type of secret বেছে নিন <Cite n={25} />।
3. secret-টা key/value pair হিসেবে দিন, বা Plaintext tab বেছে নিয়ে যেকোনো format-এ দিন <Cite n={25} />। টিউটোরিয়ালের নিজের পরামর্শ: বানানো একটা মান ব্যবহার করুন, কখনো আসল credential নয়।
4. Encryption key-র জন্য সেই AWS KMS key বেছে নিন, যা Secrets Manager secret-এর মান encrypt করতে ব্যবহার করে <Cite n={25} />। বেশির ভাগ ক্ষেত্রে `aws/secretsmanager` বেছে নিন <Cite n={25} />।
5. শেষে পরিষ্কার করুন। secret-এর তালিকায় secret-টা বেছে নিন, তারপর Actions আর Delete secret বেছে নিন <Cite n={26} />। Waiting period-এ মুছে ফেলা স্থায়ী হওয়ার আগে কত দিন অপেক্ষা করবেন তা দিন, আর Schedule deletion বেছে নিন <Cite n={26} />।

**৬. পাশাপাশি পড়ুন: একটা KMS key মুছে ফেলার জন্য schedule করা।** এটা AWS-এর নিজের page। টিউটোরিয়াল এটা চালায়নি। **খরচের সতর্কতা।** আপনার account-এ একটা customer managed key রাখার জন্য মাসিক খরচ আছে <Cite n={18} />। মুছে ফেলার জন্য schedule করা customer managed KMS key-র জন্য কোনো খরচ নেই <Cite n={23} />। আপনি অপেক্ষার সময়ে মুছে ফেলা বাতিল করলে key-টার জন্য এমনভাবে খরচ হয়, যেন সেটা কখনো মুছে ফেলার জন্য schedule করাই হয়নি <Cite n={23} />। টিউটোরিয়ালের নিজের পরামর্শ: এটা শুধু এমন key-তে করুন, যা আপনি এই অনুশীলনের জন্য বানিয়েছেন। page সতর্ক করে, একটা KMS key মুছে ফেলা ধ্বংসাত্মক আর সম্ভাব্য বিপজ্জনক <Cite n={33} />।

1. navigation pane-এ Customer managed keys বেছে নিন <Cite n={33} />। আপনি AWS managed key বা AWS owned key মুছে ফেলার জন্য schedule করতে পারেন না <Cite n={33} />।
2. যে KMS key মুছতে চান তার পাশের checkbox বেছে নিন, তারপর Key actions, Schedule key deletion বেছে নিন <Cite n={33} />।
3. Waiting period (in days)-এর জন্য ৭ থেকে ৩০-এর মধ্যে একটা দিনের সংখ্যা দিন <Cite n={33} />।
4. I confirm that I want to schedule these keys for deletion-এর পাশের check box বেছে নিন <Cite n={33} />। key-গুলো সঙ্গে সঙ্গে cryptographic operation-এর জন্য অব্যবহারযোগ্য হয়ে যায় <Cite n={33} />।

## How a tester uses it

<Voices>
<Technical>

- **Check the deny matrix, not only the happy path.** A request is allowed only if a policy explicitly allows it <Cite n={12} />. An explicit deny overrides an explicit allow <Cite n={12} />. In one account, an `Allow` in either the identity-based or the resource-based policy is enough for most resources <Cite n={12} />.
- **Use the simulator before you change a live policy.** The IAM policy simulator shows how AWS would evaluate a request, without sending a real request to any AWS service <Cite n={13} />. Its results can differ from your live AWS environment <Cite n={13} />.
- **Wait for IAM changes.** IAM, like many other AWS services, is eventually consistent <Cite n={1} />. Be sure to verify that the changes have been propagated before production workflows depend on them <Cite n={1} />.
- **Find long-term keys.** Do NOT put access keys or credential information in your application files <Cite n={6} />. Credentials in the shared AWS credentials file are stored in plaintext <Cite n={6} />. Secrets Manager replaces hard-coded credentials with a runtime call <Cite n={24} />.
- **Test with the role of the workload.** AWS delivers the temporary credentials of an IAM role to a compute resource such as EC2 or Lambda <Cite n={3} />. After temporary credentials expire, AWS no longer recognizes them <Cite n={5} />. A caching application should get a refreshed set at least 15 minutes before the current set expires <Cite n={16} />.
- **Check MFA on powerful identities.** AWS recommends MFA for an IAM user or the root user <Cite n={3} />. The root user should be used only for tasks that require root-level permissions <Cite n={7} />.
- **Check the life of a secret.** A deleted secret stays recoverable until the recovery window ends <Cite n={26} />. A CloudWatch alarm can tell you about access attempts during the recovery window <Cite n={26} />.
- **Check that rotation does not break the app.** Rotating credentials no longer requires updating your applications and deploying changes to application clients <Cite n={24} />. Automatic rotation can run as often as every four hours <Cite n={27} />.
- **Check data after a KMS key rotates.** When you use the rotated KMS key to decrypt ciphertext, AWS KMS uses the key material that was used to encrypt it <Cite n={21} />. You can safely use a rotated KMS key in applications without code changes <Cite n={21} />. Key rotation has no effect on the data that the KMS key protects <Cite n={21} />.
- **Watch a KMS key that is pending deletion.** A KMS key pending deletion cannot be used in any cryptographic operations <Cite n={22} />. A CloudWatch alarm can warn you if a person or application attempts to use the key during the waiting period <Cite n={22} />.
- **Run policy checks on the policy text.** AWS checks JSON policy syntax and grammar <Cite n={14} />. IAM Access Analyzer validates IAM policies against policy grammar and AWS best practices <Cite n={15} />.

## Common mistakes

<Voices>
<Technical>

- **Using the root user every day.** AWS strongly recommends that you don't use the root user for everyday tasks <Cite n={1} />.
- **Putting long-term keys in code.** Do NOT put access keys or credential information in your application files <Cite n={6} />. Do NOT include files that contain access keys or credential information in your project area <Cite n={6} />.
- **Expecting a lost secret access key to come back.** The secret access key can be retrieved only at the time you create it <Cite n={6} />. If you lose it, you must delete the access key and create a new one <Cite n={6} />.

## Key words

| Term | Meaning |
|---|---|
| IAM | A web service that helps you securely control access to AWS resources |
| Root user | The sign-in identity that you begin with when you create an AWS account; it has complete access to all AWS services and resources |
| IAM role | An IAM identity that you can create in your account that has specific permissions |
| Access key | A long-term credential for an IAM user or the AWS account root user |
| Temporary security credentials | Credentials that you can use AWS STS to create and provide to trusted users; they can be configured to last from a few minutes to several hours |
| MFA | Unique authentication from an AWS supported MFA mechanism, in addition to sign-in credentials |
| Policy | An object in AWS that, when associated with an identity or resource, defines their permissions |
| Identity-based policy | A JSON permissions policy document that controls what actions an identity can perform, on which resources, and under what conditions |
| Resource-based policy | A JSON policy document that you attach to a resource such as an Amazon S3 bucket |
| Trust policy | A policy that defines which principal entities can assume the role |
| Permissions boundary | It sets the maximum permissions that an identity-based policy can grant to an IAM entity |
| Explicit deny | A `Deny` statement that applies to the request; it overrides an explicit allow |
| Implicit deny | By default, all requests are implicitly denied, except for the root user, which has full access |
| Policy simulator | It shows how AWS would evaluate a request against the policies that you provide, without sending a real request to any AWS service |
| IAM Access Analyzer | It helps identify resources shared with an external entity, validates IAM policies, and generates IAM policies from access activity |
| AWS KMS | An AWS managed service that makes it easy to create and control the keys used to encrypt and sign your data |
| KMS key | A key that is created, managed, used, and deleted entirely within AWS KMS, and never leaves the service unencrypted |
| Customer managed key | A KMS key that you create; you can maintain its key policies, enable and disable it, rotate its cryptographic material, and schedule it for deletion; it has a monthly cost |
| Data key | A symmetric key that you can use to encrypt data; it is returned to you for use outside of AWS KMS |
| Envelope encryption | The practice of encrypting plaintext data with a data key, and then encrypting the data key under another key |
| Root key | The top-level plaintext key encryption key |
| Key rotation | New cryptographic material for a KMS key, every year by default when you enable automatic rotation; it has no effect on the data that the KMS key protects |
| Waiting period | Required for a KMS key that is scheduled for deletion: 7 – 30 days, and 30 days by default; you can cancel the deletion before it ends |
| Secrets Manager | It helps you manage, retrieve, and rotate database credentials, application credentials, OAuth tokens, API keys, and other secrets throughout their lifecycles |
| Secret | A password, a set of credentials, an OAuth token, or other secret information that you store in an encrypted form in Secrets Manager |
| Recovery window | A minimum of seven days during which you can recover a secret that you deleted |
| Secret rotation | An automatic schedule for your secrets, as often as every four hours; Secrets Manager offers two strategies, Single user and Alternating users |
