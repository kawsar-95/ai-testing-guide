# AWS Networking and Delivery

This page is about the network around AWS resources: the VPC and its subnets, route tables, gateways, security groups, and network ACLs. Then it covers three more services: Elastic Load Balancing, Route 53, and CloudFront. The practice run checks IP ranges with Python and prints AWS CLI templates, and it needs no AWS account. It comes after [AWS Compute and Storage](/devops/aws-compute-storage/) and before [AWS Identity and Security](/devops/aws-identity-security/).

## What it is

<Voices>
<Technical>

**Amazon VPC.** With Amazon Virtual Private Cloud (Amazon VPC), you can launch AWS resources in a logically isolated virtual network that you've defined <Cite n={1} />. A VPC is a virtual network dedicated to your AWS account <Cite n={2} />. A subnet is a range of IP addresses in your VPC <Cite n={2} />. A subnet must reside in a single Availability Zone <Cite n={1} />. You launch AWS resources, such as EC2 instances, into your subnets <Cite n={2} />.

**Route tables and gateways.** A route table serves as the traffic controller for your VPC <Cite n={6} />. Each route table contains a set of rules, called routes, that determine where network traffic from your subnet or gateway is directed <Cite n={6} />. When you create a VPC, AWS also creates the main route table for the VPC <Cite n={6} />. Each route specifies a destination, which is a CIDR block or prefix list, and a target <Cite n={6} />. Examples of a target are an internet gateway, a NAT gateway, a VPC peering connection, and a VPN connection <Cite n={6} />. Traffic is routed to targets based on its destination IP address <Cite n={6} />. A gateway connects your VPC to another network. For example, an internet gateway connects your VPC to the internet <Cite n={1} />.

**Security groups and network ACLs.** A security group controls the traffic that is allowed to reach and leave the resources that it is associated with <Cite n={9} />. A network access control list (ACL) allows or denies specific inbound or outbound traffic at the subnet level <Cite n={10} />.

**Elastic Load Balancing.** Elastic Load Balancing automatically distributes your incoming traffic across multiple targets, such as EC2 instances, containers, and IP addresses, in one or more Availability Zones <Cite n={15} />. It monitors the health of its registered targets, and routes traffic only to the healthy targets <Cite n={15} />.

**Amazon Route 53.** Amazon Route 53 is a highly available and scalable Domain Name System (DNS) web service <Cite n={19} />. You can use Route 53 to perform three main functions in any combination: domain registration, DNS routing, and health checking <Cite n={19} />.

**Amazon CloudFront.** Amazon CloudFront is a web service that speeds up distribution of your static and dynamic web content to your users <Cite n={21} />. CloudFront delivers your content through a worldwide network of data centers called edge locations <Cite n={21} />.

## How it works

<Voices>
<Technical>

**IP ranges.** The IP addresses of a VPC are written in Classless Inter-Domain Routing (CIDR) notation <Cite n={4} />. When you create a VPC, you must specify an IPv4 CIDR block for it <Cite n={4} />. The allowed block size is between a /16 netmask (65,536 IP addresses) and a /28 netmask (16 IP addresses) <Cite n={4} />. The CIDR block of a subnet can be the same as the CIDR block for the VPC, or a subset of it <Cite n={5} />. If you create more than one subnet in a VPC, the CIDR blocks of the subnets cannot overlap <Cite n={5} />. Make sure that the ranges of your VPCs don't overlap with the ranges of your own network <Cite n={3} />. For connectivity between multiple VPCs, you must ensure that they have no overlapping IP addresses <Cite n={3} />.

The first four IP addresses and the last IP address in each subnet CIDR block are not available for your use <Cite n={5} />. In a subnet with CIDR block 10.0.0.0/24, AWS lists these five reserved addresses <Cite n={5} />:

- 10.0.0.0 is the network address, and 10.0.0.1 is reserved by AWS for the VPC router <Cite n={5} />.
- 10.0.0.2 is reserved by AWS, and 10.0.0.3 is reserved by AWS for future use <Cite n={5} />.
- 10.0.0.255 is the network broadcast address, and AWS reserves it because broadcast is not supported in a VPC <Cite n={5} />.

If you create a subnet using a command line tool or the EC2 API, the CIDR block is automatically modified to its canonical form. If you specify 100.68.0.18/18, AWS creates 100.68.0.0/18 <Cite n={5} />.

**Internet access.** Your AWS account includes a default VPC in each AWS Region <Cite n={1} />. A default VPC includes an internet gateway, and each default subnet is a public subnet <Cite n={2} />. A subnet that is associated with a route table that has a route to an internet gateway is a public subnet. Without that route, it is a private subnet <Cite n={7} />. In a public subnet's route table, the route for the internet gateway can be 0.0.0.0/0 for IPv4 or ::/0 for IPv6 <Cite n={7} />.

Attaching an internet gateway to a VPC does not automatically make your instances accessible from the internet <Cite n={3} />. You must also update the subnet route table with a route to the internet gateway <Cite n={3} />. The instances must also have public IP addresses <Cite n={3} />. They need an associated security group that allows traffic from the internet over specific ports and protocols <Cite n={3} />. By default, an instance in a nondefault subnet has a private IPv4 address but no public IPv4 address <Cite n={2} />. You can assign a public address at launch, or modify the subnet's public IP address attribute <Cite n={2} />.

A NAT gateway lets instances in a private subnet connect to services outside your VPC <Cite n={8} />. External services can't initiate a connection with those instances <Cite n={8} />. You create a public NAT gateway in a public subnet, and you must associate an Elastic IP address with it at creation <Cite n={8} />. If you don't explicitly associate a subnet with a route table, the subnet is implicitly associated with the main route table <Cite n={2} />.

**Security groups.** The only traffic that reaches the instance is the traffic allowed by the security group rules <Cite n={9} />. If the security group does not contain a rule that allows SSH traffic, you could not connect to your instance using SSH <Cite n={9} />. Security groups are stateful <Cite n={9} />. If you send a request from an instance, the response traffic for that request is allowed to reach the instance <Cite n={9} />. This holds regardless of the inbound security group rules <Cite n={9} />. Security groups do not filter traffic to and from Amazon DNS, Amazon DHCP, and EC2 instance metadata, among others <Cite n={9} />. When you add inbound rules for ports 22 (SSH) or 3389 (RDP), authorize only specific IP address ranges <Cite n={9} />. If you specify 0.0.0.0/0 (IPv4) and ::/ (IPv6), this enables anyone to access your instances from any IP address using the specified protocol <Cite n={9} />. Rule changes are propagated to instances as quickly as possible, but a small delay might occur <Cite n={14} />.

**Network ACLs.** Each subnet in your VPC must be associated with a network ACL <Cite n={10} />. If you don't explicitly associate a subnet with a network ACL, the subnet is automatically associated with the default network ACL <Cite n={10} />. A subnet can be associated with only one network ACL at a time <Cite n={10} />. Each rule can either allow or deny traffic <Cite n={10} />. Each rule has a number from 1 to 32766 <Cite n={10} />. AWS evaluates the rules in order, starting with the lowest numbered rule <Cite n={10} />. If the traffic matches a rule, the rule is applied, and no additional rules are evaluated <Cite n={10} />. Network ACLs are stateless <Cite n={10} />. If you create a rule to allow specific inbound traffic to a subnet, responses to that traffic are not automatically allowed <Cite n={10} />. AWS evaluates the rules when traffic enters and leaves the subnet, not as it is routed within a subnet <Cite n={10} />. Network ACLs can't block traffic to the Instance Metadata Service (IMDS) <Cite n={10} />.

AWS says to use security groups as the primary mechanism for controlling network access to your VPCs <Cite n={11} />. When necessary, use network ACLs to provide stateless, coarse-grain network control <Cite n={11} />.

**Application Load Balancer parts.** A load balancer serves as the single point of contact for clients <Cite n={16} />. A listener checks for connection requests from clients, using the protocol and port that you configure <Cite n={16} />. The rules that you define for a listener determine how the load balancer routes requests to its registered targets <Cite n={16} />. You must define a default rule for each listener <Cite n={16} />. Each target group routes requests to one or more registered targets, such as EC2 instances <Cite n={16} />. An Application Load Balancer functions at the application layer, the seventh layer of the OSI model <Cite n={16} />. It evaluates the listener rules in priority order to determine which rule to apply <Cite n={16} />. The default routing algorithm is round robin. Alternatively, you can specify the least outstanding requests routing algorithm <Cite n={16} />. Rules can forward requests based on the URL in the request <Cite n={16} />. Rules can also forward requests based on the host field in the HTTP header <Cite n={16} />.

**Health checks.** An Application Load Balancer periodically sends requests to its registered targets to test their status. These tests are called health checks <Cite n={18} />. After your target is registered, it must pass one health check to be considered healthy <Cite n={18} />. If the health checks exceed `UnhealthyThresholdCount` consecutive failures, the load balancer takes the target out of service <Cite n={18} />. When they exceed `HealthyThresholdCount` consecutive successes, it puts the target back in service <Cite n={18} />. The default of `UnhealthyThresholdCount` is 2, and the default of `HealthyThresholdCount` is 5 <Cite n={18} />. For HTTP/1.1 or HTTP/2, the default health check path is `/` <Cite n={18} />. If a target group contains only unhealthy registered targets, the load balancer routes requests to all those targets, regardless of their health status <Cite n={18} />. If all targets fail health checks at the same time in all enabled Availability Zones, the load balancer fails open <Cite n={18} />. Health checks do not support WebSockets <Cite n={18} />. When you deregister a target, `HealthyHostCount` decreases but `UnhealthyHostCount` does not increase <Cite n={18} />. The security groups for target instances must allow traffic from the load balancer on the health check port <Cite n={17} />. A load balancer is ready for client requests when each enabled Availability Zone has at least one healthy registered target <Cite n={17} />.

**Route 53 routing and health checks.** A user enters your domain name or subdomain name in a web browser. Then Route 53 connects the browser with your website or web application <Cite n={19} />. Route 53 sends automated requests over the internet to a resource, such as a web server <Cite n={19} />. This verifies that it's reachable, available, and functional <Cite n={19} />. You can also route internet traffic away from unhealthy resources <Cite n={19} />. When you create a record, you choose a routing policy, which determines how Route 53 responds to queries <Cite n={20} />. The routing policies are:

- Simple: for a single resource that performs a given function for your domain <Cite n={20} />.
- Failover: when you want to configure active-passive failover <Cite n={20} />.
- Geolocation: when you want to route traffic based on the location of your users <Cite n={20} />.
- Geoproximity: when you want to route traffic based on the location of your resources <Cite n={20} />.
- Latency: when you have resources in multiple AWS Regions and want to route traffic to the Region that provides the best latency <Cite n={20} />.
- IP-based: when you want to route traffic based on the location of your users, and have the IP addresses that the traffic originates from <Cite n={20} />.
- Multivalue answer: when you want Route 53 to respond to DNS queries with up to eight healthy records selected at random <Cite n={20} />.
- Weighted: to route traffic to multiple resources in proportions that you specify <Cite n={20} />.

**CloudFront caching.** DNS routes the request to the CloudFront POP (edge location) that can best serve the request <Cite n={22} />. This is typically the nearest POP in terms of latency <Cite n={22} />. CloudFront checks its cache for the requested object. If the object is in the cache, CloudFront returns it to the user <Cite n={22} />. If the object is not in the cache, CloudFront forwards the request to your origin server <Cite n={22} />. CloudFront also adds the object to the cache for the next time someone requests it <Cite n={22} />.

You can control how long your files stay in a CloudFront cache before CloudFront forwards another request to your origin <Cite n={23} />. After a file expires, CloudFront forwards the request to the origin to verify that the cache contains the latest version of the file <Cite n={23} />. If the cache already has the latest version, the origin returns a status code 304 Not Modified <Cite n={23} />. If it does not, the origin returns a status code 200 OK and the latest version of the file <Cite n={23} />. If you opt out of using a cache policy, the default TTL (Time to Live) is 24 hours <Cite n={23} />. You can change the cache duration for an individual file by configuring your origin <Cite n={23} />. **Application Load Balancer-এর অংশ।** একটা load balancer client-দের জন্য যোগাযোগের একমাত্র বিন্দু হিসেবে কাজ করে <Cite n={16} />। একটা listener client-এর connection request খোঁজে, আপনার configure করা protocol আর port ব্যবহার করে <Cite n={16} />। একটা listener-এর জন্য আপনি যে নিয়ম ঠিক করেন, সেগুলো ঠিক করে load balancer তার registered target-গুলোতে request কীভাবে route করবে <Cite n={16} />। প্রতিটা listener-এর জন্য আপনাকে একটা default নিয়ম ঠিক করতে হবে <Cite n={16} />। প্রতিটা target group এক বা একাধিক registered target-এ request route করে, যেমন EC2 instance <Cite n={16} />। একটা Application Load Balancer কাজ করে application layer-এ, OSI model-এর সপ্তম layer-এ <Cite n={16} />। এটা কোন নিয়ম প্রয়োগ হবে তা ঠিক করতে listener-এর নিয়ম priority অনুযায়ী যাচাই করে <Cite n={16} />। default routing algorithm হলো round robin। বিকল্প হিসেবে আপনি least outstanding requests routing algorithm ঠিক করতে পারেন <Cite n={16} />। আপনি এমন নিয়ম configure করতে পারেন, যা request-এর URL-এর ভিত্তিতে request forward করে <Cite n={16} />। এমন নিয়মও configure করা যায়, যা HTTP header-এর host field-এর ভিত্তিতে request forward করে <Cite n={16} />।

**Health check।** একটা Application Load Balancer তার registered target-গুলোর অবস্থা পরীক্ষা করতে সময়ে সময়ে তাদের কাছে request পাঠায়। এই পরীক্ষাগুলোকে health check বলা হয় <Cite n={18} />। একটা target registered হওয়ার পর সুস্থ গণ্য হতে তাকে একটা health check পাস করতে হয় <Cite n={18} />। health check পরপর `UnhealthyThresholdCount`-এর বেশি বার ব্যর্থ হলে load balancer target-টাকে service থেকে সরিয়ে নেয় <Cite n={18} />। পরপর `HealthyThresholdCount`-এর বেশি বার সফল হলে সে target-টাকে আবার service-এ ফিরিয়ে আনে <Cite n={18} />। `UnhealthyThresholdCount`-এর default ২, আর `HealthyThresholdCount`-এর default ৫ <Cite n={18} />। HTTP/1.1 বা HTTP/2-এর জন্য default health check path হলো `/` <Cite n={18} />। একটা target group-এ শুধু অসুস্থ registered target থাকলে load balancer সেই সব target-এ request route করে, তাদের health status যা-ই হোক <Cite n={18} />। সব enabled Availability Zone-এ একই সময়ে সব target health check-এ ব্যর্থ হলে load balancer fail open করে <Cite n={18} />। health check WebSocket সমর্থন করে না <Cite n={18} />। আপনি একটা target deregister করলে `HealthyHostCount` কমে কিন্তু `UnhealthyHostCount` বাড়ে না <Cite n={18} />। target instance-এর security group-কে health check port-এ load balancer থেকে আসা traffic অনুমতি দিতে হবে <Cite n={17} />। load balancer client request সামলানোর জন্য তৈরি, যখন তার প্রতিটা enabled Availability Zone-এ অন্তত একটা সুস্থ registered target থাকে <Cite n={17} />।

**Route 53 routing আর health check।** একজন user web browser-এ আপনার domain name বা subdomain name দেন। তখন Route 53 browser-টাকে আপনার website বা web application-এর সঙ্গে যুক্ত করে <Cite n={19} />। Route 53 internet দিয়ে একটা resource-এ, যেমন একটা web server-এ, স্বয়ংক্রিয় request পাঠায় <Cite n={19} />। এতে যাচাই হয় যে সেটা পৌঁছানো যায়, চালু আছে আর কাজ করছে <Cite n={19} />। আপনি internet traffic অসুস্থ resource থেকে সরিয়েও নিতে পারেন <Cite n={19} />। একটা record বানানোর সময় আপনি একটা routing policy বেছে নেন, যা ঠিক করে Route 53 query-র উত্তর কীভাবে দেবে <Cite n={20} />। routing policy-গুলো হলো:

- Simple: আপনার domain-এর জন্য একটা নির্দিষ্ট কাজ করা একটা resource-এর জন্য <Cite n={20} />।
- Failover: যখন আপনি active-passive failover configure করতে চান <Cite n={20} />।
- Geolocation: যখন আপনি user-দের অবস্থানের ভিত্তিতে traffic route করতে চান <Cite n={20} />।
- Geoproximity: যখন আপনি আপনার resource-এর অবস্থানের ভিত্তিতে traffic route করতে চান <Cite n={20} />।
- Latency: যখন আপনার একাধিক AWS Region-এ resource আছে আর আপনি সেই Region-এ traffic route করতে চান, যা সবচেয়ে ভালো latency দেয় <Cite n={20} />।
- IP-based: যখন আপনি user-দের অবস্থানের ভিত্তিতে traffic route করতে চান, আর traffic যে IP address থেকে আসে তা আপনার কাছে আছে <Cite n={20} />।
- Multivalue answer: যখন আপনি চান Route 53 DNS query-র উত্তর দিক সর্বোচ্চ আটটা সুস্থ record দিয়ে, যা এলোমেলোভাবে বাছা <Cite n={20} />।
- Weighted: একাধিক resource-এ আপনার নির্দিষ্ট করা অনুপাতে traffic route করতে <Cite n={20} />।

**CloudFront caching।** DNS request-টাকে সেই CloudFront POP (edge location)-এ route করে, যে request-টা সবচেয়ে ভালো সামলাতে পারে <Cite n={22} />। এটা সাধারণত latency-র হিসাবে সবচেয়ে কাছের POP <Cite n={22} />। CloudFront চাওয়া object-এর জন্য তার cache দেখে। object cache-এ থাকলে CloudFront তা user-কে ফেরত দেয় <Cite n={22} />। object cache-এ না থাকলে CloudFront request-টা আপনার origin server-এ forward করে <Cite n={22} />। CloudFront পরের বার কেউ চাইলে যাতে পায়, তাই object-টা cache-এও যোগ করে <Cite n={22} />।

আপনার file CloudFront cache-এ কতক্ষণ থাকবে, তা আপনি নিয়ন্ত্রণ করতে পারেন, আপনার origin-এ CloudFront আবার request পাঠানোর আগে <Cite n={23} />। একটা file-এর মেয়াদ শেষ হলে CloudFront origin-এ request forward করে যাচাই করে যে cache-এ file-টার সর্বশেষ version আছে কি না <Cite n={23} />। cache-এ সর্বশেষ version থাকলে origin 304 Not Modified status code ফেরত দেয় <Cite n={23} />। না থাকলে origin 200 OK status code আর file-টার সর্বশেষ version ফেরত দেয় <Cite n={23} />। আপনি cache policy ব্যবহার না করলে default TTL (Time to Live) ২৪ ঘণ্টা <Cite n={23} />। আপনি origin configure করে একটা আলাদা file-এর cache-এর মেয়াদ বদলাতে পারেন <Cite n={23} />। origin file-এ `max-age` বা `s-maxage` directive-সহ একটা `Cache-Control` header, বা একটা `Expires` header যোগ করে <Cite n={23} />। যে file প্রায়ই চাওয়া হয় না, CloudFront তা মেয়াদ শেষের আগেই evict করে দিতে পারে <Cite n={23} />। error, যেমন 404 Not Found, CloudFront cache-এ কতক্ষণ থাকবে তাও আপনি নিয়ন্ত্রণ করতে পারেন <Cite n={23} />।

একটা file-এর মেয়াদ শেষের আগে edge cache থেকে তা সরাতে আপনি file-টা invalidate করতে পারেন <Cite n={24} />। আলাদা নামের একটা আলাদা version দিতে file versioning-ও ব্যবহার করতে পারেন <Cite n={24} />। আপনি আপনার file ঘন ঘন হালনাগাদ করতে চাইলে AWS সুপারিশ করে, মূলত file versioning ব্যবহার করুন <Cite n={24} />। আপনি একটা file invalidate করলে user পুরোনো version-ই দেখতে থাকতে পারে, যতক্ষণ না সেই cache থেকে তার মেয়াদ শেষ হয় <Cite n={24} />।

rule = ipaddress.ip_network("10.0.0.0/25")

AWS বলে, একটা inbound rule-এর ঠিক একটা source লাগে, যা একটা IPv4 বা IPv6 address range, একটা prefix list, বা একটা security group <Cite n={14} />। সে আরও বলে, প্রতিটা rule-এর জন্য একটা protocol নির্দিষ্ট করতে হবে, আর TCP বা UDP-র জন্য একটা port বা port range <Cite n={14} />। টিউটোরিয়াল এগুলো নামের মিল দেখে মিলিয়েছে: range-এর জন্য `CidrIp`, protocol-এর জন্য `IpProtocol`, আর port-এর জন্য `FromPort` ও `ToPort`। এই মিলটা সে API reference-এর সঙ্গে যাচাই করেনি। EC2 API-র একটা `DryRun` parameter আছে। এটা যাচাই করে action-টার জন্য আপনার প্রয়োজনীয় permission আছে কি না, request আসলে না করেই <Cite n={14} />। এর জন্য account লাগে, তাই টিউটোরিয়াল এটা চালায়নি।

**৪. পাশাপাশি পড়ুন: একটা VPC-র পরিকল্পনা ও তৈরি।** এগুলো AWS-এর নিজের page। টিউটোরিয়াল এগুলো চালায়নি। **খরচের সতর্কতা।** একটা VPC ব্যবহারের জন্য কোনো বাড়তি খরচ নেই। তবে কিছু VPC উপাদানের জন্য খরচ আছে, যেমন NAT gateway, IP Address Manager, traffic mirroring, Reachability Analyzer আর Network Access Analyzer <Cite n={1} />। আপনি AWS Free Tier-এ EC2 service ব্যবহার না করলে public IPv4 address-এর জন্য খরচ হয় <Cite n={1} />।

1. আপনার IP address range ঠিক করুন। নিশ্চিত করুন, আপনার VPC-গুলোর range আপনার নিজের network-এর range-এর সঙ্গে overlap করে না <Cite n={3} />।
2. আপনার Availability Zone বেছে নিন। production environment-এর জন্য AWS অন্তত দুটো Availability Zone-এর সুপারিশ করে <Cite n={3} />। development বা test environment-এর জন্য আপনি শুধু একটা Availability Zone-এ resource চালিয়ে টাকা বাঁচাতে পারেন <Cite n={3} />।
3. আপনার internet connectivity-র পরিকল্পনা করুন। একটা private subnet-এর instance যেন internet-এ পৌঁছায় কিন্তু অযাচিত inbound সংযোগ না আসে, সে জন্য প্রতিটা সক্রিয় Availability Zone-এ একটা public NAT gateway যোগ করুন, আর route table হালনাগাদ করুন <Cite n={3} />।
4. console-এ VPC dashboard-এ Create VPC বেছে নিন, আর Resources to create-এর জন্য VPC and more বেছে নিন <Cite n={26} />। একটা VPC-র একটা IPv4 address range থাকতেই হবে <Cite n={26} />।
5. NAT gateway option ঐচ্ছিক। page বলে, NAT gateway-এর সঙ্গে একটা খরচ যুক্ত আছে <Cite n={26} />।

**৫. পাশাপাশি পড়ুন: একটা Application Load Balancer তৈরি।** এটা AWS-এর নিজের page। টিউটোরিয়াল এটা চালায়নি। **খরচের সতর্কতা।** একটা Application Load Balancer যতক্ষণ চলে, প্রতিটা ঘণ্টা বা আংশিক ঘণ্টার জন্য আপনার খরচ হয়। প্রতিটা আংশিক ঘণ্টা পুরো এক ঘণ্টা হিসেবে বিল হয় <Cite n={30} />। page এই পূর্বশর্তগুলো বলে:

1. আপনার application কোন Availability Zone আর IP address type সমর্থন করবে তা ঠিক করুন <Cite n={17} />।
2. target instance-এর security group যেন listener port-এ client IP address থেকে traffic অনুমতি দেয়, নিশ্চিত করুন, যদি target instance ID দিয়ে নির্দিষ্ট করা হয় <Cite n={17} />।
3. নিশ্চিত করুন, সেগুলো health check port-এ load balancer থেকে আসা traffic-ও অনুমতি দেয় <Cite n={17} />।

একটা Application Load Balancer তৈরির সময় আপনি load balancer, অন্তত একটা listener আর অন্তত একটা target group তৈরি করেন <Cite n={17} />। এটা পরীক্ষা করতে যাচাই করুন যে আপনার EC2 instance প্রাথমিক health check পাস করে, তারপর দেখুন load balancer আপনার EC2 instance-এ traffic পাঠাচ্ছে কি না <Cite n={17} />। page load balancer মুছে ফেলার ধাপগুলোর link দেয় <Cite n={17} />।

**৬. পাশাপাশি পড়ুন: একটা CloudFront standard distribution।** এটা AWS-এর নিজের টিউটোরিয়াল। টিউটোরিয়াল এটা চালায়নি। **খরচের সতর্কতা।** আপনি distribution আর S3 bucket শুধু শেখার অনুশীলনের জন্য বানালে সেগুলো মুছে ফেলুন, যাতে আর খরচ না জমে <Cite n={25} />। আগে distribution মুছুন <Cite n={25} />।

1. ধাপগুলো একটা standard distribution দাঁড় করায় <Cite n={25} />। টিউটোরিয়ালের জন্য আপনি একটা S3 bucket বানান, নমুনা hello world file-সহ, যা দিয়ে একটা সাধারণ webpage বানাবেন <Cite n={25} />।
2. distribution আপনার S3 origin-এ authenticated request পাঠাতে origin access control (OAC) ব্যবহার করে <Cite n={25} />।
3. Create distribution বেছে নিন। CloudFront আপনার জন্য S3 bucket policy হালনাগাদ করে <Cite n={25} />।
4. আপনার distribution-এর deploy শেষ হলে Last modified field Deploying থেকে একটা তারিখ ও সময়ে বদলে যায় <Cite n={25} />।
5. distribution আপনার object-গুলো CloudFront edge location-এ default ২৪ ঘণ্টা রাখে। সর্বনিম্ন মেয়াদ ০ সেকেন্ড <Cite n={25} />।

- **DNS routing test।** একটা weighted policy একাধিক resource-এ আপনার নির্দিষ্ট করা অনুপাতে traffic route করে <Cite n={20} />। একটা multivalue answer policy সর্বোচ্চ আটটা সুস্থ record দিয়ে উত্তর দেয়, যা এলোমেলোভাবে বাছা <Cite n={20} />। Route 53 internet traffic অসুস্থ resource থেকে সরিয়ে নিতে পারে <Cite n={19} />।
- **cache test।** একটা object cache-এ না থাকলে CloudFront request-টা origin-এ forward করে, আর পরের বারের জন্য object-টা cache-এ যোগ করে <Cite n={22} />। একটা file-এর মেয়াদ শেষ হলে CloudFront origin-এ request forward করে যাচাই করে যে cache-এ সর্বশেষ version আছে কি না <Cite n={23} />। origin 304 Not Modified বা 200 OK ফেরত দেয় <Cite n={23} />। error, যেমন 404 Not Found, কিছু সময় cache-এ থাকে <Cite n={23} />।
- **cache invalidation না file versioning।** আপনি একটা file invalidate করলে user পুরোনো version-ই দেখতে থাকতে পারে, যতক্ষণ না সেই cache থেকে তার মেয়াদ শেষ হয় <Cite n={24} />। versioning কম খরচের, কারণ file invalidate করার জন্য আপনাকে দাম দিতে হয় না <Cite n={24} />।

## Common mistakes

<Voices>
<Technical>

- **Thinking an internet gateway is enough.** Attaching an internet gateway to a VPC does not automatically make your instances accessible from the internet <Cite n={3} />.
- **A nondefault subnet without a public address.** By default, an instance in a nondefault subnet has a private IPv4 address but no public IPv4 address <Cite n={2} />. Such instances can communicate with each other, but can't access the internet <Cite n={2} />.
- **Opening SSH or RDP to everyone.** If you specify 0.0.0.0/0 (IPv4) and ::/ (IPv6), anyone can access your instances from any IP address using the specified protocol <Cite n={9} />.
- **Expecting a network ACL to work like a security group.** Network ACLs are stateless <Cite n={10} />. Security groups are stateful <Cite n={9} />.
- **Expecting a security group to filter everything.** Security groups do not filter traffic to and from Amazon DNS, Amazon DHCP, and EC2 instance metadata, among others <Cite n={9} />. Network ACLs can't block traffic to the Instance Metadata Service (IMDS) <Cite n={10} />.
- **Overlapping address ranges.** The CIDR blocks of the subnets of a VPC cannot overlap <Cite n={5} />. VPCs that need connectivity must have no overlapping IP addresses <Cite n={3} />.
- **Using a host address as a CIDR block.** Python's `ip_network` raises a ValueError if the network has host bits set <Cite n={27} />. AWS modifies the CIDR block of a subnet to its canonical form instead <Cite n={5} />.
- **Counting every subnet address as usable.** The first four IP addresses and the last IP address in each subnet CIDR block are not available for your use <Cite n={5} />.
- **Expecting inbound connections through a NAT gateway.** External services can't initiate a connection with the instances behind a NAT gateway <Cite n={8} />.
- **Forgetting what costs money.** There is a cost associated with NAT gateways <Cite n={26} />. You are charged for each hour or partial hour that an Application Load Balancer is running <Cite n={30} />.
- **Reading "all targets unhealthy" as "no traffic".** If all targets fail health checks at the same time in all enabled Availability Zones, the load balancer fails open <Cite n={18} />.
- **Blocking the health check.** The security groups for target instances must allow traffic from the load balancer on the health check port <Cite n={17} />.
- **Expecting one fixed DNS answer.** A multivalue answer policy responds with up to eight healthy records selected at random <Cite n={20} />. A weighted policy routes traffic in proportions that you specify <Cite n={20} />.
- **Testing a changed file before the cache expires.** Typically, CloudFront serves a file from an edge location until the cache duration that you specified passes <Cite n={23} />.
- **Invalidating when versioning would do.** If you want to update your files frequently, AWS recommends that you primarily use file versioning <Cite n={24} />.
- **Deleting in the wrong order.** AWS says to delete the distribution first <Cite n={25} />.

</Technical>

## What a tester can check

<Voices>
<Technical>

<Callout type="tip" title="Tutorial advice">
This list is the tutorial's own advice for a tester who works with AWS networking and delivery.

- Draw the path of a failing request hop by hop before you change a rule: client, DNS, cache, load balancer, security group, network ACL, route table, and target.
- Change one thing at a time, and wait for it to take effect before you test again.
- When a test cannot connect, check the route table, the public address, the security group, and the network ACL.
- Keep the CIDR ranges of your test VPCs in one file, and check that they do not overlap before you create anything.
- Test a security group rule with an address inside its range and an address just outside it.
- For a load balancer, test a healthy target, an unhealthy target, and the case where every target is unhealthy.
- For a weighted or multivalue DNS answer, repeat the query many times and look at the spread, not at one answer.
- For a cache, ask for the same object twice and compare the responses. Then change the file at the origin and ask again.
- Use a new file name instead of an invalidation when a test changes a file often.
- Delete NAT gateways, load balancers, and distributions on the day that you create them for a test.
- Do not use `0.0.0.0/0` for SSH or RDP in a shared environment, even for a short test.
- Print a CLI template before a real call, and read its parameter names.

## Key words

| Term | Meaning |
|---|---|
| VPC | A virtual network dedicated to your AWS account |
| Subnet | A range of IP addresses in your VPC; it must reside in a single Availability Zone |
| CIDR block | The IP addresses of a VPC, written in Classless Inter-Domain Routing (CIDR) notation; the allowed block size of a VPC is between a /16 and a /28 netmask |
| Route table | A set of rules, called routes, that determine where network traffic from your subnet or gateway is directed |
| Internet gateway | A gateway that connects your VPC to the internet |
| Public subnet | A subnet that is associated with a route table that has a route to an internet gateway |
| NAT gateway | Lets instances in a private subnet connect to services outside your VPC, but external services can't initiate a connection with those instances |
| Security group | Controls the traffic that is allowed to reach and leave the resources that it is associated with; it is stateful |
| Network ACL | Allows or denies specific inbound or outbound traffic at the subnet level; it is stateless |
| Flow logs | Capture information about the IP traffic going to and from network interfaces in your VPC |
| Reachability Analyzer | A configuration analysis tool for connectivity testing between a source resource and a destination resource in your VPCs |
| Listener | Checks for connection requests from clients, using the protocol and port that you configure |
| Target group | Routes requests to one or more registered targets, such as EC2 instances |
| Health check | A request that a load balancer sends periodically to a registered target, to test its status |
| Fail open | When every target is unhealthy, the load balancer routes requests to all of them |
| Route 53 | A highly available and scalable Domain Name System (DNS) web service |
| Routing policy | You choose it when you create a record; it determines how Route 53 responds to queries |
| CloudFront | A web service that speeds up distribution of static and dynamic web content through edge locations |
| TTL | Time to Live; if you opt out of a cache policy, the default TTL is 24 hours |
| Invalidation | Removing a file from CloudFront edge caches before it expires |
