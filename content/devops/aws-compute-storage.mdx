# AWS Compute and Storage

This page is about three AWS services that a tester meets early: Amazon EC2, Amazon EBS, and Amazon S3. It covers which instance states are billed, what survives a stop and a terminate, and how S3 versioning, lifecycle rules, Block Public Access, and presigned URLs behave. The practice run uses the AWS CLI and needs no AWS account. It comes after [Cloud Concepts](/devops/cloud-concepts/) and before [AWS Networking and Delivery](/devops/aws-networking/).

## What it is

<Voices>
<Technical>

**Amazon EC2.** Amazon Elastic Compute Cloud (Amazon EC2) provides on-demand, scalable computing capacity in the AWS Cloud <Cite n={1} />. An EC2 instance is a virtual server in the AWS Cloud <Cite n={1} />. The instance type that you specify determines the hardware available to your instance <Cite n={1} />. Each instance type offers a different balance of compute, memory, network, and storage resources <Cite n={1} />.

Amazon EC2 provides these high-level features <Cite n={1} />:

- **Instances.** Virtual servers <Cite n={1} />.
- **Amazon Machine Images (AMIs).** Preconfigured templates for your instances that package the components you need for your server, including the operating system and additional software <Cite n={1} />.
- **Instance types.** Various configurations of CPU, memory, storage, networking capacity, and graphics hardware for your instances <Cite n={1} />.
- **Amazon EBS volumes.** Persistent storage volumes for your data <Cite n={1} />.
- **Instance store volumes.** Storage volumes for temporary data that is deleted when you stop, hibernate, or terminate your instance <Cite n={1} />.
- **Key pairs.** Secure login information for your instances. AWS stores the public key and you store the private key in a secure place <Cite n={1} />.
- **Security groups.** A virtual firewall that allows you to specify the protocols, ports, and source IP ranges that can reach your instances <Cite n={1} />.

**Amazon EBS.** Amazon Elastic Block Store (Amazon EBS) provides scalable, high-performance block storage resources that can be used with EC2 instances <Cite n={17} />. After you attach a volume to an instance, you can use it in the same way you would use a local hard drive attached to a computer <Cite n={17} />. Snapshots are point-in-time backups of EBS volumes that persist independently from the volume itself <Cite n={17} />.

**Amazon S3.** Amazon Simple Storage Service (Amazon S3) is an object storage service <Cite n={10} />. It stores data as objects, hierarchical data, or tabular data within buckets <Cite n={10} />. An object is a file and any metadata that describes the file. A bucket is a container for objects <Cite n={10} />. Each object has a key, which is the unique identifier for the object within the bucket <Cite n={10} />. By default, S3 buckets and the objects in them are private <Cite n={10} />.

## How it works

<Voices>
<Technical>

**Instance states and billing.** An EC2 instance transitions through different states from the moment you launch it through to its termination <Cite n={2} />. The states are:

- `pending`: the instance is preparing to enter the running state, and it is not billed <Cite n={2} />.
- `running`: the instance is running and ready for use, and it is billed <Cite n={2} />.
- `stopping`: the instance is preparing to be stopped, and it is not billed <Cite n={2} />. If you hibernate an instance, you're billed while it is in the stopping state <Cite n={2} />.
- `stopped`: the instance is shut down and cannot be used. It can be started at any time, and it is not billed <Cite n={2} />.
- `shutting-down`: the instance is preparing to be terminated, and it is not billed <Cite n={2} />.
- `terminated`: the instance has been permanently deleted and cannot be started. It is not billed <Cite n={2} />.

As soon as the instance is running, you're billed for each second, with a one-minute minimum, even if the instance remains idle and you don't connect to it <Cite n={2} />. Some AWS resources, such as EBS volumes and Elastic IP addresses, incur charges regardless of the instance's state <Cite n={2} />.

**Reboot, stop, hibernate, and terminate.** You can reboot, stop, hibernate, or terminate an instance, and each one keeps different things.

- Reboot. Rebooting an instance is equivalent to rebooting an operating system <Cite n={2} />. The instance remains on the same host computer. It maintains its public DNS name, private IP address, and any data on its instance store volumes <Cite n={2} />.
- Stop and start. When you stop and start your instance, you lose any data on the instance store volumes attached to the previous host computer <Cite n={2} />. The instance gets a new public IPv4 address, unless it has a secondary network interface or a secondary private IPv4 address that is associated with an Elastic IP address <Cite n={2} />.
- Hibernate. The operating system is signaled to perform hibernation (suspend-to-disk), which saves the contents from the instance memory (RAM) to your EBS root volume <Cite n={2} />.
- Terminate. You can't connect to or recover a terminated instance <Cite n={2} />. If you enable termination protection, you can't terminate the instance using the console, CLI, or API <Cite n={2} />.

The `DeleteOnTermination` attribute of an EBS volume controls whether the volume is deleted or preserved when you terminate the instance it is attached to. The default is to delete the root volume and preserve any other EBS volumes <Cite n={2} />. The table sums up the differences that AWS lists <Cite n={2} />:

| | Reboot | Stop and start | Hibernate | Terminate |
|---|---|---|---|---|
| Private IPv4 address | kept | kept | kept | none <Cite n={2} /> |
| Elastic IP address (IPv4) | stays associated | stays associated | stays associated | disassociated <Cite n={2} /> |
| Instance store volumes | data preserved | data erased | data erased | data erased <Cite n={2} /> |
| Root volume | preserved | preserved | preserved | deleted by default <Cite n={2} /> |
| RAM (contents of memory) | erased | erased | saved to a file on the root volume | erased <Cite n={2} /> |

**Buying EC2 capacity.** AWS lists these options to optimize your costs for EC2 <Cite n={4} />:

- On-Demand Instances: pay, by the second, for the instances that you launch <Cite n={4} />.
- Savings Plans: make a commitment to a consistent amount of usage, in USD per hour, for a term of 1 or 3 years <Cite n={4} />.
- Reserved Instances: make a commitment to a consistent instance configuration, including instance type and Region, for a term of 1 or 3 years <Cite n={4} />.
- Spot Instances: request unused EC2 instances, which can reduce your costs significantly <Cite n={4} />.
- Capacity Reservations: reserve capacity for your EC2 instances in a specific Availability Zone <Cite n={4} />.

A Spot Instance uses spare EC2 capacity that is available for less than the On-Demand price <Cite n={5} />. EC2 terminates, stops, or hibernates your Spot Instance when it needs the capacity back <Cite n={5} />. EC2 provides a Spot Instance interruption notice, which gives the instance a two-minute warning before it is interrupted <Cite n={5} />. Spot Instances are a cost-effective choice if you can be flexible about when your applications run and if your applications can be interrupted <Cite n={5} />. For an On-Demand Instance, if capacity is not available when you make a launch request, you get an insufficient capacity error (ICE) <Cite n={5} />.

**What you choose at launch: AMI and key pair.** An Amazon Machine Image (AMI) is an image that provides the software that is required to set up and boot an EC2 instance <Cite n={3} />. You must specify an AMI when you launch an instance <Cite n={3} />. The AMI must be compatible with the instance type that you chose <Cite n={3} />. An AMI is specific to Region, operating system, processor architecture, root volume type, and virtualization type <Cite n={3} />.

A key pair is a set of security credentials that you use to prove your identity when connecting to an EC2 instance <Cite n={8} />. Anyone who possesses your private key can connect to your instances that use the key pair <Cite n={8} />. Because EC2 doesn't keep a copy of your private key, there is no way to recover a private key if you lose it <Cite n={8} />.

**User data and instance metadata.** When you launch an EC2 instance, you can pass user data that performs automated configuration tasks or runs scripts after the instance starts <Cite n={6} />. User data is limited to 16 KB, in raw form, before it is base64-encoded <Cite n={6} />. By default, user data scripts and cloud-init directives run only during the boot cycle when you first launch an instance <Cite n={6} />. If you create an AMI from an instance, the instance user data is not included in the AMI <Cite n={6} />.

A running instance can read its instance metadata through the Instance Metadata Service (IMDS) <Cite n={7} />. By default, you can use either IMDSv1 or IMDSv2, or both <Cite n={7} />. You can configure the IMDS on each instance to only accept IMDSv2 calls, which will cause IMDSv1 calls to fail <Cite n={7} />. IMDSv2 uses session-oriented requests <Cite n={7} />. You create a session token that defines the session duration, a minimum of one second and a maximum of six hours <Cite n={7} />.

**EBS volumes and snapshots.** EBS provides multiple volume types that differ in performance characteristics and price <Cite n={19} />. SSD-backed volume types include General Purpose SSD and Provisioned IOPS SSD <Cite n={19} />. HDD volume types include Throughput Optimized HDD and Cold HDD <Cite n={19} />. SSD-backed volumes are optimized for transactional workloads <Cite n={19} />. HDD-backed volumes are optimized for large streaming workloads where the dominant performance attribute is throughput <Cite n={19} />.

Volume data is automatically replicated across multiple servers in an Availability Zone <Cite n={17} />. io2 Block Express volumes provide 99.999% durability. Other volume types provide 99.8% to 99.9% durability <Cite n={17} />. You can use Elastic Volumes operations to dynamically increase capacity or tune performance, with no downtime <Cite n={17} />.

A snapshot is an incremental backup, which means that AWS saves only the blocks on the volume that have changed since the most recent snapshot <Cite n={18} />. AWS does not automatically back up the data stored on your EBS volumes <Cite n={18} />. It is your responsibility to create EBS snapshots on a regular basis, or to set up automatic snapshot creation <Cite n={18} />.

**S3 storage classes, versioning, and lifecycle.** Each object in S3 has a storage class associated with it <Cite n={15} />. By default, objects are stored in the S3 Standard storage class <Cite n={15} />. All of these storage classes offer high durability <Cite n={15} />.

Versioning in S3 is a means of keeping multiple variants of an object in the same bucket <Cite n={11} />. By default, S3 Versioning is disabled on buckets, and you must explicitly enable it <Cite n={11} />. If you delete an object, S3 inserts a delete marker instead of removing the object permanently <Cite n={11} />. If you overwrite an object, it results in a new object version in the bucket <Cite n={11} />. After you version-enable a bucket, it can never return to an unversioned state, but you can suspend versioning on that bucket <Cite n={11} />. Normal S3 rates apply for every version of an object that is stored and transferred <Cite n={11} />. Each version of an object is the entire object, not just a diff from the previous version <Cite n={11} />.

An S3 Lifecycle configuration is a set of rules that define actions that S3 applies to a group of objects <Cite n={12} />. Transition actions define when objects transition to another storage class. Expiration actions define when objects expire <Cite n={12} />. S3 deletes expired objects on your behalf <Cite n={12} />. When you add a Lifecycle configuration to a bucket, the rules apply to both existing objects and objects that you add later <Cite n={12} />. For general purpose buckets, you can't use a bucket policy to prevent deletions or transitions by an S3 Lifecycle rule <Cite n={12} />. To keep the permanent delete behavior of an expiration rule after you enable versioning, add a noncurrent expiration configuration <Cite n={11} />.

**S3 access: Block Public Access and presigned URLs.** By default, new buckets, access points, and objects don't allow public access <Cite n={13} />. However, users can modify bucket policies, access point policies, or object permissions to allow public access <Cite n={13} />. S3 Block Public Access settings override these policies and permissions so that you can limit public access to these resources <Cite n={13} />. Block Public Access provides four settings: `BlockPublicAcls`, `IgnorePublicAcls`, `BlockPublicPolicy`, and `RestrictPublicBuckets` <Cite n={13} />. AWS recommends that you turn on all four settings for your account <Cite n={13} />. Block public access settings don't alter existing policies or ACLs. So removing a setting makes a bucket or object with a public policy or ACL publicly accessible again <Cite n={13} />. S3 doesn't support block public access settings on a per-object basis <Cite n={13} />.

You can use presigned URLs to grant time-limited access to objects in S3 without updating your bucket policy <Cite n={14} />. The credentials that the URL uses are those of the IAM principal who generated it <Cite n={14} />. You can use the presigned URL multiple times, up to the expiration date and time <Cite n={14} />. With the S3 console, the expiration time can be set between 1 minute and 12 hours. With the AWS CLI or AWS SDKs, it can be set as high as 7 days <Cite n={14} />. S3 checks the expiration date and time of a signed URL at the time of the HTTP request <Cite n={14} />. If the connection drops and the client tries to restart the download after the expiration time passes, the download fails <Cite n={14} />. In general, a presigned URL expires when the credential that created it is revoked, deleted, or deactivated, even if the URL was created with a later expiration time <Cite n={14} />. Presigned URLs are bearer tokens that grant access to those who possess them <Cite n={14} />.

**S3 consistency.** S3 provides strong read-after-write consistency for PUT and DELETE requests of objects in all AWS Regions <Cite n={10} />. After a successful PUT, a read (GET or LIST request) returns the data written by the PUT request <Cite n={10} />. Bucket configurations have an eventual consistency model <Cite n={10} />. If you delete a bucket and immediately list all buckets, the deleted bucket might still appear in the list <Cite n={10} />. AWS recommends that you wait for 15 minutes after enabling versioning before issuing write operations on objects in the bucket <Cite n={10} />. S3 does not support object locking for concurrent writers <Cite n={10} />. If two PUT requests are simultaneously made to the same key, the request with the latest timestamp wins <Cite n={10} />.

</Technical>

- `pending`: the instance is preparing to enter the running state, and it is not billed <Cite n={2} />.

- `shutting-down`: the instance is preparing to be terminated, and it is not billed <Cite n={2} />.
- `terminated`: the instance has been permanently deleted and cannot be started. It is not billed <Cite n={2} />.

As soon as the instance is running, you're billed for each second, with a one-minute minimum, even if the instance remains idle and you don't connect to it <Cite n={2} />. Some AWS resources, such as EBS volumes and Elastic IP addresses, cost money regardless of the instance's state <Cite n={2} />.

**Reboot, stop, hibernate, and terminate.** You can reboot, stop, hibernate, or terminate an instance, and each one keeps different things.

- Reboot. Rebooting an instance is equivalent to rebooting an operating system <Cite n={2} />. The instance remains on the same host computer. It maintains its public DNS name, private IP address, and any data on its instance store volumes <Cite n={2} />.
- Stop and start. When you stop and start your instance, you lose any data on the instance store volumes attached to the previous host computer <Cite n={2} />. The instance gets a new public IPv4 address, unless it has a secondary network interface or a secondary private IPv4 address that is associated with an Elastic IP address <Cite n={2} />.
- Hibernate. The operating system is signaled to perform hibernation (suspend-to-disk). That saves the contents of the instance memory (RAM) to your EBS root volume <Cite n={2} />.
- Terminate. You can't connect to or recover a terminated instance <Cite n={2} />. If you enable termination protection, you can't terminate the instance using the console, CLI, or API <Cite n={2} />.

The `DeleteOnTermination` attribute of an EBS volume controls whether the volume is deleted or kept when you terminate the instance it is attached to. The default is to delete the root volume and keep any other EBS volumes <Cite n={2} />. The table sums up the differences that AWS lists <Cite n={2} />:

| | Reboot | Stop and start | Hibernate | Terminate |
|---|---|---|---|---|
| Private IPv4 address | kept | kept | kept | none <Cite n={2} /> |
| Elastic IP address (IPv4) | stays associated | stays associated | stays associated | disassociated <Cite n={2} /> |
| Instance store volumes | data preserved | data erased | data erased | data erased <Cite n={2} /> |
| Root volume | preserved | preserved | preserved | deleted by default <Cite n={2} /> |
| RAM (contents of memory) | erased | erased | saved to a file on the root volume | erased <Cite n={2} /> |

**Buying EC2 capacity.** AWS lists these options to optimize your costs for EC2 <Cite n={4} />:

- On-Demand Instances: pay, by the second, for the instances that you launch <Cite n={4} />.
- Savings Plans: make a commitment to a consistent amount of usage, in USD per hour, for a term of 1 or 3 years <Cite n={4} />.
- Reserved Instances: make a commitment to a consistent instance configuration, including instance type and Region, for a term of 1 or 3 years <Cite n={4} />.
- Spot Instances: request unused EC2 instances, which can reduce your costs significantly <Cite n={4} />.
- Capacity Reservations: reserve capacity for your EC2 instances in a specific Availability Zone <Cite n={4} />.

A Spot Instance uses spare EC2 capacity that is available for less than the On-Demand price <Cite n={5} />. EC2 terminates, stops, or hibernates your Spot Instance when it needs the capacity back <Cite n={5} />. EC2 gives the instance a two-minute warning before it is interrupted. This is the Spot Instance interruption notice <Cite n={5} />. Spot Instances are a cost-effective choice if you can be flexible about when your applications run and if your applications can be interrupted <Cite n={5} />. For an On-Demand Instance, if capacity is not available when you make a launch request, you get an insufficient capacity error (ICE) <Cite n={5} />.

**What you choose at launch: AMI and key pair.** An Amazon Machine Image (AMI) is an image that provides the software that is required to set up and boot an EC2 instance <Cite n={3} />. You must specify an AMI when you launch an instance <Cite n={3} />. The AMI must be compatible with the instance type that you chose <Cite n={3} />. An AMI is specific to Region, operating system, processor architecture, root volume type, and virtualization type <Cite n={3} />.

A key pair is a set of security credentials that you use to prove your identity when connecting to an EC2 instance <Cite n={8} />. Anyone who possesses your private key can connect to your instances that use the key pair <Cite n={8} />. EC2 doesn't keep a copy of your private key. So there is no way to recover a private key if you lose it <Cite n={8} />.

**User data and instance metadata.** When you launch an EC2 instance, you can pass user data that performs automated configuration tasks or runs scripts after the instance starts <Cite n={6} />. User data is limited to 16 KB, in raw form, before it is base64-encoded <Cite n={6} />. By default, user data scripts and cloud-init directives run only during the boot cycle when you first launch an instance <Cite n={6} />. If you create an AMI from an instance, the instance user data is not included in the AMI <Cite n={6} />.

A running instance can read its instance metadata through the Instance Metadata Service (IMDS) <Cite n={7} />. By default, you can use either IMDSv1 or IMDSv2, or both <Cite n={7} />. You can configure the IMDS on each instance to only accept IMDSv2 calls, which will cause IMDSv1 calls to fail <Cite n={7} />. IMDSv2 uses session-oriented requests <Cite n={7} />. You create a session token that defines the session duration, a minimum of one second and a maximum of six hours <Cite n={7} />.

**EBS volumes and snapshots.** EBS provides multiple volume types that differ in performance characteristics and price <Cite n={19} />. SSD-backed volume types include General Purpose SSD and Provisioned IOPS SSD <Cite n={19} />. HDD volume types include Throughput Optimized HDD and Cold HDD <Cite n={19} />. SSD-backed volumes are optimized for transactional workloads <Cite n={19} />. HDD-backed volumes are optimized for large streaming workloads where the dominant performance attribute is throughput <Cite n={19} />.

Volume data is automatically replicated across multiple servers in an Availability Zone <Cite n={17} />. io2 Block Express volumes provide 99.999% durability. Other volume types provide 99.8% to 99.9% durability <Cite n={17} />. You can use Elastic Volumes operations to dynamically increase capacity or tune performance, with no downtime <Cite n={17} />.

A snapshot is an incremental backup, which means that AWS saves only the blocks on the volume that have changed since the most recent snapshot <Cite n={18} />. AWS does not automatically back up the data stored on your EBS volumes <Cite n={18} />. It is your responsibility to create EBS snapshots on a regular basis, or to set up automatic snapshot creation <Cite n={18} />.

**S3 storage classes, versioning, and lifecycle.** Each object in S3 has a storage class associated with it <Cite n={15} />. By default, objects are stored in the S3 Standard storage class <Cite n={15} />. All of these storage classes offer high durability <Cite n={15} />.

Versioning in S3 is a means of keeping multiple variants of an object in the same bucket <Cite n={11} />. By default, S3 Versioning is disabled on buckets, and you must explicitly enable it <Cite n={11} />. If you delete an object, S3 inserts a delete marker instead of removing the object permanently <Cite n={11} />. If you overwrite an object, it results in a new object version in the bucket <Cite n={11} />. After you version-enable a bucket, it can never return to an unversioned state, but you can suspend versioning on that bucket <Cite n={11} />. Normal S3 rates apply for every version of an object that is stored and transferred <Cite n={11} />. Each version of an object is the entire object, not just a diff from the previous version <Cite n={11} />.

An S3 Lifecycle configuration is a set of rules that define actions that S3 applies to a group of objects <Cite n={12} />. Transition actions define when objects transition to another storage class. Expiration actions define when objects expire <Cite n={12} />. S3 deletes expired objects on your behalf <Cite n={12} />. When you add a Lifecycle configuration to a bucket, the rules apply to both existing objects and objects that you add later <Cite n={12} />. For general purpose buckets, you can't use a bucket policy to prevent deletions or transitions by an S3 Lifecycle rule <Cite n={12} />. To keep the permanent delete behavior of an expiration rule after you enable versioning, add a noncurrent expiration configuration <Cite n={11} />.

**S3 access: Block Public Access and presigned URLs.** By default, new buckets, access points, and objects don't allow public access <Cite n={13} />. However, users can modify bucket policies, access point policies, or object permissions to allow public access <Cite n={13} />. S3 Block Public Access settings override these policies and permissions so that you can limit public access to these resources <Cite n={13} />. Block Public Access provides four settings: `BlockPublicAcls`, `IgnorePublicAcls`, `BlockPublicPolicy`, and `RestrictPublicBuckets` <Cite n={13} />. AWS recommends that you turn on all four settings for your account <Cite n={13} />. Block public access settings don't alter existing policies or ACLs. So removing a setting makes a bucket or object with a public policy or ACL publicly accessible again <Cite n={13} />. S3 doesn't support block public access settings on a per-object basis <Cite n={13} />.

You can use presigned URLs to grant time-limited access to objects in S3 without updating your bucket policy <Cite n={14} />. The credentials that the URL uses are those of the IAM principal who generated it <Cite n={14} />. You can use the presigned URL multiple times, up to the expiration date and time <Cite n={14} />. With the S3 console, the expiration time can be set between 1 minute and 12 hours. With the AWS CLI or AWS SDKs, it can be set as high as 7 days <Cite n={14} />. S3 checks the expiration date and time of a signed URL at the time of the HTTP request <Cite n={14} />. If the connection drops and the client tries to restart the download after the expiration time passes, the download fails <Cite n={14} />. In general, a presigned URL expires when the credential that created it is revoked, deleted, or deactivated, even if the URL was created with a later expiration time <Cite n={14} />. Presigned URLs are bearer tokens that grant access to those who possess them <Cite n={14} />.

**S3 consistency.** S3 provides strong read-after-write consistency for PUT and DELETE requests of objects in all AWS Regions <Cite n={10} />. After a successful PUT, a read (GET or LIST request) returns the data written by the PUT request <Cite n={10} />. Bucket configurations have an eventual consistency model <Cite n={10} />. If you delete a bucket and immediately list all buckets, the deleted bucket might still appear in the list <Cite n={10} />. AWS recommends that you wait for 15 minutes after enabling versioning before issuing write operations on objects in the bucket <Cite n={10} />. S3 does not support object locking for concurrent writers <Cite n={10} />. If two PUT requests are simultaneously made to the same key, the request with the latest timestamp wins <Cite n={10} />.

- On-Demand Instances: আপনি যে instance চালু করেন, তার জন্য সেকেন্ড ধরে দাম দিন <Cite n={4} />।
- Savings Plans: ১ বা ৩ বছরের মেয়াদে ঘণ্টায় USD হিসাবে একটা স্থির পরিমাণ ব্যবহারের প্রতিশ্রুতি দিন <Cite n={4} />।

**User data আর instance metadata।** একটা EC2 instance চালু করার সময় আপনি user data পাঠাতে পারেন, যা automated configuration-এর কাজ করে বা instance চালু হওয়ার পর script চালায় <Cite n={6} />। User data raw অবস্থায়, base64-encode হওয়ার আগে, ১৬ KB পর্যন্ত সীমিত <Cite n={6} />। by default, user data script আর cloud-init directive শুধু সেই boot cycle-এ চলে, যখন আপনি প্রথম instance চালু করেন <Cite n={6} />। আপনি একটা instance থেকে AMI বানালে ওই instance-এর user data AMI-তে থাকে না <Cite n={6} />।

একটা চলমান instance Instance Metadata Service (IMDS) দিয়ে নিজের instance metadata পড়তে পারে <Cite n={7} />। by default আপনি IMDSv1 বা IMDSv2 ব্যবহার করতে পারেন, বা দুটোই <Cite n={7} />। আপনি প্রতিটা instance-এ IMDS এমনভাবে configure করতে পারেন, যাতে সে শুধু IMDSv2 call নেয়, ফলে IMDSv1 call ব্যর্থ হবে <Cite n={7} />। IMDSv2 session-oriented request ব্যবহার করে <Cite n={7} />। আপনি একটা session token বানান, যা session-এর মেয়াদ ঠিক করে, কমপক্ষে এক সেকেন্ড আর সর্বোচ্চ ছয় ঘণ্টা <Cite n={7} />।

**EBS volume আর snapshot।** EBS একাধিক volume type দেয়, যেগুলোর performance-এর বৈশিষ্ট্য আর দাম আলাদা <Cite n={19} />। SSD-backed volume type-এর মধ্যে আছে General Purpose SSD আর Provisioned IOPS SSD <Cite n={19} />। HDD volume type-এর মধ্যে আছে Throughput Optimized HDD আর Cold HDD <Cite n={19} />। SSD-backed volume transactional workload-এর জন্য optimize করা <Cite n={19} />। HDD-backed volume বড় streaming workload-এর জন্য optimize করা, যেখানে throughput-ই প্রধান performance বৈশিষ্ট্য <Cite n={19} />।

volume-এর data একটা Availability Zone-এর একাধিক server-এ স্বয়ংক্রিয়ভাবে replicate হয় <Cite n={17} />। io2 Block Express volume ৯৯.৯৯৯% durability দেয়। অন্য volume type ৯৯.৮% থেকে ৯৯.৯% durability দেয় <Cite n={17} />। আপনি Elastic Volumes operation দিয়ে কোনো downtime ছাড়াই গতিশীলভাবে capacity বাড়াতে বা performance tune করতে পারেন <Cite n={17} />।

snapshot হলো একটা incremental backup, মানে AWS শুধু সেই block-গুলো সেভ করে, যেগুলো সবচেয়ে সাম্প্রতিক snapshot-এর পর volume-এ বদলেছে <Cite n={18} />। AWS আপনার EBS volume-এর data স্বয়ংক্রিয়ভাবে backup করে না <Cite n={18} />। নিয়মিত EBS snapshot বানানো বা স্বয়ংক্রিয় snapshot তৈরির ব্যবস্থা করার দায়িত্ব আপনার <Cite n={18} />।

**S3 storage class, versioning আর lifecycle।** S3-এর প্রতিটা object-এর সঙ্গে একটা storage class যুক্ত থাকে <Cite n={15} />। by default object S3 Standard storage class-এ রাখা হয় <Cite n={15} />। এই সব storage class উচ্চ durability দেয় <Cite n={15} />।

S3-এ versioning হলো একই bucket-এ একটা object-এর একাধিক রূপ রাখার উপায় <Cite n={11} />। by default bucket-এ S3 Versioning বন্ধ থাকে, আর আপনাকে স্পষ্টভাবে তা চালু করতে হয় <Cite n={11} />। আপনি একটা object মুছলে S3 object-টা স্থায়ীভাবে সরানোর বদলে একটা delete marker বসায় <Cite n={11} />। আপনি একটা object overwrite করলে bucket-এ একটা নতুন object version তৈরি হয় <Cite n={11} />। একটা bucket version-enable করার পর সেটা আর কখনো unversioned অবস্থায় ফিরতে পারে না, তবে আপনি ওই bucket-এ versioning suspend করতে পারেন <Cite n={11} />। একটা object-এর প্রতিটা version, যা রাখা ও স্থানান্তরিত হয়, তার জন্য স্বাভাবিক S3 হার প্রযোজ্য <Cite n={11} />। একটা object-এর প্রতিটা version পুরো object, আগের version থেকে শুধু diff নয় <Cite n={11} />।

S3 Lifecycle configuration হলো একসেট নিয়ম, যা ঠিক করে S3 একদল object-এর ওপর কোন action নেবে <Cite n={12} />। Transition action ঠিক করে কখন object অন্য storage class-এ যাবে। Expiration action ঠিক করে কখন object-এর মেয়াদ শেষ হবে <Cite n={12} />। S3 আপনার পক্ষ থেকে মেয়াদ-শেষ object মুছে দেয় <Cite n={12} />। একটা bucket-এ Lifecycle configuration যোগ করলে নিয়মগুলো বিদ্যমান object আর পরে যোগ করা object, দুটোর ওপরই প্রযোজ্য হয় <Cite n={12} />। general purpose bucket-এর ক্ষেত্রে আপনি bucket policy দিয়ে একটা S3 Lifecycle rule-এর মুছে ফেলা বা transition আটকাতে পারেন না <Cite n={12} />। versioning চালু করার পরও একটা expiration rule-এর স্থায়ী মুছে ফেলার আচরণ ধরে রাখতে একটা noncurrent expiration configuration যোগ করুন <Cite n={11} />।

**S3 access: Block Public Access আর presigned URL।** by default নতুন bucket, access point আর object public access দেয় না <Cite n={13} />। তবে user bucket policy, access point policy বা object permission বদলে public access দিতে পারে <Cite n={13} />। S3 Block Public Access setting এই policy আর permission-কে override করে, যাতে আপনি এই resource-গুলোতে public access সীমিত করতে পারেন <Cite n={13} />। Block Public Access চারটা setting দেয়: `BlockPublicAcls`, `IgnorePublicAcls`, `BlockPublicPolicy` আর `RestrictPublicBuckets` <Cite n={13} />। AWS সুপারিশ করে, আপনার account-এর জন্য চারটা setting-ই চালু করুন <Cite n={13} />। block public access setting বিদ্যমান policy বা ACL বদলায় না। তাই একটা setting সরালে public policy বা ACL থাকা bucket বা object আবার public হয়ে যায় <Cite n={13} />। S3 per-object ভিত্তিতে block public access setting সমর্থন করে না <Cite n={13} />।

আপনি presigned URL দিয়ে bucket policy না বদলেই S3-এর object-এ সময়-সীমিত access দিতে পারেন <Cite n={14} />। URL-টা যে credential ব্যবহার করে, তা যে IAM principal URL বানিয়েছে তার <Cite n={14} />। আপনি একই presigned URL একাধিকবার ব্যবহার করতে পারেন, মেয়াদের তারিখ ও সময় পর্যন্ত <Cite n={14} />। S3 console দিয়ে মেয়াদ ১ মিনিট থেকে ১২ ঘণ্টার মধ্যে ঠিক করা যায়। AWS CLI বা AWS SDK দিয়ে তা ৭ দিন পর্যন্ত ঠিক করা যায় <Cite n={14} />। S3 একটা signed URL-এর মেয়াদের তারিখ ও সময় যাচাই করে HTTP request-এর সময় <Cite n={14} />। সংযোগ কেটে গেলে আর মেয়াদ পেরোনোর পর client download আবার শুরু করার চেষ্টা করলে download ব্যর্থ হয় <Cite n={14} />। সাধারণভাবে একটা presigned URL-এর মেয়াদ শেষ হয়, যে credential দিয়ে সেটা বানানো তা revoke, delete বা deactivate হলে, URL-টা পরের কোনো মেয়াদ দিয়ে বানানো হলেও <Cite n={14} />। presigned URL হলো bearer token, যা যার কাছে আছে তাকে access দেয় <Cite n={14} />।

**S3 consistency।** S3 সব AWS Region-এ object-এর PUT আর DELETE request-এর জন্য strong read-after-write consistency দেয় <Cite n={10} />। একটা সফল PUT-এর পর একটা read (GET বা LIST request) PUT request-এ লেখা data ফেরত দেয় <Cite n={10} />। Bucket configuration-এর eventual consistency model আছে <Cite n={10} />। আপনি একটা bucket মুছে সঙ্গে সঙ্গে সব bucket-এর তালিকা চাইলে মুছে ফেলা bucket-টা তখনো তালিকায় দেখা যেতে পারে <Cite n={10} />। AWS সুপারিশ করে, versioning চালু করার পর bucket-এর object-এ write operation চালানোর আগে ১৫ মিনিট অপেক্ষা করুন <Cite n={10} />। S3 একসঙ্গে লেখা writer-দের জন্য object locking সমর্থন করে না <Cite n={10} />। একই key-তে দুটো PUT request একসঙ্গে করা হলে latest timestamp-ওয়ালা request জেতে <Cite n={10} />।

## Common mistakes

<Voices>
<Technical>

- **Leaving an instance running.** A running instance is billed for each second, even if it remains idle <Cite n={2} />. In AWS's tutorial, if the Free Tier conditions don't apply to your account, you incur the standard fees from the time that you launch the instance (even if it remains idle) until you terminate it <Cite n={9} />.
- **Thinking that a stop ends all cost.** You are not charged for usage or data transfer fees for a stopped instance, but charges are incurred for the storage of any EBS volumes <Cite n={2} />. Elastic IP addresses also incur charges regardless of the instance's state <Cite n={2} />.
- **Expecting instance store data to survive.** Instance store volumes hold temporary data that is deleted when you stop, hibernate, or terminate your instance <Cite n={1} />.
- **Terminating when you meant to stop.** Terminating an instance is permanent and irreversible <Cite n={9} />. The default is to delete the root volume <Cite n={2} />.
- **Leaving SSH open to the world.** AWS says that 0.0.0.0/0 for SSH might be acceptable for a short time in a test environment, but it's unsafe for production environments <Cite n={9} />.
- **Losing or sharing the private key.** EC2 doesn't keep a copy of your private key, so there is no way to recover a private key if you lose it <Cite n={8} />. Anyone who possesses it can connect to your instances that use the key pair <Cite n={8} />.
- **Expecting user data to run on every boot.** By default, user data scripts and cloud-init directives run only during the boot cycle when you first launch an instance <Cite n={6} />. The instance user data is not included in an AMI that you create from the instance <Cite n={6} />.
- **Assuming that AWS backs up your disks.** AWS does not automatically back up the data stored on your EBS volumes <Cite n={18} />.
- **Treating versioning as a switch.** After you version-enable a bucket, it can never return to an unversioned state <Cite n={11} />. You are charged for every version of an object that is stored <Cite n={11} />.
- **Expecting a bucket policy to stop a lifecycle rule.** For general purpose buckets, you can't use a bucket policy to prevent deletions or transitions by an S3 Lifecycle rule <Cite n={12} />.
- **Relying on Block Public Access alone.** In addition to enabling Block Public Access, carefully inspect the other policies to confirm that they don't grant public access <Cite n={13} />. Removing a block public access setting makes a bucket or object with a public policy or ACL publicly accessible again <Cite n={13} />.
- **Treating a presigned URL as private.** Presigned URLs are bearer tokens that grant access to those who possess them <Cite n={14} />.
- **Two writers on one key.** S3 does not support object locking for concurrent writers <Cite n={10} />.
- **Using `aws s3` where a template is needed.** Custom commands, such as the `aws s3` commands, don't support `--generate-cli-skeleton` <Cite n={20} />.
- **Expecting to resume a failed `aws s3` upload.** You can't resume a failed upload when using these commands <Cite n={16} />. If the multipart upload or cleanup process is canceled by a kill command or system failure, the created files remain in the bucket <Cite n={16} />.

- **stop করতে চেয়ে terminate করা।** একটা instance terminate করা স্থায়ী আর অপরিবর্তনীয় <Cite n={9} />। by default root volume মুছে যায় <Cite n={2} />।
- **SSH পুরো দুনিয়ার জন্য খোলা রাখা।** AWS বলে, SSH-এর জন্য 0.0.0.0/0 একটা test environment-এ অল্প সময়ের জন্য গ্রহণযোগ্য হতে পারে, কিন্তু production environment-এর জন্য তা অনিরাপদ <Cite n={9} />।
- **private key হারানো বা অন্যকে দেওয়া।** EC2 আপনার private key-র কোনো কপি রাখে না। তাই private key হারালে তা ফিরে পাওয়ার কোনো উপায় নেই <Cite n={8} />। যার কাছে তা আছে, সে ওই key pair ব্যবহার করা আপনার instance-গুলোতে সংযোগ দিতে পারে <Cite n={8} />।
- **user data প্রতিবার boot-এ চলবে ভাবা।** by default user data script আর cloud-init directive শুধু সেই boot cycle-এ চলে, যখন আপনি প্রথম instance চালু করেন <Cite n={6} />। আপনি একটা instance থেকে যে AMI বানান, তাতে ওই instance-এর user data থাকে না <Cite n={6} />।
- **ধরে নেওয়া যে AWS আপনার disk-এর backup নেয়।** AWS আপনার EBS volume-এর data স্বয়ংক্রিয়ভাবে backup করে না <Cite n={18} />।
- **versioning-কে একটা switch ভাবা।** একটা bucket version-enable করার পর সেটা আর কখনো unversioned অবস্থায় ফিরতে পারে না <Cite n={11} />। একটা object-এর যতগুলো version রাখা আছে, প্রতিটার জন্য আপনার খরচ হয় <Cite n={11} />।
- **ভাবা যে bucket policy একটা lifecycle rule আটকাবে।** general purpose bucket-এর ক্ষেত্রে আপনি bucket policy দিয়ে একটা S3 Lifecycle rule-এর মুছে ফেলা বা transition আটকাতে পারেন না <Cite n={12} />।
- **শুধু Block Public Access-এর ওপর ভরসা করা।** Block Public Access চালু করার পাশাপাশি অন্য policy-গুলো সাবধানে দেখুন, যাতে নিশ্চিত হন সেগুলো public access দিচ্ছে না <Cite n={13} />। একটা block public access setting সরালে public policy বা ACL থাকা bucket বা object আবার public হয়ে যায় <Cite n={13} />।
- **presigned URL-কে private ভাবা।** presigned URL হলো bearer token, যা যার কাছে আছে তাকে access দেয় <Cite n={14} />।
- **একই key-তে দুই writer।** S3 একসঙ্গে লেখা writer-দের জন্য object locking সমর্থন করে না <Cite n={10} />।
- **যেখানে template দরকার সেখানে `aws s3` ব্যবহার।** custom command, যেমন `aws s3` command, `--generate-cli-skeleton` সমর্থন করে না <Cite n={20} />।
- **ব্যর্থ `aws s3` upload আবার শুরু করা যাবে ভাবা।** এই command দিয়ে ব্যর্থ upload আপনি আবার শুরু করতে পারেন না <Cite n={16} />। multipart upload বা পরিষ্কারের কাজ kill command বা system failure-এ বাতিল হলে তৈরি হওয়া file bucket-এ থেকে যায় <Cite n={16} />।

</Bangla>

## What a tester can check

<Voices>
<Technical>

<Callout type="tip" title="Tutorial advice">
This list is the tutorial's own advice for a tester who uses EC2, EBS, and S3.

- Before a run, write down every resource that it creates: instances, volumes, addresses, buckets, and objects.
- Name or tag everything that a test creates, so that the cleanup can find it.
- After each run, list what is left and delete it. Then look at the bill, not only at the console.
- Terminate a test instance instead of stopping it, unless you need its disks later. A stopped instance still pays for its EBS volumes.
- Copy logs and reports out of an instance, for example to S3, before you terminate it.
- Do not store a fixed public address in a test. Read the address again after each start.
- Check the Block Public Access settings of a bucket first, and then its policies and ACLs.
- Test a presigned URL three times: before it expires, after it expires, and with a different HTTP method.
- After you enable versioning in a test, wait as AWS advises. Do not add a sleep to every test.
- Check which IMDS versions an instance accepts, and try one call of each version.
- Never put a real credential in user data, in a skeleton file, or in a script that you commit.
- Use `s3api` when you need a template, and `aws s3` when you copy files.
- Before a real launch, run it with `--dry-run` to see whether your permissions are enough.
</Callout>

## Key words

| Term | Meaning |
|---|---|
| EC2 instance | A virtual server in the AWS Cloud |
| AMI | An Amazon Machine Image: an image that provides the software that is required to set up and boot an EC2 instance |
| Instance type | It determines the hardware available to your instance; each type offers a different balance of compute, memory, network, and storage resources |
| EBS volume | A storage volume that you attach to an instance and use in the same way as a local hard drive |
| Instance store volume | Storage for temporary data that is deleted when you stop, hibernate, or terminate your instance |
| Snapshot | A point-in-time backup of an EBS volume; it is an incremental backup |
| Key pair | A public key and a private key: security credentials that you use to prove your identity when connecting to an instance |
| User data | Data that you pass to an instance at launch, to perform automated configuration tasks or to run scripts |
| IMDS | The Instance Metadata Service, which a running instance uses to read its instance metadata; IMDSv2 uses session-oriented requests |
| Spot Instance | An instance that uses spare EC2 capacity that is available for less than the On-Demand price; EC2 gives it a two-minute interruption notice |
| S3 bucket | A container for objects |
| Object key | The unique identifier for an object within a bucket |
| Storage class | Each S3 object has one; objects are stored in S3 Standard by default |
| Versioning | Keeps multiple variants of an object in the same bucket; it is disabled by default |
| Delete marker | What S3 inserts instead of removing an object permanently, when you delete an object in a versioning-enabled bucket |
| Lifecycle rule | A rule in an S3 Lifecycle configuration: a transition action or an expiration action |
| Block Public Access | Four S3 settings that override policies and permissions, to limit public access |
| Presigned URL | A URL that grants time-limited access to an object without updating your bucket policy |
| `--generate-cli-skeleton` | An AWS CLI option that generates and displays a parameter template for a command |
| `--dry-run` | An option of `aws ec2 run-instances` that checks whether you have the required permissions for the operation, without actually making the request |
