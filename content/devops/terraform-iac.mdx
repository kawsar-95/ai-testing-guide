# Terraform and Infrastructure as Code

This page covers three tools: Terraform, Packer, and Crossplane. The practice run uses Terraform with local files, builds a Docker image with Packer, and renders a Crossplane composition on your own machine. It needs no cloud account. It comes after [AWS Databases and Serverless](/devops/aws-data-serverless/) and before [Ansible](/devops/ansible/).

<PageMeta />

## What it is

<Voices>
<Technical>

**Terraform.** Terraform is an infrastructure as code tool that lets you build, change, and version cloud and on-prem resources safely and efficiently <Cite n={1} />. You define the resources in human-readable configuration files that you can version, reuse, and share <Cite n={1} />. Terraform creates and manages the resources through the APIs of cloud platforms and other services <Cite n={1} />.

**The Terraform workflow.** The core workflow has three stages: write, plan, and apply <Cite n={1} />. In the plan stage, Terraform describes the infrastructure that it will create, update, or destroy <Cite n={1} />. In the apply stage, Terraform performs the proposed operations after approval, in the correct order <Cite n={1} />.

**Packer.** Packer is a community tool for creating identical machine images for multiple platforms from a single source configuration <Cite n={30} />. A machine image is a single static unit that contains a pre-configured operating system and installed software <Cite n={30} />. Packer does not replace configuration management like Chef or Puppet <Cite n={30} />.

**Crossplane.** Crossplane is a control plane framework for platform engineering <Cite n={43} />. It lets you build control planes to manage your cloud native software <Cite n={43} />. A control plane is software that controls other software <Cite n={43} />.

## How it works

<Voices>
<Technical>

**The configuration language.** The main purpose of the Terraform language is declaring resources, which represent infrastructure objects <Cite n={2} />. Blocks are containers for other content <Cite n={2} />. Arguments assign a value to a name <Cite n={2} />. Expressions represent a value, either literally or by referencing and combining other values <Cite n={2} />. The language is declarative, describing an intended goal rather than the steps to reach that goal <Cite n={2} />.

The resource block defines a piece of infrastructure <Cite n={3} />. The arguments that an individual resource supports are determined by the provider <Cite n={3} />. The variable block is similar to a function argument in other programming languages <Cite n={7} />. A validation block can refuse a value <Cite n={7} />. The output block lets you expose information about your infrastructure <Cite n={8} />. One use of an output is passing information from a Terraform operation to an automation tool <Cite n={8} />. The locals block is similar to function-scoped variables in other programming languages <Cite n={9} />. The data block fetches data about a resource from the provider without provisioning an associated infrastructure object <Cite n={10} />.

**Providers and the lock file.** Terraform relies on plugins called providers to interact with cloud providers, SaaS providers, and other APIs <Cite n={4} />. Every resource type is implemented by a provider <Cite n={4} />. Providers are distributed separately from Terraform itself, and each has its own version numbers <Cite n={4} />. A configuration declares the providers that it requires in a required_providers block <Cite n={5} />. Running terraform init locally installs a provider and updates the dependency lock file <Cite n={5} />. The lock file is always named .terraform.lock.hcl <Cite n={6} />. You should include it in your version control repository <Cite n={6} />. In production, HashiCorp recommends constraining the acceptable provider versions <Cite n={4} />.

**The commands.** The terraform init command initializes a working directory that contains Terraform configuration files <Cite n={18} />. It is the first command that you should run after writing a new configuration or cloning an existing one <Cite n={18} />. It is safe to run it multiple times <Cite n={18} />. The terraform fmt command formats configuration files to the canonical format and style <Cite n={20} />. The terraform validate command checks that a configuration is syntactically valid and internally consistent <Cite n={19} />. It does not validate remote services <Cite n={19} />. It needs an initialized working directory <Cite n={19} />. HashiCorp's style guide says to run terraform fmt and terraform validate before committing code <Cite n={28} />.

The terraform plan command creates an execution plan, which lets you preview the changes that Terraform plans to make <Cite n={21} />. By default, it reads the current state of existing remote objects <Cite n={21} />. It compares the configuration to the prior state <Cite n={21} />. It proposes a set of change actions that should, if applied, make the remote objects match the configuration <Cite n={21} />. Without the -out option, it creates a speculative plan <Cite n={21} />. You should always re-check the final non-speculative plan before applying <Cite n={21} />. With -detailed-exitcode, the command returns a detailed exit code when it exits <Cite n={21} />. The terraform apply command executes the operations of a plan <Cite n={22} />. Without a saved plan file, it creates a new plan and prompts you to approve it <Cite n={22} />. With a saved plan file, it does not prompt <Cite n={22} />. The terraform destroy command deprovisions all objects that a configuration manages <Cite n={23} />.

**State.** Terraform must store state about your workspace's managed infrastructure and configuration <Cite n={11} />. It uses state to map real world resources to your configuration <Cite n={11} />. Before any operation, Terraform does a refresh to update the state with the real infrastructure <Cite n={11} />. By default, the state is a local file named terraform.tfstate <Cite n={11} />. It is a JSON text file, and you should not edit it directly <Cite n={11} />. With remote state, Terraform writes the state data to a remote data store that a whole team can share <Cite n={12} />. If the backend supports it, Terraform locks the state for all operations that could write state <Cite n={13} />. The lock prevents others from corrupting the state <Cite n={13} />. If locking fails, Terraform does not continue <Cite n={13} />.

State and plan files can hold secrets <Cite n={14} />. A local state file is a plaintext file <Cite n={14} />. HashiCorp says to treat it as sensitive data and to keep it out of Git workflows <Cite n={14} />. It also says to avoid storing the state in a version control system or other storage that does not support state locking and secure access control <Cite n={11} />.

**Reuse and control.** A module is a collection of resources that Terraform manages together <Cite n={15} />. The configuration in the root directory is the root module <Cite n={15} />. Modules that you call with module blocks are child modules <Cite n={15} />. The for_each meta-argument manages several similar objects without a separate block for each <Cite n={17} />. It accepts a map or a set of strings <Cite n={17} />.

By default, when an argument cannot change in place, Terraform destroys the object and then creates a replacement <Cite n={16} />. The create_before_destroy rule reverses that order <Cite n={16} />. With prevent_destroy set to true, Terraform rejects plans that would destroy the object <Cite n={16} />. That rule does not stop the destruction when you remove the resource's configuration <Cite n={16} />. The ignore_changes argument lists attributes that Terraform should ignore when it plans updates <Cite n={16} />.

**Reading a plan, and tests.** The terraform show command provides human-readable output from a state or plan file <Cite n={24} />. The apply page says to inspect a saved plan file with it before applying <Cite n={22} />. With the -json flag, it generates machine-readable output <Cite n={24} />. For a plan file, the JSON holds the plan, the configuration, and the current state <Cite n={24} />. With -json, sensitive values in the state show in plain text <Cite n={24} />. Terraform can output a machine-readable JSON representation of a plan file's changes <Cite n={25} />. The same page says to use terraform show -json to produce it <Cite n={25} />.

Terraform tests let authors validate that module configuration updates do not introduce breaking changes <Cite n={26} />. Tests run against test-specific, short-lived resources <Cite n={26} />. Terraform finds test files by their extension, .tftest.hcl or .tftest.json <Cite n={26} />. A test file has one or more run blocks <Cite n={26} />. A run block can hold assert blocks <Cite n={26} />. By default, a run block applies the configuration, which creates real infrastructure <Cite n={26} />. With command = plan, a run block creates no infrastructure <Cite n={26} />. The expect_failures attribute lists objects that should fail their custom conditions <Cite n={26} />. Terraform v1.7.0 added the ability to mock data that providers return during a test <Cite n={26} />.

The terraform test command searches the current directory and the testing directory for test files and runs them <Cite n={27} />. The default testing directory is named tests <Cite n={27} />. Each test file keeps its state in memory, apart from the state of the configuration under test <Cite n={27} />. After a test file has run, Terraform tries to destroy any infrastructure that is left <Cite n={27} />. The command can create real infrastructure that can cost money <Cite n={27} />. The -json option displays machine-readable JSON output, and the -junit-xml option saves a test report in JUnit XML format <Cite n={27} />.

**Packer.** Packer reads and applies configurations defined in HCL template files <Cite n={32} />. When you pass a directory, Packer parses every file whose name ends in .pkr.hcl or .pkr.json <Cite n={32} />. A template defines one or more builds <Cite n={31} />. A build is a single task that produces an artifact for a single platform <Cite n={31} />. A builder creates a machine image for a single platform <Cite n={31} />. Provisioners install and configure software in a running machine before it becomes a static artifact <Cite n={31} />. A post-processor takes the result of a builder or another post-processor and creates a new artifact <Cite n={31} />. An artifact is the result of a single build <Cite n={31} />.

The source block defines reusable builder configuration <Cite n={33} />. The build block says which builders to run, how to provision them, and what post-processing to do <Cite n={34} />. The provisioner block defines how to configure a provisioner <Cite n={35} />. The post-processor block defines how to configure a post-processor <Cite n={36} />. The packer init command downloads and installs the plugins that the required_plugins block lists <Cite n={37} />. The packer validate command checks the syntax and configuration of a template <Cite n={39} />. It returns a zero exit status on success and a non-zero exit status on failure <Cite n={39} />. The packer build command runs all the builds of a template <Cite n={38} />. The builds run in parallel unless the template says otherwise <Cite n={38} />.

The shell provisioner runs shell scripts on the machine that Packer builds <Cite n={40} />. The docker builder builds Docker images using Docker <Cite n={41} />. It starts a container, runs the provisioners in it, then exports the container or commits the image <Cite n={41} />. Packer builds the container without a Dockerfile <Cite n={41} />. The builder needs a machine with Docker Engine installed <Cite n={41} />. With commit set to true, Packer commits the container to an image instead of exporting it <Cite n={41} />. The pull option defaults to true, so Packer pulls the base image first <Cite n={41} />. The docker-tag post-processor tags a committed artifact of the docker builder into a repository <Cite n={42} />.

**Crossplane.** Control planes expose an API <Cite n={43} />. You use the API to tell the control plane what software to configure and how, which is your desired state <Cite n={43} />. If the software drifts from the desired state, the control plane corrects the drift <Cite n={43} />. Crossplane is built on Kubernetes <Cite n={43} />. It has four major components: Composition, managed resources, operations, and a package manager <Cite n={43} />. Composition lets you build custom APIs <Cite n={43} />. With Crossplane you configure a pipeline of functions instead of writing a controller <Cite n={43} />. The functions return declarative configuration that Crossplane should apply <Cite n={43} />.

A composite resource definition (XRD) defines the schema for a custom API <Cite n={44} />. Users create composite resources (XRs) with the schema of an XRD <Cite n={44} />. A composition is a template for creating several Kubernetes resources as a single composite resource <Cite n={45} />. A composite resource represents a set of Kubernetes resources as a single Kubernetes object <Cite n={46} />. Providers enable Crossplane to provision infrastructure on an external service <Cite n={47} />. A managed resource represents an external service in a provider <Cite n={49} />. Functions extend Crossplane with new ways to configure composition <Cite n={48} />. The tutorial of the Crossplane docs creates an App custom resource that Crossplane turns into a Deployment and a Service <Cite n={50} />.

## How a tester uses it

<Voices>
<Technical>

- **Gate a change on exit codes.** `terraform fmt -check` has the exit status 0 if the input is properly formatted, and a non-zero exit status otherwise <Cite n={20} />. `packer fmt -check` does the same <Cite n={53} />. `packer validate` returns a non-zero exit status on failure <Cite n={39} />. `terraform plan -detailed-exitcode` returns 0 for no changes, 1 for an error, and 2 for changes <Cite n={21} />. HashiCorp's style guide says to run `terraform fmt` and `terraform validate` before you commit code <Cite n={28} />.
- **Read the plan as data.** `terraform show -json` shows a JSON representation of a plan file <Cite n={24} />. Each item of `resource_changes` has a list of `actions` <Cite n={25} />. A replacement shows as two actions, so you can scan the list for `delete` to find every case that deletes an object <Cite n={25} />.
- **Test the code with `terraform test`.** A run block with `command = plan` creates no infrastructure <Cite n={26} />. A run block that applies creates real infrastructure, which can cost money <Cite n={27} />. A test file keeps a state that is separate from the state of the configuration <Cite n={27} />. Since Terraform v1.7.0, a test can mock the data that providers return <Cite n={26} />. The `-junit-xml` option saves a report in JUnit XML format <Cite n={27} />.
- **Test the image, and not only the template.** `packer validate` checks the syntax and the configuration of a template <Cite n={39} />. The result of a build is an artifact <Cite n={31} />. In step 7 of Try it, the tutorial ran the built image and read a file and a version from it.
- **Check custom resources before a cluster sees them.** `crossplane resource validate` checks resources against schemas, and it detects unknown fields <Cite n={52} />. `crossplane composition render` shows what resources a composition would create or change, by running the composition locally <Cite n={52} />. In step 9 of Try it, `render` accepted a typo that `validate` refused.
- **Keep secrets out of reports.** State and plan files can hold sensitive values, such as initial database passwords or API tokens <Cite n={14} />. `terraform show -json` shows sensitive values of the state in plain text <Cite n={24} />. So a plan, a state file, or its JSON can contain a secret.
- **Use short-lived resources, and clean up.** Terraform tests run against test-specific, short-lived resources <Cite n={26} />. `terraform destroy` deprovisions all objects that a configuration manages <Cite n={23} />. A `prevent_destroy` rule also prevents the `terraform destroy` command from operating once the objects are created <Cite n={16} />.
- **Verify what you download.** A binary can contain malicious code, and HashiCorp says to verify that it created and signed the binary before you run it <Cite n={54} />.

- **exit code-এর ওপর একটা পরিবর্তন আটকান।** input ঠিকমতো format করা থাকলে `terraform fmt -check`-এর exit status ০, নইলে শূন্য নয় <Cite n={20} />। `packer fmt -check` একই কাজ করে <Cite n={53} />। ব্যর্থ হলে `packer validate` শূন্য নয় এমন exit status দেয় <Cite n={39} />। `terraform plan -detailed-exitcode` কোনো পরিবর্তন না থাকলে ০, error হলে ১, আর পরিবর্তন থাকলে ২ দেয় <Cite n={21} />। HashiCorp-এর style guide বলে, code commit করার আগে `terraform fmt` আর `terraform validate` চালাতে <Cite n={28} />।
- **plan-কে data হিসেবে পড়ুন।** `terraform show -json` একটা plan file-এর JSON রূপ দেখায় <Cite n={24} />। `resource_changes`-এর প্রতিটা item-এ `actions`-এর একটা তালিকা থাকে <Cite n={25} />। একটা replacement দুটো action হিসেবে দেখা যায়, তাই কোন কোন ক্ষেত্রে একটা object মুছে যায়, তা খুঁজতে আপনি তালিকায় `delete` খুঁজতে পারেন <Cite n={25} />।
- **`terraform test` দিয়ে code test করুন।** `command = plan` সহ একটা run block কোনো infrastructure তৈরি করে না <Cite n={26} />। যে run block apply করে, সেটা বাস্তব infrastructure তৈরি করে, যাতে টাকা খরচ হতে পারে <Cite n={27} />। একটা test file এমন একটা state রাখে, যা configuration-এর state থেকে আলাদা <Cite n={27} />। Terraform v1.7.0 থেকে একটা test provider-এর ফেরত দেওয়া data mock করতে পারে <Cite n={26} />। `-junit-xml` option JUnit XML format-এ একটা report save করে <Cite n={27} />।
- **শুধু template নয়, image-ও test করুন।** `packer validate` একটা template-এর syntax আর configuration যাচাই করে <Cite n={39} />। একটা build-এর ফল হলো একটা artifact <Cite n={31} />। Try it-এর ৭ নম্বর ধাপে টিউটোরিয়াল বানানো image চালিয়েছে, আর তার ভেতর থেকে একটা file আর একটা version পড়েছে।
- **cluster দেখার আগে custom resource যাচাই করুন।** `crossplane resource validate` resource-গুলোকে schema-র বিপরীতে যাচাই করে, আর অজানা field ধরে <Cite n={52} />। `crossplane composition render` composition স্থানীয়ভাবে চালিয়ে দেখায় এটা কোন resource তৈরি বা বদলাবে <Cite n={52} />। Try it-এর ৯ নম্বর ধাপে `render` এমন একটা typo মেনে নিয়েছে, যা `validate` প্রত্যাখ্যান করেছে।
- **report-এ secret রাখবেন না।** state আর plan file-এ সংবেদনশীল মান থাকতে পারে, যেমন database-এর প্রাথমিক password বা API token <Cite n={14} />। `terraform show -json` state-এর সংবেদনশীল মান সাধারণ text-এ দেখায় <Cite n={24} />। তাই একটা plan, একটা state file বা তার JSON-এ secret থাকতে পারে।
- **অল্পস্থায়ী resource ব্যবহার করুন, আর পরিষ্কার করুন।** Terraform test চলে test-এর নিজস্ব, অল্পস্থায়ী resource-এর বিরুদ্ধে <Cite n={26} />। `terraform destroy` একটা configuration যে সব object পরিচালনা করে, সেগুলো সরিয়ে দেয় <Cite n={23} />। `prevent_destroy` rule object তৈরি হওয়ার পর `terraform destroy` command-কেও কাজ করতে দেয় না <Cite n={16} />।

## Common mistakes

<Voices>
<Technical>

- **Keeping the state in version control.** HashiCorp says to avoid storing the state in a version control system or other storage that does not support state locking and secure access control <Cite n={11} />.
- **Editing the state file by hand.** The state is a JSON text file, and you should not edit it directly <Cite n={11} />.
- **Using a backend that cannot lock.** If the backend supports it, Terraform locks the state for all operations that could write state <Cite n={13} />. If state locking fails, Terraform does not continue <Cite n={13} />.
- **Leaving the lock file out of version control.** You should include `.terraform.lock.hcl` in your version control repository, so that a code review can discuss changes to your external dependencies <Cite n={6} />.
- **Leaving provider versions open in production.** HashiCorp recommends constraining the acceptable provider versions in production <Cite n={4} />.
- **Applying a plan that nobody re-checked.** You should always re-check the final non-speculative plan before applying it, to make sure that it still matches your intent <Cite n={21} />.
- **Using `-auto-approve` on shared infrastructure.** HashiCorp recommends making sure that no one can change your infrastructure outside of your Terraform workflow, because this minimizes the risk of unpredictable changes and configuration drift <Cite n={22} />.
- **Trusting `prevent_destroy` too much.** The rule does not stop Terraform from destroying a resource when you remove its configuration <Cite n={16} />. HashiCorp says to use it sparingly <Cite n={16} />.
- **Expecting `terraform validate` to look at remote services.** It does not validate remote services, such as remote state or provider APIs <Cite n={19} />. It needs an initialized working directory <Cite n={19} />.
- **Writing a secret into `local_file`.** If the file content is sensitive, the provider says to use the `local_sensitive_file` resource instead <Cite n={29} />.
- **Being surprised by the noise of `local_file` in CI.** Terraform detects the resource as deleted each time a configuration is applied on a new machine where the file is not present, and it generates a diff to re-create it <Cite n={29} />.
- **Running `terraform test` without knowing what it creates.** The command can create real infrastructure that can cost money <Cite n={27} />.
- **Expecting Packer to replace configuration management.** Packer does not replace configuration management like Chef or Puppet <Cite n={30} />.
- **Forgetting that Packer pulls the base image.** The `pull` option defaults to true <Cite n={41} />. The tutorial's template sets it to false, so it uses the image that is already on the machine.
- **Treating `crossplane composition render` as a check of the schema.** In step 9 of Try it, `render` exited with 0 for a typo in a field name, and `resource validate` refused it. The docs say that `validate` detects unknown fields <Cite n={52} />.
- **Running a binary that nobody verified.** HashiCorp says that you can avoid running an executable with malicious code by verifying that HashiCorp created and signed the binary <Cite n={54} />.

</Technical>

- প্রতিটা test-এর ফলের সঙ্গে তারিখ, tool-এর version আর হুবহু command রাখুন।

## Key words

| Term | Meaning |
|---|---|
| Infrastructure as code | Terraform is an infrastructure as code tool that lets you build, change, and version cloud and on-prem resources safely and efficiently |
| Provider | Terraform relies on plugins called providers to interact with cloud providers, SaaS providers, and other APIs |
| Resource | The resource block defines a piece of infrastructure |
| Variable | The variable block is similar to a function argument in other programming languages |
| Output | The output block lets you expose information about your infrastructure |
| Plan | The terraform plan command creates an execution plan, which lets you preview the changes that Terraform plans to make |
| Speculative plan | Without the -out option, it creates a speculative plan |
| Apply | The terraform apply command executes the operations of a plan |
| State | Terraform must store state about your workspace's managed infrastructure and configuration |
| Remote state | With remote state, Terraform writes the state data to a remote data store that a whole team can share |
| Dependency lock file | The lock file is always named .terraform.lock.hcl |
| Module | A module is a collection of resources that Terraform manages together |
| Terraform test | Terraform tests let authors validate that module configuration updates do not introduce breaking changes |
| Machine image | A machine image is a single static unit that contains a pre-configured operating system and installed software |
| Template | A template defines one or more builds |
| Builder | A builder creates a machine image for a single platform |
| Provisioner | Provisioners install and configure software in a running machine before it becomes a static artifact |
| Post-processor | A post-processor takes the result of a builder or another post-processor and creates a new artifact |
| Artifact | An artifact is the result of a single build |
| Control plane | A control plane is software that controls other software |
| Drift | If the software drifts from the desired state, the control plane corrects the drift |
| Composite resource definition (XRD) | A composite resource definition (XRD) defines the schema for a custom API |
| Composition | A composition is a template for creating several Kubernetes resources as a single composite resource |
| Composite resource (XR) | A composite resource represents a set of Kubernetes resources as a single Kubernetes object |
| Managed resource | A managed resource represents an external service in a provider |
| Function | Functions extend Crossplane with new ways to configure composition |
| Render | The composition render command shows what resources a composition would create or change |
