# Kubernetes Security and Troubleshooting

This page is about two jobs on a Kubernetes cluster: keeping it safe (Secrets, who may do what, which Pods may run, which Pods may talk to which) and finding out why a Pod fails, with a practice run on the local cluster of [Kubernetes Basics](/devops/kubernetes-basics/).

<PageMeta />

## What it is

<Voices>
<Technical>

**Secrets.** A Secret is an object that contains a small amount of sensitive data such as a password, a token, or a key <Cite n={1} />. Kubernetes Secrets are, by default, stored unencrypted in the API server's underlying data store (etcd) <Cite n={1} />. Anyone with API access can retrieve or modify a Secret, and so can anyone with access to etcd <Cite n={1} />.

**Who may do what.** Role-based access control (RBAC) is a method of regulating access to computer or network resources based on the roles of individual users within your organization <Cite n={5} />. A service account is a type of non-human account that, in Kubernetes, provides a distinct identity in a Kubernetes cluster <Cite n={6} />.

**Which Pods may run.** The Pod Security Standards define three different policies to broadly cover the security spectrum <Cite n={10} />, and Kubernetes offers a built-in Pod Security admission controller to enforce the Pod Security Standards <Cite n={11} />.

**Which Pods may talk to which.** If you want to control traffic flow at the IP address or port level for TCP, UDP, and SCTP protocols, then you might consider using Kubernetes NetworkPolicies for particular applications in your cluster <Cite n={13} />.

**Why a Pod fails.** The first step in debugging a Pod is taking a look at it <Cite n={15} />. Ephemeral containers are useful for interactive troubleshooting when `kubectl exec` is insufficient because a container has crashed or a container image doesn't include debugging utilities, such as with distroless images <Cite n={16} />.

</Technical>

## How it works

<Voices>
<Technical>

**Secrets are encoded, not encrypted.** The values for all keys in the `data` field of a Secret have to be base64-encoded strings <Cite n={1} />. A comment in the TLS example of the Secrets page says that base64 encoded values are obscured, but that this does NOT provide any useful level of confidentiality <Cite n={1} />. By default, the API server stores plain-text representations of resources into etcd, with no at-rest encryption <Cite n={3} />; if you are running the kube-apiserver without the `--encryption-provider-config` command line argument, you do not have encryption at rest enabled <Cite n={3} />. To check this, you can use the etcdctl command line program to retrieve the contents of your secret data <Cite n={3} />:

```text
ETCDCTL_API=3 etcdctl get /registry/secrets/default/secret1 [...] | hexdump -C
```

Here `[...]` must be the additional arguments for connecting to the etcd server <Cite n={3} />. In the docs' check of an `aescbc` setup, the stored Secret has to be prefixed with `k8s:enc:aescbc:v1:`, which indicates the aescbc provider has encrypted the resulting data <Cite n={3} />.

**How a Pod gets a Secret, and who can read it.** Secrets can be mounted as data volumes or exposed as environment variables to be used by a container in a Pod <Cite n={1} />. To use a Secret in an environment variable, you add an environment variable for each Secret key that you want to use to the `env[].valueFrom.secretKeyRef` field <Cite n={1} />. Anyone who is authorized to create a Pod in a namespace can use that access to read any Secret in that namespace; this includes indirect access such as the ability to create a Deployment <Cite n={1} />. Two of the good practices for Secrets: for humans, restrict get, watch, or list access to Secrets <Cite n={2} />, and note that granting list access to Secrets implicitly lets the subject fetch the contents of the Secrets <Cite n={2} />; and avoid sharing Secret manifests, because sharing the file or checking it in to a source repository means the secret is available to everyone who can read the manifest <Cite n={2} />.

**Roles, bindings, and service accounts.** An RBAC Role or ClusterRole contains rules that represent a set of permissions <Cite n={5} />. Permissions are purely additive (there are no "deny" rules) <Cite n={5} />. A Role always sets permissions within a particular namespace; when you create a Role, you have to specify the namespace it belongs in <Cite n={5} />. ClusterRole, by contrast, is a non-namespaced resource <Cite n={5} />. A role binding grants the permissions defined in a role to a user or set of users; it holds a list of subjects (users, groups, or service accounts), and a reference to the role being granted <Cite n={5} />. A RoleBinding grants permissions within a specific namespace whereas a ClusterRoleBinding grants that access cluster-wide <Cite n={5} />. Every namespace gets a default ServiceAccount upon creation <Cite n={6} />. If you deploy a Pod in a namespace, and you don't manually assign a ServiceAccount to the Pod, Kubernetes assigns the default ServiceAccount for that namespace to the Pod <Cite n={6} />.

These commands create the pieces and ask the API what an identity may do <Cite n={7} /> <Cite n={8} /> <Cite n={9} />:

| Command | What it does |
|---|---|
| `kubectl create role pod-reader --verb=get --verb=list --verb=watch --resource=pods` | Creates a role with a single rule |
| `kubectl create rolebinding NAME --clusterrole=NAME\|--role=NAME [--user=username] [--group=groupname] [--serviceaccount=namespace:serviceaccountname]` | Creates a role binding for a particular role or cluster role; a service account is given in the format `<namespace>:<name>` |
| `kubectl auth can-i list pods --as=system:serviceaccount:dev:foo -n prod` | Checks whether an action is allowed, as another identity: `--as` is the username to impersonate for the operation, a regular user or a service account in a namespace |

**Which Pods may run: Pod Security.** The Pod Security Standards define three different policies; these policies are cumulative and range from highly-permissive to highly-restrictive <Cite n={10} />:

| Profile | Description |
|---|---|
| Privileged | Unrestricted policy, providing the widest possible level of permissions |
| Baseline | Minimally restrictive policy which prevents known privilege escalations |
| Restricted | Heavily restricted policy, following current Pod hardening best practices |

Kubernetes defines a set of labels that you can set to define which of the predefined Pod Security Standard levels you want to use for a namespace <Cite n={11} />. The label you select defines what action the control plane takes if a potential violation is detected <Cite n={11} />:

| Mode | What a violation does |
|---|---|
| `enforce` | Policy violations will cause the pod to be rejected |
| `audit` | Policy violations will trigger the addition of an audit annotation to the event recorded in the audit log, but are otherwise allowed |
| `warn` | Policy violations will trigger a user-facing warning, but are otherwise allowed |

The label has the form `pod-security.kubernetes.io/<MODE>: <LEVEL>`, where MODE must be one of `enforce`, `audit`, or `warn`, and LEVEL must be one of `privileged`, `baseline`, or `restricted` <Cite n={11} />. Enforce mode is not applied to workload resources, only to the resulting pod objects <Cite n={11} />. The docs add the labels `pod-security.kubernetes.io/enforce=restricted` and `pod-security.kubernetes.io/enforce-version=v1.37` to an existing namespace with `kubectl label --overwrite ns my-existing-namespace`, which adds the `enforce=restricted` policy and pins the restricted policy version to v1.37 <Cite n={12} />. These are the four controls of the Restricted policy that step 3 of the tutorial's run meets <Cite n={10} />:

| Control | What the Restricted policy says | Field |
|---|---|---|
| Privilege escalation | Allowed value `false` | `securityContext.allowPrivilegeEscalation` |
| Capabilities | Containers must drop ALL capabilities, and are only permitted to add back the NET_BIND_SERVICE capability | `securityContext.capabilities.drop` |
| Running as non-root | Containers must be required to run as non-root users; allowed value `true` | `securityContext.runAsNonRoot` |
| Seccomp | The profile must be explicitly set to one of the allowed values, `RuntimeDefault` or `Localhost`; both the Unconfined profile and the absence of a profile are prohibited | `securityContext.seccompProfile.type` |

**Which Pods may talk to which: NetworkPolicy.** Network policies are implemented by the network plugin <Cite n={13} />. Creating a NetworkPolicy resource without a controller that implements it will have no effect <Cite n={13} />. By default, a pod is non-isolated for ingress; all inbound connections are allowed <Cite n={13} />. A pod is isolated for ingress if there is any NetworkPolicy that both selects the pod and has "Ingress" in its policyTypes <Cite n={13} />. When a pod is isolated for ingress, the only allowed connections into the pod are those from the pod's node and those allowed by the ingress list of some NetworkPolicy that applies to the pod for ingress <Cite n={13} />. Network policies do not conflict; they are additive <Cite n={13} />. An empty `podSelector` selects all pods in the namespace <Cite n={13} />, so a NetworkPolicy that selects all pods but does not allow any ingress traffic to those pods makes a default ingress isolation <Cite n={13} />. In an `ingress` rule, a `podSelector` under `from` selects particular Pods in the same namespace as the NetworkPolicy which should be allowed as ingress sources <Cite n={13} />. A default deny-all egress policy also blocks DNS traffic <Cite n={13} />. kind ships with a simple networking implementation (“kindnetd”) based around standard CNI plugins, and you may disable the default to install a different CNI <Cite n={14} />; network policies are implemented by the network plugin <Cite n={13} />.

**Why a Pod fails: the order of the checks.** `kubectl get pods` lists all pods in the namespace <Cite n={27} />. When a pod is failing to start repeatedly, CrashLoopBackOff may appear in the Status field of some kubectl commands <Cite n={17} />, and the docs show such a listing with the columns READY, STATUS, and RESTARTS <Cite n={17} />. To check the current state of the Pod and recent events, run `kubectl describe pods ${POD_NAME}` <Cite n={15} />; once your pod has been scheduled, the methods described in Debug Running Pods are available <Cite n={15} />. After containers in a Pod exit, the kubelet restarts them with an exponential backoff delay (10s, 20s, 40s, …), that is capped at 300 seconds (5 minutes) <Cite n={17} />; once a container has executed for 10 minutes without any problems, the kubelet resets the restart backoff timer for that container <Cite n={17} />. CrashLoopBackOff state indicates that the backoff delay mechanism is currently in effect for a given container that is in a crash loop, failing and restarting repeatedly <Cite n={17} />. To investigate it, check the logs with `kubectl logs <name-of-pod>`, and inspect the events with `kubectl describe pod <name-of-pod>` <Cite n={17} />. `kubectl logs` prints the logs for a container in a pod or specified resource, and `-p, --previous` prints the logs for the previous instance of the container in a pod if it exists <Cite n={18} />. `kubectl exec my-pod -- ls /` runs a command in an existing pod <Cite n={27} />. `kubectl debug` can add an ephemeral container to an already running pod, for example to add debugging utilities without restarting the pod <Cite n={19} />; its `--target` flag names the container whose processes to target <Cite n={19} />, and the `--target` parameter targets the process namespace of another container, and must be supported by the container runtime <Cite n={16} />. If you run `kubectl debug` to add an ephemeral container without the required permission, you will see an error similar to `Error from server (Forbidden)` <Cite n={16} />. This diagram is the tutorial's own list of those commands, in the order of the tutorial's run:

```text
Pod not working? Go down the list until you know why.

kubectl get pod            STATUS, RESTARTS            crashing? ready?
kubectl describe pod       Events                      scheduled, pulled, started, backed off
kubectl logs --previous    logs of the last run        what the container printed before it exited
kubectl exec               a command inside it         needs a shell in the image
kubectl debug              a new container beside it   for an image with no shell
```

The docs add the labels `pod-security.kubernetes.io/enforce=restricted` and `pod-security.kubernetes.io/enforce-version=v1.37` to an existing namespace with `kubectl label --overwrite ns my-existing-namespace`, which adds the `enforce=restricted` policy and pins the restricted policy version to v1.37 <Cite n={12} />. These are the four controls of the Restricted policy that step 3 of the tutorial's run meets <Cite n={10} />:

| Control | What the Restricted policy says | Field |
|---|---|---|
| Privilege escalation | Allowed value `false` | `securityContext.allowPrivilegeEscalation` |
| Capabilities | Containers must drop ALL capabilities, and may only add back the NET_BIND_SERVICE capability | `securityContext.capabilities.drop` |
| Running as non-root | Containers must be required to run as non-root users; allowed value `true` | `securityContext.runAsNonRoot` |
| Seccomp | The profile must be set explicitly to an allowed value, `RuntimeDefault` or `Localhost`; both the Unconfined profile and no profile at all are prohibited | `securityContext.seccompProfile.type` |

**Which Pods may talk to which: NetworkPolicy.** Network policies are implemented by the network plugin <Cite n={13} />. A NetworkPolicy resource created without a controller that implements it has no effect <Cite n={13} />. By default, a pod is non-isolated for ingress: all inbound connections are allowed <Cite n={13} />. A pod is isolated for ingress if some NetworkPolicy both selects the pod and has "Ingress" in its policyTypes <Cite n={13} />. When a pod is isolated for ingress, the only connections allowed into it are those from the pod's node and those allowed by the ingress list of some NetworkPolicy that applies to the pod for ingress <Cite n={13} />. Network policies do not conflict; they are additive <Cite n={13} />. An empty `podSelector` selects all pods in the namespace <Cite n={13} />, so a NetworkPolicy that selects all pods but allows no ingress traffic to them makes a default ingress isolation <Cite n={13} />. In an `ingress` rule, a `podSelector` under `from` selects particular Pods in the same namespace as the NetworkPolicy that should be allowed as ingress sources <Cite n={13} />. A default deny-all egress policy also blocks DNS traffic <Cite n={13} />. kind ships with a simple networking implementation (“kindnetd”) based on standard CNI plugins, and you may disable the default to install a different CNI <Cite n={14} />; network policies are implemented by the network plugin <Cite n={13} />.

**Why a Pod fails: the order of the checks.** `kubectl get pods` lists all the pods in the namespace <Cite n={27} />. When a pod is failing to start repeatedly, CrashLoopBackOff may appear in the Status field of some kubectl commands <Cite n={17} />, and the docs show such a listing with the columns READY, STATUS, and RESTARTS <Cite n={17} />. To see the current state of the Pod and its recent events, run `kubectl describe pods ${POD_NAME}` <Cite n={15} />; once your pod has been scheduled, the methods in Debug Running Pods are available <Cite n={15} />. After containers in a Pod exit, the kubelet restarts them with an exponential backoff delay (10s, 20s, 40s, …) that is capped at 300 seconds (5 minutes) <Cite n={17} />; once a container has run for 10 minutes without any problems, the kubelet resets the restart backoff timer for that container <Cite n={17} />. CrashLoopBackOff means that the backoff delay mechanism is in effect for a container that is in a crash loop, failing and restarting repeatedly <Cite n={17} />. To investigate it, check the logs with `kubectl logs <name-of-pod>`, and inspect the events with `kubectl describe pod <name-of-pod>` <Cite n={17} />. `kubectl logs` prints the logs for a container in a pod or specified resource, and `-p, --previous` prints the logs for the previous instance of the container in a pod if it exists <Cite n={18} />. `kubectl exec my-pod -- ls /` runs a command in an existing pod <Cite n={27} />. `kubectl debug` can add an ephemeral container to an already running pod, for example to add debugging utilities without restarting the pod <Cite n={19} />; its `--target` flag names the container whose processes to target <Cite n={19} />, and the `--target` parameter targets the process namespace of another container, and must be supported by the container runtime <Cite n={16} />. If you run `kubectl debug` to add an ephemeral container without the required permission, you will see an error similar to `Error from server (Forbidden)` <Cite n={16} />. **Secret encoded, encrypted নয়।** একটা Secret-এর `data` field-এর সব key-এর মান base64-encoded string হতে হয় <Cite n={1} />। Secrets পাতার TLS উদাহরণের একটা comment বলে, base64 encoding মানগুলো obscure করে, কিন্তু তাতে কোনো কার্যকর মাত্রার confidentiality পাওয়া যায় না <Cite n={1} />। ডিফল্টভাবে API server resource-গুলো plain text হিসেবে etcd-তে রাখে, at-rest encryption ছাড়া <Cite n={3} />; kube-apiserver `--encryption-provider-config` command line argument ছাড়া চালালে encryption at rest চালু থাকে না <Cite n={3} />। এটা যাচাই করতে etcdctl command line program দিয়ে আপনার secret data পড়তে পারেন <Cite n={3} />:

```text
ETCDCTL_API=3 etcdctl get /registry/secrets/default/secret1 [...] | hexdump -C
```

এখানে `[...]` হলো etcd server-এর সাথে সংযোগের জন্য দরকারি বাড়তি argument <Cite n={3} />। `aescbc` setup-এর docs-এর check-এ stored Secret-এর শুরুতে `k8s:enc:aescbc:v1:` থাকতে হয়, যা দেখায় aescbc provider data encrypt করেছে <Cite n={3} />।

**Pod কীভাবে Secret পায়, আর কে পড়তে পারে।** Secret data volume হিসেবে mount করা যায়, অথবা Pod-এর একটা container-এর জন্য environment variable হিসেবে দেওয়া যায় <Cite n={1} />। একটা Secret environment variable-এ ব্যবহার করতে আপনি যে Secret key ব্যবহার করতে চান, তার জন্য `env[].valueFrom.secretKeyRef` field-এ একটা environment variable যোগ করেন <Cite n={1} />। একটা namespace-এ Pod তৈরির অনুমতি আছে এমন যে কেউ সেই access দিয়ে ওই namespace-এর যেকোনো Secret পড়তে পারে, এর মধ্যে আছে পরোক্ষ access, যেমন Deployment তৈরির ক্ষমতা <Cite n={1} />। Secret-এর কয়েকটা good practice: মানুষের জন্য Secret-এ get, watch বা list access সীমিত করুন <Cite n={2} />, আর মনে রাখুন Secret-এ list access দিলে access-প্রাপক পরোক্ষভাবে Secret-গুলোর বিষয়বস্তু আনতে পারে <Cite n={2} />; আর Secret manifest শেয়ার করা এড়িয়ে চলুন, কারণ ফাইলটা শেয়ার করলে বা source repository-তে check in করলে manifest যে কেউ পড়তে পারে, সে-ই secret পেয়ে যায় <Cite n={2} />।

**Role, binding আর service account।** একটা RBAC Role বা ClusterRole-এ এমন rule থাকে, যা একটা permission-এর সেট বোঝায় <Cite n={5} />। Permission সম্পূর্ণ যোগাত্মক ("deny" rule বলে কিছু নেই) <Cite n={5} />। একটা Role সবসময় একটা নির্দিষ্ট namespace-এর ভেতরে permission ঠিক করে; Role তৈরির সময় কোন namespace-এ সেটা থাকবে, তা বলে দিতে হয় <Cite n={5} />। ClusterRole তার বিপরীতে namespace-এর সাথে বাঁধা নয় <Cite n={5} />। একটা role binding একটা role-এর permission একজন user বা একদল user-কে দেয়; এতে subject-এর (user, group বা service account) একটা তালিকা আর যে role দেওয়া হচ্ছে তার একটা reference থাকে <Cite n={5} />। RoleBinding একটা নির্দিষ্ট namespace-এর ভেতরে permission দেয়, আর ClusterRoleBinding সেই access দেয় cluster জুড়ে <Cite n={5} />। প্রতিটা namespace তৈরির সময় একটা default ServiceAccount পায় <Cite n={6} />। একটা namespace-এ Pod deploy করে আপনি নিজে Pod-কে কোনো ServiceAccount না দিলে Kubernetes সেই namespace-এর default ServiceAccount Pod-কে দেয় <Cite n={6} />।

এই command-গুলো টুকরোগুলো তৈরি করে আর API-কে জিজ্ঞেস করে একটা identity কী করতে পারে <Cite n={7} /> <Cite n={8} /> <Cite n={9} />:

| Command | কী করে |
|---|---|
| `kubectl create role pod-reader --verb=get --verb=list --verb=watch --resource=pods` | একটা মাত্র rule-সহ role তৈরি করে |
| `kubectl create rolebinding NAME --clusterrole=NAME\|--role=NAME [--user=username] [--group=groupname] [--serviceaccount=namespace:serviceaccountname]` | একটা নির্দিষ্ট role বা cluster role-এর জন্য role binding তৈরি করে; service account লেখা হয় `<namespace>:<name>` format-এ |

**কোন Pod চলতে পারবে: Pod Security।** Pod Security Standards তিনটা আলাদা policy ঠিক করে; এগুলো ক্রমযোজ্য (cumulative) আর অত্যন্ত শিথিল থেকে অত্যন্ত কঠোর পর্যন্ত বিস্তৃত <Cite n={10} />:

| Profile | বিবরণ |
|---|---|
| Privileged | বাধাহীন policy, সম্ভাব্য সবচেয়ে বিস্তৃত permission-সহ |
| Baseline | ন্যূনতম বাধা দেওয়া policy, যা পরিচিত privilege escalation আটকায় |
| Restricted | অত্যন্ত কঠোর policy, যা বর্তমান Pod hardening-এর best practice মেনে চলে |

Kubernetes এমন কিছু label ঠিক করে, যা দিয়ে আপনি একটা namespace-এর জন্য আগে থেকে ঠিক করা Pod Security Standard level-এর কোনটা ব্যবহার করবেন, তা বেছে নিতে পারেন <Cite n={11} />। আপনি যে label বেছে নেন, সেটা ঠিক করে সম্ভাব্য violation ধরা পড়লে control plane কী করবে <Cite n={11} />:

| Mode | violation হলে কী হয় |
|---|---|
| `enforce` | policy violation হলে pod reject হয় |
| `audit` | policy violation হলে audit log-এ রেকর্ড করা event-এ একটা audit annotation যোগ হয়, তবে অন্যথায় তা অনুমোদিত |
| `warn` | policy violation হলে user-কে একটা warning দেখানো হয়, তবে অন্যথায় তা অনুমোদিত |

label-এর রূপ `pod-security.kubernetes.io/<MODE>: <LEVEL>`, যেখানে MODE হলো `enforce`, `audit` বা `warn`-এর একটা, আর LEVEL হলো `privileged`, `baseline` বা `restricted`-এর একটা <Cite n={11} />। Enforce mode শুধু ফলস্বরূপ pod object-এ প্রয়োগ হয়, workload resource-এ নয় <Cite n={11} />। docs একটা বিদ্যমান namespace-এ `pod-security.kubernetes.io/enforce=restricted` আর `pod-security.kubernetes.io/enforce-version=v1.37` label যোগ করে `kubectl label --overwrite ns my-existing-namespace` দিয়ে, যা `enforce=restricted` policy যোগ করে আর restricted policy version v1.37-এ বেঁধে দেয় <Cite n={12} />। টিউটোরিয়ালের run-এর ধাপ ৩ Restricted policy-র যে চারটা control পূরণ করে, সেগুলো এই <Cite n={10} />:

| Control | Restricted policy কী বলে | Field |
|---|---|---|
| Privilege escalation | অনুমোদিত মান `false` | `securityContext.allowPrivilegeEscalation` |
| Capabilities | Container-কে সব capability drop করতে হবে, আর শুধু NET_BIND_SERVICE capability ফিরিয়ে যোগ করার অনুমতি আছে | `securityContext.capabilities.drop` |
| Running as non-root | Container-কে non-root user হিসেবে চালানো বাধ্যতামূলক করতে হবে; অনুমোদিত মান `true` | `securityContext.runAsNonRoot` |
| Seccomp | profile স্পষ্টভাবে অনুমোদিত মানগুলোর একটায় (`RuntimeDefault` বা `Localhost`) ঠিক করতে হবে; Unconfined profile আর profile না থাকা, দুটোই নিষিদ্ধ | `securityContext.seccompProfile.type` |

**কোন Pod কার সাথে কথা বলবে: NetworkPolicy।** Network policy প্রয়োগ করে network plugin <Cite n={13} />। যে controller NetworkPolicy প্রয়োগ করে, সেটা ছাড়া একটা NetworkPolicy resource তৈরি করলে তার কোনো প্রভাব পড়ে না <Cite n={13} />। ডিফল্টভাবে একটা pod ingress-এর জন্য non-isolated; সব inbound connection অনুমোদিত <Cite n={13} />। কোনো NetworkPolicy যদি pod-টাকে select করে আর তার policyTypes-এ "Ingress" থাকে, তাহলে pod-টা ingress-এর জন্য isolated <Cite n={13} />। একটা pod ingress-এর জন্য isolated হলে তার ভেতরে শুধু সেই connection-গুলো অনুমোদিত, যেগুলো pod-এর node থেকে আসে আর যেগুলো সেই pod-এ ingress-এর জন্য প্রযোজ্য কোনো NetworkPolicy-র ingress list অনুমতি দেয় <Cite n={13} />। Network policy-গুলো সংঘর্ষ করে না; সেগুলো যোগাত্মক <Cite n={13} />। খালি `podSelector` namespace-এর সব pod select করে <Cite n={13} />, তাই যে NetworkPolicy সব pod select করে কিন্তু সেগুলোতে কোনো ingress traffic অনুমতি দেয় না, সেটা একটা default ingress isolation বানায় <Cite n={13} />। একটা `ingress` rule-এর `from`-এর নিচে `podSelector` NetworkPolicy-র একই namespace-এর সেই নির্দিষ্ট Pod-গুলো select করে, যাদের ingress source হিসেবে অনুমতি দেওয়া উচিত <Cite n={13} />। একটা default deny-all egress policy DNS traffic-ও আটকায় <Cite n={13} />। kind একটা সরল networking implementation (“kindnetd”) নিয়ে আসে, যা standard CNI plugin-এর ওপর দাঁড়িয়ে, আর আপনি ডিফল্টটা বন্ধ করে অন্য একটা CNI install করতে পারেন <Cite n={14} />; network policy প্রয়োগ করে network plugin <Cite n={13} />।

**Pod কেন ব্যর্থ হয়: check-এর ক্রম।** `kubectl get pods` namespace-এর সব pod তালিকাভুক্ত করে <Cite n={27} />। একটা pod বারবার চালু হতে ব্যর্থ হলে কিছু kubectl command-এর Status field-এ CrashLoopBackOff দেখা যেতে পারে <Cite n={17} />, আর docs READY, STATUS ও RESTARTS column-সহ এমন একটা তালিকা দেখায় <Cite n={17} />। Pod-এর বর্তমান state আর সাম্প্রতিক event দেখতে `kubectl describe pods ${POD_NAME}` চালান <Cite n={15} />; আপনার pod schedule হয়ে গেলে Debug Running Pods-এর পদ্ধতিগুলো পাওয়া যায় <Cite n={15} />। একটা Pod-এর container exit করার পরে kubelet সেগুলো exponential backoff delay (10s, 20s, 40s, …) দিয়ে restart করে, যা 300 সেকেন্ডে (5 মিনিট) সীমিত <Cite n={17} />; একটা container কোনো সমস্যা ছাড়া 10 মিনিট চললে kubelet সেই container-এর restart backoff timer reset করে <Cite n={17} />। CrashLoopBackOff মানে crash loop-এ থাকা, বারবার ব্যর্থ হয়ে restart হওয়া একটা container-এর জন্য backoff delay mechanism এখন কার্যকর <Cite n={17} />। এটা তদন্ত করতে `kubectl logs <name-of-pod>` দিয়ে log দেখুন, আর `kubectl describe pod <name-of-pod>` দিয়ে event পরীক্ষা করুন <Cite n={17} />। `kubectl logs` একটা pod বা নির্দিষ্ট resource-এর container-এর log দেখায়, আর `-p, --previous` pod-এর container-এর আগের instance-এর log দেখায়, যদি থাকে <Cite n={18} />। `kubectl exec my-pod -- ls /` একটা বিদ্যমান pod-এ command চালায় <Cite n={27} />। `kubectl debug` একটা চলমান pod-এ ephemeral container যোগ করতে পারে, যেমন pod restart না করেই debugging utility যোগ করতে <Cite n={19} />; তার `--target` flag বলে কোন container-এর process-গুলোকে target করা হবে <Cite n={19} />, আর `--target` parameter অন্য একটা container-এর process namespace target করে, আর container runtime-কে সেটা support করতে হয় <Cite n={16} />। প্রয়োজনীয় permission ছাড়া `kubectl debug` দিয়ে ephemeral container যোগ করতে গেলে আপনি `Error from server (Forbidden)`-এর মতো একটা error দেখবেন <Cite n={16} />। এই diagram সেই command-গুলোর টিউটোরিয়ালের নিজের তালিকা, টিউটোরিয়ালের run-এর ক্রমে:

**২. জিজ্ঞেস করুন একটা identity কী করতে পারে।** `kubectl create serviceaccount` দেওয়া নামে একটা service account তৈরি করে <Cite n={22} />। `kubectl create role` একটা মাত্র rule-সহ role তৈরি করে <Cite n={7} />, আর `kubectl create rolebinding` একটা নির্দিষ্ট role বা cluster role-এর জন্য role binding তৈরি করে, service account লেখা হয় `<namespace>:<name>` format-এ <Cite n={8} />। `kubectl auth can-i` একটা action অনুমোদিত কি না যাচাই করে, আর impersonation-এর সাথে ভালো মানায়, যা `--as` flag <Cite n={9} />:

```bash
kubectl create serviceaccount tester -n sec-lab
kubectl create role pod-reader -n sec-lab --verb=get --verb=list --verb=watch --resource=pods
kubectl create rolebinding tester-reads-pods -n sec-lab --role=pod-reader --serviceaccount=sec-lab:tester
kubectl auth can-i list pods -n sec-lab --as=system:serviceaccount:sec-lab:tester
kubectl auth can-i delete pods -n sec-lab --as=system:serviceaccount:sec-lab:tester
kubectl auth can-i get secrets -n sec-lab --as=system:serviceaccount:sec-lab:tester
kubectl auth can-i list pods -n default --as=system:serviceaccount:sec-lab:tester
kubectl get pods -n sec-lab --as=system:serviceaccount:sec-lab:tester
kubectl get secret db-creds -n sec-lab --as=system:serviceaccount:sec-lab:tester
```

| `sec-lab`-এ `delete pods` | `no` | 1 |
| `sec-lab`-এ `get secrets` | `no` | 1 |
| `default`-এ `list pods` | `no` | 1 |

**৩. একটা namespace-কে policy ভাঙা Pod reject করান।** run একটা নতুন namespace-এ `enforce` mode সেট করেছে `restricted` level-এ, docs-এর মতো একটা label দিয়ে <Cite n={12} />। `kubectl run` একটা নির্দিষ্ট image একটা pod-এ তৈরি করে চালায় <Cite n={20} />, আর তার `--restart` flag Pod-এর restart policy ঠিক করে, বৈধ মান Always, OnFailure আর Never <Cite n={20} />। নিচের সাধারণ Pod policy ভাঙে; manifest `sec-restricted-ok.yaml` Restricted policy-র table-এর চারটা field সেট করে। user ID `1000` টিউটোরিয়ালের নিজের বেছে নেওয়া: Restricted policy বলে container `runAsUser` 0 সেট করতে পারবে না, আর যেকোনো non-zero মান অনুমোদিত <Cite n={10} />:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: restricted-ok
  namespace: psa-lab
spec:
  securityContext:
    runAsNonRoot: true
    runAsUser: 1000
    seccompProfile:
      type: RuntimeDefault
  containers:
  - name: app
    image: busybox:1.28
    command: ["sleep", "3600"]
    securityContext:
      allowPrivilegeEscalation: false
      capabilities:
        drop: ["ALL"]
```

```bash
kubectl create namespace psa-lab
kubectl label namespace psa-lab pod-security.kubernetes.io/enforce=restricted
kubectl run plain -n psa-lab --image=busybox:1.28 --restart=Never -- sleep 3600
kubectl apply -f sec-restricted-ok.yaml
kubectl wait --for=condition=Ready pod/restricted-ok -n psa-lab --timeout=120s
kubectl get pods -n psa-lab
```

**৪. NetworkPolicy দিয়ে traffic আটকান।** `kubectl create deployment` দেওয়া নামে একটা deployment তৈরি করে <Cite n={23} />, আর `kubectl expose` একটা resource-কে নতুন Kubernetes service হিসেবে প্রকাশ করে <Cite n={24} />। `kubectl rollout status` rollout-এর status দেখায় <Cite n={25} />, আর `kubectl run`-এর `--labels` flag pod-এ দেওয়ার জন্য কমা-দিয়ে-আলাদা-করা label নেয় <Cite n={20} />। run `sec-lab`-এ দুটো client Pod বানিয়েছে: `tester-client`-এর label `role=tester`, আর `other-client`-এর নিজের কোনো label নেই:

```bash
kubectl create deployment web -n sec-lab --image=nginx:1.16.1
kubectl expose deployment web -n sec-lab --port=80
kubectl rollout status deployment/web -n sec-lab --timeout=120s
kubectl run tester-client -n sec-lab --image=busybox:1.28 --restart=Never --labels=role=tester -- sleep 3600
kubectl run other-client -n sec-lab --image=busybox:1.28 --restart=Never -- sleep 3600
kubectl wait --for=condition=Ready pod/tester-client pod/other-client -n sec-lab --timeout=120s
```

যে প্রশ্ন run তিনবার করেছে, `busybox` image-এর `wget` আর 5 সেকেন্ডের time-out (`-T 5`) দিয়ে, যা টিউটোরিয়ালের নিজের বেছে নেওয়া: Service `web` কি উত্তর দেয়?

```bash
kubectl exec -n sec-lab tester-client -- sh -c 'wget -qO- -T 5 http://web | grep "<title>"'
kubectl exec -n sec-lab other-client -- sh -c 'wget -qO- -T 5 http://web | grep "<title>"'
```

run নিচের দুটো policy একটার পর একটা apply করেছে, আর প্রতিটা `kubectl apply`-এর পরে আবার জিজ্ঞেস করার আগে 5 সেকেন্ড অপেক্ষা করেছে; 5 সেকেন্ড টিউটোরিয়ালের নিজের বেছে নেওয়া। প্রথম policy সব pod select করে আর তার `policyTypes`-এ `Ingress` আছে, আর ভেতরে কিছু ঢুকতে দেয় না; দ্বিতীয়টা `role=tester` label-ওয়ালা Pod-কে `app=web` label-ওয়ালা Pod-এর port 80-এ পৌঁছাতে দেয় <Cite n={13} />:

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-ingress
  namespace: sec-lab
spec:
  podSelector: {}
  policyTypes:
  - Ingress
```

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: web-allow-testers
  namespace: sec-lab
spec:
  podSelector:
    matchLabels:
      app: web
  policyTypes:
  - Ingress
  ingress:
  - from:
    - podSelector:
        matchLabels:
          role: tester
    ports:
    - protocol: TCP
      port: 80
```

```bash
kubectl apply -f sec-deny.yaml
kubectl apply -f sec-allow.yaml
kubectl get networkpolicy -n sec-lab
```

যে request-এর উত্তর এসেছে, সেটা নিচের প্রথম block প্রিন্ট করেছে, আর যে request-এর উত্তর আসেনি, সেটা দ্বিতীয়টা:

```text

```


|---|---|---|
| কোনো policy-র আগে | উত্তর এসেছে | উত্তর এসেছে |

**৫. জানুন একটা Pod কেন বারবার crash করে।** `kubectl run`-এর syntax-এ `--`-এর পরে একটা command আর তার argument থাকে <Cite n={20} />, আর সে যে Pod বানায় তার restart policy ডিফল্টভাবে Always <Cite n={20} />। `crashy`-র container একটা line প্রিন্ট করে, 1 সেকেন্ড অপেক্ষা করে, একটা error প্রিন্ট করে, আর exit code 1 দিয়ে বেরিয়ে যায়। `kubectl wait` একটা field-এর জন্য অপেক্ষা করতে পারে: `kubectl wait --for=jsonpath='{.status.phase}'=Running pod/busybox1` <Cite n={26} />। run অপেক্ষা করেছে waiting reason `CrashLoopBackOff`-এর জন্য, তারপর দেখেছে Pod, container-এর আগের run-এর log আর event <Cite n={15} /> <Cite n={18} />। kubectl দিয়ে এমন একটা Pod জিজ্ঞেস করলে, যার একটা container Terminated, আপনি একটা reason, একটা exit code, আর সেই container-এর execution-এর সময়কালের শুরু ও শেষের সময় দেখেন <Cite n={17} />; run শেষ termination-এর exit code পড়েছে `-o jsonpath` দিয়ে <Cite n={27} />:

**৬. shell নেই এমন একটা container debug করুন।** docs `pause` image থেকে একটা Pod বানায়, কারণ তাতে debugging utility নেই <Cite n={16} />: `kubectl run ephemeral-demo --image=registry.k8s.io/pause:3.1 --restart=Never` <Cite n={16} />। `kubectl exec` দিয়ে shell খুলতে গেলে আপনি একটা error দেখবেন, কারণ এই container image-এ কোনো shell নেই, আর তার বদলে আপনি `kubectl debug` দিয়ে একটা debugging container যোগ করতে পারেন <Cite n={16} />। command-এর syntax `--`-এর পরে একটা command-এর অনুমতি দেয়: `kubectl debug (POD | TYPE[[.VERSION].GROUP]/NAME) [ -- COMMAND [args...] ]` <Cite n={19} />, আর `-c, --container` debug container-এর নাম দেয় <Cite n={19} />। docs এটা interactive-ভাবে চালায়, `-it` দিয়ে <Cite n={16} />; run-এর কোনো terminal ছিল না, তাই সে debug container চালু করেছে `ps` command দিয়ে আর output পড়েছে `kubectl logs -c debugger` দিয়ে:

## How a tester uses it

<Voices>
<Technical>

**Read a Secret the way anyone with access would.** Anyone with API access can retrieve or modify a Secret, and so can anyone with access to etcd <Cite n={1} />. In step 1, one command turned the base64 value back into the password, and the password was readable in etcd. To test encryption at rest, read the Secret out of etcd and look at the start of the stored value; the docs expect `k8s:enc:aescbc:v1:` for an `aescbc` setup <Cite n={3} />.

**Ask as the identity under test, and ask for the "no" answers too.** `kubectl auth can-i` pairs nicely with impersonation <Cite n={9} />. In step 2, the identity could list Pods in its own namespace, and could not delete Pods, get Secrets, or list Pods in `default`; a Role always sets permissions within a particular namespace <Cite n={5} />.

**Read the whole rejection.** With the `enforce` mode, policy violations will cause the pod to be rejected <Cite n={11} />. In step 3, one message named four violations at once, and each one is a control of the Restricted policy <Cite n={10} />. A Deployment is not rejected as such: enforce mode is not applied to workload resources, only to the resulting pod objects <Cite n={11} />, so look at the Pods.

**Prove a NetworkPolicy with a request that should fail.** Creating a NetworkPolicy resource without a controller that implements it will have no effect <Cite n={13} />, and kind lets you install a different CNI <Cite n={14} />. In step 4, the same request changed from an answer to a timeout after the policy, and the label of the client decided which client was let in again.

**Go down the list of checks in order.** `kubectl describe` shows the current state and the recent events <Cite n={15} />, `kubectl logs` shows the logs of the container <Cite n={17} />, and `--previous` shows the previous instance <Cite n={18} />. `kubectl debug` helps when `kubectl exec` is insufficient <Cite n={16} />. In step 5, the exit code 1 and the two lines of the previous logs named the failure that the container printed.

**Check that you may debug at all.** If you run `kubectl debug` to add an ephemeral container without the required permission, you will see an error similar to `Error from server (Forbidden)` <Cite n={16} />. When granting permission to add ephemeral containers to Pods governed by the baseline or restricted policy, the docs say to choose a matching debugging profile such as `--profile=baseline` or `--profile=restricted` with `kubectl debug` <Cite n={16} />.

## Common mistakes

<Voices>
<Technical>

- **Calling base64 "encrypted".** Base64 encoded values are obscured, but that does NOT provide any useful level of confidentiality <Cite n={1} />.
- **Sharing Secret manifests.** Sharing the file, or checking it in to a source repository, means the secret is available to everyone who can read the manifest <Cite n={2} />.
- **Forgetting who can read Secrets through a Pod.** Anyone who is authorized to create a Pod in a namespace can use that access to read any Secret in that namespace <Cite n={1} />.
- **Trusting a NetworkPolicy that was only created.** Without a controller that implements it, a NetworkPolicy resource will have no effect <Cite n={13} />.
- **Forgetting DNS.** A default deny-all egress policy also blocks DNS traffic <Cite n={13} />.
- **Reading only the Deployment under a Pod Security policy.** Enforce mode is not applied to workload resources, only to the resulting pod objects <Cite n={11} />.
- **Using `kubectl exec ... sh` on an image with no shell.** There is no shell in such an image, and you can instead add a debugging container using `kubectl debug` <Cite n={16} />.
- **Reading the logs of a crashing container without `--previous`.** `-p, --previous` prints the logs for the previous instance of the container in a pod if it exists <Cite n={18} />.

</Technical>

<Callout type="tip" title="Tutorial advice">
This list is the tutorial's own advice for a tester whose app runs on Kubernetes.

- Check whether a Secret value can be read in clear text from the API and from etcd, and whether encryption at rest is enabled.

- Make a test run clean up the namespaces that it made.

## Key words

| Term | Meaning |
|---|---|
| Secret | An object that contains a small amount of sensitive data such as a password, a token, or a key |
| base64 | The encoding of the values in the `data` field of a Secret; it obscures them but gives no useful confidentiality |
| Encryption at rest | Not enabled by default: the API server stores plain-text representations of resources into etcd |
| etcd | The data store that the API server uses underneath |
| RBAC | Regulates access to resources based on the roles of individual users |
| Role, RoleBinding | A set of permissions in one namespace, and the grant of it to subjects |
| ServiceAccount | A non-human account that gives a distinct identity in the cluster |
| `kubectl auth can-i` | Checks whether an action is allowed; `--as` asks as another identity |
| Pod Security Standards | Three policies: Privileged, Baseline, and Restricted |
| `enforce`, `audit`, `warn` | What a policy violation does: rejects the Pod, adds an audit annotation, or shows a warning |
| NetworkPolicy | Rules for traffic at the IP address or port level; needs a network plugin that implements it |
| Isolated for ingress | A Pod that some NetworkPolicy selects, with "Ingress" in its policyTypes |
| CrashLoopBackOff | The backoff delay between restarts of a container that keeps failing is in effect |
| `kubectl logs --previous` | Prints the logs for the previous instance of the container, if it exists |
| Ephemeral container | A container added to a running Pod for troubleshooting, with `kubectl debug` |
