# Docker in Practice

This page is about the everyday work with containers in testing: where test data lives (volumes, bind mounts, and tmpfs), how containers find each other on a network, and the commands that show what a container holds and uses, with a practice run of each. It builds on [Docker Basics](/devops/docker-basics/) and [Docker Images and Compose](/devops/docker-images-compose/).

<PageMeta />

## What it is

<Voices>
<Technical>

**Data in a container.** By default, all files created inside a container are stored on a writable container layer <Cite n={1} />. Data written to the container layer doesn't persist when the container is destroyed <Cite n={1} />. Docker supports storage mounts for storing data outside the writable layer of the container, among them volume mounts, bind mounts, and tmpfs mounts <Cite n={1} />. No matter which type of mount you choose to use, the data looks the same from within the container <Cite n={1} />.

| Mount | What it is | Use it for |
|---|---|---|
| Volume | A persistent data store for containers, created and managed by Docker <Cite n={2} /> | Volumes are the preferred mechanism for persisting data generated by and used by Docker containers <Cite n={2} /> |
| Bind mount | A file or directory on the host machine, mounted from the host into a container <Cite n={3} /> | Sharing source code or build artifacts between a development environment on the Docker host and a container <Cite n={3} /> |
| tmpfs mount | Temporary, and only persisted in the host memory; when the container stops, the tmpfs mount is removed <Cite n={4} /> | Non-persistent state data that should not be stored anywhere permanently <Cite n={2} /> |

**Networks.** All containers without a `--network` specified are attached to the default bridge network <Cite n={5} />. Containers on the default bridge network can only access each other by IP addresses, unless you use the `--link` option, which is considered legacy <Cite n={5} />. User-defined bridges provide automatic DNS resolution between containers <Cite n={5} />.

</Technical>
<Layman>

**Data in a container.** By default, every file that a container creates goes into a writable layer <Cite n={1} />. When the container is destroyed, that data is gone <Cite n={1} />. To keep data outside that layer, Docker has storage mounts, among them volume mounts, bind mounts, and tmpfs mounts <Cite n={1} />. Whichever mount you choose, the data looks the same from inside the container <Cite n={1} />.

| Mount | What it is | Use it for |
|---|---|---|
| Volume | A store for data that lasts, made and managed by Docker <Cite n={2} /> | The preferred way to keep data that containers make and use <Cite n={2} /> |
| Bind mount | A file or folder of the host machine, mounted into a container <Cite n={3} /> | Sharing source code or build results between the Docker host and a container <Cite n={3} /> |
| tmpfs mount | Temporary, kept only in the host's memory; when the container stops, it is removed <Cite n={4} /> | Data that does not need to last and should not be stored anywhere for good <Cite n={2} /> |

**Networks.** A container started without `--network` joins the default bridge network <Cite n={5} />. On the default bridge network, containers can reach each other only by IP address, unless you use the old `--link` option <Cite n={5} />. A bridge network that you create yourself gives its containers automatic DNS resolution between them <Cite n={5} />.

</Layman>

## How it works

<Voices>
<Technical>

**A volume outlives its container.** A volume's contents exist outside the lifecycle of a given container <Cite n={2} />. When a container is destroyed, the writable layer is destroyed with it, but using a volume ensures that the data is persisted even if the container using it is removed <Cite n={2} />. A given volume can be mounted into multiple containers simultaneously <Cite n={2} />. When no running container is using a volume, the volume is still available to Docker and isn't removed automatically <Cite n={2} />.

**Two flags to mount.** To mount a volume with `docker run`, you can use either the `--mount` or the `--volume` flag <Cite n={2} />. In general, `--mount` is preferred: it is more explicit and supports all the available options <Cite n={2} />.

| Mount | `--mount` form | Short form |
|---|---|---|
| Volume | `--mount type=volume,src=<volume-name>,dst=<mount-path>` <Cite n={2} /> | `--volume <volume-name>:<mount-path>` <Cite n={2} /> |
| Bind mount | `--mount type=bind,src=<host-path>,dst=<container-path>` <Cite n={3} /> | `--volume <host-path>:<container-path>` <Cite n={3} /> |
| tmpfs | `--mount type=tmpfs,dst=<mount-path>` <Cite n={4} /> | `--tmpfs <mount-path>` <Cite n={4} /> |

**Mounting over files.** If you mount a non-empty volume into a directory in the container in which files or directories exist, the pre-existing files are obscured by the mount <Cite n={2} />. If you mount an empty volume there, these files or directories are propagated (copied) into the volume by default <Cite n={2} />.

**Named and anonymous volumes.** A volume may be named or anonymous; anonymous volumes are given a random name <Cite n={2} />. Like named volumes, anonymous volumes persist even if you remove the container that uses them, except if you use the `--rm` flag when creating the container <Cite n={2} />.

**Bind mounts can change the host.** Bind mounts have write access to files on the host by default <Cite n={3} />. A process in the container can change the host filesystem, including creating, modifying, or deleting important system files or directories <Cite n={3} />. You can use the `readonly` or `ro` option to prevent the container from writing to the mount <Cite n={3} />.

**Names on a network.** On the default bridge network, containers can't resolve each other by name <Cite n={5} />. On user-defined networks, containers can resolve each other by name <Cite n={5} />. Automatic service discovery only resolves custom container names, not default automatically generated names <Cite n={5} />. This diagram is the tutorial's own picture of step 4 of the practice run below:

```text
alpine-net (user-defined)
┌─────────────────────────────┐
│ alpine1 ── ping ──> alpine2 │
└─────────────────────────────┘
bridge (default)
┌─────────┐
│ alpine3 │
└─────────┘

alpine1 ── ping alpine3 ──X
ping: bad address 'alpine3'
```

</Technical>
<Layman>

**A volume lives longer than its container.** What is in a volume lives outside the life of any one container <Cite n={2} />. When a container is destroyed, its writable layer goes with it, but the data in a volume stays, even when the container that used it is removed <Cite n={2} />. One volume can be mounted into many containers at the same time <Cite n={2} />. When no running container uses a volume, Docker still keeps it; it is not removed by itself <Cite n={2} />.

**Two flags to mount.** To mount a volume with `docker run`, you can use `--mount` or `--volume` <Cite n={2} />. Most of the time, `--mount` is the better choice: it says more clearly what you want, and it supports all the options <Cite n={2} />.

| Mount | `--mount` form | Short form |
|---|---|---|
| Volume | `--mount type=volume,src=<volume-name>,dst=<mount-path>` <Cite n={2} /> | `--volume <volume-name>:<mount-path>` <Cite n={2} /> |
| Bind mount | `--mount type=bind,src=<host-path>,dst=<container-path>` <Cite n={3} /> | `--volume <host-path>:<container-path>` <Cite n={3} /> |
| tmpfs | `--mount type=tmpfs,dst=<mount-path>` <Cite n={4} /> | `--tmpfs <mount-path>` <Cite n={4} /> |

**Mounting over files.** If you mount a volume that already has data onto a folder that already has files, the mount hides those files <Cite n={2} />. If the volume is empty, Docker copies those files into the volume by default <Cite n={2} />.

**Named and anonymous volumes.** A volume can have a name, or be anonymous; an anonymous volume gets a random name <Cite n={2} />. Like named volumes, anonymous volumes stay after you remove their container, unless you started the container with `--rm` <Cite n={2} />.

**Bind mounts can change the host.** By default, a bind mount can write to files on the host <Cite n={3} />. A process in the container can change the host's file system, and even create, change, or delete important system files or folders <Cite n={3} />. The `readonly` or `ro` option stops the container from writing to the mount <Cite n={3} />.

**Names on a network.** On the default bridge network, containers cannot find each other by name <Cite n={5} />. On networks that you create, they can <Cite n={5} />. This works only for names that you give the containers, not for the names that Docker makes up <Cite n={5} />. This diagram is the tutorial's own picture of step 4 of the practice run below:

```text
alpine-net (user-defined)
┌─────────────────────────────┐
│ alpine1 ── ping ──> alpine2 │
└─────────────────────────────┘
bridge (default)
┌─────────┐
│ alpine3 │
└─────────┘

alpine1 ── ping alpine3 ──X
ping: bad address 'alpine3'
```

</Layman>
<Bangla>

**volume তার container-এর চেয়ে বেশিদিন টেকে।** একটা volume-এর বিষয়বস্তু কোনো একটা container-এর lifecycle-এর বাইরে থাকে <Cite n={2} />। container ধ্বংস হলে তার writable layer-ও যায়, কিন্তু volume ব্যবহার করলে সেটা ব্যবহার করা container মুছে ফেলার পরও data থেকে যায় <Cite n={2} />। একটা volume একসাথে একাধিক container-এ mount করা যায় <Cite n={2} />। কোনো চলমান container একটা volume ব্যবহার না করলেও Docker-এর কাছে সেটা থাকে, নিজে থেকে মোছে না <Cite n={2} />।

**mount করার দুটো flag।** `docker run`-এ volume mount করতে `--mount` বা `--volume`, যেকোনো একটা flag ব্যবহার করা যায় <Cite n={2} />। সাধারণভাবে `--mount` বেশি পছন্দনীয়: এটা বেশি স্পষ্ট, আর সব option সমর্থন করে <Cite n={2} />।

| Mount | `--mount` রূপ | ছোট রূপ |
|---|---|---|
| Volume | `--mount type=volume,src=<volume-name>,dst=<mount-path>` <Cite n={2} /> | `--volume <volume-name>:<mount-path>` <Cite n={2} /> |
| Bind mount | `--mount type=bind,src=<host-path>,dst=<container-path>` <Cite n={3} /> | `--volume <host-path>:<container-path>` <Cite n={3} /> |
| tmpfs | `--mount type=tmpfs,dst=<mount-path>` <Cite n={4} /> | `--tmpfs <mount-path>` <Cite n={4} /> |

**file-এর ওপর mount করা।** container-এর যে directory-তে আগে থেকে file আছে, সেখানে data-ভরা একটা volume mount করলে আগের file-গুলো mount-এর আড়ালে ঢাকা পড়ে <Cite n={2} />। খালি volume mount করলে default-ভাবে ওই file বা directory-গুলো volume-এ copy হয় <Cite n={2} />।

**Named আর anonymous volume।** একটা volume named বা anonymous হতে পারে; anonymous volume একটা random নাম পায় <Cite n={2} />। named volume-এর মতো anonymous volume-ও ব্যবহার করা container মুছে ফেলার পরও থেকে যায়, যদি না container তৈরির সময় `--rm` flag দেওয়া হয় <Cite n={2} />।

**bind mount host বদলাতে পারে।** default-ভাবে bind mount-এর host-এর file-এ লেখার অধিকার থাকে <Cite n={3} />। container-এর একটা process host-এর filesystem বদলাতে পারে, গুরুত্বপূর্ণ system file বা directory তৈরি, বদল বা মুছে ফেলাসহ <Cite n={3} />। container যাতে mount-এ লিখতে না পারে, সেজন্য `readonly` বা `ro` option ব্যবহার করা যায় <Cite n={3} />।

**network-এ নাম।** default bridge network-এ container-গুলো নাম দিয়ে একে অপরকে খুঁজে পায় না <Cite n={5} />। user-defined network-এ পায় <Cite n={5} />। automatic service discovery শুধু আপনার দেওয়া container-এর নাম resolve করে, Docker-এর নিজে বানানো নাম নয় <Cite n={5} />। এই diagram নিচের practice run-এর ধাপ ৪-এর টিউটোরিয়ালের নিজের ছবি:

## Try it

<Voices>
<Technical>

The tutorial ran these steps on 2026-11-16 with Docker Engine 29.9.3 on Linux, as a user in the `docker` group. The file contents (`run 1: 12 passed`, `1 passed`) are the tutorial's own sample data. IDs, sizes, and paths differ on your machine.

**1. Keep a result in a volume, and copy it out.** If you start a container with a volume that doesn't yet exist, Docker creates the volume for you; the first command is Docker's own example, on one line <Cite n={2} />. `docker exec` runs a new command in a running container <Cite n={6} />. The command must be an executable, and a chained or a quoted command doesn't work, so the second command runs in `sh -c`, as Docker's example does <Cite n={6} />. `docker cp` works with a running or a stopped container <Cite n={7} />:

```bash
docker run -d --name devtest --mount source=myvol2,target=/app nginx:latest
docker exec devtest sh -c 'echo "run 1: 12 passed" > /app/result.txt'
docker container stop devtest
docker cp devtest:/app/result.txt ./result-copy.txt
docker container rm devtest
docker run --rm --mount source=myvol2,target=/app alpine cat /app/result.txt
```

In the tutorial's run, `docker cp` copied the file out of the stopped container, and `ls -l result-copy.txt` showed the user who ran `docker cp` as its owner. The last command starts a new container with the same volume. It printed `run 1: 12 passed`, the line that the removed container had written.

**2. Write a report to the host.** A bind mount puts a host folder into the container, and the container can write to it by default <Cite n={3} />:

```bash
mkdir reports
docker run --rm --mount type=bind,src="$(pwd)"/reports,dst=/reports alpine sh -c 'echo "1 passed" > /reports/result.txt'
cat reports/result.txt
```

In the tutorial's run, `cat` printed `1 passed`, and `ls -l reports` showed that `result.txt` belonged to `root`, not to the user who ran the command.

**3. See what a wrong path does.** By default, `--mount` does not create a directory that does not exist on the host; it produces an error <Cite n={3} />. With `--volume` (`-v`), Docker creates the missing directory on the host for you, and it's always created as a directory <Cite n={3} />:

```bash
docker run --rm --mount type=bind,src="$(pwd)"/no-such-dir,dst=/reports alpine ls /reports
docker run --rm -v "$(pwd)"/typo-dir:/reports alpine ls -la /reports
```

In the tutorial's run, the first command printed `docker: Error response from daemon: invalid mount config for type "bind": bind source path does not exist:` with the full path, and exited with code 125. The second one exited with 0: it created `typo-dir` on the host, owned by `root`, and `ls -la` in the container listed an empty `/reports`.

**4. Let containers find each other by name.** These commands follow Docker's tutorial on user-defined bridge networks, with three containers instead of its four; the `-dit` flags mean detached, interactive, and with a TTY <Cite n={5} />. Docker's tutorial attaches to `alpine1` to run the ping <Cite n={5} />; here, `docker exec` runs it:

```bash
docker network create --driver bridge alpine-net
docker run -dit --name alpine1 --network alpine-net alpine ash
docker run -dit --name alpine2 --network alpine-net alpine ash
docker run -dit --name alpine3 alpine ash
docker exec alpine1 ping -c 2 alpine2
docker exec alpine1 ping -c 2 alpine3
```

From `alpine1`, you can't connect to `alpine3`, because it's on a different network <Cite n={5} />. The tutorial's run printed these two lines, among others, and the second `docker exec` exited with 1:

```text
2 packets transmitted, 2 packets received, 0% packet loss
ping: bad address 'alpine3'
```

**5. Look at what the containers use.** By default, a container has no resource constraints <Cite n={10} />. `-m` sets the maximum amount of memory the container can use <Cite n={10} />. `docker stats` displays a live stream of container resource usage statistics; `--no-stream` only pulls the first result <Cite n={8} />. `docker system df` shows Docker disk usage <Cite n={11} />:

```bash
docker run -dit --name alpine4 -m 64m alpine ash
docker stats --no-stream alpine1 alpine4
docker system df
```

The tutorial's run printed this for `docker stats`:

```text
CONTAINER ID   NAME      CPU %     MEM USAGE / LIMIT   MEM %     NET I/O         BLOCK I/O   PIDS
59221f342cc3   alpine1   0.00%     536KiB / 30.16GiB   0.00%     9.87kB / 406B   0B / 0B     1
2f4caa24caf0   alpine4   0.00%     528KiB / 64MiB      0.81%     644B / 84B      0B / 0B     1
```

The limit of `alpine1`, which has no `-m`, was the memory of the whole host (30.16GiB); the limit of `alpine4` was 64MiB. `docker system df` printed one row each for images, containers, local volumes, and build cache, with the columns `TOTAL`, `ACTIVE`, `SIZE`, and `RECLAIMABLE`.

**6. Clean up.** Docker's tutorial stops and removes the containers, then removes the network <Cite n={5} />. `docker volume rm` removes the volume <Cite n={2} />:

```bash
docker container stop alpine1 alpine2 alpine3 alpine4
docker container rm alpine1 alpine2 alpine3 alpine4
docker network rm alpine-net
docker volume rm myvol2
rm -rf reports typo-dir result-copy.txt
```

In the tutorial's run, the last line worked without `sudo`.

</Technical>

The last command starts a new container with the same volume. It printed `run 1: 12 passed`, the line that the removed container had written.

**2. Write a report to the host.** A bind mount puts a folder of the host into the container, and by default the container can write to it <Cite n={3} />:

```bash
mkdir reports
docker run --rm --mount type=bind,src="$(pwd)"/reports,dst=/reports alpine sh -c 'echo "1 passed" > /reports/result.txt'
cat reports/result.txt
```

In the tutorial's run, `cat` printed `1 passed`, and `ls -l reports` showed that `result.txt` belonged to `root`, not to the user who ran the command.

**3. See what a wrong path does.** By default, `--mount` does not make a folder that is missing on the host; it stops with an error <Cite n={3} />. With `--volume` (`-v`), Docker makes the missing folder on the host for you, and it is always a folder <Cite n={3} />:

```bash
docker run --rm --mount type=bind,src="$(pwd)"/no-such-dir,dst=/reports alpine ls /reports
docker run --rm -v "$(pwd)"/typo-dir:/reports alpine ls -la /reports
```

In the tutorial's run, the first command printed `docker: Error response from daemon: invalid mount config for type "bind": bind source path does not exist:` with the full path, and exited with code 125. The second one exited with 0: it made `typo-dir` on the host, owned by `root`, and `ls -la` in the container listed an empty `/reports`.

**4. Let containers find each other by name.** These commands follow Docker's tutorial on bridge networks that you create, with three containers instead of its four; the `-dit` flags mean detached, interactive, and with a TTY <Cite n={5} />. Docker's tutorial attaches to `alpine1` to run the ping <Cite n={5} />; here, `docker exec` runs it:

```bash
docker network create --driver bridge alpine-net
docker run -dit --name alpine1 --network alpine-net alpine ash
docker run -dit --name alpine2 --network alpine-net alpine ash
docker run -dit --name alpine3 alpine ash
docker exec alpine1 ping -c 2 alpine2
docker exec alpine1 ping -c 2 alpine3
```

From `alpine1`, you cannot reach `alpine3`, because it is on another network <Cite n={5} />. The tutorial's run printed these two lines, among others, and the second `docker exec` exited with 1:

```text
2 packets transmitted, 2 packets received, 0% packet loss
ping: bad address 'alpine3'
```

**5. Look at what the containers use.** By default, a container has no limits <Cite n={10} />. `-m` sets the most memory that the container can use <Cite n={10} />. `docker stats` shows a live stream of how much the containers use; `--no-stream` shows only the first result <Cite n={8} />. `docker system df` shows how much disk Docker uses <Cite n={11} />:

```bash

docker stats --no-stream alpine1 alpine4
docker system df
```

The tutorial's run printed this for `docker stats`:

```text

59221f342cc3   alpine1   0.00%     536KiB / 30.16GiB   0.00%     9.87kB / 406B   0B / 0B     1
2f4caa24caf0   alpine4   0.00%     528KiB / 64MiB      0.81%     644B / 84B      0B / 0B     1
```

The limit of `alpine1`, which has no `-m`, was the memory of the whole host (30.16GiB); the limit of `alpine4` was 64MiB. `docker system df` printed one row each for images, containers, local volumes, and build cache, with the columns `TOTAL`, `ACTIVE`, `SIZE`, and `RECLAIMABLE`.

**6. Clean up.** Docker's tutorial stops and removes the containers, then removes the network <Cite n={5} />. `docker volume rm` removes the volume <Cite n={2} />:

```bash

docker container rm alpine1 alpine2 alpine3 alpine4
docker network rm alpine-net
docker volume rm myvol2
rm -rf reports typo-dir result-copy.txt
```

In the tutorial's run, the last line worked without `sudo`.

## How a tester uses it

<Voices>
<Technical>

**Prepare test data once.** New volumes can have their content pre-populated by a container or build <Cite n={2} />. Mounting an empty volume over files copies those files into the volume, which is a good way to pre-populate data that another container needs <Cite n={2} />. Volumes can be more safely shared among multiple containers <Cite n={2} />.

**Use fast, throwaway data.** If your container generates non-persistent state data, a tmpfs mount avoids storing the data anywhere permanently, and increases the container's performance by avoiding writing into the container's writable layer <Cite n={2} />. Unlike volumes and bind mounts, you can't share tmpfs mounts between containers, and tmpfs is only available if you're running Docker on Linux <Cite n={4} />.

**Get the evidence out.** `docker cp` copies files or folders between a container and the local filesystem <Cite n={7} />. The container can be a running or stopped container <Cite n={7} />. Files copied to the local machine are created with the UID:GID of the user which invoked the `docker cp` command <Cite n={7} />:

```bash
docker cp <container>:/path/in/container/report.txt ./report.txt
```

**Reach services by name.** Put the application and the test container on one user-defined network, so that DNS resolves the container names <Cite n={5} />. Give the containers names, because automatic service discovery does not resolve default generated names <Cite n={5} />.

**Know where the logs go.** By default, `docker logs` shows the command's STDOUT and STDERR <Cite n={9} />. A web server or a database may send its output to log files instead <Cite n={9} />. For example, the official nginx image creates symbolic links from its log files to `/dev/stdout` and `/dev/stderr` <Cite n={9} />.

**Test with limits.** By default, a container has no resource constraints and can use as much of a given resource as the host's kernel scheduler allows <Cite n={10} />. `-m` (`--memory`) sets the maximum amount of memory the container can use, and `--cpus` how much of the available CPU resources it can use <Cite n={10} />. On Linux hosts, when there isn't enough memory for important system functions, the kernel throws an Out Of Memory Exception and starts killing processes <Cite n={10} />. Docker's advice is to perform tests to understand the memory requirements of your application before placing it into production <Cite n={10} />.

</Technical>

## Common mistakes

<Voices>
<Technical>

- **A typo in a `-v` path.** With `--volume`, Docker creates a missing host directory for you <Cite n={3} />. In step 3 of the tutorial's run, the container then saw an empty folder. Use `--mount`, which produces an error when the source path doesn't exist <Cite n={3} />.
- **Mounting over files that the image needs.** The pre-existing files are obscured by the mount <Cite n={2} />. With containers, there's no straightforward way of removing a mount to reveal the obscured files again <Cite n={2} />.
- **A writable bind mount of your work.** Bind mounts have write access to files on the host by default <Cite n={3} />. Add `readonly` (`ro`) when the container only needs to read <Cite n={3} />.
- **Expecting names on the default bridge.** On the default bridge network, containers can't resolve each other by name <Cite n={5} />.
- **Expecting tmpfs data to stay.** When the container stops, the tmpfs mount is removed, and files written there won't be persisted <Cite n={4} />.
- **Letting unused volumes pile up.** A volume that no running container uses isn't removed automatically <Cite n={2} />. `docker volume prune` removes unused volumes <Cite n={2} />.
- **Pruning a shared machine.** `docker system prune` removes all unused containers, networks, images (both dangling and unused), unused build cache, and optionally, volumes <Cite n={12} />. Without options, its warning lists all stopped containers, all networks not used by at least one container, all dangling images, and unused build cache <Cite n={12} />. `--all` removes all unused images, not just dangling ones, and `--volumes` prunes anonymous volumes <Cite n={12} />.

</Technical>
<Layman>

- **A typo in a `-v` path.** With `--volume`, Docker makes a missing host folder for you <Cite n={3} />. In step 3 of the tutorial's run, the container then saw an empty folder. Use `--mount`, which stops with an error when the folder does not exist <Cite n={3} />.
- **Mounting over files that the image needs.** The mount hides the files that were there <Cite n={2} />. With containers, there is no easy way to take the mount away and see the hidden files again <Cite n={2} />.
- **A writable bind mount of your work.** By default, a bind mount can write to files on the host <Cite n={3} />. Add `readonly` (`ro`) when the container only needs to read <Cite n={3} />.
- **Expecting names on the default bridge.** On the default bridge network, containers cannot find each other by name <Cite n={5} />.
- **Expecting tmpfs data to stay.** When the container stops, the tmpfs mount is removed, and the files in it are gone <Cite n={4} />.
- **Letting unused volumes pile up.** A volume that no running container uses is not removed by itself <Cite n={2} />. `docker volume prune` removes unused volumes <Cite n={2} />.
- **Pruning a shared machine.** `docker system prune` removes all unused containers, networks, images (both dangling and unused), unused build cache, and, if you ask, volumes <Cite n={12} />. Without options, its warning lists all stopped containers, all networks that no container uses, all dangling images, and unused build cache <Cite n={12} />. `--all` removes all unused images, not only dangling ones, and `--volumes` removes anonymous volumes <Cite n={12} />.

</Layman>
<Bangla>

- **`-v` path-এ বানান ভুল।** `--volume` দিলে Docker host-এ না থাকা directory আপনার জন্য তৈরি করে <Cite n={3} />। টিউটোরিয়ালের run-এর ধাপ ৩-এ container তখন একটা খালি folder দেখেছে। `--mount` ব্যবহার করুন, source path না থাকলে এটা error দেয় <Cite n={3} />।
- **image-এর দরকারি file-এর ওপর mount করা।** আগে থেকে থাকা file-গুলো mount-এর আড়ালে ঢাকা পড়ে <Cite n={2} />। container-এ mount সরিয়ে ঢাকা file আবার দেখার সহজ কোনো উপায় নেই <Cite n={2} />।
- **নিজের কাজের writable bind mount।** default-ভাবে bind mount-এর host-এর file-এ লেখার অধিকার থাকে <Cite n={3} />। container-এর শুধু পড়ার দরকার হলে `readonly` (`ro`) যোগ করুন <Cite n={3} />।
- **default bridge-এ নাম কাজ করবে ভাবা।** default bridge network-এ container-গুলো নাম দিয়ে একে অপরকে খুঁজে পায় না <Cite n={5} />।
- **tmpfs-এর data থেকে যাবে ভাবা।** container থামলে tmpfs mount সরিয়ে ফেলা হয়, আর সেখানে লেখা file টিকে থাকে না <Cite n={4} />।
- **অব্যবহৃত volume জমতে দেওয়া।** কোনো চলমান container ব্যবহার করছে না এমন volume নিজে থেকে মোছে না <Cite n={2} />। `docker volume prune` অব্যবহৃত volume মুছে দেয় <Cite n={2} />।
- **shared machine-এ prune করা।** `docker system prune` সব অব্যবহৃত container, network, image (dangling ও unused দুটোই), অব্যবহৃত build cache, আর চাইলে volume-ও মুছে দেয় <Cite n={12} />। কোনো option ছাড়া এর warning-এ থাকে সব থেমে থাকা container, অন্তত একটা container ব্যবহার করছে না এমন সব network, সব dangling image আর অব্যবহৃত build cache <Cite n={12} />। `--all` শুধু dangling নয়, সব অব্যবহৃত image মুছে দেয়, আর `--volumes` anonymous volume মুছে দেয় <Cite n={12} />।

## Key words

| Term | Meaning |
|---|---|
| Writable container layer | Where the files created inside a container are stored; its data doesn't persist when the container is destroyed |
| Volume | A persistent data store for containers, created and managed by Docker |
| Anonymous volume | A volume with a random name; it stays after its container is removed, unless the container was started with `--rm` |
| Bind mount | A file or directory on the host machine mounted into a container; writable by default |
| tmpfs mount | A temporary mount in the host memory, removed when the container stops |
| `--mount` | The preferred, more explicit flag to mount; for a bind mount it errors when the source path doesn't exist |
| `--volume` (`-v`) | The short flag to mount; for a bind mount it creates a missing host directory |
| `readonly` (`ro`) | The option that prevents the container from writing to the mount |
| Default bridge network | The network of containers started without `--network`; no name resolution |
| User-defined bridge network | A network made with `docker network create`; containers resolve each other by name |
| `docker cp` | Copies files or folders between a container, running or stopped, and the local filesystem |
| `docker stats` | Displays a live stream of container resource usage statistics |
| `-m` (`--memory`) | The maximum amount of memory that a container can use |
| `docker system prune` | Removes stopped containers, unused networks, dangling images, and unused build cache; `--all` and `--volumes` remove more |
