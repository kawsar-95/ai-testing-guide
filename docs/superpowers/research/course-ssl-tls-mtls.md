| C1 | The main goal of TLS is a secure channel between two peers. It needs only a reliable, in-order data stream from the transport. | S1 s1 | "The primary goal of TLS is to provide a secure channel between two communicating peers; the only requirement from the underlying transport is a reliable, in-order data stream." |
| C2 | The channel should give authentication, confidentiality, and integrity. | S1 s1 | "the secure channel should provide the following properties: - Authentication ... - Confidentiality ... - Integrity" |
| C3 | The server side is always authenticated. The client side is optionally authenticated. | S1 s1 | "The server side of the channel is always authenticated; the client side is optionally authenticated." |
| C4 | Confidentiality: data after establishment is only visible to the endpoints. The size of the data is not hidden, unless the endpoints pad it. | S1 s1 | "Data sent over the channel after establishment is only visible to the endpoints. TLS does not hide the length of the data it transmits, though endpoints are able to pad TLS records in order to obscure lengths and improve protection against traffic analysis techniques." |
| C5 | Integrity: data cannot be modified by attackers without detection. | S1 s1 | "Data sent over the channel after establishment cannot be modified by attackers without detection." |
| C6 | These properties should hold even against an attacker with complete control of the network. | S1 s1 | "These properties should be true even in the face of an attacker who has complete control of the network" |
| C7 | TLS has two parts: a handshake protocol (authenticates the parties, negotiates parameters, sets up shared keys) and a record protocol (protects the traffic with the keys). | S1 s1 | "A handshake protocol ... that authenticates the communicating parties, negotiates cryptographic modes and parameters, and establishes shared keying material." / "A record protocol ... uses the parameters established by the handshake protocol to protect traffic" |
| C8 | (Common mistakes, RFC 8446 half only, cite n=1) The RFC leaves it to the protocol above TLS to decide how to read the certificates that were exchanged. The other half of that bullet (TLS does not test how the application treats the data, so a site can use TLS and still have login bugs) is the tutorial's own advice and has no cite. | S1 s1 | "The TLS standard, however, does not specify how protocols add security with TLS; how to initiate TLS handshaking and how to interpret the authentication certificates exchanged are left to the judgment of the designers and implementors of protocols that run on top of TLS." |
| C9 | In the handshake, the server sends a CertificateRequest if certificate-based client authentication is wanted. This message is omitted if client authentication is not desired." |
| C10 | Certificate carries the certificate of the endpoint. The client omits it if the server did not send CertificateRequest. | S1 s2 | "Certificate: The certificate of the endpoint ... omitted ... by the client if the server did not send CertificateRequest" |
| C11 | CertificateVerify is a signature over the whole handshake, made with the private key that matches the public key in the Certificate message. | S1 s2 | "CertificateVerify: A signature over the entire handshake using the private key corresponding to the public key in the Certificate message." |
| C12 | TLS 1.3 supersedes and obsoletes earlier TLS versions, including 1.2. | C13 | RFC 8446 is dated August 2018 (TLS 1.3). | S1 header | "RFC 8446 TLS August 2018" |

| C15 | SSLv3 was released in 1996. TLS 1.0 replaced it in 1999, TLS 1.1 in 2002, TLS 1.2 in 2006. | S2 s1 | "Since it was released in 1996, the SSLv3 protocol ... Despite being replaced by TLS 1.0 in 1999, and subsequently TLS 1.1 in 2002 and 1.2 in 2006" |
| C16 | SSLv3 had a long series of attacks on its key exchange and its encryption; many TLS implementations still allowed it. | S2 s1 | "has been subject to a long series of attacks, both on its key exchange mechanism and on the encryption schemes it supports." / "many implementations of TLS have permitted the negotiation of SSLv3" |

| C18 | Any version of TLS is more secure than SSLv3, but the highest available version is preferable. | S2 s3 | "Any version of TLS is more secure than SSLv3, though the highest version available is preferable." |

| C21 | TLS 1.0 and 1.1 lack support for current cryptographic algorithms; profiles now require avoiding them. | S3 abstract | "These versions lack support for current and recommended cryptographic algorithms and mechanisms, and various government and industry profiles of applications using TLS now mandate avoiding these old TLS versions." |
| C22 | TLS 1.0 and TLS 1.1 must not be used. Negotiation must not be permitted. | S3 s4, s5 | "TLS 1.0 MUST NOT be used. Negotiation of TLS 1.0 from any version of TLS MUST NOT be permitted." (same for 1.1, line 310) |

| C24 | TLS 1.2 became the recommended version for IETF protocols in 2008, and TLS 1.3 obsoleted it in 2018. | S3 abstract | "TLS version 1.2 became the recommended version for IETF protocols in 2008 (subsequently being obsoleted by TLS version 1.3 in 2018)" |
| C25 | TLS 1.0 and 1.1 use SHA-1 for handshake integrity and signatures; a downgrade attack on the handshake is possible with 2^77 operations, well below a modern margin; there is no way to pick a stronger hash, so the upgrade path is a newer version. | S3 s3 | "The integrity of both TLS 1.0 and TLS 1.1 depends on a running SHA-1 hash" / "making the only upgrade path the use of a newer protocol version." |
| C26 | MDN: TLS lets a client talk to a server over an untrusted network. It secures HTTP; the result is HTTPS. | S5 intro | "a protocol which enables a client to communicate securely with a server across an untrusted network. Most notably it's used to secure HTTP connections on the web: the resulting protocol is called HTTPS" |
| C27 | MDN: TLS secures the connection by encryption, integrity, and authentication. On the web, servers usually authenticate to clients, but clients usually do not authenticate to servers. | S5 intro | "On the web, servers usually authenticate themselves to clients, but clients don't usually authenticate themselves to servers." |
| C28 | MDN: the handshake sets the version, the cipher suite, optional mutual authentication, and a secret key. | S5 handshake | "Client and server agree on which version of TLS to use." / "Client and server agree on the cipher suite" / "Optionally, client and server authenticate each other." / "agree on a secret key" |
| C29 | MDN: TLS 1.3 (RFC 8446) is the current and most used version. TLS 1.2 is still used by some sites. TLS 1.1 and 1.0 should no longer be used. | S5 handshake | "The current version of TLS is 1.3 (RFC 8446), and this is the most widely-used version. TLS 1.2 is still used by some websites, and TLS 1.1 and 1.0 should no longer be used." |
| C30 | MDN: on the web, client authentication appears mostly in specialized applications. Server authentication is fundamental to web security. | C31 | MDN: after the handshake, both sides use the secret key to encrypt HTTP headers and bodies. | S5 handshake | "client and server use the secret key to encrypt and decrypt any messages, including HTTP headers as well as bodies." |
| C32 | MDN: for server authentication a site needs a digital certificate with a signed copy of the public key that matches the private key. | C33 | MDN: a Certification Authority (CA), for example Let's Encrypt, issues certificates. | S5 server auth | "Let's Encrypt is a widely used nonprofit Certification Authority which issues free TLS certificates." |

| C35 | MDN: mixed content (an HTTPS page that loads a subresource over HTTP) is unsafe; browsers upgrade or block it. | S5 mixed | "Mixed content is unsafe because the subresources don't get the protection that HTTPS offers" / "they either upgrade the load request to use HTTPS, or block the request entirely." |
| C36 | RFC 8705: it defines two ways to use mTLS client certificates for OAuth client authentication. | C37 | RFC 8705: the client Certificate and CertificateVerify messages are sent in the handshake. | S4 s2 | "(i.e., the client Certificate and CertificateVerify messages are sent during the TLS handshake)" |
| C38 | RFC 8705: the client sends client_id; the server checks the certificate against what it expects for that client; no certificate or a mismatch gives an invalid_client error. | S4 s2 | "If no certificate is presented, or that which is presented doesn't match that which is expected for the given "client_id", the authorization server returns a normal OAuth 2.0 error response ... with the "invalid_client" error code" |
| C39 | RFC 8705 PKI method: relies on a validated certificate chain and one subject DN or SAN; revocation checking is a deployment decision. | S4 s2.1 | "It relies on a validated certificate chain [RFC5280] and a single subject distinguished name (DN) or a single subject alternative name (SAN)" / "if and how to check a certificate's revocation status is a deployment decision at the discretion of the authorization server" |
| C40 | RFC 8705 self-signed method: the client registers its certificates; the chain is not validated; success if the certificate matches a registered one; no need to maintain a PKI. | S4 s2.2 | "the client's certificate chain is not validated by the server in this case. ## Not on the page

- The origin of the name "SSL" and the story of the rename are not in the sources, so the page does not tell it. The sentence that people still say "SSL" is the tutorial's own observation and is marked so.
- The page gives no cipher-suite list, no attack steps, and no tool commands for attacks. The tester examples (checking versions, expiry, the client-certificate case) are the tutorial's own text with no cite.
- The page does not say that TLS makes an app secure. C8 shows that TLS does not cover how the protocol above it uses it.
