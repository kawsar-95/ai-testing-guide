## Claims

| # | Claim on the page | Source | Quote |
|---|---|---|---|
| C1 | A consistent hash function is one that changes minimally when the range of the function (the set of buckets) changes. | S1 abstract | "Roughly speaking, a consistent hash function is one which changes minimally as the range of the function changes." |
| C2 | Unlike standard hashing, a small change in the set of buckets does not remap all items. | S1 section 1.1 | "Unlike standard hashing schemes, a small change in the bucket set does not induce a total remapping of items to buckets." |
| C3 | With a plain modulo hash, when the range changes almost every item hashes to a new place, so cached data becomes useless. | S1 section 4 | "When the range of the hash function (p in the example) changed, almost every item would be hashed to a new location. Suddenly, all cached data is useless because clients are looking for it in a different location." |
| C4 | Cassandra: naive hashing takes the hash of the key modulo the number of buckets, and adding one node can invalidate almost all mappings. | S3 | "you typically allocate keys to buckets by taking a hash of the key modulo the number of buckets" / "adding a single node might invalidate almost all of the mappings." |
| C5 | Consistent hashing only moves a small fraction of keys when the number of nodes changes. | S3 | "when the number of nodes (buckets) to hash into changes, consistent hashing only has to move a small fraction of the keys." |
| C6 | Smoothness: when a machine is added or removed, the expected fraction of objects that move is the minimum needed to keep the load balanced. | S1 section 1.2 (before 4.1) | "When a machine is added to or removed from the set of caches, the expected fraction of objects that must be moved to a new cache is the minimum needed to maintain a balanced load across the caches." |
| C7 | Monotone: when new buckets are added, an item may move from an old bucket to a new bucket, but not from one old bucket to another. | S1 section 4.1 | "then an item may move from an old bucket to a new bucket, but not from one old bucket to another." |
| C8 | The paper's construction maps buckets and items to points on the unit interval (a circle), an item goes to the closest bucket point, and each bucket gets more than one point (about log C). | S1 section 4.2 | "rB maps buckets randomly to the unit interval, and rI does the same for items. fV(i) is defined to be the bucket b that minimizes |rB(b) - rI(i)|." / "we actually need to have more than one point in the unit interval associated with each bucket." |
| C9 | Dynamo: the output range of the hash function is a fixed circular space or ring. The largest value wraps around to the smallest. | S2 4.2 | "the output range of a hash function is treated as a fixed circular space or 'ring' (i.e. the largest hash value wraps around to the smallest hash value)." |
| C10 | Dynamo: each node gets a random value in this space, its position on the ring. | S2 4.2 | "Each node in the system is assigned a random value within this space which represents its 'position' on the ring." |
| C11 | Dynamo: a key is hashed to a position, then the ring is walked clockwise to the first node with a larger position. | S2 4.2 | "hashing the data item's key to yield its position on the ring, and then walking the ring clockwise to find the first node with a position larger than the item's position." |
| C12 | Dynamo: each node is responsible for the region between it and its predecessor. Departure or arrival of a node only affects its immediate neighbours. | S2 4.2 | "each node becomes responsible for the region in the ring between it and its predecessor node on the ring. The principle advantage of consistent hashing is that departure or arrival of a node only affects its immediate neighbors and other nodes remain unaffected." |
| C13 | Dynamo: Dynamo hashes the key with MD5 to a 128-bit identifier. | S2 4.1 | "It applies a MD5 hash on the key to generate a 128-bit identifier" |
| C14 | Dynamo: the basic algorithm has two problems: random positions give uneven data and load, and it ignores differences in node performance. | S2 4.2 | "the random position assignment of each node on the ring leads to non-uniform data and load distribution. Second, the basic algorithm is oblivious to the heterogeneity in the performance of nodes." |
| C15 | Dynamo: virtual nodes. A node gets several positions ("tokens"). A virtual node looks like a single node, but a node can be responsible for more than one. | S2 4.2 | "instead of mapping a node to a single point in the circle, each node gets assigned to multiple points in the ring." / "A virtual node looks like a single node in the system, but each node can be responsible for more than one virtual node." |
| C16 | Dynamo: benefits of virtual nodes: when a node is unavailable, its load is spread across the other nodes. A new or returning node accepts a roughly equal amount of load from each other node. The number of virtual nodes can follow node capacity. | S2 4.2 | "the load handled by this node is evenly dispersed across the remaining available nodes." / "accepts a roughly equivalent amount of load from each of the other available nodes." / "decided based on its capacity" |
| C17 | Cassandra: each node maps to one or more tokens on a continuous hash ring. A key is hashed onto the ring and the ring is walked in one direction. | S3 | "Cassandra instead maps every node to one or more tokens on a continuous hash ring, and defines ownership by hashing a key onto the ring and then 'walking' the ring in one direction" |
| C18 | Cassandra: with replication factor 3, the key is hashed to a token, and the ring is walked clockwise until three distinct nodes are found. These are the replicas. | S3 | "we 'walk' the ring in a clockwise fashion until we encounter three distinct nodes, at which point we have found all the replicas of that key." |
| C19 | Cassandra: single-token consistent hashing with a small number of nodes makes adding a few nodes hard, because no token choice keeps the ring balanced. Uneven token ranges give uneven request load. | S3 | "with evenly spaced tokens and a small number of physical nodes, incremental scaling (adding just a few nodes of capacity) is difficult because there are no token selections for new nodes that can leave the ring balanced." / "uneven token ranges lead to uneven request load." |
| C20 | Cassandra: vnodes give a physical node many tokens, so one added node takes many smaller pieces of data from many neighbours. | S3 | "assigning multiple tokens in the token ring to each physical node" / "taking many smaller pieces of data from more ring neighbors when we add even a single node." |
| C21 | Cassandra terms: a token is a single position on the ring; a vnode is a token owned by the same physical node (same host id). | S3 | "Token: A single position on the Dynamo-style hash ring." / "Virtual Node (or vnode): A token on the hash ring owned by the same physical node" |
| C22 | Cassandra: costs of many tokens: more token neighbours (up to 2 * (RF - 1) per token), so more failure combinations that lose availability for part of the ring; repair and maintenance can be slower. | S3 | "Every token introduces up to 2 * (RF - 1) additional neighbors on the token ring, which means that there are more combinations of node failures where we lose availability for a portion of the token ring." / "Cluster-wide maintenance operations are often slowed." |
| C23 | Cassandra: in 2.x only random token choice existed, so the default was a high 256 tokens; from 3.x a deterministic allocator picks tokens for balance with far fewer tokens. | S3 | "in Cassandra 2.x, the only token allocation algorithm available was picking random tokens, which meant that to keep balance the default number of tokens per node had to be quite high, at 256." / "in 3.x+ a new deterministic token allocator was added" |
| C24 | Cassandra: a token range maps to the same set of nodes (for example the keys in range (t1, t2] are on nodes 2, 3 and 4 in the eight-node example). | S3 | "ranges of keys, also known as token ranges, map to the same physical set of nodes." |
| C25 | Cassandra replicates every partition to many nodes. The ring step picks the owners. | S3 | "Cassandra replicates every partition of data to many nodes across the cluster to maintain high availability and durability." |
| C26 | Key words: RF is the replication factor used when walking the ring to find the replica nodes. | S3 | "an eight node cluster with evenly spaced tokens, and a replication factor (RF) of 3 ... three distinct nodes ... all the replicas of that key." |
