## Claims

| # | Claim on the page | Source | Quote |
|---|---|---|---|
| C1 | PACELC (said "pass-elk"): if there is a partition (P), the system trades availability (A) against consistency (C); else (E), in normal running, it trades latency (L) against consistency (C). | S1 p.41 | "rewriting CAP as PACELC (pronounced “pass-elk”): if there is a partition (P), how does the system trade off availability and consistency (A and C); else (E), when the system is running normally in the absence of partitions, how does the system trade off latency (L) and consistency (C)?" |
| C2 | The paper says CAP is often misunderstood: CAP sets limits only when certain failures happen, and does not limit a system in normal operation. | S1 p.37 | "In reality, CAP only posits limitations in the face of certain types of failures, and does not constrain any system capabilities during normal operation." |
| C3 | The trade between consistency and availability needs two things together: partition tolerance and a real partition. | S1 p.38 | "it is the combination of • partition tolerance and • the existence of a network partition itself." |
| C4 | Network partitions are somewhat rare, and often rarer than other serious failures. | S1 p.38 | "in general, network partitions are somewhat rare, and are often less frequent than other serious types of failure events in DDBSs." |
| C5 | A trade-off between consistency and latency exists even when there is no partition. It is separate from the CAP trade-offs. | S1 p.39 | "This tradeoff exists even when there are no network partitions, and thus is completely separate from the tradeoffs CAP describes." |
| C6 | Why: a high-availability need means the system must replicate data, because a failed component makes its data unavailable if there is no other copy. | S1 pp.39-40 | "a high availability requirement implies that the system must replicate data." / "all data that component controlled will become unavailable unless the system replicated another version of the data prior to the failure." |
| C7 | The latency/consistency part (ELC) applies only to systems that replicate data. | S1 p.41 | "the latency/consistency tradeoff (ELC) only applies to systems that replicate data." |
| C8 | Synchronous replication: the master waits until the replicas have the update. Replicas stay consistent, but the wait adds latency, over a WAN especially, and the slowest entity limits the speed. | S1 p.39 | "The replication is synchronous: the master node waits until all updates have made it to the replica(s). This ensures that the replicas remain consistent, but synchronous actions across independent entities, especially over a WAN, increase latency ... latency is limited by the slowest entity." |
| C9 | Asynchronous replication: the system treats the update as done before it has been copied. If reads can go to any node, read latency is better, but reads of the same item can be inconsistent while updates spread. | S1 pp.39-40 | "The replication is asynchronous: the system treats the update as if it were completed before it has been replicated." / "If the system can serve reads from any node, read latency is much better, but this can also result in inconsistent reads of the same data item" |
| C10 | Quorum rule: with N replicas, W nodes in a synchronous write and R nodes in a synchronous read, R + W > N can keep consistency (with the latency costs, to a lesser degree), and R + W <= N allows inconsistent reads. | S1 p.40 | "when R + W > N in a quorum protocol, where R is the number of nodes involved in a synchronous read, W is the number of nodes involved in a synchronous write, and N is the number of replicas—then consistency can be preserved." / "when R + W ≤ N, then inconsistent reads are possible" |
| C11 | Over a WAN there is no way around the trade-off. Over short distances, options such as (2)(a) (synchronous replication from a master) are reasonable, because network latency is small in a local data center. | S1 p.40 | "for carefully controlled replication across short distances, reasonable options such as (2)(a) exist because network communication latency is small in local datacenters; however, for replication over a WAN, there is no way around the consistency/latency tradeoff." |
| C12 | The paper cites studies that say a delay as small as 100 ms can strongly reduce the chance that a customer keeps using a site or comes back. | S1 p.39 | "Studies indicate that latency is a critical factor in online interactions: an increase as small as 100 ms can dramatically reduce the probability that a customer will continue to interact or return in the future." |
| C13 | The paper treats availability and latency as nearly the same thing: an unavailable system gives extremely high latency. For the paper, a latency above a typical request timeout (a few seconds) is "unavailable". | S1 p.39 | "availability and latency are arguably the same thing: an unavailable system essentially provides extremely high latency. ... I consider systems with latencies larger than a typical request timeout, such as a few seconds, as unavailable" |
| C14 | A cited study of Cassandra compared "weak reads" (any replica) with "quorum reads" (check several replicas). Quorum reads give more consistency and cost more latency, a factor of four or more. | S1 p.40-41 | "The second option clearly increases consistency at the cost of additional latency relative to the first option. The difference in latency between these two options can be a factor of four or more." |
| C15 | The paper says the default versions of Dynamo, Cassandra, and Riak are PA/EL: in a partition they give up consistency for availability, and in normal running they give up consistency for lower latency. | S1 p.42 | "The default versions of Dynamo, Cassandra, and Riak are PA/EL systems: if a partition occurs, they give up consistency for availability, and under normal operation they give up consistency for lower latency." |
| C16 | These systems have settings that a user can change. A higher R + W gives more consistency at the cost of latency, but not the full consistency of the CAP proof. | S1 p.42 | "these systems have user-adjustable settings to alter the ELC tradeoff—for example, by increasing R + W, they gain more consistency at the expense of latency (although they cannot achieve full consistency as defined by Gilbert and Lynch, even if R + W > N)." |
| C17 | The paper focuses on the original design of the systems. Some became adjustable after the first versions. | S1 p.38 | "(Although consistency of some of these systems became adjustable after the initial versions were released, the focus here is on their original design.)" |
| C18 | The paper says fully ACID systems such as VoltDB/H-Store and Megastore are PC/EC: they refuse to give up consistency and pay the cost in availability and latency. BigTable and related systems such as HBase are also PC/EC. | S1 p.42 | "Fully ACID systems such as VoltDB/H-Store and Megastore are PC/EC: they refuse to give up consistency, and will pay the availability and latency costs to achieve it. BigTable and related systems such as HBase are also PC/EC." |
| C19 | The paper classes MongoDB as PA/EC: consistent reads and writes in the base case. If the master fails or is cut off, the rest of the system elects a new master, so the old and new masters can differ until a repair. | S1 p.42 | "MongoDB can be classified as a PA/EC system. In the baseline case, the system guarantees reads and writes to be consistent." / "the rest of the system elects a new master to remain available for reads and writes. Therefore, the state of the old master and the state of the new master become inconsistent until the system repairs the failure" |
| C20 | The paper classes PNUTS as PC/EL: in normal running it gives up consistency for latency, and in a partition it gives up availability for consistency. | S1 p.42 | "PNUTS is a PC/EL system. In normal operation, it gives up consistency for latency; however, if a partition occurs, it trades availability for consistency." |
| C21 | PC does not mean the system is fully consistent. It means the system does not lower consistency below its normal level in a partition, and lowers availability instead. | S1 p.42 | "PC does not indicate that the system is fully consistent; rather it indicates that the system does not reduce consistency beyond the baseline consistency level when a network partition occurs—instead, it reduces availability." |
| C22 | The paper says that neither CAP nor PACELC can explain all the trade-offs of distributed databases. | S1 p.42 | "neither CAP nor PACELC can explain them all." |
| C23 | In CAP's proof, "consistency" means a strict kind: the system acts as if it ran on a single node and answered one operation at a time. | S1 p.38 | "requests of the distributed shared memory to act as if they were executing on a single node, responding to operations one at a time." |
