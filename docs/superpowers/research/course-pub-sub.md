## Claims

| # | Claim on the page | Source | Quote |
|---|---|---|---|
| C1 | In pub/sub messaging a sender publishes events through an intermediary without knowing which consumers receive them. | S1 intro | "lets a sender publish events without knowing which consumers receive them" |
| C2 | If a sender talks directly to its consumers, it must know the identity and endpoint of each one, deliver to each, and handle failures one by one. Adding or removing a consumer needs a change in the sender. | S1 Context and problem | "it must know the identity and endpoint of every consumer, deliver messages to each consumer, and manage failures individually. Adding or removing a consumer requires changes to the sender" |
| C3 | A standard queue links a sender to a single consumer. For many consumers the sender needs a separate queue for each, which adds routing complexity and does not scale well. | S1 Context and problem | "A standard queue creates a direct relationship between a sender and a single consumer. To support multiple consumers, the sender must create a separate queue for each consumer" |
| C4 | The pattern has an input channel for the sender (the publisher), one output channel for each consumer (the subscribers), and a mechanism that copies each message from the input channel to the output channels of the interested subscribers. A message broker or event bus usually does the copying. | S1 Solution | "An input messaging channel that the sender uses." / "One output messaging channel for each consumer. The consumers are known as subscribers." / "A mechanism for copying each message from the input channel to the output channels for all subscribers interested in that message. An intermediary like a message broker or event bus typically handles this operation." |
| C5 | A message is a packet of data. An event is a message that tells other components about a change or action. The pattern usually works with events but also carries commands and state notifications. | S1 Solution note | "A message is a packet of data. An event is a message that notifies other components about a change or an action that occurs. This pattern typically works with events, but it also carries any type of message, including commands and state notifications." |
| C6 | Benefits: decoupling (the broker keeps messages if receivers are offline), sender returns to its work after sending one message, fault isolation (a subscriber failure does not affect the publisher or other subscribers), integration of different platforms and languages, testability (messages can be inspected or logged). | S1 benefits list | "the broker retains messages even if one or more receivers are offline" / "A subscriber failure doesn't affect the publisher or other subscribers" / "messages are available for inspection or logging as part of an integration test strategy" |
| C7 | Subscribers usually want only a subset of messages. Two ways: topics (each topic has its own output channel; a consumer subscribes to the relevant topics) and content filtering (the broker inspects the content; a subscriber says what it needs). | S1 Subsets of messages | "Topics: Each topic has a dedicated output channel, and each consumer can subscribe to all relevant topics." / "Content filtering: The broker inspects and distributes messages based on their content." |
| C8 | Topic size choice: broad topics are simpler to manage but subscribers must filter out messages they do not need; narrow topics reduce filtering but add more topics to manage. | S1 | "Broad topics are simpler to manage but require subscribers to filter out messages that they don't need. Narrow topics reduce subscriber-side filtering but increase the number of topics to manage." |
| C9 | Channels are unidirectional. If a subscriber must answer the publisher, use Request-Reply with a separate reply channel. | S1 Bidirectional communication | "Channels in a publish-subscribe system are unidirectional. If a subscriber needs to acknowledge or communicate status back to the publisher, use the Request-Reply pattern." |
| C10 | Order of receipt is not guaranteed and may differ from the order of creation. If order matters, a broker may offer ordered delivery within a partition or session, but that limits scalability. Design subscribers to work in any arrival order. | S1 Message ordering | "The order in which subscribers receive messages isn't guaranteed and doesn't necessarily reflect the order in which the sender created them." / "the broker might support ordered delivery within a partition or session, but that constrains scalability. Design subscribers to handle messages independently of arrival order." |
| C11 | Delivery guarantees: at-most-once can lose messages if the broker or subscriber fails; at-least-once delivers but can duplicate (for example when a sender fails after it posts and a new instance posts again); exactly-once removes duplicates but adds coordination overhead and latency. | S1 Delivery guarantees | "At-most-once delivery minimizes overhead but can lose messages if the broker or subscriber fails." / "At-least-once delivery ensures message delivery but can result in duplicates" / "Exactly-once delivery removes duplicates but adds coordination overhead and latency" |
| C12 | If the broker has no deduplication, design subscribers to handle messages idempotently. | S1 | "If your broker doesn't provide deduplication, design subscribers to handle messages idempotently." |
| C13 | Poison messages: a malformed message can make a service instance fail. Store its details elsewhere. Some brokers, such as Service Bus, offer dead-letter queues. | S1 Poison messages | "Capture and store these message details elsewhere for analysis. Some message brokers, like Service Bus, support this process through dead-letter queues." |
| C14 | Add a correlation ID to every message, because the broker makes the end-to-end flow harder to trace. | S1 Correlation | "The broker decouples publishers from subscribers, which makes it harder to trace the end-to-end flow of a message. Include a correlation ID in every message" |
| C15 | When subscribers fall behind, messages pile up in the broker and can use up its resources. | S1 Backpressure | "unprocessed messages accumulate in the broker and can deplete its resources" |
| C16 | Use pub/sub when: broadcast to many consumers; independently developed consumers; no real-time reply needed; eventual consistency is acceptable; consumers have different uptime from the sender. | S1 When to use | "An application needs to broadcast information to a significant number of consumers." / "An application can send information to consumers without requiring real-time responses from them." / "The systems being integrated are designed to support an eventual consistency model for their data." |
| C17 | It may not suit: only a few consumers that need very different data (broker overhead adds complexity; direct calls or separate queues may fit better); near real-time interaction (the broker adds latency; use request-reply); a strict guaranteed order; one atomic transaction across publisher and consumers (pub/sub is asynchronous and eventually consistent; consider a database transaction or the Saga pattern). | S1 When not | "The overhead of a broker adds complexity without any scaling benefit." / "The pub/sub model introduces latency through the broker." / "Pub/Sub systems generally don't guarantee ordering across subscribers" / "Pub/Sub messaging is inherently asynchronous and eventually consistent." |
| C18 | Google: publishers broadcast events asynchronously instead of synchronous RPCs. Publishers send events without regard to how or when they are processed, and Pub/Sub delivers them to all services that react. | S2 | "Publishers communicate with subscribers asynchronously by broadcasting events, rather than by synchronous remote procedure calls (RPCs)." / "Publishers send events to the Pub/Sub service, without regard to how or when these events are to be processed. Pub/Sub then delivers events to all the services that react to them." |
| C19 | Google lists use cases: ingesting events, real-time event distribution, distributing change events from databases, parallel processing of tasks, refreshing distributed caches (invalidation events). | S2 Common use cases | "Real-time event distribution." / "Replicating data among databases." / "Refreshing distributed caches. For example, an application can publish invalidation events" |
| C20 | Google Pub/Sub is for service-to-service communication, not for end-user or IoT clients. | S2 | "Pub/Sub is intended for service-to-service communication rather than communication with end-user or IoT clients." |
| C21 | Google definitions: publisher creates messages and sends them to a topic; topic is a named entity that represents a feed of messages; subscription is a named entity that represents an interest in receiving messages on a topic; subscriber receives messages on a subscription. | S3 components | "Topic: a named entity that represents a feed of messages." / "Subscription: a named entity that represents an interest in receiving messages on a particular topic." |
| C22 | Fan-out: a topic attached to two subscriptions; each subscription receives a copy of each message. Inside one subscription, the subscriber applications share the messages (a subset each). A subscription with a single subscriber gets all messages. | S3 workflow | "Each subscription receives a copy of A and B messages from the topic." / "The two subscriber applications receive a subset of the messages from the topic." / "Thus, Subscriber 3 receives all the messages from the topic." |
| C23 | Life of a message in Google Pub/Sub: publisher sends to a topic; message is written to storage; Pub/Sub delivers it to all attached subscriptions; subscriber sends an acknowledgment after processing; after at least one subscriber for each subscription has acknowledged, Pub/Sub deletes the message from storage. | S3 Life of a message | "A publisher application sends a message to a Pub/Sub topic. The message is written to storage." / "After at least one subscriber for each subscription has acknowledged the message, Pub/Sub deletes the message from storage." |
| C24 | While a message is outstanding, Pub/Sub does not try to give it to another subscriber of the same subscription. The subscriber has a configurable time, the ackDeadline. After it passes, the message is available again. | S3 Status of a message / S4 | "While a message is outstanding to a subscriber, Pub/Sub doesn't try to deliver it to any other subscriber on the same subscription." / "After the deadline passes, the message is no longer considered outstanding, and is available for delivery again." |
| C25 | An unacknowledged message may be delivered more than once (for example the ack comes after the deadline, or the ack is lost to a network issue). It is delivered until the retention duration ends. | S3 | "a message might be delivered more than once. For example, the subscriber might send an acknowledgment after the deadline expires or the acknowledgment might be lost due to transient network issues. | C26 | To receive messages you must create a subscription. Only messages published after the subscription exists are available to it. | C27 | Subscription types: pull (subscriber asks the server), push (the server sends requests to the subscriber app), export (to a Google Cloud resource such as BigQuery or Cloud Storage). | S4 | "Pull subscriptions use a subscriber client to request messages from the Pub/Sub server. | C28 | By default Pub/Sub gives at-least-once delivery with no ordering guarantee on all subscription types. Messages may be delivered out of order or more than once. Pub/Sub might redeliver even after a successful ack; this is rare, but any message can be redelivered at any time. The subscriber must be idempotent. | S4 Default properties | "By default, Pub/Sub offers at-least-once delivery with no ordering guarantees on all subscription types." / "although rare, any message can be redelivered at any time. | C29 | Pub/Sub also supports exactly-once delivery (an option). | S4 | "Pub/Sub also supports exactly-once delivery." |
| C30 | Ordering in Google Pub/Sub: set the same ordering key on related messages, publish them in the same region, and turn on message ordering in the subscription. Messages with an empty key are not ordered. Without the setting, a subscription gets no expected order. | S5 | "set the same ordering key on all related messages that should be received in order. | C31 | Ordering is per subscription: if two subscriptions are attached to one topic and ordering is on in only one, order is kept only for that one. | S5 | "Although both subscriptions receive the same set of messages from topic T, ordering is only preserved for subscription A." |
