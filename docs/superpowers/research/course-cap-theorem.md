## Claims

| # | Claim on the page | Source | Quote |
|---|---|---|---|
| C1 | Brewer made the conjecture in an invited talk at PODC 2000: a web service cannot give all of consistency, availability, and partition tolerance. | S1 1 | "At PODC 2000, Brewer, in an invited talk, made the following conjecture: it is impossible for a web service to provide the following three guarantees: Consistency, Availability, Partition-tolerance" |
| C2 | The 2002 paper proves the conjecture in the asynchronous network model. | S1 abstract | "we prove this conjecture in the asynchronous network model" |
| C3 | C (as the paper defines it) is atomic, also called linearizable, consistency: a total order of all operations such that each looks as if it completed at one instant. It is like one node answering one operation at a time. | S1 2.1 | "Atomic, or linearizable, consistency is the condition expected by most web services today. Under this consistency guarantee, there must exist a total order on all operations such that each operation looks as if it were completed at a single instant. This is equivalent to requiring requests of the distributed shared memory to act as if they were executing on a single node, responding to operations one at a time." |
| C4 | A: every request received by a non-failing node must result in a response, so an algorithm must eventually terminate. There is no bound on how long it may run. | S1 2.2 | "every request received by a non-failing node in the system must result in a response. That is, any algorithm used by the service must eventually terminate." / "it puts no bound on how long the algorithm may run before terminating" |
| C5 | A holds even when severe network failures occur: every request must end. | S1 2.2 | "even when severe network failures occur, every request must terminate." |
| C6 | P: the network may lose arbitrarily many messages from one node to another. When it is partitioned, all messages between components are lost. | S1 2.3 | "the network will be allowed to lose arbitrarily many messages sent from one node to another. When a network is partitioned, all messages sent from nodes in one component of the partition to nodes in another component are lost." |
| C7 | Theorem 1: in the asynchronous model it is impossible to implement a read/write object that guarantees availability and atomic consistency in all fair executions, including those where messages are lost. | S1 3.1 | "It is impossible in the asynchronous network model to implement a read/write data object that guarantees the following properties: Availability, Atomic consistency in all fair executions (including those in which messages are lost)." |
| C8 | Proof idea: split the nodes in two sets that lose all messages between them. A write in one set, then a read in the other, cannot return the new value. | S1 3.1 | "The basic idea of the proof is to assume that all messages between G1 and G2 are lost. If a write occurs in G1, and later a read occurs in G2, then the read operation cannot return the results of the earlier write operation." |
| C9 | In the asynchronous model a node cannot tell a lost message from a delayed one. | S1 3.1 Corollary 1.1 | "in the asynchronous model an algorithm has no way of determining whether a message has been lost, or has been arbitrarily delayed in the transmission channel." |
| C10 | Any two of the three can be achieved (asynchronous model). | S1 3.2 | "While it is impossible to provide all three properties: atomicity, availability, and partition tolerance, any two of these three properties can be achieved." |
| C11 | Atomic and partition tolerant without availability: for example a system that ignores all requests, or a single designated node. Many distributed databases give this kind of guarantee (locking or quorums); when certain failures occur the service no longer returns responses. | S1 3.2.1 | "The trivial system that ignores all requests meets these requirements." / "Many distributed databases provide this type of guarantee, especially algorithms based on distributed locking or quorums: if certain failure patterns occur, then the liveness condition is weakened and the service no longer returns responses." |
| C12 | Atomic and available without partitions: systems on intranets and LANs are an example. | S1 3.2.2 | "If there are no partitions, it is clearly possible to provide atomic, available data." / "Systems that run on intranets and LANs are an example of these types of algorithms." |
| C13 | Available and partition tolerant without atomic consistency: the service can return the initial value to every request; web caches are an example of a weakly consistent network. | S1 3.2.3 | "the service can trivially return v0, the initial value, in response to every request." / "Web caches are one example of a weakly consistent network." |
| C14 | The impossibility also holds in the partially synchronous model (clocks as timers, known message time bound). | S1 4.2 | "It is still impossible to have an always available, atomic data object when arbitrary messages may be lost, even in the partially synchronous model." |
| C15 | In the partially synchronous model, an algorithm can give atomic data when no message is lost, and only stale data when messages are lost. | S1 4.3 | "There are partially synchronous algorithms that will return atomic data when all messages in an execution are delivered (i.e., there are no partitions), and will only return inconsistent (and, in particular, stale) data when messages are lost." |
| C16 | The C of the paper is not the C of ACID: database consistency refers to transactions; atomic consistency refers to one request/response sequence. | S1 footnote 3 | "database consistency refers to transactions, while atomic consistency refers only to a property of a single request/response operation sequence." |
| C17 | Brewer originally required only almost all requests to get a response; the paper requires 100%. | S1 footnote 4 | "Brewer originally only required almost all requests to receive a response." |
| C18 | Brewer 2012 states CAP: a networked shared-data system can have at most two of three properties: C (a single up-to-date copy of the data), A (high availability of the data for updates), P (tolerance to network partitions). | S2 | "any networked shared-data system can have at most two of three desirable properties: consistency (C) equivalent to having a single up-to-date copy of the data; high availability (A) of that data (for updates); and tolerance to network partitions (P)." |
| C19 | "2 of 3" was always misleading: it oversimplified the tensions. | S2 | "The "2 of 3" formulation was always misleading because it tended to oversimplify the tensions among properties." |
| C20 | CAP forbids only a small part of the design space: perfect availability and consistency during partitions, which are rare. | S2 | "CAP prohibits only a tiny part of the design space: perfect availability and consistency in the presence of partitions, which are rare." |
| C21 | Designers still need to choose between C and A when a partition is present, but they have wide flexibility in handling the partition and recovering. | S2 | "designers still need to choose between consistency and availability when partitions are present, there is an incredible range of flexibility for handling partitions and recovering from them." |
| C22 | Two nodes on opposite sides of a partition: if one may update, the nodes become inconsistent (C lost); if consistency is kept, one side must act as unavailable (A lost). | S2 | "Allowing at least one node to update state will cause the nodes to become inconsistent, thus forfeiting C. Likewise, if the choice is to preserve consistency, one side of the partition must act as if it is unavailable, thus forfeiting A." |
| C23 | Only when nodes communicate can both C and A hold. For wide-area systems, designers cannot give up P, so they choose between C and A. | S2 | "Only when nodes communicate is it possible to preserve both consistency and availability, thereby forfeiting P. The general belief is that for wide-area systems, designers cannot forfeit P and therefore have a difficult choice between C and A." |
| C24 | Three reasons "2 of 3" misleads: (1) partitions are rare, so there is little reason to give up C or A when there is no partition; (2) the C-versus-A choice can happen many times in one system, at fine granularity, and can change by operation, data, or user; (3) the three properties are more continuous than binary. | S2 "CAP Confusion" sidebar | "First, because partitions are rare, there is little reason to forfeit C or A when the system is not partitioned. Second, the choice between C and A can occur many times within the same system at very fine granularity; not only can subsystems make different choices, but the choice can change according to the operation or even the specific data or user involved. Finally, all three properties are more continuous than binary." |
| C25 | Availability runs from 0 to 100 percent. There are many levels of consistency. Partitions have nuances. | S2 | "Availability is obviously continuous from 0 to 100 percent, but there are also many levels of consistency, and even partitions have nuances" |
| C26 | The C in CAP is single-copy consistency, a strict subset of ACID consistency. | S2 "ACID, BASE, and CAP" sidebar | "the C in CAP refers only to single-copy consistency, a strict subset of ACID consistency." |
| C27 | Latency: a partition is a time bound on communication. A timeout forces the "partition decision": cancel the operation (less availability) or proceed (risk inconsistency). Retrying forever is choosing C over A. | S2 | "Operationally, the essence of CAP takes place during a timeout ... cancel the operation and thus decrease availability, or proceed with the operation and thus risk inconsistency." / "retrying communication indefinitely is in essence choosing C over A." / "a partition is a time bound on communication." |
| C28 | Tighter time bounds mean the system enters partition mode more often, also when the network is only slow. | S2 | "systems with tighter bounds will likely enter partition mode more often and at times when the network is merely slow and not actually partitioned." |
| C29 | Brewer's strategy for partitions has three steps: detect the start of a partition, enter an explicit partition mode that may limit some operations, start recovery when communication returns. Recovery restores consistency and compensates for mistakes. | S2 "Managing partitions" | "detect the start of a partition, enter an explicit partition mode that may limit some operations, and initiate partition recovery when communication is restored. The last step aims to restore consistency and compensate for mistakes the program made while the system was partitioned." |
| C30 | In partition mode a system can limit some operations (less availability) or record extra information for recovery. | S2 | "The first is to limit some operations, thereby reducing availability. The second is to record extra information about the operations that will be helpful during partition recovery." |
| C31 | Example of a delayed operation: charging a credit card. The system records the intent and runs it after recovery; users only see that the order will be executed later. | S2 | "Externalized events, such as charging a credit card, often work this way. In this case, the strategy is to record the intent and execute it after the recovery." / "The users know only that they placed an order and that the system will execute it later." |
| C32 | ATM example: A trumps C because higher availability means higher revenue. In stand-in (partition) mode, modern ATMs limit the net withdrawal to at most k, for example 200 dollars. | S2 sidebar "Compensation Issues in an Automated Teller Machine" | "in practice, A trumps C. The reason is straightforward enough: higher availability means higher revenue." / "modern ATMs limit the net withdrawal to at most k, where k might be $200." |
| C33 | If the system chooses A, it must say which invariants (rules) must hold and restore them after the partition; this is hard and error-prone. | S2 | "when designers choose A, which requires restoring invariants after a partition, they must be explicit about all the invariants, which is both challenging and prone to error." |
| C34 | Choosing "CA" is unclear: if a partition happens, the choice reverts to C or A. Think of it as a probability: a partition far less likely than other failures. | S2 | "If the choice is CA, and then there is a partition, the choice must revert to C or A. It is best to think about this probabilistically" |
| C35 | The NoSQL movement is in some sense about choices that put availability first and consistency second. ACID databases do the opposite. | S2 | "In some sense, the NoSQL movement is about creating choices that focus on availability first and consistency second; databases that adhere to ACID properties ... do the opposite." |
