| # | Claim on the page | Source | Quote |
|---|---|---|---|
| C1 | The pattern temporarily blocks access to a remote service after failures reach a threshold, instead of retrying an operation that is likely to fail. It lets the failing service recover. | S1 intro | "Temporarily block access to a remote service or resource after failures reach a threshold, instead of repeatedly retrying an operation that's likely to fail." / "lets the failing service recover" |
| C2 | It stops a caller from retrying a call that caused repeated timeouts or failures, and it detects when the callee works again. | S2 Intent | "can prevent a caller service from retrying a call to another service (callee) when the call has previously caused repeated timeouts or failures. The pattern is also used to detect when the callee service is functional again." |
| C3 | The AWS guidance says breaker objects work like electrical circuit breakers. The breaker object sits between caller and callee and trips if the callee is unavailable. | S2 Motivation | "the circuit breaker object is situated between the caller and the callee service, and trips if the callee is unavailable." |
| C4 | The pattern was popularized by a book (Release It, 2018 edition cited). | S2 Motivation | "The circuit breaker pattern was popularized by Michael Nygard in his book, Release It (Nygard 2018)." (Not used on the page: the page names no person.) |
| C5 | Transient faults (overcommitted or unavailable resources, slow network, time-outs) typically correct themselves after a short time. A strategy such as Retry helps. | S1 Context and problem | "These faults typically correct themselves after a short period of time." / "use a strategy, such as the Retry pattern." |
| C6 | Some faults take longer to fix, from partial loss of connectivity to complete service failure. The app should not keep retrying an operation that is unlikely to succeed. | S1 Context and problem | "an application shouldn't continually retry an operation that's unlikely to succeed." |
| C7 | With a time-out only, blocked requests can hold memory, threads, and database connections. This can exhaust resources and fail unrelated parts of the system. | S1 Context and problem | "These blocked requests might hold critical system resources, such as memory, threads, and database connections. This problem can exhaust resources, which might fail other unrelated parts of the system" |
| C8 | Repeated retries can cause network contention and database thread pool use. Many users retrying can make it worse and reduce performance of the whole application. | S2 Motivation | "these retries might result in network contention and database thread pool consumption." / "if multiple users are retrying the application repeatedly, this will exacerbate the problem" |
| C9 | The operation should fail at once and call the service only when it is likely to succeed. | S1 Context and problem | "an operation should fail immediately and only attempt to invoke the service if it's likely to succeed." |
| C10 | The breaker acts as a proxy. It watches recent failures and decides to let the call go or to return an exception at once. It can be a state machine whose states mimic an electrical breaker. | S1 Solution | "A circuit breaker acts as a proxy for operations that might fail. The proxy should monitor the number of recent failures" / "You can implement the proxy as a state machine" |
| C11 | Closed: requests go through. The proxy counts recent failures. If the count passes a threshold in a time period, the proxy goes to Open and starts a time-out timer. When it expires, the proxy goes to Half-Open. | S1 Solution | "Closed: The request from the application is routed to the operation." / "If the number of recent failures exceeds a specified threshold within a given time period, the proxy is placed into the Open state and starts a time-out timer. When the timer expires, the proxy is placed into the Half-Open state." |
| C12 | Open: the request fails at once and an exception returns. | S1 Solution | "Open: The request from the application fails immediately and an exception is returned to the application." |
| C13 | Half-Open: a limited number of requests pass. If they succeed, the breaker assumes the fault is fixed, goes to Closed, and resets the failure counter. If any fails, it goes back to Open and restarts the timer. | S1 Solution | "A limited number of requests from the application are allowed to pass through" / "switches to the Closed state. The failure counter is reset." / "reverts to the Open state. It restarts the time-out timer" |
| C14 | Half-Open helps prevent a recovering service from being flooded with requests. | S1 Solution note | "The Half-Open state helps prevent a recovering service from suddenly being flooded with requests." |
| C15 | The failure counter in Closed is time based and resets at intervals. This design helps prevent a few random failures from opening the breaker. | S1 Solution | "The failure counter for the Closed state is time based. It automatically resets at periodic intervals. This design helps prevent the circuit breaker from entering the Open state if it experiences occasional failures." |
| C16 | The Half-Open success counter: the breaker returns to Closed after a specified number of successful, consecutive calls. Any failure opens it at once. | S1 Solution | "The circuit breaker reverts to the Closed state after a specified number of successful, consecutive operation invocations. If any invocation fails, the circuit breaker enters the Open state immediately" |
| C17 | Recovery depends on outside actions such as restoring or restarting a component or repairing a network link. | S1 Solution note | "System recovery is based on external operations, such as restoring or restarting a failed component or repairing a network connection." |
| C18 | A breaker can reject at once instead of waiting for time-out. It can raise an event at each state change, for monitoring or alerts when it opens. | S1 Solution | "This pattern quickly rejects a request for an operation that's likely to fail, rather than waiting for the operation to time out or never return." / "If the circuit breaker raises an event each time it changes state, this information can help monitor the health" |
| C19 | The time-out can grow: a few seconds at first, then minutes if the fault remains. | S1 Solution | "You can place the circuit breaker in the Open state for a few seconds initially. If the failure isn't resolved, increase the time-out to a few minutes and adjust accordingly." |
| C20 | In Open, the breaker can return a default value that is meaningful to the application, instead of an exception. | S1 Solution | "the Open state can return a default value that's meaningful to the application." |
| C21 | Traditionally breakers use preset thresholds such as failure count and time-out length. | S1 Solution note | "Traditionally, circuit breakers relied on preconfigured thresholds, such as failure count and time-out duration." |
| C22 | The app must handle the exception when the operation is unavailable: degrade, call an alternative, or tell the user to try later. | S1 Problems | "an application might temporarily degrade its functionality, invoke an alternative operation to try to perform the same task or obtain the same data, or report the exception to the user and ask them to try again later." |
| C23 | A breaker can look at exception types, for example need more time-outs than "service unavailable" failures to open. | S1 Problems | "it might require a larger number of time-out exceptions to trigger the circuit breaker to the Open state compared to the number of failures caused by the unavailable service." |
| C24 | Monitoring: show failed and successful requests so teams can judge health. | S1 Problems; S2 Issues | S1: "A circuit breaker should provide clear observability into both failed and successful requests" / S2: "The application should have logging set up to identify the calls that fail when the circuit breaker is open." |
| C25 | Recoverability: too long in Open can give exceptions after the fault is fixed. Switching to Half-Open too fast can make the breaker fluctuate and slow response times. | S1 Problems | "if the circuit breaker remains in the Open state for a long period, it can raise exceptions even if the reason for the failure is resolved." / "can fluctuate and reduce the response times of applications if it switches from the Open state to the Half-Open state too quickly." |
| C26 | Instead of a timer, a breaker can ping the service, with a previously failed call or a health-check operation, to decide when to go to Half-Open. | S1 Problems | "rather than using a timer to determine when to switch to the Half-Open state, a circuit breaker can periodically ping the remote service" |
| C27 | Manual override: an administrator can close a breaker and reset the counter, or force it open and restart the timer. Useful when recovery time varies a lot. | S1 Problems; S2 Issues | S1: "you should provide a manual reset option that enables an administrator to close a circuit breaker and reset the failure counter." / S2: "System administrators should have the ability to open or close a circuit." |
| C28 | Resource differentiation: one breaker for several independent providers (for example shards) can block access that would work or allow access that will fail. | S1 Problems | "one shard might be fully accessible while another experiences a temporary problem." / "access to other shards might be blocked even though it's likely to succeed." |
| C29 | A failure response can carry enough information to trip the breaker at once for a minimum time, for example an overloaded resource that says to retry in a few minutes. HTTP 429 and 503 may include the expected delay. | S1 Problems | "the error response from a shared resource that's overloaded can indicate that the application should instead try again in a few minutes" / "A service can return HTTP 429 (too many requests)... or HTTP 503 (service unavailable)" |
| C30 | A time-out that is too long can leave a thread blocked a long time before the breaker sees the failure, so a breaker may not fully protect. | S1 Problems | "A circuit breaker might not fully protect applications from failures in external services that have long time-out periods." |
| C31 | Concurrency: many instances can use the same breaker. The implementation should not block concurrent requests or add much overhead. | S1 Problems | "The implementation shouldn't block concurrent requests or add excessive overhead to each call to an operation." |
| C32 | Service meshes often support circuit breaking without app code changes. | S1 Problems | "service meshes often support circuit breaking as a sidecar or as a standalone capability without modifying application code." |
| C33 | Retry and circuit breaker have different purposes. Retry expects the operation to succeed in the end. The breaker stops an operation likely to fail. | S1 Solution note | "The Retry pattern enables an application to retry an operation with the expectation that it eventually succeeds. The Circuit Breaker pattern prevents an application from performing an operation that's likely to fail." |
| C34 | They can be combined: retry through a breaker. The retry logic should stop when the breaker says the fault is not transient. | S1 Solution note | "the retry logic should be sensitive to any exceptions that the circuit breaker returns and stop retry attempts if the circuit breaker indicates that a fault isn't transient." |
| C35 | Transient errors can be handled with retry with backoff. | S2 Motivation | "(The transient errors can be handled by using the retry with backoff pattern.)" |
| C36 | Use when you want to: prevent cascading failures; protect against slow dependencies to keep service-level objectives; manage intermittent connectivity problems. The lede says a breaker helps prevent cascading failure. | S1 When to use | "prevent cascading failures by stopping excessive remote service calls" / "protect against slow dependencies so that you can maintain your service-level objectives" / "manage intermittent connectivity problems" |
| C37 | Use when (AWS): the call is most likely to fail; high callee latency causes time-outs; a synchronous call to a callee that is unavailable or slow. | S2 Applicability | "The caller service makes a call that is most likely going to fail." / "The caller service makes a synchronous call, but the callee service isn't available or exhibits high latency." |
| C38 | Might not suit: local private resources such as in-memory data (adds overhead); as a substitute for exception handling in business logic; when well-known retry is enough and dependencies handle retry (adds complexity); when waiting for a reset would cause unacceptable delay; message-driven or event-driven systems (dead letter queues); when the platform handles recovery (health checks in load balancers or meshes). | S1 When to use | "local private resources in an application, such as in-memory data structures. In this environment, a circuit breaker adds overhead" / "substitute for handling exceptions in the business logic" / "Waiting for a circuit breaker to reset might introduce unacceptable delays." / "dead letter queue" / "Failure recovery is managed at the infrastructure or platform level" |
| C39 | AWS: if timeouts pass a threshold the circuit opens, the breaker returns a failure at once without calling the callee, and it periodically checks whether calls succeed. When a call succeeds, the circuit closes. | S2 Implementation | "If the timeouts exceed a specified threshold, the application opens the circuit." / "It returns an immediate failure when the order service calls the payment service." / "The circuit breaker object periodically tries to see if the calls to the payment service are successful." / "the circuit is closed, and all further calls are routed" |
| C40 | AWS expiration timeout: the time the circuit stays tripped before calls are routed again. With many threads, the first failed call sets it. Later calls should not keep moving it. | S2 Issues | "The expiration timeout value is defined as the period of time the circuit remains tripped before calls are routed again to check for service availability." / "the first call that failed defines the expiration timeout value" |
| C41 | AWS sample: Step Functions and a DynamoDB table track status. The workflow retries with exponential backoff a set number of times. After the retries fail it saves a record with an expiry time stamp. Later calls fail at once while the record has not expired. | S2 Implementation | "the application retries with exponential backoff for a defined number of times." / "inserts a record in the CircuitStatus table for the service with the an ExpiryTimeStamp" / "Subsequent calls to the same service return an immediate failure as long as the circuit breaker is open." |
| C42 | AWS: the callee can close the circuit itself when it recovers (an extension, useful if the recovery time objective needs it). | S2 Issues | "When the callee recovers from the performance issue or failure, they can update the circuit status to CLOSED." |
| C43 | AWS: build the breaker in a service-agnostic, API-driven way to prevent code bloat. | S2 Issues | "we recommend that you implement the circuit breaker object in a microservice-agnostic and API-driven way." |
