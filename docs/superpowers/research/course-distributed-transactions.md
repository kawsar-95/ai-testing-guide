## Claims

| # | Claim on the page | Source | Quote |
|---|---|---|---|
| C1 | `PREPARE TRANSACTION` prepares the current transaction for two-phase commit. After it, the transaction is not tied to the session. Its state is fully stored on disk. | S1 | "prepares the current transaction for two-phase commit. After this command, the transaction is no longer associated with the current session; instead, its state is fully stored on disk" |
| C2 | There is a "very high probability" that a prepared transaction can be committed, even after a crash. (The docs say probability, not certainty.) | S1 | "there is a very high probability that it can be committed successfully, even if a database crash occurs before the commit is requested." |
| C3 | A prepared transaction is later committed or rolled back with `COMMIT PREPARED` or `ROLLBACK PREPARED`, from any session. | S1 | "a transaction can later be committed or rolled back with COMMIT PREPARED or ROLLBACK PREPARED, respectively. Those commands can be issued from any session, not only the one that executed the original transaction." |
| C4 | After `PREPARE TRANSACTION`, the effects are not visible. They become visible if the transaction is committed. | S1 | "there is no active current transaction, and the effects of the prepared transaction are no longer visible. (The effects will become visible again if the transaction is committed.)" |
| C5 | If `PREPARE TRANSACTION` fails, it becomes a rollback. | S1 | "If the PREPARE TRANSACTION command fails for any reason, it becomes a ROLLBACK: the current transaction is canceled." |
| C6 | The purpose of the command is to let an external transaction manager do atomic global transactions across databases or other transactional resources. It is not for applications or interactive sessions. | S1 | "is not intended for use in applications or interactive sessions. Its purpose is to allow an external transaction manager to perform atomic global transactions across multiple databases or other transactional resources." |
| C7 | The transaction id is a string literal under 200 bytes and must differ from any other prepared transaction id. | S1 | "must be written as a string literal, and must be less than 200 bytes long. It must not be the same as the identifier used for any currently prepared transaction." |
| C8 | It must be used inside a transaction block. | S1 | "This command must be used inside a transaction block." |
| C9 | A prepared transaction that stays long is unwise: it blocks `VACUUM` from reclaiming storage, and in extreme cases can shut down the database (transaction ID wraparound). | S1 | "It is unwise to leave transactions in the prepared state for a long time. This will interfere with the ability of VACUUM to reclaim storage, and in extreme cases could cause the database to shut down to prevent transaction ID wraparound" |
| C10 | A prepared transaction keeps the locks it held. | S1 | "the transaction continues to hold whatever locks it held." |
| C11 | Intended use: commit or roll back as soon as the external manager has checked that the other databases are also prepared to commit. | S1 | "a prepared transaction will normally be committed or rolled back as soon as an external transaction manager has verified that other databases are also prepared to commit." |
| C12 | Without a manager to close prepared transactions promptly, the docs advise `max_prepared_transactions` = 0. | S1 | "it is best to keep the prepared-transaction feature disabled by setting max_prepared_transactions to zero." |
| C13 | `max_prepared_transactions` default is 0, which disables the feature. It is set at server start. | S4 | "Setting this parameter to zero (which is the default) disables the prepared-transaction feature. This parameter can only be set at server start." |
| C14 | Prepared transactions are listed in the `pg_prepared_xacts` view. | S1, S2, S3 | "All currently available prepared transactions are listed in the pg_prepared_xacts system view." |
| C15 | A prepared transaction cannot have used temporary tables, `WITH HOLD` cursors, `LISTEN`, `UNLISTEN`, or `NOTIFY`. | S1 | "It is not currently allowed to PREPARE a transaction that has executed any operations involving temporary tables ... created any cursors WITH HOLD, or executed LISTEN, UNLISTEN, or NOTIFY." |
| C16 | `COMMIT PREPARED` commits a prepared transaction. Same user or a superuser. Not in a transaction block. Committed immediately. | S2 | "commits a transaction that is in prepared state." / "you must be either the same user that executed the transaction originally, or a superuser." / "This command cannot be executed inside a transaction block. The prepared transaction is committed immediately." |
| C17 | `ROLLBACK PREPARED` rolls back a prepared transaction. Same user or a superuser. Not in a transaction block. Rolled back immediately. | S3 | "rolls back a transaction that is in prepared state." / "you must be either the same user that executed the transaction originally, or a superuser." / "The prepared transaction is rolled back immediately." |
| C18 | The SQL side of the external managers (for example X/Open XA) is not standardized. The commands are a PostgreSQL extension. | S2 | "COMMIT PREPARED is a PostgreSQL extension. It is intended for use by external transaction management systems, some of which are covered by standards (such as X/Open XA), but the SQL side of those systems is not standardized." |
| C19 | Each microservice usually has its own database. ACID guarantees do not directly apply across separate stores. | S5 | "Microservices architectures typically assign a dedicated database to each microservice." / "Traditional database guarantees like ACID aren't directly applicable to multiple independently managed data stores." |
| C20 | A saga breaks a transaction into a sequence of local transactions. Each one completes atomically in one service, updates its database, and starts the next step with an event or message. | S5 | "manages transactions by breaking them into a sequence of local transactions." / "Completes its work atomically within a single service. Updates the service's database. Initiates the next transaction via an event or message." |
| C21 | If a local transaction fails, the saga runs compensating transactions to reverse the earlier changes. | S5 | "If a local transaction fails, the saga performs a series of compensating transactions to reverse the changes that the preceding local transactions made." |
| C22 | A pivot transaction is the point of no return. After it, the later steps must finish. Retryable steps follow it and are idempotent. | S5 | "Pivot transactions serve as the point of no return in the saga." / "All subsequent actions must be completed for the system to achieve a consistent final state." / "Retryable transactions follow the pivot transaction. Retryable transactions are idempotent" |
| C23 | Choreography: services exchange events with no central controller. Orchestration: a central orchestrator tells participants what to do and handles failure recovery with compensating transactions. | S5 | "services exchange events without a centralized controller." / "a centralized controller, or orchestrator, handles all the transactions and tells the participants which operation to perform based on events." / "handles failure recovery by using compensating transactions." |
| C24 | Choreography is good for simple workflows. It is hard to follow when steps grow, and integration tests need all services running. | S5 | "Good for simple workflows that have few services" / "Workflow can be confusing when you add new steps." / "Integration testing is difficult because all services must run to simulate a transaction." |
| C25 | Orchestration suits complex workflows. The orchestrator is a point of failure. | S5 | "Better suited for complex workflows or when you add new services." / "Introduces a point of failure because the orchestrator manages the complete workflow." |
| C26 | Participants commit to their own databases, so data cannot be rolled back. Compensating transactions might not always succeed. | S5 | "Data can't be rolled back because saga participants commit changes to their respective databases." / "Compensating transactions might not always succeed, which can leave the system in an inconsistent state." |
| C27 | Saga steps must handle transient failures and be idempotent (repeating does not change the outcome). | S5 | "ensure idempotence, when repeating the same operation doesn't alter the outcome." |
| C28 | There is no built-in isolation across services. Anomalies: lost updates, dirty reads, fuzzy (nonrepeatable) reads. | S5 | "there's no built-in isolation across services." / "Lost updates", "Dirty reads", "Fuzzy, or nonrepeatable, reads" |
| C29 | A countermeasure is a semantic lock: an application-level lock that marks an update in progress. | S5 | "Semantic lock: Use application-level locks when a saga's compensable transaction uses a semaphore to indicate that an update is in progress." |
| C30 | Debugging sagas can be complex. Monitoring and tracking sagas is essential. | S5 | "Debugging sagas can be complex" / "Monitoring and tracking the workflow of a saga are essential tasks" |
| C31 | A compensating transaction undoes completed steps. It cannot simply restore the old state, because that can overwrite changes of other instances. It is application specific. | S6 | "the compensating transaction must intelligently account for concurrent work. This process is usually application specific and depends on the original operation." / "this approach can overwrite changes from other concurrent application instances" |
| C32 | The system records how to undo each step. If the operation fails, the workflow rewinds through the finished steps. | S6 | "the system records information about each step and how to undo it. If the operation fails, the workflow rewinds through the completed steps and reverses each step." |
| C33 | Compensating transactions can fail. Record progress to resume. Design steps as idempotent commands. Manual intervention can be the only way, so raise an alert. | S6 | "Compensating transactions are eventually consistent operations and can fail. The system should record progress so that it can resume the compensating transaction from the point of failure." / "design each step as an idempotent command" / "the system should raise an alert" |
| C34 | The compensation need not undo steps in exact reverse order, and does not necessarily return data to the start state. Example: a cancelled flight may not give a full refund. | S6 | "don't always reverse the original operation in the exact opposite order" / "A compensating transaction doesn't necessarily return the system data to its state at the start" / "canceling a flight reservation might not entitle the customer to a complete refund" |
| C35 | Define points of no return. Do irreversible steps only after critical validations pass. | S6 | "Define clear points of no return and irreversible steps." / "Design the workflow so that irreversible steps occur only after all critical validations succeed." |
| C36 | A step may be blocked, not failed. A timeout may be needed. | S6 | "A step might not fail immediately but instead get blocked. You might need to implement a timeout mechanism." |
| C37 | In the eventual consistency model the overall view can be inconsistent during the steps, and should become consistent when all steps finish. | S6 | "During these steps, the overall view of the system state might be inconsistent. But the system should become consistent again when all steps finish." |

## Not on the page

The PostgreSQL pages do not describe the protocol of the external transaction manager step by step (a "vote" phase and a "decision" phase). The page describes only the 2 steps that the docs show: prepare on each database, then commit or roll back. It says that the manager's own rules are not in these docs. The page does not say how a manager recovers from its own crash, and it does not give any blocking behavior beyond locks held, `VACUUM`, and wraparound.
