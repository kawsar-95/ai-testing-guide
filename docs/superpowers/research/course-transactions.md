## Claims

| # | Claim on the page | Source | Quote |
|---|---|---|---|
| C1 | A transaction bundles several steps into one all-or-nothing operation. Other concurrent transactions do not see the steps in between. If a failure stops it, none of the steps affect the database. | S1 | "it bundles multiple steps into a single, all-or-nothing operation. The intermediate states between the steps are not visible to other concurrent transactions, and if some failure occurs that prevents the transaction from completing, then none of the steps affect the database at all." |
| C2 | The updates of an open transaction are invisible to others until it completes; then they all become visible at once. | S1 | "The updates made so far by an open transaction are invisible to other transactions until the transaction completes, whereupon all the updates become visible simultaneously." |
| C3 | COMMIT makes the changes visible to others and guaranteed to be durable if a crash occurs. | S3 | "All changes made by the transaction become visible to others and are guaranteed to be durable if a crash occurs." |
| C4 | In PostgreSQL a transaction is set up with BEGIN and COMMIT around the statements. ROLLBACK instead of COMMIT cancels all updates so far. | S1, S4 | S1: "a transaction is set up by surrounding the SQL commands of the transaction with BEGIN and COMMIT commands." / "we can issue the command ROLLBACK instead of COMMIT, and all our updates so far will be canceled." S4: "ROLLBACK rolls back the current transaction and causes all the updates made by the transaction to be discarded." |
| C5 | Without BEGIN, each statement runs in its own transaction and is committed at its end if it worked (autocommit). | S1, S2 | S1: "If you do not issue a BEGIN command, then each individual statement has an implicit BEGIN and (if successful) COMMIT wrapped around it." S2: "PostgreSQL executes transactions in "autocommit" mode, that is, each statement is executed in its own transaction" |
| C6 | Some client libraries send BEGIN and COMMIT automatically. Check the documentation of the interface. | S1 | "Some client libraries issue BEGIN and COMMIT commands automatically, so that you might get the effect of transaction blocks without asking. Check the documentation for the interface you are using." |
| C7 | Statements run faster in a transaction block, because start and commit need CPU and disk work. Several related changes in one block hide the middle states from other sessions. | S2 | "Statements are executed more quickly in a transaction block, because transaction start/commit requires significant CPU and disk activity." / "other sessions will be unable to see the intermediate states wherein not all the related updates have been done." |
| C8 | BEGIN inside a block gives a warning and does not change the state. To nest, use savepoints. | S2 | "Issuing BEGIN when already inside a transaction block will provoke a warning message. The state of the transaction is not affected. To nest transactions within a transaction block, use savepoints" |
| C9 | COMMIT outside a transaction does no harm but gives a warning. ROLLBACK outside a block gives a warning and has no other effect. | S3, S4 | S3: "Issuing COMMIT when not inside a transaction does no harm, but it will provoke a warning message." S4: "Issuing ROLLBACK outside of a transaction block emits a warning and otherwise has no effect." |
| C10 | A savepoint is a mark inside a transaction. Commands after it can be rolled back, to restore the state at the savepoint. It can only be set inside a transaction block. A transaction can have several. | S5 | "A savepoint is a special mark inside a transaction that allows all commands that are executed after it was established to be rolled back, restoring the transaction state to what it was at the time of the savepoint." / "Savepoints can only be established when inside a transaction block. There can be multiple savepoints defined within a transaction." |
| C11 | After ROLLBACK TO, changes before the savepoint are kept and changes after are discarded. The savepoint stays defined, so one can roll back to it more than once. RELEASE frees it. Rolling back to or releasing a savepoint releases the savepoints defined after it. | S1 | "All the transaction's database changes between defining the savepoint and rolling back to it are discarded, but changes earlier than the savepoint are kept." / "After rolling back to a savepoint, it continues to be defined, so you can roll back to it several times." / "either releasing or rolling back to a savepoint will automatically release all savepoints that were defined after it." |
| C12 | RELEASE SAVEPOINT destroys a savepoint and keeps the effects of the commands after it. | S5 | "Use RELEASE SAVEPOINT to destroy a savepoint, keeping the effects of commands executed after it was established." |
| C13 | ROLLBACK TO is the only way, short of a full rollback, to regain control of a transaction block that the system put in aborted state after an error. | S1 | "ROLLBACK TO is the only way to regain control of a transaction block that was put in aborted state by the system due to an error, short of rolling it back completely and starting again." |
| C14 | A savepoint with the same name as an older one hides the older one until the newer one is released. | S5 | "If savepoints with the same name already exist, they will be inaccessible until newer identically-named savepoints are released." |
| C15 | The SQL standard defines 4 isolation levels. Serializable is the strictest: the result equals running the transactions one at a time in some order. The other 3 are defined by phenomena that must not occur. | S7 | "The SQL standard defines four levels of transaction isolation. The most strict is Serializable ... guaranteed to produce the same effect as running them one at a time in some order. The other three levels are defined in terms of phenomena" |
| C16 | Dirty read: reads data written by a concurrent uncommitted transaction. | S7 | "A transaction reads data written by a concurrent uncommitted transaction." |
| C17 | Nonrepeatable read: re-reads data and finds another transaction changed it (committed since the first read). | S7 | "A transaction re-reads data it has previously read and finds that data has been modified by another transaction (that committed since the initial read)." |
| C18 | Phantom read: re-runs a query and finds the set of matching rows changed because of another recently committed transaction. | S7 | "finds that the set of rows satisfying the condition has changed due to another recently-committed transaction." |
| C19 | Serialization anomaly: the result of committing a group of transactions fits no one-at-a-time order. | S7 | "The result of successfully committing a group of transactions is inconsistent with all possible orderings of running those transactions one at a time." |
| C20 | Table 13.1: Read uncommitted: dirty read "Allowed, but not in PG"; nonrepeatable, phantom, serialization anomaly possible. Read committed: dirty not possible; the other 3 possible. Repeatable read: dirty and nonrepeatable not possible; phantom "Allowed, but not in PG"; serialization anomaly possible. Serializable: none possible. | S7 | Table 13.1 rows as listed. |
| C21 | PostgreSQL implements 3 distinct levels. Its Read Uncommitted behaves like Read Committed. | S7, S8 | S7: "internally only three distinct isolation levels are implemented, i.e., PostgreSQL's Read Uncommitted mode behaves like Read Committed." S8: "In PostgreSQL READ UNCOMMITTED is treated as READ COMMITTED." |
| C22 | The PostgreSQL docs say Read Committed is the default isolation level in PostgreSQL. | S7, S8 | S7: "Read Committed is the default isolation level in PostgreSQL." S8: "A statement can only see rows committed before it began. This is the default." |
| C23 | Read Committed: a SELECT sees only data committed before the query began. Two successive SELECTs in one transaction can see different data if others commit in between. | S7 | "a SELECT query ... sees only data committed before the query began" / "two successive SELECT commands can see different data, even though they are within a single transaction, if other transactions commit changes after the first SELECT starts and before the second SELECT starts." |
| C24 | Read Committed is adequate for many applications and is fast and simple, but not for all cases. | S7 | "adequate for many applications, and this mode is fast and simple to use; however, it is not sufficient for all cases." |
| C25 | Repeatable Read sees only data committed before the transaction began (snapshot at the first non-transaction-control statement). Successive SELECTs see the same data. | S7 | "only sees data committed before the transaction began" / "successive SELECT commands within a single transaction see the same data" |
| C26 | In Repeatable Read, an update of a row that another transaction changed and committed since the start fails with "could not serialize access due to concurrent update". The application should abort and retry the whole transaction. Only updating transactions might need a retry. | S7 | "ERROR: could not serialize access due to concurrent update" / "it should abort the current transaction and retry the whole transaction from the beginning." / "only updating transactions might need to be retried; read-only transactions will never have serialization conflicts." |
| C27 | In PostgreSQL, Repeatable Read prevents all the phenomena except serialization anomalies. Business rules enforced at this level are not likely to work without careful use of explicit locks. | S7 | "prevents all of the phenomena described in Table 13.1 except for serialization anomalies." / "Attempts to enforce business rules by transactions running at this isolation level are not likely to work correctly without careful use of explicit locks to block conflicting transactions." |
| C28 | Serializable emulates running transactions one after another. It works like Repeatable Read plus monitoring. Monitoring adds overhead and may cause a serialization failure. Applications must be ready to retry. | S7 | "This level emulates serial transaction execution for all committed transactions" / "applications using this level must be prepared to retry transactions due to serialization failures" / "there is some overhead to the monitoring" |
| C29 | Example: A sums class 1 and inserts 30 as class 2; B sums class 2 and inserts 300 as class 1. At Repeatable Read both commit; at Serializable one is rolled back with "could not serialize access due to read/write dependencies among transactions". | S7 | "If either transaction were running at the Repeatable Read isolation level, both would be allowed to commit; but since there is no serial order of execution consistent with the result, using Serializable transactions will allow one transaction to commit and will roll the other back" |
| C30 | Do not treat data read at Serializable as valid until the transaction commits; do not depend on results of a transaction that aborted; retry until it succeeds. | S7 | "any data read from a permanent user table not be considered valid until the transaction which read it has successfully committed" / "they should retry the transaction until it succeeds" |
| C31 | The level is set with SET TRANSACTION or in BEGIN. It cannot be changed after the first query or data-modification statement. | S7, S2, S8 | S7: "To set the transaction isolation level of a transaction, use the command SET TRANSACTION." S2: "If the isolation level ... is specified, the new transaction has those characteristics, as if SET TRANSACTION was executed." S8: "The transaction isolation level cannot be changed after the first query or data-modification statement ... of a transaction has been executed." |
| C32 | Changes to a sequence (the counter of a serial column) are visible at once to other transactions and are not rolled back if the transaction aborts. | S7 | "changes made to a sequence (and therefore the counter of a column declared using serial) are immediately visible to all other transactions and are not rolled back if the transaction that made the changes aborts." |
| C33 | In a Read Committed transfer of money between two fixed rows, a second command starts from the updated row version. | S7 | "we clearly want the second statement to start with the updated version of the account's row." |
