## Claims

| # | Claim on the page | Source | Quote |
|---|---|---|---|
| C1 | Instead of storing only current state, the pattern stores the full series of actions on an object in an append-only store, which is the system of record. | S1 intro | "Instead of storing only the current state of the data in a relational database, store the full series of actions taken on an object in an append-only store. The store acts as the system of record" |
| C2 | It is a complex pattern with significant trade-offs; it is costly to migrate to or from, and it constrains later design. For most systems and most parts, traditional data management is enough. | S1 Important box | "It's costly to migrate to or from an event sourcing solution" / "For most systems and most parts of a system, traditional data management is sufficient." |
| C3 | In CRUD an app reads, modifies, and updates the current state; it only stores the latest state, so history is lost without a separate audit log. | S1 Context | "CRUD systems only store the latest state of the data. If you don't implement an auditing mechanism ... you lose data history." |
| C4 | Each event is a logical change, for example AddedItemToOrder or OrderCanceled. | S1 Solution | "Each event represents a logical change to the object, such as AddedItemToOrder or OrderCanceled." |
| C5 | Each entity has its own eventstream: the ordered sequence of events that records every change. | S1 Solution | "Each entity in an event-sourced system has its own eventstream, which is the ordered sequence of events that records every change to that entity." |
| C6 | The current state is derived by replaying all events of the stream; this is "rehydration" and can happen on demand. | S1 Solution | "Applications derive the current state of an entity by replaying all the events in its stream. This process is known as rehydration. It can occur on demand" |
| C7 | The command handler loads the entity by reading its eventstream and replays the events to rebuild the current state before any new action. | S1 Workflow | "The command handler loads the entity by retrieving its eventstream from the event store." / "It replays those events against the entity to reconstruct its current state before any new action occurs." |
| C8 | Business logic runs and events are raised; in most implementations the events go to a queue or topic to decouple producers and consumers. | S1 Workflow | "In most implementations, the events are pushed to a queue or topic to decouple the event producers and event consumers." |
| C9 | Event handlers can write events to the store, update a read-only store, or integrate with external systems. | S1 Workflow | "Write the events to the event store / Update a read-only store optimized for queries / Integrate with external systems" |
| C10 | Materialized views are read-only projections of the event store, optimized for querying; apps use them because reading and replaying events is costly. | S1 Solution | "Applications typically implement materialized views because it's costly to read and replay events. Materialized views are read-only projections of the event store that are optimized for querying." |
| C11 | Events are immutable and stored by append-only operations; append-only writes avoid the row-level lock contention of update-in-place systems, so write throughput improves. | S1 Advantages | "Events are immutable, and you can store them by using an append-only operation." / "append-only writes avoid the row-level lock contention that update-in-place systems create." |
| C12 | The append-only store gives an audit trail, and state can be regenerated as views or projections by replaying events at any time; it can help test and debug. | S1 Advantages | "Append-only event storage provides an audit trail ... It can regenerate the current state as materialized views or projections by replaying the events at any time, and it can help test and debug the system." |
| C13 | Optimistic concurrency: the event store rejects an append if the stream changed since it was read; the handler reloads, re-evaluates, and retries. | S1 Advantages | "Event stores address this scenario by using optimistic concurrency control and reject an append if the stream changed since it was read. Upon rejection, the handler reloads the entity, reevaluates, and retries." |
| C14 | Event design: capture the business intent, not only the resulting state. "Two seats were reserved" is more valuable than "remaining seats changed to 42". | S1 Problems | "an event that records two seats were reserved is more valuable than an event that records remaining seats changed to 42." |
| C15 | Eventual consistency: views built by replaying events are only eventually consistent. There is a delay between handling a request, publishing events, and consumers handling them. Customers must understand this. | S1 Problems | "The system is only eventually consistent when it creates materialized views or generates projections of data by replaying events. A delay exists between ..." / "Ensure that your customers understand that data is eventually consistent" |
| C16 | Event data is never updated. To undo a change, add a compensating event; the original stays. Example: ReservationCanceled compensates SeatsReserved. | S1 Problems (Versioning) | "you should never update the event data. The only way to update an entity or undo a change is to add a compensating event" / "a ReservationCanceled event compensates for a prior SeatsReserved event. The original event remains in the stream" |
| C17 | If a bug produces wrong events, they persist; fixing the code does not fix history, so compensating events or upcasters may be needed during replay. | S1 Problems | "if a bug produces incorrect events, those events persist in the store. Fixing the bug in application code doesn't fix the historical events" |
| C18 | If the event schema must change, it can be difficult to combine old and new events. | S1 Problems | "it can be difficult to combine existing events in the store with the new version." |
| C19 | Versioning strategies: tolerant deserialization (ignore unknown fields, defaults for missing ones, for additive changes); event versioning (a version identifier in each event); upcasting (convert old schemas to the current one when reading; stored events stay unchanged); in-place migration (rewrite old events; breaks immutability; last resort). | S1 Problems | "Tolerant deserialization: ..." / "Event versioning: Include a version identifier in each event" / "Upcasting: ... The stored events remain unchanged" / "In-place migration: ... should be a last resort because it undermines the audit trail." |
| C20 | Event querying: no standard approach such as SQL; you can only read a stream by event identifier (usually one entity); current state only by replaying. | S1 Problems | "There's no standard approach or existing mechanisms, such as SQL queries, for reading events" / "You can determine the current state of an entity only by replaying all of the events" |
| C21 | An event store can be a purpose-built database or a general database with an append-only table. Purpose-built stores support stream reads, optimistic concurrency, and snapshots; relational ones need you to build these. | S1 Problems | "An event store can be a purpose-built database designed for append-only eventstreams or a general-purpose relational or document database with an append-only table." |
| C22 | Do not confuse an event store with a message broker. Brokers such as Apache Kafka typically lack per-entity stream queries and optimistic concurrency; they work as a distribution layer, not as a substitute. | S1 Important box | "Don't confuse an event store with an eventstream message broker. Message brokers such as Apache Kafka typically lack per-entity stream queries and optimistic concurrency." |
| C23 | Snapshots: long streams make replay costly. A snapshot is a serialized state at a point in the stream, created at intervals such as every N events. Load the latest snapshot and replay only later events. Balance storage cost against time saved. | S1 Problems | "create snapshots at specific intervals, such as every N events." / "load the most recent snapshot and replay only the events that occur after it" / "balance the storage cost of snapshots against the time saved" |
| C24 | Snapshots are an optimization, not a replacement; the stream stays the source of truth and snapshots can be regenerated from it. | S1 Note | "Snapshots are an optimization, not a replacement for the eventstream. The eventstream remains the source of truth, and you can regenerate snapshots from it at any time." |
| C25 | Idempotency: delivery is typically at least once, so handlers must be idempotent; without it, projections drift and side effects (payments, notifications) repeat. | S1 Problems | "Event delivery to consumers is typically at least once, so consumers can receive the same event more than once. Event handlers must be idempotent" |
| C26 | Circular logic: processing one event that creates new events can cause an infinite loop. | S1 Problems | "This sequence can result in an infinite loop." |
| C27 | Testing: given-when-then (set up past events, issue a command, assert on new events). Integration tests are also needed for projections, idempotency, and schema evolution, which adds test surface compared to CRUD. | S1 Problems | "Set up past events, issue a command, and assert on the new events produced." / "which adds testing surface compared to CRUD systems." |
| C28 | Personal data: the immutable store conflicts with deletion laws. Options: keep personal data outside the store and refer to it by identifier; or crypto-shredding (per-subject key, delete the key). | S1 Problems | "conflicts with data protection regulations that require deletion of personal data" / "store personal data outside the event store and reference it by identifier" / "Delete the key to render the data unrecoverable" |
| C29 | When to use: capture intent or reason; minimize conflicting updates; keep history, replay, roll back, audit log; decouple input from tasks; flexibility to change materialized models; with CQRS, if eventual consistency is acceptable. | S1 When to use | "You want to capture intent, purpose, or reason in the data." / "You must minimize or completely avoid conflicting updates to data." |
| C30 | Not suitable: simple CRUD with no need for audit, replay, or history; prototypes, MVPs, short-lived systems; systems that need consistent, real-time views; mostly static or reference data; teams without event-driven experience. | S1 When to use | "This pattern might not be suitable when:" (the five items) |
| C31 | Apply it only to the parts that benefit, such as a payment ledger or order pipeline; use CRUD for user profile or configuration. | S1 Tip | "Apply it selectively to the parts of your system that it benefits the most, such as a payment ledger or order-processing pipeline." |
| C32 | Often combined with CQRS: handle data tasks in response to events and build views from stored events; scale reads and writes independently. The write store of CQRS is typically based on event sourcing. | S1 Tip, Next step | "Event sourcing is commonly combined with the CQRS pattern" / "The write store that provides the permanent source of information for a CQRS implementation is typically based on an implementation of the Event Sourcing pattern." |
