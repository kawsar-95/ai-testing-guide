## Claims

| # | Claim on the page | Source | Quote |
|---|---|---|---|
| C1 | VMs and containers both let several apps share the same physical infrastructure, but they separate the apps in different ways. | S1 2.2 | "Both VMs and containers allow multiple apps to share the same physical infrastructure, but they use different methods of separation." |
| C2 | A VM uses a hypervisor for hardware-level isolation. Each VM sees its own virtual hardware and has a full guest OS. VMs let different OSs (Linux, Windows) share hardware. | S1 2.2 | "VMs use a hypervisor that provides hardware-level isolation of resources across VMs. Each VM sees its own virtual hardware and includes a complete guest OS in addition to the app and its data. VMs allow different OSs, such as Linux and Windows, to share the same physical hardware." |
| C3 | Containers share one OS kernel instance but are segregated. The kernel is part of the host OS. Containers depend on the OS family: a Linux host runs Linux containers, a Windows host runs Windows containers. | S1 2.2 | "With containers, multiple apps share the same OS kernel instance but are segregated from each other." / "Containers are OS-family specific; a Linux host can only run containers built for Linux, and a Windows host can only run Windows containers." |
| C4 | The container runtime uses OS features so each container sees its own view of the OS: namespace isolation (file systems, network interfaces, processes, and more), resource allocation limits (on Linux, mainly cgroups), and filesystem virtualization. | S1 2.2 | "The container runtime coordinates multiple OS components that isolate resources and resource usage so that each container sees its own dedicated view of the OS" / "Namespace isolation limits which resources a container may interact with." / "Resource allocation limits how much of a host's resources a given container can consume." / "On Linux, this is accomplished primarily with control groups (cgroups)" / "Filesystem virtualization allows multiple containers to share the same physical storage without the ability to access or alter the storage of other containers." |
| C5 | Containers give a strong degree of isolation, but not as clear a security boundary as a VM. They share the kernel and can run with varied capabilities and privileges, so the segmentation between them is far less than between VMs. A carelessly configured environment may let containers interact with each other and the host more easily than VMs could. | S1 2.2 | "While containers provide a strong degree of isolation, they do not offer as clear and concrete of a security boundary as a VM." / "the degree of segmentation between them is far less than that provided to VMs by a hypervisor. Thus, carelessly configured environments can result in containers having the ability to interact with each other and the host far more easily and directly than multiple VMs on the same host." |
| C6 | The shared kernel gives a larger inter-object attack surface than hypervisors, even with a container-specific OS. The isolation of container runtimes is not as high as that of hypervisors. | S1 3.5.2 | "the use of a shared kernel invariably results in a larger inter-object attack surface than seen with hypervisors, even for container-specific OSs. In other words, the level of isolation provided by container runtimes is not as high as that provided by hypervisors." |
| C7 | Containers and VMs often coexist. An organization need not choose: it can use VMs to deploy, partition, and manage hardware, and containers to package apps and use each VM more efficiently. VMs bring strong isolation, OS automation, and a wide ecosystem. | S1 2.2 | "Containers and hardware virtualization not only can, but very frequently do, coexist well" / "Organizations do not need to make a choice between containers and VMs. Instead, organizations can continue to use VMs to deploy, partition, and manage their hardware, while using containers to package their apps and utilize each VM more efficiently." |
| C8 | Best practice: group containers by sensitivity so that a host kernel runs only one sensitivity level. This can use separate physical servers, or VMs (hypervisors give strong enough isolation to mitigate the risk). Most runtimes isolate containers well, but mixing sensitivity levels on one host may be an unnecessary risk. | S1 4.3.4 | "a best practice is to group containers together by relative sensitivity and to ensure that a given host kernel only runs containers of a single sensitivity level." / "This segmentation may be provided by using multiple physical servers, but modern hypervisors also provide strong enough isolation to effectively mitigate these risks." / "While most container runtime environments do an effective job of isolating containers from each other and from the host OS, in some cases it may be an unnecessary risk to run apps of different sensitivity levels together on the same host OS." |
| C9 | A host should not mix containerized and non-containerized workloads. | S1 4.5.2 | "organizations should not mix containerized and non-containerized workloads on the same host instance." |
| C10 | A container image is an immutable snapshot of what the app needs in user space (language runtime, libraries, init scripts, OS tools). Developer, build system, and production run the same artifact, which solves the "works on my machine" problem. | S1 2.4 | "The image is an immutable snapshot of all userspace requirements of the app" / "This solves the "works on my machine" problem since the developer, build, and production all run the same immutable artifact." (the PDF text reads "the developer, build system, and production") |
| C11 | A container is an isolated process for each component of an app. Docker lists four traits: self-contained (no reliance on pre-installed dependencies on the host), isolated (minimal influence on the host and other containers), independent (deleting one does not affect others), portable. | S2 | "containers are isolated processes for each of your app's components." / "Self-contained. Each container has everything it needs to function with no reliance on any pre-installed dependencies on the host machine." / "Isolated. Since containers run in isolation, they have minimal influence on the host and other containers" / "Independent. Each container is independently managed. Deleting one container won't affect any others." / "Portable." |
| C12 | A VM is a whole OS with its own kernel, drivers, and programs. Starting a VM to isolate one app is a lot of overhead. A container is an isolated process with its files. Several containers share the kernel, so you can run more apps on less infrastructure. | S2 | "a VM is an entire operating system with its own kernel, hardware drivers, programs, and applications. Spinning up a VM only to isolate a single application is a lot of overhead." / "If you run multiple containers, they all share the same kernel, allowing you to run more applications on less infrastructure." |
| C13 | Containers and VMs are often used together. In a cloud, the provisioned machines are typically VMs. A VM with a container runtime can run many containerized apps, which raises resource use and can cut cost. | S2 | "in a cloud environment, the provisioned machines are typically VMs. However, instead of provisioning one machine to run one application, a VM with a container runtime can run multiple containerized applications, increasing resource utilization and reducing costs." |
| C14 | Kubernetes: a container is repeatable (dependencies included, same behavior wherever it runs) and decouples the app from the host infrastructure. | S3 | "Each container that you run is repeatable; the standardization from having dependencies included means that you get the same behavior wherever you run it." / "Containers decouple applications from the underlying host infrastructure." |
| C15 | A container image is a ready-to-run package: code, runtime, libraries, default settings. Containers are meant to be stateless and immutable: do not change a running container; build a new image and recreate the container. | S3 | "A container image is a ready-to-run software package containing everything needed to run an application" / "Containers are intended to be stateless and immutable: you should not change the code of a container that is already running." / "the correct process is to build a new image that includes the change, then recreate the container" |
| C16 | In Kubernetes each node runs the containers of its Pods. Containers in one Pod are co-located and co-scheduled on one node. A container runtime (containerd, CRI-O, or another CRI implementation) manages execution and lifecycle. The word "container" is overloaded, so check the definition. | S3 | "Containers in a Pod are co-located and co-scheduled to run on the same node." / "Kubernetes supports container runtimes such as containerd, CRI-O, and any other implementation of the Kubernetes CRI" / "The word container is an overloaded term. Whenever you use the word, check whether your audience uses the same definition." |
| C17 | You usually build an image and push it to a registry before a Pod refers to it. | S4 | "You typically create a container image of your application and push it to a registry before referring to it in a Pod." |
| C18 | Tags identify versions of an image series but can be moved to point to other images. Digests are hashes of the image content, and are fixed. With no tag Kubernetes assumes `latest`. | S4 | "Tags can be moved to point to different images, but digests are fixed." / "If you don't specify a tag, Kubernetes assumes you mean the tag latest." |
| C19 | Kubernetes advises avoiding `:latest` in production (harder to track the running version and to roll back) and using a meaningful tag or a digest. A tag that a registry changes may give a mix of Pods with old and new code; a digest gives the same code every start. | S4 | "You should avoid using the :latest tag when deploying containers in production as it is harder to track which version of the image is running and more difficult to roll back properly." / "if the image registry were to change the code that the tag on that image represents, you might end up with a mix of Pods running the old and new code." |
| C20 | Traditional VMs are typically run as stateful entities that are deployed, reconfigured, and upgraded throughout their life. Immutability is a basic operational difference between containers and hardware virtualization. | S1 Executive summary | "Immutability is a fundamental operational difference between containers and hardware virtualization. Traditional VMs are typically run as stateful entities that are deployed, reconfigured, and upgraded throughout their life." |
| C21 | NIST says "most container platforms do an effective job of isolating containers" (summary wording; C8 has the section 4.3.4 wording). | S1 Executive summary | "While most container platforms do an effective job of isolating containers from each other and from the host OS, it may be an unnecessary risk to run apps of different sensitivity levels together on the same host OS." |
