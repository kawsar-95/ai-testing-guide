## Claims

| # | Claim on the page | Source | Quote |
|---|---|---|---|
| C1 | Normalization is organizing data in a database: tables plus relationships, by rules that protect the data and make the database more flexible by removing redundancy and inconsistent dependency. | S1 | "Normalization is the process of organizing data in a database. It includes creating tables and establishing relationships between those tables according to rules designed both to protect the data and to make the database more flexible by eliminating redundancy and inconsistent dependency." |
| C2 | Redundant data wastes disk space and creates maintenance problems. Data in more than one place must be changed the same way in all places. | S1 | "Redundant data wastes disk space and creates maintenance problems. If data that exists in more than one place must be changed, the data must be changed in exactly the same way in all locations." |
| C3 | A customer address change is easier when the address is stored only in the Customers table. | S1 | "A customer address change is easier to implement if that data is stored only in the Customers table and nowhere else in the database." |
| C4 | Inconsistent dependency: data that depends on one thing sits in the table of another thing (an employee salary belongs in Employees, not Customers). It can make data hard to find because the path may be missing or broken. | S1 | "The employee's salary is related to, or dependent on, the employee and thus should be moved to the Employees table. Inconsistent dependencies can make data difficult to access because the path to find the data may be missing or broken." |
| C5 | Each rule is a normal form. Rule one met is first normal form. The first three rules met is third normal form. Third normal form is the highest level necessary for most applications. | S1 | "Each rule is called a 'normal form.' If the first rule is observed, the database is said to be in 'first normal form.' If the first three rules are observed, the database is considered to be in 'third normal form.' Although other levels of normalization are possible, third normal form is considered the highest level necessary for most applications." |
| C6 | 1NF: eliminate repeating groups, a separate table for each set of related data, identify each set with a primary key. Do not store similar data in several fields (Vendor Code 1 and 2). A third vendor would need program and table changes, so use a Vendors table linked by a key. | S1 | "Eliminate repeating groups in individual tables. Create a separate table for each set of related data. Identify each set of related data with a primary key." / "Don't use multiple fields in a single table to store similar data." / "Adding a field isn't the answer; it requires program and table modifications and doesn't smoothly accommodate a dynamic number of vendors. Instead, place all vendor information in a separate table called Vendors" |
| C7 | 2NF: separate tables for sets of values that apply to multiple records, related with a foreign key. Records should not depend on anything but the primary key (compound key if needed). A customer address needed by many tables is stored in one place. | S1 | "Create separate tables for sets of values that apply to multiple records. Relate these tables with a foreign key. Records shouldn't depend on anything other than a table's primary key (a compound key, if necessary)." / "Instead of storing the customer's address as a separate entry in each of these tables, store it in one place" |
| C8 | 3NF: eliminate fields that do not depend on the key. If a group of fields can apply to more than one record, consider a separate table. Example: a Universities table, because with university data inside Candidates you cannot list universities that have no candidate. | S1 | "Eliminate fields that don't depend on the key." / "anytime the contents of a group of fields may apply to more than a single record in the table, consider placing those fields in a separate table." / "If university information is stored in the Candidates table, there is no way to list universities with no current candidates." |
| C9 | Student example. Unnormalized: Class1, Class2, Class3 fields are a sign of design trouble. 1NF: one row per student and class (two dimensions). 2NF: Students table and Registration table. 3NF: advisor room depends on the advisor, so it moves to a Faculty table. | S1 | "Fields Class1, Class2, and Class3 in the above records are indications of design trouble." / "Tables should have only two dimensions." / "Adv-Room (the advisor's office number) is functionally dependent on the Advisor attribute. The solution is to move that attribute from the Students table to the Faculty table" |
| C10 | In general normalization requires more tables. Real scenarios do not always allow perfect compliance. If you break one of the first three rules, the application must anticipate the problems (redundant data, inconsistent dependencies). | S1 | "In general, normalization requires additional tables and some customers find this cumbersome. If you decide to violate one of the first three rules of normalization, make sure that your application anticipates any problems that could occur, such as redundant data and inconsistent dependencies." |
| C11 | Third normal form is not always practical: removing all dependencies between fields needs separate tables for cities, ZIP codes, and so on; many small tables may degrade performance or exceed open file and memory capacities. | S1 | "In theory, normalization is worth pursuing. However, many small tables may degrade performance or exceed open file and memory capacities." |
| C12 | It may be more feasible to apply 3NF only to data that changes often. If dependent fields remain, design the app so the user must verify all related fields when one changes. | S1 | "It may be more feasible to apply third normal form only to data that changes frequently. If some dependent fields remain, design your application to require the user to verify all related fields when any one is changed." |
| C13 | Fourth normal form (also called BCNF) and fifth normal form exist but are rarely considered in practical design. | S1 | "Fourth normal form, also called Boyce-Codd Normal Form (BCNF), and fifth normal form do exist, but are rarely considered in practical design." |
| C14 | A primary key is a column or group of columns that can identify rows uniquely. Its values must be unique and not null. | S2 | "A primary key constraint indicates that a column, or group of columns, can be used as a unique identifier for rows in the table. This requires that the values be both unique and not null." |
| C15 | A foreign key constraint says the values in a column (or group) must match values in a row of another table. This keeps referential integrity between the two tables. | S2 | "A foreign key constraint specifies that the values in a column (or a group of columns) must match the values appearing in some row of another table. We say this maintains the referential integrity between two related tables." |
| C16 | With a foreign key from orders to products, an order cannot have a non-NULL product number that is absent from products. The orders table is the referencing table, products the referenced table. | S2 | "Now it is impossible to create orders with non-NULL product_no entries that do not appear in the products table." / "the orders table is the referencing table and the products table is the referenced table" |
| C17 | A table with more than one foreign key implements many-to-many relationships (an order_items table between products and orders). | S2 | "A table can have more than one foreign key constraint. This is used to implement many-to-many relationships between tables." |
| C18 | When a referenced row is deleted, the default action (NO ACTION) lets the delete go ahead but the constraint must still hold, so it usually gives an error. RESTRICT prevents deleting a referenced row. CASCADE deletes the referencing rows too. SET NULL / SET DEFAULT change the referencing columns. | S2 | "ON DELETE NO ACTION; ... this operation will usually result in an error." / "RESTRICT ... prevents deletion of a referenced row." / "CASCADE specifies that when a referenced row is deleted, row(s) referencing it should be automatically deleted as well." / "SET NULL and SET DEFAULT. These cause the referencing column(s) in the referencing row(s) to be set to nulls or their default values" |
| C19 | CASCADE can suit a component that cannot exist alone (order items in an order); RESTRICT or NO ACTION suit independent objects (products and orders). | S2 | "When the referencing table represents something that is a component of what is represented by the referenced table and cannot exist independently, then CASCADE could be appropriate. If the two tables represent independent objects, then RESTRICT or NO ACTION is more appropriate" |
| C20 | ON UPDATE exists too, with the same actions; CASCADE copies the new value of the referenced column into the referencing rows. | S2 | "there is also ON UPDATE which is invoked when a referenced column is changed (updated)." / "CASCADE means that the updated values of the referenced column(s) should be copied into the referencing row(s)." |
| C21 | A rule of relational theory: every table must have a primary key. PostgreSQL does not enforce it but it is usually best to follow it. | S2 | "Relational database theory dictates that every table must have a primary key. This rule is not enforced by PostgreSQL, but it is usually best to follow it." |
