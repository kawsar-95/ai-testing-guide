## Claims

| # | Claim on the page | Source | Quote |
|---|---|---|---|
| 1 | Computer clusters can give highly available services. The redundancy of many machines guards against failures. | S1 | "Computer clusters can be used to provide highly available services or resources. The redundancy of multiple machines is used to guard against failures of many types." |
| 2 | Pacemaker is HA cluster software that runs on a set of nodes to keep services running and reduce downtime. | S1 | "Pacemaker is a high-availability cluster resource manager – software that runs on a set of hosts (a cluster of nodes) in order to preserve integrity and minimize downtime of desired services (resources)." |
| 3 | Pacemaker supports active/active and active/passive designs. | S1 | "Pacemaker supports practically any node redundancy configuration including Active/Active, Active/Passive, N+1, N+M, N-to-1, and N-to-N." |
| 4 | Active/passive: one node gives the service; if it fails, the other takes over. | S1 | "One of the nodes provides the desired services, and if it fails, the other node takes over." |
| 5 | Active/active: the data must be available on both machines at the same time. Pacemaker can run many copies of a service to spread the work. | S4, S1 | S4: "The primary requirement for an active/active cluster is that the data required for your services is available, simultaneously, on both machines." S1: "Pacemaker can even run multiple copies of services to spread out the workload." |
| 6 | Failover example: stop the cluster software on the node that runs a resource, and the resource starts on the other node by itself. | S3 | "Notice that pcmk-2 is OFFLINE for cluster purposes ... Also notice that ClusterIP is now running on pcmk-1 – failover happened automatically, and no errors are reported." |
| 7 | A Kubernetes cluster has a control plane and worker nodes. In production the control plane usually runs on many computers, for fault tolerance and high availability. | S6 | "A Kubernetes cluster consists of a control plane plus a set of worker machines, called nodes, that run containerized applications." "In production environments, the control plane usually runs across multiple computers and a cluster usually runs multiple nodes, providing fault-tolerance and high availability." |
| 8 | Kubernetes nodes send heartbeats, which help the cluster know if a node is available and act on failures. There are two forms: updates to the Node `.status` and Lease objects. | S7 | "Heartbeats, sent by Kubernetes nodes, help your cluster determine the availability of each node, and to take action when failures are detected. For nodes there are two forms of heartbeats: Updates to the .status of a Node. Lease objects within the kube-node-lease namespace." |
| 9 | If a node is unreachable, the node controller sets its Ready condition to Unknown; by default it waits 5 minutes before the first Pod eviction request. | S7 | "In the case that a node becomes unreachable, updating the Ready condition in the Node's .status field. In this case the node controller sets the Ready condition to Unknown." "By default, the node controller waits 5 minutes between marking the node as Unknown and submitting the first eviction request." |
| 10 | Quorum: when the cluster splits into groups that cannot talk, quorum stops resources from starting on more nodes than wanted, which would risk data corruption. A group has quorum when more than half of all known nodes are online in it. | S3 | "If a cluster splits into two (or more) groups of nodes that can no longer communicate with each other (a.k.a. partitions), quorum is used to prevent resources from starting on more nodes than desired, which would risk data corruption. A cluster has quorum when more than half of all known nodes are online in the same partition" |
| 11 | Example: a 5-node cluster splits 3 and 2, the 3 group has quorum. A 6-node cluster splits 3 and 3, neither has quorum, and by default Pacemaker stops all resources. | S3 | "if a 5-node cluster split into 3- and 2-node paritions, the 3-node partition would have quorum and could continue serving resources. If a 6-node cluster split into two 3-node partitions, neither partition would have quorum; Pacemaker's default behavior in such cases is to stop all resources, in order to prevent data corruption." |
| 12 | Two-node clusters are a special case: Corosync can require only one node for quorum (`two_node: 1`); with fencing configured there is no danger. | S3 | "Corosync has the ability to require only one node for quorum in a two-node cluster." "As long as fencing is configured, there is no danger" |
| 13 | Split brain: nodes cannot talk to each other but can still run resources, so many copies of a resource could start. | S5 | "Fencing protects against the “split brain” failure scenario, where cluster nodes have lost the ability to reliably communicate with each other but are still able to run resources. If the cluster just assumed that uncommunicative nodes were down, then multiple instances of a resource could be started on different nodes." |
| 14 | An IP address on two hosts sends packets at random to one or the other. For a database or cluster file system the effect can be data corruption or divergence. | S5 | "an IP address brought up on two hosts on a network will cause packets to randomly be sent to one or the other host, rendering the IP useless. For a database or clustered file system, the effect could be much more severe, causing data corruption or divergence." |
| 15 | Fencing (STONITH) makes sure a node is truly offline before another node uses the data. A node that does not answer may still access the data. | S2 | "Just because a node is unresponsive doesn't mean it has stopped accessing your data. The only way to be 100% sure that your data is safe, is to use fencing to ensure that the node is truly offline before allowing the data to be accessed from another node." |
| 16 | A common form of fencing is cutting a host's power. STONITH means "Shoot The Other Node In The Head". | S2 | "Fencing is also known as STONITH, an acronym for “Shoot The Other Node In The Head”, since the most popular form of fencing is cutting a host's power." |
| 17 | Fencing is on by default. Turning it off makes the cluster pretend failed nodes are off, and a test cluster without it cannot test real failure scenarios. | S2 | "fencing is enabled by default" "It tells the cluster to simply pretend that failed nodes are safely powered off." "Even disabling it for a test cluster means you won't be able to test real failure scenarios." |
| 18 | A stacked HA Kubernetes control plane needs at least three control plane nodes. If one node goes down, an etcd member and a control plane instance are both lost. | S8 | "If one node goes down, both an etcd member and a control plane instance are lost, and redundancy is compromised." "You should therefore run a minimum of three stacked control plane nodes for an HA cluster." |
