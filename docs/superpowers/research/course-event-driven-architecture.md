## Claims

| # | Claim on the page | Source | Quote |
|---|---|---|---|
| C1 | An event-driven architecture has event producers, event consumers, and event channels (often event brokers or ingestion services) that move events from producers to consumers. | S1 intro | "event producers that generate a stream of events, event consumers that listen for these events, and event channels (often implemented as event brokers or ingestion services) that transfer events from producers to consumers." |
| C2 | AWS names the three parts producers, event routers, consumers. A producer publishes an event to the router, which filters and pushes events to consumers. | S2 overview | "three key components: event producers, event routers, and event consumers. A producer publishes an event to the router, which filters and pushes the events to consumers." |
| C3 | An event is a change in state or an update, for example an item put in a shopping cart. | S2 overview | "An event is a change in state, or an update, like an item being placed in a shopping cart" |
| C4 | An event can carry the state (item, price, address) or be an identifier (a notice that an order shipped). | S2 overview | "Events can either carry the state (the item purchased, its price, and a delivery address) or events can be identifiers (a notification that an order was shipped)." |
| C5 | Events are delivered in near real time, so consumers can react at once. | S1 | "Events are delivered in near real time, so consumers can respond immediately to events as they occur." |
| C6 | A producer does not know which consumers listen. Consumers are decoupled from each other. | S1 | "a producer doesn't know which consumers are listening. Consumers are also decoupled from each other" |
| C7 | Services know only the router, not each other; if one service fails the rest keep running; the router acts as an elastic buffer for surges. | S2 benefits | "they are only aware of the event router, not each other." / "if one service has a failure, the rest will keep running. The event router acts as an elastic buffer that will accommodate surges in workloads." |
| C8 | Producers and consumers can be scaled, updated, and deployed independently. | S2 overview | "which allows them to be scaled, updated, and deployed independently." |
| C9 | Competing Consumers differs: consumers pull from a queue and each message is processed one time (if no errors). In pub/sub every consumer sees all events. | S1 | "in a publish-subscribe model, every consumer sees all of the events." / "consumers pull messages from a queue. Each message is processed only one time, assuming that there are no errors." |
| C10 | Two models: publish-subscribe and event streaming. | S1 | "An event-driven architecture can use a publish-subscribe model or an event stream model." |
| C11 | Pub/sub: the infrastructure tracks subscriptions and sends a published event to each subscriber. The event is not kept in a durable log, so new subscribers do not see past events. | S1 | "The publish-subscribe messaging infrastructure tracks subscriptions. When an event is published, it sends the event to each subscriber. After the event is received, it isn't stored in a durable log, so new subscribers don't see past events." |
| C12 | Streaming: events are written to a log, strictly ordered within a partition, durable. Clients do not subscribe; they read from any part of the stream and move their own position, so they can join at any time and replay. | S1 | "Events are written to a log. Events are strictly ordered within a partition and are durable. Clients don't subscribe to the stream. Instead, a client can read from any part of the stream. The client is responsible for advancing their position in the stream, which means that a client can join at any time and can replay events." |
| C13 | Replay supports recovery, late consumers, and reprocessing after a bug fix. | S1 | "This replayability supports recovery scenarios, late-arriving consumers, and reprocessing after a bug fix." |
| C14 | AWS: two main router types, event buses and event topics (EventBridge, SNS). | S2 where to start | "There are two main types of routers used in event-driven architectures: event buses and event topics." |
| C15 | AWS router benefits: no custom polling/filter/route code; router filters and pushes events; it is a central place to audit and set policies on who may publish and subscribe; events can be encrypted in transit and at rest. | S2 benefits | "You no longer need to write custom code to poll, filter, and route events" / "restrict who can publish and subscribe to a router" / "encrypt your events both in transit and at rest." |
| C16 | Push-based: no paying for continuous polling. | S2 benefits | "Event-driven architectures are push-based ... you’re not paying for continuous polling to check for an event." |
| C17 | Consumer variations: simple event processing (an event triggers an action), basic event correlation (correlate by an identifier, keep earlier info), complex event processing (patterns over a series of events, e.g. moving average over a window), event stream processing (a streaming platform feeds stream processors). | S1 | "Simple event processing: An event immediately triggers an action in the consumer." / "correlates them by an identifier, and persists information from earlier events" / "analyze a series of events and identify patterns" / "Use a data streaming platform ... as a pipeline to ingest events and feed them to stream processors." |
| C18 | Two payload styles: all attributes in the payload, or only keys. All-attributes: consumers need no extra query, but bigger payloads cost bandwidth and can cause consistency problems with several systems of record. Keys-only: one system of record, better consistency, but more queries and maybe worse performance. | S1 | "Larger payloads increase transport cost and bandwidth consumption, and can lead to data consistency problems because of multiple systems of record" / "This method provides better data consistency because it has a single system of record. However, it can have worse performance" |
| C19 | Multiple consumer instances avoid a single point of failure and handle volume; with several instances and threads, in-order processing or exactly-once semantics become a challenge. | S1 | "it's typical to have multiple instances of a consumer." / "This setup can create challenges if events must be processed in order or require exactly-once semantics." |
| C20 | Challenge, guaranteed delivery: in some systems, especially IoT, it is crucial to guarantee delivery. | S1 challenges | "it's crucial to guarantee that events are delivered." |
| C21 | Challenge, order and one-time: multiple instances can make a problem if events must be in order within a consumer type or if idempotent processing logic is missing. | S1 challenges | "Running multiple instances can create a challenge if the events must be processed in order within a consumer type or if idempotent message processing logic isn't implemented." |
| C22 | Challenge, data loss: if a component crashes before it hands over the event, the event is dropped. To reduce this: persist in-transit events and remove them only when the next component acknowledges receipt. | S1 | "the event is dropped and never reaches the final destination." / "persist in-transit events and remove or dequeue the events only when the next component acknowledges the receipt of the event." |
| C23 | Challenge, eventual consistency: data is not at once consistent after an event; consumers work at their own pace; for a time parts of the system see different state. Consumers must tolerate stale data. | S1 | "data across services isn't immediately consistent after an event is published." / "different parts of the system have a different view of the current state." / "design consumers and downstream reads to tolerate stale or partially updated data" |
| C24 | Challenge, error handling: a dedicated error-handler processor receives the problem event; if it fixes it, it resubmits to the original channel; if not, it may forward to a dead-letter queue (DLQ) for an administrator. Resubmitted events are processed out of sequence. | S1 | "sends the problematic event to the error-handler processor" / "forward the event to a dead-letter queue (DLQ) for administrator inspection" / "resubmitted events are processed out of sequence." |
| C25 | Challenge, observability and testing: no shared call context; include a correlation ID in every event; testing end to end across async parts needs more deliberate strategies. | S1 | "there's no shared call context." / "include a correlation ID in every event" / "Verifying end-to-end behavior across asynchronous, decoupled components requires more deliberate test strategies" |
| C26 | Challenge, schema evolution: producers and consumers deploy independently; a changed event structure can break consumers that do not know it; define a versioning strategy early. | S1 | "consumers that don't yet understand the new schema can break. Define a schema versioning strategy early" |
| C27 | Challenge, number of events: too many fine-grained events can overwhelm the system; over-consolidated events cause needless processing. | S1 | "Generating an excessive number of fine-grained events can saturate and overwhelm the system." / "overly consolidating events can also create problems" |
| C28 | Request-response is possible with a request queue and a response queue; the producer waits for the reply; a session ID is usually used to match them. | S1 | "implemented with a request queue and a response queue." / "usually uses a session ID for tracking" |
| C29 | Broker topology: components broadcast events to the whole system; others act or ignore; no central coordination; useful when the flow is simple. No component owns the state of a multistep transaction; distributed transactions are risky, no built-in restart or replay; can cause data inconsistency. | S1 | "Components broadcast events to the entire system." / "No component owns or is aware of the state of any multistep business transaction" / "no built-in mechanism for restarting or replaying them" |
| C30 | Mediator topology: a mediator manages the flow, keeps state, handles errors and restarts, and dispatches commands to designated channels (often queues). More control, but more coupling, and the mediator can become a bottleneck or reliability concern. | S1 | "There's an event mediator that manages and controls the flow of events. The event mediator maintains the state and manages error handling and restart capabilities." / "the event mediator can become a bottleneck or a reliability concern." |
| C31 | When to use (Azure): several subsystems process the same events; real-time with little lag; complex event processing; high volume and velocity such as IoT; decoupling for independent scaling and reliability. | S1 | "Multiple subsystems must process the same events." / "Real-time processing with minimum time lag is required." |
| C32 | May not suit: simple request-response where synchronous calls are enough; business transactions that need strong consistency; a team with no experience of distributed asynchronous systems. | S1 | "simple request-response workflows where synchronous calls meet your latency and throughput requirements" / "Business transactions require strong consistency across services." / "Your team doesn't have experience operating distributed asynchronous systems." |
| C33 | AWS considerations: durable, reliable event source that guarantees delivery if every event must be processed; the app must handle the async nature; flow tracking by monitoring, not by static code analysis; to rebuild state, the event source should be deduplicated and ordered. | S2 | "Your event source should be reliable and guarantee delivery if you need to process every single event." / "dynamic tracking via monitoring services, but not static tracking via code analysis." / "your event source should be deduplicated and ordered." |
| C34 | AWS use cases: cross-account/region replication, resource state monitoring and alerting, fanout and parallel processing, integration of different systems. | S2 | "Cross-account, cross-region data replication" / "Resource state monitoring and alerting" / "Fanout and parallel processing" / "Integration of heterogeneous systems" |
| C35 | Events are often visible to many components, so be careful what information an event holds. | S1 other | "events are often visible to multiple components in a workload ... be mindful of what information you include in events to prevent unintended information exposure." |
